# Сохранение InternalInfo в снимке конфигурации

## Контекст

Полный round-trip XML → YAML → XML не сохраняет идентификаторы внутри
`InternalInfo`. При импорте они не попадают в YAML, что соответствует
пользовательскому YAML-договору, но также не записываются в снимок
конфигурации. При последующем экспорте `getUUID()` обращается к адресу
владельца и повторно использует его UUID для `TypeId` и `ValueId`.

Исправление должно сохранять технические идентификаторы вне YAML и
восстанавливать их через существующий снимок конфигурации.

## Цели

- Сохранить при XML → YAML все технические UUID из `InternalInfo`.
- Восстановить те же UUID при YAML → XML.
- Создавать устойчивые UUID для новых объектов и новых элементов
  `InternalInfo`.
- Оставить знания о структуре `InternalInfo` рядом с реализацией этого типа.
- Устранить во всём `cf/all` изменения UUID внутри `InternalInfo`.

## Не входит в задачу

- Порядок `InternalInfo`, `Properties` и `ChildObjects` в XML.
- Сохранение явно пустых XML-значений.
- Изменение пользовательского YAML-договора.
- Совместимость со снимками конфигурации, созданными прежней
  нереализованной версией механизма.

## Архитектура

Снимок конфигурации остаётся единственным техническим представлением данных,
которые нужны для точного восстановления XML, но не должны попадать в YAML.
Новых скрытых YAML-полей и исходных XML-фрагментов не добавляется.

Обработчик типа `InternalInfo` отвечает за преобразование между его XML-
структурой и записями идентификаторов снимка. Общая оркестрация предоставляет
контекст сборщика или чтения снимка, но не знает о `ThisNode`,
`GeneratedType` и `ContainedObject`.

## Логические адреса

Каждый UUID получает отдельный устойчивый логический адрес относительно
владельца метаданных:

```text
<владелец>.InternalInfo.ThisNode
<владелец>.InternalInfo.GeneratedType.<имя>.TypeId
<владелец>.InternalInfo.GeneratedType.<имя>.ValueId
<владелец>.InternalInfo.ContainedObject.<ClassId>.ObjectId
```

Сегменты формируются существующими функциями логической адресации, чтобы
экранирование точек и квадратных скобок оставалось единообразным.

Имя `GeneratedType` берётся из декларативного списка `items` правила
`InternalInfo`, а `ClassId` — из XML или декларативного списка
`containedObjectClassIds`. Позиция элемента в массиве не является частью
адреса.

## Поток XML → YAML

1. Оркестрация вызывает импорт типа `InternalInfo` с контекстом сборщика
   частичного снимка.
2. Обработчик разбирает `xr:ThisNode`, каждый `xr:GeneratedType` и каждый
   `xr:ContainedObject`.
3. Найденные UUID записываются в сборщик по семантическим логическим адресам.
4. Пользовательский YAML не получает технические значения `InternalInfo`.
5. Частичный снимок объединяется с частичными снимками остальных заданий
   существующим механизмом проверки конфликтов.

## Поток YAML → XML

1. Обработчик `InternalInfo` строит тот же логический адрес для каждого
   ожидаемого значения.
2. Если снимок содержит UUID по этому адресу, обработчик использует его без
   изменений.
3. Если объект или элемент новый, обработчик создаёт устойчивый UUID через
   среду экспорта снимка.
4. Созданный или восстановленный UUID записывается в частичный снимок
   результата синхронизации.
5. Повторная синхронизация неизменного проекта формирует те же UUID.

## Ошибки и конфликты

- Разные UUID по одному логическому адресу считаются конфликтом снимка и
  обрабатываются существующей проверкой конфликтов.
- Некорректная XML-структура `InternalInfo` продолжает диагностироваться
  импортом; механизм снимка не исправляет и не скрывает такие данные.
- Отсутствие записи допустимо только для нового объекта или нового элемента:
  в этом случае создаётся новый устойчивый UUID.

## Тестирование

- Модульный тест импорта проверяет записи снимка для `ThisNode`,
  `GeneratedType.TypeId`, `GeneratedType.ValueId` и
  `ContainedObject.ObjectId`.
- Модульный тест экспорта проверяет восстановление исходных UUID из снимка.
- Тест нового объекта проверяет создание разных устойчивых UUID для всех
  логических адресов и их повторное использование.
- Интеграционный тест полного sync проверяет, что `InternalInfo` проходит
  XML → YAML → XML без изменения UUID.
- Полный `pnpm test` остаётся обязательной итоговой проверкой.
- Round-trip на `cf/all` подтверждает отсутствие diff, вызванных UUID внутри
  `InternalInfo`; остальные категории расхождений не входят в критерий этой
  задачи.

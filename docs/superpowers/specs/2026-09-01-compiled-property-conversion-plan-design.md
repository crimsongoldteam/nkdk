# Единый скомпилированный план преобразования свойств

## Статус

Согласованный проект оптимизации обоих направлений преобразования свойств:
XML → YAML и YAML → XML.

## Цель

Сократить время преобразования метаданных без изменения XML, YAML,
configuration index, аннотаций и diagnostics.

Оптимизация состоит из двух независимо измеряемых слоёв:

1. единый скомпилированный план свойства устраняет повторную подготовку правил
   в обоих направлениях;
2. прямые атомарные преобразователи объединяют наиболее частые пары
   преобразований там, где это даёт дополнительный измеримый выигрыш.

Разработка и измерения выполняются на
`/Users/nikita/git/round-trip-compact/cf/doc`. ERP не используется для частых
прогонов этой работы.

## Исходное состояние

`convertPropertiesFromYAMLToXML` и `importPropertiesFromXMLToYAML` получают
декларативный `MetadataItemRule`, но не получают полностью подготовленную модель
его выполнения.

В YAML → XML уже существует лёгкий `YAMLToXMLPlan` с ключом, правилом и
XML-путём свойства. При каждом преобразуемом объекте код дополнительно:

- фильтрует порядок свойств через `getOrderedKeysToXML`;
- строит новый `Map` из ключа свойства в элемент плана;
- многократно ищет обработчики одного типа через `getTypeRule`;
- повторно проверяет наличие одного свойства через `source.has` в разных
  ветвях общей оркестрации.

В XML → YAML уже существует кэшированное дерево `XMLImportPlan`, которое
сопоставляет XML-узлы со свойствами. Однако после нахождения свойства общая
функция повторно разрешает через реестр обработчики вложенности, индекса,
импорта, экспорта, финализации и XML-поведения. Один и тот же набор ответов
получается заново для каждого объекта с тем же правилом.

Профиль YAML → XML на `cf/doc` показал 5 995 687 посещений свойств. Наиболее
частые типы в сумме времени worker:

| Тип | Посещений | Исключительное время |
|---|---:|---:|
| `SystemEnumeration` | 1 443 464 | 3,96 с |
| `boolean` | 1 468 007 | 3,89 с |
| `string` | 430 716 | 1,79 с |
| `number` | 511 149 | 1,22 с |

Это время включает общую оркестрацию свойства, а не только тело предметного
обработчика. Поэтому первая оптимизация должна быть общей, а не набором частных
ветвей по именам типов в runtime.

## Критерии результата

- один план обслуживает XML → YAML и YAML → XML;
- план создаётся не чаще одного раза на `MetadataItemRule` и версию реестра в
  одном `PropertyRuleExecutor`;
- после подготовки плана обработка объекта не строит новый `Map` правил и не
  ищет заново уже разрешённые обработчики;
- обе стороны сохраняют прежние значения, порядок, defaults, configuration
  index, audit, аннотации, отложенную финализацию и diagnostics;
- контрольный экспорт XML-import строит известные свойства только из YAML,
  правил и индексов; исходный XML используется для сравнения, но не как
  источник отсутствующих известных значений;
- итоговый импорт и контрольный экспорт `cf/doc` не получают новых ошибок,
  предупреждений или round-trip расхождений;
- каждый слой имеет отдельный профиль до и после;
- Peak RSS не увеличивается больше измерительного шума.

Минимальный обязательный процент общего ускорения заранее не задаётся. Слой
сохраняется, только если повторные одинаковые прогоны показывают выигрыш выше
шума и не показывают ухудшение другого направления или памяти.

## Выбранная архитектура

### Владелец плана

`PropertyRuleExecutor` владеет кэшем `CompiledPropertyPlan`. Ключом служит
объект `MetadataItemRule`; запись дополнительно содержит номер версии
`PropertyRuleRegistrySet`.

Такой владелец гарантирует, что:

- план использует обработчики именно текущего собранного runtime;
- конкретные реализации метаданных остаются в `@nkdk/rules`;
- worker не делятся функциями или изменяемым состоянием;
- кэш не удерживает XML, YAML, configuration index и данные заданий.

Глобальный кэш только по `MetadataItemRule` запрещён: два runtime могут собрать
разные наборы обработчиков для одного объекта правила.

### Один план для двух направлений

`CompiledPropertyPlan` является одним объектом и содержит:

- неизменяемую запись каждого свойства;
- отображение ключа свойства в эту запись;
- готовый порядок обхода YAML → XML;
- корневое дерево сопоставления XML → YAML;
- варианты XML-обхода для разных наборов `tag` внутри того же плана;
- разрешённые обработчики и статические признаки обоих направлений.

Вариант по `tag` является внутренним представлением одного плана, а не вторым
скомпилированным планом правила.

Ориентировочный внутренний договор:

```ts
interface CompiledPropertyPlan {
  readonly rule: MetadataItemRule
  readonly registryRevision: number
  readonly properties: readonly CompiledProperty[]
  readonly propertiesByKey: ReadonlyMap<string, CompiledProperty>
  readonly yamlToXMLOrder: readonly CompiledProperty[]
  xmlImportView(tags: readonly string[] | undefined, includeAllTags: boolean): CompiledXMLImportView
}

interface CompiledProperty {
  readonly propertyKey: string
  readonly rule: PropertyRule
  readonly yamlKey: string | undefined
  readonly xmlPath: readonly string[]
  readonly operations: CompiledPropertyOperations
  readonly flags: CompiledPropertyFlags
}
```

Точные имена могут быть уточнены при реализации, но владелец, один объект
плана и граница статических сведений остаются обязательными.

### Версия и инвалидирование

`PropertyRuleRegistrySet.revision()` уже изменяется после `registerTypeRule`.
При запросе плана executor сравнивает сохранённую версию с текущей:

- одинаковая версия возвращает тот же план;
- новая версия полностью пересобирает план этого `MetadataItemRule`;
- частично обновлённый план никогда не публикуется.

Обычная рабочая композиция собирает правила до работы worker, поэтому
инвалидирование почти не участвует в горячем пути. Оно сохраняет корректность
тестовых и расширяемых runtime.

## Статические и динамические решения

В план переносятся сведения, зависящие только от `MetadataItemRule`,
`PropertyRule` и версии реестра:

- канонические XML/YAML-имена, aliases и XML-путь;
- порядок и допустимость свойства для направления;
- служебные признаки `runtimeOnly`, `syncExternalOnly`, `filePath` и постоянные
  варианты `toXML`/`toYAML`;
- наличие статических defaults, implicit values и других собственных полей
  правила;
- ссылки на все операции типа, нужные обоим направлениям;
- описание вложенности, повторяемости, финализации и индексного значения;
- предварительно построенные XML-маршруты.

Для каждого объекта продолжают вычисляться только зависящие от данных решения:

- присутствует ли значение в текущем YAML или XML;
- какое значение находится в configuration index;
- результат функции `toXML`, если она динамическая;
- текущий вариант XML-default и контекст логического адреса;
- audit, аннотации, metadata targets, diagnostics и результаты предметных
  обработчиков.

Наличие свойства в YAML вычисляется один раз на итерацию и переиспользуется
всеми общими ветвями. Передаваемый предметному обработчику `YAMLPropertySource`
остаётся доступен и сохраняет прежний договор.

### Стратегия отсутствующего YAML-свойства

План один раз назначает каждому свойству действие на случай, когда YAML-ключ
отсутствует. Это общее решение для всех типов, а не частная оптимизация
`boolean`:

- `skip` — свойство доказанно не может создать XML без YAML-ключа;
- `default` — план содержит подготовленное действие для канонического
  XML-default;
- `evaluate` — результат зависит от контекста, соседних значений, вложенности
  или специального обработчика и вычисляется общей оркестрацией.

`skip` разрешён только при отсутствии всех договоров, способных породить XML:
XML-default любого поддерживаемого варианта, `implicitValueXML`,
`evaluateWhenYAMLMissing`, `exportNilValue`, динамического `toXML`, резервирования
вложенного элемента и других зарегистрированных операций обработки
отсутствующего значения. Неизвестный или неоднозначный случай всегда получает
`evaluate`; оптимизация не имеет права угадывать.

Наличие ключа и его значение различаются. YAML-ключ со значением `undefined`
считается присутствующим и не использует стратегию отсутствия: это необходимо,
в частности, для управляемого XML-default расширения конфигурации.

Во время обработки объекта оркестратор сначала один раз вызывает
`source.has(propertyKey)`. Присутствующее значение идёт в преобразователь.
Для отсутствующего значения выполняется подготовленное действие: немедленный
`continue`, запись default либо вычисление. Поэтому простой отсутствующий
случай не запускает преобразователь и последующие общие проверки.

## YAML → XML

`convertPropertiesFromYAMLToXML` получает готовый план от executor и проходит
непосредственно по `yamlToXMLOrder`.

Из горячего пути удаляются:

- вызов `getOrderedKeysToXML` для каждого объекта;
- создание `planByKey` для каждого объекта;
- повторные `getTypeRule` для одного свойства;
- повторное разрешение статических признаков и обработчиков.

Общая функция по-прежнему выполняет выбор outputs, defaults, sparse YAML,
configuration-index context, metadata targets, вложенные объекты,
запись XML и отложенную финализацию. Перенос этих обязанностей в предметный тип
не допускается.

## XML → YAML

`importPropertiesFromXMLToYAML` получает XML-представление из того же плана.
Существующий структурный обход и правила выбора canonical/alias узлов
сохраняются, но `XMLImportPlanEntry` ссылается на общий `CompiledProperty`.

После нахождения XML-узла код использует уже сохранённые операции вложенности,
индекса, прямого или обычного импорта, экспорта YAML, финализации и
XML-поведения. Обратные вызовы реестра из функций повторяемости и владения
вложенным XML также заменяются статическими сведениями записи свойства.

Audit, journal rollback, configuration index, facts-only режим, metadata
targets, defaults, зависимые свойства и сортировка YAML остаются общей
динамической обработкой.

## Прямые атомарные преобразователи

Этот слой измеряется после внедрения единого плана. Он не переиспользует
существующий `importFromXMLToYAML`: тот договор предназначен для полного
прямого импорта сложного свойства и обходит часть обычного атомарного пути.

Прямой атомарный преобразователь является подготовленной функцией конкретного
свойства. Он заменяет пару простых предметных преобразований, но возвращает и
смысловое, и внешнее значение:

```text
XML "true"          → { metadata: true,      yaml: "Истина" }
YAML "Истина"      → { metadata: true,      xml: true }

XML "Switcher"     → { metadata: "Switch", yaml: "Выключатель" }
YAML "Выключатель" → { metadata: "Switch", xml: "Switcher" }
```

Смысловое значение необходимо общей логике defaults, configuration index и
metadata targets. Прямой путь не имеет права самостоятельно решать эти задачи.

Подготовку прямого преобразователя регистрирует конкретный тип в
`@nkdk/rules`; `@nkdk/runtime` не содержит условий по именам
`SystemEnumeration`, `boolean`, `string` или `number`. Во время компиляции
плана фабрика связывает функцию с конкретным `PropertyRule`. Для
`SystemEnumeration` это позволяет один раз получить таблицы `FromYAML` и
`ToYAML`, а также XML aliases конкретного `typeSE`.

Кандидаты первой реализации:

- `SystemEnumeration` в обоих направлениях;
- `boolean` в обоих направлениях;
- `string` в направлениях, где прямой путь действительно заменяет обычное
  преобразование;
- `number` в направлениях, где прямой путь действительно заменяет обычное
  преобразование, включая `typedXML`.

Прямой преобразователь вызывается после общей стратегии присутствия/default и
не дублирует metadata targets, scalar tags, configuration index или вложенность.
Для типа, переведённого на прямое преобразование, прежняя пара предметных
функций больше не регистрируется и не служит резервным путём: новый обработчик
обязан полностью покрывать поддержанный договор типа в обоих направлениях.
Неоднозначность отсутствующего свойства решает общая стратегия
`skip/default/evaluate`, а не возврат к старой функции.

Каждый кандидат измеряется отдельно поверх уже внедрённого единого плана. Если
он не ускоряет соответствующее направление выше шума, его реализация удаляется,
а готовый план продолжает использовать кэшированные обычные обработчики.

## Ошибки

Ошибка компиляции плана содержит `itemType`, ключ и тип свойства, а также
операцию, которую не удалось подготовить. Она возникает до частичного
преобразования текущего объекта.

Ошибка предметного обработчика проходит через существующие границы:

- YAML → XML сохраняет `YAMLImportError` и путь свойства;
- XML → YAML сохраняет `DirectImportConversionError`, audit attempt и rollback;
- прямой атомарный путь формирует ту же ошибку и тот же путь, что обычный.

План не превращает ошибки в `!xml` и не вводит новые классы XML-аномалий.

## Производительность и память

Измеряются три состояния одной и той же рабочей сборкой и на одном входном
каталоге:

1. исходное состояние текущего коммита;
2. единый план без прямых преобразователей;
3. единый план с каждым прямым преобразователем.

Перед серией выполняется один прогревочный прогон. Для сравнения используются
не менее трёх одинаковых измерительных прогонов; сравниваются медиана и разброс.

Профиль обязан разделять:

- полное время XML → YAML;
- полное время YAML → XML;
- подготовку или получение плана;
- общую обработку свойств;
- число обычных и прямых атомарных преобразований по типу;
- исключительное время частых типов;
- Peak RSS и Peak Heap.

План хранит `O(число правил × число свойств)` небольших записей на worker.
Запрещено сохранять в нём значения объектов, XML/YAML-деревья, reference XML,
контексты заданий и collectors.

## Проверки

### Модульные runtime

- один executor и одно правило возвращают один объект плана;
- один план содержит маршруты обоих направлений;
- разные executor не разделяют план;
- изменение revision пересобирает план;
- XML tag views остаются частями одного плана;
- порядок YAML → XML совпадает с `getOrderedKeysToXML`;
- XML traversal совпадает с действующим `XMLImportPlan` для canonical, aliases,
  xmlParents, повторов и неоднозначных узлов;
- наличие YAML вычисляется один раз на свойство без изменения результата;
- ошибки содержат вид объекта, свойство и операцию.

### Дифференциальные тесты правил

Для `SystemEnumeration`, `boolean`, `string` и `number` результат нового пути
проверяется на:

- обычном значении;
- отсутствующем YAML-ключе без XML-default (`skip`);
- отсутствующем YAML-ключе со статическим XML-default (`default`);
- отсутствующем YAML-ключе с `implicitValueXML` или вычислением (`evaluate`);
- присутствующем YAML-ключе со значением `undefined`;
- default и implicit value;
- XML-объекте с `#text` и `xsi:type`;
- XML aliases системных перечислений;
- `typedXML` числа;
- допустимых и ошибочных YAML-значениях.

Сравниваются смысловое значение, XML/YAML-результат и ошибка с путём. Матрица
закрепляется ожидаемым XML/YAML и существующими фикстурами, а не вызовом
удалённой старой функции.

### Интеграционные на `cf/doc`

- импорт создаёт тот же YAML, configuration index и diagnostics;
- контрольный YAML → XML создаёт тот же объектный XML;
- round-trip не получает новых semantic/triage diff;
- отдельно сравнивается время обоих направлений и частых типов;
- Peak RSS и Peak Heap не растут выше разброса исходных измерений.

Перед завершением выполняются полный `pnpm test`, проверки дубликатов и
архитектурные тесты проекта.

## Последовательность внедрения

1. Зафиксировать исходные измерения обоих направлений на `cf/doc`.
2. Ввести единый `CompiledPropertyPlan` и его кэш в
   `PropertyRuleExecutor`.
3. Перевести YAML → XML на готовый порядок, операции и однократное чтение
   наличия свойства.
4. Добавить общую стратегию отсутствующего YAML-свойства и доказать, что
   `skip` не применяется к значениям, способным породить XML.
5. Перевести XML → YAML на XML-представление того же плана и готовые операции.
6. Доказать равенство результатов и измерить эффект единого плана.
7. Добавить и отдельно измерить прямые преобразователи частых типов, начиная с
   `boolean`; общий договор отсутствия сразу действует для всех типов.
8. Удалить прямые варианты, не давшие воспроизводимого выигрыша.
9. Выполнить интеграционный round-trip `cf/doc` и полный набор тестов.

## Не входит в работу

- изменение XML- и YAML-форматов;
- изменение XML-фикстур;
- новые применения `!xml`;
- предметные условия по именам типов в нейтральном runtime;
- кэширование данных объектов или перенос плана между worker;
- генерация JavaScript-кода или `eval`;
- оптимизация XML-парсера, MessagePack, anomaly proof и сериализации YAML/XML;
- ERP round-trip во время разработки этой оптимизации.

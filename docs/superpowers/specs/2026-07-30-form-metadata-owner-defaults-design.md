# XML-default метаданных вложенных форм

## Контекст

Полный YAML round-trip конфигурации `cf/doc` выявил два массовых
расхождения в метаданных управляемых форм:

- из 1 931 XML-файла удаляется
  `<IncludeHelpInContents>false</IncludeHelpInContents>`;
- в 1 432 XML-файла ошибочно добавляется `<ExtendedPresentation/>`.

Оба свойства отсутствуют в компактном YAML, поэтому экспорт должен
восстанавливать их каноническую XML-форму без чтения reference XML и без
хранения признака присутствия тега в снимке.

В версии 0.0.3 каноническое правило не вычислялось:
`syncFormToXML` импортировал исходную форму как reference, а
`preserveFromReferenceXML` переносил наличие `ExtendedPresentation` из
исходного XML. После отказа от reference этот механизм больше не подходит.

## Исходные данные

Проверены 32 351 форма из семи конфигураций в
`/Users/nikita/git/round-trip-compact/cf`.

`ExtendedPresentation` присутствует ровно у:

- всех 7 108 форм обработок;
- всех 5 068 форм отчётов.

У остальных 20 175 форм тег отсутствует. Совпадение с типом владельца
полное во всех исследованных конфигурациях.

Тип основного реквизита не определяет наличие тега:

- у 6 572 форм отчётов и обработок нет основного реквизита, но
  `ExtendedPresentation` присутствует;
- у 47 форм другого владельца основной реквизит имеет тип
  `DataProcessorObject` или `ReportObject`, но `ExtendedPresentation`
  отсутствует;
- обычные формы отчётов также содержат тег, поэтому правило не зависит от
  `FormType`.

## Решения

### IncludeHelpInContents

`IncludeHelpInContents` является общим обязательным XML-свойством формы.
Правило получает `defaultValueXML: false`.

`defaultValueXMLEmpty: false` для этого поведения не подходит:
`defaultValueXMLEmpty` описывает значение явно присутствующего пустого
XML-тега при импорте, а исходный XML содержит непустой скаляр `false`.

Значение `false` по-прежнему не записывается в YAML благодаря
`implicitValueYAML`, но восстанавливается при прямом YAML → XML.

### ExtendedPresentation

Свойство разрешено только формам, вложенным в отчёт или обработку.

- базовое `ClientApplicationFormRules` не содержит
  `extendedPresentation`;
- специализированное правило формы отчёта/обработки расширяет базовое и
  добавляет `extendedPresentation` с
  `defaultValueXMLEmpty: { items: {} }` и `defaultValueXMLRaw: ""`;
- пустое значение не хранится в YAML и восстанавливается как
  `<ExtendedPresentation/>`;
- заполненное значение импортируется в YAML и экспортируется обратно;
- для форм остальных владельцев `РасширенноеПредставление` является
  неизвестным полем YAML и приводит к ошибке проверки.

Правило зависит только от декларации владельца формы. Тип основного
реквизита и `FormType` не участвуют в выборе.

## Архитектура

### Варианты правил формы

В `forms/clientApplicationForm/rules.ts` объявляются:

1. базовое правило формы без `extendedPresentation`;
2. специализированный вариант с `extendedPresentation`.

Оба варианта описывают один формат файла формы. Специализированный вариант
собирается из базового правила и переопределяет только набор свойств,
доступных формам отчётов и обработок.

### Декларация владельца

`ChildFormNamesPropertyRule` получает необязательный `itemRule`.

Декларации `forms` в `MetadataDataProcessorRules` и
`MetadataReportRules` передают специализированное правило. Остальные
прикладные объекты не передают `itemRule` и используют базовое правило
формы.

Таким образом, знание о допустимых свойствах формы остаётся в
декларативных `rules.ts` конкретных прикладных объектов. Общие слои не
проверяют `itemType` владельца и не знают про отчёты или обработки.

### Resource topology

Обработчик `ChildFormNames` использует:

```text
propertyRule.itemRule ?? ClientApplicationFormRules
```

Выбранный `itemRule` записывается в content-декларацию формы и становится
`assignment.itemRule`.

Возможность подготовки XML формы передаёт `assignment.itemRule` в
`prepareFormXML`. Импорт, экспорт, проверка YAML и построение JSON Schema
используют один и тот же выбранный вариант правила.

`prepareFormXML` и преобразования формы больше не должны жёстко выбирать
`ClientApplicationFormRules`, если правило уже передано декларацией
ресурса.

## Поток данных

### XML → YAML

1. Resource topology определяет владельца файла формы через декларацию
   свойства `forms`.
2. Для отчёта или обработки выбирается специализированный `itemRule`, для
   остальных владельцев — базовый.
3. `IncludeHelpInContents=false` исключается как неявное YAML-значение.
4. Пустой `ExtendedPresentation` формы отчёта или обработки исключается
   из YAML; заполненное значение сохраняется.

### YAML → XML

1. Подготовленное назначение формы содержит выбранный `assignment.itemRule`.
2. `IncludeHelpInContents` восстанавливается общим правилом как `false`.
3. Специализированное правило восстанавливает пустой
   `<ExtendedPresentation/>` или экспортирует заданное значение.
4. Базовое правило не знает свойства `РасширенноеПредставление` и не
   создаёт XML-тег.

Reference XML и снимок для выбора этих defaults не используются.

## Проверка ошибок

Проверка YAML обязана использовать тот же `itemRule`, что импорт и экспорт.
Если форма объекта, отличного от отчёта и обработки, содержит
`РасширенноеПредставление`, проверка сообщает о неизвестном поле с обычным
путём к свойству формы.

Отдельные новые условия по `itemType` в orchestration, validation и project
не добавляются.

## Тестирование

Существующие XML-фикстуры не изменяются.

Нужны узкие тесты:

1. Базовая форма из минимального YAML создаёт
   `IncludeHelpInContents=false` и не создаёт `ExtendedPresentation`.
2. Форма обработки и форма отчёта без значения в YAML создают
   `<ExtendedPresentation/>` без reference XML.
3. Заполненное `РасширенноеПредставление` формы отчёта/обработки
   сохраняется в XML.
4. Форма другого владельца с `РасширенноеПредставление` не проходит
   проверку YAML.
5. Resource topology переносит специализированный `itemRule` из
   `childFormNamesRule` в подготовку обоих XML-документов формы.
6. Импорт пустого `ExtendedPresentation` формы отчёта/обработки не
   раздувает YAML, а повторный экспорт восстанавливает тег.

Перед завершением выполняется полный `pnpm test`.

Повторный полный round-trip `cf/doc` должен:

- устранить 1 931 удаление `IncludeHelpInContents=false`;
- устранить 1 432 добавления `ExtendedPresentation` формам других
  владельцев;
- сохранить четыре заполненных и 536 пустых `ExtendedPresentation` форм
  отчётов и обработок;
- не использовать reference XML или данные снимка для этих решений.

## Вне границ

- Исправление остальных XML-default и перестановок round-trip.
- Возврат `preserveFromReferenceXML`.
- Хранение присутствия пустого XML-тега в YAML или снимке.
- Определение `ExtendedPresentation` по основному реквизиту формы.
- Условия по конкретному `itemType` в общих слоях metadata.

# Исправление ложных ошибок "Не найден владелец" для YAML-kind

## Контекст

После импорта ERP в `/home/nikita/git/temp-yaml` команда `nkdk validate /home/nikita/git/temp-yaml` нашла 589 ошибок вида:

```text
Не найден владелец Обработка.ПодборПлановЛимитов
Не найден владелец ЖурналДокументов.РегламентныеДокументы
Не найден владелец ОтчетОбъект.ОтчетыПоСотрудникам
```

При этом файлы владельцев существуют, например:

```text
Обработка/ПодборПлановЛимитов/Свойства.yaml
ЖурналДокументов/РегламентныеДокументы/Свойства.yaml
```

Для 528 ошибок по `Обработка` и 56 ошибок по `ЖурналДокументов` проблема не в том, что YAML-файлы потеряны. Валидатор доходит до ссылки на член объекта, но неправильно сопоставляет тип владельца с каталогом проекта.

Оставшиеся 5 ошибок из этой группы имеют другую причину:

- 4 ошибки `РегистрБухгалтерии.*` доходят до каталога `РегистрБухгалтерии`, но для него сейчас нет `ValidationProjectSpec`;
- 1 ошибка `ОтчетОбъект.*` доходит до каталога `Отчет`, но для него тоже нет `ValidationProjectSpec`.

Эти 5 ошибок не лечатся добавлением прямых YAML-kind в `ownerCache`; для них нужен отдельный дизайн включения `РегистрБухгалтерии` и `Отчет` в проектную валидацию.

## Причина

Пример ссылки в YAML:

```yaml
СвязьПоТипу: Обработка.ПодборПлановЛимитов.Реквизит.ВидБюджета
```

Ожидаемое поведение:

1. Валидатор понимает, что нужно проверить реквизит `ВидБюджета`.
2. Открывает владельца `Обработка/ПодборПлановЛимитов/Свойства.yaml`.
3. Проверяет, есть ли такой реквизит у обработки.

Фактическое поведение:

1. `resolveMember` разбирает корень ссылки как `DataProcessor`.
2. Для загрузки владельца он передает в `ownerCache` русское имя корня из `rootToYAML`: `Обработка`.
3. `ownerCache` знает `ОбработкаОбъект -> Обработка`, но не знает прямой kind `Обработка`.
4. Поэтому возвращает `Не найден владелец Обработка.ПодборПлановЛимитов`, хотя файл есть.

Такой же класс проблемы есть для `ЖурналДокументов`: каталог и `ValidationProjectSpec` есть, но `ownerCache` не принимает kind `ЖурналДокументов`.

## Выбранный подход

Расширить таблицу `ownerDirByRefKind` в `packages/core/metadata/validation/dataPath/ownerCache.ts`, добавив прямые YAML-kind, которые уже поддержаны в `ValidationProjectSpec`:

```text
Обработка -> Обработка
ЖурналДокументов -> ЖурналДокументов
```

Существующие соответствия вроде `ОбработкаОбъект -> Обработка` остаются. Это важно для путей, которые приходят из описаний типов платформы, например `DataProcessorObject`.

Не добавлять в рамках этой задачи `Отчет -> Отчет` и `РегистрБухгалтерии`-спеки: это расширит поверхность валидации и может потребовать отдельных тестов для правил `MetadataReportRules` и правил регистра бухгалтерии.

## Почему не другой подход

Не меняем разбор `metadataTarget` и не подменяем `DataProcessor` на `ОбработкаОбъект` в `resolveMember`. Там есть разные смысловые случаи: ссылка может указывать на сам объект или на его член. Локальная правка в `ownerCache` безопаснее, потому что она только учит загрузчик владельца находить уже существующий YAML-файл.

Не делаем полностью динамическое сопоставление по `ValidationProjectSpec`, потому что явная таблица сейчас проще для чтения и уже используется как договор между типами платформы и YAML-каталогами.

## Проверки

Добавить тесты для `OwnerMetadataCache`:

1. `Обработка` читается из каталога `Обработка`.
2. `ЖурналДокументов` читается из каталога `ЖурналДокументов`.

Добавить тест уровня валидации ссылки на член:

```yaml
СвязьПоТипу: Обработка.ПодборПлановЛимитов.Реквизит.ВидБюджета
```

Ожидание: ошибка `Не найден владелец Обработка.ПодборПлановЛимитов` больше не появляется. Если реквизита нет, валидатор должен выдать более точную ошибку про отсутствующий реквизит.

## Ожидаемый результат

После исправления 584 ложные ошибки "Не найден владелец" для существующих `Обработка` и `ЖурналДокументов` должны исчезнуть. На их месте могут появиться реальные ошибки содержимого, например "не найден реквизит" или "не найден член"; это считается улучшением, потому что валидатор начнет проверять фактическую структуру объекта.

Оставшиеся 5 ошибок (`РегистрБухгалтерии.*` и `ОтчетОбъект.*`) останутся отдельной группой до добавления соответствующих `ValidationProjectSpec`.

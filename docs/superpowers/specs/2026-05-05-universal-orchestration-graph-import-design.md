# Универсальный графовый импорт orchestration

## Контекст

`packages/core/metadata/orchestration` сейчас совмещает универсальные механизмы и знание о конкретных объектах. Особенно это видно в графовом входе: `importMetadataFileWithGraph.ts` напрямую импортирует правила catalog/document/enumeration/form, импортёры YAML/NKDK и особую логику формы.

Для агентной работы это плохая граница: чтобы безопасно изменить одну часть, приходится читать слишком много соседних файлов и помнить скрытые побочные эффекты. Цель дизайна — сделать графовый импорт маленьким универсальным протоколом, а конкретные объекты вынести в регистрацию рядом с владельцами этих объектов.

## Цель

Слой `orchestration` должен перестать знать, какими объектами он управляет. Он предоставляет общий протокол «источник → модель → граф» и применяет зарегистрированные обработчики. Конкретные модули метаданных регистрируют свои правила, импорт модели, шаблоны путей, объявление корня и дополнительные вклады в граф.

Главный критерий успеха: агент может взять один зарегистрированный тип или один шаг общего протокола, понять его контракт без чтения всех форм и прикладных объектов, изменить его и проверить локальными тестами.

## Не Цель

Этот дизайн не меняет XML/YAML round-trip, `GraphBuilder`, `GraphOps` и семантику рёбер. Он не добавляет новые типы метаданных и не переписывает правила fromXML/toXML/fromYAML/toYAML.

## Архитектура

Внутри `orchestration` остаётся универсальное ядро:

- реестр графовых импортёров;
- общий сценарий импорта зарегистрированного источника;
- применение `buildGraphFromModel`;
- работа с `GraphBuilder`, `GraphOps`, позициями YAML и filePath;
- разбор путей только через зарегистрированные шаблоны.

Из универсального ядра должны исчезнуть прямые импорты из `~/metadata/appliedObjects/*` и `~/metadata/forms/*`. Слова «справочник», «документ», «перечисление», «форма» допустимы в тестовых данных и документации, но не как зашитые зависимости общего сценария.

## Компоненты

`graphImportRegistry` хранит регистрации. Каждая регистрация описывает, какой источник она понимает, как получить модель и как объявить графовый корень.

`importRegisteredMetadataSourceWithGraph` — новый универсальный вход. Он получает источник, ищет подходящую регистрацию, импортирует модель, объявляет корень, вызывает `buildGraphFromModel` и применяет дополнительные вклады, если регистрация их вернула.

`sourcePathPatterns` — регистрация шаблонов путей. Вместо жёсткого `KIND_BY_DIR` конкретный модуль сам говорит, какие пути ему принадлежат и какие параметры извлечь из пути.

Переходный модуль совместимости может сохранить старый публичный вход, если это нужно для потребителей. В нём допустима временная привязка к существующим регистрациям, но универсальное ядро от неё не зависит.

## Поток Данных

1. Вызывающий передаёт путь, текст YAML и опциональные парные источники.
2. Реестр находит регистрацию по пути или явному kind.
3. Регистрация импортирует модель из YAML/NKDK и возвращает правило обхода.
4. Оркестратор объявляет корневой узел через функцию регистрации.
5. Оркестратор вызывает `buildGraphFromModel` и применяет универсальные графовые операции.
6. Регистрация может вернуть дополнительные вклады в граф, например перенос filePath для парного файла. Оркестратор применяет их через общий контракт, без знания предметного типа.

Ошибки по смыслу остаются прежними: прямой импорт неизвестного kind бросает понятную ошибку, а сборка проектного графа может молча пропускать неподдержанные файлы, если такой контракт уже есть у вызывающего слоя.

## Типизация

Новый универсальный API проектируется без `as any` и `as unknown`. Типы регистрации должны выражать связь между моделью, правилом и результатом импорта через обобщения.

Если при переходе от старого кода невозможно сразу убрать приведение, оно допускается только в маленьком переходнике с говорящим именем. Приведение не должно расползаться по сценарию импорта; поведение переходника покрывается тестом.

## Тестирование

Основные тесты общего оркестратора должны использовать фиктивный тестовый тип, зарегистрированный прямо в тесте. Это закрепляет универсальный контракт без зависимости от catalog/document/enumeration/form.

Нужны отдельные проверки:

- регистрация фиктивного kind строит модель и графовый корень;
- парный источник добавляет вклад в граф через общий контракт;
- неизвестный kind даёт прежнее поведение;
- `orchestration` не импортирует `~/metadata/appliedObjects/*` и `~/metadata/forms/*` из универсального ядра;
- переходник со старого API содержит все временные приведения в одном месте.

Существующие крупные тесты на реальные объекты можно оставить как интеграционную защиту, но новые проверки должны быть маленькими и контрактными.

## Документация

`.claude/architecture-orchestration.md` должен фиксировать инвариант универсальности: конкретика живёт в регистрациях снаружи, оркестратор применяет только общий протокол.

На новых публичных типах и функциях нужен короткий JSDoc: кто регистрирует обработчик, что именно оркестратор вызывает, какие поля графа обработчик может менять и где допустимы переходники совместимости.

## План Перехода

1. Ввести универсальный реестр и тестовый фиктивный тип.
2. Перевести текущие catalog/document/enumeration/form на внешние регистрации без изменения поведения.
3. Заменить прямые импорты в `orchestration` на работу через реестр.
4. Сохранить старый вход как тонкий переходник или удалить его, если потребители уже переведены.
5. Разнести крупные тесты: оставить интеграционные сценарии, но добавить маленькие контрактные тесты на новый протокол.

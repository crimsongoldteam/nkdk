# Полное восстановление порядка XML-свойств

## Цель

Вернуть временный анализатор порядка XML-свойств и расширить его так, чтобы он учитывал все
конкретные runtime-правила, фактически используемые при импорте предоставленных конфигураций и
расширений. На основании наблюдений анализатор обновляет `xmlOrder` в `rules.ts`.

Анализатор остаётся в репозитории до отдельной явной команды пользователя на удаление. Успешное
завершение анализа и проверок само по себе не разрешает удалять инструмент.

- `/Users/nikita/git/round-trip/cf/clean`;

После `cf/all` анализируются три расширения:

- `/Users/nikita/git/round-trip/cfe/control`;

Все три расширения используют `cf/all` как базовую конфигурацию и получают её reference-снимок.
Анализировать расширения как независимые конфигурации нельзя.

## Границы

### Обязательное покрытие

Анализатор обязан сопоставить с исходным `rules.ts` каждое конкретное runtime-правило, которое
фактически передано в рабочий XML-import хотя бы для одного узла из указанных `cf` или `cfe`.

Конкретным считается объект с `itemType` и `properties`, используемый при преобразовании
XML-свойств. К ним относятся:

- экспортируемые правила metadata-объектов;
- вложенные `property.itemRule`;
- правила элементов форм;
- `itemRule` дочерних объектов из `childCollections`;
- локальные варианты правил, собранные в файле владельца через spread.

### Исключения

Отдельный `xmlOrder` не требуется:

- наборам свойств без самостоятельных `itemType` и `properties`;
- общим заготовкам, которые существуют только для spread и никогда не передаются в import как
  самостоятельное runtime-правило;
- правилам, которые не встретились ни в одном из указанных источников.

Последняя группа остаётся в информационном разделе отчёта. Анализатор не выводит для неё порядок
из объявления properties или XSD и не записывает предположительный `xmlOrder`.

Порядок самих коллекций и специальных структур продолжает храниться через
`ConfigurationXmlNode.order`. Эта работа не заменяет его на `xmlOrder`.

## Архитектура

### Сбор наблюдений

Наблюдатель подключается только в режиме анализа. Обычный XML-import не создаёт результат анализа,
но использует тот же маршрут обхода.

Для каждого физического XML-узла наблюдатель получает:

- идентификатор исходной конфигурации или расширения;
- путь XML-файла;
- логический адрес объекта и XML-узла;
- точный runtime-объект правила;
- последовательность model property key, найденных в исходном XML.

Наблюдатель передаётся через импорт metadata-объектов, вложенные свойства, формы и элементы форм.
Дочерние metadata-объекты, импортируемые отдельными заданиями, анализируются с тем конкретным
`itemRule`, который указан владельцем.

### Каталог правил

Каталог связывает runtime-объект правила с изменяемым местом в `rules.ts`.

Он индексирует:

- прямые экспорты правил;
- вложенные `properties.<key>.itemRule`;
- `childCollections.<index>.itemRule`;
- локальные объекты, созданные через object spread;
- зарегистрированные top-level варианты, которые ссылаются на исходное правило.

Канонический source содержит файл, экспорт и путь внутри объявления. Один runtime-объект не может
соответствовать двум различным изменяемым source. Неоднозначность является ошибкой анализа.

Чистые property-фрагменты в каталог правил не входят.

### База и расширения

Сначала анализируется `cf/all` и формируется обычный configuration reference-снимок. Затем каждое
расширение импортируется как `configurationExtension` с этим базовым слоем.

Наблюдения расширения объединяются с наблюдениями конфигураций по каноническому source правила,
но сохраняют имя источника и XML-путь для диагностики конфликтов.

### Вычисление `xmlOrder`

Для каждого наблюдавшегося правила последовательности задают ограничения «свойство A находится
раньше свойства B». Из объединения ограничений строится стабильный топологический порядок.

При нескольких допустимых вариантах порядок объявления `properties` используется только как
детерминированный tie-breaker. Он не создаёт ограничений, которых не было в XML.

В явный `xmlOrder` попадают только свойства, встретившиеся хотя бы в одном наблюдении. Во время
экспорта `getCompiledXMLPropertyOrder` добавляет остальные свойства в конец в порядке объявления.

Повторное применение анализатора к неизменным источникам и к уже обновлённым `rules.ts` не должно
создавать diff.

## Ошибки и отчёт

Автоматическая запись запрещена, если обнаружено хотя бы одно из условий:

- встретившееся runtime-правило не сопоставлено с source;
- один runtime-объект сопоставлен с различными source;
- наблюдение содержит неизвестный или повторяющийся property key;
- две конфигурации задают противоположный порядок пары свойств;
- объединённый граф порядка содержит цикл;
- расширение анализируется без reference-снимка `cf/all`;
- отдельное наблюдение не является подпоследовательностью вычисленного порядка.

Отчёт разделяет:

- наблюдавшиеся и успешно сопоставленные правила;
- встретившиеся правила без source;
- объявленные, но не встретившиеся правила;
- конфликты и циклы;
- статистику отдельно по каждому `cf` и `cfe`.

Наличие объявленного, но не встретившегося переиспользуемого правила не является ошибкой.

## Проверка

### Автоматические тесты

- каталог прямых экспортов и top-level registrations;
- вложенные `property.itemRule`;
- `childCollections.itemRule`;
- локальный вариант правила через spread;
- вложенные элементы форм;
- объединение наблюдений базы и расширения;
- отказ анализировать расширение без базового reference;
- конфликты, циклы, неоднозначности и неизвестные ключи;
- идемпотентная перезапись `xmlOrder`;
- сохранение `present` и специального `ConfigurationXmlNode.order`.

После реализации выполняются:

```bash
pnpm --dir packages/core type-check
pnpm test
```

### Анализ реальных источников

Анализатор запускается на семи `cf` и трёх `cfe`. Перед применением требуется:

- ноль встретившихся правил без source;
- ноль неоднозначностей;
- ноль конфликтующих пар;
- ноль циклов;
- каждое наблюдение является подпоследовательностью вычисленного порядка.

После записи выполняется повторный dry-run, который не должен менять `rules.ts`.

### Полный round-trip

Проверка выполняется актуальным навыком `round-trip-yaml`, то есть по полному циклу:

```text
XML -> модель -> YAML -> модель -> XML
```

Проверяются семь конфигураций и три расширения. Расширения проходят цикл в контексте `cf/all`.

Целевой результат — отсутствие XML-diff. Если остаётся расхождение, не относящееся к текущей
ветке, оно допустимо только после воспроизведения того же diff на свежем `develop`.

## Жизненный цикл инструмента

После заполнения `xmlOrder`, повторного анализа, полного `round-trip-yaml` и `pnpm test`
анализатор остаётся в ветке. Его удаление проектируется и выполняется только после отдельной явной
команды пользователя.

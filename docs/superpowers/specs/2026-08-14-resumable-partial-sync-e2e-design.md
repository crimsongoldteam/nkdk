# Возобновляемая проверка частичной синхронизации

## Цель

Добавить отдельный параметризованный сценарий, который проверяет публичный
MCP-цикл частичной синхронизации на реальной файловой информационной базе:

1. подготавливает базу из e2e-конфигурации и `Расширение_All`;
2. импортирует оба компонента через MCP и сверяет их с e2e-фикстурой;
3. добавляет в NKDK-проект новый справочник и синхронизирует его через MCP;
4. добавляет реквизит в созданный справочник и повторяет синхронизацию;
5. после каждого изменения заново импортирует оба компонента через MCP и
   проверяет полученное состояние;
6. после сбоя продолжает с последней подтверждённой контрольной точки.

Сценарий не входит в обычные `pnpm test` и `pnpm test:e2e`. Его запускают
явно, когда доступна поддерживаемая платформа.

## Границы первой версии

Входит:

- файловая информационная база в отдельном каталоге сценария;
- e2e-компоненты `cf` и `cfe/Расширение_All`;
- создание одного нового справочника в `cf`;
- последующее добавление одного строкового реквизита в этот справочник;
- работа через настоящий MCP stdio-сервер;
- повторный импорт `cf` и расширения после каждого этапа;
- побайтовое сравнение NKDK-файлов каждого компонента без служебного `.nkdk`;
- контрольные точки базы и рабочего NKDK-проекта;
- автоматическое продолжение после ошибки.

Не входит:

- проверка остальных двух e2e-расширений;
- удаление или переименование созданных объектов;
- матрица всех видов metadata-объектов;
- клиент-серверные базы;
- автоматический запуск в CI или общей e2e-команде;
- публичные MCP-операции создания, заполнения, копирования или восстановления
  тестовой базы;
- обновление конфигурации базы данных после частичной загрузки сохранённой
  конфигурации.

Последующая проверка всех видов metadata-объектов должна расширять таблицу
этапов этого исполнителя, а не создавать отдельный механизм управления базой и
контрольными точками.

## Граница MCP и тестового окружения

Наблюдаемое поведение проверяется только через публичный MCP-протокол. Сценарий
запускает настоящий stdio-сервер и вызывает его тем же способом, что внешний
потребитель.

Через MCP выполняются:

- `nkdk.list_infobase_extensions`;
- `nkdk.import_from_infobase` для `cf`;
- `nkdk.import_from_infobase` для `cfe/Расширение_All`;
- `nkdk.validate_project` перед каждой синхронизацией;
- `nkdk.sync_to_infobase` для `cf`;
- `nkdk.close_platform_connection` перед копированием базы.

Тестовая обвязка обращается к установленной платформе и файловой системе
напрямую только для операций, которых нет в публичном MCP:

- создания пустой файловой базы;
- первоначальной полной загрузки e2e `cf` и `Расширение_All`;
- копирования и восстановления базы и NKDK-проекта.

Прямой вызов внутренних функций `@nkdk/runtime`, `@nkdk/rules`,
`@nkdk/platform` или сервисов `@nkdk/mcp` для проверяемого цикла запрещён.

## Импорт расширения из информационной базы

Существующий `nkdk.import_from_infobase` умеет импортировать только `cf`. Для
содержательной проверки расширения его вход получает необязательное поле:

```ts
type ImportFromInfobaseInput = {
  projectDir: string
  componentPath?: "cf" | `cfe/${string}`
  allowWrite?: boolean
}
```

Отсутствующее значение сохраняет прежнее поведение и означает `cf`.
`cfe/<Имя>` выбирает одно расширение и импортирует его в отсутствующий или
пустой компонент с тем же путём. Импорт расширения выполняется после импорта
основной конфигурации в этот же проект, чтобы resolver располагал индексом
родительского компонента.

Граница платформы получает необязательное `extensionName` в параметрах
экспорта. Оба существующих режима добавляют платформенный параметр выбора
расширения к своей штатной команде выгрузки. MCP передаёт имя, полученное из
проверенного `componentPath`, а затем использует обычный XML → YAML импорт.

Ограничения существующего импорта сохраняются:

- запись требует `allowWrite: true`;
- целевой компонент должен отсутствовать либо быть пустым;
- временная XML-выгрузка удаляется только после полного успеха;
- при ошибке сохраняются безопасная диагностика, журнал и временный каталог;
- формат успешного ответа не меняется.

## Каталог сценария

Команда принимает корень сценария:

```bash
pnpm test:partial-sync -- --root /path/to/workspace
```

Внутри находятся только принадлежащие сценарию данные:

```text
workspace/
  state.json
  base/
  data/
  project/
  checkpoints/
    01-baseline/
      base/
      project/
      manifest.json
    02-catalog/
    03-attribute/
  verification/
    baseline/
    catalog/
    attribute/
  logs/
    <attempt-id>/
```

`base/` — рабочая файловая база, `data/` — служебные данные подготовительных
команд, `project/` — рабочий NKDK-проект с `.nkdk/project.yaml` и индексами.
`verification/<этап>/` содержит чистый проект, повторно импортированный из базы
через MCP. Журналы каждой попытки имеют отдельный каталог и не перезаписывают
предыдущую ошибку.

## Этапы сценария

### Предварительные проверки

Исполнитель:

1. требует абсолютный непустой `--root`;
2. разрешает только отсутствующий, пустой или уже размеченный этим сценарием
   каталог;
3. отклоняет символические ссылки в управляемых путях;
4. находит поддерживаемую установку платформы и обязательные исполняемые
   компоненты;
5. проверяет наличие e2e XML- и NKDK-фикстур `cf` и `Расширение_All`;
6. если есть завершённая контрольная точка, проверяет её manifest и
   восстанавливает рабочие `base/` и `project/`;
7. определяет следующий незавершённый этап по `state.json`.

### Этап 01: исходное состояние

Тестовая обвязка создаёт пустую базу и полностью загружает e2e `cf` и
`Расширение_All`. Затем она создаёт настройки подключения в `project/` и через
MCP:

1. убеждается, что список расширений содержит ровно ожидаемое расширение;
2. импортирует `cf`;
3. импортирует `cfe/Расширение_All`;
4. сравнивает каждый импортированный компонент с соответствующим каталогом
   e2e NKDK-фикстуры;
5. исключает из сравнения `.nkdk` и настройки подключения;
6. закрывает платформенное соединение;
7. публикует контрольную точку `01-baseline`.

### Этап 02: новый справочник

Исполнитель добавляет в `project/cf` минимальный справочник
`ПроверкаЧастичнойСинхронизации` с детерминированным YAML. Затем:

1. вызывает `nkdk.validate_project` и требует отсутствие ошибок;
2. вызывает `nkdk.sync_to_infobase` для `cf` и требует состояние
   `synchronized`;
3. повторный вызов без изменений должен вернуть `unchanged`;
4. импортирует `cf` и `Расширение_All` в чистый проект
   `verification/catalog`;
5. сравнивает повторно импортированный `cf` с рабочим `project/cf`;
6. сравнивает повторно импортированное расширение с исходной e2e-фикстурой;
7. подтверждает отсутствие ожидающего partial sync через следующий публичный
   ответ `unchanged`, не читая внутреннее хранилище напрямую;
8. закрывает соединение и публикует `02-catalog`.

### Этап 03: новый реквизит

Исполнитель добавляет в тот же YAML справочника реквизит `ТестоваяСтрока` типа
`Строка(20)`. После этого он повторяет validation, синхронизацию, проверку
`unchanged`, чистый импорт обоих компонентов и сравнения этапа 02. Успешный
этап публикует `03-attribute` и завершает сценарий.

## Сравнение результата

Сравнение выполняется существующим помощником файловых деревьев и показывает
добавленные, удалённые и изменённые пути. Для XML-деталей не создаётся второй
параллельный договор: состояние базы наблюдается через повторный MCP-импорт в
NKDK.

Проверки имеют два разных основания:

- `cf` после изменения должен побайтово совпадать с рабочим `project/cf`;
- `cfe/Расширение_All` всегда должно побайтово совпадать с исходной e2e
  NKDK-фикстурой, потому что сценарий его не меняет.

Отдельно проверяются успешные MCP-ответы, наличие расширения, отсутствие
ошибок validation и переход `synchronized` → `unchanged`. Последний переход
одновременно подтверждает, что MCP завершил публикацию снимка и не оставил
ожидающий пакет.

## Контрольные точки и продолжение

`state.json` имеет версионированный минимальный формат:

```json
{
  "version": 1,
  "scenario": "partial-sync-catalog-attribute",
  "completedStage": "02-catalog",
  "checkpoint": "checkpoints/02-catalog"
}
```

Каждая контрольная точка содержит полные копии `base/` и `project/`, а также
manifest с версией формата, именем этапа и хэшами файлов. Публикация происходит
так:

1. MCP-соединение закрывается, чтобы снять блокировки базы;
2. копии записываются в новый временный каталог внутри `checkpoints/`;
3. manifest строится по фактически записанным файлам;
4. копия повторно проверяется по manifest;
5. временный каталог атомарно переименовывается в итоговый;
6. новый `state.json` записывается во временный файл и атомарно заменяет старый.

Этап считается завершённым только после повторного импорта и всех сравнений.
Ошибка до публикации не меняет `state.json`.

При следующем запуске исполнитель всегда проверяет последнюю контрольную точку
и восстанавливает из неё обе рабочие части перед продолжением. Если предыдущая
попытка оборвалась во время замены рабочего каталога, восстановление безопасно
повторяется. Контрольная точка при этом остаётся неизменной.

До первой опубликованной точки незавершённая подготовка пересоздаётся с нуля,
но только внутри каталога с валидным маркером текущего сценария.

## Ошибки и безопасность

- Чужой непустой `--root` отклоняется без изменений.
- Канонические пути `base`, `project`, `checkpoints` и `verification` должны
  оставаться внутри канонического корня и не пересекаться.
- Исполнитель не принимает корень файловой системы, домашний каталог или
  корень репозитория как рабочий каталог сценария.
- Повреждённые `state.json`, manifest или контрольная точка не удаляются и не
  восстанавливаются автоматически; команда возвращает путь и причину ошибки.
- Удаляются и заменяются только заранее известные управляемые каталоги внутри
  размеченного корня.
- Пароли не нужны для созданной тестовой базы и не попадают в состояние или
  журналы.
- Ошибка MCP сохраняет полный безопасный ответ, журнал платформы и путь
  временного результата в каталоге текущей попытки.
- Неизвестный результат доставки не очищается принудительно. Сценарий
  завершается, а повторный запуск начинает с предыдущей контрольной точки.

## Организация кода

Ответственности разделяются на небольшие модули:

- MCP-контракт и сервис импорта выбирают компонент;
- платформенный слой умеет выгружать выбранное расширение;
- MCP stdio-клиент сценария вызывает только опубликованные инструменты;
- драйвер подготовки владеет созданием и исходной полной загрузкой базы;
- хранилище состояния владеет маркером, manifest, публикацией и
  восстановлением контрольных точек;
- координатор этапов выбирает следующий этап и не знает деталей копирования;
- определения этапов владеют изменением YAML и наблюдаемыми проверками;
- Vitest-файл только читает `--root`, запускает координатор и задаёт большой
  тайм-аут.

Реальный тест и его отдельная конфигурация используют имя `partial-sync` без
суффикса, обозначающего платформу.

## Проверки без внешней платформы

Обычный набор тестов покрывает:

- обратную совместимость `import_from_infobase` без `componentPath`;
- выбор `cf` и `cfe/<Имя>` в контракте, сервисе и обоих платформенных
  адаптерах;
- отказ для некорректного component path и непустого целевого компонента;
- построение команд выгрузки выбранного расширения;
- переходы этапов и продолжение с каждой контрольной точки;
- отсутствие публикации состояния при сбое подготовки, проверки, копирования
  или записи manifest;
- отклонение повреждённой контрольной точки;
- восстановление после искусственно оборванного этапа;
- защиту от чужого непустого каталога, выхода за корень и символических ссылок;
- явное исключение реального сценария из `pnpm test:e2e`.

Реальный сценарий запускается только отдельной командой
`pnpm test:partial-sync -- --root <каталог>` и в первой реализации не
выполняется разработчиком без доступной платформы.

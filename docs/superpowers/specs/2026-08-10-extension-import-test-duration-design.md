# Устойчивый бюджет теста импорта расширения

## Контекст

После объединения `codex/implicit-form-data-paths` с `origin/develop` все 6 201 функциональные проверки проходят, но штатный `pnpm test` дважды завершился ошибкой бюджета: `metadata/importFromXml/importConfigurationExtension.test.ts` занял 1 016–1 058 мс при пределе 1 000 мс.

Причина находится в тесте: один файл дважды выполняет полный публичный импорт одного расширения. Первый импорт проверяет обычную заимствованную форму со встроенным `BaseForm`, второй повторяет всю операцию только ради варианта той же формы без встроенного `BaseForm`.

## Цель

- сохранить обе сквозные проверки через `importConfigurationFromXml`;
- выполнять один импорт расширения вместо двух;
- не менять пределы длительности и коэффициенты окружения;
- не изменять существующие XML-фикстуры;
- добиться устойчивого прохождения `pnpm test`.

## Решение

Тест продолжит копировать исходную XML-фикстуру во временный каталог. В этой временной копии он создаст вторую заимствованную форму:

- исходная `ФормаОтчета` останется формой со встроенным `BaseForm`;
- новая форма получит отдельное имя и идентификаторы, будет добавлена в `ChildObjects` справочника и не будет содержать `BaseForm`;
- для обеих форм будут записаны соответствующие текущие формы `cf`, чтобы импорт мог определить заимствованные и собственные элементы;
- один вызов `importConfigurationFromXml` импортирует обе формы.

Первый тест сохранит существующие проверки результата импорта и сохранённой `БазоваяФорма.yaml`. Второй тест будет читать результат второй формы из того же импорта и проверять:

- у собственного поля отсутствует явный `ПутьКДанным`;
- у заимствованного поля записан `ПутьКДанным: ""`;
- `БазоваяФорма.yaml` для формы без встроенного `BaseForm` не создана.

Production-код не меняется.

## Проверка

1. До изменения целевой тест должен воспроизводить два полных импорта и превышение бюджета в штатном запуске.
2. После изменения целевой файл должен проходить с обеими сквозными проверками.
3. Три последовательных запуска `@nkdk/core` с перемешиванием должны соблюдать предел 1 000 мс для каждого файла.
4. Затем выполняются `pnpm test`, `pnpm duplicates -- --base origin/develop`, `pnpm test:architecture:rules` и `pnpm test:architecture`.

## Ограничения

- не разделять тесты по файлам ради формального обхода лимита;
- не заменять второй сквозной договор низкоуровневой проверкой;
- не ослаблять утверждения существующего теста;
- не переносить работу в неучитываемый этап жизненного цикла Vitest.

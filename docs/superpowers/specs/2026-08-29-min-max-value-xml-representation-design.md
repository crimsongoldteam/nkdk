# XML-представление `MinMaxValue`

## Статус документа

Документ фиксирует решение о точном round-trip свойств `MinValue` и
`MaxValue`, представленных common-типом `MinMaxValue`.

Общий механизм XML-аномалий и нормативный YAML-договор `!xml/raw` определены в
[спецификации XML-аномалий common-типов](2026-08-23-common-types-xml-anomaly-framework-design.md).
Настоящий документ не вводит новый тег или частный runtime-механизм. Он
согласовывает применение существующего `!xml/raw` к `MinMaxValue` и объясняет,
почему низкоуровневый прямой round-trip одной rules-фикстуры недостаточен.

## Проблема

YAML хранит числовое значение `MinMaxValue` как число. Поэтому обычная запись

```xml
<MinValue xsi:type="xs:string">1</MinValue>
```

преобразуется в смысловое YAML-значение `1`. При обратном экспорте правило
элемента формы создаёт каноническое представление

```xml
<MinValue xsi:type="xs:decimal">1</MinValue>
```

Смысл числа сохранён, но точный XML round-trip нарушен: YAML-число само по себе
не различает `xs:string`, `xs:decimal` и отсутствие `xsi:type`.

Это не ошибка числового преобразования и не основание менять смысловой тип
YAML. Отличается только XML-форма понятного значения, поэтому расхождение
относится к общему классу XML-аномалий.

## Наблюдения по конфигурациям

Исследование выполнено по XML-каталогу
`/Users/nikita/git/round-trip-compact/cf`. Подсчитывались непустые `MinValue` и
`MaxValue`, их `xsi:type`, текст и расположение в metadata-объектах и формах.

| Область | `xs:string` | `xs:decimal` | без `xsi:type` |
|---|---:|---:|---:|
| metadata | 5 454 | 0 | 0 |
| формы | 48 | 5 712 | 107 |

Для форм `xs:decimal` составляет 97,4% непустых значений. 48 строковых
вхождений сводятся к трём повторяющимся исходным формам, а значения без
`xsi:type` встречаются по 17 путям. У редких строковых значений совпадают версия
формы и эффективный тип реквизита с обычными decimal-случаями. Следовательно,
вариант нельзя надёжно вывести из версии формы, типа данных или другого
стабильного признака конфигурации.

Все 5 502 исследованных значения с `xs:string` имеют числовой смысл: 5 476
записаны целыми числами, 26 — десятичными числами с запятой. Это подтверждает,
что менять обычный YAML-тип с числа на строку не нужно.

## Каноническое представление

Канонический `xsi:type` определяется конкретным `PropertyRule`:

- если правило задаёт `typedXML: "xs:string"`, каноничен `xs:string`;
- если правило задаёт `typedXML: "xs:decimal"`, каноничен `xs:decimal`;
- если `typedXML` не задан, `MinMaxValue` использует `xs:decimal`.

Поэтому `InputField` и `TableInputField` канонически экспортируют
`MinValue`/`MaxValue` как `xs:decimal`. Некоторые metadata-правила, например
свойства констант и общих реквизитов, явно задают `xs:string`.

Категория владельца — «форма» или «metadata» — не является частью алгоритма.
Запрещены частные условия по `itemType`, XML-корню, имени свойства или пути к
файлу. Один и тот же common-тип следует параметрам уже выбранного правила.

## Решение

Обычный YAML сохраняет смысловое конечное число. После импорта выполняется
общий контрольный экспорт без reference XML и сравнивается с исходным XML.

- Если `xsi:type`, текст и присутствие атрибута восстановлены, значение остаётся
  обычным YAML-числом.
- Если отличается только XML-форма, общий механизм создаёт `!xml/raw` на
  минимальной границе свойства `МинимальноеЗначение` или
  `МаксимальноеЗначение`.
- `$значение` содержит смысловое число, а `$xml` — только минимальную поправку,
  необходимую для точного XML.
- Новый тег, служебное поле в `MinMaxValue` или специальная ветвь контрольного
  экспорта не добавляются.

Строковый тип у числового значения формы записывается так:

```yaml
МинимальноеЗначение: !xml/raw
  $значение: 1
  $xml:
    _xsi:type: xs:string
```

Здесь `#text` не нужен: обычный экспорт уже создаёт правильный текст `1`, а
поправка заменяет только `xsi:type`.

Отсутствующий в исходном XML `xsi:type`, который обычный экспорт добавляет,
записывается так:

```yaml
МаксимальноеЗначение: !xml/raw
  $значение: 11
  $xml:
    _xsi:type: null
```

Если одновременно отличается точная числовая запись, `$xml` содержит и текст.
Например, для неканонического строкового значения формы `1,5` минимальная
поправка включает `_xsi:type: xs:string` и `"#text": "1,5"`.

## Почему не строка в обычном YAML

Строка сохранила бы `xsi:type="xs:string"` только косвенно и смешала бы два
разных договора:

- смысл свойства остаётся числовым и участвует в числовой проверке;
- `xsi:type` и точная лексема относятся к форме XML.

Кроме того, строка не выражает отсутствие `xsi:type` и не решает общий случай
других XML-атрибутов. `!xml/raw` явно разделяет смысл и минимальную XML-поправку.

## Почему не отдельный тег MinMax

Теги вроде `!xml/minmax` или `!xml/type` создали бы новый публичный договор для
частного проявления уже известной XML-аномалии. Такой тег пришлось бы отдельно
поддерживать в парсере YAML, проверке, импорте, полном и частичном экспорте.

Общий `!xml/raw` уже умеет сохранить замену и отсутствие атрибута, точную
лексему и сочетание нескольких отличий. Специальный механизм не добавляет
выразительности и повышает стоимость сопровождения.

## Граница прямого round-trip

Тест
`packages/rules/metadata/forms/elements/__tests__/roundTrip.integration.test.ts`
проверяет непосредственный вызов rules элемента: XML → смысловой YAML → XML.
Он намеренно не запускает контрольный экспорт и локализацию XML-аномалий.
Поэтому фикстура `inputField/__fixtures__/minMaxStringType.xml` остаётся
исключённой из этого набора.

Исключение не означает допустимое расхождение в продукте. Производственный
договор проверяется в
`packages/rules/metadata/importFromXml/controlExport.integration.test.ts`:

1. в существующую форму импортируются `MinValue xsi:type="xs:string"` и
   канонический `MaxValue xsi:type="xs:decimal"` из фикстуры;
2. контрольный экспорт создаёт минимальный raw только для `MinValue`;
3. YAML содержит смысловое число и `_xsi:type: xs:string`;
4. следующий полный экспорт восстанавливает оба исходных XML-элемента точно.

## Критерии приёмки

1. Канонический `MinMaxValue` остаётся обычным конечным YAML-числом без
   `!xml/raw`.
2. Неканонический `xsi:type` числового значения сохраняется через
   `!xml/raw` на самом свойстве, а не на всём элементе или форме.
3. `$xml` содержит только отличающиеся части XML; совпадающий `#text` не
   дублируется.
4. Отсутствующий `xsi:type` восстанавливается явной поправкой
   `_xsi:type: null`.
5. Каноничность определяется параметрами `PropertyRule`, без условий по типу
   владельца или месту файла.
6. Round-trip через сериализованный YAML восстанавливает исходные `MinValue` и
   `MaxValue` без reference XML.
7. Прямая rules-фикстура сопровождается комментарием, указывающим на
   производственный контрольный тест.

## Вне границ решения

- изменение числовой модели `MinMaxValue`;
- добавление нового публичного YAML-тега;
- нормализация или исправление исходного XML конфигурации;
- вывод редкого варианта по версии формы, типу реквизита или имени владельца;
- использование `!xml/raw` вместо устранения дефектов rules или resolver.

# Новые расхождения round-trip CashdeskDev и Conversion

## XML-псевдоним `CheckBoxType.Switcher`

### Контекст

Полный XML → YAML → XML round-trip конфигурации
`CashdeskDev_3_32_26_0_setup1c` изменяет 32 файла форм. Во всех случаях
исходное значение:

```xml
<CheckBoxType>Switcher</CheckBoxType>
```

заменяется на:

```xml
<CheckBoxType>Auto</CheckBoxType>
```

Всего в этих файлах изменяется 127 элементов формы.

### Причина

Внутреннее системное перечисление `CheckBoxType` содержит значение `Switch`,
которому в YAML соответствует `Выключатель`. XML-импорт не знает лексическую
форму `Switcher`, поэтому XML → YAML не создаёт `ВидФлажка`. При обратном
преобразовании существующий XML-default для отсутствующего YAML-ключа создаёт
`CheckBoxType=Auto`.

Исследование всех конфигураций `/Users/nikita/git/round-trip-compact/cf`, кроме
`all`, обнаружило:

| XML-значение | Количество |
|---|---:|
| `Auto` | 98 759 |
| `Switcher` | 1 542 |
| `CheckBox` | 1 048 |
| `Tumbler` | 877 |
| `Switch` | 0 |

`Switcher` встречается в 30 конфигурациях. Это не единичное повреждённое
значение и не отдельное смысловое состояние: XML использует иную лексическую
форму того же вида `Выключатель`.

### Решение

Использовать существующий общий механизм XML-псевдонимов системных
перечислений. Для `CheckBoxType` зарегистрировать двустороннее соответствие:

```ts
CheckBoxType: {
  toXML: { Switch: "Switcher" },
  fromXML: { Switcher: "Switch" },
}
```

Преобразование становится однозначным:

```text
XML Switcher → внутреннее Switch → YAML Выключатель
YAML Выключатель → внутреннее Switch → XML Switcher
```

YAML остаётся смысловым:

```yaml
ВидФлажка: Выключатель
```

### Границы

- Не добавлять `Switcher` как второе смысловое значение перечисления.
- Не менять YAML-наименование `Выключатель`.
- Не применять `!xml`: XML однозначно восстанавливается из смыслового значения.
- Не читать reference XML и не ветвиться по версии формы или конфигурации.
- Не изменять общий механизм псевдонимов и общие типы правил.
- Решение одинаково применяется к `CheckBoxField` и `TableCheckBoxField` через
  общий тип `SystemEnumeration`.

### Проверки

- XML `Switcher` преобразуется в YAML `ВидФлажка: Выключатель`.
- YAML `ВидФлажка: Выключатель` преобразуется в XML `Switcher` без reference.
- Полный XML → YAML → XML договор сохраняет `Switcher`.
- Остальные значения `Auto`, `Tumbler` и `CheckBox` не меняются.
- Существующий договор отсутствующего `ВидФлажка` → `CheckBoxType=Auto`
  сохраняется.
- Round-trip `CashdeskDev_3_32_26_0_setup1c` больше не содержит эти 32
  расхождения.

## Проверка зарегистрированных источников DataPath

### Контекст

Импорт `Conversion_3_1_6_15_setup1c` завершается 11 ошибками вида:

```text
typeInfo.table.kind имеет неизвестное значение
```

Первый случай относится к реквизиту обработки
`ВыгрузкаЗагрузкаEnterpriseData.КомпоновщикОтбораВсехДокументов`:

```xml
<Type>
  <v8:Type xmlns:dcsset="http://v8.1c.ru/8.1/data-composition-system/settings">
    dcsset:SettingsComposer
  </v8:Type>
</Type>
```

Такой тип корректно преобразуется в описание зарегистрированного источника
DataPath:

```ts
{
  kind: "Registered",
  type: "DataCompositionSettingsComposer",
}
```

Остальные ошибки возникают на таких же зарегистрированных источниках в
реквизитах обработок и форм.

### Причина

Общий тип `DataPathTableInfo`, преобразование типов и двоичное хранилище уже
поддерживают вариант `Registered`. Однако пограничная проверка
`assertDataPathTableInfo` перечисляет все остальные варианты и ошибочно
отклоняет `Registered` до сохранения результата импорта.

XML и YAML корректны. Ошибка находится только в неполном перечне допустимых
значений внутренней проверки.

### Решение

В `assertDataPathTableInfo` разрешить вариант:

```ts
{
  kind: "Registered",
  type: string,
}
```

Для него допустимы ровно поля `kind` и `type`; `type` обязан быть строкой.
Одинаковая проверка применяется независимо от места вложения: к
`typeInfo.table`, самостоятельному `table` поля и `source.table` формы.

### Границы

- Не менять XML, YAML и rules.ts.
- Не добавлять `!xml`: это обычный поддерживаемый тип, а не XML-аномалия.
- Не ослаблять проверку неизвестных значений `kind` и лишних полей.
- Не добавлять частных условий по `SettingsComposer`, форме или конфигурации.
- Использовать существующий общий вариант `DataPathTableInfo.Registered`.

### Проверки

- `Registered` со строковым `type` принимается в `typeInfo.table`.
- `Registered` принимается в самостоятельном `table` поля и в
  `source.table` формы.
- отсутствующий или нестроковый `type` отклоняется;
- лишнее поле у `Registered` отклоняется;
- неизвестный `kind` по-прежнему отклоняется;
- импорт всех 11 файлов Conversion с зарегистрированными источниками проходит
  эту пограничную проверку и продолжается до следующего независимого
  расхождения.

## Пустой DataPath как запрет на создание XML-узла

### Контекст

В двух формах справочника `ПалитраБыстрыхТоваров` конфигурации
`CashdeskDev_3_32_26_0_setup1c` исходный XML не содержит `DataPath` у таблицы
`БыстрыеТовары` и восьми её колонок. Импорт сохраняет это состояние в YAML:

```yaml
БыстрыеТовары:
  Вид: ТаблицаФормы
  ПутьКДанным: ""
  Элементы:
    БыстрыеТоварыНомерСтроки:
      Вид: ПолеНадписи
      ПутьКДанным: ""
```

Пустая строка запрещает автоматически подставлять предполагаемые пути
`Объект.БыстрыеТовары` и
`Объект.БыстрыеТовары.НомерСтроки`. При обратном преобразовании пустой путь
таблицы отключает вычисление путей её колонок. Текущая подготовка YAML удаляет
пустой путь колонки только при наличии вычисленного предполагаемого пути.
Поэтому пустая строка остаётся в данных, переданных обычному XML-сериализатору,
и превращается в лишний узел:

```xml
<DataPath/>
```

Расхождение повторяется в двух формах: по восемь лишних узлов, всего 16.

### Договор

Для любого собственного элемента формы:

```yaml
ПутьКДанным: ""
```

всегда означает отсутствие узла `DataPath` в XML. Результат не зависит от
того, удалось ли вычислить предполагаемый путь элемента:

```xml
<InputField name="БыстрыеТоварыНомерСтроки">
  <!-- DataPath отсутствует -->
</InputField>
```

Пустая строка не должна преобразовываться в `<DataPath/>`.

### Решение

При подготовке формы к YAML → XML удалять свойство `ПутьКДанным` с пустой
строкой у любого собственного элемента формы. Проверка наличия вычисленного
предполагаемого пути для этого действия не нужна. Изменяется только копия YAML,
подготовленная для XML-сериализатора; исходный YAML и контекст формы не
изменяются.

Отсутствующий ключ имеет другой смысл: действующий механизм по-прежнему может
материализовать автоматически вычисленный путь. Непустое значение по-прежнему
создаёт обычный узел `DataPath`.

### Границы

- Не добавлять частные условия для таблиц, колонок, Cashdesk или конкретных
  имён элементов.
- Не изменять правила отдельных видов полей в `rules.ts`.
- Не использовать `!xml`: XML однозначно определяется пустой строкой YAML.
- Не изменять обработку заимствованных элементов формы.
- Не превращать отсутствующий `ПутьКДанным` в пустой и не подавлять непустой
  путь.

### Проверки

- Собственный обычный элемент с `ПутьКДанным: ""` не получает `DataPath` в
  XML, даже если предполагаемый путь вычислить нельзя.
- Колонка таблицы с `ПутьКДанным: ""` не получает `DataPath`, когда путь самой
  таблицы также пуст.
- Отсутствующий путь собственного элемента по-прежнему материализуется, если
  его можно однозначно вычислить.
- Непустой путь по-прежнему экспортируется в XML.
- Существующая обработка заимствованных элементов не меняется.
- Round-trip двух форм `ПалитраБыстрыхТоваров` больше не добавляет 16 пустых
  узлов `DataPath`.

## Явно пустые параметры данных динамического списка

### Контекст

В форме списка документа `СписаниеОприходованиеТоваров` конфигурации
`CashdeskDev_3_32_26_0_setup1c` настройки динамического списка содержат явно
пустой XML-контейнер:

```xml
<ListSettings>
  <dcsset:filter>...</dcsset:filter>
  <dcsset:dataParameters/>
  <dcsset:order>...</dcsset:order>
</ListSettings>
```

Импорт `SettingsParameterValueCollection` возвращает `undefined`, когда внутри
нет ни одного `dcscor:item`. Поэтому явно пустой контейнер становится
неотличим от отсутствующего и пропадает при round-trip.

Проверка `HEAD` всех 34 конфигураций, кроме `all` и Tester, обнаружила 7 таких
узлов в 6 файлах пяти конфигураций: BMO — 2, CashdeskDev — 1, FXDVUZ — 2,
GMZ — 1, PayDesk — 1. При этом найдено 36 839 блоков `ListSettings`, поэтому
присутствие пустого `dataParameters` нельзя однозначно вывести из окружающей
структуры.

### Договор YAML

Три состояния представляются раздельно:

| YAML | XML |
|---|---|
| `ПараметрыДанных` отсутствует | `dcsset:dataParameters` отсутствует |
| `ПараметрыДанных: !xml/present` | `<dcsset:dataParameters/>` |
| `ПараметрыДанных: { ... }` | контейнер с элементами `dcscor:item` |

`!xml/present` не принимает значение. Пустой YAML-словарь `{}` не заменяет
маркер, потому что не выражает исключительный факт присутствия пустого
XML-контейнера.

### Решение

Разрешить `!xml/present` для свойства типа
`SettingsParameterValueCollection`. XML → YAML сохраняет маркер, только если
контейнер присутствует, но не содержит ни одного элемента. YAML → XML
восстанавливает пустой контейнер по маркеру. Заполненная коллекция продолжает
использовать существующее смысловое YAML-представление.

Регистрация выполняется на общем типе коллекции, без частных условий по
`DynamicList`, конфигурации или XML-пути `ListSettings`. Тег допустим в каждом
месте применения этого типа, где XML явно содержит пустой контейнер.

### Границы

- Не создавать `dcsset:dataParameters` при отсутствующем YAML-свойстве.
- Не выводить присутствие контейнера из соседних настроек или версии
  конфигурации.
- Не использовать пустой словарь как неявный синоним `!xml/present`.
- Не менять представление непустых параметров и элементов `dcscor:item`.
- Не добавлять отдельное правило для динамического списка.

### Проверки

- явно пустой XML-контейнер импортируется как `!xml/present`;
- маркер экспортируется как пустой XML-контейнер;
- отсутствующий контейнер остаётся отсутствующим;
- непустая коллекция сохраняет существующий XML ↔ YAML договор;
- тег со значением и тег другой категории отклоняются;
- round-trip всех семи найденных узлов сохраняет исходный XML.

## Общий перенос битых ссылок XML ↔ YAML

### Контекст

В XML встречаются ссылки, записанные внутренним представлением платформы вместо
обычного имени объекта. Если это представление содержит UUID, восстановить
смысловую ссылку без исходного XML нельзя.

Текущая реализация переносит такие случаи отдельными обработчиками для
`MetadataItemLinks`, `DesignTimeRef`, порядка подсистем и локальных ссылок форм.
Из-за этого новый ссылочный тип требует ещё одного частного механизма.

Текущий пример — `CashdeskDev_3_32_26_0_setup1c`. Четыре свойства
`FunctionalOptionsProperty` содержат отсутствующие функциональные опции:

- `76e70e66-9e54-4a40-95ce-cff9444899e7` в трёх формах отчётов;
- `6537a19c-3357-46a2-96a6-1fe4619ddbc8` в общей форме
  `РедактированиеСтроки`.

В `Contracts_1_0_7_2_setup1c` тот же общий договор требуется обычному свойству
типа `MetadataItemLink`: форма обработки
`ОценкаПроизводительности.АвтоматическийЭкспортЗамеровПроизводительности`
содержит внутренний UUID хранилища настроек:

```xml
<SettingsStorage>3062c54f-92ed-42c5-b62f-1c0e685cfe75</SettingsStorage>
```

Правило `ХранилищеНастроек` уже содержит `metadataTarget`, поэтому отдельный
обработчик формы или свойства не нужен. Строгая UUID-грамматика должна быть
подключена ко всему типу `MetadataItemLink`, а значение представлено так:

```yaml
ХранилищеНастроек: !xml/reference 3062c54f-92ed-42c5-b62f-1c0e685cfe75
```

Ещё один носитель — ключ события формы. В форме обработки
`НастройкиПриложения.ОтправкаSMS` два события записаны через UUID:

```xml
<Event name="047d4d09-961c-4bdc-8519-eef10674c35b">ПослеЗаписи</Event>
<Event name="c1bc0d3e-d35e-4207-a06b-ece68ed25314">ПриЗаписиНаСервере</Event>
```

Текст узла `Event` является именем функции-обработчика в модуле формы. Он не
определяет вид события. Существующий импорт ошибочно ищет известное событие по
совпадению имени функции с русским YAML-именем события. Поэтому в данном
примере UUID теряются, а обратный экспорт создаёт канонические XML-имена
`AfterWrite` и `OnWriteAtServer`.

### Цель

Сделать `!xml/reference` общим способом точного переноса известных внутренних
форм битых ссылок:

- для всех ссылочных свойств;
- для одиночных значений, элементов коллекций, вложенных значений и ключей
  YAML-словарей;
- через единое описание `metadataTarget`, используемое преобразованием,
  проверкой, поиском и переносом аномалии;
- без поиска UUID среди объектов конфигурации;
- без reference XML;
- без частных условий по конкретным свойствам в нейтральных слоях.

Для ключей `Events` тот же перенос применяется как к зарегистрированному
носителю битой ссылки без `metadataTarget`: UUID обозначает внутреннее имя
события платформы, а не объект метаданных конфигурации.

### Что считается битой ссылкой

Битая ссылка распознаётся только по строгой внутренней форме, заранее
зарегистрированной общим типом свойства. В утверждённый перечень входят:

| Тип формы | Пример |
|---|---|
| UUID | `76e70e66-9e54-4a40-95ce-cff9444899e7` |
| пара UUID `DesignTimeRef` | форма, уже поддерживаемая обработчиком `DesignTimeRef` |
| ссылка с числовым сегментом | `1:93701593-5ac8-4266-b471-7e9ed35a9c3e` |
| сегментированная ссылка формы | `1/0:<UUID>` |
| пустое имя роли `UserVisible` | `<xr:Value name="">false</xr:Value>` |

Если текст соответствует такой форме в ссылочном поле, он сразу считается
битой ссылкой. UUID:

- не ищется в индексах метаданных;
- не преобразуется в имя объекта;
- не добавляется в индекс ссылок;
- не возвращается поиском ссылок;
- не участвует в переименовании и определении затронутых файлов.

Совпадение UUID с идентификатором существующего объекта ничего не меняет: само
внутреннее UUID-представление в этом ссылочном поле является аномалией XML.

Произвольная ошибочная строка битой ссылкой не считается. Ошибка
fromXML/toYAML также не превращается в `!xml/reference` автоматически.

UUID в атрибуте `Event.name` является битой ссылкой независимо от текста
функции-обработчика. Текст обработчика не участвует в распознавании ссылки и не
используется для определения смыслового вида события.

Пустая строка является отдельной строгой внутренней формой только для ключа
роли `UserVisible`. В других ссылочных свойствах пустое значение не получает
`!xml/reference` автоматически.

В исследованных конфигурациях, кроме `all` и Tester, найдено 24 таких значения
в пяти конфигурациях: 21 со значением `false` и 3 со значением `true`. Во всех
случаях пустое имя находится внутри `UserVisible` или совместимого узла `Use`.

### Обычные ссылки

Обычная ссылка, записанная каноническим именем, сохраняет текущую обработку.
Если цель не найдена или ссылка неоднозначна, обычная проверка проекта сообщает
ошибку. `!xml/reference` в таких случаях не добавляется: исходный XML можно
однозначно восстановить из текста YAML.

Отдельно сохраняется ранее поддержанный совместимый случай `DesignTimeRef`:
уже помеченная именованная ссылка переносится обратно в тот же XML-тип. Такая
метка по-прежнему создаётся прежней зависимой проверкой `DesignTimeRef`, когда
именованная цель отсутствует. Новый общий перенос не расширяет этот случай и
сам распознаёт по форме только зарегистрированные внутренние UUID-значения.

Таким образом, общий перенос битых ссылок:

- не вводит состояния `found`, `missing` и `ambiguous`;
- не требует второго прохода импорта;
- не меняет механизм разрешения обычных ссылок;
- не создаёт таблицу соответствий UUID и имён объектов.

### Единое описание `metadataTarget`

Каждая ссылка представляется общим ссылочным вхождением. Оно содержит:

- путь от значения свойства до ссылки;
- положение ссылки: значение или ключ YAML-словаря;
- ограничение `metadataTarget`;
- чтение и изменение канонического значения;
- при необходимости строгую внутреннюю XML-форму битой ссылки.

Для простого ссылочного свойства вхождение строится из `metadataTarget` его
rules.ts. Для составного типа общий обработчик типа перечисляет вложенные
вхождения с такими же ограничениями. В частности, `UserVisible` объявляет каждый
ключ `Роли` как ссылку с `metadataTarget` на `Role`, а не использует отдельный
механизм ссылок на роли.

Одно и то же перечисление вхождений используют:

- преобразование обычных ссылок XML ↔ YAML;
- проверка существования и допустимого вида цели;
- построение структурного индекса и поиск ссылок;
- распознавание и перенос `!xml/reference`.

Поэтому `UserVisible` не получает отдельный реестр или особый путь проверки.
Различие только в положении ссылки: ключ словаря вместо обычного значения.

`metadataTarget` с `validation: "translateOnly"` сохраняет прежнюю
синтаксическую трансляцию и не участвует в проверке существования.

Новые поля не добавляются в `PropertyRule`, `BasePropertyRule` и построители
rules.ts. Грамматика внутренней ссылки и её преобразование объявляются
операциями общего типа в существующем реестре type rules.

Нейтральный runtime знает только:

- перечисленные типом ссылочные вхождения и их `metadataTarget`;
- соответствует ли значение зарегистрированной внутренней форме;
- как поставить тег и как вернуть исходное XML-представление.

Он не содержит проверок по `itemType`, XML-корням, UUID функциональных опций,
папкам форм или другим предметным деталям.

Локальные ссылки формы, для которых сейчас нет `metadataTarget`, сохраняют
зарегистрированные грамматики как ограниченную совместимость. Они используют
тот же перенос тегов, проверку содержимого и экспорт в XML, но не становятся
ссылками метаданных и не попадают в проектный индекс.

Ключи `Events` используют такую же регистрацию носителя без `metadataTarget`.
Общий конвейер знает только положение ссылки в ключе словаря и строгую
UUID-грамматику. Он не ищет событие по UUID или имени функции и не добавляет
ссылку в проектный индекс.

### Представление в YAML

Тег ставится на минимальное значение, содержащее битую ссылку.

Одиночное значение:

```yaml
ФункциональнаяОпция: !xml/reference 76e70e66-9e54-4a40-95ce-cff9444899e7
```

Элемент смешанной коллекции:

```yaml
ФункциональныеОпции:
  - ИспользоватьСкидкиНаценки
  - !xml/reference 76e70e66-9e54-4a40-95ce-cff9444899e7
```

Ссылочный ключ:

```yaml
Роли:
  !xml/reference 6537a19c-3357-46a2-96a6-1fe4619ddbc8: Истина
```

Пустое имя роли `UserVisible`:

```yaml
Роли:
  !xml/reference "": Ложь
```

Значение ключа сохраняет исходное значение `xr:Value`: `Истина` для `true` и
`Ложь` для `false`.

Битые ссылки в ключах событий:

```yaml
События:
  !xml/reference 047d4d09-961c-4bdc-8519-eef10674c35b: ПослеЗаписи
  !xml/reference c1bc0d3e-d35e-4207-a06b-ece68ed25314: ПриЗаписиНаСервере
```

Значение каждого ключа остаётся неизменным именем функции-обработчика.

Ссылочное свойство с числовым сегментом:

```yaml
ОсновнаяТаблица: !xml/reference 1:93701593-5ac8-4266-b471-7e9ed35a9c3e
```

Форма `число:UUID` распознаётся только в ссылочном вхождении с
`metadataTarget`. Числовой сегмент и UUID сохраняются дословно, поиск UUID в
индексах не выполняется.

Содержимое тега — исходное ссылочное значение, а не XML-фрагмент.

### Теги YAML-ключей

В памяти тегированный ключ остаётся обычной строкой. Сам тег хранится отдельно
в служебных отметках, связанных с объектом-контейнером и именем ключа.

Парсер YAML:

1. читает тег скалярного ключа через публичные события или AST `js-yaml`;
2. создаёт обычный строковый ключ JS-объекта;
3. сохраняет `!xml/reference` в служебных отметках контейнера;
4. сохраняет текущие координаты диагностики и порядок ключей.

Сериализатор выполняет обратное преобразование и возвращает тег скалярному
узлу ключа. Исходный код зависимости `js-yaml` не изменяется.

Копирование и пересоздание YAML-словарей переносит отметки ключей вместе с
существующими тегами значений и порядком ключей. Тег составного ключа и иной
класс XML-аномалии в месте ссылочного ключа отклоняются. Пустой ключ разрешён
только для `UserVisible`, только с `!xml/reference`; нетегированный пустой ключ
остаётся структурной ошибкой.

### XML → YAML

Для каждого ссылочного вхождения обработчик общего типа выполняет одну
проверку:

- строгая внутренняя форма распознана — сохраняет исходное значение и ставит
  `!xml/reference`;
- форма не распознана — продолжает обычный fromXML/toYAML;
- значение не является ни допустимой обычной ссылкой, ни зарегистрированной
  внутренней формой — возвращает прежнюю ошибку импорта.

Поиск цели для распознанной внутренней формы не выполняется. Дополнительный
проход по конфигурации не нужен.

Для `UserVisible` пустое имя `xr:Value` распознаётся до обычного разбора цели
метаданных, поэтому не вызывает ошибку «Некорректный формат цели метаданных».

Для `Events` UUID из `Event.name` распознаётся до обычного сопоставления
известных имён. Импорт ставит `!xml/reference` на UUID-ключ и сохраняет имя
функции значением. Поиск известного события по имени функции удаляется
полностью. Обычное известное XML-имя по-прежнему переводится в русский
YAML-ключ, а обычное неизвестное текстовое имя сохраняет прежний договор.

### YAML → XML

При экспорте:

- нетегированное значение проходит обычные fromYAML/toXML и проверку ссылки;
- `!xml/reference` передаёт исходное значение обработчику общего типа;
- обработчик проверяет строгую грамматику своего типа и восстанавливает
  соответствующую XML-форму;
- обычные и тегированные элементы смешанной структуры обрабатываются
  независимо.

Если содержимое `!xml/reference` не соответствует грамматике типа, экспорт
возвращает структурную ошибку. Нетегированный UUID в ссылочном поле также
является ошибкой: несовместимое изменение вводится сразу, без поддержки старого
неявного синтаксиса.

Тегированный UUID-ключ `Events` восстанавливается дословно в `Event.name`.
Значение ключа восстанавливается как текст узла `Event`; по нему не выполняется
обратное сопоставление с известными событиями. Нетегированный UUID-ключ события
является структурной ошибкой.

### Перенос существующих реализаций

`BrokenXMLReferenceCarrierRegistry` остаётся общим конвейером, но ссылки
метаданных он получает из единого перечисления `metadataTarget`. Сведения о
строгих внутренних формах переносятся в операции общих типов.

На общий договор переводятся:

- `MetadataItemLinks/MDObjectRef`;
- UUID в порядке подсистем CommandInterface;
- `MetadataValue/DesignTimeRef`;
- `FunctionalOptionsProperty`;
- ссылочные словари вроде `UserVisible`, если их ключи допускают внутреннюю
  форму ссылки;
- UUID-ключи `Events`.

Локальные ссылки формы сохраняют свои грамматики, но используют общую работу с
тегами значений и ключей.

## Строковое значение заполнения и ограничение длины

### Наблюдаемое расхождение

В `Contracts_1_0_7_2_setup1c` стандартный реквизит `Код` имеет
`ДлинаКода: 0`, `ДопустимаяДлинаКода: Фиксированная` и строковый
`xr:FillValue` из девяти пробелов. Действующий особый обработчик считает любую
непустую строку из пробелов неявным значением стандартного `Кода`, удаляет её
из YAML, а экспорт восстанавливает `xsi:nil`. Исходное строковое значение
теряется.

### Проверенное распределение

Исследованы зафиксированные в `HEAD` XML всех 33 конфигураций
`round-trip-compact/cf`, кроме `all` и `Tester`. Тип стандартного реквизита
определялся по декларации и свойствам владельца: `CodeType`, `NumberType` и
строковой декларации `Description`. Обычное поле включалось в выборку, если
его `Type` непосредственно содержит `xs:string`.

| Семейство | `xsi:nil` | Пустая `xs:string` | Строка из пробелов | Содержательная строка |
|---|---:|---:|---:|---:|
| Стандартные реквизиты строкового типа | 28 624 | 1 316 | 1 656 | 43 |
| Обычные поля, допускающие строку | 34 932 | 101 445 | 2 453 | 463 |

Из 139 293 обычных полей выборки 138 209 имеют единственный тип `Строка`, а
1 084 — составной тип со строковой альтернативой. Поэтому пустые XML-формы и
смысловые строковые значения должны оставаться разными договорами.

Для непустых строк из пробелов совпадение с объявленной длиной распространено,
но не является универсальным: у стандартных реквизитов при положительной
длине совпадают 1 045 значений, короче 343 и длиннее 12; ещё 256 значений
имеют объявленную длину `0`. В частности, сочетание длины `0` и девяти
пробелов встречается 186 раз в 30 конфигурациях. Исходную строку нельзя
вычислять по длине.

### Итоговый смысловой договор

Непустой `xs:string` сначала является обычным строковым значением независимо
от его содержимого: текст и строки только из пробелов проходят один путь.
Сам факт наличия пробелов и совпадение их количества с объявленной длиной не
определяют применение `!xml/value`; после этого строка проверяется по общему
ограничению длины.

```xml
<xr:FillValue xsi:type="xs:string">         </xr:FillValue>
```

```yaml
СтандартныеРеквизиты:
  Код:
    ЗначениеЗаполнения: "         "
```

Строка выводится обычным YAML-скаляром с точным сохранением всех символов.
Специальный тег для пробелов не вводится.

Ограничение длины применяется общей проверкой строкового типа:

| Ограничение строки | Допустимое значение |
|---|---|
| длина `0` | любая строка |
| переменная длина `N` | не более `N` символов |
| фиксированная длина `N` | ровно `N` символов |

Пробелы считаются обычными символами. Особая ветвь, которая безусловно считает
любую пробельную строку стандартного `Кода` неявной, удаляется. `Код`,
строковый `Номер`, `Наименование` и обычные поля используют ограничения своего
эффективного строкового типа.

Этот договор заменяет прежнее правило, по которому любая непустая пробельная
строка стандартного `Кода` считалась неявной независимо от длины.

Если строка нарушает ограничение, это несовместимое XML-значение:

```yaml
ЗначениеЗаполнения: !xml/value "       "
```

- XML → YAML сохраняет исходную строку и добавляет `!xml/value`;
- YAML без тега получает ошибку проверки длины;
- импортированный `!xml/value` является явным исключением и точно
  восстанавливает исходный `xs:string`;
- `!xml/value` на строке, которая удовлетворяет ограничению, отклоняется как
  ненужный тег.

Несовпадение числа пробелов с объявленной длиной само по себе не является
аномалией: для переменной длины более короткая строка допустима, а при длине
`0` ограничение отсутствует. Аномалией является только фактическое нарушение
описанного ограничения.

### Пустые XML-формы

Действующий договор пустых значений не меняется:

| Контекст и XML | YAML | Классификация |
|---|---|---|
| обычное поле с единственным типом `Строка`, пустой `xs:string` | поле отсутствует | каноническое пустое значение |
| такое же поле, `xsi:nil` | `ЗначениеЗаполнения: !xml/value Nil` | аномальная XML-форма |
| обычное поле составного типа, пустой `xs:string` | `ЗначениеЗаполнения: ""` | выбор строковой альтернативы |
| обычное поле составного типа, `xsi:nil` | поле отсутствует | каноническое отсутствие значения |
| строковый стандартный реквизит, `xsi:nil` | поле отсутствует | каноническое отсутствие значения |
| строковый стандартный реквизит, пустой `xs:string` | `ЗначениеЗаполнения: !xml/value String` | аномальная XML-форма |
| `xs:string` при несовместимом эффективном типе | `ЗначениеЗаполнения: !xml/value <исходная строка>` | несовместимое значение |

### Проверки

- прямой классификатор строк проверяется для длины `0`, переменной и
  фиксированной положительной длины;
- одинаковые случаи повторяются для текста и строк только из пробелов;
- стандартные `Код`, строковый `Номер` и `Наименование` получают ограничения
  из владельца без частного безусловного удаления пробелов;
- обычное и стандартное поле импортируют допустимую пробельную строку без
  тега, а недопустимую — с `!xml/value`;
- YAML → XML точно восстанавливает пробелы в обоих случаях;
- пустые `xs:string` и `xsi:nil` сохраняют ранее согласованный договор;
- round-trip Contracts сохраняет исходные девять пробелов как обычное значение
  при `ДлинаКода: 0` и переходит к следующему независимому расхождению;
- round-trip Conversion также устраняет первое расхождение строкового
  `FillValue` и переходит к следующему независимому расхождению.

## Локальное объявление пространства имён типа

### Наблюдаемое расхождение

В реквизите обработки
`ИнтерактивноеИзменениеВыгрузки.КомпоновщикОтбораВсехДокументов` исходный XML
объявляет пространство имён непосредственно на значении типа:

```xml
<v8:Type xmlns:dcsset="http://v8.1c.ru/8.1/data-composition-system/settings">
  dcsset:SettingsComposer
</v8:Type>
```

YAML содержит обычный смысловой тип:

```yaml
Тип: КомпоновщикНастроекКомпоновкиДанных
```

Экспорт восстанавливает текст `dcsset:SettingsComposer`, но без объявления
префикса:

```xml
<v8:Type>dcsset:SettingsComposer</v8:Type>
```

Корень `MetaDataObject` не объявляет `dcsset`, поэтому результат теряет
необходимый namespace и отличается от исходного XML.

### Проверенное распределение

В `HEAD` всех 33 конфигураций, кроме `all` и `Tester`, найдено 2 194 значения
`v8:Type` с префиксом `dcsset`:

| Контекст | Количество | Способ объявления `dcsset` |
|---|---:|---|
| формы | 2 122 | один раз на корне `Form`; локальных объявлений нет |
| XML прикладных объектов | 72 | локально на каждом `v8:Type` |

Исключений в исследованной выборке нет. Место объявления однозначно
восстанавливается по декларативному правилу свойства: форма использует
namespace своего XML-корня, а `TypeDescription` реквизита прикладного объекта
должен объявить `dcsset` локально.

### Декларативный договор rules.ts

Существующий параметр `declareTypeNamespaceXML` расширяется без изменения
прежней формы:

```ts
declareTypeNamespaceXML?: boolean | readonly string[]
```

- `true` сохраняет действующий смысл «объявлять локально все пространства имён
  типов»;
- список объявляет локально только перечисленные префиксы;
- `false` или отсутствие параметра сохраняет действующую политику типа.

Правило `Тип` обычного реквизита прикладного объекта получает:

```ts
type: {
  yaml: "Тип",
  xml: "Type",
  type: "TypeDescription",
  declareTypeNamespaceXML: ["dcsset"],
}
```

Общий экспорт `TypeDescription` проверяет политику отдельно для префикса
каждого создаваемого `v8:Type`. Для `dcsset` он добавляет:

```xml
xmlns:dcsset="http://v8.1c.ru/8.1/data-composition-system/settings"
```

Префикс `cfg` и остальные пространства имён список `dcsset` не затрагивает.
В нейтральных слоях не появляется условий по `itemType`, имени реквизита,
`SettingsComposer` или пути файла. YAML и договор `!xml/type` не меняются.

### Отклонённые варианты

- Добавление `xmlns:dcsset` на корень каждого `MetaDataObject` не соответствует
  исходной структуре всех 72 найденных случаев.
- Безусловное локальное объявление у каждого `dcsset:*` создаст лишние
  атрибуты в 2 122 формах.
- `!xml` не применяется: наличие namespace вычисляется из XML-контекста и
  декларации свойства.

### Проверки

- прежнее `declareTypeNamespaceXML: true` объявляет все namespace как раньше;
- список `['dcsset']` объявляет локально `dcsset`;
- тот же список не добавляет локальный `xmlns:cfg` типу `cfg:*`;
- реквизит прикладного объекта с `SettingsComposer` получает локальный
  `xmlns:dcsset`;
- тип формы остаётся без локального объявления, поскольку namespace находится
  на корне формы;
- XML → YAML → XML для
  `ИнтерактивноеИзменениеВыгрузки.КомпоновщикОтбораВсехДокументов` точно
  восстанавливает исходный `v8:Type` и переходит к следующему независимому
  расхождению.

## Обычные формы без Form.xml

### Наблюдаемое расхождение

У формы обработки
`РегистрацияИзмененийДляОбменаДанными.СообщениеОбОбычномИнтерфейсе`
исходный дескриптор содержит:

```xml
<FormType>Ordinary</FormType>
```

Тело обычной формы хранится в `Ext/Form.bin`; `Ext/Form.xml` отсутствует.
После импорта YAML не сохраняет тип формы, поэтому экспорт применяет
неявное значение `Managed`, меняет дескриптор на `<FormType>Managed</FormType>`
и создаёт лишний минимальный `Ext/Form.xml`.

Поле `НазначенияИспользования` не участвует в выборе типа формы. Оно является
отдельным свойством исходного дескриптора и сохраняется по существующим
правилам.

### Проверенное распределение

Во всех конфигурациях из исследуемой выборки, кроме `all` и `Tester`, найдено
214 обычных форм в восьми конфигурациях:

| Тело формы | Количество |
|---|---:|
| только `Form.bin` | 213 |
| без `Form.bin` и `Form.xml` | 1 |
| с `Form.xml` | 0 |

Следовательно, наличие `Form.bin` нельзя использовать как единственный
признак обычной формы, а создание `Form.xml` для неё противоречит всем
найденным примерам.

### YAML-договор

Существующее правило `formType` получает имя YAML-поля:

```ts
yaml: "ТипФормы"
```

Обычная форма записывается явно:

```yaml
ТипФормы: Обычная
НазначенияИспользования: ПлатформаИМобильноеПриложение
```

`НазначенияИспользования` показано только как соседнее существующее свойство.
Оно не требуется для определения обычной формы. Управляемая форма остаётся
неявным значением и не получает `ТипФормы` в YAML.

### Импорт и экспорт

- XML → YAML читает `<FormType>Ordinary</FormType>` через существующее
  декларативное правило и выводит `ТипФормы: Обычная`;
- YAML → XML восстанавливает `<FormType>Ordinary</FormType>`;
- для обычной формы экспорт не создаёт `Ext/Form.xml`;
- существующий внешний ресурс продолжает копировать `Ext/Form.bin` без
  разбора его содержимого;
- обычная форма без `Form.bin` также остаётся допустимой;
- управляемые формы сохраняют действующий обмен через `Ext/Form.xml`.

### Проверка несовместимого содержимого

Если у формы указано `ТипФормы: Обычная`, свойства элементов, реквизиты формы,
команды и другие данные управляемого `Form.xml` недопустимы. Проверка YAML
выдаёт ошибку вместо молчаливого удаления этих данных при экспорте.

### Отклонённые варианты

- Определять обычную форму по наличию `Form.bin`: одна найденная обычная форма
  не имеет ни одного файла тела.
- Хранить служебный признак вместо `ТипФормы`: тип формы является смысловым
  свойством метаданных и уже описан существующим `systemEnumerationRule`.
- Создавать пустой `Form.xml` для обычной формы: такого файла нет ни в одном
  из 214 исследованных случаев.

### Проверки

- Ordinary XML без `Form.xml` импортируется с `ТипФормы: Обычная`;
- обратный экспорт сохраняет `<FormType>Ordinary</FormType>` и не создаёт
  `Form.xml`;
- `Form.bin` сохраняется побайтно существующим механизмом внешних ресурсов;
- обычная форма без `Form.bin` проходит round-trip без создания тела;
- управляемая форма по-прежнему не выводит неявный `ТипФормы` и создаёт
  `Form.xml`;
- управляемые данные при `ТипФормы: Обычная` дают ошибку проверки;
- round-trip Contracts сохраняет обычную форму и переходит к следующему
  независимому расхождению.

## Пустой файл состава плана обмена

### Наблюдаемое расхождение

У плана обмена `ОбновлениеИнформационнойБазы` исходный
`Ext/Content.xml` существует, но не содержит элементов:

```xml
<ExchangePlanContent
  xmlns="http://v8.1c.ru/8.3/xcf/extrnprops"
  xmlns:xr="http://v8.1c.ru/8.3/xcf/readable"
  xmlns:xs="http://www.w3.org/2001/XMLSchema"
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  version="2.20"/>
```

Импорт сворачивает пустую коллекцию и не выводит `Состав`. Экспорт без
reference не отличает пустой существующий файл от отсутствующего и удаляет
`Content.xml`.

Свойство `exportReferenceFileOnMissingValue: true` было рассчитано на
копирование пустого файла из reference. Reference больше не является
источником содержимого XML, поэтому этот признак не обеспечивает договор
полного round-trip и не должен определять результат.

### Проверенное распределение

Во всех конфигурациях исследуемой выборки, кроме `all` и `Tester`, найдено 380
планов обмена:

| Состояние `Content.xml` | Количество |
|---|---:|
| файл содержит элементы состава | 350 |
| файл существует и пуст | 14 |
| файл отсутствует | 16 |

Наличие пустого файла не вычисляется из свойства
`РаспределеннаяИнформационнаяБаза`: среди пустых и отсутствующих файлов есть
оба значения этого свойства. Значит, три состояния должны различаться самим
YAML.

### Однозначный YAML-договор

| YAML | XML |
|---|---|
| поле `Состав` отсутствует | `Content.xml` отсутствует |
| `Состав: !xml/present` | пустой `Content.xml` |
| `Состав` содержит непустой список | `Content.xml` с соответствующими `Item` |

Пустой список `Состав: []` недопустим и даёт ошибку проверки. Он не является
синонимом `!xml/present`. Тег применяется к самому свойству без значения и
использует уже согласованную категорию явно присутствующего пустого
XML-контейнера.

### Импорт и экспорт

- XML → YAML выводит `!xml/present`, только когда файл `Content.xml`
  существует и его коллекция `Item` пуста;
- отсутствие файла не создаёт свойства `Состав`;
- непустой файл импортируется существующим списком элементов без тега;
- YAML → XML материализует канонический корень `ExchangePlanContent` для
  `!xml/present` без обращения к reference;
- отсутствие свойства не создаёт файл;
- `exportReferenceFileOnMissingValue` удаляется из правила `content`, потому
  что различие теперь полностью выражено в YAML.

### Отклонённые варианты

- `Состав: []`: не классифицирует исключительную XML-форму и смешивает её с
  обычным пустым значением коллекции.
- Всегда создавать пустой файл при отсутствии `Состав`: добавляет лишний файл
  в 16 найденных планов обмена.
- Восстанавливать файл из reference: нарушает принятые границы использования
  reference и не делает YAML самодостаточным.
- Новый тег: существующий `!xml/present` уже означает ровно присутствие
  пустого XML-контейнера.

### Проверки

- пустой `ExchangePlanContent` импортируется как `!xml/present`;
- `!xml/present` экспортирует канонический пустой `Content.xml` без reference;
- отсутствующий файл остаётся отсутствующим после round-trip;
- непустой список сохраняет существующий формат и элементы;
- `Состав: []`, значение у `!xml/present` и иной тег дают ошибку проверки;
- round-trip Contracts сохраняет исходный пустой `Content.xml` и переходит к
  следующему независимому расхождению.

## Документация после реализации

- добавить четыре случая `FunctionalOptionsProperty` CashdeskDev в
  `.agents/xml-anomalies.md`;
- уточнить в `.agents/xml-anomalies.md`, что `!xml/value` на строковом
  `FillValue` означает нарушение ограничения эффективного типа, а не сам факт
  наличия пробелов;
- добавить пустой `ExchangePlanContent` как случай `!xml/present`;
- актуализировать общее описание `!xml/reference` в действующей спецификации
  классифицированных XML-аномалий.

Изменение `.agents/architecture.md` не требуется: новый проход, индекс или
зависимость между слоями не вводятся. Если реализация всё же потребует такого
изменения, работа останавливается до отдельного согласования.

## Критерии готовности

- прямые и вложенные ссылочные свойства используют единое перечисление
  `metadataTarget`, без частных условий в нейтральных слоях;
- известные UUID-формы всегда получают `!xml/reference` и не разрешаются;
- обычные ссылки сохраняют прежнюю проверку отсутствия и неоднозначности;
- значения и ключи поддерживают единый `!xml/reference`;
- существующие обработчики ссылок используют общий договор;
- CashdeskDev точно восстанавливает четыре исходных UUID;
- Contracts точно восстанавливает UUID свойства `SettingsStorage` через общий
  тип `MetadataItemLink`;
- полный набор обязательных проверок проекта проходит.

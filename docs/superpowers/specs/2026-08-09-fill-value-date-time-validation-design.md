# Проверка даты в `ЗначениеЗаполнения`

## Контекст

Зависимая проверка `ЗначениеЗаполнения` уже сопоставляет строки, числа, булевы
значения и ссылки с эффективным типом реквизита. Тип `dateTime` пока не входит
в `FillValueEffectiveType`, поэтому каждое исследованное значение даты обычного
реквизита даёт предупреждение `проверка значения для типа dateTime не поддержана`.

Контрольный import конфигурации SED показал 75 таких предупреждений. В
сформированном YAML найдено 106 явных значений даты, и все они равны
`01.01.0001 00:00:00` — начальному значению даты 1С. Часть значений относится
к обычным реквизитам, часть — к стандартным реквизитам даты, которые пока
используют нейтральную политику `notSpecified`.

Общий `MetadataValue` уже преобразует YAML-даты во внутреннее значение
`{ type: "dateTime", value: "yyyy-MM-dd'T'HH:mm:ss" }`. `TypeDescription`
сохраняет уточнение `Date`, `Time` или `DateTime`; отсутствие уточнения означает
`DateTime`. Новое поведение должно использовать эти существующие модели, а не
вводить параллельное представление даты.

## Цель

- полноценно классифицировать дату в `ЗначениеЗаполнения` обычных реквизитов;
- учитывать уточнения типа `Дата`, `Время` и `ДатаВремя`;
- считать `01.01.0001 00:00:00` неявным значением одиночного типа даты;
- включить проверку исследованных стандартных реквизитов даты;
- удалить начальную дату из YAML при import, сохранив точный XML round-trip;
- устранить предупреждения о неподдержанном `dateTime` в контрольном import SED.

## Не входит в задачу

- изменение YAML- или XML-представления `MetadataValue`;
- изменение общего формата снимка конфигурации;
- добавление `!xml`;
- автоматическое включение проверки для любого будущего стандартного реквизита
  с `kind: "dateTime"`;
- изменение общих типов правил `BasePropertyRule`, `PropertyRule` или параметров
  построителей rules.ts;
- исправление остальных ошибок и предупреждений контрольного import SED.

## Эффективный тип даты

`FillValueAlternative` получает отдельный вариант:

```ts
{
  readonly kind: "dateTime"
  readonly dateFractions: "Date" | "Time" | "DateTime"
}
```

`effectiveTypeFromTypeDescription` преобразует внутренний тип `dateTime` в этот
вариант и переносит `dateQualifiers.dateFractions`. Если уточнение отсутствует,
используется `DateTime`, как при существующем экспорте `TypeDescription` в XML.

Для стандартного реквизита семейства `primitive` с `kind: "dateTime"` политика
`byEffectiveType` строит тот же вариант с уточнением `DateTime`. Особых ветвей
по виду прикладного объекта или имени стандартного реквизита в общем
классификаторе не появляется.

## Классификация значения

Внутреннее значение даты должно иметь `type: "dateTime"` и корректную
каноническую форму `yyyy-MM-dd'T'HH:mm:ss`. Проверка календарной корректности не
должна зависеть от часового пояса или преобразовывать год `0001` через текущее
локальное время.

Уточнения типа применяются так:

- `Date` допускает календарную дату только с временем `00:00:00`;
- `Time` допускает время только с датой `0001-01-01`;
- `DateTime` допускает обе содержательные части;
- `0001-01-01T00:00:00` является неявным значением каждого из трёх уточнений.

Значение другого вида `MetadataValue`, календарно некорректная дата или дата с
частями, запрещёнными уточнением, классифицируются как `invalid`.

Начальная дата является `implicit` только у одиночного эффективного типа даты.
Если дата является одной из ветвей составного типа, начальная дата выбирает
эту ветвь и считается содержательным значением, аналогично пустой ссылке
выбранной ветви составного ссылочного типа.

## Стандартные реквизиты

Проверка включается явной политикой
`fillValue: { policy: "byEffectiveType" }` у всех существующих деклараций
стандартных реквизитов с `kind: "dateTime"`:

| Прикладной объект | Стандартный реквизит |
|---|---|
| Документ | `Дата` |
| Бизнес-процесс | `Дата` |
| Задача | `Дата` |
| Журнал документов | `Дата` |
| План обмена | `ДатаОбмена` |
| Регистр сведений | `Период` |
| Регистр накопления | `Период` |
| Регистр бухгалтерии | `Период` |
| Регистр расчёта | `ПериодРегистрации` |
| Регистр расчёта | `НачалоПериодаДействия` |
| Регистр расчёта | `КонецПериодаДействия` |
| Регистр расчёта | `ПериодДействия` |
| Регистр расчёта | `НачалоБазовогоПериода` |
| Регистр расчёта | `КонецБазовогоПериода` |

Политика указывается в каждой декларации. Общий исполнитель не выводит её
автоматически из `kind`, поэтому неисследованные будущие декларации сохраняют
безопасное поведение `notSpecified`.

## Поведение операций

### XML → YAML import

Существующий адаптер import применяет общий классификатор после формирования
окончательного YAML:

- `valid` сохраняется;
- начальная дата с результатом `implicit` удаляется из YAML;
- `invalid` сохраняется и даёт одну предметную ошибку;
- остальные результаты обрабатываются по существующему договору проверки
  `ЗначениеЗаполнения`.

При удалении начальной даты существующий механизм снимка сохраняет исходные
`xsi:type`, текст и признаки пустой XML-формы. Новый формат снимка и отдельный
транспортный признак не нужны.

### Validation YAML-проекта

Явно записанная начальная дата одиночного типа выдаёт ошибку `поле содержит
неявное значение; удалите ЗначениеЗаполнения` по точному YAML-пути. Содержательная
совместимая дата проходит проверку. Несовместимое значение или нарушение
уточнения выдаёт одну предметную ошибку на поле и не останавливает проверку
остальных файлов.

### YAML → XML

Явное содержательное значение экспортируется существующим обработчиком
`MetadataValue.dateTime`. Если поле удалено при import, исходная XML-форма
восстанавливается из снимка. Без снимка существующие правила формируют
каноническое пустое значение. Явно заданное новое YAML-значение имеет приоритет
над снимком.

## Диагностика и отказоустойчивость

- Некорректная дата превращается в diagnostic, а не в необработанное исключение.
- На одно поле формируется не более одной локальной предметной diagnostic.
- Путь diagnostic заканчивается на `ЗначениеЗаполнения`.
- Уточнение типа входит в эффективный тип и не восстанавливается по имени
  реквизита.
- Ошибка одного значения не препятствует import остальных объектов и полной
  проверке проекта.

## Проверки

### Эффективный тип и классификатор

Расширить существующие проверки `effectiveType.test.ts` и `classify.test.ts`,
не создавая параллельный набор тестов:

- перенос каждого уточнения `Date`, `Time`, `DateTime`;
- значение по умолчанию `DateTime` без уточнения;
- содержательная корректная дата;
- начальная дата как `implicit` одиночного типа;
- начальная дата как содержательный выбор ветви составного типа;
- значение другого вида как `invalid`;
- календарно некорректное значение;
- ненулевое время для `Date`;
- содержательная дата для `Time`.

- Проверить наличие `byEffectiveType` у всех 14 перечисленных деклараций.

  содержательная дата допустима, начальная дата неявна.

- Расширить существующий import-тест представителем начальной даты: поле не

## Критерии готовности

- обычные и перечисленные стандартные реквизиты используют один общий
  классификатор даты;
- все три уточнения платформенной даты проверяются по согласованному договору;
- начальная дата удаляется только у одиночного типа и точно восстанавливается
  из снимка;
- ручной YAML получает одну diagnostic по точному пути;
- в общих metadata-слоях нет условий по `itemType` или имени реквизита;
- контрольный import SED не содержит предупреждений о неподдержанном
  `dateTime` и не скрывает остальные diagnostics.

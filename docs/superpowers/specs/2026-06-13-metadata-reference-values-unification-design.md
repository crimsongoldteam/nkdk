# Унификация ссылок, путей и значений метаданных

Дата: 2026-06-13

Статус: согласованный дизайн для ревью перед планом реализации.

Ветка: `codex/metadata-value-unification`

## Контекст

В `packages/core/metadata` есть несколько типов, которые хранят ссылки, пути,
типы и значения метаданных строками:

- `commonObjects/metadataValue`;
- `commonObjects/metadataValueCollection`, который после миграции
  переименовывается в `metadataObjectRefCollection`;
- `commonObjects/metadataPath`;
- `commonObjects/metadataRef`;
- `commonObjects/typeDescription`;
- `commonObjects/picture`;
- `commonObjects/predefined`, `predefinedItem`, `predefinedCode`;
- формовый `forms/commonObjects/dataPath`;
- смежные типы: `metadataField(s)`, `typeLink`, `fieldsList`,
  `dataCompositionSystem/dcsMetadataValue`, `ButtonParameter` и другие
  потребители строковых ссылок.

Сейчас русско-английские соответствия дублируются. Например,
`CatalogRef -> Справочник` описан в `TypeDescriptionRules`, а
`Catalog/CatalogRef -> Справочник` отдельно описан в `metadataPath`.
Из-за этого YAML, `DataPath`-валидация и JSON Schema могут расходиться.

## Согласованные решения

Массовая смена моделей допустима. Цель — не фасад поверх разрозненных строк, а
единая каноническая модель ссылок и путей метаданных.

YAML должен использовать только русские имена. Значение вида `Catalog.Товары`
в YAML не поддерживается как совместимость; валидатор должен выдавать обычную
ошибку неизвестного корня `Catalog`.

В первый дизайн входят все строковые ссылки и пути метаданных, а не только
исходный список. Это включает `MetadataField(s)`, `TypeLink`, `FieldsList`,
`DataPath`, `DcsMetadataValue` как потребителя и прочие места, где строка
фактически означает ссылку, путь или тип метаданных.

Целевая внутренняя модель хранит ссылки и пути метаданных английскими
XML-совместимыми строками. YAML остаётся только русским; XML использует формат
1С. Формовый `DataPath` остаётся отдельным видом цели со своей строковой
формой. Структурная цель существует как рабочее представление общего API при
разборе, сериализации, построении schema и проверке `validate`, но не обязана
храниться в модели постоянно.

Выбран маршрут миграции (А): сначала вводится общий реестр и пограничные
преобразователи для строк, затем потребители переводятся на единую
английскую каноническую строку по слоям, после чего лишние частные типы и
дублирующие таблицы соответствий удаляются.

Совместимость со старыми внутренними строковыми формами не сохраняется. Если
строка не совпадает с новой канонической формой модели или допустимой внешней
формой XML/YAML, она должна падать с диагностикой, а не неявно
нормализоваться.

## Канонические строки модели

Внутренняя модель хранит не полностью английские пути, а английскую грамматику
пути с реальными именами объектов из конфигурации. Имена метаданных,
реквизитов, табличных частей, измерений, ресурсов и предопределённых значений
остаются такими, как они заданы в проекте.

Для объектов метаданных каноническая строка использует XML-имя корня:

```text
Catalog.Номенклатура
Document.РеализацияТоваровУслуг
Enum.ВидыДоговоров
InformationRegister.ЦеныНоменклатуры
```

Для полей служебные сегменты обязательны и также хранятся в английской
XML-совместимой форме:

```text
Catalog.Номенклатура.Attribute.Артикул
Catalog.Номенклатура.StandardAttribute.Description
Catalog.Номенклатура.TabularSection.Товары.Attribute.Количество
Catalog.Номенклатура.TabularSection.Товары.StandardAttribute.LineNumber
InformationRegister.ЦеныНоменклатуры.Dimension.Номенклатура
InformationRegister.ЦеныНоменклатуры.Resource.Цена
```

Для значений ссылок действуют отдельные правила:

```text
Catalog.СтавкиНДС.БезНДС
Catalog.СтавкиНДС.EmptyRef
Enum.ВидыДоговоров.EnumValue.СПоставщиком
Enum.ВидыДоговоров.EmptyRef
```

`EmptyRef` в модели всегда пишется по-английски, а в YAML — как
`ПустаяСсылка`. Для значений перечислений каноническая строка модели явно
содержит сегмент `EnumValue`, хотя YAML его скрывает:
`Перечисление.ВидыДоговоров.СПоставщиком`. Для обычных предопределённых
значений справочников, документов, планов счетов и других ссылочных объектов
сегмент `PredefinedData` не является частью канонической модели.

`TypeDescription` остаётся отдельным объектом, а не простой строкой, потому что
он описывает набор допустимых типов, квалификаторы строки, числа и даты, а
также составные типы. При этом значения в его массиве типов используют тот же
общий словарь английских идентификаторов: `CatalogRef.Номенклатура`,
`CatalogObject.Номенклатура`, `EnumRef.ВидыДоговоров`, `DocumentRef.Заказ`,
`string`, `decimal`, `dateTime`, `boolean`. YAML-представление этих типов
остаётся русским: `Справочник.Номенклатура`, `Перечисление.ВидыДоговоров`,
`Строка`, `Число`.

`DataPath` не приводится к обычному `MetadataPath`, потому что это язык путей
формы: корнем может быть реквизит формы, таблица формы, динамический список,
платформенный источник или специальный платформенный путь. Каноническая строка
`DataPath` остаётся в его собственной форме, например `Объект.Количество`,
`Товары.Цена`, `Таблица.СписокЗначений` или поддержанный платформенный вариант.
Общий API участвует здесь не через замену строки, а через проектный резолвер:
когда `DataPath` проходит внутрь объекта метаданных, проверяются те же
реквизиты, стандартные реквизиты, табличные части, измерения и ресурсы.

## Оформительские значения

`Picture`, `Color`, `Font`, `Border` и `StyleItemValue` не сводятся к
`MetadataPath`: это доменные значения, у которых может быть абсолютное
значение, системное значение или ссылка на объект проекта. Для них нужен общий
механизм оформительских ссылок поверх того же проектного резолвера.

Встроенные значения платформы могут оставаться короткими русскими значениями,
если они однозначны:

```yaml
ЦветТекста: ЦветОсобогоТекста
ЦветФона: АкварельноСиний
Шрифт:
  Вид: КрупныйШрифтТекста
```

Проектные ссылки должны быть явными и начинаться с русского корня:

```yaml
ЦветТекста: ЭлементСтиля.ТекстЗапрещеннойЯчейкиЦвет
Шрифт:
  Вид: ЭлементСтиля.ОсновнойШрифт
Рамка:
  Имя: ЭлементСтиля.ОсновнаяРамка
Картинка: ОбщаяКартинка.Логотип
```

Такие ссылки проверяет `ProjectMetadataResolver`: `ЭлементСтиля.<имя>` должен
существовать и иметь подходящий тип `Цвет`, `Шрифт` или `Рамка`, а
`ОбщаяКартинка.<имя>` должна существовать как объект `CommonPicture`.

Сырые XML-префиксы не являются каноническим YAML: `style:<имя>`,
`CommonPicture.<имя>`, `StdPicture.<имя>` и похожие формы должны падать с
ошибкой неизвестного корня или недопустимой формы значения. Для встроенных
значений используется короткое русское имя, для проектных ссылок — явный
русский корень.

Внутренняя модель этих значений остаётся типизированной. Например, цвет хранит
тип источника (`Absolute`, `WebColor`, `WindowsColor`, `StyleItem`) и значение,
шрифт хранит `kind`, ссылку и параметры шрифта, рамка хранит ссылку и параметры
рамки, картинка хранит вид источника и параметры прозрачности. Строковая
канонизация применяется только к ссылочной части значения, а не заменяет весь
объект значения.

## Инвариант имён

Имена пользовательских реквизитов, платформенных стандартных реквизитов,
настраиваемых стандартных реквизитов и коллекций данных в одной области поиска
уникальны.

Для справочника это означает, что нельзя:

- создать стандартный реквизит `Наименование`, потому что он уже платформенный
  стандартный реквизит справочника;
- одновременно иметь реквизит и табличную часть с одним именем, например
  `Товары`.

Для регистров в одной области уникальны имена измерений, ресурсов, реквизитов и
соответствующих стандартных реквизитов.

Стандартные реквизиты не являются только списком запретов. Они должны входить в
тот же индекс имён, что и пользовательские элементы, с явным источником имени:
платформенный стандартный реквизит, настраиваемый стандартный реквизит или
пользовательский элемент.

Этот инвариант должен быть общим источником для:

- проверки YAML-проекта;
- разрешения `DataPath`;
- построения допустимых ссылок и путей в проектном резолвере.

Следствие для читаемых путей: YAML использует русские служебные сегменты там,
где без них теряется структура пути. Для полей каноническая форма полная:
`Справочник.Контрагенты.Реквизит.Реквизит1`,
`Справочник.Номенклатура.ТабличнаяЧасть.Товары.Реквизит.Количество`,
`РегистрСведений.Остатки.Измерение.Номенклатура`. Короткие формы без
`Реквизит`, `ТабличнаяЧасть`, `Измерение`, `Ресурс` не являются каноническими.
Это упрощает `toXML`: русские служебные сегменты напрямую переводятся в
`Attribute`, `TabularSection`, `Dimension`, `Resource` и `StandardAttribute`.

## Предопределённые значения

Предопределённые элементы входят в ту же историю ссылок, но являются не полями
объекта, а значениями ссылки. Поэтому индекс должен хранить их как отдельный
вид цели: `предопределённое значение`.

Для обычных предопределённых значений YAML использует короткий русский путь:

```text
Справочник.<имя>.<значение>
ПланВидовХарактеристик.<имя>.<значение>
ПланСчетов.<имя>.<значение>
```

XML-совместимое строковое представление для таких значений остаётся без
служебного `PredefinedData`:

```text
Catalog.<имя>.<значение>
ChartOfCharacteristicTypes.<имя>.<значение>
ChartOfAccounts.<имя>.<значение>
```

`ПустаяСсылка` — специальное предопределённое значение владельца ссылки. В YAML
оно пишется как `Справочник.<имя>.ПустаяСсылка`, а в XML-совместимой строке —
как `Catalog.<имя>.EmptyRef`.

Новая модель не должна использовать старую служебную канонизацию вида
`Catalog.<имя>.PredefinedData.<значение>`. Для значений ссылок каноническая
английская строка остаётся XML-совместимой: `Catalog.<имя>.<значение>` или
`Catalog.<имя>.EmptyRef`. При разборе общий API временно различает
`predefinedValue` и `emptyRef`, чтобы построить правильную схему и диагностику.

Короткие пути остаются только для значений ссылок: `MetadataValue` ищет
предопределённое значение или `ПустаяСсылка`. Для `MetadataField` короткая
форма не используется: поле должно быть записано с русскими служебными
сегментами, чтобы экспорт в XML не зависел от эвристик.

## Текущие наблюдения

`MetadataValueCollection` используется редко и фактически является частным
случаем массива ссылок на объекты метаданных: XML хранит `MetadataValue` с
`objectRef`, YAML хранит массив русифицированных ссылок, модель хранит
`string[]`. Целевое имя после миграции — `MetadataObjectRefCollection`.

`MetadataRef`, `MetadataField(s)` и `TypeLink` уже ходят через
`metadataPath`, но сами модели остаются строковыми. У `MetadataField` также
видны подозрительные регистрации одиночного и множественного типов через один
и тот же обработчик.

`DataPath` форм уже проверяется через `metadata/validation/dataPath`. Новая
унификация должна переиспользовать этот слой проверки и расширить его общим
реестром путей.

`Picture` связан с метаданными только частично: стандартные картинки,
общие картинки и абсолютные картинки имеют свою доменную семантику. Его нужно
учесть в общем реестре ссылок, но не сводить механически к обычному
`MetadataRef`.

`metadataPath` уже умеет преобразовывать `ПустаяСсылка` в `EmptyRef`, а обычные
предопределённые значения в YAML и XML-совместимых строках сейчас идут без
служебного сегмента `PredefinedData`. Новая модель должна сохранить эту внешнюю
форму и перенести правила в общий словарь и проектный резолвер.

## Архитектура и поток данных

Решение состоит из трех слоев.

Первый слой — статический словарь видов метаданных. Он хранит единственное
соответствие между XML/1С-именами, внутренними видами и русскими YAML-именами:
например `Catalog`, `CatalogRef` и `Справочник`. Этот слой не знает конкретный
проект.

Второй слой — общий проектный резолвер метаданных. Он работает внутри
`validate`, лениво читает YAML-файлы проекта, импортирует модели через общий
реестр `ValidationProjectSpec`, кэширует результат и строит нужные индексы
поверх загруженных объектов. Это не отдельный файл и не отдельная база, а
построенная в памяти служба для всех потребителей metadata-ссылок.

Резолвер включает объекты метаданных, реквизиты, табличные части, измерения,
ресурсы, пользовательские реквизиты, стандартные реквизиты, предопределённые
значения, специальные значения вроде `ПустаяСсылка`, общие картинки и элементы
стиля. Он проверяет уникальность имён внутри владельца и существование целей,
но не нужен для восстановления служебных сегментов полей при экспорте в XML:
эти сегменты уже присутствуют в каноническом YAML.

Третий слой — пограничные преобразователи для XML, YAML и CLI. Они переводят
вход в английскую каноническую строку модели
или сериализуют её обратно в нужный формат. Структурная цель используется
внутри этих функций как рабочий результат разбора.

Поток чтения: `fromXML` обычно нормализует XML-совместимую строку в
английскую каноническую строку модели, а `fromYAML` переводит русскую строку в
эту же каноническую форму. Затем проектный резолвер проверяет существование,
область поиска и однозначность цели.

Поток записи: `toYAML` пишет русский путь. Для полей это полный путь с
русскими служебными сегментами; для значений ссылок — короткий путь вида
`Справочник.СтавкиНДС.БезНДС` или
`Справочник.СтавкиНДС.ПустаяСсылка`. `toXML` берёт английскую каноническую
строку модели и возвращает формат, который ждут XML и 1С. `DataPath`
использует тот же проектный резолвер, но добавляет формовый контекст: реквизиты
формы, данные формы и связанные с ними метаданные.

## Предварительная целевая модель

Нужен общий модуль, который описывает:

- вид корня метаданных в канонической внутренней форме;
- русское YAML-имя корня;
- XML/1С-имя корня;
- допустимые сегменты пути;
- вид ссылки: объект, поле, значение, предопределённое значение,
  `ПустаяСсылка`, тип, путь данных формы;
- источник элемента: пользовательский, платформенный стандартный или
  настраиваемый стандартный;
- возможность проверить существование цели в YAML-проекте через общий
  проектный резолвер;
- возможность описать шаблон и ограничения для JSON Schema.

Каноническая строковая модель, рабочая структурная цель и словарь
соответствий должны быть доступны через один общий API, но это не означает
один большой файл. Лучше использовать механизм регистрации: каждый доменный
модуль регистрирует свой вклад в общий реестр, а потребители работают только
через публичные функции разбора, сериализации, построения schema-шаблона и
проверки.

В `rules.ts` должны оставаться только ограничения конкретного поля: какой вид
цели ожидается (`объект`, `поле`, `значение`, `тип`, `DataPath`), какие корни
допустимы, нужен ли ссылочный тип, доступна ли `ПустаяСсылка`, требуется ли
формовый контекст. Обнаружение ссылок для `validate` тоже должно идти через
`rules.ts`: валидатор обходит `MetadataItemRule.properties`, видит тип
свойства и вызывает типовой обработчик проверки ссылок для этого типа.

Иными словами, `rules.ts` не должен заново знать, что `Catalog` — это
`Справочник` или как сериализовать `ПустаяСсылка`. Он только говорит: «это поле
содержит значение ссылки на справочник» или «это поле содержит путь к реквизиту
формы». Общий модуль разбирает, сериализует, строит шаблон схемы и участвует в
проверке `validate`.

### Граница общего модуля и `rules.ts`

Знания делятся на три уровня.

Первый уровень — общий словарь метаданных. Он живёт централизованно и отвечает
на вопросы предметной области:

- какие существуют корни метаданных;
- как один корень называется в YAML, XML и внутренней модели;
- какие корни бывают ссылочными;
- что такое поле, значение, тип, `ПустаяСсылка`, предопределённое значение;
- как строка разбирается в структуру и как структура пишется обратно.

Второй уровень — резолвер текущего проекта. Он строится в памяти во время
`validate`, лениво читает нужные YAML-файлы, импортирует модели и отдаёт
индексы для всех потребителей ссылок. В нём находятся реальные имена проекта:
`Контрагенты`, `Товары`, `БезНДС`, стандартные реквизиты, табличные части,
измерения, ресурсы, предопределённые значения, `ЭлементСтиля.ОсновнойШрифт` и
`ОбщаяКартинка.Логотип`.

Третий уровень — ограничения конкретного поля в `rules.ts`. Правило не хранит
словарь метаданных и не перечисляет реальные имена проекта. Оно только сужает
допустимую цель для конкретного свойства. Например:

```text
Поле "ЗначениеЗаполнения":
  ожидается значение;
  допустимы ссылочные типы;
  разрешена ПустаяСсылка.

Поле "ПоляБлокировкиДанных":
  ожидаются поля владельца;
  допустимы реквизиты, стандартные реквизиты, измерения и ресурсы.

Поле формы "Данные":
  ожидается DataPath;
  нужен формовый контекст;
  допустимы только значения подходящего типа.
```

Так `rules.ts` остаётся местом настройки конкретного свойства, а не местом
описания всей платформенной грамматики ссылок.

### `metadataTarget` в `rules.ts`

Текущий `referenceScope` считается устаревшей функциональностью. Он был
добавлен как локальная подсказка для CompletionProvider и позже частично
использован синхронизацией XML для поиска ожидаемых локальных форм. Для новой
модели он слишком узкий: хранит русские `allowedTypes`, смешивает подсказки,
локальные ссылки и будущую проверку проекта, а также не описывает поля,
предопределённые значения, `ПустаяСсылка`, типы, элементы стиля и картинки.

Новые правила не должны расширять `referenceScope`. На время миграции старое
поле можно читать только как источник для переноса в `metadataTarget` и для
существующего поведения синхронизации форм. После перевода потребителей
`referenceScope` должен быть удалён.

`metadataTarget` — это внутреннее поле `rules.ts`, а не расширение JSON Schema.
Оно описывает машинные ограничения конкретного свойства на английских
идентификаторах модели. Русские YAML-имена, `pattern`, примеры и человекочитаемое
описание строит общий `metadataTargets`-API.

Поле добавляется в `BasePropertyRule`, чтобы им могли пользоваться и простые
строки, и составные типы вроде `MetadataValue`, `TypeDescription`, `DataPath`,
`Picture`, `Color`, `Font`, `Border` и списочные типы.

Предлагаемая форма:

```ts
type MetadataTargetConstraint =
  | {
      kind: "object"
      roots?: MetadataRootName[]
      scope?: "project" | "owner"
    }
  | {
      kind: "field"
      owner: "this" | "explicit"
      roots?: MetadataRootName[]
      fieldKinds?: MetadataFieldKind[]
      filters?: MetadataTargetFilterName[]
    }
  | {
      kind: "value"
      roots?: MetadataRootName[]
      valueKinds?: Array<"predefinedValue" | "enumValue" | "emptyRef">
      allowEmptyRef?: boolean
    }
  | {
      kind: "type"
      roots?: MetadataRootName[]
      typeKinds?: Array<"ref" | "object" | "primitive">
      primitives?: Array<"string" | "decimal" | "dateTime" | "boolean" | "ValueStorage">
    }
  | {
      kind: "dataPath"
      context: "form"
      allowedKinds?: readonly DataPathAllowedKind[]
      allowComposite?: boolean
    }
  | {
      kind: "localChild"
      owner: "this"
      childKind: "Form" | "Template"
    }
  | {
      kind: "styleItem"
      styleItemTypes: Array<"Color" | "Font" | "Border">
    }
  | {
      kind: "commonPicture"
    }
```

`MetadataRootName`, `MetadataFieldKind` и имена примитивов — английские
канонические идентификаторы. Например `Catalog`, `Document`, `Enum`,
`InformationRegister`, `Attribute`, `StandardAttribute`, `TabularSection`,
`Dimension`, `Resource`. В `rules.ts` не должны появляться русские корни вроде
`Справочник` или `РегистрСведений`.

Примеры правил:

```ts
// ВводитсяНаОсновании / Владельцы:
{
  type: "MetadataObjectRefCollection",
  yaml: "ВводитсяНаОсновании",
  metadataTarget: {
    kind: "object",
    roots: ["Catalog", "Document"],
    scope: "project",
  },
}

// ПоляБлокировкиДанных у регистра:
{
  type: "MetadataFields",
  yaml: "ПоляБлокировкиДанных",
  metadataTarget: {
    kind: "field",
    owner: "this",
    fieldKinds: ["Attribute", "StandardAttribute", "Dimension", "Resource"],
  },
}

// ВводПоСтроке у справочника:
{
  type: "MetadataFields",
  yaml: "ВводПоСтроке",
  metadataTarget: {
    kind: "field",
    owner: "this",
    fieldKinds: ["Attribute", "StandardAttribute"],
    filters: ["stringIndexedAttribute"],
  },
}

// ЗначениеЗаполнения:
{
  type: "MetadataValue",
  yaml: "ЗначениеЗаполнения",
  metadataTarget: {
    kind: "value",
    valueKinds: ["predefinedValue", "enumValue", "emptyRef"],
    allowEmptyRef: true,
  },
}

// Тип реквизита:
{
  type: "TypeDescription",
  yaml: "Тип",
  metadataTarget: {
    kind: "type",
    roots: ["Catalog", "Document", "Enum"],
    typeKinds: ["ref", "object", "primitive"],
    primitives: ["string", "decimal", "dateTime", "boolean"],
  },
}

// ПутьКДанным формы:
{
  type: "DataPath",
  yaml: "Данные",
  metadataTarget: {
    kind: "dataPath",
    context: "form",
    allowedKinds: ["boolean", "dateTime", "Picture"],
    allowComposite: false,
  },
}

// ОсновнаяФормаОбъекта:
{
  type: "string",
  yaml: "ОсновнаяФормаОбъекта",
  metadataTarget: {
    kind: "localChild",
    owner: "this",
    childKind: "Form",
  },
}

// Цвет, Шрифт, Рамка и Картинка:
{
  type: "Color",
  yaml: "ЦветТекста",
  metadataTarget: {
    kind: "styleItem",
    styleItemTypes: ["Color"],
  },
}

{
  type: "Picture",
  yaml: "Картинка",
  metadataTarget: {
    kind: "commonPicture",
  },
}
```

Старые `referenceScope`-формы переводятся так:

```ts
referenceScope: { target: "this", kind: "Form" }
// -> metadataTarget: { kind: "localChild", owner: "this", childKind: "Form" }

referenceScope: { target: "this", kind: "Template" }
// -> metadataTarget: { kind: "localChild", owner: "this", childKind: "Template" }

referenceScope: { target: "this", kind: "Attribute", filter: "stringIndexedAttribute" }
// -> metadataTarget: { kind: "field", owner: "this", fieldKinds: ["Attribute", "StandardAttribute"], filters: ["stringIndexedAttribute"] }

referenceScope: { target: "topLevel", allowedTypes: ["Справочник", "Документ"] }
// -> metadataTarget: { kind: "object", roots: ["Catalog", "Document"], scope: "project" }
```

Семантика `metadataTarget` одинакова для schema и `validate`. Schema получает
из него шаблон и примеры русских строк без реальных имён проекта. `validate`
использует те же ограничения, но дополнительно обращается к
`ProjectMetadataResolver` и проверяет существование конкретной цели.

### Публичный API `metadataTargets`

`metadataTargets` — чистый слой строк, словаря и шаблонов. Он не читает проект,
не знает, существует ли `Контрагенты`, и не ходит в файловую систему. Его
задача — понять форму строки, перевести её между YAML/XML/моделью и построить
информативную schema.

Минимальный API:

```ts
parseMetadataTargetFromYAML(params: {
  value: string
  constraint: MetadataTargetConstraint
}): MetadataTargetParseResult

formatMetadataTargetToYAML(params: {
  canonical: string
  constraint: MetadataTargetConstraint
}): string

parseMetadataTargetFromModel(params: {
  canonical: string
  constraint?: MetadataTargetConstraint
}): MetadataTargetParseResult

buildMetadataTargetSchema(params: {
  constraint: MetadataTargetConstraint
}): TSchema
```

`parseMetadataTargetFromYAML` принимает только русскую YAML-форму. Например
`Справочник.Контрагенты` при ограничении `{ kind: "object", roots:
["Catalog"] }` возвращает каноническую строку `Catalog.Контрагенты` и рабочую
структуру цели:

```ts
{
  canonical: "Catalog.Контрагенты",
  target: {
    kind: "object",
    root: "Catalog",
    objectName: "Контрагенты",
  },
}
```

`formatMetadataTargetToYAML` делает обратное: из `Catalog.Контрагенты` получает
`Справочник.Контрагенты`. Для поля
`Catalog.Номенклатура.TabularSection.Товары.Attribute.Количество` он вернёт
`Справочник.Номенклатура.ТабличнаяЧасть.Товары.Реквизит.Количество`.

`parseMetadataTargetFromModel` проверяет уже каноническую строку модели. Он
нужен для `toYAML`, `toXML`, `validate` и отказа от старых внутренних форм:
`Catalog.Товары.PredefinedData.БезНДС` или короткий путь поля без
`Attribute`/`TabularSection` должны возвращать обычную ошибку разбора или
неизвестного сегмента без попытки совместимого преобразования.

`buildMetadataTargetSchema` строит обычную JSON Schema: `type`, `pattern`,
`examples`, `description`. Реальные имена проекта туда не попадают. Например
для `{ kind: "value", roots: ["Catalog"], allowEmptyRef: true }` схема должна
подсказать шаблон
`Справочник.<ИмяСправочника>.<ИмяПредопределенногоЗначенияИлиПустаяСсылка>`.

Отдельные сборщики ссылок по доменам не вводятся. Для составных типов
регистрируется операция проверки ссылок в общем реестре правил типов:
`Picture` извлекает ссылку на `ОбщаяКартинка`, `Color`/`Font`/`Border` и
`StyleItemValue` извлекают ссылки на `ЭлементСтиля`, `MetadataValue` извлекает
ссылочные значения, `DcsMetadataValue` делегирует проверку вложенному значению,
а `DataPath` проверяет найденную строку с учётом формового контекста. Общий
обход правил передаёт каждому обработчику путь YAML, значение, `PropertyRule` и
`ProjectMetadataResolver`.

### Проектный резолвер

`ProjectMetadataResolver` должен стать общим механизмом чтения и проверки
ссылок на объекты проекта. Его используют все потребители, которым нужно
обратиться к другим YAML-файлам проекта:

- `MetadataPath`, `MetadataField(s)`, `MetadataRef`, `TypeLink`, `FieldsList`;
- ссылочные ветки `MetadataValue` и `MetadataObjectRefCollection`;
- `TypeDescription`, когда нужно проверить существование ссылочного типа
  конкретного объекта;
- `DataPath`, когда формовый путь проходит внутрь объекта метаданных;
- `Color`, `Font`, `Border` и `StyleItemValue`, когда значение ссылается на
  `ЭлементСтиля`;
- `Picture`, когда значение ссылается на `ОбщаяКартинка`;
- `DcsMetadataValue` и другие потребители, которые хранят те же ссылки внутри
  составных значений.

Резолвер отвечает за:

- единый реестр путей к YAML-файлам объектов проекта;
- ленивое чтение и кэширование YAML через общий `ProjectYamlCache`;
- импорт модели через `ValidationProjectSpec`;
- единые диагностические ошибки чтения, импорта и отсутствующей цели;
- проверку уникальности имён в загруженном владельце;
- построение специализированных индексов: поля владельца, предопределённые
  значения, элементы стиля по типам `Цвет`/`Шрифт`/`Рамка`, общие картинки.

Публичные операции резолвера должны быть предметными, а не файловыми:
`resolveObject`, `resolveField`, `resolvePredefinedValue`,
`resolveTypeTarget`, `resolveStyleItem`, `resolveCommonPicture`. Потребители не
должны сами вычислять путь к `Свойства.yaml`, читать файл или повторно
импортировать модель. Текущий `metadata/validation/dataPath/ownerCache` нужно
рассматривать как прототип этого слоя: его поведение по ленивому чтению,
кэшированию и построению индекса полей переносится в общий резолвер, а
`DataPath` остаётся только потребителем с дополнительным формовым контекстом.

Минимальный API резолвера:

```ts
resolveObject(params: {
  target: MetadataObjectTarget
  constraint?: MetadataTargetConstraint
}): MetadataResolveResult

resolveField(params: {
  target: MetadataFieldTarget
  owner?: MetadataObjectTarget
  constraint?: MetadataTargetConstraint
}): MetadataResolveResult

resolveValue(params: {
  target: MetadataValueTarget
  constraint?: MetadataTargetConstraint
}): MetadataResolveResult

resolveTypeTarget(params: {
  target: MetadataTypeTarget
  constraint?: MetadataTargetConstraint
}): MetadataResolveResult

resolveStyleItem(params: {
  name: string
  expectedTypes: Array<"Color" | "Font" | "Border">
}): MetadataResolveResult

resolveCommonPicture(params: {
  name: string
}): MetadataResolveResult
```

Результат резолвера должен быть единым для всех потребителей: либо `ok` с
найденной целью и полезными сведениями, либо `error`/`warning` с диагностикой.
Диагностика содержит путь YAML, исходную строку, ожидаемый вид цели,
проверяемый проектный объект и ближайший неизвестный корень, сегмент или поле.

Разделение ответственности такое:

```text
metadataTargets:
  "Справочник.Контрагенты" -> "Catalog.Контрагенты"
  знает шаблон строки, но не знает, есть ли файл проекта.

ProjectMetadataResolver:
  "Catalog.Контрагенты" -> найден / не найден
  знает файлы проекта, индексы владельца и типы элементов стиля.
```

### Механизм регистрации

Новый реестр не должен повторять форму больших агрегаторов вроде
`metadata/orchestration/property/registry.ts`. Цель — единая точка доступа, но
распределённое объявление данных.

Например:

```text
metadataTargets/core:
  типы MetadataTarget;
  registerMetadataTargetKind(...);
  parseMetadataTargetFromYAML(...);
  formatMetadataTargetToYAML(...);
  buildMetadataTargetSchema(...);

metadataTargets/catalog:
  регистрирует корень Catalog / Справочник;
  регистрирует ссылочные типы CatalogRef и CatalogObject;
  регистрирует стандартные реквизиты справочника;
  регистрирует поддержку ПустаяСсылка.

metadataTargets/enumeration:
  регистрирует корень Enum / Перечисление;
  регистрирует значения перечисления;
  регистрирует ПустаяСсылка.

metadataTargets/registers:
  регистрирует измерения, ресурсы, реквизиты и стандартные реквизиты регистров.
```

Так модель остаётся единой на уровне API и типов, но знания добавляются малыми
модулями. `rules.ts` подключается к этому через короткие ограничения поля, а не
через повторение таблиц соответствий.

Строковые преобразователи должны стать пограничными функциями:

- `fromXML`: XML-строка или XML-узел -> английская каноническая строка модели;
- `toXML`: английская каноническая строка модели -> XML-строка или XML-узел;
- `fromYAML`: русская YAML-строка -> английская каноническая строка модели;
- `toYAML`: английская каноническая строка модели -> русская YAML-строка;
- `parseMetadataTarget`: строка модели или YAML/XML-строка -> рабочая
  структурная цель для schema и `validate`.

Отдельной функции совместимости со старыми внутренними строками не вводится.
Старые служебные формы вроде `Catalog.<имя>.PredefinedData.<значение>`,
короткие пути полей без `Attribute`/`TabularSection`/`Dimension`/`Resource` и
графовые формы должны возвращать обычную ошибку разбора, неизвестного корня,
неизвестного сегмента или неизвестного поля.

## Миграция старых типов

Миграция идёт по ролям типов, а не просто по файлам.

### Целевая судьба существующих типов

`metadataPath` перестаёт быть самостоятельным владельцем таблиц соответствий и
становится частью общего API `metadataTargets`: разбор, запись, schema-шаблон,
диагностика и проверка целей идут через один механизм. Графовые формы и
частная канонизация путей из этого слоя удаляются.

`metadataRef` и `metadataField(s)` остаются как имена типов правил, потому что
они выражают разные ожидания конкретного свойства: ссылка на объект
метаданных или путь к полю. Модель при этом остаётся строкой или массивом
строк в новой английской канонической форме. Собственных правил перевода
`Catalog`/`Справочник`, `EmptyRef`/`ПустаяСсылка` и служебных сегментов у них
быть не должно.

`MetadataValue` остаётся отдельным доменным типом. Он нужен для XML-типов
`string`, `decimal`, `dateTime`, `boolean`, `ref`, `objectRef`, `typeRef`,
`valueList`, `fixedArray`, `standardPeriod` и составных значений. Унификация
затрагивает только ссылочные ветки: `ref`, `objectRef` и `typeRef` хранят
канонические строки общего формата и проверяются через общий резолвер.

`MetadataValueCollection` не считается общей коллекцией произвольных значений и
переименовывается в `MetadataObjectRefCollection`. Текущее поведение показывает,
что это список объектных ссылок: XML пишет элементы как `objectRef`, YAML хранит
массив ссылок, модель хранит `string[]`. Новое имя должно появиться и в типах,
и в имени правила `rules.ts`; старое имя может существовать только в рамках
механической миграции кода и не должно оставаться публичной концепцией.

`TypeDescription` остаётся отдельной моделью, потому что описывает допустимые
типы, набор типов и квалификаторы строки, числа и даты. Общий API отдаёт ему
словарь корней и ссылочных типов (`CatalogRef`, `CatalogObject`, `EnumRef` и
т.п.), но не заменяет сам `TypeDescription` на `MetadataPath`.

`TypeLink` остаётся объектом `{ dataPath, linkItem }`. Его строковая YAML-форма
удобна для пользователя, но внутри есть самостоятельное поле `linkItem` и
отдельная XML/DCS-форма. Поэтому общий API применяется только к `dataPath`, а
сам `TypeLink` остаётся доменным типом.

`FieldsList` остаётся списочным потребителем общего механизма, а не
механически удаляется. Он встречается в формах, внешних источниках данных и
прикладных объектах с разными XML-тегами (`Field`, `xr:Field`) и разным
контекстом проверки. В `rules.ts` для него сохраняются ограничения поля и
XML-форма списка, а проверка каждого элемента передаётся общему резолверу с
учётом контекста владельца.

`Picture`, `Color`, `Font`, `Border` и `StyleItemValue` остаются доменными
значениями оформления. Абсолютные значения, встроенные значения платформы,
параметры прозрачности, параметры шрифта и параметры рамки не превращаются в
`MetadataPath`. Через общий резолвер проверяются только проектные ссылки
внутри этих значений: `ОбщаяКартинка.<имя>` и `ЭлементСтиля.<имя>` с
ожидаемым типом элемента стиля.

`DataPath` остаётся отдельным языком путей формы. Он использует общий
`ProjectMetadataResolver`, когда путь проходит внутрь объекта метаданных, но
не становится обычным `MetadataField`: у него есть корни формы, таблицы формы,
динамические списки и платформенные варианты путей.

Миграция идёт вертикальным проходом, а не массовой заменой всех типов за один
шаг. Сначала вводится общий API ссылок и путей: разбор YAML/XML, запись
YAML/XML, построение schema-шаблона и проверка для `validate`. Затем на
пилотном наборе потребителей проверяется полный путь от YAML до validate и
обратно в XML.

Пилотный набор:

- `MetadataObjectRefCollection`, бывший `MetadataValueCollection`, потому что
  это простая коллекция объектных ссылок и сразу проверяет переименование;
- `MetadataItemLink(s)`, потому что это распространённые ссылки на объекты и
  они уже имеют разные XML-формы;
- `MetadataField(s)`, потому что они проверяют полные пути полей со служебными
  сегментами;
- один `MetadataValue` со ссылочным значением, чтобы проверить
  `predefinedValue`, `enumValue` и `EmptyRef`.

После прохождения пилота переводятся остальные потребители ссылок:

- `metadataPath`, `metadataRef`, `metadataField(s)`, `typeLink` и `fieldsList`
  перестают хранить собственные таблицы соответствий и используют общий API и
  общий проектный резолвер;
- ссылочные ветки `metadataValue` (`ref`, `objectRef`, `typeRef`) начинают
  хранить английскую каноническую строку общего формата, при этом остальные
  значения (`string`, `decimal`, `dateTime`, `boolean`, массивы) остаются в
  `MetadataValue`;
- `metadataValueCollection` переименовывается в `metadataObjectRefCollection`
  / `MetadataObjectRefCollection` и становится списком канонических объектных
  ссылок;
- `TypeDescription` использует тот же реестр корней и типов, но остаётся
  отдельным типом, потому что описывает допустимый тип значения, а не ссылку на
  конкретную цель проекта;
- `Picture`, `Color`, `Font`, `Border` и `StyleItemValue` остаются отдельными
  доменными типами значений, но ссылки внутри них на `ОбщаяКартинка` и
  `ЭлементСтиля` проходят через общий проектный резолвер;
- `DataPath` переводится последним: он использует общий проектный резолвер для
  прохода внутрь объектов метаданных, но сохраняет формовый контекст и
  существующий слой `metadata/validation/dataPath`.

После перевода потребителей удаляются лишние частные типы и дублирующие
таблицы соответствий. Кода для чтения старых внутренних строковых форм быть не
должно.

## Верификация и схема

`nkdk validate` должен проверять не только JSON Schema-форму, но и существование
ссылок и путей там, где для этого хватает проекта. Обнаружение проверяемых
ссылок идёт через обход `rules.ts` и зарегистрированные обработчики типов, а не
через отдельные сборщики по доменам.

`nkdk schema` в этой итерации должен отдавать обычную JSON Schema для YAML:
строковый тип, информативный шаблон допустимых значений, примеры и ограничения,
которые наложены на конкретное поле. Шаблон должен быть достаточно понятным для
ИИ и человека: по нему должно быть видно, где искать реальные имена в проекте
и какой смысл имеет каждый сегмент строки.

- примеры русских префиксов (`Справочник`, `Документ`, `Перечисление`);
- допустимые виды ссылки: объект, поле, значение, тип, `DataPath`;
- текстовый шаблон или `pattern` вроде
  `Справочник.<ИмяСправочника>.<ИмяЗначенияИлиПустаяСсылка>`;
- текстовый шаблон или `pattern` для полей вроде
  `Справочник.<ИмяСправочника>.ТабличнаяЧасть.<ИмяТабличнойЧасти>.Реквизит.<ИмяРеквизита>`;
- ограничения поля: ожидается объект, поле, значение, тип, только конкретные
  корни метаданных, только ссылочные типы и т.п.
- примеры корректных строк для каждого поддержанного вида цели;
- пояснение в `description`, какие сегменты являются литералами, а какие нужно
  искать в YAML-проекте.

Конкретные имена вроде `Контрагенты`, `Товары`, `БезНДС` не должны зашиваться в
общую схему, потому что они зависят от текущего YAML-проекта. Их проверяет
`nkdk validate`: команда читает проект через общий проектный резолвер и
проверяет существование цели для конкретного поля. Отдельный механизм
CLI-подсказок в этом дизайне не вводится.

Машинно-читаемые расширения схемы вроде `x-nkdk-metadataTarget` не входят в
текущую итерацию. Их можно добавить позже, когда обычных шаблонов, примеров и
`description` станет недостаточно для редакторов или ИИ. Это ограничение
относится только к выходной JSON Schema: внутреннее поле `metadataTarget` в
`rules.ts` уже нужно сейчас как единый источник ограничений для schema и
`validate`.

Для английских YAML-префиксов диагностика должна быть обычной ошибкой
неизвестного корня. Специальной подсказки про русское соответствие не нужно.

## Стратегия проверок

Проверки нужны на четырёх уровнях.

Первый уровень — маленькие тесты общего API ссылок и путей. Они должны
проверять, что YAML/XML корректно переводятся в английскую каноническую строку
модели, что из неё строится рабочая структурная цель, и что эта строка
записывается обратно в YAML/XML. Обязательные случаи: `ПустаяСсылка`,
предопределённые значения, обычные поля, стандартные реквизиты, измерения,
ресурсы и регистры.

Второй уровень — тесты JSON Schema. Для каждого поля схема должна содержать
информативный шаблон строки, допустимые русские корни, вид ожидаемой цели и
ограничения поля в обычных средствах JSON Schema: `type`, `pattern`,
`examples`, `description`. Реальные имена проекта в схему не попадают.

Третий уровень — тесты `validate` на маленьких YAML-проектах. Нужны проверки:

- существующая ссылка проходит;
- английский YAML-префикс падает как неизвестный корень;
- конфликт имён падает с указанием конфликтующих источников;
- стандартный реквизит учитывается как занятое имя;
- предопределённое значение и `ПустаяСсылка` проверяются как значения ссылки;
- `DataPath` проверяется с учётом формового контекста;
- ссылки на `ЭлементСтиля` проверяются с учётом типа ожидаемого значения:
  `Цвет`, `Шрифт` или `Рамка`;
- ссылки на `ОбщаяКартинка` проверяются через тот же проектный резолвер, что и
  остальные metadata-ссылки.

Четвёртый уровень — существующие XML/YAML round-trip тесты. Они подтверждают,
что внешний XML и русский YAML не изменились случайно во время миграции.

Отдельные тесты нужны на отказ от старых форм: старый формат на границе должен
падать как обычная ошибка разбора или неизвестного сегмента. Обязательные случаи:
`PredefinedData` в значении ссылки, короткий путь поля без служебных сегментов,
английский корень в YAML и графовая форма пути.

## Связанные ограничения проекта

Существующие XML-фикстуры остаются источником истины и не изменяются без
явного решения.

Перед изменениями в `packages/core/metadata/**` обязательны правила из
`.agents/knowledge/metadata/INDEX.md`, особенно `sources-of-truth.md`,
`yaml-contract.md` и `round-trip-cycle.md`.

Перед закрытием реализации нужен полный `pnpm test` из корня worktree.

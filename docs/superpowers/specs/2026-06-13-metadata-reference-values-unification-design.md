# Унификация ссылок, путей и значений метаданных

Дата: 2026-06-13

Статус: согласованный дизайн для ревью перед планом реализации.

Ветка: `codex/metadata-value-unification`

## Контекст

В `packages/core/metadata` есть несколько типов, которые хранят ссылки, пути,
типы и значения метаданных строками:

- `commonObjects/metadataValue`;
- `commonObjects/metadataValueCollection`;
- `commonObjects/metadataPath`;
- `commonObjects/metadataRef`;
- `commonObjects/typeDescription`;
- `commonObjects/picture`;
- `commonObjects/predefined`, `predefinedItem`, `predefinedCode`;
- формовый `forms/commonObjects/dataPath`;
- смежные типы: `metadataField(s)`, `typeLink`, `fieldsList`,
  `dataCompositionSystem/dcsMetadataValue`, `ButtonParameter` и другие
  потребители строковых ссылок.

Сейчас русско-английские соответствия дублируются. Например,
`CatalogRef -> Справочник` описан в `TypeDescriptionRules`, а
`Catalog/CatalogRef -> Справочник` отдельно описан в `metadataPath`.
Из-за этого YAML, `DataPath`-валидация и JSON Schema могут расходиться.

## Согласованные решения

Массовая смена моделей допустима. Цель — не фасад поверх старых строк, а
каноническая структурная модель ссылок и путей метаданных.

YAML должен использовать только русские имена. Значение вида `Catalog.Товары`
в YAML не поддерживается как совместимость; валидатор должен выдавать ошибку и
подсказку с русским вариантом вроде `Справочник.Товары`.

В первый дизайн входят все строковые ссылки и пути метаданных, а не только
исходный список. Это включает `MetadataField(s)`, `TypeLink`, `FieldsList`,
`DataPath`, `DcsMetadataValue` как потребителя и прочие места, где строка
фактически означает ссылку, путь или тип метаданных.

Целевая внутренняя модель — структурная. Строки остаются на XML, YAML и CLI
границах. На время миграции допустим переходник, который принимает старые
строки от существующих потребителей и сразу переводит их в структуру.

Выбран маршрут миграции (А): сначала вводится общий структурный реестр и
пограничные преобразователи для старых строк, затем потребители переводятся на
структуру по слоям, после чего лишние частные типы и дублирующие таблицы
соответствий удаляются.

## Инвариант имён

Имена пользовательских реквизитов, платформенных стандартных реквизитов,
настраиваемых стандартных реквизитов и коллекций данных в одной области поиска
уникальны.

Для справочника это означает, что нельзя:

- создать стандартный реквизит `Наименование`, потому что он уже платформенный
  стандартный реквизит справочника;
- одновременно иметь реквизит и табличную часть с одним именем, например
  `Товары`.

Для регистров в одной области уникальны имена измерений, ресурсов, реквизитов и
соответствующих стандартных реквизитов.

Стандартные реквизиты не являются только списком запретов. Они должны входить в
тот же индекс имён, что и пользовательские элементы, с явным источником имени:
платформенный стандартный реквизит, настраиваемый стандартный реквизит или
пользовательский элемент.

Этот инвариант должен быть общим источником для:

- проверки YAML-проекта;
- разрешения `DataPath`;
- построения допустимых ссылок и путей.

Следствие для читаемых путей: пользовательский путь не должен включать
служебные группы вроде `Реквизиты`, если имя однозначно разрешается в области
владельца. Правильная форма: `Справочник.Контрагенты.Реквизит1`, а не
`Справочник.Контрагенты.Реквизиты.Реквизит1`.

## Предопределённые значения

Предопределённые элементы входят в ту же историю ссылок, но являются не полями
объекта, а значениями ссылки. Поэтому индекс должен хранить их как отдельный
вид цели: `предопределённое значение`.

Для обычных предопределённых значений YAML использует короткий русский путь:

```text
Справочник.<имя>.<значение>
ПланВидовХарактеристик.<имя>.<значение>
ПланСчетов.<имя>.<значение>
```

XML-совместимое строковое представление для таких значений остаётся без
служебного `PredefinedData`:

```text
Catalog.<имя>.<значение>
ChartOfCharacteristicTypes.<имя>.<значение>
ChartOfAccounts.<имя>.<значение>
```

`ПустаяСсылка` — специальное предопределённое значение владельца ссылки. В YAML
оно пишется как `Справочник.<имя>.ПустаяСсылка`, а в XML-совместимой строке —
как `Catalog.<имя>.EmptyRef`.

Новая модель не должна использовать старую служебную канонизацию вида
`Catalog.<имя>.PredefinedData.<значение>`. Вместо этого структурная ссылка
хранит `kind: predefinedValue` или `kind: emptyRef`, а нужная строковая форма
создаётся только на XML/YAML/CLI-границе.

Разрешение короткого пути должно учитывать ожидаемый вид цели. Например,
`MetadataValue` ищет значение ссылки: предопределённое значение или
`ПустаяСсылка`; `MetadataField` ищет поле: реквизит, стандартный реквизит,
измерение, ресурс или табличную часть. Если ожидаемый вид цели неизвестен,
индекс должен уметь вернуть диагностическую неоднозначность.

## Текущие наблюдения

`MetadataValueCollection` используется редко и выглядит как частный случай
массива ссылок на объекты метаданных: XML хранит `MetadataValue` с
`objectRef`, YAML хранит массив русифицированных ссылок, модель хранит
`string[]`.

`MetadataRef`, `MetadataField(s)` и `TypeLink` уже ходят через
`metadataPath`, но сами модели остаются строковыми. У `MetadataField` также
видны подозрительные регистрации одиночного и множественного типов через один
и тот же обработчик.

`DataPath` форм уже проверяется через `metadata/validation/dataPath`. Новая
унификация должна переиспользовать этот слой проверки и расширить его общим
реестром путей.

`Picture` связан с метаданными только частично: стандартные картинки,
общие картинки и абсолютные картинки имеют свою доменную семантику. Его нужно
учесть в общем реестре ссылок, но не сводить механически к обычному
`MetadataRef`.

`metadataPath` уже умеет преобразовывать `ПустаяСсылка` в `EmptyRef`, а обычные
предопределённые значения в YAML и XML-совместимых строках сейчас идут без
служебного сегмента `PredefinedData`. Новая модель должна сохранить эту внешнюю
форму и перенести правила в общий словарь и проектный индекс.

## Архитектура и поток данных

Решение состоит из трех слоев.

Первый слой — статический словарь видов метаданных. Он хранит единственное
соответствие между XML/1С-именами, внутренними видами и русскими YAML-именами:
например `Catalog`, `CatalogRef` и `Справочник`. Этот слой не знает конкретный
проект.

Второй слой — проектный индекс имён. Он строится по модели проекта и включает
объекты метаданных, реквизиты, табличные части, измерения, ресурсы,
пользовательские реквизиты, стандартные реквизиты, предопределённые значения и
специальные значения вроде `ПустаяСсылка`. Индекс проверяет уникальность имён
внутри владельца и разрешает короткие пользовательские пути вида
`Справочник.Контрагенты.Товары`. Это не отдельный файл и не отдельная база, а
построенная в памяти структура для `validate` и преобразователей.

Третий слой — пограничные преобразователи для XML, YAML, CLI и старых
внутренних строк. Они разбирают строку в структурную ссылку или сериализуют
структурную ссылку обратно в нужный формат.

Поток чтения: `fromXML` или `fromYAML` разбирает входную строку в структурную
ссылку, затем проектный индекс проверяет существование, область поиска и
однозначность цели.

Поток записи: `toYAML` всегда пишет русский путь, а `toXML` возвращает формат,
который ждут XML и 1С. `DataPath` использует тот же проектный индекс, но
добавляет формовый контекст: реквизиты формы, данные формы и связанные с ними
метаданные.

## Предварительная целевая модель

Нужен общий модуль, который описывает:

- вид корня метаданных в канонической внутренней форме;
- русское YAML-имя корня;
- XML/1С-имя корня;
- допустимые сегменты пути;
- вид ссылки: объект, поле, значение, предопределённое значение,
  `ПустаяСсылка`, тип, путь данных формы;
- источник элемента: пользовательский, платформенный стандартный или
  настраиваемый стандартный;
- возможность проверить существование цели в YAML-проекте;
- возможность описать шаблон и ограничения для JSON Schema.

Сама структурная модель и словарь соответствий должны быть доступны через один
общий API, но это не означает один большой файл. Лучше использовать механизм
регистрации: каждый доменный модуль регистрирует свой вклад в общий реестр, а
потребители работают только через публичные функции разбора, сериализации,
построения schema-шаблона и проверки.

В `rules.ts` должны оставаться только ограничения конкретного поля: какой вид
цели ожидается (`объект`, `поле`, `значение`, `тип`, `DataPath`), какие корни
допустимы, нужен ли ссылочный тип, доступна ли `ПустаяСсылка`, требуется ли
формовый контекст.

Иными словами, `rules.ts` не должен заново знать, что `Catalog` — это
`Справочник` или как сериализовать `ПустаяСсылка`. Он только говорит: «это поле
содержит значение ссылки на справочник» или «это поле содержит путь к реквизиту
формы». Общий модуль разбирает, сериализует, строит шаблон схемы и участвует в
проверке `validate`.

### Граница общего модуля и `rules.ts`

Знания делятся на три уровня.

Первый уровень — общий словарь метаданных. Он живёт централизованно и отвечает
на вопросы предметной области:

- какие существуют корни метаданных;
- как один корень называется в YAML, XML и внутренней модели;
- какие корни бывают ссылочными;
- что такое поле, значение, тип, `ПустаяСсылка`, предопределённое значение;
- как строка разбирается в структуру и как структура пишется обратно.

Второй уровень — индекс текущего проекта. Он строится в памяти во время
`validate` из уже прочитанной YAML-модели проекта. В нём находятся реальные
имена проекта: `Контрагенты`, `Товары`, `БезНДС`, стандартные реквизиты,
табличные части, измерения, ресурсы и предопределённые значения.

Третий уровень — ограничения конкретного поля в `rules.ts`. Правило не хранит
словарь метаданных и не перечисляет реальные имена проекта. Оно только сужает
допустимую цель для конкретного свойства. Например:

```text
Поле "ЗначениеЗаполнения":
  ожидается значение;
  допустимы ссылочные типы;
  разрешена ПустаяСсылка.

Поле "ПоляБлокировкиДанных":
  ожидаются поля владельца;
  допустимы реквизиты, стандартные реквизиты, измерения и ресурсы.

Поле формы "Данные":
  ожидается DataPath;
  нужен формовый контекст;
  допустимы только значения подходящего типа.
```

Так `rules.ts` остаётся местом настройки конкретного свойства, а не местом
описания всей платформенной грамматики ссылок.

### Механизм регистрации

Новый реестр не должен повторять форму больших агрегаторов вроде
`metadata/orchestration/property/registry.ts`. Цель — единая точка доступа, но
распределённое объявление данных.

Например:

```text
metadataTargets/core:
  типы MetadataTarget;
  registerMetadataTargetKind(...);
  parseMetadataTargetFromYAML(...);
  formatMetadataTargetToYAML(...);
  buildMetadataTargetSchema(...);

metadataTargets/catalog:
  регистрирует корень Catalog / Справочник;
  регистрирует ссылочные типы CatalogRef и CatalogObject;
  регистрирует стандартные реквизиты справочника;
  регистрирует поддержку ПустаяСсылка.

metadataTargets/enumeration:
  регистрирует корень Enum / Перечисление;
  регистрирует значения перечисления;
  регистрирует ПустаяСсылка.

metadataTargets/registers:
  регистрирует измерения, ресурсы, реквизиты и стандартные реквизиты регистров.
```

Так модель остаётся единой на уровне API и типов, но знания добавляются малыми
модулями. `rules.ts` подключается к этому через короткие ограничения поля, а не
через повторение таблиц соответствий.

Строковые преобразователи должны стать пограничными функциями:

- `fromXML`: XML-строка или XML-узел -> структурная ссылка;
- `toXML`: структурная ссылка -> XML-строка или XML-узел;
- `fromYAML`: русская YAML-строка -> структурная ссылка;
- `toYAML`: структурная ссылка -> русская YAML-строка;
- `fromLegacyInternalString`: старый внутренний формат -> структурная ссылка,
  только как переходный адаптер.

## Миграция старых типов

Миграция идёт по ролям типов, а не просто по файлам.

Сначала вводится общий API ссылок и путей: разбор YAML/XML, запись YAML/XML,
построение schema-шаблона и проверка для `validate`. На этом этапе старые типы
остаются на месте и становятся тонкими переходниками к общему API.

Затем переводятся потребители ссылок:

- `metadataPath`, `metadataRef`, `metadataField(s)`, `typeLink` и `fieldsList`
  перестают хранить собственные таблицы соответствий и используют общий API;
- ссылочные ветки `metadataValue` (`ref`, `objectRef`, `typeRef`) начинают
  хранить структурную цель, при этом остальные значения (`string`, `decimal`,
  `dateTime`, `boolean`, массивы) остаются в `MetadataValue`;
- `metadataValueCollection` становится массивом структурных ссылок и после
  миграции может исчезнуть как отдельная концепция, если не останется
  самостоятельного поведения;
- `TypeDescription` использует тот же реестр корней и типов, но остаётся
  отдельным типом, потому что описывает допустимый тип значения, а не ссылку на
  конкретную цель проекта;
- `Picture` остаётся отдельным доменным типом, но ссылка на общую картинку
  проекта внутри него проходит через общий механизм;
- `DataPath` переводится последним: он использует общий индекс имён, но требует
  формовый контекст и существующий слой `metadata/validation/dataPath`.

После перевода потребителей удаляются лишние частные типы, дублирующие таблицы
соответствий и переходники старых внутренних строк.

## Верификация и схема

`nkdk validate` должен проверять не только JSON Schema-форму, но и существование
ссылок и путей там, где для этого хватает проекта.

`nkdk schema` должен отдавать общую схему YAML: шаблон допустимых строк и
ограничения, которые наложены на конкретное поле. Этот шаблон должен быть
достаточно информативным для ИИ и редакторов: по нему должно быть понятно, где
искать реальные имена в проекте и какой смысл имеет каждый сегмент строки.

- примеры русских префиксов (`Справочник`, `Документ`, `Перечисление`);
- допустимые виды ссылки: объект, поле, значение, тип, `DataPath`;
- машинно-читаемый шаблон вроде
  `Справочник.<ИмяСправочника>.<ИмяЗначенияИлиПустаяСсылка>`;
- ограничения поля: ожидается объект, поле, значение, тип, только конкретные
  корни метаданных, только ссылочные типы и т.п.
- примеры корректных строк для каждого поддержанного вида цели;
- указание, какие сегменты являются литералами, а какие нужно искать в
  YAML-проекте.

Конкретные имена вроде `Контрагенты`, `Товары`, `БезНДС` не должны зашиваться в
общую схему, потому что они зависят от текущего YAML-проекта. Их проверяет
`nkdk validate`: команда читает проект, строит индекс имён в памяти и проверяет
существование цели для конкретного поля. Отдельный механизм CLI-подсказок в
этом дизайне не вводится.

Для английских YAML-префиксов диагностика должна быть ошибкой с предложением
русского соответствия, если оно однозначно.

## Стратегия проверок

Проверки нужны на четырёх уровнях.

Первый уровень — маленькие тесты общего API ссылок и путей. Они должны
проверять, что одна структурная цель корректно читается из YAML/XML и
записывается обратно. Обязательные случаи: `ПустаяСсылка`, предопределённые
значения, обычные поля, стандартные реквизиты, измерения, ресурсы и регистры.

Второй уровень — тесты JSON Schema. Для каждого поля схема должна содержать
информативный шаблон строки, допустимые русские корни, вид ожидаемой цели и
ограничения поля. Реальные имена проекта в схему не попадают.

Третий уровень — тесты `validate` на маленьких YAML-проектах. Нужны проверки:

- существующая ссылка проходит;
- английский YAML-префикс падает с русской подсказкой;
- конфликт имён падает с указанием конфликтующих источников;
- стандартный реквизит учитывается как занятое имя;
- предопределённое значение и `ПустаяСсылка` проверяются как значения ссылки;
- `DataPath` проверяется с учётом формового контекста.

Четвёртый уровень — существующие XML/YAML round-trip тесты. Они подтверждают,
что внешний XML и русский YAML не изменились случайно во время миграции.

Пока старые строки ещё принимаются переходниками, их нужно покрыть отдельными
тестами: переходник принимает старый формат на границе и возвращает структурную
цель, но дальше по модели строка не распространяется.

## Связанные ограничения проекта

Существующие XML-фикстуры остаются источником истины и не изменяются без
явного решения.

Перед изменениями в `packages/core/metadata/**` обязательны правила из
`.agents/knowledge/metadata/INDEX.md`, особенно `sources-of-truth.md`,
`yaml-contract.md` и `round-trip-cycle.md`.

Перед закрытием реализации нужен полный `pnpm test` из корня worktree.

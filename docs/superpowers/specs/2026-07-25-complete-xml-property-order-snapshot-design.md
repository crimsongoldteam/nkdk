# Полный порядок XML-свойств в снимке конфигурации

## Контекст

Полный round-trip XML → YAML → XML меняет положение технических
reference-only узлов. Например, исходный объект имеет порядок:

```text
InternalInfo
Properties
ChildObjects
```

При импорте снимок конфигурации сохраняет порядок только свойств,
участвующих в YAML:

```text
name, synonym, ..., resources
```

Ключ `internalInfo` отсутствует. При экспорте известные снимку свойства
считаются закреплёнными, а неизвестный `internalInfo` добавляется после них.
Результирующий XML получает порядок:

```text
Properties
ChildObjects
InternalInfo
```

Снимок должен хранить полный порядок всех распознанных свойств физического
XML-узла независимо от их участия в YAML.

## Цели

- Сохранять исходный порядок обычных и reference-only XML-свойств.
- Не добавлять технические свойства в пользовательский YAML.
- Восстанавливать относительный порядок существовавших XML-свойств.
- Вставлять новые свойства по декларативному порядку `rules.ts`.
- Не добавлять в общую оркестрацию знания об `InternalInfo` или конкретных
  типах метаданных.
- Устранить во всём `cf/all` расхождения, вызванные неполным порядком
  распознанных XML-свойств.

## Не входит в задачу

- Сохранение UUID и других значений внутри `InternalInfo`.
- Сохранение явно пустых XML-значений.
- Сохранение неизвестных `rules.ts` XML-узлов.
- Изменение пользовательского YAML-договора.

## Представление в снимке

Формат снимка не расширяется. Полный порядок сохраняется в существующем поле
`ConfigurationXmlNode.order`.

Список содержит канонические ключи свойств из `rules.ts`, а не исходные имена
XML-тегов. Соответствие альтернативных XML-имён каноническим ключам
продолжает храниться существующим механизмом `aliases`.

Пример:

```text
internalInfo, uuid, name, synonym, ..., resources
```

Атрибуты и элементы могут присутствовать в одном списке свойств, но XML-
экспорт по-прежнему отвечает за их корректное физическое представление.

## Наблюдение порядка при XML → YAML

План преобразования в YAML и план наблюдения порядка имеют разные задачи:

- план преобразования определяет, какие значения должны попасть в YAML;
- план наблюдения сопоставляет фактически встреченные XML-узлы всем
  распознанным свойствам соответствующего `rules.ts`.

Reference-only свойство участвует в плане наблюдения, даже когда оно
исключено из YAML-преобразования. Наблюдение порядка не запускает для него
YAML-конвертацию и не меняет YAML-результат.

Для одного физического XML-узла формируется один полный список. Если
оркестрация представляет этот узел несколькими частичными источниками,
наблюдения сначала объединяются в исходной XML-последовательности, а затем
однократно записываются в частичный снимок. Частичные источники не записывают
конкурирующие неполные списки по одному логическому адресу.

Неизвестные XML-узлы не включаются в `order` и продолжают обрабатываться
существующей диагностикой импорта.

## Применение порядка при YAML → XML

Экспорт получает канонический порядок из объединённого снимка и применяет
его один раз.

Свойства, присутствующие в снимке, сохраняют взаимный порядок. Свойство,
которого не было в исходном XML, считается новым и вставляется относительно
соседей по декларативному порядку `rules.ts`. Добавление нового свойства не
переставляет существовавшие свойства.

Если снимка для нового объекта нет, весь порядок определяется `rules.ts`.
Существующее правило контейнеров `InternalInfo → Properties → ChildObjects`
остаётся порядком по умолчанию для такого объекта.

## Границы модулей

- Общая оркестрация строит план наблюдения и управляет единственной записью
  порядка физического XML-узла.
- `rules.ts` остаётся источником соответствия XML-структуры каноническим
  ключам и порядка новых свойств.
- Сборщик снимка только сохраняет и проверяет переданный список.
- Читатель снимка только возвращает список экспорту.
- Конкретные объекты метаданных и `InternalInfo` не получают специального
  кода для порядка.

## Ошибки и конфликты

- Разные полные списки порядка по одному логическому адресу считаются
  конфликтом снимка.
- Несколько частичных источников одного физического узла должны быть
  объединены до обращения к сборщику; их наличие само по себе не является
  конфликтом.
- Неоднозначное соответствие XML-узла нескольким свойствам `rules.ts`
  остаётся ошибкой плана импорта.
- Отсутствие снимка допустимо для нового объекта и приводит к порядку из
  `rules.ts`.

## Тестирование

- Модульный тест импорта проверяет, что reference-only свойство попадает в
  `ConfigurationXmlNode.order`, но отсутствует в YAML.
- Модульный тест проверяет порядок
  `InternalInfo → Properties → ChildObjects`.
- Тест нескольких частичных источников проверяет один объединённый порядок
  без конфликта сборщика.
- Модульный тест экспорта проверяет сохранение относительного порядка
  существующих свойств.
- Тест нового свойства проверяет вставку по `rules.ts` без перестановки
  существующих свойств.
- Интеграционный тест полного sync проверяет передачу порядка через
  объединённый снимок.
- Полный `pnpm test` остаётся обязательной итоговой проверкой.
- Round-trip на `cf/all` подтверждает отсутствие diff, вызванных неполным
  порядком распознанных XML-свойств; UUID и пустые значения оцениваются
  отдельно.

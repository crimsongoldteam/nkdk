# Устранение оставшихся ошибок ERP XML-import

## Статус

Согласованный дизайн устранения четырёх причин, которые останавливают импорт
`/Users/nikita/git/round-trip-compact/cf/erp` после исправления привязки raw
для команд формы. До этой работы импорт завершается с 14 ошибками:

- 10 ошибок отрицательных ID элементов формы;
- 2 ошибки виртуальной таблицы задачи `TasksByExecutive`;
- 1 ошибка XML-аннотации вне YAML-дерева при импорте команд формы;
- 1 конфликт `logicalAddress` у повторных дополнительных колонок.

## Цель

Импортировать ERP без этих ошибок, сохранив точный XML-договор каждого вида
формы и не добавляя частных условий в нейтральные слои runtime.

После успешного импорта полный ERP round-trip должен продолжиться до сравнения
XML. Новые расхождения round-trip, не относящиеся к четырём причинам выше, не
входят в эту работу и разбираются по результату следующего запуска.

## Основные решения

### Отрицательные ID элементов формы

Отрицательный ID сам по себе допустим. В ERP встречаются обычные элементы,
созданные платформой 1С, например `Дата` с `id="-4"` или `id="-6"`,
`СписокДата` с `id="-66"`, а также их `ContextMenu` и `ExtendedTooltip`.
Эти значения должны храниться в configuration index и точно
восстанавливаться при YAML → XML.

Назначение ID различает два договора:

1. **Индексный ID** принадлежит обычному элементу, реквизиту, команде или
   параметру. Значение из import snapshot или reference XML принимается, если
   оно является целым XML-ID, в том числе отрицательным. При отсутствии
   сохранённого значения NKDK по-прежнему создаёт только положительный ID.
2. **Постоянный ID правила** не является состоянием проекта. Формовый
   `AutoCommandBar` всегда получает `-1` из `directId` и не читает и не пишет
   `xmlId` в configuration index.

`AutoCommandBar` таблицы не имеет постоянного ID: его обычный положительный ID
остаётся индексным. Наличие `directId` является достаточным признаком, поэтому
общий singleton-механизм не знает имя или `itemType` командной панели.

При экспорте приоритеты не смешиваются:

- элемент с `directId` получает постоянное значение правила;
- обычный элемент получает ID из snapshot, затем из reference XML;
- при отсутствии обоих источников создаётся новый положительный ID.

Проверка повторных ID в одном XML-контейнере сохраняется. Запрет любого
отрицательного значения удаляется: корректность определяется происхождением
ID, а не его знаком.

### Виртуальная таблица задач по исполнителю

Общий словарь виртуальных таблиц получает симметричное отображение:

```text
TasksByExecutive ↔ ЗадачиПоИсполнителю
```

Правила прикладных таблиц объявляют `TasksByExecutive` для корня `Task` так же,
как `Points` объявляется для `BusinessProcess`. Поэтому строка

```text
Task.ЗадачаИсполнителя.TasksByExecutive
```

преобразуется в YAML как

```text
Задача.ЗадачаИсполнителя.ЗадачиПоИсполнителю
```

и восстанавливается обратно. Договор применяется к `MainTable` динамического
списка и к общей проверке путей таблиц, без условий по имени задачи или формы.

### Представление команды формы

YAML использует одно смысловое значение:

```yaml
ОтображениеКнопки: КартинкаИТекст
```

XML-значение зависит от владельца свойства. Исследование всего каталога
`/Users/nikita/git/round-trip-compact/cf` дало следующую матрицу:

| XML-значение | Непосредственный родитель | Количество |
|---|---|---:|
| `TextPicture` | `Command` | 157 101 |
| `PictureAndText` | `Button` | 21 924 |
| `PictureAndText` | `Popup` | 10 690 |
| `PictureAndText` | `Properties` | 1 116 |

Следовательно, `TextPicture` не является глобальным псевдонимом
`ButtonRepresentation`. Для `FormCommand` вводится собственный декларативный
тип системного перечисления с теми же YAML-значениями, но с XML-значением
`TextPicture` для `КартинкаИТекст`. `Button`, `Popup` и metadata-команды
продолжают использовать существующий `ButtonRepresentation` и
`PictureAndText`.

Импорт работает на исходных `XmlElementNode`. Клонирование `Command` или его
дочернего `Representation` для подмены compatibility-значения удаляется:
клон не принадлежит исходному audit-сеансу и переводит всю коллекцию
`Commands` в raw-кандидат. После перехода на точное перечисление аннотации
неизвестных языков, например `tr`, остаются привязаны к итоговым значениям
`Заголовок` и `Подсказка`, а не к отброшенной попытке импорта.

### Известные повторные дополнительные колонки ERP

В форме

```text
Catalogs/СпособыОтраженияРасходовПоАмортизацииМСФО/
Forms/ФормаСписка/Ext/Form.xml
```

таблица `Список.Способы` содержит пять одинаковых по смыслу колонок
`Реквизит1` с ID `1`–`5`. Это уже зарегистрированная точечная XML-аномалия
ERP. Канонический YAML хранит только первую колонку:

```yaml
ДополнительныеКолонки:
  Список.Способы:
    Реквизит1:
      Тип: Строка
```

Импорт распознаёт точную комбинацию известного XML-пути, таблицы, имени и пяти
одинаковых колонок до записи identities:

- первая колонка проходит обычный смысловой импорт и сохраняет `xmlId="1"`;
- остальные четыре не создают YAML-ключей и записей configuration index;
- их XML-узлы отмечаются audit как покрытые известной аномалией, поэтому не
  становятся unknown или raw;
- любое другое количество, имя, таблица или путь не сворачивается этим
  правилом и проходит общий механизм повторных ключей.

При YAML → XML существующее специальное правило восстанавливает пять колонок
с ID `1`–`5`. Новое применение `!xml` не вводится. Конфликт
`logicalAddress ...Колонка.Реквизит1` исчезает, потому что identities второй и
последующих известных копий не записываются.

## Границы модулей

- `@nkdk/runtime` различает индексную identity и существующий `directId` в
  общих singleton- и ID-механизмах, не зная `AutoCommandBar` или ERP.
- `@nkdk/runtime` содержит общий словарь имён metadata roots и виртуальных
  таблиц, включая симметричное имя `TasksByExecutive`.
- `@nkdk/rules` объявляет виртуальную таблицу для `Task`, точное перечисление
  `FormCommand` и известную аномалию дополнительных колонок.
- Нейтральные `validation`, `project`, `projectState` и
  `resourceTopology/core` не получают условий по `itemType`, XML-путям или
  именам ERP.

Новые поля в `BasePropertyRule`, `PropertyRule` и параметрах общих построителей
правил не добавляются. Используются существующие `directId`, отдельный тип
системного перечисления и предметный обработчик известных аномалий формы.

## Проверка

Реализация выполняется по TDD; существующие XML-фикстуры не изменяются.

### ID формы

- тест `assignFormXmlIds` сначала падает на отрицательном ID из snapshot, затем
  подтверждает его точное сохранение;
- отдельный случай подтверждает отрицательный ID из reference XML;
- новый элемент без snapshot/reference получает положительный ID;
- формовый `AutoCommandBar` получает `-1`, даже если index отсутствует, и не
  публикует identity;
- `AutoCommandBar` таблицы продолжает читать и публиковать обычный индексный
  ID;
- повторный ID в одном контейнере остаётся ошибкой.

### Виртуальная таблица задачи

- точные литералы проверяют оба направления
  `TasksByExecutive ↔ ЗадачиПоИсполнителю`;
- декларации таблиц задачи содержат виртуальную таблицу;
- `MainTable` из двух ERP-форм импортируется и экспортируется без диагностики
  неизвестного корня.

### Команды формы

- `FormCommand` преобразует `TextPicture ↔ КартинкаИТекст`;
- `Button` и `Popup` сохраняют договор
  `PictureAndText ↔ КартинкаИТекст`;
- импорт выполняется на исходном audit-узле и не создаёт raw-кандидат для
  `Commands`;
- форма с незарегистрированным языком сохраняет аннотацию внутри итогового
  YAML-дерева;
- XML → YAML → XML восстанавливает исходное `TextPicture`.

### Повторные дополнительные колонки

- точная ERP-группа из пяти `Реквизит1` даёт одну YAML-колонку и одну identity;
- audit не оставляет четыре известные копии неизвестными;
- обратный экспорт восстанавливает пять колонок и ID `1`–`5`;
- соседний путь, другое имя или другое количество не активирует исключение.

### Итоговая проверка

1. Запустить целевые тесты каждого договора в цикле red-green-refactor.
2. Выполнить `pnpm type-check`.
3. Выполнить `pnpm test` вне песочницы.
4. Выполнить `pnpm duplicates -- --base <базовый-коммит>` после каждого
   законченного слоя и перед завершением.
5. Выполнить `pnpm test:architecture:rules` и `pnpm test:architecture`.
6. Повторить `round-trip-yaml` для
   `/Users/nikita/git/round-trip-compact/cf/erp`.
7. Убедиться, что 14 описанных ошибок отсутствуют; новые round-trip
   расхождения зафиксировать отдельно.

## Вне границ решения

- изменение исходного ERP XML;
- хранение четырёх избыточных `Реквизит1` в YAML или configuration index;
- глобальное преобразование `TextPicture` для всех `ButtonRepresentation`;
- разрешение отрицательных ID, явно заданных новым публичным полем YAML;
- перечисление конкретных форм или значений `-4`, `-6`, `-66` в правилах;
- новые применения `!xml`;
- исправление round-trip расхождений, которые проявятся только после успешного
  импорта.

## Документация архитектуры

`.agents/architecture.md` не изменяется. Спецификация уточняет предметные
правила и уже существующий договор configuration index, не меняя границы
операций, направленность зависимостей или состав общих metadata-слоёв.

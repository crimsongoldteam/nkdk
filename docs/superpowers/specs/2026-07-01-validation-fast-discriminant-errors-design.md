# Быстрые ошибки discriminantKey в validation

## Контекст

Полная validation YAML-проекта уже распараллелена и читает каждый YAML-файл один раз в первом проходе. После этого заметная часть времени остается в структурной проверке схемы.

Профиль `/Users/nikita/git/nkdk-yaml` показал, что дорогим является не быстрый `schema.Check`, а генерация подробных ошибок TypeBox через `schema.Errors` на невалидных формах. Особенно дорогие случаи связаны с формами и вложенными `anyOf`, которые помечены нашим `discriminantKey: "Вид"`.

Сейчас путь такой:

1. `validateParsedFile` вызывает `schema.Check(parsed.data)`.
2. Если файл невалиден, вызывается `schema.Errors(parsed.data)` по всей корневой схеме.
3. Только после этого `typeboxErrorsToDiagnostics` вызывает `expandDiscriminatedUnionErrors`.
4. `expandDiscriminatedUnionErrors` раскрывает `Union`-ошибку по `Вид`, выбирает ветку и повторно получает ошибки уже по выбранной ветке.

То есть нужная ветка выбирается слишком поздно: сначала TypeBox успевает пройти по большой union-схеме и собрать дорогую обобщенную ошибку.

## Цель

Уменьшить время генерации schema-диагностик для невалидных форм, не меняя формат YAML Schema для подсказчика и не уменьшая полноту диагностик.

## Ограничения

- Сохраняем быстрый `schema.Check` для валидных файлов.
- Сохраняем полный список schema-ошибок.
- Не меняем JSON Schema, которую получает `schema` CLI и подсказчик.
- Не добавляем новый внешний валидатор в основной путь.
- При любом неподдержанном случае возвращаемся к старому TypeBox-пути.
- Общий validation-слой не должен знать конкретные виды metadata-объектов, папки или itemType.

## Решение

Добавить быстрый сборщик ошибок для схем с `discriminantKey`.

После неуспешного `schema.Check` `validateParsedFile` сначала попробует новый путь:

1. Передать compiled schema, `parsed.data` и `ParsedYaml` в быстрый сборщик.
2. Быстрый сборщик идет по JSON Schema и данным.
3. Для обычных узлов он может делегировать TypeBox текущей схемы.
4. Если встречает union-схему с `discriminantKey`, он читает значение discriminator-поля из YAML-данных.
5. Если значение найдено и соответствует ветке, сборщик запускает `Errors` только для выбранной ветки.
6. Если значение неизвестно или отсутствует, сборщик строит такую же targeted diagnostic, как текущий `expandDiscriminatedUnionErrors`.
7. Если быстрый сборщик не может безопасно обработать схему, он возвращает статус fallback, и `validateParsedFile` использует текущую связку `schema.Errors` + `typeboxErrorsToDiagnostics`.

Быстрый путь должен жить рядом с текущим `discriminatedUnionErrors.ts`, потому что это тот же смысловой слой: преобразование грубых TypeBox union-ошибок в точные ошибки по discriminator.

## Поведение

Для пользователя diagnostics должны остаться совместимыми:

- известный `Вид` внутри union дает ошибки выбранной ветки, без `Expected union value`;
- неизвестный `Вид` дает targeted diagnostic по полю `Вид`;
- отсутствующий или нестроковый `Вид` дает текущий текст с `не задано`;
- вложенные discriminant union сохраняют полный JSON Pointer path;
- ошибки дополнительных свойств остаются привязанными к ключу YAML;
- порядок и дедупликация диагностик остаются на существующем уровне validation.

## Fallback

Fallback включается, если быстрый сборщик встречает схему, для которой нельзя гарантировать тот же результат:

- union без `discriminantKey`;
- branch без уникального `const` по discriminator-полю;
- `$ref`, который не удалось разрешить через references compiled schema;
- unsupported keyword, который влияет на выбор или полноту ошибок;
- любая внутренняя ошибка быстрого сборщика.

Fallback должен быть прозрачным: диагностики строятся старым кодом.

## Тестирование

Нужны тесты на поведение и на то, что быстрый путь реально обходится без полного `schema.Errors` по union:

- существующие тесты `validateFile` для discriminant union должны остаться зелеными;
- добавить тест, где быстрый путь раскрывает вложенный `discriminantKey` и не возвращает `Expected union value`;
- добавить тест неизвестного/отсутствующего `Вид`;
- добавить тест fallback для обычного union без `discriminantKey`;
- добавить spy/счетчик, подтверждающий, что на поддержанном discriminant union не вызывается `Errors` корневой union-схемы;
- добавить выборочный performance guard без жестких секунд: например, счетчик количества вызовов branch/full errors.

## Проверка на реальном проекте

После реализации:

1. Запустить focused validation tests.
2. Запустить `pnpm --filter @nakidka/core type-check`.
3. Запустить полный `pnpm test`.
4. Сравнить время validation `/Users/nikita/git/nkdk-yaml` с текущей базой.

Текущая база для сравнения:

- CLI full validation: около 70 секунд real time на `/Users/nikita/git/nkdk-yaml`;
- API `concurrency=4`: около 80 секунд;
- выборка 2 000 файлов: `schema.Check` около 3.3 секунды, `schema.Errors` около 24.6 секунды.

Ожидаемый эффект должен быть заметен в проектах с большим числом schema-ошибок в формах. На полностью валидных проектах эффект будет небольшим, потому что `schema.Errors` почти не вызывается.

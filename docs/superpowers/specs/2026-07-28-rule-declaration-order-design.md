# Declaration Order as the XML Property Order

## Цель

Сделать порядок объявления свойств в `MetadataItemRule.properties` единственным договором порядка
свойств при XML-экспорте. Удалить числовое поле `BasePropertyRule.order` и перестать сохранять в снимке
конфигурации порядок свойств объектов, описанных через `rules.ts`.

Порядок элементов коллекций, интерфейсов и других специальных структур в эту задачу не входит. Их
существующие записи `ConfigurationXmlNode.order` сохраняются.

## Исходные данные

Временный анализатор обработал конфигурации `acc`, `all`, `clean`, `doc`, `erp`, `small` и `trade`:

- 164 571 XML-файл;
- 114 340 заданий импорта;
- 148 662 наблюдения порядка;
- 52 фактически использованных правила;
- 0 пропущенных наблюдений;
- 0 противоположных пар;
- 0 циклов.

Разные полные последовательности одного правила объясняются отсутствием необязательных свойств.
Относительный порядок совместно присутствующих свойств во всех наблюдениях согласован.

## Договор порядка

Для каждого правила каноническим является порядок ключей:

```ts
Object.keys(rule.properties)
```

XML-экспорт обрабатывает свойства в этой последовательности. Порядок референса, объектный `order` из
снимка, алфавитная сортировка XML-имён и числовой `PropertyRule.order` больше не меняют эту
последовательность.

Свойство, которого не было в референсе, при первом экспорте сразу занимает место, заданное
`rule.properties`. Оно не добавляется временно в конец, поэтому повторная синхронизация не перемещает
его.

Порядок YAML остаётся независимым. `sortYamlRuleProperties` продолжает помещать `Заголовок` и
`Синоним` первыми, затем `Вид`, `Тип`, а остальные YAML-ключи сортирует по имени.

## Построение канонического порядка

Из каждого наблюдения строятся ограничения `A → B` для всех пар совместно присутствующих свойств.
Ограничения объединяются отдельно для конкретного экспортированного правила.

Перед автоматическим изменением worker сопоставляет runtime-объект правила с экспортом `rules.ts`
внутри того же процесса. Объектная идентичность имеет приоритет над структурным отпечатком. Запасное
объединение только по `itemType` запрещено, поскольку несколько правил одного типа могут требовать
разных изменений.

Каноническая последовательность получается устойчивой топологической сортировкой:

1. наблюдаемые ограничения обязательны;
2. прежний порядок объявления разрешает несвязанные вершины;
3. существующие числовые `order` используются только как дополнительная подсказка при равенстве;
4. свойства, не встретившиеся в XML, сохраняют прежний относительный порядок.

После вычисления свойства физически переставляются в исходном коде. Числовые `order` удаляются.

## Композиция правил

`rules.ts` содержит простые объектные литералы, spread-композиции и ссылки на общие фрагменты.
Переписывание должно учитывать итоговый runtime-объект, а не только ближайший литерал `properties`.

Инструмент может изменить исходный фрагмент только когда способен однозначно связать каждый итоговый
ключ с его объявлением и доказать требуемый порядок после повторной загрузки модуля. Он может:

- переставлять соседние объявления свойств в объектном литерале;
- переставлять целые явные группы относительно spread, если это не меняет состав и значения объекта;
- рекурсивно упорядочивать общий фрагмент, если новый порядок совместим со всеми потребителями.

Инструмент не разворачивает spread копированием и не дублирует общие правила. Неоднозначная композиция,
вычисляемый ключ, повторное перекрытие ключа или несовместимые требования потребителей останавливают
преобразование с диагностикой до записи файлов.

## Разделение порядка и присутствия

Сейчас `ConfigurationXmlNode.order` одновременно задаёт последовательность и служит косвенным
доказательством присутствия свойства:

```ts
node.present?.includes(propertyKey) || node.order?.includes(propertyKey)
```

После изменения эти обязанности разделяются:

- порядок объекта определяется только `rules.ts`;
- каждое фактически найденное свойство объекта явно добавляется в `ConfigurationXmlNode.present`;
- `present` трактуется как множество и сериализуется канонически, без семантики последовательности;
- `aliases`, `xsi:nil`, явная пустота, XML-текст, namespace и другие индивидуальные факты сохраняются
  без изменений.

Это необходимо для свойств, которые явно присутствуют в XML, но отсутствуют в YAML из-за
`implicitValueYAML`, XML-значения по умолчанию или `preserveFromReferenceXML`. Без отдельного
`present` обратная синхронизация могла бы ошибочно считать тег отсутствующим.

`configurationIndexPresenceFromOrder` удаляется вместе с объектной ролью `order`. Проверки
присутствия используют только `present` и специализированные XML-value факты.

## Изменения XML-импорта

Общий обход `MetadataItemRule`:

- сохраняет `present` для каждого ключа, реально найденного в соответствующем XML-узле;
- сохраняет alias и XML-value факты как раньше;
- не вызывает `ConfigurationIndexCollector.setOrder`;
- продолжает передавать наблюдения временному анализатору до завершения миграции.

Специальные обработчики коллекций и интерфейсов продолжают вызывать `setOrder`. Формат снимка и
кодирование `ConfigurationXmlNode.order` поэтому пока не удаляются.

## Изменения XML-экспорта

Общий экспорт `MetadataItemRule`:

- строит план обхода в порядке объявления `properties`;
- сохраняет допустимую группировку `xmlParents` и порядок XML-контейнеров, заданный первым свойством
  соответствующей группы;
- не читает объектный порядок через `getConfigurationIndexPropertyOrder`;
- не копирует объектный порядок в новый снимок;
- определяет существование свойства только через `present`, reference XML и индивидуальные XML-value
  факты.

Общие функции чтения `ConfigurationXmlNode.order` остаются для специальных потребителей. Частные
профили расширений и BaseForm должны отличать специальный порядок структуры от присутствия обычного
свойства и использовать `present` для последнего.

## Безопасность автоматического изменения

Перестановка выполняется как транзакция:

1. построить каталог и ограничения;
2. вычислить все желаемые изменения в памяти;
3. проверить точное сопоставление правил и исходных объявлений;
4. применить изменения;
5. повторно загрузить изменённые правила;
6. проверить итоговый порядок каждого runtime-правила;
7. проверить все исходные наблюдения;
8. только после успеха оставить изменения в worktree.

При ошибке до шага 4 файлы не меняются. При ошибке после шага 4 инструмент восстанавливает только
собственные изменения из сохранённых исходных текстов, не затрагивая посторонние изменения worktree.

## Проверка

Модульные тесты должны доказать:

- порядок XML следует порядку объявления, а не XML-имени;
- порядок референса и объектный порядок снимка не переопределяют `rules.ts`;
- новое свойство сразу вставляется в каноническое место;
- YAML по-прежнему сортируется независимо;
- каждое найденное XML-свойство записывается в `present`;
- отсутствие объектного `order` не меняет явные значения по умолчанию, implicit-значения и
  `preserveFromReferenceXML`;
- специальные порядки коллекций продолжают round-trip через снимок;
- spread-композиции переписываются только при доказуемом результате;
- неоднозначное сопоставление прекращает изменение без частичного результата.

Проверка миграции должна подтвердить:

- все 148 662 наблюдения являются подпоследовательностями новых порядков правил;
- в общем обходе `MetadataItemRule` отсутствуют чтение, копирование и запись объектного `order`;
- в кодовой базе отсутствуют `BasePropertyRule.order` и числовые `order` свойств;
- `pnpm test` проходит;
- полный XML round-trip семи конфигураций не создаёт расхождений порядка;
- исходные XML-фикстуры и `/Users/nikita/git/round-trip/cf` не изменены.

## Не входит в задачу

- удаление `ConfigurationXmlNode.order` из бинарного формата снимка;
- изменение порядка элементов коллекций;
- изменение порядка интерфейсов, событий, команд и других специальных структур;
- изменение сортировки YAML;
- ручное исправление XML-источников.

## Критерии завершения

- Порядок объявления `MetadataItemRule.properties` является единственным договором порядка обычных
  XML-свойств.
- Все используемые правила физически упорядочены по доказанным ограничениям.
- Числовой `PropertyRule.order` удалён.
- Обычные объектные порядки больше не сохраняются в снимке.
- Присутствие свойств сохраняется явно и не зависит от `order`.
- Специальные порядки вне границ задачи продолжают работать.
- Полный набор тестов и внешний round-trip проходят без ошибок.

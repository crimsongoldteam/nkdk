# Explicit XML Property Order in rules.ts

## Цель

Перенести порядок обычных XML-свойств из снимка конфигурации в конкретные объекты
`MetadataItemRule` и описывать его единым полем `xmlOrder`. Удалить числовой
`BasePropertyRule.order`, не смешивать порядок полей объекта с порядком элементов коллекции и
сохранить явный факт присутствия XML-свойства через `ConfigurationXmlNode.present`.

## Почему недостаточно порядка `properties`

Для простого объектного литерала порядок `Object.keys(rule.properties)` мог бы быть договором
XML-экспорта. Однако rules.ts переиспользуют общие словари свойств через spread. Общие и собственные
свойства конкретного объекта не всегда образуют отдельные непрерывные группы.

Например, `UsualGroupRules` добавляет `formGroupCommonProperties` одним spread, а реальный XML требует
последовательность:

```text
Title                 — общее свойство FormGroup
VerticalStretch       — общее свойство FormGroup
Group                 — собственное свойство UsualGroup
ShowTitle             — собственное свойство UsualGroup
ExtendedTooltip       — общее свойство FormGroup
```

Такой порядок нельзя выразить перестановкой цельного spread. Разворачивать общие словари во всех
конкретных правилах означало бы многократно перечислять одни и те же определения. Поэтому состав
свойств и порядок XML описываются независимо:

- `properties` хранит определения и может использовать spread;
- `xmlOrder` хранит порядок полей конкретного XML-объекта.

## Границы порядка

`xmlOrder` задаёт только порядок полей внутри одного объекта. Он не задаёт порядок элементов
коллекции.

Например:

- позиция свойства `childItems` среди других свойств объекта может входить в `xmlOrder`;
- последовательность конкретных элементов внутри `childItems` остаётся данными и сохраняется в YAML
  или существующем специальном снимке;
- `formGroupCommonProperties`, `formFieldCommonProperties` и другие словари определений не получают
  `xmlOrder`, поскольку не являются самостоятельными правилами объектов;
- объект, используемый как элемент коллекции, может иметь собственный `xmlOrder` для своих внутренних
  полей.

Порядок YAML остаётся независимым. `sortYamlRuleProperties` продолжает применять существующие правила
для `Заголовок`, `Синоним`, `Вид`, `Тип` и остальных YAML-ключей.

## Договор `MetadataItemRule`

Общий тип получает необязательное поле:

```ts
export interface MetadataItemRule {
  xmlOrder?: readonly string[]
  properties: Record<string, PropertyRule>
  // остальные поля
}
```

В конкретном правиле:

```ts
export const UsualGroupRules = {
  itemType: "UsualGroup",
  xmlOrder: [
    "name",
    "title",
    "verticalStretch",
    "group",
    "showTitle",
    "extendedTooltip",
  ],
  properties: {
    // Собственные определения и общие spread остаются без дублирования.
  },
} as const satisfies ElementRule
```

Поле добавляется каждому конкретному правилу, для которого порядок был собран из XML. Если правило не
встретилось ни в одной исходной конфигурации, инструмент не выдумывает `xmlOrder`, а включает правило
в отдельную диагностику.

`xmlOrder` содержит только ключи, встреченные в XML. Свойства, не вошедшие в список, экспортируются
после перечисленных ключей в порядке объявления в `properties`. Поэтому новое или ранее не
наблюдавшееся свойство получает предсказуемое место в конце без изменения снимка.

При построении runtime-плана считаются ошибкой:

- неизвестный ключ, отсутствующий в `rule.properties`;
- повтор ключа;
- попытка записать в `xmlOrder` имя элемента коллекции вместо ключа свойства правила.

Свойство правила, содержащее коллекцию, например `childItems`, является обычным допустимым ключом
`xmlOrder`.

## Runtime-порядок и производительность

Для каждого object identity правила один раз строится итоговая последовательность:

1. существующие ключи из `xmlOrder`;
2. остальные ключи `properties` в порядке объявления.

Результат и множество перечисленных ключей кэшируются в `WeakMap<MetadataItemRule, ...>`. Последующие
экспорты не сортируют свойства, не читают reference order и не выполняют повторный поиск через
`Array.includes`. Они только линейно фильтруют уже подготовленную последовательность по `tag`,
`runtimeOnly`, `syncExternalOnly` и `filePath`.

Таким образом, подготовка выполняется один раз за O(n) на правило, а каждый экспорт остаётся O(n), как
и необходимый обход свойств. Это особенно важно для часто встречающихся элементов форм. Кэш опирается
на существующий договор: зарегистрированные объекты правил после загрузки не изменяются.

## Построение `xmlOrder`

Для каждого точного правила из наблюдения добавляются ограничения `A → B` для всех совместно
присутствующих пар свойств. Ограничения всех конфигураций объединяются в один ориентированный граф.

Канонический порядок строится устойчивой топологической сортировкой:

1. все наблюдаемые ограничения обязательны;
2. при нескольких допустимых следующих ключах используется прежний порядок объявления;
3. свойства, ни разу не встреченные в XML, в `xmlOrder` не включаются.

Результат обязан содержать каждое наблюдение как подпоследовательность. Противоположная пара, цикл,
неизвестный ключ или неоднозначное сопоставление правила прекращают миграцию до записи файлов.

## Запись rules.ts

Временный инструмент обновляет или добавляет `xmlOrder` в конкретном объекте правила. Он не
переставляет определения в `properties`, не разворачивает spread и не дублирует общие словари.

Путь к изменяемому объекту берётся из точного каталога rules.ts и поддерживает:

- экспортированный объект правила;
- локальную переменную, на которую ссылается экспорт;
- вложенный статический `itemRule`;
- динамически зарегистрированное правило с точным экспортом.

Из каждого `PropertyRule` удаляется прежний числовой `order`. Само поле
`BasePropertyRule.order` удаляется после успешной миграции всех правил.

Изменение выполняется транзакционно:

1. собрать все наблюдения и диагностики;
2. вычислить все `xmlOrder` и изменения исходников в памяти;
3. проверить неизменность исходных файлов;
4. записать изменения;
5. повторно загрузить правила;
6. проверить `xmlOrder` и все наблюдения;
7. при ошибке восстановить только записанные инструментом файлы.

## Разделение порядка и присутствия

Обычный объектный порядок больше не читается и не записывается через
`ConfigurationXmlNode.order`. Каждое свойство, реально найденное в XML, явно добавляется в
`ConfigurationXmlNode.present`.

Это сохраняет различие между отсутствующим тегом и явно записанным значением по умолчанию, даже если
свойство не попало в YAML из-за `implicitValueYAML`, `preserveFromReferenceXML` или другого правила
преобразования.

Проверка присутствия использует `present` и специализированные XML-value факты. Поле
`configurationIndexPresenceFromOrder` удаляется.

`ConfigurationXmlNode.order` остаётся в формате снимка для специальных структур, где порядок является
данными: коллекций, интерфейсов и других зарегистрированных потребителей. Этот порядок не участвует в
сортировке полей обычного `MetadataItemRule`.

## XML-экспорт

Общий экспорт:

- получает кэшированный итоговый порядок правила;
- применяет существующие фильтры свойства;
- сохраняет группировку `xmlParents`;
- не читает порядок из reference XML или снимка конфигурации;
- не копирует обычный объектный порядок в новый снимок.

Первое свойство каждой группы `xmlParents` определяет позицию XML-контейнера в итоговой
последовательности. Порядок элементов внутри коллекционных значений обрабатывается соответствующим
типом свойства и не меняется этим механизмом.

## Проверка

Модульные тесты должны доказать:

- `xmlOrder` перемешивает общие и собственные свойства `UsualGroupRules` без разворачивания spread;
- вложенный импорт формы создаёт наблюдение для точного `UsualGroupRules`;
- неизвестные и повторные ключи отклоняются;
- свойства вне `xmlOrder` добавляются в конец в порядке объявления;
- итоговый порядок кэшируется по identity правила;
- reference XML и обычный порядок снимка не переопределяют `xmlOrder`;
- каждое найденное XML-свойство записывается в `present`;
- YAML-сортировка и порядок элементов коллекций не изменяются;
- ошибка анализа или записи не оставляет частичных изменений.

Итоговая проверка должна подтвердить:

- все семь конфигураций обработаны;
- отсутствуют несопоставленные наблюдения, конфликты и циклы;
- каждое наблюдение является подпоследовательностью `xmlOrder`;
- правила без наблюдений явно перечислены в отчёте;
- в `PropertyRule` отсутствуют числовые `order`;
- `pnpm test` проходит;
- XML round-trip семи конфигураций не создаёт расхождений порядка;
- исходные XML-файлы не изменены.

## Не входит в задачу

- изменение порядка элементов коллекций в YAML;
- удаление специальных `ConfigurationXmlNode.order`;
- изменение сортировки YAML;
- изменение XML-источников;
- разворачивание общих spread в конкретных rules.ts.

## Критерии завершения

- Все наблюдавшиеся конкретные rules.ts имеют проверенный `xmlOrder`.
- Элементы форм участвуют в анализе наравне с другими объектами.
- XML-export использует единый кэшированный механизм `xmlOrder` с дополнением неизвестных свойств в
  конце.
- Числовой `PropertyRule.order` удалён.
- Обычный объектный порядок отсутствует в новых снимках, а присутствие хранится через `present`.
- Порядок элементов коллекций и другие специальные порядки продолжают работать независимо.
- Полный набор тестов и внешний round-trip проходят без ошибок.

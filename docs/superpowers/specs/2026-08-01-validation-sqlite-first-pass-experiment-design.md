# Эксперимент записи первого прохода validation в SQLite

## Цель

Проверить на `/Users/nikita/git/nkdk-yaml`, допустима ли по времени и памяти
потоковая запись индекса первого прохода validation в SQLite `:memory:`.

Гипотеза: дополнительная передача и запись фактического результата первого
прохода увеличивает его wall-clock не более чем на 10% относительно текущего
compiled standalone validation.

## Границы

- Каждый запуск начинает с пустой базы и считает все файлы изменёнными.
- Эксперимент не загружает SQLite с диска и не создаёт backup.
- Хэши и инкрементальное сравнение файлов не реализуются.
- Второй проход продолжает использовать текущий индекс и должен вернуть те же
  diagnostics.
- Эксперимент не меняет MCP-договор и включается только переменной окружения
  `NKDK_VALIDATION_SQLITE_EXPERIMENT=1`.
- Эксперимент проверяет накладные расходы записи, но не доказывает скорость
  будущих SQL-запросов межфайловой validation.

## Архитектура эксперимента

Один отдельный `project-state worker` создаёт `DatabaseSync(":memory:")` и
является единственным владельцем соединения. Validation worker не открывают
SQLite.

Во время существующего первого прохода каждый validation worker после обработки
YAML отправляет индексный вклад файла в `project-state worker`. Сообщения
объединяются в ограниченные пачки. На одного producer допускается не более двух
неподтверждённых пачек; исчерпание кредита создаёт измеряемое ожидание.

`project-state worker` открывает одну транзакцию на весь проход, вставляет пачки
подготовленными выражениями и возвращает кредит после вставки. После получения
всех данных он выполняет `COMMIT`, сверяет счётчики и запускает
`PRAGMA quick_check`.

Текущий результат первого прохода одновременно возвращается главному потоку без
изменения. Это временное дублирование сохраняет существующий второй проход и
делает замер верхней границей накладных расходов. Эксперимент не используется
как целевая архитектура памяти.

## Данные SQLite

Минимальная схема хранит реальные категории текущего первого прохода:

- файлы проекта;
- локальные diagnostics и результат обработки файла;
- object records;
- object/member/value index entries;
- pending references и pending checks.

Каждая содержательная запись связана с `source_file_id`. Вложенные значения,
нормализация которых не нужна для проверки записи, кодируются версионированным
BLOB. Пути файлов не повторяются в содержательных таблицах.

Схема предназначена только для эксперимента и не считается утверждённой схемой
runtime-кэша.

## Корректность

Обычный и экспериментальный режимы должны совпадать по:

- числу файлов;
- числу object records;
- числу object/member/value index entries;
- числу pending references;
- итоговым diagnostics полного validation.

Эксперимент считается неуспешным при расхождении счётчиков, diagnostics или
отрицательном `quick_check` независимо от скорости.

## Измерение

Перед каждым замером выполняется свежая сборка `@nkdk/core`. Используется только
compiled standalone runner `validation-profile` с четырьмя worker.

Последовательно выполняются:

1. три запуска обычного режима;
2. три запуска `NKDK_VALIDATION_SQLITE_EXPERIMENT=1`;
3. по одному timing-запуску каждого режима.

Для сравнения фиксируются:

- wall-clock первого прохода;
- время SQL-вставок и `COMMIT`;
- время ожидания кредита validation worker;
- число и объём пачек;
- размер SQLite как `page_count * page_size`;
- Peak RSS процесса;
- итоговые diagnostics.

## Критерии решения

Гипотеза подтверждается, если:

- результаты validation полностью совпадают;
- первый проход замедляется не более чем на 10%;
- очередь не превышает два пакета на validation worker;
- процесс завершает все три запуска без OOM.

Изменение Peak RSS публикуется отдельно, но не блокирует вывод о скорости:
эксперимент намеренно одновременно удерживает старый индекс и его SQLite-копию.

Положительный результат разрешает следующий отдельный эксперимент: убрать
старое представление первого прохода и выполнять межфайловую validation через
SQLite. Отрицательный результат останавливает этот вариант до анализа времени
передачи, кодирования и SQL-вставок по отдельности.

## Документация архитектуры

`.agents/architecture.md` не меняется по результатам одного экспериментального
режима. Договор runtime-кэша будет добавлен туда только после подтверждения
гипотезы и согласования целевой схемы.

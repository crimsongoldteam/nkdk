# Восстановление одиночных элементов формы и их XML-id

## Цель

Тонкий снимок конфигурации хранит идентификаторы, но не хранит обычное
XML-состояние. После импорта пустой одиночный элемент формы может полностью
исчезнуть из YAML: его `id` находится в снимке, имя вычисляется правилом, а
остальные свойства имеют канонические значения. Экспорт должен всё равно
создать такой XML-элемент, восстановить или назначить ему `id` и записать
использованный идентификатор в следующий снимок.

Эта спецификация дополняет
`2026-08-12-xml-values-without-snapshot-design.md`. Она не меняет формат снимка
и не возвращает в него обычное XML-состояние.

## Установленная причина

Для типов `AutoCommandBar`, `ContextMenu`, `ExtendedTooltip`,
`SingleSearchControlAddition`, `SingleSearchStringAddition` и
`SingleViewStatusAddition` уже зарегистрирован вложенный одиночный элемент с
`nestedItemIdentity.reserveWhenAbsent: true`.

При импорте объект без смысловых свойств становится пустым и не записывается в
YAML. При экспорте общий ранний пропуск для индексированного свойства видит
отсутствующее поле YAML, отсутствие reference XML и отсутствие XML-значения по
умолчанию. Он завершает обработку до того, как вложенное правило вычисляет
`logicalAddress` и создаёт элемент.

Ниже этого пропуска уже предусмотрено преобразование отсутствующего значения в
пустой объект при наличии identity. Однако наличие identity не должно быть
условием существования одиночного элемента: элемент задаётся правилом, а
identity только определяет его идентификатор.

Назначение ID выполняется после сборки формы функцией `assignGeneratedIds`.
Сейчас этот проход не знает `logicalAddress` XML-объекта и поэтому не может
записать вновь назначенный ID в сборщик снимка.

## Договор одиночного элемента

`nestedItemIdentity.reserveWhenAbsent: true` означает одновременно:

1. свойство описывает обязательный одиночный XML-элемент;
2. отсутствие свойства в YAML передаёт вложенному преобразователю пустой объект
   `{}`;
3. свойства элемента восстанавливаются из действующих правил;
4. отсутствие identity в снимке не отменяет создание элемента;
5. новое общее поле `PropertyRule` или отдельный признак присутствия в снимке не
   добавляется.

Если свойство присутствует в YAML, его значение настраивает тот же обязательный
элемент. Удалить такой XML-элемент отсутствием YAML-поля нельзя.

## Регистрация XML-объектов

Во время построения формы каждый XML-объект с `id` регистрируется вместе с:

- эффективным `logicalAddress`;
- runtime снимка, выбранным для этого преобразования;
- пространством ID: элементы формы, реквизиты, команды или параметры;
- специальным ID правила, если он существует;
- ссылкой на созданный XML-объект.

Регистрация охватывает одиночные элементы, элементы коллекций, реквизиты,
команды и параметры формы. Благодаря этому вновь назначенные ID сохраняются не
только для исправляемых одиночных элементов, а наравне с остальными объектами
формы, как требует общий договор снимка.

Связь является внутренней частью текущего преобразования и не сериализуется в
XML, YAML или снимок. Общие типы `PropertyRule` и параметры построителей правил
не расширяются.

## Назначение ID

После сборки всего `Form`, включая вложенный `BaseForm`, единый проход сначала
собирает все уже занятые числовые ID по каждому пространству и только затем
заполняет отсутствующие.
Для каждого зарегистрированного объекта действует приоритет:

1. ID из эффективного снимка;
2. ID одноимённого элемента из существующего целевого XML;
3. специальный ID правила;
4. очередной свободный положительный числовой ID формы.

Для нового корневого `AutoCommandBar` специальным значением остаётся `-1`.
Если импортированный снимок или целевой XML содержит другое непустое значение,
оно сохраняется согласно более высокому приоритету.

Снимок является источником истины при конфликте со старым целевым XML. Один
неотрицательный ID не может принадлежать двум разным объектам внутри одного
пространства ID: такой конфликт является ошибкой синхронизации. Одинаковые ID
в разных пространствах допустимы и встречаются в штатном XML, например у
элемента формы, реквизита и команды. Специальный `-1` допускается только там,
где его задаёт правило.

Это подтверждено полным просмотром реальной конфигурации ERP: из 12 649 форм в
11 703 (92,5 %) найдены одинаковые ID в разных пространствах, а в 7 357
(58,2 %) один ID встречается одновременно у элемента формы, реквизита и
команды. Например, в
`AccountingRegisters/МСФО/Forms/ФормаСписка/Ext/Form.xml` значение `id="1"`
имеют `Table Список`, `Attribute Список` и
`Command ПереключитьАктивностьПроводок`.

После назначения каждый ID записывается через сборщик того компонента, которому
принадлежит зарегистрированный объект. Повторный экспорт получает этот ID из
снимка и не назначает его заново.

## Обычная форма

Для обычной формы эффективным источником является снимок текущей конфигурации.
Импортированный ID переиспользуется. Если его нет, используется ID из целевого
`Form.xml`; если нет и его, назначается новый ID. Любой использованный ID
записывается в новый блок снимка формы.

## Форма расширения и `BaseForm`

Основной `Form` расширения принадлежит выбранному `cfe`; его использованные ID
записываются в снимок этого `cfe`.

`BaseForm` является производной проекцией и использует действующий составной
reader:

- автоматически заимствованные элементы и их служебные одиночные элементы
  получают ID из `cf`;
- явно заимствованные реквизиты, команды и параметры получают локальный ID из
  `cfe` как в основном `Form`, так и в `BaseForm`;
- собственные элементы расширения в `BaseForm` не появляются, если их не
  включает действующая проекция.

Использование базового ID внутри производного `BaseForm` не создаёт отдельную
запись этого ID в снимке `cfe`. При этом тот же элемент основного внешнего
`Form`, если он присутствует там, сохраняет свой ID обычным способом как часть
снимка `cfe`.

Фактическая выгрузка
`round-trip-compact/cfe/all-extension/Catalogs/СправочникПолный/Forms/ФормаЭлемента/Ext/Form.xml`
подтверждает договор: `Код`, его `ContextMenu` и `ExtendedTooltip` имеют в
`BaseForm` те же ID `1`, `2`, `3`, что и в соответствующей форме `cf/all`, а
локальные реквизиты расширения используют ID `1000001` и `1000002`.

Временный сборщик производного `BaseForm` по-прежнему не публикует отдельный
фрагмент снимка. Регистрация ID должна сохранять выбранный составным reader
источник и не заменять базовую identity локальной identity расширения.

## Ошибки

Синхронизация завершается ошибкой, если:

- снимок содержит один ID для двух разных объектов одного пространства ID;
- после распределения два разных объекта одного пространства получили один
  неотрицательный ID;
- зарегистрированный объект в штатной индексированной синхронизации не имеет
  однозначного `logicalAddress`;
- специальный отрицательный ID используется правилом, которое его не объявляет.

Отсутствующий ID сам по себе ошибкой не является: он восстанавливается из
целевого XML либо создаётся. Действующий запрет генерации отсутствующего ID при
построении `BaseForm` заменяется этим договором.

## Проверки

1. Каждый зарегистрированный обязательный одиночный тип создаётся при
   отсутствующем YAML-поле.
2. ID из снимка имеет приоритет и повторно записывается в новый снимок.
3. При пустом снимке ID берётся из одноимённого элемента целевого XML и
   записывается в снимок.
4. При отсутствии обоих источников назначается свободный числовой ID и
   записывается в снимок.
5. Новый корневой `AutoCommandBar` получает `id="-1"`.
6. Распределение учитывает ID элементов, расположенных ниже по XML, и не
   создаёт коллизий из-за порядка обхода; одинаковые ID разных пространств не
   считаются коллизией.
7. Элемент формы, реквизит и команда могут одновременно получить `id="1"`;
   распределители их пространств работают независимо.
8. В `BaseForm` автоматически заимствованные элементы используют ID `cf`, а
   явно заимствованные компоненты — ID `cfe`.
9. Производный `BaseForm` не создаёт отдельные записи базовых identity в
   снимке `cfe`.
10. Полная и частичная синхронизация сохраняют ID после успешной публикации
   снимка.
11. Полный e2e exact round-trip проходит для обычной конфигурации и расширения.

Оставшиеся после этого изменения расхождения канонических значений XML не
маскируются снимком и рассматриваются отдельно по правилам соответствующих
свойств.

## Вне границ

- изменение двоичного или LMDB-формата снимка;
- сохранение присутствия одиночного элемента отдельным флагом;
- добавление `!xml` для обязательных одиночных элементов;
- изменение смысловой структуры YAML формы;
- изменение правил проекции состава `BaseForm`.

# Восстановление идентификаторов и обязательной XML-структуры

## Цель

Тонкий снимок конфигурации хранит идентификаторы, но не хранит обычное
XML-состояние. После импорта пустой одиночный элемент формы может полностью
исчезнуть из YAML: его `id` находится в снимке, имя вычисляется правилом, а
остальные свойства имеют канонические значения. Экспорт должен всё равно
создать такой XML-элемент, восстановить или назначить ему `id` и записать
использованный идентификатор в следующий снимок.

Эта спецификация дополняет
`2026-08-12-xml-values-without-snapshot-design.md`. Она не меняет формат снимка
и не возвращает в него обычное XML-состояние.

Полный e2e после истончения снимка выявил 238 изменённых файлов. Расхождения
разделены без пересечений: 105 форм теряют обязательные одиночные элементы,
97 файлов метаданных теряют `InternalInfo`, 34 описания форм теряют пустой
`Comment`, а два дополнительных индекса — пустой `AdditionalFields`.

## Установленная причина

Для типов `AutoCommandBar`, `ContextMenu`, `ExtendedTooltip`,
`SingleSearchControlAddition`, `SingleSearchStringAddition` и
`SingleViewStatusAddition` уже зарегистрирован вложенный одиночный элемент с
`nestedItemIdentity.reserveWhenAbsent: true`.

При импорте объект без смысловых свойств становится пустым и не записывается в
YAML. При экспорте общий ранний пропуск для индексированного свойства видит
отсутствующее поле YAML, отсутствие reference XML и отсутствие XML-значения по
умолчанию. Он завершает обработку до того, как вложенное правило вычисляет
`logicalAddress` и создаёт элемент.

Ниже этого пропуска уже предусмотрено преобразование отсутствующего значения в
пустой объект при наличии identity. Однако наличие identity не должно быть
условием существования одиночного элемента: элемент задаётся правилом, а
identity только определяет его идентификатор.

Назначение ID выполняется после сборки формы отдельным проходом.
Сейчас этот проход не знает `logicalAddress` XML-объекта и поэтому не может
записать вновь назначенный ID в сборщик снимка.

## Договор одиночного элемента

`nestedItemIdentity.reserveWhenAbsent: true` означает одновременно:

1. свойство описывает обязательный одиночный XML-элемент;
2. отсутствие свойства в YAML передаёт вложенному преобразователю пустой объект
   `{}`;
3. свойства элемента восстанавливаются из действующих правил;
4. отсутствие identity в снимке не отменяет создание элемента;
5. новое общее поле `PropertyRule` или отдельный признак присутствия в снимке не
   добавляется.

Если свойство присутствует в YAML, его значение настраивает тот же обязательный
элемент. Удалить такой XML-элемент отсутствием YAML-поля нельзя.

## Регистрация XML-объектов

Во время построения формы каждый XML-объект с `id` регистрируется вместе с:

- эффективным `logicalAddress`;
- runtime снимка, выбранным для этого преобразования;
- категорией ID: элементы формы, реквизиты, команды или параметры;
- XML-контейнером, внутри которого ID должен быть уникален;
- специальным ID правила, если он существует;
- ссылкой на созданный XML-объект.

Регистрация охватывает одиночные элементы, элементы коллекций, реквизиты,
команды и параметры формы. Благодаря этому вновь назначенные ID сохраняются не
только для исправляемых одиночных элементов, а наравне с остальными объектами
формы, как требует общий договор снимка.

Связь является внутренней частью текущего преобразования и не сериализуется в
XML, YAML или снимок. Общие типы `PropertyRule` и параметры построителей правил
не расширяются.

## Назначение ID

После сборки всего `Form`, включая вложенный `BaseForm`, единый проход сначала
собирает все уже занятые числовые ID внутри каждого XML-контейнера и только
затем заполняет отсутствующие. Коллекция задаёт область уникальности своим
элементам; зарегистрированный элемент задаёт отдельную область своим вложенным
одиночным элементам. Поэтому одинаковые ID допустимы не только у реквизита,
команды и элемента формы, но и на разных уровнях вложенности элементов формы.
Для каждого зарегистрированного объекта действует приоритет:

1. ID из эффективного снимка;
2. ID одноимённого элемента из существующего целевого XML;
3. специальный ID правила;
4. очередной свободный положительный числовой ID формы.

Для нового корневого `AutoCommandBar` специальным значением остаётся `-1`.
Если импортированный снимок или целевой XML содержит другое непустое значение,
оно сохраняется согласно более высокому приоритету.

Снимок является источником истины при конфликте со старым целевым XML. Один
неотрицательный ID не может принадлежать двум разным объектам внутри одного
XML-контейнера: такой конфликт является ошибкой синхронизации. Одинаковые ID
в разных контейнерах допустимы и встречаются в штатном XML, например у элемента
формы, его вложенного элемента, реквизита и команды. Специальный `-1`
допускается только там, где его задаёт правило.

Это подтверждено полным просмотром реальной конфигурации ERP: из 12 649 форм в
11 703 (92,5 %) найдены одинаковые ID в разных XML-контейнерах, а в 7 357
(58,2 %) один ID встречается одновременно у элемента формы, реквизита и
команды. Например, в
`AccountingRegisters/МСФО/Forms/ФормаСписка/Ext/Form.xml` значение `id="1"`
имеют `Table Список`, `Attribute Список` и
`Command ПереключитьАктивностьПроводок`.

После назначения каждый ID записывается через сборщик того компонента, которому
принадлежит зарегистрированный объект. Повторный экспорт получает этот ID из
снимка и не назначает его заново.

Три дополнения вложенной таблицы поля диаграммы Ганта — строка поиска,
состояние просмотра и управление поиском — являются необязательными: в реальном
XML они могут присутствовать или отсутствовать при одинаковых значениях
`*Location`. Поэтому их наличие определяется сохранённым `xmlId`, а не
положением элемента. При наличии ID дополнение и его обязательные вложенные
элементы восстанавливаются; при отсутствии ID и явного YAML-поля не создаются.

## Обычная форма

Для обычной формы эффективным источником является снимок текущей конфигурации.
Импортированный ID переиспользуется. Если его нет, используется ID из целевого
`Form.xml`; если нет и его, назначается новый ID. Любой использованный ID
записывается в новый блок снимка формы.

## `InternalInfo`

`InternalInfo` не является обычным XML-состоянием снимка. Его структура
однозначно определяется видом объекта, его именем и действующими правилами, а
снимок хранит только устойчивые UUID из `TypeId`, `ValueId`, `ObjectId` и
`ThisNode`.

Экспорт выполняет правило `InternalInfo` даже при отсутствии поля в YAML и при
наличии владельца в снимке. Он строит `GeneratedType`, `ContainedObject` и
`ThisNode` по предметным правилам, подставляет сохранённые UUID, а при отсутствии
UUID создаёт новые и записывает их в следующий снимок. Имена, категории,
`ClassId`, признак присутствия и сырой XML `InternalInfo` в снимок не попадают.

Если правило корневого или вложенного объекта содержит `internalInfo`, экспорт
всегда создаёт элемент `InternalInfo`, в том числе для профиля `adopted`. При
наличии зарегистрированной структуры он заполняется вычисленными элементами и
UUID, иначе экспортируется как `<InternalInfo/>`. Его присутствие не хранится в
YAML, через `!xml` или в снимке.

Во всех трёх эталонных расширениях из `e2e/fixtures/xml/cfe` ветки `develop` у
каждого заимствованного объекта с поддерживаемым `InternalInfo` элемент
присутствует: заполненный для видов с генерируемой структурой и пустой для
остальных. Случаев его отсутствия у таких объектов не найдено.

Ранний пропуск отсутствующего `forReferenceOnly`-свойства не должен отменять
вычисляемое правило `InternalInfo`: наличие владельца в снимке означает, что его
идентификаторы доступны для восстановления, а не что всё свойство надо
пропустить.

В e2e эта причина затрагивает 97 файлов метаданных, в том числе 512 записей
`GeneratedType`.

## Обязательный пустой `Comment`

В описании формы отсутствующий смысловой комментарий канонически экспортируется
как обязательный пустой элемент:

```xml
<Comment/>
```

Поле `Комментарий` при этом отсутствует в YAML. Пустой `Comment` не хранится в
снимке и не требует `!xml`: это однозначный XML-default правила формы. Непустой
комментарий по-прежнему хранится обычной YAML-строкой.

То же правило действует для профиля `adopted`: если правило корневого или
вложенного объекта расширения содержит свойство `comment`, отсутствие поля
`Комментарий` в YAML экспортируется как `<Comment/>`. Договор выражается
существующим `defaultValueAdoptedXML`; новый общий признак не добавляется.

Проверка всех трёх эталонных расширений из `e2e/fixtures/xml/cfe` ветки
`develop` подтвердила, что у каждого объекта с поддерживаемым комментарием
элемент `Comment` присутствует. Без него встречаются только `Activity`,
`Completion`, `ConnectionLine` и `Start`, для которых свойства комментария в
модели нет.

## Пустой `AdditionalFields`

Для двух оставшихся пустых `AdditionalFields` действует уже согласованный
договор из `2026-08-12-xml-values-without-snapshot-design.md`:

```yaml
ДополнительныеПоля: !xml
```

Он экспортируется как `<AdditionalFields/>`. Эти e2e-расхождения являются
дефектом включения существующего предметного правила в полный путь импорта и
экспорта, а не новым видом данных снимка.

## Обязательный контейнер `Attributes`

Внешний `Form` и каждый существующий `BaseForm` всегда содержат контейнер
`Attributes`. При отсутствии реквизитов экспорт создаёт `<Attributes/>`; при их
наличии — заполненный контейнер. Присутствие пустого контейнера не хранится в
YAML, через `!xml` или в снимке.

Во всех формах из `e2e/fixtures/xml/cfe` ветки `develop` отсутствующая форма
контейнера не встречается: 119 внешних `Form` содержат 33 пустых и 86
заполненных `Attributes`, а 60 `BaseForm` — 33 пустых и 27 заполненных.

## Пустое изменённое свойство заимствованного объекта

Для заимствованного объекта расширения присутствие свойства в `Properties`
может быть признаком его изменения, даже если XML-элемент пуст. Например,
изменённая и очищенная подсказка записывается как:

```xml
<ToolTip/>
```

Отсутствие `ToolTip` означает, что подсказка не изменялась. У двух реквизитов
одинакового вида и типа поэтому допустимы разные формы XML. В эталонных
расширениях ветки `develop` среди 169 заимствованных объектов, тип которых
поддерживает `ToolTip`, элемент присутствует у 72 и отсутствует у 97.

Договор определяется реестром состояний свойств, а не именем `ToolTip`. Для
свойства с `availability: borrowed`, единственным режимом `extend` и
представлением `plain` действуют правила:

1. явно присутствующее XML-свойство обязательно создаёт ключ YAML, даже если
   предметное преобразование получает пустое значение;
2. наличие ключа YAML означает, что свойство изменено;
3. отсутствие ключа YAML означает, что свойство не изменялось, и XML-элемент
   не создаётся;
4. пустое значение хранится в естественной форме своего YAML-типа: `""`, `[]`
   или `{}`;
5. сокращение `Свойство:` не используется, потому что YAML разбирает его как
   `null`, а не как естественное пустое значение типа;
6. при экспорте присутствующее поле создаёт XML-свойство даже тогда, когда его
   значение совпадает с неявным значением обычного правила.

Например:

```yaml
Синоним: ""
Подсказка: ""
```

означает два изменённых и очищенных свойства. Отсутствующая `Подсказка`
означает неизменённое свойство. Тот же механизм применяется ко всем
зарегистрированным `plain`-свойствам, включая `Синоним`, `Формат`,
`ФорматРедактирования`, `Подсказка`, `ФормаВыбора`, `Картинка`, `Состав` и
`Пояснение`; частные проверки по `propertyKey` не добавляются. Реестр должен
также объявить этим способом поддерживаемые конкретным типом объекта основные
формы, обычные и расширенные представления, `Владельцы` и `Содержимое`.

Это не XML-default объекта. На объединённой выборке эталонного расширения и
`/Users/nikita/git/sed_xml/cfe` среди 513 заимствованных корневых объектов
`DefaultListForm` присутствует только у 17: в 16 случаях пустая, в одном
содержит ссылку на форму. `Owners` встречается у двух заимствованных
справочников: один раз пустым и один раз заполненным. Поэтому присутствие этих
элементов нельзя выводить только из типа объекта; оно означает явно изменённое
свойство.

Примеры естественного YAML-представления:

```yaml
ОсновнаяФормаСписка: ""
ПредставлениеОбъекта: ""
РасширенноеПредставлениеСписка: ""
Владельцы: []
Содержимое: []
```

Непустые значения используют те же поля без дополнительных тегов. Набор
разрешённых `plain`-свойств определяется декларативно для каждого `itemType`;
незарегистрированное XML-свойство не становится `plain` автоматически и
считается пробелом предметного правила.

Пустой `TypeDescription` представляется пустым списком, например `Тип: []`.
Такое поле создаётся только при наличии соответствующего пустого XML-элемента;
его отсутствие не материализует `<Type/>`. При обратном экспорте реестр
присутствия восстанавливает пустой XML-элемент, даже если обычное предметное
преобразование пустого списка не формирует значение.

Тот же договор действует для пустых массивов составных свойств. Тип свойства,
для которого наличие XML влияет на экспорт, явно объявляет
`presenceAffectsExport` и естественное пустое значение. Поэтому, например,
`ПраваяКолонка: []` восстанавливает `<RightColumn/>`, а отсутствие ключа не
создаёт колонку. Общий YAML-экспорт не отбрасывает пустой массив такого типа.

Описание управляемой формы импортируется из внутреннего узла `Form`, поэтому
пути её metadata-свойств вычисляются относительно `Properties`, без повторного
сегмента `Form`. Это позволяет одному реестру симметрично сохранять пустое
`РасширенноеПредставление` как для обычных metadata-item, так и для
`ClientApplicationForm`. Для формы это свойство остаётся `tagged`: состояние
`Notify` представляется тегом `!проверять`, включая пустое значение.

Свойства с представлениями `tagged`, `multi` и `section` продолжают
использовать действующие `!изменять`, составные значения и разделы
`Изменять`. Пустое изменённое `plain`-свойство не хранится в снимке и не
помечается `!xml` или `!изменять`.

## Точный XML без снимка

Явное значение свойства в YAML экспортируется, даже если оно равно неявному
значению правила. Это необходимо, например, для исходного
`<SkipOnInput>false</SkipOnInput>`.

Пустой `RowFilter` сохраняется как `ОтборСтрок: !xml` для любого профиля
источника таблицы. Отсутствие поля означает отсутствие XML-элемента; экспорт не
создаёт `RowFilter` только по вычисленному типу источника.

Пустые XML-элементы сохраняются XML-парсером до применения предметных правил,
иначе зарегистрированный `!xml` невозможно отличить от отсутствующего тега.
Порядок дочерних тегов DCS восстанавливается предметным экспортёром.

Для заимствованного объекта расширения отсутствующее `FillValue` не создаётся:
профиль `adopted` не применяет обычный XML-default. Для корня расширения
отсутствующие `CompatibilityMode`, `ModalityUseMode` и
`SynchronousPlatformExtensionAndAddInCallUseMode` также не создаются; явно
присутствующие значения остаются в YAML и экспортируются.

Корень расширения также использует профиль `adopted`. Его обязательный
`Synonym`, совпадающий с представлением имени, восстанавливается предметным
правилом `MetadataConfigurationExtension`, хотя в YAML поле `Синоним` опущено.
Это правило не распространяется на заимствованные объекты расширения.

## XML-default в расширении

Режим `adopted` применяется только к действительно заимствованному объекту и
его производной форме. Он не наследуется собственными объектами расширения
только потому, что их предком является корень расширения. Для каждого
собственного объекта профиль явно выбирает обычный режим `full`; для каждого
заимствованного объекта — `adopted`.

Это различие обязательно. Сейчас `adopted` корня распространяется на
собственные вложенные объекты и, например, удаляет у собственного канала
сервиса интеграции канонические `MessageDirection`, `Transactioned` и пустые
обработчики. Такие значения восстанавливаются обычными правилами собственных
объектов и не записываются в YAML или снимок.

Профиль `adopted` не означает безусловный запрет всех XML-default. Для него
действуют три разных договора:

1. изменяемое `plain`-свойство создаётся только при наличии YAML-ключа согласно
   разделу «Пустое изменённое свойство заимствованного объекта»;
2. обязательное или однозначно вычисляемое свойство создаётся по предметному
   правилу без YAML и снимка;
3. обычный XML-default разрешается для `adopted` только после явного
   подтверждения правилом `defaultValueAdoptedXML` либо равнозначным
   предметным условием; автоматически считать каждый `defaultValueXML`
   обязательным для заимствованного объекта нельзя.

На эталонных расширениях подтверждены следующие обязательные значения
заимствованных объектов:

- общий модуль всегда содержит `Global`, `ClientManagedApplication`, `Server`,
  `ExternalConnection`, `ClientOrdinaryApplication` и `ServerCall`;
- регистр сведений всегда содержит `InformationRegisterPeriodicity` и
  `WriteMode`;
- явно присутствующие XML-default, наличие которых различается у объектов
  одного вида (`ReturnValuesReuse`, `NumberPeriodicity`, `CheckUnique` и
  подобные), сохраняются как обычные явные значения YAML;
- вид макета, вид формы, вид таблицы внешнего источника, вид элемента стиля,
  категория группы команд и `UseStandardCommands` восстанавливаются из
  соответствующего правила вида объекта;
- значения формы, обязательные при известном виде формы или элемента,
  восстанавливаются по условию правила. К ним относятся defaults динамического
  списка, документа, отчёта, флажка, отбора DCS и периода DCS.

Например, наличие у таблицы динамического списка `AutoRefresh`, `ShowRoot`,
`AllowGettingCurrentRowURL` и остальных зарегистрированных defaults
определяется видом элемента, а `AutoTime`, `UsePostingMode` и
`RepostOnWrite` — наличием основного реквизита документа. Эти значения не
переносятся в YAML только ради точного XML.

Корень расширения является отдельным специальным случаем `adopted`. Во всех
трёх эталонных расширениях у него присутствуют и потому восстанавливаются как
обязательные `Comment`, `ConfigurationExtensionCompatibilityMode`,
`UsePurposes`, `ScriptVariant`, `DefaultRoles`, `Vendor`, `Version`,
`BriefInformation`, `DetailedInformation`, `Copyright`,
`VendorInformationAddress` и `ConfigurationInformationAddress`. Пустые
значения этих свойств не записываются в YAML или снимок.

Если наличие XML-default различается у объектов одного применимого вида и не
выводится из реестра, типа объекта или другого смыслового значения, его нельзя
объявлять `defaultValueAdoptedXML`: такой случай исследуется отдельно.

## Флажок «Объект расширяемой конфигурации»

`ExtendedConfigurationObject` представляет не просто второй идентификатор, а
включённый флажок «Объект расширяемой конфигурации». Значение элемента — UUID
соответствующего объекта основной конфигурации. При снятом флажке XML-элемент
отсутствует, хотя одноимённый объект и его UUID существуют в основной
конфигурации.

Это подтверждается эталонными расширениями:

- в `all-extension` из 411 заимствованных объектов 410 содержат
  `ExtendedConfigurationObject`; единственное исключение — реквизит
  `СправочникВладелец.РеквизитДвоичныеДанныеБезХранилища` со снятым флажком;
- в `control` и `default` элемент отсутствует у корня `Configuration`, но
  присутствует у остальных заимствованных объектов;
- состояние `Notify` существующего флажка уже представляется как
  `ОбъектРасширяемойКонфигурации: !проверять`.

YAML хранит только исключительное выключенное состояние:

```yaml
ОбъектРасширяемойКонфигурации: Ложь
```

Договор экспорта:

1. поле отсутствует — флажок включён, UUID находится по логическому адресу в
   индексе основной конфигурации и записывается как
   `ExtendedConfigurationObject`;
2. значение `Ложь` — флажок выключен, XML-элемент не создаётся;
3. `!проверять` — флажок включён, UUID вычисляется тем же способом, а в
   `InternalInfo` создаётся состояние `Notify`;
4. UUID не записывается ни в YAML, ни в снимок расширения;
5. отсутствие соответствующего UUID основной конфигурации при включённом
   флажке является ошибкой синхронизации.

Значение `Истина` в YAML не требуется: оно совпадает с неявным включённым
состоянием. Схема подсказывает `Ложь` только для заимствованных объектов,
которые поддерживают этот флажок.

## Порядок `PropertyState`

Порядок записей `InternalInfo/xr:PropertyState` определяется внутренним
перечнем изменяемых свойств конкретного типа метаданных 1С. Это не алфавитный
порядок, не порядок свойств в YAML и не порядок общего `rules.ts`.

Для плана счетов реестр поддерживаемых состояний содержит:

| YAML-поле | Внутренний ключ | Допустимые режимы |
| --- | --- | --- |
| `ДлинаКода` | `codeLength` | контролировать, проверять, изменять |
| `ДлинаНаименования` | `descriptionLength` | контролировать, проверять, изменять |
| `ВидыСубконто` | `extDimensionTypes` | контролировать, проверять |
| `ДлинаПорядка` | `orderLength` | контролировать, проверять |
| `МаксКоличествоСубконто` | `maxExtDimensionCount` | контролировать, проверять |

Режим «контролировать» представлен обычным YAML-значением без тега,
«проверять» — тегом `!проверять`, «изменять» — тегом `!изменять`. Поэтому
исходные `CodeLength=9` и `DescriptionLength=25` со состоянием `Extended`
импортируются как:

```yaml
ДлинаКода: !изменять 9
ДлинаНаименования: !изменять 25
```

Для этих известных состояний служебный `!xml` не применяется. Ограничения
задаются декларативно в реестре плана счетов; сами числовые свойства уже
определены в `rules.ts`.

Для очищенного `tagged`-свойства, смысловым типом которого является ссылка,
пустая строка не используется: она выглядела бы как строковое значение, а не
как отсутствие ссылки. Значение представляется тегом без следующего за ним
скаляра. Например, заимствованный реквизит адресации задачи с очищенной связью
с измерением регистра записывается так:

```yaml
ИзмерениеАдресации: !изменять
```

Наличие ключа и тега означает «свойство изменено, ссылка очищена». Отсутствие
ключа означает «свойство не изменялось», а непустая изменённая ссылка
записывается как `ИзмерениеАдресации: !изменять <ссылка>`. Аналогичная пустая
проверяемая ссылка представляется тегом `!проверять` без значения. Это
предметное представление зарегистрированного состояния, поэтому `!xml` не
требуется.

Очищенная ссылка в режиме «контролировать» записывается пустым YAML-значением
без тега:

```yaml
ИзмерениеАдресации:
```

В этом случае YAML `null` означает именно отсутствие цели ссылки. Такой договор
разрешён только для свойств с предметным типом ссылки. Для строк, коллекций и
объектов продолжают использоваться естественные пустые значения `""`, `[]` и
`{}`; для них сокращение `Свойство:` недопустимо.

Например, таблица внешнего источника использует последовательность:

```text
NameInDataSource
KeyFields
RecordSetModule
ManagerModule
ReadOnly
```

Экспорт не должен сначала обходить обычные свойства, а затем дописывать
состояния разделов `Изменять`: такой обход помещает `ReadOnly` раньше модулей и
меняет порядок самих модулей. Все состояния, независимо от YAML-представления
`plain`, `tagged`, `multi` или `section`, собираются вместе и упорядочиваются
предметным реестром типа объекта.

Дополнительная проверка `/Users/nikita/git/sed_xml/cfe` охватила 516 XML-файлов,
из которых 86 содержат `PropertyState`. Для повторяющихся типов не найдено ни
одной пары свойств с противоположным относительным порядком: в частности, у
десяти заимствованных справочников `ObjectModule` всегда располагается раньше
`ManagerModule`. Таблиц внешнего источника в этой выборке нет, поэтому их
конкретная последовательность подтверждена эталонным `cfe`, а общий принцип —
также дополнительной выборкой.

Порядок `PropertyState` не хранится в YAML или снимке. Неизвестное состояние,
неизвестное свойство либо состояние, которое реестр не разрешает для этого
свойства, останавливает импорт с ошибкой. Импорт не маскирует такие случаи
служебным `!xml configurationExtensionPropertyStateXML` и не пропускает их
молча. Проверка применяется одинаково к `Notify`, `Extended` и другим
состояниям.

## Явные значения свойств с состояниями

Для любого свойства расширения, зарегистрированного в реестре состояний,
явное YAML-значение допустимо даже тогда, когда оно совпадает с
`implicitValueYAML`. Неявное значение позволяет опустить обычное поле, но не
запрещает записать то же значение явно.

Представление режима едино для всех скалярных `tagged`-свойств:

| YAML-представление | Режим | XML-состояние |
| --- | --- | --- |
| обычное явное значение | контролировать | отдельный `PropertyState` отсутствует |
| `!проверять <значение>` | проверять | `Notify` |
| `!изменять <значение>` | изменять | `Extended` |

Конкретный набор допустимых строк таблицы задаётся возможностями свойства в
реестре. Например, для `ДлинаКода` допустимы все три формы:

```yaml
ДлинаКода: 9
ДлинаКода: !проверять 9
ДлинаКода: !изменять 9
```

Для `Балансовый` допустимы только контролировать и проверять:

```yaml
Балансовый: Истина
Балансовый: !проверять Истина
```

Импорт не удаляет явное значение, равное `implicitValueYAML`, если на нём есть
`!проверять` или `!изменять`: без самого значения состояние невозможно точно
восстановить. Экспорт также не отбрасывает явно указанное значение только из-за
совпадения с `implicitValueYAML`.

Схема разрешает полный предметный диапазон значений в каждой допустимой форме,
включая `implicitValueYAML`. Подсказка может не предлагать неявное значение для
обычного поля, но обязана принимать его явно и вместе с допустимым тегом.

## Порядок групп `ExtendedProperty`

Составное свойство с состоянием `MultiState` хранит части типа в группах
`xr:CheckValue`, `xr:NotifyValue` и `xr:ExtendValue`. Их относительный порядок
является частью точной XML-формы и сохраняется порядком элементов YAML-списка.

Например, XML:

```xml
<Type xsi:type="xr:ExtendedProperty">
  <xr:ExtendValue xsi:type="v8:TypeDescription">…</xr:ExtendValue>
  <xr:NotifyValue xsi:type="v8:TypeDescription">…</xr:NotifyValue>
</Type>
```

представляется как:

```yaml
Тип:
  - !изменять Булево
  - !проверять Дата
```

Импорт сохраняет порядок XML-групп в этом списке. Экспорт группирует элементы
одинакового состояния, но создаёт сами группы по порядку первого появления
соответствующего состояния в YAML. Он не пересортировывает их в общий порядок
`CheckValue`, `NotifyValue`, `ExtendValue`.

В эталонных расширениях найдены последовательности `CheckValue → ExtendValue`,
`ExtendValue → NotifyValue` и одиночный `ExtendValue`; дополнительное расширение
`/Users/nikita/git/sed_xml/cfe` подтверждает первые и одиночные формы. Порядок
не хранится в снимке и не требует `!xml`, поскольку уже однозначно выражен
порядком смыслового YAML-списка.

## Стандартные реквизиты регистра бухгалтерии

Состав и порядок канонических стандартных реквизитов регистра бухгалтерии
определяются его свойствами:

- `PeriodAdjustment` присутствует только при ненулевой
  `PeriodAdjustmentLength`;
- `RecordType` создаётся только при явно импортированном `ВидДвижения` и
  располагается после `Account`; в обычном регистре бухгалтерии без такого
  реквизита он не создаётся;
- остальные известные стандартные реквизиты следуют в зарегистрированном
  порядке;
- явно настроенные значения стандартного реквизита берутся из YAML, а его
  канонические значения восстанавливаются предметными правилами.

При `PeriodAdjustmentLength=0` экспорт не добавляет `PeriodAdjustment`. Состав
и порядок не хранятся в снимке и не требуют `!xml`.

## Свойство `Балансовый`

Каждое измерение и каждый ресурс регистра бухгалтерии содержит XML-свойство
`Balance`. Его неявное значение — `true`; значение `false` сохраняется в YAML
явно:

```yaml
Балансовый: Ложь
```

Для заимствованного поля доступны режимы «контролировать» и «проверять», но не
«изменять». Режим «контролировать» представлен обычным значением без тега, а
«проверять» — тегом `!проверять`:

```yaml
Балансовый: !проверять Ложь
```

Если режим «проверять» включён для истинного значения, неявное значение нельзя
сокращать и поле сохраняется явно:

```yaml
Балансовый: !проверять Истина
```

Экспорт всегда создаёт `<Balance>true</Balance>` либо
`<Balance>false</Balance>` для измерения или ресурса регистра бухгалтерии,
включая заимствованные поля. При `!проверять` дополнительно создаётся
`PropertyState=Notify`. Значение и режим не хранятся в снимке и не требуют
`!xml`.

## Форма расширения и `BaseForm`

Основной `Form` расширения принадлежит выбранному `cfe`; его использованные ID
записываются в снимок этого `cfe`.

`BaseForm` является производной проекцией и использует действующий составной
reader:

- автоматически заимствованные элементы и их служебные одиночные элементы
  получают ID из `cf`;
- явно заимствованные реквизиты, команды и параметры получают локальный ID из
  `cfe` как в основном `Form`, так и в `BaseForm`;
- собственные элементы расширения в `BaseForm` не появляются, если их не
  включает действующая проекция.

Использование базового ID внутри производного `BaseForm` не создаёт отдельную
запись этого ID в снимке `cfe`. При этом тот же элемент основного внешнего
`Form`, если он присутствует там, сохраняет свой ID обычным способом как часть
снимка `cfe`.

Фактическая выгрузка
`e2e/fixtures/xml/cfe/all-extension/Catalogs/СправочникПолный/Forms/ФормаЭлемента/Ext/Form.xml`
подтверждает договор: `Код`, его `ContextMenu` и `ExtendedTooltip` имеют в
`BaseForm` те же ID `1`, `2`, `3`, что и в соответствующей форме `cf/all`, а
локальные реквизиты расширения используют ID `1000001` и `1000002`.

Временный сборщик производного `BaseForm` по-прежнему не публикует отдельный
фрагмент снимка. Регистрация ID должна сохранять выбранный составным reader
источник и не заменять базовую identity локальной identity расширения.

## Ошибки

Синхронизация завершается ошибкой, если:

- снимок содержит один ID для двух разных объектов одного XML-контейнера;
- после распределения два разных объекта одного XML-контейнера получили один
  неотрицательный ID;
- зарегистрированный объект в штатной индексированной синхронизации не имеет
  однозначного `logicalAddress`;
- специальный отрицательный ID используется правилом, которое его не объявляет;
- `PropertyState` содержит неизвестное состояние, неизвестное свойство либо
  режим, не разрешённый предметным реестром для этого свойства.

Отсутствующий ID сам по себе ошибкой не является: он восстанавливается из
целевого XML либо создаётся. Действующий запрет генерации отсутствующего ID при
построении `BaseForm` заменяется этим договором.

## Проверки

1. Каждый зарегистрированный обязательный одиночный тип создаётся при
   отсутствующем YAML-поле.
2. ID из снимка имеет приоритет и повторно записывается в новый снимок.
3. При пустом снимке ID берётся из одноимённого элемента целевого XML и
   записывается в снимок.
4. При отсутствии обоих источников назначается свободный числовой ID и
   записывается в снимок.
5. Новый корневой `AutoCommandBar` получает `id="-1"`.
6. Распределение учитывает ID элементов, расположенных ниже по XML, и не
   создаёт коллизий из-за порядка обхода; одинаковые ID разных контейнеров не
   считаются коллизией.
7. Элемент формы, реквизит и команда могут одновременно получить `id="1"`;
   распределители их XML-контейнеров работают независимо. То же относится к
   элементу формы и его вложенному одиночному элементу.
8. В `BaseForm` автоматически заимствованные элементы используют ID `cf`, а
   явно заимствованные компоненты — ID `cfe`.
9. Производный `BaseForm` не создаёт отдельные записи базовых identity в
   снимке `cfe`.
10. Полная и частичная синхронизация сохраняют ID после успешной публикации
   снимка.
11. Полный e2e exact round-trip проходит для обычной конфигурации и расширения.
12. `InternalInfo` восстанавливается по предметному правилу и UUID снимка без
    поля YAML и без обычного XML-состояния снимка.
13. При отсутствии UUID `InternalInfo` получает новые UUID, которые записываются
    в следующий снимок и переиспользуются при повторной синхронизации.
14. Отсутствующий YAML-комментарий описания формы создаёт `<Comment/>`.
15. `ДополнительныеПоля: !xml` проходит полный import/export и создаёт
    `<AdditionalFields/>`.
16. Пустое `plain`-свойство заимствованного объекта проходит полный
    import/export как явно присутствующий YAML-ключ с естественным пустым
    значением; отсутствие ключа не создаёт XML-свойство.
17. Неподдерживаемый `PropertyState` останавливает импорт и не маскируется
    служебным `!xml`.

Для поддерживаемых входных данных побайтовое равенство всего XML после
round-trip является обязательным. Любое оставшееся расхождение, включая
присутствие или отсутствие явного значения по умолчанию, считается дефектом.
Если исходную форму нельзя однозначно вывести из смыслового YAML и действующих
правил, она должна сохраняться уже согласованным предметным `!xml`; возвращать
обычное XML-состояние в снимок нельзя. Неподдерживаемый `PropertyState` является
ошибкой входных данных согласно разделу «Ошибки», а не таким случаем `!xml`.

## Вне границ

- изменение двоичного или LMDB-формата снимка;
- сохранение присутствия одиночного элемента отдельным флагом;
- добавление `!xml` для обязательных одиночных элементов;

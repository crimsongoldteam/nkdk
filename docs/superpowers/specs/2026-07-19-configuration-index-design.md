# Файл индекса конфигурации для import и sync с 1С

> Статус: согласованный проект. Двоичный формат 1.0 определён; подключение к 1С и договор удалённого агента остаются вне первой реализации.

## Цель

Спроектировать файл индекса конфигурации, который в целевом механизме подтверждает соответствие Проекта конкретной Конфигурации после успешного `import` или `sync`. В первой реализации import получает готовую XML-выгрузку, поэтому индекс описывает соответствие Проекта этой выгрузке, но ещё не подтверждает привязку к базе.

Файл индекса конфигурации должен одновременно:

- обнаруживать изменения всех файлов проекта, влияющих на XML;
- хранить канонические идентификаторы объектов и вложенных элементов 1С;
- заменять reference XML выжимкой данных, явно необходимых правилам при обратном преобразовании YAML -> XML;
- обнаруживать изменения конфигурации, выполненные вне NKDK;
- обновляться только после успешного применения XML в базе 1С.

## Границы

Спецификация описывает логическую модель файла индекса конфигурации, его жизненный цикл и договор с удалённым агентом. Она не проектирует SSH-транспорт, запуск платформы 1С и конкретную команду загрузки XML.

Первая реализация использует единый двоичный файл со строгой версионируемой спецификацией. SQLite, несколько контейнеров и другие физические представления можно проверить позднее по результатам измерений, не меняя логический договор.

Точная раскладка версии 1.0 описана в [двоичном формате файла индекса конфигурации](../../../.agents/configuration-index-format/v1_0.md).

## Согласованные решения

- Один YAML-проект может иметь несколько независимых привязок к базам 1С.
- Одинаковые логические объекты имеют одинаковые UUID во всех привязанных базах. UUID являются канонической идентичностью проекта.
- Автоматическое распространение смены UUID после внешнего удаления и повторного создания объекта между несколькими базами пока не проектируется и зафиксировано как ограничение.
- Файл индекса конфигурации не хранится в Git.
- Каждая привязка хранится в одном файле `.nkdk/configuration-index/<base-id>.bin`.
- Первая реализация поддерживает одну привязку; импорт из готовой XML-выгрузки использует `baseId = "default"`.
- При импорте из готовой XML-выгрузки отпечаток базы и подтверждённая версия Конфигурации остаются пустыми.
- Отслеживаются все файлы, описанные правилами проекта: YAML, BSL, HTML, картинки, макеты и другие ресурсы.
- Логические адреса идентификаторов и reference-данных используют формат `uid` из эксперимента `reference-order-spec`.
- Файл индекса конфигурации совместим только с той же версией NKDK; после обновления NKDK требуется повторный import.
- Файл индекса конфигурации хранит не только UUID, но и rule-guided выжимку скрытых/reference-only данных, необходимых для экспорта без локального каталога reference XML. Исходные XML-файлы целиком не сохраняются.
- Конфигурация базы может изменяться вне NKDK. Файл индекса конфигурации хранит непрозрачный токен удалённой ревизии.
- Если текущая удалённая ревизия не совпадает с сохранённой, `sync` прекращается и требует повторного `import`.
- Локальные хэши и удалённая ревизия обновляются только после подтверждения успешного применения XML удалённым агентом.
- Код механизма в рамках этой спецификации не реализуется.

## Логическая модель

Индекс конфигурации одной привязки физически хранится в одном двоичном файле. Внутри файл состоит из четырёх логических частей.

Единый файл выбран как начальный вариант с минимальным числом служебных сущностей и понятным договором доставки. Решение принимается до измерений новой нагрузки: если полное чтение или атомарная перезапись окажутся узким местом, альтернативные представления будут сравниваться отдельно.

### Идентификация формата и привязки

- версия формата файла индекса конфигурации;
- идентификатор привязки к базе;
- непрозрачный идентификатор или отпечаток удалённой базы без SSH-реквизитов и других секретов;
- версия NKDK, необходимая для проверки совместимости сохранённых данных.

### Подтверждённая точка синхронизации

- токен удалённой ревизии, полученный от агента;
- хэши всех файлов проекта, соответствующих этой ревизии;
- алгоритм каждого хэша либо общий алгоритм уровня файла индекса конфигурации;
- нормализованные пути относительно корня YAML-проекта.

Точка считается подтверждённой только после успешного завершения удалённой операции. Частичный или неуспешный `import`/`sync` не меняет её.

### Каноническая идентичность 1С

Карта идентичности связывает нейтральный логический адрес элемента проекта с UUID 1С. Она должна покрывать не только верхнеуровневые объекты, но и вложенные сущности, для которых XML содержит устойчивую идентичность: формы, реквизиты, табличные части, реквизиты табличных частей, команды, элементы форм и другие поддержанные правилами элементы.

Логические адреса и обход структуры должны строиться по `rules.ts` и регистрациям типов, а не через частные условия по `itemType` в общих слоях.

### Reference-sidecar

Reference-sidecar хранит только данные исходной XML-модели, которые не представлены в пользовательском YAML и явно объявлены необходимыми для `toXML`: например, порядок, служебные атрибуты и другие reference-only значения. Исходные XML-файлы и полностью восстанавливаемые данные в sidecar не копируются.

Данные извлекаются по `rules.ts` и регистрациям типов, затем индексируются по нейтральным областям синхронизации. Изменение одной области не должно требовать разбирать reference-данные всей конфигурации.

## Целевой жизненный цикл удалённого import

1. NKDK подключается к выбранной базе через SSH и агентский режим.
2. Агент возвращает идентификатор базы и начальный токен ревизии.
3. Агент выгружает конфигурацию в XML.
4. NKDK импортирует XML в YAML тем же rule-guided механизмом, который используется сейчас.
5. Во время импорта NKDK собирает хэши файлов, карту идентичности и reference-sidecar.
6. Перед публикацией результата NKDK убеждается, что удалённая ревизия не изменилась во время выгрузки.
7. После полного успешного импорта файл индекса конфигурации атомарно записывается для выбранной привязки.

Если импорт завершился частично или ревизия изменилась во время выгрузки, новый файл индекса конфигурации не публикуется.

## Жизненный цикл sync

1. NKDK читает файл индекса конфигурации выбранной привязки.
2. NKDK вычисляет текущие хэши всех rule-guided файлов проекта и определяет добавленные, изменённые и удалённые пути.
3. Если изменений нет, операция завершается без открытия нового соединения с 1С.
4. По декларативным маршрутам изменения группируются в XML-области.
5. Затронутые YAML и ресурсы преобразуются в XML с использованием канонической идентичности и reference-sidecar.
6. NKDK открывает или переиспользует агентский сеанс и проверяет идентификатор базы.
7. Агент сравнивает текущую удалённую ревизию с ожидаемой. При несовпадении операция останавливается и требует повторного `import`.
8. Агент применяет один согласованный набор изменённых XML-файлов с той же ожидаемой ревизией и возвращает новую удалённую ревизию.
9. NKDK обновляет хэши, идентичность и reference-sidecar затронутых областей.
10. Новый файл индекса конфигурации записывается атомарно только после подтверждения агента.

Если агент не подтвердил применение всего набора, подтверждённая точка синхронизации остаётся прежней.

## Внешние изменения

Токен удалённой ревизии является непрозрачным значением: NKDK сравнивает его на равенство, но не интерпретирует. Агент обязан изменять токен после любого изменения конфигурации, способного повлиять на XML-выгрузку.

Расхождение токенов означает, что локальные хэши и reference-sidecar больше не доказывают соответствие базе. Автоматическое объединение внешних и локальных изменений в первой версии не выполняется.

Если внешний `import` обнаружил смену UUID при неизменном логическом адресе объекта, он может зафиксировать фактическую идентичность импортируемой базы. Механизм выбора нового канонического UUID и его распространения в остальные привязанные базы в этой спецификации не определяется; это известное ограничение из `.agents/restrictions.md`.

## Надёжность локальной записи

После успешного ответа агента новый индекс конфигурации записывается во временный файл в том же каталоге и атомарно заменяет предыдущий файл. До подтверждения удалённой операции файл не меняется.

Если процесс завершится после успешной удалённой операции, но до локальной замены файла индекса конфигурации, следующая попытка обнаружит расхождение удалённой ревизии и потребует повторного `import`.

Первая версия не выполняет обновление двоичного файла на месте. Она строит полную новую версию во временном файле, проверяет её целостность и затем выполняет атомарную замену.

## Безопасность

Файл индекса конфигурации не содержит пароли, закрытые ключи, строки подключения с секретами или содержимое SSH-конфигурации. Идентификатор привязки ссылается на настройки подключения, хранящиеся отдельно.

Каталог `.nkdk/configuration-index/` должен быть исключён из Git. Отсутствие исключения считается ошибкой настройки проекта, а не поводом молча записать файл индекса конфигурации в отслеживаемый файл.

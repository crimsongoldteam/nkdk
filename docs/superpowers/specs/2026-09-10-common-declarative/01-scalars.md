## Следствия для языка

### Разные значения при отсутствии XML и YAML

Отсутствие свойства в двух форматах может обозначать разные значения.
Например, у таблицы `AutoInsertNewRow` отсутствие XML означает `false`,
а отсутствие YAML означает `true`. Переносчик сохраняет оба договора:

```yaml
presence:
  - target: {field: autoInsertNewRow}
    xml:
      missing: {denotes: {literal: false}}
      canonical:
        - {when: {eq: [{field: autoInsertNewRow}, {literal: false}]}, form: missing}
    yaml: {default: {literal: true}}
```

Пустой XML превращается в `АвтоВводНовойСтроки: Ложь`; отсутствие YAML
восстанавливает `<AutoInsertNewRow>true</AutoInsertNewRow>`. Явная XML-запись
`false` отличается от канонического отсутствия и сохраняется общим механизмом
аномалий. Отдельная декларация аномалии не нужна.

Скалярный Rust-генератор поддерживает условный `form: missing` для элементов
через общий механизм выражений. Для XML-атрибутов этот профиль пока явно
отклоняется при компиляции. Мигратор применяет его только к проверенному
логическому `implicitValueXML`, без одновременного `defaultValueXML/Raw`.

У пустого XML-элемента каноническая форма может включать объявленный тип:

```yaml
canonical:
  - {when: {not: {present: {field: value}}}, form: empty-element, type: xs:string}
```

`type` — QName из `namespaces`, допустимый только у `empty-element`. Общий
выбор канонической формы действует и для корня значения, и для поля записи;
условия используют значение и входы. При чтении такой пустой элемент означает
отсутствие смыслового значения, а XML без ожидаемого типа сохраняется как
отклонение общим механизмом аномалий. Свойство и имя common не участвуют в
работе генератора. Профиль `exportNilValue` переносчик превращает в выбор
между `nil` и типизированным пустым элементом.

Одной пары «XML-тип/YAML-тип» недостаточно. Нужны смысловой тип, лексическое представление, принимаемые варианты, канонический вариант, ограничения и присутствие. Более терпимый parser не расширяет автоматически публичную YAML-схему. Общая календарная и числовая библиотека допустима как механизм языка; специальная функция конкретного common — нет.

В `boolean`, `string`, `number` уже есть `atomicConversion.ts`: объединённые переходы XML→YAML/YAML→XML выбираются при компиляции правила. Boolean переиспользует неизменяемые результаты, Number заранее вычисляет XML-тип. Это полезный образец устранения промежуточных вызовов, но пока он реализован отдельными функциями. Целевой компилятор должен получать такие специализированные переходы из декларации и сохранять различие смыслового значения и его представления без обязательного выделения объекта для этой пары.

## Реализованная основа присутствия скаляров

Для обычного boolean подключено двустороннее отсутствие, заданное в самой декларации:

```yaml
presence:
  - target: self
    xml: {missing: {denotes: {absent: true}}}
    yaml: {missing: {denotes: {absent: true}}}
```

Общий генератор хранит такое поле как `Option<T>`; пропуск не подменяет false, ноль или пустую строку. XML-экспорт всегда сохраняет корень документа, даже если все поля отсутствуют. Структурная схема делает поле необязательным, не расширяя перечень его допустимых значений. Неизвестный XML-токен и пустой boolean-узел теперь сохраняются общей оболочкой аномалии без выдуманного смыслового значения. Тот же механизм работает для строки с дополнительными XML-атрибутами и точного числа с недопустимой или неканонической записью. Ограничения скалярного владельца выводят `!xml/invalid` из существующего условия; дополнительный список аномалий не требуется. Внутренний TS-переходник, принимающий JS boolean, не расширяет публичный договор YAML: там остаются Истина/Ложь.

Этот механизм не объявляет готовыми default/implicit и сохранение явного значения по умолчанию в правилах владельца. Другие формы presence компилятор пока явно отвергает; их нельзя молча игнорировать. Поэтому флажок полного переноса boolean остаётся пустым.

Проверены точные существующие пары boolean, отдельные границы отсутствия/недопустимых токенов и согласованность JSON Schema. Через рабочую команду конвертера проверены 67 свойств e2e: 47 true, 5 false, 15 отсутствующих. Это договор простого значения Server/UseStandardCommands, без сокращений владельца и без полного преобразования проекта. [Результаты](../../../../tests/migration/boolean-value-e2e.json), [повторяемая проверка](../../../../tests/migration/checks/boolean-e2e.py).


### Общие аномалии простых значений

Общий слой сохраняет исходный XML при невозможности прочитать значение, а при изменении записи корректного числа — смысловое значение и минимальную XML-разницу. Например, `NaN` не превращается в ноль; `1e3` имеет точное значение 1000 и сохраняет исходную запись; нарушение ограничения числа и отличие записи могут сохраняться одновременно. Соседние корректные свойства остаются обычным YAML. Дополнительные пространства имён сохраняются независимо от префиксов исходного файла.

Проверка неизменённых e2e-фикстур охватывает 157 свойств boolean/string/number. Проверяется договор базового скаляра, а не все ограничения MetadataName и не преобразование всего проекта. [Результаты](../../../../tests/migration/scalar-value-e2e.json). Для обычных значений хранилище аномалий не выделяет память; XML-дерево строится только на исключительном пути.

Это ещё не завершает остальные скалярные common-объекты: типизированные варианты, default/implicit владельца, даты, UUID и специальные ограничения остаются отдельными задачами. Повторы целого свойства, неизвестные контейнеры, синтаксически повреждённый XML и некорректный YAML без пометок пока могут завершаться диагностикой ошибки; общий резервный путь для них не реализован. Флажки полного переноса не изменены.
## Следующий реализованный слой

Общий генератор поддерживает постоянные XML-атрибуты скаляров, отсутствие с константой по умолчанию и условия сокращения common/владельца. Обратное восстановление отличает явный default, отсутствие и пустой узел. Структурная схема и Rust-проверка исключают явные значения, для которых задано сокращение. Проверены сочетания typed XML с пустым default, неизвестными значениями и изменённой числовой лексикой.

Подключены декларации обычной и типизированной даты. По явному ответу пользователя время сохраняется как записано; смещение не пересчитывается. Пример `2026-09-10T12:00:00+03:00` даёт смысловое значение `10.09.2026 12:00`, а исходное смещение сохраняется в XML-разнице. Календарный механизм поддерживает минуты/секунды и исключение нулевого времени, не использует системный часовой пояс. Точное поведение нового профиля описано в единой спецификации; это не заявление о завершении всех специализированных common.

Через рабочую команду проверены 498 типизированных свойств e2e: 447 строк, 25 чисел и 26 дат. [Повторяемая проверка](../../../../tests/migration/checks/typed-scalars-e2e.py) использует Python с PyYAML; [результаты](../../../../tests/migration/typed-scalar-value-e2e.json). Исходные XML не изменялись. Даты также проверены на границах календаря, смещения, дробных секунд и коротких/не-ASCII входах.

Открыты minMaxValue, собственные UUID и простые составные календарные объекты. Кроме того, остаются зависимые параметры common, условные XML-атрибуты скаляров и общий резервный путь для неизвестной структуры. Поэтому флажки полного переноса ещё не установлены.


### Приёмка MetadataName — 2026-09-10

Норма имени задаётся единственным `value.pattern` в `common/metadata-name.yaml`: первая буква или подчёркивание, далее буквы русского/латинского алфавита, цифры и подчёркивание. Компилятор выводит проверку обеих сторон, структурную схему и пометку недопустимого значения. Шаблон компилируется при сборке; при преобразовании не компилируются регулярные выражения. Недопустимое имя сохраняет смысловой текст с `!xml/invalid`, исходная XML-форма проверяется обратным преобразованием.

Приняты 773 имени существующих e2e-объектов; отдельно проверены пустое имя, ведущая цифра, дефис и завершающий перевод строки. Последний запрещён, как требуют существующие TS-тесты, хотя старый JavaScript-шаблон с `$` мог его принять. Схема теперь действительно проверяет имя, вместо прежнего общего `Type.String()`. Флажок и машинный реестр обновлены.


### Продолжение проверки простых значений

Постоянные default и сокращения владельца уже реализованы (ранние ограничения выше описывают первый слой). Неканонический сокращаемый ноль сохраняет `$значение: 0` и исходную запись XML. Вложенные элементы вместо скаляра сохраняются общей raw-оболочкой на границе свойства, без выдуманного смысла; порядок, повторы и атрибуты проходят round-trip. Смешанный текст с элементами, повторы целого свойства и неизвестные контейнеры пока требуют общего резервного пути.


### Приёмка семейства М1 — 2026-09-10

StringOrNumber и PredefinedCode перенесены одним механизмом `scalar-choice`, описанным в единой спецификации. Различие экспорта (`emit: xs:decimal` только для PredefinedCode) находится в декларациях. Число точное; строка `001` остаётся строкой. Отсутствующий/пустой XML, недопустимое число, QName и неканоническая запись проходят общий путь аномалий. Новых предметных Rust-функций нет.

Проверены все 29 найденных свойств e2e: 23 Code в Predefined.xml (из них 3 xs:decimal), 6 ReportResult/DetailsData форм. Редкие числовые типы, большой целый, точная дробь, неизвестный тип и отсутствие покрыты общей проверкой механизма. Схема отвергает boolean/null/коллекции. Обе записи приняты в чеклисте, coverage обновлён. Сохранён существующий экспорт нового числового YAML у StringOrNumber без XML-типа; дополнительный цикл такого нового XML даёт текстовый смысл, как и раньше, — это явно зафиксированная граница, не потеря исходного XML при импорте.


### Приёмка minMaxValue и общих механизмов М2 — 2026-09-10

Приняты оба профиля minMaxValue: точное число с `xs:decimal` и точкой, либо `xs:string` и запятой. Оба читают точку/запятую; YAML содержит точное число. Различия типа, разделителя и лексики сохраняются общим механизмом. Отсутствие не подменяется нулём. У владельцев с пустым nil отсутствующий YAML экспортируется как `xsi:nil="true"`; обычный nil не получает аномалию. Этот договор выражен существующим presence, а не списком исключений.

Проверены все 1934 найденных свойства minMaxValue e2e: InputField, StandardAttribute, Constant/CommonAttribute и потребители общего фрагмента атрибутов (Attribute, Field, Dimension, Resource, AddressingAttribute, AccountingFlag, ExtDimensionAccountingFlag). MinValue/MaxValue у TrackBarField и ProgressBarField имеют другой тип number и не входят в этот отчёт. Сами владельцы целиком этим не приняты. Контрольные ожидания используют независимый разбор XML и точные Python Decimal, XML-фикстуры не менялись.

Общий компилятор также разрешает постоянные аргументы скаляров при сборке и выводит условия XML-атрибутов от значения. Дублирующие специализации объединяются. Ссылка через подготовленный индекс остаётся обязанностью М6; остальные флажки М2 не выставлены до полной сверки профилей.


### Приёмка dateTime — 2026-09-10

Поддержаны обычный и типизированный XML, отсутствие, календарный default владельца и сокращение. Значение по умолчанию проверяется и превращается в компоненты при сборке. Ограничение сокращения в структурной схеме использует запись YAML. Существующие общие проверки сохраняют секунды, смещения и ошибочный XML через аномалии, без зависимости от часового пояса машины.

Повторяемая проверка `typed-scalars-e2e.py --dates` принимает 26 типизированных календарных свойств e2e, из них 10 periodAdditionBegin/End проверяются с настоящим default владельца `0001-01-01T00:00:00`: YAML сокращается без аномалии. [Отчёт](../../../../tests/migration/calendar-profile-e2e.json). Отсутствующий и пустой исходный узел при таком default сохраняют своё отличие. Составные standardPeriod/standartBeginningDate остаются отдельным семейством М3.


### Приёмка boolean и number — 2026-09-10

Boolean проверен с сокращаемым false и с сохраняемым явным default true: сохранение выражается отсутствием omitWhen, отдельный признак в общем языке не нужен. Number поддерживает обычный XML, тип decimal и тип string; последний пишет точку, как существующий numberRule, в отличие от MinMaxValue. Числовые minimum/maximum и максимум по соседнему полю выражаются уже имеющимися ограничениями. Общие проверки скаляров и схем дополнены случаями профилей; отдельных предметных Rust-функций нет.

Приняты boolean, number и dateTime; string ждёт привязок metadataTarget из М6. Отметки не означают, что перенесены целиком владельцы этих свойств или весь проект. Несовместимость с округлением JS Number и независимость дат от часового пояса остаются ранее согласованными изменениями.

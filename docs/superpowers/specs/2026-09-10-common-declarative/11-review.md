# Готовность, открытые решения и следующий проход

Этот файл фиксирует готовность первого обзора. Последующее описание синтаксиса и предложения по `rules.yaml` ведутся в [спецификации языка](../2026-09-10-declaration-language-design.md); перечисленные ниже незакрытые договоры остаются обязательными для детализации.

## Что завершено в этом документе

- Учтены все 90 верхних каталогов commonObjects, 14 корневых исходных TS-файлов и все 25 вложенных DCS-каталогов с прямыми исходниками (плюс корневой index.ts DCS).
- Для каждого верхнего common есть карточка существующего поведения, требуемых конструкций и значимых проверок. DCS разбит на вложенные карточки, MetadataValue — на составные варианты.
- Сохранены пути/хеши 636 исходных TS-файлов common и связанных тестов/фикстур, отдельно прочие файлы фикстур. Реэкспорты, пустой registry.ts и служебные каталоги не объявлены самостоятельными преобразователями.
- Предложен общий интерфейс значений, представлений, ограничений, фактов, состояний, ресурсов и идентичности. Объяснены границы ручного Rust-кода и запрет специальных common callbacks.

Уровень результата — архитектурный обзор договоров по кодовой базе. Полнота списка каталогов проверена автоматически. Это не построчная сертификация 636 файлов, не выполненные round-trip для каждого common и не доказательство выразимости всех деталей в окончательной грамматике.

## Решения по совместимости

1. Полнота декларативности не означает усиление валидации. `translateOnly`, частичная проверка CharacteristicsDescription/AdditionalIndex и календарные ограничения сохраняются как явно названные уровни текущего договора. Закрытие пробелов — отдельное изменение поведения.
2. Багоподобный fallback parser, например строковое приведение объекта даты, не становится новой нормой. Случай заносится в сравнительные примеры; сохранение ошибочного исходного XML решается действующим договором аномалий. Изменение принимаемого публичного YAML согласуется отдельно.
3. Таблица допустимых тегов остаётся закрытой и привязанной к точному типу/границе. `!xml/important` не появляется автоматически. Теги расширений `!проверять`/`!изменять` рассматриваются отдельно.
4. Собственные UUID и служебные XML ID получают подготовленные идентичности; metadata UUID-reference сохраняет свой отдельный `!xml/uuid` договор без lookup.
5. Служебные языки `#` и пустой код не объявляются обычными зарегистрированными языками. Сохраняется существующая разница областей проверки: XML-импорт исключает служебный код из проверки зарегистрированности по вхождениям, а специальная YAML-проверка пропускает карту с таким кодом целиком. Подробности и источник зафиксированы в карточке I8nText.
6. Enterprise учтён как существующая внешняя проекция. Эта спека проектирует XML↔YAML+validation; существующая Enterprise-функциональность не удаляется в ходе миграции.

## Порядок дальнейшей детализации спеки

1. I8nText и FormattedI8nText: полностью описать присутствие, сокращение, дубли/порядок/языковые ограничения и оформление существующих аномалий.
2. Color/Font/Border/StyleItemValue: закрыть union, ссылки и вложенные оболочки; проверить, что хватает общих конструкций.
3. TypeDescription/MetadataValue/FillValue: закрыть текстовые грамматики, зависимость типов, graph-expansion и предметные constraints.
4. StandardAttributeDescriptions/ExchangePlanContent: закрыть canonical members и join/state relation.
5. DCS ParameterValue и рекурсивные структуры; ClientApplicationInterface — совместное использование definition/identity.
6. Ресурсы/Help/InternalInfo: окончательно определить подготовку, отсутствие IO в чистом правиле и публикацию результатов.
7. Применить уточнённую грамматику к остальным карточкам. Каталог считается описанным полностью только когда для всех его вариантов есть конкретная декларация, а не одно обещание «use common.X».

Порядок — продолжение проектирования, не разрешение на реализацию. После этого проводится ревью единого интерфейса; отдельный план реализации составляется только по согласованной спецификации.

## Критерий допуска к реализации

Не должно остаться скрытой специальной функции common, неописанного варианта восстановления или потерянной действующей проверки. Для каждого варианта указаны независимые примеры XML, YAML, ожидаемых диагностик/аннотаций и допустимого результата обратного экспорта. Невыразимый случай либо расширяет общий язык с явным договором, либо блокирует перенос этого компонента — он не исчезает из реестра.

## Проверка документации перед сохранением

Проверены точное покрытие 90/90 верхних каталогов, наличие карточек вложенных DCS-частей, существование всех локальных Markdown-ссылок, хеши исходников/фикстур и синтаксический разбор двух YAML-примеров. Семантический компилятор нового языка ещё не реализован, поэтому это не проверка исполнимости деклараций.

Проверка новых дублей относительно исходной ревизии не обнаружила новых дублей. Изменяются только файлы спецификации; тесты конвертера не запускались и не изменялись, XML-фикстуры не изменялись.

## Требования, которые нельзя спрятать за именем компонента

`resolveDefinedType`, `classifyFillValue`, `parseMetadataPath`, `normalizeSynonym` не становятся декларативными от переименования функции в operation. Для них нужно разложение на общие конструкции и предметные таблицы. Кандидаты: конечный выбор, проверка множества альтернатив, безопасная грамматика строк, проекция/поиск в индексе, обход ссылочного графа с состояниями visited/resolving/resolved. Последний требует отдельного договора ограничений и диагностики цикла; текущая спецификация не выдаёт его за готовую грамматику.

Нынешнее размещение предметной FillValue-классификации в `packages/runtime/.../fillValueSemantics.ts` не является целевой границей: ядро не должно знать 1С-типы. Семантика типов остаётся декларациями common; общий обход графа и числовая/строковая проверка — механизмами языка.

### Наблюдаемый договор FillValue на e2e

Исследование неизменённых `e2e/fixtures/xml/cf` и `cfe` от 21 сентября:
1080 наблюдений, 273 точных варианта, 0 неразобранных конструкций XML.
Это счётчики наблюдений, а не число валидных значений. Отдельная оценка
старых `rules.ts`: 886 `notSpecified`, 112 `unresolved`, 52 `implicit`,
30 `explicit`; нельзя выдавать `unresolved` за XML-аномалию.

| XML-факт | Наблюдений | Договор представления |
|---|---:|---|
| `xsi:nil` | 761 | Отдельное явное пустое состояние; обычная форма для разных типов и стандартных реквизитов. |
| Свойство отсутствует | 231 | Состояние отсутствия, не равное присутствующему пустому. |
| Пустой `xs:string` | 51 | Контекстное начальное значение обычного строкового реквизита; восстанавливать по объявленному/эффективному типу и профилю владельца. |
| `v8:Null` | 4 | Отдельный транспорт XML; допустимость зависит от объявленного типа и владельца. |
| Остальные типизированные значения | 33 | Проверять по объявленному типу, ограничениям и смыслу ссылки; точные числа без округления. |

Различие `nil`/пустая строка/отсутствие задают входы и правило присутствия.
Общий Rust-код не выбирает форму по имени `FillValue` или каталогу владельца.
Несовместимый тип значения, недопустимая ссылка, слишком длинная строка,
дробность/знак числа, цикл DefinedType и неизвестное направление ссылки дают
адресную диагностику, а не отказ преобразования данных. Исходная форма XML,
которую обычный обратный путь не доказывает, сохраняется общим механизмом
аномалий. Никаких предметных обработчиков аномалий в YAML не перечисляем.

Для классификации разделяем: наблюдаемый XML, эффективный тип (список
альтернатив и ограничения), политику владельца (обычный/стандартный реквизит,
допустимость транспорта и подразумеваемое значение) и итог проверки. Случаи
`ValueStorage`, UUID, составных типов и недостающих объявлений стандартных
реквизитов из e2e входят в корпус как ограничения полноты; 112 старых
`unresolved` нельзя автоматически объявить корректными или аномальными.

Текущие тесты `classify.test.ts`, `definedType.test.ts` и
`standardMember.test.ts` задают проверяемую матрицу переноса. Это ожидаемое
поведение для проектирования декларации, а не требование сохранить потерю
точности TypeScript-чисел:

| Эффективный тип | Обычное значение | Неявное значение при единственной альтернативе | Ограничение |
|---|---|---|---|
| Строка | Текст, включая пробелы | Пустая строка | Переменная длина `≤ N`, фиксированная `= N`; ноль означает без ограничения. |
| Число | Точное десятичное | Ноль | Разрядность, число дробных знаков, разрешённый знак; без преобразования в `f64`. |
| Булево | Истина и Ложь | Нет | Значение другого типа несовместимо. |
| Дата | Календарное значение | `0001-01-01T00:00:00` | Для Date часы/минуты/секунды нулевые, для Time дата `0001-01-01`; календарная корректность общая. |
| Ссылка на один вид объекта | Значение указанного объекта и допустимая пустая ссылка | Пустая ссылка того же объекта | Корень, объект и вид значения сверяются с объявленным типом. |
| Составной тип | Любая из объявленных альтернатив | Нет | Пустая ссылка/невыбранная ветвь может быть допустима без сокращения. |

Длина текста в ограничениях измеряется единицами UTF-16: символ вне BMP
занимает две единицы. Общие выражения `variantValue`, `textLengthAtMost` и
`textLengthEquals` дают декларации доступ к выбранной текстовой ветви и
сравнивают её с длиной из соседнего `TypeDescription`; генератор не проверяет
имя `FillValue`.

`DefinedType` разворачивается по подготовленному графу типов, сохраняя
порядок альтернатив и устраняя дубли. Отсутствующий тип, пустое определение
и цикл возвращают состояние `unresolved` с адресной диагностикой. Политики
стандартных реквизитов (`forbidden`, `byEffectiveType`, код/номер/наименование
из свойств владельца, ссылка на владельца) принадлежат декларациям владельца;
общий механизм получает данные и таблицу политики, не знает их имён.

### Порядок решения для FillValue

Это отдельное применение уже объявленного `MetadataValue`, а не второй разбор
XML. Для каждого реквизита подготовка передаёт тип и свойства владельца в
декларацию; результаты подготовки имеют три состояния: известный набор
альтернатив, тип не задан, тип не разрешён. Отсутствующий/циклический
`DefinedType` нельзя незаметно превращать в строку или пустое значение.

| Шаг | Правило, из которого выводится результат | Пример |
|---|---|---|
| Форма | Общая декларация присутствия отличает отсутствующее свойство, `xsi:nil`, пустой `xs:string`, `v8:Null` и типизированное значение. Профиль владельца определяет обычную форму записи. | Пустая строка обычного строкового реквизита может быть обычным `xs:string`; та же оболочка у числового реквизита требует диагностики. |
| Эффективный тип | Развернуть альтернативы `TypeDescription` и `DefinedType` с ограничениями и без повторов. Неразрешённая ссылка на тип даёт `unresolved`, а не догадку по значению. | `DefinedType.А` → `CatalogRef.Товары`; цикл `А` → `Б` → `А` остаётся неразрешённым. |
| Политика | Выбрать профиль обычного/стандартного реквизита декларацией владельца. `forbidden` запрещает указанное значение; `notSpecified` не выводит подразумеваемое; `codeFromOwner`, `stringFromOwner` и `ownerReference` получают поля владельца через входы. | Стандартный `Код` зависит от длины и вида кода объекта; `Владелец` — от множества владельцев справочника. |
| Подразумеваемое | Только у единственной известной альтернативы сравнить с её начальным значением: пустая строка, точный ноль, начальная дата, пустая ссылка нужного объекта. У булевого нет подразумеваемого значения; у составного типа ветвь не сокращается. | `CatalogRef.Товары` + `Catalog.Товары.EmptyRef` сокращается; при двух каталогах та же ссылка остаётся явной. |
| Совместимость | Для явного значения выбрать хотя бы одну допустимую альтернативу с проверкой длины, разрядности/знака, даты или вида ссылки. При несовпадении выдать диагностику в адрес свойства и сохранить вход. | Числовой тип и строка `"12"` несовместимы, хотя текст похож на число. |

### Конечная таблица для FillValue

Таблица разделяет XML-оболочку, разрешение объявленного типа и смысловое
значение. Результат классификации один из `valid`, `implicit`, `invalid`,
`unresolved`, `notSpecified`; при первых двух исходная XML-форма всё равно
проверяется на обратимость. Неизвестное не превращается в `invalid`.

| Вход | Альтернатива или решение | Когда значение подразумевается | Когда явно допустимо |
|---|---|---|---|
| Тип отсутствует, пуст или `DefinedType` не найден/цикличен | `unresolved`; сохранить значение и причину | Никогда | Проверку отложить до появления полного графа типов |
| `xs:string` / `Строка` | `string` с длиной и режимом Fixed/Variable | Пустая строка при единственной альтернативе | Строка в пределах длины; Fixed требует точную длину |
| `xs:decimal` / `Число` | `number` с числом разрядов, дробных разрядов и знаком | Точный ноль при единственной альтернативе | Точное десятичное число в ограничениях; кавычки YAML не меняют строку в число |
| `xs:boolean` / `Булево` | `boolean` | Никогда | Только смысловое булево |
| `xs:dateTime` / `Дата` | `dateTime` с Date/Time/DateTime | `0001-01-01T00:00:00` при единственной альтернативе | Корректная дата/время и разрешённая точность |
| `CatalogRef`, `DocumentRef`, `EnumRef`, `ChartOfAccountsRef`, `ChartOfCharacteristicTypesRef`, `ChartOfCalculationTypesRef`, `ExchangePlanRef`, `BusinessProcessRef`, `BusinessProcessRoutePointRef`, `TaskRef` | `reference` с видом корня и, если задано, именем объекта | Пустая ссылка того же объекта или пустое ссылочное значение при единственной альтернативе | Разрешённый вид и цель ссылки; существование цели проверяет общий индекс |
| Несколько типов | Удалить лишь точные повторы альтернатив, затем проверять хотя бы одну | Никогда, даже если значение подходит одной ветви | Пустое ссылочное значение допустимо явно, если это разрешено договором состава |
| Другой объявленный тип, включая UUID и ValueStorage, пока нет правила его ограничений | `unresolved` с именем типа | Никогда | Не угадывать совместимость по виду YAML; расширять таблицу типов после отдельного e2e |
| Известный тип, но значение не подходит ни одной альтернативе | `invalid` и адрес свойства | Никогда | Исходное значение сохраняется аномалией |

XML-оболочка проверяется отдельно: отсутствующий элемент, `xsi:nil`, пустой
типизированный `xs:string`, `v8:Null`, `xr:DesignTimeRef` и обычный
типизированный элемент не равнозначны. Профиль владельца задаёт каноническую
пустую форму; несоответствие исходной формы сохраняет общий механизм аномалий.
При отсутствующем значении единственный эффективный строковый тип, включая
строку фиксированной длины, выбирает пустой `xs:string` даже при
`exportNilValue: true`; для остальных типов этот
параметр выбирает `xsi:nil`. Поэтому перенесённое правило должно читать
соседний `Тип` либо подготовленный из него общий факт, а не только параметр
`exportNilValue`. Общее правило `common.metadata-value` принимает признак
`onlyStringType`: его вычисляют из `TypeDescription` без повторного чтения
XML. При ложном признаке `exportNilValue` выбирает `xsi:nil`; другие
потребители передают `false`, пока не подключён их собственный профиль.
При проверке описания типа имя (`Строка`, `Число` и т. п.) и его параметры
хранятся раздельно. Ограничение длины/точности обязано проверять поля
параметров, а не сопоставлять готовую строку с одним полем имени. Для
строки допускается отсутствие длины или положительная целая длина; для
фиксированной строки длина обязательна; для числа точность допустима только
при положительной длине.
Для обычного реквизита `xsi:nil` допустим лишь при единственном строковом типе,
а `v8:Null` — только у поля внешнего источника данных. Для стандартного
реквизита выбор транспорта зависит от его декларации: `String` разрешён
строковому, `TypeDescription` — `ТипЗначения`, `DesignTimeRef` — ссылочному
профилю; остальные сочетания дают диагностику и сохраняются.

Политики стандартных реквизитов — данные владельца: `notSpecified` не
классифицирует значение; `forbidden` даёт `invalid`; `byEffectiveType`
использует ту же таблицу; `codeFromOwner` берёт вид, длину и фиксированность
кода; `stringFromOwner` берёт длину строки; `ownerReference` разворачивает
список владельцев в ссылочные альтернативы. Если требуемый параметр
неизвестен, результат `unresolved`. Единственный корректный владелец может
давать подразумеваемую пустую ссылку, несколько владельцев — нет.

Порядок важен: сперва чтение формы без потерь, затем разрешение типа и политики,
потом сравнение с начальным значением и проверка остальных явных значений.
Отсутствие XML-атрибута и отсутствие смысла FillValue — разные факты. Значение,
которое нельзя классифицировать из-за неготового индекса, остаётся
`unresolved`, а не `implicit` или `invalid`. Неверные данные регистрируются
общим механизмом аномалий и не прерывают преобразование.

Для составного значения декларация может проверить выбранную ветвь общим
выражением `isVariant: {value: ..., variant: ...}`. Компилятор проверяет имя
ветви по объявленному выбору, а генератор выполняет одно и то же ограничение
при XML-импорте и YAML-проверке, в том числе если поле находится в составном
владельце. Если явное значение не соответствует единственному известному
простому типу, но его обычная YAML-запись и XML-тип позволяют восстановить
исходное значение, оно остаётся явным и сопровождается диагностикой; для этого
не нужен `!xml`. Ошибка данных не прерывает преобразование. Если форма XML
теряется, действует отдельное правило согласования `!xml` из `AGENTS.md`.
Проверка календарного вида работает с уже разобранными частями значения:
для `Date` время равно нулю, для `Time` дата равна `0001-01-01`, для
`DateTime` оба компонента допустимы. Декларация задаёт условие и адрес
аномалии; генератор использует общий типизированный доступ без повторного
разбора строки.

Нынешние `effectiveFillValueType`/`resolveAlternatives` заменяются общим
обходом графа и таблицей корней ссылок в YAML; `classifyFillValue` — выбором
альтернатив и декларативным сравнением с начальными значениями; проверки
`matchesStringLength`, `matchesNumber`, `matchesDateTime` — общими проверками
текстовой длины, точного десятичного числа и календаря. Функции
`classifyCode`, `classifyStringFromOwner`, `classifyOwnerReference` становятся
профилями полей владельца, а проверка существования ссылки использует общий
индекс целей. Ни одна из этих функций не переезжает в Rust как обработчик с
именем `FillValue`.

## Составные части MetadataValue

- `fixedArray/*`: реэкспорты обработки рекурсивного массива; один/несколько XML Value, null → xsi:nil.
- `formChoiceList/*`: общий Record Presentation:I8nText + Value:MetadataValue и особый явный вариант внутри массива. Считается отдельным вариантом договора, не пропущенным из-за реэкспорта.
- `AssociatedTable`: отдельная строковая проекция со схемой; не приравнивать автоматически к проверенной ссылке на физическую таблицу.
- `handlers.ts`: существующие функции примитивов должны превратиться в описания форматов, enum и references; точные отличия календарных форматов от общего dateTime сохраняются.

`MetadataValue` задаёт один рекурсивный выбор вариантов. `fixedArray` и
`formChoiceList` ссылаются на него декларативно; генератор не содержит условий
по их именам. Параметры свойства из `rules.ts` определяют профиль подключения.
В частности, единственный эффективный строковый тип выбирает пустой
типизированный `xs:string`; иначе `exportNilValue` выбирает `xsi:nil`.
Обе формы разбираются как отсутствие, но отличие исходной формы сохраняется,
если она не совпала с профилем владельца.

Неизвестный `xsi:type`, `v8:Null` и ссылка, которую нельзя однозначно выразить
обычным YAML, не должны останавливать преобразование. Общий механизм выводит
аномалию из несовпадения декларации и доказанного обратного преобразования.
Такие случаи не перечисляются в декларации отдельными обработчиками. Частая
форма корпуса обязана стать обычным профилем, а не массовой аномалией.

## Связанные источники вне common

Проверять вместе с `packages/runtime/metadata/ruleRuntime/property/fillValueSemantics.ts`, `packages/rules/metadata/validation/projectValidationPendingChecks.ts`, `packages/rules/metadata/validation/projectStateDependencyValidation.ts`, runtime metadataTarget и `packages/rules/metadata/validation/dataPath/`. Нейтральная validation исполняет собранные декларации и не получает новых частных веток common.

## Уточнение договора путей перед подключением М6

Источник поведения: `packages/runtime/metadata/ruleRuntime/metadataTarget/{parse,format,roots}.ts`.
Пять словарей вынесены в `rust/declarations/common/metadata-path-lexicons.yaml`:
50 корней, 12 видов членов, 5 видов вложенных объектов, 17 стандартных реквизитов,
12 виртуальных таблиц. Это словари будущей грамматики, а не готовый `metadataPath`.
`fieldKindToYAML` — подмножество словаря членов; дублировать эту таблицу не нужно.

| Форма | Пример XML-смысла → YAML | Что должна выражать декларация |
|---|---|---|
| Полный объект | `Catalog.Товары` → `Справочник.Товары` | Перевод только вида; имя объекта не переводится, даже если совпадает со словарём. |
| Единственный известный корень | `Catalog.Товары` → `Товары` | Обратимое сокращение корня из параметров; допустимо только без фильтров, вложенности и точных путей. В нынешнем договоре полная YAML-форма при таком профиле не является нормальной. |

| Член текущего владельца | Тот же путь → `КодПоставщика` при единственном разрешённом виде | Восстановление владельца из входа и вида из параметра; при нескольких видах сохраняется `Реквизит.КодПоставщика`. |

| Значение перечисления | `Enum.Статусы.EnumValue.Готово` → `Перечисление.Статусы.Готово` | Пропущенный постоянный сегмент восстанавливается из выбранного варианта грамматики. |

| Вложенный объект | `ExternalDataSource.Источник.Table.Товары` → `ВнешнийИсточникДанных.Источник.Таблица.Товары` | Последовательность пар вида и имени, ограниченная разрешёнными путями владельца. |

Общие требования к реализации:

- Разделитель — точка; пустые сегменты, пробелы, нечётные пары и недопустимые имена
  не нормализуются молча. Используется уже принятый договор MetadataName.
- Нормальная структура, допустимые варианты и сокращения описываются одним
  договором. Из него выводятся чтение, печать и отклонения; отдельного списка
  аномалий пути нет. Rust не выбирает ветку по имени вида метаданных.
- Точные пути и вложенные корни — разные ограничения. Совпадение отдельного
  вида не означает, что разрешена вся последовательность.
- Совместимые полные модельные имена, которые старый YAML-парсер принимает для
  членов, учитываются как формы чтения. Каноническая печать остаётся русской.
- Проверка структуры выполняется до поиска существования. Нельзя превратить
  отсутствующую цель, неоднозначность и неготовый индекс в один результат.
- Указание текущего владельца не разрешает произвольную чужую цель. Исключение
  для явно разрешённого полного пути также принадлежит декларации.
- `dataPath` и `type` не поддерживаются данным старым парсером целей: их поведение
  берётся из соответствующих common и контекста формы/типов, а не придумывается
  из названия варианта. Служебное отрицательное число в `dataTableField` — отдельная
  существующая форма, которую нельзя принять за имя поля.

Инвентаризация `tests/migration/metadata-path-inventory.json`: 1125 XML-файлов,
2095 кандидатов явных путей, без ошибок разбора. Это не доказательство round-trip;
относительные ссылки и имена типов с суффиксами требуют отдельного отбора.

### Проверенные фиксированные профили

`metadata-root-path.yaml` и `metadata-member-paths.yaml` выражают парными
`text-pattern` полный корневой путь, обычного члена, стандартного реквизита
из открытого словаря и значение перечисления. Пользовательское имя `Ref`
не переводится у обычного члена; постоянный сегмент `EnumValue` восстанавливается
из декларации. Проверка MetadataName наследуется полями. Для этих профилей
не добавлено предметного кода в Rust.

На неизменённом e2e проверены 695 корневых путей и 1211 путей членов, включая
454 обычных, 737 стандартных и 20 вложенных объектов. Это проекция отдельных свойств, без выбора
профиля владельцем и проверки существования. В e2e нет выбранных случаев
EnumValue: его фиксированная форма проверена независимым примером. Все common
ссылок сохраняют незавершённый статус.

`formatMemberSegmentName` оставляет без перевода имя, отсутствующее в
`standardAttributeToYAML`. Для этого реализована общая форма
`yaml: {kind: text-table, use: words}`: `common.standard-attribute-name`
использует существующий словарь из 17 пар, остальные имена сохраняются.
Все 105 первоначально исключённых вхождений теперь проверены в обоих направлениях;
в `notCovered` остаются 15 иных четырёхсегментных форм.

Неизменяемый остаток обязан оставаться обратимым: XML-имя `Ссылка` не должно
незаметно восстановиться как `Ref` из-за совпадения с переводом. Коллизия
определяется из таблицы и общего обратного преобразования. Отдельного перечня
аномалий или обработчика стандартных реквизитов на Rust нет.

Коллизия XML-имени с переводом, неверное имя и пустой последний сегмент проверены
существующей матрицей с сохранением соответствующих аномалий. Независимая
декларация проверяет тот же механизм отдельно и внутри строкового шаблона.
Дальше нужны выбор всех форм, относительные и сокращённые пути,
проверка существования и ограничения владельца по общим индексам.

### Фиксированный путь вложенного объекта

Профиль `common.metadata-object-path` использует тот же общий `text-pattern`: корень, имя владельца, вид вложенного объекта и его имя. Переводятся только корень и вид из существующих словарей; пользовательские имена сохраняются. Отдельного обработчика Rust для таблиц, кубов, функций или перерасчётов нет. Это строительный блок полного metadataPath, а не завершённый выбор всех его форм и проверка ссылок.

### Общий выбор члена и вложенного объекта

`common.metadata-structural-path` объединяет существующие `metadata-member-path`
и `metadata-object-path` декларацией `choice`. Компилятор выводит различие из
закрытых словарей видов и точек между слотами. Имена и правила их проверки
сохраняются в соответствующем варианте; неизвестные слова и неверные имена
обрабатываются общим механизмом аномалий.

Это ещё не полный metadataPath: стандартные реквизиты, корневые и остальные
формы пока имеют отдельные профили; индексы и сокращения остаются следующими
этапами. Предметных проверок по типам 1С в автомате нет.

### Пустая ссылка и виртуальная таблица

Каталог `metadata-terminal-paths.yaml` использует существующие шаблоны, словари
и `choice`; расширения языка или предметных обработчиков Rust не требуется.

| XML | YAML | Декларация |
|---|---|---|
| `Catalog.Owner.EmptyRef` | `Справочник.Owner.ПустаяСсылка` | `metadata-empty-ref-path` |
| `InformationRegister.Owner.SliceLast` | `РегистрСведений.Owner.СрезПоследних` | `metadata-virtual-table-path` |
| `CalculationRegister.Owner.BaseSource` | `РегистрРасчета.Owner.БазаSource` | `metadata-base-table-path` |

`metadata-table-path` объединяет два вида виртуальных таблиц. Обычные имена
переводятся существующим закрытым словарём из 12 пар; у `Base…` меняется только
постоянный префикс, имя базы сохраняется. Неверные и пустые имена, неизвестный
вид таблицы и неправильное окончание пустой ссылки проверяются общим механизмом
аномалий. Отдельные правила аномалий в каталог не добавляются.

Это фиксированные формы, а не полный перенос DataTable/MetadataValue:
допустимость цели у конкретного владельца, вложенные пути, сокращения и
существование цели требуют оставшейся части М6. Для e2e виртуальные таблицы
отбираются только из свойства `MainTable`; совпавшее имя обычного значения
не считается таблицей по одному слову.

`AdditionalIndex.Table`, `ScheduledJob.MethodName` и `EventSubscription.Handler`
в существующих rules.ts используют stringRule. Их текст, включая английский
префикс, сохраняется без перевода. Их нельзя направлять в профиль ссылки только
по числу сегментов или знакомому окончанию. Предыдущий отбор e2e по одному
имени Table был слишком широким и исправлен.

### Предопределённое значение и пустая ссылка

`metadata-value-path.yaml` объединяет три сегмента значения. Последний сегмент
использует MetadataName с открытым словарём `EmptyRef: ПустаяСсылка`: остальные
имена сохраняются. Ограничение имени наследуется через `value: {use: name}`.
Исходное имя `ПустаяСсылка` автоматически требует сохранения формы, поскольку
обычное обратное чтение означало бы EmptyRef. Отдельной декларации аномалии нет.

Для корня Enum этот профиль разрешает только EmptyRef: обычное значение
перечисления использует отдельную форму с сегментом EnumValue. Это нормальное
смысловое ограничение декларации; его нарушение регистрируется как аномалия.
Допуск вида ссылки владельцем и проверка существования остаются частью М6.

### Общий допуск ссылок «Вводится на основании»

Девять видов владельцев используют один договор BasedOn. Цель — корень
ChartOfAccounts, ExchangePlan, Catalog, Document, ChartOfCharacteristicTypes,
BusinessProcess, ChartOfCalculationTypes или Task; альтернативно — ровно одна
Table внутри ExternalDataSource. Сам ExternalDataSource без таблицы, Cube,
Function и дальнейшие вложенные уровни не входят в нормальный договор.

Наличие цели и допуск владельцем проверяются независимо: существующий объект
может быть запрещён этим свойством. Проверки выражены нормальными ограничениями
YAML, нарушения автоматически сохраняются как аномалии. Для условия «ровно
одна таблица» нужны непустота, верхняя граница длины и проверка вида; each над
пустым хвостом не заменяет проверку непустоты.

Декларация common/based-on-links.yaml задаёт общий договор всей коллекции.
Она сохраняет порядок, повторы, отсутствие/пустоту и оболочку xr:Item с
QName xsi:type= xr:MDObjectRef. Владелец передаёт типизированные индексы через
bind; common не выбирает глобальные имена индексов. Ограничения each задают
норму коллекции, поэтому смысловой тег выводится на её границе. Неизвестная
грамматика или невосстановимое отличие атрибута сохраняются как форма XML
только после проверки обратного преобразования. Отдельных правил аномалий нет.

Одиночные проверочные примеры используют ту же декларацию коллекции.
Структурная схема — массив строк; проверка значения и цели выполняется Rust.

### Корневые ссылки документа и журнала

`Document.RegisterRecords` допускает только корни InformationRegister,
AccumulationRegister, AccountingRegister и CalculationRegister.
`DocumentJournal.RegisteredDocuments` допускает только корни Document.
Непустой хвост пути запрещён независимо от существования вложенного объекта.
Порядок и повторы сохраняются; наличие цели и допуск вида проверяются отдельно.

Договоры находятся в common/document-register-links.yaml и
common/journal-document-links.yaml. Оба используют существующий генератор
типизированных коллекций без изменений Rust и без обработчиков аномалий.
Владельцы в probes задают XML-путь, YAML-ключ и привязку индексов.
Это проекции свойств: публикация ownerFactRole=registerRecords и полный импорт
документа ещё не подключены. У остальных свойств ограничения нельзя выводить
из названия: отсутствие metadataTarget.roots в TS не означает неявный запрет
других корней.

### Подготовка сведений о движениях владельца

`metadata.owner-register-records` хранит принадлежность регистра владельцу:
ключ `{owner, kind, name}`, значение — идентичность владельца. Разделители
в строках не склеивают части ключа; вид берётся из смысла перечисления.
Декларация probes/document-register-records.yaml связывает роль с
Document/Properties/RegisterRecords и индексами существования целей.

При подготовке вкладов XML читается непосредственно из файла документа.
Общий читатель проекции пропускает соседние свойства, но проверяет корень,
наличие контейнера владельца и все элементы объявленного свойства.
Ошибка данных внутри вклада оставляет индекс неготовым. Это отдельная операция
подготовки фактов: она не заявляет поддержку преобразования пропущенных полей.
Неизвестные поля обычного преобразования не игнорируются этим механизмом.

Полный перенос владельцев дополнительно требует совместного чтения нескольких
common, UUID и внутренней информации, дочерних реквизитов/табличных частей,
форм/команд/шаблонов и внешних файлов. Эти части нельзя заменять !xml/raw.

### Обычная XML-форма группы команды

В 74 вхождениях Command/CommonCommand.Properties.Group из e2e cf/cfe
атрибут xsi:type отсутствует. Источники и хеши записаны в
tests/migration/command-group-e2e.json. Обычная декларация MetadataCommandGroup
поэтому не добавляет этот атрибут. Типизированный вариант сохраняется общим
механизмом формы XML; отдельного обработчика аномалии нет.

Стандартная группа задаётся перечислением, пользовательская — ссылкой на
индекс корневых объектов. Отсутствующая пользовательская группа нарушает
объявленное ограничение и получает смысловую аномалию. Независимый обратный
экспорт проверяется с заново подготовленным индексом.

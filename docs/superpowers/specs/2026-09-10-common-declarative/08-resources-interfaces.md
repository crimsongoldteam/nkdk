## Граница чистого правила

Не все каталоги common являются конвертерами значения. Из файловой топологии нельзя получить содержимое без IO, а новый UUID не выводится из текста детерминированно. Поэтому декларация сообщает операции, какие ресурсы/идентичности подготовить и какие результаты опубликовать. Общий исполнитель файлов и allocator ID пишутся один раз; специальные `syncHelp()`/`syncTemplate()` заменяются данными маршрутов, групп файлов и проекций.

Проверка обратимости не имеет права генерировать новые UUID, читать неопределённый каталог или изменять снимок. Все такие входы должны быть подготовлены и закреплены за версией операции. XML-only служебное значение не обязано появляться в пользовательском YAML: его восстановление должно иметь явно объявленный источник.


## Сверка исполняемого файлового профиля, 2026-09-12

В едином языке реализованы resources/oneOf, forEach подготовленных имён и
remainder для остатка каталога. Модули, имена путей, суффиксы и размещение
макетов задаются YAML-фрагментами; общий Rust-код не содержит условий по ним.
Прошли общие группы файлов Document/DocumentJournal, обратные пути, пустые
файлы/каталоги, двоичные данные, повторные ссылки, конфликты и ограничения.
Это не завершает полные common-объекты и публикацию проектной операции.

Для Help подтверждён отдельный оставшийся договор: импорт читает Page из
Ext/Help.xml, переносит перечисленные HTML и дерево _files; экспорт получает
языки из имён HTML и сортирует их по байтам UTF-8. В обычном Свойства.yaml
отдельного значения справки нет. Следовательно, простой перенос каталога не
заменяет подготовку и восстановление XML-оболочки. Нестандартный порядок,
повторы, отсутствующие страницы и дополнительные XML-данные нужно проверить
как отклонения общего договора, сохранив холодное восстановление из YAML.


### Справка: сверка e2e 2026-09-12

Все 39 Help.xml в e2e (основа и расширение) имеют один и тот же смысловой
вид: корень Help в пространстве extrnprops, version="2.20", единственная
страница ru без атрибутов. Это подтверждает краткую нормальную декларацию,
но не позволяет считать остальные формы невозможными.

Фрагмент help-resources переносит Ext/Help ↔ Справка через remainder:
HTML, вложенные файлы и пустые каталоги сохраняются общим файловым исполнителем.
Сам Help.xml не копируется в YAML-каталог: его список восстанавливается
из подготовленных имён файлов и явно сохранённых отличий. Внешнее XML-свойство
подключено к Document/DocumentJournal через fragment.help и общий маршрут file.
Проверены отсутствие файла, пустой корень, порядок, повторы, неизвестная XML-форма
и восстановление без референса. Help принят; публикация проекта остаётся
отдельным этапом общей операции.

### ExternalFile: единый ресурсный фрагмент

`common.external-file` описывает пару подготовленных путей sourcePath и
 targetPath как списки сегментов. Оба направления выводятся из одной пары;
никакого преобразования содержимого нет. Отсутствующий файл не создаётся,
пустой файл остаётся существующим пустым файлом. Двоичные данные сохраняются
побайтово. Пути относительны выбранному каталогу владельца; его выбор остаётся
обязанностью сборки, как у Help. Недопустимые пути в декларации/входах операции
не маскируются под аномалии содержимого файла.

Существующий язык resources расширен готовым входом sequence<text> для пути
целиком. Проверка относительных сегментов и лимитов выполняется тем же
RelativePath, что и для пути из отдельных выражений. В инструменте переноса
постоянные пути передаются через bind; разные bind получают разные кандидаты.

### Исполняемая файловая сборка

`kind: resources` задаёт самостоятельную сборку файловых маршрутов. Она
использует те же `imports`, `compose`, `bind` и `resources`, что и объект.
Пустые `value.fields`, XML- и YAML-представления означают отсутствие основного
документа, а не фиктивный XML-корень. Проверка после раскрытия композиции
запрещает поля и поведение значений, в том числе пришедшие из фрагмента.

Сборка получает подготовленные входы и выдаёт план переноса файлов для общей
операции Rust. Прямое и обратное направления используют один маршрут.
Вызов преобразования, валидации или проверки основного документа для такой
сборки является ошибкой выбора операции (`entry.resource-only`). Это ошибка
программы, а не аномалия входных данных. Файловые аномалии обрабатывает прежний
общий механизм; частных условий по конфигурации или XDTO в нём нет.

Постоянные маршруты ExternalFile закреплены в сборках
`resources.configuration-external-files`,
`resources.configuration-extension-external-files` и
`resources.xdto-package-external-files`. Вызывающая сторона передаёт каталог
владельца, но не повторяет пути его свойств. Проверка миграции сопоставляет
каждое фиксированное значение со старым правилом и с реальной композицией;
два разных применения одного фрагмента допустимы, дублирование одного — нет.
Готовность этой файловой части не означает приёмку полного объекта метаданных.

Каталог `source_root` — уже выбранный каталог владельца: корень конфигурации
либо каталог конкретного XDTO-пакета. Старый поиск «сначала относительно
переданного каталога, затем внутри имени объекта» не переносится в common как
скрытая эвристика. Выбор каталога относится к сборке проекта; общий файловый
механизм применяет один и тот же относительный маршрут к выбранному корню.
Проверки владельцев используют реальные каталоги e2e. Подключение выбора
корней к полному обходу проекта учитывается в готовности самих владельцев.

### Статические модули

Статический Module выражается существующим oneOf из двух маршрутов:
.bsl и .bin. Оба направления получаются из той же пары XML/YAML-путей.
Наличие обеих альтернатив обрабатывает общая файловая диагностика;
содержимое файлов не разбирается и не перекодируется.

Точные профили 57 вхождений подключены к файловым сборкам. Они подтверждают
файловую часть, а не полную служебную регистрацию объекта в модели проекта.
Вычисляемые пути и syncArea остаются отдельными обязанностями; их нельзя
отбрасывать при сопоставлении параметров. Полная приёмка Module и владельцев
требует закрытия этих обязанностей. Проверки групп альтернатив и общая
матрица файлов не размножаются для каждого свойства.

### Список внешних файлов с сохранением имени

WSDefinitionSchemas использует файловую декларацию
`resources.ws-definition-schemas`: для каждого подготовленного имени задаётся
единственная пара `Ext/<имя>` ↔ `XSD/<имя>`. Файл переносится побайтно,
включая пустой файл; содержимое не разбирается как XSD или XML. Отсутствующий
каталог означает пустой список. Подготовка списка повторяется по текущему
исходному каталогу для выбранного направления, поэтому удалённые и новые файлы
не восстанавливаются из устаревшего списка импорта.

Общий параметр `resourceNames` задаёт каталог, расширения и поле списка.
`fullNames: true` сохраняет расширение в имени; по умолчанию передаётся имя
без расширения. `caseSensitive: false` сравнивает расширения без учёта регистра;
по умолчанию сравнение точное. Проверяются только непосредственные обычные
файлы; вложенные каталоги и символические ссылки исключаются. Список имеет
стабильный порядок и ограничения количества и суммарной длины имён.
Неверные параметры — ошибка настройки операции, а не аномалия содержимого.

Выбор корня владельца относится к сборке проекта. Общая подготовка не знает
про WSReference, WSDL или XSD; маршруты находятся только в декларациях.
Приёмка common не означает приёмку полного WSReference. В текущем e2e-корпусе
нет отдельных XSD: проверка положительного копирования использует точные
байты существующих WSDefinition.xml в временном каталоге и не подтверждает
смысловую проверку XSD или загрузку таких файлов в 1С.

### Подготовка XML-оболочки из исходного правила

Переносчик получает путь оболочки, пространства имён и постоянные атрибуты
из XMLRoot. Обычный объект имеет путь MetaDataObject/контейнер; корень
отдельного файла — только контейнер. Объявления xmlns становятся таблицей
пространств имён декларации, обычные атрибуты — списком with-attributes.
Конфликт префикса с URI и неверная форма параметров диагностируются при
переносе, а не обходятся специальной веткой общего Rust-преобразователя.

Если исходная функция зависит только от постоянного контекста владельца,
ограниченный анализатор TypeScript вычисляет её при переносе. Проверяются
хеш файла, положение и точный текст функции. Анализатор разбирает синтаксис
и не исполняет исходный JavaScript. Логические && и || используют короткое
вычисление; неизвестные операции, внешние зависимости и изменённый исходник
блокируют перенос. Контекст должен сохраняться при записи в JSON без потерь,
иначе специализация отклоняется. Полученный результат — прежние постоянные
атрибуты YAML-декларации, без callback в исполняемом коде.

Для предопределённых данных тип владельца известен при сборке; функция
источника определяет xsi:type четырёх вариантов без новой таблицы типов
в Rust. Проверка подготовки оболочки не заменяет полное XML → YAML → XML:
контроль исходной формы, неизвестных атрибутов и пространств имён остаётся
условием полной приёмки XMLRoot, а содержимое владельца принимается отдельно.

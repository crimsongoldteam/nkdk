## Выводы из DCS

Уточнение `AvailableFields` по исходным XML: `full.xml` и e2e-форма
`УсловноеОформление` содержат только `dcsset:field`, поэтому элемент YAML —
строка. В `selected-item.xml` присутствуют `use`, `title` или `lwsTitle` и
`viewMode`, поэтому элемент YAML — запись с обязательным `Поле` и
соответствующими необязательными свойствами. Явная `Ложь` не сокращается до
отсутствия. Полная запись с единственным `Поле` означает ту же короткую форму.
Порядок и повторы элементов значимы. Неизвестное или неверное содержимое
сохраняется общей аномалией в наименьшей обратимой границе; отдельный перечень
аномалий в декларацию объекта не добавляется. Обе формы, схема и ограничения
получаются из `rust/declarations/common/dcs-available-fields.yaml`.

1. Нужен конечный выбор схемы по ключу параметра и по дискриминатору; нельзя получить его автоматически из «любого JSON».
2. Collection<T> и T, которое само является collection, различаются по объявленному типу. Проверка Array.isArray не является договором.
3. Явный порядок выбора вариантов допустим только как часть декларации; компилятор обнаруживает коллизии известных областей. Для неразрешимых статически пересечений требуется явная политика и проверочный пример, а не молчаливый first-match.
4. Короткие формы описываются как представление конкретного полного значения, чтобы обе стороны использовали один договор. Отдельные normalize/detect функции common исключаются.
5. Текущие DCS-проекции требуют подробного развёрнутого примера ParameterValue перед замораживанием грамматики. Список нужных конструкций не доказывает, что этот пример уже написан.

### Компактное поле фильтра (2026-09-25)

`common.dcs-filter-field` задаёт соответствие XML
`xsi:type="dcscor:Field"` с текстом `Ссылка` и YAML-скаляра `.Ссылка`.
Точка — часть YAML-представления, а не смыслового имени. Обе стороны описаны
общими текстовыми шаблонами над `common.string`; XML-тип задаёт стандартная
оболочка `with-attributes`. Для явной записи `Тип: Поле` в режиме
`DesignTimeValue` сохраняется существующая отдельная проекция.

Это профиль поля, а не весь режим `Field`: выбор между полем, строкой,
примитивом, значением перечисления и системным перечислением ещё должен быть
объединён. Непрефиксованный скаляр не принимается этим узким профилем; его смысл
в полном режиме определяется общим выбором. Весь `DcsMetadataValue` остаётся
незавершённым.

### Совместный выбор значений поля (2026-09-25)

`common.dcs-field-choice` объединяет компактное поле, явную строку, значение
времени проектирования, булево, точное десятичное число и дату с секундами.
`xsi:type` выбирает XML-ветвь; YAML-форма выбирает ту же смысловую ветвь:

```yaml
Значение: .Ссылка                    # поле
```

```yaml
Значение:                           # строка с тем же содержимым
  Тип: Строка
  Значение: .Ссылка
```

`Истина` как булево остаётся скаляром; строка `Истина` получает явную запись
`Тип: Строка`. Число `9007199254740993` не округляется. Тип строки задаёт
конечное перечисление, а не проверка имени объекта в Rust. Ошибочная XML-лексика
сохраняется существующим механизмом аномалий на границе свойства.

Полный режим `Field` ещё не принят: системные перечисления, пустые состояния,
совместимость всех прежних входных форм и подключение к общему договору
`DcsMetadataValue` остаются обязательными. Пробные проверки вынесены в пакет
`nkdk-probe-dcs-fields`, чтобы не повышать предел размера крупного каталога.


### 2026-09-26 — словарь системных перечислений для СКД

Имена XML-типов определяет один конечный `qname-lexicon`, автоматически
получаемый из принятых деклараций системных перечислений. Значения переводятся
через два подготовленных индекса: `(имя, XML-код) → YAML-название` и обратный.
Это одна декларация записи с обычными выражениями поиска и ограничениями,
а не отдельный Rust-обработчик для каждого перечисления. Наполнение индексов
в проверочном пакете пока выполняет объявленный поставщик фактов; подключение
этого поставщика к рабочей сборке является отдельным незавершённым шагом.

Неизвестное значение или имя типа сохраняется общим механизмом аномалий.
Если пометка отдельного поля лишает зависимое поле данных для восстановления,
повторная проверка уточняет границу сохранения до вложенного свойства.
Ошибка отсутствующего входа или неподготовленного индекса не становится
аномалией данных. Пространство имён атрибута учитывается по URI, не по префиксу.

Проверочная матрица использует независимый корпус 678 перечислений / 3501
значения, новый YAML, неизвестные значения и URI, соседнее свойство. Отдельная
проверка двух обычных QName-атрибутов защищает независимость от `xsi:type`.
Проверки СКД перенесены из `scalars.rs` в `dcs_fields.rs`; их сценарии сохранены.
Оба пакета сохраняют предел 8 МиБ генерируемого кода.

`DcsMetadataValue` не принят целиком: остаются подключение словаря к общему
выбору Field/Primitive, фиксированный режим SystemEnumeration, пустые состояния,
выбор всех режимов по декларации свойства и проверка рабочих владельцев.
Чеклист остаётся двоичным, флажок этого объекта не установлен.


### 2026-09-26 — перечисления включены в общий Field

`common.dcs-field-value` объединяет шесть существующих вариантов Field с
одной декларацией системного перечисления. Список допустимых имён и объединённый
выбор генерируются вместе из принятых деклараций, актуальность проверяет
`node tools/rules-migration/src/dcs-enumeration-names.mjs --check`.
Компилятор допускает отсутствие `emit` только при точном совпадении конечного
набора QName вложенного атрибута и селектора. Это общий механизм языка,
без условий по именам DCS или конкретным перечислениям.

Матрица 3501 значения теперь проходит через общий Field, включая новый YAML,
неверные значения и соседние свойства. В том же договоре проверены смешанные
булево, точное число, поле и явно типизированная строка. Проверки перечислений
выделены в `probe-dcs-enumerations`; предел 8 МиБ не повышен.

Полный `DcsMetadataValue` остаётся незавершённым: требуются Primitive с
перечислениями, фиксированный SystemEnumeration, пустые состояния, выбор всех
режимов и рабочие владельцы с подготовкой индексов. Чеклист не изменён.


### 2026-09-26 — объединённый режим Primitive

`common.dcs-primitive-choice` генерируется из принятого `common.metadata-value`
и общей декларации системного перечисления. QName, уже занятые исходными
вариантами, исключаются из словаря дополнительного варианта по URI и локальному
имени. Поэтому специальные формы `ВидСравнения`, `ВидСчета` и
`ВидСравненияКомпоновкиДанных` сохраняются, остальные перечисления используют
`Тип: СистемноеПеречисление`. Все различия находятся в декларациях и их сборщике;
компилятор и исполнитель не знают имён этих типов.

Одна матрица проверяет оба режима Field/Primitive по независимому корпусу
3501 значения, новые YAML, неверные значения и соседнее свойство. Дополнены
случаи nil, строки, похожей на число, и стандартного периода. Nil сокращается
согласно унаследованному договору отсутствия; экспорт восстанавливает xsi:nil.

Общий механизм аномалий выбора исправлен: если raw-конверт не имеет смыслового
значения, его разность рассчитывается относительно XML, полученного именно
из пустого YAML через резервный вариант. Это предотвращает появление лишнего
xsi:nil, когда первоначальный вариант и резервный имеют разные пустые формы.
Перерасчёт применяется только к исключительному raw без смыслового значения.
Обычные значения сохраняют предварительно скомпилированные преобразования.

Приёмка полного `DcsMetadataValue` ещё не завершена. Новый Primitive пока
подключён к проверочному владельцу; прежний `common.dcs-primitive-value`
сохраняет старые входы до подготовки словарей у всех потребителей. Остаются
рабочие владельцы, все режимы и полный договор пустых состояний. Флажок
общего объекта не устанавливается.


### 2026-09-26 — Primitive подключён к существующим common и коллекции

`common.dcs-primitive-value` теперь использует `common.dcs-primitive-choice`;
`common.dcs-primitive-values` передаёт те же подготовленные индексы каждому
элементу. Индексы связываются у владельца, типизированные входы передаются
через декларации; в компиляторе и исполнителе условий по именам типов DCS нет.
Обновлены все найденные потребители этих двух common в каталоге деклараций.
Владелец общей матрицы тоже использует public-common, а не обращается к выбору
напрямую. Прежнего отдельного пути Primitive без перечислений больше нет.

Подготовка словарей для проверок вынесена в один помощник с общим поставщиком
фактов; повторная реализация наполнения индексов в каждом тесте не создаётся.
Матрица коллекций расширена перечислением, повторами и неизвестным значением
между двумя корректными значениями. Проверяются обычный YAML для корректных
значений, локальная аномалия, порядок и восстановление исходного XML.
Исходный случай сначала воспроизвёл ошибку: корректный Auto сохранялся как raw;
после подключения деклараций преобразуется в СистемноеПеречисление / Авто.

Полный `DcsMetadataValue` остаётся неотмеченным: ещё не завершены остальные
режимы и автоматическая сборка рабочих владельцев приложения. Подготовка
словарей в проверочном контуре не объявляется готовой инициализацией приложения.

При подключении выявлены и исправляются два общих расхождения обёрток.
Захваченные входы ранее переносились при размещении элемента коллекции,
но не записи: общий `scoped_inputs` теперь используется обоими путями.
Проверка намеренно сохраняет разный порядок входов у владельца и common.
Второе расхождение: отсутствующее значение проекции записи записывалось как
`{}`, хотя пустой объект не является её скалярным значением. Проекция теперь
выводит `null`; для DCS это соответствует существующему `toYAML.ts`, который
сохраняет null. Поэтому public-wrapper для xsi:nil имеет `Значение: null`;
предыдущая проверка прямого выбора с пропуском свойства не считалась приёмкой
публичной обёртки. Изменения относятся к проекции/областям входов, не к DCS.


### 2026-09-26 — Primitive: null отдельно от отсутствия

Используется существующее представление: внешняя запись может отсутствовать,
а присутствующая запись может содержать пустое значение nullable-выбора.
Поэтому новый специальный тип null в языке не добавляется. У обычного
Primitive отсутствующее свойство остаётся отсутствующим, а `Значение: null`
создаёт `xsi:nil="true"`. При exportNilValue=true отсутствующее свойство тоже
выводится как nil. false сохраняет обычное поведение. Null не сворачивается
в отсутствие правилом присутствия внешнего свойства.

Общий генератор записей теперь поддерживает условную каноническую форму nil,
как уже поддерживал missing и empty-element. Пространство имён xsi включается
и при отсутствующем теле записи. Никаких имён DCS в этом механизме нет.
Указание отдельного XML-типа в этой форме пока отклоняется: игнорировать его
при генерации нельзя. Переносчик разрешает exportNilValue для Primitive;
для остальных режимов ограничение остаётся до проверки их nullable-договора.

RED→GREEN: отсутствие значения ранее превращалось в лишний raw-конверт;
явное правило присутствия устранило его. Условный nil ранее отвергался стадией
генерации; после общего исправления матрица проверяет `{}` и явный null при
обоих значениях политики. Существующие XML-файлы не изменялись.

Отдельный случай primitive-type-ref.xml (`v8:Type` с текстом `*:Undefined`)
ещё требует сохранения смыслового null, а не только исходного XML. Это
не считается закрытым данным исправлением. Флажок DcsMetadataValue не меняется.


### 2026-09-26 — Договор Primitive Undefined

Примитивный XML `v8:Type` со значением `префикс:Undefined` означает YAML null;
одноимённый текст при `xs:string` остаётся строкой. Декларация
`common.dcs-primitive-text` связывает XML-тип, исходный текст и проекцию
значения существующими выражениями. Пустота проекции явно соответствует null.
Исходная запись восстанавливается через автоматически выведенную аномалию.
Скалярная проекция передаёт сохранение XML содержащему свойству: ключей
для вложенных пометок у скаляра нет. Неизвестный XML-тип также передаётся
этому механизму, а не вызывает ошибку всего преобразования.

У nullable-записи XML nil и YAML null означают отсутствующее тело; присутствие
внешнего свойства учитывается отдельно. Канонический nil ограничивается
отсутствием значения. Обычный текст не превращается в nil при включённом
exportNilValue. Неисполняемая каноническая ветвь с вычисленным false не
ограничивает выбор общего генератора. Текстовый default словаря QName
проверяется на наличие соответствующей записи словаря.

Приёмка ведётся существующими матрицами: неизменная primitive-type-ref.xml,
другая запись префикса, обычная строка с тем же текстом, одиночное значение,
коллекция с соседними повторами, отсутствие, явный null и неизвестный XML-тип.
Для полной приёмки DcsMetadataValue остаются остальные nullable-режимы и
подключение индексов в рабочем приложении; общий флажок пока не ставится.


### 2026-09-26 — Null в режимах Color и Font

Непустое значение и nullable-оболочка разделены декларативно. Оболочка
имеет одно проецируемое поле, XML nil и YAML null означают его отсутствие,
а каноническая форма отсутствующего внутреннего значения — nil. Внешнее
свойство независимо задаёт отсутствие XML/YAML: поэтому отсутствующий цвет
или шрифт не превращается в явно заданный null. В XML nil не добавляется
тип Color/Font: атрибут принадлежит только непустому внутреннему значению.

Общий генератор допускает вложенные проекции записей с их собственными
атрибутами. Структурная проекция сначала формируется как целое YAML-значение;
простой скаляр сохраняет прямую запись. Пометка проецируемого значения
читается как пометка всего значения, а не внешнего ключа свойства.
Невосстановимая внутренняя форма передаётся ближайшей границе свойства.
В Rust нет условий по именам цвета или шрифта.

Переносчик теперь принимает boolean exportNilValue для Primitive, Color и
Font. При true он использует уже проверенное общее правило внешнего свойства
«отсутствует → nil», при false отсутствие сохраняется. Null остаётся
внутренним значением и не сворачивается во внешнее отсутствие. Матрица
проверяет параметры и подключение; общий условный экспорт проверен на Primitive.
Остальные режимы с явным exportNilValue всё ещё отклоняются до их приёмки.
Флажок всего DcsMetadataValue остаётся снятым.

### 2026-09-26 — кардинальность параметра выбора

Режим `Parameter` раскрывает в обычном YAML только первый `dcscor:item`.
Дополнительные элементы XML нельзя молча терять: они автоматически
сохраняются аномалией и восстанавливаются при обратном преобразовании.
Ограничение задаётся общим параметром `maxItems: 1` у YAML-представления
`record-mapping`, без обработки по имени СКД в генераторе. Отсутствие
значения и явный null остаются разными состояниями; `exportNilValue`
управляет только экспортом отсутствующего значения. Полная приёмка
`DcsMetadataValue` по-прежнему требует проверки владельцев и индексов.

### 2026-09-26 — плоский YAML для линейной XML-цепочки

`StructureItemGroup` хранит в YAML список группировок, но в XML каждый узел
содержит `dcsset:groupItems/dcsset:item` и необязательный следующий узел
`dcsset:item` того же типа. Это не обычная коллекция соседних элементов.
Существующие семь узлов в трёх корневых цепочках e2e-формы имеют ровно по
одному элементу `groupItems` и не ветвятся. Исходная фикстура
`structureItemGroup/__fixtures__/dynamicList.xml` подтверждает ту же форму.

Нужен общий вид XML-представления последовательности — **линейная цепочка**.
Декларация указывает путь к элементу внутри узла, путь к следующему узлу и
постоянные атрибуты узла. Компилятор проверяет, что пути различимы, а
элемент последовательности имеет собственную декларацию. YAML-представление
остаётся обычной последовательностью: правила `GroupItemField` и
`GroupItemAuto` не дублируются в обходчике цепочки. При экспорте без
XML-референса каждый элемент YAML создаёт один узел цепочки в том же порядке.

Необычная структура — два элемента внутри одного узла, несколько следующих
узлов, пустой промежуточный узел, чужой атрибут или ребёнок — не должна
теряться при сокращении. Общий контроль восстановления обнаруживает разницу
и сохраняет её как автоматически выведенную аномалию на минимальной
восстанавливаемой границе. Отдельные перечни аномалий в декларации не нужны.
Нормальная цепочка должна читаться потоково; создание дерева всего XML ради
каждого значения не принимается без замера и сравнения с потоковым вариантом.

Здесь используется уже существующий `element-sequence` с дополнительным
маршрутом `next`; обычные коллекции без `next` сохраняют прежний путь:

```yaml
xml:
  kind: with-attributes
  attributes: [{name: xsi:type, value: {qname: dcsset:StructureItemGroup}}]
  content:
    kind: element-sequence
    path: [dcsset:groupItems, dcsset:item]
    next: [dcsset:item]
    item: {kind: declared}
```

`path` относится к текущему узлу цепочки; `next` указывает вложенный узел.
Их первые имена должны различаться. Атрибут оболочки применяется к каждому
создаваемому узлу, а элемент обрабатывается той же декларацией, что и в
обычной коллекции.

### 2026-09-27 — полная матрица ParameterValue перед расширением

Оболочка параметра должна быть единой для обычного `ParameterValue` и
`SettingsParameterValue`: различие `xsi:type` задаётся параметром декларации.
Имя параметра поступает от владельца, а XML-имя проверяется. Уже проверены
в обе стороны цвет, явное `use=false`, `viewMode`, `userSettingID`, оба варианта внешнего типа, неверный
цвет и несовпадающее имя; `Авто` пока выводится в полной форме
`Значение: Авто`. Это не приёмка всего объекта.

Для поля `value` парные декларативные пустые формы означают именно явное
значение: XML `xsi:nil="true"` ↔ YAML `Значение: null`. Если XML-элемента
`value` нет, ключ `Значение` отсутствует. Общий генератор хранит этот признак
у поля записи, поэтому строка коллекции не требует отдельной nullable-оболочки
или обработчика DCS. Лишние атрибуты у `nil` сохраняются как аномалия.

| Профиль значения | Исходный пример | Требуемое различие |
|---|---|---|
| `Color` | e2e `CommonForms/УсловноеОформление/Ext/Form.xml`: `ЦветФона`, `ЦветТекста` | Обычный цвет и короткое `Авто`; отсутствие, nil и чужой текст не смешиваются. |
| `Font` | та же форма: `Шрифт`, `v8ui:Font` | Объектные ключи шрифта не трактуются как имя параметра; ошибки атрибутов остаются аномалиями. |
| `Primitive`, `Field`, `DesignTimeValue` | формы динамического списка и [исходные сценарии](../../../../packages/rules/metadata/commonObjects/dataCompositionSystem/parameterValue/__fixtures__/data.ts) | `xs:string`, `dcscor:Field`, многоязычный и форматированный текст; явный `Тип` не теряется. |
| `TypeLink`, `Parameter`, `SystemEnumeration` | те же исходные сценарии | Профиль вложенного значения выбирается правилом свойства, неизвестное значение не прерывает импорт. |
| `ChoiceParameterLinks` | исходный сценарий с одним `dcscor:value` и несколькими `dcscor:item` внутри | Массив ссылок — одно составное значение, а не несколько соседних значений параметра. |
| Несколько значений | исходный сценарий `fewValues` с двумя `dcscor:value` | Порядок и количество внешних узлов восстанавливаются отдельно от внутренней коллекции значения. |
| Настройки и рекурсия | XML `dcsset:*`, вложенные `dcscor:item` | `viewMode`, ID, представление, дочерние параметры, предел глубины и аномалии на точном вхождении. |

Промежуточные DCS-проекции `Color` и `Font` ошибочно направляли составной
выбор в обработку текста. Прямые ссылки на общие `common.color` и
`common.font-normal` с XML-различением по `xsi:type` уже прошли проверку в
одной оболочке без изменения компилятора. Остальные профили следует добавлять
к ней тем же способом, сохраняя непересекающиеся YAML-формы. Для короткого
`Авто` требуется общий обратимый
литеральный вариант сокращения записи; нынешнее сокращение захваченного текста
не выражает константный вложенный вариант.

При размещении варианта вложенного выбора компилятор обязан подставлять
входы и параметры внешней ссылки в ссылки выбранного варианта. Иначе
вложенный `common.i8n-text` обращается к номеру входа из своей декларации,
который у владельца занят индексом стилей. Общее правило подстановки
проверено для `userSettingPresentation` в формах `xs:string` и
`v8:LocalStringType` вместе с цветом в той же оболочке; специального
обработчика представления нет. Тот же договор проверен на цвете
`style:СпециальныйЦвет`: выбранный вариант получает индекс элементов
стиля от владельца и восстанавливает ссылку без сырого XML.

Для `dcscor:use` обычное отсутствие означает разрешённое значение.
`false` остаётся явным YAML-полем, а редкое явное XML `true` сокращается
с автоматической пометкой формы: при обратном преобразовании узел не теряется.
Это задаётся общей таблицей присутствия поля, без обработки `use` в
генераторе.

Следующий шаг для остальных значений — фиксировать профиль по декларации
свойства владельца. Один и тот же YAML-скаляр может обозначать цвет,
`dcscor:Field`, ссылку на тип или системное перечисление; выбор по тексту
значения был бы неоднозначен. Исходный `valueType` и при необходимости
`typeSE` должны попадать в сгенерированную привязку к общему договору,
а не в ветвление Rust-исполнителя. Общая оболочка `ParameterValue` остаётся
одной; профиль значения специализируется при сборке. Для вариантов с
`Тип` и `Значение` эти ключи должны располагаться на уровне самой оболочки,
как в существующем YAML, без вложенной карты внутри `Значение`.

Специализация обязана ограничивать **обе стороны** выбора: правило параметра
`ЦветФона` не должно принимать `dcscor:Field`, а правило `Текст` с профилем
`DesignTimeValue` не должно принимать `v8ui:Color`. Если XML содержит чужой
тип, импорт сохраняет его как выведенную аномалию на ближайшем свойстве YAML
и продолжает преобразование соседних полей. Ограничение задаётся профилем
в декларации владельца; перечислять аномалии и писать обработчик для каждого
имени параметра нельзя. Реализация должна разделять машинный код общей
оболочки между профилями, чтобы добавление варианта не размножало всю запись.

Переносчик проверяет эту статическую привязку отдельно от сборки коллекции:
для прямых свойств `AppearanceFieldsRules` он распознаёт все 12 профилей, но
не объявляет их готовыми по отдельности. В XML они повторяют путь
`dcscor:item`; общая коллекция должна сопоставлять элемент с декларацией по
`dcscor:parameter`, сохраняя повторы, порядок и неизвестные имена как аномалии.
До появления такой коллекции результат переноса остаётся заблокированным.

В `FilterItem` значения `DcsField` и `DcsBoolean` имеют разные контракты.
Первое уже задаётся `common.dcs-filter-field`: XML `dcscor:Field` ↔ YAML
`.Ссылка`. Второе — строка XML с `xsi:type="xs:boolean"`, которая в YAML
остаётся **строкой** `"true"` или `"false"`, как в существующем преобразовании.
Декларация ограничивает обычные значения этими двумя строками; иное значение
и чужой XML-тип автоматически сохраняются как аномалия.

Для `ChoiceParameterLinks` прямой вариант
`common.dcs-choice-parameter-links-items` уже прошёл проверку с одним и
двумя внутренними пунктами. Промежуточную обёртку с YAML-проекцией
компилятор выбора пока не распознаёт как последовательность; прямой вариант
сохраняет единую общую декларацию элементов без дублирования правил.

### 2026-10-09 — различие обычного поля и поля фильтра

Режим Field построителя `MetadataDcsMetadataValue` использует уже существующую
декларацию `common.dcs-parameter-field-value`: XML `dcscor:Field` с текстом
`Реквизит1` соответствует YAML `Реквизит1`. Договор поля фильтра с YAML
`.Реквизит1` остаётся отдельной проекцией. Переносчик выбирает форму по исходному
параметру правила, а не по специальной ветке в Rust.

Обычные примеры девяти профилей проверяются общей матрицей из исходных фикстур.
Проверка сохранения всего XML и проверка локальности аномалии разделены:
внешний raw-конверт, восстановивший XML, сам по себе не закрывает требование
сохранить соседние смысловые значения и узкую границу пометки.


При уточнении аномалии общий механизм обязан сохранять три границы:

- строка восстанавливается по положению текущей вложенной коллекции в потоке
  YAML; имя свойства от корня не определяет её однозначно;
- отсутствующий соседний вариант не получает конверт и не становится
  присутствующим; пустой XML-элемент проверяется отдельно;
- атрибут выбора варианта сохраняется при уточнении дочернего значения, если
  его принимает сама дочерняя декларация. Атрибут, принадлежащий только
  внешнему выбору, отделяется от содержимого.

Эти правила выводятся из структуры деклараций и действуют для всех объектов.
Для сокращённой коллекции единственный элемент с аномалией допускает явную
форму списка: так пометка остаётся на элементе, а смысловые данные, соседние
поля и порядок не теряются.


В `dscMetadataTypedValue` кавычки являются частью смысловой записи строки,
а не только оформлением YAML. Например, XML `xs:string` с текстом `.PDF`
получает YAML-значение `'.PDF'`; поле `dcscor:Field` получает `.PDF`.
Оба направления выводятся из пары текстовых шаблонов: XML содержит поле,
YAML — апостроф, поле, апостроф. Пустая строка становится `''`.

Пустой `v8:ValueListType` описывается записью с пустым `valueType` и
`lastId = -1`; сокращение `СписокЗначений` восстанавливает эти же поля.
Литерал сокращения участвует в общем автомате выбора, без отдельного
обработчика списка. Нормальная форма и отклонения определяются объявленными
полями и их типами; дополнительные XML-элементы не игнорируются.


Ссылки `dscMetadataTypedValue` имеют одну смысловую декларацию: корень,
имя объекта и имя значения через точку. Корни выводятся из общего словаря
путей метаданных. Нормальный XML использует русские имена и тип
`dcscor:DesignTimeValue`; прежние английские корни и `EmptyRef` принимаются
через существующий `accept` словаря. Например,
`Catalog.Организации.EmptyRef` означает
`Справочник.Организации.ПустаяСсылка`. Исходный `xr:DesignTimeRef` и прежнее
написание сохраняются общей аномалией формы, а новый YAML экспортируется
с каноническим типом независимо от старого источника.

Часть текстового шаблона может сама быть декларативным текстовым выбором.
Её читает тот же автомат выбора, проверяет тот же договор, а запись возвращает
текстовую часть без дополнительного оформления YAML. Точный вариант словаря
имеет своё конечное множество написаний; общий вариант имени остаётся
резервным. Ограничения имени не исчезают при вложении в шаблон. Никаких
проверок по именам объектов СКД в оркестраторе не требуется.


Пустая позиция последовательности обозначается `{}` и означает отсутствие
смыслового значения, а не пустую строку. Без сохранённой пометки она не создаёт
XML-узел: это существующий договор `dscMetadataTypedValue/toXML`. Если исходный
XML содержит `xsi:nil`, общий механизм сохраняет его на этой позиции локальным
`!xml/raw`; соседние позиции и порядок остаются обычными данными. Отдельное
перечисление аномалий в декларации не требуется. В пустом конверте смысл `{}`
подразумевается; повторять `$значение: {}` не требуется.

`v8:Type` с QName `Undefined` в пространстве
`http://v8.1c.ru/8.2/data/types` также означает отсутствие значения. QName
описан обычным текстовым шаблоном с привязанным пространством имён; условие
сокращения задано на варианте выбора. Исходная форма сохраняется автоматически.
Пометка хранит QName как пару пространства имён и локального имени: `t` и
любой иной XML-префикс обозначают одно значение. Служебный литерал декларации
`Неопределено` при этом в смысловой YAML не выводится.

Открытая коллекция с `xml.path: []` повторяет собственный элемент свойства.
Его имя и пространство имён берутся из размещения свойства у владельца.
Компилятор разделяет этот путь на родительский контейнер и элемент списка;
дополнительный вложенный XML-элемент не создаётся. Это общий режим, без
условий по типу СКД. Атрибуты контейнера для такой коллекции не допускаются:
у неё нет отдельного контейнера, к которому их можно присоединить.


### Принятые значения и параметры: 2026-10-09

Девять профилей `dcsMetadataValue` выбираются переносчиком по исходным
параметрам правила; отдельного преобразователя для каждого свойства нет.
Для вложенной многоязычной строки сохраняется пустое состояние через
существующий параметр I8nText `preserveEmptyXML`. Исходная форма пустого
LocalStringType, UUID с отличающимся XML-типом и Type/Undefined сохраняется
общим механизмом локальных аномалий, без новых обработчиков Rust.
Неразрешённая ссылка Color остаётся явным текстовым значением по принятому
договору Color, а не исчезает из YAML.

Приёмка common отделена от полной формы: все 12 свойств `dcsParameter`,
коллекция с соседями, повторениями и аномалиями принимаются здесь; построение
индекса владельца с адресацией `yamlPath` проверяется при сборке полной формы.
Рабочие источники фактов оформления и перечислений общие с каталогом.

### Поле набора данных: приёмка 2026-10-09

Все 15 свойств DataCompositionSchemaDataSetField и три вида выражаются
общими записями, условиями и коллекциями. Отсутствующая коллекция без своего
контейнера не владеет пустым корнем родителя. Проекция атрибутов обязана
сохранять пространства имён QName-значений, даже если обычный экспорт меняет
их префиксы. Схема словаря XML QName ограничивает смысловые YAML-значения.
Отклонения и изменение порядка сохраняет общий механизм аномалий.
[Приёмка и ограничения](../../reports/2026-10-09-dcs-data-set-field.md).

### Элемент сравнения отбора: 2026-10-09

Все сериализуемые свойства сравнения и постоянный XML-тип собираются из
исходной декларации владельца. runtimeOnly не является смысловым свойством;
исключение должно иметь явную запись происхождения. Неявное значение выбора
относится к единственному подходящему скалярному варианту декларации, а не
к отдельному обработчику UserSettingsID. XML-проекция списка поддерживает
как вложенный контейнер, так и элементы непосредственно под корнем.
[Проверки и оставшиеся границы](../../reports/2026-10-09-dcs-filter-comparison.md).

### Рекурсивный отбор и пустые контейнеры: 2026-10-09

Группа содержит тот же объявленный выбор, что и верхняя коллекция: сравнение
или группа. Наличие YAML-ключа «ТипГруппы» выбирает группу; его отсутствие,
включая пустую запись, выбирает сравнение. Запасной вариант применяется после
чтения всех ключей, поэтому поздний ключ группы не меняет смысл в зависимости
от порядка. Отдельные обработчики сравнения и группы в оркестраторе запрещены.

Рекурсия значений через общий фрагмент допустима; цикл самого `compose`
остаётся ошибкой декларации. XML-тип берётся из исходной регистрации. Прямое
создание смысловой последовательности выбора без чтения XML/YAML пока не
поддержано; преобразование обоих форматов поддерживается.

Если источник не записал `comparisonType`, обычный экспорт пустого сравнения
добавляет `Equal`. Это различие формы автоматически сохраняется как аномалия.
Пропущенные типизированные списки не должны появляться в YAML пустыми массивами.
Аномалия проекции библиотечной записи не должна раскрывать внутреннее имя
служебного поля `item`; здоровые поля и соседние элементы остаются читаемыми.

Пара исходных параметров `defaultValueXMLRaw: {}` и
`evaluateWhenYAMLMissing: true` означает пустой **контейнер**, а не новый
пустой элемент коллекции. Переносчик выражает это общим правилом присутствия
на границе свойства для объявленных записей и коллекций. Без этих параметров
явно пустой необязательный контейнер и отсутствие различаются автоматически.
Подготовленные индексы прикрепляются к объекту-владельцу; библиотека и фрагмент
получают их через входы и не выбирают поставщика самостоятельно.

### Условное оформление: полный договор

Все 18 свойств элемента и четыре свойства владельца собираются из rules.ts.
Отбор внутри оформления ссылается на ту же рекурсивную библиотеку, доступные
поля и оформление — на принятые common; специальных обработчиков нет.
Пустые контейнеры восстанавливаются правилом присутствия на границе свойства.
Повторы, неверное значение и отсутствие исходного контейнера проверяются
вместе со здоровыми соседями. Смысловой xs:string сохраняет !xml/string,
а обычный многоязычный текст использует принятый краткий вид.
[Примеры и границы приёмки](../../reports/2026-10-09-dcs-filter-appearance-acceptance.md).

# TypeDescription: идентификаторы типов

Дата: 2026-05-08

Статус: выбран подход с явным полем `typeId`; реализация не начата.

## Контекст

Разбор short round-trip XML -> модель -> XML показал потерю узла:

```xml
<dcssch:valueType>
	<v8:TypeId>8c1e3694-da12-44d5-8b1f-d134b89a1282</v8:TypeId>
</dcssch:valueType>
```

Сейчас `TypeDescription` импортирует только `v8:Type` и `v8:TypeSet`. Если описание типа состоит только из `v8:TypeId`, модель становится пустой, `importTypeDescriptionFromXML` возвращает `undefined`, и родительский узел `dcssch:valueType` исчезает при экспорте.

Проблема общая для `TypeDescription`, а не частная для `DCSParameter`.

## Выбранный подход

Добавить в модель `TypeDescription` явное поле:

```ts
type: string[]
typeId?: string[]
```

Семантика:

- `type` продолжает хранить строковые имена типов из `v8:Type` и `v8:TypeSet`;
- `type` остается обязательным массивом; для TypeId-only описания используется `type: []`;
- `typeId` хранит значения из `v8:TypeId`;
- один `v8:TypeId` и несколько `v8:TypeId` в XML представлены массивом строк;
- `TypeDescription` с пустым `type` и без `typeId` по-прежнему считается пустым и импортируется как `undefined`;
- `type` и `typeId` могут сосуществовать, если такой XML встретится.

Этот подход не смешивает имена типов и идентификаторы типов в одном массиве, поэтому формат остается явным.

## XML

`TypeDescriptionXML` расширяется полем:

```ts
"v8:TypeId"?: string | string[]
```

Импорт:

- нормализует `v8:TypeId` к массиву строк;
- добавляет `typeId` в результат, если массив не пуст;
- для XML только с `v8:TypeId` возвращает модель `{ type: [], typeId: [...] }`;
- возвращает `undefined` только когда `type` пустой и `typeId` отсутствует.

Экспорт:

- выводит `v8:TypeId` из `typeDescription.typeId`;
- один элемент может экспортироваться как одиночный узел, несколько элементов - как массив узлов;
- существующий порядок XML-узлов для `v8:Type`, `v8:TypeSet`, квалификаторов и `v8:TypeId` должен быть стабильным через тестовую фикстуру.

## YAML

`TypeDescriptionYAML` расширяется объектной формой:

```yaml
ИдентификаторТипа:
  - 8c1e3694-da12-44d5-8b1f-d134b89a1282
  - 6b99868d-5f3a-44e2-bb6d-3ad3b5d3198c
```

Импорт YAML:

- строка и массив строк продолжают работать как раньше для обычных типов;
- объект с `ИдентификаторТипа` импортируется в `typeId`;
- если объект содержит пустой массив `ИдентификаторТипа`, результат считается пустым;
- смешанную объектную форму с обычными типами не вводим в этой задаче.

Экспорт YAML:

- если `typeDescription` содержит только `typeId`, результатом будет объект с `ИдентификаторТипа`;
- если есть обычные `type`, старый строковый или массивный формат сохраняется;
- смешанный случай `type` + `typeId` можно экспортировать объектом только после отдельного решения, поэтому текущая задача покрывает и тестирует сценарий с `type: []` и одними идентификаторами типов.

## Тесты

Добавить фикстуру в `packages/core/metadata/commonObjects/typeDescription/__fixtures__/data.ts` с двумя UUID в `typeId`.

Эта фикстура должна проходить существующие табличные тесты:

- `fromXML.test.ts` проверяет импорт XML в модель с `typeId`;
- `toXML.test.ts` проверяет экспорт модели в XML с двумя `v8:TypeId`;
- `fromYAML.test.ts` проверяет импорт YAML-объекта `ИдентификаторТипа`;
- `toYAML.test.ts` проверяет экспорт модели в YAML-объект `ИдентификаторТипа`.

Отдельно полезен тест на пустой YAML-объект с `ИдентификаторТипа: []`, чтобы зафиксировать поведение `undefined`.

## Не входит в эту задачу

- Исправление конкретного `DCSParameter` round-trip через отдельную фикстуру.
- Поддержка смешанной YAML-формы, где одновременно заданы обычные типы и `ИдентификаторТипа`.
- Изменение существующих XML-фикстур проекта.
- Новый слой правил fromXML/toXML/fromYAML/toYAML вне текущих модулей `TypeDescription`.

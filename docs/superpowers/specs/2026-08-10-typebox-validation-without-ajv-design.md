# Переход schema validation с AJV на TypeBox без патча библиотеки

## Цель

Убрать AJV из структурной валидации YAML-проекта и заменить его runtime-компиляцией TypeBox 1.3.11 в каждом worker.

Переход должен:

- сохранить существующий интерфейс `ValidationSchemaValidator` с методами `Check` и `Errors`;
- возвращать не более одной структурной ошибки на файл, как текущий AJV с `allErrors: false`;
- быстро выбирать ветвь `oneOf` по `discriminator`;
- не требовать патча или форка TypeBox;
- удалить AJV standalone generation и связанные зависимости;
- сохранить или снизить расход памяти при сопоставимой скорости полной валидации.

## Контекст

Схемы проекта уже строятся средствами TypeBox, но `compileValidationSchema` преобразует их для AJV. Для production worker сборка дополнительно генерирует `projectValidationAjvStandalone.js`, а core и MCP загружают или копируют этот модуль.

TypeBox 1.3.11 компилирует обычные схемы быстро, но не использует JSON Schema `discriminator`: стандартный `oneOf` последовательно проверяет все ветви. Его `Errors()` также продолжает интерпретировать схему после достижения `Settings.maxErrors`, поэтому простое ограничение `maxErrors: 1` не обеспечивает раннего выхода.

Исправленный прототип на `/Users/nikita/git/sed_nkdk/cf` показал для варианта без патча TypeBox:

- 10 091 корректный файл: 253–277 мс на validation pass, среднее около 263 мс;
- тот же набор решений valid/invalid, что у AJV;
- 2 036 форм с искусственно внесёнными структурными ошибками верхнего уровня: одна ошибка на файл за 29–33 мс;
- peak RSS около 687 MiB;
- компиляция полного набора использованных схем около 259 мс.

Текущий AJV standalone на корректном проекте служит ориентиром около 271 мс и 800 MiB peak RSS. Значит, вариант TypeBox без патча сопоставим по скорости и расходует меньше памяти.

## Рассмотренные варианты

### Выбранный: локальный адаптер TypeBox

Перед компиляцией адаптер преобразует только дискриминированные `oneOf` в TypeBox refinement, который выбирает ветвь по значению дискриминатора и переиспользует её лениво созданный валидатор. Сбор первой ошибки прерывается локальной обёрткой над публичным механизмом `Locale`.

Преимущества:

- TypeBox остаётся обычной зависимостью без `pnpm patch`;
- вся специальная семантика находится в validation-слое проекта;
- обновление TypeBox проверяется тестами адаптера, а не переносом патча на новую версию;
- существующие схемы и их статические типы не меняются.

Недостаток: `~refine` является TypeBox-расширением JSON Schema, а структурированную ошибку выбранной ветви нужно передавать через локальный служебный payload. Временную замену `Locale` требуется аккуратно изолировать.

### Отклонённый: `pnpm patch` TypeBox

Патч `oneOf` и error engine даёт более прямую реализацию и потенциально меньший сгенерированный код, но привязывает проект к внутренней структуре конкретной версии TypeBox. При каждом обновлении библиотеки патч пришлось бы проверять и, возможно, переносить.

### Отклонённый: собственный компилятор ошибок

Локальный компилятор мог бы формировать первую ошибку без глобальной настройки `Locale`, но потребовал бы повторить значительную часть JSON Schema semantics: объекты, массивы, `$ref`, рекурсию, объединения и форматы. Это существенно больше выбранного решения.

## Архитектура

### Подготовка схемы

Новый модуль validation-слоя подготавливает схему непосредственно для TypeBox. Он рекурсивно обходит корневую схему и внешний контекст `$ref`, сохраняя нативные TypeBox-конструкции, включая `type: "undefined"`.

Обычные `oneOf` без `discriminator` не преобразуются.

Для `oneOf` с `discriminator.propertyName` подготовка:

1. разрешает значение дискриминатора каждой ветви из обязательного свойства с `const` или одноэлементным `enum`;
2. умеет находить это свойство непосредственно в ветви, через `$ref` и внутри `allOf`;
3. проверяет, что значения определены, уникальны и присутствуют во всех ветвях;
4. создаёт таблицу `значение -> схема ветви` и лениво компилирует каждую выбранную ветвь с повторным использованием валидатора;
5. заменяет исходный `oneOf` на `~refine` с двумя callback: `check` выбирает ветвь и вызывает её `Check`, `error` возвращает служебный payload с первой ошибкой выбранной ветви;
6. для отсутствующего, неверного по типу или неизвестного значения создаёт в payload синтетическую ошибку на поле дискриминатора.

Если контракт дискриминатора нарушен, компиляция завершается понятной ошибкой с путём схемы. Молча возвращаться к медленному стандартному `oneOf` нельзя: это скроет ошибку схемы и вернёт исходную проблему производительности.

Преобразование не изменяет исходные схемы. Для повторно используемых объектов и циклических ссылок оно использует мемоизацию.

### Компиляция и кэш

`compileValidationSchema` перестаёт создавать AJV и вызывает `Compile` из `typebox/compile` для подготовленной корневой схемы и контекста ссылок.

Возвращаемый адаптер сохраняет текущий договор:

```ts
interface ValidationSchemaValidator {
  Check(value: unknown): boolean
  Errors(value: unknown): [boolean, ValidationSchemaError[]]
}
```

Каждый worker создаёт `ValidationSchemaCache` для своего `ConfigurationContext` и компилирует набор схем один раз при инициализации. Последующие файлы используют существующие кэши по правилу формы и `itemType`.

Runtime-компиляция является частью времени готовности worker. Standalone-модуль больше не создаётся и не загружается.

### Одна ошибка с ранним выходом

`validateParsedFile` продолжает вызывать только `schema.Errors(value)`. Внутри адаптер:

1. запускает скомпилированный `Check`;
2. для корректного значения возвращает `[true, []]`;
3. для некорректного значения запоминает текущий `Locale` TypeBox;
4. временно устанавливает callback, который локализует первую полученную ошибку прежним `Locale` и выбрасывает внутренний sentinel;
5. вызывает стандартный `Errors()` TypeBox;
6. если получена ошибка `~refine` со служебным payload, заменяет её ошибкой выбранной ветви и добавляет родительские `instancePath` и `schemaPath`;
7. перехватывает только собственный sentinel и возвращает одну ошибку;
8. восстанавливает прежний `Locale` в `finally` при любом исходе.

`Errors()` TypeBox синхронен, а validation выполняется внутри отдельного worker isolate. Между установкой и восстановлением `Locale` не должно быть `await`, пользовательских callback или другой работы. Неизвестные исключения не подавляются.

Такой ранний выход сохраняет работу стандартного TypeBox error engine для `$ref`, массивов, объектов и обычных объединений, но прекращает обход сразу после первой итоговой ошибки.

### Диагностики дискриминатора

Ошибка внутри выбранной ветви должна сохранять точный `instancePath`, `keyword` и параметры TypeBox. `typeboxErrorsToDiagnostics` продолжает вычислять координаты YAML по `instancePath`.

Для отсутствующего, неверного по типу или неизвестного значения дискриминатора refinement формирует синтетическую ошибку на самом поле. Путь, координаты, severity и source сохраняются. Текст может отличаться от AJV-специфичного сообщения и должен описывать TypeBox-условие нейтрально.

Ошибка выбранной ветви сначала имеет путь относительно корня этой ветви. Перехватчик refinement добавляет путь родительского значения, поэтому вложенные и рекурсивные дискриминаторы сохраняют полный `instancePath`. Минимальный прототип подтвердил пути `/Child/count` для ошибки ветви и `/Child/Kind` для неизвестного дискриминатора.

## Изменения production path

### Core

- заменить внутренности `compileValidationSchema` на адаптер TypeBox;
- удалить AJV-специфичные преобразования, custom keyword `x-nkdk-undefined` и обёртку standalone-функции;
- перевести `createProjectValidationWorkerSchemaCache` на обычный `createValidationSchemaCache(context)` и runtime-компиляцию;
- удалить standalone generator, loader, types, entrypoint и их тесты;
- убрать генерацию `projectValidationAjvStandalone.js` из `packages/core/scripts/build.mjs`;
- убрать `ajv` и `ajv-formats` из зависимостей и списка external core build.

### MCP

- удалить сборку и копирование `projectValidationAjvStandalone.js`;
- обновить publish/build тесты;
- убрать `ajv` и `ajv-formats` из зависимостей и списка external.

Публичные API schema validation и формат `Diagnostic` не меняются.

## Тестирование

### Адаптер схем

- простой объект, массив и скаляр;
- внешний и локальный `$ref`;
- рекурсивный `Type.Cyclic`;
- нативный `undefined`;
- обычный `oneOf` без дискриминатора;
- дискриминатор непосредственно в ветви, через `$ref` и `allOf`;
- вложенные и рекурсивные дискриминированные объединения;
- ошибка компиляции при отсутствующем или повторяющемся значении дискриминатора.

### Ошибки

- корректное значение возвращает пустой массив;
- некорректное значение возвращает ровно одну ошибку;
- ошибка выбранной ветви содержит полный вложенный `instancePath`;
- неизвестный, отсутствующий и неверный по типу дискриминатор указывает на его поле;
- обычный `oneOf` по-прежнему выдаёт полезную первую ошибку;
- прежний `Locale` восстанавливается после корректной ошибки, неожиданного исключения и повторного вызова;
- служебный payload refinement не выходит за границу адаптера и преобразуется в обычный `ValidationSchemaError`;
- адаптер не подавляет исключения, не являющиеся его sentinel.

### Интеграция и сборка

- тесты `validateFile` проверяют путь, координаты и сообщение первой ошибки;
- worker и MCP build не создают и не ожидают AJV standalone-файл;
- поиск по production-коду не находит импортов AJV;
- полный проект `/Users/nikita/git/sed_nkdk/cf` даёт тот же набор valid/invalid файлов;
- отдельная ошибочная выборка подтверждает одну диагностику на файл;
- повторный профиль фиксирует validation time, compile time и peak RSS.

Перед завершением выполняются обязательные проверки проекта:

```bash
pnpm test
pnpm duplicates -- --base <base-commit>
pnpm test:architecture:rules
pnpm test:architecture
```

## Риски и ограничения

### Глобальный `Locale`

`Locale` является состоянием TypeBox на уровне isolate. Риск ограничивается синхронной секцией `try/finally`; тесты должны доказывать восстановление состояния. Если TypeBox перестанет вызывать `Locale` при добавлении ошибки, тест раннего выхода завершится ошибкой и обновление зависимости будет остановлено.

### Служебный payload refinement

Callback `error` у TypeBox refinement типизирован как возвращающий сообщение. Адаптер намеренно возвращает из него локальный структурированный payload и распознаёт его только внутри собственного `Locale` callback. Это приведение типа должно находиться в одном именованном переходнике и быть покрыто тестами; служебное значение не становится частью публичного формата ошибок.

Текущий прототип укладывается примерно в 259 мс компиляции и 687 MiB peak RSS на целевом проекте. Эти значения являются контрольными ориентирами, а не жёсткими тестовыми порогами.

### Одна ошибка

Validation намеренно возвращает только первую структурную ошибку файла. Это соответствует текущей настройке AJV `allErrors: false`. Исчерпывающий список ошибок не входит в эту итерацию.

## Критерии готовности

- production validation не импортирует AJV и не загружает standalone AJV module;
- TypeBox не изменён патчем или форком;
- корректный целевой проект имеет тот же результат valid/invalid;
- ошибочный файл получает ровно одну диагностику с корректным YAML-путём;
- вложенный дискриминатор проверяет только выбранную ветвь;
- core и MCP собираются без standalone validation file;
- обязательные тесты и архитектурные проверки проходят;
- профиль не показывает существенного ухудшения относительно прототипа без патча.

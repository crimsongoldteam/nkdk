# Досрочное освобождение YAML при XML-import

## Контекст

XML-import выполняется в два прохода. В первом worker преобразуют XML в YAML,
собирают факты и частичные индексы, но сохраняют полный `PreparedImportYaml`
каждого успешного задания в памяти. После построения общего индекса второй
проход уточняет отложенные значения, записывает YAML и освобождает его.

В production единственный тип с `finalizeImportedYAML` — `DataPath`. Полный
индекс нужен только для перевода стандартных реквизитов внутри путей к данным,
но сейчас откладывается любой `DataPath`. Кроме удержания YAML это запускает
resolver и для путей, в которых вообще нет потенциально переводимых сегментов.
Поэтому до второго прохода в памяти остаются все YAML, включая файлы, которые
точно не изменятся.

Текущий formatter также переводит отключённые пути с `~`, хотя такие пути не
должны преобразовываться или валидироваться. Новый предварительный предикат
исправляет это поведение.

## Цель

После первого прохода удерживать в памяти только YAML, содержащие хотя бы один
`DataPath`, который потенциально требует перевода стандартного реквизита.
Остальные YAML нужно сразу записывать в Проект и освобождать. Все созданные
связанные файлы нужно записывать и освобождать на первом проходе независимо от
того, удерживается ли основной YAML до второго прохода.

Оптимизация применяется ко всем заданиям XML-import, а не только к формам.

## Не входит в границы

- Точное определение стандартного реквизита с учётом владельца на первом
  проходе.
- Изменение результата перевода поддерживаемых стандартных реквизитов, кроме
  отключённых путей с `~`, которые теперь сохраняются без изменений.
- Транзакционная запись Проекта и удаление частичного результата при ошибке.
- Изменение XML-фикстур.

## Договор финализации импортированного значения

У property-типа остаётся существующая возможность `finalizeImportedYAML`,
которая выполняет окончательное преобразование с полным индексом.

Дополнительно вводится необязательный нейтральный предикат
`requiresImportedYAMLFinalization(value)`. Он отвечает только на вопрос: может
ли конкретное значение измениться при `finalizeImportedYAML`.

Правила договора:

- если финализатор отсутствует, значение не откладывается;
- если финализатор есть, а предикат отсутствует, значение всегда откладывается;
- если присутствуют оба, значение откладывается только при результате `true`;
- общий orchestration-слой вызывает возможности property-типа и не знает о
  `DataPath`, формах или стандартных реквизитах.

Такой безопасный режим по умолчанию позволяет будущим property-типам добавлять
финализацию без риска преждевременной записи.

## Быстрый предикат `DataPath`

Поля путей к данным определяются исключительно по `rule.type === "DataPath"`.
Имена YAML- или XML-полей не участвуют в распознавании: у разных rules одно и
то же значение `DataPath` может находиться под разными ключами.

Type-rule `DataPath` использует общий реестр стандартных реквизитов как
единственный источник имён. В набор включаются только пары, у которых
внутреннее и YAML-имя различаются, включая колонки, вложенные в декларации
стандартных табличных частей.

Проверка консервативна: ложное срабатывание допустимо и лишь оставляет YAML до
второго прохода; ложный пропуск недопустим.

Порядок проверки:

1. Нестроковое значение возвращает `false`.
2. Значение с первым символом `~` возвращает `false`: отключённые пути не
   преобразуются, не валидируются и не передаются resolver.
3. Путь без точки возвращает `false`, как и существующий formatter.
4. Одна заранее скомпилированная проверка ищет стандартное имя в границах
   сегмента. Начало сегмента — начало строки или `.`, конец — `.`, `[`
   либо конец строки. Поэтому `LineNumber` находится в
   `Объект.Товары.LineNumber[0]`, но не в `Объект.MyLineNumber`.

Ожидаемая реализация — скомпилированное один раз регулярное выражение вида:

```text
(?:^|\.)(?:LineNumber|Ref|Code|...)(?=\.|\[|$)
```

Имена экранируются при построении выражения. Кэш проверки сбрасывается при
изменении реестра в тестах. Перед окончательным выбором реализация сравнивается
с `split + Set` на одинаковом наборе реальных путей; в production остаётся
вариант с меньшим временем без изменения описанной семантики.

Для двух направлений используются разные проекции того же реестра:

- `internal-to-yaml` ищет внутренние имена;
- `yaml-to-internal` ищет YAML-имена.

Formatter вызывает предикат до построения контекста и запуска resolver. Если
совпадений нет, он сразу возвращает исходную строку. Следовательно, пути без
стандартных реквизитов не обрабатываются ни на первом, ни на втором проходе и
не проходят лишнее разрешение в остальных операциях.

Этот же предикат используется там, где formatter решает, нужно ли выдавать
`unresolved_data_path`. Отдельного списка стандартных имён для откладывания,
преобразования и диагностики не возникает.

## Поток данных

Все обычные преобразования свойств `importFromXML` и `exportToYAML`
завершаются в первом проходе до решения о досрочной записи. Например,
`Catalog` к этому моменту уже преобразован в `Справочник`.

`DataPath` при XML-import на первом проходе сохраняется без преобразования:
общий индекс и owner cache ещё недоступны. Предварительный предикат не
преобразует путь, а только решает, нужно ли удерживать содержащий его YAML до
второго прохода. Он не отключает и не изменяет обычный экспорт остальных
свойств.

Для каждого задания worker:

1. Читает XML и формирует полный YAML.
2. Определяет `DataPath` по типу свойства в `rules.ts`, а не по имени поля.
3. Собирает факты владельца, validation contribution и фрагмент индекса.
4. Сразу записывает все созданные связанные файлы: общий индекс им не нужен.
   Их компактные `ImportResultFile`, как и описания исходных внешних файлов
   XML-выгрузки, возвращаются координатору в результате первого прохода.
5. Добавляет в список отложенных только значения, для которых договор
   финализации потребовал второй проход.
6. Если список пуст, сразу сериализует и записывает основной YAML, возвращает
   его компактный `ImportResultFile` и освобождает полное дерево.
7. Если список не пуст, сохраняет до второго прохода только YAML, отложенные
   значения, rule, owner context, целевой путь, данные для диагностики и
   необходимый локальный индекс. Содержимое связанных файлов и остальные поля
   задания в удерживаемое состояние не входят.

После успешного первого прохода координатор строит и распространяет общий
индекс. Второй проход обрабатывает только оставшиеся `PreparedImportYaml`.
Координатор объединяет списки файлов обоих проходов перед переносом внешних
файлов, хэшированием и записью индекса конфигурации.

Первый проход не должен удерживать компактные описания ранних файлов внутри
worker после возврата результата: ими владеет координатор.

Каждый worker обрабатывает и записывает не более одного задания одновременно.
Общая параллельность записи ограничена настроенной параллельностью XML-import;
отдельная внутренняя очередь параллельной записи не создаётся.

## Ошибки и частичный результат

Ошибка ранней сериализации или записи становится диагностикой соответствующего
задания. Worker продолжает обработку остальных заданий, чтобы собрать остальные
диагностики.

При любой ошибке первого прохода координатор:

- не запускает второй проход;
- не переносит внешние файлы;
- не вычисляет и не записывает индекс конфигурации;
- не удаляет уже записанные YAML и созданные связанные файлы.

Это сознательно расширяет существующее поведение частичного результата:
ранняя запись непосредственно в Проект важнее прежней границы «до завершения
первого прохода YAML не записываются».

## Профилирование

Профилировщик XML-import отдельно показывает:

- количество YAML, записанных в первом проходе;
- суммарный размер их сериализованного текста;
- количество YAML, оставленных до второго прохода;
- количество подозрительных значений, потребовавших откладывания.

Счётчики агрегируются по worker и позволяют оценить результат на реальной
конфигурации без включения подробного журнала.

## Проверка

### Предикат

- путь с `~` не требует финализации;
- formatter оставляет путь с `~` без изменений и не вызывает resolver;
- точное внутреннее имя требует финализации;
- русское имя и неизвестное имя не требуют финализации;
- часть другого имени, например `MyLineNumber`, не совпадает;
- индексированный сегмент `LineNumber[0]` совпадает;
- путь без потенциально переводимого стандартного реквизита не совпадает;
- одноимённые YAML-поля с типом, отличным от `DataPath`, не участвуют в
  проверке;
- поля `DataPath` распознаются независимо от имени YAML- или XML-ключа;
- formatter не вызывает resolver для пути без потенциально переводимого
  сегмента;
- изменение реестра в тесте обновляет скомпилированную проверку.

### Worker

- в смешанном наборе обычные YAML записаны после первого прохода и отсутствуют
  в состоянии worker;
- подозрительные формы остаются в состоянии worker и записываются во втором
  проходе;
- ранняя запись включает созданные из YAML связанные файлы и возвращает их
  компактные описания;
- связанные файлы подозрительного YAML также записываются в первом проходе и
  не входят в удерживаемое состояние;
- описания исходных внешних файлов возвращаются в первом проходе, но сами файлы
  переносятся координатором только после успешного завершения обоих проходов;
- ошибка одной ранней записи не мешает собрать диагностики других заданий.

### Координатор

- объединяет файлы первого и второго проходов без повторов;
- при ошибке первого прохода не запускает второй и не записывает индекс;
- сохраняет уже записанный частичный результат;
- успешный импорт формирует тот же Проект и индекс, что до оптимизации, кроме
  намеренно неизменённых путей с `~`.

### Производительность

На одинаковом наборе путей сравниваются скомпилированное регулярное выражение и
`split + Set`.

До изменения и после него выполняется `import-profile` на одной XML-выгрузке:

```text
/Users/nikita/git/round-trip/cf/doc
```

Оба замера используют одинаковое число прогонов, степень параллелизма и один
режим `mcp stdio source tsx`. Обязателен сопоставимый cold-прогон; warm-замеры,
если выполняются, используют одинаковое число повторов. Сравниваются время, Peak RSS,
распределение времени по этапам и новые счётчики ранней записи. Выходные
YAML-каталоги для каждого прогона создаются заново.

Проверка памяти не становится пороговым тестом CI, чтобы избежать
нестабильности.

### Зафиксированный исходный замер `doc`

Текущий `develop` успешно завершает cold-профиль с одним worker и
`NODE_OPTIONS=--max-old-space-size=8192`:

- заданий импорта: `9 937`;
- полное время runner: `70,05 с`;
- первый проход worker: `29,35 с`;
- второй проход worker: `6,49 с`;
- сериализация YAML: `2,38 с`;
- запись основных YAML: `3,31 с`;
- запись связанных файлов: `0,14 с`;
- Peak RSS worker: `2 377,8 МиБ`;
- Peak RSS main: `2 332,4 МиБ`;
- предупреждений: `0`;
- ошибок: `0`.

После изменения выполняется такой же cold-прогон с одним worker и heap `8 ГиБ`.
Главный показатель оптимизации — снижение Peak RSS worker. Cold-время не должно
превысить исходное более чем на `10%`: при baseline `70,05 с` верхняя граница
составляет `77,06 с`. Распределение времени по этапам фиксируется для анализа
изменения.

## Критерий готовности

После первого прохода в памяти worker остаются только YAML с потенциально
переводимыми `DataPath`. Пути без таких сегментов и отключённые пути с `~` не
передаются resolver ни на одном этапе. Итоговый успешный импорт сохраняет
прежнее содержимое Проекта, диагностик и индекса конфигурации с оговорённым
изменением для `~`, а профилировщик показывает эффект раннего освобождения и
успешно завершает `doc`.

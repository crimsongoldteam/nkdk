# Декларативные ресурсы и области инкрементальной XML-синхронизации

## Контекст

Инкрементальная синхронизация сейчас строит список изменённых YAML-файлов через `.nkdk-sync.bin`, затем превращает каждый путь в XML-область и выполняет частичную выгрузку.

Проблема проявилась на изменении:

```text
Справочник/Бригады/Формы/ФормаЭлемента/Форма.yaml
```

Планировщик распознал этот путь как область формы, CLI сообщил `1 успешно`, но XML-файл не изменился:

```text
Catalogs/Бригады/Forms/ФормаЭлемента.xml
```

Причина: связь `Формы/<Имя>/Форма.yaml -> Forms/<Имя>.xml` сейчас частично зашита в коде `xmlAreas.ts`, а исполнитель инкрементальной синхронизации не обязан обработать каждый вид области. В результате новый или забытый `kind` может быть добавлен в план, но молча пропущен при записи XML.

Та же проблема шире одного файла: разные механизмы проекта уже вручную знают про конечные реализации. Например, `metadata/project/resources.ts` и `directoryStructure.ts` знают про папку `Формы` и файл `Форма.yaml`, `xmlAreas.ts` знает про `Forms`, а общие helpers местами знают про `MetadataCatalog`, `ChildFormNames` и `ChildTemplateNames`. Эти знания должны жить в правилах объекта или в описаниях property-типов, а не в orchestration и project helpers.

## Цели

- Все связи YAML-путей с XML-путями должны описываться декларативно в правилах объекта или в правилах типа свойства.
- Orchestration и project helpers не должны содержать частных знаний о конечных metadata item, например `if (rule.itemType === "MetadataCatalog") return "Catalog"`.
- Orchestration и project helpers не должны содержать частных знаний о стандартных дочерних структурах, например ручные проверки `Формы`, `Макеты`, `ChildFormNames` и `ChildTemplateNames`.
- Discovery, sync-state, incremental plan, executor и CLI-описание структуры проекта должны использовать один декларативный источник ресурсов.
- Каждая область, попавшая в план, должна либо быть записана в XML, либо завершить команду ошибкой.
- `.nkdk-sync.bin` должен обновляться только после успешной записи всех областей плана.
- CLI-команда `sync` при частичной выгрузке должна показывать список XML-файлов, содержимое которых изменилось.

## Не цели

- Не менять формат YAML-проекта.
- Не переписывать всю orchestration-синхронизацию.
- Не добавлять параллельность на этом этапе.
- Не делать полный `syncConfigurationToXML` вместо частичной выгрузки.

## Дизайн

### Архитектурный договор

Общий слой видит только нейтральные договоры:

```text
MetadataItemRule
PropertyRule
ProjectResourceDescriptor
XmlSyncRoute
XmlSyncWriter
```

Он не знает слов `Catalog`, `Document`, `Формы`, `Макеты`, `ChildFormNames`, `ChildTemplateNames`, `ObjectModule`, `ManagerModule` как особых случаев. Если такое слово появляется в общем механизме, это признак утечки конкретной реализации.

Конкретика регистрируется снаружи:

- правило объекта сообщает `itemTypePrefix`, `xmlDir`, `XMLRoot.container`, `externalMetadata`, свойства и их параметры;
- описание property-типа сообщает стандартные ресурсы, маршруты и исполнители для этого типа;
- частные отличия сообщает конкретное свойство через декларацию маршрута.

Общий поток должен выглядеть так:

```text
rules.ts + type descriptions
        ↓
единый реестр project resources / sync routes / sync writers
        ↓
discovery, sync-state, incremental plan, CLI directory structure
        ↓
универсальный executor вызывает зарегистрированный writer
```

### Источники ресурсов и маршрутов

Ресурс или маршрут строится из двух уровней правил.

Правило объекта даёт общий контекст:

```ts
{
  itemTypePrefix: "Справочник",
  xmlDir: "Catalogs",
  externalMetadata: { segment: "Catalog", placement: "rootEntry" },
  properties: { ... }
}
```

Если `externalMetadata.segment` не задан явно, top-level wrapper уже добавляет его из `XMLRoot.container`. Код планировщика, построителя dump-info имён, metadata-target helpers и другие общие helpers не должны знать, что `MetadataCatalog` соответствует `Catalog`; они должны читать это из правила или из зарегистрированного контекста.

Правило типа свойства даёт стандартные ресурсы и маршруты для повторяющихся структур. Например, описание типа `ChildFormNames` означает:

```text
YAML: <itemTypePrefix>/<itemName>/Формы/<formName>/Форма.yaml
XML:  <xmlDir>/<itemName>/Forms/<formName>.xml
```

и:

```text
YAML: <itemTypePrefix>/<itemName>/Формы/<formName>/Модуль.bsl
XML:  <xmlDir>/<itemName>/Forms/<formName>/Ext/Form/Module.bsl
```

Аналогично `ChildTemplateNames` задаёт стандартные маршруты для макетов. Частные отличия остаются в правиле свойства через явную декларацию маршрута, но стандартный случай не должен копироваться в каждом прикладном объекте.

### Единый реестр ресурсов

Нужен один слой, который по `MetadataItemRule` строит список `ProjectResourceDescriptor`. Он заменяет ручные знания в:

- discovery YAML-файлов;
- построении `.nkdk-sync.bin`;
- `metadata/project/resources.ts`;
- `metadata/project/directoryStructure.ts`;
- incremental XML plan.

Descriptor должен описывать минимум:

```ts
{
  projectPattern: "Формы/{childName}/Форма.yaml",
  role: "fileItem",
  required: true,
  repeatable: true,
  owner: "currentItem",
  compositionImpact: "none",
  source: { kind: "propertyType", type: "ChildFormNames" }
}
```

Для `Свойства.yaml` descriptor строится из самого `MetadataItemRule`: это корневой YAML-файл объекта. Такой descriptor должен иметь `compositionImpact: "owner-list"`, потому что добавление или удаление корневого объекта меняет список `ChildObjects` в `Configuration.xml`. Изменение существующего `Свойства.yaml` не меняет состав конфигурации само по себе.

Для `Configuration.yaml` descriptor строится из правила конфигурации. Для вложенных подсистем descriptor тоже должен прийти из правил или type-регистрации, а не из отдельного ручного разбора `Подсистемы`.

### Единый реестр маршрутов

Нужен один слой, который по `MetadataItemRule` строит список `XmlSyncRoute`.

Пример формы:

```ts
{
  kind: "fileItem",
  yamlPattern: "Формы/{childName}/Форма.yaml",
  xmlPath: "Forms/{childName}.xml",
  childKind: "form"
}
```

Пример модуля формы:

```ts
{
  kind: "externalFile",
  yamlPattern: "Формы/{childName}/Модуль.bsl",
  xmlPath: "Forms/{childName}/Ext/Form/Module.bsl",
  childKind: "form"
}
```

Для `МодульОбъекта.bsl`, `МодульМенеджера.bsl`, `Help.xml`, внешних файлов и других нестандартных случаев маршрут берётся из декларации свойства: `syncArea`, `filePath`, `xmlPath`, `externalFile` или специализированной регистрации типа.

`XmlSyncRoute` должен ссылаться на соответствующий `ProjectResourceDescriptor` или строиться из того же источника, чтобы discovery и incremental plan не расходились. Если файл входит в sync state, он должен иметь маршрут или явно быть помечен как resource-only без XML-выгрузки. Для resource-only файлов решение должно быть явным в описании типа, а не побочным эффектом отсутствия маршрута.

### Планирование

Планировщик получает изменённый путь, находит top-level rule по `itemTypePrefix`, затем ищет подходящий descriptor и маршрут среди ресурсов этого правила и его свойств.

Для пути:

```text
Справочник/Бригады/Формы/ФормаЭлемента/Форма.yaml
```

он должен получить:

```text
itemTypePrefix = Справочник
itemName = Бригады
route = ChildFormNames: Форма.yaml
xmlPath = Catalogs/Бригады/Forms/ФормаЭлемента.xml
```

Если изменены и объект, и форма:

```text
Справочник/Бригады/Свойства.yaml
Справочник/Бригады/Формы/ФормаЭлемента/Форма.yaml
```

план группируется по владельцу `Справочник/Бригады`. Модель объекта читается один раз, а записываются только нужные XML-области:

```text
Catalogs/Бригады.xml
Catalogs/Бригады/Forms/ФормаЭлемента.xml
```

Полная выгрузка справочника дважды выполняться не должна.

Решение о пересборке `Configuration.xml` строится из descriptor и вида изменения:

```text
added/deleted + compositionImpact: "owner-list" => пересобрать Configuration.xml
changed       + compositionImpact: "owner-list" => не пересобирать Configuration.xml
compositionImpact: "none"                       => не пересобирать Configuration.xml
```

Это заменяет частную логику «added/deleted owner значит rebuild». Добавление нового справочника определяется как появление `Справочник/<Имя>/Свойства.yaml`, descriptor этого файла сообщает `compositionImpact: "owner-list"`, поэтому планировщик включает пересборку `Configuration.xml`. Переименования и структурные миграции, которые меняют состав верхнего уровня, тоже должны давать `owner-list`.

### Исполнение

Исполнитель получает не произвольный `kind`, а типизированную область из плана. Обработчик области тоже должен быть зарегистрирован декларативно.

Для каждой области обязателен обработчик:

- `owner` пишет XML владельца, например `Catalogs/Бригады.xml`;
- `fileItem` пишет XML дочернего файлового объекта, например `Catalogs/Бригады/Forms/ФормаЭлемента.xml`;
- `externalFile` пишет внешний файл, например `Catalogs/Бригады/Forms/ФормаЭлемента/Ext/Form/Module.bsl`.

В коде должен быть исчерпывающий `switch`. Если появится новый вид области, TypeScript должен потребовать добавить его обработку. Если во время исполнения маршрут не поддержан, команда должна завершиться ошибкой и не обновлять `.nkdk-sync.bin`.

Исполнитель не должен проверять `area.childKind === "form"` и дальше напрямую вызывать знание о формах, если это знание можно передать через writer. Нейтральный вариант: `XmlSyncRoute` содержит `writerType` или ссылку на зарегистрированный writer property-типа. Общий executor подготавливает контекст владельца и вызывает writer, а writer знает, как записать форму, макет, модуль или внешний файл.

### Вывод CLI

Результат инкрементальной синхронизации должен включать список XML-файлов, которые реально изменили содержимое на диске. Внутри core можно дополнительно хранить список обработанных областей, но пользовательский CLI-вывод должен отвечать на вопрос: какие XML-файлы поменялись.

CLI при частичной выгрузке выводит:

```text
Готово: 1 успешно, 0 с ошибкой
Изменены файлы:
Catalogs/Бригады/Forms/ФормаЭлемента.xml
```

Если файл был пересобран, но содержимое совпало с прежним, он не попадает в список изменённых. Для диагностики такой файл может быть доступен в программном результате как обработанный, но строка `Изменены файлы:` печатает только реальные изменения содержимого.

## Ошибки и инварианты

- Если YAML-путь входит в sync state, но для него нет маршрута, это ошибка планирования.
- Если маршрут найден, но нет исполнителя, это ошибка реализации, а не успешная синхронизация.
- Если запись хотя бы одной области завершилась ошибкой, `.nkdk-sync.bin` не обновляется.
- `Configuration.xml` пересобирается только по декларативному `compositionImpact`, а не по частным знаниям планировщика об `owner`.
- Нельзя добавлять частные условия по `itemType` в планировщик, project helpers и общие helpers. Данные берутся из правил.
- Нельзя добавлять ручной разбор стандартных папок вроде `Формы` и `Макеты` в orchestration/project helpers. Эти папки описывает property-тип или свойство.
- Новые стандартные структуры добавляются через регистрацию типа свойства, а не через ручной разбор путей в `xmlAreas.ts`, `resources.ts` или `directoryStructure.ts`.
- Если общему механизму нужно имя XML-корня, оно берётся из `externalMetadata.segment` или `XMLRoot.container`, а не из карты `MetadataCatalog -> Catalog`.
- Если общему механизму нужно понять, что property является файловой дочерней коллекцией, это должно быть свойство descriptor/type-регистрации, а не проверка `rule.type === "ChildFormNames"`.

## Тестирование

Нужны тесты архитектурной границы:

- route/resource builders не содержат частных веток для `MetadataCatalog`;
- project resource discovery получает `Формы/<Имя>/Форма.yaml` из регистрации `ChildFormNames`, а не из ручного `parts[2] === "Формы"`;
- directory structure показывает формы из descriptor-регистрации, а не из постоянной строки в `directoryStructure.ts`;
- helper, строящий dump-info имя, использует `externalMetadata.segment` или `XMLRoot.container`.

Нужны тесты на уровне планировщика:

- `Справочник/Бригады/Формы/ФормаЭлемента/Форма.yaml` планируется как `fileItem` с XML-путём `Catalogs/Бригады/Forms/ФормаЭлемента.xml`;
- `Справочник/Бригады/Формы/ФормаЭлемента/Модуль.bsl` планируется как `externalFile` с XML-путём `Catalogs/Бригады/Forms/ФормаЭлемента/Ext/Form/Module.bsl`;
- для маршрута используется `externalMetadata.segment` или `XMLRoot.container`, без частных `if itemType`.
- каждый YAML-ресурс из общего реестра либо имеет XML-маршрут, либо явно помечен как `resource-only`.

Нужны интеграционные тесты на временных каталогах, созданных прямо в тесте:

- изменение `Форма.yaml` меняет соответствующий XML формы;
- изменение `Свойства.yaml` и `Форма.yaml` одного объекта записывает две нужные XML-области;
- `Catalogs/<Имя>.xml` не переписывается, если изменена только форма;
- при неподдержанном маршруте state не обновляется.

Нужна проверка partial-vs-full на временных каталогах:

- тест создаёт маленький YAML-проект и XML-reference;
- выполняет полную синхронизацию во временный каталог;
- выполняет частичную синхронизацию после изменения одного YAML-файла;
- сравнивает только затронутые XML-файлы: результат partial sync должен совпадать с full sync для этих файлов.

Нужны тесты CLI:

- при инкрементальном `sync` выводится список XML-файлов, содержимое которых изменилось;
- при отсутствии изменений список не печатается.

Большие реальные проекты вроде `/Users/nikita/git/nkdk-yaml` и `/Users/nikita/git/round-trip/erp` не используются в автоматических тестах. Они остаются только для ручного замера скорости и проверки реального сценария после реализации.

## Порядок реализации

1. Ввести нейтральные типы `ProjectResourceDescriptor`, `XmlSyncRoute` и `XmlSyncWriter`.
2. Добавить регистрацию resources/routes/writers для property-типов.
3. Зарегистрировать стандартные resources/routes/writers для `ChildFormNames`.
4. Зарегистрировать стандартные resources/routes/writers для `ChildTemplateNames`.
5. Перевести `xmlAreas.ts` на маршруты из правил и type-регистраций.
6. Перевести `metadata/project/resources.ts` на общий реестр ресурсов.
7. Перевести `metadata/project/directoryStructure.ts` на общий реестр ресурсов.
8. Добавить исполнитель `fileItem` через зарегистрированный writer.
9. Добавить сбор списка изменённых XML-файлов в результат синхронизации.
10. Обновить CLI-вывод для частичной выгрузки.
11. Добавить тесты и прогнать `pnpm test`.

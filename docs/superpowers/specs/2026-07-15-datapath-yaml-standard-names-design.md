# DataPath: YAML-имена стандартных реквизитов

## Контекст

При импорте XML-проекта `/Users/nikita/git/round-trip/erp` в YAML-проект `/Users/nikita/git/nkdk-yaml` в формах остались пути вида `Объект.Товары.LineNumber`.

Это неверно для YAML-слоя. XML хранит внутренние имена платформы, но YAML должен использовать человекочитаемые имена проекта: `LineNumber` должен становиться `НомерСтроки`, `Date` — `Дата`, `Ref` — `Ссылка` и так далее.

## Цель

Сделать YAML-слой каноническим: в YAML-полях типа `DataPath` используются только YAML-имена стандартных реквизитов.

## Решение

Граница преобразования проходит только на вводе и выводе XML:

- XML -> YAML: все значения `DataPath` проходят через общий преобразователь стандартных имён и записываются в YAML-формате.
- YAML -> XML: все значения `DataPath` проходят обратное преобразование и записываются во внутреннем формате платформы.
- YAML validation не считает английские стандартные имена допустимыми алиасами.

Специальная диагностика для английских имён не нужна. Если в YAML осталось `Объект.Товары.LineNumber`, резолвер должен обработать это как обычный неизвестный сегмент пути и вернуть стандартную ошибку вида `неизвестная колонка "LineNumber"`.

## Область

В область входят все YAML-поля, описанные в rules.ts как `DataPath`, включая:

- `ПутьКДанным`;
- `ПутьКДаннымПодвала`;
- `ПутьКДаннымЗаголовка`;
- другие свойства формы и общих объектов, которые используют тип `DataPath`.

В область не входят metadata target-пути вроде `Document.Товары.StandardAttribute.LineNumber`, если конкретное правило описывает их не как `DataPath`. Для таких полей должен применяться их собственный механизм преобразования.

## Архитектура

Уже существующий общий механизм остаётся основой:

- `exportDataPathStandardMembersToYAML` — преобразует внутренние имена в YAML-имена;
- `importDataPathStandardMembersFromYAML` — преобразует YAML-имена обратно во внутренние;
- `formatDataPathStandardMembers` — выполняет разрешение пути через индекс формы и владельца.

Исправление должно быть сделано там, где импорт XML формирует YAML-представление `DataPath`, но сейчас не применяет этот общий механизм.

Важно не добавлять частные условия по `LineNumber` в общие metadata-слои. `LineNumber` должен обрабатываться через уже существующую таблицу стандартных реквизитов и общий форматтер.

## Поток данных

Импорт XML:

1. XML содержит `DataPath` с внутренними именами платформы.
2. fromXML строит модель формы.
3. toYAML экспортирует модель в YAML.
4. При экспорте каждого `DataPath` стандартные сегменты переводятся в YAML-имена.
5. В YAML записывается `Объект.Товары.НомерСтроки`.

Синхронизация YAML в XML:

1. YAML содержит `Объект.Товары.НомерСтроки`.
2. fromYAML читает `DataPath`.
3. Стандартные сегменты переводятся во внутренние имена платформы.
4. В XML записывается `Объект.Товары.LineNumber`.

Валидация YAML:

1. YAML содержит `Объект.Товары.LineNumber`.
2. Валидация не применяет английский алиас как допустимое YAML-имя.
3. Резолвер не находит колонку `LineNumber`.
4. Пользователь получает обычную ошибку неизвестного сегмента.

## Проверки

Нужны тесты на оба направления:

- XML -> YAML: форма с `DataPath` на стандартный реквизит табличной части экспортируется как `НомерСтроки`.
- YAML -> XML: `НомерСтроки` импортируется обратно как `LineNumber`.
- validation: YAML с `LineNumber` в `DataPath` не проходит валидацию.
- regression: импорт `/Users/nikita/git/round-trip/erp` больше не оставляет `LineNumber` в YAML-полях `DataPath`.

## Вне области

Эта задача не исправляет другие найденные ошибки валидации:

- пустые `ЦветТекста` / `ЦветФона` в условном оформлении;
- строковое значение `"[Авто]"` в `ДинамическийСписок.Порядок.Элементы`.

# Локальный lookup configuration index для назначения sync

**Статус:** согласовано

**Дата:** 2026-08-04

## Контекст

Чистая YAML → XML синхронизация конфигурации `doc` при `concurrency: 4` обрабатывает 22 135 YAML-файлов за 51,14 секунды с максимальным RSS 2,36 ГиБ. CPU-профиль четырёх worker показал, что 44,3% полезного CPU уходит на чтение configuration index:

- 24,2% — кодирование и декодирование строк снимка;
- 20,1% — двоичный hash-index и поиск entity.

Индекс `doc` содержит 302 754 строки и 246 823 entity. Каждая entity уже хранит `sourceProjectPath` YAML-файла, который её создал. На один YAML-файл приходится в среднем около 11 entity.

Текущий горячий путь выполняется для множества свойств:

```text
logicalAddress
→ UTF-8
→ xxHash
→ глобальный строковый lookup
→ lookup entity
→ декодирование entity
```

Главный процесс уже читает configuration index и создаёт общий `SharedConfigurationIndexSnapshot`. В снимке уже есть `sourceEntityOffsets`, `sourceEntityRanges` и lookup `sourceProjectPath → rangeId`. Построение этих общих таблиц не является узким местом: на профиле `doc` собственное CPU-время `buildSharedLookups` составляет около 0,1 секунды.

## Цель

Устранить глобальный строковый lookup из обработки свойств YAML → XML. После изменения обычное назначение должно читать entity преимущественно из маленького локального каталога своего YAML-файла.

После реализации повторно профилируется `doc`. Если lookup перестал быть главным потребителем CPU, оптимизация продолжается по следующему узкому месту отдельным циклом.

Жёсткий порог времени не задаётся: приоритетом является максимальное фактическое ускорение при сохранении XML-семантики.

## Не входит в решение

- изменение дискового формата configuration index `1.3`;
- сохранение нестабильных `rangeId` между операциями или поколениями индекса;
- изменение `refreshAndValidate`;
- изменение `concurrency: 4`;
- оптимизация XML → YAML import;
- оптимизация validation, использующей отдельный двоичный project state;
- отдельная оптимизация base configuration index расширения до появления подтверждённого узкого места;
- изменение `rules.ts`, прикладных metadata-типов или XML-фикстур.

## Рассмотренные подходы

### (А) Диапазон entity текущего назначения

Выбран. Главный процесс один раз связывает каждое исполняемое назначение с уже построенным диапазоном entity его `sourceProjectPath`. Worker строит маленький локальный каталог адресов только для этого диапазона.

Преимущества:

- глобальный UTF-8/xxHash lookup исчезает из обработки свойств;
- двоичные данные остаются общими и не копируются между worker;
- одна entity декодируется не более одного раза в назначении;
- память локального каталога ограничена данными текущего YAML-файла;
- переиспользуются существующие `sourceEntityOffsets` и `sourceEntityRanges`.

### (Б) Числовой граф logicalAddress

Runtime хранит числовой идентификатор entity и перемещается по графу родителей и детей без строковых адресов. Подход имеет максимальную теоретическую скорость, но требует глубокого изменения адресации правил, динамических коллекций и `ConfigurationIndexExportRuntime`. Отклонён до подтверждения, что локальный каталог назначения недостаточен.

### (В) Полные Map в каждом worker

Каждый worker декодирует все строки и entity configuration index. Поиск после построения быстр, но четыре worker создают четыре полные объектные копии. Этот подход уже приводил ERP к 6,73 ГиБ RSS и дорогому холодному запуску. Отклонён.

## Архитектура

### Связывание назначения

Логический `FullXmlSyncPlan` не содержит смещений configuration index: они зависят от конкретного снимка и меняются после каждого успешного sync.

После создания `SharedConfigurationIndexSnapshot` координатор формирует временное исполняемое представление назначения:

```ts
interface ConfigurationIndexEntityRange {
  readonly start: number
  readonly count: number
}
```

`start` и `count` адресуют диапазон внутри `sourceEntityOffsets` того же снимка, который передаётся worker при инициализации. Координатор вычисляет диапазон один раз по `assignment.sourceProjectPath`. Это не требует повторного чтения или полного декодирования configuration index.

Диапазон передаётся вместе с существующим исполняемым назначением. Два числа не содержатся в YAML, project state или дисковом configuration index и не переживают текущую операцию.

### Локальный reader назначения

Worker создаёт `AssignmentConfigurationIndexReader` из:

- общего `SharedConfigurationIndexSnapshot`;
- `ConfigurationIndexEntityRange` назначения;
- существующего глобального `ConfigurationIndexReader` как резервного источника.

Reader проверяет диапазон и проходит только указанные `sourceEntityOffsets`. Для каждой записи он один раз читает `logicalAddress` и строит локальный каталог:

```text
logicalAddress → binary entity offset
```

При первом запросе entity декодируется из общего двоичного буфера и кэшируется внутри reader. Повторные `identity()`, `xml()` и `omittedChildren()` для того же адреса используют кэш. Reader, каталог и кэш освобождаются после обработки назначения.

Ожидаемый размер локального каталога определяется данными одного YAML-файла, а не всего configuration index. Для `doc` среднее значение — около 11 записей.

### Интеграция с YAML → XML

`prepareFullXmlSyncAssignment` создаёт `ConfigurationIndexExportRuntime` поверх локального reader назначения. Публичная семантика runtime не меняется:

- `identity(address)` восстанавливает `uuid`, `xmlId` и `xmlName`;
- `xml(address)` восстанавливает `xsiType`, текст, префикс и XML-флаги;
- `omittedChildren(address)` восстанавливает пропущенных детей.

Правила продолжают заново строить `logicalAddress`. Изменяется только область поиска: сначала маленький каталог текущего YAML-файла, а не глобальный строковый индекс.

### Резервный глобальный lookup

Если локальный каталог не содержит адрес, reader вызывает существующий глобальный `ConfigurationIndexReader.entity(address)`. Это сохраняет поведение для:

- нового или переименованного YAML-файла;
- базовой формы расширения;
- редкого межфайлового обращения;
- ещё не выявленного договора, который читает entity другого `sourceProjectPath`.

Резервный путь является механизмом совместимости, а не штатным путём производительности. Профиль отдельно считает его вызовы. Если обычный `doc` часто использует fallback, причины исследуются до следующей оптимизации.

Base configuration index расширения на первом этапе остаётся глобальным. Его оптимизация выполняется только по результатам отдельного профиля расширения.

## Поток данных

1. `refreshAndValidate` формирует подтверждённое состояние проекта как прежде.
2. Координатор читает configuration index `1.3` и создаёт общий снимок.
3. Координатор связывает `sourceProjectPath` каждого назначения с `{ start, count }`.
4. Один общий снимок передаётся всем worker через `SharedArrayBuffer`.
5. Исполняемое назначение передаёт worker два числа диапазона.
6. Worker строит локальный каталог адресов текущего YAML-файла.
7. Все свойства назначения сначала читают configuration index через локальный reader.
8. Редкий локальный промах использует глобальный reader.
9. Worker возвращает существующий двоичный результат и фрагмент нового configuration index.
10. После назначения локальный reader освобождается; после операции освобождается общий снимок.

## Целостность и ошибки

- `start` и `count` должны задавать диапазон внутри `sourceEntityOffsets`; выход за границу является технической ошибкой операции.
- Каждое смещение диапазона должно указывать на корректную entity текущего снимка.
- Два одинаковых `logicalAddress` внутри диапазона считаются повреждением индекса.
- Пустой диапазон допустим для нового файла.
- Локальный промах не является ошибкой и использует глобальный reader.
- Повреждение локального диапазона не должно скрываться глобальным fallback.
- Диапазон никогда не сохраняется и не используется с другим поколением снимка.
- Configuration index обновляется и публикуется только после успешной синхронизации, как прежде.

## Профилирование

В профиль full sync добавляются счётчики:

- число локальных попаданий;
- число локальных промахов;
- число вызовов глобального fallback;
- число декодированных entity;
- суммарное число entity в диапазонах назначений.

Для обычной конфигурации `doc` ожидается почти полное обслуживание через локальный reader. Результат оценивается по чистому sync без CPU-профилировщика и отдельному V8 CPU-профилю четырёх worker.

Исходная точка сравнения:

- 22 135 обработанных YAML-файлов;
- 51,14 секунды реального времени;
- 147,69 секунды user CPU;
- 23,01 секунды system CPU;
- 2,36 ГиБ максимального RSS;
- 44,3% полезного CPU worker в строковом кодировании и lookup configuration index.

## Проверки

Тесты следуют `.agents/testing.md`: сначала усиливается ближайший существующий тест, новый файл создаётся только для отдельного договора.

### Связывание

- `sourceProjectPath` получает правильный `{ start, count }`;
- новый путь получает пустой диапазон;
- диапазон относится к тому же снимку, что передан worker;
- назначение не выполняет повторный строковый lookup диапазона внутри worker.

### Локальный reader

- находит entity своего диапазона;
- не принимает entity соседнего диапазона за локальную;
- декодирует одну entity не более одного раза;
- использует глобальный fallback при локальном промахе;
- отклоняет выход диапазона за границы;
- отклоняет повторный `logicalAddress` внутри диапазона;
- сохраняет результаты `identity`, `xml` и `omittedChildren` существующего reader.

### Интеграция

- обычное назначение обслуживается локальным reader без глобальных lookup;
- новый и переименованный файл сохраняют прежнюю семантику;
- формы и конфигурация сохраняют XML-идентификаторы и XML-флаги;
- существующие тесты расширений и базовых форм остаются зелёными;
- round-trip `doc` сохраняет число и содержимое трёх существующих XML-diff.

### Итоговые проверки

- целевые тесты и `pnpm type-check`;
- полный `pnpm test`;
- `pnpm duplicates -- --base <commit>` после законченного слоя и в конце;
- dependency-cruiser в конце реализации;
- чистый sync `doc` при `concurrency: 4`;
- V8 CPU-профиль основного потока и четырёх worker;
- сравнение времени, CPU и RSS с исходной точкой;
- выбор следующего узкого места по новому профилю.

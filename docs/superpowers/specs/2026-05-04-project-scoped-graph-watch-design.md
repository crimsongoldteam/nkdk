# Project-Scoped Graph Watch Design

## Цель

Сделать `update-graph` и `watch` жизнеспособными для больших YAML/NKDK-проектов, где у каждого каталога должна быть своя graph-БД. Все режимы должны строить граф одинаковым способом там, где это возможно, чтобы полный прогрев, начальная догонка `watch` и текущие события `watch` не расходились по правилам чтения `Форма.yaml` и `Форма.nkdk`.

## Текущая проблема

Сейчас полный `update-graph` вызывает `readProjectGraphSources(projectPath, { includePairedText: false })`, поэтому `Форма.nkdk` не участвует в полном построении graph. При этом `watch` считает `Форма.nkdk` поддерживаемыми tracked files, сверяет их stats с `File`-узлами в graph и после полного прогрева видит тысячи отсутствующих `nkdk`-файлов как изменения. На `erp_nkdk` это превращает запуск `watch` в долгую последовательность одиночных обновлений.

Вторая проблема: graph name по умолчанию сейчас общий (`nakidka`). Полный `update-graph` удаляет graph целиком, поэтому два разных YAML-каталога по умолчанию пишут в одну БД и могут перетирать друг друга.

## Термины

- **Tracked file** — файл, за которым следит CLI и по которому сравниваются disk stats: `Свойства.yaml`, `Форма.yaml`, `Форма.nkdk`.
- **Graph source** — файл, из которого строится graph source-модель: `Свойства.yaml` или `Форма.yaml`.
- **Paired text** — `Форма.nkdk`, читаемый только как парный текст для `Форма.yaml`.

`Форма.nkdk` никогда не является самостоятельным graph source.

## Правила формы

Матрица состояния формы:

- есть `Форма.yaml` и есть `Форма.nkdk` — форма входит в graph; `Форма.nkdk` участвует как paired text и получает свой `File` stats;
- есть `Форма.yaml`, нет `Форма.nkdk` — форма входит в graph только по YAML-части; `Форма.nkdk` в graph отсутствует;
- нет `Форма.yaml`, есть `Форма.nkdk` — формы в graph нет; одинокий `Форма.nkdk` не включается в graph;
- нет обоих файлов — формы в graph нет.

Удаление `Форма.nkdk` при сохранённом `Форма.yaml` пересобирает форму по YAML и удаляет вклад `nkdk`-части. Удаление `Форма.yaml` равно удалению graph source формы; одинокий `Форма.nkdk` не должен удерживать форму в graph.

## Единый batch-путь построения

Нужен общий CLI-слой для построения graph payload из набора graph sources:

1. нормализовать tracked files в affected graph sources и deletion set;
2. читать YAML source и paired `Форма.nkdk`, если он существует;
3. собирать `FileGraphData[]` через общий batch-вызов `buildGraph`;
4. сохранять stats для YAML и paired `Форма.nkdk`;
5. записывать payload через `@nakidka/graph.updateGraph`.

Этот путь используют:

- полный `update-graph`;
- `update-graph --file`;
- начальная догонка `watch`;
- текущая очередь событий `watch`.

Различаются только выбор входных файлов и режим удаления перед записью, но не правила чтения YAML/NKDK и не построение `FileGraphData`.

## Режимы применения

### Полный `update-graph <path>`

Полный `update-graph` берёт все graph sources проекта, строит payload через единый batch-путь, затем именно удаляет всю graph-БД этого каталога и создаёт её заново.

Это сознательный контракт: команда без `--file` является полной пересборкой БД.

### `update-graph --file`

`update-graph --file` становится частным случаем batch-обновления. Отдельная логика `updateGraphFile` больше не нужна; если совместимость с экспортом функции потребуется, она должна быть тонкой обёрткой над `updateGraphFiles(projectPath, [file])`.

Этот режим удаляет и пересоздаёт только затронутые `File`-узлы, рёбра и связанные данные, но не всю graph-БД.

### `watch`

При старте `watch`:

1. вычисляет автоимя graph-БД от `resolve(projectPath)`;
2. запускает watcher достаточно рано, чтобы не потерять события между сканированием и началом наблюдения;
3. читает `File`-узлы из graph;
4. читает tracked files с диска;
5. считает diff по `mtimeMs` и `size`;
6. нормализует diff в affected graph sources/deletion set;
7. пакетно применяет изменения через тот же batch-путь;
8. сливает события, накопленные watcher во время начальной догонки;
9. дальше обрабатывает текущие события тем же batch-алгоритмом.

Порог перехода на полный rebuild пока не нужен: `watch` всегда делает пакетный diff.

## Project-scoped graph name

Для проектных CLI-команд graph name всегда вычисляется из абсолютного пути проекта:

```text
nkdk_<hash(resolve(projectPath))>
```

Требования к hash:

- стабилен для одного и того же абсолютного пути;
- безопасен для имени graph в FalkorDB;
- достаточно короткий для чтения в логах.

`NKDK_GRAPH_URL` продолжает выбирать сервер FalkorDB. `NKDK_GRAPH_NAME` не должен влиять на проектные CLI-команды `update-graph` и `watch`, чтобы полный `update-graph` одного каталога не мог случайно удалить graph другого каталога.

## Проверка

Минимальные проверки:

- `readProjectGraphSources` по умолчанию читает paired `Форма.nkdk` и stats для него;
- полный `update-graph` строит graph с `File` stats для `Форма.nkdk`;
- `watch` после полного `update-graph` не запускает массовую догонку `Форма.nkdk`;
- `Форма.nkdk` без парного `Форма.yaml` не попадает в graph;
- `update-graph <path>` и `watch <path>` выбирают одинаковое автоимя graph-БД;
- `update-graph <path>` и `update-graph <other-path>` используют разные graph-БД.

Производительность проверяется на `/Users/nikita/git/erp_nkdk/`: если учёт `Форма.nkdk` заметно замедляет полный прогрев, нужно измерять и исправлять чтение/парсинг формы, а не исключать `nkdk` из graph.

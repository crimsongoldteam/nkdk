# Быстрые тесты операций с worker

## Контекст

Часть тестов `packages/core` запускает настоящие Piscina worker из TypeScript.
Каждый холодный worker подключает `tsx`, загружает metadata-регистрации и большой
граф модулей. Полезная обработка небольших фикстур занимает миллисекунды, но
запуск инфраструктуры добавляет несколько секунд.

Обычный тест не должен проверять одновременно предметную логику, координатор
операции и транспорт Piscina. Такая проверка медленная, а при падении плохо
локализует причину.

## Цели

- Каждый отдельный тест в `pnpm test` выполняется не дольше 50 мс.
- Ни один тест в `pnpm test` не запускает настоящий Piscina worker.
- Предметная логика XML/YAML проверяется напрямую, без межпоточного транспорта.
- Координаторы операций проверяются с управляемыми mock worker.
- Превышение бюджета времени автоматически приводит к падению `pnpm test`.

## Не входит в работу

- Изменение production-поведения worker.
- Ускорение или переиспользование worker в CLI/MCP.
- Создание отдельного набора тестов запуска Piscina.
- Проектирование e2e-сценариев. Оно будет выполнено отдельно через публичные
  интерфейсы CLI/MCP.

Тесты, проверяющие только факт запуска настоящего worker, удаляются без переноса:
они не являются ни unit-тестами предметной логики, ни e2e-сценариями.

## Проект решения

### Разделение проверок

Тесты делятся на два вида:

1. **Предметные unit-тесты.** Вызывают настоящие функции преобразования,
   индексирования и формирования результата непосредственно в текущем процессе.
   Они не создают pool и не знают о Piscina.
2. **Unit-тесты координаторов и протоколов pool.** Подставляют mock worker с
   заданными ответами и проверяют распределение заданий, объединение результатов,
   диагностики, обработку ошибок и закрытие ресурсов.

Полные сценарии вида «создать проект → импортировать через worker → изменить
проект → синхронизировать через другой worker» удаляются из `pnpm test`.
Покрываемое ими предметное поведение переносится в небольшие тесты ближайшей
публичной функции, а поведение координатора — в тесты с mock worker.

### Граница подмены

Production-код продолжает создавать Piscina через существующие фабрики pool.
Тесты получают единые фабрики mock worker из test helpers и передают их через
существующие зависимости операций. Если операция не предоставляет узкой точки
подмены, добавляется нейтральный договор фабрики или handle без знаний о
конкретных metadata itemType.

Mock реализует настоящий протокол соответствующего pool, но не вычисляет
предметный результат. Тест явно задаёт ответы и может проверить полученные
команды. Общие mock helpers скрывают управление фазами, распределение worker и
освобождение ресурсов, чтобы тесты не дублировали инфраструктурный код.

### Сохранение предметного покрытия

Удаление медленного интеграционного теста допускается только после сопоставления
его утверждений с быстрыми тестами предметных функций. Недостающие утверждения
переносятся, а не заменяются ответом mock, совпадающим с ожидаемым результатом.
Существующие XML-фикстуры не изменяются.

### Бюджет времени

Vitest получает общий контроль длительности отдельного теста. После запуска
собираются длительности test case; любое значение больше 50 мс завершает команду
ошибкой и выводит отсортированный список нарушителей с файлом, названием и
временем.

Контроль применяется ко всем пакетам, входящим в `pnpm test`. Бюджет не
ослабляется локально через увеличенный timeout. Если тест нестабилен около
границы, уменьшается объём проверяемого сценария или устраняется дорогая
подготовка.

## Последовательность миграции

1. Добавить общий контроль бюджета 50 мс и получить исходный список нарушителей.
2. Удалить тесты, проверяющие только настоящий запуск Piscina.
3. Добавить общие mock helpers для prepared YAML, XML import и full XML sync.
4. По одному кластеру заменять worker-интеграции на предметные unit-тесты и
   тесты координаторов.
5. После каждого кластера запускать его тесты и полный `pnpm test`.
6. Завершить работу, когда все тесты проходят и ни один test case не превышает
   50 мс.

## Критерии готовности

- `pnpm test` завершается успешно.
- Автоматическая проверка подтверждает отсутствие тестов дольше 50 мс.
- В тестовом процессе не создаётся настоящий Piscina pool.
- Нет тестов, предназначенных только для проверки запуска настоящего worker.
- Утверждения удалённых интеграционных тестов сопоставлены с быстрыми
  предметными или координаторными тестами.
- Production-путь создания и выполнения worker не изменил поведение.

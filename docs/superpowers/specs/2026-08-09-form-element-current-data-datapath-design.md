# Дизайн: пути к текущим данным таблиц и деревьев формы

## Контекст

В форме 1С `DataPath` может начинаться не с реквизита формы, а со служебного
пространства элементов формы. Например, XML содержит:

```text
Items.ВходящиеСообщения.CurrentData.Вложения.ИндексКартинки
```

Смысл пути:

1. `Items` — служебный корень элементов формы;
2. `ВходящиеСообщения` — элемент формы вида таблица или дерево;
3. `CurrentData` — текущая строка этого элемента;
4. `Вложения.ИндексКартинки` — продолжение пути по данным текущей строки.

Это не путь от реквизита формы `Items`. Действующий resolver не знает такого
источника и пытается разрешить разные части пути как обычные реквизиты и колонки.
В результате корректный путь получает ошибку validation.

При этом в форме разрешены реквизиты и параметры с именами `Items`, `Элементы`,
`CurrentData` и `ТекущиеДанные`. В `/Users/nikita/git/round-trip-compact/cf`
найдены параметры с именами `Элементы` и `ТекущиеДанные`, поэтому служебный смысл
нельзя определять только по тексту отдельного сегмента.

## Цель

Добавить в общий двусторонний resolver `DataPath` поддержку текущих данных таблиц
и деревьев формы так, чтобы один механизм использовался:

- при XML → YAML;
- при YAML → XML;
- при validation;
- при полной синхронизации;
- при поиске ссылок;
- при переименовании.

В YAML путь из примера должен иметь канонический вид:

```text
Элементы.ВходящиеСообщения.ТекущиеДанные.Вложения.ИндексКартинки
```

## Канонические имена

На границе XML и YAML действуют строгие пары имён:

| Смысл | XML/internal | YAML |
|---|---|---|
| Пространство элементов формы | `Items` | `Элементы` |
| Текущая строка таблицы или дерева | `CurrentData` | `ТекущиеДанные` |

XML → YAML переводит только семантически разрешённые служебные сегменты. YAML →
XML выполняет обратное преобразование. Validation YAML принимает только YAML-
имена. Английские служебные имена в YAML не считаются допустимыми алиасами.

Обычный реквизит или параметр формы с именем `Элементы` либо `ТекущиеДанные` не
переименовывается: совпадение текста не придаёт ему служебный смысл.

## Индекс метаданных

### Текущее ограничение

Сейчас `FormDataPathIndex` хранит `tableDataPathByElementName`: соответствие имени
табличного элемента формы его `ПутьКДанным`. В индекс попадают только элементы с
непустым `ПутьКДанным`.

Этого недостаточно: для распознавания конструкции `Элементы.<Имя>.ТекущиеДанные`
нужно знать сам факт объявления элемента и его вид, даже если собственный
`ПутьКДанным` отсутствует.

### Новая проекция

Индекс метаданных формы хранит объявления только тех элементов, которые могут
быть владельцами `ТекущиеДанные`: таблиц и деревьев формы. Все остальные элементы
формы в эту проекцию не входят.

Логически запись имеет вид:

```text
ВходящиеСообщения → {
  kind: tabularFormElement,
  dataPath: Объект.ВходящиеСообщения
}
```

`dataPath` необязателен. Отсутствие пути не удаляет объявление элемента из
индекса и позволяет выдать точную диагностику при обращении к его текущим данным.

Проекция заменяет узкое соответствие `tableDataPathByElementName`. Она строится
из готового смыслового объекта YAML единым построителем независимо от операции.
Порядок полей в объекте и порядок прихода XML-свойств не влияют на результат.

### Единое построение индекса формы

XML-импорт сначала полностью формирует смысловой объект формы YAML, включая
обычные и дополнительные колонки реквизитов. После этого он вызывает общий
`createFormDataPathIndexFromYAML`. Тот же построитель уже используется при
validation, YAML → XML, синхронизации, поиске ссылок и переименовании.

Отдельный `formDataPathMetadataCollector` внутри XML-импорта не используется.
Иначе нестандартный преобразователь свойства может записать значение в YAML, но
не сообщить о нём параллельному сборщику. Именно такое расхождение обнаружено для
`ДополнительныеКолонки`: они присутствовали в окончательном YAML, но отсутствовали
в `additionalColumnsByTablePath` предварительного индекса, поэтому второй проход
считал их неизвестными.

Общий построитель работает непосредственно с уже находящимся в памяти объектом;
повторного чтения, разбора или сериализации YAML нет. Полученный индекс становится
единственным входом resolver и единственным DataPath-вкладом формы в состояние
проекта.

В общем состоянии проекта запись принадлежит файлу формы, заменяется атомарно с
его вкладом и удаляется при удалении файла.

## Индекс зависимостей

Индекс метаданных отвечает на вопрос, какие таблицы и деревья формы существуют.
Индекс зависимостей хранит обращения к ним из значений `DataPath`.

Для пути:

```yaml
ПутьКДанным: Элементы.ВходящиеСообщения.ТекущиеДанные.Вложения.ИндексКартинки
```

индекс зависимостей сохраняет исходное значение, YAML-путь и координаты, а после
разрешения связывает обращение как минимум с:

- элементом формы `ВходящиеСообщения`;
- конечным полем `ИндексКартинки`, если оно разрешено индексом метаданных.

Описание самого элемента формы в индексе зависимостей не дублируется.

## Расширение общего resolver

### Нейтральный договор

Общий resolver не получает условий по конкретным типам формы и русским либо
английским служебным словам. Реализация формы регистрирует нейтральный диалект
`DataPath`, содержащий:

- пару имён служебного корня в internal- и YAML-представлениях;
- пару имён служебного члена текущей строки;
- способ найти объявленный элемент формы по имени;
- признак, что найденный элемент может быть владельцем текущей строки;
- способ получить источник данных и тип текущей строки.

Так `metadata/orchestration`, `metadata/validation` и `metadata/project` работают
через общий договор и не знают о `Items`, `CurrentData`, таблицах формы или
деревьях формы.

### Семантическое разрешение

Resolver обрабатывает путь последовательно и хранит текущую разрешённую сущность.

1. Первый сегмент рассматривается как служебный корень только в диалекте формы.
2. Следующий сегмент должен разрешиться в индексе метаданных как таблица или
   дерево формы.
3. `CurrentData` / `ТекущиеДанные` получает служебный смысл только тогда, когда
   текущая сущность уже является такой таблицей или деревом.
4. После перехода к текущей строке оставшиеся сегменты разрешаются обычными
   правилами `DataPath`: как колонки, объектные поля, стандартные реквизиты и
   другие уже поддержанные источники.

Следовательно, смысл `ТекущиеДанные` определяется владельцем, а не фиксированным
номером сегмента.

### Разрешение коллизий

Служебная конструкция имеет приоритет только при полном семантическом совпадении:

```text
Элементы.<объявленная таблица или дерево>.ТекущиеДанные
```

Если элемент после `Элементы` не найден среди таблиц и деревьев формы, resolver
возвращается к обычному пространству реквизитов формы и пытается разрешить
`Элементы` как реквизит или параметр. Один лишь текст `Элементы` не переключает
режим разрешения.

Аналогично сегмент `ТекущиеДанные` вне владельца-таблицы или владельца-дерева
остаётся обычным именем данных.

## Единый результат анализа

Общая часть resolver возвращает структурированный результат без YAML-координат:

- исходный путь;
- каноническое internal-представление;
- каноническое YAML-представление;
- конечную разрешённую цель и её тип;
- все разрешённые цели, необходимые индексу зависимостей;
- выполненные замены сегментов и их семантические причины;
- машинно-читаемую причину неразрешённости.

Преобразование имён, validation и извлечение зависимостей не разбирают путь
повторно и не поддерживают отдельные таблицы исключений. Validation-обёртка лишь
добавляет к результату `filePath`, YAML-путь, координаты и уровень диагностики.

## Потоки операций

### XML → YAML

1. Первый проход читает форму и полностью формирует смысловой объект YAML,
   включая реквизиты, обычные и дополнительные колонки, таблицы и деревья формы.
2. Общий `createFormDataPathIndexFromYAML` строит по этому объекту локальный индекс
   формы без отдельного разбора текста.
3. После готовности индекса все отложенные `DataPath` проходят через общий
   resolver в направлении internal → YAML.
4. Служебные сегменты переводятся только после семантического разрешения.
5. В окончательный YAML записывается канонический путь с `Элементы` и
   `ТекущиеДанные`.
6. Из окончательного значения и того же индекса формируется вклад состояния
   проекта, который использует последующая validation.

### Validation YAML

1. Первый этап разбирает YAML и строит локальный индекс метаданных формы.
2. Значения `DataPath` сохраняются как отложенные проверки с координатами.
3. После обновления общего неизменяемого индекса второй этап вызывает общий
   resolver.
4. Resolver одновременно проверяет путь и возвращает его цели для индекса
   зависимостей.
5. Validation-обёртка формирует диагностику по машинной причине ошибки.

### YAML → XML, синхронизация, поиск ссылок и переименование

Эти операции используют тот же индекс метаданных, те же сохранённые зависимости
и тот же resolver. YAML → XML берёт его internal-представление; поиск ссылок и
переименование используют разрешённые цели. Отдельного распознавания
`Элементы`/`ТекущиеДанные` в каждой операции нет.

## Диагностика

Нужны отдельные машинные причины как минимум для следующих случаев:

- после служебного корня не найдена таблица или дерево формы, и обычный путь от
  реквизита `Элементы` также не разрешился;
- у таблицы или дерева отсутствует источник данных, необходимый для определения
  типа текущей строки;
- английское служебное имя использовано в YAML;
- путь продолжен неизвестным полем текущей строки.

Диагностика должна указывать всё исходное значение `DataPath`, проблемный сегмент
и его YAML-координаты. Отсутствие `ПутьКДанным` у найденной таблицы или дерева не
должно превращаться в сообщение `неизвестный корень`.

## Тестирование

### Индекс метаданных формы

- таблица с `ПутьКДанным` сохраняется с путём;
- таблица без `ПутьКДанным` всё равно сохраняется;
- дерево формы сохраняется наравне с таблицей;
- остальные элементы формы не попадают в проекцию;
- import и validation вызывают один построитель по смысловому объекту YAML;
- обычные и дополнительные колонки попадают в индекс при XML-импорте;
- индекс не зависит от уведомлений нестандартных XML-преобразователей о
  завершённых свойствах;
- двоичное состояние проекта сохраняет, читает, заменяет и удаляет записи.

### Resolver

- XML-путь `Items.Таблица.CurrentData.Поле` преобразуется в
  `Элементы.Таблица.ТекущиеДанные.Поле`;
- YAML-путь преобразуется обратно в internal-представление;
- `ТекущиеДанные` распознаётся только у таблицы или дерева;
- путь продолжает разрешаться по типу текущей строки;
- реквизит формы `Элементы` разрешается как обычный реквизит, когда служебная
  конструкция не подтверждена индексом;
- обычное поле `ТекущиеДанные` не переименовывается;
- английские служебные имена в YAML не проходят validation;
- таблица без источника данных получает точную диагностику.

### Общие потребители

- import и validation разрешают один путь одинаково;
- `Items.Таблица.CurrentData.ДополнительнаяКолонка` разрешается при XML-импорте
  через `ДополнительныеКолонки` готовой формы;
- YAML → XML использует internal-форму того же результата;
- поиск ссылок находит обращение к элементу формы;
- переименование таблицы или дерева обновляет соответствующий сегмент `DataPath`;
- удаление элемента оставляет проверяемую неразрешённую зависимость;
- существующие пути от реквизитов формы и стандартные реквизиты не меняют
  поведение.

## Вне области

- Индексирование всех видов элементов формы.
- Новая логика для элементов, которые не являются таблицами или деревьями.
- Эвристическое распознавание служебных сегментов только по их тексту.
- Отдельный resolver для import, validation, синхронизации или операций со
  ссылками.
- Изменение правил уже поддержанных обычных и произвольных путей `DataPath`.

# Значение заполнения владельца при пустом списке владельцев справочника

## Контекст

Эффективный тип стандартного реквизита `Владелец` определяется свойством
справочника `Владельцы`. Если список содержит несколько объектов, тип реквизита
составляется из ссылок на эти объекты.

В контрольном импорте SED найдены 11 собственных справочников, у которых
исходный XML одновременно содержит:

```xml
<Owners/>
```

и явно заполненный `xr:FillValue` стандартного реквизита `Owner`. Текущая
проверка не может определить тип значения и выдаёт предупреждение
`не определены владельцы справочника`.

Это не случай пропущенного YAML-значения по умолчанию: список владельцев
действительно пуст в исходном XML. Выводить тип владельца из самого
`ЗначениеЗаполнения` нельзя, потому что такая проверка подтверждала бы значение
с его же помощью и скрывала повреждённую конфигурацию.

## Цель

Считать любое значение заполнения стандартного реквизита `Владелец`
несовместимым, если у собственного справочника нет владельцев, и сохранять
исходную XML-форму только через явный `!xml`.

После реализации 11 предупреждений контрольного импорта должны исчезнуть без
потери исходного XML.

## Границы

В задачу входят только:

- собственный справочник;
- стандартный реквизит `Владелец`;
- пустое или отсутствующее YAML-свойство `Владельцы`;
- явно присутствующий `ЗначениеЗаполнения`.

В задачу не входят:

- заимствованные объекты расширения;
- поиск владельцев заимствованного объекта в базовом компоненте;
- изменение свойств стандартных реквизитов заимствованного объекта;
- вывод владельца из значения заполнения;
- изменение общего формата `!xml`;
- раскрытие DefinedType и значения по умолчанию свойств `Код`.

Платформа не позволяет расширению изменять свойства стандартных реквизитов
заимствованного объекта. В XML такого объекта отсутствует `StandardAttributes`:
выгружаются служебная привязка объекта и добавленные расширением реквизиты.
Поэтому проверка этой задачи не выполняет наследование свойств стандартного
реквизита из базового компонента.

## Предметный договор

Для стандартного реквизита `Владелец` действуют три состояния:

1. Список `Владельцы` непустой — значение проверяется по составному ссылочному
   типу владельцев, как сейчас.
2. Список пуст и `ЗначениеЗаполнения` отсутствует — диагностики нет.
3. Список пуст и `ЗначениеЗаполнения` присутствует — значение несовместимо с
   моделью справочника.

В третьем состоянии обычное YAML-значение является ошибкой. Исходное значение
из XML сохраняется с согласованным исключительным тегом `!xml`.

Пустой список включает обе эквивалентные YAML-формы:

- ключ `Владельцы` отсутствует, потому что пустое XML-значение было опущено;
- явно записано `Владельцы: []`, если такая форма поступила во внутреннюю
  проверку.

## YAML-представление исключений

В 5 из 11 случаев исходный XML содержит пустой `DesignTimeRef`. Он записывается
как:

```yaml
СтандартныеРеквизиты:
  Владелец:
    ЗначениеЗаполнения: !xml DesignTimeRef
```

Это точно восстанавливает:

```xml
<xr:FillValue xsi:type="xr:DesignTimeRef"/>
```

В остальных 6 случаях XML содержит типизированную пустую ссылку. Она
записывается с исходным значением, например:

```yaml
СтандартныеРеквизиты:
  Владелец:
    ЗначениеЗаполнения: !xml Справочник.ПапкиФайлов.ПустаяСсылка
```

Обычные формы без тега не разрешены:

```yaml
ЗначениеЗаполнения: .
ЗначениеЗаполнения: Справочник.ПапкиФайлов.ПустаяСсылка
```

Они создают ошибку, потому что у справочника отсутствует допустимый тип
владельца.

## Архитектура

Решение остаётся в предметном модуле `commonObjects/fillValue`.
`classifyOwnerReference()` различает отсутствие значения заполнения и
присутствующее значение при пустом списке владельцев. Второй случай возвращает
`invalid`, а не `unresolved`.

Общий механизм `!xml` уже сохраняет несовместимое значение
`ЗначениеЗаполнения`. Пустой `DesignTimeRef` использует согласованный
транспортный литерал `!xml DesignTimeRef` из спецификации DefinedType. Для
состояния без владельцев этот литерал разрешён как XML-исключение, хотя
эффективный ссылочный тип отсутствует: вся политика стандартного реквизита в
этом состоянии запрещает обычное значение.

В общие metadata-операции не добавляются условия по типу объекта или имени
стандартного реквизита. Политика остаётся привязана к декларации `Владелец` и
исполняется предметным классификатором заполнения.

## Поведение операций

### XML → YAML

- Пустой `<Owners/>` импортируется по существующему правилу справочника.
- Отсутствующий `FillValue` не создаёт YAML-свойство.
- Пустой `xr:DesignTimeRef` создаёт `!xml DesignTimeRef`.
- Типизированная пустая ссылка создаёт `!xml <ссылка>`.
- Для этих 11 значений не создаётся запись снимка: XML-форма полностью задана
  явным YAML.

### Validation YAML

- Обычное значение заполнения при пустом `Владельцы` создаёт одну ошибку по
  точному пути `СтандартныеРеквизиты/Владелец/ЗначениеЗаполнения`.
- Согласованное `!xml` проходит локальную проверку несовместимости.
- Типизированная ссылка внутри `!xml` продолжает участвовать в проверке
  зависимостей, поиске и переименовании.
- `!xml DesignTimeRef` не создаёт ссылочную зависимость, потому что конкретной
  цели нет.
- Отсутствующее значение заполнения проходит без диагностики.

Схема подсказок не предлагает `!xml`, `DesignTimeRef` или произвольное значение
как штатный способ заполнения. Внутренняя validation-схема принимает только
зарегистрированные транспортные формы.

### YAML → XML

- `!xml DesignTimeRef` создаёт пустой
  `<xr:FillValue xsi:type="xr:DesignTimeRef"/>`.
- `!xml Справочник.<Имя>.ПустаяСсылка` создаёт типизированный
  `xr:DesignTimeRef` с соответствующим XML-значением.
- Тег и транспортное имя `DesignTimeRef` не попадают в текст XML.

## Диагностики

Обычное значение при пустом списке владельцев должно давать предметную ошибку:

```text
у справочника отсутствуют владельцы; значение заполнения реквизита Владелец допускается только с !xml
```

Диагностика `не определены владельцы справочника` для этого состояния больше не
используется. `unresolved` сохраняется только для случаев, когда список
присутствует, но один из его элементов невозможно разобрать.

## Проверки

Модульные и интеграционные проверки должны подтвердить:

1. Пустой список без `ЗначениеЗаполнения` проходит без диагностики.
2. Обычная пустая или типизированная ссылка при пустом списке даёт предметную
   ошибку.
3. `!xml DesignTimeRef` при пустом списке проходит validation и точно создаёт
   пустой `xr:DesignTimeRef` без reference XML и снимка.
4. `!xml <типизированная пустая ссылка>` проходит локальную проверку и сохраняет
   ссылочную зависимость.
5. При непустом списке владельцев сохраняется текущая проверка совместимости.
6. Неразбираемый элемент непустого списка остаётся `unresolved`.
7. Заимствованный справочник без `StandardAttributes` не создаёт проверку этой
   политики и не читает владельцев базового компонента.
8. Схема подсказок не содержит транспортные значения.

## Контрольный импорт SED

После реализации повторный чистый импорт должен дать:

- 5 значений `!xml DesignTimeRef`;
- 6 значений `!xml <типизированная пустая ссылка>`;
- ноль предупреждений `не определены владельцы справочника`;
- ноль ошибок для согласованных XML-исключений;
- точный YAML → XML round-trip всех 11 исходных `xr:FillValue`.

Остальные группы диагностик не меняются этой задачей.

# Частичная синхронизация Проекта в XML

Дата: 2026-08-09
Статус: согласованный проект решения

## Назначение

Частичная sync формирует отдельный пакет только для изменений Проекта после
последней подтверждённой XML-синхронизации. Пакет является ZIP-архивом внутри
`.nkdk`, который создаётся потоком через `zip.js`, передаётся в 1С и удаляется
после фиксации успешной передачи.

Операция поддерживает основную конфигурацию `cf` и отдельные расширения
`cfe/<Имя>`. Исходной точкой служит компонентный снимок конфигурации версии
1.3. При отсутствии применимого снимка частичная sync завершается ошибкой и не
переходит к полной выгрузке.

## Цели

- Находить добавленные, изменённые и удалённые файлы по составу и хэшам между
  текущим состоянием компонента и последним подтверждённым снимком.
- Через единую топологию ресурсов вычислять XML, затронутый каждым изменением.
- Разрешать сокращённые YAML-ссылки в канонические адреса по `rules.ts`, а не
  эвристиками по строкам и каталогам.
- Переиспользовать worker, правила и профили новой полной XML-sync.
- Различать физический состав пакета и точные цели в `load.lst`.
- Подготавливать пакет и фиксировать его успешную передачу разными операциями.
- Допускать не более одного неподтверждённого пакета одного компонента.
- Не создавать промежуточный распакованный XML-каталог.

## Не входит в первый этап

- Передача пакета в 1С и запуск загрузки.
- Публичные MCP-операции подготовки и фиксации пакета.
- Публичный полный цикл NKDK «подготовить → передать в 1С → зафиксировать».
- Автоматический переход к полной sync при отсутствии снимка.
- Сохранение архива после успешной передачи в 1С.
- Отдельный преобразователь YAML в XML для частичной sync.

## Выбранный подход

Полная и частичная sync используют общий конвейер XML-заданий. Новыми частями
являются определение непосредственных изменений, вычисление их влияния,
потоковая запись ZIP с `load.lst` и отложенная фиксация снимка после успешной
передачи в 1С.

Восстановление удалённой реализации на основе `owner`, `fileItem` и
`externalFile` отклонено: она зависела от старой оркестрации и существующего
XML-каталога как reference. Полная временная выгрузка с последующим сравнением
также отклонена: она требует прежней полной XML-копии и не даёт требуемого
выигрыша по времени.

## Компоненты

### Детектор изменений

Детектор получает полный текущий состав и хэши файлов компонента из
согласованного состояния Проекта и сравнивает их с `files` снимка. Результат
содержит три непересекающихся множества путей:

- `added` — путь есть только в текущем состоянии;
- `changed` — путь есть в обоих состояниях, но хэш отличается;
- `deleted` — путь есть только в снимке.

Отдельный `.nkdk-sync` не является источником состояния и новой операции не
нужен.

### Источники хэшей

Стороны сравнения берутся из двух существующих файлов, у которых разные
назначения:

- `.nkdk/cache/project-state.bin` содержит актуальные хэши всего Проекта после
  этапов Б1–Б6. Это восстанавливаемый кэш текущего состояния, который может
  обновляться validation и другими операциями; предыдущая версия этого файла не
  является точкой синхронизации;
- `.nkdk/components/<компонент>/configuration-index.bin`, секция `files`,
  содержит состав и хэши последнего опубликованного состояния компонентной
  синхронизации: import, полной sync либо подтверждённой частичной sync. Для
  основной конфигурации используется компонент `cf`, для расширения —
  `cfe/<Имя>`.

Детектор сравнивает текущую компонентную проекцию `project-state.bin` с
`files` соответствующего `configuration-index.bin`: путь только в текущем
состоянии считается добавленным, разные хэши одного пути — изменением, путь
только в компонентном снимке — удалением.

При выполнении XML-задания worker повторно вычисляет хэш фактически прочитанных
байтов и сверяет его с текущим ожидаемым хэшем из `project-state.bin`. Эта
проверка защищает от редактирования файла во время `prepare`, но не участвует в
определении изменений с прошлой подтверждённой синхронизации.

### Канонические ссылки

Текст ссылки сам по себе не определяет состав пакета. Во время этапов Б1–Б6
значение разбирается правилом свойства вместе с его ограничением и контекстом
владельца. Например:

- `Справочник.Номенклатура` становится `Catalog.Номенклатура`;
- `Номенклатура` становится `Catalog.Номенклатура`, только если правило
  разрешает единственный корень `Catalog`;
- локальный `Артикул` внутри справочника становится
  `Catalog.Товары.Attribute.Артикул`, если правило ожидает реквизит текущего
  владельца.

Неизвестное, запрещённое или неоднозначное сокращение является ошибкой
validation. Планировщик не пытается угадать адрес по имени файла.

Общий индекс связывает канонический адрес с компонентом и исходным путём
Проекта. Для `cfe` поиск выполняется сначала в выбранном расширении, затем в
`cf`; соседние расширения не видны.

Обычная ссылка не расширяет пакет. Например, если изменился
`Справочник/Заказы/Свойства.yaml` с типом реквизита
`Справочник.Номенклатура`, выгружается XML справочника `Заказы`, но не XML
`Номенклатура`. Если изменилась сама `Номенклатура`, её собственный хэш выберет
её XML отдельно.

Если цель удалена, а ссылка осталась, подготовку останавливает validation. Если
ссылка исправлена или переписана migration, изменится содержащий её YAML и он
попадёт в непосредственные изменения.

Согласованность заимствованной формы расширения с текущей формой `cf` также
обеспечивает validation. Если в основной форме появился элемент, которого нет в
форме расширения, пакет не создаётся. После обновления YAML расширения его хэш
изменится, и форма попадёт в пакет обычным способом. Снимок не хранит отдельные
отпечатки зависимостей или поколение `cf`.

Этот валидатор является обязательной частью первого этапа, а не предположением
о существующей реализации. До его готовности частичная sync компонентов с
заимствованными формами не считается поддержанной. Минимальный договор
валидатора: каждый элемент текущей базовой формы должен присутствовать в форме
расширения; диагностика указывает форму расширения и отсутствующий элемент.

### Планировщик влияния

Планировщик классифицирует пути единой топологией ресурсов. Он строит два
независимых множества:

- `payload` — ресурсы и XML-задания, файлы которых физически войдут в пакет;
- `loadTargets` — нормализованные XML-пути, записываемые в `load.lst`.

Изменение существующего содержательного файла выбирает его обычное XML-задание.
Изменение внешнего файла выбирает точный внешний путь. Добавление или удаление
дочернего объекта поднимает влияние до ближайшего владельца, XML которого
содержит состав дочерней коллекции. Изменение состава объектов верхнего уровня
поднимается до `Configuration.xml`.

Удалённый путь классифицируется по шаблонам топологии без обращения к уже
отсутствующему файлу. XML удалённого элемента не создаётся: удаление выражается
актуальным XML владельца и соответствующей целью загрузки.

После непосредственных и структурных изменений планировщик добавляет явно
объявленные сопутствующие файлы пакета. Расширение повторяется до неподвижной
точки; множества заданий и путей устраняют циклы и повторы. Обычные
metadata-ссылки в это замыкание не входят.

### Декларативные правила пакета

Общая оркестрация не содержит условий по `itemType`, именам XML-корней или
каталогам `Формы` и `Макеты`. Особенности пакета объявляются рядом с
регистрациями конкретных metadata:

- какой XML-документ задания является целью `load.lst`;
- какие XML-документы являются только сопутствующим содержимым;
- нужно ли при изменении состава включить актуальный подкаталог владельца;
- какие корневые спутники обязательны при загрузке `Configuration.xml`;
- попадает ли сопутствующий ресурс в `load.lst` или только в `payload`;
- на каком владельце прекращается рекурсивное расширение пакета.

Для `Configuration` запрещено рекурсивно включать весь компонент. Корневая
композиция добавляет только непосредственно затронутые объекты и явно
объявленные спутники, например используемый язык и клиентский интерфейс.

### Общий исполнитель XML-заданий

Исполнитель получает подмножество заданий той же формы, что и полная sync.
Worker используют те же `rules.ts`, общий индекс, снимок идентификаторов,
resolver, профиль конфигурации или расширения и проверки ожидаемых выходов.

Получатель результата различается: полная sync записывает файлы в XML-каталог,
частичная возвращает сгенерированные XML-байты главному процессу. Один
принадлежащий главному процессу `ZipWriter` из `zip.js` добавляет эти байты в
архив; worker не пишут в общий ZIP напрямую. Число готовых, но ещё не записанных
результатов ограничивается очередью, чтобы память зависела от выбранного
параллелизма, а не от размера всего пакета.

Внешние файлы, включая модули, читаются с диска потоком непосредственно в ZIP с
одновременным вычислением и проверкой хэша. Сам ZIP также пишется потоком сразу
по уникальному пути
`.nkdk/tmp/incremental-sync/<компонент>/<package-id>.zip`; отдельного
промежуточного `.zip.tmp` и распакованного каталога нет. До успешного закрытия и
проверки ZIP не считается подготовленным пакетом. При ошибке незавершённый файл
удаляется.

`load.lst` записывается в UTF-8, по одному пути с `/` на строку. Порядок строк
не имеет предметного смысла и стабилизируется сортировкой по UTF-8-байтам. Файл
находится в корне ZIP рядом со штатной XML-иерархией `payload`.

## Правила состава пакета

| Изменение | Файлы `payload` | `loadTargets` |
|---|---|---|
| Реквизит объекта | XML объекта | XML объекта |
| Содержимое формы | XML формы и `Ext/Form.xml` | XML формы |
| Модуль | Сам файл `.bsl` | Тот же `.bsl` |
| Очистка модуля | Файл `.bsl`, содержащий только UTF-8 BOM | Тот же `.bsl` |
| Добавление формы | XML владельца и актуальный XML-подкаталог владельца | Владелец и новая форма |
| Удаление формы | XML владельца и оставшийся XML-подкаталог владельца | Владелец |
| Добавление объекта верхнего уровня | Новый объект с содержимым, `Configuration.xml` и обязательные корневые спутники | Новый объект, корень и обязательные зависимости |
| Удаление объекта верхнего уровня | `Configuration.xml` и обязательные корневые спутники | Корень и обязательные зависимости |
| Переименование | Объединённый результат удаления старого и добавления нового | Новые пути и владельцы |

Матрица основана на пакетах EDT из `nkdk_service/edt_changes`. В частности:

- изменение формы физически создаёт её XML и `Ext/Form.xml`, но загружает XML
  формы;
- изменение модуля создаёт и загружает только сам `.bsl`;
- очистка модуля создаёт и загружает файл из трёх байтов UTF-8 BOM;
- добавление формы загружает новую форму и владельца;
- удаление формы загружает только владельца, но сохраняет в пакете весь его
  оставшийся актуальный подкаталог;
- изменение состава справочников включает `Configuration.xml`, язык и
  клиентский интерфейс согласно их разным ролям в `payload` и `loadTargets`.

## Переименования и migration

Переименование не определяется эвристикой по совпавшему содержимому. Источником
связи старого и нового логического адреса остаётся проверенная migration.
Планировщик объединяет влияние удаления старого пути и добавления нового.
Worker получают отображение прежних адресов на новые и переносят сохранённые
идентификаторы, поэтому переименование не превращается в создание другого
объекта.

Состояние применённых migration входит в отложенное подтверждение пакета и не
обновляется во время подготовки.

## Подготовка пакета

Внутренняя операция ядра `preparePartialXmlSyncPackage` выполняет следующий
договор. На этом этапе она не регистрируется как MCP-инструмент; позднее её
вызовет полный цикл NKDK перед передачей архива в 1С.

1. Нормализует адрес компонента. Удаляет оставшиеся от предыдущей неуспешной
   попытки ожидающее состояние, его ZIP и незарегистрированные незавершённые ZIP
   этого компонента: новая попытка всегда начинается заново от последнего
   опубликованного снимка.
2. Актуализирует и валидирует весь Проект обычными этапами Б1–Б6.
3. Читает и проверяет компонентный снимок. Отсутствующий или повреждённый
   снимок является ошибкой.
4. Для `cfe/<Имя>` подтверждает совпадение текущего `cf` с его снимком и строит
   обычный составной контекст индексов расширения и основной конфигурации.
5. Вычисляет непосредственные изменения и проверенную цепочку migration.
6. Если изменений и неприменённых migration нет, возвращает результат «нет
   изменений», не создаёт ZIP и не публикует ожидающее состояние.
7. Строит `payload` и `loadTargets`, затем выполняет выбранные XML-задания в
   потоковый ZIP через единственный `ZipWriter` главного процесса.
8. Повторно проверяет хэши прочитанных или скопированных байтов и точное
   совпадение состава записей закрытого ZIP с планом.
9. Формирует кандидат следующего снимка и состояние применённых migration.
10. Публикует ожидающее состояние и возвращает идентификатор, путь и хэш ZIP.

Если YAML изменился между первым чтением и обработкой задания, подготовка
завершается ошибкой. Снимок и состояние migration остаются прежними.

## Кандидат следующего снимка

Кандидат строится во время `prepare`, но не публикуется. Он содержит:

- полный состав и хэши компонента на момент подготовки;
- прежние `entity` неизменившихся исходных путей;
- полные новые фрагменты `entity` выполненных заданий;
- удаление прежних `entity` исчезнувших путей;
- перенесённые migration идентификаторы;
- следующее значение `indexGeneration`.

Фрагмент выполненного задания заменяет прежние `entity` своего
`sourceProjectPath` целиком; пустой фрагмент означает их удаление. Таким образом,
частичное выполнение не оставляет смесь старых и новых сведений одного файла.

## Ожидающее состояние

Ожидающее состояние хранится отдельно от ZIP и логически содержит:

- идентификатор и адрес компонента;
- путь и хэш ZIP;
- поколение и контрольную сумму исходного снимка;
- готовые байты следующего снимка;
- поколение и контрольную сумму снимка `cf`, фактически использованного при
  подготовке пакета расширения;
- готовое следующее состояние применённых migration.

На один компонент допускается одно ожидающее состояние. Новая частичная
`prepare` является единственным исключением: она явно заменяет его и начинает
всю попытку заново. Пока ожидающее состояние существует, import и полная sync
этого компонента блокируются. Validation и операции только для чтения
разрешены.

Изменение `cf` не помечает файлы расширения изменёнными. Их согласованность с
текущей основной конфигурацией проверяет validation до планирования. Ожидающий
пакет расширения фиксирует поколение и контрольную сумму снимка `cf` только для
защиты промежутка между `prepare` и фиксацией: если основная конфигурация была
подтверждённо изменена в этот промежуток, пакет нужно подготовить заново.

## Фиксация успешной передачи

Фиксация является внутренней операцией ядра и не регистрируется как отдельный
MCP-инструмент. На текущем этапе публичного цикла частичной синхронизации нет,
поскольку передача в 1С не реализуется. В будущем общий цикл NKDK сначала
вызовет внутреннюю подготовку, передаст ZIP и вызовет внутреннюю фиксацию только
после того, как 1С сообщит об успешном применении ZIP. Она:

1. Проверяет идентификатор, принадлежность компоненту и хэш сохранённого ZIP.
2. Проверяет поколение и контрольную сумму текущего снимка, а для расширения —
   неизменность подтверждённого снимка `cf`.
3. Атомарно публикует заранее подготовленный снимок.
4. Публикует состояние применённых migration.
5. Удаляет ZIP и снимает ожидающее состояние.

Текущие YAML-файлы при фиксации не обязаны совпадать с пакетом. Если после
`prepare` их снова изменили, подтверждается именно применённый пакет, а
следующая `prepare` обнаружит новые изменения относительно его хэшей.

Фиксация восстанавливается после сбоя между шагами. Если снимок уже равен
кандидату ожидающего состояния, повторный вызов завершает публикацию migration,
удаление ZIP и ожидающего состояния без повторного увеличения поколения. После
успешной передачи в 1С нельзя вызывать новую `prepare`: при сбое повторяется
только операция фиксации, чтобы не передать пакет в 1С второй раз.

До появления полного цикла внутренний договор фиксации проверяется напрямую в
тестах ядра. Пользователь текущего MCP не вызывает его и не сообщает NKDK об
успехе 1С вручную.

## Ошибки

Подготовка не публикует ожидающее состояние при следующих ошибках:

- снимок отсутствует, повреждён или относится к другому компоненту;
- validation блокирует sync;
- изменённый путь не классифицируется топологией и не объявлен игнорируемым;
- для ресурса отсутствует правило влияния или возможность XML-обработки;
- основная конфигурация расширения не синхронизирована;
- форма расширения не содержит элемент текущей базовой формы;
- исходный файл изменился во время операции;
- worker, перенос внешнего файла или проверка состава завершились ошибкой.

Фиксация ничего не меняет при неизвестном идентификаторе, изменённом ZIP, чужом
текущем поколении снимка или изменившейся основе расширения. Ошибка фиксации
сохраняет ожидающее состояние, чтобы повторить только эту операцию.

Частично записанный ZIP при ошибке подготовки удаляется, не считается пакетом и
не блокирует следующий вызов. Опубликованный снимок и migration не меняются.

## Проверка

Главный инвариант: каждый сгенерированный XML-файл частичного пакета побайтно
совпадает с соответствующим файлом свежей полной sync того же состояния
Проекта.

Модульные проверки покрывают:

- сравнение составов и хэшей `added`, `changed`, `deleted`;
- свёртку повторного влияния нескольких путей;
- независимость `payload` и `loadTargets`;
- канонизацию полного, сокращённого и локального YAML-адреса;
- отсутствие расширения пакета по обычной metadata-ссылке;
- раздельное включение сопутствующего файла в `payload` и `load.lst`;
- потоковую запись ZIP без распакованного каталога и без накопления всего архива
  в памяти;
- ограничение очереди XML-результатов при параллельной генерации;
- завершение замыкания при циклических правилах сопутствующих файлов;
- остановку рекурсивного расширения на корне конфигурации;
- детерминированную сериализацию `load.lst`;
- классификацию удалённого пути по топологии;
- перенос идентификаторов migration.

Контрактные проверки топологии доказывают, что каждый учитываемый путь Проекта
либо даёт план влияния, либо явно игнорируется. Особенности конкретных metadata
проверяются рядом с их регистрациями.

Интеграционные проверки покрывают:

- сценарии `edt_changes` для реквизита, формы, модуля, состава владельца,
  верхнеуровневого объекта и переименования;
- точные множества файлов пакета и строк `load.lst`;
- побайтовое равенство файлов частичной и полной sync;
- `cf` и `cfe`, включая заимствованные формы;
- блокировку validation, когда обновлённая базовая форма содержит отсутствующий
  в форме расширения элемент;
- отсутствие пакета расширения при изменении только `cf`;
- очистку модуля с записью UTF-8 BOM и прямой целью в `load.lst`;
- отсутствие снимка и отсутствие изменений;
- замену предыдущего неподтверждённого ZIP новой полной попыткой `prepare`;
- очистку незавершённого ZIP после ошибки и после аварийного завершения процесса;
- изменение файла во время подготовки и после неё;
- `prepare → успешная передача → фиксация`, удаление ZIP и восстановление
  повторной фиксации после сбоя;
- обнаружение следующего изменения после подтверждения ранее подготовленного
  пакета.

После каждого законченного слоя выполняется проверка дубликатов относительно
базового коммита. Перед завершением реализации выполняются проверка типов и
полный `pnpm test` из корня проекта.

# XML-defaults элементов формы без reference

## Проблема

Round-trip форм содержит три разных класса XML-defaults:

1. разные значения, подразумеваемые отсутствием XML-тега и YAML-ключа;
2. XML-default, зависящий от соседнего свойства элемента;
3. default, зависящий от контекста и поэтому не имеющий единственного
   `implicitValueYAML`.

### Разные неявные значения

`Table.EnableStartDrag` и `Table.EnableDrag` имеют разные компактные
представления в XML и YAML:

| Конфигуратор | XML | YAML |
|---|---|---|
| `Истина` — default | явный тег со значением `true` | ключ отсутствует |
| `Ложь` | тег отсутствует | явный ключ со значением `false` |

Каталог `all` содержит обе формы в одном `Form.xml` версии 2.20. Таблица
`ПоУмолчанию` содержит явное `true`, а таблица со свойством, переключённым в
`false`, не содержит XML-тег. Следовательно, отсутствие XML-тега означает
`false`, а отсутствие YAML-ключа — `true`.

Для `EnableDrag` вывод подтверждён всеми конфигурациями в
`/Users/nikita/git/round-trip-compact/cf`. Среди 28 192 таблиц 16 067 содержат
`<EnableDrag>true</EnableDrag>`, 12 125 не содержат тег, явный `false` не
встречается. В каталоге `doc` все 1 041 расхождение этой группы соответствуют
удалению явного `true`.

Существующие поля не выражают этот договор:

- `implicitValueYAML` описывает только значение отсутствующего YAML-ключа;
- `defaultValueXML` создаёт XML-значение при отсутствии данных, но не описывает
  значение отсутствующего XML-тега.

### Контекстный XML-default

`CheckBoxField.CheckBoxType` зависит от `ThreeState`:

| Конфигуратор | XML | YAML |
|---|---|---|
| Обычный флажок, вид `Auto` | `<CheckBoxType>Auto</CheckBoxType>` | ключ `ВидФлажка` отсутствует |
| `ThreeState=true` | тег `CheckBoxType` отсутствует | `ТриСостояния: true` |

Условие подтверждается всеми 2 033 флажками каталога `doc`: 1 963 обычных
флажка содержат `Auto`, 34 трёхсостояния не содержат `CheckBoxType`, остальные
36 явно задают другой вид.

Здесь отсутствие XML-тега не означает отдельное значение `CheckBoxType`.
Поэтому `implicitValueXML` к этому свойству не применяется: экспорт XML-default
нужно разрешать или запрещать по `threeState`.

### Контекстно-зависимый default

`Table.Representation` зависит от источника данных таблицы. Полный анализ всех
конфигураций в `/Users/nikita/git/round-trip-compact/cf` дал следующую картину:

| Источник | `List` | `Tree` | Тег отсутствует |
|---|---:|---:|---:|
| `ValueTable` | 6 704 | 109 | 74 |
| `ValueTree` | 272 | 3 325 | 18 |
| `DynamicList` | 7 381 | 547 | 3 092 |
| `ValueList` | 763 | 0 | 1 |

Всего исследовано 28 192 элемента `Table` из конфигураций `acc`, `all`,
`doc`, `erp`, `small` и `trade`: 17 605 содержат явный `List`, 4 645 — `Tree`,
5 942 не содержат тег. Каталог `clean` не содержит форм с таблицами. Все
исследованные формы имеют версию 2.20.

Явный `List` нельзя считать безусловным YAML-default. В частности, 272 таблицы
с источником `ValueTree` явно переключены в `List`, тогда как для того же типа
источника преобладает `Tree`. У каждого основного типа источника одновременно
встречаются явный `List` и отсутствие тега. Поэтому присутствие `List` нельзя
восстановить по типу источника или версии формы.

Текущее `implicitValueYAML: "List"` склеивает два состояния: явный `List` и
отсутствующее свойство. В версии 0.0.3 различие восстанавливалось только из
reference XML, а не из `rules.ts`.

## Решение

В базовое декларативное правило свойства добавляется нейтральное поле:

```ts
implicitValueXML?: unknown
```

Оно означает значение, представленное отсутствием XML-тега. Договор включается
только для правил, явно содержащих `implicitValueXML`; поведение остальных
правил не меняется.

`TableRules.enableStartDrag` описывается так:

```ts
enableStartDrag: booleanRule({
  yaml: "РазрешитьНачалоПеретаскивания",
  implicitValueYAML: true,
  implicitValueXML: false,
})
```

`TableRules.enableDrag` использует тот же договор:

```ts
enableDrag: booleanRule({
  yaml: "РазрешитьПеретаскивание",
  implicitValueYAML: true,
  implicitValueXML: false,
})
```

`implicitValueXML` и `defaultValueXML` нельзя задавать одновременно: первое
описывает отсутствие XML-узла, второе — создаваемое XML-значение. Такое
сочетание считается ошибкой договора rules.ts.

Для общего правила `CheckBoxField` используется существующий
`defaultValueXML` с локальным условием:

```ts
checkBoxType: {
  yaml: "ВидФлажка",
  type: "SystemEnumeration",
  typeSE: "CheckBoxType",
  implicitValueYAML: "Auto",
  defaultValueXML: "Auto",
  toXML: (source) => source.raw("threeState") !== true,
}
```

Правило используется `CheckBoxField` и `TableCheckBoxField`, поэтому одинаково
работает для обычного и табличного флажка.

У `TableRules.representation` удаляется безусловный YAML-default:

```ts
representation: {
  yaml: "Отображение",
  type: "SystemEnumeration",
  typeSE: "TableRepresentation",
  noImplicitValueYAML: true,
}
```

Отсутствие свойства остаётся отсутствием в обеих формах, а явные `List`,
`Tree` и `HierarchicalList` сохраняются. Конфигуратор выбирает представление
для отсутствующего свойства в контексте источника данных. Частные проверки
`ValueTable`, `ValueTree` и `DynamicList` не добавляются.

## Преобразования

### XML → YAML

Если XML-тег присутствует, используется его явное значение. Если тег
отсутствует, используется `implicitValueXML`. Полученное значение исключается
из YAML только при совпадении с `implicitValueYAML`.

Для `EnableStartDrag` и `EnableDrag`:

- явное XML `true` совпадает с YAML-default и не записывается в YAML;
- отсутствующий XML-тег становится явным YAML `false`.

### YAML → XML

Если YAML-ключ присутствует, используется его значение. Если ключ отсутствует,
используется `implicitValueYAML`. Полученное значение не записывается в XML
только при совпадении с `implicitValueXML`.

Для `EnableStartDrag` и `EnableDrag`:

- отсутствующий YAML-ключ создаёт XML `true`;
- явный YAML `false` не создаёт XML-тег.

### CheckBoxType

При отсутствии YAML-ключа `ВидФлажка` существующий `defaultValueXML`
восстанавливает `Auto`. Локальное условие проверяет `ТриСостояния`:

- если `threeState !== true`, создаётся `<CheckBoxType>Auto</CheckBoxType>`;
- если `threeState === true`, свойство не экспортируется.

Явно заданный вид обычного флажка экспортируется без изменений.

### Representation

При наличии XML-тега значение всегда записывается в YAML, в том числе
`Отображение: Список`. При отсутствии XML-тега YAML-ключ не создаётся.

При экспорте явное YAML-значение создаёт соответствующий XML-тег. Отсутствующий
YAML-ключ не создаёт `Representation`, оставляя выбор default Конфигуратору.
Таким образом, явное значение не смешивается с контекстным default.

Механизм не читает reference XML и не сохраняет присутствие свойства в снимке.

## Границы архитектуры

Общая orchestration знает только два неявных значения представлений и не знает
про `Table`, `EnableStartDrag`, `EnableDrag` или формы. Частное соответствие
объявляется в `TableRules`.

На первом этапе новый договор `implicitValueXML` применяется только к
`TableRules.enableStartDrag` и `TableRules.enableDrag`. Контекстный default
добавляется только к общему правилу `CheckBoxField.checkBoxType`. Для
`TableRules.representation` новый механизм не нужен: отсутствие безусловного
default явно отмечается `noImplicitValueYAML: true`. Остальные свойства
переводятся на эти механизмы лишь после отдельного подтверждения их
XML-семантики.

## Отклонённые варианты

- Локальные `fromXML/toXML` для `EnableStartDrag` и `EnableDrag` дублируют
  нейтральную симметрию представлений переходным кодом формы.
- Отдельный property-тип булевого XML-флага избыточен: договор применим не
  только к boolean и выражается парой неявных значений.
- Безусловный `defaultValueXML: "Auto"` для `CheckBoxType` неверен: он добавит
  тег трёхсостоянию.
- `implicitValueYAML: "List"` для `Representation` неверен: default зависит от
  источника данных, а явный `List` может быть осознанным переопределением.
- `implicitValueXML` для `Representation` не решает проблему: он также смешает
  отсутствующее свойство с одним из явных значений.
- Ветвление правила `Representation` по `ValueTable`, `ValueTree` и
  `DynamicList` не восстанавливает исходную явность тега и добавляет знание о
  типах источников в преобразование.
- Reference XML и снимок не используются для известных и вычислимых значений.

## Проверка

Существующие тесты общего преобразования расширяются полной матрицей:

- отсутствующий XML → явный YAML `false`;
- XML `true` → отсутствующий YAML-ключ;
- отсутствующий YAML-ключ → XML `true`;
- YAML `false` → отсутствующий XML-тег.

Проверка правила таблицы подтверждает ту же матрицу отдельно на
`TableRules.enableStartDrag` и `TableRules.enableDrag`, не изменяя исходные
XML-фикстуры. Полный YAML round-trip каталога `doc` должен убрать 1 041
расхождение, вызванное удалением `EnableDrag=true`. Отдельная архитектурная
проверка запрещает совместное использование `implicitValueXML` и
`defaultValueXML`.

Существующая проверка флажков расширяется двумя границами:

- обычный флажок без `ВидФлажка` получает XML `CheckBoxType=Auto`;
- флажок с `ТриСостояния: true` не получает `CheckBoxType`.

Проверка `TableRules.representation` покрывает четыре преобразования:

- XML `List` → явный YAML `Отображение: Список`;
- отсутствующий XML-тег → отсутствующий YAML-ключ;
- явный YAML `Отображение: Список` → XML `List`;
- отсутствующий YAML-ключ → отсутствующий XML-тег.

Архитектурная проверка defaults таблицы требует для `representation`
`noImplicitValueYAML: true` и не допускает возврата безусловного
`implicitValueYAML`.

Дополнительная проверка с источником `ValueTree` подтверждает, что явный `List`
не исключается как default. Полный YAML round-trip каталога `doc` должен убрать
все 1 198 расхождений, вызванных удалением `Representation=List`; остальные
классы расхождений проверяются отдельно.

Отдельный тест `TableCheckBoxField` добавляется только при обнаружении
отличающегося пути экспорта; общий договор защищается одним набором проверок.

После реализации выполняются mutation testing изменённых production-файлов,
`pnpm type-check` и полный `pnpm test`.

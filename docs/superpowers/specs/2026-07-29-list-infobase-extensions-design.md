# Получение списка расширений информационной базы

## Контекст

NKDK уже умеет работать с информационной базой через два режима платформы
1С:Предприятие 8.3.27:

- агент Конфигуратора (`designer-agent`) с интерактивными командами по SSH;
- offline-режим `ibcmd` (`standalone-server`) с приватным `config.yaml`.

Оба режима скрыты за `PlatformSession` и управляются единым
`PlatformSessionManager`. Менеджер выбирает установку платформы, последовательно
выполняет операции одного проекта, переиспользует подходящий сеанс и закрывает
его после `sessionIdleTimeout`.

После успешного импорта конфигурации параметры подключения сохраняются в
`.nkdk/project.yaml`. Для последующего импорта выбранного расширения нужен
публичный способ получить полный типизированный список расширений этой базы без
повторной передачи строки подключения и учётных данных.

## Цель

Добавить публичный MCP-инструмент `nkdk.list_infobase_extensions`, который по
корню проекта читает сохранённые настройки подключения и возвращает свойства
всех расширений информационной базы через любой из двух поддерживаемых режимов
работы с платформой.

## Границы первой версии

В первую версию входят:

- вход только с `projectDir`;
- чтение подключения из `.nkdk/project.yaml`;
- оба существующих режима платформы;
- файловые и клиент-серверные подключения, допустимые текущими настройками;
- полный типизированный набор поддерживаемых платформой свойств расширения;
- сохранение порядка, возвращённого платформой;
- отмена через `AbortSignal`;
- полностью мокированные автоматические тесты.

В первую версию не входят:

- передача или переопределение подключения в MCP-запросе;
- выбор области данных или значений разделителей;
- получение свойств одного расширения по имени;
- импорт, выгрузка, изменение или удаление расширения;
- кэширование полученного списка отдельно от живого сеанса;
- запуск реальной 1С в автоматических тестах.

## Рассмотренные подходы

### Типизированная операция сеанса

В `PlatformSession` добавляется `listExtensions()`. Каждый режим сам выполняет
свои команды и преобразует ответ в единый тип. Менеджер предоставляет
`listExtensions(...)` с тем же жизненным циклом сеанса, что и существующий
экспорт конфигурации.

Это выбранный подход: различия платформы остаются внутри адаптеров, а очередь,
переиспользование, отмена и таймер простоя не дублируются.

### Универсальный исполнитель команд платформы

Менеджер мог бы принимать произвольное описание команды и возвращать сырой
ответ. Это облегчило бы добавление некоторых будущих операций, но вынесло бы
различия SSH и `ibcmd` наружу, ослабило типизацию и увеличило риск утечки
служебного вывода.

### Ветвление в MCP-сервисе

MCP-сервис мог бы самостоятельно выбирать режим и запускать соответствующие
команды. Это короче только для первой операции, но дублирует поиск платформы,
подключение, очередь и очистку, поэтому нарушает существующую границу пакета
`@nkdk/platform`.

## Публичный договор

Инструмент:

```ts
nkdk.list_infobase_extensions({
  projectDir: string
})
```

Успешный результат:

```ts
type ListInfobaseExtensionsSuccess = {
  ok: true
  extensions: ConfigurationExtensionInfo[]
  mode: "designer-agent" | "standalone-server"
  reusedConnection: boolean
}
```

Отсутствие расширений является успешным результатом с `extensions: []`.
`allowWrite` не нужен, потому что операция не изменяет проект или базу.

Сведения об одном расширении:

```ts
type ConfigurationExtensionInfo = {
  name: string
  version: string
  active: boolean
  purpose: "customization" | "add-on" | "patch"
  safeMode: boolean
  securityProfileName: string
  unsafeActionProtection: boolean
  usedInDistributedInfobase: boolean
  scope: "infobase" | "data-separation"
  hashSum: string
}
```

Поля соответствуют фактическому полному ответу `ibcmd 8.3.27.2214 extension
list`. Пустые `version` и `securityProfileName` сохраняются как пустые строки.
Значения платформы `yes`/`no` преобразуются в `boolean`. Неизвестное значение
перечисления не передаётся наружу как строка, а считается нарушением договора
платформы.

Сырые ответы платформы, команды, пути служебного сеанса и учётные данные в
публичный результат не входят.

## Компоненты

### MCP-договор

В `packages/mcp/src/contracts` добавляются строгая входная схема с единственным
`projectDir` и схема результата. Схема `ConfigurationExtensionInfo` не допускает
неизвестных полей.

### MCP-сервис

Сервис:

1. читает `.nkdk/project.yaml` через `readProjectSettings`;
2. при отсутствии файла возвращает `invalid_project_settings`;
3. передаёт нормализованные настройки и `projectDir` в
   `PlatformSessionManager.listExtensions`;
4. преобразует `PlatformSessionError` в существующий безопасный MCP-договор;
5. возвращает список вместе с режимом и признаком переиспользования.

Сервис не знает команды платформы и форматы их ответов.

### Менеджер сеансов

В `PlatformSessionManager` добавляется типизированная операция
`listExtensions`. Общая часть выполнения экспортирования и чтения списка
выделяется во внутренний исполнитель операции над сеансом. Он отвечает за:

- канонизацию корня проекта;
- очередь операций проекта;
- нормализацию настроек и вычисление отпечатка;
- создание либо переиспользование сеанса;
- обработку отмены;
- повторный запуск таймера простоя.

Внутренний исполнитель не принимает произвольных строк команд. Публичные методы
менеджера остаются предметными и типизированными.

### Агент Конфигуратора

Адаптер выполняет:

```text
config extensions properties get --all-extensions
```

SSH-протокол уже включает JSON-формат ответов. В 8.3.27 команда возвращает
записи `extension-properties` внутри массива `body` завершающего сообщения
`success`. Тела этих записей строго разбираются и нормализуются; логические
значения агента и текстовые `yes`/`no` от `ibcmd` приводятся к единому виду.
Отсутствующий, не-массивный или содержащий неизвестные записи `success.body`
считается ошибкой команды, а сама команда ограничена тем же 30-минутным
временем, что вызов `ibcmd`.

Публичный `PlatformCommandSession` не превращается в универсальный интерфейс
сырых ответов: он предоставляет минимальный типизированный способ получить
содержательные сообщения, необходимый адаптеру платформы.

### Offline-режим `ibcmd`

Адаптер использует подготовленный приватный `config.yaml` и те же параметры
пользователя информационной базы, что и экспорт. Выполняется одна команда:

```text
ibcmd infobase config extension list
```

Команда получает `--config`, а также `--user` и `--password`, если они заданы.
В 8.3.27 её табличный текстовый вывод уже содержит полный набор свойств каждого
расширения, поэтому дополнительные вызовы `extension info` не нужны. Вывод
строго разбирается внутри адаптера с сохранением порядка записей.

## Поток операции

1. MCP проверяет форму запроса.
2. Сервис читает настройки проекта.
3. Менеджер канонизирует `projectDir` и ставит операцию в очередь проекта.
4. Менеджер переиспользует совместимый живой сеанс либо создаёт новый.
5. Адаптер выбранного режима получает и нормализует сведения о расширениях.
6. Менеджер заново запускает `sessionIdleTimeout`.
7. MCP возвращает атомарный типизированный список.

Список не сортируется в NKDK. Порядок платформы сохраняется, чтобы не скрывать
её фактическое представление и не вводить зависимость от локали.

## Отмена

`AbortSignal` передаётся каждой команде платформы.

Для агента отмена текущей команды останавливает принадлежащий NKDK процесс,
закрывает SSH и удаляет сеанс из кэша менеджера. Для `ibcmd` завершается текущий
дочерний процесс; приватная конфигурация сеанса удаляется, а сеанс исключается
из кэша. Ошибка отмены имеет приоритет над ошибками очистки.

Если сигнал уже отменён до начала операции, команда не запускается.

## Ошибки и атомарность

Операция возвращает либо полный проверенный список, либо ошибку. Частичный
список не возвращается, в том числе когда `ibcmd` успел получить свойства
нескольких расширений.

Используются существующие коды:

- `invalid_project_settings`;
- `platform_not_found`;
- `platform_component_missing`;
- `unsupported_connection`;
- `authentication_failed`;
- `session_start_failed`;
- `session_timeout`;
- `platform_command_failed`;
- `operation_cancelled`.

Неожиданная структура ответа, отсутствие обязательного свойства, неизвестное
значение перечисления и неразбираемый вывод считаются
`platform_command_failed`. MCP возвращает стабильное безопасное сообщение без
`stdout`, `stderr`, исходной команды и секретов.

После обычной ошибки менеджер может сохранить живой сеанс для повторного
использования. После отмены или `session_timeout` сеанс обязательно
останавливается и удаляется, чтобы поздний ответ команды не попал в следующую
операцию.

## Тестирование

Все тесты изолированы от установленной платформы и используют моки.

### Разбор и команды

- полный набор свойств для каждого режима;
- пустые допустимые строки;
- преобразование `yes`/`no`;
- пустой список;
- неизвестные поля, отсутствующие обязательные поля и неизвестные перечисления;
- повреждённый JSON агента и неразбираемый вывод `ibcmd`;
- точные аргументы `list`;
- отсутствие секретов в диагностике и ошибках.

### Адаптеры сеанса

- один ответ агента с несколькими `extension-properties` в `success.body`;
- один табличный ответ `ibcmd` с несколькими записями и сохранением порядка;
- ограничение времени;
- отмена до команды и во время команды;
- закрытие и повторный вызов закрытого сеанса.

### Менеджер

- создание и переиспользование каждого режима;
- общий отпечаток подключения с существующим экспортом;
- последовательность списка и экспорта одного проекта;
- независимость очередей разных проектов;
- смена режима или настроек;
- повторный запуск таймера простоя;
- удаление отменённого сеанса и сеанса с истёкшим временем операции.

### MCP

- чтение корректных настроек;
- отсутствие и некорректность `.nkdk/project.yaml`;
- полный и пустой успешный результат;
- безопасное преобразование каждой ошибки платформы;
- Zod-договор входа и выхода;
- регистрация `nkdk.list_infobase_extensions`;
- пакетный smoke-тест.

Итоговая проверка реализации выполняется командой `pnpm test` из корня
репозитория.

## Изменение архитектурного описания

При реализации в `.agents/architecture.md` добавляется операция «Получение
списка расширений информационной базы» с действиями чтения настроек, получения
сеанса, чтения и нормализации свойств и формирования результата. Общие действия
по получению сеанса переиспользуются; знания о конкретных командах остаются в
адаптерах `@nkdk/platform`.

## Критерии готовности

- один публичный MCP-договор работает с обоими режимами;
- вход содержит только `projectDir`;
- подключение берётся только из настроек проекта;
- свойства расширений одинаково типизированы для обоих режимов;
- пустой список успешен, частичный список невозможен;
- операция не пишет в проект и информационную базу;
- очередь, переиспользование, отмена и таймер согласованы с экспортом;
- автоматические тесты полностью мокированы;
- `pnpm test` завершается успешно.

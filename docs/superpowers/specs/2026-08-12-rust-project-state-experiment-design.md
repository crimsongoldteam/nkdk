# Эксперимент переноса ProjectState на Rust

## Цель

Проверить, может ли реализация двоичного `ProjectState` на Rust заметно снизить пиковый расход памяти и ускорить import, validation и export без одновременного переноса предметных правил и управления операциями.

Эксперимент считается успешным, если на согласованном большом проекте Rust:

- снижает пиковую RSS не менее чем на 25%;
- ускоряет целевой этап не менее чем на 20%;
- не замедляет обработку неизменившегося проекта более чем на 5%;
- сохраняет поведение существующих контрактов и совместимость `project-state.bin 0.5.0`.

Первый эксперимент собирается только для текущей macOS. Подготовка сборок для Linux и Windows не входит в этот этап.

## Рассмотренные варианты

### Только построитель снимка

Rust объединяет исходный снимок, изменения и удаления, но все запросы выполняются текущим TypeScript-кодом. Вариант прост, однако оставляет в V8 декодирование строк, поисковые структуры и объектные кэши. Он недостаточно полно проверяет ожидаемый выигрыш памяти.

### Двоичный движок ProjectState

Rust строит снимок и выполняет чистые пакетные запросы по нему. TypeScript сохраняет публичные интерфейсы, управление операциями и предметную проверку. Этот вариант выбран: он достаточно глубок для измеримого результата, но не требует переписывать import, validation и export целиком.

### Отдельная служба Rust

Единый процесс Rust владеет состоянием, а Node.js обращается к нему через IPC. Это добавляет асинхронный протокол, сериализацию, отдельный жизненный цикл и восстановление после сбоя. Для первого эксперимента вариант неоправданно сложен.

## Архитектурная граница

Rust подключается к Node.js через `napi-rs` и работает внутри того же процесса. Отдельная служба и сетевой обмен не используются.

Публичные `ProjectStateStore`, `ProjectStateQueryPort` и `ProjectStateService` не меняются. Выбор реализации выполняется в `metadata/composition`, где создаётся один из двух внутренних вариантов:

- `typescript` — существующая эталонная реализация;
- `rust` — экспериментальная реализация через `napi-rs`.

Автоматический резервный переход на TypeScript допустим только при загрузке дополнения, до открытия хранилища. После начала транзакции ошибка Rust приводит к отмене операции; продолжать ту же операцию на другой реализации нельзя.

В TypeScript остаются:

- порядок import, validation и export;
- транзакции `beginUpdate`, `commit` и `rollback`;
- `ProjectStateDependencyValidator` и предметные правила;
- чтение и запись `project-state.bin`;
- checkpoint, `AbortSignal` и управление worker;
- эталонная реализация для сравнительных проверок.

Rust отвечает за:

- проверку и чтение двоичных фрагментов и снимков;
- объединение исходного снимка, фрагментов и удалений;
- построение строковых таблиц, таблиц фактов и поисковых индексов;
- чистые пакетные запросы по неизменяемому снимку;
- проверку границ, размеров, версий и служебных значений двоичного формата.

## Представление снимка и время жизни

Формат `project-state.bin 0.5.0` и существующие шесть секций сохраняются:

1. `header`;
2. `strings`;
3. `files`;
4. `facts`;
5. `lookups`;
6. `diagnostics`.

`ProjectStateReadToken` продолжает содержать одноразовый `claim` и общие `SharedArrayBuffer`. Нативный указатель нельзя передавать между `worker_threads`, поэтому каждый worker открывает собственный лёгкий Rust-reader над теми же общими неизменяемыми буферами.

Rust-reader удерживает ссылки на буферы до явного `close`. Финализатор сборщика мусора служит только страховкой. После публикации нового снимка уже открытые сеансы продолжают видеть прежний снимок; старые буферы освобождаются после закрытия всех использующих их сеансов.

Rust не должен создавать полную вторую копию поисковых индексов. Допустимые внутренние кэши ограничиваются по размеру, явно закрываются и отражаются в результатах измерения памяти.

## Обновление состояния

TypeScript начинает транзакцию и передаёт Rust:

- опубликованный снимок, если он существует;
- существующие двоичные `ProjectStateFragment`;
- пути удаляемых файлов;
- команды очистки выбранных компонентов и удаления необнаруженных файлов.

Обновление выполняется в две стадии:

```ts
interface NativeSnapshotPlan {
  layout(): ProjectStateSectionSizes
  writeInto(output: ProjectStateSharedBuffers): NativeSnapshotStats
  close(): void
}

function planProjectStateSnapshot(input: NativeSnapshotInput): NativeSnapshotPlan
```

На первой стадии Rust проверяет входы, вычисляет новое состояние и точные размеры секций. TypeScript выделяет шесть `SharedArrayBuffer` нужного размера. На второй стадии Rust напрямую заполняет эти буферы. Промежуточный `ArrayBuffer` размером с полный снимок не создаётся.

План используется один раз. При ошибке заполнения снимок не публикуется. `commit` атомарно заменяет ссылки на опубликованный снимок, а `rollback` освобождает рабочее состояние.

Если безопасная прямая запись в `SharedArrayBuffer` через `napi-rs` окажется технически недоступной, допускается отдельный запасной замер с Rust-owned `Buffer` и одной явной копией. Такой результат фиксируется как вариант с копированием и не считается подтверждением целевого расхода памяти.

## Чтение состояния

Нативный reader открывается над шестью секциями снимка:

```ts
interface NativeProjectStateReader {
  execute(operation: ProjectStateQueryOperation, request: Uint8Array): Uint8Array
  close(): void
}

function openProjectStateReader(
  buffers: ProjectStateSharedBuffers,
): NativeProjectStateReader
```

Запросы передаются пачками в версионированном двоичном протоколе, а не массивами больших JavaScript-объектов. Протокол содержит код операции, число запросов, таблицу строк, строки фиксированного размера и раздел значений переменной длины. Он является внутренним договором `napi-rs` и не записывается в `project-state.bin`.

В первый полный набор входят:

- чтение исходных хэшей и сравнение файлов;
- поиск целей и владельцев;
- чтение полей, форм и входов для проверки зависимостей;
- поиск ссылок в хранилище;
- постраничное чтение владельцев и целей компонента;
- чтение состояния validation;
- чтение ссылок отдельного файла;
- чтение записей составных документов.

TypeScript-адаптер преобразует компактные ответы в существующий `ProjectStateQueryPort`. Составные действия, включая предметное разрешение DataPath и формирование диагностик, остаются в TypeScript.

## Ошибки

Rust до чтения проверяет:

- версию и сигнатуру формата;
- длины, смещения и выравнивание секций;
- переполнения при вычислении размеров;
- диапазоны идентификаторов и служебные значения;
- контрольную сумму сохраняемого снимка.

`panic` перехватывается на границе дополнения. Ошибки возвращаются в Node.js с устойчивым кодом и категорией; русское сообщение не является частью машинного договора.

Повреждённый сохранённый снимок обрабатывается по существующему договору: он отбрасывается и позднее перестраивается. Ошибка Rust во время активной транзакции отменяет эту транзакцию и не вызывает скрытого переключения на TypeScript.

## Совместимость

Rust должен читать снимки TypeScript, а TypeScript — снимки Rust. Обязательна одинаковая семантика запросов. Побайтово одинаковый снимок является предпочтительным результатом и упрощает проверку, но не заменяет проверку поведения.

Для побайтового совпадения требуется воспроизвести:

- little-endian layout секций и big-endian представление восьмибайтовых хэшей в публичном пакете;
- алгоритмы XXH3/XXH64 и параметры хэш-таблиц;
- служебное значение `0xffff_ffff`;
- сортировку файлов и диапазонов индексов;
- дедупликацию строк и детерминированный порядок записей.

До переноса построителя создаются эталонные наборы строк с кириллицей, символами вне BMP, комбинируемыми символами и суррогатными парами. Rust повторяет фактический порядок текущего TypeScript-кода, не полагаясь на локаль платформы.

## Последовательность эксперимента

1. Зафиксировать исходные показатели TypeScript на одном большом проекте.
2. Добавить локальное дополнение `napi-rs`, проверяющее и открывающее существующий снимок без копирования.
3. Реализовать чтение исходных хэшей и поиск целей; сравнить ответы с TypeScript.
4. Реализовать `planProjectStateSnapshot` и прямую запись нового снимка в заранее выделенные `SharedArrayBuffer`.
5. Провести основной замер построения снимка и пикового расхода памяти.
6. Довести чистые запросы хранилища до полного контракта `ProjectStateQueryPort`.
7. Провести полный сравнительный validation и принять решение о продолжении переноса.

Rust не включается по умолчанию до выполнения критериев успеха. Если критерии не достигнуты, эксперимент остаётся изолированным и не расширяется на предметную validation.

## Проверка корректности

Обе реализации проходят один набор контрактных тестов:

- существующий `runProjectStateStoreContract`;
- существующие проверки `binary/readSession`;
- TypeScript-снимок → Rust-reader;
- Rust-снимок → TypeScript-reader и сохранение;
- одинаковые последовательности `begin`, `append`, `delete`, `commit` и `rollback`;
- чтение старого token после публикации нового снимка;
- работа нескольких Piscina worker над общими буферами;
- закрытие reader и освобождение ссылок;
- повреждённые заголовки, размеры, диапазоны и версии;
- эталонные строки, хэши и порядок записей.

Дополнительно применяются сравнительные случайные последовательности операций и fuzz-проверка Rust-декодеров. Сравнительный режим запускается отдельным тестом, а не одновременно с рабочей validation, чтобы не удваивать память измеряемого процесса.

## Методика измерения

TypeScript и Rust запускаются в отдельных процессах с одинаковым проектом и числом worker. Для каждого сценария выполняются прогрев и не менее пяти измерений; сравниваются медиана и худший наблюдённый пик памяти.

Сценарии:

- загрузка существующего снимка;
- полное перестроение;
- неизменившийся проект;
- изменение 1% YAML-файлов;
- полный validation;
- характерный набор запросов export.

По фазам собираются:

- wall time и CPU time;
- максимальная RSS средствами операционной системы;
- `heapUsed`, `external` и `arrayBuffers` Node.js;
- размер каждого `SharedArrayBuffer`;
- выделенная и пиковая память Rust;
- объём внутренних кэшей reader.

Отдельно фиксируется пик построения, когда одновременно могут существовать опубликованный снимок, входные фрагменты, временные структуры Rust и новый снимок.

## Решение после эксперимента

Если все критерии успеха выполнены, Rust-реализация доводится до промышленных сборок для поддерживаемых платформ и рассматривается как основа для следующего контура. Следующим кандидатом может стать полный проход проверки зависимостей, если измерения покажут, что основная оставшаяся память расходуется на TypeScript-объекты `ProjectStateDependencyValidator`.

Если выигрыш меньше порогов, Rust не включается по умолчанию. Результаты измерений используются для выбора следующего узкого места без обязательства продолжать перенос.

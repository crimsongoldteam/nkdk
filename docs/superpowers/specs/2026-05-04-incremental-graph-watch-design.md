# Инкрементальное обновление графа через `nkdk watch`

Дата: 2026-05-04
Тип: дизайн-документ.

## Контекст

Сейчас граф формируется командой `nkdk update-graph` из
`packages/cli/src/commands/updateGraph.ts`. Команда читает все поддержанные YAML-файлы проекта,
передаёт их в `buildGraph`, а затем записывает результат через `@nakidka/graph.updateGraph`.

В пакете `@nakidka/graph` уже есть базовая семантика инкрементальной записи: `updateGraph(files)`
удаляет и заново записывает только сегменты графа, привязанные к переданным `filePath`. Но привязка
через свойство `filePath` плохо подходит для watcher: манифест синхронизации становится отдельной
структурой, а файл как источник графа не виден в самой модели графа.

Целевое решение — сделать файл полноценным узлом графа. Тогда информация о файле, его версии на
диске и объявленных им узлах хранится в одном месте.

## Цель

Добавить режим `nkdk watch`, который:

- при старте синхронизирует граф с проектом;
- следит за изменениями `Свойства.yaml`, `Форма.yaml` и `.nkdk`;
- на изменение пересобирает только затронутый графовый сегмент;
- на удаление очищает только сегмент удалённого файла.

Дополнительно добавить ручной путь `nkdk update-graph --file <path>`, который использует тот же
инкрементальный механизм без долгоживущего процесса.

## Не входит в задачу

- Новые правила `fromXML/toXML/fromYAML/toYAML`.
- Изменение существующих XML-фикстур.

## Основное решение

### Узлы файлов

Каждый поддержанный файл представлен служебным узлом:

```cypher
(:File {
  path: "Справочник/Контрагенты/Свойства.yaml",
  mtimeMs: 1777890000000,
  size: 1234,
  updatedAt: 1777890000500
})
```

Индекс: `:File(path)`.

Узлы, объявленные файлом, связываются с ним ребром:

```cypher
(:File)-[:DECLARES]->(:MetadataCatalog)
```

Для графовых узлов `props.filePath` больше не является целевой моделью владения. Источник узла
определяется входящим `DECLARES` от `File`.

### `FileGraphData`

`FileGraphData` остаётся входной единицей `@nakidka/graph.updateGraph`, но его смысл расширяется:

```ts
interface FileGraphData {
  filePath: string
  fileStats?: {
    mtimeMs: number
    size: number
    updatedAt: number
  }
  nodes: NodeData[]
  edges: EdgeData[]
}
```

`filePath` задаёт `File.path`. `fileStats` нужен watcher для сравнения состояния диска с состоянием
графа. Для ручного обновления без статистики графовый пакет может заполнить только `path` и
`updatedAt`.

При записи файла `@nakidka/graph.updateGraph`:

1. находит или создаёт `(:File {path: filePath})`;
2. обновляет свойства `File`;
3. удаляет прежние исходящие `DECLARES` этого файла и графовые узлы, которые больше никем не
   объявлены и не имеют входящих рёбер;
4. узлы со входящими рёбрами превращает в stub;
5. записывает новые узлы и рёбра;
6. создаёт `DECLARES` от `File` ко всем узлам сегмента, объявленным этим файлом.

Stub-узлы не получают `DECLARES`, пока не появится файл, который их объявляет.

### Инкрементальный API core

В core появляется API для построения графа по одному сохранённому файлу проекта. Условно:

```ts
buildGraphForChangedFile({
  projectPath,
  filePath,
  text,
  context,
}): FileGraphData[]
```

`filePath` в результате должен оставаться тем же относительным путём, который использует полный
`buildGraph`: например `Справочник/Контрагенты/Свойства.yaml` или
`Справочник/Контрагенты/Формы/ФормаЭлемента/Форма.yaml`.

Полный `buildGraph(yamlFiles, context)` остаётся для полной синхронизации, но его внутреннюю
логику определения kind и построения сегментов нужно разделить так, чтобы одиночный путь и полный
путь использовали один и тот же разбор.

## Поток данных

### `Свойства.yaml`

Для путей вида:

- `Справочник/<name>/Свойства.yaml`
- `Документ/<name>/Свойства.yaml`
- `Перечисление/<name>/Свойства.yaml`

core строит граф только этого файла. Соседние файлы проекта не читаются. Ссылки на другие объекты
остаются обычными stub-узлами, которые позже сольются с полными узлами при обновлении
соответствующих файлов.

### `Форма.yaml`

Для пути вида:

`<ownerKind>/<ownerName>/Формы/<formName>/Форма.yaml`

core строит сегмент формы и вычисляет `ownerNodeId` из пути. Если узел владельца уже есть в графе,
связь формы ляжет на него. Если владельца ещё нет, он останется stub-узлом до обновления
`Свойства.yaml` владельца.

### `.nkdk`

`.nkdk` не является самостоятельным сегментом графа. Он влияет на форму, поэтому изменение
`<...>/Форма.nkdk` должно нормализоваться в обновление соответствующего
`<...>/Форма.yaml`.

Инкрементальный API для формы должен уметь принять дополнительный источник `nkdk` и передать его в
существующий путь импорта формы. Если парный `Форма.yaml` отсутствует, watcher пишет понятное
предупреждение и не меняет граф.

### Удаление

На удаление файла CLI вызывает:

```ts
updateGraph([{ filePath, nodes: [], edges: [] }])
```

Так `@nakidka/graph` найдёт `(:File {path: filePath})`, удалит его `DECLARES`, зачистит узлы,
которые объявлялись только этим файлом, и удалит сам `File`-узел. Stub-узлы, на которые ещё есть
входящие рёбра, сохраняются.

Для удаления `.nkdk` пересобирается парный `Форма.yaml` без дополнительного `nkdk`-источника.

## Команда `nkdk watch`

`nkdk watch <projectPath>` запускает долгоживущий процесс:

1. Сканирует поддержанные файлы проекта.
2. Читает `(:File)`-узлы из графа.
3. Для новых и изменённых файлов выполняет инкрементальное обновление.
4. Для `File.path`, которые есть в графе, но исчезли с диска, очищает сегменты.
5. Создаёт файловый наблюдатель по поддержанным путям.
6. На события `add` и `change` кладёт нормализованный путь в очередь.
7. На событие `unlink` кладёт задачу очистки сегмента.
8. Схлопывает повторные события одного файла через короткую задержку.
9. Последовательно применяет задачи к FalkorDB.

Запись в FalkorDB выполняется строго последовательно. Это защищает от гонок, когда редактор или
операционная система присылает несколько событий на один файл подряд.

Сравнение изменений использует `File.path`, `File.mtimeMs` и `File.size`. Хеш содержимого не нужен
для первого варианта, потому что watcher оптимизирует обычный путь разработки, а не защищается от
всех возможных изменений файловой системы.

## Ручная команда

`nkdk update-graph --file <path>` делает один инкрементальный проход:

1. Нормализует путь относительно `projectPath`.
2. Если файл существует, читает его и строит только нужный сегмент.
3. Если файл удалён, передаёт пустой сегмент для очистки.
4. Вызывает `@nakidka/graph.updateGraph`.

Эта команда нужна для отладки, тестов и ручной проверки поведения watcher без запуска постоянного
процесса.

## Ошибки и крайние случаи

Если изменённый файл не относится к поддержанным путям, watcher игнорирует его.

Если YAML временно не разбирается, watcher не должен удалять старый рабочий сегмент. Он пишет
ошибку в консоль и ждёт следующего изменения файла.

Если файл удалён, очистка сегмента выполняется даже без возможности разобрать содержимое.

Если `.nkdk` изменился, но парный `Форма.yaml` не найден, граф не обновляется, потому что
невозможно определить полный сегмент формы.

Если в графе есть `File`, которого больше нет на диске, watcher очищает сегмент и удаляет `File`.

## Тестирование

Нужны точечные тесты:

- core строит `FileGraphData` для одного `Свойства.yaml`;
- core строит `FileGraphData` для одного `Форма.yaml` с `ownerNodeId` из пути;
- изменение `.nkdk` нормализуется в обновление парного `Форма.yaml`;
- удаление файла вызывает `updateGraph` с пустым сегментом;
- `@nakidka/graph.updateGraph` создаёт `File`-узел и `DECLARES`-рёбра;
- удаление сегмента через `File` сохраняет stub-узлы с входящими рёбрами;
- старт watcher сравнивает файлы на диске с `File`-узлами графа;
- очередь watcher схлопывает повторные события и применяет записи последовательно.

Перед закрытием задачи требуется `pnpm test` из корня проекта.

# Анализ порядка свойств из XML-конфигураций

## Цель

Собрать фактический XML-порядок свойств всех объектов, описанных через `MetadataItemRule` в `rules.ts`, по конфигурациям из `/Users/nikita/git/round-trip/cf` и найти случаи, где одно и то же правило задаёт противоположный относительный порядок одной пары свойств.

Первая итерация заканчивается отчётом. Она не добавляет `order` в `rules.ts`, не меняет формат снимка конфигурации и не изменяет XML-фикстуры.

## Границы

Анализируются все фактически выбранные при импорте правила из `rules.ts`, включая:

- корневые applied-объекты;
- общие вложенные metadata-объекты;
- реквизиты и другие дочерние объекты;
- формы и элементы форм;
- вложенные объекты, создаваемые через property type rules.

Не анализируется порядок элементов коллекций. Такой порядок сохраняется в YAML и не является кандидатом для переноса в `order` свойств.

Источниками служат все непосредственные подкаталоги `/Users/nikita/git/round-trip/cf`: `acc`, `all`, `clean`, `doc`, `erp`, `small`, `trade`. Список каталогов определяется во время запуска и сортируется побайтово; отчёт фиксирует фактически обработанный список.

## Выбранный подход

Диагностический сбор встраивается в существующий rule-guided обход XML. Отдельный XML-парсер или восстановление правила по готовому снимку не используются.

Точка наблюдения находится в общем импорте свойств, где уже известны:

- конкретный `MetadataItemRule`;
- соответствие XML-тега ключу свойства;
- `xmlParents`, `xmlAliases` и выбранный XML-источник;
- фактическая последовательность найденных свойств одного XML-узла.

Благодаря этому анализатор не повторяет правила импорта и не смешивает XML-теги с ключами `rules.ts`.

## Модель наблюдения

Каждое наблюдение описывает порядок свойств одного правила внутри одного XML-узла:

```ts
interface RuleOrderObservation {
  configuration: string
  sourceXmlPath: string
  logicalAddress: string
  xmlNodeLogicalAddress: string
  ruleId: string
  ruleCandidates: string[]
  itemType: string
  fields: string[]
}
```

`fields` содержит уникальные ключи свойств из `rules.ts` в порядке их появления в XML. Канонические XML-имена и alias-теги сводятся к одному ключу свойства существующим import plan.

Наблюдение создаётся только общим обходом свойств `MetadataItemRule`. Частные вызовы `ConfigurationIndexCollector.setOrder`, сохраняющие порядок элементов коллекций, интерфейсов, служебных XML-секций или имён дочерних объектов, не подключаются к диагностическому сбору.

## Идентификация правила

`itemType` недостаточен: несколько разных правил могут иметь одинаковый `itemType`. Анализатор строит устойчивый отпечаток полного правила без поля `order`.

В отпечаток входят:

- `itemType`;
- набор и структура свойств;
- типы свойств;
- XML-имена, `xmlParents`, `xmlAliases` и теги;
- значимые декларативные параметры;
- структура достижимых вложенных правил;
- непрозрачный маркер функций, устойчивый между главным процессом и `tsx` worker-ами.

Поля `order` исключаются на всех уровнях, поскольку именно они являются будущим результатом анализа.

Перед обработкой XML анализатор строит каталог правил. Он загружает `rules.ts`, находит экспортированные `MetadataItemRule` и рекурсивно проходит вложенные правила через зарегистрированные property type descriptors. Кандидат получает имя вида:

```text
packages/core/metadata/commonObjects/metadataAttribute/rules.ts#MetadataAttributeRules
```

Для динамического вложенного правила к имени добавляется путь свойства родительского правила.

Отпечаток является `ruleId`; каталог связывает его с исходными кандидатами. Если отпечаток различается
между средами исполнения, каталог использует `itemType` как запасной ключ и возвращает все соответствующие
экспорты `rules.ts`. Если найдено несколько исходных правил, все кандидаты попадают в `ruleCandidates`.
Такое совпадение считается неоднозначностью отчёта: наблюдения можно сравнить по одинаковой структуре,
но автоматически выбрать место будущего изменения нельзя.

Наблюдение, которое не сопоставляется с правилом из `rules.ts`, не входит в анализ: это ожидаемо для production-правил из файлов вроде `predefinedRules.ts` и `types.ts`. Число таких наблюдений и их `itemType` выводятся отдельной статистикой. Неоднозначные кандидаты не скрываются и выводятся отдельным разделом.

## Сбор данных

Временная команда имеет интерфейс:

```bash
pnpm --filter @nkdk/core analyze-rule-order \
  --xml-root /Users/nikita/git/round-trip/cf \
  --output /private/tmp/nkdk-rule-order-report
```

Команда выполняет следующие действия:

1. Проверяет корень XML и перечисляет конфигурации.
2. Строит каталог и отпечатки правил.
3. Для каждой конфигурации запускает существующие discovery и XML-import worker.
4. Worker выполняют rule-guided разбор, но операция останавливается до второго прохода импорта, записи YAML, копирования внешних файлов, вычисления хэшей проекта и записи снимка.
5. Наблюдения передаются главному процессу вместе с частичным результатом задания.
6. Главный процесс пишет исходные наблюдения и обновляет агрегаты конфликтов.

Конфигурации обрабатываются последовательно, а задания одной конфигурации — с ограниченной параллельностью. Это не позволяет нескольким крупным конфигурациям одновременно удерживать результаты в памяти.

Исходные XML и рабочий проект остаются неизменными. Каталог результата должен отсутствовать либо быть пустым.

## Определение нарушения

Из каждого наблюдения строятся попарные ограничения. Последовательность:

```text
name, synonym, use, indexing
```

даёт ограничения:

```text
name → synonym
name → use
name → indexing
synonym → use
synonym → indexing
use → indexing
```

Ограничения объединяются отдельно для каждого `ruleId`. Нарушение существует, если для одной пары свойств найдены оба направления:

```text
use → indexing
indexing → use
```

Отсутствие свойства в конкретном XML не создаёт ограничения и не считается нарушением. Одинаковые повторные наблюдения увеличивают счётчик и сохраняют ограниченное число примеров, но не раздувают агрегат.

Анализатор дополнительно строит ориентированный граф всех ограничений правила. Противоположная пара всегда является конфликтом. Цикл из трёх и более свойств также выводится отдельно, даже если ни одна непосредственная пара не встречалась в обоих направлениях.

Граф нужен для последующего построения канонического `order`, но первая итерация не выполняет топологическую сортировку и не изменяет правила.

## Результаты

Анализатор создаёт:

- `observations.jsonl` — все исходные наблюдения;
- `conflicts.json` — полный машинно-читаемый отчёт;
- `report.md` — краткий отчёт для разбора человеком.

`conflicts.json` содержит:

- обработанные конфигурации и статистику файлов;
- число правил, наблюдений и уникальных последовательностей;
- число пропущенных наблюдений правил вне `rules.ts` и их `itemType`;
- противоположные пары по каждому правилу;
- циклы ограничений;
- неоднозначные исходные кандидаты;
- конфигурации, XML-пути, логические адреса и полные последовательности для свидетельств обоих направлений.

`report.md` сначала показывает итоговые числа, затем конфликты по правилам. Для каждой пары приводятся счётчики направлений и несколько коротких свидетельств. Количество сохраняемых свидетельств задаётся константой анализатора, чтобы крупная конфигурация не делала отчёт неограниченным.

Успешный пустой результат явно сообщает, что конфликтов не найдено. Отсутствие отчёта не трактуется как отсутствие конфликтов.

## Обработка ошибок

Запуск считается неуспешным, если:

- XML-корень или ожидаемые конфигурации невозможно прочитать;
- discovery или разбор хотя бы одного задания завершился ошибкой;
- внутри наблюдения повторяется ключ свойства;
- правило из каталога `rules.ts` не получило устойчивый `ruleId`;
- каталог результата уже содержит файлы;
- запись любого итогового файла не завершилась.

При ошибке процесс возвращает ненулевой код. Частичные данные могут сохраняться в каталоге с явным статусом `incomplete`, но `report.md` с видом успешного итогового отчёта не создаётся.

Неоднозначность нескольких исходных кандидатов одного отпечатка не останавливает сбор фактов, но делает соответствующее правило непригодным для автоматического изменения на следующем этапе.

## Проверка

Модульные тесты покрывают:

- построение всех попарных ограничений;
- обнаружение противоположного порядка;
- отсутствие конфликта при пропущенных свойствах;
- подсчёт повторных наблюдений;
- обнаружение длинного цикла;
- ограничение числа свидетельств;
- стабильность сериализации результатов.

Тесты сбора покрывают:

- преобразование XML alias в ключ свойства;
- раздельные XML-узлы из `xmlParents`;
- вложенное правило;
- два разных правила с одинаковым `itemType`;
- исключение порядка элементов коллекций;
- пропуск правила, не происходящего из `rules.ts`;
- отказ при нестабильном `ruleId` правила из каталога.

Интеграционный тест обрабатывает два небольших XML-объекта одного правила с противоположным порядком и проверяет оба свидетельства в `conflicts.json`.

Полный запуск на `/Users/nikita/git/round-trip/cf` не становится обычным тестом репозитория: путь внешний, а объём конфигураций велик. Он выполняется вручную в отдельном worktree после прохождения `pnpm test`.

## Критерии завершения первой итерации

- Все найденные конфигурации обработаны без ошибок.
- Порядок элементов коллекций отсутствует в наблюдениях.
- Каждое включённое наблюдение связано с устойчивым `ruleId`; правила вне `rules.ts` явно учтены как пропущенные.
- Для каждого конфликта доступны свидетельства обоих направлений.
- Созданы `observations.jsonl`, `conflicts.json` и `report.md`.
- `rules.ts`, XML-фикстуры и формат снимка конфигурации не изменены.
- В worktree проходит `pnpm test`.

После разбора отчёта отдельно проектируется следующий этап: выбор канонического порядка, добавление `order` и доказательство, какие записи порядка можно удалить из снимка конфигурации.

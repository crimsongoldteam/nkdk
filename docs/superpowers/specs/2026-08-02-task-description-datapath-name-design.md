# Task Description DataPath Name Design

## Контекст

В полном XML → YAML → XML round-trip формы
`Tasks/ЗадачаИсполнителя/Forms/ПодробнаяФормаЗадачи/Ext/Form.xml` путь

```xml
<DataPath>Объект.Описание</DataPath>
```

ошибочно превращается в:

```xml
<DataPath>Объект.Description</DataPath>
```

Первоначально расхождение выглядело как конфликт между стандартным `Description` и пользовательским
реквизитом `Описание`. Проверка в конфигураторе показала, что стандартный реквизит задачи называется
`Наименование`, поэтому конфликта в корректной YAML-модели нет.

## Первопричина

Для задачи в двух регистрациях задано неверное соответствие `Description → Описание`:

- `MetadataTaskStandardAttributeNames` в `metadataTask/rules.ts` используется для представления
  описаний стандартных реквизитов;
- декларация стандартного члена в `metadataTask/standardMembers.ts` используется для преобразования
  и проверки `DataPath`.

Ошибка появилась в `MetadataTaskStandardAttributeNames` при добавлении задачи, а затем была
перенесена в декларацию DataPath. Старое решение также попало в таблицу стандартных реквизитов.

Независимые признаки корректного имени:

- конфигуратор показывает стандартный реквизит задачи как `Наименование`;
- свойство задачи `DescriptionLength` уже представлено в YAML как `ДлинаНаименования`;
- общий словарь стандартных реквизитов задаёт `Description → Наименование`;
- все остальные объектные декларации `Description` используют `Наименование`.

Проверка всех общих соответствий между общим словарём, объектными rules и декларациями
`standardMembers` не выявила других отклонений. Единственное расхождение — задача.

## Договор

Для задачи действуют два разных имени без специальных маркеров:

| Реквизит | XML DataPath | YAML DataPath |
|---|---|---|
| стандартный `Description` | `Объект.Description` | `Объект.Наименование` |
| пользовательский `Описание` | `Объект.Описание` | `Объект.Описание` |

Тот же договор применяется к корню динамического списка и другим путям, тип которых разрешается до
задачи.

## Статистика конфигураций

В пяти вариантах `ЗадачаИсполнителя` из `/Users/nikita/git/round-trip-compact/cf` найдены оба
реквизита:

- 30 путей к стандартному `Description`;
- 10 путей к пользовательскому `Описание`.

Следовательно, сохранять оба пути как `Описание` нельзя: это объединяет разные реквизиты. После
исправления имени стандартные пути становятся `Наименование`, а пользовательские остаются
`Описание`.

## Решение

Заменить `Описание` на `Наименование` в двух регистрациях задачи:

```ts
Description: "Наименование"
```

и:

```ts
names: { internal: "Description", yaml: "Наименование" }
```

Также исправить строку задачи и общее правило `Description` в таблице стандартных реквизитов.

Специальная обработка совпадений, сохранение внутреннего имени в YAML, reference и configuration
index не нужны.

## Архитектурные границы

- Исправление принадлежит декларациям задачи; общий резолвер `DataPath` менять не нужно.
- Пользовательский реквизит `Описание` не переименовывать и не считать стандартным.
- Не вводить исключения в общий договор YAML-имён стандартных реквизитов.
- Расхождение не добавляется в `.agents/restrictions.md`, потому что точный round-trip достижим
  существующим механизмом.

## Проверки

- Добавить проверку `MetadataTaskStandardAttributeNames.Description === "Наименование"` в
  существующий табличный тест договора стандартных реквизитов.
- Проверить преобразование `Объект.Description ↔ Объект.Наименование` для задачи.
- Проверить, что `Объект.Описание` остаётся пользовательским реквизитом без преобразования.
- Проверить пути через основной реквизит формы и динамический список задачи.
- Запустить целевые тесты DataPath, затем `pnpm type-check`, `pnpm test`, `pnpm duplicates`.
- Stryker не запускать.
- Итоговый round-trip `cf/doc` не должен содержать изменение `Объект.Описание` в
  `Объект.Description`.

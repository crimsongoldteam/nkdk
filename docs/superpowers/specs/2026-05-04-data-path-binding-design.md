# DataPathBinding для dataPath-свойств

## Контекст

Сейчас `dataPath`-подобные поля представлены неоднородно. Для элементов формы
`DataPath` создаёт reference-рёбра вроде `DATA_PATH`, `FOOTER_DATA_PATH`,
`TITLE_DATA_PATH`, `ROW_PICTURE_DATA_PATH`. Для `ChoiceParameterLinks` поле
`dataPath` хранится как свойство узла `ChoiceParameterLink` и дополнительно
может создавать `DATA_PATH`-ребро.

Нужно привести это к общей модели, которая:

- работает для всех `dataPath`-подобных свойств;
- не хранит исходный путь как property владельца;
- поддерживает глобальные и form-local пути;
- позволяет восстановить модель из графа;
- позволяет `nkdk watch` понять, какие пути надо перечитать при изменении
  промежуточных объектов;
- показывает неподтверждённые пути через существующий механизм stub-узлов.

## Целевая модель графа

Для каждого `dataPath`-подобного свойства создаётся узел `DataPathBinding`.

```text
(owner)
  -[:HAS_DATA_PATH_BINDING { property, yaml }]->
(:DataPathBinding { sourcePath, kind })
```

`owner` — исходный узел, которому принадлежит свойство. Это может быть
`InputField`, `Table`, `ChoiceParameterLink` или другой узел с dataPath-полем.

Свойства ребра `HAS_DATA_PATH_BINDING`:

- `property` — имя свойства в JS-модели, например `dataPath`,
  `footerDataPath`, `titleDataPath`, `rowPictureDataPath`;
- `yaml` — YAML-имя свойства, например `ПутьКДанным`,
  `ПутьКДаннымПодвала`, `ПутьКДаннымЗаголовка`.

Свойства узла `DataPathBinding`:

- `sourcePath` — исходная строка пути, например
  `Объект.Владелец.Наименование`;
- `kind` — режим разбора: `global` или `formLocal`.

На `DataPathBinding` не вводятся `resolved`, `errorCode`, `errorMessage` и
похожие поля. Ошибки определяются через связи на stub-узлы.

## Смысл связей

У `DataPathBinding` есть два вида исходящих связей:

```text
(:DataPathBinding)-[:RESOLVES_TO]->(target)
(:DataPathBinding)-[:DEPENDS_ON]->(node)
```

`RESOLVES_TO` показывает конечные цели пути. Если путь неоднозначен из-за
нескольких возможных типов, таких рёбер может быть несколько.

`DEPENDS_ON` показывает узлы, которые повлияли на разбор пути. Это техническая
память для инкрементального пересчёта: если один из этих узлов изменился,
binding надо перечитать.

Пример для пути:

```text
Объект.Владелец.Наименование
```

Если `Владелец` имеет типы `Справочник.Договоры` и
`Справочник.Контрагенты`, граф содержит:

```text
binding -[:RESOLVES_TO]-> Договоры.Наименование
binding -[:RESOLVES_TO]-> Контрагенты.Наименование

binding -[:DEPENDS_ON]-> FormAttribute Объект
binding -[:DEPENDS_ON]-> Документ.ЗаказКлиента
binding -[:DEPENDS_ON]-> Attribute Владелец
binding -[:DEPENDS_ON]-> Справочник.Договоры
binding -[:DEPENDS_ON]-> Справочник.Контрагенты
```

## Алгоритм разбора form-local пути

Разбор идёт слева направо. На каждом шаге поддерживается множество текущих
возможных типов.

1. Найти корневой сегмент среди реквизитов формы.
2. Добавить `DEPENDS_ON` на найденный корневой реквизит формы.
3. Получить тип или типы корневого реквизита.
4. Для следующего сегмента найти реквизит с таким именем во всех текущих
   типах.
5. Добавить `DEPENDS_ON` на найденные реквизиты и типы, которые участвовали в
   поиске.
6. Если сегмент не последний, заменить множество текущих типов на типы
   найденных реквизитов.
7. Если сегмент последний, создать `RESOLVES_TO` ко всем найденным конечным
   реквизитам.

Если сегмент не найден в одном или нескольких текущих типах, создаётся
stub-цель внутри каждого такого типа:

```text
binding -[:RESOLVES_TO]-> Справочник.Договоры.НеизвестноеПоле
binding -[:RESOLVES_TO]-> Справочник.Контрагенты.НеизвестноеПоле
```

При этом binding зависит от контейнеров, где этот сегмент мог бы появиться:

```text
binding -[:DEPENDS_ON]-> Справочник.Договоры
binding -[:DEPENDS_ON]-> Справочник.Контрагенты
```

Если позже в одном из этих справочников появится нужный реквизит, изменение
контейнера приведёт к перечтению binding.

## Алгоритм разбора глобального пути

Глобальный путь разбирается как путь к объекту метаданных, например:

```text
Catalog.Товары.Attribute.Владелец
```

Для него также создаётся `DataPathBinding`, но `kind = "global"`.

Если путь разрешён, создаётся:

```text
binding -[:RESOLVES_TO]-> Справочник.Товары.Реквизит.Владелец
```

`DEPENDS_ON` ставится на узлы, которые участвовали в разрешении пути: объект
метаданных и конечный реквизит. Если конечный узел отсутствует, используется
обычный stub-узел.

## Пересчёт в nkdk watch

После обновления графового сегмента изменённого файла watcher получает
изменённые узлы и ищет зависимые binding:

```cypher
MATCH (changed:GraphNode)<-[:DEPENDS_ON]-(b:DataPathBinding)
WHERE changed.id IN $changedNodeIds
RETURN DISTINCT b
```

Для каждого найденного binding:

1. найти владельца через `HAS_DATA_PATH_BINDING`;
2. прочитать `sourcePath` с binding;
3. прочитать `property` и `yaml` с ребра владения;
4. удалить старые `RESOLVES_TO` и `DEPENDS_ON`;
5. заново разобрать путь относительно владельца;
6. создать новые `RESOLVES_TO` и `DEPENDS_ON`.

Для live-редактирования используется схлопывание событий с правилом
«последняя версия побеждает»: если файл меняется много раз подряд, watcher
ждёт короткую паузу и пересчитывает только последнюю версию.

## Восстановление модели из графа

При восстановлении модели `DataPathBinding` читается как свойство владельца.

```text
(:InputField)
  -[:HAS_DATA_PATH_BINDING { property: "dataPath" }]->
(:DataPathBinding { sourcePath: "Объект.Владелец.Наименование" })
```

Даёт:

```ts
inputField.dataPath = "Объект.Владелец.Наименование"
```

`RESOLVES_TO` и `DEPENDS_ON` при восстановлении модели не участвуют. Они нужны
для анализа, диагностики и инкрементального пересчёта.

## Диагностика неподтверждённых путей

Отдельных полей ошибки на binding нет. Неподтверждённый путь определяется
через `RESOLVES_TO` в stub-узел:

```cypher
MATCH (b:DataPathBinding)-[:RESOLVES_TO]->(target)
WHERE target.filePath IS NULL
RETURN b, target
```

Это совместимо с текущей моделью графа: stub-узел означает, что ссылка уже
есть, но полного определения узла пока нет.

## Границы первого этапа

В первый этап входит:

- общий `DataPathBinding` для всех dataPath-подобных свойств;
- перенос имени свойства на ребро `HAS_DATA_PATH_BINDING`;
- единое `RESOLVES_TO` вместо разных предметных `DATA_PATH`-рёбер;
- `DEPENDS_ON` для инкрементального пересчёта;
- диагностика через stub-узлы.

В первый этап не входит:

- отдельный trace-узел на каждый сегмент пути;
- хранение `resolved` или `error*` на binding;
- отдельный пользовательский интерфейс для объяснения разбора пути.

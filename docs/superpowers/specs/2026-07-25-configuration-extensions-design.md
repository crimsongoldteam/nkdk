# Импорт расширения конфигурации из XML

## Контекст

NKDK-проект уже разделяет компоненты по каталогам:

```text
cf/
cfe/<ИмяРасширения>/
erf/<ИмяОтчёта>/
epf/<ИмяОбработки>/
```

MCP умеет адресовать `cfe/<ИмяРасширения>` как отдельный компонент, однако core пока обрабатывает его как независимую конфигурацию. У расширения нет архитектурно выраженной зависимости от `cf`, отдельного снимка, разрешения идентификаторов базовой конфигурации и совместной валидации.

XML расширения содержит два вида объектов:

- собственные объекты расширения;
- заимствованные объекты базовой конфигурации.

Заимствованный XML-объект имеет собственный UUID расширения и ссылается на UUID базового объекта через:

```xml
<ObjectBelonging>Adopted</ObjectBelonging>
<ExtendedConfigurationObject>...</ExtendedConfigurationObject>
```

Заимствование рекурсивно относится к реквизитам, табличным частям, их реквизитам, формам, макетам, командам и другим дочерним объектам. Управляемые формы дополнительно хранят полную базовую форму в `BaseForm`.

## Цели

- Импортировать расширение только при наличии базового компонента `cf`.
- Хранить расширение в `cfe/<Name из Configuration.xml>`.
- Представлять в YAML состав заимствования без служебных XML-идентификаторов.
- Поддерживать собственные и заимствованные объекты на любом зарегистрированном уровне metadata-дерева.
- Сохранять отдельный снимок `cf` и каждого расширения.

## Границы текущего этапа

Спецификация описывает только импорт расширения из XML. В текущий этап не входят:

- полная и частичная синхронизация расширения в XML;
- валидация расширения;
- исследование допустимых наборов свойств заимствованных объектов разных видов;
- генерация YAML-схем расширения;
- переименование объектов и дочерних элементов;
- поддержка состояний свойств, появившихся начиная с режима совместимости `8.3.28`, включая `Auto`.

Импорт поддерживает формат примеров с режимом совместимости не выше `8.3.27`: состояние `Notify` переносится в YAML, состояние `Extended` сохраняется в снимке конфигурации расширения.

Неизвестные значимые XML-свойства и неподдерживаемые состояния `xr:PropertyState` пропускаются без ошибки и не переносятся в YAML или снимок конфигурации расширения.

## Основные решения

### Обязательная база

`cfe/<Имя>` всегда является зависимым компонентом. Самостоятельный импорт расширения без `cf` не поддерживается.

Расширение видит:

1. собственные объекты;
2. заимствованные объекты и элементы;
3. остальные доступные объекты `cf`.

Расширение не видит и не индексирует другие каталоги `cfe`.

### Нейтральная модель компонентов

Общие слои metadata не получают частных условий по имени каталога `cfe`, XML-полям `ObjectBelonging`, `ExtendedConfigurationObject` или узлу `BaseForm`.

Операция получает нейтральный контекст компонента:

- корень NKDK-проекта;
- выбранный компонент;
- вид компонента: базовый или зависимый;
- базовый компонент зависимого компонента;
- целевой путь снимка выбранного компонента;
- порядок разрешения ссылок.

При импорте снимок `cf` не читается. Общий индекс конфигурации строится непосредственно из YAML базового компонента.

Для разрешения ссылок поиск выполняется сначала в выбранном `cfe`, затем в `cf`. Поисковый слой найденного элемента известен только механизму разрешения ссылок и не используется для определения принадлежности.

Особенности XML расширения регистрируются рядом с правилами конкретных объектов и дочерних типов.

## YAML-представление

### Определение принадлежности

Отдельное поле принадлежности в YAML не вводится.

- Если логический путь объекта или дочернего элемента существует в `cf`, его наличие в `cfe` означает заимствование.
- Если логического пути нет в `cf`, элемент является собственным элементом расширения.
- Собственный элемент расширения не может иметь логический путь, совпадающий с элементом `cf`.

Имя верхнеуровневого объекта определяется каталогом проекта. Имя дочернего объекта определяется ключом коллекции.

### Заимствованные элементы

YAML заимствованного объекта хранит:

- факт заимствования самого объекта через наличие его YAML-файла;
- состав заимствованных дочерних объектов через наличие ключей или файлов;
- обязательное представление каждого заимствованного элемента;
- собственные дочерние элементы расширения в полном виде.

Для каждого вида объекта `rules.ts` декларативно определяет обязательные свойства заимствованного представления. Например:

- `Attribute` требует `Type`;
- `Command` требует `Group`;
- `Form` требует `FormType`;
- `Template` требует `TemplateType`.

Эти свойства импортируются в YAML и не восстанавливаются неявно из `cf`.

Заимствованный объект может поддерживать не все свойства собственного объекта того же вида. Импорт не определяет этот допустимый набор и не отклоняет свойства: он переносит все распознанные свойства, фактически присутствующие в XML. Ограничения конкретных видов заимствованных объектов требуют отдельного исследования и в дальнейшем проверяются валидацией с учётом принадлежности элемента.

Служебные значения не попадают в YAML:

- `ObjectBelonging`;
- `ExtendedConfigurationObject`;
- UUID расширения;
- UUID базового элемента;
- служебная часть `InternalInfo`, кроме состояния `Notify`, представленного разделом `Контроль`.

### Контроль свойств

Раздел `Контроль` — компактный массив YAML-имён свойств, для которых в XML задано:

```xml
<xr:PropertyState>
  <xr:Property>...</xr:Property>
  <xr:State>Notify</xr:State>
</xr:PropertyState>
```

Например:

```yaml
Контроль:
  - ОсновнойРежимЗапуска
```

В `Контроль` не хранятся само значение свойства, `ExtendedConfigurationObject` или состояние `Extended`.

`Контроль` обрабатывается для каждого metadata-item при рекурсивном импорте, а не только для верхнеуровневого объекта. Поэтому собственный раздел `Контроль` может появиться у реквизита, табличной части, формы, команды и любого другого вложенного элемента, если соответствующий `InternalInfo` находится в XML этого элемента.

Обычное контролируемое свойство хранится своим обычным YAML-полем. Его отсутствие означает, что свойство не входит в XML расширения; явное пустое значение означает, что в XML требуется пустой узел.

`State=Extended` относится к отдельно хранимым расширяемым данным: формам, модулям, правам, командным интерфейсам, картинкам и другим зарегистрированным видам. Оно не попадает в YAML. При импорте его наличие сохраняется как служебная информация в снимке конфигурации расширения.

Пример заимствованной части справочника:

```yaml
Реквизиты:
  СтроковыйРеквизитСИндексом:
    Тип: Строка(10)
  РеквизитСправочника:
    Тип: Дата

ТабличныеЧасти:
  ТабличнаяЧасть:
    Реквизиты:
      РеквизитТабличнойЧасти:
        Тип: Строка(10)
      ЗацикленныйРеквизит:
        Тип: СправочникСсылка.СправочникПолный

Команды:
  ПолнаяКоманда:
    Группа: ВажноеВПанелиНавигации
```

### Собственные элементы

Собственный объект или дочерний элемент расширения хранится по обычной полной YAML-схеме соответствующего `rules.ts`.

В одном заимствованном объекте могут одновременно находиться заимствованные и собственные реквизиты, табличные части, команды, формы и другие дочерние элементы.

### Корневая конфигурация расширения

Корневой `Configuration.xml` расширения импортируется по отдельным `MetadataConfigurationExtensionRules`, а не по правилам основной конфигурации. Эти правила:

- содержат общие свойства, допустимые и для основной конфигурации, и для расширения;
- добавляют свойства, существующие только у расширения;
- не включают свойства основной конфигурации, отсутствующие у расширения;
- задают собственные значения по умолчанию расширения;
- используют тот же рекурсивный механизм `Контроль`, что и остальные metadata-item.

Точный состав правил определяется поддерживаемыми XML-примерами `cfe/default`, `cfe/all-extension` и `cfe/control`. Неизвестное корневое свойство пропускается по общей политике импорта.

### Формы

YAML формы расширения всегда хранит полную итоговую форму. Частичный формат формы и отдельный язык операций добавления, перемещения или удаления элементов не вводятся.

Для заимствованной формы:

- `Форма.yaml` содержит полное итоговое содержимое формы расширения;
- `BaseForm` в YAML не хранится;
- при импорте вложенный `BaseForm` игнорируется;
- UUID формы и идентификаторы её элементов сохраняются по обычным правилам снимка конфигурации расширения.

## Импорт расширения из XML

Импорт расширения дополняет существующую операцию импорта из XML нейтральным контекстом зависимого компонента. Общий координатор и worker не проверяют имена каталогов `cfe` и конкретные XML-поля расширения. Распознавание расширения и игнорирование служебных XML-полей задаются регистрациями и `rules.ts`.

### Определение компонента и предварительные проверки

До формирования заданий импорта координатор:

1. читает корневой `Configuration.xml`;
2. определяет по зарегистрированному правилу, что выгрузка является расширением;
3. получает имя расширения и вычисляет целевой компонент `cfe/<Имя>`;
4. проверяет наличие компонента `cf`;
5. проверяет, что целевой каталог расширения отсутствует либо пуст;
6. проверяет, что снимок конфигурации расширения с тем же именем ещё не существует.

Имя каталога расширения не передаётся пользователем отдельно и не выводится из имени исходного XML-каталога. Конфликт имени с существующим каталогом или снимком является ошибкой; существующие данные автоматически не очищаются.

### Общий индекс конфигурации

До разбора XML расширения координатор строит общий индекс только базового компонента `cf`:

1. обнаруживает и классифицирует YAML-файлы `cf`;
2. распределяет их между worker;
3. собирает частичные metadata-индексы тем же механизмом, что используется при валидации;
4. объединяет частичные вклады в общий индекс конфигурации;
5. создаёт его неизменяемое представление в общей памяти.

Полная валидация `cf` при этом не запускается. Ошибка чтения, разбора или построения необходимого факта остаётся ошибкой операции.

Первоначально индекс строится холодным проходом. В дальнейшем тот же договор допускает получение индекса из кэша, если хэши файлов `cf` подтверждают его актуальность.

### Обработка XML

Дальнейший поиск файлов, классификация, формирование заданий и распределение между worker используют существующий конвейер импорта.

Во время единственного обхода XML worker дополнительно формирует нейтральные факты зависимого компонента:

- собственный UUID элемента расширения;
- вид и логический адрес элемента;
- сведения об исходных XML-узлах и значениях для снимка конфигурации расширения.

`ObjectBelonging`, `ExtendedConfigurationObject` и `BaseForm` считаются служебными входными данными: они не попадают ни в YAML, ни в снимок конфигурации расширения.

Для записей `xr:PropertyState` действуют отдельные правила:

- `Notify` преобразуется в имя свойства в массиве `Контроль`;
- `Extended` в YAML не попадает и сохраняется в снимке конфигурации расширения как служебное состояние отдельно хранимого свойства;
- остальные состояния пропускаются;
- правила конкретного объекта задают соответствие XML-имени свойства его YAML-имени.

Импорт не определяет, является элемент собственным или заимствованным. Он преобразует фактически присутствующие XML-свойства и дочерние элементы по обычным `rules.ts`. Поэтому сокращённый XML заимствованного элемента даёт компактный YAML, а полный XML собственного элемента — полное YAML-представление.

Различия в допустимом составе свойств собственного и заимствованного элемента не являются ошибкой импорта. Для последующей валидации принадлежность определяется по совпадению логического пути с `cf`, после чего применяется набор ограничений соответствующего вида metadata-item.

### Разрешение ссылок

Общий индекс `cf` при импорте используется только для разрешения ссылок на объекты основной конфигурации. Принадлежность элементов во время импорта не проверяется.

Индекс разрешения ссылок расширения строится слоями:

1. worker объединяют частичные вклады в локальный индекс только выбранного `cfe`;
2. координатор создаёт составное поисковое представление над локальным индексом `cfe` и общим индексом конфигурации.

Поиск выполняется сначала в локальном индексе расширения, затем в общем индексе конфигурации. Индексы физически не объединяются и не копируются. Элемент первого слоя перекрывает одноимённый базовый элемент только в контексте выбранного расширения; индекс `cf` не изменяется.

### Импорт форм

Внешняя часть XML формы импортируется как полная итоговая `Форма.yaml`.

Вложенный `BaseForm` игнорируется и не записывается ни в YAML, ни в снимок конфигурации расширения.

### Запись результата

Результат записывается так же, как при импорте основной конфигурации:

1. после построения необходимых индексов worker уточняет отложенные значения одного YAML-результата;
2. сразу сериализует YAML, вычисляет хэш по записываемым байтам и записывает файл непосредственно в `cfe/<Имя>`;
3. внешние файлы копируются непосредственно в целевой компонент с одновременным вычислением хэша;
4. после успешной записи всех файлов формируется снимок конфигурации расширения;
5. снимок `.nkdk/components/cfe/<Имя>/configuration-index.bin` записывается последним.

Временная область и журнал публикации не вводятся. Импорт не является транзакцией: при ошибке в целевом компоненте могут остаться уже записанные файлы, а снимок конфигурации расширения не создаётся или не обновляется. Для повторного импорта частичный каталог расширения требуется очистить.

## Снимки компонентов

Каждый компонент имеет самостоятельный бинарный снимок в общей корневой папке `.nkdk`:

```text
.nkdk/
  components/
    cf/
      configuration-index.bin
    cfe/
      Расширение_All/
        configuration-index.bin
```

Вложенные `.nkdk` внутри `cf` и `cfe` запрещены.

Снимок `cf` содержит:

- поколение и версию производителя;
- хэши файлов `cf`;
- идентификаторы metadata-объектов;
- сведения об узлах и значениях исходного XML.

Снимок конфигурации расширения содержит:

- поколение и версию производителя;
- хэши файлов только выбранного `cfe`;
- локальные metadata-индексы и зависимости только выбранного `cfe`;
- собственные идентификаторы объектов расширения;
- сведения об XML-узлах и значениях расширения.

Общий индекс конфигурации и составное поисковое представление в снимок конфигурации расширения не копируются.

Текущий формат `.nkdk/configuration-index/default.bin` не поддерживается и не переносится. Новая архитектура сразу использует отдельную адресацию снимков компонентов.

# Расширения конфигурации: импорт из XML и построение `BaseForm`

## Контекст

NKDK-проект уже разделяет компоненты по каталогам:

```text
cf/
cfe/<ИмяРасширения>/
erf/<ИмяОтчёта>/
epf/<ИмяОбработки>/
```

MCP умеет адресовать `cfe/<ИмяРасширения>` как отдельный компонент, однако core пока обрабатывает его как независимую конфигурацию. У расширения нет архитектурно выраженной зависимости от `cf`, отдельного снимка, разрешения идентификаторов базовой конфигурации и совместной валидации.

XML расширения содержит два вида объектов:

- собственные объекты расширения;
- заимствованные объекты базовой конфигурации.

Заимствованный XML-объект имеет собственный UUID расширения и ссылается на UUID базового объекта через:

```xml
<ObjectBelonging>Adopted</ObjectBelonging>
<ExtendedConfigurationObject>...</ExtendedConfigurationObject>
```

Заимствование рекурсивно относится к реквизитам, табличным частям, их реквизитам, формам, макетам, командам и другим дочерним объектам. Управляемые формы дополнительно хранят служебное представление основной формы в `BaseForm`.

## Цели

- Импортировать расширение только при наличии базового компонента `cf`.
- Хранить расширение в `cfe/<Name из Configuration.xml>`.
- Представлять в YAML состав заимствования без служебных XML-идентификаторов.
- Поддерживать собственные и заимствованные объекты на любом зарегистрированном уровне metadata-дерева.
- Сохранять отдельный снимок `cf` и каждого расширения.
- Строить `BaseForm` заимствованной формы из текущей `cf` без хранения основы
  в YAML или снимке расширения.
- Сохранять компактное YAML-представление обработчиков событий расширения с
  режимами вызова `Before`, `After` и `Override`.

## Границы текущего этапа

Спецификация описывает импорт расширения из XML и построение `BaseForm` при
полной синхронизации расширения в XML. В текущий этап не входят:

- остальные механизмы полной синхронизации расширения, уже определённые
  отдельной спецификацией унифицированной XML-синхронизации;
- частичная синхронизация расширения;
- валидация расширения;
- исследование допустимых наборов свойств заимствованных объектов разных видов;
- генерация YAML-схем расширения;
- переименование объектов и дочерних элементов;
- поддержка состояний свойств, появившихся начиная с режима совместимости `8.3.28`, включая `Auto`.

Импорт поддерживает формат примеров с режимом совместимости не выше `8.3.27`: состояние `Notify` переносится в YAML, состояние `Extended` сохраняется в снимке конфигурации расширения.

Неизвестные значимые XML-свойства и неподдерживаемые состояния `xr:PropertyState` пропускаются без ошибки и не переносятся в YAML или снимок конфигурации расширения.

## Основные решения

### Обязательная база

`cfe/<Имя>` всегда является зависимым компонентом. Самостоятельный импорт расширения без `cf` не поддерживается.

Расширение видит:

1. собственные объекты;
2. заимствованные объекты и элементы;
3. остальные доступные объекты `cf`.

Расширение не видит и не индексирует другие каталоги `cfe`.

### Нейтральная модель компонентов

Общие слои metadata не получают частных условий по имени каталога `cfe`, XML-полям `ObjectBelonging`, `ExtendedConfigurationObject` или узлу `BaseForm`.

Операция получает нейтральный контекст компонента:

- корень NKDK-проекта;
- выбранный компонент;
- вид компонента: базовый или зависимый;
- базовый компонент зависимого компонента;
- целевой путь снимка выбранного компонента;
- порядок разрешения ссылок.

При импорте снимок `cf` не читается. Общий индекс конфигурации строится непосредственно из YAML базового компонента.

Для разрешения ссылок поиск выполняется сначала в выбранном `cfe`, затем в `cf`. Поисковый слой найденного элемента известен только механизму разрешения ссылок и не используется для определения принадлежности.

Особенности XML расширения регистрируются рядом с правилами конкретных объектов и дочерних типов.

## YAML-представление

### Определение принадлежности

Отдельное поле принадлежности в YAML не вводится.

- Если логический путь объекта или дочернего элемента существует в `cf`, его наличие в `cfe` означает заимствование.
- Если логического пути нет в `cf`, элемент является собственным элементом расширения.
- Собственный элемент расширения не может иметь логический путь, совпадающий с элементом `cf`.

Имя верхнеуровневого объекта определяется каталогом проекта. Имя дочернего объекта определяется ключом коллекции.

### Заимствованные элементы

YAML заимствованного объекта хранит:

- факт заимствования самого объекта через наличие его YAML-файла;
- состав заимствованных дочерних объектов через наличие ключей или файлов;
- обязательное представление каждого заимствованного элемента;
- собственные дочерние элементы расширения в полном виде.

Для каждого вида объекта `rules.ts` декларативно определяет обязательные свойства заимствованного представления. Например:

- `Attribute` требует `Type`;
- `Command` требует `Group`;
- `Form` требует `FormType`;
- `Template` требует `TemplateType`.

Эти свойства импортируются в YAML и не восстанавливаются неявно из `cf`.

Заимствованный объект может поддерживать не все свойства собственного объекта того же вида. Импорт не определяет этот допустимый набор и не отклоняет свойства: он переносит все распознанные свойства, фактически присутствующие в XML. Ограничения конкретных видов заимствованных объектов требуют отдельного исследования и в дальнейшем проверяются валидацией с учётом принадлежности элемента.

Служебные значения не попадают в YAML:

- `ObjectBelonging`;
- `ExtendedConfigurationObject`;
- UUID расширения;
- UUID базового элемента;
- служебная часть `InternalInfo`, кроме состояния `Notify`, представленного разделом `Контроль`.

### Контроль свойств

Раздел `Контроль` — компактный массив YAML-имён свойств, для которых в XML задано:

```xml
<xr:PropertyState>
  <xr:Property>...</xr:Property>
  <xr:State>Notify</xr:State>
</xr:PropertyState>
```

Например:

```yaml
Контроль:
  - ОсновнойРежимЗапуска
```

В `Контроль` не хранятся само значение свойства, `ExtendedConfigurationObject` или состояние `Extended`.

`Контроль` обрабатывается для каждого metadata-item при рекурсивном импорте, а не только для верхнеуровневого объекта. Поэтому собственный раздел `Контроль` может появиться у реквизита, табличной части, формы, команды и любого другого вложенного элемента, если соответствующий `InternalInfo` находится в XML этого элемента.

Обычное контролируемое свойство хранится своим обычным YAML-полем. Его отсутствие означает, что свойство не входит в XML расширения; явное пустое значение означает, что в XML требуется пустой узел.

`State=Extended` относится к отдельно хранимым расширяемым данным: формам, модулям, правам, командным интерфейсам, картинкам и другим зарегистрированным видам. Оно не попадает в YAML. При импорте его наличие сохраняется как служебная информация в снимке конфигурации расширения.

Пример заимствованной части справочника:

```yaml
Реквизиты:
  СтроковыйРеквизитСИндексом:
    Тип: Строка(10)
  РеквизитСправочника:
    Тип: Дата

ТабличныеЧасти:
  ТабличнаяЧасть:
    Реквизиты:
      РеквизитТабличнойЧасти:
        Тип: Строка(10)
      ЗацикленныйРеквизит:
        Тип: СправочникСсылка.СправочникПолный

Команды:
  ПолнаяКоманда:
    Группа: ВажноеВПанелиНавигации
```

### Собственные элементы

Собственный объект или дочерний элемент расширения хранится по обычной полной YAML-схеме соответствующего `rules.ts`.

В одном заимствованном объекте могут одновременно находиться заимствованные и собственные реквизиты, табличные части, команды, формы и другие дочерние элементы.

### Корневая конфигурация расширения

Корневой `Configuration.xml` расширения импортируется по отдельным `MetadataConfigurationExtensionRules`, а не по правилам основной конфигурации. Эти правила:

- содержат общие свойства, допустимые и для основной конфигурации, и для расширения;
- добавляют свойства, существующие только у расширения;
- не включают свойства основной конфигурации, отсутствующие у расширения;
- задают собственные значения по умолчанию расширения;
- используют тот же рекурсивный механизм `Контроль`, что и остальные metadata-item.

Точный состав правил определяется поддерживаемыми XML-примерами `cfe/default`, `cfe/all-extension` и `cfe/control`. Неизвестное корневое свойство пропускается по общей политике импорта.

### Формы

YAML формы расширения всегда хранит полную итоговую форму. Частичный формат формы и отдельный язык операций добавления, перемещения или удаления элементов не вводятся.

Для заимствованной формы:

- `Форма.yaml` содержит полное итоговое содержимое формы расширения;
- `BaseForm` в YAML не хранится;
- при импорте вложенный `BaseForm` игнорируется;
- UUID формы и идентификаторы её элементов сохраняются по обычным правилам снимка конфигурации расширения.

### События формы расширения

Обычная привязка одного обработчика сохраняет существующее компактное представление:

```yaml
События:
  ПриИзменении: КодПриИзменении
```

Расширение может привязать к одному событию несколько обработчиков с разным
порядком вызова. Для этого значение события становится объектом:

```yaml
События:
  ПриИзменении:
    Перед: allext_КодПриИзмененииПеред
    После: allext_КодПриИзмененииПосле
  НачалоВыбора:
    Вместо: allext_КодНачалоВыбораВместо
  НачалоВыбораИзСписка:
    После: allext_КодНачалоВыбораИзСпискаПосле
```

Значения `Перед`, `После` и `Вместо` соответствуют XML-атрибуту `callType`
со значениями `Before`, `After` и `Override`. Составной ключ события в снимке
включает имя события и `callType`, поэтому два обработчика `OnChange` не
перезаписывают друг друга, а исходный порядок привязок восстанавливается.

Привязки обработчиков расширения находятся только во внешней форме. События
основной формы не копируются в `BaseForm`: основная конфигурация предоставляет
их платформе самостоятельно.

## Импорт расширения из XML

Импорт расширения дополняет существующую операцию импорта из XML нейтральным контекстом зависимого компонента. Общий координатор и worker не проверяют имена каталогов `cfe` и конкретные XML-поля расширения. Распознавание расширения и игнорирование служебных XML-полей задаются регистрациями и `rules.ts`.

### Определение компонента и предварительные проверки

До формирования заданий импорта координатор:

1. читает корневой `Configuration.xml`;
2. определяет по зарегистрированному правилу, что выгрузка является расширением;
3. получает имя расширения и вычисляет целевой компонент `cfe/<Имя>`;
4. проверяет наличие компонента `cf`;
5. проверяет, что целевой каталог расширения отсутствует либо пуст;
6. проверяет, что снимок конфигурации расширения с тем же именем ещё не существует.

Имя каталога расширения не передаётся пользователем отдельно и не выводится из имени исходного XML-каталога. Конфликт имени с существующим каталогом или снимком является ошибкой; существующие данные автоматически не очищаются.

### Общий индекс конфигурации

До разбора XML расширения координатор строит общий индекс только базового компонента `cf`:

1. обнаруживает и классифицирует YAML-файлы `cf`;
2. распределяет их между worker;
3. собирает частичные metadata-индексы тем же механизмом, что используется при валидации;
4. объединяет частичные вклады в общий индекс конфигурации;
5. создаёт его неизменяемое представление в общей памяти.

Полная валидация `cf` при этом не запускается. Ошибка чтения, разбора или построения необходимого факта остаётся ошибкой операции.

Первоначально индекс строится холодным проходом. В дальнейшем тот же договор допускает получение индекса из кэша, если хэши файлов `cf` подтверждают его актуальность.

### Обработка XML

Дальнейший поиск файлов, классификация, формирование заданий и распределение между worker используют существующий конвейер импорта.

Во время единственного обхода XML worker дополнительно формирует нейтральные факты зависимого компонента:

- собственный UUID элемента расширения;
- вид и логический адрес элемента;
- сведения об исходных XML-узлах и значениях для снимка конфигурации расширения.

`ObjectBelonging`, `ExtendedConfigurationObject` и `BaseForm` считаются служебными входными данными: они не попадают ни в YAML, ни в снимок конфигурации расширения.

Для записей `xr:PropertyState` действуют отдельные правила:

- `Notify` преобразуется в имя свойства в массиве `Контроль`;
- `Extended` в YAML не попадает и сохраняется в снимке конфигурации расширения как служебное состояние отдельно хранимого свойства;
- остальные состояния пропускаются;
- правила конкретного объекта задают соответствие XML-имени свойства его YAML-имени.

Импорт не определяет, является элемент собственным или заимствованным. Он преобразует фактически присутствующие XML-свойства и дочерние элементы по обычным `rules.ts`. Поэтому сокращённый XML заимствованного элемента даёт компактный YAML, а полный XML собственного элемента — полное YAML-представление.

Различия в допустимом составе свойств собственного и заимствованного элемента не являются ошибкой импорта. Для последующей валидации принадлежность определяется по совпадению логического пути с `cf`, после чего применяется набор ограничений соответствующего вида metadata-item.

### Разрешение ссылок

Общий индекс `cf` при импорте используется только для разрешения ссылок на объекты основной конфигурации. Принадлежность элементов во время импорта не проверяется.

Индекс разрешения ссылок расширения строится слоями:

1. worker объединяют частичные вклады в локальный индекс только выбранного `cfe`;
2. координатор создаёт составное поисковое представление над локальным индексом `cfe` и общим индексом конфигурации.

Поиск выполняется сначала в локальном индексе расширения, затем в общем индексе конфигурации. Индексы физически не объединяются и не копируются. Элемент первого слоя перекрывает одноимённый базовый элемент только в контексте выбранного расширения; индекс `cf` не изменяется.

### Импорт форм

Внешняя часть XML формы импортируется как полная итоговая `Форма.yaml`.

Вложенный `BaseForm` игнорируется и не записывается ни в YAML, ни в снимок конфигурации расширения.

Событие без `callType` импортируется строковым значением. События с `callType`
группируются по YAML-имени события и режиму вызова. Повторяющиеся XML-имена
событий не считаются конфликтом, если у них различается `callType`.

### Запись результата

Результат записывается так же, как при импорте основной конфигурации:

1. после построения необходимых индексов worker уточняет отложенные значения одного YAML-результата;
2. сразу сериализует YAML, вычисляет хэш по записываемым байтам и записывает файл непосредственно в `cfe/<Имя>`;
3. внешние файлы копируются непосредственно в целевой компонент с одновременным вычислением хэша;
4. после успешной записи всех файлов формируется снимок конфигурации расширения;
5. снимок `.nkdk/components/cfe/<Имя>/configuration-index.bin` записывается последним.

Временная область и журнал публикации не вводятся. Импорт не является транзакцией: при ошибке в целевом компоненте могут остаться уже записанные файлы, а снимок конфигурации расширения не создаётся или не обновляется. Для повторного импорта частичный каталог расширения требуется очистить.

## Снимки компонентов

Каждый компонент имеет самостоятельный бинарный снимок в общей корневой папке `.nkdk`:

```text
.nkdk/
  components/
    cf/
      configuration-index.bin
    cfe/
      Расширение_All/
        configuration-index.bin
```

Вложенные `.nkdk` внутри `cf` и `cfe` запрещены.

Снимок `cf` содержит:

- поколение и версию производителя;
- хэши файлов `cf`;
- идентификаторы metadata-объектов;
- сведения об узлах и значениях исходного XML.

Снимок конфигурации расширения содержит:

- поколение и версию производителя;
- хэши файлов только выбранного `cfe`;
- локальные metadata-индексы и зависимости только выбранного `cfe`;
- собственные идентификаторы объектов расширения;
- сведения об XML-узлах и значениях расширения.

Общий индекс конфигурации и составное поисковое представление в снимок конфигурации расширения не копируются.

Текущий формат `.nkdk/configuration-index/default.bin` не поддерживается и не переносится. Новая архитектура сразу использует отдельную адресацию снимков компонентов.

## Удаление решений, основанных на некорректном XML

После очистки примеров `cfe/all-extension` часть доработок round-trip больше не имеет корректного XML-основания и должна быть удалена точечно. Целые коммиты не откатываются: они содержат также необходимые общие механизмы.

### Пакеты XDTO

В актуальном `WebServices/WebСервисВсеСвойстваExt.xml` пустая ссылка представлена как:

```xml
<xr:Value xsi:type="xr:MDObjectRef"/>
```

Произвольного UUID внутри `xr:Value` больше нет. Поэтому необходимо удалить:

- распознавание любой UUID-подобной строки как `xr:MDObjectRef` из `commonObjects/xDTOPackages/toXML.ts`;
- тест с UUID `70d80fbc-fade-411f-b1bd-5058df6b4362`.

Обычное правило остаётся прежним: ссылка `XDTOPackage.<Имя>` выгружается как `xr:MDObjectRef`, строковое пространство имён — как `xs:string`. Представление пустого `xr:MDObjectRef` рассматривается отдельно и не должно восстанавливаться эвристикой по тексту.

### Корневой интерфейс команд

Из `Subsystems/ПодсистемаВсеСвойстваExt/Ext/CommandInterface.xml` удалены незначащие UUID ролей и подсистем. Поэтому необходимо удалить из `commonObjects/rootCommandInterface`:

- пропуск произвольных UUID без разрешения metadata-ссылки для ролей;
- пропуск произвольных UUID в `ПорядокПодсистем`;
- разрешение произвольного UUID в YAML-схеме `ПорядокПодсистем`;
- тесты, добавленные специально для UUID роли `00000000-efd0-f8ea-3002-0000aa2905e2` и подсистемы `f8eaf128-0230-0000-28f1-eaf830020000`.

Корректные внутренние ссылки на команды вида `0:<UUID>` и `1:<UUID>` этим решением не затрагиваются: они встречаются в XML основной конфигурации и уже обрабатываются отдельно как имена команд интерфейса.

### `DataPath` базовой формы

В актуальном `Catalogs/СправочникПолный/Forms/ФормаЭлемента/Ext/Form.xml` элементы `Код` и `Наименование` внутри `BaseForm` не содержат `DataPath`. Поэтому необходимо удалить требование и тест, ожидающий восстановление `Объект.Code` внутри заново построенного `BaseForm`.

Общий механизм преобразования `DataPath` не удаляется. Он по-прежнему требуется итоговой форме расширения, где YAML-имена стандартных реквизитов должны преобразовываться во внутренние XML-имена платформы.

### Механизмы, которые сохраняются

Очистка некорректных примеров не отменяет:

- общий снимок порядка, присутствия узлов и невосстановимых XML-значений;
- отдельный снимок конфигурации расширения;
- `defaultValueAdoptedXML` для обязательных XML-значений заимствованных объектов;
- составной индекс `cfe → cf`;
- преобразование `DataPath` полной итоговой формы расширения;
- построение `BaseForm` из актуальной основной конфигурации.

Согласованное правило состава описано ниже в разделе
[«Построение `BaseForm`»](#построение-baseform).

## Построение `BaseForm`

### Назначение

`BaseForm` не хранится в YAML или снимке конфигурации расширения. При
синхронизации она строится из текущей синхронизированной формы `cf` и формы
выбранного расширения.

`BaseForm` является не полной копией формы `cf`, а допустимой для выбранного
расширения проекцией основной формы. В проверенных примерах состав, исходный
вид и иерархия элементов `BaseForm` совпадают с текущей формой `cf`; различается
состав остальных компонентов и зависимых от них свойств.

### Состав компонентов

Промежуточная модель `BaseForm` формируется по следующим правилам:

- все элементы формы берутся из `cf` с исходным видом, именем и иерархией;
- собственные элементы формы `cfe` в `BaseForm` не включаются;
- реквизиты, команды и параметры включаются только по пересечению имён
  соответствующей коллекции в `cf` и форме `cfe`;
- совпавший по имени компонент считается явно заимствованным;
- собственный компонент `cfe`, имя которого отсутствует в `cf`, в `BaseForm`
  не включается;
- значения явно заимствованного реквизита, команды или параметра для
  `BaseForm` берутся из `cf`, а изменения расширения остаются во внешней форме.

Например, если расширение меняет исходное поле ввода на поле надписи, внешняя
форма содержит поле надписи, а `BaseForm` сохраняет исходное поле ввода из
текущей формы `cf`.

### Идентификаторы

Идентификаторы автоматически заимствованных элементов формы и их служебных
дочерних элементов берутся из формы `cf`.

Явно заимствованный реквизит, команда или параметр имеет локальную идентичность
расширения. Поэтому его значение для `BaseForm` берётся из `cf`, но собственный
идентификатор берётся из соответствующего компонента внешней формы `cfe`.
Например, реквизит формы может иметь `id="4"` в `cf` и `id="1000001"` как во
внешней форме расширения, так и в её `BaseForm`.

Собственный идентификатор расширения извлекается из снимка выбранного `cfe`.
Идентификатор основного компонента извлекается из подтверждённого состояния
`cf`. Построитель не генерирует новый идентификатор, если требуемая идентичность
зафиксирована одним из этих источников.

### Порядок и вложенность

Порядок, родительские группы и исходная вложенность автоматически
заимствованных элементов внутри `BaseForm` берутся из текущей формы `cf`.

Перемещение элемента, добавление собственной группы и размещение в ней
заимствованного элемента описываются только внешней формой расширения.
Собственная группа `cfe` в `BaseForm` не добавляется, а перемещённый элемент
остаётся в исходной позиции основной формы.

Элементы основной и внешней формы сопоставляются по имени независимо от
конкретного XML-вида. При допустимой смене вида элемент сохраняет идентичность:
например, внешнее `LabelField name="Код"` соответствует исходному
`InputField name="Код"`. Внешняя форма сохраняет новый вид, а `BaseForm` —
исходный вид и идентификатор элемента из `cf`. Пересечение свойств выполняется
по YAML-именам, общим для двух видов.

### Проекция свойств

После выбора компонентов механизм обрабатывает свойства формы и её элементов:

- обычное свойство включается только тогда, когда соответствующее YAML-свойство
  присутствует одновременно в текущей форме `cf` и во внешней форме `cfe`;
- значение включённого свойства для `BaseForm` берётся из `cf`;
- правило пересечения применяется рекурсивно к форме, элементам и вложенным
  объектам свойств;
- `Events` основной формы не копируются;
- `DataPath` и другие ссылки на реквизиты формы сохраняются только тогда,
  когда их корневой реквизит включён в `BaseForm`;
- обязательная XML-ссылка `CommandName` получает служебное значение `0`, если
  связанная команда формы не включена в `BaseForm`;
- вложенные ссылочные коллекции очищаются по тем же правилам разрешения ссылок.

Например, исходный `DataPath` поля `Код` удаляется, если корневой реквизит формы
`Объект` не заимствован явно. Если реквизит формы заимствован и включён в
проекцию, его `DataPath` сохраняется.

Кнопка, связанная в `cf` с незамствованной командой, остаётся элементом
`BaseForm`, но получает `<CommandName>0</CommandName>`. Остальные свойства
кнопки сохраняются по обычным правилам проекции.

Например, `CommandSet` входит в `BaseForm`, если он присутствует и в `cf`, и во
внешней форме расширения. Наличие `CommandSet` только в `cf` недостаточно.
Аналогично обрабатываются скалярные свойства формы, включая
`UseForFoldersAndItems`.

Для обычной внешней формы продолжает использоваться полный поисковый контекст
`cfe → cf`: расширение видит собственные объекты и основную конфигурацию.

Для `BaseForm` создаётся отдельный контекст проекции. Он содержит элементы
основной формы и только явно заимствованные реквизиты, команды и параметры,
выбранные в состав `BaseForm`. Наличие одноимённого компонента в полном
контексте `cf` не делает его доступным внутри проекции. Поэтому ссылка на
незамствованный реквизит удаляется из `BaseForm`, хотя обычная внешняя форма
может разрешить этот реквизит через основную конфигурацию.

Для ссылочного свойства рядом с его существующим правилом формы задаётся
поведение на случай, если целевой компонент не вошёл в контекст проекции.
Это внутреннее правило построения `BaseForm`, а не операция над пользовательским
YAML:

- для `DataPath` свойство не включается в промежуточную модель и XML-тег не
  создаётся;
- для `CommandName` промежуточная модель получает служебную пустую ссылку,
  которая сериализуется как `0`;
- если ссылочное свойство стало недоступным, но его правило не определяет
  допустимое представление, синхронизация завершается ошибкой.

Общие слои синхронизации не проверяют имена XML-тегов `DataPath`,
`CommandName`, `Events` и другие частные поля формы.

Полученная промежуточная YAML-модель преобразуется существующим обработчиком
`ClientApplicationForm`. Отдельный XML-построитель `BaseForm` и вычитание
готовых XML-деревьев не вводятся.

### Ошибки построения

Синхронизация завершается ошибкой, если:

- не найдена соответствующая форма `cf`;
- отсутствует требуемый идентификатор элемента основной формы или явно
  заимствованного компонента расширения;
- после построения контекста проекции обнаружена недоступная ссылка, для
  которой правило свойства не задаёт допустимого представления;
- сформированную промежуточную модель нельзя преобразовать обычными правилами
  `ClientApplicationForm`.

Уже записанные XML-файлы не откатываются по общей политике полной
синхронизации.

### Будущая валидация

Ограничения редактирования заимствованной формы фиксируются для отдельного
этапа валидации и не проверяются текущей операцией синхронизации:

- каждый элемент текущей формы `cf` должен присутствовать в YAML заимствованной
  формы расширения;
- элемент, существующий в основной форме, нельзя удалить из результирующей
  формы расширения;
- для исключения элемента из работы используется его допустимое свойство,
  например `Доступность: Ложь`;
- явно заимствованные реквизиты, команды и параметры нельзя удалить из
  основной формы посредством расширения: удаление из представления расширения
  отменяет их заимствование;
- допустимы только поддерживаемые платформой изменения вида элемента;
- несовместимая смена категории, например превращение поля в группу,
  запрещена;
- точная матрица совместимых видов элементов требует отдельного исследования
  и не кодируется в построителе `BaseForm`.

Построитель `BaseForm` исходит из согласованного входа и не повторяет эти
проверки. Текущее отсутствие такой валидации отдельно зафиксировано в
`.agents/restrictions.md`.

## Проверка и критерии приёмки

### Модульные проверки

Проверки построителя `BaseForm` покрывают:

- сохранение исходного вида, идентификатора, порядка и вложенности элементов
  `cf`;
- сопоставление элемента по имени при допустимой смене вида во внешней форме;
- исключение собственных элементов и собственных компонентов `cfe`;
- включение явно заимствованных реквизитов, команд и параметров с локальными
  идентификаторами `cfe` и значениями `cf`;
- рекурсивное пересечение свойств;
- удаление `DataPath`, ведущего к незамствованному реквизиту;
- сохранение `DataPath`, ведущего к явно заимствованному реквизиту;
- преобразование недоступного `CommandName` в `0`;
- отсутствие событий основной формы внутри `BaseForm`;
- ошибку для недоступной ссылки без зарегистрированного поведения.

Проверки YAML-договора событий покрывают:

- прежнее строковое представление обычного обработчика;
- несколько обработчиков одного события с разными режимами вызова;
- преобразование `Перед`/`После`/`Вместо` в
  `Before`/`After`/`Override` и обратно;
- сохранение порядка событий через составной ключ имени события и `callType`.

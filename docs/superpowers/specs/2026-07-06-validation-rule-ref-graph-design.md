# Ref-граф validation-схем

## Контекст

Project validation сейчас экспортирует многие JSON Schema из `rules.ts` как большие inline-деревья. Для форм уже есть частичный реестр схем: `ClientApplicationForm`, реквизиты формы, команды, параметры и элементы формы могут регистрироваться как именованные схемы, а exporter-ы свойств умеют отдавать ссылки вида `nkdk://schema/...` в режиме `externalRefs`.

Текущий путь validation использует этот граф непоследовательно. Большие схемы всё ещё содержат локальные `$defs` и повторяющиеся rule-backed поддеревья, что увеличивает время компиляции и расход памяти. Замер большой формы показал, что cold-путь почти целиком тратится на работу со схемой: экспорт JSON Schema, компиляцию AJV и первый validation-pass, который уходит в TypeBox fallback для `$defs`.

## Цель

Каждая переиспользуемая структура, построенная на `rules.ts`, должна иметь именованную схему и уметь переиспользоваться через `$ref`. Worker должен компилировать граф общих схем один раз на validation context при инициализации, а затем валидировать файлы через корневые схемы, которые ссылаются на этот граф.

Критерии успеха:

- RSS validation worker-ов снижается;
- компиляция схем отделена от валидации файлов и видна в профильном выводе;
- существующие schema-, fixture- и validation-тесты не теряют качество диагностик;
- общие слои `validation`, `project` и `orchestration` не получают частного знания о конкретных metadata-типах.

## Дизайн

Добавляем rule-backed ref-граф поверх существующего project schema registry.

Каждая rule-backed схема получает стабильный schema id, например `ClientApplicationForm`, `FormAttribute`, `InputField`, `MetadataAttribute`, `MetadataTabularSection`, `DcsFilter`, `DcsOrder`. Существующие ручные регистрации остаются валидными; новая работа стандартизирует именование, сбор зависимостей и компиляцию таких схем.

Экспорт схем получает режим graph/ref. В этом режиме, если свойство или вложенный элемент указывает на другую зарегистрированную rule-backed схему, exporter отдаёт `$ref: "nkdk://schema/<Name>"`, а не встраивает целевую схему внутрь текущей. Экспорт также фиксирует достижимые ссылки, чтобы validation мог собрать полный граф для корневой схемы.

Worker создаёт один компилятор схем на validation context. При инициализации worker обязан скомпилировать все схемы, нужные validation roots: `ClientApplicationForm`, все project properties schemas и весь достижимый shared schema graph. Worker не считается запущенным и не принимает файлы в first-pass, пока эта компиляция не завершилась успешно.

AJV нужно настроить так, чтобы `$ref` действительно уменьшали размер скомпилированного кода. В первой реализации надо сравнить `inlineRefs: false` с небольшим числовым лимитом, потому что AJV по умолчанию может встраивать referenced schemas обратно в скомпилированную функцию. Если для части схем всё ещё нужен TypeBox fallback, он также должен компилироваться во время инициализации worker-а, а не лениво на первом реальном файле.

## Включение

Используем allowlist, хотя целевая модель — «каждый `rules.ts` имеет ref». Так поведение можно измерять и включать по слоям.

Этап 1: формы.

- `ClientApplicationForm`
- `FormAttribute`, `FormAttributeColumn`
- `FormCommand`, `FormParameter`
- все правила элементов формы
- общие формовые объекты, которые сейчас дублируются внутри element-схем

Этап 2: обычные common objects метаданных.

- реквизиты, табличные части, команды, предопределённые элементы, состав плана обмена и похожие rule-backed common objects;
- корневые схемы прикладных объектов остаются validation roots и ссылаются на эти общие схемы.

Этап 3: схема компоновки данных.

СКД обрабатываем отдельно. Там есть рекурсивные структуры, большие union-ы, typed values и кастомные `toJSONSchema.ts` exporters. Нельзя слепо переводить всё дерево СКД на refs первым шагом.

Начинаем с небольших leaf- и collection-правил СКД: order, filter, appearance fields, structure item groups. Более тяжёлые схемы, например parameter values, metadata values и typed values, переводим только после fixture- и performance-замеров.

## Поток данных

Validation строит граф схем для context:

1. Загружает schema registries.
2. Определяет validation root schemas.
3. Обходит `x-nkdk-schemaRefs` или эквивалентный список собранных refs.
4. Экспортирует каждую referenced named schema один раз.
5. Добавляет все схемы в один AJV instance.
6. Компилирует корневые и общие validators во время инициализации worker-а.
7. Переиспользует скомпилированные validators для всех файлов, которые обрабатывает этот worker.

Корневая схема отвечает за форму файла. Referenced schemas отвечают за переиспользуемые rule-backed фрагменты.

## Ошибки

Отсутствующий schema id — ошибка инициализации worker-а, а не диагностика конкретного YAML-файла. Если root schema ссылается на незарегистрированную rule-backed схему, запуск worker-а должен падать с понятным именем схемы и root validator, который пытались скомпилировать.

Неподдержанные или рискованные DCS-схемы остаются inline до явного добавления в allowlist. Это защищает диагностики сложных DCS-значений, пока для них нет отдельных замеров и тестов.

## Тестирование

Нужны тесты на:

- registry экспортирует стабильные schema id для выбранных rule-backed схем;
- root-схема формы в graph/ref режиме отдаёт refs вместо inline element-схем;
- AJV компилирует root вместе с referenced schemas и валидирует существующие form fixtures;
- отсутствующая referenced schema даёт понятную ошибку инициализации;
- DCS allowlist не переводит неподдержанные тяжёлые схемы на refs случайно;
- инициализация worker-а компилирует все validation-схемы до first-pass валидации файлов.

Performance-проверка сравнивает состояние до и после на `/Users/nikita/git/nkdk-yaml`:

- время компиляции схем при запуске worker-а;
- first-pass wall time;
- RSS и heap после инициализации схем;
- RSS и heap после валидации всех форм;
- parity по количеству и составу diagnostics.

## Открытые решения

Точное соглашение об именовании schema id нужно вывести из существующих registry names там, где они уже есть. Для rules без текущей регистрации предпочтительны `itemType` правила или устоявшееся имя типа.

Первая реализация должна измерить `inlineRefs: false` против небольшого числового лимита `inlineRefs`. Выбираем настройку, которая лучше снижает память без неприемлемого замедления validation.

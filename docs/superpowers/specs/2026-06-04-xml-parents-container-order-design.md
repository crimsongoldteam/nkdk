# Порядок XML-контейнеров из xmlParents

## Цель

XML без reference должен сохранять порядок контейнеров, который принимает 1С: `InternalInfo`, затем `Properties`, затем `ChildObjects`. Модель metadata остаётся линейной: XML-дерево не переносится внутрь `properties`, а контейнеры остаются правилом XML-экспорта.

## Контекст

В `/home/nikita/git/round-trip/all` встречаются устойчивые верхние комбинации:

- `InternalInfo > Properties > ChildObjects`;
- `InternalInfo > Properties`;
- `Properties > ChildObjects`;
- `Properties`.

По `rules.ts` в `packages/core/metadata/**` реальные `xmlParents` используют такие пути:

- `[]` — 79 правил;
- `["Properties"]` — 1154 правила;
- `["ChildObjects"]` — 116 правил;
- `["ListSettings"]` — 7 правил;
- `["Form", "Properties"]` — 7 правил;
- `["ListSettings", "dcsset:dataParameters"]` — 1 правило;
- одиночные специальные контейнеры: `Attributes`, `Form`, `dcssch:inputParameters`, `dcsset:groupItems`, `xr:CharacteristicTypes`, `xr:CharacteristicValues`.

`xmlParents` уже является массивом и задаёт путь контейнеров. Текущая максимальная вложенность — 2 уровня, но существующий обход в `buildPathStructure` уже рассчитан на произвольную глубину.

Текущий `requiredXMLParents` только создаёт пустой контейнер после экспорта. Он не задаёт порядок и в реальных правилах используется только как массив путей вроде `["ChildObjects"]` и `["ListSettings"]`. Форма `{ path, tag }` есть в типе и тестах, но в `rules.ts` не используется.

Проблема видна на XML без reference: вложенные `TabularSection` могут получить `Properties`, затем `InternalInfo`, затем `ChildObjects`, хотя 1С ожидает `InternalInfo`, затем `Properties`, затем `ChildObjects`.

## Решение

Не вводить `XMLContainer`. Контейнеры выводятся из уже существующих `xmlParents`, а порядок верхних XML-групп задаётся на уровне XML-экспорта.

Базовое правило сортировки без reference:

- reference-порядок остаётся главным, если `referenceMetadata` есть;
- без reference верхние группы сортируются по рангу `InternalInfo`, `Properties`, `ChildObjects`;
- остальные корневые узлы и специальные контейнеры идут по существующему порядку путей/ключей правила;
- внутри одного `xmlParents` порядок остаётся прежним: `order`, затем reference-порядок, затем порядок правила/XML-ключа;
- `order` не должен поднимать поле из `Properties` выше корневого `InternalInfo`.

Это исправляет исходную ошибку: `order` у свойств внутри `Properties` больше не перебивает порядок верхних контейнеров.

## InternalInfo

`InternalInfo` не является контейнером и не должен становиться служебным свойством. Это обычное содержательное XML-свойство с типом `InternalInfo`, обычно `forReferenceOnly: true`.

В сортировке оно участвует как корневой XML-узел с высоким приоритетом перед контейнером `Properties`.

## Замена requiredXMLParents

`requiredXMLParents` удаляется. Его текущие случаи заменяются выводом обязательных контейнеров из конкретного `MetadataItemRule`.

Контейнер считается обязательным не глобально по имени XML-узла и не по типу объекта, а по правилу после тех же фильтров, что использует экспорт: `tag`, `toXML`, `runtimeOnly`, `syncExternalOnly`, `filePath`.

- если правило содержит хотя бы одно экспортируемое свойство с первым `xmlParents`-сегментом `ChildObjects`, экспорт создаёт пустой `<ChildObjects/>`, даже когда дочерние коллекции пустые;
- если правило содержит хотя бы одно экспортируемое свойство с первым `xmlParents`-сегментом `ListSettings`, экспорт создаёт пустой `<ListSettings/>`, даже когда настройки пустые;
- наличие такого свойства означает, что контейнер является частью XML-формата именно для этого rule и должен присутствовать при экспорте даже без дочернего содержимого;
- `Properties` не создаётся через этот механизм как обязательный контейнер: он появляется при наличии экспортируемых свойств внутри `["Properties"]`;
- вложенные контейнеры вроде `["ListSettings", "dcsset:dataParameters"]` не создаются пустыми автоматически, если конкретное свойство не экспортирует значение.

Форма `{ path, tag }` удаляется вместе с `requiredXMLParents`, потому что в реальных правилах не используется. Если она понадобится позже, её лучше вернуть отдельным правилом XML-экспорта, а не полем модели.

## Отношение к order

`order` остаётся способом явно описывать порядок XML-свойств внутри одного XML-пути. Это важно для общих spread-блоков вроде `commonTabularSectionProperties`, где физический порядок ключей в конкретном `MetadataItemRule` не всегда совпадает с XML-порядком.

Порядок контейнеров не задаётся через `order`: он выводится из `xmlParents` и ранга известных верхних XML-групп. Внутри контейнера порядок по-прежнему может задаваться `order`; если `order` не указан, используется существующий порядок ключей правила с учётом reference.

## Изменения

1. Обновить сортировку в `getOrderedKeysToXML`: при отсутствии reference сортировать сначала по верхней XML-группе, потом по `order`/порядку внутри пути.
2. Добавить вывод обязательных пустых контейнеров `ChildObjects` и `ListSettings` из `xmlParents`.
3. Удалить `requiredXMLParents` из правил, типов и тестов.
4. Оставить `order` в правилах, где он уже нужен для порядка XML-свойств внутри контейнера.

## Проверка

Нужны точечные тесты:

- без reference порядок XML равен `InternalInfo`, `Properties`, `ChildObjects`;
- `order` внутри `Properties` не поднимает свойство выше `InternalInfo`;
- `ChildObjects` создаётся пустым только для rule, где после фильтров экспорта есть свойство с `xmlParents[0] === "ChildObjects"`;
- `ListSettings` создаётся пустым только для rule, где после фильтров экспорта есть свойство с `xmlParents[0] === "ListSettings"`;
- вложенный путь `["ListSettings", "dcsset:dataParameters"]` сохраняется и не создаётся пустым без значения;
- reference-порядок остаётся главным для round-trip с reference.

После реализации прогоняется точечный набор тестов orchestration и повторная диагностика `round-trip-yaml-1c` на `all`.

# Оптимизация длительности тестов core

## Контекст

Обычный `pnpm test` проходит все функциональные проверки, но завершается с кодом 1 из-за бюджета длительности `@nkdk/core`. Три последовательных прогона текущей ветки дали 42,92–44,83 с по отчёту Vitest и 44,33–46,15 с реального времени. Setup стабильно занял 6,46–7,02 с при пределе 3 с.

Одни и те же пять файлов стабильно превысили предел 1 с:

- `metadata/forms/commonObjects/dynamicList/fromXMLToYAML.test.ts` — 1,80–1,87 с;
- `metadata/importFromXml/importConfigurationExtension.test.ts` — 1,70–1,82 с;
- `metadata/validation/schemaRegistry.test.ts` — 1,39–1,61 с;
- `metadata/importFromXml/worker.test.ts` — 1,32–1,40 с;
- `metadata/validation/projectFileSchema.test.ts` — 1,27–1,38 с.

Контрольный прогон актуального `origin/develop` также нарушает бюджет: 33,30 с всего, setup 5,76 с, а два файла превышают 1 с. Поэтому требуется исправить как существующее превышение, так и добавленное текущей веткой замедление.

## Цель

Добиться прохождения обычного `pnpm test` без платформенных коэффициентов и изменения исходных пределов:

- setup пакета — не более 3 с;
- один test file — не более 1 с;
- число и смысл проверяемых договоров не сокращаются;
- XML-фикстуры не изменяются.

Дополнительная цель — существенно сократить добавленные веткой 10–16 с относительно `develop`, а не только перераспределить измеряемое время.

## Выбранный подход

Тесты разделяются на изолированные проекты Vitest по слоям `commonObjects`, `forms`, `appliedObjects`, `validation` и `integration`. Каждый проект получает только необходимый ему слой регистрации и отдельное окружение реестров. Полная регистрация `registerCoreMetadata()` остаётся только у интеграционного проекта.

Проекты запускаются одним вызовом Vitest, чтобы сохранить общий кэш преобразования TypeScript, но их тестовые окружения не разделяют изменяемые глобальные реестры. При этом внутри одного проекта допускается `--no-isolate`, если случайный порядок файлов не меняет результат.

Сначала выполняется измерительный прототип без изменения production-композиции. Он должен подтвердить фактическую изоляцию окружений Vitest, соблюдение бюджетов и устойчивость на трёх seed. Если хотя бы одно условие не выполняется, прототип не принимается, а переход к явной повторяемой production-регистрации проектируется отдельно на основании измерений.

## Изменения тестового окружения

Перед реализацией отменяются экспериментальные коммиты `ab81294da` и `74b3745cd`: выборочные импорты `registerCoreMetadata()` зависят от порядка тестов, а записанный результат не подтверждён случайными seed.

Конфигурация Vitest разделяет тесты по фактическим зависимостям:

1. Нейтральные unit-тесты используют только запрет настоящего `Piscina` и сброс тестового контекста.
2. Тесты common objects подключают регистрацию common objects.
3. Тесты forms подключают common objects и forms.
4. Тесты applied objects подключают common objects и applied objects; forms добавляются только при доказанной зависимости.
5. Тесты validation подключают минимальный набор слоёв, необходимый проверяемому графу schema.
6. Полный граф метаданных подключается лишь в интеграционных проверках, где предметом договора является полная композиция.

Сначала добавляется служебный тест, доказывающий, что изменение реестра в одном проекте не видно другому. Затем проекты проверяются отдельно и совместно. Тест не должен проходить только благодаря регистрации, выполненной ранее файлом другого проекта.

## Запасной подход

Если Vitest не обеспечивает требуемую изоляцию либо полный интеграционный проект всё равно превышает бюджет setup, production-регистрация переводится с однократных побочных эффектов импортов на явные повторяемые функции слоёв. `registerCoreMetadata()` в этом варианте не просто защищается булевым флагом, а может гарантированно установить отсутствующие записи после очистки реестров.

Этот вариант затрагивает production-композицию и не входит в текущий этап. Для него потребуются отдельный дизайн, согласование и RED-тест, воспроизводящий невозможность восстановить реестр текущей реализацией.

## Медленные файлы

### DynamicList

Проверка `ПоляКлюча` обращается к ближайшему экспортёру правила `DynamicListKeyFields`, а не строит полную JSON Schema DynamicList в `beforeAll`. XML → YAML → XML проверки остаются неизменными.

### Реестр и выбор JSON Schema проекта

`schemaRegistry.test.ts` и `projectFileSchema.test.ts` сохраняют по одному сквозному договору полного графа. Договоры отдельных типов, свойств и маршрутизации проверяются на ближайших экспортёрах. Повторная компиляция одинаковых inline-схем исключается; кэш допускается только внутри одного файла и не создаёт зависимости между тестами.

### Импорт расширения конфигурации

Сначала измеряются стадии `beforeAll`: подготовка каталогов, импорт XML, обновление ProjectState и чтение результата. Оптимизируется только подтверждённое узкое место. Сквозной вызов публичного API и проверки результата сохраняются.

### Worker импорта

Большой файл разделяется по самостоятельным договорам первого прохода, второго прохода и проверки `ПутьКДанным`. Общая тяжёлая подготовка заменяется ближайшими тестовыми переходниками и кэшами там, где она не является предметом проверки. Простое механическое разделение ради обхода лимита недопустимо: суммарное время сценариев не должно увеличиться.

## Проверка результата

После каждого слоя выполняются целевые тесты и `pnpm duplicates -- --base 0d550245a`. Перед завершением выполняются:

1. три последовательных `@nkdk/core` прогона с фиксированными seed;
2. обычный `pnpm test` без `CI=true` и иных коэффициентов;
3. `pnpm test:architecture:rules`;
4. `pnpm test:architecture`;
5. `pnpm duplicates -- --base 0d550245a`.

Для каждого прогона фиксируются setup, общая длительность и все файлы дольше 1 с. Результат считается устойчивым, только если все три core-прогона соблюдают бюджет.

Дополнительно каждый проект запускается отдельно, а затем все проекты запускаются совместно. Сумма тестов отдельных запусков и их исходы должны совпадать с совместным запуском; это подтверждает отсутствие скрытой регистрации из соседнего проекта.

## Ограничения

- Не повышать лимиты и не добавлять коэффициент macOS.
- Не переносить дорогую работу из `beforeAll` в test case или другой hook ради изменения отчёта.
- Не скрывать полную загрузку графа в общем тестовом помощнике.
- Не изменять production-регистрацию без отдельного подтверждения измерениями.
- Не считать перенос дорогого импорта из setup в тело test file оптимизацией.
- Не принимать разделение проектов, если их реестры фактически остаются общими.
- Не уменьшать наблюдаемое покрытие и не заменять сквозной договор заранее подготовленным предметным результатом.

# Оптимизация длительности тестов core

## Контекст

Обычный `pnpm test` проходит все функциональные проверки, но завершается с кодом 1 из-за бюджета длительности `@nkdk/core`. Три последовательных прогона текущей ветки дали 42,92–44,83 с по отчёту Vitest и 44,33–46,15 с реального времени. Setup стабильно занял 6,46–7,02 с при пределе 3 с.

Одни и те же пять файлов стабильно превысили предел 1 с:

- `metadata/forms/commonObjects/dynamicList/fromXMLToYAML.test.ts` — 1,80–1,87 с;
- `metadata/importFromXml/importConfigurationExtension.test.ts` — 1,70–1,82 с;
- `metadata/validation/schemaRegistry.test.ts` — 1,39–1,61 с;
- `metadata/importFromXml/worker.test.ts` — 1,32–1,40 с;
- `metadata/validation/projectFileSchema.test.ts` — 1,27–1,38 с.

Контрольный прогон актуального `origin/develop` также нарушает бюджет: 33,30 с всего, setup 5,76 с, а два файла превышают 1 с. Поэтому требуется исправить как существующее превышение, так и добавленное текущей веткой замедление.

## Цель

Добиться прохождения обычного `pnpm test` без платформенных коэффициентов и изменения исходных пределов:

- setup пакета — не более 3 с;
- один test file — не более 1 с;
- число и смысл проверяемых договоров не сокращаются;
- XML-фикстуры не изменяются.

Дополнительная цель — существенно сократить добавленные веткой 10–16 с относительно `develop`, а не только перераспределить измеряемое время.

## Выбранный подход

Существующее разделение на проекты `unit` и `core-metadata` сохраняется. Полная регистрация metadata остаётся обязательной и детерминированной для всего проекта `core-metadata`; тесты не получают выборочных импортов и не зависят от порядка файлов.

`tests/registerCoreMetadata.ts` становится лёгким setup-файлом без статических импортов metadata. При первом выполнении он создаёт в `globalThis` один `Promise`, динамически импортирует `metadata/composition/coreMetadata` и вызывает `registerCoreMetadata()`. Все последующие test files того же окружения ожидают уже завершённый Promise и не проводят большой статический граф через setup повторно.

`maxWorkers: 1` и штатный запуск `--no-isolate` означают одно окружение и одну загрузку полной metadata. Promise одновременно служит признаком завершённой регистрации и защитой от параллельного повторного запуска. Ошибка импорта или регистрации остаётся в отклонённом Promise, поэтому все последующие файлы получают ту же исходную ошибку без частично повторённой регистрации.

Production-композиция и API `registerCoreMetadata()` не меняются.

## Изменения тестового окружения

Перед реализацией уже отменены экспериментальные коммиты `ab81294da` и `74b3745cd`: выборочные импорты `registerCoreMetadata()` зависели от порядка тестов, а записанный результат не был подтверждён случайными seed.

Служебные проекты `isolation-mutation` и `isolation-observation` доказали, что проекты Vitest не разделяют `globalThis`, но одновременно подтвердили повторную загрузку setup в каждом окружении. После фиксации результата этот исследовательский договор удаляется: итоговое решение не опирается на разделение metadata-тестов по новым проектам.

Архитектурный тест фиксирует два свойства setup-файла:

1. в нём нет статических импортов из `metadata`;
2. полная композиция загружается одним динамическим импортом `metadata/composition/coreMetadata`.

Функциональный договор проверяется существующими тестами `registerCoreMetadata()` и сквозными тестами проекта `core-metadata`. Перенос тяжёлой работы в `globalSetup`, test case, hook или другой неучитываемый этап запрещён: первый динамический импорт остаётся внутри обычного setup и входит в lifecycle-измерение.

## Результаты исследования и отклонённые подходы

- Выборочные импорты полной композиции в отдельных test files ускорили один фиксированный порядок, но дали функциональные падения на других seed из-за общего изменяемого состояния.
- Изолированные проекты Vitest устранили общее состояние, но повторили setup каждого слоя. Отдельные прогоны дали примерно 1,64 с для common objects, 1,64 с для forms, 1,82 с для applied objects, 2,06 с для validation и 2,14 с для integration — уже около 9,3 с суммарно при лимите 3 с. Дополнительно проявились скрытые applied-зависимости в common, forms и unit-тестах.
- Три отдельных измерения холодного динамического импорта `metadata/composition/coreMetadata` дали 0,94–1,00 с, а сам вызов `registerCoreMetadata()` занял 0,3–1,5 мс. Следовательно, production-регистрация не является узким местом.
- Явная повторяемая production-регистрация отклонена как несоразмерная подтверждённой причине. Она понадобится только при отдельном требовании восстанавливать вручную очищенные реестры во время работы приложения.

## Медленные файлы

До оптимизации setup пять файлов превышали 1 с: DynamicList, импорт расширения, schema registry, import worker и project file schema. Эксперимент без статического полного setup показал, что все они могут опуститься ниже лимита без изменения самих тестов.

Поэтому сначала изменяется только setup. Предметные тесты оптимизируются лишь в случае, если один и тот же файл останется выше 1 с минимум в двух из трёх итоговых прогонов. Для такого файла отдельно измеряются setup, collect, hooks и test time; договор не разделяется механически ради изменения отчёта.

## Проверка результата

После каждого слоя выполняются целевые тесты и `pnpm duplicates -- --base 0d550245a`. Перед завершением выполняются:

1. три последовательных `@nkdk/core` прогона с фиксированными seed;
2. обычный `pnpm test` без `CI=true` и иных коэффициентов;
3. `pnpm test:architecture:rules`;
4. `pnpm test:architecture`;
5. `pnpm duplicates -- --base 0d550245a`.

Для каждого прогона фиксируются setup, общая длительность и все файлы дольше 1 с. Результат считается устойчивым, только если все три core-прогона соблюдают бюджет.

Дополнительно фиксируется число test files и tests. После удаления двух исследовательских тестов изоляции оно должно совпадать между тремя seed и с baseline, полученным после отката неустойчивого эксперимента.

## Ограничения

- Не повышать лимиты и не добавлять коэффициент macOS.
- Не переносить дорогую работу из `beforeAll` в test case или другой hook ради изменения отчёта.
- Не переносить полную загрузку графа в `globalSetup` или другой неучитываемый lifecycle-этап.
- Не изменять production-регистрацию: измерения не подтверждают её как узкое место.
- Не считать перенос дорогого импорта из setup в тело test file оптимизацией.
- Не разделять metadata-тесты на дополнительные окружения, повторяющие полный setup.
- Не уменьшать наблюдаемое покрытие и не заменять сквозной договор заранее подготовленным предметным результатом.

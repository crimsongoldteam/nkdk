# Ускорение поиска файлов проекта через общий обход

## Контекст

Сейчас `discoverMetadataProjectResources(projectDir)` строит список файлов проекта от правил к файловой системе:

1. Берет зарегистрированные metadata `rules.ts`.
2. Для каждого владельца metadata строит ожидаемые шаблоны файлов.
3. Для каждого кандидата проверяет наличие через `existsSync + statSync`.
4. Отдельно обходит recursive `Свойства.yaml`.

На большом YAML-проекте это приводит к сотням тысяч проверок существования файлов. В профиле `/Users/nikita/git/nkdk-yaml` основной расход времени в `Поиск файлов проекта` пришелся на проверки кандидатов, а не на чтение YAML.

## Цель

Заменить существующий механизм поиска проектных файлов на один обход файловой системы:

1. Получить список файлов проекта.
2. Для каждого файла построить `projectPath`.
3. Классифицировать путь через существующий `classifyMetadataProjectPath(projectPath)`.
4. Вернуть только распознанные файлы проекта.

Так мы сохраняем роль `rules.ts` как источника структуры проекта, но меняем направление поиска: от реальных файлов к правилам, а не от правил к множеству возможных путей.

## API

`discoverMetadataProjectResources` получает опцию фильтра:

```ts
type MetadataProjectResourceInclude = "all" | "yaml"

function discoverMetadataProjectResources(
  projectDir: string,
  options?: { include?: MetadataProjectResourceInclude }
): MetadataProjectResourceRef[]
```

- `include: "all"` возвращает YAML и прочие файлы проекта. Это поведение по умолчанию для синхронизации и общих операций.
- `include: "yaml"` возвращает только YAML-файлы проекта. Этот режим используется в validation.

## Поток данных

Новый discovery:

1. Рекурсивно обходит `projectDir`.
2. Пропускает служебные и явно нерелевантные директории, если такие уже есть в проектных соглашениях.
3. Для каждого файла вызывает `classifyMetadataProjectPath(projectPath)`.
4. Отбрасывает неизвестные пути.
5. Применяет `include`-фильтр.
6. Сортирует результат по `projectPath`, как сейчас.

`classifyMetadataProjectPath` остается центральной точкой принятия решения, является ли путь проектным ресурсом.

## Validation

`prepareYamlProjectWithPool` для validation должен вызывать discovery в режиме `include: "yaml"`.

Это означает:

- validation не ищет модули, картинки, макеты и прочие внешние файлы на этапе подготовки YAML;
- worker получает только YAML-файлы;
- проверки, которым нужны ссылки на внешние файлы, должны опираться на отдельные YAML-факты и специализированные проверки, а не на полный список `resourceFiles` из общей подготовки.

## Синхронизация и другие операции

Синхронизация в XML и общие операции подготовки проекта продолжают использовать `include: "all"`, чтобы видеть:

- YAML-файлы метаданных;
- модули;
- макеты;
- картинки;
- другие внешние файлы, описанные через `rules.ts`.

Семантика результата должна остаться совместимой с текущими тестами `resourceFiles`.

## Ошибки и неизвестные файлы

Неизвестные файлы не являются ошибкой discovery. Они просто не попадают в результат, как и сейчас не попадали бы, если для них нет project resource-правила.

Ошибки чтения директорий должны вести себя так же, как текущий синхронный обход: если проектная директория недоступна, операция падает с ошибкой файловой системы.

## Тестирование

Нужно покрыть:

- `discoverMetadataProjectResources(projectDir, { include: "yaml" })` возвращает только YAML-файлы;
- `discoverMetadataProjectResources(projectDir, { include: "all" })` возвращает YAML и прочие resource-файлы;
- recursive `Свойства.yaml` находится через общий обход без отдельного второго прохода;
- `prepareYamlProjectWithPool` для validation не передает прочие resource-файлы в подготовку;
- существующие тесты синхронизации и подготовки проекта сохраняют совместимость.

## Проверка производительности

После реализации нужно запустить:

```bash
pnpm --filter @nkdk/core build
node .agents/skills/validation-profile/validation-profile.mjs /Users/nikita/git/nkdk-yaml --runs 1 --timing
```

Ожидаемый эффект: снижение времени шага `Поиск файлов проекта` за счет удаления массовых `existsSync + statSync` по несуществующим кандидатам.

## Не входит в задачу

- Чтение YAML на этапе discovery.
- Исправление validation diagnostics.
- Изменение модели worker validation.

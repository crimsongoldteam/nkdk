# Русские ссылки на объекты метаданных в YAML

## Порядок принятия решений

Случаи рассматриваются по одному. Для каждого поля отдельно фиксируется допустимая форма ссылки в YAML.

## Принятые решения

### Отложенные случаи

`ИмяМетода` регламентного задания вида `CommonModule.<ИмяМодуля>.<ИмяМетода>` не входит в текущую реализацию. Поле требует индекса исходного кода общих модулей и их доступных экспортных методов; до появления такого индекса платформенная форма сохраняется без перевода. Ограничение также зафиксировано в `.agents/restrictions.md`.

`Обработчик` подписки на событие вида `CommonModule.<ИмяМодуля>.<ИмяМетода>` также не входит в текущую реализацию. Это ссылка на код общего модуля, поэтому до появления индекса модулей и экспортных методов платформенная форма сохраняется без перевода и смысловой проверки. Ограничение также зафиксировано в `.agents/restrictions.md`.

`ИмяКоманды` элемента управляемой формы не входит в текущую реализацию. Все платформенные формы команды сохраняются без перевода и смысловой проверки до отдельного проектирования составной цели команды формы. Ограничение также зафиксировано в `.agents/restrictions.md`.

Ссылки на группы команд, включая `CommandGroup.<Имя>`, не входят в текущую реализацию и сохраняются в платформенной форме без перевода и смысловой проверки. Они будут проектироваться вместе с командами и командным интерфейсом. Ограничение также зафиксировано в `.agents/restrictions.md`.

### Общее правило кратких ссылок

Для всех полей и ключей отображений действует единое правило: если декларация допустимых целей разрешает ровно один тип объектов метаданных, YAML должен содержать краткое имя без префикса типа. Правило задаётся существующим декларативным механизмом допустимых целей и не реализуется отдельными преобразованиями для конкретных объектов или полей.

### `ФункциональныеОпции`

Исходное представление:

```yaml
ФункциональныеОпции:
  - FunctionalOption.ФункциональнаяОпцияБулево
```

Целевое представление:

```yaml
ФункциональныеОпции:
  - ФункциональнаяОпцияБулево
```

Поле декларативно ограничивается ссылками на `FunctionalOption`, поэтому применяется общее правило кратких ссылок.

### `Размещение` функциональной опции

Исходные представления:

```yaml
Размещение: Constant.КонстантаБулево
Размещение: Catalog.СправочникПолный.Attribute.РеквизитСправочника
Размещение: InformationRegister.ЗначенияХарактеристикОбъектов.Resource.Значение
```

Целевые представления:

```yaml
Размещение: Константа.КонстантаБулево
Размещение: Справочник.СправочникПолный.Реквизит.РеквизитСправочника
Размещение: РегистрСведений.ЗначенияХарактеристикОбъектов.Ресурс.Значение
```

Поле обязательно и допускает ровно три вида целей:

- константу;
- непосредственный реквизит справочника;
- непосредственный ресурс регистра сведений.

Тип значения цели не ограничивается. В частности, `Булево` требуется для использования функциональной опции в автоматическом управлении интерфейсом, но не является ограничением свойства `Размещение`.

Ограничение выражается существующим `metadataTarget` как объединение точных путей объекта и членов: объект `Constant`, член `Catalog → Attribute` и член `InformationRegister → Resource`. Отдельный обработчик функциональной опции не нужен.

### `Роли`

Исходное представление:

```yaml
Роли:
  Role.Администратор: Ложь
```

Целевое представление:

```yaml
Роли:
  Администратор: Ложь
```

Ключи отображения декларативно ограничиваются ссылками на `Role`, поэтому к ним применяется общее правило кратких ссылок.

### `ФормаВыбора` реквизита

Исходное представление:

```yaml
ФормаВыбора: Catalog.СправочникРеквизит.Form.ФормаВыбора
```

Целевое представление:

```yaml
ФормаВыбора: ФормаВыбора
```

Допустимые значения зависят от типа реквизита:

- для реквизита с одним ссылочным типом разрешены только формы выбора объекта этого типа;
- владелец формы однозначно восстанавливается из типа реквизита, поэтому YAML содержит краткое имя формы;
- для реквизита с составным типом свойство `ФормаВыбора` недоступно и не должно присутствовать в YAML.

Ограничение должно быть описано декларативно через тип реквизита и допустимые цели метаданных.

### `ОсновнаяТаблица` динамического списка

`ОсновнаяТаблица` — ссылка не просто на объект метаданных, а на доступную динамическому списку физическую или виртуальную таблицу. Поле допускает разные типы объектов, поэтому краткая форма без типа здесь неоднозначна. Английские корни объектов и имена виртуальных таблиц должны заменяться русскими именами.

На этом этапе `ПроизвольныйЗапрос: Истина` не запрещает присутствие `ОсновнаяТаблица`. Если поле указано, его значение проходит обычное разрешение и проверку `dataTable` независимо от режима запроса.

Английская форма ссылки в YAML не поддерживается как совместимый псевдоним. Значения вида `Catalog.СправочникПолный` должны отклоняться проверкой; допустима только русская форма. XML при этом продолжает использовать канонические английские имена платформы.

Пример преобразования:

```yaml
ОсновнаяТаблица: Задача.ЗадачаВсеСвойства
```

Полный набор образцов находится в `e2e/fixtures/xml/cf/CommonForms/ДинамическийСписокОсновнаяТаблица/Ext/Form.xml`.

Допустимые основные таблицы:

- `КритерийОтбора.<Имя>`;
- `ПланОбмена.<Имя>`;
- `Константа.<Имя>`;
- `Справочник.<Имя>`;
- `Документ.<Имя>`;
- `ЖурналДокументов.<Имя>`;
- `Перечисление.<Имя>`;
- `ПланВидовХарактеристик.<Имя>`;
- `ПланСчетов.<Имя>`;
- `ПланВидовРасчета.<Имя>`;
- `РегистрСведений.<Имя>`;
- `РегистрНакопления.<Имя>`;
- `РегистрБухгалтерии.<Имя>`;
- `РегистрРасчета.<Имя>`;
- `БизнесПроцесс.<Имя>`;
- `Задача.<Имя>`;
- вложенные таблицы, кубы и таблицы измерений внешнего источника данных. Сам объект внешнего источника основной таблицей быть не может.

Допустимые формы для внешнего источника:

```yaml
ОсновнаяТаблица: ВнешнийИсточникДанных.<Источник>.Куб.<Куб>
ОсновнаяТаблица: ВнешнийИсточникДанных.<Источник>.Куб.<Куб>.ТаблицаИзмерения.<ТаблицаИзмерения>
ОсновнаяТаблица: ВнешнийИсточникДанных.<Источник>.Таблица.<Таблица>
```

Виртуальные таблицы разрешаются только при выполнении условий владельца:

- `РегистрСведений.<Имя>.СрезПервых` и `.СрезПоследних` — только для периодического регистра сведений. `РазрешитьИтогиСрезПервых` и `РазрешитьИтогиСрезПоследних` создают физические таблицы итогов и влияют на способ выполнения запроса, но не определяют существование виртуальных таблиц;
- для регистра накопления вида `Обороты` разрешена виртуальная таблица `.Обороты`;
- для регистра накопления вида `Остатки` разрешены `.Остатки`, `.Обороты` и `.ОстаткиИОбороты`;
- для регистра бухгалтерии разрешены `.Остатки`, `.Обороты` и `.ОстаткиИОбороты`;
- `.ОборотыДтКт` регистра бухгалтерии разрешена при включённой корреспонденции;
- `.ДвиженияССубконто` и `.Субконто` регистра бухгалтерии разрешены при наличии у связанного плана счетов видов субконто;
- `РегистрРасчета.<ИмяОсновногоРегистра>.База<ИмяБазовогоРегистра>` разрешена, если у основного регистра включён базовый период, назначенный ему план видов расчёта зависит от базы по периоду действия или регистрации, а план видов расчёта базового регистра входит в список `Базовые планы видов расчёта` основного плана. Для каждого подходящего базового регистра существует отдельная виртуальная таблица;
- `РегистрРасчета.<Имя>.ДанныеГрафика` разрешена при поддержке периода действия и заданном графике. Графиком должен быть непериодический регистр сведений с измерением типа `Дата` и числовым ресурсом;
- `РегистрРасчета.<Имя>.ФактическийПериодДействия` разрешена при поддержке периода действия;
- `БизнесПроцесс.<Имя>.Точки` относится к таблице точек маршрута бизнес-процесса;
- для внешнего источника данных разрешены только реально объявленные вложенные объекты: `Куб`, `Таблица` и `ТаблицаИзмерения`.

#### Зависимости доступности виртуальных таблиц

В таблице указаны YAML-реквизиты, из которых декларативно выводится точный набор целей `dataTable`. Отсутствующий в YAML реквизит учитывается с его стандартным неявным значением.

| Виртуальная таблица | Реквизиты и условие доступности |
|---|---|
| `РегистрСведений.<Имя>.СрезПервых` | `Периодичность` регистра сведений не равна `Непериодический`. `РазрешитьИтогиСрезПервых` на доступность не влияет. |
| `РегистрСведений.<Имя>.СрезПоследних` | `Периодичность` регистра сведений не равна `Непериодический`. `РазрешитьИтогиСрезПоследних` на доступность не влияет. |
| `РегистрНакопления.<Имя>.Обороты` | Доступна при обоих значениях `ВидРегистра`: `Обороты` и `Остатки`. |
| `РегистрНакопления.<Имя>.Остатки` | `ВидРегистра: Остатки`. |
| `РегистрНакопления.<Имя>.ОстаткиИОбороты` | `ВидРегистра: Остатки`. |
| `РегистрБухгалтерии.<Имя>.Остатки` | Доступна для любого регистра бухгалтерии; условного реквизита нет. |
| `РегистрБухгалтерии.<Имя>.Обороты` | Доступна для любого регистра бухгалтерии; условного реквизита нет. |
| `РегистрБухгалтерии.<Имя>.ОстаткиИОбороты` | Доступна для любого регистра бухгалтерии; условного реквизита нет. |
| `РегистрБухгалтерии.<Имя>.ОборотыДтКт` | `Корреспонденция: Истина`. |
| `РегистрБухгалтерии.<Имя>.Субконто` | `ПланСчетов` регистра разрешается в план счетов, у которого `МаксКоличествоСубконто > 0`. |
| `РегистрБухгалтерии.<Имя>.ДвиженияССубконто` | `ПланСчетов` регистра разрешается в план счетов, у которого `МаксКоличествоСубконто > 0`. |
| `РегистрРасчета.<Основной>.База<Базовый>` | У основного регистра `БазовыйПериод: Истина`; его `ПланВидовРасчета` разрешается в план, у которого `ЗависимостьОтВидовРасчета` не равна отсутствию зависимости и `БазовыеВидыРасчета` содержит план, указанный в `ПланВидовРасчета` базового регистра. Отдельная цель создаётся для каждого такого базового регистра. |
| `РегистрРасчета.<Имя>.ДанныеГрафика` | У регистра `ПериодДействия: Истина`; заполнены `График`, `ДатаГрафика` и `ЗначениеГрафика`; `График` указывает на непериодический регистр сведений, `ДатаГрафика` — на его измерение типа `Дата`, `ЗначениеГрафика` — на его числовой ресурс. |
| `РегистрРасчета.<Имя>.ФактическийПериодДействия` | `ПериодДействия: Истина`. |
| `БизнесПроцесс.<Имя>.Точки` | Доступна для каждого бизнес-процесса; условного реквизита нет. |

Условия, затрагивающие только владельца, вычисляются из локальных фактов его файла. Условия с `ПланСчетов`, `ПланВидовРасчета`, базовым регистром или регистром графика вычисляются по ссылкам в общем индексе проекта. Результат в обоих случаях — обычная точная цель `dataTable`, а не отдельная проверка поля формы.

Преобразование должно быть обратимым: русские имена используются только в YAML, а при восстановлении XML возвращаются канонические английские сегменты платформы (`SliceFirst`, `BalanceAndTurnovers`, `RecordsWithExtDimensions` и другие).

#### Единый механизм ограничений таблиц

Ссылки на физические, вложенные и виртуальные таблицы описываются одним расширением стандартного механизма `metadataTarget`:

- в `MetadataTargetConstraint` и `ParsedMetadataTarget` добавляется самостоятельный вид цели `dataTable`;
- `ОсновнаяТаблица` объявляется обычным строковым свойством с `metadataTarget: { kind: "dataTable", roots: [...] }` и не получает отдельного обработчика проверки или преобразования;
- все допустимые варианты представляются одинаковыми записями индекса таблиц: основная физическая таблица объекта, вложенная таблица внешнего источника и виртуальная таблица различаются данными цели, но проходят один разбор, форматирование, разрешение и проверку;
- предметные модули декларативно публикуют доступные таблицы своих объектов. Общий runtime знает только устройство цели `dataTable` и индекса, но не содержит условий для конкретных регистров или других типов метаданных;
- локальные условия вычисляются из фактов владельца, а условия со связями между объектами — после объединения фактов проекта. В обоих случаях результатом является тот же набор точных целей `dataTable`;
- XML-имена и русские YAML-имена сегментов задаются в едином каталоге вариантов таблиц. Этот каталог используется и при XML → YAML, и при YAML → XML, поэтому отдельные таблицы преобразований для формы не создаются;
- проверка ссылки сводится к наличию точной цели в общем индексе. Произвольный суффикс виртуальной таблицы не принимается;
- структурные ссылки, поиск ссылок и переименование используют стандартный путь `metadataTarget`, поэтому имя объекта-владельца и имя базового регистра внутри `База<ИмяБазовогоРегистра>` участвуют в операциях над ссылками;
- JSON Schema описывает русскую форму таблицы и допустимые корни, а существование конкретного объекта и условно доступной виртуальной таблицы проверяется по индексу проекта.

Реестр предметных деклараций таблиц собирается в `metadata/composition`. Модуль форм зависит только от общего контракта `dataTable` и не импортирует applied objects; нейтральные слои не содержат проверок по конкретным `itemType`.

### Описание характеристик

Для блока `Характеристики` на этом этапе реализуется только смысловое преобразование ссылок и имён в русскую YAML-форму и обратно. Ограничения доступности таблиц и полей, проверка их типов и межполевой совместимости не входят в задачу.

- `ВидыХарактеристик` и `ЗначенияХарактеристик` преобразуются как ссылки на таблицы данных;
- `ПолеКлюча`, `ПолеОтбораВидов`, `ПолеПутиКДанным` и `ПолеИспользованияМножественныхЗначений` преобразуются как поля таблицы `ВидыХарактеристик`;
- `ПолеОбъекта`, `ПолеВида`, `ПолеЗначения`, `ПолеКлючаМножественныхЗначений` и `ПолеПорядкаМножественныхЗначений` преобразуются как поля таблицы `ЗначенияХарактеристик`;
- `ЗначениеОтбораВидов` преобразуется существующим механизмом значений и ссылок без дополнительной проверки соответствия типу `ПолеОтбораВидов`.

Ссылки на служебные отрицательные значения платформы (`-1`, `-8` и аналогичные) сохраняются без перевода и не разрешаются как ссылки на метаданные.

### Дополнительные индексы (отложено)

Преобразование и проверка `Таблица`, `ИндексируемыеПоля` и `ДополнительныеПоля` не входят в текущую реализацию. Все три поля сохраняют платформенные английские значения без смысловой проверки, включая стандартные таблицы планов видов расчёта. Ограничение зафиксировано в `.agents/restrictions.md`; проектирование будет продолжено после исследования полного состава и индексируемости полей таблиц.

<!-- Отложенное проектирование

`Таблица` дополнительного индекса использует тот же вид цели `dataTable`, что и `ОсновнаяТаблица` динамического списка, но с областью текущего объекта. Допустимы только его основная таблица, его табличная часть либо доступная ему виртуальная таблица. Таблица другого объекта не допускается.

`ИндексируемыеПоля` и `ДополнительныеПоля` содержат поля выбранной `Таблицы`. Пользовательские поля сохраняют свои имена, а платформенные имена стандартных полей переводятся в русскую YAML-форму и обратно, например `Ref` ↔ `Ссылка`, `Date` ↔ `Дата`, `DeletionMark` ↔ `ПометкаУдаления`.

```yaml
ДополнительныеИндексы:
  - Имя: Индекс1
    Таблица: Задача.ЗадачаВсеСвойства
    ИндексируемыеПоля:
      - Ссылка
      - РеквизитХранилище
    ДополнительныеПоля:
      - Дата
```

Оба списка ограничиваются полями выбранной таблицы. Нельзя смешивать поля разных источников, повторять поле в обоих списках, выбирать двоичные данные или строку неограниченной длины. `ДополнительныеПоля` могут отсутствовать или быть пустыми. Порядок `ИндексируемыхПолей` значим; дополнительные поля являются включёнными колонками и не входят в ключ индекса. Общий предел платформы — 16 физических колонок, поэтому число элементов YAML само по себе недостаточно для проверки предела у составных типов.

Преобразование и ограничение реализуются расширением общего механизма `metadataTarget`, без специальных `fromXML`/`toXML` для дополнительных индексов:

- в `MetadataTargetConstraint` добавляется общий вид `dataTableField` с декларативной зависимостью `tableProperty: "table"`;
- правило `Таблица` использует `metadataTarget: { kind: "dataTable", owner: "this" }`;
- правила `ИндексируемыеПоля` и `ДополнительныеПоля` используют `metadataTarget: { kind: "dataTableField", tableProperty: "table" }`;
- общий обработчик `metadataTarget` применяется к каждому элементу массивного свойства, поэтому существующий `IndexField` перестаёт самостоятельно отвечать за смысловое преобразование имён;
- цель `dataTable` публикует точный набор своих полей: пользовательские поля, применимые стандартные поля и сведения о типе, необходимые для ограничения индексируемости;
- единый каталог русских и внутренних имён стандартных членов используется и для полей таблиц; отдельная таблица псевдонимов дополнительных индексов не создаётся;
- разбор, форматирование, JSON Schema, индекс ссылок и проверка существования поля используют общий путь `metadataTarget`;
- зависимые правила уровня элемента `AdditionalIndexItem` проверяют отношения между свойствами: поле не повторяется между двумя списками, все цели разрешены через выбранную таблицу, а вычислимое число физических колонок не превышает платформенный предел;
- если число физических колонок нельзя достоверно вывести из описания типа, проверка предела не выдаёт ложную ошибку; остальные ограничения продолжают проверяться.

## Ошибки и проверка

Неразрешимая русская ссылка и недоступная условная виртуальная таблица обрабатываются существующим механизмом диагностики `metadataTarget`. Произвольные английские ссылки не принимаются как совместимая YAML-форма. Отложенные случаи из раздела выше, дополнительные индексы и служебные отрицательные значения блока `Характеристики` исключены из этого правила и сохраняются без перевода.

Реализация защищается тестами на самом узком стабильном уровне согласно `.agents/testing.md`:

- табличными тестами общего разбора и форматирования кратких ссылок, `dataTable` и `dataTableField`;
- предметными тестами деклараций доступных физических, вложенных и виртуальных таблиц, включая каждое условие появления виртуальной таблицы;
- тестами rules.ts для `ФункциональныеОпции`, ключей `Роли`, `Размещение`, `ФормаВыбора`, `ОсновнаяТаблица` и блока `Характеристики`;
- интеграционными XML → YAML → XML случаями только для договоров между слоями: русская каноническая YAML-форма, обратное восстановление платформенных сегментов и сохранение служебных отрицательных значений;
- проверками ссылок и переименования для владельцев таблиц, их полей и имени базового регистра внутри виртуальной таблицы расчёта.

Существующие XML-фикстуры остаются источником истины и не редактируются реализацией. Если для наблюдаемого договора недостаточно существующего примера, добавляется отдельный тестовый YAML либо новая минимальная фикстура без изменения имеющейся XML.

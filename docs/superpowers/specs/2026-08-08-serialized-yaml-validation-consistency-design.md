# Согласованность validation сериализованного YAML

## Контекст

Импорт XML использует общий модуль локальной validation, но передаёт ему объект, полученный непосредственно из XML. Такой объект ещё может содержать транспортные значения YAML, например `ExplicitYAMLString`. После сериализации и последующего разбора то же значение становится обычной строкой.

Из-за этого общий валидатор получает разные смысловые данные для одного файла:

- обычная validation разбирает записанный текст YAML;
- import передаёт исходный объект с транспортными значениями.

JSON Schema воспринимает `ExplicitYAMLString` как объект и создаёт ложные diagnostics о неверном типе и отсутствующих свойствах. Те же данные используются дополнительными локальными проверками и извлечением сведений индекса. На контрольном проекте import вернул 5 903 diagnostics, а чистая validation записанных файлов после удаления снимка — 68.

Существующий проект универсального пула worker правильно требует общих модулей import и validation, но ошибочно считает объект, полученный из XML, готовым смысловым представлением YAML. Договор нужно уточнить без повторного чтения и разбора записанного файла.

## Цель

Diagnostics import должны совпадать с результатом чистой validation тех же записанных байтов. Import и обычная validation должны использовать один конвейер JSON Schema, локальных проверок, извлечения ссылок и построения индекса.

## Не входит в задачу

- изменение правил JSON Schema или состава содержательных diagnostics;
- подавление отдельных ошибок `ExplicitYAMLString` внутри схем;
- изменение этапа Б5 или правил видимости ссылок компонентов;
- повторное чтение записанного YAML с диска;
- повторный разбор сериализованного текста во время import;
- изменение двоичного формата состояния проекта.

## Архитектурная граница

YAML-модуль через `serializeYAMLDocument` формирует неделимый сериализованный документ:

```ts
interface SerializedYAMLDocument {
  readonly text: string
  readonly data: unknown
}
```

`text` — окончательный текст YAML. `data` — смысловые данные, которые обычный YAML-парсер вернул бы для этого текста. Оба значения создаются одной операцией из одного исходного объекта и не принимаются независимо от вызывающего кода.

Потоки сходятся перед общим валидатором:

```text
Обычная validation:
байты → текст → YAML-парсер ───────────────┐
                                           ├→ ParsedYaml → общий локальный validator
Import:                                    │
объект XML → сериализованный YAML-документ ┘
```

Metadata-validation не знает о `ExplicitYAMLString` и других транспортных деталях сериализации. Знание о них остаётся внутри YAML-модуля.

## Сериализация

Общий обход сериализации одновременно строит:

- печатное представление для `js-yaml` и последующего формирования `text`;
- смысловое `data` для validation.

Для `ExplicitYAMLString("001")` печатное представление обеспечивает YAML-строку `"001"`, а смысловое представление содержит обычную строку `"001"`. Для отсутствующих свойств, `undefined` в массивах и зарегистрированных YAML-тегов смысловое представление должно соответствовать результату штатного парсера.

Публичный `exportToYAML` остаётся тонкой оболочкой и возвращает только `text`. Import использует расширенный результат сериализации, добавляет к нему `bytes`, хэш и описание целевого файла.

## Локальная validation

Опасный интерфейс `validateKnownProjectYaml({ text, yaml })`, позволяющий передать несогласованную пару, заменяется на `validateSerializedProjectYaml`, принимающий сериализованный YAML-документ одним параметром. Старый интерфейс удаляется.

Оба входных пути создают одинаковый `ParsedYaml` и далее вызывают существующий `validateProjectFileFirstPass`. Общими остаются:

- JSON Schema;
- дополнительные локальные проверки;
- проверка одинаковых имён;
- извлечение YAML-фактов;
- построение ссылок и сведений индекса.

Отдельный validator или отдельные правила для import не создаются.

## Простые и ссылочные значения

JSON Schema проверяет допустимую форму любого значения. Для ссылочной строки локальный проход дополнительно извлекает отложенную ссылку. Этап Б5 проверяет её существование и видимость по окончательному индексу проекта.

После приведения `ExplicitYAMLString` к смысловой строке поток выглядит так:

```text
ExplicitYAMLString("Справочник.Контрагенты")
  → data: "Справочник.Контрагенты"
  → JSON Schema принимает строку
  → локальный проход извлекает ссылку
  → Б5 проверяет ссылку по окончательному индексу
```

Простые значения завершают содержательную проверку на локальном этапе. Исправление первого этапа не скрывает настоящие ошибки Б5.

## Ошибки и публикация состояния

Если сериализация не может сформировать согласованный документ, import считает это технической ошибкой задания и не публикует его незавершённый вклад состояния.

Если сериализация успешна, содержательные diagnostics не отменяют запись YAML. Сохраняется действующий договор import: файл записывается, diagnostics возвращаются пользователю, а технически согласованное состояние проекта публикуется.

Запасного пути с передачей исходного `prepared.yaml` в validator нет.

## Изменение архитектурного описания

В `.agents/architecture.md` формулировка «проверяет тот же объект без повторного чтения и разбора файла» уточняется:

> Import проверяет смысловые данные, сформированные одновременно с окончательным текстом YAML. Повторное чтение и разбор текста не выполняются.

Остальные границы универсального пула worker, ранняя запись YAML, ограничение памяти и общий двоичный накопитель не меняются.

## Проверка решения

### Договор YAML-слоя

Для представительных значений проверяется равенство:

```ts
expect(serializeYAMLDocument(source).data).toEqual(parseMetadataYaml(text).data)
```

Набор включает вложенные `ExplicitYAMLString`, пустые и похожие на числа строки, обычные scalar, `undefined` в объектах и массивах, а также зарегистрированные YAML-теги.

### Договор validation

Общий validator должен возвращать одинаковый результат для:

- сериализованного документа в import;
- файла, содержащего тот же `text`.

Тест использует настоящий объект import с `ExplicitYAMLString`, а не объект, заранее полученный YAML-парсером.

### Интеграционная проверка

Небольшой XML-import сравнивает свои diagnostics с последующей чистой validation записанного проекта после удаления `project-state.bin`.

Итоговая проверка на `/Users/nikita/git/sed_xml/cf` должна вернуть одинаковые 68 diagnostics во время import и при чистой validation `/Users/nikita/git/sed_nkdk`, включая `cfe/дкз`.

### Производительность

Профиль подтверждает, что import не читает записанный YAML и не разбирает сериализованный текст. Дополнительный смысловой результат строится в существующем обходе сериализации и не создаёт второго обхода предметной модели.

## Критерии готовности

- import и чистая validation одинаковых байтов возвращают одинаковые diagnostics;
- YAML-модуль гарантирует согласованность `text` и `data` договорными тестами;
- `ExplicitYAMLString` и другие транспортные значения не попадают в metadata-validation;
- используется один локальный validation-конвейер без правил и условий для import;
- ссылочные значения после локальной проверки корректно доходят до Б5;
- повторное чтение и разбор YAML во время import отсутствуют;
- итоговые тесты и профиль проходят установленные проектом проверки.

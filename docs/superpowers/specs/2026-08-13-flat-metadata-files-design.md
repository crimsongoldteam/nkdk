# Однофайловые объекты метаданных

## Цель

Не создавать отдельный каталог с `Свойства.yaml` для видов объектов, чьё
проектное представление всегда состоит ровно из одного YAML-файла. Такие
объекты хранятся непосредственно в каталоге вида:

```text
Нумератор/НумераторЗаказов.yaml
```

вместо:

```text
Нумератор/НумераторЗаказов/Свойства.yaml
```

## Границы

Плоское размещение включается для десяти видов:

- `ГруппаКоманд`;
- `Нумератор`;
- `ОбщийРеквизит`;
- `ОпределяемыйТип`;
- `ПараметрСеанса`;
- `ПараметрФункциональныхОпций`;
- `ПодпискаНаСобытие`;
- `ФункциональнаяОпция`;
- `ЭлементСтиля`;
- `Язык`.

`Константа` не входит в список: у неё могут быть `МодульМенеджера.bsl` и
`МодульМенеджераЗначения.bsl`, поэтому она не является строго однофайловой.

Совместимость со старым путём не поддерживается. Путь
`Вид/Имя/Свойства.yaml` для перечисленных видов не входит в топологию, не
импортируется, не проверяется и не синхронизируется. Автоматическая миграция и
удаление старых каталогов также не выполняются.

## Договор ProjectSpec

`RegisteredProjectSpec` получает явный режим размещения проектного файла.
Рекомендуемое имя поля — `projectLayout`, значения:

- `"objectDirectory"` — существующий режим по умолчанию с путём
  `Вид/{ownerName}/Свойства.yaml`;
- `"flatFile"` — новый режим с путём `Вид/{ownerName}.yaml`.

Поле необязательное; отсутствие означает `"objectDirectory"`, поэтому все
остальные виды сохраняют текущие пути без массового изменения регистраций.
Десять согласованных видов объявляют `projectLayout: "flatFile"` явно в своих
`ProjectSpec`. Режим нельзя выводить автоматически из текущего состава правил:
добавление нового свойства не должно молча менять структуру проекта.

XML-размещение не меняется. Например, `Нумератор/НумераторЗаказов.yaml`
по-прежнему соответствует `DocumentNumerators/НумераторЗаказов.xml`.

## Построение топологии

Общий построитель `describeProjectSpecResourceTopology` выбирает базовый путь
назначения по `projectLayout`:

- для `objectDirectory` — `${spec.dir}/{ownerName}/Свойства.yaml`;
- для `flatFile` — `${spec.dir}/{ownerName}.yaml`.

Все операции продолжают использовать скомпилированную топологию как единый
источник путей. Частные проверки по `itemType` или имени каталога в импорте,
проверке, индексах, состоянии проекта и синхронизации не добавляются.

Плоский режим допустим только для назначения, не создающего других проектных
ресурсов объекта. Компиляция топологии должна завершаться понятной ошибкой,
если правило с `projectLayout: "flatFile"` порождает хотя бы одно из следующего:

- дочернее YAML-назначение;
- YAML-спутник;
- внешний проектный файл.

XML-документ свойств объекта не считается дополнительным проектным файлом и
разрешён. Проверка выполняется после сбора деклараций конкретного
`ProjectSpec`, чтобы учитывать как свойства правила, так и явно заданные
`spec.resources`.

## Поток данных

При XML → YAML сопоставление XML сохраняет имя объекта в `ownerName`, а
проекция импорта подставляет его в плоский шаблон и записывает один YAML-файл.
При YAML → XML классификатор извлекает `ownerName` из имени YAML-файла, после
чего существующая подготовка прикладного объекта создаёт прежний XML-путь.

Проверка YAML, построение индекса, состояние проекта, определение влияния
изменений и частичная синхронизация получают новое размещение через то же
назначение топологии. Их предметная логика и модель владельца не меняются.

## Ошибки и ограничения

- Старый путь не классифицируется как metadata-файл. Специальная диагностика
  совместимости не добавляется.
- Конфликт плоского режима с дополнительным проектным ресурсом выявляется при
  компиляции топологии до выполнения операции.
- Имя объекта продолжает проходить существующие правила допустимого сегмента
  пути; расширение `.yaml` является частью шаблона, а не имени объекта.
- Архитектурный файл `.agents/architecture.md` менять не требуется: принятый
  принцип единой топологии сохраняется, меняется только декларативный договор
  размещения одного назначения.

## Проверки

1. Узкий тест построителя подтверждает новый шаблон для `flatFile` и прежний
   шаблон для режима по умолчанию.
2. Узкий тест подтверждает отказ компиляции при дочернем YAML, YAML-спутнике
   или внешнем проектном файле у плоского вида.
3. Табличный тест зарегистрированной топологии проверяет все десять путей
   `Вид/{ownerName}.yaml` и отсутствие их прежних назначений.
4. Сквозной представитель XML → YAML подтверждает запись плоского файла.
5. Сквозной представитель YAML → XML подтверждает чтение плоского файла и
   сохранение прежнего XML-пути.
6. Существующие тестовые YAML-пути для десяти видов переводятся на новый
   договор. Существующие XML-фикстуры не изменяются.
7. Итоговая проверка включает `pnpm type-check`, `pnpm test`,
   `pnpm test:architecture:rules`, `pnpm test:architecture` и
   `pnpm duplicates -- --base origin/develop`.

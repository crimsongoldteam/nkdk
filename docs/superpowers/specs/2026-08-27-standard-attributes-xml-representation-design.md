# Точный XML round-trip оставшихся непредметных различий

## Контекст

`StandardAttributes` может присутствовать в XML, даже если каждый стандартный
реквизит содержит только значения по умолчанию. Такой блок не несёт предметных
настроек и после импорта превращается в пустое смысловое значение. При этом
отсутствующий блок и присутствующий полностью стандартный блок должны
восстанавливаться по-разному.

Действующий импорт осмысленно исключает оба варианта из обычного YAML. Для
нескольких e2e-фикстур последующее исчезновение присутствующего блока было
признано допустимой канонизацией через список конкретных XML-файлов. На большой
конфигурации тот же дефект проявился в сотнях файлов: правила восстановили
смысл, но не исходное присутствие XML-узла.

Поддержанный XML должен проходить `XML -> YAML -> XML` без потерь. E2E не имеет
права скрывать расхождения списками допустимых файлов или строк diff.

## Цель

Сохранить присутствие полностью стандартного `StandardAttributes` кратким
тегом формы XML, не выводя в YAML значения по умолчанию и не сохраняя полный
XML-снимок.

## YAML-договор

### Блок отсутствует

Поле отсутствует в YAML:

```yaml
ТабличныеЧасти:
  История:
    Синоним: История
```

### Блок присутствует и полностью стандартный

Импорт записывает:

```yaml
ТабличныеЧасти:
  Исполнители:
    СтандартныеРеквизиты: !xml/standard-attributes
```

Тег означает только: «создать канонический блок стандартных реквизитов этого
владельца». Он не является предметным значением и не содержит XML.

### Есть предметные изменения

YAML хранит только изменённые свойства обычным способом:

```yaml
СтандартныеРеквизиты:
  Дата:
    ПроверкаЗаполнения: ВыдаватьОшибку
```

Существующий `completeItemNames` дополняет экспорт остальными каноническими
стандартными реквизитами.

## Семантика тега

`!xml/standard-attributes` является зарегистрированным тегом формы XML, как
`!xml/string`, а не XML-аномалией:

- не подавляет диагностики;
- не содержит `$xml` и не участвует в механизме `!xml/raw`;
- не добавляет предметного значения в модель;
- допустим только для точного типа свойства `StandardAttributeDescriptions`;
- не имеет payload;
- при экспорте требует непустой канонический список стандартных реквизитов
  владельца и строит обычный XML через существующие rules.

Любое применение тега к другому типу свойства, тег с payload или невозможность
получить канонический состав является ошибкой YAML.

## Импорт

Обработчик `StandardAttributeDescriptions` сначала выполняет обычный смысловой
импорт.

- Непустой результат остаётся обычным YAML.
- Полностью стандартный присутствующий блок, который без дополнительной
  отметки исчезнет при обычном экспорте, получает
  `!xml/standard-attributes`.
- Если обычный экспорт и без отметки точно восстанавливает блок, лишний тег не
  создаётся.
- Отсутствующий блок не создаёт поле.
- Неизвестный реквизит, неизвестное свойство или иное необратимое отличие не
  сворачивается в тег и продолжает обрабатываться общим proof/raw-механизмом.

Решение о теге подтверждается существующим контрольным экспортом: краткое
представление допустимо только тогда, когда rules действительно восстанавливают
исходный блок. Частных списков владельцев или файлов в импорте не появляется.

## Экспорт

При встрече `!xml/standard-attributes` обработчик использует тот же путь
`StandardAttributeDescriptions`, что и обычное непустое значение, но запускает
его с пустым смысловым отображением и обязательной материализацией
`completeItemNames`.

Экспорт не читает reference XML и не применяет сохранённый `$xml`: состав,
значения и порядок полностью выводятся из действующих rules владельца.

## E2E

Проверка XML round-trip для каждого компонента требует:

```text
equal: true
added: []
removed: []
changed: []
```

Из e2e удаляются:

- `CANONICAL_STANDARD_ATTRIBUTE_ELISIONS`;
- `CANONICAL_LINE_NUMBER_DIFF_LINES`;
- специальная функция, принимающая эти расхождения;
- любая ветка сравнения, разрешающая отдельный результат для `cf`.

Списки ожидаемых YAML-тегов могут проверять форму результата, но не могут
разрешать расхождение восстановленного XML с исходным.

## Порядок смешанных элементов формы

В формах обычные rules уже восстанавливают смысловые `ChildItems` в исходном
порядке. Однако частичная `!xml/raw`-поправка может содержать дочерние элементы,
сгруппированные по XML-имени: сначала все `Button`, затем `ButtonGroup`. Это
техническая форма mapping, а не указание переставить элементы.

Порядок, построенный обычным экспортом, является основным. Частичная
XML-поправка не имеет права менять его только из-за порядка ключей mapping.
Изменять порядок существующих XML-sibling разрешено исключительно явным
терминалом `#order`.

Это правило действует для любого смешанного XML-содержимого, не только для
`ChildItems` формы. Поправка по-прежнему может добавлять, удалять и изменять
узлы; новые узлы размещаются общим механизмом raw-границ, а существующие
сохраняют взаимный порядок обычного экспорта.

## Отсутствующий вычисляемый RowFilter

Для некоторых таблиц rules вычисляют канонический
`<RowFilter xsi:nil="true"/>`, даже когда в исходном XML узел отсутствовал.
Отсутствие и пустой `RowFilter` являются разной формой XML и должны
восстанавливаться точно.

Предметного свойства в YAML для этого не появляется. Общий proof отсутствующих
узлов обязан создать минимальную локальную отметку:

```yaml
"@Form\\ОтборСтрок": !xml/raw
  $xml: null
```

Это не частное правило таблицы: любой отсутствующий XML-узел, который обычный
экспорт собирается добавить по вычисляемому значению по умолчанию, проходит тот
же договор planned absence. Подробный повторный импорт для proof должен
выполнять те же стадии уточнения отложенных значений и путей формы, что и
основной второй проход; иначе proof сравнивает не тот обычный экспорт.

Например, минимальная форма без `<Attributes>` получает аналогичную локальную
отметку `"@Form\\Реквизиты": !xml/raw` с `$xml: null`: обычный экспорт формы
создаёт пустой контейнер, но точный round-trip обязан сохранить его отсутствие.

## Явная строка, похожая на ссылку метаданных

`xs:string` может содержать текст, синтаксически похожий на ссылку, например:

```yaml
Значение: "Перечисление.ВидыКорреспонденции.Входящая"
```

Кавычки являются достаточной стандартной YAML-формой. Новый тег и `!xml/raw`
не нужны. Служебная отметка явной строки должна сохраняться при каждом
копировании, нормализации и подстановке дерева во время import proof. Тогда
повторный экспорт восстанавливает `xsi:type="xs:string"`. Такое же значение без
отметки явной строки продолжает распознаваться как ссылка метаданных и
восстанавливается как `xr:DesignTimeRef`.

## Общий proof

`semanticallyElided` означает только отсутствие предметного YAML. Оно больше не
является разрешением потерять присутствующий XML-узел. Контрольный экспорт
обязан либо:

1. точно восстановить узел обычными rules;
2. получить зарегистрированное краткое представление формы XML;
3. создать минимальный `!xml/raw` с явным `$xml` для действительно
   невосстанавливаемого случая.

Присутствующий полностью стандартный `StandardAttributes` выбирает второй
вариант. Это правило не зависит от имени владельца или XML-файла.

## Минимальная область `!xml/raw`

Диагностический round-trip `cf/doc` точно восстановил XML, но выявил слишком
широкую локализацию непредметных отличий. Из 10 170 тегов `!xml/raw` 303 блока
занимали больше 50 строк, а 155 — больше 100 строк. Все блоки больше 50 строк
приходились на целые `КоманднаяПанель` или `КонтекстноеМеню`; максимальный блок
занимал 1 259 строк. Кроме того, 8 532 коротких raw находились по адресам
`ExtendedTooltip`. Канонические пустые `ExtendedTooltip` среди них должны
полностью восстанавливаться rules без следа в YAML; реальные неканонические
отличия должны получать минимальный raw только на собственной границе.

Точный XML round-trip сам по себе недостаточен: `!xml/raw` обязан сохранять
только минимальное отличие, которое нельзя вывести из смыслового YAML, rules и
индексов конфигурации. Объект с зарегистрированными вложенными rules нельзя
целиком превращать в raw, если отличие можно связать с его свойством,
дочерним элементом или структурным терминалом.

### Единая карта соответствий

Обычный импорт, контрольный экспорт и локализация raw используют одну
составленную из rules карту:

```text
XML-узел ↔ rule ↔ логический адрес ↔ YAML-узел
```

Отдельные эвристики для форм, командных панелей, контекстных меню и других
common-объектов запрещены. Повторяющиеся элементы сопоставляются тем же
механизмом, что и fromXML/toXML: по правилу элемента, логическому имени и
внутренней привязке конкретного экземпляра. Если смысловые имена повторяются,
используется существующая внутренняя привязка импорта, а не публичный XML `id`
и не новый селектор raw.

Нейтральное описание адреса находится в runtime-слое. Конкретные metadata-rules
только публикуют сведения через существующую composition; общий сопоставитель
не знает имён metadata-типов и XML-папок.

### Атомарное сравнение и локализация

Сравнение исходного и контрольного XML выдаёт атомарные отличия:

- значение или форма конкретного атрибута;
- текст конкретного узла;
- присутствие или отсутствие узла;
- порядок непосредственных соседей.

Для каждого отличия сопоставитель выбирает самую глубокую доступную границу из
единой карты. Несколько отличий объединяются только тогда, когда их невозможно
представить на разных более глубоких границах. Переход к родителю является
последовательным и объяснимым: результат хранит причину каждого подъёма.

Raw-патч повторяющейся XML-группы не заменяет массив целиком. Конкретный
экземпляр получает собственную границу через существующую привязку элемента.
Порядок является отдельным структурным терминалом `#order` минимальной
коллекции и не копирует содержимое её элементов.

### YAML-договор

Для произвольной XML-формы используется существующий `!xml/raw`. Узкие
зарегистрированные теги формы XML описываются отдельно и не заменяются raw:

- если отличается смысловое свойство, raw ставится на это свойство;
- если отличается только непредметное присутствие скрытого XML-узла, создаётся
  короткая локальная поправка на адресе этого узла;
- если отличается только порядок, `$xml` содержит только `#order`;
- канонические вычисляемые узлы, включая пустую `ExtendedTooltip`, не создают
  YAML;
- `id`, UUID, имена заимствованных объектов и другие сведения, сохраняемые
  индексами конфигурации, не записываются в raw.

Пример допустимой локальной поправки — отсутствие вычисляемого `RowFilter`:

```yaml
"@Form\\ОтборСтрок": !xml/raw
  $xml: null
```

Целая форма, реквизит, командная панель, контекстное меню или другой
rule-объект не может быть нормальным результатом локализации, пока внутри него
есть более глубокая адресуемая граница.

### Диагностика широкой области

Если сопоставитель не смог выбрать минимальную границу, импорт пока не
прерывается. Он сохраняет резервный широкий raw и создаёт диагностическое
сообщение `Слишком широкая область !xml/raw` со следующими данными:

- исходный XML-файл и XML-путь;
- выбранный YAML-путь;
- ближайшая найденная и ожидаемая более глубокая граница;
- причина невозможности сопоставления;
- размер созданного raw.

E2E не должен содержать таких диагностик. Сообщение предназначено для
обнаружения неполной топологии или дефекта общего сопоставителя, а не для
разрешения известного исключения.

## Нестандартное техническое имя singleton

Имя встроенного singleton элемента формы обычно однозначно выводится из имени
владельца и зарегистрированного набора суффиксов. Поэтому каноническое имя не
является предметным свойством и не выводится в YAML.

Если исходный XML использует другое имя, сохранять весь элемент через raw
избыточно. Для типов, явно зарегистрированных общим механизмом singleton,
импорт создаёт одно короткое поле:

```yaml
ОтображениеСтрокиПоиска:
  Имя: !xml/name ДеревоПодсистемSearchString
```

`!xml/name` является тегом формы XML, а не `XmlAnomalyKind`: он не содержит
`$xml`, не подавляет проверку и не добавляет имя в смысловую модель. Обычное
поле `Имя` без тега запрещено. Типы, не зарегистрировавшие явное XML-имя, также
не принимают этот тег.

Зарегистрированные варианты суффиксов образуют единое семейство имён. Если
верхний singleton использует `SearchString`, вложенные `ContextMenu` и
`ExtendedTooltip` получают английские суффиксы автоматически. Их имена не
дублируются в YAML. Произвольное имя, не принадлежащее известному семейству,
сохраняется точно; для его потомков используется канонический вариант, а
отличающийся потомок при необходимости получает собственный `!xml/name`.

Логический адрес и XML `id` singleton продолжают определяться каноническим
rules-адресом и индексом конфигурации. Техническое имя влияет только на
`name` экспортируемого XML-узла и на вычисление имён его вложенных singleton.
Reference XML и полный raw для этого не требуются.

### Производительность и память

Карта соответствий наполняется во время уже выполняемых fromXML и контрольного
toXML. Отдельный полный обход модели и копия XML-дерева для raw не создаются.
Сравнение удерживает атомарные отличия и адреса; полный XML-фрагмент кодируется
только после выбора окончательной минимальной границы.

Объём работы остаётся линейным от числа обработанных XML-узлов и найденных
отличий. Повторяющиеся элементы индексируются один раз и переиспользуются при
локализации всех отличий документа.

## Совместимость

Совместимость с YAML, созданным во время допустимой канонизации, не требуется.
Повторный импорт исходного XML создаёт новый тег. `!xml/raw` сохраняет прежний
договор и всегда требует явный `$xml`.

Эта спека заменяет решения о допустимом исчезновении полностью стандартных
коллекций из
`2026-08-25-semantic-xml-elision-design.md` и старое предложение использовать
для этой цели пустой `!xml` из
`2026-08-10-standard-attributes-xml-marker-design.md`.

## Проверки

1. Разбор и запись пустого `!xml/standard-attributes` без payload.
2. Ошибка для payload и для незарегистрированного свойства.
3. Импорт различает отсутствующий и присутствующий полностью стандартный блок.
4. Экспорт тега восстанавливает канонические элементы, значения и порядок.
5. Непустой предметный YAML продолжает работать без тега.
6. Неизвестное содержимое не заменяется кратким тегом.
7. E2E восстанавливает все компоненты без XML-расхождений и без списков
   исключений.
8. Частичная raw-поправка без `#order` не переставляет смешанные дочерние
   элементы обычного XML; явный `#order` по-прежнему переставляет их.
9. Отсутствующий вычисляемый `RowFilter` получает локальный `$xml: null` и не
   появляется после round-trip.
10. Подробный повторный импорт proof проходит те же стадии уточнения, что и
    основной второй проход.
11. Значение `xs:string`, похожее на ссылку метаданных, сериализуется в кавычках
    и повторно восстанавливается как `xs:string`; некавычечное значение остаётся
    ссылкой.
12. Полный e2e не содержит списков допустимых XML-расхождений ни для одного из
    перечисленных случаев.
13. Отличие внутри повторяющейся кнопки создаёт raw только на конкретном
    свойстве или дочернем узле, но не на всей `КоманднаяПанель`.
14. Raw-патч повторяющейся XML-группы не содержит полную замену массива
    rule-элементов.
15. Каноническая пустая `ExtendedTooltip` не появляется в YAML.
16. Порядок повторяющихся элементов хранится отдельным `#order` без копирования
    содержимого элементов.
17. `id` и другие индексируемые сведения не попадают в raw.
18. Невозможность минимальной локализации создаёт диагностику с XML/YAML-путями,
    причиной и размером raw, но не прерывает импорт.
19. Полный e2e не содержит диагностик слишком широкой области raw.
20. Общий сопоставитель одинаково работает для metadata-объектов, элементов
    форм и common-объектов без частных проверок их типов и имён.
21. Нестандартное имя зарегистрированного singleton создаёт только поле
    `Имя: !xml/name ...`, а не raw всего элемента.
22. Каноническое имя singleton не появляется в YAML.
23. Поле `Имя` без `!xml/name` и тег у незарегистрированного типа отклоняются.
24. Известный вариант суффикса родителя автоматически применяется к вложенным
    singleton без дублирования их имён в YAML.
25. Экспорт без reference XML точно восстанавливает нестандартное имя, XML
    `id` и имена вложенных singleton.

## Итог реализации

Полный e2e проходит без XML-исключений: 19 файлов тестов и 170 тестов. Повторный
импорт создаёт байт-в-байт те же YAML, а экспорт каждого `cf` и `cfe` точно
совпадает с исходным XML.

В e2e остались только явно согласованные представления формы XML:

- 11 `!xml/raw`: восемь редких `FillValue` и три различия отсутствующего и
  пустого `Settings` у `СписокЗначений`;
- 9 `!xml/string`: одноязычные `xs:string` в полях представления DCS;
- 9 `!xml/standard-attributes`: присутствующие полностью стандартные блоки
  `LineNumber`;
- 0 `!xml/name`: в e2e нет нестандартных имён зарегистрированных singleton;
- 0 `!xml/invalid`.

Большой `!xml/raw` для стандартных реквизитов возникал не из-за отличия их
значений. Пустой scalar-тег корректно сохранялся в YAML, но общий YAML → XML
runtime видел его значение `undefined`, принимал за отсутствующее свойство и не
запускал правило вложенной коллекции. Теперь наличие разрешённого scalar-тега
само считается явным входом для правила; нормализация вложенной коллекции также
переносит служебные YAML-метаданные на новый объект.

Перестановка `ChildItems` возникала в другом общем механизме. Raw-поправка
представляла смешанных соседей как mapping, сгруппированный по XML-имени, и
merge ошибочно выводил из порядка ключей новый `#order`. Поэтому обычный
правильный порядок `Button`, `ButtonGroup`, `Button` превращался в
`Button`, `Button`, `ButtonGroup`. Теперь неявный порядок raw-поправки не
заменяет порядок обычного экспорта; перестановку разрешает только явно заданный
`#order`.

Минимальная локализация повторяющихся элементов и диагностическое сообщение о
слишком широкой области реализованы общим сопоставителем rules-границ.

Повторная проверка `cf/doc` после реализации `!xml/name` завершилась без
XML-различий. Прежние 42 diff исчезли: нестандартные имена singleton
восстановлены коротким тегом.

### Пустой форматированный текст

`formatted="true"` является предметным признаком, даже когда у текста нет ни
одного языкового значения. Такой XML не является аномалией:

```xml
<Title formatted="true"/>
```

Он представляется обычным YAML общего типа `FormattedI8nText`:

```yaml
Заголовок:
  Форматированный: Истина
```

Отсутствие `Текст` означает, что языковых значений нет. Запись `Текст: ""`
остаётся другим случаем: явно задан пустой текст языка по умолчанию. Договор
действует для всех свойств `FormattedI8nText`, а не только для `Title` внутри
`ExtendedTooltip`; `!xml/raw` для обеих форм не используется.

В измерении `cf/doc` до выделения пустого форматированного текста было
зарегистрировано 11 131 `!xml/name`, 938
`!xml/raw`, 108 `!xml/invalid`, 131 `!xml/string` и 1 015
`!xml/standard-attributes`. Максимальный raw занимает 22 строки; целые формы,
реквизиты, командные панели и контекстные меню в raw больше не попадают.

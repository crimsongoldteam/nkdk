# Импортная аномалия неявного пути заимствованной формы

## Статус и связь с прежними решениями

Эта спецификация уточняет и проверяет импортную часть спецификации
`2026-09-01-explicit-borrowed-form-attribute-validation-design.md`. Она не
вводит новый вид аномалии и не меняет правило заимствования реквизитов формы.

Правило избыточной `БазоваяФорма.yaml` уже задано в части 3 спецификации
`2026-08-30-reliable-long-mcp-operations-and-created-resource-sync-design.md`.
Настоящая работа проверяет, что оба правила совместно применяются к реальной
форме расширения и не маскируют друг друга.

## Наблюдаемый случай

В выгрузке расширения `sed_nkdk` форма
`Catalogs/ДокументыПредприятия/Forms/ФормаСпискаСПапками/Ext/Form.xml`
содержит элемент:

```xml
<Table name="Список" id="1">
  ...
  <RadioButtonField name="ПоказыватьОписаниеИлиЗадачи" id="1139">
    ...
  </RadioButtonField>
</Table>
```

У `RadioButtonField` отсутствует явный `DataPath`. Платформенный путь
вычисляется из родительской таблицы и имени элемента:
`Список.ПоказыватьОписаниеИлиЗадачи`.

При этом корневой реквизит формы `Список` отсутствует во внешнем `Attributes`
как явно заимствованный реквизит. Это некорректное состояние исходного XML,
которое импорт не должен ни исправлять молча, ни терять при уплотнении YAML.

Тот же `Form.xml` содержит вложенный `<BaseForm>`. Поэтому прежний импорт
создал `БазоваяФорма.yaml`; файл не был добавлен вручную. Если эта основа после
смысловой проекции полностью восстанавливается из текущей формы `cf` и рабочей
формы `cfe`, её хранение избыточно.

## Требуемое поведение

### Свежий импорт XML

Импорт вычисляет эффективный путь элемента тем же общим механизмом, который
используется для остальных неявных путей формы. Если корень эффективного пути
не присутствует в `Реквизиты` рабочей заимствованной формы, импорт:

1. не добавляет отсутствующий реквизит автоматически;
2. материализует отсутствовавшее в XML свойство в YAML;
3. помечает только это свойство существующим тегом `!xml/invalid`.

Ожидаемый результат для исследованного элемента:

```yaml
ПоказыватьОписаниеИлиЗадачи:
  Вид: ПолеПереключателя
  ПутьКДанным: !xml/invalid Список.ПоказыватьОписаниеИлиЗадачи
```

`!xml/raw` для элемента, формы или реквизита не применяется. Импорт продолжает
работу и сохраняет остальные смысловые данные формы.

### Валидация существующего YAML

Валидатор остаётся только проверяющим механизмом. Для старого YAML, где
неявный путь ещё не материализован, он вычисляет тот же эффективный путь и
выдаёт ошибку:

> Путь `Список.ПоказыватьОписаниеИлиЗадачи` использует реквизит формы
> `Список`, который не добавлен в `Реквизиты` заимствованной формы.

Валидатор не добавляет тег, не переписывает файл и не создаёт реквизит.
Повторная диагностика обычного resolver для того же корня подавляется, чтобы
пользователь получил одну предметную причину.

### Основа формы

Наличие импортной ошибки пути не делает сохранённую основу необходимой.
Вложенный `<BaseForm>` независимо проходит действующий общий предикат
необходимости основы:

- если смысловая проекция совпадает с вычисляемой основой, файл
  `БазоваяФорма.yaml` не создаётся;
- если остаётся хотя бы одно значимое отличие, файл сохраняется;
- при недоступной или неподтверждённой форме `cf` основа не удаляется по
  предположению.

Сравниваются смысловые модели, а не текст YAML или XML. Технические поля и
порядок ключей незначимы; состав, порядок и иерархия элементов значимы.

## Проверка перед изменением производственного кода

Сначала выполняется свежий импорт реального XML из `C:/git/temp` актуальной
сборкой NKDK во временный проект. Каталог `sed_nkdk` при этой проверке не
перезаписывается.

Проверка фиксирует два независимых результата:

1. у `ПоказыватьОписаниеИлиЗадачи` появился точечный
   `!xml/invalid Список.ПоказыватьОписаниеИлиЗадачи`;
2. восстановимая `БазоваяФорма.yaml` не создана.

Если оба результата уже выполняются, производственный код не меняется:
добавляется только регрессионное покрытие. Если любой результат не выполняется,
сначала добавляется падающий тест, затем исправляется общий механизм на его
существующей предметной границе. Частные условия по имени формы, элемента,
реквизита `Список` или каталогу `sed_nkdk` запрещены.

## Регрессионное покрытие

Существующие XML-фикстуры не изменяются. Интеграционный тест программно строит
производный вход из существующей фикстуры заимствованной формы:

- помещает собственный элемент внутрь таблицы;
- не задаёт ему `DataPath`;
- не добавляет корневой реквизит таблицы во внешний `Attributes`;
- сохраняет соответствующий элемент во вложенном `BaseForm`;
- импортирует конфигурацию и проверяет точечный тег;
- проверяет отсутствие восстановимой `БазоваяФорма.yaml`;
- запускает валидацию результата и ожидает одну предметную ошибку пути.

Отдельный положительный вариант явно добавляет корневой реквизит формы и
подтверждает отсутствие `!xml/invalid` и диагностики. Вариант со значимо
отличающейся основой подтверждает, что `БазоваяФорма.yaml` по-прежнему
сохраняется.

## Архитектурные ограничения

- Вычисление эффективного пути использует действующий resolver и регистрации
  свойств формы.
- Политика явного заимствования остаётся в concrete-модуле
  `clientApplicationForm`.
- Классификация импорта использует общий механизм импортных решений и
  существующий `!xml/invalid`.
- Решение о сохранении основы использует единый смысловой предикат импорта и
  валидатора.
- Нейтральные слои не получают условий по metadata-типу, физическим папкам или
  именам элементов.
- `.agents/architecture.md` менять не требуется: новые зависимости и границы
  не вводятся.

## Критерии готовности

- Реальный свежий импорт воспроизводит ожидаемую точечную аномалию.
- Старый немаркированный YAML даёт ошибку без изменения файла.
- Корректно заимствованный корень не даёт ложной ошибки.
- Восстановимая основа не сохраняется, значимо отличающаяся сохраняется.
- Производственный код изменён только при доказанном провале действующего
  общего механизма.
- Целевые тесты, `pnpm test`, проверки архитектуры и проверка дублей проходят.

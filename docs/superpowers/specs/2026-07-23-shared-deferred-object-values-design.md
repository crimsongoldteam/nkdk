# Общий механизм отложенных значений XML и YAML

## Цель

Устранить удержание разобранных YAML между проходами полной синхронизации YAML → XML и унифицировать уточнение отложенных значений для импорта XML → YAML и синхронизации YAML → XML.

После изменения worker полной синхронизации должен:

- прочитать и разобрать каждый YAML один раз;
- во время того же обхода `rules.ts` извлечь локальные факты и построить окончательные XML-деревья задания;
- привязать отложенные значения к полям уже готовых XML-деревьев;
- освободить YAML до чтения следующего файла;
- хранить между проходами только подготовленные XML, отложенные значения, описание выходов и незавершённое состояние сборщика снимка конфигурации.

Импорт и синхронизация используют один нейтральный механизм хранения, проверки и замены отложенных значений. Правила вычисления значений остаются раздельными для направлений XML → YAML и YAML → XML.

## Границы

В эту итерацию входят:

- общий договор отложенного значения в объектном дереве;
- перевод существующего уточнения импортированного YAML на общий договор;
- подготовка XML полной синхронизации в первом проходе;
- хранение `PreparedXMLAssignment` вместо `PreparedYamlFile`;
- уточнение отложенных XML-значений и завершение фрагмента снимка конфигурации во втором проходе;
- сохранение текущего результата импорта и побайтового результата XML-синхронизации.

В эту итерацию не входят:

- ранняя запись XML или YAML, у которых нет отложенных значений;
- выгрузка подготовленных деревьев во временные файлы;
- ограничение памяти заданным числом байт;
- изменение формата `.nkdk`;
- изменение декларативных правил конкретных metadata-объектов без выявленной необходимости;
- повторное чтение YAML во втором проходе.

Договор должен позволять в будущем определить полностью готовый документ по условию `deferred.length === 0`, сразу записать его и освободить. Эта возможность в текущей итерации не используется.

## Критерии результата

- Один YAML читается, хэшируется и разбирается один раз.
- Один YAML обходится по `rules.ts` один раз.
- После подготовки одного задания worker не удерживает корневой разобранный YAML.
- Между проходами worker хранит готовые XML-деревья, а не YAML.
- XML полной синхронизации побайтово совпадает с результатом до изменения.
- YAML импорта семантически и текстово совпадает с результатом до изменения на существующих проверках.
- Новый снимок конфигурации корректен и детерминирован при одинаковых входах. Побайтовое совпадение с прежней реализацией не является отдельным требованием.
- Результат не зависит от числа worker.
- Снижение измеренного пика памяти не является обязательным критерием этой итерации: подготовленные XML намеренно остаются в памяти.

## Термины

**Временная координата** — путь из строковых и числовых сегментов, записанный во время обхода правил до окончательной сборки документа.

**Цель отложенного значения** — прямая ссылка на контейнер в окончательном XML- или YAML-дереве и ключ заменяемого значения.

**Подготовленный документ** — окончательно собранное объектное дерево XML или YAML вместе со связанными отложенными значениями.

**Уточнение** — вычисление окончательного значения после появления общих сведений проекта и замена значения по связанной цели.

## Общий договор

Общий слой располагается в нейтральной части `metadata/orchestration` и не знает о конкретных `itemType`, XML-корнях, именах каталогов и правилах отдельных metadata-объектов.

Концептуальные типы:

```ts
type DeferredObjectTarget =
  | { object: Record<string, unknown>; key: string }
  | { object: unknown[]; key: number }

interface DeferredValuePath {
  readonly valuePath: readonly (string | number)[]
  readonly rulePath: readonly DeferredRulePathSegment[]
}

interface DeferredObjectValue {
  readonly target: DeferredObjectTarget
  readonly valuePath: readonly (string | number)[]
  readonly rulePath: readonly DeferredRulePathSegment[]
}
```

`valuePath` сохраняется в связанном значении для диагностики и проверки актуальности ссылки. Он не используется как основной способ доступа во втором проходе.

Общий слой предоставляет две операции:

1. `bindDeferredObjectValues(root, paths)` вызывается только после окончательной сборки дерева. Для каждой временной координаты он находит родительский контейнер и создаёт цель `{ object, key }`.
2. `finalizeDeferredObjectValues(root, deferred, finalize)` проверяет актуальность цели, читает `object[key]`, передаёт значение направленному обработчику и записывает результат обратно.

Обработчик `finalize` передаётся адаптером операции. Общий слой не разрешает `rulePath` и не знает, как вычисляется значение.

Существующий термин архитектуры «отложенный путь XML» обозначает временную координату во время построения дерева. Между проходами хранится уже связанное отложенное значение с прямой ссылкой на контейнер.

### Инварианты ссылки

- Цель связывается только с окончательным деревом документа.
- Ключ должен существовать в контейнере в момент связывания.
- После связывания дерево нельзя пересобирать так, чтобы контейнер был заменён новым объектом.
- Перед уточнением общий слой повторно разрешает родительский контейнер по `valuePath` и проверяет, что он совпадает с `target.object`.
- Для объекта используется строковый ключ, для массива — числовой индекс.
- Преобразователь обязан создать заменяемое поле до связывания, даже если его промежуточное значение равно `undefined`.
- Отложенное значение не содержит функции-замыкания и не удерживает исходный YAML или XML через контекст вычисления.

Проверка по сохранённому пути делает устаревшую ссылку явной ошибкой, а не молчаливой записью в объект, который больше не входит в результат.

## Почему ссылка связывается после сборки дерева

Текущие преобразования выполняют завершающие структурные операции:

- импорт сортирует поля YAML и может создать новый объект;
- экспорт объединяет сгенерированные значения с reference-представлением;
- правила корня и формы добавляют внешние узлы, пространства имён и служебные атрибуты.

Ссылка, созданная до этих операций, может указывать в промежуточный объект. Поэтому обход правил сначала сохраняет временную координату, а верхнеуровневый преобразователь связывает её только после получения окончательного корня документа.

## Направленные адаптеры

### XML → YAML

Существующий `finalizeImportedYAML` остаётся операцией реестра типов и сохраняет текущую семантику.

Изменяется способ адресации:

- локальный сборщик по-прежнему записывает `valuePath` и `rulePath` во время единственного обхода XML;
- после сортировки и окончательной сборки YAML временные координаты связываются с полями итогового YAML;
- `PreparedImportYaml` хранит связанные отложенные значения;
- второй проход разрешает `rulePath`, вызывает `finalizeImportedYAML` и заменяет `target.object[target.key]`.

Отложенные значения перестают быть частью `LocalIndexes`: общий сборщик возвращает временные координаты отдельно, а `LocalIndexes` содержит только локальные metadata-факты. Это устраняет смешение индекса и жизненного цикла подготовленного дерева.

### YAML → XML

Для синхронизации добавляется направленная операция реестра типов `finalizeExportedXML`. Она вызывается только для свойств, окончательное XML-значение которых зависит от общих сведений проекта, недоступных во время обработки текущего YAML.

Во время обхода `rules.ts` преобразователь:

- строит XML обычным способом;
- для зависимого значения сохраняет временную координату и `rulePath`;
- оставляет в поле промежуточное значение, которое направленный обработчик получит во втором проходе;
- сохраняет сведения, необходимые для завершения соответствующей записи снимка конфигурации.

После окончательной сборки каждого XML-документа координаты связываются с его реальными контейнерами. Специальных значений или маркеров внутри XML-дерева нет.

Если для текущих правил нет зависимых XML-значений, список остаётся пустым. Общий механизм всё равно задаёт единый договор для появления таких правил в будущем.

## Подготовленный результат синхронизации

Подготовка и запись XML разделяются. Концептуально worker хранит:

```ts
interface PreparedXMLDocument {
  readonly targetXmlPath: string
  readonly xml: Record<string, unknown>
  readonly deferred: readonly DeferredObjectValue[]
}

interface PreparedXMLAssignment {
  readonly assignment: FullXmlSyncAssignment
  readonly documents: readonly PreparedXMLDocument[]
  readonly indexCollector: ConfigurationIndexCollector
}
```

Существующий `ConfigurationIndexCollector`:

- содержит уже собранные идентификаторы, порядок и окончательные значения;
- позволяет дополнить записи значениями, уточнёнными во втором проходе;
- формирует фрагмент нового снимка без повторного чтения записанного XML.

`PreparedXMLAssignment` не содержит `PreparedYamlFile`, YAML-текст или корневой объект разобранного YAML.

## Поток полной синхронизации

### До первого прохода

Координатор уже располагает:

- полным планом заданий и составом проекта;
- прежним снимком `.nkdk`;
- целевыми путями XML.

Эти данные передаются worker до обработки YAML. Состав проекта выделяется из общего снимка сведений так, чтобы его можно было создать из плана до извлечения YAML-фактов.

### Первый проход

Для каждого задания worker последовательно:

1. читает байты одного YAML;
2. вычисляет хэш по тем же байтам;
3. разбирает YAML;
4. извлекает факты для общих индексов;
5. за один обход `rules.ts` строит все окончательные XML-документы задания;
6. связывает временные координаты с полями окончательных XML-деревьев;
7. сохраняет `PreparedXMLAssignment`;
8. освобождает YAML-текст и разобранный YAML до перехода к следующему заданию.

Факты могут извлекаться непосредственно из разобранного YAML либо испускаться тем же обходом правил. Для этого не выполняются повторное чтение файла и второй преобразующий обход `rules.ts`.

Ошибки синтаксиса, преобразования или связывания относятся к первому проходу. Если любой worker возвращает ошибку, второй проход и запись XML не начинаются.

### Между проходами

Главный процесс объединяет YAML-факты, создаёт неизменяемое общее представление индексов и передаёт его worker. Полные YAML и подготовленные XML между процессами не передаются.

### Второй проход

Для каждого подготовленного задания worker:

1. уточняет только связанные отложенные значения XML;
2. завершает записи сборщика снимка конфигурации, относящиеся к этим значениям;
3. проверяет, что все метки успешно обработаны;
4. сериализует готовые XML-деревья;
5. записывает документы по объявленным путям;
6. формирует фрагмент нового снимка конфигурации;
7. освобождает подготовленное задание.

Ранней записи документов с пустым `deferred` в первом проходе нет.

## Поток импорта

Первый проход импорта продолжает читать и разбирать XML одного задания, строить окончательный YAML и извлекать локальные факты. После завершающей сортировки YAML временные координаты связываются с полями итогового дерева.

Во втором проходе общий механизм:

1. проверяет актуальность ссылки;
2. передаёт текущее значение импортному адаптеру;
3. адаптер разрешает `rulePath` и вызывает `finalizeImportedYAML`;
4. общий механизм записывает результат по ссылке;
5. worker сериализует и записывает YAML.

Поведение связанных внешних файлов и сбор configuration index не меняется.

## Ошибки и диагностика

Связывание завершается ошибкой, если:

- путь пуст или не ведёт к заменяемому полю;
- родитель не является объектом или массивом;
- ключ отсутствует;
- тип ключа не соответствует контейнеру.

Уточнение завершается ошибкой, если:

- сохранённая ссылка больше не совпадает с контейнером по `valuePath`;
- `rulePath` не разрешается;
- для типа не зарегистрирован направленный обработчик;
- направленный обработчик завершился исключением.

Диагностика содержит:

- направление преобразования;
- путь исходного или целевого файла задания;
- `valuePath`;
- `rulePath`;
- исходное сообщение ошибки.

Документ записывается только после успешного уточнения всех своих значений. При ошибке второго прохода операция завершается неуспешно, а новый `.nkdk` не записывается. Как и до изменения, уже начавшийся второй проход может оставить частичный XML-результат.

## Совместимость

- Общий механизм не меняет правила конкретных metadata-объектов.
- Регистрация и сигнатура `finalizeImportedYAML` не меняются; импортный адаптер вызывает её через общий механизм.
- XML-экспорт использует прежний снимок `.nkdk` как источник порядка, имён, значений и идентификаторов.
- Подготовка XML и последующая запись используют те же корневые обёртки и `xmlExport`, что и текущая реализация.
- Число worker и порядок завершения заданий не влияют на XML или итоговый снимок.

## Проверки

### Общий механизм

Быстрые модульные проверки покрывают:

- замену поля объекта;
- замену элемента массива;
- связывание вложенного пути;
- отсутствующий путь или ключ;
- устаревшую ссылку после замены контейнера;
- передачу текущего значения направленному обработчику;
- сохранение `valuePath` и `rulePath` в ошибке.

### Импорт

- Существующие проверки `finalizeImportedYAML` переводятся на общий механизм.
- Фикстуры импорта подтверждают неизменность итогового YAML.
- Отдельная проверка подтверждает, что ссылки создаются на окончательное отсортированное YAML-дерево.

### Синхронизация

- Проверка подготовки задания подтверждает, что результат содержит XML, а не `PreparedYamlFile`.
- Искусственное нейтральное правило подтверждает связывание и уточнение XML-значения без частного условия по `itemType`.
- Профиль подтверждает один обход `rules.ts`.
- Существующие XML-фикстуры подтверждают побайтовую неизменность результата.
- Небольшая интеграционная фикстура запускается с разным `concurrency` и подтверждает одинаковые XML и корректный детерминированный снимок.
- Ошибка первого прохода не начинает запись XML; ошибка второго прохода не обновляет `.nkdk`.

Большой проект не добавляется в постоянный `pnpm test`, чтобы не замедлять основной контур. Он используется только для разовой проверки перед завершением реализации. Измерение памяти является наблюдением, а не условием успешности.

## Будущее развитие

После накопления практических данных можно отдельно спроектировать раннюю запись:

- документ с `deferred.length === 0` сериализуется и записывается после подготовки;
- его XML-дерево освобождается до завершения первого прохода;
- документы с отложенными значениями остаются в памяти до второго прохода.

Такая оптимизация должна отдельно решить поведение частичного результата при ошибке более позднего YAML и не входит в текущую спецификацию.

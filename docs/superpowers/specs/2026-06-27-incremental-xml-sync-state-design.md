# Incremental XML Sync State Design

## Цель

Ускорить YAML -> XML синхронизацию: при обычной работе перезаписывать только те XML-области, для которых изменились исходные YAML-файлы или связанные ресурсные файлы.

Файл состояния хранится в XML-проекте и называется `.nkdk-sync.yaml`. Он описывает, какому YAML-состоянию соответствует текущий XML-каталог.

## Основные решения

- Файл состояния хранит хэши YAML-стороны, а не XML-стороны.
- Хэш считается от сырых байтов файла на диске, без нормализации переносов строк, кодировки, пробелов или форматирования.
- Формат файла состояния в первой версии плоский: ключ - относительный путь YAML-файла или ресурсного файла, значение - `sha256`.
- XML-пути не хранятся в `.nkdk-sync.yaml`; соответствие YAML-файла XML-области вычисляется из `rules.ts` и зарегистрированных обработчиков.
- Переименования в первой версии не поддерживаются. Если файл исчез из состояния и появился новый похожий файл, это трактуется как удаление старого и добавление нового.
- Если файл есть в `.nkdk-sync.yaml`, но текущая версия правил не умеет определить XML-область для такого пути, sync падает с понятной ошибкой.
- Если при инкрементальной замене происходит ошибка, пользователь получает сообщение об ошибке; state-файл не должен фиксировать частично применённый результат.

Пример:

```yaml
version: 1
files:
  Справочники/Товары/Свойства.yaml: sha256:aaa
  Справочники/Товары/Формы/ФормаЭлемента/Форма.yaml: sha256:bbb
  Справочники/Товары/Формы/ФормаЭлемента/Модуль.bsl: sha256:ccc
  Справочники/Товары/Формы/ФормаЭлемента/Справка/ru.html: sha256:ddd
  Справочники/Товары/Шаблоны/Макет/Template.txt: sha256:eee
```

## Инициализация state

`.nkdk-sync.yaml` нельзя строить напрямую по текущему рабочему YAML-каталогу, потому что пользователь мог уже изменить YAML после последнего соответствия с XML.

Инициализация должна идти от XML:

1. Взять текущий `xmlDir`.
2. Импортировать XML во временный YAML-каталог.
3. Собрать список файлов, участвующих в хэшировании.
4. Посчитать `sha256` от сырых байтов каждого такого файла.
5. Записать результат в `<xmlDir>/.nkdk-sync.yaml`.
6. Удалить временный каталог.

После такой инициализации `.nkdk-sync.yaml` отражает именно то YAML-состояние, которому соответствует текущий XML. Если пользователь уже изменил рабочий `yamlDir`, следующий инкрементальный sync увидит разницу между state и рабочими файлами и выгрузит только изменённые области.

Если `.nkdk-sync.yaml` уже существует, команда инициализации перезаписывает его сразу, без отдельного флага подтверждения.

## CLI и MCP

Для CLI:

- обычный `nkdk sync <yamlDir> <xmlDir>` без `.nkdk-sync.yaml` не падает;
- он выполняет полный YAML -> XML sync, чтобы сохранить round-trip сценарии;
- в полном режиме `ConfigDumpInfo.xml` не обновляется;
- отдельная CLI-команда инициализации строит `.nkdk-sync.yaml` от XML через временный YAML-каталог.

Для MCP:

- обычный sync без `.nkdk-sync.yaml` не должен молча выполнять полный sync;
- MCP должен сообщить, что для точечной синхронизации нужно инициализировать `.nkdk-sync.yaml`;
- отдельный MCP tool инициализации строит `.nkdk-sync.yaml` от XML через временный YAML-каталог;
- если пользователь явно запросил полный round-trip/full sync через MCP, полный sync разрешён, но `ConfigDumpInfo.xml` не обновляется.

## Инкрементальный поток

1. Прочитать `<xmlDir>/.nkdk-sync.yaml`.
2. Собрать текущие хэши файлов из рабочего `yamlDir`.
3. Найти добавленные, изменённые и удалённые файлы.
4. Для каждого изменённого пути через декларативные правила определить область XML, которую нужно заменить.
5. Сгруппировать изменения по областям, чтобы одна область пересобиралась один раз.
6. Пересобрать только затронутые области во временный каталог или память.
7. Удалить в XML-проекте только известные файлы старой области.
8. Записать новый результат.
9. Обновить `.nkdk-sync.yaml` только после успешной записи всех областей.

`orchestration` не должен знать про конкретные типы объектов и `ConfigDumpInfo.xml`. Он работает с нейтральным договором: правила сообщают, какая YAML-область соответствует какой операции записи XML, а внешний слой решает, как обновлять служебные файлы.

## Области пересборки

Правила должны позволять вычислять XML-область для всех поддерживаемых YAML-путей.

Согласованные примеры:

- Изменение `Справочники/Товары/Свойства.yaml` пересобирает только объект `Catalog.Товары`, но не его формы, модули, справку, картинки и макеты.
- Добавление или удаление формы меняет состав владельца, поэтому пересобирается файл владельца и сама форма.
- Изменение существующей формы пересобирает форму, но не файл владельца.
- Изменение модуля формы пересобирает модуль формы.
- Изменение справки формы пересобирает справку формы.
- Изменение картинки или другого ресурсного файла формы заменяет только этот файл и обновляет версию формы в `ConfigDumpInfo.xml`, если такая запись есть.
- Изменение модуля объекта пересобирает только модуль объекта и обновляет `ConfigDumpInfo.xml` для владельца и записи модуля.
- Изменение существующего макета пересобирает макет и его содержимое.
- Добавление или изменение синонима команды меняет состав владельца/команды и обновляет соответствующие записи `ConfigDumpInfo.xml`.
- Изменение модуля команды пересобирает модуль команды и обновляет запись модуля команды в `ConfigDumpInfo.xml`.
- Изменение элемента существующей формы обновляет записи формы и внутренней записи `Form` в `ConfigDumpInfo.xml`.
- Удаление многофайловой области, например справки или макета, удаляет старую XML-область целиком перед записью новой версии.
- Если `Форма.yaml` удалён, удаляется вся форма.
- Если удалён ресурсный файл формы, например `Картинки/Иконка.png`, соответствующий файл удаляется в XML-проекте.

## Configuration.xml и ConfigDumpInfo.xml

`Configuration.xml` пересобирается, если изменился хэш любого YAML-объекта, входящего в конфигурацию, или изменился состав объектов, который должен быть отражён в конфигурации.

`ConfigDumpInfo.xml` в первой версии обновляется только при инкрементальном sync и только когда изменилась затронутая область, для которой нужна версия:

- при изменении объекта обновляется версия объекта;
- при изменении формы обновляются обе записи формы, если обе есть: `...Form.ИмяФормы` и `...Form.ИмяФормы.Form`;
- при изменении справки формы обновляется запись `...Form.ИмяФормы.Help`;
- при изменении картинки формы обновляется версия формы;
- при изменении модуля объекта обновляются записи владельца и `...ObjectModule`;
- при изменении макета обновляются записи макета и внутренней записи содержимого, если она есть;
- при изменении модуля команды обновляется запись `...CommandModule`;
- при изменении модуля управляемого приложения обновляются записи конфигурации и `Configuration.Имя.ManagedApplicationModule`.

Полная YAML -> XML синхронизация не обновляет `ConfigDumpInfo.xml`. Она нужна для round-trip через CLI и для явного полного sync через MCP.

## Ошибки и ограничения v1

- Миграции и переименования откладываются.
- Если правило для changed/deleted path отсутствует, sync падает с ошибкой.
- Если невозможно безопасно определить XML-область, sync падает с ошибкой.
- Если существующая XML-область содержит неизвестные файлы, инкрементальный sync удаляет только известные файлы области.
- Сверку того, что рабочий YAML действительно был получен из текущего XML, в обычном sync не выполняем.
- State-файл хранится в XML-части проекта, а не в YAML-части.

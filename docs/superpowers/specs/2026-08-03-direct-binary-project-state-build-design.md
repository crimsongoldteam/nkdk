# Прямая сборка двоичного состояния проекта

## Контекст

Текущее состояние проекта хранится в `.nkdk/cache/project-state.bin` и во время работы представлено несколькими `SharedArrayBuffer`. Фиксированные записи читаются через `structurae`, но путь холодной актуализации использует лишние преобразования:

```text
объекты worker
→ универсальные двоичные пачки
→ объекты главного процесса
→ Map замен
→ итоговые двоичные буферы
```

На контрольном проекте worker тратят до 8,18 с на двоичное кодирование, главный процесс — 9,70 с на применение 7643 пачек общим объёмом 334,6 МБ. Последующая материализация снимка скрыта в чтении локальных диагностик и занимает ещё 13,63 с. Полная проверка зависимостей занимает 18,27 с, потому что восстанавливает полный объект каждого YAML-файла из универсального двоичного значения.

## Цели

- Удалить из рабочего пути восстановление полных файловых объектов и промежуточный `Map`.
- Кодировать строки в UTF-8 и вычислять их хэши один раз на уникальную строку локального фрагмента.
- Проверять структуру полученного от worker фрагмента один раз на границе хранилища.
- Хранить сведения проверки зависимостей в типизированных таблицах `structurae` и читать только необходимые записи.
- Использовать один сборщик для validation и обоих этапов import.
- Перекрыть обнаружение файлов с их чтением и хэшированием на тёплом проходе.
- Сохранить предметный интерфейс `ProjectStateReadSession` и атомарную публикацию снимка.

## Не входит в задачу

- Частичная sync.
- Миграция прежнего двоичного формата.
- Журнал изменений, поколения снимка или слой изменений поверх опубликованного состояния.
- Изменение правил validation и состава возвращаемых диагностик.
- Автоматическое уплотнение таблицы строк при обычном обновлении.

## Формат состояния `0.4.2`

Формат `0.4.2` заменяет `0.4.1`. Снимок по-прежнему состоит из одного файла на диске и нескольких `SharedArrayBuffer` в памяти. `0.4.1` не читается и не мигрируется: несовместимый файл удаляется, после чего выполняется холодная перестройка.

Снимок содержит следующие логические разделы:

- строки;
- файлы, identity и хэши;
- ссылки на объекты, поля и значения;
- владельцы и их свойства;
- поля объектов и форм;
- отложенные ссылки metadata target;
- отложенные проверки `DataPath`;
- зависимости файлов;
- локальные и schema-диагностики;
- поисковые таблицы.

Физически снимок сохраняет шесть общих буферов: `header`, `strings`, `files`, `facts`, `lookups` и `diagnostics`. `facts` содержит отдельный каталог всех типизированных таблиц ссылок, владельцев, полей, форм, отложенных проверок и зависимостей. Каждая таблица имеет число записей и точные границы. Фиксированные записи описываются через `structurae`. Переменная длина представляется дополнительными таблицами и диапазонами:

- YAML-путь — диапазон строковых и числовых сегментов;
- описание типа — запись и диапазоны видов и определяемых типов;
- диагностическое сообщение — фиксированная запись со ссылками на строки;
- вариант составного значения — числовой признак и поля выбранного варианта.

Универсальный `valueCodec` не используется для состояния проекта `0.4.2` и промежуточных фрагментов.

## Двоичный фрагмент worker

Каждый worker накапливает один логический нормализованный двоичный фрагмент на фазу операции. Его таблицы повторяют соответствующие таблицы итогового снимка, но используют локальные идентификаторы строк и файлов. Маленькие файловые пачки нужны только для обратного давления и не создают самостоятельные таблицы строк.

Логический фрагмент содержит отдельные переносимые `ArrayBuffer` для заголовка, строк, файлов, фактов и диагностик:

- заголовок и каталог таблиц;
- локальную таблицу уникальных UTF-8 строк с готовыми `xxHash64`;
- файловые записи и хэши;
- факты, диагностики и индексные записи файла;
- счётчики записей и размеры переменных разделов.

Строка кодируется в UTF-8 и хэшируется при первом добавлении в локальную таблицу worker. Повторные вхождения любых обработанных этим worker пачек используют тот же локальный идентификатор. После завершения выдачи файлов главный процесс отправляет команду завершения полосы, и worker передаёт все буферы фрагмента через Piscina `move()` без копирования. Таким образом, одна фаза validation создаёт не более одного фрагмента на worker, а import — не более одного фрагмента на worker для каждого из двух проходов.

Сбой или отмена до команды завершения освобождает накопленные таблицы worker. После передачи владения worker забывает фрагмент и готов к следующей операции.

Фрагмент является непрозрачным значением для оркестрации и `ProjectStateWriterHandle`. Только хранилище открывает его и один раз проверяет сигнатуру, версию, границы, числа записей, допустимые значения признаков, диапазоны и ссылки на локальные идентификаторы. Отдельная предварительная проверка в `ProjectStateWriterHandle` удаляется. Нарушение договора является технической ошибкой и отменяет кандидат.

## Двухпроходная сборка

Главный процесс является единственным владельцем построения и публикации состояния.

Первый проход сборщика:

1. Сливает отсортированные файловые записи прежнего снимка и новых фрагментов.
2. Исключает удалённые пути и прежние версии изменённых файлов.
3. Сохраняет идентификаторы существующих строк.
4. Для каждой уникальной локальной строки использует переданный хэш и сравнение UTF-8 байтов, затем переиспользует прежний идентификатор либо назначает новый.
5. Рассчитывает соответствия локальных идентификаторов строк и файлов итоговым идентификаторам.
6. Считает точные размеры всех итоговых таблиц и поисковых индексов.

Второй проход:

1. Выделяет итоговые `SharedArrayBuffer` точного размера.
2. Копирует неизменённые записи и переменные данные непосредственно из прежнего снимка.
3. Копирует записи новых фрагментов, заменяя числовые идентификаторы строк и файлов без восстановления предметных объектов.
4. Строит диапазоны и поисковые хэш-таблицы с заполнением не выше 80%.
5. Формирует заголовок и проверяет целостность готового кандидата.

Если нет изменённых и удалённых файлов, сборщик не запускается и прежний набор буферов переиспользуется целиком.

## Добавление, изменение и удаление

Вход сборщика состоит из прежнего снимка, новых фрагментов и множества удалённых путей:

```text
старые записи
− удалённые пути
− прежние версии изменённых файлов
+ новые фрагменты
```

Удаление исключает файловую запись, хэш, факты, диагностики, отложенные проверки, зависимости и все индексные записи с этим `sourceFileId`. Идентификаторы оставшихся файлов перенумеровываются в двоичных записях сборщиком.

Строки, оставшиеся без ссылок после удаления или изменения, физически сохраняются. Это удерживает прежние идентификаторы и позволяет копировать неизменённые данные без переписывания всех ссылок. Холодная перестройка и команда сброса создают таблицу строк заново. Автоматическое уплотнение допускается позднее только по результатам отдельного измерения.

Опубликованные буферы неизменяемы. Кандидат строится рядом с прежним снимком и публикуется одной заменой ссылки. При технической ошибке прежнее состояние остаётся доступным.

## Потоковая актуализация validation

Обнаружение файлов и работа worker образуют ограниченный конвейер:

1. Обход проекта выдаёт ограниченные пачки путей вместо полного массива файлов.
2. Для каждого пути снимок сразу возвращает прежний идентификатор и сохранённый хэш.
3. Пачка передаётся свободному worker; ограниченная очередь обеспечивает обратное давление, а результаты изменённых файлов добавляются в накопитель этого worker.
4. Worker читает файл и вычисляет хэш из прочитанных байтов.
5. При совпадении worker возвращает только признак неизменности.
6. Изменённый YAML разбирается и локально проверяется из тех же байтов, после чего включается во фрагмент.
7. Изменённый внешний ресурс создаёт только файловую запись и хэш.
8. `ENOENT` после обнаружения добавляет путь в удаления.
9. Главный процесс отмечает найденные прежние `fileId` в битовом массиве; неотмеченные после окончания обхода записи также считаются удалёнными.
10. После обработки всех пачек каждый worker завершает и передаёт один логический фрагмент; сборщик публикует кандидат либо переиспользует прежний снимок.
11. Полная проверка зависимостей выполняется по актуальным типизированным таблицам.

Обнаружение следующих путей продолжается одновременно с чтением и хэшированием предыдущих пачек. Одновременно изменять состояние одного проекта может только одна операция; существующая очередь проекта сохраняется.

## Полная проверка зависимостей

Б5 не вызывает `decodeUpdate()` для каждого YAML. Она обходит таблицы статуса validation, отложенных metadata target ссылок, владельцев и отложенных `DataPath`-проверок непосредственно через типизированные представления.

`ProjectStateReadSession` сохраняет существующие предметные методы. Реализация создаёт обычные объекты только для строк, затронутых конкретным запросом. Для полного Б5 запросы группируются по `fileId` и диапазонам записей без предварительного массива полных обновлений файлов.

Полные dependency diagnostics не сохраняются и рассчитываются заново при каждой актуализации. Локальные и schema-диагностики остаются связанными с хэшем файла.

## Import

Import использует тот же формат фрагментов и тот же сборщик, но не запускает файловое обнаружение.

1. Первый проход XML создаёт фрагменты с `references`, `owners`, `fields` и `forms`.
2. Сборщик публикует временный типизированный рабочий индекс.
3. Отдельные одноразовые read token передают его worker второго прохода без копирования общих буферов.
4. Второй проход уточняет и сразу записывает YAML, затем возвращает окончательные хэши, локальные диагностики, отложенные ссылки, проверки и зависимости в типизированных фрагментах.
5. Сборщик накладывает окончательные сведения на рабочий индекс и строит окончательный снимок.
6. Выполняются локальная и полная dependency validation, после чего снимок публикуется и асинхронно сохраняется.

Оба состояния строятся без файловых объектов в главном процессе и без промежуточного `Map` вкладов.

## Остальные операции

Полная sync, поиск ссылок и переименование сначала выполняют общую актуализацию, затем читают опубликованное состояние через `ProjectStateReadSession`. Частичная sync не реализуется, но в будущем должна использовать тот же блок актуализации и те же предметные запросы.

## Ошибки и отмена

- Обычные YAML- и schema-диагностики сохраняются и не отменяют публикацию.
- Неразрешённые зависимости возвращаются Б5 и не сохраняются.
- Повреждённый фрагмент, неизвестное значение признака, выход идентификатора за границы, сбой worker или ошибка сборки отменяют кандидата.
- Отмена прекращает выдачу новых пачек, дожидается завершения уже начатых границ и отбрасывает незавершённые фрагменты.
- Ошибка сохранения после публикации не повреждает состояние в памяти; прежний дисковый файл остаётся до атомарного переименования.
- Две validation одного проекта последовательно проходят через очередь состояния, поэтому гонки публикации и записи файла отсутствуют.

## Проверка решения

Модульные проверки должны подтверждать наблюдаемые договоры:

- чтение и запись каждой типизированной таблицы;
- сопоставление локальных и глобальных строк, включая коллизии хэшей;
- холодную сборку, переиспользование неизменного снимка, добавление, замену и удаление;
- удаление всех зависимых записей по `sourceFileId`;
- единственную структурную проверку фрагмента на границе хранилища;
- сохранение результатов всех методов `ProjectStateReadSession`;
- прямой обход Б5 без восстановления полного обновления файла;
- ограничение очереди, перекрытие обхода с worker и обработку `ENOENT`;
- оба этапа import через общий сборщик;
- атомарный откат при технической ошибке.

Архитектурные тесты запрещают рабочему пути состояния импорт универсального `valueCodec` и хранение полных обновлений файлов в `Map`. Существующие договорные тесты хранилища сохраняются и переводятся на новый формат. Реальный SQLite не используется.

Интеграционные проверки validation, import и полной sync выполняются на `/Users/nikita/git/round-trip-compact/cf/all`. Модульные тесты подменяют файловую систему и worker; отдельный тест должен выполняться не более 50 мс, желательно не более 10 мс. Перед завершением запускаются `pnpm test` и `pnpm check:duplicates`. Mutation testing в этой задаче не выполняется.

## Критерии производительности

Измерения выполняются через `validation-profile` на временной копии большого YAML-проекта. Контрольная сумма диагностик должна остаться:

```text
75106694d1310a4abb65bc2323b58ca4c72765b38401faa6ea4007fc2ddf02d3
```

Целевые границы:

| Этап | Текущее время | Цель |
|---|---:|---:|
| Холодная validation целиком | 71,65 с | не более 40 с |
| Б1–Б4 `processFiles` | 33,83 с | не более 25 с |
| Чтение локальных диагностик | 13,63 с | не более 2 с |
| Полная проверка зависимостей Б5 | 18,27 с | не более 3 с |
| Кодирование и применение фрагментов | 17,88 с | не более 5 с суммарно |
| Тёплая validation без изменений | более 10 с | не более 10 с, цель около 5 с |

Пиковая память не должна превышать текущий профиль. Если функциональные договоры выполнены, но одна из временных границ нарушена, реализация не считается завершённой: профиль должен показать оставшийся узкий этап до дальнейшего архитектурного решения.

# Видимость метаданных и заимствованные формы расширения

## Цель

Не считать все метаданные основной конфигурации автоматически доступными при проверке YAML расширения.

Если свойство метаданных в `cfe/<Имя>` ссылается на объект или подчинённый объект основной конфигурации, соответствующий объект должен быть явно представлен в том же расширении. Например:

- для типа `Справочник.Номенклатура` справочник `Номенклатура` должен присутствовать в `cfe/<Имя>`;
- для ссылки `Справочник.Номенклатура.Реквизит.Артикул` в `cfe/<Имя>` должны присутствовать справочник `Номенклатура` и реквизит `Артикул`.

Одного наличия цели в `cf` недостаточно.

Для заимствованных управляемых форм дополнительно требуется:

- проверять итоговую форму расширения относительно актуальной формы `cf`;
- разрешать `ПутьКДанным` только через явно представленные в расширении
  реквизиты формы;
- сохранять историческую `BaseForm` только тогда, когда она отличается от
  основы, которую можно построить из текущей `cf`;
- позволять удалить сохранённую основу и тем самым адаптировать расширение к
  текущей форме `cf`.

В части `BaseForm` эта спецификация заменяет решение из
`2026-07-25-configuration-extensions-design.md`, по которому вложенная основа
всегда игнорировалась при импорте и безусловно перестраивалась из текущей `cf`.
Остальные решения той спецификации сохраняют силу.

## Основание

Заимствование фиксирует зависимость расширения от необходимого объекта основной конфигурации, а не создаёт полную копию конфигурации. В расширение переносится минимально необходимый состав объектов, подчинённых объектов и свойств.

Публичный проект NKDK не хранит UUID заимствованных объектов. UUID доступны только в скрытом снимке конфигурации после XML-import и используются при XML-sync. Поэтому YAML-validation определяет доступность по вкладу компонента и его логическим адресам, а не по UUID.

Официальные материалы:

- [описание расширений](https://v8.1c.ru/platforma/rasshireniya/);
- [руководство разработчика, глава 36](https://its.1c.ru/db/v8322doc/bookmark/dev/TI000001535);
- [соответствие по внутренним идентификаторам в 8.3.15](https://wonderland.v8.1c.ru/blog/razvitie-mekhanizma-rasshireniy-konfiguratsii-15/).

Механизм основы формы существовал до изменения правил заимствования в 8.3.14.
Платформа фиксирует визуальное состояние формы при заимствовании и сравнивает с
ним изменения каждого элемента в основной конфигурации и расширении. В 8.3.14
изменился не этот принцип, а состав автоматически заимствуемых частей: вместе с
формой автоматически заимствуются её элементы, а реквизиты, команды и параметры
нужно включать явно. Это уменьшает зависимость расширения от обновлений основной
конфигурации:

- [исходный механизм расширения форм в 8.3.6](https://wonderland.v8.1c.ru/blog/rasshireniya/);
- [изменение правил заимствования форм в 8.3.14](https://wonderland.v8.1c.ru/blog/razvitie-mekhanizma-rasshireniy-konfiguratsii-14/).

## Текущее расхождение

Сейчас dependency validation использует видимость:

```text
cf       -> cf
cfe/X    -> cfe/X, затем cf
```

Из-за резервного поиска в `cf` ссылка из `cfe/X` успешно разрешается даже тогда, когда цель не представлена в `cfe/X`. Это скрывает отсутствующее заимствование.

## Решение

Для dependency validation вводится строгая компонентная видимость:

```text
cf       -> только cf
cfe/X    -> только cfe/X
```

Правило применяется ко всем чтениям зависимостей, инициированным YAML проверяемого компонента:

- разрешению metadata target;
- поиску владельца объекта;
- поиску полей для DataPath и других проверок свойств;
- обратному поиску владельцев;
- чтению связанных форм и иных dependency inputs.

Соседние расширения также остаются невидимыми друг другу.

Индекс `cf` не смешивается с индексом `cfe/X` и не дополняет неполное представление объекта расширения. Собственный объект расширения и явно представленный объект основной конфигурации одинаково доступны через вклад `cfe/X`.

Стандартные поля, которые validation выводит из правила самого объекта, остаются доступны при наличии объекта в `cfe/X`: они не являются отдельно заимствуемыми подчинёнными объектами. Пользовательский реквизит, табличная часть, команда, форма и другой самостоятельный подчинённый объект доступны только при наличии собственного вклада в `cfe/X`.

## Заимствованные формы

### Два представления формы

Полная итоговая форма расширения является рабочим представлением, которое
пользователь изменяет и которое проверяется относительно актуальной формы
основной конфигурации. Для дочерней формы она хранится в `Форма.yaml`. Для общей
формы то же содержимое остаётся разделом `Форма` в `Свойства.yaml`.

Историческая основа дочерней формы при необходимости хранится отдельным файлом
рядом с рабочей формой:

```text
Формы/<Имя>/Форма.yaml
Формы/<Имя>/БазоваяФорма.yaml
```

Для общей формы файл основы располагается рядом со `Свойства.yaml`:

```text
ОбщаяФорма/<Имя>/Свойства.yaml
ОбщаяФорма/<Имя>/БазоваяФорма.yaml
```

В обоих случаях `БазоваяФорма.yaml` содержит непосредственно тело формы, без
обёртки `Форма` и без свойств metadata-объекта общей формы.

`БазоваяФорма.yaml` — служебное, но версионируемое смысловое представление
вложенного XML-узла `BaseForm`. Оно не содержит `BaseForm` рекурсивно, UUID,
числовые `id`, XML-пространства имён и другие служебные детали выгрузки.

Файл предназначен для совместимости с состоянием основной формы, относительно
которого создавалось или в последний раз адаптировалось расширение. Он не
считается второй актуальной формой основной конфигурации и может закономерно
расходиться с текущей `cf`.

### Отличие `BaseForm` от основной формы

`BaseForm` не является полной копией формы `cf`. Это проекция состояния основной
формы для конкретного расширения:

- визуальные элементы образуют зафиксированную структуру основы;
- реквизиты, команды и параметры присутствуют только тогда, когда они явно
  представлены в форме расширения;
- зависимые свойства, включая `DataPath`, остаются только при доступности их
  целей внутри проекции;
- события основной формы не копируются в `BaseForm`;
- значения включённых свойств берутся из основной формы, а изменения
  расширения остаются во внешней `Form`.

Кроме проекции существует временное расхождение. В исследованных примерах
`round-trip-compact` состав и иерархия элементов всех 60 основ совпали с
текущими формами `cf`. В `sed_xml` 13 из 29 основ уже отличались от текущих
форм: в `cf` появились, исчезли или переместились элементы, а в отдельных
случаях изменился их вид. Поэтому восстановление каждой основы только из
текущей `cf` меняет смысл существующего расширения.

### XML-import

При импорте заимствованной формы:

1. внешняя XML-`Form` преобразуется в рабочее представление: `Форма.yaml` для
   дочерней формы или раздел `Форма` в `Свойства.yaml` для общей;
2. вложенная XML-`BaseForm` преобразуется в смысловую модель формы;
3. из текущей `cf` и импортированной рабочей формы строится ожидаемая проекция
   основы;
4. импортированная и ожидаемая основы сравниваются после смысловой
   нормализации;
5. равная ожидаемой основа не записывается, отличающаяся записывается в
   `БазоваяФорма.yaml`.

Если заимствованная XML-форма не содержит `BaseForm`, import не создаёт
`БазоваяФорма.yaml` и не формирует диагностику. При последующей синхронизации
действует обычное правило отсутствующего файла: основа строится из текущей `cf`.
Это защитное поведение NKDK, а не утверждение о штатной выгрузке платформы: во
всех 89 исследованных заимствованных формах узел `BaseForm` присутствовал.

Сравнение не учитывает UUID, числовые `id`, XML-пространства имён и порядок
незначимых XML-свойств. Оно учитывает значения свойств, состав, вид, порядок и
иерархию элементов, а также порядок других коллекций, для которых порядок имеет
смысл.

### XML-sync

При формировании XML расширения выбирается один источник:

- если `БазоваяФорма.yaml` существует, `BaseForm` строится из сохранённой
  исторической основы;
- если файла нет, `BaseForm` строится из текущей синхронизированной формы `cf`
  и актуального рабочего представления формы расширения.

Таким образом, удаление `БазоваяФорма.yaml` является явной операцией
«пересоздать основу из текущей основной конфигурации». Отдельная команда или
служебный флаг для этого не вводятся.

Отсутствие файла является постоянным выбором актуальной основы, а не только
решением на момент импорта. Если позже изменится `cf`, следующая успешная
XML-синхронизация построит `BaseForm` уже из новой основной формы. Историческая
основа автоматически не материализуется; для её фиксации нужен существующий
`БазоваяФорма.yaml`.

Сохранённые в снимке исходные числовые `id` используются по возможности, чтобы
уменьшать XML-различия. Их отсутствие не является ошибкой: экспорт назначает
свободные локальные номера и согласованно обновляет внутренние ссылки формы.

Числовой `id` — локальный технический номер узла внутри конкретного дерева
`Form` или `BaseForm`, а не идентификатор сопоставления элемента основной формы
с элементом расширения. Исследованные данные подтверждают независимость
нумерации: в `sed_xml` для 47 из 50 различавшихся элементов номер `BaseForm`
совпадал с `cf`, но отличался во внешней форме расширения, где тот же номер уже
был занят другим узлом. Соответствие заимствованных элементов определяется не
равенством этих чисел.

### Архитектурные границы

Модуль управляемой формы регистрирует `БазоваяФорма.yaml` как необязательный
сопутствующий YAML-ресурс любого задания, содержащего
`ClientApplicationForm`: рядом с `Форма.yaml` дочерней формы или со
`Свойства.yaml` общей формы. Общие слои `resourceTopology`, `projectState`,
import, sync и validation работают с регистрацией ресурса и не получают частных
условий по имени файла, виду владельца или XML-узлу `BaseForm`.

Историческая основа не публикует реквизиты, команды, параметры или элементы в
общий metadata-индекс компонента. Иначе её устаревший состав мог бы сделать
недоступную зависимость видимой рабочей форме расширения. Для неё создаётся
изолированный индекс, используемый только при внутренней проверке и
формировании вложенного XML.

Если `БазоваяФорма.yaml` сохраняется, её XML-факты и локальные идентификаторы
записываются в снимок `cfe` в отдельном адресном пространстве основы. Они не
перекрывают идентификаторы внешней формы. Удаление файла исключает эти записи
при следующем построении состояния проекта; отсутствие записей не блокирует
генерацию новых локальных `id`.

### Валидация формы расширения

Рабочее представление формы расширения проверяется относительно текущей формы
`cf`, независимо от наличия исторической основы:

- каждый элемент текущей формы `cf` должен присутствовать в итоговой форме
  расширения;
- сопоставленный по имени элемент нельзя переименовать;
- новый элемент расширения, отсутствующий в `cf`, разрешён;
- отсутствие нового элемента, появившегося в `cf` после создания расширения,
  означает необходимость адаптации и является ошибкой validation;
- одноимённый элемент с изменённым XML-видом считается присутствующим; отдельная
  матрица допустимых платформой смен вида в эту работу не входит, поскольку она
  зависит также от типа связанного реквизита формы. Ограничение зафиксировано в
  `.agents/restrictions.md`.

`БазоваяФорма.yaml` не сравнивается с текущей `cf`: её расхождение является
назначением файла. Она проверяется по схеме формы и на внутреннюю связность.

При этом историческая основа должна быть согласована с рабочей формой того же
расширения:

- каждый элемент `БазоваяФорма.yaml` должен присутствовать в рабочей форме с
  тем же именем;
- каждый реквизит, команда и параметр исторической основы должен присутствовать
  в рабочей форме;
- порядок, иерархия и значения свойств могут различаться, поскольку именно эти
  изменения описывает расширение;
- содержимое, существующее только в рабочей форме, является собственным или
  появившимся позднее и не обязано присутствовать в исторической основе.

Правило одинаково применяется к `Форма.yaml` дочерней формы и разделу `Форма`
в `Свойства.yaml` общей формы.

### `ПутьКДанным`

В рабочем представлении корень `ПутьКДанным` разрешается только среди
реквизитов, явно присутствующих в этой же форме расширения. Резервный поиск
реквизита формы в `cf` запрещён, даже если одноимённый реквизит существует в
основной форме.

Для `БазоваяФорма.yaml` применяется изолированный контекст её собственных
реквизитов. Историческая основа не получает реквизиты из текущей `cf` и не
расширяет видимость рабочей формы.

Ошибка указывает файл, YAML-путь свойства и отсутствующий корневой реквизит.

## Диагностика

Если цель не найдена в `cfe/X`, validation не должна принимать совпадение из `cf` как успешное разрешение.

После неуспешного поиска разрешается отдельная проверка существования точной цели в `cf` только для уточнения сообщения. Такая проверка не возвращает сведения цели в resolver и не делает её доступной расширению.

Когда точная цель найдена только в `cf`, диагностика сообщает, что объект или подчинённый объект не включён в расширение. Когда цели нет ни в `cfe/X`, ни в `cf`, сохраняется обычная диагностика отсутствующей ссылки. Диагностика указывает файл и YAML-путь исходного свойства.

Для формы используются отдельные сообщения:

- отсутствие элемента текущей `cf` указывает рабочий файл формы и имя
  отсутствующего элемента;
- отсутствие элемента, реквизита, команды или параметра исторической основы в
  рабочей форме указывает `БазоваяФорма.yaml` и путь компонента основы;
- отсутствие XML-`BaseForm` при импорте не формирует диагностику.

## Границы

В эту работу не входят:

- проверка BSL: обращение из BSL выполняется в объединённом пространстве имён и не подчиняется этому правилу metadata validation;
- проверка UUID и соответствия после переименования;
- проверка контролируемых и модифицируемых свойств;
- проверка применимости расширения и настроек поведения платформы 8.5.4;
- проверка полноты цепочки владельцев подчинённого объекта;
- восстановление `ExtendedConfigurationObject`, кроме уже существующего
  механизма XML-sync;
- точная матрица допустимых платформой изменений вида сопоставленного элемента
  формы с учётом типа связанного реквизита;
- автоматическое содержательное редактирование исторической основы при
  обновлении `cf`.

Проверка цепочки владельцев требует отдельного проекта решения из-за специальных правил платформы, в частности для форм и разных режимов совместимости.

## Проверки

Нужны тесты следующих договоров:

- ссылка из `cf` на объект `cf` остаётся допустимой;
- ссылка из `cfe/X` на собственный объект `cfe/X` допустима;
- ссылка из `cfe/X` на объект, представленный и в `cfe/X`, и в `cf`, допустима;
- ссылка из `cfe/X` на объект только из `cf` отклоняется с сообщением о необходимости включить объект в расширение;
- наличие справочника в `cfe/X` не делает доступным пользовательский реквизит, присутствующий только в `cf`;
- явно представленный в `cfe/X` пользовательский реквизит доступен;
- стандартное поле явно представленного объекта остаётся доступным;
- ссылка из `cfe/X` на объект `cfe/Y` недопустима;
- DataPath и owner-dependent проверки не получают поля только из `cf`;
- отсутствие цели во всех компонентах сохраняет обычную диагностику отсутствующей ссылки;
- уточняющий поиск в `cf` не меняет результат разрешения и не раскрывает цель последующим проверкам.

Для заимствованных форм дополнительно проверяются следующие договоры:

- равная актуальной проекции XML-`BaseForm` не создаёт
  `БазоваяФорма.yaml`;
- отсутствие XML-`BaseForm` у заимствованной формы не создаёт диагностику и
  `БазоваяФорма.yaml`;
- отличающаяся историческая основа импортируется в отдельный YAML-файл;
- сравнение основ игнорирует служебные идентификаторы, но учитывает значимые
  значения, состав, порядок и иерархию элементов;
- при наличии `БазоваяФорма.yaml` XML-sync использует её, а не текущую `cf`;
- после удаления файла XML-sync строит `BaseForm` из текущей `cf`;
- последующее обновление `cf` при отсутствующем файле автоматически изменяет
  строящуюся основу и не создаёт `БазоваяФорма.yaml`;
- отсутствие сохранённого числового `id` приводит к назначению свободного
  номера, а не к ошибке;
- каждый элемент текущей формы `cf` обязан присутствовать в рабочем
  представлении формы расширения;
- собственный элемент расширения, отсутствующий в `cf`, допустим;
- сохранённая историческая основа не отклоняется из-за расхождения с текущей
  `cf`;
- каждый элемент, реквизит, команда и параметр исторической основы присутствует
  в рабочей форме расширения;
- историческая основа общей формы хранится в `БазоваяФорма.yaml` рядом со
  `Свойства.yaml` и использует те же правила импорта, удаления и XML-sync;
- `ПутьКДанным` рабочей формы не разрешается через реквизит, существующий только
  в `cf`;
- `ПутьКДанным` разрешается через реквизит, явно представленный в рабочей
  форме;
- ссылки исторической основы разрешаются только внутри
  `БазоваяФорма.yaml`.

Строгая компонентная видимость проверяется на границе ProjectState query и на
полном проходе project validation, чтобы одинаковый договор соблюдался двоичным
состоянием и публичной операцией validation. Договор `BaseForm` дополнительно
проверяется тестами XML-import, полной и частичной XML-синхронизации,
сопутствующего ресурса общей и дочерней формы и межфайловой validation.

# Системная финализация имён DataPath при XML-импорте

## Контекст

Рабочий XML → YAML import worker сохраняет часть зарегистрированных внутренних имён DataPath без перевода. Например, путь
`КомпоновщикНастроек.Settings.ReportStructurePicture` остаётся в YAML общей формы вместо
`КомпоновщикНастроек.Настройки.КартинкаСтруктурыОтчета`.

Словарь `formattingNamePairs` и общий `resolveDataPathCore` уже знают эти имена. Прямой интеграционный сценарий способен выполнить преобразование, но производственный worker не обеспечивает тот же договор отложенной финализации. E2E сравнивает результат чистого импорта с зафиксированной NKDK-фикстурой и поэтому закрепляет одинаковый, но некорректный результат.

## Цель

Обеспечить единый системный договор для всех зарегистрированных пар имён DataPath:

- XML хранит внутренние имена платформы;
- обычный YAML хранит канонические YAML-имена;
- XML → YAML и YAML → XML используют один реестр и один resolver;
- переводимое внутреннее имя, оставшееся в обычном YAML, является ошибкой;
- прямой импорт и import worker ведут себя одинаково.

## Не входит в работу

- отдельный resolver или собственная проверка типов и имён;
- изменение таблиц `implicitValueYAML`;
- новые применения `!xml`;
- ручное редактирование XML-фикстур;
- перевод неизвестных пользовательских сегментов, отсутствующих в реестре.

## Архитектура

`formattingNamePairs` остаётся единственным источником пар внутренних и YAML-имён. Предикат `requiresImportedYAMLFinalization`, отложенный `finalizeImportedYAML`, resolver и проверка YAML должны работать с одним `DataPathRegistrySet` в прямом и worker-импорте.

Исправление выполняется на существующей границе DataPath. Оно не добавляет предметных условий по `SettingsComposer`, отдельного прохода со своей таблицей имён или нового слоя проверки. Причина расхождения контекстов прямого импорта и worker должна быть зафиксирована отдельным регрессионным тестом до изменения реализации.

## Поток данных

1. Импорт свойства `DataPath` проверяет значение общим предикатом на наличие зарегистрированных внутренних сегментов.
2. Подходящее значение попадает в существующую очередь отложенной финализации.
3. После построения полного индекса формы `finalizeImportedYAML` вызывает `resolveDataPathCore` в направлении `internal-to-yaml`.
4. Resolver заменяет только зарегистрированные сегменты и сохраняет пользовательские имена элементов и реквизитов.
5. Проверка `allowedKinds` выполняется над каноническим YAML-путём.
6. Перед записью результата тот же resolver проверяет путь в режиме `yaml`. Если в разрешимой позиции осталось зарегистрированное внутреннее имя, импорт возвращает ошибку с адресом YAML-свойства.
7. YAML → XML выполняет обратное преобразование через тот же реестр.

Порядок «канонизация, затем `allowedKinds`» обязателен. Проверка совместимости не должна возвращать исходный английский путь после успешного преобразования.

## Диагностика

Переводимое внутреннее имя в обычном YAML — ошибка структуры DataPath. Диагностика должна содержать путь к файлу и свойству, исходное значение и ожидаемое каноническое имя либо сообщение о необходимости YAML-имени.

Неизвестные пользовательские сегменты продолжают обрабатываться существующей диагностикой resolver. Значения с ранее согласованным `!xml` проверяются в режиме внутренних имён и не подпадают под требование YAML-канонизации. Новый `!xml` для обхода ошибки не вводится.

## Тестирование

Реализация ведётся через TDD и включает следующие уровни:

1. Модульный тест предиката подтверждает, что все `formattingNamePairs`, включая пары `SettingsComposer`, обнаруживаются в нужном направлении активного реестра.
2. Интеграционный тест прямого импорта подтверждает преобразование внутренних имён в YAML.
3. Интеграционный тест реального import worker воспроизводит прежнее расхождение без ручного вызова финализатора и ожидает тот же канонический результат.
4. Негативный тест подтверждает, что зарегистрированное внутреннее имя в обычном YAML даёт ошибку, а не предупреждение или молчаливое сохранение.
5. Регрессия порядка подтверждает, что `allowedKinds` получает канонический путь и не откатывает его к внутренним именам.
6. Round-trip подтверждает восстановление исходного XML-пути из русского YAML-пути.

## Фикстуры и приёмка

NKDK-фикстуры перегенерируются только штатным импортом из существующих XML-фикстур. XML вручную не изменяется. В частности,
`КомпоновщикНастроек.Settings.ReportStructurePicture` должен стать
`КомпоновщикНастроек.Настройки.КартинкаСтруктурыОтчета`, а остальные зарегистрированные сегменты должны быть исправлены системно, а не выбранным списком строк.

Работа считается завершённой, когда:

- прямой и worker-импорт формируют одинаковые канонические DataPath;
- обычный YAML с разрешимым зарегистрированным внутренним именем отклоняется как ошибка;
- перегенерированные NKDK-фикстуры не содержат переводимых внутренних сегментов DataPath;
- XML → YAML → XML сохраняет исходные XML-пути;
- проходят целевые тесты, `pnpm type-check`, `pnpm test`, архитектурные проверки, `pnpm test:e2e` и проверка дублей относительно `origin/develop`.

Известное состояние исходной линии: перед записью спецификации `pnpm test` прошёл 186 тестов `@nkdk/platform`, но команда завершилась ошибкой из-за превышения временных лимитов несколькими тестами. Это не связано с изменениями спецификации и должно быть повторно проверено перед завершением реализации.

# Постоянное состояние и единая актуализация проекта

**Статус:** согласовано для реализации
**Дата:** 2026-08-01

## Контекст

Сейчас validation каждый раз читает и разбирает все YAML-файлы, заново собирает общий индекс и затем выполняет межфайловые проверки. Import и sync строят часть тех же сведений независимо. Из-за этого повторная validation неизменившегося проекта оплачивает полный первый проход, а актуальность хэшей, индексов и диагностик не выражена единым договором.

Эксперимент с параллельной записью полных вкладов в SQLite был отклонён: он дублировал данные в памяти и замедлил первый проход на 28,6%. Следующий эксперимент сделал нормализованную SQLite `:memory:` единственным хранилищем reference-части. На `/Users/nikita/git/nkdk-yaml` он сохранил точный результат validation, ускорил полный проход на 10,3% и снизил Peak RSS на 16%. Поэтому целевая архитектура развивает второй вариант и не вводит ещё один полный буфер индекса.

## Цели

- Иметь одно согласованное рабочее состояние всего YAML-проекта для validation, import, sync, переименования и поиска ссылок.
- При каждой validation вычислять хэши всех управляемых правилами ресурсов, но локально разбирать и проверять только новые и изменённые YAML-файлы.
- Заменять в общем индексе только вклады изменённых файлов и удалять вклады исчезнувших файлов.
- При каждом запуске выполнять межфайловую validation целого проекта по актуальному индексу.
- Сохранять локальные диагностики неизменённых файлов и возвращать полный результат проекта без их повторной проверки.
- Загружать состояние с диска лениво при первом обращении MCP к проекту и фиксировать его после каждой завершённой операции.
- Скрыть SQLite за абстрактным хранилищем, чтобы прикладная логика не зависела от выбранной СУБД.
- Не дублировать пути, хэши и полные представления индекса в нескольких таблицах или постоянных структурах памяти.
- Выполнять актуализацию индекса и полную проверку проекта через одну внутреннюю операцию перед validation, sync и поиском ссылок, а при переименовании — до и после изменения файлов.

## Не входит в решение

- Публичная validation отдельного файла или компонента.
- Кэширование итоговых межфайловых диагностик: они всегда пересчитываются для всего проекта.
- Использование `mtime` вместо чтения и хэширования содержимого.
- Изменение формата снимка конфигурации, используемого sync. Он остаётся отдельной точкой подтверждённого состояния XML.
- Одновременная работа одного процесса MCP с несколькими активными проектами.
- Новый цикл экспериментов с СУБД. Следующий шаг — реализация с проверками договора и итоговым профилированием.

## Основные решения

### Одно состояние на проект

Runtime-кэш принадлежит всему проекту, включая `cf` и все `cfe/<имя>`. Компонент остаётся атрибутом файла и индексной строки, а не отдельной базой. Это позволяет выражать видимость `cf → cf` и `cfe/<имя> → своё расширение, затем cf` одним набором запросов и не копировать сведения основной конфигурации в каждое расширение.

Публичная validation не получает ключ файла или компонента. Она всегда возвращает диагностики всего проекта.

### SQLite в памяти как основное представление

Во время работы основным источником хэшей, локальных результатов и глобальных индексов является именованная SQLite в памяти. SQLite-реализация открывает её по закрытому внутри адаптера URI вида `file:<идентификатор>?mode=memory&cache=shared`, чтобы несколько соединений одного MCP-процесса могли читать одну базу. Отдельный полный `SharedArrayBuffer`, объектный граф или набор `Map`, повторяющий те же индексные строки, не создаётся.

Записывающее соединение принадлежит отдельному project-state worker. Validation worker не открывают базу и не выполняют SQL. Они читают файлы, вычисляют хэши, а для изменённых YAML выполняют парсинг, локальную validation и извлечение нормализованных вкладов. Обмен идёт ограниченными пачками с обратным давлением.

Тот же договор записи используется при import. Каждый import worker передаёт завершённые YAML владельцу состояния небольшими пакетами: DTO файлов, общий буфер хэшей, локальные диагностики и нормализованные строки проверок. Project-state worker записывает пакеты по мере поступления. Worker ждёт при заполнении ограниченной очереди, а после подтверждения приёма освобождает данные YAML. Основной поток не накапливает все результаты до конца прохода.

Для второго прохода import действует исключение только для чтения. После фиксации рабочего индекса в памяти каждый import worker через абстрактный слой открывает собственный сеанс чтения того же состояния. SQLite-адаптер реализует сеанс отдельным соединением `readOnly`; прикладной код worker не получает URI, `DatabaseSync` или возможность выполнить произвольный SQL. Таблицы рабочего индекса до конца прохода не изменяются. Записывающее соединение может параллельно добавлять хэши, локальные диагностики и отложенные проверки в другие таблицы.

Межфайловые проверки выполняются в project-state worker:

- reference-проверки разрешаются массовыми SQL-запросами с приоритетом видимого компонента;
- owner-, field-, data-path- и form-проверки читают нормализованные строки из SQLite;
- если существующую проверку целесообразно оставить в TypeScript, worker получает её вход пакетами из SQL и не строит долгоживущую полную копию базы.

### Абстракция хранилища

Общая логика зависит от договора `ProjectStateStore`, а не от `node:sqlite`. Договор отвечает за:

- открытие и проверку совместимости состояния проекта;
- сравнение актуальных хэшей с сохранёнными;
- транзакционную замену вклада файла;
- удаление исчезнувших файлов;
- чтение сохранённых локальных диагностик;
- завершение первого прохода import и выдачу переносимого разрешения на чтение рабочего индекса;
- открытие и закрытие `ProjectStateReadSession` в worker;
- полную проверку межфайловых зависимостей;
- фиксацию, откат, создание дискового снимка, сброс и закрытие.

`ProjectStateReadSession` предоставляет типизированные операции чтения состояния, а не SQL и не таблицы конкретной СУБД. Переносимое разрешение непрозрачно для оркестрации: SQLite-реализация может хранить в нём имя базы в памяти, другая реализация — собственный способ доступа. Создание соединения, подготовленные SQL-запросы и схема таблиц остаются внутри адаптера project-state слоя.

Сеанс чтения выражает нейтральные запросы предметной области:

- поиск объектов, членов и значений по каноническим ключам с учётом видимости компонента;
- чтение сведений владельцев, полей, табличных частей и источников формы;
- поиск обращений к канонической цели для поиска ссылок и переименования;
- чтение нормализованных входов, необходимых проверке зависимостей.

Результаты представлены нейтральными типизированными записями и не содержат строк таблиц SQLite. Сеанс применяет правила видимости и поиска, являющиеся частью договора индекса, но не форматирует `DataPath`, не создаёт диагностики и не принимает решения конкретных validation-правил. Такие решения остаются в соответствующих metadata-операциях и зарегистрированных обработчиках типов.

Все операции `ProjectStateReadSession` являются пакетными. Они принимают массив запросов, в том числе массив из одного элемента, и возвращают результаты с идентификатором исходного запроса. Отдельных одиночных методов нет, поэтому вызывающий код не может незаметно превратить обход YAML в тысячи отдельных SQL-запросов. Размер внутренней порции и разбиение большого пакета остаются ответственностью адаптера и определяются профилированием, а не входят в предметный договор.

SQLite-реализация находится на границе project-state слоя. Оркестрация metadata не получает условий по конкретным `itemType`, именам файлов или типам прикладных объектов и не зависит от `node:sqlite`. Это позволяет заменить SQLite другой СУБД или двоичным представлением без изменения операций import, validation, sync, переименования и поиска ссылок.

## Дисковое состояние и жизненный цикл

Снимок хранится в `.nkdk/cache/project-state.sqlite`. Он не является источником пользовательских данных и может быть полностью восстановлен из проекта.

MCP держит один активный проект:

1. При первом вызове с `projectDir` project-state worker лениво загружает весь совместимый дисковый снимок в именованную SQLite в памяти.
2. Следующие операции используют ту же базу в памяти.
3. При переключении проекта предыдущая завершённая операция уже имеет снимок на диске; worker закрывает старую базу и загружает новый проект.
4. Операции изменения состояния сериализуются. Две validation или validation и sync не меняют один проект параллельно.
5. При штатном завершении процесса новых смысловых данных не фиксируется: каждая завершённая операция уже создала снимок.

Если снимок отсутствует, повреждён или несовместим, операция начинает холодное построение. Повреждение кэша не является диагностикой YAML-проекта. Ошибка полного восстановления или публикации нового снимка является технической ошибкой операции.

## Совместимость состояния

В `cache_meta` хранятся как минимум:

- версия схемы кэша;
- версия производителя NKDK;
- отпечаток правил структуры, схем и локальной validation;
- алгоритм и версия хэша.

При несовпадении любого смыслового отпечатка старый снимок не мигрирует данные validation частично, а считается недоступным. Новая база строится холодно и заменяет старый файл только после успешной операции. Миграции допустимы позднее только для заведомо структурных изменений, не меняющих смысл сохранённых результатов.

## Модель данных

Перечисленные группы таблиц, связи между ними и правила нормализации являются обязательным договором. Имена и физические типы столбцов определяются при реализации по существующим типам первого и второго проходов без изменения этих границ.

| Группа | Назначение |
|---|---|
| `cache_meta` | Версии и отпечатки совместимости. |
| `components` | Уникальный путь компонента: `cf` или `cfe/<имя>`. |
| `project_files` | Уникальный относительный путь, ссылка на компонент, вид ресурса и роль YAML. Путь хранится один раз. |
| `file_hashes` | Текущий xxHash64 по `file_id` как BLOB ровно из 8 байт в big-endian. Хэш отделён от идентичности файла и не повторяется в индексах или результатах validation. |
| `file_validation_results` | Признак, что локальная validation выполнена для текущего состояния файла, а также необходимые для текущей семантики признаки schema-готовности и `contributed_facts`. Строка не содержит копию хэша. Отсутствие строки означает, что файл ещё не проверен либо результат признан несовместимым. |
| `local_diagnostics` | Сохранённые синтаксические, schema- и локальные диагностики YAML с координатами и ссылкой на исходный файл. |
| `reference_entries` | Нормализованные object/member/value entries, принадлежащие исходному YAML-файлу. |
| `pending_references` | Отложенные reference-проверки с фильтрами, координатами и исходным файлом. |
| `owner_facts` и `field_entries` | Нормализованные сведения владельцев, полей, табличных частей и стандартных псевдонимов. |
| `pending_dependency_checks` | Data-path, form и прочие отложенные проверки с типом и минимальным набором параметров. |
| `file_dependencies` | Локальные зависимости между ресурсами, если они нужны для определения затронутых единиц sync или составного YAML. |

Индексные и отложенные строки всегда содержат `source_file_id`; `component_id` получается через файл и не копируется без измеренной необходимости для индекса SQL. Удаление `project_files` каскадно удаляет хэш, локальный результат и все вклады файла.

Во время незавершённого import основные таблицы могут временно содержать индексные строки YAML без `file_hashes` и `file_validation_results`. Эти строки сразу образуют рабочий индекс и не копируются во временные таблицы или `Map`. После первого прохода рабочий индекс фиксируется только в базе в памяти и остаётся неизменным до завершения второго прохода. Пакет завершения файла добавляет хэш, локальный результат и отложенные проверки, рассчитанные по окончательному YAML, но не заменяет сведения рабочего индекса.

Договор `finalizeImportedYAML` разрешает изменять только значения, которые не формируют рабочий индекс, необходимый другим уточнениям этого же прохода. Сейчас это форматирование `DataPath`: оно меняет окончательный YAML и его отложенные проверки, но не owner-, object- или member-сведения рабочего индекса. Новый уточнитель, нарушающий этот договор, требует отдельного изменения архитектуры, а не неявного обновления индекса во время прохода. Перед фиксацией транзакции хранилище проверяет, что каждый YAML-файл завершён; неполное состояние никогда не публикуется.

Большие объектные JSON/BLOB-вклады рядом с нормализованными строками не хранятся. JSON допустим только для небольшого типизированного параметра проверки, который не раскладывается без значительного усложнения и не повторяет другие таблицы. Повторяющиеся строки внутри самих индексных ключей считаются содержимым индекса; отдельный словарь строк вводится только по результатам профилирования, а не заранее.

## Инварианты согласованности

- `project_files` задаёт идентичность файла; `file_hashes` задаёт только его текущее содержимое.
- Локальные диагностики и индексные строки относятся к текущему хэшу не через продублированный столбец, а через общую транзакцию файла.
- При изменении файла старые `file_validation_results`, диагностики и индексные строки удаляются до вставки новых в той же транзакции.
- При удалении файла его вклад исчезает целиком до межфайловой validation.
- При диагностических ошибках YAML новое состояние всё равно фиксируется: неизменившийся ошибочный файл не проверяется локально повторно.
- При технической ошибке или отмене текущая транзакция откатывается. Если внутренний этап уже был зафиксирован только в памяти, вся незавершённая база в памяти отбрасывается и восстанавливается предыдущее опубликованное состояние. Дисковый снимок не заменяется.
- Межфайловые диагностики в базе не сохраняются и к поколению индекса не привязываются.
- Полный итог validation равен холодной validation того же содержимого независимо от истории кэша.

## Хэширование и определение изменений

Список файлов строится по `rules.ts`. Validation читает все управляемые правилами ресурсы и вычисляет xxHash64 по исходным байтам. Это относится не только к YAML, но и к BSL, HTML, изображениям и другим внешним файлам: их хэши нужны для корректного состава sync.

Каноническое представление xxHash64 на границах worker, store и SQLite — ровно 8 байт в порядке big-endian. Долгоживущие DTO и протоколы не хранят хэш как `bigint` или строку. Локальный вызов библиотеки хэширования может кратковременно вернуть `bigint`, но до передачи или сохранения значение ровно один раз кодируется в общий буфер пачки.

Нейтральный пакет записи имеет вид `ProjectStateFileUpdateBatch { updates; hashBytes }`. Элементы `ProjectStateFileUpdate` не содержат хэш и не имеют `hashOffset`: для элемента с индексом `i` восемь байт находятся в диапазоне `[i * 8, i * 8 + 8)`. Пачка владеет одним переносимым `Uint8Array` и всем его `ArrayBuffer`: `byteOffset` равен нулю, а `byteLength` представления и буфера равен `updates.length * 8`; отдельные буферы или представления на каждый файл не создаются. Та же позиционная схема применяется к пакетам сравнения хэшей и проекциям, где хэш сопоставляется со списком файлов.

Границы протокола явно проверяют `byteOffset`, длину `hashBytes` и его `ArrayBuffer` и отклоняют пакет, если буфер не принадлежит пачке целиком или его длина не равна `updates.length * 8`. Пакет обязан успешно проходить `structuredClone`; явная проверка DTO по разрешённым полям и типам дополнительно запрещает функции, rule-объекты, разобранный YAML и общий граф. Для отправки worker разрешён transfer общего `ArrayBuffer`. SQLite сохраняет соответствующий восьмибайтовый диапазон как BLOB без преобразования в строку, JSON или знаковый `INTEGER`.

Project-state worker сравнивает полный актуальный список с `project_files` и `file_hashes` и возвращает:

- новые файлы;
- файлы с изменившимся хэшем;
- неизменённые файлы;
- удалённые файлы.

Только новые и изменённые YAML передаются на парсинг и локальную validation. Неизменённый YAML использует сохранённые локальные диагностики и индексный вклад. Не-YAML ресурсы обновляют хэш, но сами по себе не создают validation-индекс. Если правила объявляют несколько файлов одной неделимой validation-единицей, изменение одного файла затрагивает всю эту единицу; такой договор должен быть явным в правилах.

## Внутренняя операция актуализации и проверки

`Актуализация и проверка состояния проекта` — единая внутренняя операция Core. Она не публикуется как MCP-инструмент и не позволяет вызывающей стороне пропускать отдельные шаги. Её вызывают validation, полная и частичная sync, поиск ссылок и переименование.

Операция принимает корень проекта и возвращает актуальное состояние вместе с полным набором локальных и межфайловых диагностик. Параметр `ignoreValidationErrors` в её договор не входит: решение блокировать дальнейшее действие принимает вызывающая публичная операция.

| Шаг | Исполнитель | Действие |
|---|---|---|
| 1 | Основной поток | Находит и классифицирует все управляемые правилами файлы проекта. |
| 2 | Validation worker | Читает исходные байты и вычисляет xxHash64 всех файлов без парсинга YAML. |
| 3 | Project-state worker | Сравнивает хэши и определяет новые, изменённые, неизменённые и удалённые файлы. |
| 4 | Validation worker | Только для новых и изменённых YAML выполняет парсинг, JSON Schema, локальные проверки и извлечение нормализованных индексных строк. |
| 5 | Project-state worker | Начинает транзакцию, удаляет старые вклады изменённых и удалённых файлов, записывает новые хэши, локальные диагностики и индексные строки. |
| 6 | Project-state worker | Выполняет полную межфайловую validation по всем актуальным строкам SQLite. |
| 7 | Основной поток | Объединяет сохранённые и новые локальные диагностики с новыми межфайловыми, удаляет повторы и стабильно сортирует результат. |
| 8 | Project-state worker | Фиксирует транзакцию даже при validation-ошибках и атомарно обновляет дисковый снимок. При технической ошибке откатывает транзакцию. |

Если файлы не изменились, шаг 4 не парсит ни одного YAML, но шаг 6 всё равно проверяет зависимости всего проекта. Это намеренный договор: изменение индекса любого файла потенциально влияет на диагностику любого другого файла, а итоговые межфайловые результаты не кэшируются.

Перед глобальными проверками project-state worker вычисляет готовность компонентов из сохранённых и новых результатов файлов. Если первый проход `cf` не готов, сохраняется действующая семантика деградации: глобальные проверки расширений не выполняются, их schema-диагностики публикуются, и каждому затронутому расширению добавляется блокирующая диагностика. Эти итоговые диагностики не записываются в кэш, а воспроизводятся при каждом проходе.

Видимость reference и других глобальных записей сохраняет текущую семантику:

- `cf` видит только `cf`;
- `cfe/<имя>` сначала видит своё расширение, затем `cf`;
- расширение не видит соседние расширения;
- неоднозначность определяется в выбранном приоритетном слое, а не между всеми слоями сразу.

### Использование внутренней операции

- **Validation** вызывает её один раз и возвращает полученные диагностики всего проекта.
- **Полная и частичная sync** вызывает её один раз перед формированием XML. Ошибки блокируют sync по умолчанию.
- **Поиск ссылок** вызывает её один раз, после чего обращается к актуальному индексу. Ошибки блокируют поиск по умолчанию, потому что неисправный файл мог не дать полный вклад.
- **Предварительный просмотр переименования** вызывает её один раз, затем по актуальному индексу находит цель и все обращения и строит план без изменения файлов.
- **Фактическое переименование** вызывает её до построения плана и второй раз после записи и переименования файлов. Первый результат определяет, разрешено ли начинать изменение. Второй вызов пересчитывает хэши, заменяет вклады затронутых файлов, повторно проверяет весь индекс и фиксирует итоговое состояние.

Если первый вызов перед переименованием вернул ошибки, файлы по умолчанию не меняются. После применения плана второй вызов обязателен при любом результате: обычные диагностики уже не отменяют записанные файлы и сохраняются вместе с новым состоянием. Техническая ошибка второго вызова оставляет прежний снимок состояния на диске, но не откатывает уже применённый план файлов; следующая операция обнаружит расхождение по хэшам.

### Разрешение продолжить при ошибках

Публичные sync, переименование и поиск ссылок принимают единый параметр `ignoreValidationErrors: true`. Он разрешает продолжить действие после обычных диагностик внутренней операции, но не меняет её выполнение:

- хэши, локальная validation, обновление индекса и полная проверка зависимостей всё равно выполняются;
- актуальное состояние и локальные диагностики фиксируются;
- диагностики возвращаются вместе с результатом вызывающей операции;
- технические ошибки чтения, worker, SQLite и проверки целостности никогда не игнорируются.

Поиск ссылок при таком разрешении может быть неполным, если ошибочный файл не удалось разобрать и включить в индекс. Переименование аналогично может не увидеть обращение из такого файла. Возвращаемые диагностики должны явно сохранять этот риск. Параметр не называется `skipValidation`, поскольку ни один шаг проверки не пропускается.

## Import

Import использует те же договоры индексных вкладов, локальной и межфайловой validation, но получает данные не через сканирование готового проекта. Он уже читает XML, строит YAML, необходимые индексы и хэши:

1. Первый проход XML формирует YAML-результаты и одновременно собирает частичные индексные вклады, зависимости, сведения для снимка конфигурации и созданные связанные файлы. Предварительные вклады сразу записываются в основные таблицы SQLite внутри транзакции import.
2. YAML без отложенных значений завершается и записывается сразу в первом проходе. До второго прохода worker удерживает только YAML, которым для окончательного значения требуется общий индекс.
3. После первого прохода project-state слой фиксирует рабочий индекс в базе в памяти, но не публикует дисковый снимок. Он выдаёт worker переносимое разрешение, по которому каждый worker через `ProjectStateReadSession` открывает отдельный сеанс только для чтения.
4. Во втором проходе import уточняет отложенные YAML по неизменяемому рабочему индексу и сразу записывает каждый завершённый файл. Записанные ранее файлы не меняют индекс, видимый оставшимся worker; хэши, локальные диагностики и отложенные проверки добавляются записывающим соединением в другие таблицы.
5. Завершение одного YAML является общим блоком для обоих проходов: данные сериализуются один раз, запись файла начинается немедленно, а параллельно вычисляется хэш по тем же байтам и выполняются schema- и локальные проверки по данным в памяти. После окончания записи worker добавляет DTO файла и big-endian хэш в общий буфер небольшой пачки и передаёт её вместе с diagnostics и отложенными проверками владельцу состояния проекта. Тот сразу записывает пакет в транзакцию текущего этапа import и подтверждает приём, после чего worker освобождает YAML. Повторно читать записанный YAML не требуется.
6. После записи всех YAML worker закрывают сеансы чтения. Рабочие индексные таблицы первого прохода считаются окончательными без повторной записи; отложенные проверки окончательных YAML к этому моменту уже сохранены отдельно. Import переносит и хэширует внешние файлы.
7. Перед полной межфайловой validation хранилище проверяет, что каждый YAML получил хэш и результат локальной проверки. Затем validation выполняется по окончательному индексу, после чего итоговые хэши, локальные диагностики и индексные вклады сохраняются как единое завершённое состояние проекта.
8. Диагностики проекта возвращаются отдельно и не отменяют import: записанные файлы не откатываются, поскольку import не является транзакцией файловой системы. Если техническая ошибка произошла после фиксации рабочего индекса в памяти, project-state слой закрывает сеансы чтения, отбрасывает незавершённую базу в памяти и восстанавливает прежний дисковый снимок либо начинает холодное построение. Сохранённый снимок не заменяется; следующая операция обнаружит оставшиеся файлы по хэшам и восстановит состояние.

Таким образом, import сам строит рабочий и окончательный индексы и хэши. Общие блоки расчёта хэшей и локальной validation выполняются для каждого завершённого YAML до освобождения его данных, а полная validation зависимостей — один раз по окончательному индексу. В SQLite в памяти можно писать по мере готовности файлов, а долговечный снимок заменяется только в конце завершённой операции.

## Sync

Полная и частичная sync всегда начинают с внутренней операции актуализации и проверки состояния проекта. Поэтому XML строится по актуальным хэшам и индексам.

По умолчанию diagnostics уровня error блокируют sync до обращения к 1С. Предупреждения не блокируют. Параметр `ignoreValidationErrors: true` разрешает продолжить sync при обычных validation-ошибках, но:

- validation всё равно выполняется полностью;
- актуальное состояние и локальные диагностики всё равно фиксируются;
- ошибки возвращаются вызывающей стороне вместе с результатом;
- технические ошибки чтения, SQLite, worker или проверки целостности никогда не игнорируются.

## Поиск ссылок

Поиск ссылок сначала выполняет внутреннюю актуализацию и проверку, затем запрашивает актуальный индекс обращений. Без `ignoreValidationErrors` любая error-диагностика блокирует запрос, чтобы не вернуть заведомо ненадёжный полный результат. С разрешением операция продолжает поиск, возвращает найденные места вместе с diagnostics и не скрывает, что результат может быть неполным.

Поиск не перечитывает и не строит metadata-модели всех YAML: индекс уже содержит каноническую цель, исходный файл и путь значения. Содержимое файла понадобится только следующей изменяющей операции, например переименованию.

## Переименование

Предварительный просмотр переименования выполняет внутреннюю актуализацию один раз и строит план по актуальному индексу. Фактическое переименование использует следующий порядок:

1. Выполнить внутреннюю актуализацию и полную проверку проекта.
2. При ошибках остановиться, если `ignoreValidationErrors` не установлен.
3. По индексу разрешить цель, найти все обращения и построить план.
4. Прочитать и изменить только затронутые YAML и пути файлов.
5. Повторно выполнить внутреннюю актуализацию и полную проверку проекта.
6. Вернуть применённые изменения и диагностики второго вызова.

Второй вызов нельзя заменить ручным исправлением строк кэша: только повторная актуализация подтверждает, что записанные файлы, их хэши, локальные результаты и общий индекс согласованы.

## Снимок на диск

После каждой завершённой внутренней актуализации или import именованная SQLite в памяти копируется во временный файл в `.nkdk/cache`. Публикация состоит из следующих шагов:

1. Создать уникальный временный файл в том же каталоге.
2. Выполнить SQLite backup текущей базы.
3. Выполнить `quick_check` временной базы.
4. Синхронизировать файл с диском.
5. Атомарно переименовать его в `project-state.sqlite`.
6. Синхронизировать каталог, где это поддерживается платформой.

Старый снимок остаётся пригодным до последнего шага. Временный файл после ошибки удаляется. Для SQLite используется встроенный `node:sqlite`; внешняя служба и отдельная зависимость не требуются.

## Служебные команды MCP

### `nkdk.reset_project_cache`

- Принимает `projectDir`, но не ключ файла или компонента.
- Требует `allowWrite: true`, поскольку удаляет файл внутри проекта.
- Закрывает активную базу без checkpoint, если открыт этот проект.
- Удаляет только runtime-состояние в памяти и `.nkdk/cache/project-state.sqlite`.
- Не запускает validation или перестроение.
- Не затрагивает снимок конфигурации sync.
- Следующая операция выполняет холодное построение.

### `nkdk.rebuild_project_cache`

- Принимает `projectDir`, но не ключ файла или компонента.
- Требует `allowWrite: true` из-за публикации `.nkdk/cache/project-state.sqlite`.
- Строит новое состояние всего проекта в отдельной базе, выполняет полную validation и проверку целостности.
- Атомарно заменяет активное и дисковое состояние только после успешного завершения.
- Возвращает полный набор диагностик. Обычные validation-ошибки не мешают сохранить корректно построенный кэш; технические ошибки оставляют прежнее состояние без изменений.

Сброс нужен для удаления, rebuild — для явного восстановления здесь и сейчас. Они не объединяются, чтобы после сброса пользователь мог сохранить холодное состояние до следующей обычной операции.

## Ошибки и отмена

Различаются два класса неуспеха:

- **Диагностики проекта:** синтаксис YAML, JSON Schema, локальные правила и межфайловые зависимости. Они являются корректным результатом, сохраняются в локальной части кэша и не откатывают транзакцию состояния.
- **Техническая ошибка:** невозможность прочитать файл, сбой worker/SQLite, нарушение протокола, `quick_check`, отмена операции. Она откатывает текущую транзакцию и не публикует новый снимок. Если первый проход import уже зафиксирован только в памяти ради read-only сеансов, незавершённая база в памяти отбрасывается целиком и восстанавливается предыдущее опубликованное состояние.

Если содержимое файлов изменилось параллельно с операцией между хэшированием и публикацией, реализация должна обнаружить это повторной проверкой сведений об обработанных файлах либо признать снимок недействительным и повторить проход ограниченное число раз. Нельзя публиковать состояние, заведомо не соответствующее файловой системе.

## Проверки реализации

Тесты следуют существующей архитектуре тестов и проверяют наблюдаемый договор, а не конкретные SQL-тексты.

### Хранилище

- Общая проверка договора запускается через фабрику адаптера и не знает о SQLite. Любая новая реализация `ProjectStateStore` и `ProjectStateReadSession` обязана пройти тот же набор проверок.
- Store принимает `ProjectStateFileUpdateBatch`, проверяет единственный общий буфер хэшей и отклоняет любую длину, отличную от `updates.length * 8`; каждый BLOB после round-trip содержит те же 8 big-endian байт.
- Проверяются пакетные предметные запросы, связь ответа с исходным запросом, видимость компонентов, запрет записи через read-only сеанс, закрытие сеанса и отказ использовать разрешение от другого или уже закрытого состояния.
- Путь и компонент не дублируются в индексных таблицах, хэш отделён от файла.
- Замена изменённого файла и каскадное удаление исчезнувшего не оставляют старых строк.
- Ошибка внутри обновления откатывает весь вклад.
- Backup загружается обратно с тем же состоянием.
- Повреждённый, несовместимый и незавершённый снимок приводят к холодному восстановлению, не к частичному чтению.
- Ошибка атомарной публикации сохраняет предыдущий снимок.

### SQLite-адаптер и архитектурная граница

- Несколько worker открывают отдельные `readOnly`-соединения к одной именованной базе в памяти и получают одинаковый рабочий индекс.
- Пока read-only сеансы читают неизменяемые индексные таблицы, записывающее соединение добавляет хэши, локальные диагностики и отложенные проверки в другие таблицы без изменения результатов чтения.
- Ошибка после внутренней фиксации первого прохода закрывает сеансы, отбрасывает незавершённую базу в памяти и восстанавливает прежний снимок.
- Архитектурная проверка запрещает импорт `node:sqlite`, SQL и имён таблиц за пределами SQLite-адаптера project-state слоя.

### Новые дубли кода

- Реализация добавляет корневую команду `pnpm check:duplicates -- --base <commit>`. Исходный коммит обязателен: локально это состояние до начала реализации, в CI — общий предок проверяемой ветки и целевой ветки PR.
- jscpd закреплён в зависимостях проекта и запускается с единой конфигурацией для всех поддерживаемых вручную файлов TypeScript и JavaScript, включая тесты и служебные сценарии. Сгенерированные файлы, внешние зависимости, результаты сборки, отчёты и фикстуры исключаются явно.
- Команда сканирует весь настроенный исходный код, чтобы новый фрагмент сравнивался не только с изменёнными файлами, но и с уже существующим кодом. jscpd формирует JSON-отчёт; проектный переходник сопоставляет оба диапазона каждого клона с добавленными строками `git diff` относительно исходного коммита с учётом переименований файлов.
- Проверка завершается ошибкой, если хотя бы один диапазон клона пересекает добавленную строку. Поэтому запрещаются как дубли между двумя новыми фрагментами, так и копирование существующего кода в новый. Неизменённые старые дубли сами по себе проверку не блокируют.
- Параметры чувствительности jscpd хранятся в одном конфигурационном файле и не ослабляются для отдельного изменения без отдельного архитектурного решения. JSON-отчёт сохраняется как диагностический результат проверки, но не добавляется в репозиторий.
- Тесты переходника используют небольшие искусственные отчёты и диапазоны Git: неизменённый старый дубль проходит, новый фрагмент против старого и два новых фрагмента завершают проверку ошибкой, а чистое переименование не считается новым кодом. Отсутствующий исходный коммит, сбой jscpd и повреждённый или неполный JSON-отчёт также завершают команду ошибкой.
- Команда обязательна после каждого слоя реализации, при итоговой локальной проверке и в CI наряду с `pnpm type-check` и `pnpm test`.

### Семантика глобальной validation

- Reference hit, not found, неоднозначность, фильтры и ошибочный result совпадают с текущей validation.
- Проверяется видимость `cf`, собственного `cfe` и запрет соседнего `cfe`.
- Owner-, field-, data-path- и form-проверки дают те же диагностики, что текущий shared graph.
- Неготовый первый проход `cf` воспроизводит текущую деградацию расширений без сохранения итоговых межфайловых диагностик.
- Отдельно закрываются ветви, которых не было в целевом каталоге эксперимента: missing reference, conflict, filter failure и межкомпонентная видимость.

### Инкрементальность

- Хэшируются все управляемые ресурсы, но при неизменном проекте не парсится ни один YAML.
- Пакеты хэшей структурно клонируются и передаются одним общим `ArrayBuffer` без отдельного буфера или `hashOffset` на файл; некорректная длина отклоняется на каждой границе.
- При изменении одного YAML локально проверяется только он, а глобальная validation выполняется целиком.
- Локальные ошибки неизменённого файла возвращаются из кэша.
- Изменение ошибочного YAML заменяет старые локальные диагностики.
- Удаление файла удаляет его индексный вклад и меняет глобальные диагностики зависимых файлов.
- Техническая ошибка не делает частично обновлённое состояние видимым.

### Операции

- Import строит индекс до уточнения полей, вычисляет хэши окончательных файлов, проверяет YAML без повторного чтения и сохраняет согласованный кэш.
- Sync блокируется error-диагностикой по умолчанию.
- Поиск ссылок актуализирует состояние перед запросом индекса и блокируется error-диагностикой по умолчанию.
- С `ignoreValidationErrors: true` поиск возвращает найденные обращения и диагностики, указывающие на возможную неполноту результата.
- Предварительный просмотр переименования актуализирует состояние один раз, фактическое переименование — до и после изменения файлов.
- Ошибки первого вызова блокируют переименование по умолчанию; второй вызов после записи обязателен.
- `ignoreValidationErrors: true` продолжает sync, поиск ссылок и переименование, но не пропускает validation и не скрывает диагностики.
- Техническая ошибка блокирует вызывающую операцию при любом значении параметра.
- Reset удаляет только runtime-кэш и не создаёт новый снимок.
- Rebuild заменяет состояние атомарно.
- Переключение единственного активного проекта не смешивает строки двух проектов.
- MCP-команды соблюдают договор `allowWrite`.

### Компактная сквозная проверка import и sync

- Для локальной сквозной проверки import и полной/частичной sync использовать компактную XML-выгрузку `/Users/nikita/git/round-trip-compact/cf/all` размером около 4,5 МБ.
- Исходная выгрузка используется только для чтения. YAML-проект, результирующая XML-выгрузка, кэш и прочие изменяемые файлы создаются во временном каталоге.
- Абсолютный путь не встраивается в production-код и обязательные CI-тесты: локальная проверка получает его как явный вход. Репозиторные тесты продолжают использовать собственные фикстуры.
- Один и тот же компактный сценарий проверяет раннюю запись import, построение project state, полную sync и выборочную sync после прогретой актуализации.

## Критерии приёмки

- На всех validation-фикстурах холодный и прогретый проходы возвращают полностью одинаковые массивы диагностик, включая пути, координаты, сообщения и порядок.
- На `/Users/nikita/git/nkdk-yaml` результат совпадает с холодной validation не только по числу, но и по содержимому диагностик.
- Прогретая validation неизменённого проекта хэширует все ресурсы и разбирает ноль YAML-файлов.
- Import и sync проходят локальную сквозную проверку на `/Users/nikita/git/round-trip-compact/cf/all`, не изменяя исходную XML-выгрузку.
- Нет постоянного полного дубликата индексов в SQLite и shared graph/`SharedArrayBuffer`.
- Холодный первый проход не замедляется более чем на 10% относительно обычного режима на целевом каталоге; отдельно публикуются полное время, Peak RSS, размер снимка, время загрузки и checkpoint.
- Прогретый проход показывает выигрыш от исключения парсинга неизменённых YAML.
- `pnpm check:duplicates -- --base <commit>` не находит клонов, хотя бы один диапазон которых пересекает добавленные реализацией строки.
- `pnpm test` проходит полностью.

Профилирование по этим критериям является проверкой готовой реализации, а не отдельным выбором новой СУБД.

## Последовательность реализации

Решение удобно доставлять тремя проверяемыми слоями:

1. Абстракции `ProjectStateStore` и `ProjectStateReadSession`, именованная SQLite в памяти, схема, загрузка/checkpoint, cold rebuild, reset и rebuild.
2. Инкрементальная validation: хэши, замена вкладов файлов, локальные диагностики из кэша и полный глобальный проход из SQLite.
3. Интеграция import, sync, поиска ссылок и переименования, включая общий договор `ignoreValidationErrors` и жизненный цикл одного активного проекта в MCP.

Перед началом первого слоя фиксируется исходный коммит для сравнения jscpd. Внутри задачи связанные договоры объединяются в TDD-блоки: один общий RED-набор, быстрые целевые тесты во время реализации и один узкий mutation-прогон после GREEN всего блока. После всех блоков задачи один раз выполняются `pnpm check:duplicates -- --base <commit>`, `pnpm type-check` и полный `pnpm test` непосредственно перед независимой рецензией; повторный полный прогон требуется только после исправлений рецензии или воспроизводимого сбоя. Новый слой не начинается при появлении нового дубля. Широкий mutation-прогон всех production-изменений этой реализации выполняется один раз перед итоговой приёмкой; его можно разбить на воспроизводимые пакетные запуски, но не сужать до выборочных строк.

Подробный план файлов и тестов составляется после рецензии этой спецификации.

# Постоянное состояние проекта для validation, import и sync

**Статус:** согласовано для реализации
**Дата:** 2026-08-01

## Контекст

Сейчас validation каждый раз читает и разбирает все YAML-файлы, заново собирает общий индекс и затем выполняет межфайловые проверки. Import и sync строят часть тех же сведений независимо. Из-за этого повторная validation неизменившегося проекта оплачивает полный первый проход, а актуальность хэшей, индексов и диагностик не выражена единым договором.

Эксперимент с параллельной записью полных вкладов в SQLite был отклонён: он дублировал данные в памяти и замедлил первый проход на 28,6%. Следующий эксперимент сделал нормализованную SQLite `:memory:` единственным хранилищем reference-части. На `/Users/nikita/git/nkdk-yaml` он сохранил точный результат validation, ускорил полный проход на 10,3% и снизил Peak RSS на 16%. Поэтому целевая архитектура развивает второй вариант и не вводит ещё один полный буфер индекса.

## Цели

- Иметь одно согласованное runtime-состояние всего YAML-проекта для validation, import и sync.
- При каждой validation вычислять хэши всех управляемых правилами ресурсов, но локально разбирать и проверять только новые и изменённые YAML-файлы.
- Заменять в общем индексе только вклады изменённых файлов и удалять вклады исчезнувших файлов.
- При каждом запуске выполнять межфайловую validation целого проекта по актуальному индексу.
- Сохранять локальные диагностики неизменённых файлов и возвращать полный результат проекта без их повторной проверки.
- Загружать состояние с диска лениво при первом обращении MCP к проекту и фиксировать его после каждой завершённой операции.
- Скрыть SQLite за абстрактным хранилищем, чтобы прикладная логика не зависела от выбранной СУБД.
- Не дублировать пути, хэши и полные представления индекса в нескольких таблицах или постоянных структурах памяти.

## Не входит в решение

- Публичная validation отдельного файла или компонента.
- Кэширование итоговых межфайловых диагностик: они всегда пересчитываются для всего проекта.
- Использование `mtime` вместо чтения и хэширования содержимого.
- Изменение формата снимка конфигурации, используемого sync. Он остаётся отдельной точкой подтверждённого состояния XML.
- Одновременная работа одного процесса MCP с несколькими активными проектами.
- Новый цикл экспериментов с СУБД. Следующий шаг — реализация с проверками договора и итоговым профилированием.

## Основные решения

### Одно состояние на проект

Runtime-кэш принадлежит всему проекту, включая `cf` и все `cfe/<имя>`. Компонент остаётся атрибутом файла и индексной строки, а не отдельной базой. Это позволяет выражать видимость `cf → cf` и `cfe/<имя> → своё расширение, затем cf` одним набором запросов и не копировать сведения основной конфигурации в каждое расширение.

Публичная validation не получает ключ файла или компонента. Она всегда возвращает диагностики всего проекта.

### SQLite в памяти как основное представление

Во время работы основным источником хэшей, локальных результатов и глобальных индексов является SQLite `:memory:`. Отдельный полный `SharedArrayBuffer`, объектный граф или набор `Map`, повторяющий те же индексные строки, не создаётся.

SQLite принадлежит отдельному project-state worker. Validation worker не открывают базу и не выполняют SQL. Они читают файлы, вычисляют хэши, а для изменённых YAML выполняют парсинг, локальную validation и извлечение нормализованных вкладов. Обмен идёт ограниченными пачками с обратным давлением.

Межфайловые проверки выполняются в project-state worker:

- reference-проверки разрешаются массовыми SQL-запросами с приоритетом видимого компонента;
- owner-, field-, data-path- и form-проверки читают нормализованные строки из SQLite;
- если существующую проверку целесообразно оставить в TypeScript, worker получает её вход пакетами из SQL и не строит долгоживущую полную копию базы.

### Абстракция хранилища

Общая логика зависит от договора `ProjectStateStore`, а не от `node:sqlite`. Договор отвечает за:

- открытие и проверку совместимости состояния проекта;
- сравнение актуальных хэшей с сохранёнными;
- транзакционную замену вклада файла;
- удаление исчезнувших файлов;
- чтение сохранённых локальных диагностик;
- полную проверку межфайловых зависимостей;
- фиксацию, откат, создание дискового снимка, сброс и закрытие.

SQLite-реализация находится на границе project-state слоя. Оркестрация metadata не получает условий по конкретным `itemType`, именам файлов или типам прикладных объектов.

## Дисковое состояние и жизненный цикл

Снимок хранится в `.nkdk/cache/project-state.sqlite`. Он не является источником пользовательских данных и может быть полностью восстановлен из проекта.

MCP держит один активный проект:

1. При первом вызове с `projectDir` project-state worker лениво загружает весь совместимый дисковый снимок в SQLite `:memory:`.
2. Следующие операции используют ту же базу в памяти.
3. При переключении проекта предыдущая завершённая операция уже имеет снимок на диске; worker закрывает старую базу и загружает новый проект.
4. Операции изменения состояния сериализуются. Две validation или validation и sync не меняют один проект параллельно.
5. При штатном завершении процесса новых смысловых данных не фиксируется: каждая завершённая операция уже создала снимок.

Если снимок отсутствует, повреждён или несовместим, операция начинает холодное построение. Повреждение кэша не является диагностикой YAML-проекта. Ошибка полного восстановления или публикации нового снимка является технической ошибкой операции.

## Совместимость состояния

В `cache_meta` хранятся как минимум:

- версия схемы кэша;
- версия производителя NKDK;
- отпечаток правил структуры, схем и локальной validation;
- алгоритм и версия хэша.

При несовпадении любого смыслового отпечатка старый снимок не мигрирует данные validation частично, а считается недоступным. Новая база строится холодно и заменяет старый файл только после успешной операции. Миграции допустимы позднее только для заведомо структурных изменений, не меняющих смысл сохранённых результатов.

## Модель данных

Точные столбцы уточняются по существующим типам первого и второго проходов, но границы таблиц и правила нормализации обязательны.

| Группа | Назначение |
|---|---|
| `cache_meta` | Версии и отпечатки совместимости. |
| `components` | Уникальный путь компонента: `cf` или `cfe/<имя>`. |
| `project_files` | Уникальный относительный путь, ссылка на компонент, вид ресурса и роль YAML. Путь хранится один раз. |
| `file_hashes` | Текущий xxHash64 по `file_id`. Хэш отделён от идентичности файла и не повторяется в индексах или результатах validation. |
| `file_validation_results` | Признак, что локальная validation выполнена для текущего состояния файла, а также необходимые для текущей семантики признаки schema-готовности и `contributed_facts`. Строка не содержит копию хэша. Отсутствие строки означает, что файл ещё не проверен либо результат признан несовместимым. |
| `local_diagnostics` | Сохранённые синтаксические, schema- и локальные диагностики YAML с координатами и ссылкой на исходный файл. |
| `reference_entries` | Нормализованные object/member/value entries, принадлежащие исходному YAML-файлу. |
| `pending_references` | Отложенные reference-проверки с фильтрами, координатами и исходным файлом. |
| `owner_facts` и `field_entries` | Нормализованные сведения владельцев, полей, табличных частей и стандартных псевдонимов. |
| `pending_dependency_checks` | Data-path, form и прочие отложенные проверки с типом и минимальным набором параметров. |
| `file_dependencies` | Локальные зависимости между ресурсами, если они нужны для определения затронутых единиц sync или составного YAML. |

Индексные и отложенные строки всегда содержат `source_file_id`; `component_id` получается через файл и не копируется без измеренной необходимости для индекса SQL. Удаление `project_files` каскадно удаляет хэш, локальный результат и все вклады файла.

Большие объектные JSON/BLOB-вклады рядом с нормализованными строками не хранятся. JSON допустим только для небольшого типизированного параметра проверки, который не раскладывается без значительного усложнения и не повторяет другие таблицы. Повторяющиеся строки внутри самих индексных ключей считаются содержимым индекса; отдельный словарь строк вводится только по результатам профилирования, а не заранее.

## Инварианты согласованности

- `project_files` задаёт идентичность файла; `file_hashes` задаёт только его текущее содержимое.
- Локальные диагностики и индексные строки относятся к текущему хэшу не через продублированный столбец, а через общую транзакцию файла.
- При изменении файла старые `file_validation_results`, диагностики и индексные строки удаляются до вставки новых в той же транзакции.
- При удалении файла его вклад исчезает целиком до межфайловой validation.
- При диагностических ошибках YAML новое состояние всё равно фиксируется: неизменившийся ошибочный файл не проверяется локально повторно.
- При технической ошибке или отмене вся транзакция состояния откатывается и дисковый снимок не заменяется.
- Межфайловые диагностики в базе не сохраняются и к поколению индекса не привязываются.
- Полный итог validation равен холодной validation того же содержимого независимо от истории кэша.

## Хэширование и определение изменений

Список файлов строится по `rules.ts`. Validation читает все управляемые правилами ресурсы и вычисляет xxHash64 по исходным байтам. Это относится не только к YAML, но и к BSL, HTML, изображениям и другим внешним файлам: их хэши нужны для корректного состава sync.

Project-state worker сравнивает полный актуальный список с `project_files` и `file_hashes` и возвращает:

- новые файлы;
- файлы с изменившимся хэшем;
- неизменённые файлы;
- удалённые файлы.

Только новые и изменённые YAML передаются на парсинг и локальную validation. Неизменённый YAML использует сохранённые локальные диагностики и индексный вклад. Не-YAML ресурсы обновляют хэш, но сами по себе не создают validation-индекс. Если правила объявляют несколько файлов одной неделимой validation-единицей, изменение одного файла затрагивает всю эту единицу; такой договор должен быть явным в правилах.

## Проход validation

| Шаг | Исполнитель | Действие |
|---|---|---|
| 1 | Основной поток | Находит и классифицирует все управляемые правилами файлы проекта. |
| 2 | Validation worker | Читает исходные байты и вычисляет xxHash64 всех файлов без парсинга YAML. |
| 3 | Project-state worker | Сравнивает хэши и определяет новые, изменённые, неизменённые и удалённые файлы. |
| 4 | Validation worker | Только для новых и изменённых YAML выполняет парсинг, JSON Schema, локальные проверки и извлечение нормализованных индексных строк. |
| 5 | Project-state worker | Начинает транзакцию, удаляет старые вклады изменённых и удалённых файлов, записывает новые хэши, локальные диагностики и индексные строки. |
| 6 | Project-state worker | Выполняет полную межфайловую validation по всем актуальным строкам SQLite. |
| 7 | Основной поток | Объединяет сохранённые и новые локальные диагностики с новыми межфайловыми, удаляет повторы и стабильно сортирует результат. |
| 8 | Project-state worker | Фиксирует транзакцию даже при validation-ошибках и атомарно обновляет дисковый снимок. При технической ошибке откатывает транзакцию. |

Если файлы не изменились, шаг 4 не парсит ни одного YAML, но шаг 6 всё равно проверяет зависимости всего проекта. Это намеренный договор: изменение индекса любого файла потенциально влияет на диагностику любого другого файла, а итоговые межфайловые результаты не кэшируются.

Перед глобальными проверками project-state worker вычисляет готовность компонентов из сохранённых и новых результатов файлов. Если первый проход `cf` не готов, сохраняется действующая семантика деградации: глобальные проверки расширений не выполняются, их schema-диагностики публикуются, и каждому затронутому расширению добавляется блокирующая диагностика. Эти итоговые диагностики не записываются в кэш, а воспроизводятся при каждом проходе.

Видимость reference и других глобальных записей сохраняет текущую семантику:

- `cf` видит только `cf`;
- `cfe/<имя>` сначала видит своё расширение, затем `cf`;
- расширение не видит соседние расширения;
- неоднозначность определяется в выбранном приоритетном слое, а не между всеми слоями сразу.

## Import

Import использует то же `ProjectStateStore`, но не обязан повторно читать только что записанный YAML:

1. По мере готовности окончательного YAML import worker вычисляет его хэш и передаёт байты в тот же договор локальной validation, после чего отправляет результат и нормализованный вклад project-state worker. Повторно читать уже записанный файл для этого не требуется, но обход schema- и локальных проверок не допускается.
2. Worker сразу пишет поступающие данные в открытую транзакцию SQLite `:memory:`. Ждать окончания import перед записью в СУБД не нужно.
3. После записи всех файлов сверяется окончательная структура проекта, удаляются исчезнувшие вклады и выполняется полная межфайловая validation.
4. Диагностики проекта возвращаются отдельно и не отменяют import: YAML к этому моменту уже записан, а import не является транзакцией файловой системы.
5. Успешно завершённое состояние фиксируется и публикуется на диск. Техническая ошибка откатывает базу, но уже записанные файлы остаются; следующая операция обнаружит их по хэшам и восстановит кэш.

Таким образом, в SQLite в памяти пишем сразу, а долговечный снимок заменяем только в конце завершённой операции.

## Sync

Полная и частичная sync всегда начинают с того же прохода обновления состояния и полной validation. Поэтому XML строится по актуальным хэшам и индексам.

По умолчанию diagnostics уровня error блокируют sync до обращения к 1С. Предупреждения не блокируют. Параметр `ignoreValidationErrors: true` разрешает продолжить sync при обычных validation-ошибках, но:

- validation всё равно выполняется полностью;
- актуальное состояние и локальные диагностики всё равно фиксируются;
- ошибки возвращаются вызывающей стороне вместе с результатом;
- технические ошибки чтения, SQLite, worker или проверки целостности никогда не игнорируются.

Параметр не называется `skipValidation`, потому что validation и обновление индекса не пропускаются.

## Снимок на диск

После каждой завершённой validation, import или sync SQLite `:memory:` копируется во временный файл в `.nkdk/cache`. Публикация состоит из следующих шагов:

1. Создать уникальный временный файл в том же каталоге.
2. Выполнить SQLite backup текущей базы.
3. Выполнить `quick_check` временной базы.
4. Синхронизировать файл с диском.
5. Атомарно переименовать его в `project-state.sqlite`.
6. Синхронизировать каталог, где это поддерживается платформой.

Старый снимок остаётся пригодным до последнего шага. Временный файл после ошибки удаляется. Для SQLite используется встроенный `node:sqlite`; внешняя служба и отдельная зависимость не требуются.

## Служебные команды MCP

### `nkdk.reset_project_cache`

- Принимает `projectDir`, но не ключ файла или компонента.
- Требует `allowWrite: true`, поскольку удаляет файл внутри проекта.
- Закрывает активную базу без checkpoint, если открыт этот проект.
- Удаляет только runtime-состояние в памяти и `.nkdk/cache/project-state.sqlite`.
- Не запускает validation или перестроение.
- Не затрагивает снимок конфигурации sync.
- Следующая операция выполняет холодное построение.

### `nkdk.rebuild_project_cache`

- Принимает `projectDir`, но не ключ файла или компонента.
- Требует `allowWrite: true` из-за публикации `.nkdk/cache/project-state.sqlite`.
- Строит новое состояние всего проекта в отдельной базе, выполняет полную validation и проверку целостности.
- Атомарно заменяет активное и дисковое состояние только после успешного завершения.
- Возвращает полный набор диагностик. Обычные validation-ошибки не мешают сохранить корректно построенный кэш; технические ошибки оставляют прежнее состояние без изменений.

Сброс нужен для удаления, rebuild — для явного восстановления здесь и сейчас. Они не объединяются, чтобы после сброса пользователь мог сохранить холодное состояние до следующей обычной операции.

## Ошибки и отмена

Различаются два класса неуспеха:

- **Диагностики проекта:** синтаксис YAML, JSON Schema, локальные правила и межфайловые зависимости. Они являются корректным результатом, сохраняются в локальной части кэша и не откатывают транзакцию состояния.
- **Техническая ошибка:** невозможность прочитать файл, сбой worker/SQLite, нарушение протокола, `quick_check`, отмена операции. Она откатывает транзакцию и не публикует новый снимок.

Если содержимое файлов изменилось параллельно с операцией между хэшированием и публикацией, реализация должна обнаружить это повторной проверкой сведений об обработанных файлах либо признать снимок недействительным и повторить проход ограниченное число раз. Нельзя публиковать состояние, заведомо не соответствующее файловой системе.

## Проверки реализации

Тесты следуют существующей архитектуре тестов и проверяют наблюдаемый договор, а не конкретные SQL-тексты.

### Хранилище

- Путь и компонент не дублируются в индексных таблицах, хэш отделён от файла.
- Замена изменённого файла и каскадное удаление исчезнувшего не оставляют старых строк.
- Ошибка внутри обновления откатывает весь вклад.
- Backup загружается обратно с тем же состоянием.
- Повреждённый, несовместимый и незавершённый снимок приводят к холодному восстановлению, не к частичному чтению.
- Ошибка атомарной публикации сохраняет предыдущий снимок.

### Семантика глобальной validation

- Reference hit, not found, неоднозначность, фильтры и ошибочный result совпадают с текущей validation.
- Проверяется видимость `cf`, собственного `cfe` и запрет соседнего `cfe`.
- Owner-, field-, data-path- и form-проверки дают те же диагностики, что текущий shared graph.
- Неготовый первый проход `cf` воспроизводит текущую деградацию расширений без сохранения итоговых межфайловых диагностик.
- Отдельно закрываются ветви, которых не было в целевом каталоге эксперимента: missing reference, conflict, filter failure и межкомпонентная видимость.

### Инкрементальность

- Хэшируются все управляемые ресурсы, но при неизменном проекте не парсится ни один YAML.
- При изменении одного YAML локально проверяется только он, а глобальная validation выполняется целиком.
- Локальные ошибки неизменённого файла возвращаются из кэша.
- Изменение ошибочного YAML заменяет старые локальные диагностики.
- Удаление файла удаляет его индексный вклад и меняет глобальные диагностики зависимых файлов.
- Техническая ошибка не делает частично обновлённое состояние видимым.

### Операции

- Import пишет вклад по мере готовности, возвращает validation-ошибки и сохраняет согласованный кэш.
- Sync блокируется error-диагностикой по умолчанию.
- `ignoreValidationErrors: true` продолжает sync, но не пропускает validation и не скрывает диагностики.
- Техническая ошибка блокирует sync при любом значении параметра.
- Reset удаляет только runtime-кэш и не создаёт новый снимок.
- Rebuild заменяет состояние атомарно.
- Переключение единственного активного проекта не смешивает строки двух проектов.
- MCP-команды соблюдают договор `allowWrite`.

## Критерии приёмки

- На всех validation-фикстурах холодный и прогретый проходы возвращают полностью одинаковые массивы диагностик, включая пути, координаты, сообщения и порядок.
- На `/Users/nikita/git/nkdk-yaml` результат совпадает с холодной validation не только по числу, но и по содержимому диагностик.
- Прогретая validation неизменённого проекта хэширует все ресурсы и разбирает ноль YAML-файлов.
- Нет постоянного полного дубликата индексов в SQLite и shared graph/`SharedArrayBuffer`.
- Холодный первый проход не замедляется более чем на 10% относительно обычного режима на целевом каталоге; отдельно публикуются полное время, Peak RSS, размер снимка, время загрузки и checkpoint.
- Прогретый проход показывает выигрыш от исключения парсинга неизменённых YAML.
- `pnpm test` проходит полностью.

Профилирование по этим критериям является проверкой готовой реализации, а не отдельным выбором новой СУБД.

## Последовательность реализации

Решение удобно доставлять тремя проверяемыми слоями:

1. Абстракция `ProjectStateStore`, SQLite `:memory:`, схема, загрузка/checkpoint, cold rebuild, reset и rebuild.
2. Инкрементальная validation: хэши, замена вкладов файлов, локальные диагностики из кэша и полный глобальный проход из SQLite.
3. Интеграция import и sync, включая `ignoreValidationErrors` и жизненный цикл одного активного проекта в MCP.

Подробный план файлов и тестов составляется после рецензии этой спецификации.

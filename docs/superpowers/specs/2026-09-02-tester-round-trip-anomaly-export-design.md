# Исправление экспорта XML-аномалий Tester

**Статус:** согласовано

**База сравнения:** `0c879181b23384cfa868d63d0765f455d021f3eb` (`origin/develop` на момент создания worktree)

## Контекст

Round-trip конфигурации `Tester_1_0_10_34_setup1c` импортирует XML, но полная
синхронизация YAML → XML останавливается на двух ошибках:

1. `ПорядокПодсистем` содержит UUID отсутствующих подсистем. Импорт сохраняет
   такие значения как `!xml/invalid`, однако обычный экспорт повторно отклоняет
   их как неизвестные ссылки.
2. У табличного `InputField` исходный XML содержит `FixingInTable` перед
   `CellHyperlink`. Текущее правило `TableInputField` ожидает обратный порядок,
   импорт ошибочно создаёт `!xml/raw`, а экспорт raw-поправки строит путь
   `InputField\InputField` вместо применения поправки к уже выбранному
   `InputField`.
3. После устранения двух падений выявлено 98 одинаковых расхождений: формы
   Tester не объявляют необязательное пространство имён `dcssch`, а экспорт
   добавляет его безусловно.

Проверка каталога `/Users/nikita/git/round-trip-compact/cf` без `all` и `clean`
нашла 683 табличных поля, в которых одновременно присутствуют `FixingInTable`
и `CellHyperlink`. Во всех случаях `FixingInTable` расположен первым. Правила
`TableCheckBoxField`, `TableLabelField` и `TablePictureField` уже используют
этот порядок; отличается только `TableInputField`.

## Цели

- Экспортировать неразрешимую metadata-ссылку без изменения, только если
  конкретное YAML-вхождение принято тегом `!xml/invalid` или `!xml/important`.
- Считать `FixingInTable` → `CellHyperlink` каноническим порядком
  `TableInputField`.
- Применять raw-поправку корня элемента формы к текущему экспортированному
  XML-элементу, когда внутренний `itemType` отличается от физического
  `xmlTag`.
- Восстанавливать присутствие необязательного `xmlns:dcssch` по
  configuration index без служебного YAML-поля.
- Получить успешный round-trip `Tester_1_0_10_34_setup1c` без потери XML.

## Решение

### 1. Точное разрешение принятой metadata-ссылки

`metadataTargetOccurrences` продолжает преобразовывать каждую metadata-ссылку
отдельно. При неудачном разборе UUID разрешается сохранить без преобразования,
если выполняется хотя бы одно условие:

- идёт контрольный экспорт XML-импорта, где это уже разрешено действующим
  договором;
- точное вхождение значения или ключа имеет семантическую аннотацию
  `!xml/invalid` либо `!xml/important`.

Проверка аннотации выполняется по `MetadataTargetOccurrence.location` и
исходному YAML-дереву. Аннотация родителя, соседнего элемента или другого
повтора не разрешает текущее значение. Обычный UUID без тега по-прежнему
вызывает ошибку.

Для аннотированного YAML-ключа преобразование использует его `logicalKey` из
таблицы аннотаций, а не технический ключ разобранного объекта. Поэтому принятый
UUID сохраняется буквально, а обычная допустимая ссылка по-прежнему получает
канонический XML-префикс.

Аннотации не копируются в изменяемый клон значения и не превращаются в поля
правил. Оркестратор передаёт преобразованию функцию, которая отвечает только на
вопрос, принято ли конкретное вхождение.

### 2. Канонический порядок TableInputField

В `TableInputFieldRules.xmlOrder` `fixingInTable` располагается непосредственно
перед `cellHyperlink`, как в исследованных XML и соседних правилах табличных
полей. Новая XML-фикстура и новый `!xml/raw` для этого не требуются.

Если исходный XML действительно использует иной порядок, общий контрольный
экспорт по-прежнему имеет право сохранить его существующим `!xml/raw`.

### 3. Физический XML-тег raw-границы

При определении, относится ли публичный путь raw к текущему элементу,
`fullSyncToXml` сравнивает последний сегмент не только с внутренним
`rule.itemType`, а с физическим именем элемента:

- `rule.xmlTag`, если правило его объявляет;
- иначе `rule.itemType`.

Для `TableInputField` это означает соответствие
`TableInputField` ↔ `InputField`. Raw-поправка `@Form\InputField` получает путь
`$item` и накладывается на уже экспортированную колонку, не создавая
`InputField\InputField`.

Механизм остаётся нейтральным: в `fullSyncToXml` не добавляются проверки
конкретных `itemType`, имён форм или видов колонок. Общие типы `PropertyRule` и
`BasePropertyRule` не расширяются.

### 4. Необязательное пространство имён формы

При импорте формы наличие `xmlns:dcssch` фиксируется в configuration index по
дочернему адресу формы. Сохраняется именно состояние `present` либо `absent`,
поэтому отсутствие записи остаётся отдельным случаем новой формы, для которой
действует прежний полный набор пространств имён.

При экспорте форма читает это состояние из configuration index:

- `absent` — не добавляет `xmlns:dcssch`;
- `present` — добавляет каноническое объявление;
- записи нет — сохраняет прежнее поведение и добавляет объявление для новой
  формы.

Прочитанное состояние переносится в новый configuration index экспорта. Это
предметная часть адаптера управляемой формы: общие metadata-слои и типы правил
не получают условий по имени пространства.

## Проверки

1. `RootCommandInterface` экспортирует UUID из
   `ПорядокПодсистем: [!xml/invalid <uuid>]` без изменения.
2. Соседний или такой же UUID без тега продолжает отклоняться.
3. Экспорт нового `TableInputField` располагает `FixingInTable` перед
   `CellHyperlink`.
4. Полная сериализация формы применяет `@Form\InputField` с `#order` к текущей
   табличной колонке, сохраняет один `InputField` и заданный порядок.
5. Форма без `xmlns:dcssch` после XML → YAML → XML остаётся без него; форма с
   объявлением и новая форма продолжают его получать.
6. Целевые тесты, `pnpm type-check`, проверка дублей относительно базы,
   архитектурные проверки и полный `pnpm test` не обнаруживают регрессий.
7. Диагностический round-trip `Tester_1_0_10_34_setup1c` завершается без ошибок
   и расхождений.

## Границы

- Новые применения `!xml/raw`, `!xml/invalid` или `!xml/important` не вводятся.
- Существующие XML-фикстуры не изменяются.
- Неразрешимые metadata-ссылки без точного семантического тега не разрешаются.
- `.agents/architecture.md` менять не требуется: его действующий договор уже
  требует, чтобы принятые смысловые значения оставались доступны экспорту, а
  нейтральный runtime не знал конкретные metadata-типы.
- Исправление нестабильных лимитов длительности исходного `pnpm test` не входит
  в задачу. При проверке отдельно учитываются результаты assertions и исходное
  состояние базы.

# Декларативная матрица частичной синхронизации

## Цель

Расширить ручной внешний сценарий частичной синхронизации так, чтобы он
последовательно проверял создание каждого поддерживаемого корневого типа
метаданных, добавление каждой поддерживаемой комбинации дочернего элемента с
его владельцем, создание одной формы у каждого поддерживающего формы владельца,
а затем удаление всего добавленного в обратном порядке.

Каждое отдельное изменение является самостоятельным этапом:

1. изменить NKDK-проект;
2. проверить проект;
3. выполнить частичную синхронизацию;
4. повторить синхронизацию и получить `unchanged`;
5. импортировать `cf` в проверочный проект и сравнить деревья;
6. атомарно заменить единственную контрольную копию.

Расширение на этом этапе не импортируется и не сравнивается. Сценарий остаётся
ручным и не входит в `pnpm test`, `pnpm test:e2e` или CI.

## Полнота матрицы

Матрица содержит по одному минимальному объекту каждого правила из
`TopLevelMetadataItemRules`. На момент проектирования это 47 типов:

- справочник, документ, обработка, отчёт, журнал документов;
- HTTP-сервис, Web-сервис, сервис интеграции, WebSocket-клиент и WS-ссылка;
- регистры сведений, накопления, бухгалтерии и расчёта;
- план обмена, нумератор, перечисление и последовательность;
- планы счетов, видов расчёта и видов характеристик;
- бизнес-процесс и задача;
- внешний источник данных;
- определяемый тип, параметр сеанса, подписка на событие и критерий отбора;
- функциональная опция и параметр функциональной опции;
- константа, общий реквизит, хранилище настроек и элемент стиля;
- роль, регламентное задание и язык;
- общий макет, модуль, форма, картинка и команда;
- группа команд, подсистема, стиль, пакет XDTO и бот.

Обычный тест сравнивает множество типов матрицы с
`TopLevelMetadataItemRules`. Добавление или удаление правила требует явного
обновления сценария.

Для каждого корневого владельца матрица явно перечисляет все поддерживаемые
его правилами коллекции дочерних объектов. В их число входят, где применимо:

- реквизиты;
- табличные части и реквизиты табличных частей;
- измерения, ресурсы и реквизиты регистров;
- реквизиты адресации задачи;
- колонки журнала документов;
- команды, формы, макеты и вложенные подсистемы;
- предопределённые элементы;
- шаблоны URL и методы HTTP-сервиса;
- операции и параметры Web-сервиса;
- каналы сервиса интеграции;
- таблицы, поля, функции, кубы, измерения и ресурсы внешнего источника данных;
- остальные зарегистрированные коллекции метаданных, доступные владельцу.

Проверка полноты дочерних комбинаций извлекает коллекционные возможности из
правил владельца и сравнивает их с декларациями. Исключение допускается только
как именованная запись с причиной, чтобы неподдержанная комбинация была видна в
отчёте, а не молча пропускалась.

Для каждого владельца, поддерживающего формы, матрица создаёт ровно одну
минимальную форму. Проверка всех назначений форм в этот сценарий не входит.

## Декларативная модель

Матрица не выполняет файловых или платформенных операций. Она описывает
исходные данные, зависимости и возможности объекта. Декларация корневого
объекта содержит:

- стабильный ключ типа и русское имя каталога NKDK;
- уникальное тестовое имя объекта;
- минимальный набор файлов объекта и их содержимое;
- ключи объектов, которые должны быть созданы раньше;
- декларации поддерживаемых дочерних элементов;
- необязательную декларацию минимальной формы.

Из матрицы строится линейный план из ограниченного набора операций:

```ts
type ScenarioOperation =
  | { kind: "create-object"; key: string; changes: readonly ScenarioFileChange[] }
  | { kind: "add-child"; key: string; ownerKey: string; changes: readonly ScenarioFileChange[] }
  | { kind: "add-form"; key: string; ownerKey: string; changes: readonly ScenarioFileChange[] }
  | { kind: "remove"; key: string; targetKey: string; changes: readonly ScenarioFileChange[] }

type ScenarioFileChange = {
  path: string
  before: string | Uint8Array | null
  after: string | Uint8Array | null
}
```

Исполнитель знает только семантику этих четырёх операций. Особенности типов,
пути, YAML и дополнительные файлы находятся в матрице. `null` означает
отсутствующий файл. Перед применением исполнитель побайтово проверяет состояние
`before`; обратная операция автоматически меняет `before` и `after` местами.
Поэтому удаление inline-дочернего элемента восстанавливает прежний
`Свойства.yaml`, а не удаляет файл владельца. Зависимости образуют
ацикличный граф; создание выполняется в его топологическом порядке, удаление —
в обратном. Порядок групп фиксирован:

1. создание всех корневых объектов;
2. добавление всех дочерних элементов;
3. добавление форм;
4. удаление форм;
5. удаление дочерних элементов;
6. удаление корневых объектов.

Каждая операция имеет стабильный ключ, не зависящий от порядкового номера.
Человекочитаемый номер вычисляется только для вывода прогресса.

Первичная подготовка базы является отдельной начальной фазой, а не скрытой
операцией матрицы. После полной загрузки и контрольного импорта она публикует
`checkpoints/current` с `completedOperation: null`. Поэтому сбой на первой
операции также восстанавливается из подтверждённого исходного состояния.

## Исполнение и проверка

После применения одной операции универсальный исполнитель:

1. вызывает `nkdk.validate_project` и отклоняет любую ошибку;
2. вызывает `nkdk.sync_to_infobase` для `cf` и ожидает `synchronized`;
3. повторяет вызов и ожидает `unchanged`;
4. закрывает соединение с рабочим проектом;
5. импортирует `cf` из базы в очищенный проверочный проект;
6. побайтово сравнивает проектный и проверочный `cf` без служебного `.nkdk`;
7. публикует контрольную копию;
8. выводит ключ операции, длительность и общий прогресс.

Расширение не участвует в этом цикле. Исходная конфигурация и база создаются
тем же проверенным механизмом, что и в существующем сценарии.

## Единственная контрольная копия

Сценарий хранит только `checkpoints/current`. Публикация выполняется безопасно:

1. база и NKDK-проект копируются во временный каталог;
2. для файлов строится manifest SHA-256;
3. временная копия полностью проверяется;
4. прежняя `current` переименовывается в служебную предыдущую копию;
5. проверенная временная копия переименовывается в `current`;
6. атомарно записывается `state.json`;
7. предыдущая копия удаляется.

При ошибке переключения или записи `state.json` новая `current` удаляется, а
предыдущая копия возвращается на место. Сбой до успешной записи состояния не
подтверждает операцию. При запуске рабочая база и проект восстанавливаются из
`current`, после чего выполняется следующая операция.

`state.json` версии 2 хранит:

- имя нового сценария;
- ключ последней завершённой операции либо `null`;
- относительный путь `checkpoints/current` либо `null`;
- SHA-256 канонического представления декларативного плана.

Несовпадение хэша плана останавливает запуск до изменения базы. Это защищает от
продолжения по другой матрице с тем же ключом этапа.

## Сброс старого сценария

Состояние существующего трёхэтапного сценария несовместимо с новой матрицей.
Команда без дополнительных параметров не удаляет его и сообщает о
несовместимости. Явный параметр `--reset` разрешает удалить только управляемые
пути уже распознанного каталога сценария, кроме накопленных журналов, создать
состояние версии 2 и заново подготовить исходную базу. Неизвестный каталог и
символические ссылки остаются запрещены.

## Диагностика и устойчивость

Журналы попыток не входят в контрольную копию и не удаляются при её замене.
Ошибка этапа содержит:

- стабильный ключ операции и позицию в плане;
- тип и имя владельца;
- вид дочернего элемента, если применимо;
- изменённые пути NKDK;
- каталог журналов и отчёта сравнения.

Проверочный каталог может очищаться и переиспользоваться после каждого этапа.
Незавершённые временные копии удаляются при следующем безопасном открытии
каталога сценария только после проверки, что их имена принадлежат механизму.

## Автоматические проверки

Быстрые тесты без установленной платформы защищают следующие договоры:

- матрица в точности покрывает `TopLevelMetadataItemRules`;
- ключи объектов и операций уникальны;
- все зависимости существуют и граф не содержит циклов;
- каждая поддерживаемая комбинация владельца и дочернего правила объявлена или
  имеет именованное исключение с причиной;
- каждому поддерживающему формы владельцу соответствует одна форма;
- план создаёт зависимости раньше потребителей и удаляет их позже;
- каждая операция изменяет только объявленные пути;
- исполнитель не публикует контрольную копию при ошибке любого шага;
- атомарная замена сохраняет предыдущую копию при сбое;
- восстановление продолжает со следующего стабильного ключа;
- несовпадение хэша плана останавливает исполнение;
- `--reset` работает только внутри распознанного управляемого каталога.

Реальный внешний тест остаётся одним длинным сценарием. Его уникальный договор —
каждое объявленное изменение действительно принимается платформой через
частичную синхронизацию и полностью возвращается контрольным импортом.

## Ожидаемая длительность

Один этап включает две синхронизации, полный контрольный импорт и копирование
базы. При десятках корневых объектов и множестве комбинаций дочерних элементов
полный прогон может занимать часы. Это принято сознательно: отдельный этап и
контрольная копия после каждого изменения важнее скорости ручной проверки.

# Разбор GraphStub и канонические id графа

Дата: 2026-05-25
Тип: рабочий дизайн-документ.

## Контекст

В живом FalkorDB-графе `nkdk_1f5594ee3af5` найдено `63 646` узлов с меткой
`GraphStub`. По выборке большая часть выглядит не как настоящие отсутствующие
цели, а как реальные метаданные, которым не достался канонический id или
предметный тип.

Основные входящие связи к `GraphStub`:

| kind | yaml | Количество |
| --- | --- | ---: |
| `COMMAND_NAME` | `ИмяКоманды` | `42 828` |
| `DATA_PATH_DEPENDS_ON` | `ЗависимостьПутиКДанным` | `26 105` |
| `DATA_PATH` | `ПутьКДанным` | `26 099` |
| `TYPE` | `Тип` | `21 569` |

## Базовый инвариант

`id` узла графа должен быть модельным путём с техническими английскими
сегментами. Русские имена остаются в YAML-ключах, `name`, `yaml` на рёбрах и
других человекочитаемых свойствах.

Примеры канонических путей:

| Сейчас | Целевой id |
| --- | --- |
| `Справочник.Товары` | `Catalog.Товары` |
| `Документ.Заказ` | `Document.Заказ` |
| `...Форма.ФормаСписка` | `...Form.ФормаСписка` |
| `...Команда.Печать` | `...Command.Печать` |
| `...Реквизит.Контрагент` | `...Attribute.Контрагент` |

Это несовместимое изменение формата graph id. Его нужно делать как целостную
миграцию построения графа и связанных резолверов, а не точечно подменять только
отдельные ссылки.

## Случай 1: `COMMAND_NAME` для `Form.Command.*`

### Наблюдение

`COMMAND_NAME` даёт крупнейшую группу `GraphStub`. Внутри неё:

| Группа значения `CommandName` | Количество |
| --- | ---: |
| `Form.Command.*` | `29 411` |
| `Form.StandardCommand.*` | `5 798` |
| `Form.Item.*.StandardCommand.*` | `5 777` |
| Прочее | `1 842` |

Для `Form.Command.*` все найденные stub-цели резолвятся в реальные команды
формы: если заменить старый путь `...Команда.Form.Command.<name>` на
`...Команда.<name>`, находится `25 361` существующий узел `FormCommand`.

### Причина

Сейчас граф смешивает два пространства имён:

- узлы команд формы создаются с русским служебным сегментом
  `...Форма.<form>.Команда.<name>`;
- значение из XML/модели `Form.Command.<name>` добавляется к этому сегменту как
  строка, поэтому ссылка ведёт в `...Команда.Form.Command.<name>`.

После принятия базового инварианта оба варианта считаются неканоническими:
правильная цель должна иметь английские технические сегменты.

### Решение

Канонический id команды формы:

```text
<OwnerKind>.<OwnerName>.Form.<FormName>.Command.<CommandName>
```

Для значения `CommandName = "Form.Command.<CommandName>"` ребро
`COMMAND_NAME` должно вести прямо в этот узел. Stub-узел для такого значения не
создаётся, если команда объявлена в текущей форме.

Пример:

```text
Catalog.Товары.Form.ФормаСписка.Command.Печать
```

`Form.StandardCommand.*` и `Form.Item.*.StandardCommand.*` не смешиваются с этим
решением. Это отдельный класс системных команд формы и элемента; он разбирается
следующим случаем.

### Проверка

После реализации:

- `Form.Command.*` не создаёт `GraphStub`;
- число `COMMAND_NAME -> GraphStub` уменьшается минимум на группу
  `Form.Command.*`;
- узлы `FormCommand` и ссылки на них используют один и тот же канонический id;
- тесты фиксируют, что `CommandName = "Form.Command.Печать"` ссылается на
  `...Form.<form>.Command.Печать`.

## Случай 1.1: `COMMAND_NAME` к внешним командам

### Наблюдение

В `COMMAND_NAME -> GraphStub` есть значения, которые уже содержат полный
metadata path команды:

```text
CommonCommand.ДополнительныеСведенияКоманднаяПанель
Report.ПараметрыВНА.Command.ПараметрыВНА
DataProcessor.ОтражениеДокументовВРеглУчете.Command.ПроводкиРеглУчета
InformationRegister.СообщенияФССОбИзмененииСостоянийЭЛН.Command.СообщенияФССОбИзмененииЭЛН
```

Сейчас они ошибочно приклеиваются к текущей форме:

```text
<formNodeId>.Команда.CommonCommand.ДополнительныеСведенияКоманднаяПанель
<formNodeId>.Команда.Report.ПараметрыВНА.Command.ПараметрыВНА
```

### Причина

Текущий обработчик `CommandName` считает любое значение именем команды текущей
формы и всегда строит цель как `<formNodeId>.Команда.<value>`.

Но `CommonCommand.*` и `<ObjectKind>.<ObjectName>.Command.<CommandName>` — это
ссылки на внешние команды, а не на `FormCommand` текущей формы.

### Решение

`CommandName` делится на несколько классов:

- `Form.Command.<name>` — команда текущей формы, см. случай 1;
- `Form.StandardCommand.*` и `Form.Item.*.StandardCommand.*` — системные
  команды, см. случай 2;
- `CommonCommand.<name>` — верхнеуровневая общая команда;
- `<ObjectKind>.<ObjectName>.Command.<CommandName>` — команда другого
  metadata object.

Для внешних команд `formNodeId` не добавляется к цели. Значение резолвится как
канонический metadata path через общую таблицу соответствий:

```text
CommonCommand.<name>
Report.<report>.Command.<command>
DataProcessor.<processor>.Command.<command>
InformationRegister.<register>.Command.<command>
```

Если соответствующий узел команды пока не материализуется в графе, diagnostic
stub создаётся в этом каноническом пространстве, а не внутри текущей формы.

### Проверка

После реализации:

- `COMMAND_NAME = "CommonCommand.<name>"` ведёт к `CommonCommand.<name>`;
- `COMMAND_NAME = "Report.<name>.Command.<command>"` ведёт к команде отчёта;
- внешние команды не создают stub под `...Form.<form>.Command.*`;
- префиксы внешних объектов преобразуются через общую таблицу соответствий.

## Случай 1.2: `COMMAND_NAME = 0` и `0:<uuid>`

### Наблюдение

В XML встречаются значения:

```xml
<CommandName>0</CommandName>
<CommandName>0:198ea630-fda2-4cda-8a23-f999f4c67ee6</CommandName>
```

Сейчас они превращаются в цели:

```text
<formNodeId>.Команда.0
<formNodeId>.Команда.0:<uuid>
```

и становятся `GraphStub`.

В проверенных формах рядом нет объявленных команд с `id="0"`. Значения вида
`0:<uuid>` часто стоят на стандартных кнопках вроде «Изменить форму» и похожи
на платформенные внутренние идентификаторы, а не на metadata path команды.

### Решение

`CommandName = "0"` и `CommandName = "0:<uuid>"` не добавляются в граф:
обработчик не создаёт ни `COMMAND_NAME`-ребро, ни узел, ни диагностическое
свойство на графовом узле.

Сырое значение сохраняется только в модели/YAML/XML для round-trip.

Это временно консервативное правило: пока мы не знаем надёжный способ
резолвить такие идентификаторы в реальные команды, граф не должен создавать
уверенную ссылку на несуществующий узел.

### Проверка

После реализации:

- `COMMAND_NAME = "0"` не создаёт `GraphStub`;
- `COMMAND_NAME = "0:<uuid>"` не создаёт `GraphStub`;
- исходное значение сохраняется при round-trip;
- в графе нет ни ребра, ни свойства, представляющего это значение.

## Случай 2: системные команды формы и элемента

### Наблюдение

Внутри `COMMAND_NAME -> GraphStub` есть две крупные группы встроенных команд:

| Группа значения `CommandName` | Количество |
| --- | ---: |
| `Form.StandardCommand.*` | `5 798` |
| `Form.Item.*.StandardCommand.*` | `5 777` |

Частые команды формы: `Help`, `Close`, `CustomizeForm`, `Cancel`, `Write`.
Частые команды элемента: `Find`, `CancelSearch`, `Delete`, `Add`,
`OutputList`, `Change`.

### Причина

Текущее построение `CommandName` трактует любую строку как ссылку на узел
команды формы и создаёт цель под сегментом команд:

```text
...Команда.Form.StandardCommand.Help
...Команда.Form.Item.Список.StandardCommand.Find
```

Но системные команды платформы не являются метаданными проекта и не должны
становиться отдельными узлами графа.

### Решение

Для системных команд `COMMAND_NAME` не создаёт узел команды.

`Form.StandardCommand.<command>`:

- цель ребра — текущая форма;
- на ребре сохраняются свойства:
  - `commandScope: "form"`;
  - `standardCommand: "<command>"`.

`Form.Item.<elementName>.StandardCommand.<command>`:

- цель ребра — элемент формы с именем `<elementName>`;
- на ребре сохраняются свойства:
  - `commandScope: "item"`;
  - `standardCommand: "<command>"`;
  - `targetItemName: "<elementName>"`.

Канонический id элемента после общей миграции:

```text
<OwnerKind>.<OwnerName>.Form.<FormName>.Element.<ElementName>
```

Если целевой элемент формы не найден, это остаётся диагностическим stub только
для элемента, а не для системной команды. То есть отсутствующая цель должна
выглядеть как `...Element.<ElementName>`, а `StandardCommand.<command>` остаётся
свойством ребра.

### Проверка

После реализации:

- `Form.StandardCommand.*` не создаёт `GraphStub`;
- `Form.Item.*.StandardCommand.*` не создаёт stub-узлы команд;
- ребро к форме или элементу хранит `commandScope` и `standardCommand`;
- если элемент формы существует, `COMMAND_NAME` ведёт к `FormElement`;
- если элемент отсутствует, stub создаётся только для элемента формы.

## Случай 3: `DATA_PATH` через `DocumentObject.*` и `CatalogObject.*`

### Наблюдение

Крупнейшая часть `DATA_PATH`-stub связана с runtime-представлениями объектов:

| Префикс цели | kind | Количество |
| --- | --- | ---: |
| `DocumentObject` / `ДокументОбъект` | `DATA_PATH` | `18 207` |
| `DocumentObject` / `ДокументОбъект` | `DATA_PATH_DEPENDS_ON` | `18 207` |
| `CatalogObject` / `СправочникОбъект` | `DATA_PATH` | `7 768` |
| `CatalogObject` / `СправочникОбъект` | `DATA_PATH_DEPENDS_ON` | `7 768` |

Примеры:

```text
sourcePath: Объект.ПрочиеРасходы
target: ДокументОбъект.АвансовыйОтчет.ПрочиеРасходы

sourcePath: Объект.Number
target: ДокументОбъект.АвансовыйОтчет.Number

sourcePath: ДоговорОбъект.Description
target: СправочникОбъект.ДоговорыКонтрагентов.Description
```

Для значительной части таких целей уже есть реальные узлы проекта. Например
`ДокументОбъект.<doc>.<field>` часто соответствует `MetadataAttribute` у
документа, а `СправочникОбъект.<catalog>.<field>` — `MetadataAttribute` у
справочника. Но встречаются и стандартные реквизиты (`Date`, `Number`, `Ref`),
табличные части и другие owning-дочерние узлы, поэтому простая строковая замена
недостаточна.

### Причина

`DocumentObject.*` и `CatalogObject.*` — это runtime-представления объекта 1С,
а не отдельные метаданные проекта. Сейчас резолвер `DataPath` превращает их в
отдельные цели, из-за чего появляются stub-узлы вроде:

```text
ДокументОбъект.АвансовыйОтчет.ПрочиеРасходы
СправочникОбъект.ДоговорыКонтрагентов.Description
```

### Решение

Runtime-представление объекта должно резолвиться в канонический узел
метаданных:

```text
DocumentObject.<name> -> Document.<name>
CatalogObject.<name> -> Catalog.<name>
```

Следующий сегмент `DataPath` ищется среди реальных owning-детей объекта по
`name`. В первую очередь поддерживаются:

- `Attribute`;
- `StandardAttribute`;
- `TabularSection`;
- другие зарегистрированные owning-дочерние коллекции объекта.

Итоговая цель `DATA_PATH` — найденный реальный узел. То же правило применяется
к родственным свойствам формы, которые несут путь к данным: `Данные`,
`ПутьКДаннымЗаголовка`, `ПутьКДаннымПодвала` и аналогичным ссылкам.
`DATA_PATH_DEPENDS_ON` фиксирует зависимости от объекта и найденных
промежуточных узлов, но не создаёт отдельный stub для `DocumentObject` или
`CatalogObject`.

Если дочерний сегмент не найден, диагностический stub создаётся в каноническом
модельном пространстве, например:

```text
Document.АвансовыйОтчет.Attribute.НесуществующийРеквизит
```

а не в runtime-пространстве `DocumentObject.*`.

### Проверка

После реализации:

- `DocumentObject.*` и `CatalogObject.*` не появляются как `GraphStub`;
- `Объект.Реквизит` ведёт к реальному `Attribute`, если он объявлен у объекта;
- `Объект.Date`, `Объект.Number`, `Объект.Ref` ведут к `StandardAttribute`;
- путь к табличной части ведёт к `TabularSection`;
- нерезолвленная цель остаётся stub только в каноническом модельном id.

## Случай 4: глобальные `DataPath` к `StandardAttribute`

### Наблюдение

Отдельная группа ссылок к `GraphStub` приходит из глобальных строк вида:

```text
Document.АвансовыйОтчет.StandardAttribute.Date
Document.ЗаказКлиента.StandardAttribute.Ref
```

Для `DATA_PATH` таких рёбер найдено `462`. `ChoiceParameterLink` даёт ещё
`959` `DATA_PATH` и `482` `DATA_PATH_DEPENDS_ON` к тем же стандартным
реквизитам. Для `FIELD` найдено ещё `874` ребра:

| fieldName | Количество |
| --- | ---: |
| `Number` | `834` |
| `Description` | `19` |
| `Code` | `18` |
| `Date` | `3` |

Реальные узлы стандартных реквизитов сейчас существуют, но их id построен через
русский служебный сегмент и русское имя последнего сегмента:

```text
Документ.АвансовыйОтчет.СтандартныйРеквизит.Ссылка
Документ.АвансовыйОтчет.СтандартныйРеквизит.ПометкаУдаления
```

При этом `name` на этих узлах уже хранит модельное имя:

```text
name: Ref
name: DeletionMark
```

### Причина

`DataPath`, `ChoiceParameterLink`, `FIELD` и родственные ссылочные свойства
используют модельную строку `StandardAttribute.Date` /
`StandardAttribute.Number`, а графовый id стандартного реквизита использует
русское представление. Из-за этого ссылка попадает в stub:

```text
Документ.АвансовыйОтчет.СтандартныйРеквизит.Date
```

### Решение

Стандартные реквизиты должны использовать модельное имя как последний сегмент
канонического id:

```text
Document.<name>.StandardAttribute.Date
Document.<name>.StandardAttribute.Ref
Catalog.<name>.StandardAttribute.Description
```

Русское представление (`Дата`, `Ссылка`, `Наименование`) остаётся только в
YAML/enterprise-представлении и человекочитаемых свойствах.

Это согласуется с базовым инвариантом: технический сегмент `StandardAttribute`
английский, а последний сегмент id берётся из модели, чтобы совпадать с
`DataPath`, `TypeDescription` и будущими графовыми запросами.

Решение применяется ко всем ссылочным рёбрам на стандартные реквизиты:
`DATA_PATH`, `DATA_PATH_DEPENDS_ON`, `FIELD`, связям `ChoiceParameterLink` и
будущим свойствам с тем же форматом цели.

### Проверка

После реализации:

- `Document.*.StandardAttribute.*` из `DataPath` ведёт к реальному
  `StandardAttributeDescription`;
- `FIELD` к `Number`, `Description`, `Code`, `Date` ведёт к тому же
  `StandardAttributeDescription`;
- `ChoiceParameterLink` к `Date`, `Ref` и другим стандартным реквизитам ведёт
  к тому же `StandardAttributeDescription`;
- стандартные реквизиты не создают stub из-за русско-английского расхождения
  последнего сегмента;
- `name` узла и последний сегмент id совпадают для стандартных реквизитов;
- русское имя стандартного реквизита не теряется и остаётся доступным для
  YAML/XML-представления.

## Случай 5: `TYPE` к метаданным и runtime-представлениям

### Наблюдение

`TYPE -> GraphStub` в основном создаётся для типов, у которых префикс уже
известен модели, но в графе используется русское enterprise-представление:

| Префикс цели | Количество |
| --- | ---: |
| `ОпределяемыйТип` | `12 987` |
| `Характеристика` | `3 708` |
| `ПланВидовХарактеристик` | `2 114` |
| `CatalogObject` | `961` |
| `DocumentObject` | `945` |
| `ПланВидовРасчета` | `450` |
| `ПланСчетов` | `370` |

Примеры:

```text
MetadataAttribute --TYPE--> ОпределяемыйТип.ДенежнаяСуммаЛюбогоЗнака
MetadataAttribute --TYPE--> CatalogObject.Номенклатура
MetadataAttribute --TYPE--> DocumentObject.ЗаказКлиента
```

### Причина

`TypeDescription` сейчас строит цель из `rule.enterprise` и имени типа. Для
enterprise-строк это даёт русские graph id (`ОпределяемыйТип.*`,
`ПланСчетов.*`), которые не совпадают с каноническими id реальных узлов.

При этом таблица соответствий уже есть:

- `MetadataTypeToYAML` / `MetadataTypeFromYAML` для типов метаданных;
- `MetadataFieldsRulesToYAML` и производные правила для путей и дочерних
  полей.

Нельзя заводить вторую таблицу соответствий только для графа: она быстро
разойдётся с YAML/XML-представлением.

### Решение

Построение graph id для `TYPE` должно использовать существующую таблицу
соответствий как единый источник истины.

Правила:

- `DefinedType.<name>` резолвится в `DefinedType.<name>`;
- `Characteristic.<name>` резолвится в `Characteristic.<name>`;
- `ChartOfCharacteristicTypes.<name>`, `ChartOfAccounts.<name>`,
  `ChartOfCalculationTypes.<name>` и другие верхнеуровневые типы резолвятся в
  свои канонические английские префиксы из таблицы соответствий;
- `CatalogObject.<name>` и `DocumentObject.<name>` не создают отдельные
  runtime-узлы, а резолвятся в `Catalog.<name>` и `Document.<name>`;
- если важно сохранить различие object/ref-типа, оно хранится на ребре `TYPE`
  как свойство, а не в отдельном namespace узла;
- примитивные, встроенные и игнорируемые типы из `TypeDescriptionRules` не
  создают графовую ссылку на metadata-узел.

Если метаданный тип поддержан таблицей, но соответствующий объект не загружен в
граф, diagnostic stub создаётся уже в каноническом модельном namespace:

```text
DefinedType.ДенежнаяСуммаЛюбогоЗнака
ChartOfAccounts.Хозрасчетный
```

а не как `ОпределяемыйТип.*` или `ПланСчетов.*`.

### Проверка

После реализации:

- `TYPE` не создаёт stub из-за русских enterprise-префиксов;
- `CatalogObject.*` и `DocumentObject.*` в типах ведут к `Catalog.*` и
  `Document.*`;
- все преобразования graph id проходят через существующую таблицу соответствий;
- тесты фиксируют хотя бы `DefinedType`, `CatalogObject`, `DocumentObject` и
  один из видов планов.

## Случай 6: `TABLE` у дополнительных колонок формы

### Наблюдение

Оставшаяся крупная группа после `COMMAND_NAME`, `DATA_PATH` и `TYPE`:

| Связь | Источник | Количество |
| --- | --- | ---: |
| `TABLE` / `Таблица` | `AdditionalColumnsProxy` | `1 128` |

Примеры:

```text
Документ.АвансовыйОтчет.Форма.ФормаДокумента.Реквизит.Объект.ПрочиеРасходы
  --TABLE-->
ДокументОбъект.АвансовыйОтчет.ПрочиеРасходы
```

Для выборочных целей уже существуют реальные узлы табличных частей:

```text
Документ.АвансовыйОтчет.ТабличнаяЧасть.ПрочиеРасходы
Документ.АктВыполненныхРабот.ТабличнаяЧасть.Услуги
```

### Причина

`AdditionalColumns.table` сейчас трактует таблицу как путь в
runtime-представлении объекта (`DocumentObject.*`, `CatalogObject.*`). Это тот
же класс проблемы, что и в `DATA_PATH`: runtime-префикс попадает в graph id и
становится отдельным stub.

### Решение

`TABLE` у `AdditionalColumnsProxy` резолвится тем же механизмом, что
`DataPath` через runtime-объект:

```text
DocumentObject.<doc>.<table> -> Document.<doc>.TabularSection.<table>
CatalogObject.<catalog>.<table> -> Catalog.<catalog>.TabularSection.<table>
```

Итоговая цель ребра — реальный `MetadataTabularSection`. После общей миграции
канонический id использует английские технические сегменты:

```text
Document.<doc>.TabularSection.<table>
Catalog.<catalog>.TabularSection.<table>
```

Если табличная часть не найдена, diagnostic stub создаётся в каноническом
модельном namespace `...TabularSection.<table>`, а не в
`DocumentObject.*`/`CatalogObject.*`.

### Проверка

После реализации:

- `TABLE` от `AdditionalColumnsProxy` ведёт к `MetadataTabularSection`;
- `DocumentObject.*` и `CatalogObject.*` не появляются как цели `TABLE`;
- отсутствующая таблица диагностируется stub-узлом с каноническим id
  `...TabularSection.<table>`.

## Случай 7: `VALUE` и `VALUE_TYPE` к значениям метаданных

### Наблюдение

Оставшиеся содержательные stub-ссылки:

| Связь | Источник | Частые префиксы цели |
| --- | --- | --- |
| `VALUE` / `Значение` | `ChoiceParameter`, `MetadataAttribute`, регистровые поля | `Справочник`, `ПланВидовХарактеристик`, `ПланСчетов` |
| `VALUE_TYPE` / `ТипЗначения` | `FormAttribute` | `ОпределяемыйТип`, `ПланВидовХарактеристик`, `ПланСчетов` |

Примеры:

```text
MetadataAttribute --VALUE--> Справочник.СтавкиНДС.БезНДС
ChoiceParameter --VALUE--> ПланВидовХарактеристик.ВидыБюджетов.БюджетДвиженияДенежныхСредств
FormAttribute --VALUE_TYPE--> ОпределяемыйТип.УникальныйИдентификаторИС
```

### Причина

Для `VALUE_TYPE` причина та же, что у `TYPE`: цель строится через русское
enterprise-представление, а не через канонический модельный префикс.

Для `VALUE` третья часть пути сейчас оказывается «подвешенной» сразу под
объектом метаданных:

```text
Справочник.СтавкиНДС.БезНДС
ПланВидовХарактеристик.ВидыБюджетов.БюджетДвиженияДенежныхСредств
```

Но это не дочерний metadata item неизвестного типа, а значение предопределённых
данных соответствующего объекта.

### Решение

`VALUE_TYPE` использует тот же резолвер канонических type-id, что и `TYPE`:

```text
ОпределяемыйТип.<name> -> DefinedType.<name>
ПланСчетов.<name> -> ChartOfAccounts.<name>
ПланВидовХарактеристик.<name> -> ChartOfCharacteristicTypes.<name>
```

`VALUE` к конкретному значению метаданных вводит явный сегмент
`PredefinedData`:

```text
Справочник.<catalog>.<value>
  -> Catalog.<catalog>.PredefinedData.<value>

ПланВидовХарактеристик.<plan>.<value>
  -> ChartOfCharacteristicTypes.<plan>.PredefinedData.<value>

ПланСчетов.<chart>.<value>
  -> ChartOfAccounts.<chart>.PredefinedData.<value>
```

Значения перечислений остаются значениями самого `Enum`, потому что текущий
graph-слой строит узлы перечислений без промежуточного `EnumValue`:

```text
Enum.<enum>.EnumValue.<value>
  -> Enum.<enum>.<value>
```

`ПустаяСсылка` в YAML остаётся человекочитаемым представлением, но graph-id
использует внутреннее имя модели:

```text
Справочник.<catalog>.ПустаяСсылка
  -> Catalog.<catalog>.EmptyRef
```

Если предопределённые значения уже материализованы в графе, ребро ведёт к
реальному узлу `PredefinedData`. Если они пока не строятся как узлы,
diagnostic stub создаётся в этом каноническом пространстве, а не напрямую под
объектом метаданных.

### Проверка

После реализации:

- `VALUE_TYPE` не создаёт stub из-за русских enterprise-префиксов;
- `VALUE` для каталогов, планов счетов и планов видов характеристик ведёт в
  `...PredefinedData.<value>`;
- `VALUE` для перечислений удаляет служебный `EnumValue` и не добавляет
  `PredefinedData`;
- `VALUE` к пустой ссылке и терминальный узел владельца сходятся на
  `...EmptyRef`;
- если предопределённое значение не загружено, stub id всё равно содержит
  `PredefinedData`;
- преобразование префиксов использует общую таблицу соответствий, как в
  случаях `TYPE` и `DataPath`.

# Прямой GRAPH.BULK replace-путь для графа

## Контекст

Текущий `nkdk update-graph --replace` уже убрал инкрементальный `MERGE`-путь, но на ERP-проекте запись через Cypher `CREATE` все еще занимает около `253 с`, а полный запуск - около `312 с`.

Профилирование `GRAPH.PROFILE` показало, что основные `MATCH` в `createEdges` и `createFileLinks` используют индексы (`Node By Index Scan`). Узкое место не в широком поиске, а в массовой записи через Cypher: создание отношений, установка свойств, разбор больших `UNWIND`-запросов и последовательная отправка пачек.

Официальный `falkordb-bulk-insert` через `GRAPH.BULK` загрузил расширенный ERP-граф (`727467` узлов, `1552454` ребер) за `16.87 с`; экспорт CSV перед этим занял `64.3 с`. Это доказывает, что `GRAPH.BULK` радикально быстрее текущего Cypher-пути, а следующий выигрыш - убрать промежуточные CSV-файлы и кодировать binary blobs напрямую из `FileGraphData`.

## Цель

Добавить экспериментальный полный replace-путь, который пишет новый граф через `GRAPH.BULK` напрямую из памяти, без промежуточных CSV-файлов и без Cypher `CREATE` для узлов и ребер.

Ожидаемый ориентир на ERP: `buildGraph` около `55-65 с` плюс bulk-загрузка около `15-25 с`, то есть полный запуск порядка `70-90 с`.

Не цели:

- менять обычный инкрементальный `updateGraph(files)`;
- использовать `GRAPH.BULK` для частичного обновления, потому что endpoint создает новый граф, а не обновляет существующий;
- менять модель графа, набор узлов, ребер или свойства ради скорости;
- зависеть от Python bulk-loader в runtime.

## Включение

Новый путь включается явно:

```bash
nkdk update-graph <path> --replace --bulk
```

На уровне API:

```ts
updateGraph(files, { replace: true, bulk: true })
```

Если `bulk` не передан, `replace` продолжает использовать текущий безопасный `CREATE`-путь. Это оставляет fallback на случай несовместимости `GRAPH.BULK` с конкретной версией FalkorDB.

## Архитектура

В `packages/graph` добавляются изолированные модули:

- `bulk/encoder.ts` - кодирует binary blob-формат `GRAPH.BULK`: header, property names, typed property values, node records и edge records.
- `bulk/plan.ts` - превращает `FileGraphData[]` в стабильный bulk-план: порядок узлов, внутренние numeric IDs, группы node blobs по label и edge blobs по kind.
- `bulk/write.ts` - режет blobs и команды по лимитам, отправляет `GRAPH.BULK`, затем создает индексы.
- `internal/connection.ts` - добавляет минимальный raw-command метод для отправки `GRAPH.BULK` с binary buffers.

`updateGraph.ts` выбирает путь так:

1. пустой `files` - старый `resetGraph`;
2. `replace && bulk` - `replaceGraphBulk`;
3. `replace` - текущий `replaceGraph`;
4. иначе - текущий инкрементальный путь.

## Bulk-план

План должен сохранить текущую семантику `replace`:

- каждый YAML-файл становится узлом `File` со свойствами `path`, `mtimeMs`, `size`, `updatedAt`;
- каждый `NodeData` становится узлом с его предметным label и свойствами из `props`;
- неизвестные концы ребер становятся stub-узлами `GraphNode`;
- каждое предметное ребро `EdgeData` становится отношением `kind` со свойствами `props` и дополнительным `filePath`;
- `DECLARES` и `CONTRIBUTES` создаются из `filePath` к `nodeId`.

Поскольку `GRAPH.BULK` сам назначает внутренние numeric IDs узлам по порядку создания, `bulk/plan.ts` должен:

- назначить каждому логическому id (`File.path` или `NodeData.id`) будущий numeric ID до записи ребер;
- гарантировать стабильный порядок узлов;
- сгруппировать узлы по label, но сохранить глобальный счетчик numeric ID;
- построить ребра уже через numeric IDs источника и цели.

## Typed-свойства

Bulk-путь должен сохранять полноценные типы, а не превращать все в строки.

Правила кодирования:

- `null` не пишется как свойство, как и в текущем Cypher-пути;
- `boolean` кодируется как `BI_BOOL`;
- `string` кодируется как `BI_STRING`;
- `number` кодируется как `BI_LONG`, если `Number.isSafeInteger(value)`, иначе как `BI_DOUBLE`;
- `number` должен быть finite, иначе запись падает до отправки в FalkorDB;
- массивы кодируются как `BI_ARRAY`;
- массив должен содержать элементы одного поддерживаемого типа после удаления `null`;
- пустой массив и массив только из `null` не пишутся как свойство.

Если в одном label или relation type одно и то же свойство встречается с разными типами, encoder не должен смешивать их в один blob. Он должен разбить группу на совместимые schema-группы с одинаковым набором property names и type signatures. Это важнее компактности: header blob фиксирует порядок и типы свойств для всех записей внутри blob.

## Лимиты GRAPH.BULK

Спецификация `GRAPH.BULK` задает важные ограничения:

- один binary blob не больше `512MB`;
- вся Redis-команда по умолчанию не больше `1GB`;
- большие импорты нужно отправлять инкрементально;
- первый вызов использует `BEGIN`, последующие продолжают частично созданный граф без `BEGIN`.

В реализации:

- `maxBlobBytes` - дефолт `256MB`, допустимый максимум `512MB`;
- `maxCommandBytes` - дефолт `768MB`;
- если следующая запись переполняет blob, текущий blob закрывается и начинается новый с тем же header;
- если следующий blob переполняет команду, текущая команда отправляется и начинается следующая;
- `nodeCount` и `edgeCount` в каждом вызове `GRAPH.BULK` отражают число сущностей именно в этой команде;
- порядок команд должен сохранять требование endpoint: сначала все node blobs, затем edge blobs. Нельзя отправлять ребра до того, как созданы все узлы, на которые они ссылаются.

Первый implementation должен начинать с консервативных лимитов и оставить их опциями для тестовых замеров.

## Индексы

После завершения bulk-загрузки создаются те же индексы, что нужны текущему графовому слою:

- `File.path`;
- `GraphNode.id`;
- `<label>.id` для каждого предметного label.

Индексы создаются после загрузки, как в successful CSV bulk-эксперименте, чтобы не замедлять массовую вставку.

## Ошибки и откат

`GRAPH.BULK` не обновляет существующий граф. Поэтому `replaceGraphBulk` должен работать только после удаления старого графа или с новым временным именем.

Безопасный вариант для первого шага:

1. удалить целевой граф через текущий `resetGraph` или `GRAPH.DELETE`, если граф существует;
2. выполнить `GRAPH.BULK ... BEGIN ...`;
3. создать индексы;
4. если ошибка случилась после начала bulk, граф может остаться неполным; пользователь повторяет `--replace --bulk`.

Для атомарного swap между временным и целевым графом отдельной поддержки в FalkorDB не закладываем, потому что это усложняет первую версию и не требовалось текущему `replace`.

## Проверки

Перед первой отправкой в FalkorDB выполняются проверки `validateReplacePayload`:

- уникальность `File.path`;
- уникальность `Node.id`;
- отсутствие дублей `DECLARES` и `CONTRIBUTES`.

Дополнительно bulk-план проверяет:

- каждый edge endpoint имеет numeric ID;
- property type conflicts внутри schema-групп корректно разбиты;
- blob не может превысить `maxBlobBytes` одной одиночной записью; если одна запись слишком большая, выдаем понятную ошибку.

## Тестирование

Unit-тесты:

- кодирование `BI_BOOL`, `BI_DOUBLE`, `BI_STRING`, `BI_LONG`, `BI_ARRAY`;
- пропуск `null` и пустых массивов;
- разбиение schema-групп при конфликте типов одного свойства;
- назначение numeric IDs и построение edge endpoints;
- разбиение blobs и команд по искусственно маленьким лимитам.

Integration-тест:

- маленький граф загружается через текущий `replace`;
- тот же граф загружается через `replace + bulk`;
- сравниваются counts, labels, свойства узлов и ребер, `DECLARES/CONTRIBUTES`.

Замер:

- повторить ERP `/private/tmp/erp_nkdk`;
- отдельно вывести `buildGraph`, `bulkGraph`, `total`;
- сравнить с текущими `312.4 с` для `--replace` и `81.1 с` для CSV bulk path.

## Критерий успеха

Функциональный критерий: `update-graph --replace --bulk` создает граф, эквивалентный текущему `--replace` для проверяемого набора узлов, ребер и свойств.

Производительный критерий: на ERP полный запуск без CSV должен быть не медленнее CSV bulk path (`~81 с`) и существенно быстрее текущего Cypher replace (`~312 с`). Если typed encoding заметно дороже строкового CSV-экспорта, это фиксируется отдельным замером и оптимизируется после корректной первой версии.

# Чистка репозитория от extension и старого веб-слоя

## Контекст

Репозиторий сейчас является `pnpm`-монорепозиторием с пакетами `@nakidka/core`, `@nakidka/cli`, `@nakidka/graph` и устаревшим `packages/extension`. Корневой `package.json` всё ещё описывает старое веб-приложение для расширения VS Code и содержит зависимости, связанные с React/Vite/Monaco/VS Code, хотя актуальная работа ведётся в пакетах `core`, `cli` и `graph`.

## Цель

Удалить устаревший VS Code extension-пакет и лишние корневые Node.js-зависимости, не меняя поведение `core`, `cli` и `graph`.

## Границы

Входит в работу:

- удалить `packages/extension` целиком, включая локальный `packages/extension/node_modules`;
- обновить workspace/lockfile так, чтобы `packages/extension` и его зависимости исчезли из `pnpm-lock.yaml`;
- убрать из корневого `package.json` зависимости старого веб/extension-слоя, если они не используются вне `packages/extension`;
- проверить и удалить `organize-imports-cli`, если для него нет корневого скрипта или прямого использования;
- при необходимости обновить корневое описание проекта, чтобы оно не называло репозиторий веб-приложением для VS Code extension.

Не входит в работу:

- изменения в `packages/core/metadata/**`;
- переписывание сборки пакетов `core`, `cli` и `graph`;
- изменение XML-фикстур;
- перенос зависимостей между пакетами без подтверждённой необходимости.

## Подход

Основной подход — консервативная чистка с проверкой по импортам и скриптам. Сначала удаляется `packages/extension`, затем корневые зависимости делятся на три группы:

- явно устаревшие зависимости VS Code/extension: `@types/vscode` и связанные пакеты, если остались только в корне;
- явно устаревшие зависимости веб-интерфейса: React, Ant Design, Monaco, Vite, testing-library, браузерные полифилы, сборщики и загрузчики, если они не используются текущими пакетами;
- общие инструменты и предметные зависимости: остаются только при наличии корневого скрипта, импорта или использования в `core`, `cli`, `graph`.

`organize-imports-cli` удаляется вместе с прочими корневыми инструментами, если поиск не найдёт его использования.

## Проверка

После изменений нужно выполнить:

1. `pnpm install --lockfile-only` из корня, чтобы обновить `pnpm-lock.yaml`.
2. `pnpm test` из корня, чтобы проверить все пакеты workspace.

Если обновление lockfile потребует сеть, работа запрашивает разрешение на запуск команды с доступом к сети.

## Риски

Главный риск — удалить корневую зависимость, которая используется не через прямой импорт, а как скрытый инструмент. Чтобы снизить риск, перед удалением каждая зависимость проверяется поиском по репозиторию и по скриптам `package.json`.

Второй риск — lockfile может измениться шире ожидаемого из-за пересчёта зависимостей `pnpm`. Это допустимо, если изменения объясняются удалением `packages/extension` и корневых зависимостей.

# Следующие расхождения XML → YAML → XML

Дата: 2026-08-15

## Назначение

Спецификация собирает следующие независимые расхождения, найденные после
случаев из `2026-08-15-round-trip-next-discrepancies-design.md`. Предыдущая
спецификация реализуется отдельно и здесь не изменяется.

## 1. `v8:TypeId` в описании типа

### Исходное расхождение

В форме
`Contracts_1_0_7_2_setup1c/SettingsStorages/ХранилищеВариантовОтчетов/Forms/ПанельДругихОтчетов/Ext/Form.xml`
колонка `ВариантыПанели.Отчет` содержит смешанное описание типа:

```xml
<Type>
	<v8:Type>cfg:CatalogRef.ИдентификаторыОбъектовРасширений</v8:Type>
	<v8:Type>xs:string</v8:Type>
	<v8:Type>cfg:CatalogRef.ИдентификаторыОбъектовМетаданных</v8:Type>
	<v8:TypeId>ad99c086-2ae3-4648-ad31-fef3acf326e4</v8:TypeId>
	<v8:StringQualifiers>
		<v8:Length>0</v8:Length>
		<v8:AllowedLength>Variable</v8:AllowedLength>
	</v8:StringQualifiers>
</Type>
```

UUID соответствует внутреннему идентификатору
`CatalogRef.ДополнительныеОтчетыИОбработки`, но такого объекта в Contracts
нет. Текущий импорт сохраняет `v8:TypeId` в модели, однако экспорт в YAML
выводит `typeId` только при отсутствии обычных типов. В смешанном описании UUID
молча отбрасывается и не восстанавливается при обратном экспорте.

### Результаты проверки конфигураций

Проверены все конфигурации каталога `cf`, кроме `all`, по состоянию `HEAD`:

| XML-представление | Количество |
|---|---:|
| именованный тип метаданных с существующей целью | 844 872 |
| именованный тип метаданных без цели | 0 |
| `v8:TypeId`, совпадающий с локальным `xr:GeneratedType` | 584 |
| `v8:TypeId`, не совпадающий с локальным `xr:GeneratedType` | 6 |

Шесть отсутствующих целей находятся в четырёх конфигурациях:

- три в `AppealsProf_1_0_6_2_setup1c`;
- одна в `Contracts_1_0_7_2_setup1c`;
- одна в `FXDVUZ_1_1_9_4_setup1c`;
- одна в `erp`.

Три случая входят в составной тип вместе с обычными `v8:Type`, ещё три
являются единственным типом. Именованных ссылок на отсутствующие типы не
обнаружено: во всех исследованных случаях платформа оставляет отсутствующий
тип как `v8:TypeId`.

Сопоставление UUID при исследовании нужно только для проверки закономерности.
Рабочий алгоритм импорта не должен искать UUID в метаданных: согласно общему
договору `!xml/reference`, внутренняя UUID-форма переносится как есть.

### YAML-представление

`v8:TypeId` становится ссылочным элементом `!xml/reference` в том же значении
`Тип`, где находятся обычные типы.

Смешанное описание:

```yaml
Тип:
  - Справочник.ИдентификаторыОбъектовРасширений
  - Строка
  - Справочник.ИдентификаторыОбъектовМетаданных
  - !xml/reference ad99c086-2ae3-4648-ad31-fef3acf326e4
```

Единственный `v8:TypeId`:

```yaml
Тип: !xml/reference fede0318-ea6b-40e9-ae43-afc5d8a85768
```

Прежняя объектная форма удаляется без периода совместимости:

```yaml
Тип:
  ИдентификаторТипа:
    - fede0318-ea6b-40e9-ae43-afc5d8a85768
```

Она больше не создаётся при импорте и считается недопустимой во входном YAML.

### Преобразование

XML → YAML:

- каждый `v8:Type` продолжает преобразовываться в обычный именованный тип;
- каждый `v8:TypeId` становится скаляром `!xml/reference`;
- UUID не ищется в индексах и не преобразуется в найденное имя;
- обычные и тегированные элементы могут находиться в одном списке;
- если `v8:TypeId` является единственным элементом, `Тип` остаётся скаляром,
  как и любой одиночный обычный тип.

YAML → XML:

- обычный элемент `Тип` создаёт `v8:Type` по существующему правилу;
- элемент `!xml/reference <UUID>` создаёт `v8:TypeId` с исходным UUID;
- XML-схема задаёт порядок: сначала все `v8:Type`, затем все `v8:TypeId`;
- поэтому при смешанном YAML тегированные ссылки записываются после обычных
  типов независимо от их положения в YAML;
- квалификаторы строки, числа и даты сохраняют существующее положение после
  списка типов.

### Проверка и поиск

- содержимое `!xml/reference` в `Тип` обязано быть UUID;
- UUID без `!xml/reference` недопустим;
- тег иной категории в этом месте недопустим;
- тегированное значение не разрешается через индекс метаданных;
- тегированное значение не попадает в поиск ссылок, переименование и расчёт
  затронутых файлов;
- обычные именованные типы сохраняют существующую проверку допустимых типов.

Обработка должна использовать общий перенос `!xml/reference`, а
`TypeDescription` объявляет вложенные ссылочные элементы своего значения. В
нейтральных слоях не добавляются проверки конкретных UUID, XML-корней или
владельцев формы.

### Совместимость с существующим договором

Решение расширяет общий механизм из
`2026-08-15-general-broken-reference-transport-design.md` на вложенные ссылки
`TypeDescription`. Оно заменяет YAML-договор
`2026-05-08-type-description-type-id-design.md` только в части объектной формы
`ИдентификаторТипа`; внутренняя модель `typeId` и XML-поддержка `v8:TypeId`
остаются применимыми.

### Проверки реализации

- одиночный `v8:TypeId` импортируется как скаляр `!xml/reference` и точно
  восстанавливается;
- несколько `v8:TypeId` импортируются как список тегированных скаляров;
- смешанный `v8:Type` + `v8:TypeId` сохраняет все элементы;
- при обратном экспорте все `v8:TypeId` следуют после `v8:Type`;
- объектная форма `ИдентификаторТипа` отклоняется;
- нетегированный UUID и неверное содержимое тега отклоняются;
- тегированный UUID отсутствует в результатах поиска ссылок;
- round-trip Contracts восстанавливает исходный `TypeId` без reference XML;
- те же проверки покрывают одиночные случаи AppealsProf, FXDVUZ и `erp`;
- исходные XML-фикстуры не изменяются.

# Снимок конфигурации 1.3

## Контекст

Текущий снимок разрезает сведения одного логического элемента между
`IDENTITIES`, `XML_NODES`, `XML_VALUES` и `LOGICAL_ADDRESSES`. Это повторяет
`logicalAddress`, разрывает связь с исходным файлом и позволяет сохранять
данные, уже представленные YAML или `rules.ts`.

Целевой логический договор определён в
[`.agents/configuration-snapshot.md`](../../../.agents/configuration-snapshot.md).
Эта спецификация описывает архитектуру его реализации. Постоянным хранилищем
остаётся один двоичный файл на компонент; SQLite в дизайн не входит.

## Цели

- Объединить идентификаторы и особое XML-представление одного
  `logicalAddress` в одной `entity`.
- Связать каждую `entity` с точным файлом Проекта.
- Сохранять только сведения, которые нельзя восстановить из YAML и `rules.ts`.
- Получать обычный порядок XML-свойств из `rules.ts`, а порядок коллекций — из
  YAML.
- Сохранять порядок дочерних объектов только для списков, отсутствующих в
  родительском YAML.
- Исключить пустые `entity`.
- Сохранить потоковую обработку заданий и независимость результата от порядка
  worker.
- Публиковать снимок только после успешного завершения операции.

## Вне границ

- Выбор новой технологии хранилища.
- SQLite, SQL-схема и миграция через SQL.
- Сохранение validation-индексов или metadata-зависимостей.
- Привязка к базе 1С и проверка версии конфигурации в базе.
- Изменение YAML-договора прикладных объектов.
- Добавление частных условий по `itemType` в общие metadata-слои.
- Изменение существующих XML-фикстур.

## Рассмотренные подходы

### (А) Единая логическая `entity`

Одна запись содержит адрес, исходный файл, идентификаторы, специальный порядок
дочерних объектов и особое XML-представление. Двоичный codec самостоятельно
выбирает компактную физическую раскладку.

Преимущества:

- один смысловой владелец данных;
- нет отдельных списков адресов и повторной привязки к файлу;
- формат не зависит от конкретной технологии хранения;
- reader возвращает целостный элемент.

### (Б) Исправленные независимые секции

Сохранить `IDENTITIES`, `XML_NODES` и `XML_VALUES`, добавив общий идентификатор
элемента и файла.

Недостаток: физическая нормализация остаётся публичной моделью и допускает
рассинхронизацию частей одного элемента.

### (В) Только поток XML-фактов

Не вводить `entity`, а хранить последовательность событий сборщика.

Недостаток: чтение требует повторного сведения событий, сложнее проверять
конфликты и удалять состояние одного файла.

Выбран подход (А).

## Логическая модель

```ts
interface ConfigurationSnapshot {
  specificationVersion: "1.3"
  indexGeneration: bigint
  componentPath: string
  files: readonly ConfigurationSnapshotFile[]
  entities: readonly ConfigurationSnapshotEntity[]
}

interface ConfigurationSnapshotFile {
  projectPath: string
  contentHash: bigint
}

interface ConfigurationSnapshotEntity {
  logicalAddress: string
  sourceProjectPath: string
  identities?: {
    uuid?: string
    xmlId?: string
    xmlName?: string
  }
  omittedChildren?: OmittedChildren
  xml?: {
    extended?: true
    xsiNil?: true
    explicitEmpty?: true
    xsiType?: string
    xmlText?: string
    xmlPrefix?: string
  }
}

type OmittedChildren =
  | { kind: "names"; names: readonly string[] }
  | {
      kind: "typedNames"
      items: readonly { xmlName: string; name: string }[]
    }
```

Группировка `identities` и `xml` является договором API. Двоичный codec может
раскладывать их иначе, не изменяя логическую модель.

### Инварианты снимка

- `specificationVersion` равен `1.3`.
- `indexGeneration` начинается с `1` и увеличивается после успешного sync.
- `componentPath` совпадает с выбранным компонентом.
- `projectPath` уникален.
- `logicalAddress` уникален.
- `sourceProjectPath` каждой `entity` существует в `files`.
- Одна `entity` относится ровно к одному `sourceProjectPath`.
- `entity` содержит хотя бы одно поле в `identities`, `omittedChildren` или
  `xml`.
- Пустые `identities`, `xml` и `omittedChildren` не кодируются.
- Пустая строка `xmlName` является содержательным значением.
- Повторное одинаковое наблюдение поля допустимо; несовпадающие значения одного
  поля являются ошибкой.

## Владение данными

| Данные | Источник | Потребитель |
|---|---|---|
| `specificationVersion` | Codec снимка | Reader совместимости |
| `indexGeneration` | Import или предыдущий снимок | Генерация устойчивых идентификаторов следующего sync |
| `componentPath` | Выбранный компонент операции | Проверка принадлежности снимка |
| `projectPath` | Топология ресурсов Проекта | Поиск изменённых файлов и привязка `entity` |
| `contentHash` | Фактические байты записанного файла | Проверка актуальности снимка |
| `logicalAddress` | Единый builder по `rules.ts` и регистрациям | Точечное чтение `entity` |
| `sourceProjectPath` | `targetProjectPath` конкретного задания | Замена состояния одного файла |
| `uuid` | XML `_uuid` или зарегистрированный UUID в `_id` | fromYAML/toXML, формы, InternalInfo, расширения |
| `xmlId` | XML `_id`, не объявленный UUID | fromYAML/toXML и формы |
| `xmlName` | Невосстановимый XML `_name` | fromYAML/toXML |
| `omittedChildren` | Зарегистрированный сборщик списка из XML | Зарегистрированный восстановитель списка |
| `extended` | Правило расширения | Профиль и XML расширения |
| `xsiNil` | XML `xsi:nil`, не представленный YAML | Правило значения при fromYAML/toXML |
| `explicitEmpty` | Отличимое от default явное пустое XML-значение | Правило свойства при fromYAML/toXML |
| `xsiType` | Невосстановимый XML `xsi:type` | Правило значения при fromYAML/toXML |
| `xmlText` | Неоднозначное текстовое XML-представление | Зарегистрированный `referenceXMLFromValue` |
| `xmlPrefix` | Невосстановимый namespace-префикс | Правило типа при fromYAML/toXML |

## Архитектура компонентов

### Сборщик `entity`

Сборщик владеет `Map<logicalAddress, MutableEntity>` в пределах одного
XML/YAML-задания.

Он предоставляет узкие операции:

```ts
setIdentity(address, kind, value)
setOmittedChildren(address, value)
setXmlFlag(address, field)
setXmlValue(address, field, value)
finish(targetProjectPath)
```

`finish`:

1. назначает точный `targetProjectPath` всем содержательным записям задания;
2. удаляет пустые вложенные группы;
3. не возвращает пустые `entity`;
4. сортирует записи по `logicalAddress`;
5. возвращает частичный снимок одного файла.

Сборщик не знает `itemType`, имена папок или конкретные правила. Частные
property-типы вызывают его через зарегистрированные возможности.

### Объединение частичных снимков

Координатор объединяет `entity` по `logicalAddress`.

- Совпадающие значения с одинаковым `sourceProjectPath` объединяются.
- Разные файлы для одного адреса являются ошибкой.
- Разные значения одного идентификатора или XML-поля являются ошибкой.
- Результат сортируется по UTF-8 ключу `logicalAddress`.
- Порядок прихода worker не влияет на результат.

`files` формируется отдельно по фактически записанному Проекту. После
объединения координатор проверяет, что каждый `sourceProjectPath` присутствует
в `files`.

### Reader

Reader предоставляет:

```ts
snapshot(): Pick<ConfigurationSnapshot,
  "specificationVersion" | "indexGeneration" | "componentPath">
file(projectPath: string): ConfigurationSnapshotFile | undefined
files(): Iterable<ConfigurationSnapshotFile>
entity(logicalAddress: string): ConfigurationSnapshotEntity | undefined
entities(): Iterable<ConfigurationSnapshotEntity>
```

Удобные функции `identity`, `xmlValue` и чтение порядка могут остаться
адаптерами поверх `entity`, но не отдельными хранилищами.

Reader проверяет контейнер до возврата первого значения. Итераторы возвращают
смысловой порядок и не материализуют весь снимок.

### Двоичный codec

Codec сохраняет логическую модель 1.3 в одном файле компонента. Точная раскладка
секций не является публичным договором design-спецификации.

Обязательные свойства:

- строгая версия 1.3;
- проверка границ, длин, UTF-8 и контрольных данных;
- детерминированное кодирование одинаковой модели;
- отсутствие зависимости семантики от физического порядка записей;
- атомарная публикация завершённого файла.

## Порядок дочерних объектов

`omittedChildren` формируется только четырьмя зарегистрированными
property-типами:

| Property-тип | Вариант | Значение |
|---|---|---|
| `ConfigurationChildObjects` | `typedNames` | Пары XML-вида и имени в исходной последовательности |
| `ChildFormNames` | `names` | Имена `Form` |
| `ChildTemplateNames` | `names` | Имена `Template` |
| `ChildFileItemNames` | `names` | Имена `DimensionTable` |

Reader проверяет только структуру варианта. Его соответствие конкретному
property-типу проверяет зарегистрированный восстановитель списка. Остальные
коллекции восстанавливают порядок из YAML. Обычный порядок XML-свойств берётся
из `rules.ts`.

## Import XML

1. Discovery определяет компонент и задания с точными `targetProjectPath`.
2. Worker разбирает одно XML-задание по `rules.ts`.
3. Сборщик формирует частичные `entity` только для идентификаторов,
   `omittedChildren` и особого XML-представления.
4. Worker передаёт частичный снимок координатору.
5. YAML и внешние файлы записываются в Проект.
6. Координатор объединяет `entity`.
7. По фактическим байтам результата формируются `files`.
8. Проверяются все инварианты.
9. Снимок с `indexGeneration = 1` кодируется и публикуется последним.

Ошибка любого задания не публикует новый снимок.

## Sync YAML → XML

1. Reader проверяет версию и `componentPath`.
2. Текущие хэши Проекта сравниваются с `files`.
3. Для изменённого файла worker читает YAML и получает исходные `entity` этого
   файла.
4. Правило применяет совместимое сохранённое представление либо строит
   канонический XML.
5. Новый сборщик формирует полный набор `entity` изменённого файла.
6. Старые `entity` файла заменяются новым набором; исчезнувшие и пустые записи
   удаляются.
7. Состояние неизменённых файлов переносится без изменения.
8. После успешной записи XML пересчитываются хэши и увеличивается
   `indexGeneration`.
9. Новый снимок публикуется атомарно.

Состав объектов компонента и профиль расширения получают актуальные адреса из
YAML и `rules.ts`, а не из пустых записей снимка.

## Ошибки

Операция завершается ошибкой при:

- неподдерживаемой версии снимка;
- повреждении контейнера;
- несовпадении `componentPath`;
- повторном пути файла;
- повторном `logicalAddress`;
- ссылке `entity` на отсутствующий файл;
- пустой `entity`;
- конфликте файла, идентификатора, порядка или XML-поля одного адреса;
- неизвестном варианте `omittedChildren`;
- несоответствии варианта `omittedChildren` зарегистрированному property-типу.

При ошибке чтения старый снимок не применяется. При ошибке import/sync старый
опубликованный снимок остаётся без изменений.

## Совместимость

Версия 1.3 несовместима с существующими двоичными снимками. Reader не выполняет
частичную миграцию и не подставляет значения удалённых полей. Для перехода
требуется повторный import XML.

Изменение логического состава обязательных полей требует новой версии
спецификации. Изменение только физической раскладки при сохранении логической
модели может быть внутренней версией codec.

## Изменения относительно текущего кода

- `ConfigurationIdentity`, `ConfigurationXmlNode`,
  `ConfigurationXmlValue` и `ComponentLogicalAddress` заменяются единой
  `ConfigurationSnapshotEntity`.
- Удаляются сохранённые validation-индексы и metadata-зависимости.
- Удаляются `present`, `aliases`, общий `order`, `excludedEqualName`,
  `userSettingsId`, `producerVersion`, `baseFingerprint` и
  `configurationVersion`.
- Специальный порядок переименовывается в `omittedChildren` и доступен только
  зарегистрированным property-типам.
- Импорт назначает путь из конкретного задания, а не из первого файла Проекта.
- Профиль расширения получает полный состав адресов из актуального Проекта.

## Проверка

### Модульные тесты

- Кодирование и чтение всех полей модели 1.3.
- Отказ для пустой `entity`.
- Отказ для `entity` с отсутствующим `sourceProjectPath`.
- Объединение одинаковых фактов и отказ при конфликте.
- Детерминированный результат при разном порядке частичных снимков.
- Пустой `xmlName` считается значением.
- Удаление пустых вложенных `identities` и `xml`.
- Точечное чтение `entity` и потоковый обход.
- Строгая проверка версии и повреждённого контейнера.

### Интеграционные тесты

- Import назначает каждой `entity` путь её задания.
- Sync заменяет все `entity` изменённого файла и удаляет устаревшие.
- Неизменённый файл сохраняет свои `entity`.
- `ConfigurationChildObjects`, `ChildFormNames`, `ChildTemplateNames` и
  `ChildFileItemNames` восстанавливают исходную последовательность.
- События формы получают порядок из YAML.
- Стандартные реквизиты и обычные XML-свойства получают порядок из `rules.ts`.
- Расширение получает состав адресов из актуального Проекта.
- Ошибка операции не публикует частичный снимок.
- Одинаковый Проект при одинаковом поколении даёт одинаковый снимок.

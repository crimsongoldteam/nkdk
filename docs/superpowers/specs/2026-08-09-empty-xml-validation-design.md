# Пустой `!xml` в validation-схеме

## Контекст

Транспортный тег `!xml` сохраняет различие XML, которое нельзя восстановить из
смыслового YAML и индексов метаданных. Для табличных полей формы явный XML-узел
`<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>` сейчас импортируется как
`ГоризонтальноеПоложениеВШапке: !xml Авто`.

Обычное значение `Авто` является неявным и исключается из validation-схемы.
YAML parser передаёт JSON Schema строку `Авто`, а пометку тега хранит отдельно,
поэтому schema validation ошибочно отклоняет согласованное транспортное
исключение. В проекте `sed_nkdk` это создаёт 12 diagnostics для шести свойств.

## Цель

Сделать пустой `!xml` единым представлением зарегистрированных транспортных
исключений и описывать его допустимость непосредственно в validation-схеме.
Обычная validation записанного YAML и локальная validation во время импорта
должны использовать одинаковые данные и одну схему.

## Не входит в задачу

- Новые применения `!xml` к свойствам или классам значений.
- Частные условия по типам элементов в общих слоях orchestration, validation и
  project.
- Добавление признаков в `BasePropertyRule`, `PropertyRule` или построители
  rules.ts.
- Поддержка прежней записи `!xml Авто`.
- Отдельная семантическая validation транспортного тега.

## Пользовательский договор

Для зарегистрированного свойства YAML содержит только пустой тег:

```yaml
ГоризонтальноеПоложениеВШапке: !xml
```

Значение, которое нужно создать в XML, хранится в существующей регистрации по
паре `itemType + propertyKey`:

```text
<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>
                    ↓ XML → YAML
ГоризонтальноеПоложениеВШапке: !xml
                    ↓ YAML → XML
<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>
```

Для зарегистрированного свойства допустим только пустой тег. Прежний
`!xml Авто` отклоняется validation-схемой свойства как запрещённое неявное
значение, а `fromYAML` по-прежнему проверяет точное совпадение помеченного
значения с регистрацией. Незарегистрированный пустой `!xml` также отклоняется.

В проекте уже существует отдельное согласованное применение непустого `!xml`
для UUID нестандартной панели `ClientApplicationInterface`. Оно не использует
реестр свойств и остаётся вне этой задачи. Поэтому общий структурный переходник
заменяет внутренним маркером только пустой `!xml`; непустые теги продолжают
передавать обычное значение специализированным существующим механизмам.

## Представление для validation

`!xml` является YAML-тегом, а не JSON-значением. Обычные смысловые данные
содержат пустую строку и отдельную пометку тега. Перед JSON Schema validation
`structuralYamlValue` преобразует помеченный scalar во внутреннее значение:

- пустой `!xml` — в допустимый внутренний маркер;
- непустой `!xml` — оставляет обычным значением для существующих
  специализированных механизмов.

Маркеры существуют только внутри скомпилированного validation-пути и не
попадают в YAML, XML, индексы или публичное смысловое представление.

При построении validation-схемы exporter запрашивает существующий реестр
`ExplicitXMLProperty` по `itemType + propertyKey`. Схема зарегистрированного
свойства получает дополнительную ветвь, принимающую только допустимый внутренний
маркер пустого `!xml`. У незарегистрированного свойства такой ветви нет.

Таким образом, сама JSON Schema обеспечивает весь договор:

- зарегистрированный пустой `!xml` проходит;
- незарегистрированный пустой `!xml` не проходит;
- прежний `!xml Авто` не проходит обычную схему свойства;
- значение без тега проверяется прежней схемой;
- окружающий объект и остальные свойства проверяются без изменений.

Отдельный semantic validator для `!xml` не добавляется.

## Реестр и границы слоёв

Реестр `ExplicitXMLProperty` остаётся единственным источником допустимости и
восстанавливаемого XML. Он предоставляет нейтральный запрос регистрации для
schema exporter. Конкретные регистрации по-прежнему находятся рядом с
реализациями метаданных.

Общие слои не проверяют конкретные `itemType`, имена YAML-свойств или виды форм.
Новых параметров rules.ts не требуется. Внешние JSON Schema для подсказок не
обязаны показывать внутренний маркер; изменение относится к schema graph,
скомпилированному для project validation и standalone validation.

## XML → YAML и YAML → XML

Для регистрации с действием `emit` сохраняются `xmlValue` и пустое
`yamlValue`. При совпадении XML импорт формирует пустую строку с пометкой `xml`.
Сериализатор выводит её канонически как `Ключ: !xml`, без `""`.

При обратном преобразовании существующая проверка регистрации принимает только
пустое помеченное значение и восстанавливает зарегистрированный `xmlValue`.
Регистрации с действием `omit` продолжают использовать тот же пустой синтаксис и
не создают XML-узел.

## Единые данные импорта и обычной validation

Parser записанного YAML уже сохраняет scalar-теги отдельно от значений.
`serializeYAMLDocument` должен переносить те же пометки в возвращаемые
`SerializedYAMLDocument.data`. Тогда смысловые данные, переданные локальной
validation импорта без повторного чтения файла, эквивалентны данным штатного
parser не только по значениям, но и по тегам.

Это изменение является общим для всех зарегистрированных `!xml`, а не частным
исключением импорта форм.

## Совместимость и миграция

Прежняя форма `!xml Авто` намеренно становится ошибкой. Повторный XML-import
формирует новый канонический YAML. Автоматическая миграция вручную написанного
YAML и молчаливое принятие старой формы не предусматриваются.

После реализации описание `HeaderHorizontalAlign` в `.agents/restrictions.md`
нужно привести к новому пустому синтаксису; перечень согласованных применений
`!xml` не расширяется.

## Проверки

Нужны следующие уровни тестов:

1. YAML parser различает пустой тег, обычное пустое значение и пустую строку.
2. Сериализатор выводит строго `Ключ: !xml` и сохраняет тег в
   `SerializedYAMLDocument.data`.
3. Validation-схема принимает внутренний маркер только для зарегистрированного
   свойства.
4. Обычная пустая строка, пустое значение без тега, прежний `!xml Авто` и
   незарегистрированный пустой `!xml` отклоняются.
5. XML → YAML импортирует явный `Auto` как пустой тег, а YAML → XML
   восстанавливает `Auto` без reference XML.
6. Локальная validation импортированного YAML совпадает с validation
   сериализованного и повторно прочитанного файла.
7. Регрессионный тест формы покрывает табличные `InputField`, `LabelField`,
   `PictureField` и `CheckBoxField` без изменения существующих XML-фикстур.
8. Контрольная validation `sed_nkdk` после получения YAML нового формата не
   содержит прежние 12 diagnostics `ГоризонтальноеПоложениеВШапке`.

После законченного слоя выполняются профильные тесты и
`pnpm duplicates -- --base eb239c54a`. Перед завершением выполняются полный
`pnpm test`, `pnpm test:architecture:rules` и `pnpm test:architecture`.

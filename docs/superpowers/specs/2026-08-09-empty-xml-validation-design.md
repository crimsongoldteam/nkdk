# Строковое значение `!xml` в validation-схеме

## Контекст

Транспортное значение `!xml` сохраняет различие XML, которое нельзя
восстановить из смысловых данных YAML и индексов метаданных. Для табличных
полей формы явный XML-узел
`<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>` сейчас импортируется как
`ГоризонтальноеПоложениеВШапке: !xml Авто`.

Обычное значение `Авто` является неявным и исключается из validation-схемы.
Поэтому schema validation отклоняет согласованное транспортное исключение. В
проекте `sed_nkdk` это создаёт 12 diagnostics для шести свойств.

Ранее предполагалось передавать пустой YAML-тег в JSON Schema через скрытый
служебный маркер. От этого решения отказываемся: внешний и внутренний договор
должны использовать одно строковое значение `!xml`.

## Цель

Сделать строку `!xml` единым представлением пустого транспортного значения и
добавлять её непосредственно в validation-схему зарегистрированного свойства.
Обычная validation записанного YAML и локальная validation во время импорта
должны использовать одинаковые данные и одну схему.

Отдельно убрать непустой `!xml` у UUID нестандартной панели. Различие между
отсутствующим и пустым `panelDef` должно находиться в YAML как самостоятельное
поле `ПустоеОпределение`, а не в UUID или снимке.

## Не входит в задачу

- Хранение транспортных различий в `.nkdk`-снимках.
- Частные условия по типам элементов в общих слоях orchestration, validation и
  project.
- Добавление признаков в `BasePropertyRule`, `PropertyRule` или построители
  rules.ts.
- Поддержка прежних записей `!xml Авто` и `!xml UUID`.
- Показ транспортных значений и полей во внешних схемах подсказок.
- Автоматическая миграция вручную написанного YAML без повторного XML-import.

## Пользовательский договор `!xml`

Пустая запись:

```yaml
ГоризонтальноеПоложениеВШапке: !xml
```

имеет строковое представление:

```ts
{ ГоризонтальноеПоложениеВШапке: "!xml" }
```

`!xml` не является глобально запрещённым значением. Его смысл определяется
обычной схемой и регистрацией конкретного свойства:

- зарегистрированное свойство может придать точной строке `!xml` транспортное
  действие над XML;
- незарегистрированное свободное строковое поле считает `!xml` обычным текстом;
- перечисление или другой ограниченный тип без регистрации отклоняет `!xml`
  своей обычной схемой.

Например:

```yaml
Комментарий: !xml
```

является строковым комментарием и экспортируется как:

```xml
<Comment>!xml</Comment>
```

Для зарегистрированного `ГоризонтальноеПоложениеВШапке` та же строка означает
другое действие:

```text
<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>
                    ↓ XML → YAML
ГоризонтальноеПоложениеВШапке: !xml
                    ↓ YAML → XML
<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>
```

Регистрация хранит восстанавливаемое XML-значение `Auto`. Обычное `Авто`
остаётся запрещённым неявным значением. Прежняя запись `!xml Авто` не совпадает
с точным транспортным значением `!xml` и отклоняется.

Непустая запись у свободной строки остаётся текстом целиком. Например,
`Комментарий: !xml Текст` имеет строковое значение `!xml Текст`. Специальные
регистрации в этой задаче принимают только точную строку `!xml`.

## Parser и сериализация

Локальный YAML-тег остаётся каноническим внешним синтаксисом. Parser возвращает
строку с тем же текстовым обозначением:

- `Поле: !xml` → `"!xml"`;
- `Поле: !xml Текст` → `"!xml Текст"`.

Пометка scalar-тега может сохраняться как информация о каноническом выводе, но
не меняет смысловое значение. Сериализатор выводит зарегистрированное пустое
значение строго как `Ключ: !xml`, без `""` и без скрытой подмены данных.

`SerializedYAMLDocument.data` содержит те же строковые значения, что и
повторный `parseMetadataYaml(text)`. Поэтому validation импорта не требует
специального структурного маркера и совпадает с validation записанного файла.

## Validation-схема

При построении validation-схемы exporter запрашивает существующий реестр
`ExplicitXMLProperty` по `itemType + propertyKey`. Схема зарегистрированного
свойства получает дополнительную ветвь `const: "!xml"`.

Для `ГоризонтальноеПоложениеВШапке` итоговый договор эквивалентен объединению:

```text
SystemEnumeration без неявного Авто | literal "!xml"
```

Дополнительная ветвь создаётся только при
`validationPropertyRefs: true`. Внешняя схема подсказок остаётся прежней и не
содержит ни литерал `!xml`, ни XML-only поля.

У свободной строки `!xml` и так является обычным допустимым текстом. Это
намеренное поведение: регистрация влияет на XML-преобразование конкретного
свойства, а не делает строку глобально запрещённой для остальных свойств.

Отдельный semantic validator и служебный объект-маркер не добавляются.

## Реестр и XML-преобразование

Реестр `ExplicitXMLProperty` остаётся источником специальных действий и
восстанавливаемого XML. Он предоставляет schema exporter нейтральный запрос о
регистрации пары `itemType + propertyKey`.

Для зарегистрированного свойства точная строка `!xml` запускает действие
регистрации. Для незарегистрированного строкового свойства она проходит обычное
преобразование как текст. Конкретные регистрации по-прежнему находятся рядом с
реализациями метаданных.

Общие слои не проверяют конкретные `itemType`, имена YAML-свойств или виды форм.
Новых параметров rules.ts не требуется.

## Пустое определение нестандартной панели

Текущее непустое применение:

```yaml
Панель:
  UUID: !xml 8e10648b-f52d-4ec2-b4dd-87de33778d95
```

одновременно хранит UUID и сообщает о физическом наличии пустого XML-узла
`panelDef`. Эти две обязанности разделяются.

Если `panelDef` отсутствует, YAML содержит только UUID:

```yaml
Панель:
  UUID: 8e10648b-f52d-4ec2-b4dd-87de33778d95
```

Если XML содержит пустое определение, YAML добавляет самостоятельное XML-only
поле:

```yaml
Панель:
  UUID: 8e10648b-f52d-4ec2-b4dd-87de33778d95
  ПустоеОпределение: !xml
```

При обратном преобразовании поле создаёт:

```xml
<panelDef id="8e10648b-f52d-4ec2-b4dd-87de33778d95"/>
```

`ПустоеОпределение` принимает только точное значение `!xml`, не хранится в
снимке и не показывается в схеме подсказок. При отсутствии поля пустой
`panelDef` не создаётся. UUID всегда остаётся обычным UUID.

Исследование `/Users/nikita/git/round-trip-compact/cf` обнаружило 25 файлов
`ClientApplicationInterface.xml` и нестандартные панели в обоих вариантах:
пустой `panelDef` присутствует в 9 случаях и отсутствует в 5. Наличие нельзя
надёжно вывести из UUID, `panel id`, расположения или семейства конфигурации:
одинаковые UUID и позиции встречаются с обоими вариантами. Поэтому различие
должно быть явным в YAML; снимки и эвристики не используются.

## Совместимость и миграция

Прежние формы намеренно не поддерживаются:

- `ГоризонтальноеПоложениеВШапке: !xml Авто`;
- `UUID: !xml <UUID>`.

Повторный XML-import формирует новый канонический YAML. Для панели он переносит
признак с UUID в `ПустоеОпределение: !xml`.

После реализации описание `HeaderHorizontalAlign`, `CharacteristicsDescription`,
`Table.rowFilter` и панели в `.agents/restrictions.md` нужно привести к новому
строковому договору. Перечень специальных действий не расширяется за пределы
согласованного поля `ПустоеОпределение`.

## Проверки

Нужны следующие уровни тестов:

1. Parser возвращает `"!xml"` для пустого тега и `"!xml Текст"` для непустого.
2. Сериализатор выводит зарегистрированное значение строго как `Ключ: !xml`, а
   `SerializedYAMLDocument.data` совпадает с повторно прочитанным YAML.
3. Validation-схема `ГоризонтальноеПоложениеВШапке` принимает `!xml`, но
   отклоняет обычное `Авто` и прежнее `!xml Авто`.
4. Схема подсказок не содержит `!xml`.
5. Свободное строковое поле принимает `!xml` как текст и экспортирует его в XML
   без специального действия.
6. XML → YAML импортирует явный `HeaderHorizontalAlign=Auto` как пустой `!xml`,
   а YAML → XML восстанавливает `Auto` без reference XML.
7. `ПустоеОпределение: !xml` создаёт пустой `panelDef`; обычный UUID не создаёт
   его; XML-import различает оба варианта без снимка.
8. Прежний `UUID: !xml UUID` отклоняется validation-схемой и не запускает
   специальное действие.
9. Локальная validation импортированного YAML совпадает с validation
   сериализованного и повторно прочитанного файла.
10. Регрессионный тест формы покрывает табличные `InputField`, `LabelField`,
    `PictureField` и `CheckBoxField` без изменения XML-фикстур.
11. Контрольная validation `sed_nkdk` после повторного импорта не содержит
    прежние 12 diagnostics `ГоризонтальноеПоложениеВШапке`.

После каждого законченного слоя выполняется
`pnpm duplicates -- --base eb239c54a`. Перед завершением выполняются
`pnpm type-check`, полный `pnpm test`, `pnpm test:architecture:rules` и
`pnpm test:architecture`.

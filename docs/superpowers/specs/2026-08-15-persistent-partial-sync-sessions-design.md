# Постоянные сеансы частичной синхронизации

## Контекст

Матричный e2e частичной синхронизации сейчас открывает новый MCP-сеанс для
каждой операции, явно закрывает платформенное соединение и только затем
проверяет выгрузку базы. Агент Конфигуратора и автономный сервер поэтому
запускаются заново для каждого небольшого ZIP-пакета.

Точечные замеры показали, что запуск платформенного сеанса занимает примерно
9 секунд в агентном режиме и 18 секунд в автономном. Непосредственная загрузка
ZIP и обновление конфигурации базы занимают около 2 и 6 секунд соответственно.

## Цель

Выполнять последовательность частичных операций одного e2e-сценария через
один MCP-сеанс и один основной платформенный сеанс. Автономный процесс `ibsrv`
должен переиспользоваться так же, как агент Конфигуратора, до явного закрытия,
ошибки соединения или тайм-аута простоя.

## Границы

В изменение входят:

- постоянный жизненный цикл автономного `ibsrv` и его SSH-сеанса;
- переиспользование автономного сеанса для загрузки, выгрузки и получения
  списка расширений;
- один MCP-сеанс для всего матричного e2e;
- один основной платформенный сеанс для всех частичных операций сценария;
- итоговая проверочная выгрузка после закрытия основного сеанса;
- контрольная копия после каждой успешной операции при работающей файловой
  базе как явно принятый риск проверочного e2e;
- измерение общего и платформенного времени точечных реальных сценариев.

Не входят:

- поддержка автономного режима для клиент-серверных баз;
- новый публичный MCP-инструмент управления сеансами;
- изменение формата ZIP или алгоритма выбора затронутых объектов;
- гарантия согласованности контрольной копии работающей файловой базы.

## Жизненный цикл автономного сеанса

`createStandaloneServerSession` подготавливает `config.yaml`, запускает `ibsrv`,
открывает SSH и сохраняет процесс и командный сеанс в объекте `PlatformSession`.
Порты, ключ и каталоги данных принадлежат этому объекту до его закрытия.

Последующие вызовы `loadPartialConfiguration` создают отдельный staging-каталог,
копируют туда ZIP и `load.lst`, выполняют `config load-files`, затем безусловно
выполняют `config update-db-cfg`. Процесс и SSH после успеха не закрываются.

Выгрузка и получение расширений при живом автономном процессе выполняются через
тот же командный сеанс. Выгрузка использует служебный каталог внутри
`users-data`, после чего файлы перемещаются в каталог операции по тому же
договору безопасности путей, что и в агентном режиме.

`isAlive` проверяет одновременно состояние объекта, процесса и SSH-сеанса.
`close` и `cancel` закрывают соединение с базой, останавливают автономный сервер,
удаляют временные каталоги и `config.yaml`. `nkdk.close_platform_connection`
остаётся публичной точкой явного завершения. Менеджер также закрывает сеанс по
существующему тайм-ауту простоя.

## Ошибки

Подтверждённый платформой отказ одного пакета возвращает ошибку операции, но не
обязан уничтожать живой командный сеанс. Следующий исправленный пакет может
использовать его повторно.

Тайм-аут, отмена, потеря SSH, смерть `ibsrv` или неизвестный результат передачи
делают сеанс непригодным. Менеджер удаляет его из кэша и при следующей операции
создаёт новый. Остановка и очистка идемпотентны; ошибка очистки не заменяет
исходную ошибку команды.

## Жизненный цикл e2e

Сценарий открывает один `ScenarioMcpSession` до подготовки или восстановления
исходного состояния и закрывает его в `finally`. `PartialSyncSteps` получает
готовый сеанс и не создаёт его внутри каждой операции.

Исходный импорт открывает основной платформенный сеанс. Каждая операция затем:

1. изменяет YAML;
2. выполняет валидацию;
3. отправляет частичный ZIP;
4. повторным вызовом получает `unchanged`;
5. публикует контрольную копию без остановки платформенного сеанса.

Промежуточная полная выгрузка после каждой операции удаляется. После последней
операции сценарий вызывает `nkdk.close_platform_connection`, создаёт отдельный
проект проверки, полностью импортирует конфигурацию базы и сравнивает её с
рабочим YAML-проектом. Затем проверочное соединение также явно закрывается.

При продолжении с контрольной копии восстановление выполняется до открытия
платформенного соединения. Каталоги `.nkdk/platform-sessions` и `.nkdk/tmp` не
восстанавливаются из контрольной копии: сохранённые PID, порты, блокировки и
незавершённые попытки не являются состоянием проекта.

## Контрольные копии

Публикация сохраняет прежний атомарный порядок: новая копия полностью
записывается и проверяется по SHA-256, затем заменяет `current`, после чего
обновляется `state.json`. Ошибка копирования оставляет прежнюю контрольную точку
и состояние.

Проверка SHA-256 подтверждает только неизменность скопированных байтов. Она не
доказывает внутреннюю согласованность файловой базы, скопированной при живом
`ibsrv`. Этот риск принят только для проверочного e2e. Если восстановленная база
не открывается, сценарий завершается с указанием контрольной точки и требует
повторного запуска с `--reset`.

## Проверки

Модульные и совместные тесты фиксируют следующие договоры:

- две частичные загрузки используют один процесс `ibsrv` и один SSH-сеанс;
- staging-каталоги двух загрузок независимы и удаляются после операции;
- выгрузка и список расширений используют живой автономный сеанс;
- `close`, `cancel`, тайм-аут и потеря процесса завершают принадлежащий процесс;
- один e2e-сценарий открывает и закрывает ровно один MCP-сеанс;
- частичные операции не вызывают `close_platform_connection` между собой;
- итоговая проверка выполняется после закрытия основного соединения;
- контрольная точка не восстанавливает временное состояние платформенного
  сеанса;
- сбой операции закрывает MCP-сеанс через `finally` и не публикует её как
  завершённую.

После реализации выполняются четыре точечных реальных сценария: модуль и
структурное изменение в агентном и автономном режимах. Для каждого проверяются
`synchronized`, затем `unchanged`, фактическое применение изменений и время
первого и повторного пакетов в одном сеансе. Полная матрица повторно не
запускается.

## Критерии готовности

- второй пакет возвращает `reusedConnection: true` в обоих режимах;
- автономный режим не запускает второй `ibsrv` между пакетами;
- обновление конфигурации базы выполняется после каждого принятого ZIP;
- явное закрытие и аварийные пути не оставляют живых принадлежащих процессов;
- итоговая выгрузка совпадает с YAML-проектом;
- точечный e2e показывает сокращение времени второго изменённого пакета;
- существующее ограничение автономного режима для клиент-серверных баз
  сохраняется.

# DefinedType и пустой DesignTimeRef в значении заполнения

## Контекст

Проверка `ЗначениеЗаполнения` умеет сопоставлять значение с непосредственно
описанным типом реквизита, но останавливается на ссылке вида
`DefinedType.<Имя>`. Поэтому контрольный импорт SED создаёт 19 предупреждений
`проверка значения для типа DefinedType.<Имя> не поддержана`.

В XML использование определяемого типа содержит только ссылку:

```xml
<v8:TypeSet>cfg:DefinedType.Организация</v8:TypeSet>
```

Настоящий состав типа хранится в отдельном объекте
`DefinedTypes/Организация.xml`. В YAML этим двум уровням соответствуют:

```yaml
Тип: ОпределяемыйТип.Организация
```

и:

```yaml
# ОпределяемыйТип/Организация/Свойства.yaml
Тип: Справочник.Организации
```

## Цели

- Проверять `ЗначениеЗаполнения` по настоящему составу DefinedType.
- Переиспользовать существующий индексированный поиск определяемого типа,
  который уже применяется при проверке `ПутьКДанным`.
- Сохранять пустой XML `DesignTimeRef` явно и понятно как
  `!xml DesignTimeRef`.
- Устранить 19 предупреждений этой группы в контрольном импорте SED.

## Границы

В задачу не входят:

- значения по умолчанию свойств владельца для стандартного реквизита `Код`;
- обработка стандартного реквизита `Владелец` при пустом списке владельцев;
- изменение общего смысла тега `!xml`;
- перенос XML-namespace `xr` в пользовательский YAML;
- добавление новых полей в общие типы rules.ts.

## Получение настоящего типа

Когда тип реквизита содержит `DefinedType.<Имя>`, локальная проверка не пытается
угадать его состав и не читает соседний файл напрямую. Она откладывает
классификацию до проектного прохода.

Проектный проход находит `ОпределяемыйТип/<Имя>/Свойства.yaml` через существующий
индекс метаданных и получает его свойство `Тип`. Используется та же предметная
информация владельца, через которую `ПутьКДанным` уже раскрывает DefinedType.
После этого общий классификатор `ЗначениеЗаполнения` работает с полученным
конкретным или составным типом.

Если объект не найден, не импортируется или не содержит определяемого типа,
проверка оставляет предметное предупреждение с именем DefinedType. Такой случай
не превращается автоматически в допустимое значение и не скрывается тегом.

Для расширения заимствованный DefinedType с пустым локальным `Тип` разрешается
через соответствующий объект базового компонента по действующим правилам
проектного индекса.

## Пустой DesignTimeRef

XML допускает две разные формы отсутствующего содержательного значения:

```xml
<FillValue xsi:nil="true"/>
<FillValue xsi:type="xr:DesignTimeRef"/>
```

Вторая форма означает пустое ссылочное значение без выбранного конкретного
типа. Она не выводится автоматически только из того, что реквизит имеет
составной тип.

Проверка `/Users/nikita/git/round-trip-compact/cf` нашла 17 310 `FillValue` у
составных типов:

| XML-форма | Количество | Доля |
|---|---:|---:|
| `xsi:nil="true"` | 10 540 | 60,9% |
| пустой `DesignTimeRef` | 809 | 4,7% |
| типизированная `*.EmptyRef` | 5 539 | 32,0% |
| содержательная ссылка | 14 | 0,1% |
| прочие значения | 408 | 2,3% |

Среди 4 848 составных типов, полученных через DefinedType, `xsi:nil` встречается
4 620 раз, а пустой `DesignTimeRef` — 141 раз. Следовательно, различие нельзя
однозначно восстановить только по типу реквизита.

## YAML-представление

Пустой `DesignTimeRef` записывается явно:

```yaml
ЗначениеЗаполнения: !xml DesignTimeRef
```

Это значение имеет один точный смысл:

```xml
<FillValue xsi:type="xr:DesignTimeRef"/>
```

В YAML используется предметное имя `DesignTimeRef`, а не XML QName
`xr:DesignTimeRef`. Префикс `xr` является деталью XML-представления и
добавляется обработчиком при записи.

Обычная строка `DesignTimeRef`, пустой `!xml` и `!xml xr:DesignTimeRef` не
являются эквивалентами согласованного значения.

`!xml DesignTimeRef` — явный транспортный признак. Для него не создаётся запись
снимка конфигурации: необходимая XML-форма полностью задана самим YAML.

## Проверка тега

`!xml DesignTimeRef` разрешён только для свойства `ЗначениеЗаполнения` у
зарегистрированных типов `MetadataAttribute` и
`StandardAttributeDescription`.

Значение допустимо, когда после раскрытия эффективный тип содержит ссылочную
альтернативу. Для типа, состоящего только из строки, числа, даты или булева,
validation выдаёт ошибку несовместимости.

Внутренняя validation-схема принимает согласованный транспортный литерал. Схема
подсказок не предлагает ни `!xml`, ни `DesignTimeRef` как штатное значение.

Распознанный транспортный литерал не создаёт ссылку на объект метаданных и не
участвует в переименовании: конкретная цель в нём отсутствует.

## Несовместимые значения после раскрытия

DefinedType `АвторДействия` допускает:

- `Справочник.Сотрудники`;
- `Справочник.АвтоподстановкиДляОбъектов`;
- `Справочник.ПолныеРоли`.

В 12 объектах SED исходный XML содержит пустую ссылку
`Справочник.Пользователи`, которая не входит в этот состав. После раскрытия это
значение классифицируется как `invalid` и сохраняется действующим механизмом
исключения:

```yaml
ЗначениеЗаполнения: !xml Справочник.Пользователи.ПустаяСсылка
```

Без `!xml` то же значение остаётся ошибкой. Ссылка внутри исключения продолжает
участвовать в проверке зависимостей, поиске и переименовании.

## Поведение операций

### XML → YAML

- `xsi:nil="true"` не создаёт `ЗначениеЗаполнения`.
- Пустой `xr:DesignTimeRef` создаёт `ЗначениеЗаполнения: !xml DesignTimeRef`.
- Несовместимое значение после раскрытия DefinedType создаёт существующую форму
  `!xml <исходное значение>`.
- Неявная типизированная пустая ссылка одиночного типа удаляется из YAML и
  восстанавливается действующим снимком.
- Допустимое содержательное значение остаётся обычным YAML.

### Validation YAML

- Значение проверяется по составу найденного DefinedType.
- `!xml DesignTimeRef` принимается только для ссылочного эффективного типа.
- Несовместимое обычное значение даёт ошибку по точному пути
  `ЗначениеЗаполнения`.
- Отсутствующий или неразрешимый DefinedType даёт предупреждение и не позволяет
  использовать `!xml DesignTimeRef` как способ его скрыть.

### YAML → XML

- `!xml DesignTimeRef` создаёт пустой элемент с
  `xsi:type="xr:DesignTimeRef"`; текст `DesignTimeRef` в XML не записывается.
- Остальные формы `!xml <значение>` продолжают использовать существующий
  обработчик значения заполнения.
- Тег `!xml` никогда не попадает в XML-текст.

## Проверки

Модульные и интеграционные проверки должны подтвердить:

1. DefinedType раскрывается через проектный индекс до конкретного и составного
   типа.
2. Заимствованный пустой DefinedType расширения использует тип базового
   компонента.
3. Отсутствующий, ошибочный или пустой без базы DefinedType оставляет
   предупреждение.
4. XML с пустым `xr:DesignTimeRef` импортируется как точное
   `!xml DesignTimeRef` без снимка.
5. YAML `!xml DesignTimeRef` восстанавливает пустой `xr:DesignTimeRef` без
   reference XML.
6. Обычная строка, пустой `!xml` и `!xml xr:DesignTimeRef` не запускают это
   действие.
7. Схема подсказок не содержит транспортный литерал.
8. `!xml DesignTimeRef` у нессылочного типа отклоняется.
9. 12 ссылок `АвторДействия → Пользователи` импортируются с `!xml`, а без тега
   не проходят validation.

## Контрольный импорт SED

После реализации повторный чистый импорт должен дать следующий результат для
19 прежних предупреждений DefinedType:

- 5 пустых `DesignTimeRef` записаны как `!xml DesignTimeRef`;
- 12 несовместимых ссылок `АвторДействия → Пользователи` записаны как
  `!xml Справочник.Пользователи.ПустаяСсылка`;
- 2 неявные типизированные пустые ссылки отсутствуют в YAML и восстанавливаются
  из снимка;
- предупреждений `проверка значения для типа DefinedType.<Имя> не поддержана`
  нет.

Остальные группы предупреждений не меняются этой задачей.

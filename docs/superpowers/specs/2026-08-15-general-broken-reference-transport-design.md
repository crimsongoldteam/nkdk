# Общий перенос битых ссылок XML ↔ YAML

## Контекст

Ссылочные свойства метаданных уже описывают смысловую цель через
`metadataTarget`, а общие типы свойств умеют перечислять такие ссылки для
структурных операций и проверки проекта. При этом перенос битых XML-ссылок
сейчас реализован отдельными `BrokenXMLReferenceCarrierRegistration` для
конкретных типов и мест применения.

Из-за этого одинаковая аномалия требует отдельного кода для
`MetadataItemLinks`, `DesignTimeRef`, порядка подсистем и других XML-форм. Новый
случай в `CashdeskDev_3_32_26_0_setup1c` не покрыт: четыре
`FunctionalOptionsProperty` содержат UUID отсутствующих функциональных опций,
и импорт падает при попытке разобрать UUID как канонический корень метаданных.

Наблюдаемые UUID:

- `76e70e66-9e54-4a40-95ce-cff9444899e7` в трёх формах отчётов;
- `6537a19c-3357-46a2-96a6-1fe4619ddbc8` в общей форме
  `РедактированиеСтроки`.

Оба UUID используются как ссылки, но соответствующих объектов метаданных в
конфигурации нет.

## Цель

Сделать `!xml/reference` общим транспортом отсутствующих ссылок для всех типов
ссылочных свойств:

- свойство подключается автоматически по наличию `metadataTarget`;
- общий механизм одинаково работает со скалярами, элементами коллекций,
  вложенными значениями и ключами YAML-словарей;
- тип свойства описывает только собственную XML-форму ссылки;
- тег появляется только после подтверждённого результата `missing`;
- YAML → XML восстанавливает исходную XML-форму без reference XML.

## Границы

В работу входят:

- общий договор обнаружения, разрешения и переноса ссылок;
- все общие типы свойств с `metadataTarget` и проверяемой целью;
- поддержка `!xml/reference` на YAML-ключах;
- перенос существующих metadata-ссылок на общий договор;
- сохранение локальных ссылок формы в том же транспортном конвейере с
  отдельным локальным resolver;
- регистрация битых `FunctionalOptionsProperty` из CashdeskDev в перечне
  XML-аномалий после реализации.

В работу не входят:

- `metadataTarget` с `validation: "translateOnly"`: существование их цели
  намеренно не проверяется, поэтому `missing` доказать нельзя;
- автоматическое исправление или удаление битых ссылок;
- автоматическое снятие устаревшего `!xml/reference` после появления цели;
- трактовка любой ошибки fromXML/toYAML как битой ссылки;
- новое reference XML или использование reference XML для восстановления
  ссылок;
- изменение исходных XML-фикстур;
- изменение исходного кода зависимости `js-yaml`.

## Основные решения

### Автоматическое подключение через `metadataTarget`

Экземпляры свойств не получают нового признака. Любое свойство с
`metadataTarget`, кроме `translateOnly`, автоматически участвует в общем
механизме.

Новые поля не добавляются в `PropertyRule`, `BasePropertyRule` или построители
rules.ts. Сведения о расположении ссылки в значении и её XML-кодировании
объявляются один раз операциями соответствующего общего типа свойства в
существующем реестре type rules.

Нейтральный runtime знает только:

- ограничение `metadataTarget`;
- расположение ссылки в YAML;
- исходное представление ссылки, предоставленное обработчиком типа;
- результат resolver: `found`, `missing` либо `ambiguous`;
- операции поставить тег, подготовить обычное значение для экспорта и вернуть
  исходное XML-представление.

Он не содержит проверок по `itemType`, XML-корням, UUID функциональных опций,
папкам форм или другим concrete-деталям.

### Описание вхождения ссылки

Общий тип перечисляет вхождения ссылок. Каждое вхождение содержит:

- YAML-путь к контейнеру;
- положение `value` или `key`;
- ключ или индекс внутри контейнера;
- смысловое ограничение `metadataTarget`;
- каноническое значение, если оно построено;
- исходный XML-payload и сведения, необходимые обработчику типа для обратной
  записи.

Точное имя TypeScript-интерфейса определяется планом реализации. Договор не
требует хранить эти сведения в итоговой предметной модели: это данные прохода
импорта и sidecar YAML.

### Разрешение цели

Общий resolver возвращает только одно из состояний:

| Состояние | Смысл | Действие импорта |
|---|---|---|
| `found` | найдена единственная допустимая цель | обычное каноническое YAML-представление |
| `missing` | допустимая по XML-форме ссылка не имеет цели | исходный payload с `!xml/reference` |
| `ambiguous` | одной смысловой ссылке соответствуют несколько целей | ошибка проекта, тег не ставится |

UUID и другие XML-идентификаторы проверяются через общий индекс идентичностей,
а канонические ссылки — через существующий индекс `metadataTarget`. Результат
`missing` разрешено формировать только после построения общего снимка первого
прохода импорта.

Синтаксически недопустимая XML-форма не является `missing`: обработчик типа
возвращает обычную ошибку импорта. Исключения fromXML/toYAML не перехватываются
как способ обнаружения битой ссылки.

### Два прохода XML → YAML

Первый проход:

1. читает XML и строит предметную модель;
2. обработчики типов фиксируют ссылочные вхождения вместе с исходным XML;
3. собирает идентичности и канонические цели в общий индекс;
4. удерживает подготовленный YAML до общего барьера импорта.

Второй проход:

1. разрешает каждое отложенное ссылочное вхождение по зафиксированному снимку;
2. материализует обычное YAML-представление для `found`;
3. сохраняет исходный payload и ставит `!xml/reference` для `missing`;
4. оставляет `ambiguous` ошибкой;
5. только после этого проверяет и записывает YAML.

Это продолжает уже принятый договор отложенного разрешения ссылок и не вводит
досрочную запись отдельных типов.

### Значения и коллекции

Тег ставится на минимальное битое вхождение, а не на всё свойство. Например:

```yaml
ФункциональныеОпции:
  - ИспользоватьСкидкиНаценки
  - !xml/reference 76e70e66-9e54-4a40-95ce-cff9444899e7
```

Исправная ссылка остаётся предметным именем. При экспорте она проходит обычный
toXML, а тегированный элемент восстанавливается обработчиком XML-формы
`FunctionalOptionsProperty` как обычный текст элемента `Item`.

Для составных типов тег также ставится на конкретный скаляр внутри структуры.
Payload всегда содержит исходное ссылочное значение, а не сериализованный
XML-фрагмент.

### Ссылочные ключи YAML

Ссылки, представленные ключами словаря, получают тег на самом ключе:

```yaml
Роли:
  !xml/reference 6537a19c-3357-46a2-96a6-1fe4619ddbc8: Истина
```

Это допустимый YAML-синтаксис, но текущая конструкция scalar-тега NKDK
возвращает объект-обёртку, который `js-yaml` не может использовать как ключ
обычного JS-объекта. Поддержка реализуется в обёртке NKDK над публичными
событиями и AST `js-yaml`; исходный код зависимости не меняется.

В памяти ключ остаётся обычной строкой:

```ts
{
  Роли: {
    "6537a19c-3357-46a2-96a6-1fe4619ddbc8": "Истина",
  },
}
```

Тег ключа хранится отдельно в sidecar:

```ts
WeakMap<object, Map<string, YAMLScalarTag>>
```

YAML-парсер:

1. распознаёт scalar-ключ с `!xml/reference` по событиям/AST;
2. строит JS-объект с нетегированным строковым ключом;
3. записывает тег в sidecar контейнера;
4. сохраняет обычный порядок ключей и координаты диагностики.

YAML-сериализатор выполняет обратное преобразование: по sidecar помечает
scalar-узел ключа в создаваемом AST и передаёт дерево штатному presenter
`js-yaml`.

Операции копирования, сортировки и пересоздания YAML-словарей обязаны переносить
теги ключей вместе с существующими тегами значений и порядком ключей. После
снятия тега применяются обычные правила дубликатов ключей; два ключа, ставшие
одинаковыми, отклоняются.

Тег на составном ключе, тег ключа без payload и иная категория XML-аномалии в
месте ссылочного ключа являются ошибками.

### YAML → XML

Общий экспорт сначала перечисляет ссылочные вхождения типа и проверяет sidecar
тегов значений и ключей.

- Нетегированное вхождение проходит обычные fromYAML/toXML и resolver.
- Тегированное вхождение не канонизируется как предметная ссылка.
- Обработчик типа проверяет грамматику payload и возвращает исходную XML-форму.
- В смешанной структуре обычные и тегированные элементы обрабатываются
  независимо.

Экспорт не использует reference XML. Пользователь может вручную записать
`!xml/reference`, если payload соответствует грамматике типа и цель действительно
отсутствует.

## Области разрешения ссылок

Транспорт и правила тега едины, но resolver зависит от области ссылки.

### Metadata-ссылки

Все проверяемые свойства с `metadataTarget` используют общий индекс проекта.
На этот путь переводятся существующие случаи:

- `MetadataItemLinks` с битым `MDObjectRef`;
- UUID в порядке подсистем CommandInterface;
- `MetadataValue/DesignTimeRef` с отсутствующей целью;
- новые битые `FunctionalOptionsProperty`.

Составная грамматика `DesignTimeRef` и различия XML-обёрток остаются в
обработчиках соответствующих типов, а не в resolver.

### Локальные ссылки формы

Ссылки на команды, элементы, группы и пути внутри формы не являются
`metadataTarget`. Они сохраняют специализированный resolver по локальному
индексу формы, но используют тот же транспорт:

- те же sidecar тегов значений и ключей;
- тот же `!xml/reference`;
- тот же экспортный конвейер и проверку payload;
- те же правила избыточного тега.

Таким образом, второго механизма переноса аномалий не появляется: различается
только источник ответа `found`/`missing`.

## Валидация

Единый договор для значений и ключей:

| Ссылка | Тег | Результат |
|---|---|---|
| существует | отсутствует | корректно |
| отсутствует | отсутствует | ошибка `Не найдена ссылка` |
| отсутствует | `!xml/reference` | корректно |
| существует | `!xml/reference` | ошибка ``!xml/reference не требуется`` |
| неоднозначна | любой | ошибка `Неоднозначная ссылка` |
| payload не соответствует XML-форме | `!xml/reference` | структурная ошибка типа |

Принятый `missing + !xml/reference` не создаёт дополнительного предупреждения:
сам тег является явным описанием известной XML-аномалии.

Пользовательская JSON Schema не предлагает битые ссылки как обычные предметные
значения. Внутренний validation graph принимает только зарегистрированную
грамматику типа. Для тегов ключей одного JSON Schema недостаточно, поскольку в
предметных данных ключ остаётся строкой; структурная и межфайловая проверка
обязательно читает sidecar ключей.

Диагностика тегированного ключа указывает путь соответствующей записи, например
`Использование.Роли.<uuid>`.

`translateOnly` сохраняет прежнюю синтаксическую трансляцию и не участвует в
проверках `missing`, избыточности тега и общем переносе битых целей.

## Обработка ошибок

- Неизвестный XML-корень, сбой type rule или иное исключение преобразования не
  превращается в `!xml/reference`.
- `missing` принимается только от resolver после проверки допустимой XML-формы.
- `ambiguous` никогда не маскируется тегом.
- Тег другого класса XML-аномалии не заменяет `!xml/reference`.
- Избыточный тег не удаляется автоматически: пользователь исправляет YAML либо
  повторно импортирует XML после восстановления цели.
- Ошибка одного вхождения не меняет соседние исправные ссылки.
- Конфликт двух обработчиков одной XML-формы сохраняет диагностику конфликта
  реестра, а не выбирает произвольный обработчик.

## Миграция существующей реализации

`BrokenXMLReferenceCarrierRegistry` остаётся единым транспортным конвейером, но
выбор metadata-переноса больше не ограничивается ручной регистрацией на каждом
`propertyType`. Он делегирует перечисление вхождений и XML-кодирование операциям
общего типа, если у свойства есть проверяемый `metadataTarget`.

Специализированные переносчики `MetadataItemLinks`, порядка подсистем и
`DesignTimeRef` удаляются после переноса их XML-грамматик в обработчики типов.
Локальные переносчики формы могут сохранить отдельные регистрации resolver,
но не дублируют YAML-sidecar, экспорт и validation pipeline.

Миграция атомарная: совместимость с нетегированными UUID, которые не являются
обычными предметными значениями, не добавляется.

## Проверки

### YAML runtime

- разбор и сериализация `!xml/reference` у scalar-ключа;
- ключ остаётся строкой, а тег доступен только через sidecar;
- перенос тега при копировании и сохранении порядка словаря;
- несколько тегированных и обычных ключей;
- дубликат после нормализации ключа;
- запрет тега на составном ключе, пустого payload и чужой категории;
- отсутствие изменений в исходном коде и установленном пакете `js-yaml`.

### Общий ссылочный конвейер

- scalar value;
- смешанная коллекция;
- вложенное значение;
- ключ словаря;
- `found`, `missing`, `ambiguous`;
- исключение `translateOnly`;
- избыточный тег после появления цели;
- некорректный payload;
- независимый экспорт соседних обычных и тегированных ссылок.

### Типы и регрессии

- `MetadataItemLinks/MDObjectRef`;
- порядок подсистем CommandInterface;
- `MetadataValue/DesignTimeRef`;
- `FunctionalOptionsProperty`;
- `UserVisible` или другой ссылочный словарь;
- локальные ссылки формы.

Каждый тип проверяет собственную XML-форму в обоих направлениях и отрицательные
границы своей грамматики.

### Интеграция

- импорт CashdeskDev сохраняет четыре отсутствующих UUID как
  `!xml/reference` и не создаёт ошибок импорта;
- XML → YAML → XML восстанавливает соответствующие `Item` без reference XML;
- после исправления текущего блока round-trip CashdeskDev продолжается только
  до следующего независимого расхождения;
- существующие XML-фикстуры не изменяются.

### Проектные проверки

- адресные unit и интеграционные тесты;
- `pnpm type-check`;
- `pnpm duplicates -- --base <commit>` после каждого законченного слоя;
- `pnpm test` вне песочницы;
- архитектурные проверки перед PR.

## Документация после реализации

- `.agents/xml-anomalies.md`: добавить четыре битые
  `FunctionalOptionsProperty` CashdeskDev и сослаться на общий договор
  `!xml/reference`;
- актуализировать описание `!xml/reference` в действующей спецификации
  классифицированных XML-аномалий;
- при необходимости изменения `.agents/architecture.md` сначала получить
  отдельное явное согласование разработчика согласно проектным инструкциям.

## Критерии готовности

- любое проверяемое свойство с `metadataTarget` подключается без настройки на
  конкретном свойстве;
- `translateOnly` не получает ложных `missing`;
- тег ставится только после подтверждения отсутствующей цели;
- значения и ключи поддерживают единый `!xml/reference`;
- найденная цель с тегом отклоняется как избыточная;
- `ambiguous` остаётся ошибкой;
- существующие metadata-переносчики используют общий договор;
- локальные ссылки формы используют тот же транспорт с локальным resolver;
- CashdeskDev проходит текущий блокер и точно восстанавливает четыре исходных
  UUID;
- полный набор обязательных проверок проекта проходит.

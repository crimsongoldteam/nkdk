# Настройки и диагностика импорта из информационной базы

## Цель

`nkdk.import_from_infobase` должен читать подключение только из локального
`.nkdk/project.yaml`, проверять этот файл общим для платформенных операций
механизмом и возвращать ссылку на его JSON Schema, если настройки отсутствуют
или некорректны.

После успешной проверки настроек операция должна возвращать короткую
безопасную ошибку, полученную от платформы, и ссылку на подробный локальный
журнал. Пользователю не требуется отдельная команда проверки подключения:
сведения, необходимые для исправления подключения, формируются самой
операцией импорта.

## Границы

Входит в изменение:

- ошибки поиска и запуска платформы, подключения к информационной базе и
  выгрузки конфигурации;
- одинаковый внешний договор для агента Конфигуратора и offline-режима
  `ibcmd`;
- отдельный журнал каждой операции импорта внутри её временного каталога;
- безопасная команда, код завершения и очищенный вывод платформы в журнале;
- краткий текст ошибки и `resource_link` на журнал в результате MCP;
- общий разбор и проверка `.nkdk/project.yaml` для повторного использования
  импортом, синхронизацией и другими платформенными операциями;
- JSON Schema настроек как MCP resource;
- удаление параметров подключения из входа `import_from_infobase`;
- отдельные настройки режима и неразрешённых ссылок для импорта;
- ручное внесение всех настроек, включая пароли, в `.nkdk/project.yaml`.

Не входит:

- отдельная операция диагностики подключения;
- автоматическое исправление параметров подключения;
- автоматические попытки входа под пользователями `Администратор` или `Admin`;
- распознавание причин по словарю сообщений разных версий платформы;
- изменение способа хранения паролей;
- автоматическое создание или исправление содержимого `.nkdk/project.yaml`;
- отдельный MCP-инструмент получения схемы или записи настроек;
- журналы обычных операций импорта XML → YAML после успешной выгрузки;
- настройка числа потоков, частичной или архивной выгрузки, расширений и
  обновления существующего XML-каталога;
- настройки будущей синхронизации с информационной базой;
- автоматический переход между агентом Конфигуратора и `ibcmd` при ошибке;
- изменение поддерживаемых версий платформы и видов баз.

## Вход импорта и источник настроек

`nkdk.import_from_infobase` принимает только:

```ts
type ImportFromInfobaseInput = {
  projectDir: string
  allowWrite?: boolean
}
```

Поля `connectionString`, `user`, `password`, `useStandaloneServer`,
`sessionIdleTimeout` и `database` удаляются из входа инструмента. Единственным
источником параметров подключения становится `.nkdk/project.yaml`. Вход MCP не
может переопределять отдельные значения файла.

Минимальные настройки самой операции находятся отдельно от общего подключения:

```yaml
infobase:
  connectionString: 'Srvr="server";Ref="base";'
  user: Администратор
  password: ""
  sessionIdleTimeout: 300
  database:
    dbms: PostgreSQL
    server: db-server
    name: infobase
    user: postgres
    password: ""
  operations:
    import:
      mode: standalone-server
      unresolvedReferences: include
```

Служебного поля версии в файле нет. При будущем несовместимом изменении MCP
публикует ресурс схемы с новым URI, а диагностика указывает на актуальную
схему и конкретные несовместимые поля.

`infobase.operations.import.mode` обязателен и принимает `designer-agent` либо
`standalone-server`; прежнее общее поле `useStandaloneServer` удаляется.
Обратная совместимость не поддерживается: файл с `useStandaloneServer`
возвращает `invalid_project_settings`, автоматической миграции и запасного
чтения старого формата нет. Пользователь исправляет файл по опубликованной
схеме и повторяет операцию.
Будущая синхронизация получит собственный блок `operations.sync`, поэтому она
сможет использовать агент Конфигуратора при импорте через `ibcmd`. NKDK не
переключает режим автоматически: применение инструментов автономного сервера к
базе, которую обслуживает кластер 1С, небезопасно.

`unresolvedReferences` принимает `include` или `omit` и по умолчанию равно
`include`. Значение `omit` передаётся обоим адаптерам как
`--ignore-unresolved-refs`; при `include` этот ключ отсутствует. Положительное
поле делает смысл настройки явным: без специального ключа платформа выгружает
неразрешённые ссылки. Остальные ключи платформы NKDK для первого полного
импорта выбирает самостоятельно и не публикует в настройках.

Агент Конфигуратора также поддерживает обновление существующей выгрузки,
выбор объектов и расширений, архив, выполнение на стороне сервера и число
потоков. `ibcmd` поддерживает базовый `ConfigDumpInfo.xml`, синхронизацию
существующего каталога, расширения, архив и число потоков. Эти параметры не
нужны для первого полного импорта в новый временный каталог и остаются за
границами изменения. Поддерживаемые ключи сверяются с документацией
[агента Конфигуратора](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_4._Startup_command_lines_of_system_components_and_description_of_additional_utilities/4.7._Running_Designer_in_agent_mode/4.7.6._config_group_commands/?language=en)
и
[`ibcmd`](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_4._Startup_command_lines_of_system_components_and_description_of_additional_utilities/4.10._Standalone_server_administration_utility__ibcmd_/4.10.4._infobase_mode/?language=en).

Импорт не создаёт и не изменяет файл настроек. Пользователь сам создаёт его по
схеме, вручную вносит пароли и повторяет вызов. Пароль пользователя
информационной базы хранится в `infobase.password`, пароль СУБД — в
`infobase.database.password`; добавлять их в `connectionString` не следует.
Пустая строка означает явный пустой пароль, отсутствие поля — что пароль не
передаётся платформе.

Аутентификация информационной базы и СУБД независимы:

- отсутствие `infobase.user` и `infobase.password` означает, что NKDK не
  передаёт учётные данные пользователя 1С; платформа использует доступный для
  этого подключения способ аутентификации;
- заданный `infobase.user` без `infobase.password` означает пользователя 1С с
  пустым паролем;
- для `database.dbms: MSSQLServer` отсутствие одновременно `database.user` и
  `database.password` включает аутентификацию СУБД от имени пользователя ОС,
  запустившего MCP-процесс;
- для остальных поддерживаемых СУБД `database.user` обязателен, а отсутствие
  `database.password` означает пустой пароль;
- `database.password` без `database.user` всегда является ошибкой настроек.

Отдельный признак режима аутентификации не добавляется: вариант однозначно
определяется наличием полей. NKDK не подставляет предполагаемые имена
пользователей.

Инструмент не угадывает пользователя и пароль. Если платформа отклонила
подключение, пользователь исправляет файл и повторяет импорт. `.nkdk` остаётся
исключённым из Git. На Unix импорт перед чтением автоматически устанавливает
для существующего файла режим `0600`: только владелец может читать и изменять
его. Содержимое файла при этом не меняется. Если ограничить права не удалось,
возвращается ошибка настроек и платформа не запускается. Ограничения ACL
Windows остаются прежними.

## Общая проверка настроек

Проверка принадлежит `@nkdk/platform` и не зависит от MCP или конкретной
операции. Она разделяется на чистые преобразования и файловую границу:

```ts
type ProjectSettingsDiagnostic = {
  code: string
  path: string
  message: string
}

function parseProjectSettingsYaml(source: string): unknown
function validateProjectSettings(value: unknown): ProjectSettingsValidationResult
function readProjectSettings(projectDir: string): Promise<ProjectSettingsReadResult>
```

`parseProjectSettingsYaml` отвечает только за синтаксис YAML.
`validateProjectSettings` проверяет структурный договор, строку подключения,
настройки импорта и сочетание его режима с параметрами СУБД,
затем возвращает нормализованные `ProjectSettings` либо список diagnostics.
Функция не читает файлы и не создаёт `PlatformSessionError`.
`readProjectSettings` разрешает канонический путь, на Unix устанавливает режим
`0600`, читает файл и вызывает чистые функции. На Windows права файла не
изменяются.

Все платформенные операции используют эти функции вместо собственной проверки
полей. Текущая реализация импорта начинает применять общий договор сразу;
синхронизация и последующие операции подключаются к нему без изменения
формата настроек.

Структурный договор является единым источником для runtime-валидации и JSON
Schema. Смысловые ограничения, которые нельзя надёжно выразить JSON Schema,
например разбор `File` и `Srvr`/`Ref` внутри строки подключения, остаются в
`validateProjectSettings` и покрываются совместными тестами.

## MCP resource схемы настроек

MCP публикует один неизменяемый ресурс:

```text
URI: nkdk://project-settings/schema/v1
MIME type: application/schema+json
```

Он доступен через стандартные `resources/list` и `resources/read`; отдельного
инструмента `get_project_settings_schema` нет. Схема содержит `$id`,
`description` каждого поля, обязательность, допустимые значения и четыре объекта
в `examples`:

- агент Конфигуратора;
- `ibcmd` с файловой базой;
- `ibcmd` с клиент-серверной базой и парольной аутентификацией СУБД;
- `ibcmd` с MSSQLServer и аутентификацией СУБД средствами ОС.

Примеры не содержат секретов: поля паролей отсутствуют либо имеют пустую
строку. JSON является допустимым YAML, поэтому объект из `examples` можно
скопировать в `.nkdk/project.yaml` и отредактировать.

Если файл отсутствует, импорт возвращает:

```json
{
  "ok": false,
  "code": "project_settings_required",
  "message": "Создайте файл настроек проекта и повторите импорт.",
  "details": {
    "settingsPath": "/project/.nkdk/project.yaml",
    "schema": {
      "uri": "nkdk://project-settings/schema/v1",
      "format": "application/schema+json"
    }
  }
}
```

Если файл существует, но не проходит проверку, используется код
`invalid_project_settings`; `details` содержит `settingsPath`, массив
`diagnostics` и ту же ссылку на схему. Текстовая часть ответа остаётся краткой,
а следом возвращается `resource_link` с именем «Схема настроек проекта».
Платформа и временный каталог в обоих случаях не запускаются и не создаются.

## Внешний договор ошибки

При ошибке платформенного этапа structured content сохраняет существующие
`ok`, `code`, `message` и `details.temporaryDirectory` и добавляет этап, режим
и ссылку на журнал:

```json
{
  "ok": false,
  "code": "authentication_failed",
  "message": "Access denied",
  "details": {
    "temporaryDirectory": "/project/.nkdk/tmp/import-from-infobase/op-1",
    "stage": "authentication",
    "mode": "designer-agent",
    "log": {
      "uri": "file:///project/.nkdk/tmp/import-from-infobase/op-1/platform.log",
      "format": "text/plain"
    }
  }
}
```

`message` содержит очищенный текст, полученный от платформы. NKDK не заменяет
его собственной классификацией и не пытается определить причину по словам.
Для краткости берётся первая непустая строка, обрезанная до 500 символов. Если
платформа не вернула текста, используется устойчивое сообщение NKDK для
текущего этапа, например «Не удалось выгрузить конфигурацию из информационной
базы».

Текстовая часть MCP-ответа содержит только `message`. Сразу после неё MCP
возвращает `resource_link` с именем «Журнал импорта из информационной базы» и
типом `text/plain`. `stdout`, `stderr`, команда и пароли не включаются в
structured content.

Ошибки до создания временного каталога, включая отсутствие `allowWrite`,
непустой целевой компонент и ошибку настроек, возвращаются без ссылки на
журнал платформы. Ошибка настроек вместо неё содержит ссылку на resource
схемы. Частичные ошибки XML → YAML сохраняют существующий договор успешного
результата с массивом `failed`; эта спецификация его не меняет.

## Этапы диагностики

Платформенная ошибка содержит один из этапов:

- `platform-discovery` — поиск установки и требуемой программы;
- `session-start` — запуск агента, открытие SSH или подготовка `config.yaml`;
- `authentication` — подключение агента к информационной базе;
- `configuration-export` — выполнение выгрузки конфигурации;
- `platform-log` — ошибка безопасного ведения журнала, если платформенная
  операция сама завершилась успешно.

Режим имеет существующее значение `designer-agent` или `standalone-server`.
Если ошибка возникла до выбора режима, поле `mode` отсутствует.

`PlatformSessionError` получает необязательные безопасные подробности, но не
становится хранилищем сырого вывода:

```ts
type PlatformFailureDetails = {
  stage: PlatformFailureStage
  mode?: PlatformSessionMode
  logPath?: string
}
```

Слой `@nkdk/platform` формирует очищенный `message`, записывает подробности в
журнал и передаёт наверх только ссылочные сведения. Слой `@nkdk/mcp` переводит
`logPath` в `file:` URI и формирует `resource_link`; он не разбирает вывод
платформы и не знает аргументов её команд.

## Журнал операции

`platform.log` создаётся до обращения к менеджеру сеансов, чтобы охватить
поиск платформы и создание нового сеанса. На Unix файл создаётся с режимом
`0600`. Журнал относится к одной операции импорта, даже если менеджер
переиспользует ранее созданный сеанс.

Журнал — обычный UTF-8 текст. Записи идут по времени и содержат:

1. выбранный режим и вид подключения без паролей;
2. выбранный способ аутентификации ИБ и СУБД без имён пользователей;
3. начало и завершение каждого платформенного этапа;
4. безопасное представление запускаемой команды;
5. код завершения, признаки отмены и превышения времени;
6. очищенные `stdout` и `stderr` процессов `ibcmd`;
7. очищенные сообщения протокола агента;
8. сведения о переиспользовании сеанса;
9. запасные сообщения о недоступном дочернем журнале или иной неполной
   диагностике.

Для агента содержимое его `/Out`-журнала переносится в `platform.log` при
ошибке запуска или выполнения команды, если файл удалось прочитать. Ошибка
чтения дочернего журнала не заменяет исходную ошибку платформы.

При успехе сохраняется существующее поведение: временный каталог вместе с
журналом удаляется. При ошибке каталог остаётся, поэтому URI продолжает
указывать на доступный файл.

Если запись журнала завершилась ошибкой одновременно с ошибкой платформы,
исходная ошибка имеет приоритет. Результат не содержит `resource_link`, а к
краткому сообщению добавляется нейтральное уточнение «Журнал операции записать
не удалось». Если платформа завершилась успешно, но обязательная запись
журнала не удалась, возвращается `platform_command_failed` с этапом
`platform-log`.

## Очистка секретов

Очистка выполняется в `@nkdk/platform` до записи на диск и до создания
`PlatformSessionError`. Она получает значения `password` и
`database.password` текущего подключения и заменяет каждое непустое значение
на `***` во всех сообщениях и потоках вывода.

Безопасное представление команды дополнительно скрывает значения следующих
аргументов независимо от переданных секретов:

- `--password` и `--password=...`;
- `--database-password` и `--database-password=...`;
- `/P`, `-P` и их значения.

Очистка применяется также к причинам ошибок процесса и дочернему `/Out`-
журналу. Сырые сообщения платформы не записываются во временные
диагностические файлы NKDK. Уже существующие служебные файлы платформы с
секретами не публикуются через MCP.

## Поток выполнения

1. MCP проверяет `allowWrite`.
2. MCP через общий договор `@nkdk/platform` разрешает `projectDir`, ограничивает права
   `.nkdk/project.yaml` на Unix и читает файл.
3. Отсутствующий файл возвращает `project_settings_required` и ссылку на
   схему; некорректный — `invalid_project_settings`, diagnostics и ту же ссылку.
4. Только после успешной проверки настроек MCP проверяет отсутствующий либо
   пустой `cf`.
5. MCP создаёт временный
   каталог и пустой `platform.log`.
6. MCP передаёт настройки и путь журнала менеджеру сеансов.
7. Менеджер создаёт диагностический контекст операции с известными секретами.
8. Поиск платформы, получение сеанса и экспорт записывают события через этот
   контекст.
9. При ошибке адаптер выбирает краткий очищенный текст платформы, добавляет
   этап, режим и путь журнала в `PlatformSessionError`.
10. MCP сохраняет временный каталог, переводит путь журнала в `file:` URI и
   возвращает краткий текст вместе с `resource_link`.
11. При успехе XML импортируется обычным путём, а временный каталог удаляется.
    Содержимое файла настроек не записывается и не изменяется.

## Изменения по пакетам

### `@nkdk/platform`

- разделить синтаксический разбор, смысловую проверку и чтение настроек;
- вернуть структурированные diagnostics с путями полей;
- использовать единый договор настроек в платформенных операциях;
- передавать в экспорт режим импорта и политику неразрешённых ссылок;
- безопасно устанавливать режим `0600` существующего файла на Unix до чтения;
- ввести общий диагностический контекст одной платформенной операции;
- централизовать очистку секретов и представление команд;
- расширить безопасные подробности `PlatformSessionError`;
- передать диагностический контекст через менеджер в оба адаптера;
- перестать отбрасывать текст ошибок JSON-протокола агента;
- записывать результат процессов `ibcmd`, включая подготовку конфигурации;
- объединять доступный `/Out`-журнал агента с журналом операции.

### `@nkdk/mcp`

- сократить вход `import_from_infobase` до `projectDir` и `allowWrite`;
- добавить `project_settings_required` и типизированные подробности ошибок
  настроек;
- зарегистрировать `nkdk://project-settings/schema/v1` и обработчик чтения;
- сформировать JSON Schema из структурного договора и добавить descriptions и
  четыре examples;
- возвращать `resource_link` на схему при отсутствующих или некорректных
  настройках;
- типизировать `details.stage`, `details.mode` и `details.log` ошибки импорта;
- использовать очищенный `PlatformSessionError.message` вместо
  `safeOperationError` для платформенных ошибок;
- сформировать `resource_link` на `text/plain` без создания отдельного MCP-
  инструмента;
- уточнить описание инструмента: сначала подготовить `.nkdk/project.yaml`,
  затем повторить импорт.

`@nkdk/core` не меняется.

## Проверка

Тесты `@nkdk/platform` должны подтверждать:

- независимый синтаксический разбор и чистую смысловую проверку настроек;
- diagnostics с точными путями отсутствующих и несовместимых полей;
- условия для файловой, серверной, агентной и `ibcmd` конфигурации;
- обязательный режим импорта и значения `include`/`omit` для неразрешённых
  ссылок;
- отказ от файла с `useStandaloneServer` без автоматической миграции;
- отсутствие `--ignore-unresolved-refs` для `include` и его передачу обоим
  адаптерам для `omit`;
- отсутствие учётных данных ИБ и пустой пароль заданного пользователя ИБ;
- аутентификацию ОС для MSSQLServer без `database.user` и
  `database.password`;
- обязательность `database.user` для остальных СУБД и запрет пароля СУБД без
  пользователя;
- установку режима `0600` до чтения файла на Unix и отказ без запуска
  платформы, если изменить права не удалось;
- очистку раздельных аргументов, аргументов с `=` и буквальных значений обоих
  паролей;
- отсутствие паролей в сообщении ошибки и журнале;
- сохранение очищенных `stdout`, `stderr`, кода завершения и команды `ibcmd`;
- использование текста ошибки агента вместо общего сообщения;
- запись этапов запуска, аутентификации и экспорта;
- сохранение исходной ошибки при невозможности записать или прочитать журнал;
- независимые журналы при создании и переиспользовании сеанса.

Тесты `@nkdk/mcp` должны подтверждать:

- отсутствие параметров подключения в JSON Schema входа импорта;
- выдачу resource схемы через `resources/list` и `resources/read`;
- совпадение опубликованной JSON Schema со структурным runtime-договором;
- наличие descriptions и четырёх проверяемых examples, включая MSSQLServer с
  аутентификацией ОС;
- `project_settings_required` для отсутствующего файла без запуска платформы;
- diagnostics и ссылку на схему для некорректного файла без запуска платформы;
- краткий очищенный `message` платформы;
- `file:` URI и `text/plain` в structured content;
- наличие `resource_link` в MCP content;
- отсутствие `stdout`, `stderr`, команды и паролей в MCP-ответе;
- отсутствие ссылки до создания временного каталога и при ошибке записи
  журнала;
- сохранение существующего результата частичных ошибок XML → YAML;
- удаление временного каталога после полного успеха.

После реализации выполняются пакетные тесты изменённых модулей, полный
`pnpm test` и проверка новых дубликатов относительно исходного коммита ветки.

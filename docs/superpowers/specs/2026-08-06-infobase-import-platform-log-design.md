# Диагностика платформы при импорте из информационной базы

## Цель

`nkdk.import_from_infobase` должен возвращать короткую безопасную ошибку,
полученную от платформы, и ссылку на подробный локальный журнал операции.
Пользователю не требуется отдельная команда проверки подключения: сведения,
необходимые для исправления подключения, формируются самой операцией импорта.

## Границы

Входит в изменение:

- ошибки поиска и запуска платформы, подключения к информационной базе и
  выгрузки конфигурации;
- одинаковый внешний договор для агента Конфигуратора и offline-режима
  `ibcmd`;
- отдельный журнал каждой операции импорта внутри её временного каталога;
- безопасная команда, код завершения и очищенный вывод платформы в журнале;
- краткий текст ошибки и `resource_link` на журнал в результате MCP;
- описание обязательных параметров подключения и способа передачи паролей.

Не входит:

- отдельная операция диагностики подключения;
- автоматическое исправление параметров подключения;
- автоматические попытки входа под пользователями `Администратор` или `Admin`;
- распознавание причин по словарю сообщений разных версий платформы;
- изменение формата `.nkdk/project.yaml` или способа хранения паролей;
- журналы обычных операций импорта XML → YAML после успешной выгрузки;
- изменение поддерживаемых версий платформы, видов баз и режимов выгрузки.

## Входные данные и пароли

Состав входа остаётся прежним. MCP-описание инструмента должно объяснять,
какие поля нужны для выбранного подключения:

| Подключение | Обязательные данные | Данные при включённой аутентификации ИБ |
|---|---|---|
| Файловая база, агент | `projectDir`, `connectionString` с `File`, `allowWrite` | `user`, `password` |
| Серверная база, агент | `projectDir`, `connectionString` с `Srvr`/`Ref`, `allowWrite` | `user`, `password` |
| Файловая база, `ibcmd` | те же данные и `useStandaloneServer: true` | `user`, `password` |
| Серверная база, `ibcmd` | те же данные, `useStandaloneServer: true`, а также `database.dbms`, `server`, `name`, `user` | `user`, `password`, при необходимости `database.password` |

Пароль пользователя информационной базы передаётся только полем `password`,
а пароль СУБД — только полем `database.password`. Их не следует добавлять в
`connectionString`. Пустая строка означает явный пустой пароль, отсутствие
поля — что пароль не передаётся платформе.

Инструмент не угадывает пользователя и пароль. Если платформа отклонила
подключение, пользователь исправляет `user` и `password` и повторяет импорт.
После успешного импорта настройки по-прежнему сохраняются в локальном
`.nkdk/project.yaml`, который исключён из Git и получает режим `0600` на Unix.

## Внешний договор ошибки

При ошибке платформенного этапа structured content сохраняет существующие
`ok`, `code`, `message` и `details.temporaryDirectory` и добавляет этап, режим
и ссылку на журнал:

```json
{
  "ok": false,
  "code": "authentication_failed",
  "message": "Access denied",
  "details": {
    "temporaryDirectory": "/project/.nkdk/tmp/import-from-infobase/op-1",
    "stage": "authentication",
    "mode": "designer-agent",
    "log": {
      "uri": "file:///project/.nkdk/tmp/import-from-infobase/op-1/platform.log",
      "format": "text/plain"
    }
  }
}
```

`message` содержит очищенный текст, полученный от платформы. NKDK не заменяет
его собственной классификацией и не пытается определить причину по словам.
Для краткости берётся первая непустая строка, обрезанная до 500 символов. Если
платформа не вернула текста, используется устойчивое сообщение NKDK для
текущего этапа, например «Не удалось выгрузить конфигурацию из информационной
базы».

Текстовая часть MCP-ответа содержит только `message`. Сразу после неё MCP
возвращает `resource_link` с именем «Журнал импорта из информационной базы» и
типом `text/plain`. `stdout`, `stderr`, команда и пароли не включаются в
structured content.

Ошибки до создания временного каталога, включая отсутствие `allowWrite` и
непустой целевой компонент, возвращаются без ссылки на журнал. Частичные
ошибки XML → YAML сохраняют существующий договор успешного результата с
массивом `failed`; эта спецификация его не меняет.

## Этапы диагностики

Платформенная ошибка содержит один из этапов:

- `platform-discovery` — поиск установки и требуемой программы;
- `session-start` — запуск агента, открытие SSH или подготовка `config.yaml`;
- `authentication` — подключение агента к информационной базе;
- `configuration-export` — выполнение выгрузки конфигурации;
- `platform-log` — ошибка безопасного ведения журнала, если платформенная
  операция сама завершилась успешно.

Режим имеет существующее значение `designer-agent` или `standalone-server`.
Если ошибка возникла до выбора режима, поле `mode` отсутствует.

`PlatformSessionError` получает необязательные безопасные подробности, но не
становится хранилищем сырого вывода:

```ts
type PlatformFailureDetails = {
  stage: PlatformFailureStage
  mode?: PlatformSessionMode
  logPath?: string
}
```

Слой `@nkdk/platform` формирует очищенный `message`, записывает подробности в
журнал и передаёт наверх только ссылочные сведения. Слой `@nkdk/mcp` переводит
`logPath` в `file:` URI и формирует `resource_link`; он не разбирает вывод
платформы и не знает аргументов её команд.

## Журнал операции

`platform.log` создаётся до обращения к менеджеру сеансов, чтобы охватить
поиск платформы и создание нового сеанса. На Unix файл создаётся с режимом
`0600`. Журнал относится к одной операции импорта, даже если менеджер
переиспользует ранее созданный сеанс.

Журнал — обычный UTF-8 текст. Записи идут по времени и содержат:

1. выбранный режим и вид подключения без паролей;
2. начало и завершение каждого платформенного этапа;
3. безопасное представление запускаемой команды;
4. код завершения, признаки отмены и превышения времени;
5. очищенные `stdout` и `stderr` процессов `ibcmd`;
6. очищенные сообщения протокола агента;
7. сведения о переиспользовании сеанса;
8. запасные сообщения о недоступном дочернем журнале или иной неполной
   диагностике.

Для агента содержимое его `/Out`-журнала переносится в `platform.log` при
ошибке запуска или выполнения команды, если файл удалось прочитать. Ошибка
чтения дочернего журнала не заменяет исходную ошибку платформы.

При успехе сохраняется существующее поведение: временный каталог вместе с
журналом удаляется. При ошибке каталог остаётся, поэтому URI продолжает
указывать на доступный файл.

Если запись журнала завершилась ошибкой одновременно с ошибкой платформы,
исходная ошибка имеет приоритет. Результат не содержит `resource_link`, а к
краткому сообщению добавляется нейтральное уточнение «Журнал операции записать
не удалось». Если платформа завершилась успешно, но обязательная запись
журнала не удалась, возвращается `platform_command_failed` с этапом
`platform-log`.

## Очистка секретов

Очистка выполняется в `@nkdk/platform` до записи на диск и до создания
`PlatformSessionError`. Она получает значения `password` и
`database.password` текущего подключения и заменяет каждое непустое значение
на `***` во всех сообщениях и потоках вывода.

Безопасное представление команды дополнительно скрывает значения следующих
аргументов независимо от переданных секретов:

- `--password` и `--password=...`;
- `--database-password` и `--database-password=...`;
- `/P`, `-P` и их значения.

Очистка применяется также к причинам ошибок процесса и дочернему `/Out`-
журналу. Сырые сообщения платформы не записываются во временные
диагностические файлы NKDK. Уже существующие служебные файлы платформы с
секретами не публикуются через MCP.

## Поток выполнения

1. MCP проверяет разрешение записи и целевой компонент.
2. MCP создаёт временный каталог и пустой `platform.log`.
3. MCP передаёт путь журнала вместе с параметрами экспорта менеджеру сеансов.
4. Менеджер создаёт диагностический контекст операции с известными секретами.
5. Поиск платформы, получение сеанса и экспорт записывают события через этот
   контекст.
6. При ошибке адаптер выбирает краткий очищенный текст платформы, добавляет
   этап, режим и путь журнала в `PlatformSessionError`.
7. MCP сохраняет временный каталог, переводит путь журнала в `file:` URI и
   возвращает краткий текст вместе с `resource_link`.
8. При успехе XML импортируется обычным путём, настройки сохраняются, а
   временный каталог удаляется.

## Изменения по пакетам

### `@nkdk/platform`

- ввести общий диагностический контекст одной платформенной операции;
- централизовать очистку секретов и представление команд;
- расширить безопасные подробности `PlatformSessionError`;
- передать диагностический контекст через менеджер в оба адаптера;
- перестать отбрасывать текст ошибок JSON-протокола агента;
- записывать результат процессов `ibcmd`, включая подготовку конфигурации;
- объединять доступный `/Out`-журнал агента с журналом операции.

### `@nkdk/mcp`

- типизировать `details.stage`, `details.mode` и `details.log` ошибки импорта;
- использовать очищенный `PlatformSessionError.message` вместо
  `safeOperationError` для платформенных ошибок;
- сформировать `resource_link` на `text/plain` без создания отдельного MCP-
  инструмента;
- уточнить описание входных полей и матрицу обязательных параметров.

`@nkdk/core` не меняется.

## Проверка

Тесты `@nkdk/platform` должны подтверждать:

- очистку раздельных аргументов, аргументов с `=` и буквальных значений обоих
  паролей;
- отсутствие паролей в сообщении ошибки и журнале;
- сохранение очищенных `stdout`, `stderr`, кода завершения и команды `ibcmd`;
- использование текста ошибки агента вместо общего сообщения;
- запись этапов запуска, аутентификации и экспорта;
- сохранение исходной ошибки при невозможности записать или прочитать журнал;
- независимые журналы при создании и переиспользовании сеанса.

Тесты `@nkdk/mcp` должны подтверждать:

- краткий очищенный `message` платформы;
- `file:` URI и `text/plain` в structured content;
- наличие `resource_link` в MCP content;
- отсутствие `stdout`, `stderr`, команды и паролей в MCP-ответе;
- отсутствие ссылки до создания временного каталога и при ошибке записи
  журнала;
- сохранение существующего результата частичных ошибок XML → YAML;
- удаление временного каталога после полного успеха.

После реализации выполняются пакетные тесты изменённых модулей, полный
`pnpm test` и проверка новых дубликатов относительно исходного коммита ветки.

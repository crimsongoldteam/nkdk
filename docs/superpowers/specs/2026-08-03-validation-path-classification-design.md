# Быстрая классификация путей при актуализации проекта

## Назначение

Эта спецификация уточняет обнаружение и классификацию файлов на этапе Б1–Б4 внутренней операции «Актуализация и проверка состояния проекта».

Цели:

- ускорить холодную классификацию за счёт совместного обхода дерева каталогов и дерева правил;
- повторно использовать сохранённую классификацию путей при тёплой валидации;
- сократить число заданий worker укрупнением пачек;
- сохранить строгий договор: при каждой валидации содержимое каждого управляемого файла читается и хэшируется.

Спецификация не меняет правила определения управляемых файлов, алгоритм хэша, локальную проверку YAML, полную проверку зависимостей, import и защиту будущей синхронизации от изменения файлов после validation.

## Исходное состояние и измерения

На временной копии `/Users/nikita/git/nkdk-yaml` обнаруживается около 121 тысячи файлов. Тёплая обработка файлов занимает около 7,8 секунды.

Подробный профиль показывает:

- чистый первый обход дерева каталогов — около 2,32 секунды;
- повторный обход дерева каталогов — около 0,92 секунды;
- обход с классификацией и подготовкой пачек — около 4,8–5,2 секунды;
- чтение файлов каждым из четырёх worker — около 4,5 секунды;
- вычисление xxh3 каждым worker — около 0,08–0,09 секунды;
- сравнение хэшей каждым worker — менее 0,01 секунды;
- создаётся около 3795 пачек по 32 файла.

Текущий индекс правил содержит 561 шаблон. Для фактического состава проекта выполняется около 1,99 миллиона проверок шаблонов: в среднем 16,4 и не более 34 на один файл. Каждая проверка повторно разбирает путь и шаблон, создаёт регулярные выражения, массивы и объекты извлечённых значений.

Следовательно, смена алгоритма хэширования не устранит задержку. Нужно убрать повторную интерпретацию шаблонов и уменьшить число мелких обменов с worker.

## Принятое решение

Решение состоит из трёх связанных частей:

1. Правила путей один раз компилируются в дерево сегментов.
2. Обход файловой системы переносит курсор этого дерева из родительского каталога в дочерний и не сопоставляет полный путь заново.
3. При тёплом проходе известный путь получает минимальные сохранённые сведения из двоичного состояния; полное описание создаётся только для нового или изменённого файла.

Файлы передаются worker пачками. Начальный размер пачки — 512 файлов. Перед окончательной фиксацией значения профиль сравнивает размеры 128, 256, 512 и 1024; выбирается лучший устойчивый результат без изменения протокола.

## Компилируемое дерево правил

### Сегменты

При создании контекста проекта каждый шаблон пути один раз разбирается на узлы следующих видов:

- точное имя, например `Справочник`;
- значение сегмента, например `{ownerName}`;
- составной сегмент, например `{formName}.yaml`;
- оставшаяся часть пути, например `{resourcePath...}`;
- конечное правило с устойчивым идентификатором объявления.

Регулярное выражение составного сегмента создаётся при компиляции правила и не создаётся во время обхода. Точные дочерние сегменты хранятся в поисковой таблице. Шаблонные дочерние сегменты и правила остатка хранятся отдельными компактными списками.

### Курсор каталога

Задание обхода каталога содержит:

- абсолютный путь каталога;
- нормализованные сегменты пути проекта;
- активные узлы дерева правил;
- извлечённые значения параметров активных правил.

Для дочернего элемента проверяется только его имя. Полученное состояние передаётся дочернему каталогу либо используется для создания результата файла. Полный путь не разбирается и не сравнивается со всеми кандидатами повторно.

Обход каталогов сохраняет существующий ограниченный параллелизм. Состояние правила переносится вместе с заданием каталога, поэтому не требуется глобально сортировать все пути или сначала собирать полный список файлов.

Если для ветви не осталось ни одного активного правила и нет правила остатка пути, её дальнейший обход не требуется. Исключение `.git` и `.nkdk` сохраняется независимо от дерева правил.

### Семантическая совместимость

Новый классификатор сохраняет существующие правила:

- повторяющийся параметр должен получать одинаковое значение во всех сегментах;
- совпадение нескольких равноправных правил является ошибкой;
- обычный внешний файл имеет приоритет над объявлением с `fallback: true`;
- неподходящие и игнорируемые пути не становятся файлами проекта;
- извлечённые значения, владелец, роль YAML и правило объекта совпадают с результатом текущего классификатора.

## Холодный проход

При отсутствии пригодного двоичного состояния:

1. Главный процесс компилирует дерево правил для каждого компонента проекта.
2. Обход начинается с корневого курсора компонента.
3. Состояние классификатора переносится по каталогам.
4. Для совпавшего файла создаются его идентичность и, для YAML, полное описание.
5. Файлы группируются в ограниченные пачки и передаются worker.
6. Worker читает файл, вычисляет хэш и из тех же байтов обрабатывает новый YAML.

Холодный проход классифицирует каждый управляемый путь, но не интерпретирует полный набор строковых шаблонов для каждого файла.

## Тёплый проход

### Двоичное состояние как кэш классификации

Отдельный `Map` классификации не создаётся. Источником сохранённых сведений является уже загруженное двоичное состояние проекта.

Запрос исходного состояния принимает нормализованные пути, а для каждого найденного пути возвращает компактно:

- признак наличия;
- идентификатор сохранённого файла;
- предыдущий восьмибайтовый хэш;
- доступ к сохранённым компоненту, виду ресурса и роли YAML через идентификатор файла.

Строки и полные предметные объекты из двоичного состояния не копируются в отдельный кэш.

### Обработка известного файла

Для известного пути задание worker содержит только абсолютный путь, нормализованный путь проекта, идентификатор сохранённой записи и предыдущий хэш.

Worker:

1. читает файл;
2. вычисляет хэш по прочитанным байтам;
3. при совпадении освобождает байты и не создаёт полное описание файла;
4. при изменении классифицирует путь своим заранее подготовленным деревом правил;
5. из тех же байтов проверяет YAML либо формирует обновление внешнего ресурса.

Один экземпляр дерева правил создаётся в главном процессе и по одному экземпляру — при инициализации каждого worker. Дерево не передаётся с файловыми пачками.

### Новые, удалённые и переименованные пути

- Новый путь классифицируется главным обходчиком до передачи worker, чтобы неподходящий файл не стал частью проекта.
- Идентификаторы встретившихся сохранённых файлов отмечаются в битовой карте.
- Сохранённая запись, идентификатор которой не отмечен после завершения обхода, считается удалённой.
- Переименование представляется удалением старого пути и появлением нового.
- Полная классификация изменённого известного файла выполняется в worker ровно один раз после несовпадения хэша.

Изменение договоров правил путей требует повышения версии двоичного формата. Отдельный отпечаток правил не вводится.

## Пачки и обратное давление

Главный процесс формирует пачки из последовательного потока обнаруженных файлов. Одновременно выполняются:

- чтение следующих каталогов;
- пакетный поиск исходного состояния;
- чтение и хэширование предыдущих пачек в worker.

Начальный размер пачки — 512 файлов. При четырёх worker одновременно удерживается не более четырёх обрабатываемых пачек. Последняя неполная пачка передаётся как есть.

Содержимое файлов не передаётся между процессами. Каждый worker читает один файл, использует его байты для хэша и возможной локальной проверки, затем освобождает их до перехода к следующему файлу.

Пакетный запрос исходного состояния выполняется один раз на пачку. При размере 512 число запросов и заданий для проекта из 121 тысячи файлов уменьшается примерно с 3795 до 238.

Размер пачки является параметром внутреннего производителя, а не публичным параметром MCP. Его изменение не влияет на результаты и порядок diagnostics.

## Согласованность и ошибки

- Операции одного `ProjectStateService` сохраняют существующее последовательное выполнение.
- Хэш, локальные diagnostics и индексный вклад одного YAML относятся к одному прочитанному массиву байтов.
- Повторные `stat` и `fstat` не добавляются; `size`, `mtimeNs`, `dev` и `inode` не становятся условиями неизменности.
- `ENOENT` между обнаружением и чтением означает удаление файла в текущем проходе.
- Иная ошибка чтения, сбой worker, отмена или нарушение двоичного договора откатывает кандидатное состояние.
- Неоднозначная классификация останавливает операцию с указанием проблемного пути.
- Обычные diagnostics являются содержательным результатом и не отменяют публикацию актуальных хэшей, локальных результатов и индексных сведений.
- Асинхронное сохранение начинается после публикации целостного состояния; следующая изменяющая операция ждёт предыдущую запись согласно существующему договору.

Validation остаётся снимком по прочитанным байтам отдельных файлов, а не атомарным снимком всей файловой системы. Проверка соответствия проверенных и фактически выгружаемых байтов относится к договору синхронизации.

## Границы модулей

- Компиляция и исполнение дерева правил находятся в `metadata/resourceTopology` и не знают о двоичном состоянии проекта.
- Обход проекта связывает курсор дерева правил с каталогами и выдаёт нейтральные описания обнаруженных путей.
- `metadata/projectState` решает, использовать ли сохранённую классификацию или материализовать новую.
- Двоичная реализация скрывает поиск пути, идентификаторы записей и расположение полей в буферах.
- Worker не получает доступ на запись к общему состоянию и возвращает только двоичные вклады изменённых файлов.
- Общие слои не получают условий по конкретным `itemType`, именам каталогов метаданных или частным правилам объектов.

## Проверка решения

### Модульные договоры

Тесты дерева правил покрывают:

- точные сегменты;
- `{name}` и `{name}.yaml`;
- `{rest...}`;
- повторяющиеся параметры;
- обычные и запасные внешние файлы;
- игнорируемые пути;
- неоднозначные совпадения;
- ветви без возможных правил.

На небольшом временном дереве старый и новый классификаторы должны возвращать одинаковые результаты для всех проверяемых путей. Существующие проверки правил расширяются, а не дублируются отдельными похожими тестами.

Тесты актуализации подтверждают:

- холодный проход классифицирует каждый подходящий путь;
- известный неизменённый файл читается и хэшируется, но его полное описание не создаётся;
- изменённый известный файл классифицируется один раз и проверяется из тех же байтов;
- новый, удалённый и переименованный файлы корректно изменяют состояние;
- пачки 128, 256, 512 и 1024 не меняют результат;
- неполная последняя пачка, отмена и ошибка worker не нарушают публикацию;
- две быстро запущенные актуализации выполняются последовательно.

Модульные тесты используют подмены файловой системы и двоичного состояния. Целевое время теста — около 10 мс, предельное — 50 мс. Небольшие интеграционные тесты также не должны выполнять широкие обходы или создавать большой двоичный снимок.

Mutation testing в этой задаче не выполняется. Перед завершением обязательны проверка новых дублей через jscpd, проверка типов, целевые тесты и полный `pnpm test`.

### Профиль производительности

Измерения выполняются существующим `validation-profile` на временной копии большого проекта. В модульных тестах нет временных утверждений.

Сравниваются размеры пачек 128, 256, 512 и 1024. Выбранный размер должен давать устойчивый результат и не создавать заметного перекоса между worker.

Критерии приёмки:

- diagnostics и их контрольная сумма совпадают с исходной реализацией;
- при тёплом проходе хэшируются все управляемые файлы, а YAML без изменения хэша не разбираются;
- тёплая валидация большого проекта занимает не более 10 секунд;
- холодная классификация быстрее исходных 3,9–4,3 секунды и не ухудшает общее время холодной валидации;
- пиковая память не растёт из-за отдельной объектной копии классификации всех файлов.

# Закрытие дыр ревью rename/delete metadata-операций

Дата: 2026-07-01

Статус: готово к пользовательской проверке.

## Контекст

После реализации первой версии core-операций `rename_item`, `delete_item`, `list_operation_targets` и применения миграций при `sync_to_xml` ревью нашло несколько расхождений с исходной спекой `2026-06-29-metadata-rename-delete-mcp-design.md`.

Эта спека фиксирует только оставшиеся дыры и решения по ним. Базовый договор не меняется: MCP и CLI остаются тонкими входами, бизнес-логика живет в `@nakidka/core`, операции перед записью проверяют весь YAML-проект через validation, а XML-синхронизация отдельно применяет цепочку миграций.

## Найденные дыры

### 1. Операции видят не весь YAML-проект

Текущая реализация `metadata/operations/projectSnapshot.ts` строит собственный снимок проекта поверх `discoverMetadataProjectResources`, но затем оставляет только верхнеуровневые `Свойства.yaml`:

```ts
if (resource.role !== "properties" || resource.nesting.length > 0 || resource.absolutePath === undefined) continue
```

Из-за этого операции не видят формы, вложенные `Свойства.yaml` и другие YAML-файлы, которые уже умеет видеть общий слой проекта и validation. В результате `rename_item` может не переписать структурную ссылку внутри формы, а `delete_item` может не заблокировать внешнюю ссылку из формы на удаляемую цель.

Это нарушает исходный договор: структурные ссылки должны переписываться или проверяться во всем YAML-проекте, который NKDK понимает через общие правила.

### 2. Вложенные цели и внешний target-договор не согласованы

Первая реализация использовала структурированный target-объект:

```json
{
  "kind": "attribute",
  "owner": {
    "itemTypePrefix": "Документ",
    "name": "Заказ"
  },
  "name": "Количество"
}
```

Для вложенности обсуждался вариант `parents`, но итоговое решение другое: внешний договор должен быть строковым path через точку.

Канонический внешний путь для того же реквизита:

```text
Документ.Заказ.ТабличнаяЧасть.Товары.Реквизит.Количество
```

Сейчас CLI уже частично умеет разбирать такие строки, но parser живет в CLI, а core-resolver работает со структурированным target. Это нарушает границу слоев: MCP и CLI должны быть тонкими, а разбор и разрешение цели должны жить в core.

### 3. Цепочка миграций проверяет конфликт имени не так строго, как rename

`rename_item` проверяет занятость имени без учета регистра. Это согласовано в исходной спеке: `Товары` и `товары` считаются одним именем для конфликтов, кроме переименования того же самого узла только сменой регистра.

При проверке migration-файлов цепочка сейчас проверяет занятость целевого пути точным сравнением. Поэтому ручная миграция может провести конфликт, который обычный `rename_item` заблокировал бы.

## Решение 1: общий снимок YAML-проекта для операций

Операции не должны писать собственный обход YAML-файлов. Источником файлов должен быть тот же общий механизм, который использует validation:

```text
validateProject
  -> discoverValidationProjectFiles
  -> discoverMetadataProjectResources
```

`metadata/operations` должен переиспользовать общий список файлов и общие правила проекта. Если файл не видит `discoverMetadataProjectResources`, операция его не видит тоже. Исправлять это нужно расширением общего проектного описателя, а не частным обходом в operations.

Для каждого YAML-файла, который видит validation:

- `rename_item` ищет и переписывает структурные ссылки на target и его дочерние пути;
- `delete_item` ищет внешние структурные ссылки на target и его дочерние пути и блокирует удаление;
- поиск и запись ссылок идут через существующие правила, валидаторы и общие обработчики структурных ссылок;
- текстовые совпадения в произвольных строках, BSL, XML и комментариях не участвуют.

### Формы и DataPath

Формы входят в первый этап на тех же основаниях, что и `Свойства.yaml`: если validation умеет проверить форму и разобрать в ней структурную ссылку или DataPath, операция должна уметь эту ссылку переписать при rename и увидеть при delete.

DataPath не должен обрабатываться отдельным строковым поиском. Операция использует существующий разбор DataPath из validation. Если DataPath уверенно связан с переименовываемой metadata-целью, `rename_item` переписывает соответствующий сегмент пути. Если DataPath не разбирается, операция и так блокируется предварительной validation-проверкой всего проекта.

### Обратная запись

Если validation умеет распознать структурную ссылку и операция решила ее переписать, у правила должен быть общий механизм записи нового значения обратно в YAML-модель или YAML-документ. Если такого механизма нет, это ошибка договора правил.

В этом случае операция:

- блокируется до записи файлов;
- возвращает машинно читаемую ошибку `rule_contract_violation`;
- не применяет частичный план;
- не создает migration-файл.

В нормальной архитектуре такой ситуации быть не должно. Это защитное правило нужно для того, чтобы операция не пропускала понятную ссылку молча и не портила проект частичной записью.

## Решение 2: внешний договор operation path

Публичный договор `rename_item` и `delete_item` переходит на строковый operation path.

Основной формат:

```text
Справочник.Товары
Справочник.Товары.Реквизит.Артикул
Документ.Заказ.ТабличнаяЧасть.Товары.Реквизит.Количество
Справочник.Товары.Форма.ФормаЭлемента
Справочник.Товары.Макет.Печать
```

Путь человекочитаемый, русский и совпадает с migration/display path. Canonical model-сегменты вроде `Catalog`, `Attribute`, `Form` во внешнем договоре не используются.

Точка в локальном имени metadata недопустима. Экранирование сегментов не вводится, operation path всегда однозначно разбивается по `.`.

Структурированный target-объект убирается из публичного API core/MCP. Core может иметь приватный нормализованный результат парсинга, но наружу MCP и CLI передают только строковый `path`.

`list_operation_targets` на этом этапе удаляется из публичного MCP/API. Пользователь или агент передает path сам. Если позже понадобится интерактивный выбор допустимых целей, это будет отдельное расширение.

Чтобы агент не угадывал формат path, MCP guide и prompt для редактирования YAML должны явно описывать правило:

- если пользователь хочет переименовать или удалить metadata-цель, нельзя править YAML руками;
- нужно вызвать `rename_item` или `delete_item`;
- цель передается строкой `path`;
- path состоит из русских сегментов через точку.

Примеры для MCP guide/prompt:

```text
Справочник.Товары
Справочник.Товары.Реквизит.Артикул
Документ.Заказ.ТабличнаяЧасть.Товары.Реквизит.Количество
Справочник.Товары.Форма.ФормаЭлемента
Справочник.Товары.Макет.Печать
```

### `rename_item` и `delete_item`

Вход операций:

```json
{
  "projectDir": "...",
  "path": "Документ.Заказ.ТабличнаяЧасть.Товары.Реквизит.Количество",
  "newName": "Цена"
}
```

для `delete_item` — тот же `path`, но без `newName`.

Парсер operation path живет в core. MCP и CLI не разбирают путь на части и не строят structured target.

### Ошибки path

Операции различают три ситуации:

- `invalid_path` — строка синтаксически не является operation path: пустая строка, пустой сегмент, незавершенный путь, нечетное число сегментов для дочерней цели;
- `target_not_found` — синтаксис и роль пути поддержаны, но конкретного YAML-узла нет;
- `unsupported_target` — путь указывает на metadata-понятие, которое не описано как изменяемая цель через `operationTarget`.

Примеры:

```text
""                                  -> invalid_path
Справочник.Товары.                  -> invalid_path
Справочник..Товары                  -> invalid_path
Справочник.Товары.Реквизит          -> invalid_path
Справочник.Товары.Реквизит.НетТакого -> target_not_found
Справочник.Товары.ПредопределенныйЭлемент.БезНДС -> unsupported_target
```

Operation path указывает только на реально изменяемую YAML-цель, описанную `operationTarget`. Стандартные, вычисляемые и служебные элементы могут участвовать в ссылках, но не попадают в `list_operation_targets` и не принимаются для rename/delete.

## Решение 3: вложенные цели через общий path resolver

Вложенные цели поддерживаются не частным кодом под один сценарий, а общим механизмом цепочки коллекций через `operationTarget`.

Пример:

```text
Документ.Заказ.ТабличнаяЧасть.Товары.Реквизит.Количество
```

Core разбирает путь как:

```text
owner: Документ.Заказ
parent chain:
  - ТабличнаяЧасть.Товары
target:
  - Реквизит.Количество
```

Resolver идет по цепочке через `operationTarget`-декларации правил:

1. Находит владельца `Документ.Заказ`.
2. В правилах владельца ищет коллекцию с migration/display-сегментом `ТабличнаяЧасть`.
3. В этой коллекции находит элемент `Товары`.
4. Переходит к item rule табличной части.
5. В правилах tabular section item ищет коллекцию `Реквизит`.
6. В ней находит элемент `Количество`.

Область имен для проверки конфликта — последняя коллекция в цепочке. Для примера выше это реквизиты конкретной табличной части `Товары`, а не все реквизиты документа.

Если цепочка невозможна по правилам, это `unsupported_target`. Если цепочка поддержана, но конкретный элемент не найден, это `target_not_found`.

Отдельного перечисления всех таких путей пока нет. Но resolver должен быть общим и расширяемым, чтобы будущий `list_operation_targets` смог использовать тот же механизм без отдельного обхода.

## Решение 4: migration path и operation path используют один parser

Migration-файлы продолжают хранить текущий короткий YAML-словарь:

```yaml
"Справочник.Товары.Реквизит.Артикул": КодПоставщика
```

Ключ слева — тот же operation path. Проверка migration-цепочки использует общий parser/resolver operation path и те же правила области имен, что `rename_item`.

На каждом шаге цепочки:

- новое имя проходит общее правило metadata-имени;
- целевой path строится через замену последнего локального имени;
- конфликт в области имен проверяется без учета регистра;
- смена регистра того же самого узла допустима;
- конфликт с соседним узлом, отличающимся только регистром, блокирует всю цепочку.

Пример допустимой смены регистра:

```text
Справочник.Товары.Реквизит.Артикул -> артикул
```

Пример конфликта:

```text
Справочник.Товары.Реквизит.Код уже существует
Справочник.Товары.Реквизит.Артикул -> код
```

Такой migration-файл блокируется с `name_conflict`, как и обычный `rename_item`.

## Решение 5: CLI generate-migration

`generate-migration` остается по пользовательскому поведению: команда сравнивает XML/reference-состояние и YAML-состояние, интерактивно предлагает связать удаленный и добавленный узел как переименование и пишет migration-файл.

Но внутренние проверки должны использовать общий core parser/resolver operation path и общую проверку нового имени. У CLI не должно быть отдельной реализации разбора operation path.

Это сохраняет полезный сценарий восстановления намерения после ручной правки YAML, но убирает вторую независимую логику проверки путей.

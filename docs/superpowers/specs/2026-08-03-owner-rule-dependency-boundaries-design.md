# Локальные границы зависимостей правил владельцев

## Контекст

После объединения ветки `codex/reference-free-form-xml` с `develop` новая
проверка dependency-cruiser обнаружила 145 архитектурных нарушений. Из них 143
— новые рёбра внутри уже существующей большой циклической компоненты metadata-
слоя, ещё два — запрещённые зависимости нейтральных слоёв от конкретных
реализаций.

Расширять baseline нельзя. При этом задача не должна превращаться в устранение
всей существующей архитектурной задолженности: исправляются только зависимости,
добавленные текущей веткой.

## Решение

Правило элемента коллекции задаётся непосредственно в property rule владельца
через `itemRule`. Каждый прикладной объект остаётся владельцем правил своих
реквизитов, табличных частей, измерений и ресурсов.

Общие части правил сохраняются как переиспользуемые fragments, но становятся
чистыми листьями графа зависимостей. Они содержат декларативные свойства и
минимальные структурные типы, не импортируют `orchestration`, `validation`,
`project`, `context`, `metadata/register.ts` или конкретные прикладные объекты.
Если fragment требуется функция, зависящая от внешнего слоя, она передаётся ему
параметром при сборке правила владельца.

## Сборка правил владельца

`rules.ts` конкретного объекта:

1. выбирает необходимые общие fragments;
2. добавляет свойства, поддерживаемые только этим владельцем;
3. собирает итоговый `itemRule` с сохранением XML-порядка;
4. передаёт `itemRule` непосредственно в правило соответствующей коллекции.

Общая регистрация механики коллекций сохраняется: она задаёт импорт/экспорт,
XML-элемент, форму YAML и резервный `itemRule`. Глобальная регистрация
отдельного property type для каждой пары «владелец—роль» больше не нужна.
Удаляются промежуточные
`registerOwnerCollection.ts`, `childRules.ts` и регистрации владельцев,
которые создавали обратный путь к композиционному `metadata/register.ts`.

Неподдерживаемые владельцем поля отсутствуют в его `itemRule`, поэтому остаются
запрещёнными JSON Schema и validation. Общие fragments обеспечивают
переиспользование без общего профиля, применимого ко всем владельцам.

## Локальные исправления нейтральных границ

- `validation/dataPath/objectFields.ts` перестаёт импортировать новый concrete
  fragment табличной части и снова использует прежнюю разрешённую границу,
  существовавшую в baseline до ветки.
- Логика `resolvePropertyItemRule` переносится в существующий модуль
  `property/typeRuleRegistry.ts`, который все потребители уже использовали до
  ветки. Это не вводит новых рёбер внутри циклической компоненты. Приоритет
  остаётся прежним: явный `itemRule`, затем переданный fallback, затем
  зарегистрированное правило типа.
- `forms/clientApplicationForm/mainAttributeKinds.ts` использует минимальный
  локальный структурный интерфейс индекса вместо type-only импорта validation-
  реализации.

## Неизменяемые договоры

- YAML- и XML-представления не меняются.
- Порядок XML-полей сохраняется.
- Defaults и набор допустимых полей остаются отдельными для каждого владельца.
- XML-фикстуры не изменяются.
- Baseline dependency-cruiser не расширяется.
- Stryker в этой задаче не запускается и не возвращается в зависимости.

## Проверка

Изменение выполняется через существующие наблюдаемые тесты правил владельцев.
Падающий `pnpm test:architecture` является регрессионной проверкой границы
зависимостей. После каждого слоя выполняются целевые тесты и архитектурная
проверка; итоговая проверка включает:

```bash
pnpm type-check
pnpm test
pnpm test:architecture
pnpm duplicates -- --base=origin/develop
git diff --check
```

Завершение допустимо только при отсутствии новых архитектурных нарушений и
новых дублей относительно `origin/develop`.

## Вне границ задачи

- устранение существующей большой циклической компоненты metadata-слоя;
- сокращение уже зафиксированного baseline;
- изменение общих правил dependency-cruiser;
- изменение смыслового YAML/XML-договора ради упрощения графа.

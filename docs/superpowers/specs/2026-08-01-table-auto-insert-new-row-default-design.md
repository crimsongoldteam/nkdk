# Неявные значения свойств формы

## AutoInsertNewRow таблицы

### Договор преобразования

Для `Table.AutoInsertNewRow` используется единый договор обычной таблицы:

| Конфигуратор | YAML | XML |
|---|---|---|
| `Истина` | ключ отсутствует | `<AutoInsertNewRow>true</AutoInsertNewRow>` |
| `Ложь` | `АвтоВводНовойСтроки: Ложь` | узел отсутствует |

Правило задаёт разные неявные значения двух форматов:

```ts
autoInsertNewRow: booleanRule({
  yaml: "АвтоВводНовойСтроки",
  implicitValueYAML: true,
  implicitValueXML: false,
})
```

При XML → YAML отсутствующий узел восстанавливается как `false` и записывается
явно, а XML `true` сворачивается в отсутствующий YAML-ключ. При YAML → XML
отсутствующий ключ создаёт XML `true`, а явное `Ложь` сворачивается в
отсутствующий XML-узел.

Выбор неявного значения не зависит от `DataPath`. Для него не используются
индекс метаданных, исходный XML или снимок конфигурации.

### JSON Schema и MCP

Если у правила одновременно заданы литеральные `implicitValueYAML` и
`implicitValueXML`, экспорт JSON Schema исключает из явных YAML-значений
`implicitValueYAML`. Отдельный признак правила для этого не добавляется.

Поэтому для `АвтоВводНовойСтроки` схема разрешает только явное `Ложь`:
`Истина` считается избыточным значением, а любое не-boolean значение
отклоняется обычной проверкой типа.

MCP получает и применяет ту же схему через core. Специальная проверка в
`packages/mcp` не добавляется. Синхронизация без предварительной валидации
может принять явное `Истина` и преобразует его так же, как отсутствующий ключ.

### Архитектурные границы

- Знание об `AutoInsertNewRow` остаётся в `TableRules`.
- Общие metadata-слои работают только с `implicitValueYAML` и
  `implicitValueXML` и не знают о видах источников таблицы.
- Существующие XML-фикстуры не изменяются.

### Проверки

1. Правило содержит `implicitValueYAML: true` и `implicitValueXML: false`.
2. XML → YAML покрывает отсутствующий узел и явный XML `true`.
3. YAML → XML покрывает отсутствующий ключ и явное YAML `Ложь` без reference
   XML.
4. JSON Schema разрешает `Ложь`, запрещает `Истина` и отклоняет третье
   значение; MCP использует тот же договор.
5. Round-trip `cf/doc` больше не содержит расхождений `AutoInsertNewRow`.

## Растяжение групп формы

### Договор преобразования

В XDTO-схеме `GroupBase.HorizontalStretch` и `GroupBase.VerticalStretch` имеют
тип `BWAValue`: `true`, `false` или `auto`, default — `auto`. Это отличается от
`Table.HorizontalStretch` и обычных полей формы с типом `xs:boolean`.

Источник договора —
[`model.xdtomngbase_root.res`](https://github.com/nikitazherebtsov/1c_res/blob/79cde5b70a15bb54c674ed56e76aa4471772d035/model.xdtomngbase_root.res#L530-L548).

Автоматическое состояние представляется отсутствием значения:

| Конфигуратор | Модель | YAML | XML |
|---|---|---|---|
| `Авто` | `undefined` | ключ отсутствует | узел отсутствует |
| `Ложь` | `false` | `Ложь` | явный узел `false` |
| `Истина` | `true` | `Истина` | явный узел `true` |

Явный XML `auto` импортируется как `undefined` и при последующем экспорте
канонизируется в отсутствующий узел. Явное YAML-значение `Авто` не вводится.

### Правило

Специальный признак для состояния `Авто` не требуется:

```ts
horizontalStretch: booleanRule({
  yaml: "РастягиватьПоГоризонтали",
})
```

Без `implicitValueYAML` значения `true` и `false` всегда записываются в YAML,
а отсутствие ключа передаёт в XML `undefined`. Существующий преобразователь
boolean уже импортирует XML `auto` как `undefined`.

Full sync и MCP не принимают `referenceDir` и не читают исходный XML-каталог.
Индекс конфигурации хранит только невосстановимые XML-состояния и не хранит
обычные значения этих свойств: явные `true` и `false` полностью представлены в
YAML. Изменения общей оркестрации не требуются.

### Область применения

Обычный `booleanRule` без неявного YAML-значения задаётся для
`horizontalStretch` и `verticalStretch` в `formGroupCommonProperties`. Договор
наследуют `UsualGroup`, `CommandBar`, `ColumnGroup`, `ButtonGroup`, `Page`,
`Pages` и `Popup`.

Локальные переопределения этих свойств с другими неявными значениями
удаляются. Правила `Table` и обычных полей формы не изменяются.

Общие metadata-слои не получают условий по типам элементов формы. Решение о
трёхзначном поведении принимается декларативно в rules.ts.

### JSON Schema и MCP

YAML-ключ остаётся необязательным. Если он присутствует, обычная boolean-схема
разрешает только `Истина` и `Ложь`; `Авто` и третье значение отклоняются.
MCP использует ту же схему без специальной логики.

### Проверки

1. XML → YAML покрывает отсутствующий узел, `auto`, `false` и `true`.
2. YAML → XML покрывает отсутствующий ключ, `Ложь` и `Истина`.
3. Оба свойства всех семи видов групп используют `booleanRule` без
   `implicitValueYAML`, `noImplicitValueYAML` и локальных defaults.
4. JSON Schema разрешает отсутствующий ключ, `Истина` и `Ложь`, но отклоняет
   `Авто` и третье значение; MCP применяет эту же схему.
5. Выполняются целевые тесты, `pnpm type-check`, `pnpm test`, mutation testing
   изменённых production-диапазонов и повторный round-trip `cf/doc`.

## Критерии готовности

- Оба договора восстанавливаются без чтения исходного XML.
- Удаление ключа растяжения из YAML переводит свойство в `Авто`.
- Явные `true` и `false` растяжения сохраняются через YAML.
- Валидация применяет ограничения без второго семантического прохода.
- Все тесты проходят.

# Неявные значения свойств формы

## AutoInsertNewRow таблицы

### Договор преобразования

Для `Table.AutoInsertNewRow` используется единый договор обычной таблицы:

| Конфигуратор | YAML | XML |
|---|---|---|
| `Истина` | ключ отсутствует | `<AutoInsertNewRow>true</AutoInsertNewRow>` |
| `Ложь` | `АвтоВводНовойСтроки: Ложь` | узел отсутствует |

Правило задаёт разные неявные значения двух форматов:

```ts
autoInsertNewRow: booleanRule({
  yaml: "АвтоВводНовойСтроки",
  implicitValueYAML: true,
  implicitValueXML: false,
})
```

При XML → YAML отсутствующий узел восстанавливается как `false` и записывается
явно, а XML `true` сворачивается в отсутствующий YAML-ключ. При YAML → XML
отсутствующий ключ создаёт XML `true`, а явное `Ложь` сворачивается в
отсутствующий XML-узел.

Выбор неявного значения не зависит от `DataPath`. Для него не используются
индекс метаданных, исходный XML или снимок конфигурации.

### JSON Schema и MCP

Если у правила одновременно заданы литеральные `implicitValueYAML` и
`implicitValueXML`, экспорт JSON Schema исключает из явных YAML-значений
`implicitValueYAML`. Отдельный признак правила для этого не добавляется.

Поэтому для `АвтоВводНовойСтроки` схема разрешает только явное `Ложь`:
`Истина` считается избыточным значением, а любое не-boolean значение
отклоняется обычной проверкой типа.

MCP получает и применяет ту же схему через core. Специальная проверка в
`packages/mcp` не добавляется. Синхронизация без предварительной валидации
может принять явное `Истина` и преобразует его так же, как отсутствующий ключ.

### Архитектурные границы

- Знание об `AutoInsertNewRow` остаётся в `TableRules`.
- Общие metadata-слои работают только с `implicitValueYAML` и
  `implicitValueXML` и не знают о видах источников таблицы.
- Существующие XML-фикстуры не изменяются.

### Проверки

1. Правило содержит `implicitValueYAML: true` и `implicitValueXML: false`.
2. XML → YAML покрывает отсутствующий узел и явный XML `true`.
3. YAML → XML покрывает отсутствующий ключ и явное YAML `Ложь` без reference
   XML.
4. JSON Schema разрешает `Ложь`, запрещает `Истина` и отклоняет третье
   значение; MCP использует тот же договор.
5. Round-trip `cf/doc` больше не содержит расхождений `AutoInsertNewRow`.

## Растяжение групп формы

### Договор преобразования

В XDTO-схеме `GroupBase.HorizontalStretch` и `GroupBase.VerticalStretch` имеют
тип `BWAValue`: `true`, `false` или `auto`, default — `auto`. Это отличается от
`Table.HorizontalStretch` и обычных полей формы с типом `xs:boolean`.

Источник договора —
[`model.xdtomngbase_root.res`](https://github.com/nikitazherebtsov/1c_res/blob/79cde5b70a15bb54c674ed56e76aa4471772d035/model.xdtomngbase_root.res#L530-L548).

Автоматическое состояние представляется отсутствием значения:

| Конфигуратор | Модель | YAML | XML |
|---|---|---|---|
| `Авто` | `undefined` | ключ отсутствует | узел отсутствует |
| `Ложь` | `false` | `Ложь` | явный узел `false` |
| `Истина` | `true` | `Истина` | явный узел `true` |

Явный XML `auto` импортируется как `undefined` и при последующем экспорте
канонизируется в отсутствующий узел. Явное YAML-значение `Авто` не вводится.

### Правило

Специальный признак для состояния `Авто` не требуется:

```ts
horizontalStretch: booleanRule({
  yaml: "РастягиватьПоГоризонтали",
})
```

Без `implicitValueYAML` значения `true` и `false` всегда записываются в YAML,
а отсутствие ключа передаёт в XML `undefined`. Существующий преобразователь
boolean уже импортирует XML `auto` как `undefined`.

Full sync и MCP не принимают `referenceDir` и не читают исходный XML-каталог.
Индекс конфигурации хранит только невосстановимые XML-состояния и не хранит
обычные значения этих свойств: явные `true` и `false` полностью представлены в
YAML. Изменения общей оркестрации не требуются.

### Область применения

Обычный `booleanRule` без неявного YAML-значения задаётся для
`horizontalStretch` и `verticalStretch` в `formGroupCommonProperties`. Договор
наследуют `UsualGroup`, `CommandBar`, `ColumnGroup`, `ButtonGroup`, `Page`,
`Pages` и `Popup`.

Локальные переопределения этих свойств с другими неявными значениями
удаляются. Правила `Table` и обычных полей формы не изменяются.

Общие metadata-слои не получают условий по типам элементов формы. Решение о
трёхзначном поведении принимается декларативно в rules.ts.

### JSON Schema и MCP

YAML-ключ остаётся необязательным. Если он присутствует, обычная boolean-схема
разрешает только `Истина` и `Ложь`; `Авто` и третье значение отклоняются.
MCP использует ту же схему без специальной логики.

### Проверки

1. XML → YAML покрывает отсутствующий узел, `auto`, `false` и `true`.
2. YAML → XML покрывает отсутствующий ключ, `Ложь` и `Истина`.
3. Оба свойства всех семи видов групп используют `booleanRule` без
   `implicitValueYAML`, `noImplicitValueYAML` и локальных defaults.
4. JSON Schema разрешает отсутствующий ключ, `Истина` и `Ложь`, но отклоняет
   `Авто` и третье значение; MCP применяет эту же схему.
5. Выполняются целевые тесты, `pnpm type-check`, `pnpm test`, mutation testing
   изменённых production-диапазонов и повторный round-trip `cf/doc`.

## Свойства таблицы динамического списка

### Основание договора

В конфигураторе следующие свойства `Table` доступны только для таблицы,
`ПутьКДанным` которой указывает на динамический список:

| YAML-свойство | Неявное значение YAML | Явное значение XML |
|---|---:|---:|
| `АвтоОбновление` | `Ложь` | `false` |
| `ПериодАвтоОбновления` | `60` | `60` |
| `ВыборГруппИЭлементов` | `Элементы` | `Items` |
| `ВосстанавливатьТекущуюСтроку` | `Ложь` | `false` |
| `ОтображатьКорень` | `Истина` | `true` |
| `РазрешитьВыборКорня` | `Ложь` | `false` |
| `ОбновлениеПриИзмененииДанных` | `Авто` | `Auto` |
| `РазрешитьПолучатьНавигационнуюСсылкуТекущейСтроки` | `Истина` | `true` |

В исследованном каталоге `cf` все 11 012 таблиц с прямой связью с
динамическим списком содержат эти восемь XML-узлов явно. Поэтому компактный
YAML может опускать перечисленные значения, но при обратном преобразовании
они должны восстанавливаться как явные XML-узлы.

XDTO-схема объявляет эти свойства `Table` необязательными. Только
`AllowGettingCurrentRowURL` имеет XDTO-default `true`; остальные семь не имеют
XDTO-default. Следовательно, `defaultValueXML` ниже задаёт канонический экспорт
NKDK, подтверждённый XML конфигуратора, а не приписывает XDTO-схеме
отсутствующие значения по умолчанию.

Источник схемы —
[`model.xdtomngbase_root.res`](https://github.com/nikitazherebtsov/1c_res/blob/79cde5b70a15bb54c674ed56e76aa4471772d035/model.xdtomngbase_root.res#L947-L960).

### Определение источника таблицы

При YAML → XML источник определяется только по текущему YAML формы:

1. Из `Table` читается `ПутьКДанным`.
2. Полное значение пути передаётся в уже построенный
   `formDataPathIndex.getRoot(...)`.
3. Совпадение считается прямым динамическим списком, только если корень найден
   целиком и `root.tableSource.table.kind === "DynamicList"`.

Вложенные пути, например `Список.Filter`, таблицы без `ПутьКДанным` и
неразрешимые пути не считаются прямой связью. Исходный XML, индекс конфигурации
и снимок конфигурации для определения источника не используются.

### Правила YAML → XML

Для восьми свойств сохраняется единый компактный договор YAML:
`implicitValueYAML` содержит значение из таблицы выше. Поэтому значение
сворачивается при XML → YAML и не должно указываться явно в YAML.

При YAML → XML используются только существующие возможности правил:

```ts
autoRefreshPeriod: {
  yaml: "ПериодАвтоОбновления",
  type: "number",
  implicitValueYAML: 60,
  defaultValueXML: 60,
  toXML: isDirectDynamicListTable,
  description:
    "Доступно только для таблицы, чей ПутьКДанным напрямую указывает на реквизит DynamicList. Неявное значение — 60.",
}
```

- `implicitValueYAML` задаёт отсутствующее значение компактного YAML;
- `defaultValueXML` явно восстанавливает значение при отсутствии YAML-ключа;
- условие `toXML` разрешает экспорт только для прямого динамического списка;
- локальный построитель рядом с `TableRules` применяет этот договор ко всем
  восьми свойствам и использует общий перечень их ключей и значений.

Для таблицы другого вида отсутствующие свойства не создают XML-узлы. Явное
свойство в такой таблице является ошибкой валидации и не должно молча
теряться. Новые `defaultValue`, `implicitValueXML`, признаки экспорта и
обработчики fromXML/toXML для этого договора не добавляются.

### JSON Schema и MCP

В `BasePropertyRule` добавляется одобренное общее поле
`description?: string`. Генератор переносит его в JSON Schema свойства, не
изменяя его тип и ограничения. Для каждого из восьми свойств описание сообщает,
что оно доступно только для таблицы с прямым `ПутьКДанным` на `DynamicList`, и
называет неявное значение.

JSON Schema выполняет доступные ей статические проверки:

- проверяет тип или системное перечисление;
- запрещает явное значение, равное литеральному `implicitValueYAML`;
- показывает ограничение по источнику в подсказке редактора и MCP.

JSON Schema не определяет вид реквизита по другому разделу YAML. Ограничение
по источнику проверяется семантически в core. MCP применяет ту же JSON Schema и
ту же семантическую валидацию; специальная реализация в `packages/mcp` не
добавляется.

### Семантическая валидация

Проверка выполняется на первом этапе валидации формы:

1. `Форма.yaml` один раз разбирается в память.
2. `createFormDataPathIndexFromYAML` читает раздел `Реквизиты` и строит
   локальный индекс.
3. Существующий `collectFormDataPathOccurrencesFromYAML` рекурсивно обходит
   форму и её элементы. Нейтральная функция посещения текущего элемента
   позволяет проверить каждую `Table`, используя готовый индекс.

Новый полный обход YAML не добавляется. Существующий обход расширяется
нейтральной функцией посещения; первый этап валидации передаёт в неё локальную
проверку из модуля `Table`. Текущий YAML-элемент используется только во время
обхода. Его свойства не сохраняются в состоянии и не передаются между этапами
валидации.

Для каждого явно указанного свойства из общего перечня действует следующий
договор:

- прямой корень `DynamicList` — свойство допустимо;
- определённый корень другого вида — ошибка на ключе свойства;
- вложенный путь или отсутствующий `ПутьКДанным` — ошибка на ключе свойства;
- указанный, но не найденный корень — отдельная ошибка свойства не создаётся:
  существующая проверка `ПутьКДанным` сообщит о неразрешимом пути.

Текст ошибки:

> `<ИмяСвойства>` допустимо только для таблицы динамического списка.

Перечень свойств, их значения, описания и локальная семантическая проверка
живут рядом с `TableRules`. Общие слои обхода и валидации не содержат условий
по `Table`, `DynamicList` или именам YAML-свойств.

### Собственные свойства DynamicList

`DynamicDataRead` имеет XDTO-default `true`, а во всех 11 188 исследованных
реквизитах `DynamicList` конфигуратор записал XML-узел явно. Правило сохраняет
`implicitValueYAML: true` и получает `defaultValueXML: true`: отсутствующий
YAML-ключ остаётся компактным, но XML `true` восстанавливается явно.

Источник схемы —
[`model.xdtomngbase_root.res`](https://github.com/nikitazherebtsov/1c_res/blob/79cde5b70a15bb54c674ed56e76aa4471772d035/model.xdtomngbase_root.res#L253-L265).

У `dcsset:itemsViewMode` XSD не задаёт default. Отсутствующий XML-узел и явный
`Normal` являются разными состояниями. Поэтому у
`РежимОтображенияСтруктуры` удаляется `implicitValueYAML: "Normal"`:

| XML | YAML | Обратный XML |
|---|---|---|
| узел отсутствует | ключ отсутствует | узел отсутствует |
| `Normal` | `Обычный` | `Normal` |

Источник схемы —
[`settings.xsddcscore_root.res`](https://github.com/nikitazherebtsov/1c_res/blob/79cde5b70a15bb54c674ed56e76aa4471772d035/settings.xsddcscore_root.res#L66-L70).

### Проверки

1. Правила восьми свойств содержат согласованные `implicitValueYAML`,
   `defaultValueXML`, условие `toXML` и описание схемы.
2. YAML → XML из текущего YAML покрывает отсутствующие и явные значения для
   прямого `DynamicList`, обычной таблицы, вложенного, отсутствующего и
   неразрешимого `ПутьКДанным`.
3. XML → YAML сохраняет единый компактный договор восьми свойств.
4. JSON Schema проверяет тип, запрещает явные неявные значения и содержит
   описание области применения.
5. Семантическая валидация принимает свойства прямого `DynamicList`,
   отклоняет их для остальных определимых источников и не дублирует ошибку
   неразрешимого пути; тот же договор проверяется через MCP.
6. `DynamicDataRead` восстанавливает явный XML `true` из отсутствующего
   YAML-ключа.
7. `itemsViewMode` различает отсутствующий узел и явный `Normal` в обоих
   направлениях.
8. Выполняются целевые тесты, `pnpm type-check`, `pnpm test`, mutation testing
   изменённых production-диапазонов и повторный round-trip `cf/doc`.

## Критерии готовности

- Все договоры восстанавливаются без чтения исходного XML.
- Удаление ключа растяжения из YAML переводит свойство в `Авто`.
- Явные `true` и `false` растяжения сохраняются через YAML.
- Неявные свойства таблицы восстанавливаются в XML только для прямого
  `DynamicList`.
- Некорректная область применения свойства диагностируется общей валидацией
  core и через MCP.
- Отсутствующий и явный `Normal` для `itemsViewMode` не смешиваются.
- Валидация применяет ограничения без второго семантического прохода.
- Все тесты проходят.

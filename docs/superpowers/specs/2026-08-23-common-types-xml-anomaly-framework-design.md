# `!xml/raw`, `!xml/invalid` и `!xml/important` для XML-аномалий

## Статус

Это целевая спецификация общего механизма. Она объединяет исследование
`boolean`, `string`, `number`, остальных common-типов, `SystemEnumeration` и
границы оркестратора.

Документ фиксирует согласованный общий механизм трёх состояний:
`!xml/raw`, `!xml/invalid` и `!xml/important`. Общая реализация уже начата в
отдельной ветке. Регистрация нового частного применения `!xml/raw` у конкретного
PropertyRule и изменение `.agents/architecture.md` по-прежнему требуют
отдельного согласования.

Формат `!xml/raw` в этой спецификации заменяет раннюю гипотезу пилотов, где
payload содержал строку с полным внешним XML-элементом. `!xml/invalid`
заменяет последующую гипотезу, по которой любая ошибка проверки тоже считалась
raw. `!xml/important` является явно назначаемой разновидностью смысловой
аномалии для заранее согласованных ценных данных.

## Цель

Любой структурно разобранный XML известного проекта должен пройти импорт, даже
если текущие правила:

- не знают значение, атрибут, дочерний элемент или вариант типа;
- выбрасывают исключение;
- молча возвращают `undefined`;
- фильтруют item;
- нормализуют текст, число, QName или default;
- сворачивают несколько XML-элементов в один ключ YAML;
- не могут разрешить ссылку или проверить значение в контексте;
- неоднозначно определяют владельца XML-узла.

Неподдержанная часть сохраняется в YAML как `!xml/raw`. Любое понятное,
обратимо преобразуемое, но нарушающее правило значение сохраняется как
`!xml/invalid`. `!xml/important` используется только для явно согласованных
классов ценных данных. В текущем механизме important ведёт себя как invalid:
оба тега сохраняют значение при экспорте. Валидатор раскрывает их для проверки
необходимости тега, но не выводит уже принятую ошибку повторно. Raw исключает
из смысловой проверки только `$xml`; `$значение`, если оно есть, и остальной
проект продолжают проверяться.

После импорта каждый разобранный XML-узел обязан оказаться ровно в одном из
состояний:

1. полностью представлен обычным YAML и восстановлен без потерь;
2. сохранён как `!xml/raw`;
3. представлен обычным YAML под тегом `!xml/invalid`;
4. представлен обычным YAML под тегом `!xml/important`;
5. сохранён внешним ресурсом по проверенному обратимому договору;
6. привёл к фатальной ошибке, для которой безопасный перенос невозможен.

Молчаливо потерянного седьмого состояния быть не должно.

«Восстановлен» здесь означает экспорт из YAML и штатных индексов проекта, но
без чтения исходного XML, reference snapshot или прежнего результата импорта.
Иначе снимок мог бы скрыть, что переносимый YAML на самом деле потерял данные.

## Что означает «любая ошибка формата»

Механизм гарантирует полноту относительно нормализованного XML-дерева, которое
построил парсер. Сравниваются:

- имена элементов и атрибутов;
- значения атрибутов;
- порядок атрибутов;
- текст;
- наличие и отсутствие узлов;
- пустое и отсутствующее значение;
- вложенность;
- количество и порядок дочерних элементов;
- namespace-префиксы как часть имён и значений QName;
- processing instructions, уже представленные парсером как XML-узлы.

Не считаются различиями:

- вид кавычек;
- исходные отступы;
- `<Value/>` и `<Value></Value>`;
- CDATA и эквивалентный текст;
- запись entity и получившийся после разбора символ;
- комментарии;
- кодировка файла при одинаковом разобранном тексте.

Сведения из последнего списка текущий парсер не сохраняет. Побайтовая копия XML
не входит в договор `!xml/raw`. Порядок атрибутов, напротив, обязан входить в
аудит-дерево и структурное сравнение.

Синтаксически неверный XML не имеет надёжного дерева и остаётся фатальной
ошибкой файла. Сохранить его можно было бы только исходной строкой целиком,
что противоречит выбранному YAML-представлению raw.

Для ошибок значения полнота определяется зарегистрированным договором проверки.
Каждая обычная YAML-граница после импорта должна получить терминальный статус:
`valid`, `invalid`, `important`, `unsupportedValue` или `fatal`; временный `pending`
обязан разрешиться до завершения импорта. Отсутствие обработчика нельзя
молчаливо считать успешной проверкой, если PropertyRule объявляет предметное
или контекстное ограничение.

## Основные решения

1. Публичных тегов три: `!xml/raw`, `!xml/invalid` и `!xml/important`.
2. Выбор определяется поведением, а не частным видом ошибки:
   - сначала XML преобразуется в обычное смысловое YAML-значение без
     специальных данных аномалии;
   - затем это значение обычным экспортом, без помощи тега и исходного XML,
     должно точно восстановить своё XML-место;
   - если смысловое значение получить нельзя либо обычный смысловой экспорт
     меняет XML — raw;
   - если смысловое значение получено, обычный экспорт точен, но значение
     нарушает правило — invalid;
   - если значение прошло проверку — обычный YAML без тега;
   - если тот же случай относится к явно зарегистрированному классу ценных
     данных — important вместо invalid.
3. Raw всегда хранит mapping-контейнер с обязательным `$xml` и необязательным
   `$значение`. Пустой тег и неявное восстановление из генератора запрещены.
4. Для raw используется форма, близкая к текущему результату XML-парсера:
   `_attribute`, `"#text"`, точные XML-имена дочерних элементов и массивы
   повторов.
5. Payload invalid и important является обычным YAML-значением соответствующего
   common-типа.
6. Внешнее XML-имя известного свойства не повторяется: его знает PropertyRule.
7. `$значение` и `$xml` достаточны для восстановления аномалии без исходного
   XML, прежнего снимка компонента или частного генератора. Обычные
   генерируемые идентификаторы внутри `$значение` могут по-прежнему требовать
   индекс согласно штатному договору PropertyRule, но `$xml` всегда явен.
8. Raw не передаётся `fromYAML` common-типа и не проходит предметную проверку
   соответствующего свойства.
9. Invalid и important проходят обычные `fromYAML` и `toXML`; тег не меняет
   получаемый XML. При импорте те же правила валидации, которыми затем
   проверяется проект, выбирают смысловой тег. При последующей обычной
   валидации значение под тегом проверяется без тега: наличие той же ошибки
   подтверждает необходимость тега, а отсутствие ошибки создаёт ошибку
   `xml/anomaly-tag-unnecessary`. Пользовательская ошибка, уже принятая тегом,
   второй раз наружу не выводится.
10. Invalid и important остаются смысловыми значениями для экспорта. Сам тег не
    определяет участие ссылки в индексах: сначала ссылка разрешается без
    применения допустимого типа, отбора и filter конкретного свойства, а затем
    отдельно проверяется её допустимость. Однозначно найденная, но недопустимая
    цель остаётся доступной индексам, поиску и переименованию под тегом invalid.
    Отсутствующая или неоднозначная цель тоже получает invalid, но целевой связи
    в индексе у неё нет. Команда автоматического исправления не входит в эту
    задачу. Important пока лишь явно сохраняет решение о ценности данных для
    будущего механизма; raw также не получает политики автоматического удаления.
    Соседние свойства и остальные файлы проверяются обычно.
11. Существующие `!xml/present`, `!xml/absent`, `!xml/type`, `!xml/value`,
   `!xml/reference`, `!xml/language`, `!xml/order` и `!xml/duplicate` не
   поддерживаются новым загрузчиком. Их исторические XML-случаи при повторном
   импорте классифицируются одним из трёх новых тегов. Имя известного singleton
   является отдельной формой XML и после явного исследования снова использует
   узкий `!xml/name`; это не класс аномалии. Преобразование старого YAML и режим
   совместимости не предусмотрены.
12. Класс аномалии виден непосредственно в YAML, а не существует только в
    диагностике.
13. Каждая аномалия создаётся на минимальной устойчивой границе, которую можно
    однозначно вставить обратно. Независимые дочерние аномалии получают
    отдельные теги; общий родитель не помечается, пока эти границы не
    перекрываются и их совместный экспорт точно восстанавливает XML.
14. Для любого логического повтора, который обычный YAML mapping потерял бы,
    `!xml/invalid` ставится на YAML-ключ первого дубля без номера. Второй дубль
    получает `!xml/invalid/2`, третий — `/3` и так далее. Это относится и к
    именованным XML-коллекциям, и к повторному singleton-свойству. Повтор,
    предусмотренный обычной sequence-моделью, аномалией не является. Сам по
    себе дубль не является основанием для `important`.
15. `!xml/raw` используется только на YAML-значениях и никогда не ставится на
    YAML-ключ. Понятный и точно обратимый, но недопустимый ключ получает
    `!xml/invalid`; необратимая XML-форма item сохраняется как raw его значения
    либо всей коллекции.
16. Каждый тег должен оставаться необходимым по текущим правилам и состоянию
    проекта. Если без него значение корректно, представимо обычным YAML и точно
    экспортируется, валидация выдаёт блокирующую ошибку лишнего тега.
17. `!xml/important` допустим только на явно зарегистрированной границе или
    классе данных. Ручной important вне регистрации является ошибкой самого
    тега и не заменяет обычный invalid.
18. Если класс данных зарегистрирован как important, использование invalid
    является ошибкой `xml/important-required`: явную отметку ценности нельзя
    понижать вручную.
19. Если одна граница одновременно подходит под invalid и явно зарегистрированный
    important, выбирается `!xml/important`. Это приоритет двух смысловых тегов,
    а не правило автоматического назначения important для дублей или других
    аномалий.
20. В именованной коллекции первый обычный элемент остаётся каноническим для
    предметного индекса и resolver. Помеченные дубли не делают ссылку
    неоднозначной и не создают зависимых ошибок, но остаются в полном перечне
    элементов для экспорта, поиска и переименования.
21. Граница поднимается к родителю только когда дочерний фрагмент нельзя
    устойчиво адресовать, дочерние границы перекрываются либо их раздельный
    экспорт не собирается в исходный XML. Поднятый raw сохраняет понятные
    вложенные данные и смысловые теги в `$значение`, объединяя только
    пересекающиеся XML-поправки в своём `$xml`.
22. XML-фрагмент, для которого нет PropertyRule, адресуется служебным YAML-
    ключом полного XML-пути относительно корня текущего объекта, например
    `Properties\Future`. Сегменты разделяются обратной косой чертой. На значении
    такого ключа всегда стоит raw; служебный контейнер `#xml` не используется.
23. Иерархическая часть пути содержит только имена XML-узлов. Неизвестные
    атрибуты и объединённый порядок известных и неизвестных детей не получают
    отдельных YAML-свойств: raw ставится на путь самого элемента, атрибуты
    находятся в его `$xml` как `_имя`, а порядок — как `#order`.
    Логические повторы ключа XML-пути адресуются `!xml/invalid` и
    `!xml/invalid/N` на ключе.
    Если один YAML формирует несколько XML-документов, путь дополнительного
    документа начинается с `@ИмяДокумента`, например `@Form\Future`. Имя
    берётся из зарегистрированной топологии без каталога `Ext/` и расширения
    `.xml`. Основной документ не получает префикса; одиночный ключ `@` означает
    его корневой элемент и нужен только для raw-поправки самого корня.
24. Поддерживаемым источником всех трёх тегов является только XML-импорт.
    Валидатор участвует в импорте как источник решений `invalid`/`important`,
    но обычная команда проверки уже существующего YAML никогда не переписывает
    файл и не добавляет тег автоматически. ИИ-агент технически может записать
    такой YAML вручную, но это непредусмотренный сценарий и не получает
    отдельного договора происхождения.
25. Импортёр никогда самостоятельно не выбирает `invalid` или `important`.
    Там, где обычный YAML-object уничтожил бы данные или адрес, он до
    схлопывания сохраняет внутренние адресуемые вхождения: повторы mapping-ключа,
    отсутствующие обязательные свойства и другие коллизии представления.
    Структурный валидатор проверяет эти вхождения вместе с обычным смысловым
    YAML и только затем назначает публичный смысловой тег. Окончательный
    YAML-object строится после классификации.
26. Raw не скрывает распознанную смысловую оболочку без необходимости. Если у
    именованного элемента неизвестна только вложенная часть, его ключ, вид,
    адрес и распознанные свойства остаются обычным YAML и участвуют в
    структурных индексах; raw получает только минимальное неизвестное значение
    или полный XML-путь. Весь вложенный item или значение свойства становится
    raw лишь тогда, когда меньшую устойчивую границу восстановить невозможно.
    Корневой объект метаданных целиком raw быть не может: иначе он исчезнет из
    смысловых индексов и проверки ссылок. Нераспознаваемый XML-root или тип
    объекта завершает импорт явной ошибкой.

### Скалярные теги формы XML

`!xml/string` хранится в общей out-of-band таблице скалярных YAML-тегов, но
не входит в `XmlAnomalyKind`. Парсер принимает только scalar payload;
mapping и sequence являются синтаксической ошибкой. Нейтральная операция
типа `yamlScalarTagPolicy` разрешает тег конкретному типу свойства, а общая
граница `callAtomicFromYAML` отклоняет его у остальных типов. Теги
`!проверять` и `!изменять` остаются единственными тегами PropertyState.

| YAML | XML |
| --- | --- |
| `Представление: Текст` | `v8:LocalStringType` с основным языком проекта |
| `Представление: { ru: Текст, en: Text }` | многоязычный `v8:LocalStringType` |
| `Представление: !xml/string Текст` | `xs:string` |

Ручная вложенная проекция вызывает атомарный импорт с непосредственным
YAML-родителем и публичным ключом правила. При пересборке объекта она
переносит out-of-band теги через `copyYAMLScalarTags`, а не ставит
конкретный тег вручную.

`!xml/string` не подавляет диагностику и не участвует в proof-аудите или
назначении raw. Это только явный выбор XML-формы для обычного смыслового
значения.

## YAML-договор `!xml/raw`

`!xml/raw` всегда помечает системный mapping-контейнер с двумя
зарезервированными полями:

```yaml
Свойство: !xml/raw
  $значение: <распознанное смысловое YAML-значение>
  $xml: <точная XML-поправка>
```

`$значение` необязательно. Если оно есть, это единственный источник смысловых
данных для схемы, индексов, resolver, поиска и переименования. `$xml` обязателен
и содержит только отличие от обычного экспорта `$значение`. Если
`$значение` отсутствует, свойство не удалось представить смысловым YAML и
`$xml` содержит полное parser-shaped XML-дерево этой границы.

После разбора YAML контейнер не попадает в предметную модель. Парсер помещает
`$значение` на обычное место свойства, а `$xml` и признак наличия
`$значение` — в таблицу XML-аннотаций. При отсутствии `$значение` ключ свойства
остаётся адресуемым, но предметного значения у него нет. Сериализатор собирает
контейнер обратно только при записи YAML.

Тег разрешён только внутри уже распознанного объекта метаданных. На корне YAML
объекта метаданных и на всём файле он запрещён независимо от формы payload.

`$xml` является рекурсивной поправкой, когда `$значение` присутствует:

- отсутствующий ключ ничего не меняет в обычном экспорте;
- `null` удаляет соответствующий атрибут, текст, дочерний узел либо всю
  границу, если стоит непосредственно в `$xml`;
- scalar и sequence добавляют или заменяют соответствующую XML-часть;
- mapping рекурсивно применяет те же правила;
- `#name` заменяет внешнее имя, а `#order` — порядок дочерних узлов.

Обычный parser-shaped текст в `$xml` всегда является строкой. YAML boolean и
number запрещены: сериализатор обязан заключить похожий текст в кавычки.
Смысловой `$значение`, напротив, сохраняет обычный YAML-тип PropertyRule.

Пустой `!xml/raw` запрещён. Фиксированные и контекстные генераторы raw также
запрещены: вся необходимая для экспорта XML-информация должна находиться в
`$xml`, а не в регистрации или reference snapshot.

### Значение известного XML-места

`$xml` использует форму, которую текущий XML-парсер хранит под найденным
XML-ключом.

| XML-состояние | YAML raw |
|---|---|
| узел отсутствовал, но обычный экспорт его создаёт | `$xml: null` |
| присутствовал пустой узел, который обычный экспорт удаляет | `$xml: {}` |
| отличается только текст | `$xml: { "#text": <строка> }` |
| отличаются атрибуты или дочерние элементы | точечный mapping в `$xml` |
| повтор или порядок внутри XML-sequence | sequence и `#order` в `$xml` |
| смысловое значение полностью неизвестно | `$значение` отсутствует, `$xml` содержит полное дерево |
| повтор singleton или вычисленного YAML-ключа | отдельные YAML-записи: обычная первая и ключи `!xml/invalid`, `!xml/invalid/N` для дублей |

Отсутствие и пустой элемент различаются намеренно:

```yaml
# Обычный экспорт добавил бы отсутствующий XML-элемент
Видимость: !xml/raw
  $значение: true
  $xml: null

# В XML был явный пустой элемент
ДополнительныеПоля: !xml/raw
  $xml: {}
```

Явный default остаётся смысловым значением, а `$xml` явно добавляет удаляемый
обычным экспортом XML-текст:

```yaml
ГоризонтальноеПоложениеВШапке: !xml/raw
  $значение: Auto
  $xml:
    "#text": Auto
```

Экспорт сначала обрабатывает `Auto` обычным PropertyRule, затем `$xml` добавляет
исходный элемент. Специального генератора `HeaderHorizontalAlign` не требуется.

### Текст

Простой неподдержанный текст хранится полным XML-деревом без `$значение`:

```yaml
Использовать: !xml/raw
  $xml:
    "#text": Switch
ДлинаКода: !xml/raw
  $xml:
    "#text": "001"
```

Числоподобные, boolean-подобные, `null`, пустые и окружённые пробелами строки
обязательно цитируются обычным YAML-сериализатором, чтобы сохранить строковый
тип и точный текст.

### Атрибуты и дочерние элементы

Атрибут получает тот же `_`-префикс, который использует XML-парсер. Текст
хранится в `"#text"`, дочерний элемент — под точным XML-именем:

```xml
<Use custom="x"><Value>true</Value></Use>
```

```yaml
Использовать: !xml/raw
  $значение: true
  $xml:
    _custom: x
    Value:
      "#text": "true"
```

Для текста рядом с атрибутом:

```xml
<Use xsi:type="xs:boolean">Switch</Use>
```

```yaml
Использовать: !xml/raw
  $xml:
    "_xsi:type": xs:boolean
    "#text": Switch
```

`xsi:nil` не выделяется в отдельный общий класс. Отличающийся атрибут хранится
в `$xml`:

```yaml
Значение: !xml/raw
  $xml:
    "_xsi:nil": "true"
```

Аудит-импорт обязан запускать XML-парсер с сохранением `xsi:nil`, даже если
обычный преобразователь конкретного свойства его игнорирует.

### Повторы

Если singleton-элемент повторяется, каждый понятный и обратимый элемент
сохраняется отдельной YAML-записью. Первый остаётся обычным, первый дубль
получает `!xml/invalid`, последующие — `!xml/invalid/N`:

```xml
<Use>true</Use>
<Use>false</Use>
```

```yaml
Использовать: Истина
!xml/invalid Использовать: Ложь
```

Если повтор одновременно содержит нераспознанную форму значения, тег ключа
по-прежнему адресует дубль, а raw ставится только на его значение:

```yaml
Использовать: Истина
!xml/invalid Использовать: !xml/raw
  $значение: Ложь
  $xml:
    _future: x
```

Sequence остаётся sequence без тегов, когда повторы предусмотрены моделью.
Raw-массив нужен только если сама коллекция или структура item непредставима
смысловым YAML. Например, полностью неизвестная форма `v8:item` сохраняется
raw всей коллекции, а два понятных языка с одним ключом сохраняются отдельными
ключами `!xml/invalid` и `!xml/invalid/N`.

### Нестандартное внешнее XML-имя

Собственное имя элемента не входит в его значение у текущего парсера. Если
исходное имя отличается от канонического PropertyRule, поправка использует
зарезервированный ключ `"#name"`, а распознанное значение остаётся в
`$значение`:

```yaml
Использовать: !xml/raw
  $значение: true
  $xml:
    "#name": LegacyUse
```

`#name` разрешён только на корне `$xml` или у raw-item sequence.
Обычное дочернее XML-имя уже является ключом mapping и не требует `#name`.

Если singleton известен и его содержимое преобразуется в смысловой YAML,
из-за одного неканонического внешнего имени смысловое содержимое не исчезает:

```yaml
РасширеннаяПодсказка: !xml/raw
  $значение:
    Текст: Подсказка
  $xml:
    "#name": СтароеИмяExtendedTooltip
```

Отдельное скрытое свойство `Имя` больше не требуется. `$значение` проходит
обычное преобразование, проверку, индексацию, поиск и переименование; его
логическая идентичность остаётся канонической. При совпадении `$xml.#name` с
обычным экспортом тег становится избыточным.

### Порядок атрибутов

Порядок атрибутов является частью нормализованного XML и сравнивается до
значений дочерних элементов. В raw он выражается порядком `_...`-ключей YAML,
без отдельного служебного поля:

```xml
<Value second="2" first="1">x</Value>
```

```yaml
Значение: !xml/raw
  $значение: x
  $xml:
    _second: "2"
    _first: "1"
```

Парсер, YAML-сериализатор и XML-экспортёр не имеют права сортировать такие
ключи. `#order` описывает только дочерние элементы и не включает атрибуты. Если
обычный common-тип восстанавливает те же атрибуты в другом порядке и порядок не
выражен его смысловым YAML, минимальная граница становится raw.

### Порядок дочерних элементов

Текущий XML-парсер хранит порядок дочерних элементов в несерилизуемом
`Symbol.for("metadata")`. При переводе raw в YAML он материализуется как
зарезервированный `"#order"`:

```xml
<Root><A>1</A><B>2</B><A>3</A></Root>
```

```yaml
Свойство: !xml/raw
  $xml:
    A: ["1", "3"]
    B: "2"
    "#order": [A, B, A]
```

Повторное имя в `#order` выбирает следующий ещё не использованный элемент
соответствующего массива. Число упоминаний обязано совпадать с числом
дочерних элементов. При каноническом порядке `#order` можно не выводить.

Если нужно объединить ребёнка, созданного Rules, с неизвестным ребёнком, raw
ставится на путь родительского элемента, а порядок находится внутри его `$xml`:

```yaml
Properties: !xml/raw
  $xml:
    "#order": [Name, FutureOption]
Properties\FutureOption: !xml/raw
  $xml:
    "#text": "42"
```

Отдельный ключ XML-пути `Properties\#order` запрещён. При каноническом порядке
`#order` внутри raw родителя не выводится.

Пробельный текст между дочерними XML-элементами является форматированием 1С:
последовательности только из пробелов, табуляций и переводов строк удаляются из
нормализованного дерева до хэширования, аудита, сравнения и raw-проекции. Они не
создают `#text`, `#order` или raw. Текст элемента без дочерних элементов
сохраняется точно, даже если состоит только из пробелов, например
`<FillValue>         </FillValue>`. Непробельный mixed content также остаётся
значимым и не удаляется.

### Зарезервированные ключи

| Ключ | Смысл |
|---|---|
| `$значение` | распознанное смысловое YAML-значение raw-контейнера |
| `$xml` | обязательная XML-поправка либо полное дерево при отсутствии `$значение` |
| `_имя` | XML-атрибут `имя` |
| `#text` | текст элемента |
| `#name` | нестандартное имя самого raw-элемента |
| `#order` | YAML-массив исходного порядка дочерних узлов |
| `?target` | processing instruction, уже представленный XML-парсером |

XML-имя не может начинаться с `#`, поэтому служебные ключи не конфликтуют с
настоящими элементами. В YAML ключи с `#` всегда записываются в кавычках.
Обратная косая черта не является ключом raw-payload: она разделяет сегменты
служебного YAML-ключа XML-пути снаружи raw-значения.
Начальный `@ИмяДокумента` выбирает дополнительный XML-документ текущего YAML-
задания. Одинарный `@` выбирает корень основного XML-документа.

### XML-пути без PropertyRule

Неизвестный дочерний элемент или атрибут нельзя прикрепить к случайному
соседнему свойству и нельзя превращать промежуточные XML-обёртки в обычные
YAML-свойства. Он получает служебный ключ полного XML-пути относительно корня
текущего metadata item. Сегменты разделяются `\`, которого не бывает в XML-
именах. Значением такого ключа всегда служит raw-контейнер без
`$значение`: обязательный `$xml` хранит полное дерево ближайшей
неизвестной XML-границы. Известные соседние свойства в него не
включаются:

```xml
<Properties custom="x">
  <Name>Товары</Name>
  <FutureOption mode="new">42</FutureOption>
</Properties>
```

```yaml
Имя: Товары
Properties: !xml/raw
  $xml:
    _custom: x
    "#order": [Name, FutureOption]
Properties\FutureOption: !xml/raw
  $xml:
    _mode: new
    "#text": "42"
```

`Properties` здесь является правильной XML-обёрткой, но не YAML-свойством.
Известное `Name` продолжает импортироваться обычным PropertyRule как `Имя`, а
неизвестные части адресуются по исходному XML-пути. Атрибут `custom` находится
в `$xml` самого пути `Properties`, то есть принадлежит этому XML-узлу, но сам
не становится сегментом иерархии. `#order` внутри того же `$xml` описывает
порядок **объединённого** родителя и поэтому может ссылаться как на неизвестные
raw-дети, так и на детей, созданных обычными PropertyRule.

Если важен порядок неизвестного атрибута относительно известных, `$xml`
содержит полный упорядоченный набор атрибутов элемента:

```yaml
Properties: !xml/raw
  $xml:
    _id: a
    _future: x
    _version: "1"
```

Порядок `_...`-ключей является порядком XML-атрибутов. Известные значения в
такой поправке повторяются намеренно: это минимальная самодостаточная форма,
способная точно восстановить общий порядок без отдельного `#attributes`.

Если неизвестный атрибут принадлежит корневому элементу основного документа,
используется одиночный селектор `@`:

```yaml
'@': !xml/raw
  $xml:
    _future: x
```

Для дополнительного XML-документа первым сегментом служит его краткое имя:

```yaml
'@Form\Future': !xml/raw
  $xml:
    "#text": "42"
'@AdditionalIndexes\Future': !xml/raw
  $xml:
    "#text": "42"
```

Соответствия `@Form -> Ext/Form.xml` и
`@AdditionalIndexes -> Ext/AdditionalIndexes.xml` берутся из топологии. В YAML
не записываются ни `Ext/`, ни `.xml`. Для основного документа остаётся обычный
путь `Properties\Future` без префикса. Если свойство известно Rules и уже имеет
`filePath`, селектор документа не нужен: Rules однозначно выбирает XML сам.

Путь может иметь любую глубину:

```yaml
Properties\Appearance\Future: !xml/raw
  $xml:
    "#text": "42"
```

Для неизвестной обёртки raw ставится на значение её пути:

```yaml
Properties\FutureGroup: !xml/raw
  $xml:
    Option:
      "#text": "42"
```

Для повторного неизвестного пути действует тот же договор дублей:

```yaml
Properties\Future: !xml/raw
  $xml: { "#text": A }
!xml/invalid Properties\Future: !xml/raw
  $xml: { "#text": B }
!xml/invalid/2 Properties\Future: !xml/raw
  $xml: { "#text": C }
```

Raw не ставится на ключ. `invalid` здесь не объясняет причину, а создаёт
уникальный адрес второго и последующих XML-вхождений; фактическая неизвестная
форма каждого вхождения находится в raw-значении.

Служебный ключ XML-пути допустим только для фрагмента, которому не принадлежит
PropertyRule. Каждый иерархический сегмент обязан быть корректным XML-именем;
пустые сегменты, начальная или конечная `\`, `.` и `..` запрещены. Только
начальный селектор документа `@ИмяДокумента` и одиночный корневой селектор `@`
являются служебными и не считаются сегментами XML-иерархии. Атрибуты, `#text`
и `#order` находятся внутри raw-значения соответствующего
узла. Raw может дополнять известную XML-обёртку не принадлежащим Rules
атрибутом или ребёнком. Повторная запись одной и той же конкретной XML-части,
уже созданной обычным правилом, считается конфликтом и блокирует экспорт:
молчаливо выбирать одну сторону нельзя.

`#order` внутри `$xml` относится только к детям указанного родителя.
Порядок атрибутов полностью развёрнутого raw задаётся порядком `_...`-ключей.
При объединении неизвестных и известных атрибутов raw-поправка пути элемента
содержит полный упорядоченный набор `_...`-ключей; отдельного служебного
YAML-свойства для атрибутов нет.

### Смысловой тег на ключе именованной коллекции

Если XML-array превращается в YAML mapping, ключ обычно вычисляется из имени,
атрибута или ссылки item. Иногда точный текст XML-ключа представим строкой YAML
и обратим, но не проходит смысловую проверку. В этом случае `invalid` ставится
на ключ, а тело item остаётся обычным значением.

Например:

```xml
<UserVisible>
  <xr:Common>true</xr:Common>
  <xr:Value name="">false</xr:Value>
  <xr:Value name="Role.Кассир">true</xr:Value>
</UserVisible>
```

```yaml
Использование:
  Роли:
    !xml/invalid "": Ложь
    Кассир: Истина
```

Здесь пустая строка является точным значением XML-атрибута `name`, но не
является допустимой ссылкой на роль. Экспорт не добавляет к ней `Role.`, не
вызывает resolver и дословно восстанавливает `name=""`. Значение `Ложь`
преобразуется штатным item-rule. Роль `Кассир` остаётся обычным смысловым ключом
и продолжает участвовать в поиске и переименовании.

Если такой ключ повторяется, для уникального YAML-адреса используются суффиксы
смыслового тега:

```yaml
Использование:
  Роли:
    !xml/invalid "": Ложь
    !xml/invalid/2 "": Истина
```

Первое вхождение уже занимает адрес `!xml/invalid ""` из-за собственной ошибки
ключа, поэтому повтор получает `/2`. Если исходный ключ сам допустим и записан
без тега, первый дубль получает `!xml/invalid` без номера, а второй дубль —
`!xml/invalid/2`.

`!xml/raw` на ключах запрещён. Если значение item содержит непредставимую
XML-форму, raw ставится на значение под смысловым ключом:

```yaml
Использование:
  Роли:
    !xml/invalid "": !xml/raw
      $значение: Ложь
      $xml:
        _future: x
```

Здесь invalid сохраняет обратимый, но недопустимый ключ, а raw сохраняет
необратимую форму значения item. Если такую границу невозможно экспортировать
однозначно либо устойчивого ключа вообще нет, raw поднимается на значение всей
коллекции.

## Общий YAML-договор смысловых тегов

`!xml/invalid` и `!xml/important` поддерживают те же YAML null, scalar, mapping и
sequence, что и обычное значение соответствующего common-типа. Их payload —
штатное смысловое YAML-представление, а не дерево XML.

При экспорте тег снимается перед `fromYAML`, после чего работают обычные
`fromYAML` и `toXML`. Тег не патчит XML, не хранит причину аномалии и сам по
себе не определяет способ восстановления: его определяют PropertyRule, тип
значения и место значения в YAML.

Оба тега означают, что импортёр уже принял аномалию. Поэтому обычная валидация
не выводит ошибки отмеченной границы или её содержимого. Отдельная проба может
вывести только ошибку самого тега, если аномалия уже исчезла и тег больше не
нужен. Ошибки соседних нетегированных границ продолжают выводиться. При этом
смысловой payload остаётся доступен обычным операциям типа. Для ссылок поиск,
переименование и целевые индексы получают только однозначно разрешённую цель;
само наличие invalid или important не создаёт фиктивную связь с отсутствующей
или неоднозначной целью.

### `!xml/invalid`: смысловая аномалия по умолчанию

`!xml/invalid` используется при одновременном выполнении трёх
условий:

1. XML → смысловое YAML-представление завершилось успешно для всей границы;
2. обычный обратный экспорт значения точно восстанавливает исходное XML-место;
3. значение нарушает предметное, контекстное или структурное правило.

Это базовый результат для любой понятной обратимой аномалии. Импортёр не обязан
доказывать безопасность её удаления и не пытается автоматически определить
ценность данных.

Причина invalid в публичном теге не кодируется. В частности, одинаковое
представление используется для двух разных результатов разрешения ссылки:

- цель однозначно найдена, но не соответствует допустимому типу, отбору или
  filter свойства — ссылка преобразуется в обычный YAML, получает invalid и
  остаётся участником целевых индексов, поиска и переименования;
- цель отсутствует или неоднозначна — обратимый YAML-путь также получает
  invalid, но целевая связь в индексе не создаётся.

Для этого разрешение ссылки и проверка её допустимости являются разными
этапами. Filter свойства не имеет права помешать общему resolver найти
существующую цель; он только классифицирует уже разрешённое значение как
допустимое либо invalid. Если обычный YAML-путь вообще нельзя получить,
используется raw.

Например, если свойство допускает только другой вид метаданных, существующая
ссылка всё равно импортируется смысловым значением:

```yaml
Источник: !xml/invalid Справочник.Поставщики.Основной
```

Она экспортируется обычным ссылочным правилом и участвует в переименовании
`Справочник.Поставщики.Основной`, хотя предметная ошибка свойства под тегом
больше не выводится.

Так же разделяются выбор известного обработчика подтипа и допустимость этого
подтипа в конкретной коллекции. Сначала глобальный реестр преобразует весь
известный item обычным обработчиком. Затем ограничение коллекции проверяет поле
вида. Если вид запрещён только этим контекстом, смысловой item сохраняется, а
его дискриминатор получает invalid:

```yaml
Вид: !xml/invalid ПолеРисунка
```

Экспорт снова выбирает глобально зарегистрированный обработчик
`PictureField`; invalid не меняет XML, а только разрешает сохранить известный
подтип вопреки ограничению `ContextMenu.ChildItems`. Остальные свойства item
остаются обычным YAML и участвуют в независимых проверках. Неизвестный
глобальному реестру подтип или известный обработчик, не восстановивший исходный
XML, сохраняется raw.

Например, число полностью понятно и штатно экспортируется, но нарушает
допустимый диапазон:

```xml
<Length>-2</Length>
```

```yaml
Длина: !xml/invalid -2
```

Пока тег присутствует, экспорт сохраняет исходное значение `-2`. Команда
исправления или удаления аномалий в текущий механизм не входит.

Теги создаёт XML-импортёр. YAML не хранит доказательство происхождения, поэтому
технически идентичную ручную запись невозможно отличить от импортированной, но
такой способ создания не поддерживается. В любом случае положение тега, его
необходимость и способность значения экспортироваться проверяются структурным
договором. Обычная ошибка YAML без тега остаётся блокирующей и автоматически
аномалией не становится.

Тег относится к текущему payload, а не хранит утверждение о его совпадении с
первоначальным XML. Исходное значение, контрольная сумма и история изменений не
сохраняются. Если ИИ-агент изменил payload уже импортированного тега, новое
значение также обязано оставаться понятной обратимой аномалией:

```yaml
Длина: !xml/invalid -2
```

Если `-2` по-прежнему нарушает правило, но штатно экспортируется, значение
принимается и экспортируется. Если новое значение стало корректным, возникает
`xml/anomaly-tag-unnecessary`. Если новое значение больше нельзя восстановить
обычным экспортом common-типа, нарушен договор semantic-тега: экспорт
блокируется, а значение должно быть представлено raw.

### `!xml/important`: явно отмеченная ценная аномалия

`!xml/important` удовлетворяет тем же трём условиям, что и invalid, но
используется только для заранее явно согласованных классов данных. Импортёр не
выбирает important из осторожности и не выводит его из неизвестности: без
специальной регистрации результатом остаётся invalid.

На текущем этапе дубли и другие классы данных автоматически important не
считаются. Конкретные important-классы добавляются только после отдельного
явного решения разработчика.

В текущей реализации important и invalid одинаково сохраняются при экспорте,
участвуют в смысловых операциях и скрывают принятую внутреннюю ошибку. Различие
пока служит только явной классификацией для будущих решений. Обычный ошибочный
YAML без одного из тегов остаётся блокирующей ошибкой и автоматически тегом не
оборачивается.

### Повторы ключей именованной коллекции

Если XML-array импортируется в YAML как mapping и несколько значимых элементов
получили один логический ключ, первый допустимый ключ остаётся обычным, а
последующие получают `!xml/invalid` с номером вхождения:

```yaml
Реквизиты:
  Код:
    Тип: Строка
  Наименование:
    Тип: Строка
  !xml/invalid Код:
    Тип: Число
  Цена:
    Тип: Число
  !xml/invalid/2 Код:
    Тип: Дата
```

Тег без номера адресует первый дубль `Код`, то есть второе XML-вхождение этого
ключа. `/2` адресует второй дубль, то есть третье XML-вхождение. Суффиксы не
являются новыми классами или причинами ошибки. YAML mapping сохраняет порядок
записей, поэтому экспорт возвращает элементы именно в показанном порядке;
`#order` для такой коллекции не нужен.

Если уже первое имя нарушает договор ключа, тег ставится и на него:

```yaml
Реквизиты:
  !xml/invalid 1Код:
    Тип: Строка
  !xml/invalid/2 1Код:
    Тип: Число
```

Вторая запись одновременно сохраняет недопустимое имя и является вторым его
вхождением. Отдельные причины в теге не кодируются. Логическим именем обеих
записей остаётся `1Код`; номер нужен только для уникального YAML-адреса.

Тег на ключе адресует весь item, но не делает его невидимым. Обычная валидация
проверяет логический ключ и значение без тега, подтверждает недопустимое имя
и/или повтор, но не выводит принятую ошибку второй раз. Все вхождения остаются
доступными для экспорта, поиска и переименования как отдельные элементы.
Нетегированный повтор ключа остаётся ошибкой YAML, потому что его нельзя
сохранить без потери.

Для именованных коллекций это общее правило: любой сохранённый первый дубль
получает `!xml/invalid`, а последующие — `!xml/invalid/N`. Important применяется
только при отдельной явной регистрации конкретного класса данных; сам факт
повтора такой регистрацией не является.

`!xml/invalid` на всей коллекции может сочетаться с `!xml/invalid` и
`!xml/invalid/N` на её ключах. Внешний тег принимает общий инвариант коллекции, например
неканонический порядок `I8nText`; ключевые теги при этом только адресуют
повторные item.

На одной и той же смысловой границе important имеет приоритет над invalid.
Raw применяется только к значениям и может содержать смысловой тег внутри
`$значение`: внешний raw отвечает за XML-форму, внутренний invalid/important —
за смысловую ошибку. Смысловой тег ключа также может сочетаться с raw значения
этого item.

| Смысловое значение получено | Обычный смысловой экспорт точно восстановил XML | Нарушено правило | Явно зарегистрирован important | Представление |
|---|---|---|---|---|
| нет | — | — | — | `!xml/raw` только с полным `$xml` |
| да | нет | нет | — | `!xml/raw` с `$значение` и `$xml` |
| да | нет | да | нет | `!xml/raw`, внутри `$значение: !xml/invalid ...` |
| да | нет | да | да | `!xml/raw`, внутри `$значение: !xml/important ...` |
| да | да | да | нет | `!xml/invalid` |
| да | да | да | да | `!xml/important` |
| да | да | нет | — | обычный YAML без тега |

## Как исторические XML-случаи классифицируются в целевой схеме

Эта таблица является регрессионным перечнем исходных XML-случаев, а не таблицей
преобразования YAML. Старое имя тега не определяет новое автоматически:
`!xml/value` и `!xml/reference` исторически объединяют разные политики. Новый
результат получается только повторным импортом исходного XML.

| Прежний случай | Целевое представление |
|---|---|
| `!xml/present` для фиксированного или вычисляемого XML-результата | raw с явным `$xml`; генератор не переносится |
| `!xml/present`, не совпавший с обычным экспортом | raw с `$значение`, если оно известно, и точечной поправкой `$xml` |
| `!xml/absent` | raw с `$xml: null` |
| `!xml/name` у известного смыслового singleton | поле `Имя: !xml/name ...` внутри обычного смыслового объекта; только у явно зарегистрированного singleton |
| `!xml/name` у полностью непредставимого элемента | raw без `$значение`, полное дерево в `$xml`, включая `#name` |
| `!xml/type`, сохраняющий особую XML-форму `xsi:type` или QName | raw-поправка `$xml` с `_xsi:type` и namespace-атрибутами |
| `!xml/type` с известным смысловым видом, запрещённым только текущим контекстом | invalid на смысловом поле вида, если глобальный обработчик типа точно восстанавливает XML; иначе raw |
| `!xml/language` | invalid на ключе языка, если сам item полностью обратим; иначе raw локализованной коллекции |
| `!xml/order` | invalid на всей смысловой карте; порядок восстанавливается порядком ключей YAML |
| `!xml/duplicate` в именованной коллекции с обратимыми item | первый дубль `!xml/invalid`, последующие `!xml/invalid/N` |
| `!xml/duplicate`, который нельзя выразить отдельными смысловыми item | raw-значение item либо raw всей коллекции |
| `!xml/value`, меняющий форму или лексему XML | raw |
| `!xml/value`, у которого отличается только результат проверки | invalid, если для случая явно не зарегистрирован important |
| `!xml/reference` с UUID или внутренним путём, который нельзя преобразовать в обычную YAML-ссылку либо точно экспортировать обратно | raw значения |
| `!xml/reference` с UUID, который разрешился в обычную YAML-ссылку и точно экспортируется обратно | обычный YAML либо invalid/important по результату проверки |
| `!xml/reference` на недопустимом, но точно обратимом ключе | invalid на ключе; при необратимой XML-форме — raw значения item либо коллекции |
| `!xml/reference`, переводимый в обычный YAML, но неразрешимый или запрещённый | invalid, если для случая явно не зарегистрирован important |

Специализированные классы XML-аномалий не нужны. Узкие теги формы XML допустимы
только после отдельной регистрации, когда они компактнее raw и обычные rules
однозначно восстанавливают остальную структуру.

## Аудит прежних аномалий

До перехода на общий механизм в реестре было описано 57 случаев: 14
`!xml/value`, 18 `!xml/reference`, 10 `!xml/present`, 7 `!xml/absent`, 2
`!xml/name`, 3 `!xml/type` и по одному `!xml/language`, `!xml/order`,
`!xml/duplicate`. Текущий [реестр](../../../.agents/xml-anomalies.md) содержит
общий договор аномалий и отдельно зарегистрированные теги формы XML. Из
перечисленных исторических тегов повторно поддержан только узкий `!xml/name`
для известного singleton; остальные являются синтаксической ошибкой.

При повторном импорте исходного XML они подтверждают следующую классификацию:

| Наблюдаемая группа | Представители | Целевой тег |
|---|---|---|
| фиксированный присутствующий или отсутствующий XML-вариант | пустые `Attributes`, `RowFilter` | raw с явным `$xml`, включая `$xml: null` для отсутствия |
| явное значение по умолчанию вместо требуемого отсутствия | `HeaderHorizontalAlign=Auto` | `$значение: Auto` и явная поправка `$xml`, возвращающая элемент |
| присутствие раньше запускало построение XML из контекста либо создание внешнего файла | `StandardAttributeDescriptions`, пустой `ClientApplicationInterface`, `panelDef` с UUID, `Content.xml` | импорт материализует фактическую XML-поправку или ресурс явно; генераторов raw нет |
| нестандартное внешнее имя известного singleton | встроенное имя формы, включая `ExtendedTooltip` | обычный смысловой объект с полем `Имя: !xml/name ...`; вложенные имена известного семейства выводятся автоматически |
| нестандартный `xsi:type`, QName или точная лексема | `MinMaxValue`, `DcsLocalStringType`, префикс `TypeDescription` | raw минимального XML-значения |
| порядок является частью обратимого смыслового YAML | `I8nText` | invalid на карте; штатный экспорт сохраняет порядок ключей YAML |
| форма коллекции не восстанавливается смысловыми item | отсутствующий стандартный реквизит и неизвестная структура item | raw |
| повтор именованного item, который сам полностью понятен | реквизиты, языки и другие XML-array → YAML-map | invalid на ключе с номером вхождения |
| непреобразимое внутреннее представление ссылки | UUID, `число:UUID`, `UUID.UUID` | raw значения |
| XML-ключ item точно обратим, но не проходит смысловую проверку | пустой ключ роли `UserVisible` | invalid на ключе; повторы получают суффиксы `/N` |
| значение понятно и обратимо, но нарушает длину, диапазон или контекст | строковый FillValue неверной длины и аналогичные ограничения | invalid, пока для класса явно не согласован important |
| известный смысловой подтип запрещён только текущей коллекцией | `PictureField` внутри `ContextMenu.ChildItems` | глобально преобразовать известным обработчиком, поле `Вид` отметить invalid |
| ссылка переводится в обычный YAML, но цель отсутствует, неоднозначна или запрещена | именованные пути `MetadataItemLink` и `MetadataField` | invalid, пока для класса явно не согласован important |
| ссылка или путь не переводится в обычное YAML-представление | часть текущих переносчиков условного оформления и локальных ссылок | raw |

### Случаи, требующие повторной классификации из XML

Перед удалением прежних тегов следующие семейства требуют отдельных
контрольных примеров и явного решения. Простая замена имени тега здесь либо
потеряет XML, либо ошибочно сделает техническое значение смысловым.

| Семейство | Почему общего переименования недостаточно | Безопасное направление |
|---|---|---|
| контекстно создаваемый XML | `StandardAttributeDescriptions: !xml/present` строит канонические элементы из PropertyRule; пустой `ClientApplicationInterface` строит пять `panelDef`; пустой `panelDef` берёт UUID панели | при повторном импорте сохранить фактические элементы и UUID в явном `$xml`; зависимость от генератора и индексов удалить |
| внешний ресурс | `ExchangePlan.Состав: !xml/present` означает существование отдельного `Ext/Content.xml`, а не только XML-узел свойства | обрабатывать теми же тремя тегами на границе resource/topology; PropertyRule одного common-типа не должен имитировать наличие файла |
| переносчик, который одновременно меняет форму | DCS-поле из `!xml/value` получает `xsi:type="dcscor:Field"`, `Undefined` получает QName и namespace, FillValue-маркеры получают разные `xsi:type`/`xsi:nil` | смысл оставить в `$значение`, а отличающиеся QName, namespace и атрибуты — в явном `$xml` |
| один старый тег с разной семантикой | `!xml/value Ложь` у запрещённого FillValue является понятным boolean, а `!xml/value Nil` кодирует другую XML-форму; `!xml/reference` бывает как обычной неразрешимой ссылкой, так и строгим внутренним UUID | для каждого примера проверить обычный `fromYAML → toXML`: точное смысловое значение становится invalid либо явно зарегистрированным important; специальная форма — raw |
| тег на YAML-ключе | пустое имя роли `UserVisible` не является обычным смысловым именем, но значение роли остаётся понятным boolean | использовать `!xml/invalid ""` на ключе; тело item экспортировать обычным правилом, повторы адресовать через `!xml/invalid/N`; raw допустим только на значении item или коллекции |
| локализованный текст | порядок, незарегистрированный язык и повтор могут встретиться одновременно; нынешняя реализация канонизирует порядок и останавливается на трёх, разнесённых, различающихся или незарегистрированных дублях | `I8nText` всегда экспортирует порядок YAML; нарушение порядка — invalid на карте, неизвестный язык — invalid на ключе, первый дубль — `!xml/invalid`, последующие — `!xml/invalid/N`; raw нужен только при непонятной структуре самого `v8:item` |
| нестандартное имя singleton | имя связано с вычисляемой идентичностью, вариантами суффиксов и вложенными элементами формы | зарегистрированный singleton хранит только `Имя: !xml/name ...`; канонический логический адрес и `id` остаются в индексе, вариант суффикса наследуется потомками |
| QName и namespace | старый `!xml/type` иногда хранит только префикс и смысловое имя, а namespace достраивает частное правило | новая raw-форма хранит `_xmlns:<prefix>` и точный `#text`; старый YAML не преобразуется, требуется повторный импорт XML |
| известный подтип в запрещённой коллекции | `PictureField` внутри `ContextMenu.ChildItems` раньше требовал частный `!xml/type` | выбрать обработчик по глобальному реестру известных подтипов, преобразовать весь item в смысловой YAML и поставить `!xml/invalid` только на поле `Вид`; неизвестный глобальному реестру тип остаётся raw |
| сочетание нескольких аномалий | порядок `I8nText` может сочетаться с дублем и незарегистрированным языком | invalid на карте отмечает общий порядок, а `!xml/invalid` и `!xml/invalid/N` на ключах сохраняют повторы; raw поднимается на коллекцию только при необратимой XML-форме item |
| скрытое сохранение вне YAML | `ClientApplicationInterface` сохраняет неизвестные XML-ключи и порядок через внутренние reference-данные; это может замаскировать неполный YAML round-trip | прогнать экспорт без reference/snapshot и материализовать неизвестные части как raw по полному XML-пути до удаления старого механизма |

Фиксированный вариант наподобие `<RowFilter xsi:nil="true"/>` и ранее
контекстно создаваемый вариант используют один явный синтаксис `$xml`.
Зависимость от специальной регистрации, индексов или внешнего ресурса не
скрывается в YAML.

### Матрица повторной классификации `I8nText`

`I8nText` служит обязательным комбинированным примером, потому что один XML-
array превращается в YAML mapping.

| Исходная последовательность | Целевое представление |
|---|---|
| уникальные зарегистрированные языки в каноническом порядке | обычный YAML |
| уникальный незарегистрированный язык, а обычный экспорт сохраняет код и место | `!xml/invalid` на ключе языка |
| два и более полностью понятных повтора, включая разные и разнесённые значения | первый ключ обычный или invalid по собственной ошибке; первый дубль `!xml/invalid`, последующие `!xml/invalid/2`, `/3` и далее |
| неканонический порядок | `!xml/invalid` на всей карте; порядок записан порядком ключей YAML |
| одновременно неканонический порядок, повтор и/или неизвестный язык | invalid на карте плюс необходимые `!xml/invalid` и `!xml/invalid/N` на ключах |
| у одного `v8:item` есть неизвестный атрибут/ребёнок, но его ключ и остальное содержимое распознаны | точечный raw по полному XML-пути внутри item; ключ и известная оболочка остаются смысловыми |
| у `v8:item` отсутствует устойчивый ключ либо тело нельзя разделить на известную оболочку и неизвестный фрагмент | raw одного item с сохранённым адресом, если он устойчив; иначе raw всей последовательности |

Целевой `I8nText`-экспорт всегда сохраняет фактический порядок YAML mapping и
не канонизирует его. Каноничность становится только правилом проверки. Поэтому
при снятии `!xml/invalid` XML-порядок не меняется, но обычная проверка снова
блокирует неканонический YAML. Тег не объясняет причину и не выбирает способ
экспорта: тип `I8nText` определяет преобразователь, а порядок уже содержится в
самом YAML.

Импорт не имеет права выбрасывать исключение только потому, что встретил более
сложную комбинацию, чем существующие `!xml/order` и `!xml/duplicate`. Пока все
item смыслово понятны, комбинация выражается картой и ключевыми тегами. Общим
резервным результатом является raw коллекции только при необратимой XML-форме.

Обязанности здесь разделены без повторения правил. Импортёр до схлопывания карты
сохраняет все повторы как внутренние адресуемые вхождения без публичного тега.
Структурный валидатор назначает им ключевые `!xml/invalid` и
`!xml/invalid/N`, а также определяет каноничность порядка, регистрацию языка и
необходимость уже стоящих смысловых тегов.
Контрольный экспорт определяет только потерю XML-формы: неизвестные атрибуты и
дети одного `v8:item` сначала становятся точечным raw внутри этого item; raw
всей последовательности допустим лишь при отсутствии меньшей устойчивой
границы.

`I8nText` не вводит собственный механизм или собственные имена для дублей.
Проекция XML-последовательности в YAML использует общий построитель именованной
коллекции `projectNamedXmlCollectionForImportWithRuntimeKeys`: он создаёт
внутренние уникальные ключи, сохраняет логический код языка и назначает общий
адресный ряд `!xml/invalid`, `!xml/invalid/2` и далее. Обратное чтение использует
общий `xmlAnnotatedMappingEntries`, поэтому получает исходные логические ключи в
порядке YAML, включая повторы.

Обычный `Record<string, string>` остаётся смысловым представлением значений по
уникальному коду языка, но не считается достаточным источником XML-экспорта при
наличии повторов. Внутренняя модель преобразования дополнительно сохраняет
упорядоченные вхождения «код языка + текст»; именно они являются источником
повторных `v8:item`. Это внутреннее представление не добавляет полей в YAML и не
определяет имена тегов. При отсутствии повторов оно эквивалентно обычному
словарю и не меняет работу существующих потребителей `I8nText.items`.

Классификация остаётся отдельной от проекции: `I8nText` сообщает только
зарегистрирован ли язык и каноничен ли порядок, а общий механизм проверяет
повторы и назначает адреса ключевых тегов. Поэтому сочетание неизвестного языка
с его дублем продолжает одну общую нумерацию, а не создаёт второй, частный ряд
I8nText-аннотаций.

Для двух последних строк старый `!xml/reference` недостаточно точен: он не
различает «ссылку поняли, но она битая» и «внутреннюю запись нельзя представить
обычной YAML-ссылкой». Новый механизм различает их фактической пробой обычного
round-trip.

### Важные случаи, которых нет в текущем реестре

Текущий реестр в основном вырос из конкретных round-trip расхождений. Для
полного импорта дополнительно обязательны:

- синтаксически корректная ссылка на отсутствующий объект, член или значение;
- ссылка, которой соответствует несколько объектов;
- ссылка на существующий объект неправильного вида или не прошедший filter;
- известное `SystemEnumeration`, запрещённое конкретным PropertyRule;
- число, строка или дата, обратимые в XML, но нарушающие диапазон, длину,
  шаблон или контекстное ограничение;
- корректные по отдельности поля, нарушающие межполевой инвариант: `min > max`,
  две взаимоисключающие ветви или отсутствие зависимого поля;
- одинаковые имена объектов, item или вычисленные ключи карты;
- значение, допустимое глобально, но не принадлежащее текущему владельцу;
- неизвестный атрибут, дочерний элемент или вариант `xsi:type` будущей версии;
- успешный преобразователь, который молча удалил item, подставил default или
  нормализовал лексему.

Семантически неверные случаи становятся invalid, если обычный YAML полностью
представим и восстанавливает XML. Отдельный тег для несоответствия filter не
нужен: однозначно разрешённая цель сохраняет связь в индексе, а отсутствующая
или неоднозначная цель её не создаёт. Important выбирается только для заранее
явно согласованного класса данных. Коллизия, потеря формы либо неизвестная
часть делают границу raw. Если проверку пока нельзя выполнить из-за неготового
индекса, решение откладывается: временная недоступность проверки не является
отдельным тегом.

### Ссылочные common-типы

В реестре common-типов нет типа с точным именем `MetadataItem`; соответствующие
правила называются `MetadataItemLink`, `MetadataItemLinks`, `MetadataField` и
`MetadataFields`. Их XML-значение может быть синтаксически допустимым для КСМЛ
и без потерь преобразовываться в обычную YAML-строку, но оставаться неверным в
текущем проекте.

| XML/YAML-значение | Что установила проверка проекта | Представление | Участие цели в индексах |
|---|---|---|---|
| `Catalog.Удаленный` | объект отсутствует | `!xml/invalid Справочник.Удаленный` | нет цели для связи |
| допустимый путь к члену | объект существует, член отсутствует | `!xml/invalid` с обычным YAML-путём | нет цели-члена для связи |
| допустимый путь к объекту | найдено несколько целей | `!xml/invalid` с обычным YAML-путём | нет единственной целевой связи |
| допустимый путь к объекту или члену | цель однозначно найдена, но не проходит ограничение вида, отбор или filter PropertyRule | `!xml/invalid` с обычным YAML-путём | целевая связь сохраняется |
| внутренний UUID или служебный путь | обычное YAML-имя получить нельзя | `!xml/raw` с исходным XML-значением | нет смысловой связи |

Таким образом, соответствие строковой грамматике КСМЛ не означает корректность
значения. Форму проверяет преобразователь. Общий resolver отдельно устанавливает
существование и однозначность цели, а PropertyRule уже после этого проверяет
допустимый вид, отбор, filter и принадлежность владельцу. Второй этап может
поставить invalid, но не отменяет найденную на первом этапе связь.

## Фактические режимы потери в текущем коде

Общий механизм нужен не только для предполагаемых будущих форм. В текущей
реализации уже присутствуют все основные способы молчаливой потери:

| Место | Наблюдаемое поведение |
|---|---|
| XML-парсер | пустота и `xsi:nil` зависят от параметров; порядок хранится в несерилизуемом Symbol |
| XML import plan | неизвестные ключи не посещаются; `ambiguousXMLKey` вычисляется, но не влияет на импорт |
| direct import | исключение оборачивается в `DirectImportConversionError` и останавливает импорт |
| `boolean` | неизвестный scalar, mapping или sequence превращается в `undefined` |
| `string` | из mapping берётся только `#text`, остальные части игнорируются |
| `number` | `Number(...)` меняет запись, допускает `NaN` и теряет точность |
| `SystemEnumeration` | неизвестное XML-значение сохраняется внутри модели, но отсутствует в таблице `ToYAML` и исчезает из YAML |
| `UsePurposes` | неизвестные элементы отфильтровываются |
| `MobileDeviceCommandBarContent` | неподдержанные элементы становятся `undefined` и удаляются через `filter` |
| `AppearanceFields` | неизвестные параметры пропускаются при `skipUnknownParameters: true` |
| `UserVisible` | повтор имени роли записывается в один ключ YAML-карты |
| `AccumulationRegisterAggregateDimensions` | два XML-item одного измерения перезаписывают один ключ object |
| `I8nText` | поддерживается только узкое подмножество повторов, остальные останавливают импорт |
| `ChoiceList` | часть XML-полей item не входит в модель и при экспорте создаётся канонически |
| `MetadataValue`, DCS typed values, `StyleItemValue` | неизвестные полиморфные варианты выбрасывают исключения |
| command interface, home page, client interface | часть неизвестного XML сохраняется только в reference metadata и не видна в переносимом YAML |

Поэтому нужны одновременно реестр владения, перехват исключений и обратное
сравнение. Ни один из этих механизмов по отдельности не покрывает таблицу.

### Статический аудит собранных rules

Аудит текущей core-композиции нашёл 103 `MetadataItemRule` и 1839
`PropertyRule`. Из них 1350 используют `xmlParents`, 52 имеют `fromXML: false`,
37 связаны с `filePath`, а 73 содержат условный `toXML`. Поэтому неизвестные
части нельзя искать только среди прямых детей `Properties`: аудит обязан
проходить полные многоуровневые XML-пути, вложенные rules и внешние ресурсы.

В собранной композиции не найдено повторных YAML-ключей, перекрытий вида
«один XML-путь является предком другого» и повторов alias внутри одного
PropertyRule. Найден один намеренно разделяемый путь: `FormAttribute.Settings`
заявлен семью ветвями `valueType`, `dynamicList`, `chart`, `ganttChart`,
`flowchartContext`, `spreadsheetDocument` и `planner`.

Несколько потенциальных владельцев не означают автоматический raw. Каждая
ветвь запускается изолированно на одном исходном фрагменте:

1. ровно один кандидат получил значение и обычным экспортом точно восстановил
   исходный XML — выбирается он;
2. ни один кандидат не восстановил XML — фрагмент становится raw на ближайшей
   общей границе;
3. два и более кандидата дали точный результат — выбор неоднозначен, поэтому
   фрагмент также становится raw на общей границе.

Побочные эффекты кандидатов — записи в индексах, коллекторах и отложенных
операциях — буферизуются. В основное состояние переносятся только эффекты
единственного выбранного кандидата; эффекты отклонённых проб отбрасываются.
Иначе сама проверка ветвей изменит проект и сделает результат зависимым от
порядка обхода.

Аудит подтвердил ещё две обязательные защиты. Построители именованных карт не
могут доходить до `Object.fromEntries`, пока не обнаружены логические дубли, а
XML-экспортёр не может молча перезаписывать уже занятый путь через `setAtPath`.
Любая выходная коллизия должна быть разрешена адресными ключами до экспорта либо
завершиться блокирующей ошибкой договора.

## Общий алгоритм обнаружения

Одного списка известных аномалий недостаточно. Механизм строится на пяти
независимых страховках.

### 1. Аудит разобранного XML

Параллельно обычному импорту сохраняется структурное дерево с:

- пустыми элементами;
- `xsi:nil`;
- фактическими XML-именами и зарегистрированными псевдонимами;
- атрибутами в исходном порядке;
- повторами;
- порядком дочерних элементов.

Это дерево является источником raw и эталоном сравнения. Обычные
преобразователи могут продолжать получать привычные значения.

### 2. Реестр владения

Для каждого XML-узла и атрибута фиксируется одно из состояний:

- заявлен конкретным PropertyRule;
- заявлен вложенным item-rule;
- заявлен обработчиком внешнего ресурса или индекса;
- сохранён внешним обработчиком по проверенному обратимому договору;
- не заявлен;
- имеет несколько кандидатов-владельцев.

Незаявленная часть получает raw-значение под полным XML-путём. Для нескольких
кандидатов выполняется изолированный отбор по точному обратному экспорту; raw
на их ближайшей общей границе создаётся только если единственного точного
кандидата нет. Коллизия вычисленных ключей именованной коллекции не
считается потерей смысла, если каждый item обратим: первый повторный ключ
получает `!xml/invalid`, последующие — `!xml/invalid/N`. Существующий
`ambiguousXMLKey` должен запускать отбор кандидатов, а не оставаться
неиспользованным признаком плана.

Реестр также обнаруживает:

- одновременно каноническое XML-имя и alias одного свойства;
- один XML-ключ, зарегистрированный для нескольких свойств;
- два XML-источника одного свойства;
- несколько XML-item, вычисливших один YAML-ключ;
- два объекта метаданных с одинаковым логическим адресом.

### 3. Защищённое преобразование

Каждый импорт PropertyRule выполняется в собственной границе ошибок. В raw
переводятся исключения из:

- `importFromXML` и `importFromXMLToYAML`;
- вложенных rules.ts;
- `exportToYAML`;
- преобразования ссылок в обычное YAML-представление;
- вычисления default, если ошибка относится к одному изолируемому свойству.

Для полиморфной коллекции ограничение допустимых подтипов не участвует в выборе
преобразователя. XML-имя или смысловой дискриминатор сначала ищется в глобальном
реестре известных подтипов. Успешно преобразованный известный item передаётся
контекстной проверке коллекции и при запрете получает invalid на поле вида.
Только отсутствие глобального обработчика либо неточный обратный экспорт ведёт
к raw.

Перехват на уровне целого файла слишком крупный: одно плохое свойство не должно
останавливать импорт остальных.

### 4. Контрольный обратный экспорт

Успешный импорт не доказывает отсутствие потери. После завершения вложенных
преобразований и подготовки контекста, необходимого именно для экспорта,
выполняется обычный экспорт без помощи исходного XML. Для каждого
принадлежащего правилу места сравниваются аудит-дерево и полученный XML.

Контроль обнаруживает молчаливые:

- `undefined`;
- `continue` и `filter`;
- подстановку default;
- числовую и строковую нормализацию;
- потерю или перестановку атрибутов и дочерних узлов;
- перезапись ключа карты;
- изменение количества или порядка элементов;
- смену XML-имени, `xsi:type`, QName или namespace-префикса.

При различии сначала локализуется минимальное принадлежащее правилу XML-место.
Неизвестный атрибут или ребёнок сохраняется raw по полному пути, не заменяя
распознанного родителя. Затем проверяется raw одного свойства, одного item с
сохранением его устойчивого ключа и только в последнюю очередь всей коллекции
или объекта. Для коллизии понятных ключей именованной коллекции импортёр заранее
сохраняет все вхождения во внутренней таблице с логическим ключом и номером,
поскольку без неё до этой стадии дошёл бы уже потерянный item. Контрольный
экспорт читает эту таблицу напрямую; публичные `!xml/invalid` и
`!xml/invalid/N` добавляются только после решения структурного валидатора.
Любой выбранный вариант считается корректным только если завершающий экспорт
устраняет различие.

### 5. Общая предметная и контекстная валидация

Только кандидат, уже прошедший обычный обратный экспорт, передаётся тем же
правилам JSON Schema, resolver, проверкам ссылок, уникальности и межполевых
ограничений, которыми проверяется обычный проект. Для ссылок
resolver сначала ищет цель без допустимого типа, отбора и filter конкретного
PropertyRule. Если цель найдена однозначно, она записывается в обычные индексы.
После этого валидатор проверяет, допустима ли найденная цель именно для данного
свойства. Несоответствие этой второй проверки не откатывает индекс, а при
XML-импорте возвращает структурированное решение поставить на обычное
YAML-значение `!xml/invalid`.

Отсутствующая или неоднозначная цель также даёт invalid, но не создаёт целевой
связи. Другие проверки при ошибке либо явно неподдерживаемом варианте значения
действуют так же. Только явно зарегистрированный класс данных заменяет invalid
на `!xml/important`. Эта проверка классифицирует импортируемое значение. После
записи тега обычная валидация снова проверяет его без тега только для
подтверждения необходимости, но не выводит принятую ошибку повторно.

Проверка выполняется после построения всех необходимых индексов. Результат
`pending` или отсутствие ещё строящегося индекса откладывает решение и не
считается ни valid, ни аномалией. Явный результат `unsupportedValue` после
подготовки всех зависимостей создаёт invalid либо явно зарегистрированный
important. Системная ошибка валидатора, сломанный индекс или невозможность
закончить отложенную проверку до окончания импорта дают фатальную ошибку: такие
дефекты нельзя маскировать XML-тегом.

Импортёр не повторяет эти ограничения в common-преобразователях. Его задача —
сохранить смысловое значение, координату источника и устойчивую YAML-границу,
по которой результат валидатора можно применить. Повторы ключей, отсутствующие
свойства и аналогичные коллизии сохраняются до `Object.fromEntries` во
внутренней таблице адресуемых вхождений без публичного смыслового тега.

### Валидатор, управляемый rules.ts

Порядком проверки управляет не цельная TypeBox-схема файла, а общий обход
смыслового YAML по `rules.ts`. Для каждого объекта валидатор сопоставляет
фактические YAML-ключи с PropertyRule и выполняет три действия:

1. проверяет структуру объекта: обязательные, неизвестные и повторные свойства;
2. проверяет локальное значение текущего PropertyRule заранее скомпилированной
   TypeBox-схемой;
3. заходит во вложенный объект или коллекцию по зарегистрированному nested rule.

Схемы отдельных PropertyRule компилируются один раз при сборке среды метаданных
и переиспользуются всеми файлами. Для скаляра такая схема проверяет всё
значение. Для вложенного объекта или коллекции она не повторяет рекурсивную
проверку детей: состав, переход к детям и их локальные схемы выполняет сам
обход. Иначе TypeBox смог бы повторно зайти внутрь дочернего raw. Варианты схем
для отдельных файлов и наборов raw не создаются.

Перед проверкой свойства обход читает таблицу XML-аннотаций. Для raw-контейнера
с `$значение` он передаёт обычному правилу только `$значение` и не проверяет
`$xml`. Если `$значение` отсутствует, свойство считается присутствующим, но его
предметная проверка и спуск внутрь пропускаются. Неизвестный YAML-путь под raw
допускается только когда договор raw и сведения импорта подтверждают
соответствующую XML-границу; обычный неизвестный ключ остаётся структурной
ошибкой. Invalid и important внутри `$значение` проверяются обычным правилом.

Проверки ссылок, уникальности и межполевых ограничений запускаются после
локального обхода. Каждая такая проверка явно объявляет прочитанные пути. Raw с
`$значение` предоставляет им это смысловое значение как обычно. Проверка
пропускается только когда один из её входов закрыт raw без `$значение`;
независимые проверки сохраняются.

### Структурированный результат TypeBox и остальных проверок

Текст публичного `Diagnostic` никогда не разбирается и не участвует в выборе
тега. Установленный TypeBox 1.3.11 уже возвращает для ошибки схемы:

- `keyword` — класс ограничения, например `type`, `required`, `enum`,
  `maxLength`, `propertyNames` или `uniqueItems`;
- `instancePath` — путь до проверяемого YAML-значения;
- `schemaPath` — путь до нарушенного ограничения в скомпилированной схеме;
- `params` — структурированные параметры: предел, ожидаемый тип, допустимые
  значения, имена лишних свойств или номера повторных элементов;
- `message` — только локализованное представление для пользователя.

До превращения в `Diagnostic` эти данные нормализуются в общий внутренний
результат:

```ts
type ValidationTarget =
  | { readonly kind: "path"; readonly path: YamlPath }
  | { readonly kind: "missing"; readonly path: YamlPath }
  | { readonly kind: "occurrence"; readonly path: YamlPath; readonly occurrence: number }

interface ValidationIssue {
  readonly code: string
  readonly kind: "semantic" | "infrastructure"
  readonly target: ValidationTarget
  readonly relatedPaths?: readonly YamlPath[]
  readonly params?: Readonly<Record<string, unknown>>
}
```

Для TypeBox `code` строится из структурного ключевого слова, например
`schema.maxLength`; `instancePath` преобразуется в `target.path`, а `params`
сохраняется без разбора сообщения. `schemaPath` используется как внутренняя
привязка к скомпилированному правилу, но не становится публичной причиной в
YAML: путь может измениться при перестроении схемы.

Отсутствующее обязательное свойство не имеет собственного YAML-узла. Импортёр
создаёт для него внутренний target `missing` по пути ожидаемого ключа, но не
помещает null в смысловую модель. Если контрольный экспорт сохраняет отсутствие,
TypeBox `requiredProperties` подтверждает этот target и валидатор назначает
пустой `!xml/invalid`. Если обычный экспорт создаёт XML-default, доказательство
представления выбирает raw-контейнер с `$xml: null` до смысловой валидации. `propertyNames`,
`additionalProperties` и `uniqueItems` разворачиваются в отдельные адресуемые
ошибки по именам или индексам из `params`.

TypeBox покрывает только структурные и локальные ограничения JSON Schema.
Resolver, ссылки, уникальность проекта и межполевые проверки обязаны возвращать
тот же `ValidationIssue` напрямую со стабильным предметным `code`. Конкретный
валидатор обязан явно выбрать один `target`, на который ставится тег и
показывается ошибка. Остальные прочитанные значения перечисляются в
`relatedPaths`; общий механизм не выбирает главное поле и не поднимает ошибку к
их общему родителю. Target всего объекта допустим только по явному решению
конкретного правила. Форматирование `ValidationIssue` в публичный `Diagnostic`
происходит только после классификации импорта.

Несколько смысловых `ValidationIssue` с точно одинаковым target группируются
под одним `!xml/invalid` либо зарегистрированным `!xml/important`. Причины и их
коды в YAML не перечисляются. Тег остаётся необходимым, пока повторная проверка
находит на этом target хотя бы одну смысловую ошибку; исчезновение части причин
не меняет тег, а исчезновение всех причин создаёт
`xml/anomaly-tag-unnecessary`. Ошибки дочернего, родительского или соседнего
target в эту группу не входят.

Обычная проверка может сохранить нынешний быстрый режим первой ошибки одного
значения. При классификации XML-импорта валидатор rules.ts собирает ошибки всех
независимых свойств, вызывая заранее скомпилированную TypeBox-проверку каждого
из них. Ветви `anyOf`/`oneOf` не должны создавать ложные ошибки: nested rule
сначала выбирает единственную ветвь по дискриминатору, затем проверяется только
она. Поэтому полный результат файла не требует ни повторной компиляции схемы,
ни проверки всего файла для каждой ошибки.

`Type.Refine` допустим для локальной проверки, но в TypeBox 1.3.11 его штатная
ошибка ориентирована на строковое сообщение. Предметный код, несколько путей и
параметры нельзя кодировать в тексте `Refine`: для такого правила используется
отдельная регистрация структурированного валидатора либо скомпилированная
таблица соответствия правила и `ValidationIssue`.

### Почему страховки покрывают неизвестные заранее ошибки

Алгоритм не должен угадывать будущую форму ошибки. Он последовательно отвечает
на пять исчерпывающих вопросов:

1. XML удалось структурно разобрать? Если нет, это явная фатальная ошибка.
2. Для каждого узла найден единственный владелец либо единственный точный
   кандидат? Незаявленный узел сохраняется raw по полному XML-пути; отсутствие
   единственного кандидата поднимает raw на их общую границу.
3. Владелец смог получить смысловое YAML-значение? Если нет, это raw.
4. Нетегированное значение восстановило принадлежащее ему XML-место? Если нет,
   проверяется минимальное смысловое представление с адресными
   `!xml/invalid` и `!xml/invalid/N`;
   если и оно не помогает, это raw.
5. Обратимое значение прошло общую валидацию на окончательных индексах? Ошибка
   даёт invalid, а совпадение той же ошибки с явно зарегистрированным ценным
   классом — important; инфраструктурный сбой — fatal.

Другого исхода у разобранного узла нет. Поэтому новый неизвестный boolean,
лишний атрибут будущей версии, коллизия ключей новой коллекции и молчаливая
нормализация ещё не исследованного common-типа обнаруживаются без добавления
нового класса аномалии.

Локализация выполняется снизу вверх по дереву правил:

1. сначала проверяются независимые вложенные PropertyRule и устойчиво
   адресуемые item;
2. успешные дети закрепляются как обычные, invalid или important, непредставимые — как raw;
3. остаток сравнивается на границе родителя;
4. если родитель нельзя собрать без перекрытия детей, raw поднимается на
   ближайшую общую границу;
5. процесс повторяется до структурного равенства всего файла либо до явной
   фатальной ошибки.

Подъём границы нужен, если XML-array → YAML-object потерял не только уникальность
ключа, но и смысл item либо порядок, необходимый для экспорта. Если все item
понятны и отличаются только повторным логическим ключом, коллекция остаётся
смысловой, а повторы получают `!xml/invalid` и `!xml/invalid/N`.

## Класс аномалии и обычная валидация

Устойчивый публичный класс хранится в самом YAML:

- `!xml/raw` — обычный round-trip меняет XML-форму отмеченного места; понятная
  часть остаётся в `$значение`, а минимальное отличие хранится в `$xml`;
- `!xml/invalid` — смысловое представление и round-trip возможны, но нарушено
  правило; это класс по умолчанию;
- `!xml/important` — та же обратимая смысловая аномалия, но её класс данных
  заранее явно отмечен как ценный.

Обычная валидация различает транспортную и смысловую границы. Общий валидатор
идёт по `rules.ts`; встретив raw, он никогда не проверяет `$xml`. При наличии
`$значение` оно проверяется и индексируется обычным PropertyRule; при отсутствии
`$значение` свойство только считается присутствующим. Invalid и important
внутри `$значение` проверяются как обычные смысловые значения.
Если ожидаемая ошибка остаётся, наружу она не дублируется: тег уже сообщает о
ней. Если ошибки больше нет, валидатор выдаёт
`xml/anomaly-tag-unnecessary`. Независимые нетегированные свойства и известная
смысловая оболочка вокруг точечного raw проверяются как обычно.

Внешнее имя singleton хранится только в `$xml.#name`; отдельное скрытое поле
`Имя` запрещено. Смысловой объект singleton находится в `$значение` и
проверяется обычной схемой.

Для межполевого правила зависимость определяется по прочитанным им границам.
Если хотя бы один вход правила находится под необходимым тегом аномалии, именно
это межполевое сообщение не создаётся. Нетегированные поля не становятся
аномальными вслед за ним и продолжают проходить все независимые проверки:

```yaml
Минимум: !xml/invalid 10
Максимум: 5
```

Правило `Минимум <= Максимум` пропускается, потому что зависит от принятого
`Минимум`. Проверки типа, диапазона и остальных независимых ограничений
`Максимум` выполняются. Поднимать тег на весь объект для этого не требуется.

Необходимый `!xml/raw`, `!xml/invalid` или `!xml/important` не создаёт сообщения
валидации. Invalid/important проверяется последовательно. Пока ни одна
применимая проверка не нашла ошибку, граница остаётся ожидающей проверки и
может быть передана следующему этапу, например от проверки файла к проверке
связей. Первая найденная смысловая ошибка подтверждает тег, не публикуется и
закрывает эту границу от всех последующих смысловых и межфайловых проверок.
Построение индексов, поиск, переименование и экспорт при этом не прекращаются.

Если после последней применимой проверки ошибка так и не найдена, валидация
сообщает только об избыточном теге. Перечень причин `cause` в YAML и состоянии
проекта не хранится: публичного класса, минимальной границы и внутреннего
состояния «ожидает проверки» либо «подтверждён» достаточно для round-trip.
Для именованных повторов отсутствие номера и номер в `!xml/invalid/N` являются
адресами вхождений, а не причинами. Если тот же класс данных позднее будет
отдельно зарегистрирован important, адресный суффикс сохраняется при замене
тега на `!xml/important/N`.

Проверки грамматики тега, допустимости его положения и возможности выполнить
экспорт относятся к договору формата YAML, а не к повторной проверке пришедшей
из XML ошибки. Нарушение самого договора тега блокирует экспорт; содержимое
корректно отмеченной границы обычных сообщений не создаёт.

## Полная матрица форматных сбоев

Матрица нужна для тестов и анализа покрытия. Она не является закрытым списком:
реестр владения и обратное сравнение должны обнаружить новые формы без
изменения таблицы.

### Файл и XML-парсер

| Случай | Результат |
|---|---|
| файл не читается | фатальная ошибка ввода-вывода |
| XML синтаксически неверен | фатальная `xml/parse` |
| небезопасное имя вроде `__proto__` | фатальная ошибка безопасности |
| неизвестный, но корректный корневой элемент | фатальная ошибка неизвестного XML-root; raw всего объекта запрещён |
| лишний корневой атрибут | raw-поправка корня под одиночным ключом `@`; атрибут находится в `$xml` как `_имя` |
| неизвестная декларация namespace | `_xmlns:...` внутри `$xml` ключа `@` либо пути соответствующего элемента |
| processing instruction | raw-узел `?target`, если обычный экспорт его не восстановил |
| комментарий, CDATA-форма, entity-форма, кавычки | вне структурного договора |
| только отличие BOM или кодировки | вне структурного договора |

### Выбор PropertyRule и XML-пути

| Случай | Результат |
|---|---|
| XML-ключ неизвестен | raw-значение под полным XML-путём, например `Properties\Future` |
| неизвестный узел находится в дополнительном XML-документе | raw-значение под путём с кратким селектором документа, например `@Form\Future`; `Ext/` и `.xml` не записываются |
| неизвестный атрибут известной XML-обёртки | raw-поправка на пути самой обёртки, например `Properties`, с `_имя` внутри `$xml` |
| неизвестный промежуточный родитель | raw-значение на пути этой обёртки, например `Properties\FutureGroup` |
| узел находится не под тем `xmlParents` | raw ближайшего общего родителя |
| одновременно canonical и alias одного известного singleton | обычное первое значение; alias-дубль получает адресный invalid на ключе, а неканоническое внешнее имя — `$xml.#name`; полностью неизвестный item использует полное `$xml` с `#name` |
| один ключ сопоставлен нескольким PropertyRule | изолированный отбор кандидатов; при нуле или нескольких точных результатах — raw общей границы |
| свойство пришло из двух XML-источников | raw общей границы либо фатальная ошибка при перекрытии |
| PropertyRule не имеет YAML-свойства | проверенный переносимый индекс/ресурс либо raw по полному XML-пути владельца |
| свойство помечено `forReferenceOnly` | внешний обработчик допустим только при проверенном переносимом представлении; зависимость лишь от reference snapshot требует raw по полному XML-пути |

### Присутствие, пустота и default

| Случай | Результат raw |
|---|---|
| присутствует фиксированный или ранее вычисляемый вариант | явная поправка `$xml` |
| узел отсутствовал, обычный экспорт его добавляет | `$xml: null` |
| узел присутствовал, обычный экспорт его удаляет | `$значение` и добавляющий элемент `$xml` |
| пустой узел стал отсутствующим | `$xml: {}` |
| отсутствующий узел стал пустым | `$xml: null` |
| явный default свернулся в неявный | `$значение` и поправка точного текста/узла |
| неявный default материализовался в XML | `$xml: null` |
| `xsi:nil` потерялся или превратился в пустой элемент | mapping с `_xsi:nil` |
| вычисляемый default зависит от ошибочного контекста | raw минимального свойства либо общей зависимой границы |

Если коллекционный тип зарегистрировал `completeItemNames`, эти системные item
дополняют существующую YAML-коллекцию. При отсутствующем компактном
YAML-свойстве коллекция создаётся только по явному
`evaluateWhenYAMLMissing: true` в PropertyRule. Так Rules отличает обязательную
системную коллекцию от действительно отсутствующей, не сохраняя XML-состояние
каждого свойства в снимке. Поэтому default-only `<StandardAttributes>`
перечисления восстанавливается Rules и не становится raw, а отсутствующий
`StandardAttributes` справочника не материализуется. Raw требуется только для
фактического отклонения состава, значений или порядка от договора Rules.

`HeaderHorizontalAlign=Auto` в исследованном правиле относится к raw с
`$значение: Auto` и явной XML-поправкой: обычный смысловой экспорт удаляет
значение по умолчанию и не восстанавливает XML-элемент.
Invalid здесь был бы неверен, потому что смысловой тег не имеет права менять
форму или присутствие XML. Для другого explicit default invalid допустим только
если снятие тега перед обычным экспортом всё равно точно сохраняет явный узел.

### Форма значения

| Случай | Как обнаруживается |
|---|---|
| ожидался scalar, пришёл mapping | защищённое преобразование или обратное сравнение |
| ожидался scalar, пришёл sequence | защищённое преобразование или обратное сравнение |
| ожидался object, пришёл scalar | защищённое преобразование или обратное сравнение |
| ожидалась sequence, пришёл одиночный object | допустимо только если обычный экспорт восстанавливает исходную форму |
| лишний атрибут | реестр владения или обратное сравнение |
| лишний дочерний элемент | реестр владения или обратное сравнение |
| текст и дочерний элемент одновременно | обратное сравнение |
| неизвестный `xsi:type` | защищённое преобразование или обратное сравнение |
| отсутствует обязательный `xsi:type` | обратное сравнение |
| одновременно несколько полиморфных ветвей | реестр владения или защищённое преобразование |
| обязательная часть выбранной ветви отсутствует | raw, если экспорт добавляет её; иначе invalid либо явно зарегистрированный important |
| неизвестный вариант вложенного rules.ts | защищённое преобразование |

### Скалярный текст

| Случай | Представитель |
|---|---|
| неизвестное значение закрытого словаря | boolean, SystemEnumeration |
| другой регистр | `TRUE` вместо `true` |
| ведущие или хвостовые пробелы | ` true `, ` 1 ` |
| пустая строка или только пробелы | boolean, number, dateTime |
| лексическая нормализация | `01`, `+1`, `1.0`, `1e3`, `-0` |
| потеря точности | целое за безопасным диапазоном JavaScript |
| нечисловое число | `abc`, `1,5`, `INF` |
| `NaN` или бесконечность | raw при потере лексемы, иначе invalid |
| неканоничная дата или часовой пояс | dateTime |
| неизвестный QName или префикс | XDTOTypeName, TypeDescription |
| строка ошибочно приведена к boolean/number/null | StringOrNumber и вложенные typed values |
| значение больше ограничения при точном round-trip | invalid после контекстной проверки |

### `SystemEnumeration`

Для каждого `typeSE` не требуется собственный механизм. Общий аудит покрывает:

| Случай | Результат |
|---|---|
| XML-значения нет, но экспорт создаёт default | raw с `$xml: null` |
| XML явно содержит default, который обычный YAML точно экспортирует | обычный YAML, если явное присутствие разрешено; invalid/important, только если присутствие нарушает правило |
| XML явно содержит default, который смысловой YAML не может точно экспортировать | `$значение` с поправкой точного `$xml` либо полное `$xml` |
| XML-значение отсутствует вопреки обязательному | invalid, только если обычный экспорт тоже сохраняет отсутствие; иначе raw |
| значение отсутствует в таблице `typeSE` | raw scalar |
| значение известно таблице, но запрещено конкретным PropertyRule | invalid scalar |
| XML-значение является поддержанным системным alias | обычный YAML, если обратный XML совпадает; иначе raw |
| другое написание, похожее на alias | raw, автоматическое исправление запрещено |
| объект с `#text` и лишним атрибутом | raw mapping |
| mapping без `#text` | raw mapping |
| два понятных элемента singleton-свойства | первое обычное значение; дубль — отдельный ключ `!xml/invalid` |
| повторный элемент содержит неизвестное значение или форму | `!xml/invalid` адресует ключ дубля, raw сохраняет его значение |
| `xsi:type` отличается | raw mapping, если обычный смысловой экспорт не воспроизводит отличие; известный и точно экспортируемый подтип проходит обычную проверку и становится normal/invalid/important по её результату |

Например, `Switch`/`Switcher` не считается свободным alias. Он применяется
только в зарегистрированном направлении для конкретного `typeSE`; любое другое
обозначение сохраняется raw.

### Составные и полиморфные значения

| Случай | Представители |
|---|---|
| неизвестная ветвь `xsi:type` | MetadataValue, DcsMetadataTypedValue, StyleItemValue |
| знакомый тип с неизвестным содержимым | TypeDescription, Font, Border, Picture |
| число или boolean внутри объекта нормализовались | Font, Border, TypeLink, ClientApplicationInterface |
| неизвестный namespace-префикс | TypeDescription, XDTOTypeName |
| неизвестная ссылка внутри известного объекта | invalid, если обычное представление обратимо; иначе raw всего значения |
| две взаимоисключающие ветви одновременно | MetadataValue и DCS typed values |
| обработчик выбросил исключение | raw всего составного свойства |
| обработчик понял часть и проигнорировал остаток | raw всего свойства либо независимого вложенного PropertyRule |

Если неизвестная часть не имеет собственного PropertyRule, raw должен владеть
всем составным значением. Иначе raw одного дочернего фрагмента будет
перекрываться с обычным экспортом соседних частей объекта.

### Последовательности и карты

| Случай | Результат |
|---|---|
| item отфильтрован через `continue`/`filter` до смыслового преобразования | повторить преобразование известным глобальным правилом: при точном обычном экспорте — invalid/important по проверке, иначе raw item или коллекция |
| item вызывает исключение | raw item при устойчивой адресации, иначе коллекция |
| неизвестное XML-имя item | raw item с `#name` либо коллекция |
| известный подтип запрещён только текущей коллекцией | преобразовать глобальным обработчиком, поле вида отметить invalid |
| пустая обёртка исчезла | raw `{}` |
| отсутствующая обёртка появилась | raw `null` |
| порядок полностью выражен смысловым YAML и штатный экспорт его сохраняет | invalid на общей границе коллекции |
| порядок не выражен смысловым YAML либо штатный экспорт его меняет | raw коллекция с `#order` |
| два понятных XML-item получили один YAML-ключ | `!xml/invalid` на ключе второго item |
| item не имеет ключа | raw всей коллекции либо item при сохранённой позиции |
| ключ понятен и обратим, но не проходит проверку | invalid на ключе |
| значение item невозможно представить обычным YAML | raw значения item либо всей коллекции |
| три и более item получили один ключ | первый дубль `!xml/invalid`, следующие `!xml/invalid/2`, `/3` и далее |
| последний item мог бы перезаписать предыдущий | обнаружить до записи object и сохранить все через ключи с тегами |
| XML-array превратился в YAML-object | контроль коллизий обязателен до `Object.fromEntries` и аналогов |
| повтор допустим моделью, но обычный YAML-map его не выражает | ключи с тегами, если каждый item обратим; иначе raw коллекция |
| wrapper/item имеет лишний атрибут | raw соответствующей устойчивой границы |

`I8nText`, `UserVisible`, `StandardAttributeDescriptions`,
`PredefinedItemCollection`, `AppearanceFields` и
`AccumulationRegisterAggregateDimensions` являются обязательными тестовыми
представителями коллизии XML-array → YAML-map.

### Ссылки и контекстная проверка

| Случай | Результат |
|---|---|
| UUID или внутренний путь не переводится в обычный YAML | raw |
| ссылка имеет обычное YAML-представление, но не разрешилась | invalid без целевой связи в индексе |
| ссылка разрешилась неоднозначно | invalid без единственной целевой связи в индексе |
| ссылка однозначно указывает на объект неправильного вида | invalid; найденная цель остаётся в индексах |
| значение допустимо глобально, но запрещено отбором или filter данного свойства | invalid; найденная цель остаётся в индексах |
| resolver ещё не построил необходимый индекс | отложить решение, не создавать тег преждевременно |
| два объекта имеют одинаковое имя/адрес | первый обычный объект остаётся каноническим, повторы получают invalid; raw используется, если один из объектов иначе был бы потерян |
| ручной YAML без тега аномалии содержит битую ссылку | обычная блокирующая ошибка проверки |

Все три тега создаются только при XML-импорте. Они не должны автоматически
появляться вокруг ошибочного YAML, записанного ИИ-агентом после импорта.
Технически вручную воспроизведённый корректный тег неотличим в файле, но его
создание находится вне поддерживаемого сценария.

`$xml` не участвует в предметных индексах, resolver, поиске и переименовании.
`$значение`, напротив, участвует в них как обычное значение. Если его нет,
сохраняются только распознанные ключ, вид и адрес именованного item, а зависимые
предметные проверки пропускаются.

Invalid и important, напротив, сохраняют смысловое представление. Участие
ссылки в индексах определяется не тегом, а результатом resolver: однозначно
найденная цель участвует в индексах даже при последующем несоответствии типу,
отбору или filter свойства; отсутствующая или неоднозначная цель не создаёт
целевой связи. Это состояние не кодируется дополнительным YAML-тегом. Для
повторов именованной коллекции действует специальное правило:

- первый нетегированный элемент остаётся единственным каноническим элементом
  предметного индекса и resolver;
- помеченные повторы не добавляются в уникальный индекс, не делают обычную
  ссылку неоднозначной и не вызывают зависимых ошибок у соседних элементов;
- полный перечень коллекции содержит все вхождения с одним логическим именем и
  разными номерами, поэтому экспорт, поиск и переименование видят их все.

Операции над полным перечнем сохраняют тег. Обычная валидация после них
раскрывает смысловой тег для проверки его необходимости, но не добавляет
помеченный повтор в уникальный предметный индекс.

Если одна контекстная ошибка зависит от нескольких свойств, конкретный
валидатор обязан объявить один `target` и перечислить остальные входы в
`relatedPaths`. Например, проверка `Минимум <= Максимум` может явно назначить
ошибочным `Минимум`, если её сообщение и исправление сформулированы относительно
него. Общий runtime не выбирает случайное поле и не поднимает ошибку к общему
родителю. Весь объект становится target только по явному договору самого
межполевого правила.

| Случай | Граница |

## Выбор минимальной границы аномалии

Импортёр сначала пытается сохранить каждую ошибку отдельно на самой глубокой
устойчивой границе. Например, понятное недопустимое поле и независимо
непредставимое соседнее поле остаются двумя значениями:

```yaml
Свойство:
  Режим: !xml/invalid Авто
  Параметр: !xml/raw
    $xml:
      _future: x
      "#text": "42"
```

Весь объект `Свойство` не становится raw, если оба дочерних значения можно
однозначно вернуть на свои XML-места. Аналогично invalid на ключе item может
сочетаться с raw его значения: это две разные границы — адрес item и его
содержимое.

Для именованного элемента raw не означает, что элемента нет. Например, если у
реквизита `Код` распознаны имя, вид и тип, а неизвестен только вложенный
`Properties\Future`, структурный индекс всё равно содержит реквизит `Код`.
Непрозрачным для проверок остаётся только значение `Properties\Future`. Если
raw приходится поднять до всего значения item, индекс по-прежнему хранит сам
ключ и вид именованного item, но не строит факты из его неизвестного
содержимого.

| Ситуация | Граница |
|---|---|
| ошибка только в известном scalar | property |
| ошибка во вложенной части с собственным PropertyRule | вложенный property |
| неизвестная часть составного объекта | весь составной property |
| item имеет устойчивую уникальную идентичность | item |
| item адресуется только позицией, которую преобразование меняет | collection |
| понятные item сворачиваются в один YAML-ключ | ключ первого дубля (`!xml/invalid`) и ключи последующих (`!xml/invalid/N`) |
| порядок полностью выражен смысловым YAML и экспорт его сохраняет | invalid общей collection-границы |
| при сворачивании item теряется смысл или порядок не представлен в YAML | collection raw |
| у известного singleton отличается только внешнее XML-имя | raw-контейнер с обычным `$значение` и `$xml.#name` |
| XML-узел не принадлежит PropertyRule | raw-значение под его полным XML-путём у ближайшего YAML-владельца |
| несколько свойств претендуют на один XML-узел | единственный кандидат выбирается точным обратным экспортом; иначе ближайший общий object/collection становится raw |
| два объекта имеют один логический адрес | родительская metadata collection |
| неизвестен корень или файл | object/file/topology |

Границы raw не могут перекрываться. Если дочерний property сохранён raw, raw
родителя не должен включать тот же XML-фрагмент. Если неперекрывающуюся
границу определить невозможно, импорт останавливается вместо создания
неоднозначного YAML.

Подъём выполняется по одному уровню с повторным контрольным экспортом. Первый
родитель, который целиком и точно восстанавливает спорный XML-фрагмент,
становится raw-границей; независимые теги его соседей сохраняются. Понятные
дочерние данные и их смысловые теги остаются внутри `$значение`; пересекающиеся
XML-поправки объединяются в один `$xml` родителя.

Invalid или important ставится на минимальное смысловое YAML-значение, к
которому полностью относится ошибка импорта. Для ошибки одного элемента это
scalar или item, для межполевого инварианта — общий object. Для повтора
именованной коллекции это ключ конкретного item с номером вхождения, а не вся
коллекция. По умолчанию выбирается invalid; important выбирается только при
совпадении с явной регистрацией. Если нужная граница не представима в YAML или
её экспорт с тегом не сохраняет XML, выбирается raw.

Invalid или important могут стоять внутри `$значение` raw-контейнера: первый
слой описывает смысловую ошибку, внешний raw — только XML-поправку. Внутри
`$xml` смысловые теги запрещены. Raw, invalid и important соседних независимых
границ также допустимы.

## Проверка raw

Синтаксическая проверка `!xml/raw` выполняется независимо от предметного типа:

- тег расположен у известного XML-backed значения либо у служебного ключа
  полного XML-пути;
- payload является mapping ровно с обязательным `$xml` и необязательным
  `$значение`;
- пустой raw, неизвестные `$...`-поля и генератор без явного `$xml` запрещены;
- raw расположен только на YAML-значении, но не на ключе;
- если raw относится к item именованной коллекции, его смысловой ключ устойчиво
  адресует item либо raw поднят на значение всей коллекции;
- `$значение`, если оно есть, допускается обычным PropertyRule либо содержит
  обоснованный invalid/important;
- `$xml` является null, parser-shaped mapping либо sequence;
- ключи mapping являются строками;
- `_`-атрибуты имеют строковые значения;
- последовательность `_`-атрибутов в mapping является их XML-порядком и не
  сортируется при YAML → XML;
- `#name` является допустимым XML-именем;
- `#name` в `$xml` является допустимым XML-именем и отличается от обычного
  результата PropertyRule;
- `#text` является строкой;
- обычный `#order` ссылается ровно на дочерние элементы raw;
- иерархия ключа XML-пути содержит только XML-узлы, необязательный начальный
  селектор дополнительного документа имеет вид `@ИмяДокумента`;
- одиночный ключ `@` адресует только корень основного XML-документа;
- ключ XML-пути не содержит пустых сегментов, начальной/конечной `\`, `.` или
  `..`;
- `#order` внутри `$xml` ссылается ровно на объединение raw-детей и детей,
  созданных обычными PropertyRule для указанного XML-родителя; отдельный
  сегмент пути `#order` запрещён;
- если raw исправляет общий порядок известных и неизвестных атрибутов, `$xml`
  содержит их полный набор, а порядок `_...`-ключей совпадает с XML;
- служебные ключи не повторяются и находятся на допустимом уровне;
- raw не создаёт XML-декларацию или `DOCTYPE` внутри свойства;
- вставка не пересекается с обычным выводом соседнего PropertyRule;
- контрольный экспорт raw структурно равен сохранённому аудит-дереву.

Ошибочный raw блокирует экспорт как нарушение договора самого тега. Необходимый
raw не создаёт сообщение о самой принятой XML-ошибке. `$значение` проверяется
обычно; предметная проверка границы исключается только при его отсутствии.
Raw, который можно без потерь заменить обычным YAML без `$xml`, получает
отдельную ошибку лишнего тега.

## Проверка смысловых тегов

При XML-импорте кандидат в `!xml/invalid` или `!xml/important` проверяется через
обычный common-тип:

- расположение поддерживается PropertyRule или вложенным item-rule;
- `fromYAML` и `toXML` завершаются успешно;
- контрольный экспорт структурно совпадает с XML, из которого появился тег;
- предметная проверка возвращает ошибку или `unsupportedValue` либо тег решает
  обратимую коллизию представления, например повтор именованного ключа;
- ошибка не вызвана только неготовностью индекса или resolver;
- тег не пересекается с raw родителя или ребёнка.

Для important дополнительно обязательна явная регистрация этого класса данных.
Без неё импортёр выбирает invalid. В текущем механизме остальные проверки и
поведение этих двух тегов совпадают. Если результат проверки требует invalid,
но для той же границы существует important-регистрация, импортёр записывает
только important.

Ручной `!xml/important` вне зарегистрированного места создаёт блокирующую
ошибку `xml/important-not-registered`. Внутренняя ошибка значения при этом не
выводится: сообщение относится только к неправильно выбранному тегу и предлагает
заменить его на `!xml/invalid`. Эта проверка выполняется раньше проверки
избыточности тега.

Обратная подмена также запрещена. Если регистрация требует important, запись с
`!xml/invalid` создаёт блокирующую ошибку `xml/important-required` и предлагает
заменить тег на important, сохранив payload и суффикс адреса без изменений.

Для ключей именованных коллекций дополнительно проверяется грамматика тега:
`!xml/invalid` или `!xml/important` обозначает первое аномальное вхождение, а
суффикс `/N`, где `N >= 2`, — аномальное вхождение `N`. Для дублей исходный
ключ не входит в эту нумерацию: первый дубль идёт без суффикса, второй получает
`/2`. Номер относится к тому же логическому ключу, не повторяется и
соответствует порядку записей mapping. Последовательность адресов считается
общей для invalid и important: смена смыслового класса не начинает нумерацию
заново.

Нумерация должна быть непрерывной. Запрещены `/1`, `/0`, отрицательные и
нецелые суффиксы, первый адрес `/2`, пропуск номера, повтор номера и порядок,
не совпадающий с порядком YAML-записей. Любое такое нарушение создаёт одну
блокирующую ошибку `xml/anomaly-address-invalid` на неверном теге. Сообщение
указывает логический ключ, фактический тег и ожидаемый следующий тег.

Экспорт при этой ошибке не запускается: автоматически перенумеровывать теги или
угадывать XML-вхождение запрещено. Предметные и контекстные ошибки содержимого
по-прежнему не выводятся, потому что ошибка относится к договору самого тега.

После импорта обычная валидация последовательно запускает применимые проверки
под invalid/important только до первой смысловой ошибки. Найденная ошибка
подтверждает тег, наружу не выводится, а остальные проверки этой границы не
запускаются. Если локальная проверка файла не нашла ошибку, но для свойства
существует проверка по общему индексу, граница передаётся ей как ожидающая
проверки. Лишним тег признаётся только после успешного завершения последней
применимой проверки. Под raw без `$значение` предметные проверки не запускаются.
Грамматику тега и возможность штатного экспорта проверяет слой чтения и записи
YAML независимо от результата смысловых проверок.

При XML-импорте решение валидатора уже является доказательством ошибки.
Применённый в третьем проходе invalid/important сразу считается подтверждённым:
повторная локальная или межфайловая проверка этой границы запрещена. Это не
относится к тегу, который уже находился в открытом пользователем YAML и ещё не
имеет подтверждения текущего запуска валидации.

Невосстановимый invalid или important блокирует экспорт как нарушение договора тега:
такая запись должна была быть raw либо была испорчена ручным изменением.

## Проверка необходимости тега

Для каждого raw, invalid и important выполняется изолированная проба без
разрешения аномалии:

1. raw сначала экспортируется в нормализованный XML, затем этот XML повторно
   импортируется с отключённым fallback аномалий;
2. у invalid и important временно снимается тег;
3. проверки выполняются по порядку до первой ошибки; если ошибки нет, граница
   должна пройти все применимые структурные, предметные и контекстные проверки
   и точно восстановить XML;
4. отдельно проверяется, не нужен ли тег как адрес вхождения, например
   `!xml/invalid` для первого дубля одинакового ключа.

Если все проверки успешны и адресный тег не нужен, создаётся одна блокирующая
ошибка `xml/anomaly-tag-unnecessary` на самом теге. Внутренние пробные сообщения
не выводятся. Первая смысловая ошибка подтверждает тег и прекращает пробу этой
границы; последующие проверки не запускаются.

Например, свежий корректный импорт создаёт:

```yaml
Использовать: Истина
```

Запись `Использовать: !xml/important Истина` ошибочна сразу. А ссылка
`!xml/invalid Справочник.Удаленный` становится ошибкой лишнего тега, если
справочник позднее появился и ссылка теперь полностью корректна.

## Тестовая стратегия

### Инвариантные тесты среды

1. Каждый разобранный XML-узел отмечен как normal, raw, invalid, important, external или fatal.
2. После изолированного отбора один узел имеет не более одного зафиксированного
   владельца; непринятые кандидаты не оставляют побочных эффектов.
3. Raw-границы не перекрываются.
4. Обычная граница проходит структурный XML → YAML → XML.
5. Raw-граница проходит YAML raw → XML → YAML raw.
6. Invalid- и important-границы обычным экспортом восстанавливают исходный XML.
7. Удаление тега raw возвращает ошибку преобразования или round-trip.
8. Удаление только тега invalid или important возвращает блокирующую ошибку проверки.
9. Необходимые raw-, invalid- и important-границы не выдают внутренних ошибок;
   избыточная граница выдаёт только `xml/anomaly-tag-unnecessary` на теге.
10. Независимые нетегированные соседи продолжают проверяться.
11. Поиск видит смысловой payload всех invalid- и important-item, включая
    повторы ключей. Переименование ссылки видит только однозначно разрешённую
    цель; отсутствующая или неоднозначная цель не создаёт фиктивную связь.
12. `!xml/invalid`, `!xml/invalid/2`, `/3` и далее сохраняют число и
    порядок XML-item без отдельного `#order`.
13. `RowFilter` сохраняет явный `$xml` с `_xsi:nil: "true"`; специальный
    генератор для него отсутствует.
14. Любое отличие формы `RowFilter` выражается минимальной XML-поправкой без
    дублирования понятного `$значение`.
15. `StandardAttributeDescriptions` сохраняет фактические XML-элементы явно в
    `$xml`, а не вычисляет их повторно из изменяемых индексов.
16. `ClientApplicationInterface`, `panelDef` и другие прежние контекстные
    случаи также не зависят от raw-генератора или reference snapshot.
17. Пустой `!xml/raw`, отсутствующий `$xml` и попытка зарегистрировать
    генератор блокируются как нарушение публичного YAML-договора.
18. Пустая роль `UserVisible` импортируется как `!xml/invalid ""` на ключе и
    восстанавливает `<xr:Value name="">`, не скрывая соседние обычные роли.
19. Два одинаковых пустых имени роли не перезаписываются: первое получает
    `!xml/invalid ""`, следующее — `!xml/invalid/2 ""`.
20. Неканонический порядок `I8nText` сохраняется порядком YAML-ключей и
    отмечается `!xml/invalid` на карте; снятие тега возвращает ошибку проверки,
    но не меняет прямой XML-экспорт.
21. Три, разнесённые и различающиеся дубля языка сохраняются ключами
    `!xml/invalid`, `!xml/invalid/2` и `!xml/invalid/3` в исходном порядке.
22. Порядок, незарегистрированный язык и повторы одновременно проходят
    YAML → XML → YAML без потери; raw используется только при непредставимой
    структуре `v8:item`.
23. Invalid и important одинаково сохраняют значение, экспортируются и
    исключают внутренние ошибки обычной валидации.
24. Important создаётся только для явно зарегистрированного класса данных.
25. При отсутствии important-регистрации любая обратимая смысловая аномалия
    получает invalid.
26. Обычное корректное boolean-значение под invalid или important даёт
    `xml/anomaly-tag-unnecessary`. То же `$значение` внутри raw допустимо, пока
    `$xml` действительно меняет обычный экспорт; пустая или избыточная поправка
    даёт ошибку лишнего raw.
27. Ссылка под invalid после появления однозначной допустимой цели даёт ошибку
    лишнего тега, а прежняя ошибка ссылки не выводится.
28. `!xml/invalid` на ключе дубля не считается лишним, пока без него два item
    невозможно представить раздельными ключами YAML.
29. Raw не считается лишним, если обычный импорт понимает смысл, но его экспорт
    меняет хотя бы одну часть нормализованного XML.
30. Ручной important на незарегистрированной битой ссылке даёт только
    `xml/important-not-registered`; та же ссылка под invalid принимается без
    внутренних сообщений.
31. Если некоторый класс данных отдельно зарегистрирован как important, invalid
    на той же границе даёт только `xml/important-required`; замена тега не
    изменяет payload или положение элемента.
32. Если одна аномалия одновременно удовлетворяет invalid и зарегистрированному
    important, импорт выбирает только important; два смысловых тега не
    вкладываются и не дублируются.
33. При обычном первом реквизите `Код` и любом числе помеченных дублей ссылка на
    `Код` разрешается к первому реквизиту и не становится неоднозначной.
34. Поиск, переименование и экспорт при этом видят первый реквизит и все его
    помеченные дубли; уникальный предметный индекс содержит только первый.
35. Две независимые аномалии в соседних дочерних полях получают две минимальные
    границы; родитель остаётся обычным YAML-объектом.
36. Если дочерние границы перекрываются или не имеют устойчивых адресов, raw
    поднимается только до первого родителя, контрольный экспорт которого точно
    восстанавливает спорный XML-фрагмент.
37. Поднятый raw не поглощает независимые смысловые данные и теги: они остаются
    внутри `$значение`; `$xml` содержит только транспортную поправку без тегов.
38. `!xml/invalid/2 Код` без предшествующего `!xml/invalid Код` создаёт только
    `xml/anomaly-address-invalid` и блокирует экспорт.
39. Пропуск, повтор или перестановка номера не исправляются автоматически и не
    меняют порядок YAML-записей.
40. При неверном адресе тега внутренние ошибки отмеченного item не выводятся.
41. Ручная замена одного обратимого недопустимого payload под invalid другим
    обратимым недопустимым payload сохраняет тег и экспортирует новое значение.
42. Ручная замена payload на корректное значение создаёт только
    `xml/anomaly-tag-unnecessary`.
43. Ручная замена payload на значение, которое common-тип не может штатно
    экспортировать, блокирует экспорт как нарушение договора semantic-тега.
44. Аудит XML различает одинаковые наборы атрибутов в разном порядке.
45. Порядок `_`-ключей внутри `$xml` точно воспроизводится в порядке XML-атрибутов
    после YAML → XML → YAML.
46. Если обычный common-тип переставляет атрибуты относительно исходного XML,
    контрольный экспорт обнаруживает расхождение и выбирает минимальный raw.
47. Неизвестный `Properties\Future` импортируется как ключ XML-пути с raw-значением,
    а не как обычное YAML-свойство `Properties`.
48. Путь любой глубины, включая `Properties\Appearance\Future`, точно
    восстанавливает промежуточные XML-обёртки.
49. `#order` внутри raw пути `Properties` объединяет детей обычных PropertyRule
    и raw-ключей XML-пути и точно восстанавливает их порядок. Отдельный путь
    `Properties\#order` запрещён. Форматирующий пробельный текст между детьми
    не входит в `#order` и не создаёт raw.
49а. `<Properties>\n  <Name>A</Name>\n</Properties>` и
    `<Properties><Name>A</Name></Properties>` имеют одинаковое нормализованное
    дерево. `<FillValue>         </FillValue>` сохраняет девять пробелов как
    значимое скалярное значение.
49б. Имя повторного узла `Item` не является достаточным признаком служебного
    элемента коллекции. Предварительный raw для `Item` удаляется только тогда,
    когда наложение этой XML-поправки на обычный экспорт ничего не меняет.
    Неизвестный `<Item>` с дополнительным атрибутом, текстом или дочерним узлом
    сохраняется как raw.
50. `Properties` с raw-значением хранит неизвестные атрибуты этого XML-узла
    внутри `$xml` как `_имя`; отдельный ключ `#attributes` не используется.
    При значимом общем порядке `$xml` содержит полный упорядоченный набор
    известных и неизвестных атрибутов.
50а. Неизвестный `@Form\Future` восстанавливается в `Ext/Form.xml`, а
    `@AdditionalIndexes\Future` — в `Ext/AdditionalIndexes.xml`; каталог `Ext/`
    и расширение `.xml` не входят в YAML. Обычный `Properties\Future` относится
    к основному XML-документу. Одиночный `@` адресует его корень.
51. Два неизвестных узла одного пути сохраняются как raw-значения под обычным
    ключом и ключом `!xml/invalid`; третий получает `!xml/invalid/2`.
52. Два понятных singleton-элемента сохраняются отдельными смысловыми значениями
    с адресным invalid на дубле, а не raw-массивом.
53. Для `FormAttribute.Settings` выбирается единственная ветвь, чей обычный
    экспорт точно совпал с XML; эффекты остальных шести проб отсутствуют.
54. Ноль или несколько точных кандидатов `FormAttribute.Settings` создают raw
    общей границы без зависимости от порядка проверки ветвей.
55. Повторная запись одного выходного XML-пути не перезаписывает значение через
    `setAtPath`, а блокирует экспорт как неразрешённая коллизия.
56. `HeaderHorizontalAlign=Auto` импортируется как `$значение: Auto` с явной
    поправкой `$xml`, восстанавливающей элемент; один invalid без raw
    отклоняется, потому что обычный экспорт удаляет default.
57. Ссылка на однозначно существующую цель, запрещённую типом, отбором или
    filter свойства, импортируется обычным YAML-путём под `!xml/invalid`,
    сохраняет целевую связь в индексе и участвует в поиске и переименовании.
58. Такой invalid обычным экспортом восстанавливает исходную XML-ссылку без
    специального преобразователя и без отдельного публичного тега.
59. Ссылка на отсутствующую цель также импортируется под `!xml/invalid`, но не
    создаёт целевой связи в индексе.
60. Неоднозначная ссылка импортируется под `!xml/invalid` и не выбирает одну из
    целей для индекса в зависимости от порядка обхода.
61. `PictureField` внутри `ContextMenu.ChildItems` преобразуется глобальным
    обработчиком известного подтипа и получает
    `Вид: !xml/invalid ПолеРисунка`; остальные свойства item остаются
    смысловым YAML.
62. Экспорт такого item снова выбирает обработчик `PictureField` и точно
    восстанавливает исходный XML, игнорируя только ограничение допустимых видов
    `ContextMenu.ChildItems`.
63. Неизвестное XML-имя подтипа либо известный обработчик с неточным обратным
    экспортом создаёт raw минимального item или коллекции, а не invalid.
64. Неканоническое внешнее имя известного `ExtendedTooltip` сохраняется в
    `$xml.#name`, а остальные поля находятся в проверяемом `$значение`.
65. Отдельное скрытое транспортное `Имя` запрещено; обычное смысловое поле
    `Имя` других типов этим правилом не затрагивается.
66. Если `$xml.#name` совпало с каноническим именем singleton, создаётся
    `xml/anomaly-tag-unnecessary`; свежий канонический импорт не выводит raw.
67. `#name` используется только внутри `$xml`.
68. Item, отброшенный ранним `continue`/`filter`, повторно проверяется общим
    алгоритмом: известное смысловое значение с точным обычным экспортом получает
    invalid/important только по результату проверки, а непредставимое — raw.
69. Явный default с точным обычным экспортом остаётся нетегированным, если его
    присутствие разрешено; invalid появляется только при ошибке проверки.
70. UUID-ссылка, преобразованная в обычный YAML-путь и точно восстановленная
    обычным экспортом, не становится raw: она остаётся normal либо получает
    invalid/important по результату проверки.
71. Каждый прежний специализированный тег отклоняется как ошибка формата YAML;
    загрузчик не пытается перевести его в raw, invalid или important.
72. Один и тот же YAML с аномалией создаёт структурно одинаковый XML при полной
    и частичной синхронизации через общий `XmlAnomalyRuntime`.
73. Чистое задание проходит ровно один контрольный экспорт; число экспортов
    не зависит от количества входящих в него PropertyRule.
74. Контекстные invalid/important выбираются по окончательному смысловому
    индексу и применяются без повторного fromXML, fromYAML или toXML.
75. Raw-значение не попадает в окончательный смысловой индекс, даже если его
    payload внешне похож на допустимую ссылку или объект metadata.

### Мутации представителей

Для представителя каждого семейства автоматически создаются:

- неизвестный текст;
- пустой и отсутствующий элемент;
- явный default;
- лишний атрибут;
- перестановка атрибутов;
- лишний дочерний элемент;
- другой `xsi:type`;
- scalar/object/sequence вместо ожидаемой формы;
- повтор свойства;
- изменение порядка;
- canonical и alias одновременно;
- исключение преобразователя;
- молчаливый `undefined`/filter;
- контекстно недопустимое значение;
- неразрешимая и неоднозначная ссылка.

Обязательные представители: `boolean`, `number`, `SystemEnumeration`,
`MetadataValue`, `TypeDescription`, `UsePurposes`, `I8nText`, `UserVisible`,
`AppearanceFields`, `ClientApplicationInterface` и один внешний ресурс.

### Генеративная проверка

Помимо адресных примеров нужен генератор структурно корректных мутаций XML:

- добавить неизвестный атрибут или элемент на случайной глубине;
- повторить или удалить существующий узел;
- переставить соседей;
- заменить scalar на mapping/sequence;
- изменить XML-имя, prefix или `xsi:type`;
- создать коллизию вычисляемого YAML-ключа.

Оракул не требует заранее знать вид ошибки. Он проверяет, что импорт либо
создал raw и восстановил XML, создал обратимый invalid, создал important для
явно зарегистрированного класса данных либо вернул одну из явно разрешённых
фатальных ошибок. Молчаливое расхождение считается провалом теста.

### Корпус конфигураций

После модульных и генеративных тестов выполняются round-trip всех эталонных
конфигураций. Новое расхождение должно автоматически стать `!xml/raw` с
координатами, а не требовать немедленного добавления частного правила.

Новая ошибка проверки импортированного, но точно обратимого значения должна
автоматически стать `!xml/invalid`, а не raw. Important используется только при
совпадении с явной регистрацией.

Собранные raw, invalid и important затем можно найти по трём публичным тегам и исследовать
по месту их появления. Повторяющийся случай исправляется обычным rules.ts; при
повторном импорте исправленного XML новый тег больше не создаётся. Обычная
валидация уже сохранённого YAML не пытается автоматически переоценить или
удалить тег.

## Архитектура реализации

### Один общий runtime поверх rules

Механизм реализуется глубоким нейтральным модулем `XmlAnomalyRuntime` вокруг
существующего исполнителя PropertyRule. Он не заменяет 92 обработчика типов и
не требует от каждого из них возвращать собственный класс ошибки. Обычные
`importFromXML`, `importFromXMLToYAML`, `exportToYAML`, `fromYAML` и `toXML`
остаются смысловыми преобразователями.

Runtime отвечает за четыре общие обязанности:

1. компилирует из собранных rules карту XML-путей, вложенных правил и устойчивых
   YAML-границ;
2. во время импорта учитывает владение каждым разобранным XML-узлом и изолирует
   сбой конкретной границы;
3. доказывает обратимость обычным контрольным экспортом, а смысловые ошибки
   передаёт общей валидации с точными YAML-границами;
4. при синхронизации снимает смысловые теги и применяет `$xml` после обычного
   экспорта `$значение`, не заставляя обработчики типов знать о транспортном
   формате.

План компилируется один раз для `RuleRegistrySet` и переиспользуется всеми
worker. В `BasePropertyRule`, отдельные common-типы и их параметры новые поля
не добавляются. В отдельном реестре композиции остаются только регистрации
important. Raw всегда самодостаточен благодаря `$xml`, а внешнее имя выражается
общим `#name`; частные raw-генераторы и регистрации скрытого имени удаляются.

### Сеанс аудита одного задания

Для одного задания импорта создаётся короткоживущий `XmlImportAuditSession`.
Он получает нормализованное XML-дерево и существующий объектный вид для старых
обработчиков. Каждый узел дерева имеет устойчивый идентификатор, структурный
хэш, XML-путь с номером вхождения и состояние владения.

`XMLImportPlan` не только находит PropertyRule, но и заявляет в сеансе реально
потреблённые узлы. Неизвестный остаток, повтор singleton, canonical вместе с
alias и неиспользованный `ambiguousXMLKey` становятся явным результатом аудита.
Проверка выполняется по полным путям, поэтому `xmlParents`, вложенные rules.ts и
несколько XML-источников одного объекта проходят тот же механизм.

Вызов PropertyRule выполняется с контрольной точкой побочных эффектов. При
успехе записи в локальные коллекторы, отложенные операции и временные индексы
фиксируются; при исключении или отклонённой неоднозначной пробе откатываются.
Для обычного единственного кандидата контрольная точка должна быть O(1), а
отдельные буферы создаются только для нескольких кандидатов.

Построители YAML-map обязаны сообщить сеансу все элементы до
`Object.fromEntries` или равнозначной перезаписи. Сеанс сохраняет внутреннюю
последовательность `{ logicalKey, occurrence, value, source }`; структурный
валидатор позднее назначает понятным повторам адресные `!xml/invalid` и
`!xml/invalid/N`. До этого решения публичного тега ещё нет, но ни одно
вхождение не теряется.

### Три этапа импорта

Текущие два worker-прохода заменяются тремя этапами с двумя общими барьерами.
Третий этап не повторяет преобразование XML или валидацию: он применяет уже
принятые решения и один раз сериализует YAML.

**1. Смысловое преобразование и рабочий индекс.** Worker разбирает XML,
выполняет существующие обработчики и строит черновой смысловой YAML вместе с
картой владения XML-местами. Повторы ключей, отсутствующие ожидаемые свойства и
другие коллизии сохраняются во внутренней таблице адресуемых вхождений, но
публичных invalid/important ещё не получают. Неизвестные узлы и
локальные исключения становятся кандидатами raw, но граница raw ещё не должна
скрывать распознанных соседей. В общий рабочий индекс публикуются только эффекты
зафиксированных проб. Смысловые значения, которым требуется resolver, пока
имеют состояние `pending`.

**2. Доказательство представления.** После публикации рабочего индекса worker
завершает отложенные смысловые значения и выполняет в памяти один терпимый
YAML → XML экспорт задания без raw, исходного XML и reference snapshot. Сбой
экспорта одного свойства фиксируется на его границе и не прерывает экспорт
независимых соседей. Полученное дерево сравнивается со структурными хэшами
исходных границ. Точное значение остаётся смысловым; различие локализуется по
карте владения и становится raw по следующему порядку: точный XML-путь,
свойство, именованный item с сохранённым ключом, затем коллекция или объект.
После применения raw формируется окончательный смысловой вклад файла в индекс.

**3. Валидация и запись.** Координатор собирает доказанные смысловые вклады в
окончательный индекс и запускает обычную валидацию: JSON Schema, resolver,
допустимые типы и отборы ссылок, уникальность и межполевые правила. Её
структурированные ошибки с явно назначенным target превращаются в `invalid`
или, при явной регистрации ценности, `important`. В эту же проверку входят
внутренние вхождения повторов и отсутствующих обязательных свойств. Worker
применяет решения без повторной локальной валидации и без повторного построения
индексов: invalid/important не меняют смысловые данные. Для отложенной ссылки
или проверки он переносит в уже построенное окончательное состояние признак,
что тег уже подтверждён найденной ошибкой. Завершающая проверка связей такую
границу пропускает.
Если второй этап добавил или поднял raw-границу, worker выполняет завершающий
экспорт этой изменённой границы с raw-вставкой и требует точного совпадения с
исходным XML. Для задания без raw повторять уже точный контрольный экспорт не
нужно: invalid/important не меняют XML. Затем worker один раз сериализует и
записывает YAML и вычисляет окончательный хэш файла.

Raw определяется до построения окончательного смыслового индекса и не может
создать ложную смысловую цель. При этом распознанная оболочка именованного item
остаётся в структурном индексе: raw закрывает только неизвестные внутренние
факты. Invalid и important появляются по результатам валидатора после
доказательства обратимости; они не меняют смысловое значение, поэтому их
добавление после построения индекса безопасно. Для ссылки сам результат resolver
по-прежнему определяет, существует ли целевая связь.

`pending`, не разрешившийся к третьему этапу, является фатальной ошибкой
операции. Инфраструктурный сбой валидатора, повреждённый индекс и ошибка самого
runtime также не маскируются raw или invalid.

### Контрольный экспорт без значительного замедления

Общая гарантия обратимости требует фактического обратного экспорта; заменить
его предположением отдельного common-типа нельзя. Чтобы проверка не умножалась
на число PropertyRule, экспорт выполняется ровно один раз на задание, а
различие локализуется по заранее скомпилированной карте владения.

На обычном пути:

- совместимый XML-парсер строит смысловое представление, а отдельный потоковый
  SAX-проход вычисляет структурные хэши корней без адресного XML-дерева;
- исходное объектное XML-дерево не строится и не удерживается до второго этапа;
- между этапами хранятся хэши корней и пути исходных файлов;
- результат контрольного `toXML` по возможности преобразуется в структурные
  хэши непосредственно из окончательного XML-объекта, без промежуточной строки
  и повторного разбора; совместимый медленный путь остаётся для структур,
  которые нельзя однозначно представить напрямую;
- JSON Schema и контекстные проверки выполняются одним общим проходом после
  построения окончательных индексов, а не внутри каждого common-типа;
- третий этап не выполняет `fromXML`, `fromYAML` или `toXML` повторно.

Если корневые хэши различаются, задание повторно импортируется с адресным
деревом и аудитом владения. Подробный результат целиком заменяет черновые
смысловой YAML и таблицу аннотаций: одного подробного аудита недостаточно,
поскольку неизвестный XML создаётся именно во время его проекции в YAML.
Предварительные raw известных Rules-узлов при этом не переносятся автоматически:
они заново доказываются по `yamlPath`, `rawYamlPath`, именам уровней и целям
proof-аудита. Напрямую сохраняются только публичные пути действительно
неизвестных XML-узлов. Имя повторного `*:Item` само по себе не доказывает
принадлежность коллекционному правилу: предварительный raw удаляется только
когда обычный экспорт уже восстанавливает тот же узел; действительно
неизвестный `<Item>` сохраняется.
Только аномальный исходный файл повторно читается для извлечения
соответствующего `$xml`-фрагмента. Оболочка родительского
контейнера при этом сравнивается отдельно от независимо принадлежащих дочерних
границ, поэтому единичное отличие не поднимает raw на всю коллекцию.
После выбора или подъёма raw выполняется завершающий контроль только изменённых
границ. Чистое задание и задание только с invalid/important используют уже
полученный точный результат первого контрольного экспорта.
Повторное расхождение после подъёма границы или разрешённого числа попыток
является фатальным нарушением договора, а не бесконечным циклом.

Профилировщик импорта отдельно измеряет построение аудита, контрольный экспорт,
структурное сравнение, медленный raw-путь и применение тегов. Производительность
проверяется на эталонных конфигурациях; недопустимо заменять один общий экспорт
отдельным round-trip каждого из 1839 PropertyRule.

Рабочие линии имеют ограничение старого поколения V8 в 768 МиБ: смысловой YAML
между проходами остаётся доступным, но временные XML/YAML-деревья не могут
неограниченно расширять независимые кучи. Подробная карта исходного XML нужна
только до окончания контрольного сравнения конкретного файла и освобождается
сразу после него, не ожидая третьего прохода. Сериализованные байты до записи
не должны создавать вторую копию смыслового дерева. Raw с известным
`$значение` также не вызывает копирование всего смыслового дерева; копия
создаётся только для добавления отсутствующей границы.

### Производительность контрольного экспорта

Профиль `cf/doc` с двумя worker показал 412,0 с общего времени, из которых
322,2 с занимает второй проход; локальная проверка внутри него занимает 40,4 с.
Обычный первый проход занимает 52,0 с. Пик RSS равен 2213,5 МиБ. Ранее четыре
worker выполняли импорт за 184,6 с при пике 3143,6 МиБ. Следовательно,
ограничение двумя worker устраняет рост памяти, но не удовлетворяет целевому
времени.

Целевой договор: `cf/doc` импортируется не более чем за 120 с. Пик RSS
измеряется и сравнивается между вариантами, но не задаётся одной постоянной
величиной для компьютеров с разным объёмом памяти. Контрольный экспорт остаётся обязательным для каждого задания и
выполняется после рабочего барьера индекса, поэтому контекстные правила видят
те же данные, что и полная синхронизация.

Для выполнения договора импорт рассчитывает число worker по доступным
процессорам и памяти и разделяет хранение подготовленного состояния от его
исполнения:

1. первый проход записывает для каждого задания версионированную подготовленную
   запись в операционное projectState-хранилище и не удерживает все смысловые
   деревья в памяти worker до конца импорта;
2. запись содержит YAML, снимок аннотаций, корневой proof-аудит, пути отложенных
   значений, кандидаты зависимых значений, данные назначения и контрольную
   сумму; связанные ссылки на объекты и экземпляры rules не сериализуются;
3. после чтения записи worker заново находит rule по идентификатору и связывает
   отложенные пути с восстановленным YAML-деревом;
4. второй проход получает задания из общей динамической очереди, поэтому
   крупные формы не закрепляют одну рабочую линию, пока остальные простаивают;
5. worker удерживает только текущую ограниченную пачку, немедленно публикует
   успешный результат и освобождает подготовленное и подробное XML-дерево;
6. повреждённая запись, несовместимая версия или контрольная сумма завершают
   импорт явной ошибкой; результат задания становится видимым только после
   полного успешного контроля.

Обычный контрольный экспорт формирует тот же окончательный XML-объект, что и
полная синхронизация: после отложенных преобразований, с точным порядком узлов
и атрибутов. Для него структурные хэши вычисляются напрямую. Если прямое
представление не поддерживает конкретную конструкцию, используется прежний
путь `xmlExport → потоковый XML-разбор`; это не является основанием пропустить
проверку. При несовпадении хэшей исходный XML перечитывается подробно и
создаётся минимальный raw по существующему договору.

Контрольный экспорт всегда строится из смысловой проекции YAML. Если его
структурные хэши совпали с исходными, предварительные raw-кандидаты удаляются:
в окончательный YAML попадают именно данные и аннотации, которые использовал
обычный экспорт. Если хэши различаются, подробный аудит начинается с той же
смысловой проекции и добавляет только доказанные минимальные поправки.

Фактический профиль `cf/doc` после переноса подготовленных заданий в
операционное хранилище и динамической раздачи четырём worker: 9937 успешных
заданий, 0 ошибок, 221,2 с и 2813,4 МиБ пикового RSS. Все контрольные документы
построены напрямую без промежуточной XML-строки; для 1813 несовпадений исходный
XML перечитан подробно. Второй проход занял 140,5 с, из них 109,6 с —
контрольный экспорт. Ограничение памяти выполнено, целевые 120 с — нет;
дальнейшее ускорение требует отдельной оптимизации контрольного экспорта без
ослабления проверки обратимости.

Число worker без явного пользовательского параметра равно минимуму из двух
оценок: две трети доступных процессоров и число куч по 768 МиБ, помещающихся
после резерва 25% общей памяти, но не менее 2 ГиБ. В контейнере вместо памяти
компьютера используется меньшее из `os.totalmem()` и
`process.constrainedMemory()`. На машине с 10 процессорами
и 16 ГиБ памяти выбираются шесть worker. После записи канонического входа
структурного хэша одной порцией и устранения второго XML-разбора первого
прохода два запуска с шестью worker заняли 147,6 и 175,6 с при пике 3619,2 и
3674,5 МиБ. Для сравнения: четыре worker — 208,1 с и 2657,7 МиБ, пять —
177,0 с и 3611,2 МиБ, восемь — 175,7 с и 3761,5 МиБ. Поэтому фиксированное
число worker не используется; явный параметр операции сохраняет приоритет над
расчётом, а оценка скорости учитывает разброс повторных запусков.

Дополнительные правила адресации:

- скрытое YAML-свойство Rules (`yamlKey` отсутствует) распознаётся по
  `propertyKey`, но появляется в публичном YAML только как аномальная граница;
- `#order` неизвестных детей остаётся на XML-родителе, например внутри raw
  `Properties`, даже если подробный аудит не смог назначить владельца каждому
  ребёнку; перенос порядка на корень документа запрещён;
- запись `Свойство: !xml/raw` считается началом вложенного YAML-контейнера.
  Поэтому пустое смысловое отображение внутри `$значение` разбирается как `{}`,
  а не как пустая строка.

### Общий экспорт при полной и частичной синхронизации

Обе синхронизации используют один `XmlAnomalyRuntime` перед общим исполнителем
YAML → XML. Различаются только выбранные топологией задания, но не правила
восстановления аномалий.

1. YAML-парсер возвращает смысловые данные и единую таблицу аннотаций значений,
   ключей и корня; тег mapping или sequence не превращает предметное значение в
   специальный объект модели.
2. `!xml/invalid` и `!xml/important` проверяются как смысловые границы, после
   чего их payload передаётся обычным `fromYAML` и `toXML` без изменения.
3. `!xml/raw` перехватывается до `fromYAML`: `$значение`, если оно есть,
   передаётся обычному правилу, а `$xml` сохраняется как план поправки.
4. Обычный экспорт сначала формирует известную часть XML из `$значение`. Затем
   runtime рекурсивно применяет `$xml`; без `$значение` оно создаёт полную
   границу.
5. Защищённый XML-writer разрешает `$xml` изменять обычный результат, но
   запрещает конфликт двух независимых поправок и неоднозначное объединение
   порядка.
6. `!xml/invalid` и `!xml/invalid/N` на ключах декодируются общим адаптером
   именованных коллекций в первое, второе и последующие вхождения одного
   логического ключа.

Обычная валидация использует ту же таблицу аннотаций. Raw без `$значение`
подавляет только зависимые предметные проверки; raw с `$значение` проверяет его
как обычно. Invalid/important раскрываются,
проверяются и подавляют наружу только подтверждённую ошибку, ради которой стоит
тег. Отдельная проверка договора выполняется лишь для отмеченных границ. Она
отклоняет неправильный контейнер, неподдерживаемое место, неверный important и
тег, который после изменения значения стал лишним.

### Полный отказ от прежнего механизма

Совместимость со специализированными тегами отсутствует намеренно:

- новый YAML-парсер принимает только `!xml/raw`, `!xml/invalid` и
  `!xml/important` с согласованными адресными суффиксами;
- прежний тег в YAML является ошибкой формата, а не входом скрытой миграции;
- загрузчик не содержит двойного чтения, преобразователя старого payload или
  режима версии формата;
- существующие YAML-проекты с прежними тегами должны быть заново импортированы
  из исходного XML;
- старые регистрации и emitters удаляются, а их XML-фикстуры и тесты
  используются как регрессионный корпус нового классификатора;
- в одном завершённом изменении удаляются старые определения тегов, схемы,
  проверки и частные ветви экспорта; временный публичный формат с двумя
  механизмами не допускается.

Исторические таблицы выше объясняют ожидаемый результат повторного XML-импорта.
Они не задают преобразование старого YAML.

## Ограничения первой реализации

- синтаксически неверный XML остаётся фатальным;
- побайтовая форма XML не сохраняется;
- позиция mixed text нормализуется текущим парсером;
- бинарные и произвольные не-XML файлы обслуживаются топологией ресурсов;
- неизвестный XML-файл не преобразуется и не получает raw в первой реализации;
  существующая явная ошибка неизвестного маршрута сохраняется до отдельного
  проектирования границы оркестратора;
- коллизия скрытого UUID у двух известных объектов с разными логическими
  именами завершается явной ошибкой до записи YAML; выбирать канонический
  объект, генерировать новый UUID или сохранять UUID через raw пока запрещено;
- raw неизвестного metadata item в уже известном файле требует границы
  оркестратора и не должен имитироваться свойством последнего известного
  common-типа;
- архитектурная документация обновляется только после отдельного согласования
  реализации.

Эти ограничения не разрешают молчаливую потерю. Каждый выход за договор должен
дать явную фатальную диагностику с координатами.

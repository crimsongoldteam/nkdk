# Отказ от сокращенного YAML

## Контекст

Валидация YAML-проекта `/home/nikita/git/temp-yaml` показала десятки тысяч
ошибок схемы. Большая часть массовых ошибок связана не с синтаксически битым
YAML, а с тем, что текущий YAML-контракт допускает человеко-ориентированные
сокращения, а JSON Schema уже требует объектную форму.

Типичные примеры старого формата:

```yaml
Реквизиты:
  Организация: Справочник.Организации
Команды:
  ДокументыЭДО: ПанельНавигацииВажное
```

Для ИИ такой формат менее полезен: разные формы одного и того же понятия
усложняют чтение, генерацию, проверку и исправление YAML. Новый контракт должен
быть единым и объектным.

## Решение

Отказываемся от сокращенных YAML-форм жестко. `toYAML`, `fromYAML`, TypeScript-типы
и JSON Schema должны принимать только полный объектный формат.

Канонический формат:

```yaml
Реквизиты:
  Организация:
    Тип: Справочник.Организации
Команды:
  ДокументыЭДО:
    Группа: ПанельНавигацииВажное
```

Это несовместимое изменение YAML-контракта. Старый формат должен считаться
невалидным, а не тихо импортироваться.

## Границы

Меняется только YAML-вход, YAML-выход, типы YAML и JSON Schema. Внутреннюю
metadata-модель, XML-представление и правила XML round-trip не меняем без
отдельной причины.

Первый проход должен покрыть массовые источники сокращений:

- `FormAttributes`: реквизиты форм.
- `MetadataAttribute`: реквизиты прикладных объектов.
- `MetadataRegisterField`: измерения, ресурсы и реквизиты регистров.
- Родственные коллекции, где типы сейчас допускают `...YAML | TypeDescriptionYAML`.

Команды тоже должны быть проверены: сокращения вида `Команда: ГруппаКоманд` должны
быть заменены на объектную форму с явным полем `Группа`.

## Архитектура

Изменение проводится на границе YAML-адаптеров:

- `toYAML` всегда экспортирует объектную форму, даже если у элемента заполнен
  только тип или группа.
- `fromYAML` больше не распознает скаляр как сокращение полного объекта.
- TypeScript-типы убирают union-варианты со скаляром, чтобы старый контракт был
  невозможен на уровне типов.
- JSON Schema остается строгой и подтверждает новый контракт.

Ошибки старого YAML должны диагностироваться как структурные ошибки схемы. Если
сообщение TypeBox получается слишком общим, улучшение текста диагностики можно
делать отдельным шагом, не смешивая с удалением сокращений.

## Миграция реального YAML-проекта

`/home/nikita/git/temp-yaml` не правится вручную. После изменения экспортера
проект заново выгружается из источника `/home/nikita/git/round-trip/erp`.

Поток проверки:

1. Обновить `nkdk`, чтобы `toYAML` писал только полный объектный формат.
2. Пересобрать `/home/nikita/git/temp-yaml` из `/home/nikita/git/round-trip/erp`.
3. Запустить `validate /home/nikita/git/temp-yaml`.
4. Массовые `Expected object`, вызванные сокращениями реквизитов, полей и команд,
   должны исчезнуть.
5. Оставшиеся ошибки считать отдельными проблемами схемы, импорта или правил
   валидации.

## Тестирование

Нужны регрессионные тесты на оба направления:

- `toYAML` экспортирует полный объект вместо скаляра.
- `fromYAML` отвергает старое сокращение.
- JSON Schema отвергает старое сокращение и принимает полный объект.
- Существующие YAML-фикстуры обновлены на новый формат.

Перед завершением реализации обязательно выполнить:

```bash
pnpm test
pnpm --filter @nakidka/cli dev validate /home/nikita/git/temp-yaml
```

Второй запуск может завершиться с кодом `1`, если останутся реальные
диагностики. Критерий для этой задачи: ошибки, объясняемые сокращенным YAML, не
должны оставаться массовым классом.

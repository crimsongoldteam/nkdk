# Единое построение ProjectState при XML-import и validation

## Контекст

Последовательный импорт основной конфигурации и расширения из XML сейчас требует
промежуточного полного rebuild ProjectState. Импорт `cf` записывает YAML форм и
возвращает успешный результат, но окончательные записи ProjectState не содержат
`structuredDocuments`. Следующий импорт `cfe` не может найти текущие формы `cf`
и завершается ошибками вида «Не найдена текущая форма cf».

Обычная актуализация YAML-проекта формирует `structuredDocuments` через
`projectFormStructureDocuments`, а XML-import вызывает
`toProjectStateFileUpdate` без этих сведений. Получились два похожих, но
неэквивалентных алгоритма построения окончательного ProjectState.

На проекте `/Users/nikita/git/sed_xml` это воспроизводится так:

1. импорт `cf` завершается без diagnostics;
2. импорт `cfe/дкз` тем же `ProjectStateService` завершается 29 ошибками по
   заимствованным формам;
3. полный rebuild импортированного `cf` заполняет `structuredDocuments`;
4. повторный импорт `cfe/дкз` завершается без diagnostics и сохраняет все
   связанные шаблоны и формы.

## Цель

Окончательный ProjectState каждого импортированного YAML должен строиться тем же
алгоритмом, что и при обычной validation, без повторного чтения и разбора только
что сериализованного YAML.

После успешного импорта `cf` импорт зависимого `cfe` тем же
`ProjectStateService` должен сразу видеть формы основной конфигурации. Промежуточный
rebuild не должен требоваться.

## Решение

Вынести общий построитель окончательного `ProjectStateYamlFileUpdate`. Он получает:

- `ProjectValidationFirstPassResult` из общего `validateProjectFileFirstPass`;
- описание YAML-файла и его компонента;
- topology компонента;
- файловые metadata targets;
- режим вклада `shared` или `isolated`.

Построитель единообразно формирует:

- локальные и schema diagnostics;
- metadata targets;
- owners и fields;
- сведения форм;
- pending references и pending checks;
- зависимости;
- `structuredDocuments` рабочей или базовой формы;
- изоляцию вклада для `БазоваяФорма.yaml`.

Обычная актуализация ProjectState и XML-import используют только этот построитель
для окончательного состояния YAML. У них не должно оставаться самостоятельной
сборки отдельных полей `ProjectStateYamlFileUpdate`.

Общий построитель размещается в нейтральном project-слое рядом с преобразованием
результата validation в ProjectState. Он может использовать topology и
нейтральный реестр проекций структуры форм, но не должен содержать условий по
конкретным `itemType`, именам каталогов или видам прикладных объектов.

## Граница переиспользования

Временный индекс первого прохода XML-import остаётся специализированным. В этот
момент YAML может содержать отложенные значения и ещё не является окончательным;
индекс нужен только второму проходу и не публикуется как конечное состояние.

После уточнения отложенных значений import сериализует окончательный YAML,
вызывает общий `validateProjectFileFirstPass` через существующий
`validateSerializedProjectYaml`, а затем передаёт результат общему построителю.
Специализированный временный вклад полностью заменяется общим окончательным
вкладом.

Это сохраняет существующий договор производительности: готовые смысловые данные
YAML проверяются без повторного чтения файла и без второго разбора текста.

## Поток данных

1. XML-import преобразует XML в модель YAML и уточняет отложенные значения.
2. YAML сериализуется в окончательный текст и согласованные смысловые данные.
3. `validateSerializedProjectYaml` вызывает общий первый проход validation без
   чтения YAML с диска.
4. Общий построитель преобразует результат первого прохода в полный
   `ProjectStateYamlFileUpdate`.
5. Import разделяет готовое обновление на индексную и финальную части только для
   передачи и хранения; содержание полей не пересобирается.
6. ProjectState публикуется после существующей полной dependency validation и
   checkpoint.
7. Следующий импорт расширения читает `structuredDocuments` форм из уже
   опубликованного состояния `cf`.

## Ошибки и восстановление

Новые резервные ветки не добавляются. Если общий построитель или validation не
могут сформировать корректное обновление, import возвращает техническую ошибку и
не публикует незавершённую import session по действующему договору.

Автоматический rebuild после import не выполняется: он скрывал бы расхождение
алгоритмов, повторно читал весь проект и удваивал работу.

Если topology не классифицирует файл или для формы не зарегистрирована требуемая
проекция, сохраняется действующее поведение соответствующего общего алгоритма:
классификационная ошибка не маскируется, а отсутствие структурных компонентов
даёт пустой набор `structuredDocuments`.

## Тесты

### Интеграционный договор

Расширить интеграционные проверки XML-import сценарием:

1. импортировать минимальный `cf` из XML, содержащий владельца и управляемую
   форму;
2. не записывать базовый YAML вручную и не выполнять rebuild;
3. тем же `ProjectStateService` импортировать XML расширения с заимствованной
   формой;
4. проверить успешный импорт и отсутствие ошибки «Не найдена текущая форма cf».

Этот тест защищает самостоятельный договор между двумя import-операциями. Он не
дублирует тесты преобразования отдельных свойств формы.

### Узкий договор построителя

Проверить на одном представителе формы, что общий построитель создаёт
`structuredDocuments` как минимум для документа формы и одного структурного
компонента. Один и тот же тестируемый построитель должен использоваться обычной
validation и XML-import.

Существующие проверки `preparedYamlProjectWorker` на рабочую и базовую формы
сохраняются и переводятся на общий построитель без ослабления утверждений.

Отдельный большой тест на восемь отчётов из `sed_xml` не добавляется. Перенос
внешних файлов уже имеет собственные проверки; отсутствие шаблонов было
следствием более раннего падения импорта расширения.

## Проверка реализации

После каждого законченного слоя выполняются целевые тесты и:

```text
pnpm duplicates -- --base 44fd122b8
```

Перед завершением выполняются:

```text
pnpm type-check
pnpm test
pnpm test:architecture:rules
pnpm test:architecture
pnpm duplicates -- --base 44fd122b8
```

Дополнительно production-путём импортируются `cf` и `cfe/дкз` из
`/Users/nikita/git/sed_xml` в один временный проект без промежуточного rebuild;
после импорта запускается `nkdk.validate_project`.

## Вне границ

- исправление пяти исходных падений
  `metadata/configurationIndex/projectFiles.test.ts` при случайном порядке
  тестов;
- автоматическое восстановление частично записанного каталога после прежнего
  неуспешного import;
- изменение формата ProjectState или configuration index;
- изменение правил BaseForm, DataPath или применения `!xml`;
- восстановление файлов, удалённых коммитом `990c220c` в отдельном репозитории
  `sed_nkdk`.

## Исходный baseline

На чистом `origin/develop` перед записью этого проекта решения `pnpm test`
показал 6200 успешных и 5 неуспешных тестов. Все пять падений относятся к
`metadata/configurationIndex/projectFiles.test.ts` и сообщают, что metadata не
зарегистрирована перед `project/syncStateFiles`. Пользователь согласовал
продолжение работы без включения исправления baseline в текущие границы.

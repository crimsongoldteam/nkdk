# Переход на TypeBox 1.3.3

## Цель

Перевести `packages/core` с `@sinclair/typebox@0.34.49` на новый пакет `typebox@1.3.3`, сохранив текущее поведение YAML-валидации, диагностики и validation worker-кода.

## Контекст

В проекте TypeBox используется как основа JSON Schema для метаданных и как компилируемый валидатор в `packages/core/metadata/validation`. Похожий переход уже был сделан в коммите `d14d74c69`, где код перешёл на `typebox`, `Schema.Compile` и новый формат ошибок. Этот переход нужно применить к текущей ветке аккуратно, не перенося случайную ошибку из старого коммита: в `package.json` должна быть одна зависимость `typebox: "1.3.3"` без дублирования и без старого `@sinclair/typebox`.

## Подход

Основной путь - прямой переход на API TypeBox 1:

- заменить импорты `@sinclair/typebox` на `typebox`;
- заменить `@sinclair/typebox/compiler` на `typebox/schema`;
- заменить `ValueError`/`ValueErrorType` на новый формат ошибок из `typebox/error`;
- компилировать схемы через `Schema.Compile`;
- сохранить локальные договоры проекта поверх новых типов, когда код зависит от полей ошибки, которых нет в базовом типе TypeBox.

Совместимый переходник поверх старого и нового API не нужен: кодовая база использует TypeBox внутри `packages/core`, а старый коммит уже показал рабочую форму прямой миграции.

## Затрагиваемые области

Зависимости:

- `packages/core/package.json`;
- `pnpm-lock.yaml`.

Схемы и типы:

- файлы `toJSONSchema.ts`, `types.ts`, `register.ts` и тесты, где импортируются `Type`, `Static`, `TSchema`, `TObject`, `TProperties`;
- рекурсивные и ссылочные схемы, где TypeBox 1 требует другой формы ссылок или строгих типов.

Валидация:

- `schemaCache.ts`, `validateFile.ts`, `validateItem.ts`;
- `typeboxErrorsToDiagnostics.ts`;
- `discriminatedUnionErrors.ts`;
- validation snapshot/worker/pass-код, если он хранит или компилирует схемы.

Тесты:

- тесты, которые проверяют текст ошибок, `ValueErrorType`, `path` или внутреннюю структуру ошибок;
- snapshot-тесты схем, если TypeBox 1 иначе сериализует refs, recursive schemas или описания ошибок.

## Диагностика ошибок

Новый формат ошибок использует `keyword`, `instancePath`, `schemaPath`, `params` и сообщение. Проектная диагностика должна нормализовать этот формат к прежнему пользовательскому поведению:

- `required` разворачивается до конкретных отсутствующих свойств;
- `additionalProperties` указывает на лишний ключ YAML, а не только на родительский объект;
- ошибки дискриминированных union раскрываются до выбранной ветки, если значение дискриминатора известно;
- сообщение о неизвестном дискриминаторе остаётся русскоязычным;
- позиции YAML берутся так же, как сейчас: значение для обычных ошибок, родительский узел для отсутствующего обязательного поля, ключ для лишнего свойства.

## Ограничения

- XML-фикстуры не изменять.
- Не добавлять новые правила `fromXML`/`toXML`/`fromYAML`/`toYAML`.
- Не протаскивать знания о конкретных itemType или папках в общие metadata-слои.
- Не использовать `as any` как основной способ миграции; если приведение нужно, держать его рядом с интеграцией с новым API и покрыть тестом поведения.

## Проверка

Перед завершением реализации:

1. Запустить узкие тесты для изменённых validation/schema-файлов, если падения локализованы.
2. Запустить `pnpm --filter @nakidka/core type-check`.
3. Запустить `pnpm test` из корня проекта.

Работа считается завершённой только если общий `pnpm test` зелёный.

## Риски

Главный риск - тихое изменение структуры ошибок TypeBox и, как следствие, ухудшение YAML-диагностики. Его закрывают тесты на `typeboxErrorsToDiagnostics`, discriminated union, required/additional properties и validation snapshots.

Второй риск - сериализуемость схем для worker/snapshot-кода. TypeBox 1 должен уменьшить зависимость от внутренних меток старого пакета, но нужно проверить места, где схема передаётся между потоками или восстанавливается из снимка.

# `!xml/uuid` для UUID-ссылок на метаданные

## Статус

Согласованный проект системного договора. Реализация начинается только после
отдельного утверждения этой спецификации и написания плана.

## Контекст

Значение свойства, объявленного как metadata-ссылка, в нормальном случае
хранится в YAML смысловым путём, например `Справочник.Товары`. Такой путь
разбирается по `metadataTarget`, включается в индекс зависимостей и проверяется
на существование в проекте.

В XML встречаются ссылки, записанные не смысловым путём, а идентификатором:

- одиночный UUID, например
  `76e70e66-9e54-4a40-95ce-cff9444899e7` в `FunctionalOptions` трёх форм
  Cashdesk;
- составной `DesignTimeRef` вида `UUID.UUID`, например
  `1d400af1-c260-4c6e-bd7c-89f99aaaf5fe.7e53c8fa-b6c9-417f-b52f-516805bf72e2`
  в `Documents/Инвентаризация.xml` Cashdesk.

Сейчас составной идентификатор может быть разрешён через
`designTimeReferenceByUuid` и заменён смысловым путём. Одиночный UUID попадает в
обычный разбор metadata-ссылки и может завершить импорт ошибкой `Неизвестный
корень`. Оба поведения неверны: UUID-ссылка не содержит устойчивого смыслового
адреса и считается битой по определению, даже если текущий индекс позволяет
сопоставить её с объектом.

## Цель

Ввести общий скалярный тег `!xml/uuid` для UUID-ссылок на метаданные. Тег
сохраняет исходный текст без потерь, явно показывает аномалию и полностью
исключает попытки разрешения такой ссылки через индекс.

## Не входит в задачу

- Собственные идентификаторы объектов XML (`uuid="..."`, `_uuid`) не являются
  metadata-ссылками и не получают тег.
- Смысловые ссылки продолжают разбираться и проверяться через индекс без
  изменения договора.
- Произвольные строки, похожие на UUID, но находящиеся в обычных строковых
  свойствах без `metadataTarget`, не получают тег.
- Тег не заменяет `!xml/invalid` для других смысловых ошибок.

## Публичный договор YAML

`!xml/uuid` разрешён только на одной физической metadata-ссылке, представленной
скаляром:

```yaml
ФункциональныеОпции:
  - !xml/uuid 76e70e66-9e54-4a40-95ce-cff9444899e7

ЗначениеЗаполнения: !xml/uuid 1d400af1-c260-4c6e-bd7c-89f99aaaf5fe.7e53c8fa-b6c9-417f-b52f-516805bf72e2
```

Тег поддерживается:

- на обычном скалярном значении;
- на элементе списка;
- на YAML-ключе, если конкретный тип хранит metadata-ссылку в ключе.

Допустимы две формы текста:

1. один UUID `8-4-4-4-12` шестнадцатеричных цифр;
2. два таких UUID через одну точку.

Регистр шестнадцатеричных цифр не нормализуется. XML → YAML → XML обязан
сохранить исходный текст дословно. Тег на смысловом пути, значении другой формы,
карте или последовательности является ошибкой.

## Архитектурная граница

Классификация выполняется в общем механизме `metadataTargetOccurrences`, а не в
правилах отдельных объектов. Классификатор вызывается только для occurrence,
который уже объявлен metadata-ссылкой, поэтому технические UUID объектов и
обычные строки остаются вне его области.

Не добавляются новые признаки в `PropertyRule`, `BasePropertyRule` или
построители правил. Строки, списки, вложенные значения и YAML-ключи используют
уже существующие регистрации `metadataTargetOccurrences`.

## XML → YAML

Первый проход импорта не меняется: он только собирает индексы и факты и ничего
не проверяет.

Во втором проходе общий преобразователь metadata-ссылок классифицирует каждое
occurrence до форматирования смыслового пути:

1. смысловая ссылка проходит прежнее преобразование;
2. одиночный UUID или `UUID.UUID` остаётся без изменения;
3. вместе с преобразованным значением возвращается точное расположение
   UUID-anomaly;
4. после присоединения свойства к итоговому YAML таблица XML-аннотаций получает
   `uuid` на значение либо ключ;
5. контрольный экспорт получает уже размеченный YAML.

Тег ставится непосредственно во втором проходе, а не отдельным повторным чтением
или обходом записанного YAML.

## YAML → XML

Обратное преобразование проверяет UUID до попытки разбора смыслового пути:

- UUID с точной аннотацией `!xml/uuid` принимается и передаётся типу свойства
  дословно;
- UUID без тега отклоняется с сообщением, что UUID metadata-ссылки требует
  `!xml/uuid`;
- `!xml/uuid` на тексте неправильной формы отклоняется как необоснованный тег;
- смысловой путь проходит прежний разбор и проверку ограничений `metadataTarget`.

Составной UUID остаётся типизированным значением `DesignTimeRef`, поэтому
существующий обработчик `MetadataValue` восстанавливает `xsi:type` из типа
значения, а не из configuration index.

## Индексы и проверки ссылок

UUID-anomaly является непрозрачным значением:

- она не включается в индекс структурных ссылок и зависимостей;
- для неё не вызываются `metadataTargetLookup`, resolver проекта и
  canonicalizer;
- операции поиска и переименования ссылок её не изменяют;
- обычные смысловые ссылки по-прежнему включаются в индексы и обязаны
  разрешаться в проекте.

## Удаляемый механизм

Механизм преобразования UUID в смысловую ссылку удаляется полностью:

- поле `designTimeReferenceByUuid` из профиля восстановления XML и контекста
  экспорта;
- построение и передача этой таблицы;
- параметр `metadataTargetCanonicalizer` и замена значения при импорте;
- сохранение `DesignTimeRef` в configuration index только ради последующего
  восстановления;
- `restoreDesignTimeReferenceUuid` и обратная подстановка UUID при экспорте;
- тесты, закрепляющие разрешение UUID через индекс.

После удаления исходный UUID хранится непосредственно в YAML под `!xml/uuid`,
поэтому скрытая копия в индексе не требуется.

## Диагностика

Ошибки должны различать три случая:

- UUID metadata-ссылка без тега: требуется `!xml/uuid`;
- `!xml/uuid` содержит не UUID и не `UUID.UUID`: неверное применение тега;
- обычный смысловой путь не существует: прежняя диагностика resolver.

Наличие `!xml/uuid` подтверждает только сохранение битой UUID-ссылки. Оно не
подавляет несвязанные ошибки соседних свойств или всего объекта.

## Проверка

### Парсер и сериализатор YAML

- чтение и запись `!xml/uuid` на значении, элементе списка и ключе;
- сохранение регистра и полного текста;
- отказ для карты, последовательности и неправильной формы значения.

### Общий metadataTarget runtime

- классификация одиночного UUID и `UUID.UUID`;
- смысловой путь и обычная строка вне `metadataTarget` не классифицируются;
- XML → YAML возвращает точные координаты UUID-anomaly;
- YAML → XML принимает только точную аннотацию;
- для UUID не вызывается lookup или resolver;
- смысловая ссылка сохраняет прежнее поведение и вызывает resolver.

### Интеграция импорта

- одиночный UUID в списке `FunctionalOptions` импортируется как
  `!xml/uuid` до контрольного экспорта;
- `DesignTimeRef` вида `UUID.UUID` импортируется как `!xml/uuid` и возвращается
  с исходным `xsi:type` и текстом;
- UUID в YAML-ключе получает аннотацию ключа и round-trip без изменения;
- первый проход по-прежнему только формирует индексы и не классифицирует UUID.

### Регрессия и приёмка

- round-trip `CashdeskDev_3_32_26_0_setup1c` проходит импорт, синхронизацию и
  сравнение XML;
- `pnpm test`, `pnpm type-check`, `pnpm test:architecture:rules` и
  `pnpm test:architecture` проходят;
- `pnpm duplicates -- --base <origin/develop>` не находит новых дублей.

## Критерии готовности

1. Все UUID и `UUID.UUID` в metadata-ссылках сериализуются как `!xml/uuid`.
2. Ни один такой occurrence не обращается к индексу и не заменяется смысловым
   путём.
3. UUID без тега нельзя синхронизировать в XML.
4. Смысловые ссылки сохраняют прежнюю проверку существования.
5. Собственные UUID объектов не изменяются.
6. Cashdesk проходит полный round-trip без потери XML.

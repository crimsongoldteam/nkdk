# AppearanceFields String Values Design

## Контекст

`AppearanceFields.Текст` и `AppearanceFields.Формат` используют DCS `DesignTimeValue`, поэтому одно свойство может содержать разные XML-формы:

- `xs:string`;
- `v8:LocalStringType`;
- `v8:LocalFormattedStringType`;
- `dcscor:Field`;
- `xsi:nil="true"`;
- существующий `SettingsParameterValue` без узла `dcscor:value`.

Текущая специальная канонизация `AppearanceFields` поддерживает только строковые формы. При импорте ERP значение `Текст` с `xsi:type="dcscor:Field"` корректно попадает в модель как `{ type: "Field", value }`, но затем отклоняется с ошибкой `AppearanceFields XML: неподдерживаемое строковое значение`.

Ранее `dcscor:Field` сохранялся в YAML как явное `Тип: Поле`. Поддержка выпала при упрощении YAML строк оформления; это отдельный от строковых форм случай, который требуется вернуть.

## Цели

- Вернуть полный YAML round-trip для `dcscor:Field` в `AppearanceFields.Текст` и `AppearanceFields.Формат`.
- Оставить наиболее частый `xs:string` в короткой форме.
- Представлять многоязычную строку однозначно, не резервируя имена языков `Тип`, `Значение`, `Текст`, `Форматированный` или служебные имена.
- Однозначно различать пустую строку, пустую многоязычную строку, `xsi:nil` и отсутствующий `dcscor:value`.
- Сохранить существующие служебные поля `SettingsParameterValue`.
- Сделать JSON Schema и импорт YAML структурными и детерминированными, без эвристик по содержимому строк.

## Не входит в задачу

- Семантическая проверка пути для `Тип: Поле`.
- Определение доступных полей в контексте конкретной формы, динамического списка или условного оформления.
- Изменение общего DCS-договора за пределами `AppearanceFields.Текст` и `AppearanceFields.Формат`.
- Применение `!xml`.
- Изменение исходных XML-фикстур.

## YAML-договор

Одинаковые правила действуют для `Текст` и `Формат`. Ниже используется `Текст`.

| Смысл | Канонический YAML | XML |
|---|---|---|
| обычная строка | `Текст: Строка` | `xs:string` |
| пустая обычная строка | `Текст: ""` | пустой `xs:string` |
| многоязычная строка | `Текст: { Значение: { ru: Строка } }` | `v8:LocalStringType` |
| пустая многоязычная строка | `Текст: { Значение: {} }` | пустой `v8:LocalStringType` |
| ссылка на поле | `Текст: { Тип: Поле, Значение: Реквизит.Поле }` | `dcscor:Field` |
| форматированная строка | `Текст: { Тип: ФорматированнаяСтрока, Значение: { ru: Строка } }` | `v8:LocalFormattedStringType` |
| пустая форматированная строка | `Текст: { Тип: ФорматированнаяСтрока, Значение: {} }` | пустой `v8:LocalFormattedStringType` |
| nil | `Текст: { Значение: null }` | `xsi:nil="true"` |
| узел значения отсутствует | `Текст: {}` | `dcscor:value` отсутствует |

`Тип` допускает только `Поле` и `ФорматированнаяСтрока`. Для обычной и многоязычной строки `Тип` отсутствует; их вид определяется структурой `Значение`.

Карта языков всегда вложена в `Значение`. Поэтому произвольные имена языков остаются однозначными:

```yaml
Текст:
  Значение:
    Тип: Перевод для языка «Тип»
    Значение: Перевод для языка «Значение»
    Форматированный: Перевод для языка «Форматированный»
```

### Служебные поля

Если присутствует хотя бы одно служебное поле, значение записывается объектом. Допустимы существующие поля:

- `Использовать`;
- `РежимОтображения`;
- `ИдентификаторПользовательскойНастройки`;
- `ПредставлениеПользовательскойНастройки`.

Обычная строка со служебным полем:

```yaml
Текст:
  Значение: Строка
  Использовать: Ложь
```

Многоязычная строка со служебным полем:

```yaml
Текст:
  Значение:
    ru: Строка
  Использовать: Ложь
```

Ссылка на поле со служебным полем:

```yaml
Текст:
  Тип: Поле
  Значение: Реквизит.Поле
  Использовать: Ложь
```

## Различение форм

Импорт YAML выбирает форму только по структуре:

1. строковый скаляр — `xs:string`;
2. объект без `Тип` и со строковым `Значение` — `xs:string` в полной форме;
3. объект без `Тип` и с объектом в `Значение` — `v8:LocalStringType`;
4. объект без `Тип` и с `Значение: null` — `xsi:nil="true"`;
5. объект без `Тип` и без `Значение` — существующий параметр без `dcscor:value`;
6. `Тип: Поле` — `dcscor:Field`, `Значение` обязательно является строкой;
7. `Тип: ФорматированнаяСтрока` — `v8:LocalFormattedStringType`, `Значение` обязательно является картой языков.

Неизвестный `Тип`, неверная форма `Значение` и лишние поля отклоняются JSON Schema и импортом YAML.

## Поток данных

### XML → модель → YAML

Общий DCS-слой продолжает импортировать конкретный XML-тип в существующую модель `SettingsParameterValue`. Граница `AppearanceFields` только выбирает каноническое YAML-представление:

- короткий скаляр для `xs:string` без служебных полей;
- объект с `Значение` для остальных неявно типизированных форм;
- объект с `Тип` для поля и форматированной строки;
- служебные поля добавляются в тот же объект.

### YAML → модель → XML

Граница `AppearanceFields` нормализует согласованный YAML в общий `SettingsParameterValue`/`MetadataDcsMetadataValue`. Общий DCS-слой экспортирует модель в соответствующий `dcscor:value`. Определение XML-типа не использует reference и не угадывает тип по строковому содержимому.

## Validation и известное ограничение

JSON Schema принимает объединение короткой строки и закрытых объектных вариантов. Для `Тип: Поле` schema проверяет наличие строкового `Значение`, но не существование и не допустимость пути.

Ограничение фиксируется в `.agents/restrictions.md`: перед семантической validation необходимо отдельно определить доступные источники полей и правила разрешения пути в контексте конкретного оформления.

## Обработка ошибок

- `Тип: Поле` без строкового `Значение` — ошибка validation/import.
- `Тип: ФорматированнаяСтрока` без карты языков — ошибка validation/import.
- Неизвестный `Тип` — ошибка validation/import.
- Лишнее поле в закрытом объекте — ошибка validation/import.
- Семантически неизвестный путь при `Тип: Поле` пока не является ошибкой; действует зафиксированное ограничение.

## Проверки

Наблюдаемые договоры покрываются на самом узком стабильном уровне:

- XML → YAML для всех девяти форм из таблицы, в первую очередь регрессия `dcscor:Field`;
- YAML → модель для короткой строки, вложенной карты языков, `Поле`, `ФорматированнаяСтрока`, nil и отсутствующего значения;
- YAML → XML для различения пустой строки, пустой многоязычной строки, nil и отсутствующего `dcscor:value`;
- служебные поля на представителе обычной строки, многоязычной строки и поля;
- JSON Schema принимает все канонические формы и отклоняет неизвестный `Тип`, неверное `Значение` и лишние поля;
- карта языков с ключами `Тип`, `Значение` и `Форматированный` импортируется как `LocalStringType`;
- полный round-trip ERP проходит импорт и сохраняет исходный `dcscor:Field`.

Существующие XML-фикстуры не изменяются. После целевых тестов выполняются `pnpm type-check`, `pnpm test` и проверка новых дублей относительно базового коммита; затем повторяется `round-trip-yaml` для ERP.

## Риски

- YAML-договор строк `AppearanceFields` изменяется: прежняя голая карта языков и прежняя форма форматированной строки больше не являются каноническими.
- Различие `{}` и `{ Значение: {} }` обязательно: первая форма сохраняет отсутствие `dcscor:value`, вторая — пустой `LocalStringType`.
- Семантическая validation поля намеренно не включается в эту реализацию и не должна подменяться эвристикой по строке.

# XML-представления значений в YAML без снимка конфигурации

## Цель

После этого изменения снимок конфигурации не хранит перечисленные в документе
XML-представления значений. Обычную форму экспорт восстанавливает по виду
объекта, правилу свойства и эффективному типу, а редкая значимая для round-trip
форма остаётся видимой в YAML через `!xml`.

Смысловые и несовместимые значения `ЗначениеЗаполнения` продолжают храниться в
YAML по действующему договору.

## Граница изменения

Это первая часть перехода. Она не меняет структуру, кодек или физическое
хранение действующего снимка: сборщики перестают записывать перечисленные
XML-сведения, а экспорт — читать их. Существующие поля формата пока остаются,
но не используются этими правилами.

Новая структура снимка, удаление универсального раздела XML-состояния и переход
на LMDB описаны отдельно в
`2026-08-11-lmdb-configuration-index-design.md`. Состояние расширений в эту
часть не входит и будет удалено из снимка отдельным изменением.

## Подтверждённые формы пустого `FillValue`

| XML | Где встречается | Представление в YAML |
|---|---|---|
| `<FillValue xsi:nil="true"/>` | Обычный реквизит с единственным строковым типом | `ЗначениеЗаполнения: !xml Nil` |
| `<FillValue xsi:nil="true"/>` | Обычный реквизит другого или составного типа | Поле отсутствует; экспортируется как канонический `xsi:nil` |
| `<xr:FillValue xsi:nil="true"/>` | Стандартный реквизит | Поле отсутствует; экспортируется как канонический `xsi:nil` |
| `<FillValue xsi:type="xs:string"/>` | Обычный строковый реквизит | Поле отсутствует; экспорт строит пустой `xs:string` по типу |
| `<xr:FillValue xsi:type="xs:string"/>` | Стандартные `Code`, `Description`, `Number` | `ЗначениеЗаполнения: !xml String` |
| `<FillValue xsi:type="xr:DesignTimeRef"/>` или `<xr:FillValue …/>` | Обычный или стандартный ссылочный реквизит | `ЗначениеЗаполнения: !xml DesignTimeRef` |
| `<xr:FillValue xsi:type="v8:TypeDescription"/>` | Стандартный реквизит `ValueType` | `ЗначениеЗаполнения: !xml TypeDescription` |
| `<FillValue xsi:type="v8:Null"/>` | Поле внешнего источника данных | `ЗначениеЗаполнения: !xml Null` |

Пустой `<FillValue xsi:type="v8:Null"/>` подтверждён только в полях внешнего
источника данных из исследовательских фикстур `all`: один исходный тип поля —
`xs:string`, другой — `xs:base64Binary`. Поэтому `v8:Null` нельзя вывести из
эффективного типа поля и он сохраняется явно через `!xml Null`.

Во всём исследованном каталоге `round-trip-compact/cf` у обычных реквизитов с
единственным типом `xs:string` найдено 60 351 пустое значение `xs:string` и
18 981 значение `xsi:nil`. Обе формы встречаются при одинаковых длинах и
режимах допустимой длины строки, поэтому выбор нельзя вывести из полного
описания типа. Канонический пустой `xs:string` не требует маркера, а
неканонический `xsi:nil` сохраняется как `!xml Nil`.

## Каноническое восстановление

### Булевое значение заполнения

Для реквизита с единственным эффективным типом `Булево` оба значения являются
смысловыми. Они не считаются неявными и не требуют транспортного тега:

| XML | YAML |
|---|---|
| `<FillValue xsi:type="xs:boolean">true</FillValue>` | `ЗначениеЗаполнения: Истина` |
| `<FillValue xsi:type="xs:boolean">false</FillValue>` | `ЗначениеЗаполнения: Ложь` |
| отсутствующий, пустой или `xsi:nil` FillValue | поле `ЗначениеЗаполнения` отсутствует |

Тот же договор действует для стандартного реквизита, чья предметная политика
разрешает булевое значение заполнения, включая `DeletionMark`. Для обычных
`Истина` и `Ложь` тег `!xml` не используется.

Предметный запрет стандартного реквизита имеет приоритет над его техническим
булевым типом. Поэтому ошибочный булевый FillValue у `Predefined` сохраняется
как `ЗначениеЗаполнения: !xml Ложь`. Булевый FillValue у ссылочного `Parent`
также несовместим и сохраняется как `ЗначениеЗаполнения: !xml Ложь`. Эти две
аномалии исследуются и реализуются отдельно от общего булевого договора;
обычная `Ложь` без тега для них недопустима.

### Обычный реквизит

Если `ЗначениеЗаполнения` отсутствует, экспорт использует эффективный тип
реквизита:

| Эффективный тип | Канонический XML |
|---|---|
| Единственный тип `Строка` | `<FillValue xsi:type="xs:string"/>` |
| Другой единственный тип | `<FillValue xsi:nil="true"/>` |
| Составной тип | `<FillValue xsi:nil="true"/>` |

Пустая строка в составном типе является выбором строковой альтернативы и
хранится смысловым YAML-значением:

```yaml
ЗначениеЗаполнения: ""
```

Она экспортируется как `<FillValue xsi:type="xs:string"/>`.

Исходный `xsi:nil` у реквизита с единственным строковым типом сохраняется явно:

```yaml
ЗначениеЗаполнения: !xml Nil
```

Экспорт восстанавливает `<FillValue xsi:nil="true"/>`.

### Стандартный реквизит

Если `ЗначениеЗаполнения` отсутствует, экспорт строит
`<xr:FillValue xsi:nil="true"/>` независимо от эффективного типа стандартного
реквизита.

Пустой типизированный XML сохраняется явно:

```yaml
СтандартныеРеквизиты:
  Наименование:
    ЗначениеЗаполнения: !xml String
  ТипЗначения:
    ЗначениеЗаполнения: !xml TypeDescription
```

Результат:

```xml
<xr:FillValue xsi:type="xs:string"/>
<xr:FillValue xsi:type="v8:TypeDescription"/>
```

## Импорт XML → YAML

Импорт сначала определяет владельца, вид реквизита и эффективный тип, затем
обрабатывает пустой `FillValue`:

1. `xsi:nil="true"` обычного реквизита с единственным строковым типом
   импортируется как `!xml Nil`.
2. Остальные канонические `xsi:nil="true"` удаляются из YAML.
3. Пустой `xs:string` обычного реквизита с единственным строковым типом
   удаляется как каноническое значение.
4. Пустой `xs:string` обычного реквизита с составным типом импортируется как
   смысловая пустая строка.
5. Пустой `xs:string` стандартного реквизита импортируется как `!xml String`.
6. Пустой `xr:DesignTimeRef` импортируется по действующему договору как
   `!xml DesignTimeRef`.
7. Пустой `v8:TypeDescription` стандартного `ValueType` импортируется как
   `!xml TypeDescription`.
8. Пустой `v8:Null` поля внешнего источника данных импортируется как
   `!xml Null`.

Непустое корректное значение импортируется обычным смысловым значением.
Несовместимое значение остаётся в YAML с действующим `!xml <исходное
значение>` и не переносится в снимок.

## Экспорт YAML → XML

Экспорт различает три состояния:

| YAML | Действие |
|---|---|
| Поле отсутствует | Построить канонический пустой `FillValue` |
| Обычное значение, включая `""` | Проверить по эффективному типу и экспортировать смысловое значение |
| Зарегистрированный `!xml` | Построить соответствующую точную форму XML |

Поддерживаемые пустые транспортные значения ограничены закрытым списком:

| Значение после `!xml` | XML-тип |
|---|---|
| `Nil` | `xsi:nil="true"` без `xsi:type` |
| `String` | `xs:string` |
| `DesignTimeRef` | `xr:DesignTimeRef` |
| `TypeDescription` | `v8:TypeDescription` |
| `Null` | `v8:Null` |

`!xml Nil` разрешён только для обычного реквизита с единственным строковым
типом. `!xml String` разрешён только для строкового стандартного реквизита,
`!xml TypeDescription` — только для стандартного `ValueType`, а
`!xml DesignTimeRef` — только там, где действующий обработчик допускает
ссылочный транспорт. `!xml Null` разрешён только для `FillValue` поля внешнего
источника данных.

## `FillValue` и снимок конфигурации

Сборщик снимка не записывает для `FillValue` поля `xsiNil`, `explicitEmpty`,
`xsiType` и `xmlText`. Экспорт `FillValue` не читает эти поля из снимка.

Существующие записи старого снимка игнорируются после перехода на новый
договор. Отдельная миграция данных снимка не требуется: снимок является
восстанавливаемым локальным индексом и может быть создан повторным import.

## `MinValue` и `MaxValue`

### Каноническое представление

Числовое значение хранится в полях `МинимальноеЗначение` и
`МаксимальноеЗначение` обычным YAML-числом. XML-форму задаёт правило свойства:

| Контекст | Канонический XML |
|---|---|
| Реквизит метаданных | `xsi:type="xs:string"` |
| `InputField` управляемой формы | `xsi:type="xs:decimal"` |
| `TrackBarField`, `ProgressBarField` и другие свойства обычного числового правила | Нет `xsi:type` |
| Значение отсутствует, а XML-элемент обязателен по правилу | `xsi:nil="true"` |

Если исходные `xsi:type` или текст числа отличаются от канонического
представления, импорт сохраняет точную форму транспортным значением:

```yaml
МинимальноеЗначение: !xml "String 1"
МаксимальноеЗначение: !xml "Decimal 001.00"
МинимальноеЗначение: !xml "Raw xs:dateTime исходный-текст"
МаксимальноеЗначение: !xml "Raw - нетипизированный-текст"
```

Маркеры `String` и `Decimal` задают известный XML-тип; оставшаяся часть после
первого пробела является точным текстом XML без числовой нормализации. Маркер
`Raw` сохраняет неподдерживаемый `xsi:type` и произвольный исходный текст:

| Маркер | XML-тип | Текст XML |
|---|---|---|
| `String <текст>` | `xs:string` | `<текст>` |
| `Decimal <текст>` | `xs:decimal` | `<текст>` |
| `Raw <QName> <текст>` | `<QName>` без преобразования | `<текст>` без проверки числа |
| `Raw - <текст>` | Нет `xsi:type` | `<текст>` без проверки числа |

Имя XML-элемента определяется правилом свойства и не повторяется в маркере.

Результат примера:

```xml
<MinValue xsi:type="xs:string">1</MinValue>
<MaxValue xsi:type="xs:decimal">001.00</MaxValue>
<MinValue xsi:type="xs:dateTime">исходный-текст</MinValue>
<MaxValue>нетипизированный-текст</MaxValue>
```

### Условие применения `!xml`

Импорт сначала вычисляет канонический XML из YAML-числа без reference XML. Если
он совпадает с исходным XML по наличию `xsi:type` и точному тексту, в YAML
остаётся обычное число. Если отличается хотя бы тип или текст, импорт записывает
`!xml String …` либо `!xml Decimal …`. Неподдерживаемый XML-тип или текст,
который не является числом, импортируются как `!xml Raw …`; смысловая проверка
числа к ним не применяется.

В ERP это сохраняет пять `InputField`, у которых числовой атрибут формы имеет
тип `xs:decimal`, но `MinValue` или `MaxValue` записан как `xs:string`. Остальные
исследованные значения ERP и конфигурации `all` восстанавливаются канонически.
Сопоставление с типом связанного реквизита, его `NumberQualifiers` и параметрами
`InputField` не выявило правила выбора `xs:string`: одинаковые наборы параметров
встречаются и с `xs:string`, и с `xs:decimal`. Поэтому `xs:string` у
`InputField` не выводится из параметров и сохраняется через `!xml`.

`MinValue` и `MaxValue` не записываются в снимок конфигурации. Экспорт не читает
их XML-тип и текст из снимка или reference XML.

### Диагностики `MinValue` и `MaxValue`

- Разрешены маркеры `String`, `Decimal` и `Raw`.
- Для `String` и `Decimal` обязателен непустой текст, который разбирается как
  конечное число; при экспорте используется исходная запись без форматирования.
- Для `Raw` обязателен QName XML-типа либо `-`; оставшаяся часть является
  произвольным точным текстом XML и может быть пустой.
- Маркер разрешён только свойству типа `MinMaxValue`.

### Проверки `MinValue` и `MaxValue`

1. Канонический `xs:string`, `xs:decimal` и нетипизированный XML импортируются
   обычным YAML-числом и восстанавливаются без reference XML.
2. `InputField` с исходным `xs:string` импортируется как `!xml "String …"` и
   сохраняет тип при экспорте.
3. Неканонический текст вроде `001.00` сохраняется дословно через маркер.
4. Неподдерживаемый `xsi:type` и нечисловой текст сохраняются через `Raw`.
5. Неизвестный маркер и некорректная форма payload отклоняются.
6. Round-trip выполняется без чтения или записи сведений в снимке.

## Канонические свойства реквизита

Следующие свойства не требуют сведений из снимка. Если поле отсутствует в
YAML, его значение однозначно задаётся `implicitValueYAML` действующего правила:

| Поле YAML | Элемент XML | Значение при отсутствии в YAML |
|---|---|---|
| `РежимПароля` | `PasswordMode` | `Ложь` |
| `ВыделятьОтрицательные` | `MarkNegatives` | `Ложь` |
| `МногострочныйРежим` | `MultiLine` | `Ложь` |
| `РасширенноеРедактирование` | `ExtendedEdit` | `Ложь` |
| `ЗаполнятьИзДанныхЗаполнения` | `FillFromFillingValue` | `Ложь` |
| `БыстрыйВыбор` | `QuickChoice` | `Авто` |
| `СозданиеПриВводе` | `CreateOnInput` | `Авто` |
| `ИсторияВыбораПриВводе` | `ChoiceHistoryOnInput` | `Авто` |
| `ПроверкаЗаполнения` | `FillChecking` | `НеПроверять` |
| `ВыборГруппИЭлементов` | `ChoiceFoldersAndItems` | `Элементы` |
| `Индексирование` | `Indexing` | `НеИндексировать` |

Экспорт записывает элемент, когда свойство предусмотрено правилом объекта. Его
значение берётся из YAML, а при отсутствии поля — из таблицы выше. Имя элемента,
родитель и namespace-префикс определяются действующим правилом, поэтому отдельно
в снимке не хранятся.

Присутствие этих элементов в исходном XML не является смысловым состоянием.
Записи `xml.present` для них не создаются и не читаются; `!xml` для различения
явного значения по умолчанию и отсутствующего элемента не используется.

### Проверки канонических свойств реквизита

1. Значение, отличное от значения по умолчанию, сохраняется в YAML и
   восстанавливается в XML.
2. Значение по умолчанию отсутствует в YAML и восстанавливается из правила.
3. Экспорт с пустым снимком формирует тот же XML, что и экспорт со снимком.
4. Сборщик снимка не создаёт для перечисленных свойств `xml.present`.

## `ИспользоватьСтандартныеКоманды`

Каноническое значение свойства зависит от вида объекта и задаётся его правилом:

| Виды объектов | `implicitValueYAML` и `defaultValueXML` |
|---|---|
| Справочник, документ, отчёт, обработка, общая форма, планы, регистры и остальные правила со значением `true` | `Истина` |
| Перечисление, куб внешнего источника данных, таблица измерений внешнего источника данных | `Ложь` |

При отсутствии поля `ИспользоватьСтандартныеКоманды` в YAML экспорт использует
`implicitValueYAML` действующего правила. Если значение отличается от него, оно
хранится в YAML явно. `defaultValueXML` того же правила задаёт каноническое
значение XML.

Присутствие элемента `UseStandardCommands` не записывается в снимок. Экспорт не
читает для него `xml.present` и не использует `!xml`; элемент записывается по
правилу объекта.

### Проверки `ИспользоватьСтандартныеКоманды`

1. Для правила с каноническим значением `Истина` отсутствие поля в YAML даёт
   `<UseStandardCommands>true</UseStandardCommands>`.
2. Для правила с каноническим значением `Ложь` отсутствие поля в YAML даёт
   `<UseStandardCommands>false</UseStandardCommands>`.
3. Значение, отличное от канонического, сохраняется в YAML и XML.
4. Round-trip выполняется с пустым снимком; `xml.present` не создаётся.

## `ВключатьСправкуВСодержание`

Каноническое значение свойства задаётся правилом вида объекта:

| Вид объекта | `implicitValueYAML` и `defaultValueXML` |
|---|---|
| Подсистема | `Истина` |
| Остальные виды с этим свойством | `Ложь` |

При отсутствии поля `ВключатьСправкуВСодержание` в YAML экспорт использует
`implicitValueYAML` действующего правила. Отличающееся значение хранится в YAML
явно. Элемент `IncludeHelpInContents` записывается по правилу объекта.

Присутствие элемента не хранится в снимке: `xml.present` для него не создаётся
и не читается, `!xml` не используется. Во всех исследованных применимых объектах
конфигурации `trade` элемент присутствует в исходном XML.

### Проверки `ВключатьСправкуВСодержание`

1. Для подсистемы отсутствие поля в YAML восстанавливается как `true` в XML.
2. Для остальных правил отсутствие поля в YAML восстанавливается как `false`.
3. Отличающееся значение сохраняется в YAML и XML.
4. Round-trip выполняется с пустым снимком; `xml.present` не создаётся.

Все свойства среды исполнения общего модуля имеют канонические значения,

## Одноязычная строка СКД

Свойство типа `DcsLocalStringType` обычно экспортируется как локализованная
строка `v8:LocalStringType`. Многоязычное значение всегда использует эту форму;
для одноязычного значения она также является канонической:

```yaml

```

```xml
<dcssch:title xsi:type="v8:LocalStringType">

    <v8:content>Текст</v8:content>
  </v8:item>

```

остаётся видимой в YAML:

```yaml

```

Экспорт восстанавливает:

```xml
<dcssch:title xsi:type="xs:string">Текст</dcssch:title>
```

Маркер `String` разрешён только свойству типа `DcsLocalStringType`. Текст после
первого пробела является смысловым значением строки и может быть изменён
пользователем; маркер сохраняет только выбор XML-контейнера `xs:string`.

Во всех 27 исследованных конфигурациях найдено 1 220 значений `xs:string` и
28 469 значений `v8:LocalStringType` для зарегистрированных свойств этого типа.
Выбор контейнера не записывается в снимок конфигурации.

### Проверки одноязычной строки СКД

1. Обычный одноязычный YAML-текст экспортируется как `v8:LocalStringType`.

5. Round-trip выполняется с пустым снимком.

## Пустой форматированный заголовок элемента формы

У `LabelDecoration` и `ExtendedTooltip` различаются три состояния заголовка:
отсутствующий `Title`, непустое форматированное значение и явно присутствующая
пустая форматированная строка. Последняя сохраняется пустым маркером:

```yaml
Заголовок: !xml
```

Экспорт восстанавливает точную форму:

```xml
<Title formatted="true"/>
```

Маркер разрешён только свойству `title` элементов `LabelDecoration` и
`ExtendedTooltip`. Отсутствующее поле не создаёт `Title`, а непустой заголовок
остаётся обычным смысловым значением YAML.

Во всех 27 исследованных конфигурациях распределение имеет вид:

| Владелец `Title` | Отсутствует | Пустой `formatted="true"` | Непустой |
|---|---:|---:|---:|
| `LabelDecoration` | 71 559 | 621 | 190 296 |
| `ExtendedTooltip` | 2 760 583 | 449 | 22 465 |

Снимок не хранит для заголовка `explicitEmpty` и не участвует в экспорте.

### Проверки пустого форматированного заголовка

1. Отсутствующее поле `Заголовок` не создаёт `Title`.
2. Непустое значение экспортируется действующим правилом форматированной строки.
3. `Заголовок: !xml` экспортируется как `<Title formatted="true"/>`.
4. Маркер у другого элемента или свойства отклоняется.
5. Round-trip выполняется с пустым снимком.

При экспорте маркер восстанавливает:

## Режимы совместимости конфигурации

Конфигурация всегда экспортирует оба XML-элемента:

| Поле YAML | Элемент XML | Значение при отсутствии в YAML |
|---|---|---|
| `РежимСовместимостиРасширенияКонфигурации` | `ConfigurationExtensionCompatibilityMode` | Значение `implicitValueYAML` правила |
| `РежимСовместимости` | `CompatibilityMode` | Значение `implicitValueYAML` правила |

Значение, отличающееся от значения правила, хранится обычным полем YAML. В
исследованном наборе оба элемента присутствуют во всех 27 конфигурациях.
Снимок и `!xml` не используются.

### Проверки режимов совместимости

1. При отсутствии полей экспорт создаёт оба элемента со значениями правил.
2. Явные значения сохраняются в YAML и XML.
3. Сборщик не создаёт для этих свойств `present`.
4. Round-trip выполняется с пустым снимком.

## Настройки типа `СписокЗначений` реквизита формы

Если реквизит формы имеет единственный тип `СписокЗначений`
(`v8:ValueListType`) и поле `ТипЗначения` отсутствует, экспорт канонически
создаёт пустое описание типа элементов:

```xml
<Settings xsi:type="v8:TypeDescription"/>
```

Непустой `ТипЗначения` остаётся обычным смысловым значением YAML и формирует
непустой `Settings`. Если пустого `Settings` не было в исходном XML, это редкое
отклонение сохраняется пустым маркером:

```yaml
Тип: СписокЗначений
ТипЗначения: !xml
```

Маркер означает «не создавать `Settings`». Он разрешён только полю
`ТипЗначения` реквизита формы с единственным типом `СписокЗначений`. Для
составного типа с `СписокЗначений` отсутствие `Settings` является каноническим
и маркер не требуется.

Распределение по 27 исследованным конфигурациям:

| Форма | Количество |
|---|---:|
| Единственный `СписокЗначений`, пустой `Settings` | 11 170 |
| Единственный `СписокЗначений`, непустой `Settings` | 4 476 |
| Единственный `СписокЗначений`, `Settings` отсутствует | 1 133 |
| Составной тип с `СписокЗначений`, `Settings` отсутствует | 50 |

Пустой `Settings` не найден ни у одного другого типа. В 23 конфигурациях
одновременно встречаются пустой и отсутствующий `Settings`, поэтому исходное
отсутствие нельзя вывести из конфигурации целиком.

Снимок не хранит для `Settings` поля `explicitEmpty` и `xsiType`.

### Проверки настроек `СписокЗначений`

1. Единственный `СписокЗначений` без `ТипЗначения` создаёт пустой `Settings`.
2. Непустой `ТипЗначения` создаёт содержательный `Settings`.
3. `ТипЗначения: !xml` не создаёт `Settings`.
4. Составной тип без `ТипЗначения` не создаёт `Settings` без маркера.
5. Маркер в другом контексте отклоняется.
6. Round-trip выполняется с пустым снимком.

## Нестандартное XML-имя встроенного элемента формы

Имя одиночного встроенного элемента формы обычно вычисляется из имени
владельца и зарегистрированного правила. Это относится к расширенной подсказке,
контекстному меню, командной панели, строке поиска, управлению поиском,
состоянию просмотра и вложенной таблице диаграммы Ганта.

Если исходный XML `_name` отличается от вычисленного имени, точное значение
хранится внутри этого элемента в транспортном поле:

```yaml
РасширеннаяПодсказка:
  Имя: !xml СтароеИмяExtendedTooltip
```

Для пустого XML `_name` используется явная пустая строка:

```yaml
РасширеннаяПодсказка:
  Имя: !xml ""
```

При отсутствии поля `Имя` экспорт вычисляет XML `_name` по владельцу и правилу.
При наличии `Имя: !xml …` экспорт использует точное значение после тега. Оно
не изменяется автоматически при переименовании владельца: пользователь явно
зафиксировал исходное XML-имя и при необходимости изменяет его самостоятельно.

Поле `Имя` не является смысловым свойством встроенного элемента. Обычное
значение без `!xml` недопустимо. Внутренняя validation-схема принимает только
зарегистрированную форму `!xml`, а схема подсказок полностью скрывает поле.
Транспортное имя не участвует в построении `logicalAddress`.

Исходный XML `_name` не записывается в снимок конфигурации и не читается из
него при экспорте.

### Проверки нестандартного XML-имени

1. Вычисляемое имя не создаёт поле `Имя` в YAML.
2. Старый английский суффикс и произвольное имя импортируются как точное
   `Имя: !xml …` и восстанавливаются без снимка.
3. Пустое имя проходит round-trip через `Имя: !xml ""`.
4. Переименование владельца не изменяет явно сохранённое имя.
5. `Имя` без `!xml` отклоняется validation.
6. Схема подсказок не содержит поле `Имя`.

## Нестандартный XML-префикс поля `Тип`

Обычный тип хранится смысловым значением YAML и экспортируется в канонической
XML-форме:

```yaml
Тип: Диаграмма
```

Если исходный XML использует для этого типа нестандартный namespace-префикс,
необходимый для полного round-trip, префикс сохраняется непосредственно в
значении `!xml`:

```yaml
Тип: !xml d7p1:Диаграмма
```

Здесь `d7p1` — точный исходный XML-префикс, а `Диаграмма` — обычное русское
представление смыслового типа. XML-имя `Chart` и namespace
`http://v8.1c.ru/8.2/data/chart` определяются реестром типа. Экспорт формирует:

```xml
<Type>
  <v8:Type xmlns:d7p1="http://v8.1c.ru/8.2/data/chart">d7p1:Chart</v8:Type>
</Type>
```

Импорт применяет `!xml` только тогда, когда исходный префикс отличается от
префикса канонического экспорта. Тег не меняет смысловой тип и не содержит
namespace URI или XML-имя: они должны однозначно определяться русским именем
типа. Неизвестный тип либо несовместимый с ним префикс является ошибкой.

Для ссылочных типов предопределённых элементов ПВХ префикс не сохраняется в
`!xml`: он однозначно определяется глубиной элемента в дереве
`Predefined/Item`.

| Глубина `Item` | Префикс |
|---:|---|
| 1 | `d4p1` |
| 2 | `d6p1` |
| 3 | `d8p1` |
| 4 | `d10p1` |

Общее правило: номер в префиксе равен `2 × глубина + 2`. Проверка всех
конфигураций из исследуемого набора обнаружила 3 777 таких значений в 87
файлах и ни одного исключения. Действующий экспорт уже вычисляет эти префиксы
по вложенности, в том числе одинаковый префикс для нескольких типов одного
составного `TypeDescription`. Поэтому, например, обычное значение
`Справочник.Товары` остаётся без `!xml`.

Выбор дочернего элемента `v8:Type` или `v8:TypeSet` также не сохраняется ни в
снимке, ни в `!xml`. Он однозначно определяется реестром типов: конкретный
ссылочный тип, например `Справочник.Товары`, экспортируется как `v8:Type`,
общий тип семейства, например `Справочник`, — как `v8:TypeSet`, а определяемый
тип и характеристика — как `v8:TypeSet` по правилу соответствующего вида.

В исследуемом наборе найдено 2 651 103 значения `v8:Type` и 88 815 значений
`v8:TypeSet`; ни одно XML-имя типа не встречается в обеих формах. Поэтому
хранение контейнера дублировало бы реестр типов.

Форма `<Source xsi:type="v8:TypeSet">` не поддерживается. Она не найдена ни в
одной из 27 исследованных конфигураций и существовала в проекте только как
искусственная фикстура. Импорт не сохраняет этот атрибут, а экспорт всегда
создаёт канонический `Source` с дочерними элементами, выбранными реестром типов.

Снимок не хранит `xml.present`, префикс или текст для согласованного случая:
полную XML-форму определяют YAML и реестр типов.

### Проверки нестандартного префикса `Тип`

1. `Тип: Диаграмма` экспортируется с каноническим префиксом.
2. `Тип: !xml d7p1:Диаграмма` восстанавливает точный префикс `d7p1` и его
   namespace.
3. Неизвестный тип, префикс без типа и несовместимая пара отклоняются.
4. Ссылочные типы предопределённых элементов ПВХ получают префиксы `d4p1`,
   `d6p1`, `d8p1`, `d10p1` по глубине без `!xml`.
5. Реестр типов выбирает `v8:Type` или `v8:TypeSet` без `!xml` и снимка.
6. Round-trip выполняется с пустым снимком.

## Другие свойства типа `MetadataValue`

Вне `FillValue` правила верхнего уровня используют `MetadataValue` только для
`НезаполненноеЗначениеРодителя` внешнего источника данных и
`ЗначениеОтбораВидов` описания характеристик.

`НезаполненноеЗначениеРодителя` при отсутствии значения канонически
экспортируется как `<UnfilledParentValue xsi:nil="true"/>`. Во всех пяти
найденных примерах из исследованных конфигураций используется именно эта форма,
поэтому поле отсутствует в YAML и снимке.

`ЗначениеОтбораВидов` при отсутствии значения канонически экспортируется как
`<xr:TypesFilterValue xsi:nil="true"/>`. Непустые строки, логические значения и
ссылки остаются обычными смысловыми значениями YAML. Пустой типизированный
`DesignTimeRef` сохраняется явно:

```yaml
ЗначениеОтбораВидов: !xml DesignTimeRef
```

Результат:

```xml
<xr:TypesFilterValue xsi:type="xr:DesignTimeRef"/>
```

Во всём исследованном каталоге `round-trip-compact/cf` найдено пять таких
значений: четыре в `acc` и одно в `erp`. Других пустых XML-типов для
`TypesFilterValue` не найдено.

После введения этого маркера свойства типа `MetadataValue` не записывают
`xsiNil` и `xsiType` в снимок конфигурации и не читают их оттуда при экспорте.

## Полностью дефолтные стандартные реквизиты

Присутствующая в XML коллекция `StandardAttributes`, все элементы которой
совпадают с каноническими значениями rules.ts, сохраняется действующим пустым
маркером:

```yaml
СтандартныеРеквизиты: !xml
```

Маркер хранит только отличие присутствующей коллекции от отсутствующей. Состав
стандартных реквизитов и их канонический XML экспорт строит по виду владельца и
rules.ts. Если коллекции не было в XML, поле отсутствует в YAML и при экспорте
не создаётся.

Смысловые изменения отдельных стандартных реквизитов остаются обычным YAML-
отображением. Динамические `ExtDimension*` также записываются явно и не
сворачиваются в пустой маркер.

Механизм уже выполняет XML → YAML → XML без reference XML и снимка
конфигурации. В исследованном проекте `sed_nkdk` найдено 1030 применений
`СтандартныеРеквизиты: !xml`.

## Отсутствующие поля описания характеристик

Четыре строковых свойства имеют XML-default `-1`, поэтому обычное отсутствие
YAML-поля при экспорте создало бы XML-элемент со значением `-1`. Если элемента
не было в исходном XML, отсутствие сохраняется действующим пустым маркером:

```yaml
ПолеПутиКДанным: !xml
ПолеИспользованияМножественныхЗначений: !xml
ПолеКлючаМножественныхЗначений: !xml
ПолеПорядкаМножественныхЗначений: !xml
```

Регистрация точной пары `CharacteristicsDescription + propertyKey` преобразует
отсутствующий XML-элемент в маркер при импорте и выполняет действие `omit` при
экспорте. Непустое значение остаётся обычной строкой YAML, а незарегистрированное
свойство не получает такого поведения.

Механизм не использует reference XML или снимок конфигурации. В исследованном
проекте `sed_nkdk` найдено по четыре применения каждого из четырёх маркеров.

## Явное выравнивание заголовка колонки `Auto`

Для `TableInputField`, `TableLabelField`, `TablePictureField` и
`TableCheckBoxField` значение `Auto` является YAML-default. Обычное отсутствие
поля означает, что `<HeaderHorizontalAlign>` не было в XML. Явно присутствующее
значение сохраняется действующим пустым маркером:

```yaml
ГоризонтальноеПоложениеВШапке: !xml
```

При экспорте маркер восстанавливает:

```xml
<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>
```

Регистрация ограничена четырьмя точными `itemType`; `ColumnGroup` в неё не
входит. Payload после `!xml` не используется, прежняя форма `!xml Авто` не
поддерживается.

Механизм выполняет round-trip без reference XML и снимка конфигурации. В
исследованном проекте `sed_nkdk` найдено девять таких маркеров.

## Исключительный `RowFilter` таблицы формы

Наличие `RowFilter` обычно вычисляется по профилю источника таблицы. Для
`ValueTable`, табличной части и `RegisterRecordSet` экспорт создаёт его
канонически; для непосредственного `DynamicList` и профиля `none` не создаёт.

Если в исходном XML `RowFilter` присутствует вопреки вычисленному профилю
`none`, форма сохраняется действующим маркером:

```yaml
ОтборСтрок: !xml
```

При экспорте маркер восстанавливает:

```xml
<RowFilter xsi:nil="true"/>
```

Финализатор импорта удаляет избыточный маркер для профилей, где `RowFilter` и
так восстанавливается канонически. Регистрация ограничена свойством `rowFilter`
элемента `Table` и не использует payload.

Механизм покрыт интеграционным round-trip без reference XML и снимка
конфигурации. Поэтому сведения о `RowFilter` в снимок не записываются и при
экспорте из него не читаются.

## Пустое определение нестандартной панели

UUID нестандартной панели является значимым состоянием и хранится обычным
YAML-полем. Наличие пустого `panelDef`, которое нельзя вывести только из UUID,
сохраняется отдельным действующим маркером:

```yaml
Панель:
  UUID: 8e10648b-f52d-4ec2-b4dd-87de33778d95
  ПустоеОпределение: !xml
```

При экспорте маркер восстанавливает:

```xml
<panelDef id="8e10648b-f52d-4ec2-b4dd-87de33778d95"/>
```

Без `ПустоеОпределение` пустой `panelDef` для нестандартной панели не создаётся.
Маркер разрешён только нестандартной панели с UUID, у которой нет имени или
представления; другое значение и прежняя форма `UUID: !xml …` отклоняются.

Механизм выполняет round-trip без reference XML и снимка конфигурации. UUID и
маркер полностью определяют результат, поэтому сведения о пустом `panelDef` в
снимок не записываются.

## Несовместимый `ПутьКДанным` элемента формы

Если исходный `DataPath` разрешается в существующее поле, но его тип
несовместим с видом элемента формы, импорт не скрывает исходную некорректность и
не заменяет путь нормализованным смысловым значением. Исходная XML-строка
сохраняется в payload:

```yaml
ПутьКДанным: !xml Объект.Description
```

При экспорте payload записывается дословно, без преобразования служебных имён:

```xml
<DataPath>Объект.Description</DataPath>
```

Например, маркер нужен, когда `CheckBoxField` связан со строковым полем. Для
совместимого пути импорт сохраняет обычный канонический YAML-путь. Неразрешимый
путь обрабатывается отдельным договором битых локальных ссылок.

Механизм работает без reference XML и снимка конфигурации. В исследованном
проекте `sed_nkdk` применений такого маркера не найдено; поведение закреплено
тестами для некорректных исходных конфигураций.

## Битая `DesignTimeRef` по двум UUID

Неразрешимая ссылка типа `MetadataValue`, представленная в XML двумя UUID через
точку, не преобразуется в вымышленный смысловой адрес. Импорт сохраняет точный
текст в payload:

```yaml
ЗначениеЗаполнения: !xml 447e2bd8-fa43-442e-91db-b17634e036d9.c26f06ab-fb3e-46a7-a391-fdccd77b4231
```

При экспорте обработчик восстанавливает:

```xml
<FillValue xsi:type="xr:DesignTimeRef">447e2bd8-fa43-442e-91db-b17634e036d9.c26f06ab-fb3e-46a7-a391-fdccd77b4231</FillValue>
```

Обработчик зарегистрирован для типа свойства `MetadataValue`, поэтому имя
XML-элемента определяется конкретным правилом: это может быть `FillValue`,
`Value`, `app:value`, `v8:Value`, `xr:FillValue` или `xr:TypesFilterValue`.
Маркер разрешён только для строгой формы из двух UUID через точку.

Round-trip покрыт тестом без reference XML и снимка конфигурации. В
исследованных актуальных YAML-проектах применений маркера не найдено.

## Остальные битые ссылки

Все зарегистрированные битые ссылки сохраняются в YAML через `!xml` и не входят
в снимок конфигурации.

Битый элемент состава подсистемы хранит исходный UUID непосредственно на своём
месте в YAML-списке:

```yaml
Состав:
  - Справочник.Товары
  - !xml 447e2bd8-fa43-442e-91db-b17634e036d9
```

Экспорт восстанавливает для тегированного элемента
`<xr:Item xsi:type="xr:MDObjectRef">…</xr:Item>`. Положение ссылки задаётся
положением элемента YAML и отдельно не хранится.

Проектная валидация до разбора элемента как обычной metadata-ссылки проверяет
его через реестр переносчиков битых XML-ссылок. Элемент исключается из проверки
metadata target только тогда, когда одновременно выполнены два условия:

1. соответствующий YAML-скаляр имеет тег `!xml`;
2. зарегистрированный для правила свойства переносчик распознаёт payload и его
   положение в значении свойства.

Например, в составе подсистемы обычная ссылка продолжает участвовать в
проектной валидации, а перенесённая битая `MDObjectRef` — нет:

```yaml
Состав:
  - ОбщаяФорма.ОценитьПриложение
  - !xml 6f583fdc-08d4-45d8-9dd0-45aaff4cb2f4
```

Наличие самого префикса `!xml` в строковом значении недостаточно. Нетегированный
UUID, неизвестный `!xml`, неверный UUID и тег на свойстве, для которого
переносчик не зарегистрирован, остаются ошибками. Тот же порядок применяется к
скалярным значениям и элементам коллекций: валидация использует YAML-путь
элемента относительно значения свойства и не отключается для соседних обычных
ссылок.

Битые локальные ссылки управляемой формы используют тот же договор скаляра или
элемента массива:

```yaml
Команда: !xml Форма.Команда.Несуществующая
Сохранение:
  - Объект.Код
  - !xml 1/0:447e2bd8-fa43-442e-91db-b17634e036d9
```

Договор реализован для зарегистрированных свойств `Command`, `CommandName`,
`Field`, `DataPath`, `xr:DataPath`, `CommandGroup`, `GroupList` и
`UserSettingsGroup`. Имя XML-элемента задаётся правилом свойства, payload
записывается дословно, а положение в коллекции задаётся YAML-массивом.

Round-trip битого `MDObjectRef`, скалярных и списочных локальных ссылок покрыт
тестами без reference XML. Снимок не хранит текст, вид или положение таких
ссылок.

Проектная валидация дополнительно покрывается смешанным составом подсистемы:
обычная ссылка создаёт pending reference, а тегированная битая `MDObjectRef` не
создаёт ни pending reference, ни диагностику неизвестного корня. Отдельные
проверки подтверждают, что нетегированный и нераспознанный payload по-прежнему
диагностируются.

## Диагностики `FillValue`

- Неизвестное значение после `!xml` является ошибкой.
- `!xml Nil` не у обычного реквизита с единственным строковым типом является
  ошибкой.
- `!xml String` у нестрокового или обычного реквизита является ошибкой.
- `!xml TypeDescription` не у стандартного `ValueType` является ошибкой.
- `!xml Null` не у поля внешнего источника данных является ошибкой.
- Пустая строка у обычного составного типа без строковой альтернативы является
  ошибкой проверки значения.
- Несовместимое непустое значение без `!xml` является ошибкой по действующему
  договору `FillValue`.
- `Истина` и `Ложь` разрешены без `!xml` для единственного эффективного типа
  `Булево`; отсутствие поля означает отсутствие значения заполнения.
- `!xml Ложь` у запрещённого `Predefined` и ссылочного `Parent` сохраняет
  ошибочную XML-форму; `Ложь` без тега остаётся ошибкой.

## Проверки `FillValue`

1. Обычный строковый реквизит: `xs:string` импортируется без поля и
   восстанавливается по типу.
2. Обычный строковый реквизит: исходный `xsi:nil` импортируется как `!xml Nil`
   и восстанавливается без нормализации.
3. Обычный нестроковый реквизит: отсутствующее значение экспортируется как
   `xsi:nil`.
4. Обычный составной тип со строкой: пустая строка сохраняется в YAML и
   экспортируется как `xs:string`.
5. Стандартные `Code`, `Description` и строковый `Number`: `!xml String`
   восстанавливает пустой `xs:string`.
6. Стандартный `ValueType`: `!xml TypeDescription` восстанавливает пустой
   `v8:TypeDescription`.
7. Действующий `!xml DesignTimeRef` сохраняет поведение без снимка.
8. Поле внешнего источника данных: `!xml Null` восстанавливает пустой
   `v8:Null` независимо от эффективного типа поля.
9. Непустое корректное и несовместимое `FillValue` сохраняют действующее
   поведение.
10. Булевый реквизит различает `Истина`, `Ложь` и отсутствующее поле без
    использования `!xml` для корректных значений.
11. `Predefined` и `Parent` с булевым `false` сохраняются как `!xml Ложь` и
    рассматриваются отдельными XML-аномалиями.
12. Полный XML → YAML → XML round-trip выполняется с пустым снимком для всех
   перечисленных форм.

## Не входит в изменение

- изменение правил смысловой проверки непустых значений.

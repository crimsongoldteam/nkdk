# Дизайн: стабильный запуск тестов packages/graph

## Контекст

`packages/graph` сейчас запускает основной набор тестов командой `vitest run --no-isolate --sequence.shuffle`.
В этом режиме тестовые файлы делят кэш модулей. Несколько файлов по-разному мокают `falkordb` и `src/internal/connection`, поэтому порядок загрузки влияет на то, чей мок попадёт в уже закэшированный модуль.

Проверка показала:

- `pnpm --filter @nakidka/graph test:isolated` проходит: 89 тестов из 89.
- `vitest run --no-isolate` и `vitest run --no-isolate --sequence.shuffle` падают в зависимости от порядка файлов.
- Падения проявляются как `0 calls` у локальных моков или обращение к реальному `rawCommand` вместо мока.

## Цель

Сделать основной запуск тестов быстрым и полным: `pnpm test` должен выполнять все тесты `packages/graph` без взаимного загрязнения моков.

## Выбранный подход

Основной скрипт `test` в `packages/graph` должен запускать Vitest в обычном изолированном режиме:

```sh
vitest run
```

Старый режим `vitest run --no-isolate --sequence.shuffle` не сохраняется отдельным скриптом.

## Почему так

Обычная изоляция соответствует ожиданиям модульных тестов: каждый файл может задавать свои моки и не зависеть от порядка загрузки соседних файлов.
Это сохраняет полный набор тестов `packages/graph` и не требует переписывать тесты ради специального режима Vitest.

## Изменения

- В `packages/graph/package.json` заменить `test` на `vitest run`.
- Удалить `test:isolated`, потому что после изменения он станет дубликатом основного `test`.
- Не добавлять отдельный стресс-скрипт для режима `--no-isolate`.

## Проверка

После изменения нужно выполнить:

```sh
pnpm --filter @nakidka/graph test
pnpm test
```

Ожидаемый результат для `packages/graph`: все 89 тестов проходят.
Общий `pnpm test` может показать оставшиеся проблемы других пакетов, но `packages/graph` не должен быть причиной падения.

# Отложенное разрешение ссылок при импорте XML → YAML

## Контекст

При импорте часть YAML записывается уже в первом проходе, если подготовленное
значение не помечено как зависящее от общего индекса. Это решение требует заранее
и без полного снимка проекта определить все межфайловые зависимости.

Из-за этого значение заполнения
`Справочник.СправочникРеквизит.ПредопредленноеЗначение` сохраняется с `!xml`,
хотя целевой справочник и его предопределённое значение существуют. Сам
справочник может обрабатываться другим работником, а сведения о нём становятся
доступны всем работникам только после объединения результатов первого прохода.

Проблема не ограничивается одним полем: любой смысловой перевод XML в YAML,
которому для окончательного решения нужны сведения другого объекта, может быть
ошибочно завершён до построения общего индекса.

## Цель

Сделать общий индекс обязательной точкой перед окончательным формированием и
записью всех основных YAML-файлов импорта. Разрешение ссылок в импорте и при
проверке проекта должно опираться на один смысловой механизм.

## Не входит в задачу

- изменение правил применения `!xml`;
- добавление новых видов целей или новых предметных правил;
- проверка смыслового содержимого значений, уже помеченных `!xml`;
- изменение порядка передачи внешних файлов и записи вспомогательных файлов,
  если они не являются основным подготовленным YAML объекта;
- ограничение памяти автоматическим порогом.

## Принятые решения

### Все основные YAML ожидают второй проход

Первый проход больше не определяет, можно ли записать основной YAML досрочно.
Каждый успешно подготовленный `PreparedImportYaml` сохраняется работником до
второго прохода независимо от наличия известных отложенных значений.

Первый проход выполняет следующие действия:

1. читает XML и строит модель;
2. преобразует модель в разобранный YAML-объект;
3. извлекает локальные сведения об объекте, включая сведения владельца и
   предопределённые значения;
4. возвращает вклад в рабочий индекс;
5. удерживает разобранный YAML-объект и данные, необходимые для окончательной
   обработки.

Координатор завершает первый проход всех работников, объединяет их вклады и
фиксирует согласованный рабочий индекс. Только после этого начинается второй
проход.

Во втором проходе каждый работник:

1. читает общий индекс;
2. уточняет все отложенные и зависимые значения;
3. выполняет окончательную обработку импортированного объекта;
4. формирует текст, проверяет и записывает основной YAML;
5. публикует окончательный вклад и освобождает разобранный объект.

Порядок заданий внутри второго прохода не влияет на результат: работники читают
зафиксированный общий индекс первого прохода и не зависят от записи YAML другим
работником во втором проходе.

Если операция завершается до второго прохода или отменяется, работник освобождает
все сохранённые YAML тем же общим путём очистки, который уже используется для
отложенных файлов.

### Единый смысловой механизм разрешения ссылок

Общая часть принимает описание ссылки и доступ к снимку проекта, а возвращает
результат разрешения: цель найдена, отсутствует либо неоднозначна. Она не изменяет
YAML и не формирует сообщения проверки.

Механизм сначала ищет точную цель в общем индексе. Если ссылка обозначает
значение объекта, он использует сведения владельца и зарегистрированный
обработчик значений. Так разрешаются, в частности:

- предопределённые значения справочников;
- значения перечислений;
- пустые ссылки;
- другие зарегистрированные именованные значения объектов.

Импорт использует результат во втором проходе, чтобы определить окончательное
представление исходного XML-значения. Проверка проекта использует тот же механизм
для обычных YAML-значений, но не изменяет файлы. Значения с `!xml` проверка, как и
сейчас, полностью пропускает.

Предметные обработчики остаются зарегистрированы в слоях метаданных, а общий
механизм зависит только от нейтральных договоров индекса, сведений владельца и
реестра обработчиков. Частные проверки по виду объекта не добавляются в
`validation`, `projectState` или другие нейтральные слои.

### Результаты разрешения и `!xml`

Правила применения `!xml` в этой задаче не расширяются:

- найденная совместимая цель сохраняется обычным YAML-значением;
- действительно отсутствующая цель или несовместимый тип сохраняются согласно
  существующему правилу с `!xml`;
- неоднозначная цель сохраняет текущее поведение;
- уже помеченное `!xml` значение не проходит смысловую проверку проекта.

Для исходного
`Catalog.СправочникРеквизит.ПредопредленноеЗначение` общий механизм находит
владельца `СправочникРеквизит` и его предопределённое значение. Поэтому итоговый
YAML содержит:

```yaml
ЗначениеЗаполнения: Справочник.СправочникРеквизит.ПредопредленноеЗначение
```

без `!xml`.

### Ошибки и момент их обнаружения

Ошибки чтения XML, построения модели и подготовки YAML по-прежнему относятся к
первому проходу. Ошибки окончательного преобразования, формирования текста,
проверки сформированного YAML и записи основного файла обнаруживаются во втором
проходе для всех объектов.

Ошибка одного задания не должна оставлять его YAML в памяти после завершения или
отмены операции. Существующая сводка ошибок импорта и запрет публикации
незавершённого состояния сохраняются.

## Память

Решение подтверждено измерением полной ERP-конфигурации:

- 38 455 разобранных YAML-объектов занимают 846,4 МиБ используемой памяти V8;
- текущая реализация уже удерживает 14 504 наиболее крупных объекта;
- удержание остальных объектов добавляет около 56,8 МиБ используемой памяти V8,
  или 70–99 МиБ RSS;
- пик первого прохода импорта составляет 5,68 ГиБ RSS.

Тексты YAML не удерживаются. В памяти остаются только разобранные объекты и
необходимые данные подготовки. Дополнительный расход признан приемлемым по
сравнению с упрощением жизненного цикла и устранением класса ошибок досрочного
разрешения.

## Изменения в устройстве импорта

Из первого прохода удаляется ветвление «можно записать без общего индекса» и
связанные счётчики досрочно записанных YAML. Все основные подготовленные YAML
помещаются в существующее хранилище ожидания второго прохода.

Второй проход перестаёт быть условным только для заранее распознанных зависимых
файлов: он окончательно обрабатывает каждый успешно подготовленный основной YAML.
Объединение вкладов первого прохода и передача общего снимка работникам остаются
барьером между проходами.

Схема «Импорт XML → YAML» в `.agents/architecture.md` обновляется вместе с
реализацией: из неё удаляется досрочная запись, а первый проход всегда ведёт к
сохранению подготовленного YAML и вклада в индекс. Обновление архитектурного
документа явно согласовано разработчиком.

## Проверки

### Модульные

Общий механизм разрешения покрывается случаями:

- прямая ссылка на объект или член объекта;
- предопределённое значение через сведения владельца;
- значение перечисления;
- пустая ссылка;
- отсутствующая цель;
- несовместимый тип;
- неоднозначная цель с сохранением текущего поведения;
- пропуск значения `!xml` проверкой проекта.

### Импорт

- первый проход удерживает основной YAML независимо от наличия известных
  отложенных значений;
- основной YAML не записывается до фиксации общего индекса;
- объект-потребитель разрешает значение объекта-владельца, подготовленного другим
  работником;
- порядок заданий второго прохода не влияет на результат;
- ошибка и отмена освобождают все удерживаемые объекты;
- существующие внешние и вспомогательные файлы сохраняют прежний жизненный цикл.

### Сквозной пример

Существующая XML-фикстура `ПланОбменаВсеСвойства` остаётся источником истины.
Ожидаемая YAML-фикстура меняется так, чтобы `ЗначениеЗаполнения` со ссылкой на
предопределённое значение справочника не содержало `!xml`. Отдельная проверка
должна подтверждать разрешение через общий индекс при распределении владельца и
потребителя между разными работниками.

Числовой порог памяти в автоматические проверки не добавляется: измерение служит
обоснованием архитектурного решения, а тесты закрепляют жизненный цикл объектов.

## Критерии готовности

- ни один основной YAML импорта не записывается в первом проходе;
- второй проход получает каждый успешно подготовленный YAML и общий индекс;
- ссылка на существующее предопределённое значение сохраняется без `!xml` даже
  при обработке владельца другим работником;
- импорт и проверка используют общий смысловой механизм разрешения ссылок;
- проверка проекта по-прежнему игнорирует значения `!xml`;
- правила применения `!xml` для отсутствующих, несовместимых и неоднозначных
  целей не меняются;
- отмена и ошибки не оставляют удерживаемые YAML;
- `.agents/architecture.md` отражает новый порядок импорта;
- полный набор тестов проекта проходит.

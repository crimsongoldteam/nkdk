# Импорт конфигурации: взаимодействие главного процесса и worker

> Статус: рабочий черновик. В документ включаются только согласованные решения; остальные части импорта уточняются последовательно.

## Цель

Определить порядок импорта конфигурации из готовой временной XML-выгрузки в Проект и границы ответственности между главным процессом и worker.

Термины `Проект` и `Конфигурация` используются в значениях, определённых в `.agents/architecture.md`.

## Общий принцип

Первая реализация не подключается к 1С, не получает XML-выгрузку и не проверяет версию Конфигурации. Эти шаги остаются частью целевой архитектуры, а входом первой реализации является готовая временная XML-выгрузка.

При таком импорте отпечаток базы и подтверждённая версия Конфигурации в файле индекса конфигурации остаются пустыми. Привязка индекса к базе и проверка изменения Конфигурации после выгрузки не выполняются.

Первая реализация поддерживает только одну привязку Проекта к базе и один файл индекса конфигурации. Выбор между несколькими базами и одновременное хранение нескольких файлов индекса не поддерживаются. При импорте из готовой XML-выгрузки используется `baseId = "default"`, а индекс записывается в `.nkdk/configuration-index/default.bin`.

Импорт использует тот же принцип распределения чтения, что и полная валидация Проекта:

- главный процесс находит и классифицирует исходные файлы;
- главный процесс формирует задания импорта и распределяет их между worker;
- каждый worker самостоятельно читает и разбирает файлы назначенных ему заданий;
- metadata-модели остаются в памяти назначенного worker и используются во втором проходе;
- главный процесс не получает полные разобранные XML-данные;
- импорт выполняется в два прохода: сначала строятся модели и глобальный индекс метаданных, затем YAML.

Выполнение обработчика worker в главном процессе не допускается, в том числе при одном worker. Импорт, валидация и синхронизация должны использовать одну и ту же границу изоляции независимо от настроенной степени параллелизма.

## Единица работы

Одно задание импорта формирует ровно один итоговый YAML-файл Проекта. Например, отдельными заданиями являются `Конфигурация.yaml`, `Свойства.yaml` объекта и `Форма.yaml` формы.

Задание содержит:

- целевой путь итогового YAML-файла;
- правило преобразования;
- описание логического владельца и цепочки вложенности;
- пути всех XML-файлов, совместно образующих metadata-модель результата;
- описания связанных внешних файлов XML-выгрузки.

Одно задание может читать несколько XML-файлов. Например, задание формы читает XML метаданных формы и XML её тела. Данные, вложенные в metadata-модель и записываемые в тот же YAML, не выделяются в самостоятельные задания.

Если владелец и подчинённый объект записываются в разные YAML-файлы, для них создаются разные задания. Поэтому форма справочника не входит в задание `Свойства.yaml` справочника. Задание формы получает описание владельца, но не metadata-модель справочника.

Ссылки на другие объекты при преобразовании XML в metadata-модель остаются строковыми значениями и не требуют передачи их моделей. Межобъектные сведения, необходимые при построении YAML, поступают только через глобальный индекс метаданных после первого прохода.

## Обнаружение заданий

Главный процесс рекурсивно обходит XML-выгрузку и сопоставляет пути файлов с декларативными маршрутами импорта, зарегистрированными правилами объектов и property-типов. Содержимое `Configuration.xml`, `ChildObjects` и других XML-файлов для обнаружения заданий не читается.

Маршрут импорта определяет:

- роль исходного файла;
- итоговый YAML-файл;
- правило преобразования;
- логического владельца и цепочку вложенности;
- остальные XML-файлы metadata-модели;
- связанные внешние файлы или каталоги.

Верхнеуровневые объекты, формы, рекурсивно вложенные объекты и другие файловые подчинённые объекты обнаруживаются одинаковым механизмом маршрутов. Общий слой обнаружения не содержит условий по конкретным `itemType`, именам XML-корней или каталогам отдельных объектов.

Значения `ChildObjects` могут быть обработаны worker как часть metadata-модели или данных файла индекса конфигурации, но не являются источником списка заданий. Дополнительный предварительный проход разбора XML не выполняется.

Каждый найденный файл ДОЛЖЕН соответствовать одному из декларативных маршрутов:

- XML-файл metadata-модели задания;
- внешний файл или каталог, связанный с заданием;
- явно зарегистрированное исключение для файла XML-выгрузки, не входящего в Проект.

Если файл не классифицирован или одновременно соответствует несовместимым маршрутам, главный процесс завершает подготовку импорта ошибкой до запуска первого прохода. Неизвестные файлы не игнорируются и не понижаются до предупреждения. Исключения задаются декларативно; общий слой не содержит встроенного списка частных имён файлов.

## Результат первого прохода

Разобранные XML-данные существуют только во время первого прохода конкретного задания. Worker последовательно строит из них metadata-модель, извлекает фрагмент данных файла индекса конфигурации и определяет связанные внешние файлы, после чего освобождает XML-данные.

До второго прохода worker сохраняет только metadata-модель и компактные результаты обработки задания. Metadata-модель не передаётся главному процессу или другим worker.

По каждому успешно подготовленному заданию worker формирует два компактных результата, привязанных к целевому YAML-файлу:

- фрагмент локального индекса метаданных, необходимый для построения глобального индекса метаданных;
- фрагмент данных файла индекса конфигурации, извлечённый из XML по правилам задания и позднее включаемый в общий передаваемый буфер worker.

Фрагмент локального индекса метаданных используется только во время операции импорта и не записывается в файл индекса конфигурации. Фрагмент данных файла индекса конфигурации не содержит хэш итогового YAML-файла: хэши вычисляются главным процессом по фактически записанным файлам Проекта.

Главный процесс объединяет фрагменты локальных индексов, проверяя уникальность логических адресов, и передаёт полученный глобальный индекс всем worker. Фрагменты данных файла индекса конфигурации главный процесс сохраняет до окончательного формирования файла после успешного переноса результата импорта.

### Состав фрагмента данных файла индекса конфигурации

Фрагмент одного задания содержит целевой путь YAML-файла и извлечённые из XML логические записи будущих секций формата 1.0:

- `IDENTITIES` — идентификаторы объектов и вложенных элементов 1С;
- `XML_ORDERS` — используемые заданием порядки XML-полей;
- `XML_NODES` — сведения XML-узлов;
- `XML_VALUES` — исходные представления значений, сохраняемые форматом 1.0.

Записи используют логические адреса в формате `uid` из эксперимента `reference-order-spec`; отдельный механизм адресации для файла индекса конфигурации не создаётся. Порядки полей внутри фрагмента могут иметь локальные идентификаторы; при объединении главный процесс устраняет повторяющиеся порядки и назначает итоговые `orderId`.

Фрагмент не содержит заголовок файла, каталог секций, `BINDING`, `STRINGS`, `PROJECT_FILES`, хэши файлов и контрольные суммы. Главный процесс:

1. проверяет уникальность логических адресов и допустимость записей всех фрагментов;
2. объединяет и сортирует записи согласно спецификации формата 1.0;
3. формирует общий пул `STRINGS` и общую секцию `XML_ORDERS`;
4. после переноса результата добавляет `BINDING` и `PROJECT_FILES`;
5. вычисляет контрольные суммы и записывает итоговый файл индекса конфигурации.

Фрагмент подчиняется ограничениям формата 1.0: исходные XML-файлы и `XML_REFERENCE_RAW` в него не входят.

### Передача фрагментов главному процессу

После завершения первого прохода worker объединяет фрагменты всех своих успешно обработанных заданий в один передаваемый `ArrayBuffer`. Буфер содержит записи заданий, целевые пути и локальный пул строк, необходимый для этих записей.

Worker передаёт владение буфером главному процессу без структурного клонирования. После передачи worker не обращается к буферу. Главный процесс получает не более одного такого буфера от каждого worker, проверяет его и сохраняет до формирования итогового файла индекса конфигурации.

Буфер является внутренним представлением сообщения между процессами. Он не записывается на диск, не является самостоятельным файлом индекса конфигурации и не обязан совпадать с расположением секций итогового формата 1.0.

### Представление глобального индекса метаданных

После обобщения главный процесс один раз кодирует глобальный индекс метаданных в неизменяемый двоичный снимок на основе `SharedArrayBuffer`. Все worker получают описание одного и того же общего буфера и создают над ним локальные представления для чтения.

Снимок использует общий пул строк и компактные таблицы записей по аналогии с двоичным снимком владельцев полной валидации. Структурное клонирование полного индекса для каждого worker и запросы к главному процессу во время построения YAML не допускаются.

Двоичный снимок существует только в памяти на время операции импорта, не записывается на диск и не является файлом индекса конфигурации. После завершения второго прохода ссылки на снимок освобождаются.

## Распределение заданий

Главный процесс статически распределяет сформированный список заданий между worker по кругу, аналогично полной валидации Проекта. Каждый worker получает одну часть списка и последовательно выполняет назначенные задания первого прохода.

После распределения задание закреплено за worker до завершения импорта. Второй проход выполняется в том же worker, в памяти которого находится metadata-модель задания. Передача metadata-модели или задания другому worker между проходами не допускается.

Изменение числа worker может изменить распределение заданий, но не результат импорта. Динамическая очередь и оценка заданий по размеру входных файлов в первой реализации не используются.

## Команды проходов

Главный процесс вызывает каждый worker один раз на проход:

1. команда первого прохода содержит всю назначенную worker часть списка заданий;
2. команда второго прохода содержит описание общего двоичного снимка глобального индекса метаданных и требует обработать все сохранённые в worker модели.

Отдельные вызовы worker для каждого задания не выполняются. Внутри команды worker последовательно обрабатывает задания, собирает ошибки и формирует один результат прохода.

Во втором проходе worker освобождает metadata-модель задания сразу после успешного или неуспешного построения соответствующего YAML и связанных файлов. После завершения команды worker не хранит metadata-модели завершённой операции.

## Временные каталоги

Для каждой операции главный процесс создаёт уникальный временный корень внутри `.nkdk/tmp/import/` Проекта. Каждый worker получает отдельный подкаталог этого корня и записывает в него YAML и связанные файлы, создаваемые преобразованием.

Размещение временного корня внутри Проекта гарантирует, что подготовленные worker файлы и их целевые пути находятся в одной файловой системе. Содержимое `.nkdk/` не включается в правила обнаружения и хэширования файлов Проекта.

После успешного переноса всех файлов, вычисления хэшей и записи файла индекса конфигурации главный процесс удаляет временный корень операции. При любом неуспешном завершении временный корень сохраняется.

## Аварийное завершение worker

Если worker аварийно завершился или потерял связь с главным процессом, импорт немедленно завершается ошибкой. Worker автоматически не перезапускается, его часть заданий не повторяется, следующий проход или перенос результата не начинается.

Главный процесс прекращает работу остальных worker этой операции и не записывает файл индекса конфигурации. Временный корень операции и временные каталоги всех worker сохраняются без изменений согласно общему правилу неуспешного импорта. Сохранённые файлы являются диагностическими данными незавершённой операции и не публикуются в Проект автоматически.

## Ошибки и барьеры проходов

Ошибка одного задания не останавливает текущий проход. Worker сохраняет диагностику с исходным и целевым путями задания и продолжает обрабатывать остальные назначенные задания, чтобы вернуть все обнаруженные ошибки прохода.

После каждого этапа главный процесс ожидает завершения всех worker и проверяет общий результат:

- при ошибке чтения XML, разбора XML, построения metadata-модели или извлечения фактов второй проход не начинается;
- при неизвестном файле или конфликте маршрутов первый проход не начинается;
- при конфликте во время обобщения индексов второй проход не начинается;
- при ошибке построения YAML worker продолжает остальные задания второго прохода, но перенос результата в Проект не начинается;
- при конфликте или недопустимом целевом пути в объединённом списке файлов перенос результата в Проект не начинается.

Во всех этих случаях файл индекса конфигурации не формируется и не записывается. Успешные результаты отдельных заданий не публикуются независимо от результата всей операции.

При любом неуспешном завершении импорта временный корень операции и временные каталоги worker сохраняются без изменений, а путь временного корня включается в результат ошибки. Автоматическая очистка данных неуспешных операций в первой реализации не выполняется.

### Перенос результата в Проект

Файлы, подготовленные worker во временном каталоге, включая YAML и связанные создаваемые преобразованием файлы, перемещаются в Проект атомарным переименованием. Внешние файлы XML-выгрузки копируются через временный файл в целевом каталоге и атомарно заменяют отдельный целевой файл.

Импорт не предоставляет транзакцию для всей совокупности файлов.

При первой ошибке переноса главный процесс:

1. прекращает запуск новых перемещений и копирований;
2. ожидает завершения уже начатых операций;
3. не формирует и не записывает файл индекса конфигурации;
4. возвращает ошибку операции.

Файлы, успешно заменённые до ошибки, не откатываются. Поэтому после ошибки переноса Проект может содержать часть нового результата, но каждый отдельный целевой файл содержит либо прежнюю, либо полностью записанную новую версию. Временные каталоги сохраняются. Повторный импорт должен быть способен восстановить согласованный результат.

## Границы ответственности

### Главный процесс

Главный процесс:

1. принимает путь к готовой временной XML-выгрузке;
2. находит XML-файлы и связанные внешние файлы выгрузки по декларативным маршрутам;
3. классифицирует найденные файлы без чтения их содержимого;
4. формирует задания, каждое из которых соответствует одному итоговому YAML-файлу, и статически распределяет их между worker по кругу;
5. объединяет локальные индексы worker, формирует общий двоичный снимок глобального индекса метаданных и передаёт его описание worker;
6. объединяет списки файлов результата импорта, полученные от worker;
7. проверяет уникальность и допустимость целевых путей;
8. асинхронно с ограниченным параллелизмом перемещает подготовленные worker файлы из `.nkdk/tmp/import/` в Проект, а внешние файлы копирует из XML-выгрузки;
9. координирует завершение операции.

Главный процесс не читает содержимое XML для преобразования в Проект и не выполняет разбор XML.

### Worker

Каждый worker:

1. получает назначенные задания импорта;
2. читает XML-файлы назначенных заданий из XML-выгрузки;
3. разбирает XML;
4. строит metadata-модели, извлекает необходимые факты и освобождает разобранные XML-данные;
5. извлекает привязанные к целевым YAML-файлам фрагменты локального индекса метаданных и файла индекса конфигурации, затем возвращает локальный индекс и один передаваемый буфер фрагментов;
6. после получения одной команды второго прохода последовательно строит YAML из всех сохранённых моделей во временном каталоге worker и освобождает обработанные модели;
7. записывает в тот же временный каталог связанные файлы, создаваемые самим преобразованием;
8. формирует список источников и целевых путей для подготовленных файлов и внешних файлов назначенных ему объектов.

Worker не подключается к 1С и не управляет XML-выгрузкой целиком.

## Начальная последовательность импорта

1. Главный процесс принимает путь к готовой временной XML-выгрузке.
2. Главный процесс по декларативным маршрутам находит и классифицирует XML-файлы и связанные внешние файлы без разбора `Configuration.xml` и `ChildObjects`.
3. Главный процесс формирует задания по одному итоговому YAML-файлу и распределяет их между worker.
4. Worker читают и разбирают назначенные XML-файлы, строят модели и сохраняют данные для второго прохода.
5. Worker возвращают привязанные к целевым YAML-файлам фрагменты локальных индексов метаданных и по одному передаваемому буферу с фрагментами данных файла индекса конфигурации. Metadata-модели остаются в worker, а XML-данные уже освобождены.
6. Главный процесс объединяет локальные индексы, создаёт один общий двоичный снимок глобального индекса метаданных и передаёт его описание всем worker.
7. Главный процесс отправляет каждому worker одну команду второго прохода. Worker последовательно строят YAML из сохранённых моделей с использованием глобального индекса метаданных, записывают YAML и создаваемые преобразованием связанные файлы в собственные временные каталоги и освобождают обработанные модели.
8. Worker возвращают списки источников и целевых путей. Источником является временный каталог worker либо XML-выгрузка.
9. Главный процесс объединяет списки, проверяет целевые пути и асинхронно с ограниченным параллелизмом переносит результат в Проект: подготовленные worker файлы перемещает, внешние файлы XML-выгрузки копирует.
10. Главный процесс вычисляет хэши файлов Проекта, формирует файл индекса конфигурации и после его успешной записи удаляет временный корень операции.

## Преобразование `ПутьКДанным`

Построение YAML выполняется только после формирования глобального индекса метаданных. Это необходимо, потому что преобразование одного `ПутьКДанным` может обращаться к реквизитам и табличным частям другого объекта Конфигурации.

### Локальные сведения формы

Worker, которому назначена форма, использует сохранённую metadata-модель формы для построения локального индекса пути. Индекс содержит:

- реквизиты формы и их типы;
- колонки табличных реквизитов;
- дополнительные колонки;
- признаки специальных источников данных, включая динамический список.

Локальный индекс определяет корень пути и начальный тип перехода. Он остаётся в worker и не передаётся главному процессу.

### Сведения владельца

На первом проходе каждый worker извлекает из построенных metadata-моделей компактные сведения владельцев `ПутьКДанным`:

- вид и имя владельца;
- реквизиты и их типы;
- табличные части и их колонки;
- внутренние и YAML-имена стандартных реквизитов;
- сведения, явно необходимые зарегистрированным правилам перехода между владельцами.

Полная metadata-модель владельца в эти сведения не входит. Для первой реализации используется тот же логический состав сведений владельца и индекса полей, который уже применяется при валидации Проекта.

### Обобщение и распределение

1. Worker возвращают главному процессу сведения владельцев своих моделей.
2. Главный процесс проверяет уникальность логических адресов и объединяет сведения в глобальный индекс метаданных.
3. Главный процесс передаёт каждому worker описание одного и того же двоичного снимка глобального индекса в общей памяти перед построением YAML.
4. Worker разрешают переходы `ПутьКДанным` через локальный индекс формы, глобальный индекс метаданных и зарегистрированные правила.

Например, для внутреннего пути `Объект.Товары.LineNumber` локальный индекс определяет тип реквизита формы `Объект`, глобальный индекс находит табличную часть `Товары`, а зарегистрированное правило преобразует стандартный реквизит `LineNumber` в `НомерСтроки`. В YAML записывается `Объект.Товары.НомерСтроки`.

Если путь невозможно разрешить из-за отсутствующего владельца, неизвестного перехода или пока неподдерживаемого правила, worker сохраняет исходное строковое значение из XML без изменения и добавляет предупреждение с целевым YAML-файлом и значением пути. Предупреждение не блокирует завершение второго прохода, перенос результата и запись файла индекса конфигурации.

Построение YAML не должно читать ранее записанные YAML-файлы через `projectDir`. Глобальный индекс метаданных существует только в общей памяти во время операции и не является файлом индекса конфигурации.

## Инварианты

- Одно задание импорта формирует ровно один итоговый YAML-файл.
- Все XML-файлы одного задания читаются одним worker.
- Один XML-файл, участвующий в построении metadata-модели, относится ровно к одному заданию импорта.
- Содержимое XML читается только назначенным worker.
- Разобранные XML-данные не передаются в главный процесс и не сохраняются между проходами.
- YAML строится только после передачи каждому worker глобального индекса метаданных.
- Построение YAML не зависит от наличия или порядка записи YAML других объектов.
- Полные metadata-модели не передаются между worker и в главный процесс.
- Неразрешённый `ПутьКДанным` сохраняется без изменения и возвращается как предупреждение, а не ошибка импорта.
- Никакие файлы не переносятся в Проект до успешного построения всех YAML.
- Импорт не очищает Проект; при импорте в непустой каталог отсутствующие в новом результате файлы сохраняются.
- Изменение числа worker не меняет результат импорта.
- Ошибка чтения или разбора связывается с исходным файлом и возвращается главному процессу как диагностика.

## Очистка временных каталогов

Первая реализация не удаляет временные каталоги неуспешных операций автоматически. Их последующая очистка выполняется пользователем или внешним обслуживающим процессом и не входит в механизм import.

# Вычисляемый `ВводПоСтроке`

## Цель

Сделать YAML-представление прикладных объектов компактнее: не выводить `ВводПоСтроке`, когда его упорядоченный список совпадает со значением, которое платформа вычисляет из стандартных реквизитов и их длин. При обратном преобразовании отсутствующий ключ должен восстанавливать тот же XML.

Одновременно YAML-схема и проверка проекта должны ограничивать длины кода, номера и наименования так же, как конфигуратор 1С.

## Область изменений

Вычисляемый `ВводПоСтроке` применяется к восьми видам объектов:

- Справочник;
- Документ;
- ПланОбмена;
- ПланВидовХарактеристик;
- ПланСчетов;
- ПланВидовРасчета;
- БизнесПроцесс;
- Задача.

Таблица внешнего источника данных остаётся на обычном `FieldsList`: для неё не установлен исследованный платформенный список по умолчанию.

Правила одинаково действуют для конфигурации `cf` и расширения `cfe`.

## Выбранная архитектура

Используется отдельный `inputByStringFieldsRule`. Он переиспользует представление и проверку metadata-полей, но дополнительно декларативно задаёт:

- упорядоченные стандартные поля объекта;
- свойства длины, управляющие доступностью этих полей;
- неявные значения длин, используемые при отсутствии ключей в YAML.

Для числовых свойств `numberRule` получает типовые границы `minimum` и `maximum`. Безусловные границы входят в JSON Schema. Зависимый максимум `38` при числовом типе кода или номера проверяется на уровне объекта, потому что он зависит от соседнего свойства `ТипКода` или `ТипНомера`.

Частные сведения об объектах не добавляются в нейтральные слои ruleRuntime, diagnostics или validation. Новый тип правила содержит предметную логику рядом с commonObjects, а каждый прикладной объект только объявляет свои поля и длины.

## Вычисляемые списки

Порядок является частью значения.

| Объект | Список при ненулевых длинах |
|---|---|
| Справочник | `[Наименование, Код]` |
| Документ | `[Номер]` |
| ПланОбмена | `[Наименование, Код]` |
| ПланВидовХарактеристик | `[Наименование, Код]` |
| ПланСчетов | `[Наименование, Код]` |
| ПланВидовРасчета | `[Наименование, Код]` |
| БизнесПроцесс | `[Номер]` |
| Задача | `[Наименование, Номер]` |

Стандартное поле включается в вычисляемый список только при положительной соответствующей длине. Поэтому, например, у Задачи с `ДлинаНомера: 0` вычисляемое значение равно `[Наименование]`.

У ПланаОбмена обе длины имеют минимум `1`, поэтому его вычисляемое значение всегда равно `[Наименование, Код]`.

## Преобразования

### XML → YAML

1. Из XML читается фактический упорядоченный список `InputByString`.
2. По длинам объекта строится вычисляемый список.
3. При точном совпадении, включая порядок, `ВводПоСтроке` не выводится.
4. Любое отличие сохраняется явно: обратный порядок, неполный список или дополнительный пригодный реквизит.

Пустой вычисляемый список при обеих нулевых длинах также считается неявным значением и не выводится.

### YAML → XML

1. Если `ВводПоСтроке` отсутствует, список вычисляется по эффективным длинам и записывается в XML.
2. Если ключ присутствует, его порядок и состав переносятся явно после проверки.
3. Отсутствующая длина означает существующее значение по умолчанию объекта; нулевая длина должна быть записана в YAML явно.

Пример Задачи без номера:

```yaml
ДлинаНомера: 0
```

Ключ `ВводПоСтроке` в этом случае отсутствует, а XML получает вычисляемый список только с Наименованием.

## Проверка YAML

Проверка выдаёт ошибку в следующих случаях:

- явно заданный список полностью совпадает с вычисляемым значением, включая порядок;
- в список включён стандартный Код при `ДлинаКода: 0`;
- в список включён стандартный Номер при `ДлинаНомера: 0`;
- в список включено стандартное Наименование при `ДлинаНаименования: 0`;
- значение длины выходит за безусловные границы объекта;
- при `ТипКода: Число` или `ТипНомера: Число` длина превышает `38`;
- поле не проходит существующий фильтр пригодности для ввода по строке.

При обеих нулевых длинах запрещены оба соответствующих стандартных поля. Дополнительные пригодные реквизиты объекта разрешены.

Явный список с обратным порядком не равен вычисляемому и разрешён.

## Границы длин

| Объект | Поле | Допустимые значения |
|---|---|---|
| ПланОбмена | ДлинаКода | `1..50` |
| ПланОбмена | ДлинаНаименования | `1..250` |
| Справочник | ДлинаКода | `0..50`; при `ТипКода: Число` — `0..38` |
| Справочник | ДлинаНаименования | `0..150` |
| Документ | ДлинаНомера | `0..50`; при `ТипНомера: Число` — `0..38` |

## Подсказки схемы

Подсказчик остаётся статическим.

- Для каждой длины JSON Schema содержит безусловные `minimum` и `maximum`.
- Описание поля с переключателем типа сообщает: при значении `Число` максимальная длина равна `38`.
- Описание `ВводПоСтроке` сообщает вычисляемый порядок, зависимость стандартных полей от длин, значимость порядка и запрет явно задавать полный список по умолчанию.
- Схема элементов списка сохраняет существующее описание и формат metadata-поля, пригодного для ввода по строке.

Подсказчик не вычисляет эффективный максимум по текущему YAML. Строгая зависимая проверка выполняется командой `validate`.

## Проверки и критерии приёмки

Существующие XML-фикстуры не изменяются: они остаются источником истины.

Основной e2e-критерий: после XML → YAML в `e2e/fixtures/nkdk/cf` у всех восьми объектов `ПоУмолчанию` отсутствует ключ `ВводПоСтроке`.

Дополнительно проверяются:

- скрытие вычисляемых списков при каждой нулевой длине и при обеих нулевых длинах;
- сохранение обратного порядка, неполного списка и дополнительного пригодного реквизита;
- ошибка для явно заданного полного вычисляемого списка;
- ошибка для каждого стандартного поля с нулевой длиной, включая `СтандартныйРеквизит.Номер` у Задачи;
- принятие точных минимумов и максимумов и отклонение соседних значений;
- принятие `38` и отклонение `39` при числовом типе кода или номера;
- принятие объектного строкового максимума при строковом типе;
- одинаковое поведение правил в `cf` и `cfe`;
- XML → YAML → XML без изменения порядка и состава `InputByString`.

## Вне области изменений

- Платформенные ограничения, не относящиеся к перечисленным длинам, не добавляются.
- Новое применение `!xml` не требуется.
- XML-фикстуры не переписываются для подгонки ожидаемого результата.

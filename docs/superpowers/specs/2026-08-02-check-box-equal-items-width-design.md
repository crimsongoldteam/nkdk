# CheckBoxField EqualItemsWidth Design

## Контекст

В полном round-trip `cf/doc` у `CheckBoxField` формы
`Справочник.СтруктураПредприятия.ФормаЭлемента` теряется явный XML-тег:

```xml
<EqualItemsWidth>false</EqualItemsWidth>
```

Текущее правило ошибочно задаёт `implicitValueYAML: false`, поэтому явная `Ложь` исключается из YAML
как значение по умолчанию и не восстанавливается в XML.

## Договор платформы

По документации 1С свойство `EqualItemsWidth` имеет тип `Булево, Неопределено`:

- `Неопределено` трактуется как `Истина`;
- в конфигураторе значение по умолчанию отображается как `Авто`;
- свойство используется только при `CheckBoxType = Tumbler`;
- если итоговое значение отлично от `Истина`, `ItemWidth` не используется.

Следовательно, XML содержит три различимых состояния:

| XML | Конфигуратор | YAML |
|---|---|---|
| тег отсутствует | `Авто` | поле отсутствует |
| `<EqualItemsWidth>true</EqualItemsWidth>` | `Истина` | `ОдинаковаяШиринаЭлементов: Истина` |
| `<EqualItemsWidth>false</EqualItemsWidth>` | `Ложь` | `ОдинаковаяШиринаЭлементов: Ложь` |

`Авто` не является синонимом явной `Истины`: платформа только трактует его итоговое значение как
`Истина`. Для точного round-trip эти состояния нельзя объединять.

## Статистика конфигураций

Во всех конфигурациях `/Users/nikita/git/round-trip-compact/cf` найдено 28 419 элементов
`CheckBoxField`:

- без тега — 28 379;
- явный `false` — 27;
- явный `true` — 13.

Значения встречаются не только у `Tumbler`, но и у старых элементов с `Auto`, `CheckBox` и
`Switcher`. Платформа не использует такое значение для других видов флажка, однако оно остаётся
валидной частью исходного XML и должно сохраняться при round-trip.

## Решение

В общем фрагменте правил `CheckBoxField` заменить:

```ts
equalItemsWidth: {
  yaml: "ОдинаковаяШиринаЭлементов",
  type: "boolean",
  implicitValueYAML: false,
}
```

на:

```ts
equalItemsWidth: {
  yaml: "ОдинаковаяШиринаЭлементов",
  type: "boolean",
  noImplicitValueYAML: true,
}
```

Механизм преобразования уже не применяет `implicitValueYAML` к отсутствующему YAML-ключу. Поэтому:

- отсутствующий ключ остаётся `undefined` и не создаёт XML-тег;
- явное YAML-значение `Истина` создаёт `<EqualItemsWidth>true</EqualItemsWidth>`;
- явное YAML-значение `Ложь` создаёт `<EqualItemsWidth>false</EqualItemsWidth>`.

Отдельный тип, callback, reference, configuration index и изменение общих правил не нужны.

## Архитектурные границы

- Не добавлять строковое значение `Авто` в boolean YAML: оно представлено отсутствием ключа.
- Не канонизировать явную `Истину` или `Ложь` в отсутствие XML-тега.
- Не добавлять условную валидацию по `CheckBoxType`: она сделала бы невалидными существующие XML
  конфигураций, содержащие неиспользуемое значение у других видов флажка.
- Изменение применяется к общему фрагменту `CheckBoxField`, поэтому одинаково действует для обычного
  элемента формы и колонки таблицы.
- Расхождение не добавляется в `.agents/restrictions.md`, потому что точный round-trip достижим.

## Проверки

- Расширить существующий табличный тест правил: у `equalItemsWidth` есть
  `noImplicitValueYAML: true` и нет `implicitValueYAML`.
- Добавить наблюдаемый XML → YAML → XML договор для трёх состояний: отсутствует, `true`, `false`.
- Проверить обычный `CheckBoxField` и `TableCheckBoxField` через переиспользуемый общий фрагмент.
- Запустить целевые тесты `checkBoxField`, затем `pnpm type-check`, `pnpm test`, `pnpm duplicates`.
- Stryker не запускать.
- Итоговый round-trip `cf/doc` не должен содержать расхождение `EqualItemsWidth`.

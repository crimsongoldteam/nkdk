# Зависимая проверка `ЗначениеЗаполнения`

## Контекст

`ЗначениеЗаполнения` хранит `MetadataValue`, но допустимость этого значения определяется не самим полем:

- у обычного реквизита — соседним полем `Тип`;
- у стандартного реквизита — видом реквизита и свойствами владеющего объекта;
- у ссылочного значения — ещё и существованием допустимой цели в проекте.

Поэтому полная проверка через JSON Schema невозможна. Общая схема `MetadataValue` не знает соседние поля и владельца. Попытка закодировать все варианты значения непосредственно в JSON Schema приводит к ложным ошибкам и нескольким сообщениям от ветвей объединения вместо одной предметной diagnostic.

Контрольный import `/Users/nikita/git/sed_xml/cf` в `/Users/nikita/git/sed_nkdk/cf` показал основную группу из 5 833 ошибок. В 552 различных полях `ЗначениеЗаполнения` было 4 416 сообщений, то есть по восемь сообщений на поле. Среди значений преобладали пустые строки и строки из пробелов. Например:

```yaml
Наименование:
  Тип: Строка(250)
  ЗначениеЗаполнения: ""
```

В данном случае значение типово корректно, но семантически избыточно: пустая строка является неявным значением строкового типа, поэтому самого поля `ЗначениеЗаполнения` в YAML быть не должно.

## Цель

Создать единый зависимый механизм, который:

- определяет эффективный тип обычного и стандартного реквизита;
- проверяет `ЗначениеЗаполнения` по этому типу и его ограничениям;
- удаляет из результата import значения, равные неявному значению типа;
- считает ручное указание такого значения ошибкой YAML;
- одинаково используется import и validation;
- передаёт ссылочные значения в существующий индекс зависимостей для Б5;
- позволяет декларативно дополнять правила стандартных реквизитов без частных условий в общих слоях;
- сохраняет точный XML round-trip через существующий снимок конфигурации.

## Не входит в задачу

- полное исследование семантики `ЗначениеЗаполнения` у всех стандартных реквизитов;
- попытка выразить зависимость между `Тип` и `ЗначениеЗаполнения` в JSON Schema;
- переиспользование полного механизма DataPath;
- добавление частных условий по виду объекта или имени реквизита в `orchestration`, `validation` или `project`;
- новый формат снимка конфигурации;
- использование `!xml` для сохранения удалённых из YAML значений;
- изменение существующих XML-фикстур.

## Термины и результаты классификации

### Эффективный тип

Эффективный тип — это тип конкретного реквизита вместе с существенными ограничениями:

- вид примитивного значения;
- длина и режим допустимой длины строки или номера;
- допустимые ссылочные типы;
- количество ветвей составного типа;
- неявное значение, если оно определено исследованным правилом.

Эффективный тип не является `DataPathTypeInfo`. Для `ЗначениеЗаполнения` нет обхода составного пути: проверяется одно скалярное или ссылочное значение. С DataPath переиспользуется только нижний уровень получения сведений о стандартном реквизите и владельце.

### Результат классификации

Чистый классификатор возвращает один из результатов:

```ts
type FillValueClassification =
  | { readonly kind: "valid" }
  | { readonly kind: "implicit" }
  | { readonly kind: "invalid"; readonly reason: FillValueInvalidReason }
  | { readonly kind: "unresolved" }
  | { readonly kind: "notSpecified" }
```

- `valid` — значение допустимо и содержательно;
- `implicit` — значение совпадает с неявным значением и не должно присутствовать в YAML;
- `invalid` — значение запрещено политикой, несовместимо с типом либо нарушает ограничение;
- `unresolved` — правило существует, но эффективный тип определить не удалось;
- `notSpecified` — семантика этого стандартного реквизита ещё не исследована.

Классификатор не формирует diagnostics и не изменяет данные. Import и validation по-разному применяют один и тот же результат.

## Архитектура

### Общий определитель эффективного типа

Нейтральный определитель типа должен поддерживать два источника.

Для обычного реквизита он читает соседний `Тип` и преобразует `TypeDescription` в набор допустимых вариантов с ограничениями.

Для стандартного реквизита он получает:

- декларацию стандартного реквизита из `standardMembers.ts`;
- модель владеющего объекта;
- значения свойств владельца, указанных декларацией;
- сведения об индексных целях, только когда необходимо проверить существование ссылки.

Существующие декларации `standardMembers.ts` остаются единственным предметным описанием стандартных реквизитов. Общий механизм не ветвится по `itemType`, YAML-именам или внутренним именам реквизитов.

DataPath продолжает строить собственный результат для обхода путей, но получает исходные сведения о стандартном реквизите через тот же определитель. Полный resolver DataPath в проверке `ЗначениеЗаполнения` не вызывается.

### Общий классификатор

Классификатор последовательно проверяет:

1. разрешено ли `ЗначениеЗаполнения` политикой стандартного реквизита;
2. не является ли значение неявным;
3. соответствует ли форма значения одному из вариантов эффективного типа;
4. соблюдены ли ограничения выбранного варианта;
5. допустима ли выбранная ветвь составного типа.

Существование ссылочной цели не проверяется повторным обходом файлов или частным поиском. Классификатор формирует нормализованную зависимость, а Б5 разрешает её по индексу зависимостей и индексу метаданных.

Объекты и файловые цели Б5 разрешает непосредственно по таблице целей. Именованные значения (`EnumValue` и предопределённые элементы) описываются декларативным `ownerFactRole`, сохраняются типизированными строками в таблице сведений владельца и проверяются зарегистрированным поставщиком значения. `EmptyRef` считается существующей только при наличии самого владельца. Этот путь одинаков для import и отдельной validation.

### Что сохраняется в индексе зависимостей

Само поле `ЗначениеЗаполнения` и его полное значение в индекс зависимостей не копируются.

- строка, число и булево значение остаются только в YAML и полностью проверяются локально;
- ссылочное значение также остаётся в YAML, но дополнительно создаёт обычное ребро индекса зависимостей;
- эффективный тип целиком в индекс не записывается; ребро содержит только ограничение, необходимое Б5 для проверки найденной цели.

Например:

```yaml
ЗначениеЗаполнения: Справочник.Организации.Предопределенный.Головная
```

даёт запись, эквивалентную:

```ts
{
  sourceFile: "Справочники/БанковскиеСчета.yaml",
  sourcePath: "СтандартныеРеквизиты.Владелец.ЗначениеЗаполнения",
  target: "Catalog.Организации.Predefined.Головная",
  constraint: {
    allowedTypes: ["Catalog.Контрагенты", "Catalog.Организации"],
    predefinedOnly: true,
  },
}
```

Таким образом, первый локальный шаг отвечает на вопрос «допустимо ли значение для этого поля», а Б5 — «существует ли цель уже распознанной ссылки». Для примитивного `ЗначениеЗаполнения` второй вопрос отсутствует.

### Границы JSON Schema и семантической проверки

JSON Schema проверяет только то, что YAML-узел можно разобрать как одну из общих форм `MetadataValue`: примитив, ссылка или другая поддерживаемая форма значения. Она не сопоставляет его с соседним `Тип`.

Например:

```yaml
Тип: Строка(100)
ЗначениеЗаполнения: 123
```

Число является допустимой общей формой `MetadataValue`, поэтому структурная схема его принимает. Зависимый классификатор затем выдаёт одну предметную ошибку несовместимости числа со строковым типом.

Аналогично `ЗначениеЗаполнения: ""` структурно является строкой, но классифицируется как `implicit`.

## Декларативные политики стандартных реквизитов

`StandardMemberDeclaration` получает отдельную декларацию `fillValue`. Она не добавляется в `BasePropertyRule` или построители rules.ts.

Поддерживаются следующие политики.

### Полный запрет

```ts
fillValue: { policy: "forbidden" }
```

Любое присутствующее содержательное значение классифицируется как `invalid`. `xsi:nil` не является содержательным значением и импортируется как отсутствие поля.

### Проверка по эффективному типу

```ts
fillValue: {
  policy: "byEffectiveType",
  implicitValue: false,
}
```

Политика использует тип, уже объявленный семейством стандартного реквизита, и при необходимости задаёт исследованное неявное значение.

### Код из свойств владельца

```ts
fillValue: {
  policy: "codeFromOwner",
  typeProperty: "codeType",
  lengthProperty: "codeLength",
  allowedLengthProperty: "codeAllowedLength",
}
```

Политика строит строковый или числовой эффективный тип из свойств владельца и применяет правила раздела «Стандартный реквизит `Код`».

### Владелец из списка владельцев

```ts
fillValue: {
  policy: "ownerReference",
  ownersProperty: "owners",
  predefinedOnly: true,
  allowUnselectedTypeWhenComposite: true,
}
```

Политика строит допустимые ссылочные ветви из списка владельцев объекта.

### Семантика пока не исследована

```ts
fillValue: { policy: "notSpecified" }
```

Такая политика:

- сохраняет значение без изменений;
- сама не выдаёт ошибку;
- сама не выдаёт предупреждение;
- позволяет позднее заменить её исследованным правилом.

Если значение имеет распознаваемую ссылочную форму, ссылка всё равно включается в индекс зависимостей. `notSpecified` не отключает общую проверку существования цели в Б5, поиск ссылок и переименование.

Неполное покрытие отражается в `.agents/restrictions.md`, а не в пользовательских diagnostics.

Декларации образуют дискриминированное объединение. Общий исполнитель знает только варианты политик и указанные в них свойства, но не имена стандартных реквизитов.

## Согласованные предметные правила

### Обычные реквизиты

Для обычного реквизита значение проверяется по соседнему `Тип`.

- содержательное совместимое значение сохраняется;
- значение, соответствующее неявному значению единственного типа, классифицируется как `implicit`;
- значение другого типа классифицируется как `invalid`;
- если тип составной, одно значение сопоставляется с одной из его ветвей;
- отсутствие `FillValue` в XML в виде `xsi:nil` означает отсутствие поля в YAML.

Подтверждённые неявные значения:

- строка — пустая строка `""`;
- число — `0`;
- булево значение — `Ложь`;
- единственный ссылочный тип — `ПустаяСсылка` этого типа.

Для ещё не исследованных классов типов отдельное неявное значение не угадывается.

### Составные ссылочные типы

Составной тип не превращает `ЗначениеЗаполнения` в составное значение. Значение остаётся одной ссылкой, но может выбрать одну ветвь типа.

Нужно различать:

```xml
<xr:FillValue xsi:type="xr:DesignTimeRef"/>
```

Здесь тип значения заполнения не выбран.

```xml
<xr:FillValue xsi:type="xr:DesignTimeRef">Catalog.Пользователи.EmptyRef</xr:FillValue>
```

Здесь выбрана ветвь `Catalog.Пользователи`, но ссылка этой ветви пуста. На реальной конфигурации такой вариант встречается у реквизита `Автор` с типами `CatalogRef.Сотрудники` и `CatalogRef.Пользователи`.

Для составного типа пустая ссылка конкретной ветви является содержательным выбором ветви и может сохраняться. Она не удаляется как неявное значение всего составного типа.

### Стандартный реквизит `Владелец`

Эффективный тип строится из свойства `Владельцы` справочника.

- допустимы ссылки на предопределённые элементы одного из объявленных владельцев;
- ссылка на объект другого типа запрещена;
- ссылка на несуществующий предопределённый элемент не разрешается Б5;
- при единственном владельце его обычная пустая ссылка является неявным значением;
- при нескольких владельцах разрешено пустое значение без выбранной ветви;
- при нескольких владельцах разрешена пустая ссылка выбранной ветви, потому что она сохраняет выбор типа.

Правило нескольких владельцев применяется к любому количеству больше одного, а не только к двум.

### Стандартный реквизит `Код`

Эффективный тип зависит минимум от трёх свойств владельца:

- `ТипКода`;
- `ДлинаКода`;
- `ДопустимаяДлинаКода`.

Если `ТипКода: Строка`, значение должно быть строкой. Если `ТипКода: Число`, значение должно быть числом. Приведение строки `"123"` к числу не выполняется.

Для содержательной строки длина не должна превышать `ДлинаКода`. Исследование `round-trip-compact` показало, что `ДопустимаяДлинаКода: Фиксированная` не требует от `FillValue` уже иметь точную длину:

- при `Переменная`, `ДлинаКода: 3` встречается содержательное значение `"--"` длиной 2;
- при `Фиксированная`, `ДлинаКода: 40` встречается содержательное значение длиной 10: `"0"` и девять пробелов.

Следовательно, для `ЗначениеЗаполнения` обе разновидности применяют верхнюю границу. `Фиксированная` может влиять на последующее приведение платформой, но не вводит проверку точного равенства длины исходного `FillValue`.

Строка, состоящая только из пробелов, считается платформенным представлением пустого кода независимо от фактического количества пробелов и классифицируется как `implicit` до проверки длины. Это необходимо, потому что реальные XML содержат как совпадающие, так и устаревшие длины:

- `ДлинаКода: 3` и три пробела;
- `ДлинаКода: 11` и девять пробелов;
- `ДлинаКода: 0` и девять либо пятьдесят пробелов.

Для числового кода `0` является неявным значением. Ненулевое число проверяется по количеству цифр относительно `ДлинаКода`; знак не считается цифрой. Дробные значения для кода запрещены.

### Начальное покрытие стандартных реквизитов

| Стандартный реквизит | Политика |
|---|---|
| `Ссылка` | любое `ЗначениеЗаполнения` запрещено |
| `ЭтоГруппа` | любое `ЗначениеЗаполнения` запрещено |
| `Предопределенный` | любое `ЗначениеЗаполнения` запрещено |
| `ИмяПредопределенныхДанных` | любое `ЗначениеЗаполнения` запрещено |
| `ПометкаУдаления` | допустима только `Истина`; `Ложь` является неявным значением и запрещена в YAML |
| `Код` | `codeFromOwner` |
| `Владелец` | `ownerReference` |
| остальные неисследованные реквизиты | `notSpecified`, без собственных предметных diagnostics; ссылки проверяет Б5 |

## Поведение операций

### XML → YAML import

После окончательной обработки модели, когда доступны соседний тип и свойства владельца, import вызывает общий классификатор до окончательной сериализации YAML.

| Классификация | Действие import |
|---|---|
| `valid` | сохранить значение |
| `implicit` | не записывать поле в YAML |
| `invalid` | сохранить значение, чтобы не потерять данные, и выдать ошибку |
| `unresolved` | сохранить значение и выдать предупреждение разработчику |
| `notSpecified` | сохранить значение без предметных сообщений; распознанную ссылку передать в Б5 |

Import не должен исправлять несовместимое или запрещённое содержательное значение молча. Автоматически удаляется только доказанное неявное значение.

Ссылочное допустимое значение одновременно создаёт обычную запись зависимости. Полная проверка существования ссылки выполняется Б5 по окончательному состоянию import тем же механизмом, что и при обычной validation.

### Validation YAML-проекта

Validation выполняется в три смысловых шага:

1. JSON Schema проверяет общую структуру YAML и `MetadataValue`;
2. общий зависимый классификатор проверяет значение по эффективному типу и декларативной политике;
3. Б5 разрешает извлечённые ссылочные зависимости по индексам проекта.

Второй шаг может выполняться в worker вместе с локальной семантической проверкой файла: ему нужны данные этого YAML и декларации стандартных реквизитов, но не окончательное состояние всего проекта. Б5 остаётся общей проверкой в главном процессе.

| Классификация | Действие validation |
|---|---|
| `valid` | успешно |
| `implicit` | ошибка с требованием удалить поле |
| `invalid` | одна предметная ошибка |
| `unresolved` | предупреждение разработчику |
| `notSpecified` | предметную проверку пропустить без сообщений; распознанные ссылки всё равно проверяет Б5 |

Import и validation используют один классификатор. Различаются только реакции на результат, собранные в двух тонких адаптерах.

### Синхронизация YAML → XML

Содержательное YAML-значение экспортируется обычным `MetadataValue` exporter после успешной классификации.

Если поля нет, XML строится так:

- снимок конфигурации восстанавливает исходную XML-форму, если она была сохранена при import;
- без снимка используется каноническое пустое представление, определённое существующим правилом XML, обычно `xsi:nil`.

Явное YAML-значение всегда имеет приоритет над сохранённым состоянием снимка.

## Точный XML round-trip

Снимок конфигурации уже умеет хранить:

- `xsiNil`;
- `xsiType`;
- `xmlText`;
- признак явного пустого значения.

Сейчас пустое типизированное значение, содержащее только `xsi:type`, восстанавливается без reference XML. Однако типизированная строка с текстом из пробелов автоматически не считается непредставимой в YAML и может не попасть в снимок.

Когда классификатор import возвращает `implicit` и поле удаляется из YAML, адаптер import должен сохранить фактическую XML-форму в существующих полях снимка:

- `xsi:type` → `xsiType`;
- исходный текст, включая точное число пробелов → `xmlText`;
- `xsi:nil` и явную пустую форму — существующими признаками.

Новый формат снимка не нужен. Для обычного YAML → XML без снимка точные устаревшие пробелы не восстанавливаются: создаётся каноническое пустое значение. Это допустимо, потому что точная историческая форма доступна только из import-снимка.

## Diagnostics

Проверка должна выдавать одну diagnostic на одно поле и использовать пользовательский YAML-путь `ЗначениеЗаполнения`.

Начальные предметные причины:

- поле содержит неявное значение и должно быть удалено;
- тип значения не соответствует эффективному типу реквизита;
- строка или число превышает допустимую длину;
- значение заполнения запрещено для стандартного реквизита;
- ссылка имеет недопустимый тип;
- ссылка на предопределённое значение не разрешена Б5.

`unresolved` является предупреждением для разработчика и должно содержать сведения, достаточные для добавления или исправления декларации. `notSpecified` не создаёт собственных предметных сообщений, но не подавляет обычные dependency diagnostics Б5.

## Отказоустойчивость

- Ошибка отдельного значения не останавливает разбор остальных файлов.
- Некорректное значение сохраняется import, чтобы diagnostic указывала на фактические данные.
- Отсутствие или неисследованность декларации не превращается в ложную пользовательскую ошибку.
- Конфликт или ошибка самой декларации является программной ошибкой регистрации, а не diagnostic пользовательского YAML.
- Общий слой не выполняет `existsSync`, `statSync` или обход каталогов для проверки ссылок.

## Проверки

### Модульные проверки классификатора

- строка, число и булево значение: содержательное, неявное и несовместимое значения;
- ограничения длины;
- одиночная и составная ссылка;
- выбранная и невыбранная ветвь составного типа;
- `valid`, `implicit`, `invalid`, `unresolved`, `notSpecified`.

### Проверки деклараций стандартных реквизитов

- полный запрет для `Ссылка`, `ЭтоГруппа`, `Предопределенный`, `ИмяПредопределенныхДанных`;
- `ПометкаУдаления: Истина` допустима, `Ложь` неявна;
- строковый и числовой `Код`;
- ограничение `Код` по длине для `Variable` и `Fixed`;
- пробельный код любой длины считается неявным;
- один и несколько владельцев;
- ссылки только на допустимые предопределённые элементы;
- нейтральная политика `notSpecified`.

### Проверки операций

- import не записывает доказанные неявные значения;
- validation считает те же явно записанные YAML-значения ошибкой;
- import и validation возвращают одинаковую предметную причину для `invalid`;
- ссылочные значения проходят через общий индекс зависимостей и Б5;
- снимок восстанавливает `xsi:nil`, пустой `xsi:type` и точный пробельный `xmlText`;
- явное новое YAML-значение перекрывает снимок;
- worker validation не создаёт сообщения по каждой ветви JSON Schema;
- контрольные import и validation `/Users/nikita/git/sed_nkdk` больше не содержат массовой группы ложных schema diagnostics.

Существующие XML-фикстуры не изменяются. Новые случаи добавляются отдельными минимальными фикстурами или программно построенными моделями согласно `.agents/testing.md`.

## Ограничения первого выпуска

- Предметные политики заданы только для согласованного начального набора стандартных реквизитов.
- Остальные стандартные реквизиты получают `notSpecified` и временно не проходят предметную проверку; их распознанные ссылки по-прежнему проверяются Б5.
- Неявные значения типов, которые не перечислены в этой спецификации, не выводятся эвристически.
- Проверка ссылок ограничена видами целей, уже представленными индексом метаданных и индексом зависимостей.
- Семантика `ЗначениеЗаполнения` должна расширяться новыми декларациями и тестами после отдельного исследования каждого семейства стандартных реквизитов.

## Критерии готовности

- один общий классификатор используется import и validation;
- JSON Schema отвечает только за общую форму `MetadataValue`;
- стандартные реквизиты описываются декларативно в `standardMembers.ts`;
- общие metadata-слои не содержат частных условий по именам реквизитов и видам объектов;
- неявные значения не появляются в импортированном YAML;
- ручное неявное значение даёт одну понятную ошибку;
- допустимые ссылки включаются в индекс зависимостей и проверяются Б5;
- удалённая из YAML XML-форма восстанавливается из снимка;
- `notSpecified` не создаёт собственных ошибок и предупреждений, но не отключает dependency validation ссылок;
- неполное покрытие явно отражено в `.agents/restrictions.md`.

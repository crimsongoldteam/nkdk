# XML-аномалии common-типа `boolean`

## Статус документа

Это пилотная спецификация одного common-типа. Она фиксирует только то, что
можно вывести из текущего договора `boolean`, его кода и возможных входных
форм XML.

Документ не утверждает общий механизм для всех common-типов и оркестратора.
Здесь рабочая гипотеза проверяется только на `boolean`; её последующее
обобщение вынесено в отдельный документ.

Результат последующего исследования зафиксирован в
[общей спецификации common-типов](2026-08-23-common-types-xml-anomaly-framework-design.md).
Этот документ остаётся подробной тестовой матрицей скалярного семейства.

Нормативные решения общей спецификации имеют приоритет: целевой YAML использует
`!xml/raw` со значением текущего XML-парсера, если обычное представление или
round-trip невозможны; `!xml/invalid` с обычным YAML-значением для обратимой
смысловой аномалии; `!xml/important` только для явно согласованного класса
ценных данных. Разделы ниже о форме raw, диагностике и
проверке сохраняют ход пилотного исследования, но не задают целевой договор
реализации.

## Цель пилота

Для common-типа `boolean` определить:

- какие формы XML он сейчас понимает;
- какие формы могут молча потеряться или измениться;
- как сохранить неподдержанную форму в YAML для обратного экспорта;
- какую диагностику показать пользователю;
- какие выводы после реализации можно безопасно перенести на следующий
  common-тип.

Главный критерий: корректно разобранный XML известного булевого свойства не
должен исчезнуть из YAML только потому, что его форма не предусмотрена текущим
преобразователем.

## Фактический текущий договор

Код common-типа находится в
`packages/rules/metadata/commonObjects/boolean`.

### XML → внутреннее значение

`StringboolXML` допускает:

```ts
type StringboolXML = "true" | "false" | boolean
```

`importBooleanFromXML` работает так:

1. `undefined` преобразуется в `undefined`;
2. из объекта берётся только `#text`;
3. `"true"` и `true` преобразуются в `true`;
4. `"false"` и `false` преобразуются в `false`;
5. любое другое значение преобразуется в `undefined`.

Следствия:

- дополнительный атрибут или вложенный узел рядом с распознанным `#text`
  игнорируется;
- объект без распознанного `#text` превращается в `undefined`;
- массив повторяющихся XML-элементов превращается в `undefined`;
- неподдержанная лексическая форма не отличается от отсутствующего значения.

### Внутреннее значение → YAML

`true` записывается как `Истина`, `false` — как `Ложь`, `undefined` не
записывается. JSON Schema допускает только `Истина` и `Ложь`, с дополнительным
исключением неявного значения конкретного PropertyRule.

### YAML → внутреннее значение

Обычная схема не пропускает посторонние строки. Сам преобразователь при этом
возвращает `true` только для `Истина`, а любую другую переданную строку
превращает в `false`. Поэтому исключительный переносчик не должен попадать в
обычный `importBooleanFromYAML`.

### Внутреннее значение → XML

Отдельного `exportToXML` у `boolean` нет. Общий ruleRuntime выводит JavaScript-
значение `true` или `false` в XML-место, заданное PropertyRule. Присутствие
элемента и default зависят не от common-типа, а от конкретного правила свойства.

## Граница исследования

Пилот рассматривает только XML-место, которое уже сопоставлено булевому
PropertyRule. Например:

```ts
booleanRule({ yaml: "Использовать", xml: "Use" })
```

В границу входят содержимое `Use`, его атрибуты, вложенные узлы, количество
элементов и отличие присутствия от канонического вывода этого правила.

В границу не входят:

- полностью неизвестный `<Switch>true</Switch>`, если `Switch` не является
  зарегистрированным именем или псевдонимом `Use`;
- элемент `Use` в неизвестном родителе;
- два реквизита или других именованных объекта с одинаковым именем;
- неизвестный файл или корневой XML-элемент;
- другие common-типы, включая `string` и `SystemEnumeration`.

Эти случаи находятся выше common-типа: преобразователь `boolean` не получает
достаточно информации, чтобы связать их со своим свойством.

## Полная матрица рассматриваемых форм

В таблице `Use` — известное XML-место свойства. Наличие атрибута считается
аномалией только тогда, когда конкретный PropertyRule не восстанавливает его
сам.

| Случай | Пример XML | Текущий результат | Риск |
|---|---|---|---|
| Каноническая истина | `<Use>true</Use>` | `Истина` | Нет |
| Каноническая ложь | `<Use>false</Use>` | `Ложь` | Нет |
| Неизвестное слово | `<Use>Switch</Use>` | `undefined` | Элемент исчезает или заменяется default |
| Другая запись регистра | `<Use>TRUE</Use>` | `undefined` | Исходный текст теряется |
| Числовая запись | `<Use>1</Use>` | `undefined` | Исходный текст теряется |
| Пробелы вокруг значения | `<Use> true </Use>` | `undefined` | Исходный текст и пробелы теряются |
| Пустой элемент | `<Use/>` | `undefined` | Присутствие элемента теряется |
| `xsi:nil` | `<Use xsi:nil="true"/>` | `undefined` либо пустое значение после разбора | Атрибут и присутствие теряются |
| Распознанное значение с лишним `xsi:type` | `<Use xsi:type="xs:boolean">true</Use>` | `Истина` | `xsi:type` теряется при обычном экспорте |
| Распознанное значение с произвольным атрибутом | `<Use custom="x">true</Use>` | `Истина` | Атрибут теряется |
| Объект только с атрибутом | `<Use custom="x"/>` | `undefined` | Весь элемент теряется |
| Вложенное значение | `<Use><Value>true</Value></Use>` | `undefined` | Вложенный узел теряется |
| Текст и вложенный узел | `<Use>true<Value>false</Value></Use>` | `Истина` | Вложенный узел теряется |
| Два одинаковых XML-имени | `<Use>true</Use><Use>false</Use>` | массив, затем `undefined` | Оба элемента теряются или заменяются default |
| Явное значение, совпавшее с неявным | `<Use>true</Use>` при `implicitValueYAML: true` | поле может быть опущено | Теряется различие «элемент был» / «элемента не было» |
| XML-элемент отсутствует | нет `<Use>` при правиле, которое создаёт default | поле отсутствует | При экспорте появляется элемент, которого не было |

Матрица описывает не классы диагностик, а входные примеры для проверки одного
инварианта: обычное преобразование должно восстановить структуру XML, иначе
исходное XML-место требуется сохранить.

## Рабочая гипотеза YAML-представления, заменённая общей спецификацией

Для пилота предлагается один резервный scalar-тег `!xml/raw`. Это предложение
для обсуждения, а не согласование его общего применения.

Обычные значения не меняются:

```yaml
Использовать: Истина
```

Неподдержанная форма хранит полный XML-фрагмент свойства:

```yaml
Использовать: !xml/raw |-
  <Use xsi:type="xs:boolean">Switch</Use>
```

Повтор хранит оба соседних элемента:

```yaml
Использовать: !xml/raw |-
  <Use>true</Use>
  <Use>false</Use>
```

Отсутствие элемента, который обычный экспорт создал бы, хранится пустым
фрагментом:

```yaml
Использовать: !xml/raw ""
```

Полный элемент, а не только текст, нужен потому, что у булевого XML могут
отличаться одновременно значение, атрибуты, вложенные узлы, количество и факт
присутствия. По `!xml/raw Switch` невозможно восстановить, был ли это текст,
атрибут, имя вложенного узла или один из повторов.

Payload гарантирует структурное, а не побайтовое равенство. Сохраняются имена
элементов и атрибутов, значения атрибутов, значимый текст, вложенность, число и
порядок элементов. Отступы, порядок атрибутов, вид кавычек и формы
`<Use/>`/`<Use></Use>` эквивалентны.

## Как отличить аномалию от допустимого контекста

Сам common-тип не может решить, является ли, например,
`xsi:type="xs:boolean"` лишним. Это зависит от конкретного PropertyRule и его
XML-окружения.

Поэтому для пилота признаком аномалии служит не таблица запрещённых значений, а
проверка обратимости одного известного XML-места:

1. выполнить обычное XML → YAML;
2. без reference XML экспортировать полученное значение тем же PropertyRule;
3. структурно сравнить исходное и полученное XML-место;
4. при совпадении оставить обычное `Истина` или `Ложь`;
5. при расхождении записать исходное XML-место как `!xml/raw`;
6. повторно экспортировать и доказать, что переносчик устранил расхождение.

Проверка должна учитывать конкретные default, `implicitValueYAML`,
`defaultValueXML`, `preserveExplicitDefaultXML`, `xml`, `xmlAliases` и
`xmlParents` действующего правила. Отдельная таблица контекстных исключений для
`boolean` не вводится.

Уже зарегистрированный компактный тег, например `!xml/present` или
`!xml/absent`, имеет приоритет, если он полностью восстанавливает исходное
XML-место. Пилот не мигрирует существующие случаи на `!xml/raw`.

Проверка без reference XML здесь доказывает переносимость YAML. Общая
спецификация дополнительно выделяет режим синхронизации, где разрешены уже
согласованные сведения индекса и снимка; совпадение в этом режиме само по себе
не доказывает переносимость проекта без снимка.

## Загрузка и проверка

Свойство с `!xml/raw` считается загруженным как сырой XML, но не считается
булевым значением:

- `importBooleanFromYAML` для него не вызывается;
- схема `Истина | Ложь` к payload не применяется;
- проверки, которым необходимо булево значение, пропускают это свойство и не
  создают каскадных ошибок;
- соседние свойства и весь остальной проект проверяются обычно;
- при YAML → XML сырой фрагмент заменяет обычный вывод свойства.

Проверяется только договор переносчика:

- payload является строкой;
- строка пуста либо содержит корректный XML-фрагмент;
- фрагмент не содержит XML-декларацию и `DOCTYPE`;
- фрагмент можно вставить в XML-место свойства;
- `!xml/raw` расположен именно у XML-backed свойства `boolean`.

Корректный переносчик создаёт неблокирующую диагностику: XML можно вернуть, но
предметное значение не проверено. Некорректный переносчик блокирует экспорт,
потому что безопасно восстановить XML невозможно.

## Диагностика пилота

Все сохранённые формы получают один код `xml/raw`. Причина вроде «значение»,
«атрибут» или «дубль» в YAML и коде диагностики не фиксируется.

Сообщение содержит фактические координаты:

- путь XML-файла;
- логический адрес объекта;
- YAML-путь;
- `itemType` и `propertyKey`;
- common-тип `boolean`;
- исходное XML-имя;
- отпечаток нормализованного фрагмента.

Пример:

```text
xml/raw: XML свойства сохранён без булевого преобразования:
Справочник.Товары / ИспользоватьСтандартныеКоманды
(boolean, UseStandardCommands, отпечаток 7d91b0ff)
```

Этого достаточно, чтобы найти все случаи поиском `!xml/raw`, сгруппировать их
по свойству и отпечатку, а затем решить, является ли форма ошибкой XML или
пропуском договора NKDK.

## Исключения

Текущий `boolean` не бросает исключение на неподдержанном значении, а возвращает
`undefined`. Поэтому пилот обязан обнаруживать молчаливую потерю сравнением
XML-мест, а не перехватом исключений.

Общий договор перехвата исключений common-преобразователей на основании одного
`boolean` не вводится. Ошибка XML-парсера, файловой системы, индекса или
оркестратора продолжает останавливать импорт.

## Проверки пилота

### Модульные факты текущего преобразователя

- `true`, `false`, `"true"`, `"false"` преобразуются как сейчас;
- неизвестный текст, пустой объект, объект без `#text` и массив дают
  `undefined`;
- объект с распознанным `#text` и дополнительными полями показывает текущую
  потерю этих полей.

### YAML runtime

- однострочный, многострочный и пустой `!xml/raw` читаются и записываются;
- scalar-тег сохраняется при копировании YAML-структуры;
- mapping и sequence payload отклоняются;
- некорректный XML-фрагмент отклоняется.

### Round-trip известного булевого свойства

Каждая строка матрицы закрепляется тестом XML → YAML → XML без reference XML.

- канонические `true` и `false` не получают `!xml/raw`;
- каждое структурное расхождение получает raw-фрагмент;
- итоговое XML-место структурно равно исходному;
- соседнее корректное свойство остаётся обычным YAML и проходит проверку;
- пустой raw-фрагмент подавляет XML-default конкретного правила;
- существующий специализированный переносчик сохраняет приоритет.

XML-фикстуры не изменяются: входы для аномалий создаются программно в тестах.

## Критерии завершения пилота

Пилот успешен, если для известного булевого свойства выполняется строгая
дихотомия:

- XML-место обратимо обычным договором и получает обычный YAML;
- XML-место необратимо обычным договором, целиком сохраняется в YAML и точно
  восстанавливается.

Третьего состояния, в котором импорт считается успешным, а часть известного
XML-места исчезла, быть не должно.

## Что можно будет проверить на следующем common-типе

После пилота результаты не распространяются автоматически. На следующем типе
нужно отдельно проверить:

- достаточно ли полного XML-фрагмента для составного значения;
- можно ли выделить одно устойчивое XML-место у вложенного объекта;
- не теряется ли полезная часть смыслового значения при полной raw-подмене;
- остаётся ли проверка обратимости линейной и не требует частных признаков в
  `PropertyRule`;
- подходит ли одна диагностика `xml/raw` для группировки новых случаев.

Только после подтверждения на нескольких разных common-типах можно писать
отдельную спецификацию общего механизма. Оркестраторные коллизии, включая два
реквизита с одинаковым именем, проектируются после common-типов.

Проверка на втором common-типе продолжена в документе
[`2026-08-23-string-xml-anomalies-design.md`](2026-08-23-string-xml-anomalies-design.md).
Она подтвердила общий способ обнаружения аномалии, но показала, что полный
XML-фрагмент нельзя механически применять к свойствам, хранящимся в
XML-атрибутах или внешних файлах.

## Согласование перед реализацией

Даже в границах `boolean` новый `!xml/raw` является новым применением
исключительного тега. Его реализация требует отдельного явного согласования.
Текущая спецификация такого согласования не предполагает и не изменяет
`.agents/architecture.md`, `.agents/xml-anomalies.md` или
`.agents/restrictions.md`.

# Исправление DataPath для списков видов субконто отчета

## Контекст

После коммита `ac179926d` ERP YAML validation показывает `2254 error, 36940 warning`.
Из них `105` ошибок относятся к `DataPath`.

Крупнейший связный остаток:

- `Отчет.СписокВидовСубконто[0].Value`
- `Отчет.СписокВидовСубконто.Value`
- `Отчет.СписокВидовСубконто.Picture`
- `Отчет.СписокВидовКорСубконто[0].Value`
- `Отчет.СписокВидовКорСубконто.Value`
- `Отчет.СписокВидовКорСубконто.Picture`

Ожидаемое снижение: около 12 ошибок `DataPath`.

## Цель

Научить `DataPath` resolver разрешать объектные реквизиты владельца отчета типа `СписокЗначений` / `ValueListType` как табличный источник `ValueList`, чтобы пути к платформенным колонкам `Value` и `Picture` проходили валидацию.

## Границы

Меняем только слой валидации `DataPath`.

Не меняем:

- YAML/XML round-trip;
- XML-фикстуры;
- import/export YAML и XML;
- `rules.ts`;
- формат YAML.

## Предполагаемый механизм

Сначала нужно проверить реальные YAML-файлы отчетов и модель владельца:

- где объявлены `СписокВидовСубконто` и `СписокВидовКорСубконто`;
- какой `TypeDescription` получает `OwnerMetadataCache`;
- почему существующая поддержка `ValueList` для реквизитов формы не применяется к объектному реквизиту владельца.

Если объектный реквизит владельца имеет `DataPathTypeInfo` с `kinds: ["tableSource"]` и `table.kind: "ValueList"`, resolver должен создавать для него `tableSource`, даже если у `ObjectField` нет собственных колонок.

Для колонок используется уже существующий механизм `virtualTableColumn`:

- `Value` -> `scalar`;
- `Presentation` -> `scalar`;
- `Check` -> `boolean`;
- `Picture` -> `Picture`.

Неизвестные колонки `ValueList` остаются ошибкой `неизвестная колонка`.

## Архитектура

Изменение должно быть локальным для перехода через `ObjectField` в `packages/core/metadata/validation/dataPath/resolver.ts`.

Предпочтительный вариант:

- добавить helper, который превращает `ObjectField` с `typeInfo.table` в `tableSource`;
- использовать его только когда `field.tableSource` отсутствует;
- не смешивать это с fallback из `ДополнительныеКолонки`, чтобы поведение оставалось читаемым.

Это позволит переиспользовать тот же путь, который уже работает для form attribute `СписокЗначений`.

## Ошибки и диагностика

Если реквизит владельца не найден, диагностика остается прежней: `неизвестный реквизит`.

Если реквизит найден, но не является табличным источником, поведение не меняется.

Если реквизит является `ValueList`, но колонка неизвестна, должна остаться ошибка `неизвестная колонка`.

## Тесты

Добавить resolver-тесты:

- `Отчет.СписокВидовСубконто.Value` проходит как колонка `ValueList`;
- `Отчет.СписокВидовСубконто.Picture` проходит как колонка `ValueList`;
- `Отчет.СписокВидовКорСубконто[0].Value` проходит через нормализацию индекса;
- `Отчет.СписокВидовСубконто.Unknown` остается ошибкой неизвестной колонки.

Добавить интеграционный тест `validateForm`:

- владелец `Отчет.АнализСубконто` содержит реквизит `СписокВидовСубконто: Тип: СписокЗначений`;
- форма содержит пути `Отчет.СписокВидовСубконто.Value` и `Отчет.СписокВидовСубконто.Picture`;
- валидация не дает ошибок.

## Риски

Основной риск: часть оставшихся путей может относиться не к `ValueList`, а к неизвестному или некорректно импортированному типу владельца. В этом случае реализация должна остановиться на диагностике причины, а не расширять resolver на произвольные неизвестные поля.

Второй риск: `Value` может быть типизирован глубже через `ТипЗначения`, но этот дизайн намеренно считает `Value` терминальным `scalar`, как уже сделано для form attribute `ValueList`.

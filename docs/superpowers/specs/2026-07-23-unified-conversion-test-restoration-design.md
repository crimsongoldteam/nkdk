# Восстановление тестов единых преобразований YAML и XML

## Цель

Восстановить поведенческое покрытие, потерянное при удалении раздельных операций `fromXML`, `toYAML`, `fromYAML` и `toXML`, не возвращая промежуточную metadata-модель и старую оркестрацию.

Для каждого объекта новый тест прямого преобразования должен содержать объединение сценариев двух прежних направленных операций:

- `fromXML.test.ts` + `toYAML.test.ts` → `fromXMLToYAML.test.ts`;
- `fromYAML.test.ts` + `toXML.test.ts` → `fromYAMLToXML.test.ts`.

## Источник истины

Источником служит история feature-ветки относительно `origin/develop`, а не только текущее дерево файлов.

Основная очистка выполнена коммитом `04f50e620`: в нём удалено 353 тестовых файла. Текущая разница с `origin/develop` содержит 356 удалённых тестовых файлов. Поэтому инвентаризация должна пройти по всем коммитам ветки и для каждого события удаления читать последнюю версию файла из родителя удаляющего коммита.

Предварительный подсчёт для `04f50e620` обнаружил не менее 1042 обычных `it`/`test`-сценариев. Ещё 47 файлов используют иные формы объявления, включая параметризованные тесты, поэтому полнота не может определяться простым числом файлов или регулярным выражением.

## Карта переноса

Перед изменением тестов формируется карта каждого удалённого сценария со следующими полями:

- удаляющий коммит;
- прежний файл и название сценария;
- использованные фикстуры;
- проверяемое поведение и значимые побочные результаты;
- новый файл и название сценария;
- состояние переноса;
- обоснование, если сценарий не переносится.

Допустимы только два итоговых состояния:

1. Поведение перенесено в тест единого преобразования или самостоятельный интеграционный тест.
2. Сценарий проверял исключительно наличие удалённого API или внутреннее представление промежуточной модели; это подтверждено явным обоснованием.

Удаление сценария из-за отсутствия старого вызываемого метода само по себе не является обоснованием.

## Устройство тестов

Тесты остаются рядом с правилами конкретного объекта.

Для каждого каталога создаются или дополняются два файла:

- `fromXMLToYAML.test.ts` вызывает настоящий единый XML→YAML-обход;
- `fromYAMLToXML.test.ts` вызывает настоящий единый YAML→XML-обход.

Объединяется множество сценариев и утверждений старой пары. Тесты не обязаны сливаться попарно по совпадению названий: одному прежнему тесту может соответствовать отдельный сценарий в новом файле, если он проверяет самостоятельный граничный случай.

Тестовые переходники, воспроизводящие старую общую оркестрацию, не создаются. Атомарные обработчики `fromXML`, `toYAML`, `fromYAML`, `toXML` сохраняются и могут проверяться отдельно, но объектные тесты проходят через единое преобразование.

## Перенос ожиданий

Старое промежуточное значение metadata-модели не сравнивается буквально. Его смысл выражается через наблюдаемый итоговый YAML или XML.

Обязательно сохраняются проверки:

- значений и значений по умолчанию;
- отсутствующих, пустых и разреженных свойств;
- порядка полей и элементов;
- reference XML и неизвестных сохраняемых частей;
- вложенных объектов и коллекций;
- нескольких XML-источников и нескольких XML-выходов;
- внешних файлов и действий записи;
- идентификаторов, индексов и зависимостей;
- ошибок и диагностических путей;
- особенностей форм и составных объектов.

Существующие XML-фикстуры не изменяются.

## Самостоятельные тесты

Удалённые `convertFromXML`, sync, round-trip, reference и другие интеграционные тесты не объединяются искусственно с парными файлами. Они восстанавливаются рядом с прежним объектом и переводятся на публичные единые операции.

Если такой тест дублирует уже перенесённый сценарий, это фиксируется в карте с точной ссылкой на замену. Простого указания на общий round-trip недостаточно, если старый тест проверял отдельное значение или побочный результат.

## Порядок работы

1. Построить полную карту удалений по истории ветки.
2. Перенести общие orchestration-тесты.
3. Переносить commonObjects по одному каталогу сразу в обоих направлениях.
4. Аналогично перенести appliedObjects.
5. Перенести тесты форм.
6. Восстановить самостоятельные интеграционные сценарии.
7. Провести итоговый аудит карты и полного набора тестов.

Изменения фиксируются отдельными коммитами по слоям, чтобы каждый набор можно было проверить независимо.

## Работа с расхождениями

Если объединённый тест выявляет отсутствие прежнего поведения, сначала фиксируется падающий тест, затем изменяется только единый обход, декларативное правило или атомарный обработчик, отвечающий за это поведение.

Старые общие property/item/collection-операции и промежуточная модель не восстанавливаются. Если ожидание относилось только к внутреннему устройству модели и не имеет наблюдаемого аналога в YAML/XML, это отмечается в карте как непереносимое внутреннее представление с объяснением.

## Проверка

После каждого каталога запускаются его новые тесты. После каждого слоя запускается полный набор тестов `@nkdk/core`. Перед завершением выполняются:

- аудит карты: у каждого удалённого сценария есть новый адрес или допустимое обоснование;
- проверка отсутствия обращений к удалённым общим операциям;
- `pnpm test` из корня проекта;
- статическая проверка TypeScript;
- `git diff --check`.

Работа считается завершённой только при одновременном выполнении проверки поведения и проверки полноты карты.

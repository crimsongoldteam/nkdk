# XML-аномалии common-типа `string`

## Статус документа

Это второй пилот исследования XML-аномалий common-типов. Он проверяет на
`string` методику, сформулированную для `boolean`, но не утверждает общий
механизм для всех типов.

Реализация и новое применение `!xml` этим документом не согласовываются.

Результат обобщения зафиксирован в
[общей спецификации common-типов](2026-08-23-common-types-xml-anomaly-framework-design.md).
Этот документ остаётся подробной тестовой матрицей строкового скаляра.

Нормативные решения общей спецификации имеют приоритет: целевой YAML использует
`!xml/raw` со значением текущего XML-парсера, если обычное представление или
round-trip невозможны; `!xml/invalid` с обычным YAML-значением для обратимой
смысловой аномалии; `!xml/important` только для явно согласованного класса
ценных данных. Разделы ниже о форме raw и прежнем
разделении structural/validation сохраняют ход пилотного исследования, но не
задают целевой договор реализации.

## Что именно исследуется

`string` — произвольная строка на одном языке. Многоязычный текст относится к
отдельному common-типу `I8nText`, форматированный многоязычный текст — к
`FormattedI8nText`. Их поведение нельзя выводить из этого документа.

У одного `stringRule` встречаются разные XML-носители:

- текст XML-элемента, например `<Comment>Текст</Comment>`;
- XML-атрибут, например `name="Команда"` для правила с `xml: "_name"`;
- отдельный внешний файл при `externalFile`;
- строка-ссылка при `metadataTarget`.

Этот пилот рассматривает обычную строку в XML-элементе. Остальные варианты
нужны, чтобы проверить границы методики, но не должны автоматически получать
тот же способ сохранения.

## Фактический текущий договор

Код common-типа находится в
`packages/rules/metadata/commonObjects/string`.

### XML → внутреннее значение

`importStringFromXML` работает так:

1. `undefined` преобразуется в `undefined`;
2. из объекта берётся только `#text` и преобразуется в строку;
3. любой другой объект преобразуется в `undefined`;
4. скаляр преобразуется методом `toString()`.

Следствия:

- произвольный текст является допустимым значением;
- дополнительные атрибуты и дочерние узлы рядом с `#text` игнорируются;
- объект без `#text` и массив повторяющихся элементов становятся
  `undefined`;
- пустой элемент после разбора может быть неотличим от отсутствующего
  значения без учёта самого XML-места.

### Внутреннее значение ↔ YAML

JSON Schema допускает любую строку. Текущий YAML runtime сохраняет строковый
тип для пустого значения, числоподобных значений, `true`, `false`, `null`, `~`,
строк с пробелами по краям и многострочного текста.

Например:

```yaml
Пустая: ""
Код: "001"
Булевоподобная: "true"
Многострочная: |-
  первая строка
  вторая строка
```

Поэтому `Switch`, `TRUE`, `1`, `null` и любой другой текст для `string` не
являются неизвестным значением. В отличие от `boolean`, у строки нет класса
аномалий «неподдержанная лексическая форма».

### Внутреннее значение → XML

Отдельного `exportToXML` у `string` нет. XML-имя, родитель, default,
присутствие и способ размещения определяет конкретный PropertyRule и общий
ruleRuntime.

## Инвариант пилота

Для известного XML-места строкового свойства выполняется обычный
XML → YAML → XML без reference XML. Затем сравниваются исходное и полученное
XML-места.

- Если место структурно восстановлено, в YAML остаётся обычная строка.
- Если часть места потеряна или появилась, исходное XML-место нужно сохранить
  исключительным переносчиком.

Содержание строки не классифицируется заранее. Это позволяет обнаруживать
новые формы без пополнения перечня «плохих строк».

Проверка без reference XML доказывает переносимость YAML. Общая спецификация
отдельно рассматривает синхронизацию со сведениями индекса и снимка, что важно
для атрибутов, внешних файлов и составных типов.

## Матрица строки в XML-элементе

В таблице `Text` — XML-имя, уже сопоставленное конкретному `stringRule`.

| Случай | Пример XML | Обычный YAML | Решение по методике |
|---|---|---|---|
| Обычный текст | `<Text>abc</Text>` | `Значение: abc` | Оставить строкой |
| Текст, похожий на boolean | `<Text>true</Text>` | `Значение: "true"` | Оставить строкой |
| Числоподобный текст | `<Text>001</Text>` | `Значение: "001"` | Оставить строкой |
| Пробелы по краям | `<Text>  abc  </Text>` | `Значение: "  abc  "` | Оставить строкой, если XML восстановлен |
| Многострочный текст | `<Text>первая&#10;вторая</Text>` | блок `|-` | Оставить строкой, если XML восстановлен |
| Экранированные символы | `<Text>&lt;&amp;</Text>` | строка `<&` | Оставить строкой: XML-экранирование канонично восстанавливается |
| Пустой элемент | `<Text/>` | поле может исчезнуть или стать `""` | Сравнить с договором присутствия конкретного правила |
| Элемент отсутствует | нет `<Text>`, но правило создаёт default | поле отсутствует | Сохранить отсутствие, если экспорт добавляет элемент |
| Текст с дополнительным атрибутом | `<Text custom="x">abc</Text>` | `Значение: abc` | Сохранить исходный элемент, если правило не возвращает атрибут |
| `xsi:type` | `<Text xsi:type="xs:string">abc</Text>` | `Значение: abc` | Не считать лишним заранее; сравнить с выводом правила |
| Только атрибут | `<Text custom="x"/>` | поле исчезает | Сохранить исходный элемент |
| Дочерний элемент | `<Text><Value>abc</Value></Text>` | поле исчезает | Сохранить исходный элемент |
| Смешанное содержимое | `<Text>abc<Value>def</Value></Text>` | `Значение: abc` | Сохранить исходный элемент: `Value` теряется |
| Повтор свойства | `<Text>abc</Text><Text>def</Text>` | поле исчезает | Сохранить оба соседних элемента |
| Явное пустое значение совпало с default | `<Text/>` при неявном `""` | поле может исчезнуть | Сохранить присутствие, если правило его не восстанавливает |

Таблица является набором входов для проверки инварианта, а не перечнем кодов
диагностики.

CDATA, ссылки на символы, форма пустого элемента и порядок атрибутов
сравниваются структурно, а не побайтово. Если когда-нибудь потребуется
побайтовый round-trip, текущего XML-парсера для него недостаточно.

## Как `string` включается в методику `boolean`

### Что подтвердилось

1. Аномалию следует находить сравнением известного XML-места после обычного
   round-trip, а не списком заранее известных ошибок.
2. Default и различие «элемент отсутствует / элемент присутствует» являются
   частью XML-места, а не частью значения common-типа.
3. Атрибуты, дочерние элементы и повторы могут молча теряться даже тогда, когда
   смысловое значение успешно загружено.
4. Для всех сохранённых форм достаточно одного кода диагностики `xml/raw`;
   конкретные формы можно группировать по `itemType`, свойству и отпечатку
   фрагмента.

### Что не подтвердилось как общее правило

Полный XML-фрагмент свойства подходит только элементу. У строки с
`xml: "_name"` XML-местом является атрибут родительского элемента. Сохранение
всего родителя перезапишет соседние свойства, поэтому переносчик из пилота
`boolean` нельзя механически применить к такому правилу.

Для корректного XML строковый атрибут не может содержать дочерние элементы или
повторяться с тем же именем. Его произвольное значение и пустая строка уже
представимы обычным YAML. На этом этапе для атрибутов нужно проверить только
присутствие и default существующими средствами; новый raw-переносчик не
предлагается.

`externalFile` вообще не имеет XML-места внутри YAML-свойства. Его сохранение
должно исследоваться отдельно вместе с механизмом внешних файлов.

## Структурная аномалия и ошибка проверки — разные случаи

`stringRule` может иметь `metadataTarget`. Тогда строка является ссылкой на
объект метаданных.

- Если ссылка не разрешилась, но её текст без потерь возвращается в XML, это
  не структурная XML-аномалия common-типа `string`. Нужна обычная ошибка
  проверки или существующий специализированный переносчик ссылки.
- Если XML-форма ссылки потерялась при round-trip, применяется рассматриваемый
  механизм сохранения XML-места.

Иначе любой несуществующий объект ошибочно превращался бы в raw XML и перестал
бы давать полезную предметную диагностику.

## Рабочее YAML-представление, заменённое общей спецификацией

Для element-backed строки рабочая гипотеза `boolean` сохраняется:

```yaml
Значение: !xml/raw |-
  <Text custom="x">abc</Text>
```

Для повтора:

```yaml
Значение: !xml/raw |-
  <Text>abc</Text>
  <Text>def</Text>
```

Raw-переносчик используется только если обычная строка не восстановила
XML-место. Он не передаётся в `importStringFromYAML`, не проверяется как строка
или ссылка и при экспорте заменяет обычный вывод этого свойства.

Новый `!xml/raw` остаётся гипотезой. Перед его применением к `string` требуется
отдельное явное согласование.

## Варианты дальнейшего обобщения

### (А) Исследовать element-backed common-типы по одному — рекомендуется

Сохранить полный XML-фрагмент только там, где у свойства есть изолированный
элемент. Атрибуты, внешние файлы и составные объекты исследовать отдельными
сериями.

Плюс: общий механизм выводится из фактов, не требует преждевременно менять
`BasePropertyRule`. Минус: универсальное покрытие появится не сразу.

### (Б) Сразу ввести универсальное описание XML-места

Переносчик хранил бы вид места, присутствие и raw-содержимое для элемента,
атрибута или файла.

Плюс: единая форма. Минус: после двух простых типов ещё неизвестно, какие места
потребуются составным объектам; структура с высокой вероятностью окажется
неполной.

### (В) Хранить целиком родительский XML-элемент

Так можно сохранить и атрибут, и элемент.

Этот вариант не подходит: одно аномальное свойство начнёт владеть XML соседних
свойств, создаст перекрытия и сделает независимое редактирование YAML
непредсказуемым.

## Проверки пилота

### Модульные факты `string`

- скаляры преобразуются в строки;
- объект с `#text` возвращает текст;
- дополнительные поля объекта не попадают в результат;
- объект без `#text` и массив дают `undefined`.

### YAML runtime

- пустая, числоподобная, boolean-подобная и многострочная строки сохраняют
  строковый тип;
- пробелы по краям и завершающие переводы строк не исчезают;
- обычная строка не получает `!xml/raw` только из-за своего содержания.

### Round-trip строкового элемента

Каждая строка матрицы закрепляется программным тестом без изменения эталонных
XML-фикстур:

- обратимые формы остаются обычной строкой;
- необратимые формы получают полный XML-фрагмент;
- итоговое XML-место структурно равно исходному;
- соседнее свойство не попадает в raw-фрагмент;
- правила с разными default проверяются отдельно;
- ошибка `metadataTarget` не маскируется как структурная XML-аномалия.

## Вывод после двух common-типов

Метод обнаружения обобщается лучше, чем способ хранения:

- общий критерий — структурное равенство известного XML-места после обычного
  round-trip;
- common-тип поставляет обычное преобразование, но не перечень аномалий;
- один код `xml/raw` пригоден для последующего поиска и анализа;
- полный raw-фрагмент пока доказан только для element-backed свойства;
- ошибки предметной проверки нельзя автоматически превращать в raw XML.

Проверка на третьем common-типе продолжена в документе
[`2026-08-23-number-xml-anomalies-design.md`](2026-08-23-number-xml-anomalies-design.md).
Она подтвердила общую классификацию и добавила случай потери исходной числовой
записи и точности. После него полезно взять составной common-тип или список,
чтобы проверить границу XML-места с несколькими вложенными элементами.

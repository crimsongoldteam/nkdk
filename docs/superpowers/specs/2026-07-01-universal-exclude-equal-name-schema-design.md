# Универсальная schema для excludeIfEqualNameYAML

## Контекст

Флаг `excludeIfEqualNameYAML` запрещает явно хранить в YAML локализованное текстовое поле, если его значение совпадает с именем объекта или элемента после нормализации пробелов и PascalCase. Для полной validation это правило уже должно проверяться кодом, потому что имя известно из пути файла, модели или имени элемента коллекции.

Предыдущий вариант подсказки в JSON Schema добавлял имя-зависимый `not` для конкретного объекта. На большом YAML-проекте это делает schema уникальной для каждого имени, из-за чего `validateProject` компилирует и удерживает тысячи TypeBox-схем до конца процесса.

## Решение

JSON Schema должна снова быть универсальной для типа metadata-объекта или формы. Для полей с `excludeIfEqualNameYAML: true` schema добавляет только текстовую подсказку в `description`:

> Не указывайте это поле, если значение совпадает с именем объекта/элемента после нормализации пробелов и PascalCase.

Schema не должна содержать конкретное имя объекта, `Type.Not`, `Type.Literal(splitPascalCase(name))` или другие ограничения, зависящие от имени. Благодаря этому `validateProject` сможет компилировать schema по типу, а не по каждому объекту.

Строгий запрет остаётся в кодовой validation через `validateExcludedEqualNameYAML`. Этот валидатор получает `parsed`, `rule`, `context` и имя текущего объекта или элемента, поэтому может точно проверить `I8nText` и `FormattedI8nText` без участия JSON Schema.

## Поведение schema

- Одна schema применима ко всем объектам одного вида.
- Подсказка добавляется к любому YAML-полю с `excludeIfEqualNameYAML: true`, независимо от имени поля: `Синоним`, `Заголовок` или другое имя из `rules.ts`.
- Текст не должен говорить только про синоним, потому что у элементов форм это может быть поле с другим YAML-ключом.
- Для `FormattedI8nText` подсказка должна быть видна на соответствующем поле целиком; отдельного имени-зависимого запрета внутри `Текст` не нужно.
- Общие schema по имени типа и schema конкретного файла не должны различаться только из-за имени объекта.

## Поведение validation

- `validateProject` компилирует schema для свойств по стабильному ключу типа/spec, без имени объекта.
- После schema validation выполняется `validateExcludedEqualNameYAML`.
- Для обычных `Свойства.yaml` имя объекта берётся из metadata-пути.
- Для `Конфигурация.yaml` имя берётся из импортированной модели, то есть из поля `Имя`, если модель удалось получить.
- Для вложенных элементов имя берётся из YAML-ключа элемента или из его поля `Имя`, как уже предусмотрено валидатором.
- Проверка распространяется на `I8nText` и `FormattedI8nText`.
- Для многоязычной строки проверяется язык по умолчанию, чтобы поведение соответствовало экспорту.

## Ошибки

Если значение совпадает с именем после нормализации, validation возвращает ошибку `structure` на фактическом YAML-пути поля. Сообщение объясняет, что поле не нужно указывать, если значение совпадает с именем объекта или элемента.

Schema description остаётся только подсказкой для редакторов и агентов. Она не является источником строгого запрета.

## Проверка

- Тест schema подтверждает, что поле с `excludeIfEqualNameYAML` получает универсальный `description`.
- Тест schema подтверждает отсутствие имени-зависимого `not`/`const` для конкретного имени объекта.
- Тест `validateProject` подтверждает, что совпадающее значение всё ещё считается ошибкой.
- Тест кэша schema подтверждает, что свойства одного вида компилируются один раз или по стабильному ключу без имени объекта.
- Контрольный запуск `validate /Users/nikita/git/nkdk-yaml` больше не должен падать из-за накопления имя-зависимых скомпилированных схем.

## Критерий готовности

Полная validation снова использует общие схемы и не накапливает скомпилированную schema на каждый объект. Подсказчик schema всё ещё сообщает агенту правило `excludeIfEqualNameYAML`, а строгая проверка выполняется кодом с доступом к имени объекта или элемента.

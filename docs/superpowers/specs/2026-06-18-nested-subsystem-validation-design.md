# Валидация вложенных подсистем

## Контекст

После расширения `validate` на все верхнеуровневые metadata item проверка ERP-проекта нашла `37508` файлов: `Конфигурация.yaml`, `Свойства.yaml` верхнего уровня и `Форма.yaml`.

Отдельная сверка показала `949` файлов, которые не попали в `discoverValidationProjectFiles()`. Все они имеют вид:

```text
Подсистема/<Имя>/Подсистемы/<Имя>/.../Свойства.yaml
```

Причина пропуска находится в `packages/core/metadata/validation/projectFiles.ts`: текущий `matchPropertiesPath()` принимает только путь из трех частей `<Вид>/<Имя>/Свойства.yaml`. Вложенная подсистема имеет пять и более частей, поэтому `resolveValidationProjectFile()` возвращает `undefined`.

Валидация ссылок уже умеет строить путь к вложенной подсистеме через `nestedObjectFilePath()` в `projectMetadataResolver.ts`; проблема ограничена поиском и распознаванием файлов проекта для запуска схемной валидации.

## Цель

Включить в `validate` все `Свойства.yaml` вложенных подсистем.

В рамках этой доработки не добавлять поддержку форм вложенных подсистем: в проверенной ERP-выгрузке таких файлов нет, и для metadata subsystem они сейчас не являются ожидаемым сценарием.

## Дизайн

`projectFiles.ts` получает отдельное распознавание вложенных подсистем:

- путь должен начинаться с `Подсистема/<Имя>`;
- дальше допускается одна или несколько пар `Подсистемы/<Имя>`;
- последняя часть должна быть `Свойства.yaml`;
- `owner.spec` остается `MetadataSubsystemRules` через существующий spec для `Подсистема`;
- `owner.name` берется из последнего имени подсистемы в пути.

Пример:

```text
Подсистема/Администрирование/Подсистемы/Настройки/Свойства.yaml
```

должен распознаваться как `kind: "properties"` с владельцем `dir: "Подсистема"`, `name: "Настройки"`.

`discoverValidationProjectFiles()` должен рекурсивно обходить только каталог `Подсистема` и добавлять вложенные `Свойства.yaml`, соответствующие этому шаблону. Общий рекурсивный поиск всех `Свойства.yaml` не нужен: он расширит поведение на неизвестные вложенные структуры и повысит риск ложной валидации служебных файлов.

`resolveValidationProjectFile()` должен принимать такие пути и для `--file`, чтобы ручная проверка одного файла работала тем же способом, что и полный обход проекта.

## Ошибки и границы

Пути вложенных подсистем с нарушенной структурой, например `Подсистема/А/Подсистемы/Свойства.yaml`, должны оставаться неподдержанными и попадать в существующую ошибку CLI для неподдержанного `--file`.

Файлы форм под вложенными подсистемами не добавляются в обход. Если такой формат появится позже, его нужно проектировать отдельно после проверки XML/YAML-контракта для subsystem forms.

## Тестирование

Нужны проверки в `packages/core/metadata/validation/projectFiles.test.ts`:

- `discoverValidationProjectFiles()` находит вложенный `Подсистема/<Имя>/Подсистемы/<Имя>/Свойства.yaml`;
- поддерживается несколько уровней вложенности;
- `resolveValidationProjectFile()` распознает такой путь для `--file`;
- некорректная структура `Подсистемы` не распознается;
- формы вложенных подсистем не добавляются в результат.

Нужна проверка в `packages/core/metadata/validation/validateProject.test.ts` или CLI-тесте:

- `validate` применяет JSON Schema к вложенной подсистеме и возвращает ошибку схемы при лишнем поле.

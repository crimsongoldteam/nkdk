# Быстрое полное построение графа через replace-режим

## Контекст

На ERP-проекте `/Users/nikita/git/erp_nkdk` полный запуск `nkdk update-graph` занял около `349314.4 мс`.
Разбивка показала, что чтение файлов занимает около `5660.0 мс`, `buildGraph` - около `69662.4 мс`, а запись в FalkorDB - около `273990.1 мс`.

Основное узкое место находится в записи графа. Текущий путь рассчитан на универсальное обновление: он удаляет данные по файлам, сохраняет стабы, затем выполняет `MERGE` для файлов, узлов, ребер и связей файлов с узлами. Для первичного построения с нуля такая осторожность избыточна.

## Цель

Ускорить полный первичный импорт графа для пустого или полностью заменяемого графа.

Не цель: менять семантику обычного инкрементального обновления, watcher или поведение удаления по отдельным файлам.

## Предлагаемое решение

Добавить в `@nakidka/graph` режим полного замещения:

```ts
updateGraph(files, { replace: true })
```

В этом режиме запись идет по отдельному быстрому пути:

1. `resetGraph`
2. `ensureFileIndexes`
3. `ensureLabelIndexes`
4. `createFiles`
5. `createNodes`
6. `createEdges`
7. `createFileLinks`

Обычный `updateGraph(files)` остается без изменений и продолжает использовать `deleteByFiles`, `mergeFiles`, `mergeNodes`, `mergeEdges`, `mergeFileLinks`, `cleanupOrphanStubs`.

В CLI добавить флаг:

```bash
nkdk update-graph <path> --replace
```

Полный `update-graph --replace` должен заменить текущий двухшаговый путь `writeGraph([])` + обычный `writeGraph(graphFiles)` на один вызов `writeGraph(graphFiles, { replace: true })`.

## Быстрые операции

`createFiles`, `createNodes`, `createEdges` и `createFileLinks` используют `CREATE` вместо `MERGE`, потому что после `resetGraph` граф пустой.

Ожидаемые замены:

- `mergeFiles`: `MERGE (f:File {path}) SET ...` заменить на `CREATE (f:File {...})`
- `mergeNodes`: `MERGE (m:Label:GraphNode {id}) SET ...` заменить на `CREATE (m:Label:GraphNode {...})`
- `mergeEdges`: `MATCH ... MERGE (s)-[r:KIND]->(t) SET ...` заменить на `MATCH ... CREATE (s)-[r:KIND {...}]->(t)`
- `mergeFileLinks`: `MATCH ... MERGE (f)-[:DECLARES|CONTRIBUTES]->(n)` заменить на `MATCH ... CREATE ...`

Размер пачки оставить настраиваемым внутри реализации или начать с текущего `BATCH_SIZE`, чтобы сначала получить безопасный замер. Увеличение пачки можно делать отдельным шагом после проверки, потому что слишком крупные Cypher-запросы могут упереться в ограничения FalkorDB или Redis.

## Проверки целостности

Перед записью `replace`-режим должен проверять в памяти:

- уникальность `File.path`;
- уникальность `Node.id`;
- отсутствие дублей в `DECLARES` и `CONTRIBUTES` для пары `filePath + nodeId`.

Дубли обычных ребер можно не запрещать в первом шаге, потому что текущий графовый слой может представлять несколько семантических связей одного типа между одной парой узлов с разными свойствами. Если позже выяснится, что такие дубли невозможны по модели, это можно усилить отдельной проверкой.

Если проверка падает, запись в базу не начинается.

## Обработка ошибок

Если `replace`-запись падает после `resetGraph`, граф может остаться неполным. Это приемлемо для режима полного замещения: пользователь может повторить команду.

Сообщение об ошибке должно быть обычным исключением CLI. Дополнительный откат не нужен, потому что он усложнит путь и не восстановит старый граф после `resetGraph`.

## Тестирование

Нужны тесты на уровне `packages/graph`:

- `updateGraph(files, { replace: true })` вызывает быстрый путь и не выполняет `deleteByFiles` / `cleanupOrphanStubs`;
- `replace`-режим падает до записи при дублях `File.path`;
- `replace`-режим падает до записи при дублях `Node.id`;
- интеграционный тест на маленьком графе показывает, что результат обычного полного пути и `replace`-пути эквивалентен для файлов, узлов, ребер и связей файлов.

Нужны тесты на уровне CLI:

- `update-graph --replace` передает `replace: true` в `@nakidka/graph`;
- обычный `update-graph` остается без `replace`.

## Критерий успеха

На ERP-проекте полный импорт графа через `update-graph --replace` должен быть быстрее текущего полного пути. Минимально полезная цель - заметно сократить фазу `updateGraph`, которая в последнем замере занимала около `274 с`.

Корректность важнее максимальной скорости: первый шаг должен заменить `MERGE` на `CREATE` только в режиме полного замещения и не менять инкрементальный путь.

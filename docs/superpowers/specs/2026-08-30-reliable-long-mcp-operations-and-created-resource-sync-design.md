# Надёжные операции MCP, частичная загрузка и основы форм расширений

## Контекст

В реальном сценарии с проектом `sed_nkdk` проявились три независимых дефекта.

Первый дефект относится к длительным инструментам MCP. Импорт основной конфигурации выполняется около девяти минут, тогда как клиент завершает один вызов примерно через 300 секунд. Серверная работа после разрыва может продолжиться, но клиент теряет её состояние и итог. Увеличение внутреннего тайм-аута запуска 1С эту проблему не решает: ограничение находится снаружи процесса NKDK.

Второй дефект относится к частичной загрузке в информационную базу. При заимствовании формы NKDK сформировал полный `Ext/Form.xml`, однако в пакет загрузки вошёл только описатель формы. В результате объект формы появился в расширении, но его содержимое в Конфигураторе оказалось пустым. Причина не специфична для форм: новый metadata-элемент может состоять из нескольких XML-документов и внешних файлов, а текущая политика минимальной загрузки рассчитана прежде всего на изменение уже существующего элемента.

Третий дефект относится к сохранённой основе заимствованной формы. NKDK уже не создаёт `БазоваяФорма.yaml`, когда может восстановить `BaseForm` из формы `cf` и рабочей формы `cfe`, но сравнение выполняется для разных представлений. Например, импортированная `BaseForm` содержит `События`, а вычисленная проекция намеренно их исключает. В результате смыслово одинаковые основы считаются разными, избыточный файл сохраняется, а валидатор не запрещает добавить такой файл вручную.

Изменения решаются двумя независимыми слоями. Диспетчер операций не должен знать устройство metadata-пакета, а планировщик частичной синхронизации не должен зависеть от транспорта MCP.

## Цели

- Сделать длительные операции независимыми от времени жизни одного вызова MCP.
- Дать клиенту единый способ получить состояние и итог операции, а также отменить её.
- Сохранить состояние операции при перезапуске MCP без сохранения секретов.
- При создании metadata-элемента загружать все фактически сформированные файлы его нового поддерева.
- Сохранить минимальную загрузку для изменения и удаления существующих элементов.
- Использовать один и тот же алгоритм загрузки для `designer-agent` и `standalone-server`.
- Использовать одно смысловое правило необходимости `БазоваяФорма.yaml` при импорте и валидации.
- Не сохранять и запрещать избыточную основу, полностью восстанавливаемую из `cf` и рабочей формы `cfe`.
- Сохранять основу, содержащую хотя бы одно значимое отличие от вычисляемой.

## Не входит в изменение

- Реализация экспериментального расширения MCP Tasks.
- Автоматическое продолжение прерванной операции после перезапуска процесса.
- Изменение смысловых правил XML/YAML или применение новых тегов `!xml`.
- Частные условия для форм, макетов, `ChildFormNames` или конкретных `itemType` в нейтральных слоях.
- Изменение существующих XML-фикстур.
- Полный запрет `БазоваяФорма.yaml`: файл остаётся допустимым при значимом отличии сохранённой основы.

## Часть 1. Фоновые операции MCP

### Выбор механизма

Протокол MCP 2026-07-28 описывает Tasks как отдельное расширение, а используемый TypeScript SDK пока не предоставляет готовую серверную реализацию этого механизма. Поэтому NKDK вводит прикладной диспетчер операций поверх обычных инструментов MCP. Его договор локален для NKDK и не выдаётся за стандартный MCP Tasks API.

Когда SDK получит стабильную поддержку Tasks, транспортный слой можно будет заменить адаптером, не меняя исполнители операций и файловое хранилище их состояния.

### Какие действия становятся фоновыми

Через диспетчер выполняются операции, время которых зависит от размера конфигурации или запуска платформы:

- импорт из информационной базы;
- импорт из XML;
- синхронизация в информационную базу;
- синхронизация в XML;
- перестроение кеша проекта;
- полная валидация проекта.

Короткие запросы чтения и локального редактирования остаются синхронными.

### Договор инструментов

Длительный инструмент после проверки входного договора и права на запись создаёт задание и немедленно возвращает:

```json
{
  "ok": true,
  "status": "accepted",
  "operationId": "019d...",
  "operationKind": "sync_to_infobase",
  "projectDir": "C:/git/sed_nkdk"
}
```

Возврат `accepted` означает только успешное принятие задания. Он не означает успешного импорта или синхронизации.

Добавляются два общих инструмента:

- `nkdk_get_operation(projectDir, operationId)` возвращает состояние, этап, прогресс, диагностические сообщения и, после завершения, исходный структурированный результат операции;
- `nkdk_cancel_operation(projectDir, operationId)` запрашивает отмену и возвращает актуальное состояние.

Итог хранится как типизированный результат конкретного вида операции. Реестр операций связывает `operationKind` с исполнителем и схемой результата; общий инструмент возвращает дискриминированное объединение известных результатов, а не произвольный объект.

### Модель состояния

Состояния операции:

```text
queued -> running -> succeeded
                  -> failed
                  -> cancelled
                  -> interrupted
```

- `queued` — задание принято и ожидает существующую блокировку проекта или компонента;
- `running` — исполнитель начал работу;
- `succeeded` — сохранён полный результат исходного инструмента;
- `failed` — сохранена нормализованная ошибка и доступная диагностика;
- `cancelled` — отмена была запрошена и исполнитель подтвердил остановку;
- `interrupted` — процесс завершился до терминального состояния задания.

Процент указывается только там, где исполнитель знает общий объём. Во всех остальных случаях публикуются текущий этап, время последнего изменения и накопленные сообщения без выдуманного процента.

### Отделение от вызова клиента

Сигнал отмены исходного MCP-вызова действует только до момента сохранения задания. После ответа `accepted` работа получает отдельный `AbortController` и не связана с сигналом клиента. Остановить её можно только через `nkdk_cancel_operation` или при завершении процесса MCP.

Существующие блокировки проекта и компонента остаются единственным механизмом взаимоисключения. Диспетчер не вводит параллельную систему блокировок: если ресурс занят, операция остаётся в `queued` до входа в существующую критическую секцию.

### Хранение

Каждый проект хранит записи в `.nkdk/operations/<operationId>.json`. Запись содержит:

- идентификатор и вид операции;
- безопасные параметры маршрутизации, например `projectDir` и `componentPath`;
- состояние, этап и временные метки;
- диагностические сообщения;
- терминальный результат или нормализованную ошибку.

Запись обновляется атомарно через временный файл и переименование. Пароли, строки подключения с паролями, токены и значения секретных переменных не сериализуются. Исполнитель получает секреты через существующую конфигурацию проекта непосредственно перед запуском.

При старте диспетчер переводит найденные `queued` и `running` в `interrupted`: автоматическое повторение потенциально изменяющей базу операции небезопасно. Терминальные записи сохраняются 30 дней; очистка выполняется при старте и никогда не удаляет активные записи.

### Ошибки и диагностика

Ошибка принятия задания возвращается обычной ошибкой инструмента и не создаёт `operationId`. Ошибка после принятия переводит запись в `failed`, сохраняет код, понятное сообщение, стадию и ссылки на сформированные диагностические файлы.

Логи платформы продолжают записываться в существующий `platform.log`. Диспетчер хранит путь и краткие сообщения, но не дублирует весь потенциально большой журнал в JSON операции.

### Совместимость транспорта

Диспетчер является процессным прикладным сервисом, общим для экземпляров MCP-сервера. Это важно для HTTP-транспорта, где серверный объект может создаваться на запрос: следующий вызов `nkdk_get_operation` должен видеть задание, принятое предыдущим экземпляром. Источником восстановления после перезапуска служат файлы проекта.

## Часть 2. Полная загрузка вновь созданного metadata-поддерева

### Разделение сформированных файлов и целей загрузки

Планировщик уже различает:

- файлы, которые требуется сформировать в промежуточном XML-каталоге;
- файлы, которые требуется передать платформе как цели частичной загрузки.

Для существующего элемента это различие полезно: зависимый файл можно сформировать для целостности пакета, но не загружать. Для нового элемента такая минимизация неверна — платформа должна получить всё новое представление элемента, иначе создаётся неполный объект.

### Общий признак создания

Планировщик определяет создание по отсутствию соответствующего назначения или участника в исходном снимке и его наличию в целевом снимке. Решение принимается по модели изменений и топологии ресурсов, а не по имени каталога или типу объекта.

Для созданного назначения или file-backed участника строится замыкание нового поддерева:

- собственный metadata-документ;
- все сформированные XML-документы ресурсов этого поддерева;
- все сформированные внешние файлы этого поддерева;
- необходимые описатели владельца, уже добавляемые структурной политикой.

Кандидаты затем пересекаются с `writtenPayloadPaths`. Поэтому отсутствующий необязательный `Ext/Module.bsl`, картинка, справка или иной ресурс не становится ошибочной целью загрузки. В пакет попадает только то, что действительно записано текущим `sync_to_xml`.

### Пример формы

Для вновь заимствованной формы промежуточный каталог может содержать:

```text
Documents/АктОбУничтоженииПерсональныхДанных.xml
Documents/АктОбУничтоженииПерсональныхДанных/Forms/ФормаДокумента.xml
Documents/АктОбУничтоженииПерсональныхДанных/Forms/ФормаДокумента/Ext/Form.xml
Documents/АктОбУничтоженииПерсональныхДанных/Forms/ФормаДокумента/Ext/Module.bsl
```

Если все четыре файла были сформированы, все требуемые файлы нового поддерева входят в загрузку. Если модуль отсутствует, он автоматически отфильтровывается; описатель и `Ext/Form.xml` всё равно загружаются. Именно это предотвращает создание пустой формы.

### Существующие элементы

Для изменения существующего элемента продолжают действовать зарегистрированные политики `loadDocumentRoles`, `includeOwnerAssignment` и другие ограничения минимального пакета. Политика формы включает оба XML-документа, формируемых из её основного YAML: описатель формы и `Ext/Form.xml`; платформа не применяет тело формы только из-за его присутствия в ZIP, поэтому оба пути должны входить в `load.lst`.

Если изменяемый file-backed участник требует назначения владельца, пакет дополнительно включает непрерывную цепочку его структурных предков. Для вложенной формы это `Configuration.xml → Documents/<Документ>.xml → Forms/<Форма>.xml → Ext/Form.xml`. Без корневого и родительского описателей Конфигуратор отклоняет частичную загрузку как добавление объекта без родителя. В цепочку входят только описатели предков, а не их соседние ресурсы. Изменение только модуля при этом не превращается в полную перезагрузку формы.

Для удаления сохраняется существующий договор удаления и структурного описателя владельца. Полное новое поддерево загружается только при создании, а непрерывная цепочка структурных предков применяется к созданию, изменению и удалению вложенного участника.

### Граница ответственности

Общий `impactPlanner` работает с нейтральными понятиями назначения, участника, документа и внешнего ресурса. Конкретные metadata-модули по-прежнему регистрируют топологию и роли документов. В `impactPlanner`, `packagePolicy`, validation и project-слоях не появляются проверки `Form`, `Макеты`, `ChildFormNames` или иных конкретных типов.

Окончательный список `loadTargets` строится до вызова платформы и одинаково передаётся адаптерам `designer-agent` и `standalone-server`. Адаптеры не дополняют и не сокращают его самостоятельно.

## Часть 3. Избыточная `БазоваяФорма.yaml`

### Область действия

Сохранённая основа существует только для управляемых форм `ClientApplicationForm` и представлена необязательным `yamlCompanion` с ролью `form`. Единый договор применяется к обоим размещениям:

- вложенная форма объекта: `<Объект>/.../Формы/<Форма>/БазоваяФорма.yaml`;
- общая форма: `ОбщаяФорма/<Форма>/БазоваяФорма.yaml`.

Состояния свойств расширения, история расширения и основная конфигурация `cf` не являются сохранёнными основами формы и этим правилом не затрагиваются.

### Смысловое сравнение

Сравниваются не байты и не текст YAML-файлов. Пробелы, порядок ключей и способ форматирования не влияют на результат. Общая функция получает три смысловые модели:

1. текущую форму основной конфигурации `cf`;
2. рабочую форму расширения `cfe`;
3. сохранённую `БазоваяФорма.yaml`.

Из `cf` и рабочей формы `cfe` строится ожидаемая проекция `BaseForm`. Сохранённая основа проходит через тот же проектор с той же рабочей формой `cfe`. После этого обе проекции сравниваются через нормализованное равенство `BaseForm`.

```text
ожидаемая = projectBaseForm(cf, cfe)
сохранённая = projectBaseForm(БазоваяФорма.yaml, cfe)
избыточна = equalBaseFormYaml(сохранённая, ожидаемая)
```

Именно симметричная проекция исправляет ложное различие `Событий`: проектор намеренно исключает их с обеих сторон, а не только из ожидаемой основы. Технические XML-поля `_id`, `_uuid`, `_version`, пространства имён и порядок YAML также не участвуют в равенстве. Значимые свойства, например отличающаяся `Ширина`, состав элементов или реквизитов, продолжают различать основы.

### Единый договор импорта и валидации

Одна form-specific функция отвечает на вопрос, нужна ли сохранённая основа:

- импорт вызывает её перед записью проекта и не создаёт избыточную `БазоваяФорма.yaml`;
- валидатор вызывает тот же предикат и выдаёт ошибку для уже существующего избыточного файла;
- экспорт использует текущую форму `cf`, если основы нет, и сохранённую основу, если значимое отличие подтверждено.

Диагностика относится к корню `БазоваяФорма.yaml`, имеет уровень `error` и понятное сообщение: `БазоваяФорма.yaml избыточна: основа полностью восстанавливается из основной конфигурации и рабочей формы расширения`.

### Данные для инкрементальной валидации

Валидация не перечитывает связанные YAML-файлы с диска: это могло бы смешать содержимое файлов с другим снимком ProjectState. При извлечении фактов формы её каноническое, пригодное для проекции смысловое представление сохраняется в payload существующей записи `document` структурного документа.

Валидатор получает из одного подтверждённого снимка представления формы `cf`, рабочей формы `cfe` и сохранённой основы, восстанавливает их из payload и вызывает общий предикат. Новый отдельный файл проекта, отдельная база или специализированная таблица ProjectState не создаются. Нейтральные слои знают только о payload структурного документа; выбор проектора и диагностика остаются в concrete-модуле `clientApplicationForm`.

Если одна из трёх моделей недоступна или не готова, валидатор не делает предположения об избыточности. Существующие диагностики готовности и зависимостей сообщают первичную проблему; запрет появляется только при доказанном смысловом равенстве.

## Проверки

### Диспетчер операций

- Длительный инструмент возвращает `accepted` и `operationId`, не ожидая завершения искусственно задержанного исполнителя.
- Разрыв исходного клиентского сигнала после `accepted` не отменяет работу.
- `nkdk_get_operation` наблюдает переходы `queued`, `running` и терминальное состояние.
- Успешная операция возвращает исходный типизированный результат.
- Ошибка сохраняет код, этап и диагностику.
- `nkdk_cancel_operation` отменяет ожидающее и выполняющееся задание.
- После имитации перезапуска незавершённая запись становится `interrupted`.
- В сохранённом JSON отсутствуют пароль и другие секретные значения из тестового входа.
- Два экземпляра MCP-сервера в одном процессе видят одну операцию.

### Частичная синхронизация

- Создание многодокументного назначения включает в `loadTargets` все записанные XML-документы его поддерева.
- Создание file-backed участника включает записанные внешние файлы.
- Отсутствующий необязательный ресурс не включается и не вызывает ошибку.
- Изменение существующего элемента сохраняет прежний минимальный список загрузки.
- Удаление сохраняет прежний список загрузки.
- Оба режима платформы получают один и тот же рассчитанный список.
- Тесты используют абстрактную тестовую топологию; отдельный интеграционный тест формы подтверждает реальную регистрацию её документов.

### Основы форм

- Общий предикат признаёт равными две основы с разным порядком YAML и техническими XML-полями.
- Одинаковые `События` не заставляют сохранять основу, поскольку обе стороны проходят одну проекцию.
- Значимое отличие свойства, состава элементов, реквизитов, команд или параметров сохраняет основу.
- Импорт не создаёт избыточную основу вложенной и общей формы.
- Валидация выдаёт ошибку на избыточной основе вложенной и общей формы.
- Удаление избыточного файла очищает диагностику после инкрементального обновления ProjectState.
- Отсутствующая либо неготовая `cf` не приводит к ложной диагностике избыточности.
- Экспорт без сохранённой основы восстанавливает `BaseForm` из подтверждённой формы `cf`.

### Сквозная приёмка

На свежей сборке MCP выполняется синхронизация проекта `sed_nkdk`, содержащего заимствованную форму с изменённой надписью. После завершения операции через `nkdk_get_operation` конфигурация расширения выгружается обратно из базы. В выгрузке должны присутствовать полный `Ext/Form.xml`, исходные элементы формы и добавленная надпись; форма в Конфигураторе не должна быть пустой.

## Совместимость и переход

Ответы перечисленных длительных инструментов намеренно меняются: вместо конечного результата они возвращают принятую операцию. Внутренние клиенты и документация должны перейти на цикл `start -> get_operation`. Это изменение договора MCP, но не формата YAML-проекта.

Существующие синхронные сервисы исполнения сохраняются и становятся исполнителями диспетчера. Благодаря этому бизнес-логика остаётся доступна модульным и интеграционным тестам без MCP-транспорта.

## Документация архитектуры

Реализация добавит процессный диспетчер MCP и уточнит договор построения `loadTargets` при создании ресурса. После согласования этой спеки потребуется отдельно согласовать обновление `.agents/architecture.md`, как требует правило проекта; текущий коммит спеки этот файл не меняет.

## Критерии готовности

- Реальный импорт дольше 300 секунд завершается в фоне, а результат доступен по `operationId`.
- Клиент может явно отменить такую операцию и получить подтверждённое терминальное состояние.
- Перезапуск MCP не оставляет операцию навечно в `running` и не повторяет запись в базу.
- Заимствованная форма после частичной синхронизации содержит полный интерфейс, а не только пустой описатель.
- То же правило покрывает другие новые многодокументные и file-backed metadata-элементы без частных условий.
- Избыточная основа не создаётся импортом и запрещается валидатором для вложенных и общих форм.
- Значимо отличающаяся сохранённая основа остаётся допустимой и участвует в round-trip.
- Все модульные, интеграционные и архитектурные проверки проекта проходят.

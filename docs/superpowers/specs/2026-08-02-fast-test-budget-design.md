# Быстрый бюджет тестов

## Цель

Обычный `pnpm test` не должен содержать многосекундные unit- или интеграционные тесты. Каждый тест обязан завершаться не дольше 50 мс, а превышение 10 мс считается целью для последующей оптимизации. Подготовка файла и общие hooks также измеряются, чтобы дорогую работу нельзя было скрыть в `beforeAll` или импорте модуля.

## Наблюдаемая проблема

Полный прогон `packages/core` занимает 10–15 минут. Наиболее заметные источники задержки:

- `metadata/projectState/writerHandle.test.ts` многократно запускает настоящий worker, SQLite checkpoint и повторное открытие снимка; отдельный файл занимал несколько минут;
- `metadata/forms/elements/orchestration/toJSONSchema.test.ts` несколько раз строит и компилирует полную рекурсивную схему формы, хотя договоры относятся к отдельным свойствам; файл занимал десятки секунд и более;
- `maxWorkers: 1` усиливает суммарную задержку, но распараллеливание само по себе не исправляет медленные тесты и поэтому не является первым решением.

## Бюджет

- Жёсткий предел одного test case: `50` мс.
- Целевой предел одного test case: `10` мс. Превышение не останавливает команду, но выводится в отчёт.
- Жёсткий предел одного test file вместе с импортом, `beforeAll`, `afterAll` и test cases: `1 000` мс.
- Эти пределы одинаковы для unit- и интеграционных тестов.
- Повысить предел параметром командной строки или переменной окружения нельзя.
- Каждый неинтерактивный package script запускается переносимым runner-ом: тот создаёт уникальный каталог в системном tmp, получает JSON test cases и lifecycle-отчёт, проверяет их и удаляет каталог.

## Разделение тестов

### Unit

Координаторы, очереди, отмена, rollback и обработка ответов проверяются через подменяемые нейтральные порты. Мок воспроизводит протокол, порядок и ошибки, а не возвращает заранее подготовленный предметный результат вместо тестируемой логики.

`ProjectStateWriterHandle` не запускает настоящий `worker_threads.Worker` в каждом unit-тесте. Он получает фабрику транспорта, а быстрый тестовый транспорт записывает команды и позволяет управлять ответами, выходом worker и ошибками.

### Интеграция SQLite

Настоящий SQLite проверяется небольшими тестами на минимальной базе. Они также обязаны укладываться в 50 мс на test case и 1 000 мс на файл.

Повторные checkpoint/reopen не дублируются во всех тестах writer handle. Договоры хранения, совместимости, повреждённого снимка и атомарной публикации остаются в `sqlite/persistence.test.ts`. Если профилирование подтверждает задержку `node:sqlite backup`, production-путь загрузки и сохранения переводится на `DatabaseSync.serialize()`/`deserialize()` с той же атомарной публикацией. Ошибки записи, проверки и rename продолжают проверяться управляемыми hooks.

Отдельная команда `test:integration` не освобождается от бюджета и не используется как склад медленных сценариев.

### JSON Schema

Тест свойства не строит полную рекурсивную схему формы. Он вызывает ближайший экспортёр правила свойства и проверяет компактный фрагмент схемы. Один сквозной договор регистрации полной схемы сохраняется только если укладывается в бюджет файла; иначе проверяется более узкая наблюдаемая граница, а стоимость полной компиляции измеряется профилем, не функциональным тестом.

## Контроль длительности

Переходник объединяет JSON-отчёт Vitest и lifecycle-отчёт custom runner/reporter:

- `assertionResults[].duration` проверяется против 10 и 50 мс;
- custom runner отмечает начало импорта test module, reporter складывает import с интервалом от старта test module до завершения hooks и проверяет его против 1 000 мс; ожидание очереди между collection и исполнением не приписывается файлу;
- неизвестный или неполный формат отчёта считается ошибкой;
- вывод сортируется по длительности и содержит имя файла/test case и фактическое время;
- код возврата ненулевой, если test case превысил 50 мс или файл превысил 1 000 мс.

Проверка подключается к `packages/core`, `packages/platform` и `packages/mcp`. Интерактивный `test:ui` остаётся исключением.

## Порядок исправления

1. Сначала добавить проверку бюджета и зафиксировать RED на текущих медленных файлах.
2. Затем ускорить project-state тесты: мок транспорта writer handle, минимальные SQLite-интеграции и устранение медленного backup/reopen пути.
3. Затем перенести проверки свойств формы на ближайший экспортёр без полной рекурсивной схемы.
4. Только после соблюдения бюджета рассматривать увеличение числа Vitest workers по отдельному измерению памяти и устойчивости.

## Проверка результата

- целевые файлы проходят проверку 10/50/1 000 мс;
- `pnpm test` проходит с обязательной проверкой бюджета во всех пакетах;
- число и содержание наблюдаемых договоров не уменьшается;
- существующие XML-фикстуры не изменяются;
- mutation testing в рамках текущей реализации project-state не запускается по решению пользователя;
- до и после фиксируются полное время `pnpm test` и самые медленные test cases/files.

## Границы

- Нельзя лечить проблему только распараллеливанием.
- Нельзя повышать лимиты для отдельного теста.
- Нельзя переносить медленный тест в `test:integration` без ускорения.
- Нельзя мокать SQLite там, где проверяемый договор — SQL-схема, сериализация, совместимость или атомарная публикация.
- Нельзя сохранять настоящий worker/SQLite в тесте, если его договор полностью выражается нейтральным портом.

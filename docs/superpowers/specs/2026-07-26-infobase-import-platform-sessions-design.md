# Импорт из информационной базы через сеансы платформы

## Цель

Добавить публичную MCP-операцию, которая выгружает основную конфигурацию
выбранной информационной базы 1С во временный XML-каталог, а затем выполняет
существующий импорт XML → YAML в новый компонент `cf`.

Операция поддерживает два способа доступа к платформе 1С 8.3.27, каждый для
файловой и клиент-серверной базы:

- агентный режим Конфигуратора;
- offline-режим автономного сервера через `ibcmd`.

Сеансы сохраняются внутри долгоживущего MCP-процесса и переиспользуются до
истечения настраиваемого времени простоя или явного закрытия. Для агента это
живое SSH-соединение; для `ibcmd` — подготовленный `config.yaml`, а сама
выгрузка остаётся отдельным коротким процессом.

## Границы

Входит в первый выпуск:

- файловые и клиент-серверные информационные базы;
- основная конфигурация и компонент `cf`;
- только отсутствующий или пустой целевой `cf`;
- временная иерархическая XML-выгрузка внутри `.nkdk`;
- перенос внешних файлов из временной выгрузки вместо копирования;
- локально запускаемый агент Конфигуратора для файловой или клиент-серверной базы;
- выгрузка файловой или клиент-серверной базы через `ibcmd infobase config export`;
- параметры СУБД для клиент-серверной базы в MCP-входе и настройках проекта;
- кеширование одного сеанса на `projectDir`;
- настраиваемое закрытие сеанса по времени простоя;
- явное закрытие одного или всех сеансов через MCP;
- сохранение настроек базы, логина и пароля в `.nkdk/project.yaml`.

Не входит:

- web-базы;
- версии платформы, отличные от `8.3.27`;
- расширения, внешние отчёты и обработки;
- импорт в непустой компонент;
- обновление существующего YAML-проекта;
- подключение к заранее запущенному удалённому агенту или автономному серверу;
- сохранение соединения между перезапусками MCP;
- шифрование пароля;
- транзакционный откат частично записанного YAML-проекта.

## Основания выбора

Команда агента `config dump-config-to-files` работает для файловой и
клиент-серверной базы. Ограничение документации относится только к параметру
`--server`: серверная многопоточная выгрузка игнорируется автономным сервером и
агентом Конфигуратора в файловом режиме. NKDK не передаёт `--server`.

Каталоги команд агента разрешаются относительно служебного каталога
SSH-пользователя внутри `/AgentBaseDir`. NKDK задаёт `/AgentBaseDir` равным
`.nkdk` проекта, читает сопоставление пользователя из `agentbasedir.json`,
выгружает во внутренний staging-каталог пользователя и затем переименовывает
его в каталог операции `.nkdk/tmp`. Это не требует запрещённого перехода `..`
из служебного каталога и позволяет переиспользовать агент.

Для файловой базы используется документированный вызов
`ibcmd infobase config export --config=<config.yaml> <xmlDir>`. Запущенный
`ibsrv` держит исключительную блокировку файловой базы и мешает этому вызову,
поэтому автономный адаптер не держит постоянный процесс: он кеширует
подготовленный `config.yaml`, а каждую выгрузку выполняет отдельным `ibcmd`.

Для клиент-серверной базы `ibcmd` нужны параметры и учётные данные СУБД;
обычной строки подключения 1С `Srvr="...";Ref="...";` недостаточно. Они
передаются вложенным объектом `database` и сохраняются в
`.nkdk/project.yaml`. Для файловой базы `database` не требуется.

## Границы пакетов

### `@nkdk/platform`

Пакет владеет всей интеграцией с установленной платформой:

- читает и записывает настройки проекта;
- находит `1cv8`, `ibcmd` и `ibsrv`, но для текущих операций требует только
  `1cv8` в агентном режиме либо `ibcmd` в offline-режиме автономного сервера;
- запускает процессы платформы;
- открывает SSH-сеансы;
- выполняет команды платформы;
- кеширует и закрывает соединения;
- выгружает конфигурацию в указанный XML-каталог.

Пакет не зависит от `@nkdk/core` и `@nkdk/mcp`. Конкретные реализации агента и
автономного сервера остаются внутренними.

`@nkdk/platform` использует `ssh2` напрямую, без `node-ssh`. При публикации MCP
пакеты `ssh2` и `yaml` остаются внешними для esbuild и объявляются прямыми
runtime-зависимостями `@nkdk/mcp`: оба содержат CommonJS-код с динамическими
`require`, который нельзя надёжно встроить в основной ESM-файл. Установка через
npm доставляет эти зависимости рядом с MCP.

Публичный API строится вокруг менеджера:

```ts
type PlatformSessionManager = {
  exportConfiguration(params: ExportConfigurationParams): Promise<ExportConfigurationResult>
  closeConnection(projectDir: string): Promise<CloseConnectionResult>
  closeAllConnections(): Promise<CloseAllConnectionsResult>
}

function createPlatformSessionManager(): PlatformSessionManager
```

### `@nkdk/core`

Существующий XML → YAML импорт получает только нейтральную стратегию передачи
внешних файлов:

```ts
type ExternalFileTransfer = "copy" | "move"
```

Значение по умолчанию — `copy`, поэтому договор обычного импорта из XML не
меняется. `core` не знает об информационной базе, процессах 1С, SSH и временном
каталоге операции.

### `@nkdk/mcp`

MCP связывает экспорт платформы с существующим импортом:

1. проверяет подтверждение записи и пустой `cf`;
2. создаёт каталог операции;
3. получает XML-выгрузку через `@nkdk/platform`;
4. вызывает обычный импорт XML → YAML со стратегией `move`;
5. после полного успеха записывает настройки проекта;
6. удаляет временную XML-выгрузку;
7. возвращает единый результат.

Менеджер соединений создаётся на время жизни MCP-сервера. При завершении
сервера MCP вызывает `closeAllConnections()`.

## Настройки проекта

Файл `.nkdk/project.yaml` имеет версионированный формат:

```yaml
version: 1
infobase:
  connectionString: 'Srvr="server";Ref="base";'
  user: Администратор
  password: secret
  useStandaloneServer: true
  sessionIdleTimeout: 900
  database:
    dbms: PostgreSQL
    server: db.example.local
    name: production
    user: dbuser
    password: dbsecret
```

Правила полей:

- `connectionString` обязателен и хранится в исходном формате 1С;
- поддерживаются `File` и сочетание `Srvr`/`Ref`;
- `user` и `password` необязательны;
- `useStandaloneServer` по умолчанию равен `false`;
- `sessionIdleTimeout` — положительное целое число секунд, по умолчанию `900`;
- `database` содержит `dbms`, `server`, `name`, `user` и необязательный
  `password` пользователя СУБД;
- `database.dbms` принимает `MSSQLServer`, `PostgreSQL`, `IBMDB2` или
  `OracleDatabase`;
- для `Srvr`/`Ref` вместе с `useStandaloneServer: true` объект `database`
  обязателен;
- для файловой базы `database` не используется и отклоняется как лишняя
  настройка.

Первый успешный `import_from_infobase` записывает настройки, переданные во
входе MCP. Настройки не записываются при ошибке экспорта или импорта.

Пароль хранится открытым текстом по принятому решению. `.nkdk` должен быть
исключён из Git; операция обеспечивает локальное правило игнорирования внутри
`.nkdk`. На Unix файл получает режим `0600`. На Windows Node.js не управляет
полноценными ACL, поэтому режим файла не является отдельной гарантией доступа.
Пароль никогда не включается в журналы, сообщения, диагностику или MCP-ответ.

## Менеджер соединений

Менеджер хранит не более одного сеанса на канонический `projectDir`. Сеансы
разных проектов независимы.

Получение соединения выполняется так:

1. операции одного проекта ставятся в последовательную очередь;
2. менеджер ищет кешированный сеанс;
3. совпадают строка подключения, учётные данные информационной базы, параметры
   СУБД и режим;
4. для агента проверяются дочерний процесс и SSH-сеанс, для `ibcmd` — логическое
   состояние подготовленного сеанса;
5. живой сеанс переиспользуется;
6. устаревший сеанс закрывается, затем создаётся новый.

Время простоя отсчитывается только при отсутствии выполняемой операции. После
каждой операции таймер начинается заново. По истечении
`sessionIdleTimeout` менеджер закрывает SSH и запущенный им агент. В режиме
`ibcmd` он только удаляет логический сеанс из кеша; постоянного процесса нет.

Менеджер не объединяет соединения разных проектов, даже если их настройки
совпадают. Это сохраняет понятное владение процессом и не смешивает учётные
данные.

## Агент Конфигуратора

Адаптер:

1. принимает `File` или `Srvr`/`Ref` и переводит строку в параметры запуска
   Конфигуратора;
2. выбирает свободный локальный порт;
3. создаёт отдельный RSA-ключ, запускает `1cv8 DESIGNER` с `/AgentMode`,
   loopback-адресом, `/AgentSSHHostKey`, `/AgentBaseDir=<projectDir>/.nkdk`
   и отдельным журналом;
4. повторяет подключение до готовности либо тайм-аута;
5. открывает SSH shell;
6. включает JSON-представление ответов;
7. выполняет `common connect-ib`, отвечая на запросы логина и пароля;
8. читает и проверяет служебный каталог пустого SSH-пользователя из
   `.nkdk/agentbasedir.json`;
9. предоставляет общий сеанс команд `config`.

SSH-клиент принимает только SHA-256 хэш созданного для сеанса ключа. Логин и
пароль не могут содержать NUL, CR или LF, поэтому их нельзя превратить в
дополнительную интерактивную команду.

Закрытие сначала выполняет `common disconnect-ib`, затем `common shutdown`;
каждая служебная команда ограничена `closeTimeoutMs`. После этого адаптер
закрывает SSH и ждёт дочерний процесс. После тайм-аута процесс завершается
принудительно.

## Offline-режим автономного сервера через `ibcmd`

Адаптер принимает `File` или `Srvr`/`Ref`:

1. проверяет наличие `ibcmd`;
2. создаёт служебный каталог сеанса;
3. для `File` создаёт `config.yaml` через
   `ibcmd server config init --database-path=...`;
4. для `Srvr`/`Ref` требует `database` и создаёт `config.yaml` с параметрами
   `--dbms`, `--database-server`, `--database-name`, `--database-user` и
   необязательным `--database-password`;
5. пересоздаёт `config.yaml` с правами `0600` на Unix и удаляет его при
   закрытии сеанса;
6. на каждую выгрузку запускает
   `ibcmd infobase config export --config=<config.yaml> <xmlDir>`;
7. проверяет код завершения и записывает безопасный журнал операции.

Оба запуска `ibcmd` принудительно завершаются после 30 минут и возвращают
`session_timeout`. Платформа 8.3.27 предоставляет пароль пользователя базы и
пароль СУБД только параметрами `--password` и `--database-password`, поэтому во
время работы `ibcmd` они могут быть видны локальному пользователю с правом
просмотра аргументов чужих процессов.

`ibsrv` не запускается: он удерживает исключительную блокировку файловой базы и
делает `ibcmd export` невозможным. Закрытие удаляет приватный `config.yaml` и
подготовленный сеанс из кеша без остановки процесса; каждый процесс `ibcmd` уже
завершён к моменту ответа.

## XML-выгрузка

Каталог операции:

```text
.nkdk/
  tmp/
    import-from-infobase/
      <operation-id>/
        xml/
        platform.log
```

Агент выполняет `config dump-config-to-files` без `--server` во внутренний
staging-каталог служебного пользователя, после чего переименовывает результат
в `xml` каталога операции; частичный результат переносится и при ошибке
команды. `ibcmd` выполняет `infobase config export`. Оба режима создают
иерархическую выгрузку. Один проект не выполняет две команды платформы
одновременно.

После успешного экспорта запускается существующий XML → YAML импорт. YAML
пишется напрямую в новый `cf`. Внешние файлы переносятся из `xml` в проект.
Обычный импорт из произвольного XML-каталога продолжает их копировать.

После полного успеха каталог операции удаляется. При любой ошибке после его
создания каталог сохраняется, а путь возвращается в деталях ошибки. Если сбой
произошёл во время переноса внешних файлов, проект может быть частично
заполнен, а сохранённая выгрузка может уже не содержать перенесённые файлы.
Повторный импорт требует очистить `cf`.

## MCP

### `nkdk.import_from_infobase`

Вход:

```ts
type ImportFromInfobaseInput = {
  projectDir: string
  connectionString: string
  user?: string
  password?: string
  database?: {
    dbms: "MSSQLServer" | "PostgreSQL" | "IBMDB2" | "OracleDatabase"
    server: string
    name: string
    user: string
    password?: string
  }
  useStandaloneServer?: boolean
  sessionIdleTimeout?: number
  allowWrite?: boolean
}
```

Без `allowWrite: true` операция возвращает `confirmation_required`, не создаёт
каталоги и не запускает платформу.

Успешный результат содержит:

- число успешно импортированных заданий;
- ошибки отдельных объектов и предупреждения существующего импорта;
- путь к индексу конфигурации;
- путь `.nkdk/project.yaml`;
- использованный режим;
- признак переиспользования соединения.

### `nkdk.close_platform_connection`

Вход:

```ts
{ projectDir: string }
```

Операция закрывает соединение выбранного проекта и возвращает:

```ts
{ closed: boolean; stoppedOwnedProcess: boolean }
```

### `nkdk.close_all_platform_connections`

Операция не принимает параметров, закрывает все соединения текущего
MCP-процесса и возвращает:

```ts
{ closedCount: number; stoppedOwnedProcesses: number }
```

Операции закрытия не требуют `allowWrite`: сам вызов является явным запросом
закрыть соединение. Они не получают права останавливать неподтверждённо чужой
процесс.

## Ошибки

Новые стабильные коды:

| Код | Значение |
|---|---|
| `platform_not_found` | Поддерживаемая платформа 8.3.27 не найдена. |
| `platform_component_missing` | Для режима отсутствует `1cv8` или `ibcmd`. |
| `unsupported_connection` | Вид строки подключения не поддерживается выбранным режимом. |
| `invalid_project_settings` | Настройки проекта имеют неизвестную версию или некорректные поля. |
| `authentication_failed` | Платформа отклонила логин или пароль. |
| `session_start_failed` | Процесс завершился либо SSH-сеанс не открылся. |
| `session_timeout` | Запуск, команда или завершение превысили отведённое время. |
| `platform_command_failed` | Команда платформы вернула ошибку или неожиданный ответ. |

Существующие ошибки непустого компонента и XML → YAML импорта сохраняют свои
коды. Ошибка одного проекта не закрывает соединения других проектов.

## Тестирование

Автоматические тесты мокают функциональные границы:

- файловую систему;
- запуск и завершение процессов;
- SSH-клиент и ответы команд;
- выдачу портов;
- часы и таймеры;
- API `@nkdk/platform` в тестах MCP;
- API `@nkdk/core` в тестах MCP;
- файловые операции `copy` и `move` в тестах `core`.

Тесты не создают временные каталоги, не открывают порты и не запускают 1С.
Чистые построители команд проверяются как обычные функции; оркестраторы
проверяются по вызовам и результатам моков.

Обязательные сценарии:

- запуск агента и команд `ibcmd` на Windows, Linux и macOS;
- файловая и клиент-серверная строки для агента;
- файловая и клиент-серверная строки для `ibcmd`;
- обязательность параметров СУБД для `Srvr`/`Ref` в режиме `ibcmd`;
- отсутствие каждого требуемого приложения;
- готовность, ошибка запуска и тайм-аут агента; ошибки и тайм-ауты инициализации/экспорта `ibcmd`;
- проверка SSH-ключа и запрет управляющих символов в логине и пароле;
- запрос логина и пароля без их появления в диагностике;
- переиспользование и замена соединения;
- последовательность операций одного проекта;
- независимая работа разных проектов;
- закрытие по `sessionIdleTimeout`;
- явное закрытие одного и всех соединений;
- штатное и принудительное завершение агента;
- запрет остановки неподтверждённого процесса;
- проверка и запись настроек;
- `copy` обычного импорта и `move` импорта из базы;
- удаление временной выгрузки при успехе;
- сохранение пути выгрузки при ошибке;
- MCP-схемы и подтверждение `allowWrite`.

## Изменение архитектурного документа

В `.agents/architecture.md` добавляются операции:

- импорт из информационной базы;
- закрытие соединения платформы;
- закрытие всех соединений платформы.

Там же описываются настройки проекта, установка платформы, активный сеанс,
временная XML-выгрузка и результаты новых операций. Действие
передачи внешних файлов обычного XML-импорта уточняется как стратегия
`copy`/`move`.

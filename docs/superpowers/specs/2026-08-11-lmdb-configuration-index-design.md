# Блочный снимок компонента в LMDB

## Контекст

Снимок компонента сейчас хранится в одном `configuration-index.bin`. Любой
потребитель читает и проверяет файл целиком, после чего общий двоичный буфер
передаётся worker'ам. Частичная синхронизация повторно строит полный снимок-
кандидат и после подтверждения целиком перезаписывает опубликованный файл.

На конфигурации `/Users/nikita/git/sed_xml/cf` текущий снимок содержит 22 443
файла и 1 156 330 `entity`, занимает 217 788 512 байт. Эксперимент с
`lmdb@3.5.6` и отдельным двоичным блоком на файл показал:

| Операция | Медиана |
|---|---:|
| Кодирование текущего монолитного снимка | 2 432 мс |
| Прямая запись текущего файла | 57 мс |
| Кодирование блоков всех файлов | 2 037 мс |
| Полная LMDB-транзакция с `overlappingSync` | 194 мс |
| Замена одного блока | 4,9 мс |
| Замена 10 блоков | 4,9 мс |
| Замена 2 244 блоков объёмом 24,6 МБ | 43 мс |

Блоки заняли 229 091 296 байт, а новый LMDB-файл — 264 814 592 байта.
После серии частичных замен файл вырос до 357 957 632 байт. Этот рост принят:
автоматическая компактация в первую реализацию не входит.

Стенд сохранял каждый файл как самостоятельный контейнер прежнего codec.
Поэтому результаты подтверждают стоимость LMDB и верхнюю оценку размера, но не
фиксируют скорость будущего `BlockV1`.

## Цели

- читать сведения снимка только для известных проектных файлов;
- при частичной синхронизации записывать только дельту изменённых и затронутых
  файлов;
- не передавать полный снимок каждому worker'у через `SharedArrayBuffer`;
- сохранить атомарность публикации LMDB-дельты partial sync;
- оставить единственного писателя в координаторе операции;
- использовать штатные ACID- и MVCC-гарантии LMDB без собственного журнала.

## Не входит в решение

- чтение и миграция прежнего `configuration-index.bin`;
- автоматическая компактация или ограничение максимального размера LMDB;
- произвольный поиск `entity` по `logicalAddress` без известного проектного
  файла;
- одновременная подготовка нескольких partial sync одного компонента;
- защита от стороннего изменения LMDB между prepare и finalize;
- смысловая сериализация независимых процессов NKDK поверх отдельных
  LMDB-транзакций;
- возобновление `finalize` после завершения или сбоя подготовившего процесса;
- атомарное изменение LMDB и временного файла `applied-migrations.yaml`;
- ограничения времени benchmark в CI;
- изменение текущего механизма создания новых UUID и XML-id.

После обновления отсутствие нового LMDB-хранилища означает необходимость
повторного import. Старый `.bin` игнорируется.

## Физическое размещение

Каждый компонент владеет отдельным LMDB environment:

```text
.nkdk/components/<componentPath>/
├─ configuration-index.lmdb
└─ configuration-index.lmdb-lock
```

Используется `noSubdir`: первый файл содержит данные, второй — служебные
межпроцессные mutex и таблицу читателей. Lock-файл не является частью снимка,
может быть восстановлен LMDB и не переносится как резервная копия.

На macOS и Linux явно включается `overlappingSync`; на Windows он выключен
согласно рекомендуемому режиму пакета. `noSync`, `noLock`, `useWritemap` и
другие ослабляющие сохранность параметры не используются.
Значения открываются с `encoding: "binary"`; MessagePack-обёртка для готовых
двоичных блоков не применяется.

## Логическая структура LMDB

Корневая база не содержит прикладных записей и используется только каталогом
именованных баз.

| Именованная база | Ключ | Значение |
|---|---|---|
| `meta` | `schemaVersion` | `1` |
| `hashes` | `projectPath` | `contentHash` |
| `blocks` | `projectPath` | `BlockV1` |
| `pendingHashes` | `projectPath` | замена hash-записи либо tombstone |
| `pendingBlocks` | `projectPath` | новый `BlockV1` либо tombstone |

`projectPath` — нормализованная непустая UTF-8-строка без `NUL`. Смысловой
порядок всегда задаётся явной сортировкой UTF-8-байтов и не зависит от порядка
ключей LMDB.

`hashes` содержит все учитываемые проектные файлы. `blocks` содержит только
YAML-файлы, у которых есть идентификаторы или невосстанавливаемый порядок
вынесенных дочерних объектов; пустые блоки для BSL, двоичных и не содержащих
таких сведений YAML-файлов не создаются.

`pendingHashes` содержит только проектные файлы, байты которых добавлены,
изменены или удалены. `pendingBlocks` содержит все повторно построенные блоки,
включая блоки затронутых YAML-файлов с неизменившимся хэшем. Поэтому наборы
ключей двух таблиц независимы и запись `pendingBlocks` не обязана иметь пару в
`pendingHashes`.

Tombstone в `pendingHashes` удаляет активный хэш и соответствует удалённому
проектному файлу. Tombstone в `pendingBlocks` удаляет прежний активный блок,
если после повторной обработки YAML-файла в нём больше нет сохраняемых
сведений. Отсутствие записи в `pendingBlocks` ничего не означает.

Непустая любая из pending-таблиц является признаком ожидающей частичной
синхронизации.

Счётчик поколений и идентификатор ревизии отсутствуют. Пока хотя бы одна
pending-таблица не пуста, другие операции, изменяющие снимок этого компонента,
запрещены.
LMDB сериализует сами транзакции записи, а NKDK сериализует многошаговую
операцию prepare/finalize внутри одного runtime. Одновременные изменяющие
операции независимых процессов не поддерживаются семантически, хотя lock-файл
защищает целостность LMDB.

## Формат `BlockV1`

`BlockV1` — собственное компактное двоичное представление `entity` одного
YAML-файла. Версию его кодирования задаёт `meta.schemaVersion`; отдельного
заголовка, версии, общей длины, пула строк и контрольной суммы внутри блока нет.
`entity` отсортированы по UTF-8-байтам `logicalAddress`.

`sourceProjectPath` задаётся ключом LMDB и не повторяется в каждой `entity`.
При декодировании он восстанавливается из ключа. Внутри блока `logicalAddress`
уникален. Снимок не строит глобальный индекс адресов и не проверяет одинаковый
`logicalAddress` в разных блоках: уникальность между проектными файлами
обеспечивают проверка Проекта и однозначное построение адреса из его структуры.

Логическая структура блока:

```text
entities[]
├─ logicalAddress
├─ uuid?
├─ xmlId?
└─ children[]?
   ├─ xmlName
   └─ name
```

`entity` создаётся только при наличии `uuid`, `xmlId` или непустого
`children`. `children` всегда использует единую последовательность пар
`{ xmlName, name }`: для однотипных дочерних объектов `xmlName` повторяется.

Каждый `uuid` и `xmlId`, использованный при экспорте, записывается в новый блок:
как импортированный из XML, так и созданный для нового элемента. Повторное
вычисление уже использованного идентификатора не допускается; `operationSeed`
в снимке не хранится. При переименовании через migration чтение выполняется по
прежнему `logicalAddress`, а идентификатор записывается под новым. Ручное
переименование без migration считается удалением прежнего и созданием нового
элемента с новым идентификатором.

В снимке допускаются только следующие списки:

| Список XML | Где находится | Порядок без снимка |
|---|---|---|
| Корневые объекты конфигурации (`Language`, `Subsystem`, …, `Catalog`, `Document`, …) | `Configuration/ChildObjects` | Виды идут в `STANDARD_CHILD_OBJECT_TYPE_ORDER`, имена внутри каждого вида сортируются через `localeCompare(..., "ru")` |
| Формы (`Form`) | `ChildObjects` прикладного объекта, таблицы, таблицы измерений или куба внешнего источника данных | Имена сортируются сравнением UTF-8-байтов |
| Макеты (`Template`) | `ChildObjects` прикладного объекта, таблицы, таблицы измерений или куба внешнего источника данных | Имена сортируются сравнением UTF-8-байтов |
| Таблицы внешнего источника данных (`Table`) | `ChildObjects` внешнего источника данных | Имена сортируются сравнением UTF-8-байтов |
| Кубы внешнего источника данных (`Cube`) | `ChildObjects` внешнего источника данных | Имена сортируются сравнением UTF-8-байтов |
| Таблицы измерений (`DimensionTable`) | `ChildObjects` куба внешнего источника данных | Имена сортируются сравнением UTF-8-байтов |

Этот порядок называется восстанавливаемым: именно его экспорт строит из
проекта без снимка. `children` отсутствует, если исходный список уже имеет
восстанавливаемый порядок. Если порядок отличается, для соответствующего
`xmlName` сохраняется полный список имён, а не только перестановленные элементы.
Несколько отличающихся списков одного владельца объединяются в одном
`children`; порядок разных `xmlName` внутри такой записи значения не имеет.

Для `Configuration/ChildObjects` стандартный порядок самих XML-видов не
сохраняется. Если исходный XML нарушает и его, `children` содержит полную плоскую
последовательность всех корневых объектов; это однозначно определяется тем, что
в записи присутствует весь актуальный состав корня. В исследованных 27
конфигурациях этот запасной случай не встретился.

При объединении с актуальным составом сохранившиеся дочерние объекты оставляют
взаимный порядок из блока, удалённые исключаются, а новые добавляются в конец в
восстанавливаемом порядке. После объединения список снова сравнивается с
восстанавливаемым: совпавший список из нового блока исключается. Переименование
считается удалением прежнего и добавлением нового объекта: migrations не
переносят его позицию, поэтому новое имя попадает в конец вместе с другими
новыми объектами.

Если `children` для списка отсутствует, экспорт строит весь список в
восстанавливаемом порядке: новый элемент сразу занимает место согласно
сортировке. Поэтому добавление элемента не превращает восстанавливаемый список
в сохраняемый.
Вложенной структуры `identities`, универсальных `facts` и сведений об
XML-представлении в `BlockV1` нет. Состояние расширений также не входит в новый
формат и удаляется из снимка отдельным изменением до перехода на LMDB.

Hash-запись имеет фиксированный двоичный размер: восьмибайтовый `contentHash`.
Это XXH3-64 от точных байтов проектного файла — тот же хэш, который хранится в
YAML-индексе проекта. Читатель проверяет `meta.schemaVersion`, границы каждого
поля, корректность UTF-8 и полное потребление значения LMDB.

## Граница модулей

Пакет `@nkdk/runtime` владеет зависимостью `lmdb`, двоичным codec и реализацией
`ConfigurationIndexStore`. Типы LMDB не экспортируются в metadata-правила.

Интерфейс хранилища предоставляет операции уровня предметного договора:

- открыть короткую read-сессию и прочитать meta;
- получить hash-записи или перечислить их без чтения блоков;
- загрузить несколько проверенных блоков по `projectPath`;
- создать и наполнить временное хранилище;
- сохранить, применить или принудительно очистить pending-дельту;
- атомарно заменить активное содержимое полным кандидатом.

Запись выполняет только координатор import/sync. Worker'ы открывают environment
только для чтения. Read-транзакция ограничена заданием или небольшой пачкой и
всегда завершается, чтобы не мешать повторному использованию освобождённых
страниц.

Координатор заранее кодирует значения и использует явную короткую транзакцию.
Внутри callback нет чтения файлов, XML-разбора, ожиданий или иной асинхронной
работы. Автоматический batching отдельных `put` не является частью договора:
эксперимент не показал у него преимущества, а явная транзакция непосредственно
выражает атомарную группу изменений. Успех операции возвращается только после
`flushed`.

## Reader для XML-экспорта

Вместо полного `SharedConfigurationIndexSnapshot` worker получает:

- абсолютный путь LMDB;
- ожидаемую `schemaVersion`;
- список `projectPath`, необходимых заданию.

Планировщик заранее добавляет основной файл задания, файлы владельцев, базовую
форму и другие явно известные источники. Worker вызывает `getMany` или
предварительную выборку, проверяет блоки и строит локальный
`ConfigurationIndexReader` только над ними. После задания reader освобождается.

Отсутствующая запись `blocks` и запрос отсутствующего адреса возвращают
`undefined` по прежнему предметному договору. Это не вызывает запасного чтения
всех блоков: полнота заранее вычисленного набора проектных путей проверяется
интеграционными тестами планировщика.

Для расширения основной компонент открывается отдельной read-сессией. В worker
передаются только ключи базы, реально используемые конкретным заданием.

## Версия конфигурации

`configVersion` должен меняться между операциями, поэтому использует
случайный `operationSeed`, создаваемый координатором full/partial sync и общий
для всех его worker'ов. Для partial sync готовые XML и блоки сохраняются в
pending, поэтому finalize ничего не генерирует повторно.

## Import XML → YAML

Import создаёт LMDB во временном каталоге `.nkdk/tmp`. Результаты worker'ов
группируются по `targetProjectPath`, кодируются и последовательно записываются
координатором. При повторном вкладе того же файла координатор читает только его
текущий временный блок и объединяет сведения.

Координатор не удерживает полный список `entity` и не строит отображение
`logicalAddress → sourceProjectPath`. Повтор адреса внутри одного блока является
ошибкой codec, а непротиворечивость разных проектных файлов гарантирует
предварительная проверка Проекта. Готовые блоки сразу передаются LMDB.
Hash-записи добавляются после вычисления хэшей фактически записанных YAML и
внешних файлов.

Перед публикацией проверяется, что каждый ключ `blocks` существует в `hashes`,
завершается `meta` и выполняется flush. После успешной проверки зависимостей временный environment
закрывается. NKDK закрывает все собственные сеансы активного environment,
удаляет его восстанавливаемый lock-файл и атомарно заменяет data-файл
проверенным временным data-файлом. Временный lock-файл удаляется, а новый
активный lock-файл LMDB создаёт при следующем открытии. При ошибке до замены
временные файлы удаляются и прежний снимок остаётся опубликованным.

Одновременная работа другого процесса с environment этого компонента во время
import не поддерживается. Import не пытается обнаружить или закрыть чужие
сеансы; ответственность за их отсутствие лежит на вызывающей стороне.

## Полная синхронизация YAML → XML

Worker'ы читают только блоки своих заданий и потоково возвращают новые блоки
координатору. Координатор строит полное временное LMDB-хранилище параллельно с
записью XML.

После успешной записи и проверки XML одна транзакция активного environment:

1. проверяет, что обе pending-таблицы пусты;
2. очищает активные `hashes` и `blocks`;
3. копирует hash-записи и блоки из временного кандидата.

Существующие читатели благодаря MVCC завершают работу со старым состоянием, а
новые видят полностью заменённое. Временный environment затем удаляется.

## Подготовка partial sync

Prepare выполняет следующие шаги:

1. Актуализирует и проверяет проект.
2. Проверяет, что обе pending-таблицы пусты.
3. Сравнивает текущие хэши проекта только с `hashes`, не читая `blocks`.
4. Строит план влияния и точный набор source keys для worker'ов.
5. Worker'ы читают нужные активные блоки, формируют XML и полные новые блоки
   обработанных файлов.
6. Координатор потоково записывает ZIP и проверяет его состав и хэш.
7. Если есть неприменённая migration, но файловая дельта пуста, подготовка
   завершается ошибкой.
8. Одна LMDB-транзакция записывает `pendingHashes` и `pendingBlocks`, повторно
   проверив, что обе pending-таблицы пусты.

Изменённый или затронутый YAML-файл с сохраняемыми сведениями получает полный
новый блок. Если сведений больше нет, `pendingBlocks` получает tombstone.
Удалённый проектный файл получает tombstone в `pendingHashes` и при наличии
старого блока — в `pendingBlocks`. Неизменённые активные записи не копируются.
После prepare обычные читатели продолжают видеть только `hashes` и `blocks`.

Добавление, удаление или переименование вынесенного дочернего объекта всегда
добавляет в план XML его владельца и повторное построение блока владельца:
объект верхнего уровня затрагивает `Configuration.xml`, форма или макет —
основной XML прикладного объекта, таблица измерений — XML куба внешнего
источника данных. Если YAML владельца побайтно не изменился, его ключ появляется
в `pendingBlocks`, но отсутствует в `pendingHashes`.

Если подготовка завершилась до записи pending-таблиц, её незавершённый ZIP и
временные данные удаляются. После успешной подготовки пакет сохраняется до
finalize или явной принудительной очистки. Новая изменяющая операция при
непустой pending-таблице сообщает о незавершённой синхронизации и требует
явной принудительной очистки.

## Finalize partial sync

После подтверждения успешной загрузки ZIP в 1С finalize:

1. проверяет, что хотя бы одна pending-таблица не пуста;
2. проверяет переданный координатором путь и хэш ZIP;
3. одной транзакцией применяет `pendingHashes` и `pendingBlocks` к
   активным таблицам, но оставляет pending-таблицы без изменений;
4. повторно вычисляет состояние migrations по неизменяемому до завершения
   Проекту и публикует `applied-migrations.yaml`;
5. короткой LMDB-транзакцией очищает `pendingHashes` и `pendingBlocks`;
6. удаляет ZIP.

`finalize` является продолжением только текущей подготовившей операции. Путь и
хэш ZIP не сохраняются в LMDB, а возобновление `finalize` после завершения или
сбоя процесса не поддерживается. Обнаруженная следующей операцией pending-
дельта не применяется автоматически: пользователь должен явно принудительно
очистить обе pending-таблицы.

`applied-migrations.yaml` временно остаётся отдельным файлом. Его публикация не
атомарна с LMDB: сбой между применением дельты, записью файла и очисткой pending
может оставить эти состояния несогласованными. Pending блокирует последующие
изменяющие операции, но принудительная очистка не исправляет состояние
миграций и выполняется пользователем осознанно. Постоянное решение этого
договора не входит в текущую спецификацию.

Защиты от изменения файлов в обход `ConfigurationIndexStore` нет. Import, full
sync и новая partial prepare отказываются работать, пока хотя бы одна pending-
таблица не пуста. Явная принудительная очистка очищает обе pending-таблицы; она
не пытается откатить уже начатый `finalize` или согласовать
`applied-migrations.yaml`.

## Ошибки и восстановление

- Отсутствующая LMDB или неизвестная `schemaVersion` требуют повторного import.
- Некорректная структура `BlockV1`, некорректный UTF-8 или непрочитанное до
  конца значение немедленно прекращают операцию; автоматического экспорта без
  повреждённого блока нет.
- Отсутствие отдельной записи `blocks` допустимо. Если новый элемент требует
  идентификатор, которого ещё нет, экспорт создаёт его и записывает в новый
  блок.
- Исключение внутри LMDB-транзакции не оставляет частично опубликованных
  активных изменений.
- Ошибка публикации migrations или очистки pending оставляет незавершённое
  состояние, которое следующая операция разрешает только принудительной
  очисткой. Ошибка удаления ZIP после очистки не влияет на снимок.
- Ошибка закрытия read-сессии присоединяется к ошибке операции по принятому
  договору cleanup, но не маскирует первичную причину.
- Рост data-файла является допустимым high-water mark. Для уменьшения размера
  пользователь повторяет import; автоматическая компактация отсутствует.

Native-модуль должен загружаться из упакованного MCP. Ошибка загрузки или
открытия environment возвращается с контекстом пути. Специального обхода
ограничений mmap в песочницах не добавляется.

## Проверки

### Codec

- детерминированное кодирование независимо от порядка входных `entity`;
- максимальные допустимые значения блока;
- оборванное значение, лишние байты и некорректный Unicode;
- отсутствие повторных `logicalAddress` внутри блока;
- сохранение импортированных и созданных `uuid` и `xmlId`;
- отсутствие `children` для восстанавливаемых списков;
- точное сохранение нестандартного порядка корневых объектов, форм, макетов и
  таблиц измерений;
- добавление нового элемента по сортировке в восстанавливаемый список и в конец
  сохранённого списка;
- удаление `children`, когда полученный список стал восстанавливаемым.

### Store

- точечное чтение одного и нескольких ключей не перечисляет остальные блоки;
- перечисление `hashes` не читает значения `blocks`;
- отсутствие блока у файла без сохраняемых сведений;
- повторный import закрывает собственные сеансы и физически заменяет data-файл;
- атомарная полная замена;
- replace и tombstone partial-дельты;
- старый MVCC-читатель видит прежнее состояние до закрытия;
- независимые наборы ключей `pendingHashes` и `pendingBlocks`;
- tombstone блока при исчезновении последних сохраняемых сведений;
- запрет второй изменяющей операции при непустой любой pending-таблице;
- требование принудительной очистки после обнаружения pending новым процессом;
- ошибка при неприменённой migration без файловой дельты;
- правильное создание data- и lock-файлов.

### Операции

- import создаёт только LMDB-снимок и не удерживает полный снимок в памяти;
- старый `.bin` не читается и не мигрируется;
- full sync читает необходимые блоки и публикует полный кандидат;
- partial prepare не меняет активные hash/block-записи;
- finalize меняет только ключи дельты;
- добавление, удаление и переименование дочернего объекта перестраивает XML и
  блок его владельца, но не создаёт `pendingHashes` для неизменившегося YAML
  владельца;
- migration переносит `uuid` и `xmlId`, но не позицию переименованного объекта;
- ручное переименование создаёт новые идентификаторы;
- расширение получает точные блоки своего и базового компонентов;
- сгенерированный partial XML побайтно совпадает с полной sync того же
  состояния проекта.

### Поставка и производительность

- packed-smoke MCP открывает LMDB, записывает и читает двоичный блок;
- CI проверяет поддерживаемые платформенные native-пакеты;
- ручной benchmark измеряет import-кандидат и partial-транзакции на реальной
  конфигурации;
- ограничения времени и размера файла в автоматические тесты не входят.

## Последствия

Переход является несовместимым изменением внутреннего формата `.nkdk`.
Пользователь повторяет import; мигратора нет. После реализации удаляются codec,
shared snapshot и candidate-файл старого монолитного формата, а worker-
контракты переходят с полного буфера на LMDB descriptor и список source keys.

Цена решения — native-зависимость, служебный lock-файл, больший начальный
размер и сохранение high-water mark. Взамен partial sync читает и изменяет
только нужные файлы, coordinator и worker'ы не материализуют полный снимок, а
публикация дельты получает штатную ACID/MVCC-семантику LMDB.

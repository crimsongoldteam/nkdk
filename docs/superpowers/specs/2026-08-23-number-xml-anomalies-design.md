# XML-аномалии common-типа `number`

## Статус документа

Это третий пилот исследования XML-аномалий common-типов. Он проверяет на
`number` методику, ранее рассмотренную для `boolean` и `string`, но не
утверждает общий механизм для всех типов.

Реализация и новое применение `!xml` этим документом не согласовываются.

Результат обобщения зафиксирован в
[общей спецификации common-типов](2026-08-23-common-types-xml-anomaly-framework-design.md).
Этот документ остаётся подробной тестовой матрицей числового скаляра.

Нормативные решения общей спецификации имеют приоритет: целевой YAML использует
`!xml/raw` со значением текущего XML-парсера, если обычное представление или
round-trip невозможны; `!xml/invalid` с обычным YAML-значением для обратимой
смысловой аномалии; `!xml/important` только для явно согласованного класса
ценных данных. Вручную написанный ошибочный YAML без этих
тегов продолжает получать блокирующую ошибку. Разделы ниже о форме raw и
прежнем разделении validation сохраняют историю пилота.

## Граница исследования

Документ рассматривает только common-тип `number`, представленный в модели и
YAML как JavaScript `number`.

В границу не входят:

- `MinMaxValue`;
- `StringOrNumber`;
- числовые квалификаторы `TypeDescription`;
- числа внутри составных common-типов;
- предметные ограничения, не выраженные в `NumberPropertyRule`.

В найденных правилах `number` хранится в XML-элементе. В отличие от `string`,
для него не обнаружены прямые XML-атрибуты, `metadataTarget` или
`externalFile`. Поэтому пилот проверяет именно element-backed свойство.

## Фактический текущий договор

Код common-типа находится в
`packages/rules/metadata/commonObjects/number`.

### XML-парсер

Общий XML-парсер сохраняет числоподобный текст строкой. Например, `2.0`
поступает в common-преобразователь именно как `"2.0"`, а не как число `2`.
Следовательно, исходная запись ещё доступна в XML-месте и может участвовать в
проверке обратимости.

### XML → внутреннее значение

`importNumberFromXML` работает так:

1. `undefined` преобразуется в `undefined`;
2. для объекта с известным `xsi:type` из набора `xs:decimal`, `xs:integer`,
   `xs:double`, `xs:float` берётся `#text`;
3. в остальных случаях берётся `#text`, если он есть, иначе исходный объект
   или массив целиком;
4. `undefined` и пустой текст преобразуются в `undefined`;
5. готовое число возвращается как есть, остальные значения преобразуются через
   JavaScript `Number(...)`.

Преобразователь не проверяет:

- `NaN` и бесконечность;
- потерю точности;
- безопасный диапазон целых чисел;
- `minimum`, `maximum` и `maximumWhen`;
- соответствие текста объявленному `xsi:type`.

Поэтому неизвестный текст, обычный объект без `#text` и массив обычно становятся
`NaN`, а не `undefined`. Объект известного числового `xsi:type` без текста
становится `undefined`. Дополнительные атрибуты и дочерние элементы рядом с
`#text` не попадают во внутреннее число.

### Внутреннее значение ↔ YAML

Обычные конечные числа записываются стандартным YAML-числом. YAML runtime также
умеет технически перенести `-0`, `NaN` и бесконечности, но JSON Schema
`number` отвергает `NaN` и обе бесконечности.

Например:

```yaml
Длина: 10
Коэффициент: 1.5
```

### Внутреннее значение → XML

Без `typedXML` common-тип возвращает обычное число. При `typedXML` он создаёт
объект с `xsi:type` и текстом `String(value)`:

```xml
<MinValue xsi:type="xs:decimal">1</MinValue>
```

`typedXML: true` означает `xs:decimal`; также правило может явно требовать
`xs:decimal` или `xs:string`.

## Новая особенность числа: потеря записи

Для `boolean` главным неизвестным было значение, а для `string` — дополнительная
XML-структура. У `number` смысловое число может быть понятно, но исходная запись
теряется при `Number(...)` и последующем `String(value)`.

Фактические примеры текущего преобразования:

| Исходный текст | Внутреннее значение | Повторный XML-текст |
|---|---:|---|
| `1` | `1` | `1` |
| `-0` | `-0` | `0` |
| `+1` | `1` | `1` |
| `01` | `1` | `1` |
| `1.0` | `1` | `1` |
| `1e3` | `1000` | `1000` |
| ` 1 ` | `1` | `1` |
| один пробел | `0` | `0` |
| `1,5` | `NaN` | `NaN` |
| `abc` | `NaN` | `NaN` |
| `INF` | `NaN` | `NaN` |
| `9007199254740993` | `9007199254740992` | `9007199254740992` |
| `0.10000000000000000001` | `0.1` | `0.1` |

Это не требует отдельных классов аномалий. Во всех строках, где повторный
XML-текст отличается, обычный round-trip не восстановил XML-место.

## Инвариант пилота

Для известного XML-места числового свойства выполняется обычный
XML → YAML → XML без reference XML. Затем исходное и полученное XML-места
сравниваются структурно, включая текст элемента.

- Если место восстановлено, в YAML остаётся обычное число.
- Если изменились текст, атрибуты, дочерние узлы, количество или присутствие,
  исходное XML-место сохраняется исключительным переносчиком.

Числовая эквивалентность сама по себе недостаточна: `01` и `1` обозначают одно
число, но это разный XML-текст. Иначе механизм перестанет обеспечивать точный
XML round-trip.

Проверка без reference XML доказывает переносимость YAML. Общая спецификация
отдельно рассматривает режим синхронизации со сведениями индекса и снимка;
этот пилот таких сведений для element-backed `number` не обнаружил.

## Матрица числового XML-элемента

В таблице `Value` — XML-имя, уже сопоставленное конкретному `numberRule`.

| Случай | Пример XML | Обычный результат | Решение по методике |
|---|---|---|---|
| Каноническое целое | `<Value>10</Value>` | YAML `10`, XML `10` | Оставить числом |
| Каноничная дробь | `<Value>1.5</Value>` | YAML `1.5`, XML `1.5` | Оставить числом |
| Ведущий ноль | `<Value>01</Value>` | XML становится `1` | Сохранить исходный элемент |
| Явный плюс | `<Value>+1</Value>` | XML становится `1` | Сохранить исходный элемент |
| Нулевая дробная часть | `<Value>1.0</Value>` | XML становится `1` | Сохранить исходный элемент |
| Экспоненциальная запись | `<Value>1e3</Value>` | XML становится `1000` | Сохранить исходный элемент |
| Отрицательный ноль | `<Value>-0</Value>` | XML становится `0` | Сохранить исходный элемент |
| Пробелы | `<Value> 1 </Value>` | XML становится `1` | Сохранить исходный элемент |
| Пустой элемент | `<Value/>` | значение исчезает | Учитывать default и присутствие правила |
| Только пробел | `<Value> </Value>` | значение становится `0` | Сохранить исходный элемент |
| Нечисловой текст | `<Value>abc</Value>` | значение и XML становятся `NaN` | Сохранить исходный элемент |
| Запятая вместо точки | `<Value>1,5</Value>` | значение и XML становятся `NaN` | Сохранить исходный элемент |
| Потеря точности целого | `<Value>9007199254740993</Value>` | XML получает другое число | Сохранить исходный элемент |

| Бесконечность JavaScript | `<Value>Infinity</Value>` | XML снова `Infinity`, схема не пропускает | Оставить переносимым числом, показать ошибку проверки |
| XSD-бесконечность | `<Value>INF</Value>` | XML становится `NaN` | Сохранить исходный элемент |
| Значение вне диапазона | `<Value>51</Value>` при `maximum: 50` | XML снова `51`, схема не пропускает | Оставить числом, показать ошибку проверки |
| Известный `xsi:type` по договору | `<Value xsi:type="xs:decimal">1</Value>` при `typedXML: true` | форма восстанавливается | Оставить числом |
| Другой допустимый `xsi:type` | `<Value xsi:type="xs:integer">1</Value>` при `typedXML: true` | тип становится `xs:decimal` | Сохранить исходный элемент |
| Лишний `xsi:type` | `<Value xsi:type="xs:decimal">1</Value>` без `typedXML` | атрибут исчезает | Сохранить исходный элемент |
| Недостающий `xsi:type` | `<Value>1</Value>` при `typedXML: true` | атрибут появляется | Сохранить отсутствие атрибута вместе с элементом |
| Произвольный атрибут | `<Value custom="x">1</Value>` | атрибут исчезает | Сохранить исходный элемент |
| Дочерний элемент | `<Value><Raw>1</Raw></Value>` | получается `NaN` | Сохранить исходный элемент |
| Смешанное содержимое | `<Value>1<Raw>2</Raw></Value>` | дочерний узел исчезает | Сохранить исходный элемент |
| Повтор свойства | `<Value>1</Value><Value>2</Value>` | массив превращается в `NaN` | Сохранить оба соседних элемента |
| Элемент отсутствует | нет `<Value>`, но правило создаёт default | при экспорте появляется элемент | Сохранить отсутствие |

Матрица является набором проверок одного инварианта, а не перечнем кодов
диагностики.

## Прежнее разделение структурной аномалии и ошибки проверки

Для `number` особенно важно не смешивать два случая.

### XML не восстанавливается

Пример: `<CodeLength>001</CodeLength>` становится
`<CodeLength>1</CodeLength>`. Для обратного экспорта требуется raw-переносчик,
даже если число `1` допустимо по схеме.

### XML восстанавливается, но число недопустимо

Пример: `<CodeLength>60</CodeLength>` при `maximum: 50` снова экспортируется как
`60`. Raw-переносчик не нужен: значение понятно и не теряется. Обычная проверка
должна сообщить о нарушении диапазона.

То же относится к `minimum`, `maximumWhen`, `NaN` и бесконечностям, если их
XML-текст и `xsi:type` действительно восстанавливаются. Ошибка проверки не
должна автоматически превращаться в `xml/raw`.

## Рабочее YAML-представление, заменённое общей спецификацией

Для необратимого element-backed числа сохраняется полный XML-фрагмент:

```yaml
ДлинаКода: !xml/raw |-
  <CodeLength>001</CodeLength>
```

### Почему payload содержит внешний XML-элемент

Для одной только записи `001` внешний `<CodeLength>` избыточен: PropertyRule
уже знает каноническое XML-имя, поэтому технически было бы достаточно:

```yaml
ДлинаКода: !xml/raw "001"
```

Однако такой сокращённый договор сохраняет только текст. Он не позволяет тем
же способом перенести исходный `xmlAlias`, `xsi:type`, произвольный атрибут,
дочерний узел, повтор элемента или его отсутствие. Если разрешить обоим
вариантам иметь один scalar-payload, экспортёр должен будет угадывать, является
ли строка текстом элемента или готовым XML-фрагментом.

Поэтому в пилоте выбран один однозначный договор: `!xml/raw` всегда содержит
полное известное XML-место. Избыточность внешнего элемента в простом числовом
случае принимается ради единого формата всех структурных аномалий. Сокращённая
форма `!xml/raw "001"` в договор не входит.

Для изменившегося типа:

```yaml
Значение: !xml/raw |-
  <Value xsi:type="xs:integer">1</Value>
```

Переносчик не передаётся в обычное числовое преобразование, не проверяется как
число и при экспорте заменяет обычный вывод свойства. Для него используется тот
же код диагностики `xml/raw` с указанием common-типа `number`, PropertyRule и
отпечатка фрагмента.

Новый `!xml/raw` остаётся гипотезой и требует отдельного явного согласования
перед реализацией для `number`.

## Варианты обращения с числовой записью

### (А) Сравнивать точный XML-текст — рекомендуется

Любая запись, которую JavaScript `number` не восстанавливает, получает raw-
фрагмент. Это сохраняет единый инвариант `boolean`, `string` и `number`.

Плюс: точный XML round-trip и автоматическое обнаружение потери точности.
Минус: допустимые, но неканоничные записи вроде `1.0` займут raw-ветку.

### (Б) Считать численно эквивалентные записи одинаковыми

`01`, `1.0` и `1e0` считались бы обычным числом `1`.

Плюс: меньше raw-значений. Минус: механизм сознательно меняет исходный XML и
перестаёт отвечать поставленной задаче round-trip.

### (В) Ввести точный десятичный тип в обычный YAML

Отдельная модель хранила бы числовое значение и исходную запись без raw XML.

Плюс: число оставалось бы доступным предметным проверкам. Минус: это изменение
модели, YAML-контракта и вычислений ради редких неканоничных форм; после одного
числового типа такое усложнение преждевременно.

## Что число подтвердило в общей методике

1. Верхний класс остаётся один: известное XML-место не восстановилось обычным
   round-trip.
2. Причины — неизвестное значение, дополнительная структура, изменение
   числовой записи или потеря точности — не требуют разных YAML-тегов и кодов.
3. Сравнение должно происходить после полного обычного преобразования с
   конкретным PropertyRule, включая `typedXML` и default.
4. Исходное XML-место нужно удерживать до окончания проверки обратимости:
   внутреннего JavaScript `number` уже недостаточно для восстановления `01`
   или большого десятичного значения.
5. Предметная проверка и сохранение XML остаются независимыми: значение может
   быть невалидным, но полностью обратимым.

## Проверки пилота

### Модульные факты `number`

- канонические целые и дроби преобразуются как сейчас;
- `01`, `1.0`, `1e3`, `-0`, пробелы и длинные десятичные записи показывают
  фактическую нормализацию;
- неизвестный текст, объект без `#text` и массив показывают появление `NaN`;
- дополнительные поля объекта не попадают в результат;
- все поддерживаемые входные `xsi:type` проверяются отдельно.

### YAML runtime и проверка

- обычные конечные числа проходят YAML round-trip;
- `-0`, `NaN` и бесконечности не меняются при YAML round-trip;
- JSON Schema отвергает `NaN`, бесконечности и значения вне границ;
- нарушение границы не создаёт raw-фрагмент при точном XML round-trip.

### Round-trip числового элемента

Каждая строка матрицы закрепляется программным тестом без изменения эталонных
XML-фикстур:

- обратимые формы остаются обычным числом;
- необратимые формы получают полный XML-фрагмент;
- итоговое XML-место структурно равно исходному;
- `typedXML`, default и явное присутствие учитываются конкретным правилом;
- соседнее свойство не попадает в raw-фрагмент;
- потеря точности обнаруживается сравнением, а не порогом, зашитым в
  `numberRule`.

## Вывод после трёх common-типов

На `boolean`, `string` и `number` сохраняется одна классификация транспортных
XML-аномалий:

> обычный round-trip известного XML-места изменил или потерял его.

Различаются только входные примеры. Для анализа достаточно common-типа,
PropertyRule, XML-пути и отпечатка raw-фрагмента; отдельные коды «неизвестное
число», «точность», «атрибут» или «дубль» не нужны.

Полный raw-фрагмент по-прежнему доказан только для element-backed свойств.
Следующий составной тип или список должен проверить границу XML-места, а не
добавить новую классификацию причин.

## Объём дальнейшего исследования

На момент написания документа в `packages/rules/metadata/commonObjects`
зарегистрировано 92 уникальных PropertyRule-типа. Число получено по
`definePropertyTypeRule` в рабочих исходниках без тестов и фикстур, а не по
количеству каталогов.

Исследованы `boolean`, `string` и `number`; остаётся 89 common-типов.
`SystemEnumeration` находится в отдельном слое
`packages/rules/metadata/systemEnumerations` и в этот подсчёт не входит.

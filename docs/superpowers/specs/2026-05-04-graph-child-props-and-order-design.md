# Дизайн: дочерние коллекции в графе без дублирования props

Тип: дизайн-документ.

## Контекст

`buildGraphFromModel` строит граф по `rules.ts`: простые свойства остаются в модели узла, `TypeDescription` и другие ссылочные значения создают рёбра, а коллекции с `graphChild` или специальным `buildGraphFromModel` создают дочерние узлы.

После построения `walkGraphToFileData` вызывает `flattenItem(item)` и превращает остаток модели в свойства узла `p_*`. Сейчас `flattenItem` не знает правил и пытается распознать дочерние коллекции по форме объекта и кириллице в ключах. Это ломается на одиночных коллекциях с латинским именем элемента, например `attributes: { Total: "Строка" }`.

## Решение

Источник истины для того, что является дочерней коллекцией, — правила и регистрации типов, а не эвристика по ключам.

При обходе правила для узла нужно собрать список ключей модели, которые уже материализуются графом:

- свойство с типом, у которого зарегистрирован `graphChild`;
- свойство с типом, у которого зарегистрирован `buildGraphFromModel`.

Эти ключи передаются в слой выгрузки узла как `skipKeys` для `flattenItem`. `flattenItem` остаётся техническим преобразователем `item -> p_*` и больше не угадывает дочерние коллекции по кириллице, количеству ключей или форме значений.

## Порядок

Все дочерние коллекции считаются упорядоченными для целей будущего восстановления `граф -> модель`, включая YAML record-коллекции:

- реквизиты;
- табличные части;
- стандартные реквизиты;
- измерения последовательностей;
- реквизиты, параметры и команды формы;
- коллекции, выгружаемые через специальные `buildGraphFromModel`, например `StandardAttributeDescriptions` и колонки реквизитов формы.

Record-форма YAML не означает, что порядок незначим. Порядок элементов берётся из исходной модели/YAML и должен сохраняться явно.

Для owning-рёбер дочерних коллекций добавляется атрибут `index`. Будущий слой `граф -> модель` должен восстанавливать коллекции по owning-рёбрам, сортируя по `index`, а не полагаясь на порядок ответа FalkorDB.

## Границы

Этот дизайн не реализует восстановление `граф -> модель`. Он фиксирует контракт, который нужен для такой реализации:

- свойства, вынесенные в дочерние узлы, не дублируются в `p_*` родителя;
- порядок дочерних коллекций сохраняется на рёбрах;
- простые и композитные значения, которые не материализуются отдельными узлами/рёбрами, продолжают выгружаться через `flattenItem`.

`TypeDescription` остаётся смешанным случаем: его простая структура может быть сохранена в `p_*`, а ссылки из него дополнительно представлены рёбрами.

## Проверка

Нужны тесты на два свойства контракта:

1. `attributes: { Total: "Строка" }` и `attributes: { Total: { ... } }` не создают `p_attributes_*` на родительском узле.
2. Дочерние коллекции получают `index` на owning-рёбрах в порядке исходной коллекции, включая record-коллекции и `StandardAttributeDescriptions`.

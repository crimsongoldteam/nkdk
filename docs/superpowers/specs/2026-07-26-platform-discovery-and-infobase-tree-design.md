# Поиск платформы 1С и дерево информационных баз

## Цель

Добавить отдельный пакет `@nkdk/platform` для двух независимых задач:

- внутренний для NKDK поиск установленной платформы 1С ветки `8.3.27`;
- получение дерева информационных баз из личного и общих списков 1С.

Поиск платформы нужен будущим операциям импорта и синхронизации, но пока не
публикуется через MCP. Дерево баз публикуется как read-only MCP-инструмент.

Первый выпуск поддерживает Windows, Linux и macOS.

## Границы

Входит в первый выпуск:

- новый workspace-пакет `packages/platform`;
- поиск самой новой установленной сборки `8.3.27.*`;
- независимое определение путей к `1cv8` и `ibcmd`;
- чтение личного `ibases.v8i`;
- чтение локальных конфигураций запуска и подключённых общих списков из
  `CommonInfoBases`;
- восстановление дерева папок и баз;
- публичный MCP-инструмент для получения дерева;
- частичный результат с диагностикой недоступных или повреждённых источников.

Не входит:

- поддержка веток платформы, отличных от `8.3.27`;
- явный путь к платформе от вызывающей стороны;
- запуск `ibcmd`, `rac` или других программ для проверки версии;
- чтение PE, ELF или Mach-O;
- поиск через `PATH`;
- рекурсивное сканирование файловой системы;
- кеширование;
- `WebCommonInfoBases` и любые сетевые запросы по HTTP;
- запись `.v8i` или конфигурационных файлов;
- операции импорта и синхронизации с базой;
- публикация поиска платформы через MCP.

## Архитектура пакета

`@nkdk/platform` не зависит от `@nkdk/core` или `@nkdk/mcp`. В нём находятся
два независимых прикладных модуля:

```text
@nkdk/platform
  platform discovery
  infobase discovery and parsing
  Node.js environment adapters
```

Пакет экспортирует функции для использования другими workspace-пакетами:

```ts
type PlatformInstallation = {
  version: `8.3.27.${number}`
  directory: string
  enterprisePath?: string
  ibcmdPath?: string
}

function findPlatform(): Promise<PlatformInstallation | undefined>

type InfobaseTreeResult = {
  tree: InfobaseTreeNode[]
  sources: InfobaseSource[]
  warnings: InfobaseWarning[]
}

function listInfobases(): Promise<InfobaseTreeResult>
```

Названия конкретных файлов внутри пакета определяются планом реализации.
Публичный пакетный API должен быть собран в одном entrypoint. Поиск платформы
является публичным только на уровне TypeScript-пакета для других частей NKDK и
не регистрируется как пользовательский MCP-инструмент.

## Договор файловой системы и окружения

Логика не обращается к `node:fs`, `process.platform`, `process.arch` и
`process.env` напрямую. Между прикладными модулями и Node.js находится
небольшой внутренний договор:

```ts
type FileSystem = {
  readFile(path: string): Promise<string>
  readdir(path: string): Promise<string[]>
  stat(path: string): Promise<{
    isFile: boolean
    isDirectory: boolean
    mode: number
  }>
  realpath(path: string): Promise<string>
}

type PlatformEnvironment = {
  os: "win32" | "linux" | "darwin"
  arch: "x86" | "x64" | "arm64" | "unknown"
  env: Readonly<Record<string, string | undefined>>
}
```

Рабочие переходники используют Node.js. Модельные переходники в тестах
полностью задают файловое дерево, ошибки, ОС, архитектуру и переменные среды.
Договор остаётся внутренним и не экспортируется потребителям пакета.

`FileSystem` описывает только операции, действительно нужные реализации.

## Поиск платформы

### Источники каталогов

Источники обрабатываются в следующем порядке:

1. значения `InstalledLocation` из подключённой общей конфигурации
   `1cescmn.cfg`;
2. значения из `1cestart.cfg` для всех пользователей Windows;
3. значения из пользовательского `1cestart.cfg`;
4. стандартные каталоги установки текущей ОС.

На Linux и macOS есть только пользовательский
`$HOME/.1C/1cestart/1cestart.cfg`. На Windows сначала проверяется
`%APPDATA%\1C\1CEStart\1CEStart.cfg`, чтобы найти `CommonCfgLocation`, затем
`%ALLUSERSPROFILE%\1C\1CEStart\1CEStart.cfg`; значения `InstalledLocation`
из уже найденных файлов ранжируются в описанном выше порядке, совпадающем с
документированным порядком 1С.

Поддерживаются штатные раскладки 1С 8.3.27:

- Windows: установки для компьютера в `%ProgramFiles%\1cv8` и
  `%ProgramFiles(x86)%\1cv8`, а также установки для пользователя в
  `%LOCALAPPDATA%\Programs\1cv8`, `1cv8_x86` и `1cv8_x64`;
- Linux: `/opt/1cv8/<arch>/<version>` для `x86_64`, `i386` и `arm64`;
- macOS: `/opt/1cv8/<version>`.

`InstalledLocation` позволяет обнаружить штатно зарегистрированную установку в
нестандартном каталоге без отдельного параметра API.

Пустые и повторные корни удаляются. На Windows сравнение нормализованных путей
выполняется без учёта регистра, на Linux и macOS — с учётом регистра.

### Кандидаты

Поиск ограничен известной глубиной каждой раскладки. Каталог версии должен
иметь имя, соответствующее точному выражению:

```regex
^8\.3\.27\.(\d+)$
```

Версия берётся только из имени каталога. Каталоги других веток игнорируются.
Сборка разбирается числом, поэтому `8.3.27.1000` новее `8.3.27.999`.

В каталоге кандидата проверяются штатные расположения:

- Windows: `bin/1cv8.exe` и `bin/ibcmd.exe`;
- Linux и macOS: `1cv8` и `ibcmd`, а также варианты в `bin`.

Файл считается доступным приложением, если он существует и является обычным
файлом. На Linux и macOS дополнительно требуется хотя бы один исполняемый бит.
Отсутствие одного приложения не отбрасывает установку: `enterprisePath` и
`ibcmdPath` отражаются независимо. Кандидат без обоих приложений установкой не
считается.

Символические ссылки разрешаются рабочим `realpath`. В результате возвращаются
канонические пути приложений и канонический каталог установки. Отдельная
политика запрета символических ссылок не вводится.

### Выбор

Кандидаты сортируются по следующим признакам:

1. максимальная числовая сборка `8.3.27.*`;
2. нативная архитектура процесса, когда раскладка явно задаёт архитектуру;
3. порядок источников каталогов;
4. нормализованный путь как последний детерминированный критерий.

Если кандидатов нет, `findPlatform()` возвращает `undefined`. Отсутствие
платформы является ожидаемым состоянием, а не исключением.

## Поиск источников информационных баз

### Основной список

Первым источником всегда считается личный файл текущего пользователя:

- Windows: `%APPDATA%\1C\1CEStart\ibases.v8i`;
- Linux и macOS: `$HOME/.1C/1cestart/ibases.v8i`.

Отсутствие файла не останавливает поиск общих источников.

### Конфигурационные файлы

После основного списка читаются штатные локальные `1cestart.cfg`. На Windows
это сначала `%APPDATA%\1C\1CEStart\1CEStart.cfg`, затем
`%ALLUSERSPROFILE%\1C\1CEStart\1CEStart.cfg`; на Linux и macOS —
`$HOME/.1C/1cestart/1cestart.cfg`. Такой порядок явно отдаёт предпочтение
пользовательскому окружению при правиле «первый встретившийся». Имена
параметров сравниваются без учёта регистра. Повторяющиеся параметры сохраняют
порядок появления.

Обрабатываются два параметра:

- `CommonInfoBases` — путь к общему файлу `.v8i`;
- `CommonCfgLocation` — путь к общей конфигурации `1cescmn.cfg`, из которой
  также читаются `CommonInfoBases`.

Относительный путь разрешается относительно файла конфигурации, в котором он
объявлен. Пути с переменными окружения раскрываются только в синтаксисе,
штатном для текущей ОС. Общие файлы могут находиться на локальном диске,
UNC-ресурсе Windows или заранее смонтированном каталоге Linux/macOS.

Каждый канонический `.cfg` и `.v8i` читается не более одного раза. Это
предотвращает повторную выдачу баз и циклы через `CommonCfgLocation`.
`WebCommonInfoBases` игнорируется без сетевого обращения.

Порядок источников:

1. личный `ibases.v8i`;
2. `CommonInfoBases` локальных конфигураций в порядке поиска конфигураций и
   объявления параметров;
3. `CommonInfoBases` подключённых общих конфигураций в порядке обхода.

Этот порядок определяет, какой узел сохраняется при обнаружении дубликата.

## Разбор `.v8i`

Файл читается как UTF-8 с допустимым BOM. Разбор учитывает особенности формата:

- раздел начинается заголовком `[Имя]`;
- первая `=` отделяет имя поля от значения, поэтому последующие `=` допустимы
  в имени папки или значении;
- пустые строки пропускаются;
- неизвестные поля сохраняются во внутренней записи без попытки истолковать;
- раздел с `Connect` является базой;
- раздел без `Connect` является папкой.

`Connect` разбирается с учётом кавычек и разделителей внутри кавычек, а не
простым `split(";")`. Публичная модель подключения является объединением:

```ts
type InfobaseConnection =
  | { type: "file"; path: string }
  | { type: "server"; server: string; reference: string }
  | { type: "web"; url: string }
  | { type: "unknown"; raw: string }
```

У базы одновременно сохраняется исходное значение `Connect`. Это позволяет
диагностировать непризнанный или будущий формат без потери данных.

Раздел с синтаксической ошибкой пропускается с предупреждением. Ошибка одного
раздела не отменяет остальные разделы файла.

## Построение и объединение дерева

Публичные узлы имеют явный различающий признак:

```ts
type InfobaseFolderNode = {
  kind: "folder"
  name: string
  children: InfobaseTreeNode[]
  source: string
}

type InfobaseNode = {
  kind: "infobase"
  name: string
  id?: string
  connection: InfobaseConnection
  rawConnection: string
  version?: string
  defaultVersion?: string
  app?: string
  source: string
}

type InfobaseTreeNode = InfobaseFolderNode | InfobaseNode
```

Поле `Folder` задаёт путь родительской папки, `/` означает корень. Явные
папки без дочерних баз сохраняются. Если база или папка ссылается на
отсутствующую промежуточную папку, она создаётся неявно, а результат получает
предупреждение.

Деревья всех источников объединяются по полному пути папки. Папка, первой
задавшая путь, определяет её `source`; последующие источники только добавляют
дочерние узлы.

База из более позднего источника считается дубликатом, если в уже
обработанном источнике встречался хотя бы один из её устойчивых
идентификаторов:

- непустой `ID`;
- нормализованная строка `Connect`.

Сохраняется база из первого источника. Поздний дубликат не добавляется в
дерево и не заменяет ранний узел. Его появление не считается ошибкой. Внутри
одного `.v8i` записи с одинаковым `Connect` не удаляются: 1С разрешает
регистрировать одно подключение несколько раз с разными параметрами запуска.

Порядок дочерних узлов задаётся числовым `OrderInTree`. При отсутствии или
равенстве `OrderInTree` сохраняется порядок появления в объединённом потоке.
Служебное значение порядка остаётся внутренним и не обязано публиковаться
через MCP.

## Диагностика и частичный результат

```ts
type InfobaseSource = {
  path: string
  kind: "personal" | "common"
}

type InfobaseWarning = {
  code:
    | "source-not-found"
    | "source-unreadable"
    | "invalid-config"
    | "invalid-section"
    | "implicit-folder"
  source: string
  message: string
}
```

Это закрытый перечень кодов первого выпуска. Сообщение предназначено человеку,
а логика потребителя не должна зависеть от его текста.

Недоступный или повреждённый источник не отменяет уже прочитанные базы.
Если ни один источник не прочитан, `listInfobases()` возвращает пустое дерево
и предупреждения. Исключение допускается только для ошибки самого
программного договора, а не для обычного состояния локальной машины.

`sources` содержит успешно прочитанные `.v8i` в фактическом порядке. Пути к
проверенным, но недоступным файлам находятся в предупреждениях.

## MCP-инструмент

В `@nkdk/mcp` регистрируется read-only инструмент:

```text
nkdk.list_infobases
```

Инструмент не принимает параметров и вызывает `listInfobases()` без
дополнительной предметной логики. Результат содержит:

- `tree`;
- `sources`;
- `warnings`.

Через MCP публикуются только поля, нужные для выбора базы и будущего
подключения: имя, `ID`, дерево, версия и режим клиента, типизированное
подключение, исходный `Connect` и источник. Неизвестные поля `.v8i` остаются
внутри парсера и через MCP не выдаются.

Инструмент не пишет файлы, не запускает процессы и не обращается в сеть.
Поиск платформы через MCP не публикуется.

## Тестирование

Тесты не создают временные каталоги и файлы. Все входные данные задаются через
модельные реализации `FileSystem` и `PlatformEnvironment`.

Поиск платформы проверяется на следующих сценариях:

- стандартные корни Windows, Linux и macOS;
- `InstalledLocation`;
- несколько сборок и числовой выбор максимальной;
- одинаковая сборка разных архитектур;
- независимое отсутствие `1cv8` и `ibcmd`;
- кандидат без обоих приложений;
- права выполнения Unix;
- повторные и канонически совпадающие пути;
- ошибки чтения отдельных корней.

Разбор и дерево баз проверяются на следующих сценариях:

- UTF-8 с BOM и без BOM;
- `=` в именах папок и значениях;
- `;` и `=` внутри кавычек `Connect`;
- файловое, серверное, веб- и неизвестное подключение;
- вложенные, пустые и неявные папки;
- `OrderInTree` и устойчивый порядок при равенстве;
- относительные `CommonInfoBases`;
- `CommonCfgLocation`, повторные источники и циклы;
- совпадение по `ID` и по нормализованному `Connect`;
- правило «первый встретившийся»;
- частичный результат при нечитаемом файле и некорректном разделе;
- пустой результат с предупреждениями.

MCP-тесты подменяют `listInfobases()` и проверяют:

- регистрацию и публичную схему `nkdk.list_infobases`;
- отсутствие входных параметров;
- точное отображение дерева, источников и предупреждений;
- отсутствие внутренних полей парсера в результате.

Обязательная итоговая проверка реализации:

```text
pnpm test
```

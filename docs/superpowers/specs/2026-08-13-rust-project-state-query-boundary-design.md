# Оптимизация границы запросов ProjectState на Rust

## Цель

Подготовить следующий небольшой слой поэтапного переноса `ProjectState` на Rust: устранить лишние переходы через `napi-rs` для повторных запросов и перестать копировать строки найденных целей из общего снимка в ответ Rust.

Этап считается успешным, если на повторяющейся рабочей нагрузке Rust:

- не медленнее текущей реализации TypeScript;
- не увеличивает пиковую RSS;
- сохраняет результаты всех запросов и диагностик.

Уникальные запросы измеряются отдельно и показывают чистую стоимость границы `napi-rs`, но не являются условием остановки этого этапа.

## Выбранный подход

Кэш размещается в TypeScript-переходнике Rust-reader. Повторный запрос по паре `componentPath` и `canonicalTarget` возвращается из кэша без кодирования UTF-8 и вызова `napi-rs`. Ключ и семантика кэша совпадают с эталонной реализацией TypeScript; снимок неизменяем, поэтому сброс кэша внутри одного read session не требуется.

Rust возвращает не строки цели, а идентификаторы записей общего снимка:

- вид цели;
- `sourceFileId`;
- идентификаторы canonical, component path, item path и owner path;
- отсутствие необязательного значения обозначается существующим `0xffff_ffff`.

Путь исходного файла определяется по `sourceFileId`. TypeScript читает строки через существующий `ProjectStateSnapshotView` и формирует прежний результат `ProjectStateQueryPort`. Публичный интерфейс, формат `project-state.bin 0.5.0` и `ProjectStateReadToken` не меняются.

## Двоичный ответ

Запрос пока сохраняет существующее представление UTF-8: пара строк на каждую уникальную цель в пачке. Ответ содержит строки фиксированного размера только с числовыми идентификаторами. Раздел строк в ответе отсутствует.

Rust проверяет каждый идентификатор до записи ответа. TypeScript повторно проверяет диапазоны при чтении снимка. Повреждённый или несовместимый ответ приводит к явной ошибке; скрытый переход на TypeScript запрещён.

Выделение выходного буфера вызывающей стороной и перенос всего validation-прохода в Rust не входят в этот слой. К ним следует переходить только после повторного измерения.

## Поток данных

Для каждой пачки TypeScript разделяет запросы на найденные в кэше и новые, а одинаковые новые ключи объединяет. Только уникальные новые запросы кодируются и передаются Rust. Полученные идентификаторы преобразуются в результаты и помещаются в кэш. Затем ответы собираются в исходном порядке с исходными `requestId`.

Кэш хранит результат без `requestId`, чтобы один результат можно было использовать для разных запросов. Ошибки `missing` и `ambiguous` кэшируются наравне с найденной целью.

## Проверка

Разработка выполняется через TDD:

1. Тест фиксирует, что две последовательные пачки с одинаковой целью вызывают native reader один раз.
2. Тесты двоичного протокола фиксируют ответ с идентификаторами для найденной, отсутствующей и неоднозначной цели.
3. Сравнительные тесты подтверждают одинаковые результаты TypeScript и Rust, включая дополнительные сведения о ссылке.
4. Существующие contract-тесты проверяют отсутствие изменений публичного поведения.

Измерение выполняется в отдельных процессах, по пять запусков каждого варианта. Отдельно измеряются:

- повторяющиеся запросы, отражающие пользу кэша;
- уникальные запросы, отражающие стоимость кодирования и `napi-rs`.

Сравниваются медианы времени, CPU и максимальной RSS. Если Rust остаётся медленнее TypeScript или расходует больше RSS на повторяющейся нагрузке, дальнейшее расширение Rust query engine приостанавливается и исследуется перенос более крупной операции целиком.

## Последующие слои

После успешного результата можно последовательно рассмотреть:

1. заранее выделяемый TypeScript буфер ответа с прямой записью из Rust;
2. числовые идентификаторы и для входных запросов, если вызывающая сторона уже работает со снимком;
3. перенос полной пакетной проверки в Rust с возвратом только итоговых диагностик.

Каждый следующий слой сохраняет текущие внешние интерфейсы и получает отдельное измерение до расширения границы переноса.

# Rule runtime и направленные metadata-границы

Статус: согласовано с расширением архитектурных этапов.

## Контекст

Каталог `packages/core/metadata/orchestration` не координирует пользовательские
операции. Он исполняет декларации `rules.ts`: преобразует свойства и объекты
метаданных между XML, внутренней моделью и YAML, строит JSON Schema, выводит
типы, разрешает metadata targets и вызывает зарегистрированные обработчики.

Название `orchestration` скрывает эту ответственность и пересекается по смыслу
с настоящими координаторами в `metadata/operations`, `metadata/project`,
`metadata/importFromXml` и `metadata/fullSyncToXml`. Из-за этого направление
зависимостей между слоями трудно обсуждать и закреплять в dependency-cruiser.

Одного переименования недостаточно. Текущая конфигурация dependency-cruiser
закрывает нейтральные metadata-слои от конкретных реализаций, но разрешает
крупными группами взаимные зависимости между `project`, `validation`,
`ruleRuntime`, `resourceTopology`, `projectState`, `workerPool` и другими
общими каталогами. Часть локальных границ дополнительно проверяется чтением
исходного текста и регулярными выражениями, а не полным графом импортов.

## Цель

Сделать название общего механизма правил точным, а направления зависимостей —
явными и проверяемыми dependency-cruiser. Работа выполняется последовательными
этапами без функциональных изменений XML, YAML, JSON Schema и публичного API.

Каждый этап завершается отдельным рабочим коммитом. Новые нарушения не
принимаются в baseline; если правило нельзя включить без существующего долга,
сначала устраняется архитектурная причина долга.

## Этап 1. Переименование rule runtime

Переименовать каталог:

```text
packages/core/metadata/orchestration
    -> packages/core/metadata/ruleRuntime
```

`ruleRuntime` означает общий механизм исполнения `rules.ts`. Он владеет:

- договорами и реестрами property-, metadata item- и form element-правил;
- преобразованиями XML ↔ модель ↔ YAML;
- построением JSON Schema и Enterprise-представлений по правилам;
- общими механизмами metadata targets и data paths;
- расширениями и завершающими обработчиками, вызываемыми во время исполнения
  правил.

Само переименование не меняет ответственности модулей и не вводит новую
архитектурную границу. Оно создаёт однозначный термин для следующих этапов.

## Модель архитектурных зон

Для подсистем, где одного каталога недостаточно для описания направления,
используются четыре явные зоны:

```text
contracts -> core -> adapters -> composition
```

- `contracts` содержит устойчивые типы и порты без знания реализаций;
- `core` реализует правила подсистемы и зависит только от нижних договоров;
- `adapters` связывает core с соседними подсистемами;
- `composition` собирает реальные реализации в точках запуска.

Название зоны выражается путём каталога или однозначным шаблоном имени файла.
Исключения задаются узкими путями, а не разрешением всего верхнеуровневого
каталога.

## Этап 2. Графовые правила вместо проверок текста

Проверки из `tools/dependency-cruiser/test/*boundary*.test.mjs`, которые читают
production-файлы через `readFileSync` и ищут импорты регулярными выражениями,
заменяются правилами полного графа там, где проверяемый договор выражается как
направление зависимости или транзитивная достижимость.

Dependency-cruiser должен проверять как минимум:

- `contracts` и `core` не достигают `adapters` и `composition`;
- нижний слой не достигает верхнего через реэкспорт, type-only импорт или новый
  промежуточный файл;
- синтетические примеры графа покрывают прямой runtime-импорт, type-only импорт
  и транзитивный путь.

Файловые проверки сохраняются только для договоров, которых нет в графе
модулей, например запрета конкретного поля или побочного действия в `types.ts`.
Поведенческие тесты не удаляются.

## Этап 3. Diagnostics как нижний договор

`metadata/diagnostics` становится листовым слоем и не импортирует
`metadata/validation`. Внутренние модули diagnostics используют собственные
типы напрямую. Совместимые реэкспорты из validation могут сохраняться для
публичных потребителей, но diagnostics не импортирует их обратно.

Dependency-cruiser запрещает `diagnostics -> validation` для production-кода.
Наблюдаемая проверка этапа выполняется через публичную коллекцию diagnostics и
её двоичное представление.

## Этап 4. Resource topology как самостоятельный нижний слой

Ядро `resourceTopology` владеет декларациями ресурсов, компиляцией topology,
шаблонами путей и нейтральными проекциями. Оно не читает реестры `ruleRuntime`
или `project` самостоятельно.

Связь topology с зарегистрированными property rules и project specs находится
в явных адаптерах, подключаемых composition root. После переноса включаются
запреты:

- `resourceTopology/core -> ruleRuntime`;
- `resourceTopology/core -> project`;
- `resourceTopology/core -> configurationIndex`.

Существующие тесты compiler, provider registry и project projection
консолидируются вокруг публичной границы компиляции, когда они дублируют
внутреннее устройство.

## Этап 5. Направление project -> validation

`project` владеет сценарием подготовки файлов проекта и вызывает validation.
Обратная production-зависимость `validation -> project` запрещается.

Типы путей, описания ресурсов, project spec views, local facts и prepared YAML
descriptors, необходимые обоим слоям, переносятся в нижние contracts либо
передаются в validation готовыми снимками. Validation не читает project
registry и не получает сведения через верхнеуровневые функции project.

Граничные тесты проверяют договор:

```text
подготовленный YAML + rules snapshot -> diagnostics + index contribution
```

а не внутренние вызовы между мелкими project- и validation-модулями.

## Этап 6. Явные composition roots

Сборка реальных реализаций размещается в `metadata/composition` либо в строго
определённых `*.composition.ts`. Только composition roots могут одновременно
знать `project`, `validation`, конкретные metadata-объекты и worker-операции.

Импорт composition разрешён только из публичной точки сборки `core/index.ts` и
реальных worker entrypoints. `ruleRuntime`, `resourceTopology`, `projectState`,
`workerPool` и конкретные реализации не импортируют composition root даже
транзитивно. Тестовые composition helpers остаются test-only кодом.

## Этап 7. Направленная иерархия конкретных реализаций

Целевое направление production-зависимостей:

```text
ruleRuntime / systemEnumerations
              ^
        commonObjects
              ^
            forms
              ^
        appliedObjects
              ^
operations / importFromXml / fullSyncToXml
```

Обратные зависимости `commonObjects -> forms|appliedObjects` и
`systemEnumerations -> forms|appliedObjects` устраняются переносом общих
договоров вниз либо узкими адаптерами. Взаимодействие соседних applied objects
проходит через общие fragments и builders; композиционный
`configuration/topLevelRules.ts` остаётся явным исключением.

После устранения каждой группы dependency-cruiser запрещает соответствующее
направление целиком. Широкие разрешения для всего `commonObjects`, `forms` или
`appliedObjects` не добавляются.

## Этап 8. Межпакетная матрица

Dependency-cruiser закрепляет уже соблюдаемое направление:

- `core` не зависит от `mcp` и `platform`;
- `platform` не зависит от `core` и `mcp`;
- `mcp` зависит от `core` и `platform` только через их публичные `index.ts`;
- межпакетные deep imports запрещены.

`@nkdk/core` и `@nkdk/platform` остаются допустимыми build-time зависимостями
MCP: esbuild встраивает их в публикуемый пакет. Общее правило
`no-runtime-to-dev-dependency` не должно ошибочно запрещать эту подтверждённую
схему сборки.

## Порядок планирования

По решению разработчика все этапы входят в один реализационный план, но
выполняются последовательно отдельными рабочими коммитами. Следующий этап
начинается только после целевых, типовых, архитектурных проверок и проверки
дубликатов предыдущего.

План заранее фиксирует владельцев переносимых договоров и точки сборки для
`resourceTopology`, `project -> validation`, composition roots и
concrete-иерархии. Если при реализации обнаружится несовместимость этого
решения с фактическим публичным договором, работа останавливается на границе
этапа, а спецификация не изменяется без нового согласования разработчика.

## Границы этапа переименования

В изменение входят:

- физический перенос всего каталога через `git mv`;
- обновление production- и test-импортов;
- обновление declaration merging с путями к реестрам;
- обновление dependency-cruiser, архитектурных проверок и синтетических
  примеров графа;
- обновление `AGENTS.md` и действующих инструкций в `.agents`;
- обновление актуальных комментариев и названий тестов, где `orchestration`
  обозначает переименованный слой.

В изменение не входят:

- совместимый каталог или реэкспорты по старому пути;
- изменение публичного API `@nkdk/core`;
- перемещение отдельных модулей между архитектурными слоями;
- изменение XML-, YAML-, JSON Schema- или runtime-поведения;
- переписывание исторических документов в `docs/superpowers` и сохранённых
  отчётов о производительности.

После изменения слово `orchestration` может оставаться в исторических
документах и в обычном английском описании координации, но не как действующий
путь или название metadata-слоя.

## История Git

Перенос выполняется через `git mv`, а обновление импортов входит в тот же
коммит. Git не хранит отдельный признак переименования, но определяет его по
сходству содержимого. Изолированный коммит без функциональных изменений должен
позволить `git diff --find-renames` распознать файлы как переименованные, а
`git log --follow` — продолжить их историю через новый путь.

Не создаётся промежуточный коммит, в котором каталог уже перенесён, а импорты
ещё не обновлены: каждый коммит ветки должен оставаться собираемым.

## Проверка каждого этапа

До фиксации изменения выполняются:

1. Целевые поведенческие и архитектурные тесты изменяемой границы.
2. `pnpm type-check`.
3. `pnpm test:architecture:rules`.
4. `pnpm test:architecture`.
5. `pnpm test`.
6. `pnpm duplicates -- --base 7e64fee8a`.
7. `git diff --check`.

Для этапа 1 дополнительно выполняются поиск действующих ссылок на старый путь и
`git diff --cached --find-renames` перед коммитом.

Исходный `pnpm test` в созданном worktree функционально выполняет 5 759 тестов,
но завершается ошибкой проверки временных лимитов. При реализации это исходное
отклонение нужно отделять от функциональных и архитектурных регрессий.

## Критерии завершения программы

- каталог существует только по пути `packages/core/metadata/ruleRuntime`;
- production-код, тесты и инструменты не используют старый путь;
- публичные экспорты и наблюдаемое поведение не изменились;
- TypeScript и обе архитектурные проверки проходят;
- полный набор функциональных тестов не получает новых падений относительно
  исходного состояния worktree;
- проверка дубликатов не обнаруживает новых совпадений;
- Git распознаёт перенос большинства файлов как rename;
- файловые regex-проверки не дублируют договоры, выражаемые полным графом;
- `diagnostics` не зависит от `validation`;
- ядро `resourceTopology` не зависит от `ruleRuntime`, `project` и
  `configurationIndex`;
- production `validation` не зависит от `project`;
- composition roots изолированы и недостижимы из нижних слоёв;
- concrete-слои соответствуют направленной матрице без широких исключений;
- межпакетные импорты проходят только в разрешённом направлении и через
  публичные точки входа.

# CommandInterface YAML Design

## Цель

Реализовать полноценный YAML round-trip для XML-файлов командного интерфейса:

- корневый `Ext/CommandInterface.xml`;
- корневый `Ext/MainSectionCommandInterface.xml`;
- `Ext/CommandInterface.xml` внутри подсистем.

`ConfigDumpInfo.xml` в этой работе не рассматривается.

## Источники

- `model.xdtobackend_root.res`: `CommandInterface` описан как `CommandInterfaceFragment`.
- `/Users/nikita/git/roundTripElements/ext/CommandInterface.xml`: корневой пример с видимостью и порядком подсистем.
- `/Users/nikita/git/roundTripElements/ext/MainSectionCommandInterface.xml`: пример с видимостью, размещением и порядком команд.
- `/Users/nikita/git/roundTripElements/Subsystems/ПодсистемаВсеСвойства/Ext/CommandInterface.xml`: пример командного интерфейса подсистемы.
- `/Users/nikita/git/clean_cf`: чистая конфигурация без `Ext/CommandInterface.xml` и без `Ext/MainSectionCommandInterface.xml`.

## Принятые решения

Используем один общий YAML-тип `CommandInterface` для всех трех XML-файлов.
В корневом `Конфигурация.yaml` обычный файл пишется ключом `КомандныйИнтерфейс`, файл основного раздела - ключом `КомандныйИнтерфейсОсновногоРаздела`.
В YAML подсистемы тот же тип пишется ключом `КомандныйИнтерфейс`.

YAML-форма остается близкой к XML, но без XML-служебности:

```yaml
КомандныйИнтерфейс:
  ВидимостьПодсистем:
    Подсистема.Продажи:
      Общее: Ложь
      Роли:
        Администратор: Ложь
  ПорядокПодсистем:
    - Подсистема.Продажи
  ВидимостьКоманд:
    Catalog.Товары.StandardCommand.OpenList:
      Общее: Истина
      Роли:
        Администратор: Ложь
  РазмещениеКоманд:
    Catalog.Товары.StandardCommand.OpenList:
      ГруппаКоманд: ПанельНавигацииОбычное
      Размещение: Вручную
  ПорядокКоманд:
    - Команда: Catalog.Товары.StandardCommand.OpenList
      ГруппаКоманд: ПанельНавигацииОбычное
  ПорядокГрупп:
    - ПанельНавигацииОбычное
```

`Visibility` пишется как объект `Общее` плюс словарь `Роли`.
В YAML роли выводятся без префикса `Role.`, например `Администратор`.
При чтении YAML стоит принять и полную форму `Role.Администратор`, чтобы не ломать ручные правки и соседние соглашения проекта.

`CommandsPlacement.Placement` получает отдельное соответствие:

- `Auto` -> `Авто`;
- `Manual` -> `Вручную`.

Для групп команд используем существующее соответствие стандартных групп команд, где оно есть:

- `NavigationPanelImportant` -> `ПанельНавигацииВажное`;
- `NavigationPanelOrdinary` -> `ПанельНавигацииОбычное`;
- `NavigationPanelSeeAlso` -> `ПанельНавигацииСмТакже`;
- `ActionsPanelCreate` -> `ПанельДействийСоздать`;
- `ActionsPanelReports` -> `ПанельДействийОтчеты`;
- `ActionsPanelTools` -> `ПанельДействийСервис`.

Нестандартные группы вида `CommandGroup.ГруппаКомандПоУмолчанию` сохраняются ссылкой как есть, без попытки встроить свойства группы в этот YAML.

## Default-поведение

`КомандныйИнтерфейс` и `КомандныйИнтерфейсОсновногоРаздела` являются необязательными свойствами.
Если в XML-выгрузке нет соответствующего файла, YAML-ключ не создается.
Если в YAML нет ключа и нет reference-файла, экспорт не должен создавать новый XML-файл.

Если YAML-ключ отсутствует, но reference содержит соответствующий XML-файл, экспорт сохраняет reference-файл только в сценарии сохранения существующего XML без изменения этой части модели.
Если YAML-ключ присутствует, XML строится из YAML.

## Ссылки

Обычные ссылки на подсистемы, роли, команды и группы команд в YAML должны оставаться человекочитаемыми.
Технические идентификаторы не должны попадать в YAML, если их можно восстановить из reference или из XML основного объекта.

## Открытый вопрос

Для команд вида `0:<uuid>` и `1:<uuid>` решение не входит в список принятых.
Перед планом реализации нужно отдельно согласовать человекочитаемую форму таких ссылок.
Предпочтительный вариант для следующего обсуждения: выводить в YAML ссылку на объект и номер команды, например `Document.ДокументВсеСвойства.GeneratedCommand.0`, а при экспорте восстанавливать `0:<uuid>` из reference.
Если восстановить ссылку невозможно, нужен запасной путь с сырой XML-строкой, чтобы не терять данные.

## Архитектура

Добавить rule-driven общий объект для внешнего `CommandInterface`, не смешивая его с существующим командным интерфейсом формы.
Объект должен покрывать секции из `CommandInterfaceFragment`:

- `CommandsVisibility`;
- `CommandsPlacement`;
- `CommandsOrder`;
- `SubsystemsVisibility`;
- `SubsystemsOrder`;
- `GroupsOrder`.

Подсистемный `commandInterface`, который сейчас описан как `Template` с выключенными `fromXML` и `toXML`, должен перейти на этот общий тип.
Корневая конфигурация должна получить два внешних свойства для `Ext/CommandInterface.xml` и `Ext/MainSectionCommandInterface.xml`.

## Проверка

План проверки для будущей реализации:

1. XML -> модель -> XML для фикстур `roundTripElements/ext` и подсистемы `ПодсистемаВсеСвойства`.
2. XML -> YAML для корневого `CommandInterface.xml`: видимость и порядок подсистем попадают в `КомандныйИнтерфейс`.
3. XML -> YAML для `MainSectionCommandInterface.xml`: видимость, размещение, порядок команд и порядок групп попадают в `КомандныйИнтерфейсОсновногоРаздела`.
4. XML -> YAML для подсистемы: существующий `Ext/CommandInterface.xml` больше не теряется.
5. XML/YAML цикл для `/Users/nikita/git/clean_cf`: ключи отсутствуют, новые XML-файлы не создаются.
6. Полный `round-trip-yaml` для выбранной конфигурации после реализации.

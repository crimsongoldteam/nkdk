# Точный topology-контекст вложенных metadata-объектов

## Контекст

Metadata E2E импортирует реальную конфигурацию и расширения, после чего запускает
тёплую и холодную validation. В текущем отчёте 13 диагностик относятся к
вложенным файловым объектам внешнего источника данных: кубам, таблицам и таблицам
измерений.

Например, файл
`ВнешнийИсточникДанных/Источник/Кубы/Куб/Свойства.yaml` описывает объект
`ExternalDataSource.Источник.Cube.Куб`, но последующие стадии считают его
свойствами корневого `ExternalDataSource.Источник`. Из-за этого специализированная
схема объекта, metadata target и пути к данным расходятся с topology.

Причина состоит из двух связанных частей:

- topology уже знает фактическое `itemRule` и цепочку assignments, но
  `projectDefinition` не переносит точную идентичность объекта дальше;
- любой content assignment с ролью `fileItem` преобразуется в устаревшую роль
  `form`, хотя настоящие формы отдельно помечены `projectRole: "form"`.

Затем import и validation независимо восстанавливают владельца из пути файла и
`owner.dir`. Такой разбор работает для корневых и однородно рекурсивных объектов,
но не выражает разнородную цепочку `ExternalDataSource → Cube → DimensionTable`.

## Цель

Сделать topology единственным источником фактического правила, роли YAML-ресурса
и точного metadata target вложенного объекта.

XML-import и последующая YAML-validation должны получать одинаковый контекст
объекта без повторного угадывания по именам каталогов. Исправление должно быть
общим для любых файловых дочерних коллекций и не содержать условий по внешним
источникам данных.

## Выбранный подход

Точный контекст вычисляется при topology-классификации ресурса и передаётся через
`projectDefinition` до import и validation. Путь файла остаётся адресом ресурса,
но перестаёт быть источником смысловой идентичности.

Альтернативы не выбраны:

- общий разборщик путей всё равно дублировал бы сведения topology и зависел от
  соглашений об именах каталогов;
- специальная обработка внешних источников данных устранила бы только текущий
  пример и нарушила нейтральность общих слоёв.

## Контекст ресурса

`resourceTopology/core` формирует для каждого YAML-ресурса единый контекст:

- фактическое `itemRule` текущего файлового объекта;
- точный `TopologyMetadataTargetOwner` с корнем и полной цепочкой вложенных
  объектов;
- смысловую роль YAML-файла.

Роль `fileItem` означает отдельный YAML-файл дочернего объекта, а не форму.
Формой считается только ресурс, для которого topology явно объявляет
`projectRole: "form"`. Обычный `fileItem` без этой отметки классифицируется как
файл свойств собственного объекта.

Корневая конфигурация остаётся отдельным допустимым случаем без metadata target.

## Компоненты и поток данных

### Resource topology

Проекция файловых metadata targets использует уже существующую цепочку
assignments и resolver topology. Она возвращает идентичность именно того объекта,
чьё правило назначено YAML-файлу, включая все разнородные вложенные сегменты.

### Project definition

`MetadataProjectResourceRef` переносит фактическое правило, точный metadata target
и роль для всех YAML-ресурсов, а не только для ресурсов, ранее названных формами.
Устаревший `owner` может временно сохраняться для совместимости с размещением и
старыми интерфейсами, но не используется для выбора схемы или определения
смыслового владельца.

### Validation project file

`ValidationProjectFile` получает тот же контекст без повторной классификации.
Схема файла свойств компилируется по его фактическому `itemRule`: схема куба — по
правилу куба, схема таблицы измерений — по правилу таблицы измерений.

### Снимок правил

`ValidationRulesSnapshot` содержит сериализуемые описания всех файловых
дочерних правил, достижимых обходом topology. Поиск правила выполняется по
идентичности правила или `itemType`, а не по корневому каталогу. Обход остаётся
нейтральным и не знает конкретных прикладных типов.

### Import и validation

XML-import и YAML-validation используют один преобразователь точного metadata
target в формат смысловых фактов. Два локальных алгоритма
`objectTargetForFile`, которые восстанавливают объект из `owner.dir` и частей
пути, удаляются.

`OwnerTypeRef` остаётся компактным представлением владельца для DataPath. Полная
вложенная идентичность хранится в metadata target, а требуемое представление
DataPath получается централизованно через существующий реестр владельцев.

Итоговый поток:

```text
topology match
  → точный контекст файлового объекта
  → projectDefinition
  → ValidationProjectFile
  → общие факты import/validation
  → ProjectState
```

## Ошибки и совместимость

Если topology не может определить точный контекст YAML-ресурса, который должен
описывать metadata-объект, выполнение завершается внутренней диагностикой с путём
файла и цепочкой assignments. Молчаливого возврата к определению владельца через
`owner.dir` нет.

Формат XML и YAML не меняется. Существующие XML-фикстуры остаются источником
истины и не редактируются. Для корневых и однородно рекурсивных объектов
сохраняется наблюдаемое поведение; отдельные тесты подтверждают равенство
получаемого контекста.

## Проверки

### Узкие договоры

- вложенный `fileItem` получает собственные `itemRule` и metadata target, но не
  роль формы;
- ресурс с явным `projectRole: "form"` продолжает классифицироваться как форма;
- `projectDefinition` для куба и таблицы измерений переносит специализированное
  правило и полную цепочку владельца;
- снимок правил предоставляет вложенное файловое правило без регистрации
  конкретного прикладного типа в общем слое;
- import и YAML-validation создают одинаковый metadata target для одного файла;
- существующие корневые и рекурсивные ресурсы сохраняют прежний контекст.

### E2E-договор

После изменения из отчёта должны исчезнуть 13 диагностик первой группы:
отсутствующие вложенные объекты, неверные ссылки и ошибочные пути к данным,
вызванные потерей topology-контекста. Остальные известные проблемы остаются
видимыми, поэтому общий E2E до следующих исправлений может оставаться красным.

Тёплая validation по diff и холодная validation без `.nkdk` должны возвращать
одинаковый состав оставшихся диагностик и одинаковый diff.

## Границы

В это изменение входят только вычисление и передача точной идентичности
вложенного объекта от topology до import и validation.

Не входят:

- специальные условия для внешних источников данных;
- исправление обработки `Predefined`;
- исправление validation частичных объектов расширений;
- удаление равного имени синонима корневой конфигурации;
- изменение XML/YAML-формата или существующих фикстур;
- удаление медленных тестов.

Последующие проблемы разбираются отдельными проектами решения после завершения
этого изменения.

## Критерии готовности

- topology является единственным источником правила, роли и metadata target
  файлового объекта;
- обычный `fileItem` больше не преобразуется в форму без явного `projectRole`;
- import и validation не восстанавливают вложенную идентичность из пути;
- решение не содержит условий по `itemType`, XML-корням или каталогам конкретных
  metadata-объектов в нейтральных слоях;
- узкие тесты проходят;
- 13 связанных диагностик исчезают из тёплого и холодного E2E-отчёта;
- оставшиеся диагностики совпадают между запуском по diff и запуском без `.nkdk`.

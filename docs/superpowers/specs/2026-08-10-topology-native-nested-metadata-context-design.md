# Системное исправление ошибок metadata E2E

## Контекст

Metadata E2E импортирует основную конфигурацию `cf` и три расширения `cfe`,
проверяет тёплую и холодную validation, затем выполняет полный
XML → YAML → XML с побайтовым сравнением.

На актуальном `origin/develop` чистая validation воспроизводимо возвращает
32 диагностики:

- 13 ошибок вложенных объектов внешнего источника данных;
- 6 ошибок специализированных полей `Predefined`;
- 8 ложных ошибок обязательных полей заимствованных объектов расширения;
- 2 лишних синонима корневых расширений;
- 3 каскадные ошибки, запрещающие семантическую проверку расширений при ошибках
  основной конфигурации.

Дополнительно импорт `cfe/РасширениеКонтроль` завершается ошибкой
`Переданный файл не принадлежит топологии: МодульВнешнегоСоединения.bsl`.

Побайтовое сравнение сообщает 612, 741, 12 и 2 удалённых файла по четырём
компонентам. Это не самостоятельные расхождения преобразования: XML sync
блокируется validation либо незавершённым импортом и сравнивается пустой
выходной каталог.

После реализации перечисленных ниже первичных исправлений актуальный E2E
оставляет 13 содержательных диагностик:

- 1 отсутствующий объект встроенной функции внешнего источника данных;
- 6 отсутствующих вложенных ссылок на поля, команды, измерения и ресурсы таблиц
  и кубов внешнего источника данных;
- 6 диагностик по ссылкам `FillValue` из CFE на предопределённые значения,
  которые не добавлены в это расширение.

Эти диагностики образуют две последние системные проблемы: точный target
теряется при построении индексных записей вложенных объектов, а допустимость
`!xml` для `FillValue` определяется до появления полного индекса компонента.

## Цели

- устранить все первичные ошибки чистого E2E системными договорами;
- сделать topology единственным источником контекста файлового metadata-объекта;
- учитывать специализированные `itemRule` при построении схем;
- различать полные собственные объекты расширения и частичные заимствованные
  наложения;
- разделить техническую идентичность корня и его смысловое имя;
- использовать одну компонентную topology на всём пути import и XML sync;
- индексировать встроенные и файловые вложенные объекты по одному точному
  rule-driven договору;
- определять необходимость `!xml` для ссылочного `FillValue` во втором проходе
  по полному индексу CFE;
- не маскировать ошибки ослаблением E2E или отключением validation.

## Общие принципы

- Нейтральные слои не содержат условий по `itemType`, XML-корням или каталогам
  конкретных metadata-объектов.
- Путь файла является адресом ресурса, но не источником его смысловой
  идентичности.
- Существующие XML-фикстуры остаются источником истины и не изменяются.
- Формат XML и YAML не расширяется служебными признаками.
- Тёплая validation по diff и холодная validation без `.nkdk` используют один
  смысловой договор.
- Ссылка из CFE разрешается в рамках CFE; наличие одноимённой цели в CF не
  делает ссылку доступной расширению.
- `!xml` сохраняет XML-форму, которую нельзя выразить доступной CFE смысловой
  ссылкой, но не является способом подавить ошибку обычного YAML.

## 1. Точный topology-контекст вложенных объектов

### Проблема

Файл
`ВнешнийИсточникДанных/Источник/Кубы/Куб/Свойства.yaml` описывает
`ExternalDataSource.Источник.Cube.Куб`, но последующие стадии считают его
свойствами корневого `ExternalDataSource.Источник`.

Topology уже знает фактическое `itemRule` и цепочку assignments, однако
`projectDefinition` не переносит точную идентичность дальше. Дополнительно любой
content assignment с ролью `fileItem` преобразуется в роль формы, хотя настоящие
формы явно помечены `projectRole: "form"`.

### Решение

`resourceTopology/core` формирует для каждого YAML-ресурса единый контекст:

- фактическое `itemRule` текущего файлового объекта;
- точный `TopologyMetadataTargetOwner` с полной цепочкой вложенности;
- смысловую роль YAML-файла.

Обычный `fileItem` без `projectRole: "form"` является файлом свойств собственного
объекта. Формой считается только явно помеченный ресурс.

`MetadataProjectResourceRef` и `ValidationProjectFile` переносят этот контекст
без повторного разбора пути. XML-import и YAML-validation используют общий
преобразователь точного metadata target. Локальные `objectTargetForFile`,
восстанавливающие объект из `owner.dir`, удаляются.

`ValidationRulesSnapshot` включает правила всех достижимых файловых дочерних
объектов. Схема выбирается по фактическому правилу файла, а не по корневому
каталогу.

Если точный контекст metadata-ресурса получить невозможно, выполнение
завершается внутренней диагностикой с путём файла и цепочкой assignments.
Молчаливого возврата к разбору пути нет. Корневая конфигурация остаётся
допустимым случаем без metadata target.

## 2. Специализированные правила Predefined

### Проблема

Обработчик `Predefined:exportToJSONSchema` всегда строит схему по базовому
`PredefinedRules`. Переданное свойством специализированное `itemRule` для плана
счетов или плана видов расчёта игнорируется. Поэтому их дополнительные поля
ошибочно считаются запрещёнными.

### Решение

`Predefined` уже зарегистрирован через общий `registerMetadataItemRule` с
базовым `PredefinedRules`. Общий обработчик схемы выбирает
`propertyRule.itemRule`, если оно задано, и использует базовое правило только как
резервное. Поэтому дополнительная регистрация не требуется.

Удаляется только более поздний самостоятельный обработчик JSON Schema,
жёстко привязанный к базовому правилу и перекрывающий общий. После этого план
счетов и план видов расчёта используют переданные ими специализированные
`itemRule`, а остальные типы — базовый `PredefinedRules`. XML-import,
YAML-export, вложенный обход и JSON Schema используют один договор выбора
правила.

## 3. Частичные заимствованные объекты расширения

### Проблема

Заимствованный объект в XML расширения является наложением и может содержать
только изменённые свойства. `ObjectBelonging` и `ExtendedConfigurationObject`
являются служебными XML-данными и намеренно не записываются в YAML.

Текущая validation применяет к такому YAML полную схему самостоятельного объекта
и требует поля, которые уже находятся в `cf`.

### Классификация

Объект расширения считается заимствованным, если в `cf` существует тот же
полный metadata target: тип, имя и вся цепочка владельцев. Например,
`ExternalDataSource.Источник.Cube.Куб`, а не только имя `Куб`.

Если полного target в `cf` нет, объект считается собственным объектом расширения
и обязан быть полным. Корень расширения не классифицируется как заимствованный
прикладной объект.

Этот договор совпадает с уже существующим определением `adoptedUuids` при
XML-export и восстанавливается без `.nkdk`.

### Решение

Validation разделяется на два нейтральных договора:

1. Структурная схема расширения проверяет синтаксис, допустимые свойства и типы
   переданных значений. `required` откладывается только на границе адресуемой
   metadata-записи, для которой общий обход правил сформировал канонический
   target.
2. Общий rule-driven проход обходит каждую такую запись, сохраняет её точный
   target, фактическое `itemRule` и отсутствующие обязательные свойства, а затем
   проверяет их после появления индекса `cf`.

Адресуемая metadata-запись определяется тем же нейтральным договором
logical-address, который используется индексом конфигурации и XML-export. Это
файловые прикладные объекты и адресуемые вложенные элементы, например реквизиты,
табличные части и команды. Список конкретных `itemType` в validation не
поддерживается.

Обычные вложенные структуры значений не имеют собственного metadata target.
Их `required`, а также обязательные поля внутри каждого переданного значения,
остаются в структурной схеме и проверяются сразу. Корень расширения также
проверяется полной схемой и не участвует в отложенной классификации.

Во втором проходе:

- target найден в `cf` — отсутствующие свойства наследуются и допустимы;
- target не найден — обязательные свойства проверяются по фактическому правилу;
- каждый вложенный объект классифицируется отдельно, поэтому собственный новый
  элемент внутри заимствованного объекта нельзя оставить неполным.

Базовая конфигурация предварительно проходит полную структурную validation,
поэтому заимствованный объект не может наследовать обязательное поле из
невалидного `cf`.

В YAML не добавляются признаки заимствования. В общих слоях не появляется
условий по внешним источникам данных или другим конкретным типам.

## 4. Смысловое имя корневого задания импорта

### Проблема

Корневое `itemName` вычисляется из пути `Конфигурация.yaml` и получает значение
`Конфигурация`. Правила XML → YAML сравнивают с ним синоним, хотя настоящее имя
расширения находится в `<Properties><Name>`.

В результате синоним, равный `РасширениеКонтроль` или
`РасширениеПоУмолчанию`, ошибочно сохраняется в YAML и затем отклоняется
validation.

### Решение

Разделить два понятия:

- topology-идентичность и logical address корня — `Конфигурация`;
- смысловое имя metadata — значение `<Properties><Name>` прочитанного корневого
  XML.

Стадия определения XML-компонента уже читает `Configuration.xml`. Она формирует
единый результат с адресом компонента и смысловым именем корня. Имя передаётся
корневому import assignment и XML → YAML-преобразованию, но не меняет
`configurationUid()`.

Для некорневых объектов имя продолжает определяться topology-путём; их XML-имя
проверяется существующими правилами преобразования.

## 5. Единая компонентная topology для расширений

### Проблема

XML discovery компилирует зарегистрированную topology основной конфигурации.
После определения компонента ProjectState классифицирует готовые файлы уже по
topology расширения. Один ресурс может быть принят первой стадией и отвергнут
второй.

Кроме того, правила корня расширения вручную повторяют только часть внешних
ресурсов конфигурации. В них отсутствуют присутствующие в валидной XML-фикстуре
три корневых модуля и `StandaloneConfigurationContent.bin`.

### Решение

После определения вида XML-компонента coordinator получает его `rootRule` и
один раз компилирует компонентную topology. Один экземпляр используется в
главном процессе для:

- XML discovery;
- подготовку import assignments;
- классификацию файлов ProjectState;
- построение плана и выполнение XML sync.

Скомпилированный path-index содержит методы и не передаётся через границу
worker. Каждый worker восстанавливает эквивалентную topology из того же
компонентного descriptor; задания связываются с ней по `topologyNodeId`. Другой
rootRule или зарегистрированная topology основной конфигурации в этом пути не
используются.

Общие внешние ресурсы корня описываются переиспользуемым фрагментом правил.
Конфигурация и расширение подключают разрешённые для них свойства из одного
источника. Расширение подключает четыре корневых модуля — управляемого
приложения, сеанса, внешнего соединения и обычного приложения — и
`StandaloneConfigurationContent.bin`. Эти свойства остаются `syncExternalOnly`
и не меняют YAML-модель.

Любой XML-файл, отсутствующий в выбранной компонентной topology, должен быть
отклонён discovery до запуска worker с точным исходным путём.

## 6. Каскадные ошибки расширений

Диагностика
`Семантическая валидация расширения невозможна из-за ошибок базовой конфигурации`
остаётся без изменений. Она корректно предотвращает проверку расширения по
недостоверному индексу `cf`.

После устранения первичных ошибок `cf` три каскадные диагностики исчезают без
специальной обработки. Подавлять или исключать их из E2E не требуется.

## 7. Отчёт byte round-trip при неуспешном sync

Побайтовое сравнение выполняется только если `sync.failed` пуст. Если XML sync
не начался или завершился ошибкой, E2E публикует его диагностики и отмечает
сравнение как не выполнявшееся.

Если sync успешен, сохраняется строгий договор:

- одинаковый отсортированный список путей;
- отсутствие добавленных и удалённых файлов;
- побайтовое равенство каждого файла;
- обычный и нормализованный diff при реальном несовпадении байтов.

Это убирает ложный шум из сотен «удалённых» файлов, не ослабляя round-trip.

## 8. Точные targets встроенных и вложенных объектов

### Проблема

Topology уже передаёт точный target каждого файлового объекта. Однако общий
индексатор коллекций повторно строит target из `OwnerMetadata.ref`, где остаются
только корень и имя корневого владельца. Цепочка `Table`, `Cube` или
`DimensionTable` теряется. Поэтому, например, команда куба индексируется как
элемент внешнего источника данных, а ссылка ожидает полный адрес элемента куба.

Функция внешнего источника данных хранится встроенной коллекцией в YAML
владельца. Сейчас объектный индекс создаётся только для корня YAML-файла, поэтому
`ExternalDataSource.<имя>.Function.<имя>` не получает самостоятельной индексной
записи, хотя является адресуемым metadata-объектом.

### Решение

Точный разобранный object target становится частью фактов владельца и передаётся
в общий построитель индексных записей. Индексаторы больше не восстанавливают
адрес из `rootFromYAML`, `owner.ref` или пути файла. Вложенный member target
получается добавлением сегмента к полному object target владельца, включая всю
цепочку `objectSegments`.

Общий rule-driven обход YAML формирует объектные индексные записи не только для
корня файла, но и для встроенных адресуемых metadata-объектов. Адресуемость и
канонический сегмент берутся из существующих деклараций rules и logical-address:
`metadataTargetOwner`, `externalMetadata.segment` и
`configurationIndexUidSegment`. Для коллекции функций объявляется её
канонический сегмент `Функция` существующим параметром правила. Условий по
`itemType` в validation и projectState не добавляется.

Один и тот же обход используется при XML-import, тёплой validation и холодном
восстановлении без `.nkdk`. Он создаёт:

- object target встроенной функции;
- member targets полей и команд таблиц;
- member targets измерений, ресурсов и команд кубов;
- member targets полей таблиц измерений с полной цепочкой владельцев.

Если адресуемый элемент объявлен правилом, но его полный target построить нельзя,
это внутренняя ошибка с путём YAML и цепочкой правил. Укороченный target не
публикуется.

## 9. `!xml` для недоступного CFE значения заполнения

### Проблема

В XML собственного объекта расширения `FillValue` может содержать
`xr:DesignTimeRef` на предопределённое значение CF, которое не добавлено в CFE.
Конфигуратор показывает такое значение заполнения пустым: смысловой ссылки в
расширении нет, но исходную XML-форму необходимо восстановить побайтово.

Сейчас XML-import экспортирует ссылку как обычное YAML-значение, а второй проход
справедливо не находит цель в индексе CFE. Поиск той же цели в CF дал бы ложное
представление, что значение доступно расширению.

### Решение

Решение о форме `FillValue` принимается общим вторым проходом после построения
полного индекса текущего metadata-компонента. Первый проход сохраняет pending
fact с канонической ссылкой, исходным XML transport и наличием YAML-тега.

Для CFE действует таблица состояний:

| YAML/XML-представление | Цель есть в CFE | Цели нет в CFE |
| --- | --- | --- |
| Обычная ссылка | Допустима | Ошибка «ссылка не найдена» |
| `!xml` | Ошибка: тег не требуется | Допустимо; содержимое не валидируется |
| XML-import `DesignTimeRef` | Обычная YAML-ссылка | `!xml` с исходным значением |

Проверка необходимости тега является отдельной проверкой transport-политики.
После признания `!xml` допустимым обычные проверки значения, типа и ссылки для
этого поля не выполняются. Сам тег не добавляется валидатором к вручную
написанному YAML: пользователь обязан указать его явно.

Индекс CF в этом решении не запрашивается. Наличие цели в CF не влияет на
классификацию `FillValue` из CFE. Это ограничение относится только к разрешению
данной ссылки и не отменяет использование CF для проверки заимствованных
объектов расширения, описанной в разделе 3.

XML-export значения `!xml` восстанавливает исходный `xr:DesignTimeRef` и его
текст. Для существующей цели обычная ссылка проходит стандартное преобразование.

## Итоговый поток данных

```text
Configuration.xml
  → вид компонента + смысловое имя корня
  → компонентный rootRule
  → единая компонентная topology
  → точные assignment rule + metadata target + роль
  → XML-import / YAML-validation / XML-sync
  → успешный sync
  → побайтовое сравнение
```

Для расширений validation дополнительно использует индекс точных targets `cf`:

```text
target присутствует в cf → заимствованное наложение → missing required допустим
target отсутствует в cf   → собственный объект       → required обязателен
```

Ссылочные значения расширения разрешаются отдельно, только по индексу CFE:

```text
обычная ссылка + цель в CFE       → допустима
обычная ссылка + цели нет в CFE   → ошибка ссылки
!xml + цель в CFE                 → ошибка лишнего !xml
!xml + цели нет в CFE             → сохранить XML без смысловой validation
```

## Проверки

### Topology и projectDefinition

- вложенный `fileItem` получает собственные `itemRule` и полный metadata target;
- `fileItem` без `projectRole: "form"` не является формой;
- явная форма сохраняет роль формы;
- корневые и рекурсивные объекты сохраняют прежний контекст;
- импорт и validation получают одинаковый target;
- topology расширения одинакова на discovery, ProjectState и XML sync.

### Predefined

- схема плана счетов разрешает `Порядок` и `ПризнакиУчета`;
- схема плана видов расчёта разрешает его четыре специальных поля;
- базовая схема справочника эти поля не разрешает;
- XML/YAML round-trip специализированных Predefined не меняется.

### Расширения

- неполный объект с полным target в `cf` проходит validation;
- неполный собственный объект без target в `cf` получает ошибки required;
- собственный вложенный объект внутри заимствованного владельца проверяется
  полностью;
- обычная вложенная структура без собственного target сохраняет все required;
- одинаковые имена в разных типах или у разных владельцев не смешиваются;
- результат совпадает с `.nkdk` и без `.nkdk`.

### Корневое имя

- logical address корня остаётся `Конфигурация`;
- XML-import использует настоящее `<Name>` для equal-name;
- равный имени синоним расширения не попадает в YAML;
- отличающийся синоним сохраняется.

### Точные вложенные targets

- встроенная функция внешнего источника данных получает object target;
- поле и команда таблицы получают target с сегментом владельца `Table`;
- измерение, ресурс и команда куба получают target с сегментом владельца `Cube`;
- поле таблицы измерения сохраняет цепочку `Cube.DimensionTable`;
- импорт и validation строят одинаковые канонические targets;
- укороченные targets без цепочки владельцев в индекс не попадают.

### Недоступный `FillValue` расширения

- XML-import ставит `!xml`, если предопределённого значения нет в CFE;
- XML-import оставляет обычную ссылку, если значение добавлено в CFE;
- обычная отсутствующая ссылка получает ошибку второго прохода;
- `!xml` для существующей цели получает ошибку ненужного тега;
- допустимый `!xml` не создаёт pending reference и не проходит смысловую
  validation значения;
- наличие цели только в CF не меняет результат;
- результат одинаков с `.nkdk` и без него;
- YAML → XML побайтово восстанавливает исходный `FillValue`.

### E2E

- `cf` и все три `cfe` импортируются без ошибок;
- чистая validation не содержит диагностик;
- удалённое обязательное поле собственного объекта `cfe` одинаково
  обнаруживается по diff и без `.nkdk`;
- отсутствие того же обязательного поля у заимствованного объекта остаётся
  допустимым;
- `cfe/control` сохраняет модули и автономное содержимое;
- все четыре компонента побайтово восстанавливают XML;
- при ошибке sync сравнение не создаёт ложный список удалённых файлов;
- при настоящем различии байтов сохраняются оба diff.

## Порядок реализации

1. Точный topology-контекст вложенных объектов.
2. Единая компонентная topology и внешние ресурсы расширения.
3. Специализированное `itemRule` для Predefined.
4. Смысловое имя корневого import assignment.
5. Target-aware required validation расширений.
6. Точный owner target и rule-driven индексирование встроенных объектов.
7. Второй проход transport-политики `FillValue` по индексу CFE.
8. Уточнение E2E-отчёта и полный финальный прогон.

Такой порядок сначала создаёт точную идентичность и единый контекст, на которых
зависит корректная классификация заимствованных объектов.

## Вне границ

- изменение XML- или YAML-формата;
- добавление служебных признаков заимствования в YAML;
- специальные условия для внешних источников данных в нейтральных слоях;
- ослабление byte round-trip до нормализованного или смыслового равенства;
- экспорт с `ignoreValidationErrors` в E2E;
- поиск недоступного CFE `FillValue` в индексе CF;
- автоматическое добавление `!xml` при validation вручную написанного YAML;
- разрешение `!xml` для существующей в CFE обычной ссылки;
- удаление медленных тестов до отдельного аудита покрытия.

## Критерии готовности

- все первичные import и validation ошибки устранены;
- каскадные ошибки исчезли вслед за ошибками `cf`;
- одна компонентная topology используется всеми стадиями;
- собственные и заимствованные объекты расширения различаются по полному target;
- встроенные и файловые вложенные объекты одинаково представлены точными
  targets в индексе;
- необходимость `!xml` для `FillValue` определяется полным индексом CFE во
  втором проходе;
- тёплая и холодная validation эквивалентны;
- все четыре XML-каталога восстановлены по путям и байтам;
- решение не содержит частных исключений по конкретным metadata-типам.

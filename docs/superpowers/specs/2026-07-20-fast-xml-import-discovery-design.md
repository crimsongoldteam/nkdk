# Fast XML Import Discovery Design

## Контекст

Импорт из XML-выгрузки сейчас тратит непропорционально много времени на этап `Формирование и распределение заданий импорта`. Узкий профиль ERP показал:

- XML-выгрузка содержит 137 078 файлов;
- правил import после раскрытия `rules.ts` — 598;
- текущая классификация выполняет около 84 454 500 проверок путей по шаблонам;
- реальное количество совпадений обычно 1–2 на файл;
- последовательный обход файлов занимает около 6.8 с, параллельный обход в стиле validation — около 1.2 с;
- основное время уходит не на `readdir`, а на сопоставление каждого пути почти со всеми правилами и последующую сборку заданий.

В validation аналогичный этап `Чтение проекта` быстрее, потому что путь YAML-проекта классифицируется по структуре проекта: первый сегмент указывает на семейство метаданных, а дальше проверяется небольшой набор правил этого семейства.

## Цель

Сделать `Подготовка импорта конфигурации` быстрой и малопамятной за счёт классификации путей XML-выгрузки по подготовленным `Правила структуры XML-выгрузки`, а не полным перебором всех правил для каждого файла.

## Не цели

- Не менять формат `rules.ts`.
- Не читать содержимое XML во время discovery.
- Не менять результат discovery: набор заданий, XML-файлов и внешних файлов должен совпадать с текущей реализацией.
- Не решать в этой задаче потребление памяти worker first/second pass и запись файла индекса конфигурации.
- Не добавлять знания о конкретных прикладных объектах в общие orchestration/project слои.

## Архитектурный подход

`rules.ts` остаётся источником истины. Декларативные правила import подготавливаются в компактную структуру XML-выгрузки, пригодную для быстрого прохода по сегментам пути.

Классификация пути должна работать как дерево:

```text
Catalogs
  {ownerName}.xml
  {ownerName}
    Forms
      {itemName}.xml
      {itemName}
        Ext
          Form.xml
          Form
            Module.bsl
```

Для пути:

```text
Catalogs/Контрагенты/Forms/ФормаЭлемента/Ext/Form/Module.bsl
```

механизм должен проверять только ветку `Catalogs`, затем последовательно сегменты `Контрагенты`, `Forms`, `ФормаЭлемента`, `Ext`, `Form`, `Module.bsl`. Он не должен проверять маршруты `Documents`, `Reports`, `CommonForms` и других верхнеуровневых каталогов.

## Поведение

### Подготовка правил структуры XML-выгрузки

На входе — декларативные правила import из `rules.ts`.

На выходе — структура, которая поддерживает:

- статический сегмент: `Catalogs`, `Forms`, `Ext`;
- параметрический сегмент: `{ownerName}`, `{itemName}`;
- остаточный сегмент: `{relativePath...}`;
- рекурсивное вложение, например вложенные подсистемы;
- несколько совпадений одного пути, когда это допустимо для внешних файлов одного задания;
- игнорируемые пути;
- конфликтные совпадения, которые должны давать ту же ошибку, что и текущая реализация.

Подготовка выполняется один раз на запуск discovery и не зависит от числа файлов XML-выгрузки.

### Поиск XML-файлов выгрузки

Обход каталога должен быть параллельным с ограниченным числом одновременных `readdir`, как в validation. Этап возвращает только относительные пути обычных файлов. Содержимое файлов не читается.

### Формирование и распределение заданий импорта

Для каждого найденного пути:

1. путь классифицируется по `Правила структуры XML-выгрузки`;
2. результат классификации превращается в описание XML-файла выгрузки, описание внешнего файла XML-выгрузки или игнорируемый путь;
3. неизвестные пути остаются допустимыми только если они не описаны правилами и не конфликтуют с маршрутом;
4. внешние файлы привязываются к заданию будущего YAML-файла;
5. XML-файлы metadata-модели группируются по целевому YAML-файлу;
6. задания статически распределяются между worker по кругу.

Результат должен быть побайтно эквивалентен текущему discovery по данным `ImportAssignment`: порядок заданий, `targetProjectPath`, `xmlFiles`, `externalFiles`, `owner`, `logicalAddress`.

## Производительность и память

Целевой эффект на ERP:

- число проверяемых правил на путь должно зависеть от ветки XML-структуры, а не от общего числа import-правил;
- полный этап discovery должен приблизиться к времени обхода файлов плюс классификация по малым группам;
- подготовленная структура правил должна иметь размер порядка числа правил, а не числа файлов;
- discovery не должен хранить промежуточные совпадения для всех файлов, кроме итоговых групп заданий и списка внешних файлов, которые уже нужны операции.

## Совместимость

Внешний API `discoverXmlImport` должен сохранить поведение.

Переход можно делать под существующими тестами:

- сначала добавить новый классификатор и parity-тесты со старым алгоритмом на искусственных путях;
- затем переключить `discoverXmlImport`;
- после переключения удалить полный перебор из горячего пути, но оставить тесты на реальные маршруты.

## Проверка

Минимальные проверки:

- unit-тесты статических, параметрических и остаточных сегментов;
- тест рекурсивных подсистем;
- тест конфликтных маршрутов;
- тест внешних файлов, которые дают несколько допустимых совпадений одного assignment;
- существующий `metadata/importFromXml/discovery.test.ts`;
- профиль ERP discovery до запуска worker-проходов.

Критерий успеха: discovery ERP больше не выполняет десятки миллионов проверок маршрутов и заметно быстрее текущих ~100 секунд на том же каталоге.

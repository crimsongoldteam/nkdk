# ConfigDumpInfo UUID Store Design

## Цель

Исправить генерацию `ConfigDumpInfo.xml` при YAML -> XML sync: для новых metadata-объектов и их управляемых дочерних элементов `id` в `ConfigDumpInfo` должен совпадать с UUID, записанным в XML объекта.

## Контекст

Сейчас `ConfigDumpInfo` строится отдельным шагом после успешного экспорта объектов. Для существующих объектов данные берутся из reference `ConfigDumpInfo.xml`, а для новых `buildConfigDumpInfo` генерирует отдельные UUID. Из-за этого UUID в XML объекта и `id` в `ConfigDumpInfo.xml` расходятся.

В контексте экспорта уже есть хранилище `context.exportToXML.configDumpInfo`, но оно фактически не используется как источник UUID для итогового `ConfigDumpInfo`.

## Решения

- Использовать один механизм сбора UUID: накопитель, который заполняет существующее хранилище `context.exportToXML.configDumpInfo`.
- Не добавлять параллельные карты UUID и не перечитывать записанный XML ради сбора UUID.
- Описывать участие metadata item во внешнем реестре через нейтральное поле правила `externalMetadata`, а не через отдельную таблицу внутри `configDumpInfo`.
- Универсальный код `orchestration` не должен импортировать `configDumpInfo` и напрямую менять его Map; доступ к накопителю идёт через нейтральный договор в export-контексте.
- Для существующих и переименованных объектов приоритет остаётся у reference `ConfigDumpInfo.xml`.
- Для новых управляемых узлов UUID должен попадать в накопитель в момент экспорта XML и затем оказываться в `context.exportToXML.configDumpInfo`.
- `buildConfigDumpInfo` не должен генерировать `id` для нового управляемого узла, если этот UUID отсутствует в хранилище; отсутствие считается ошибкой.
- `configVersion` не собирается во время UUID-экспорта: для reference-записей он переносится из reference, для новых верхнеуровневых записей генерируется в `buildConfigDumpInfo`.
- Записи без собственного UUID, например `ObjectModule`, `ManagerModule`, `CommandModule`, `Form.Форма.Form` и `Form.Форма.Help`, создаются как производные записи: `id = базовый UUID + "." + свободный номер`.

## Типы записей ConfigDumpInfo

В `ConfigDumpInfo.xml` есть два разных типа `id`, и их нельзя обрабатывать одинаково.

### Записи с собственным UUID

Это metadata-элементы, у которых в XML есть собственный UUID. Их `id` в `ConfigDumpInfo` должен совпадать с UUID, который записан в XML.

Примеры:

- `Catalog.Номенклатура`
- `Catalog.Номенклатура.Attribute.Артикул`
- `Catalog.Номенклатура.TabularSection.Товары`
- `AccumulationRegister.Остатки.Dimension.Номенклатура`
- `Report.Отчет.Command.Сформировать`
- `Document.Заказ.Form.ФормаДокумента`

Такие записи регистрируются в хранилище в момент экспорта свойства `uuid`. Источником состава является не отдельный список сегментов, а сам экспортируемый metadata-элемент с правилом `uuid` и `externalMetadata`.

### Производные записи

Это записи для файлов выгрузки или внутренних частей, у которых нет собственного UUID в YAML-модели и нет отдельного UUID-свойства в XML. Их `id` строится от UUID ближайшего metadata-владельца.

Примеры:

- `Document.Заказ.ObjectModule`
- `Document.Заказ.ManagerModule`
- `Catalog.Номенклатура.Help`
- `Report.Отчет.Command.Сформировать.CommandModule`
- `Document.Заказ.Form.ФормаДокумента.Form`
- `Document.Заказ.Form.ФормаДокумента.Help`

Для этих записей не генерируется новый UUID. Вместо этого экспорт внешнего файла регистрирует производную запись с базовым внешним именем владельца. Итоговый `id` формируется как `baseId + "." + suffix`, где `suffix` — выбранный свободный номер.

## Нумерация производных записей

Постфиксы производных записей назначаются локально для каждого базового UUID.

1. Сначала собираются уже занятые числовые постфиксы из reference `ConfigDumpInfo.xml`.
2. Существующие производные записи из reference сохраняют свои `id` и `configVersion`.
3. Для новой производной записи выбирается минимальный свободный номер: `0`, затем `1`, затем `2` и так далее.
4. Новые номера не пытаются повторять каноничные номера 1С по типам объектов. Для нас достаточно стабильной уникальности с учётом reference.
5. Порядок назначения новых номеров определяется порядком регистрации производных записей во время экспорта.

Пример для нового документа без reference:

```text
Document.Заказ = 11111111-1111-4111-8111-111111111111
Document.Заказ.ObjectModule = 11111111-1111-4111-8111-111111111111.0
Document.Заказ.Help = 11111111-1111-4111-8111-111111111111.1
Document.Заказ.ManagerModule = 11111111-1111-4111-8111-111111111111.2
```

Пример для новой формы:

```text
Document.Заказ.Form.ФормаДокумента = 22222222-2222-4222-8222-222222222222
Document.Заказ.Form.ФормаДокумента.Form = 22222222-2222-4222-8222-222222222222.0
Document.Заказ.Form.ФормаДокумента.Help = 22222222-2222-4222-8222-222222222222.1
```

## Хранилище

Внутреннее хранилище остаётся текущего типа `ConfigDumpInfo`:

```ts
Map<
  string,
  {
    id: string
    configVersion: string
    children: Map<string, string>
  }
>
```

Ключи хранятся сразу в dumpinfo-формате, например `Catalog.Номенклатура` и `Catalog.Номенклатура.Attribute.Артикул`. Корневой UUID пишется в `entry.id`, UUID дочерних элементов пишутся в `entry.children`.

Форму этой Map знают только слой `configDumpInfo` и нейтральный накопитель, установленный в export-контекст. Общий экспорт metadata item не должен обращаться к Map напрямую.

Для новых записей `configVersion` в хранилище можно оставлять пустой строкой. Финальное значение задаёт построитель `ConfigDumpInfo`.

## Внешние metadata-записи в правилах

Чтобы сохранить общий подход проекта, `orchestration` не должен знать про `ConfigDumpInfo.xml`. Конкретные metadata item описывают свой внешний сегмент в `rules.ts` через нейтральное поле `externalMetadata`.

Форма поля:

```ts
externalMetadata?: {
  segment: string
  placement: "rootEntry" | "ownerChild" | "ownedEntry"
}
```

Семантика:

- `rootEntry` — верхнеуровневый metadata object с собственной записью и `configVersion`;
- `ownerChild` — дочерний metadata item, который пишется внутрь `children` ближайшего владельца;
- `ownedEntry` — отдельная верхнеуровневая запись с именем внутри владельца, например форма или макет.

Примеры:

```ts
// Справочник.Номенклатура -> Catalog.Номенклатура
externalMetadata: { segment: "Catalog", placement: "rootEntry" }

// Справочник.Номенклатура.Реквизит.Артикул -> Catalog.Номенклатура.Attribute.Артикул
externalMetadata: { segment: "Attribute", placement: "ownerChild" }

// Справочник.Номенклатура.Форма.ФормаЭлемента -> Catalog.Номенклатура.Form.ФормаЭлемента
externalMetadata: { segment: "Form", placement: "ownedEntry" }
```

`orchestration` использует это поле только как общий договор: у текущего item есть внешний сегмент, способ размещения и итоговый UUID. Он не знает, что потребитель этих данных — `ConfigDumpInfo`.

Регистрация проходит через нейтральный накопитель в export-контексте:

```ts
externalMetadataCollector.recordUuid({
  segment: "Attribute",
  placement: "ownerChild",
  uuid,
  name: "Артикул",
})
```

Этот накопитель является адаптером: наружу он выглядит как общий договор, внутри пишет в существующее `context.exportToXML.configDumpInfo`.

Слой `configDumpInfo` интерпретирует накопленные записи:

- `rootEntry` и `ownedEntry` становятся отдельными верхнеуровневыми entries;
- `ownerChild` становится записью в `children` владельца;
- отсутствие `externalMetadata` означает, что item не создаёт запись `ConfigDumpInfo`, даже если внутри него есть технический UUID для других целей.

Производные записи без собственного UUID (`ObjectModule`, `ManagerModule`, `CommandModule`, `Form.Форма.Form`, `Form.Форма.Help`) не описываются как metadata item с `externalMetadata`. Их регистрируют внешние sync-обработчики в момент фактической записи файла через тот же нейтральный накопитель, указывая внешнее имя записи и внешнее имя базового владельца.

## Архитектура

Нужен небольшой служебный слой вокруг текущего `uuid`-экспорта, а не новый сборщик:

1. Перед экспортом объекта sync-код знает текущий объект, его migration path и reference path.
2. Во время экспорта свойства `uuid` определяется итоговый UUID: значение модели, reference XML или новый UUID.
3. Если правило текущего metadata item содержит `externalMetadata`, этот же итоговый UUID передаётся в нейтральный накопитель по внешнему имени текущего объекта или дочернего элемента.
4. Когда экспорт пишет внешний файл, который должен иметь запись в `ConfigDumpInfo`, он регистрирует производную запись в нейтральном накопителе по внешнему имени файла и внешнему имени базового владельца.
5. После экспорта всех объектов `syncConfigDumpInfoToXML` получает уже заполненное хранилище и передаёт его в `buildConfigDumpInfo`.
6. `buildConfigDumpInfo` совмещает reference `ConfigDumpInfo`, migration remap, накопленные UUID и производные записи, затем формирует итоговую карту для записи XML.

## Адресация

Для записи UUID нужно определить, относится текущее свойство `uuid` к корневому объекту или к дочернему управляемому элементу.

Корневой объект определяется через текущий metadata item в `itemsTree` и правило верхнего объекта. Дочерний элемент определяется через текущий `metadataItem`, его правило и ближайший владелец в `itemsTree`.

Поддерживаемые управляемые дочерние элементы не должны задаваться вторым независимым списком. Базовое правило: если элемент экспортируется как metadata item, у его правила есть `uuid` и `externalMetadata`, он может быть зарегистрирован как запись с собственным UUID.

Первый этап должен покрыть уже встречающиеся в `ConfigDumpInfo` управляемые сегменты, которые пишет текущий экспорт:

- `Attribute`
- `AddressingAttribute`
- `TabularSection`
- `Dimension`
- `Resource`
- `Command`
- `EnumValue`

Формы, шаблоны и команды нужно разделять:

- сама форма, шаблон или команда имеет собственный UUID и регистрируется как запись с собственным UUID, если экспорт реально создаёт её XML;
- файл формы, файл шаблона, справка формы и модуль команды регистрируются как производные записи;
- записи, существующие только в reference и не создаваемые текущим экспортом, продолжают переноситься из reference для живого владельца.

## Поток Данных

Для существующего объекта:

1. Reference XML даёт UUID при экспорте объекта.
2. UUID записывается в XML.
3. Этот же UUID передаётся в накопитель через тот же механизм, что и UUID новых объектов.
4. `buildConfigDumpInfo` всё равно выбирает reference `ConfigDumpInfo` как приоритетный источник `id` и `configVersion`.

Для нового объекта:

1. Reference-записи нет.
2. `uuid`-экспорт генерирует новый UUID.
3. Новый UUID записывается в XML и передаётся в накопитель.
4. Экспорт внешних файлов нового объекта регистрирует производные записи.
5. `buildConfigDumpInfo` берёт `id` из хранилища, назначает свободные постфиксы производным записям и генерирует новый `configVersion` для новых верхнеуровневых записей.

Для переименованного объекта:

1. Migration remap связывает текущий путь с reference-путём.
2. UUID и `configVersion` берутся из reference `ConfigDumpInfo`.
3. Имя записи и имена managed-children меняются на текущие dumpinfo-имена.
4. Производные reference-записи живого владельца переименовываются вместе с владельцем и сохраняют свои `id`.

Для новой производной записи у существующего объекта:

1. Базовый UUID берётся из reference или из накопленного UUID-хранилища.
2. Занятые постфиксы собираются из reference и уже зарегистрированных производных записей.
3. Назначается минимальный свободный постфикс.
4. `configVersion` генерируется как для новой верхнеуровневой записи.

## Ошибки

Если `yamlState` содержит новый управляемый узел, для которого нет reference-записи и нет UUID в `context.exportToXML.configDumpInfo`, sync должен завершиться ошибкой `configDumpInfo`. Это защищает от скрытой повторной генерации UUID и от рассинхронизации XML с `ConfigDumpInfo`.

Если UUID нельзя адресовать во внешнее имя, механизм не должен молча писать некорректную запись. Для неподдерживаемых managed-сегментов ошибка должна быть явной.

Если производная запись зарегистрирована без базовой записи или базовый `id` не найден ни в reference, ни в накопленном хранилище, sync должен завершиться ошибкой `configDumpInfo`.

## Тестирование

Нужны проверки на двух уровнях:

- Юнит-тест `buildConfigDumpInfo`: новый объект и новый реквизит получают `id` из переданного хранилища, а не из собственного генератора.
- Юнит-тест `buildConfigDumpInfo`: новый управляемый узел без UUID в хранилище падает с понятной ошибкой.
- Интеграционный тест `syncConfigurationToXML`: новый справочник с реквизитом получает одинаковые UUID в объектном XML и `ConfigDumpInfo.xml`.
- Интеграционный тест `syncConfigurationToXML`: переименование продолжает переносить `id/configVersion` из reference `ConfigDumpInfo`.
- Юнит-тест для производных записей: новая производная запись получает минимальный свободный постфикс с учётом reference.
- Юнит-тест для производных записей: существующая производная запись из reference не перенумеровывается.
- При необходимости отдельный тест для табличной части, измерения или ресурса, чтобы покрыть не только обычный реквизит.
- При необходимости интеграционный тест для `CommandModule`, `ObjectModule` или `Form.Форма.Form`, чтобы проверить регистрацию производной записи из факта записи внешнего файла.

Перед закрытием задачи нужно запустить focused-тесты по `configDumpInfo` и `syncConfigurationToXML`, затем общий `pnpm test`.

## Вне Границ

- Не хранить UUID в YAML-модели.
- Не менять XML-фикстуры как источник истины.
- Не добавлять второй постоянный формат для UUID-сбора.
- Не пытаться восстановить каноничную таблицу постфиксов 1С по типам объектов.
- Не генерировать производные записи для файлов, которые текущий XML-экспорт фактически не пишет.

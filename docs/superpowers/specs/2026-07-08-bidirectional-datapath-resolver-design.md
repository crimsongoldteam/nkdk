# Дизайн: общий двусторонний resolver DataPath

## Контекст

Round-trip `small` снова показал изменение:

```diff
- <DataPath>Список.Код</DataPath>
+ <DataPath>Список.Code</DataPath>
```

Причина не в слове `Code` само по себе. Проблема в текущей логике `dataPathStandardMembers.ts`: она пытается переводить стандартные реквизиты по эвристике первого сегмента `Объект` / `Запись` / `Список`.

Так делать нельзя. Эти имена произвольные. Первый сегмент DataPath должен получать смысл только через реквизиты формы и их типы.

Валидация уже имеет resolver DataPath, который строит индекс реквизитов формы, идёт по типам и умеет различать реквизиты формы, таблицы, колонки, объектные поля и стандартные реквизиты. Но сейчас этот resolver используется в validation/operations, а обычный XML -> YAML -> XML round-trip идёт через отдельную упрощённую логику.

## Цель

Сделать один общий двусторонний resolver DataPath, который будет общей частью для:

- валидатора;
- преобразования XML -> YAML;
- преобразования YAML -> XML;
- операций rename/delete, которые уже ищут ссылки через DataPath.

Resolver должен одновременно уметь валидировать путь и, когда это безопасно, преобразовывать имена стандартных реквизитов между internal/XML- и YAML-представлениями.

## Общий договор

Ввод:

- исходный DataPath;
- направление имён: internal -> YAML или YAML -> internal;
- индекс реквизитов формы;
- доступ к метаданным владельцев;
- список/индекс известных metadata paths и зарегистрированных стандартных реквизитов;
- опциональный табличный контекст для колонок.

Вывод:

- статус разрешения пути;
- исходный путь;
- преобразованный путь, если есть безопасные замены;
- целевой объект/поле последнего разрешённого сегмента;
- список замен сегментов с причиной;
- машинно-читаемые причины неразрешённости для validation-обёртки.

Пример результата для YAML -> XML:

```ts
{
  ok: true,
  value: "Объект.Товары.Код",
  formattedValue: "Объект.Товары.Code",
  replacements: [
    { segmentIndex: 2, from: "Код", to: "Code", reason: "standardMember" },
  ],
}
```

## Правила разрешения

Resolver идёт по DataPath на любую глубину.

На каждом шаге он определяет смысл текущего сегмента через предыдущий тип:

- корень формы;
- реквизит формы;
- колонка таблицы значений или дерева значений;
- поле динамического списка;
- поле объекта метаданных;
- стандартный реквизит объекта метаданных;
- виртуальное поле;
- платформенный источник;
- неизвестный сегмент.

Имя сегмента само по себе не задаёт смысл. `Объект`, `Запись`, `Список` и любые другие имена равноправны: сначала ищется реквизит формы или текущий owner, затем используется его тип.

## Двусторонние имена

Resolver должен понимать стандартные реквизиты в обоих представлениях:

- internal/XML: `Code`, `Description`, `Ref`;
- YAML: `Код`, `Наименование`, `Ссылка`.

Если сегмент является стандартным реквизитом owner-а, resolver возвращает оба имени и разрешает форматтеру заменить сегмент в нужную сторону.

Если сегмент является колонкой таблицы, полем динамического списка, обычным реквизитом формы или неизвестным полем, замена стандартного реквизита запрещена.

## Поведение на примерах

`Список.Код`, где `Список` — реквизит формы типа `ТаблицаЗначений`:

- `Список` разрешается как реквизит формы;
- `Код` разрешается как колонка таблицы;
- замены нет;
- XML остаётся `Список.Код`.

`Объект.Код`, где `Объект` — реквизит формы типа ссылки на справочник:

- `Объект` разрешается как реквизит формы;
- тип ведёт к owner справочника;
- `Код` / `Code` разрешается как стандартный реквизит owner-а;
- в направлении YAML -> XML выполняется `Код -> Code`;
- в направлении XML -> YAML выполняется `Code -> Код`.

`Объект.Товары.Номенклатура.Код`:

- resolver идёт по всей цепочке;
- если `Номенклатура` ведёт к owner справочника и последний сегмент является стандартным реквизитом, меняется только последний сегмент;
- если на любом шаге путь уходит в таблицу без известных колонок, dynamic list или неизвестный тип, round-trip не делает замену.

## Потребители

### Валидация

Валидация остаётся местом, где появляются `filePath`, `ParsedYaml`, `yamlPath` и diagnostics.

Текущий validation resolver должен стать обёрткой над общей частью:

1. вызывает общий resolver;
2. получает машинно-читаемый результат;
3. превращает ошибки/предупреждения в diagnostics с YAML-позициями.

### XML -> YAML

Экспорт DataPath вызывает общий resolver в направлении internal -> YAML.

Если resolver уверенно нашёл стандартный реквизит owner-а, форматтер заменяет только соответствующий сегмент.

Если путь не разрешён уверенно, значение остаётся без изменений.

### YAML -> XML

Импорт DataPath вызывает общий resolver в направлении YAML -> internal.

Если resolver уверенно нашёл стандартный реквизит owner-а, форматтер заменяет только соответствующий сегмент.

Если путь не разрешён уверенно, значение остаётся без изменений.

### Rename/Delete

Операции rename/delete продолжают использовать DataPath resolver для поиска ссылок, но должны опираться на тот же общий результат разрешения, что и validation/import/export.

## Поведение при неуверенности

Для round-trip:

- неразрешённый путь не является ошибкой преобразования;
- значение возвращается как было;
- лучше не сократить алиас, чем испортить XML.

Для validation:

- та же причина превращается в warning или error с YAML-позицией;
- уровень severity остаётся ответственностью validation-обёртки.

## Что убираем

Нужно убрать из `dataPathStandardMembers.ts` семантику имён:

```ts
new Set(["Объект", "Запись", "Список"])
```

и любые будущие исключения по именам корней.

## Не цели

- Не включать validation как обязательный шаг `nkdk sync`.
- Не делать преобразование, если не хватает контекста формы или метаданных.
- Не угадывать тип по имени первого сегмента.
- Не заводить отдельные resolver-ы для XML и YAML.

## Тестирование

Нужно покрыть:

- `Список.Код` для `ТаблицаЗначений` не меняется в обе стороны;
- dynamic list fields не меняются в обе стороны;
- object/ref root со стандартным реквизитом меняется в обе стороны;
- глубокий путь меняет только разрешённый стандартный сегмент;
- неизвестный путь не меняется при round-trip-преобразовании;
- validation продолжает выдавать diagnostics с YAML-позициями;
- round-trip-yaml `small` больше не меняет `Список.Код` в `Список.Code`.

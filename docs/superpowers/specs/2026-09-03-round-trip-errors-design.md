# Ошибки пакетного round-trip: согласованные решения

Спецификация дополняется по мере согласования отдельных групп ошибок.
Реализация начинается после согласования всей спецификации.

Источник диагностики: `/Users/nikita/git/round-trip-reports/2026-09-02_20-48-46-530Z.md`
и соседний каталог журналов `2026-09-02_20-48-46-530Z.logs`.
Прогон выполнен на коде `c0cbf9bd0de92a32993a29419d8d8ca8d28f66ae`:
34 конфигурации, 8 без расхождений, 25 ошибок импорта, 1 ошибка экспорта.

## 1. Справка общих команд — согласовано

### Причина

Импорт останавливается с `xml_import_route_unmatched` на файлах
`CommonCommands/<Имя>/Ext/Help.xml`. В `MetadataCommonCommandRules` отсутствует
подключение существующего механизма `helpRule`, используемого, например,
общими формами.

Затронутые конфигурации: ARAutomation, Mhcsk, zpl50, zpl55cb.

### Решение

Подключить `helpRule` в
`packages/rules/metadata/appliedObjects/metadataCommonCommand/rules.ts`
по существующему договору внешней справки:

- `externalMetadata: { segment: "Help", placement: "derivedEntry" }`;
- `filePath` и `xmlPath`: `Ext/Help.xml`;
- `nkdkDir`: `Справка`;
- `toXML: false`, `fromXML: false`, как у существующих подключений
  внешнего ресурса справки.

Использовать существующий механизм импорта и экспорта списка языков и
HTML-страниц справки. Не добавлять новый обработчик преобразования или
исключительный тег `!xml`. Отсутствие справки у команды допустимо и не должно
создавать пустые файлы справки при экспорте.

### Проверка

- Расширить существующие проверки обнаружения ресурсов: `Help.xml` общей
  команды распознаётся как входной XML свойства, страницы справки попадают
  в `ОбщаяКоманда/<Имя>/Справка`.
- Проверить полный XML → YAML → XML для общей команды со справкой и команды
  без справки. Справка и остальные файлы команд должны сохраняться без
  расхождений.
- Использовать предоставленную конфигурацию непосредственно в
  `e2e/fixtures/xml/cf` этой рабочей ветки, без отдельной копии исходника.
  Пользовательскую выгрузку не откатывать. Если запуск требует чистого
  XML-каталога, сначала отдельно согласовать сохранение исходных изменений;
  не очищать их автоматически.
- Нормализация выгрузки ограничена заменой CRLF на LF в текстовых файлах.
  Двоичные файлы, включая `.bin`, ZIP и PNG, сохраняются побайтно.

Устранение ошибки маршрута не гарантирует отсутствие других ошибок в четырёх
полных конфигурациях. Критерий этой правки — корректный round-trip справки
общей команды, а не подавление последующих диагностик.

## 2. Поле рисунка внутри контекстного меню — согласовано

### Причина

В BMO, SettlementBudget, StateAccounting и UniformAllowances импорт
останавливается на элементе `ЕстьФайлы` с сообщением
`неизвестный Вид "ПолеРисунка"`. Сам вид поддерживается, но в исходной форме
документа `РегистрУчета` узел `PictureField` находится в недопустимом
контейнере `ContextMenu/ChildItems`.

### Решение

Сохранять весь недопустимый узел `<PictureField …>…</PictureField>` как
локальный raw-фрагмент через существующий механизм `!xml`, включая атрибуты
и дочернее содержимое. Применение XML-исключения для этого случая явно
согласовано пользователем.

Граница raw — только этот узел. Не оборачивать целиком `ContextMenu`,
`ChildItems` или форму. Остальные допустимые элементы продолжают
представляться обычным YAML. При экспорте возвращать фрагмент в исходное
место с сохранением порядка относительно соседей.

Не расширять список допустимых элементов контекстного меню и не превращать
ошибочное размещение в допустимую смысловую модель. Сохранять диагностику
аномалии без остановки импорта из-за данного узла. Это согласование не
распространяется автоматически на другие виды XML-исключений.

### Проверка

- Импорт формы с `PictureField` внутри `ContextMenu/ChildItems` завершается,
  сохраняя локальное XML-исключение и диагностику.
- XML → YAML → XML сохраняет атрибуты и содержимое узла, его расположение и
  порядок относительно допустимых соседей.
- Допустимые соседи не попадают в raw. Поле рисунка в разрешённом контейнере
  по-прежнему обрабатывается обычными правилами.

## 3. Повторяющиеся исходные ID элементов — согласовано

### Причина

В AccountingGC, AccountingGP, AccountingNPOCorp и acc импорт останавливается
на повторном ID `523` в форме списка справочника `КлассификаторСтранСАТУРН`.
В исходном XML разные элементы `Идентификатор` и `ЕАЭС` имеют ID `523`;
у их контекстных меню повторяется `524`, у подсказок — `525`.

### Решение

Исходные XML ID уже хранятся в снимке для соответствующих логических
адресов. Сохранять их без перенумерации, в том числе когда одинаковый ID
принадлежит разным исходным элементам. Восстановление таких значений из
снимка не должно останавливать импорт или экспорт из-за самого факта дубля.
Не переносить ID в YAML и не добавлять raw для этой ситуации: элементы
с разными именами остаются обычными элементами смысловой модели.
Не добавлять в YAML теги аномалий, комментарии или другие отметки о дублях
исходных ID. Сведения об ID остаются в снимке; их повторение само по себе
не меняет YAML-представление элемента.

Разделить сохранение исходных ID и генерацию новых:

- исходные значения сохраняются за своими элементами, включая дубли;
- все исходные значения считаются занятыми в соответствующем пространстве
  ID при генерации;
- новому элементу без сохранённого ID назначается свободное значение,
  не совпадающее ни с исходными, ни с уже сгенерированными ID;
- конфликты разных ID у одного логического адреса не приравниваются к
  разрешённым дублям ID у разных адресов.

### Проверка

- XML → YAML → XML сохраняет повторяющиеся `523`, `524` и `525` у исходных
  элементов, их меню и подсказок без ошибки и без перенумерации.
- YAML не содержит ID или отметок об их повторении.
- Добавление новых элементов к форме с такими дублями не создаёт новых
  коллизий: генератор пропускает занятые значения.
- Несколько новых элементов получают различные ID; последующий экспорт
  сохраняет уже назначенные значения из снимка.

## 4. Повторяющиеся имена элементов формы — согласовано

### Причина

В конфигурации `small` в одной форме повторяются кнопки `ЕстьКЭП` и
`НетКЭП`. У одинаково названных кнопок разные ID, но имя образует один
ключ YAML и один логический адрес. Импорт останавливается на конфликте
идентичности; простая запись в словарь по имени также потеряла бы один узел.
Это отдельный случай, не покрываемый сохранением одинаковых ID у элементов
с разными именами.

### Решение

Первое вхождение имени в исходном XML-порядке распознавать обычными
правилами и сохранять как смысловой элемент YAML с обычным ключом.
Повторные вхождения сохранять целиком как локальные raw-узлы, включая
исходные имена, ID, атрибуты и дочернее содержимое. Не подменять первое
вхождение последним и не объединять свойства разных узлов.

Использовать существующий механизм аннотированных повторных ключей:

- первое вхождение: обычный ключ `ЕстьКЭП` и обычное значение;
- второе: ключ `!xml/invalid ЕстьКЭП`, значение с тегом `!xml/raw`;
- третье: ключ `!xml/invalid/2 ЕстьКЭП`, значение с тегом `!xml/raw`;
- дальнейшие повторы: продолжение существующей нумерации тегов ключа.

Применение `!xml/invalid` и `!xml/raw` к повторным вхождениям явно
согласовано пользователем. Не добавлять суффиксы к самим именам и не
выводить внутренние служебные ключи механизма аннотаций в YAML.
Обычным логическим адресом владеет первое распознанное вхождение;
повторные raw-узлы не перезаписывают его запись в снимке.

Граница raw — отдельный повторный узел, не вся коллекция или форма.
При экспорте восстановить все вхождения на прежних местах с исходными
именами и ID, сохранив порядок относительно остальных элементов.
Разрешение не распространяется на автоматическое переименование или
удаление дублирующихся элементов.

### Проверка

- Для двух одноимённых кнопок первая остаётся обычным YAML, вторая получает
  аннотированный ключ и raw; разные ID не вызывают конфликт снимка.
- Третье вхождение получает `!xml/invalid/2`; все повторные ключи переживают
  сериализацию и повторное чтение YAML без потерь и служебных имён.
- XML → YAML → XML сохраняет все узлы, включая дочерние подсказки,
  исходные имена, ID и порядок, в том числе при наличии других элементов
  между повторными вхождениями.
- Изменение смыслового свойства первой кнопки не изменяет сохранённые
  raw-вхождения с тем же именем.

## 5. Явные ограничения памяти рабочих потоков — согласовано

### Причина

Импорт GMZ и PayDesk завершился с сообщением
`Worker terminated due to reaching memory limit: JS heap out of memory`.
Журналы не содержат значения достигнутого лимита и не определяют причину
роста памяти.

В коде установлены два явных ограничения `maxOldGenerationSizeMb`:

- 512 МБ для отдельного пула XML-import в
  `packages/rules/metadata/importFromXml/workerPool.ts`;
- 768 МБ для общего пула metadata-операций в
  `packages/rules/metadata/workerPool/handle.ts`, используемого обычным
  MCP-путём импорта.

### Решение

Удалить оба явно заданных ограничения памяти при создании рабочих потоков.
Не заменять их увеличенными значениями, новыми настройками или другим
принудительным ограничением размера кучи. Удалить ставшие неверными
комментарии о принудительно ограниченной куче.

Это отменяет ограничения, введённые проектом, но не гарантирует неограниченную
память: действуют штатные ограничения Node.js, операционной системы и среды
запуска. Автоматический выбор числа рабочих потоков и прочие настройки
параллелизма этой правкой не изменяются.

### Проверка

- Обновить существующую проверку настройки отдельного пула, которая сейчас
  требует лимит 512 МБ: опции создания потока больше не задают этот лимит.
  Проверить отсутствие явного ограничения также у общего пула.
- Повторить импорт GMZ и PayDesk после реализации согласованных исправлений,
  сохранив результат и диагностику. Если ошибка памяти останется, не считать
  её устранённой и отдельно исследовать причину потребления памяти.

## 6. Значения ent:ComparisonType — согласовано

### Причина

В StateHRMCorp импорт формы `ФормаНастройкиОтбора` справочника
`РассылкиУведомлений` останавливается на
`MetadataValue: не распознан тип: ent:ComparisonType`.
Список выбора содержит значения `Equal`, `NotEqual`, `InList`, `NotInList`.
Перечисление `ComparisonType` и таблицы его русских наименований уже
существуют, но этот тип не поддерживается как значение `MetadataValue`.

### Решение

Добавить обычную поддержку `ComparisonType` в `MetadataValue`, используя
существующие таблицы `ComparisonTypeToYAML` и `ComparisonTypeFromYAML`.
Не заменять его строкой, другим перечислением или raw-фрагментом.

Для значения в списке выбора использовать явное типизированное
YAML-представление по существующему образцу типизированных перечислений:

```yaml
Тип: ВидСравнения
Значение: Равно
```

Это представление относится к самому значению пункта списка выбора;
существующая оболочка пункта и его представление сохраняются.
При экспорте восстанавливать `xsi:type="ent:ComparisonType"` и исходное
значение перечисления, например `Equal`.

Сохранять различие между `ComparisonType`, `DataCompositionComparisonType`
и обычной строкой с тем же текстом. Явный тип `ВидСравнения` не должен
превращаться в `ВидСравненияКомпоновкиДанных` или определяться только по
строке `Равно`. Не расширять разрешённые типы посторонних свойств.

### Проверка

- Проверить XML → модель → YAML и обратное преобразование значений из
  исходного списка: `Equal`/`Равно`, `NotEqual`/`НеРавно`, `InList`/`ВСписке`,
  `NotInList`/`НеВСписке`.
- Проверить различение строки `Равно` и двух перечислений со значением
  `Равно`, включая восстановление соответствующих XML-типов.
- Проверить round-trip списка выбора из проблемной формы с сохранением
  порядка пунктов, их представлений и значений без raw для этого типа.

## 7. Перерасчёты в составе плана обмена — согласовано

### Причина

В SMTL, SSLWE и SSL обратное чтение YAML состава плана обмена завершается
ошибкой `Неизвестный корень "CalculationRegister"`. В исходном составе
присутствуют как ссылки на регистры расчёта, так и вложенные ссылки вида
`CalculationRegister.<Регистр>.Recalculation.<Перерасчёт>`.
Правило `Метаданные` в `ExchangePlanContentItemRules` использует простой
договор `metadataTarget: { kind: "object" }` без разрешения такого
вложенного пути. Общий механизм разбора точных путей перерасчётов уже есть.

### Решение

Перерасчёт является допустимым участником состава плана обмена.
Уточнить правило ссылки `Метаданные` в `exchangePlanContent/rules.ts`,
разрешив путь `CalculationRegister → Recalculation` через существующие
параметры `metadataTarget`. Сохранить поддержку уже допустимых простых
ссылок на объекты; не разрешать произвольную вложенность и не ослаблять
общие правила ссылок для посторонних свойств.

Ссылка должна преобразовываться в обычное YAML-значение, например:

```yaml
Метаданные: РегистрРасчета.РегистрРасчетаВсеСвойства.Перерасчет.ПерерасчетВсеСвойства
```

При экспорте восстанавливать исходный путь с сегментами
`CalculationRegister` и `Recalculation`. Не добавлять raw или другой
XML-тег для этой допустимой ссылки. Авторегистрация и порядок элементов
состава сохраняются по существующему договору.

### Проверка

- Использовать добавленный пользователем пример
  `e2e/fixtures/xml/cf/ExchangePlans/ПланОбменаВсеСвойства/Ext/Content.xml`:
  `CalculationRegister.РегистрРасчетаВсеСвойства.Recalculation.ПерерасчетВсеСвойства`,
  `AutoRecord=Allow`.
- Расширить существующие проверки преобразования состава: ссылка на
  перерасчёт проходит XML → YAML → XML с русскими сегментами в YAML и
  исходными сегментами в XML, включая восстановление из снимка.
- Проверить совместное присутствие обычной ссылки на регистр и ссылки
  на перерасчёт, сохранение порядка и режима авторегистрации.
- Проверить, что недопустимый вложенный путь не становится разрешённым
  в результате расширения правила.

## 8. Скрипт нормализации CRLF в XML-выгрузке — запрос пользователя

Добавить небольшой отдельный скрипт на Node.js для рекурсивной замены CRLF
на LF в явно выбранном каталоге выгрузки. Он должен работать на macOS и
Windows без Bash и применяться к обновлённому `e2e/fixtures/xml/cf` перед
контрольными прогонами.

Включить использование этого же скрипта в навык `round-trip-yaml`:
описать и подключить его на этапе подготовки выбранной XML-выгрузки до
фиксации исходного состояния для сравнения. Не дублировать алгоритм
нормализации в навыке или его runner. Нормализация не отменяет проверку
несохранённых изменений и не разрешает их откат или автоматический коммит.

Изменять только текстовые файлы. Картинки, ZIP, `.bin` и прочие двоичные
файлы сохранять побайтно, даже если внутри встречается последовательность
байтов CRLF. Соблюдать объявленные в репозитории признаки двоичных файлов;
не считать файл текстовым только из-за отсутствия нулевых байтов.
Файлы с неопределённой кодировкой пропускать с сообщением, а не перекодировать
с потерями. Не менять BOM, содержимое текста или уже нормализованные LF.

Не выходить за выбранный каталог по символическим ссылкам и не обходить
служебные каталоги Git. Выводить число изменённых и пропущенных файлов.
Не выполнять Git reset, clean, staging или commit.

Проверить смешанные LF/CRLF и повторный запуск без изменений, сохранность
кириллицы и BOM, а также побайтовую неизменность двоичного файла с CRLF
внутри. Пользовательскую выгрузку не заменять тестовыми данными.

## 9. UUID-ссылки через общий механизм — согласовано

### Договор

Соблюдать ранее принятое решение из
`2026-09-02-metadata-uuid-anomaly-design.md`: UUID-ссылки на метаданные не
разрешать самостоятельно через снимок, индекс или resolver. Наличие
соответствующего объекта в проекте не меняет способ их представления.
Предложение преобразовывать разрешимые UUID в имена ролей отклонено.

Любая UUID-ссылка предусмотренной договором формы сохраняется дословно
через `!xml/uuid`, в том числе на ключе `Роли`. Это относится к одиночному
UUID и составному `UUID.UUID`; регистр символов и исходный текст сохраняются.
Смысловые ссылки, уже записанные именами, продолжают обрабатываться обычными
правилами. Собственные ID/UUID объектов в снимке и обычные строки вне
metadata-ссылок этим решением не затрагиваются.

### Решение

Использовать и при необходимости исправить интеграцию существующего общего
механизма `metadataTargetOccurrences` для скаляров, элементов списков,
вложенных значений и ключей YAML. Не создавать отдельное распознавание UUID
в `UserVisible`, правилах ролей, командном интерфейсе или конкретной форме.
Регистрации типов объявляют расположение ссылок; классификация и сохранение
UUID выполняются общим механизмом.

Сохранять точную аннотацию при передаче вложенного значения между
преобразователями, включая обратное чтение `Использование`. При экспорте
`!xml/uuid` возвращает исходную ссылку без попытки смыслового разбора и без
оборачивания родительского блока в raw. UUID-ссылка без обязательного тега
по-прежнему отклоняется; ослаблять эту проверку ради успешного импорта нельзя.

### Проверка

- UUID в ключе роли, скалярном значении и элементе списка проходит полный
  round-trip через общий механизм с сохранением точного текста.
- Результат одинаков при наличии и отсутствии объекта с таким UUID в
  снимке; поиск, разрешение и переименование UUID-ссылки не выполняются.
- Вложенные преобразования не теряют тег и его адрес перед контрольным
  экспортом; обычные смысловые ссылки сохраняют прежнее поведение.
- Проверить UUID-ссылки из отчёта в настройках видимости и командном
  интерфейсе, не подавляя независимые ошибки этих конфигураций.

Пустой ключ `name=""` не является UUID и рассматривается в пункте 10.
Расширение исходного договора `!xml/uuid` формой `1:UUID` согласовано
отдельно в пункте 11.

## 10. Пустая ссылка на роль в настройках видимости — согласовано

### Причина

В исходных формах AppealsProf, Contracts и FXDVUZ встречается
`<xr:Value name="">false</xr:Value>`. Пустое имя не является обычной
смысловой ссылкой на роль или UUID, но его необходимо сохранить при
round-trip, не останавливая импорт на разборе такой ссылки.

### Решение

Сохранять пустой ключ с аннотацией `!xml/invalid`, оставляя значение
видимости обычным YAML:

```yaml
Роли:
  !xml/invalid '': Ложь
```

Применение `!xml/invalid` к этому ключу явно согласовано пользователем.
Не заменять пустое имя именем роли или UUID, не удалять запись и не
оборачивать `Роли` либо родительский блок видимости в raw.
Остальные записи обрабатываются независимо по своим правилам, включая
общий договор `!xml/uuid` для UUID-ссылок.

При обратном чтении учитывать аннотацию именно пустого ключа и сохранять
исходное `name=""` со значением видимости. Не объявлять пустой ключ
допустимой обычной ссылкой без аннотации и не ослаблять проверки соседних
смысловых ссылок.

### Проверка

- XML → YAML → XML сохраняет пустое имя и исходное значение видимости.
- Аннотация пустого ключа переживает сериализацию, чтение YAML и вложенное
  преобразование `Использование` без ошибки разбора metadata-ссылки.
- Соседние обычные ссылки и UUID-ссылки сохраняют собственное представление;
  raw на родительском блоке не появляется.
- Пустая ссылка без `!xml/invalid` не принимается как обычная роль.

## 11. UUID-ссылки с префиксом 1: — согласовано

### Причина

В AppealsProf и Contracts свойство `ОсновнаяТаблица` динамического списка
содержит `1:93701593-5ac8-4266-b471-7e9ed35a9c3e`.
Общий классификатор UUID-ссылок распознаёт только `UUID` и `UUID.UUID`,
поэтому значение с префиксом попадает в разбор смыслового пути и вызывает
ошибку неизвестного корня.

### Решение

Расширить общий договор `!xml/uuid` формой `1:UUID`. Сохранять весь текст,
включая префикс и регистр символов UUID, без разрешения в имя через индекс
или снимок:

```yaml
ОсновнаяТаблица: !xml/uuid 1:93701593-5ac8-4266-b471-7e9ed35a9c3e
```

Изменение применяется ко всем полям, объявленным metadata-ссылками,
независимо от типа свойства или конкретного объекта: строковым свойствам
с `metadataTarget`, специализированным типам ссылок и зарегистрированным
вхождениям во вложенных значениях, списках и ключах YAML.
Не добавлять проверку имени `ОсновнаяТаблица`, отдельную ветку для
`DynamicList` или частные распознаватели в правилах отдельных объектов.
Обычные строки вне metadata-ссылок не получают тег автоматически.

Использовать общий классификатор и согласованную с ним проверку тега,
проекцию YAML и обработку ссылок при валидации/индексации. Помеченное
значение непрозрачно для смыслового разрешения и восстанавливается дословно.
Без обязательного тега такую ссылку из YAML по-прежнему не принимать.
Не расширять договор на произвольные префиксы или повреждённые UUID.
Обновить описание допустимых форм тега в документации XML-аномалий.

### Проверка

- Расширить существующие проверки общего классификатора и тега:
  `1:UUID` принимается, сохраняет регистр, не принимается без тега;
  повреждённый UUID и неподдерживаемый префикс не считаются этой формой.
- Проверить общий путь для строкового свойства с `metadataTarget`,
  специализированного типа ссылки и вхождений в списке/ключе; отсутствие
  обращения к resolver не зависит от конкретного свойства.
- Проверить round-trip `ОсновнаяТаблица` из проблемной формы с точным
  восстановлением исходного `MainTable`.
- Сохранить поведение обычных смысловых ссылок, `UUID`, `UUID.UUID` и
  строковых свойств без `metadataTarget`.

## 12. Единый договор работы со ссылками на метаданные — согласовано

### Причина

В production-объявлениях `packages/rules/metadata` найдено 119 строковых
свойств с явно заданным `metadataTarget`: 108 через `stringRule` и 11 через
`type: "string"`. По видам цели: 103 `member`, 4 `object`, 3 `dataTable`
и 9 `dataTableField`. Это не отдельная особенность `ОсновнаяТаблица`:
так объявлены ссылки на формы, нумератор, задачу, измерение адресации,
таблицы и поля характеристик.

`metadataTarget` также используется у составных и альтернативных значений:
`Picture`, `Color`, `Font`, `Border`, `UserVisible` и коллекций ссылок.
Замена всех этих типов одиночным ссылочным правилом потеряла бы их смысл.

### Решение

Унифицировать не только объявления свойств, но и инструменты, которые
обрабатывают ссылки: XML ↔ YAML, проверку связей, сбор dependency-индекса,
поиск ссылок и переименование. Источник договора — `metadataTarget` и
зарегистрированные вхождения ссылок, а не отдельные списки имён свойств
или типов в каждой операции.

- Для одиночной ссылки использовать `metadataItemLinkRule` с заданным
  `metadataTarget`. Обобщить построитель без фиксации возвращаемого типа
  на `kind: "object"`; `object` остаётся значением по умолчанию.
  Согласовать тот же принцип для `metadataItemLinksRule`, где сейчас
  возвращаемый тип также фиксирует `object`.
- Перевести строковые объявления одиночных ссылок на общий ссылочный
  построитель, сохранив ограничения, владельца, XML-форму, пустые значения
  и неявные значения каждого свойства. Не менять публичное YAML-представление
  ради замены построителя.
- Не объединять разные виды целей в неограниченную ссылку: `member`,
  `dataTable`, `dataTableField` и остальные виды сохраняют свои ограничения
  и способы смыслового разбора. Унифицируется механизм их применения,
  а не допустимые значения.
- Составные типы сохраняют свои правила и через существующий механизм
  регистрации объявляют точные ссылочные вхождения: скаляр, элемент списка,
  ключ или вложенное значение. Обычные части значения не становятся ссылками.
- Все потребители используют согласованный разбор, ограничения и адреса
  этих вхождений. Переименование меняет те же смысловые ссылки, которые
  проверяются и доступны поиску; исключения вроде `translateOnly` сохраняются,
  а не превращаются в обязательное разрешение через индекс.
- Классификацию UUID и работу с аннотациями выполнять общим механизмом по
  пунктам 9–11. UUID-ссылки сохраняются дословно с `!xml/uuid`, не разрешаются
  через индекс или снимок, не становятся зависимостями и не переименовываются.
  Это не меняет договор первого прохода импорта, собирающего только факты:
  аннотации формируются на согласованной стадии построения YAML.
- Не создавать параллельный механизм ссылок и частные обходы для
  `ОсновнаяТаблица`, ролей или другого конкретного объекта. Предметные
  регистрации остаются в concrete-модулях; нейтральный runtime не получает
  зависимостей от конкретных метаданных.

Собственные ID/UUID объектов в снимке и обычные строки без объявленного
ссылочного смысла остаются вне этого изменения. Новые применения `!xml`
за пределами уже согласованных случаев отдельно согласовываются.

### Проверка

- Проверить типизацию построителей с разными `metadataTarget`: заданный
  вид цели сохраняется, несовместимое пересечение с `object` не возникает;
  значение по умолчанию остаётся совместимым.
- Для одиночных ссылок, списков, ключей и вложенных значений проверить
  согласованность round-trip, проверки связей, dependency-индекса,
  поиска и переименования на общем наборе примеров.
- При миграции сохранить существующие ограничения корней, владельцев,
  вложенных путей и полей; недопустимые обычные ссылки не становятся допустимыми.
- Проверить `translateOnly`, пустые и неявные значения, типизированную
  XML-форму и неизменность YAML для мигрированных свойств.
- Для `UUID`, `UUID.UUID` и `1:UUID` проверить дословное сохранение и
  отсутствие разрешения, зависимостей и переименования независимо от формы
  ссылочного вхождения; обычные нессылочные значения не затрагиваются.

## 14. Порядок XML в Tester и отдельная статистика #order

### Порядок и адресация raw — согласовано

В форме `НастройкаШага_СверитьДвиженияДокумента` обработки
`СценарноеТестированиеИнтерактивныхДействий` конфигурации Tester поле
`ТаблицаДвиженийНастройкаПроверки` содержит последовательность

В `TableInputFieldRules.xmlOrder` для этих свойств задана последовательность
`EditMode`, `CellHyperlink`, `FixingInTable`, `Width`.
Это конкретное различие исходного XML и порядка, заданного правилом.

Исследование уже выполнено в ветке `codex/tester-round-trip-fixes`:
спецификация `2026-09-02-tester-round-trip-anomaly-export-design.md`
(коммит `22395995a`) фиксирует 683 табличных поля с обоими свойствами
в каталоге конфигураций; во всех `FixingInTable` предшествует `CellHyperlink`.
Коммит `680d6042b` исправляет этот порядок в `TableInputFieldRules`
и добавляет проверку экспорта без reference. Для исследованного поля Tester
не нужен публичный `#order`, компенсирующий неверное правило.

Существующая фикстура `forms/elements/inputField/__fixtures__/fullTable.xml`
имеет другой порядок; не изменять её ради нового канонического порядка.
Действительно отличающийся исходный XML по-прежнему сохраняется существующим
механизмом исключений. Не объявлять каждый сгенерированный `#order`
необходимым без проверки корректности правил.

Независимо от необходимости поправки воспроизведена ошибка её адресации:
правило называется `TableInputField`, XML-тег — `InputField`.
Поправка корня элемента с XML-именем `InputField` получает относительный
путь `InputField`, а не привязку к самому элементу `$item`.
После разрешения привязки получается `...\\InputField\\InputField`;
поправка порядка применяется к отсутствующему дочернему узлу.
На минимальном примере это воспроизводит ошибку `содержимое []`;
контрольный вариант с именем правила привязывается к `$item` и экспортируется.
Изменять публичный YAML на внутреннее имя правила как обход ошибки не следует.

Исправление адресации также уже есть: коммит `24b5c8248` использует физический
`rule.xmlTag`, если он объявлен, иначе `rule.itemType`, чтобы поправка корня
привязывалась к текущему экспортированному элементу. Применить этот общий
договор без условий по конкретному виду поля; сохранить строгую проверку
соответствия `#order` содержимому. Проверить типы, у которых `xmlTag`
отличается от `itemType`, и обычные вложенные поправки.

На момент проверки оба коммита присутствуют только в отдельной локальной
ветке `codex/tester-round-trip-fixes` и отсутствуют в текущей
`codex/round-trip-report-mb` (`HEAD 8cfe9c6c1`). Поэтому воспроизведение здесь
использует прежние порядок и адресацию. На этапе общей реализации перенести
совместимые изменения этих коммитов с тестами, а не проектировать исправления
повторно и не вливать всю соседнюю ветку автоматически. Её старый договор
UUID через `!xml/invalid` не заменяет согласованный здесь `!xml/uuid`.

После переноса проверить исчезновение лишней поправки порядка в проблемном
поле и успешное применение отдельно заданной необходимой raw-поправки
к физическому элементу, без вложенного `InputField\\InputField`.

### Колонка #order в отчёте — согласовано

Добавить отдельную числовую колонку `#order` в единственную таблицу
пакетного round-trip: значение по каждой конфигурации и сумму в строке
`Итого`. Полный и тестовый режимы используют один формат отчёта.

Считать физические объявления порядка в импортированном YAML, а не число
элементов внутри списка порядка и не число файлов. Учитывать ключ `#order`
в XML-части raw, в том числе вложенный, и raw-поправки, адресованные
непосредственно терминалу `#order`. Каждый такой узел считать один раз;
упоминания `#order` в комментариях и обычных строковых значениях не считать.
Использовать синтаксический разбор YAML, не поиск подстроки; внутренние
порядки из `rules.ts` и невидимых метаданных YAML в статистику не входят.

Статистика порядка независима от числа `!xml/raw`: одно raw может содержать
несколько поправок порядка. Ноль означает отсутствие найденных объявлений,
а недоступные данные показываются как `—`, не как ноль. Сохранять доступную
статистику успешного импорта и при последующей ошибке экспорта, как у Tester.
Не возвращать в отчёт ранее удалённые пояснения и дополнительные таблицы.

Проверить одиночный и вложенный `#order`, терминальную поправку, несколько
поправок в одном raw, кавычки у ключа, отсутствие ложного счёта строк и
комментариев, итоговую сумму и недоступную статистику.

## 15. Ограничение одиночного типа в TypeDescription — согласовано

### Причина

В конфигурации `trade`, в документе `НачислениеИСписаниеБонусныхБаллов`,
реквизит `Баллы` табличной части `Начисление` содержит два `v8:TypeSet`:
`cfg:DefinedType.ДенежнаяСуммаЛюбогоЗнака` и
`cfg:DefinedType.ДенежнаяСуммаНеотрицательная`.
Импорт читает оба типа, но проверка `allowedTypes` при обратном преобразовании
останавливает обработку: определяемый тип разрешён только как одиночный.

### Решение

Пользователь подтвердил: это смысловая аномалия исходного XML, а не повод
разрешать такое сочетание в обычном YAML. При импорте оставлять первый элемент
обычным, а каждый последующий определяемый тип помечать `!xml/invalid`,
сохраняя все элементы в исходном порядке:

```yaml
Тип:
  - ОпределяемыйТип.ДенежнаяСуммаЛюбогоЗнака
  - !xml/invalid ОпределяемыйТип.ДенежнаяСуммаНеотрицательная
```

Аномальна комбинация типов, а не каждое имя по отдельности. По согласованию
пользователя тег ставится на отдельный элемент, добавление которого нарушает
ограничение одиночного определяемого типа, а не на последовательность целиком.
В примере имена разные: это не дубли одного значения. Старый тег
`!xml/duplicate` больше не поддерживается; новый частный тег не вводить.
Номерные варианты `!xml/invalid/2` и далее нужны для различения повторных ключей
именованных коллекций, а здесь элементы различаются позицией в списке.
Не использовать `!xml/raw`, не удалять второй тип,
не раскрывать определяемые типы в примитивные и не исправлять исходные данные.

Сохранить запрет составности определяемых типов в обычном YAML и диагностику
его нарушения. Импорт должен зафиксировать аннотацию до контрольного экспорта;
контрольный и последующий обычный экспорт учитывают точную аннотацию элемента
и восстанавливают два исходных `v8:TypeSet` без ошибки `allowedTypes`.
Использовать общий механизм принятых смысловых аномалий, не исключение по имени
документа, реквизита или конфигурации. Не отключать проверки всего объекта
или остальных ограничений `TypeDescription`.

Дополнительным согласованием пользователь расширил решение на все типы,
объявленные `singleOnly`, а не только DefinedType: UUID, ХранилищеЗначения,
Характеристика и ссылки внешних источников данных с этим ограничением.
Первый элемент остаётся обычным; каждый дополнительный элемент проверяется
на совместимость с уже принятыми обычными элементами. Несовместимый элемент
получает `!xml/invalid` и не меняет принятую часть списка. Например,
`[УникальныйИдентификатор, !xml/invalid Строка]` и
`[Строка, !xml/invalid УникальныйИдентификатор, Булево]` сохраняются как есть.

Импорт, обратное преобразование и локальная проектная validation используют
одно определение несовместимых позиций из существующих объявлений singleOnly.
Диагностика относится к дополнительному элементу, не к массиву целиком.
С точной аннотацией такая аномалия принимается общим механизмом, без неё
остаётся ошибкой; лишняя аннотация по-прежнему отвергается. Публичная JSON
Schema остаётся строгой. Внутренняя схема проектной validation проверяет форму,
допустимость отдельных типов и уникальность, а составность проверяется адресно.
Другие нарушения `allowedTypes`, синтаксиса типов и повтор одинаковых значений
не получают автоматического разрешения.

### Проверка

- Импорт двух определяемых типов создаёт одну аннотацию на втором элементе
  списка `Тип`; первый элемент и список целиком остаются без тега.
  Импорт не создаёт raw и не теряет ни один тип.
- Если определяемых типов больше двух, каждый последующий элемент получает
  собственный `!xml/invalid` без номерного суффикса.
- После сериализации и повторного чтения YAML оба исходных `v8:TypeSet`
  восстанавливаются в прежнем порядке; аннотация доступна и контрольному,
  и обычному экспорту.
- Та же комбинация без `!xml/invalid` на нарушающем ограничение элементе
  отклоняется; аннотация другого свойства или соседнего значения не разрешает её.
- Одиночный определяемый тип продолжает обрабатываться обычным YAML без тега;
  допустимые составные типы сохраняют прежнее поведение.

## 16. Вторичный ENOENT после ошибки импорта — согласовано

### Причина

`mcp-round-trip.mjs` сохраняет `import-output.json` только после успешного
завершения импорта. Пакетный запуск пытается собрать статистику и после ошибки
импорта, а сборщик безусловно читает этот файл. В результате к исходной причине
добавляется вторичный `ENOENT`, не обозначающий самостоятельную проблему.

### Решение

Если импорт завершился ошибкой и файл результата не создан, сохранять исходную
ошибку импорта и её диагностику в журнале и разделе ошибок отчёта. Не пытаться
читать отсутствующий результат для статистики и не добавлять вторичный
`ENOENT`. Недоступные показатели показывать как `—`, а не как нули;
уже доступные показатели и измеренное время сохранять.

Определять поведение по результату стадии импорта, а не только по наличию
файла или общему коду завершения round-trip. Если импорт был успешным, но
`import-output.json` отсутствует, фиксировать отдельную ошибку отсутствующего
результата. Повреждённый или неполный файл результата также не скрывать.

После успешного импорта и ошибки экспорта продолжать собирать доступную
статистику YAML и диагностики импорта. Ошибка одной конфигурации не должна
останавливать обработку остальных. Сохранить одну таблицу отчёта, отдельный
раздел текстов ошибок и удаление временных каталогов после сохранения журналов.

### Проверка

- Ошибка импорта без `import-output.json`: исходная ошибка сохранена,
  вторичного `ENOENT` нет, недоступная статистика обозначена `—`;
  следующая конфигурация обрабатывается.
- Успешный импорт без файла результата: зарегистрирована отдельная ошибка,
  а не молчаливый пропуск статистики.
- Успешный импорт с повреждённым или неполным результатом: ошибка чтения
  или проверки статистики остаётся видимой.
- Успешный импорт и ошибка экспорта: статистика по сохранённым YAML и
  диагностике импорта остаётся в отчёте, исходная ошибка экспорта не теряется.
- Доступные размеры и время не теряются; временные каталоги удаляются после
  сохранения диагностики как при успехе, так и при ошибке конфигурации.

# Служебные XML-узлы таблицы и явный XML-default колонки

## Цель

Восстанавливать `Table.Period`, `Table.TopLevelParent` и `Table.RowFilter` при
YAML → XML по конечному источнику `ПутьКДанным`, без reference XML и без
служебных полей в YAML.

Отдельно сохранять доказанное асимметричное состояние XML: явный
`HeaderHorizontalAlign=Auto` у колонки таблицы. Только для него используется
локальный YAML-тег `!xml`, потому что смысловое значение `Авто` не позволяет
определить, присутствовал ли XML-узел явно.

## Договор служебных узлов таблицы

`Period`, `TopLevelParent` и `RowFilter` являются вычисляемыми XML-узлами. Они
не экспортируются в YAML и не задаются пользователем в `Форма.yaml`, в том
числе через `!xml`.

При YAML → XML NKDK создаёт узлы по конечному источнику `ПутьКДанным`:

| Конечный источник | `Period` | `TopLevelParent` | `RowFilter` |
|---|:---:|:---:|:---:|
| Непосредственный реквизит `DynamicList` | да | да | нет |
| `ValueTable` | нет | нет | да |
| Табличная часть объекта | нет | нет | да |
| `RegisterRecordSet` | нет | нет | да |
| `ValueTree` | нет | нет | нет |
| `ValueList` | нет | нет | нет |
| `GanttChart` | нет | нет | нет |
| Внутренняя коллекция `DynamicList` или `SettingsComposer` | нет | нет | нет |
| Обычное поле, не являющееся таблицей | нет | нет | нет |
| Составной конечный тип | нет | нет | нет |
| Путь отсутствует, пуст или не разрешается | нет | нет | да |

`Period` и `TopLevelParent` используются только вместе и только для пути
непосредственно к реквизиту формы типа `DynamicList`.

К внутренним коллекциям относятся `Filter`, `Order`, `Selection`,
`ConditionalAppearance`, `UserSettings`, `Settings`, `DataParameters`,
`FixedSettings`, `OutputParameters`, `UserFields` и подобные вложенные объекты.
Они не наследуют профиль исходного `DynamicList` или `SettingsComposer`.

## Канонический XML

`Period` создаётся с пустым пользовательским периодом:

```xml
<Period>
	<v8:variant xsi:type="v8:StandardPeriodVariant">Custom</v8:variant>
	<v8:startDate>0001-01-01T00:00:00</v8:startDate>
	<v8:endDate>0001-01-01T00:00:00</v8:endDate>
</Period>
```

Остальные узлы имеют пустую форму:

```xml
<TopLevelParent xsi:nil="true"/>
<RowFilter xsi:nil="true"/>
```

## Разрешение `ПутьКДанным`

Решение принимается по всему пути, а не по текстовому префиксу. Конечный тип
определяется существующими индексами данных формы и метаданных владельца.

Классификация выполняется в следующем порядке:

1. Отсутствующий, пустой или неразрешимый путь получает резервный профиль
   `rowFilter`.
2. Успешно распознанная внутренняя коллекция платформы получает профиль
   `none`.
3. Составной или нетабличный конечный тип получает профиль `none`.
4. Однозначный табличный тип получает профиль из таблицы договора.

Экспорт не формирует отдельную ошибку неверного типа: это задача validation.
Неразрешимый путь не останавливает формирование XML и получает канонический
`RowFilter`.

## Разрешение `CurrentData`

`Items.<Таблица>.CurrentData` обозначает текущую строку элемента таблицы, а не
самостоятельный конечный источник. Поэтому resolver не должен завершать
разрешение при встрече `CurrentData`.

Для `Items.<Таблица>.CurrentData.<Поле>` resolver:

1. находит элемент `<Таблица>` в индексе элементов формы;
2. разрешает его собственный `ПутьКДанным` обычным механизмом;
3. переходит к типу строки найденного табличного источника;
4. разрешает `<Поле>` и следующие сегменты через индекс метаданных;
5. возвращает обычный конечный тип для общей классификации.

Следствия:

- конечный `ValueTable`, табличная часть или `RegisterRecordSet` получает
  `RowFilter`;
- конечный `ValueTree`, `ValueList`, `GanttChart`, скаляр или внутренняя
  коллекция компоновщика не получает служебных узлов;
- путь через `CurrentData` не считается непосредственным `DynamicList`, поэтому
  не получает `Period` и `TopLevelParent`.

Само наличие `CurrentData` не определяет результат. Проверенные конфигурации
содержат 223 таких таблицы: 30 с `RowFilter` и 193 без него. Различие
объясняется конечным типом поля, поэтому прежнее правило «любой `CurrentData`
является внутренним путём и не получает узлов» неверно.

Для разрешения пути индекс данных формы предоставляет нейтральное соответствие
имени табличного элемента и его `ПутьКДанным`. Это расширение общего resolver,
а не отдельный индекс служебных XML-узлов. Вложенный `CurrentData` обрабатывается
тем же алгоритмом. Цикл ссылок и отсутствующий элемент дают общий результат
«путь не разрешён».

## Явный `HeaderHorizontalAlign=Auto`

Для табличных `InputField`, `LabelField`, `PictureField` и `CheckBoxField`
значение `Auto` является неявным YAML-default. Обычно свойство отсутствует и в
YAML, и в XML. Если исходный XML содержит явный узел
`<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>`, YAML сохраняет факт его
присутствия:

```yaml
ГоризонтальноеПоложениеВШапке: !xml Авто
```

Договор свойства содержит три случая:

| XML | YAML | Обратный XML |
|---|---|---|
| узел отсутствует | поле отсутствует | узел отсутствует |
| явный `Auto` | `!xml Авто` | явный `Auto` |
| другое значение | обычное YAML-значение | явный узел с этим значением |

`!xml` означает только «сохранить явное присутствие XML-узла». Он не меняет
смысл `Авто`, не задаёт принудительное отсутствие узла и не используется для
`Period`, `TopLevelParent` или `RowFilter`.

Тег является транспортной пометкой синхронизации:

- JSON Schema не получает нового поля или варианта типа и не предлагает тег в
  автодополнении;
- semantic validation проверяет обычное значение `Авто`;
- информация о теге передаётся отдельно и используется только при YAML → XML;
- неизвестное или незарегистрированное применение `!xml` является ошибкой
  импорта.

Общий механизм тега включается только для явно зарегистрированного свойства
`HeaderHorizontalAlign`. Любое новое применение к другому свойству или классу
значений требует отдельного согласования разработчика.

## Архитектурные границы

- Классификатор источника находится на границе преобразования формы, а условия
  создания служебных узлов остаются декларативными в `TableRules`.
- Общая оркестрация не знает о `Table`, `DynamicList`, табличных частях и
  конкретных XML-узлах формы.
- Граница операции передаёт форме общий resolver вместе с готовым индексом
  владельцев. Классификатор использует только его нейтральный результат и не
  разбирает `Items` или текст `ПутьКДанным` самостоятельно.
- Исходный XML, reference XML и отдельный снимок конфигурации не участвуют в
  восстановлении трёх служебных узлов.
- В общие типы правил не добавляются новые признаки, если договор можно
  выразить существующими правилами `toXML`, регистрацией `!xml` и готовыми
  индексами.
- Не добавляются частные условия по именам элементов формы.
- `AutoInsertNewRow` и остальные свойства таблицы не входят в изменение.

## Изменение реализации

Локальная проверка прямого `DynamicList` обобщается до единого классификатора
источника на границе преобразования формы. Существующие безусловные
`defaultValueXMLRaw` для трёх узлов заменяются условиями `toXML`:

- `dynamicList` создаёт `Period` и `TopLevelParent`;
- `rowFilter` создаёт `RowFilter`;
- `none` не создаёт служебных узлов.

Канонические значения узлов остаются декларативными в `TableRules`. Resolver
дополняется нейтральным переходом через текущую строку элемента формы,
возвращает обычный `ResolvedDataPathTarget` и передаётся преобразованию через
контекст операции.

Поддержка локальных YAML-тегов реализуется общим транспортным механизмом, а
разрешение `!xml` для `HeaderHorizontalAlign` — явной регистрацией рядом с
правилом свойства. Общая YAML Schema и смысловой тип свойства не меняются.

## Проверки

1. Табличная проверка классификатора покрывает все строки таблицы договора,
   включая отсутствующий, пустой, ошибочный, составной и скалярный путь.
2. Существующая проверка прямого `DynamicList` подтверждает совместимость
   общего классификатора.
3. `CurrentData` проверяется минимум с конечными `ValueTable`, `ValueTree` и
   внутренней коллекцией `SettingsComposer`.
4. XML → YAML не экспортирует `Period`, `TopLevelParent` или `RowFilter`.
5. XML → YAML → XML проверяется для отсутствующего `HeaderHorizontalAlign`,
   явного `Auto` и обычного значения; незарегистрированный `!xml` отклоняется.
6. Тесты проверяют наблюдаемый договор без условий по именам конкретных
   элементов формы и без изменения существующих XML-фикстур.
7. После реализации выполняются целевые тесты, `pnpm type-check`, полный
   `pnpm test`, round-trip `cf/doc` и проверка отсутствия новых дублей через
   `jscpd`. Stryker в этой задаче не запускается.

## Критерии готовности

- Служебные узлы полностью определяются актуальным YAML и индексами проекта.
- `CurrentData` классифицируется по конечному типу поля, а не по наличию
  сегмента в пути.
- Для известных типов результат не зависит от имени элемента формы.
- Неразрешимый путь не останавливает экспорт и получает `RowFilter`.
- Три служебных узла не хранятся в YAML или отдельном снимке.
- Явный XML-default `HeaderHorizontalAlign=Auto` сохраняется только через
  зарегистрированный `!xml Авто`.
- JSON Schema и semantic validation не предлагают транспортный тег как часть
  предметной модели.
- Все обязательные проверки проходят.

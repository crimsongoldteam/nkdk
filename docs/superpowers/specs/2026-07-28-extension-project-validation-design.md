# Валидация проекта с расширениями

## Контекст

Публичная операция validation сейчас принимает корень NKDK-проекта, но MCP
выбирает только компонент `cf`, а core по-прежнему поддерживает частичный режим
через `validateProject({ filePath })` и отдельный `validateProjectPartial`.
Частичная проверка достраивает зависимости одного файла и усложняет основной
validation pipeline.

После появления компонентов `cfe/<ИмяРасширения>` проверка только `cf` больше не
соответствует понятию валидации проекта. Расширение зависит от основной
конфигурации, видит собственные метаданные и метаданные `cf`, но не должно видеть
другие расширения.

## Цель

Один вызов `validateProject({ projectDir })` проверяет весь NKDK-проект:

- базовую конфигурацию `cf`;
- все расширения `cfe/<ИмяРасширения>`;
- ссылки каждого расширения на собственные метаданные и на `cf`;
- YAML-синтаксис и JSON Schema всех проверяемых файлов;
- существующие семантические правила validation без добавления новых
  ограничений платформы для заимствованных объектов.

Диагностики адресуются относительно корня NKDK-проекта: `cf/...` и
`cfe/<ИмяРасширения>/...`.

## Границы

В эту работу не входят:

- специальные ограничения редактирования заимствованных объектов;
- матрица допустимых изменений элементов заимствованной формы;
- запрет удаления элементов основной формы из результирующей формы расширения;
- оптимизация производительности schema validation;
- валидация `erf` и `epf`.

Проверка каждого YAML по JSON Schema остаётся внутренним этапом полной
валидации. Удаляется отдельная возможность запросить валидацию одного файла, а
не сама пофайловая работа полного прохода.

## Публичный договор

`validateProject` и `ValidationWorkerPoolHandle.validateProject` принимают корень
NKDK-проекта и больше не принимают `filePath`. Публичный экспорт
`validateParsedFile` удаляется. Внутренний schema validator остаётся доступен
только validation pipeline.

Удаляются:

- `validateProjectPartial`;
- partial worker-протокол;
- ветвления по `filePath`;
- partial-очередь и значение `partial` там, где они больше не имеют других
  потребителей.

MCP не выбирает `cf` перед вызовом core. Он передаёт корень проекта и возвращает
пути диагностик от этого корня.

## Подготовка проекта

Discovery находит `cf` и непосредственные каталоги `cfe/<ИмяРасширения>`.
Каждый найденный YAML получает:

- `componentPath`;
- абсолютный путь для чтения;
- путь внутри компонента;
- путь от корня проекта;
- роль файла и применимое правило `rules.ts`.

Корневая конфигурация `cf` проверяется по правилам основной конфигурации.
Корень каждого `cfe` проверяется по зарегистрированным правилам расширения.
Общий project/validation layer получает эти сведения через нейтральные
регистрации компонентов и не ветвится по конкретным `itemType`, именам
XML-корней или каталогам прикладных объектов.

Отсутствие `cf` является ошибкой структуры проекта. При этом найденные `cfe`
могут пройти YAML-синтаксис и JSON Schema, но их семантическая проверка
невозможна по той же политике деградации, что и при повреждённой `cf`.

## Единый граф валидации

First pass обрабатывает YAML всех компонентов одним worker pool. Результаты
сливаются в единый неизменяемый граф проекта.

Каждый узел, факт, индексная запись, ожидающая ссылка и исходный путь в графе
содержат `componentPath`. Ключ объекта включает компонентную принадлежность,
поэтому одноимённые объекты `cf`, `cfe/A` и `cfe/B` не перезаписывают друг друга.

Граф предоставляет ограниченные представления:

- представление `cf` содержит только узлы `cf`;
- представление `cfe/X` ищет сначала в `cfe/X`, затем в `cf`;
- узлы остальных `cfe` в представлении `cfe/X` отсутствуют.

Second pass получает не весь граф напрямую, а представление выбранного
компонента. Это сохраняет локальное перекрытие базового объекта расширением и
запрещает случайные ссылки между расширениями.

First pass выполняет существующие проверки:

- синтаксис YAML;
- соответствие JSON Schema;
- зарегистрированные проверки файла;
- сбор owner facts, ссылок, `ПутьКДанным` и других локальных вкладов.

Second pass выполняет существующие проверки зависимостей на соответствующем
представлении графа. Новые правила платформы для заимствованных объектов в этом
этапе не добавляются.

## Повреждённая базовая конфигурация

`cf` считается непригодной для семантической проверки расширений, если хотя бы
один её YAML получил ошибку синтаксиса или JSON Schema либо не смог сформировать
обязательный first-pass вклад графа. Последний случай включает ошибку
зарегистрированной структурной проверки, после которой текущий pipeline не
извлекает факты файла. Координатор определяет пригодность по результату first
pass, а не пытается восстановить её по текстам диагностик.

Семантическая ошибка `cf`, обнаруженная в second pass при успешно построенном
графе, не делает базовый граф непригодным. Например, битая ссылка внутри `cf`
возвращается как самостоятельная диагностика, но не блокирует second pass
расширений.

Если `cf` непригодна:

1. first pass всех `cfe` всё равно завершается;
2. ошибки синтаксиса и JSON Schema расширений возвращаются;
3. весь second pass каждого `cfe` пропускается, включая ссылки на метаданные,
   `ПутьКДанным` и другие проверки по индексам;
4. для каждого расширения добавляется одна диагностика severity `error` на
   `cfe/<ИмяРасширения>/Конфигурация.yaml` с сообщением, что семантическая
   валидация невозможна из-за ошибок базовой конфигурации.

Пропуск относится ко всему semantic second pass расширения. Это намеренно
консервативная политика: частичный индекс `cf` не позволяет надёжно отличить
реальную ошибку расширения от каскадной ошибки, вызванной отсутствующими
базовыми фактами.

First pass может спекулятивно собрать локальные факты `cfe` параллельно с `cf`,
чтобы не вводить повторное чтение файлов. Если `cf` оказалась непригодной, эти
факты и зависящие от них диагностики не используются: из расширения публикуются
только диагностики синтаксиса и JSON Schema плюс блокирующая диагностика
координатора.

## Диагностики

После всех доступных проходов диагностики:

1. приводятся к путям от корня NKDK-проекта;
2. объединяются для `cf` и всех `cfe`;
3. очищаются от повторов;
4. сортируются по пути, позиции, severity и сообщению существующим
   детерминированным правилом.

Одинаковый путь внутри двух расширений остаётся различимым благодаря префиксу
`cfe/<ИмяРасширения>/`.

## Изменения компонентов

### Discovery

Получает корень проекта, находит компоненты и выдаёт общий список файлов с
`componentPath`. Он отвечает только за адресацию и классификацию.

### First pass и worker pool

Обрабатывают общий список файлов без partial-режима. Worker возвращает
компонентно-адресованные вклады графа и диагностики.

### Граф и представления

Граф хранит факты всех компонентов, а отдельная фабрика представлений задаёт
политику видимости. Разрешатели ссылок и `ПутьКДанным` зависят от нейтрального
интерфейса представления, а не от знания каталогов `cf` и `cfe`.

### Координатор validation

Определяет пригодность `cf`, строит представления, назначает second pass и
применяет политику деградации. Только этот уровень объединяет итоговые
диагностики проекта.

### MCP

Передаёт корень NKDK-проекта в core и больше не преобразует вызов в проверку
одного `cf`. Его контракт входа остаётся `projectDir`, а пути результата
включают компонент.

## Обработка ошибок структуры

- Нет каталога `cf`: диагностика структуры проекта; schema first pass найденных
  `cfe` разрешён, semantic second pass запрещён.
- Нет расширений: выполняется обычная полная проверка `cf`.
- Повреждён корневой YAML одного `cfe`: ошибки этого файла возвращаются; другие
  расширения проверяются независимо.
- Два расширения содержат одинаковые логические имена: конфликта между ними
  нет, поскольку компоненты изолированы.
- Ссылка `cfe/A` на объект только из `cfe/B`: ошибка отсутствующей ссылки в
  `cfe/A`.

## Проверка

### Unit-тесты

- составной ключ графа различает `cf`, `cfe/A` и `cfe/B`;
- представление `cf` не видит расширения;
- представление `cfe/A` предпочитает локальный объект одноимённому базовому;
- представление `cfe/A` видит `cf`, но не видит `cfe/B`;
- диагностики получают устойчивые корневые пути;
- пригодность `cf` зависит от ошибок синтаксиса, JSON Schema и невозможности
  сформировать обязательный first-pass вклад, но не от second-pass ошибок.

### Интеграционные тесты core

- проект только с `cf`;
- проект с несколькими корректными расширениями;
- корректная и битая ссылка `cfe → cf`;
- одинаковые имена в разных расширениях;
- ошибка JSON Schema в `cfe` не мешает проверке соседнего расширения;
- ошибка синтаксиса или JSON Schema в `cf` сохраняет schema-диагностики `cfe`,
  пропускает их second pass и создаёт ровно одну блокирующую диагностику на
  расширение;
- структурная first-pass ошибка `cf`, остановившая сбор фактов, использует ту
  же политику деградации;
- semantic second-pass ошибка `cf` не блокирует second pass расширений;
- отсутствующая `cf` использует ту же политику деградации.

### Контрактные тесты

- `ValidateProjectParams` и handle не принимают `filePath`;
- partial worker-сообщения и partial-очередь отсутствуют;
- MCP передаёт корень проекта;
- MCP возвращает различимые пути `cf/...` и `cfe/<ИмяРасширения>/...`.

### Итоговая проверка

Перед завершением реализации запускается полный `pnpm test` из корня worktree.

## Критерии приёмки

- Один вызов validation проверяет `cf` и все `cfe`.
- Разные расширения изолированы друг от друга.
- Каждое расширение разрешает ссылки сначала локально, затем в `cf`.
- Повреждение first pass `cf` не скрывает schema-ошибки расширений и не создаёт
  каскад ложных semantic-ошибок.
- Отдельного публичного режима валидации одного файла больше нет.
- Пути всех диагностик однозначно указывают компонент.
- Существующий проект без расширений продолжает валидироваться полным проходом.
- Полный `pnpm test` проходит.

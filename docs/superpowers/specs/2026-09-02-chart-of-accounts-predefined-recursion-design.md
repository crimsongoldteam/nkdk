# Рекурсивные предопределённые счета

## Проблема

Импорт ERP сохраняет свойство `Предопределенные` плана счетов
`Хозрасчетный` целиком как `!xml/raw` и выдаёт предупреждение
`xml_raw_scope_too_broad`. Благодаря raw полный XML round-trip остаётся точным,
но смысловой YAML неполон и содержит крупную копию исходного
`Ext/Predefined.xml`.

Причина находится в выборе правил для вложенных предопределённых элементов.
Для верхнего уровня используются `ChartOfAccountsPredefinedItemRules`, поэтому
YAML содержит `ВидСчета`, `Забалансовый`, `Порядок`, `ПризнакиУчета` и
`ВидыСубконто`. Свойство `Элементы` наследует общую коллекцию
`PredefinedItemCollection`, которая использует обычные `PredefinedItemRules`.
Из-за этого те же поля у вложенных счетов не импортируются, а при контрольном
экспорте появляется общий `IsFolder=false`.

На ERP это затрагивает 351 вложенный счёт из 434 предопределённых элементов и
создаёт 2 106 структурных XML-расхождений. Первое отличие находится по пути
`/PredefinedData[1]/Item[2]/ChildItems[1]/Item[1]/AccountType[1]` у счёта
`ОсновныеСредства → ОСвОрганизации`. Поскольку у потерянных свойств нет адресов
правил конкретного типа, доказательство XML-аномалий поднимает границу raw до
всего свойства `Предопределенные`.

## Решение

Добавить отдельный тип коллекции
`ChartOfAccountsPredefinedItemCollection`, зарегистрированный с
`ChartOfAccountsPredefinedItemRules`.

Один тип коллекции используется в двух местах:

- для `PredefinedData/Item` верхнего уровня;
- для `ChildItems/Item` на каждой глубине вложенности.

Верхняя и вложенная коллекции различаются только значениями `xml`, `yaml` и
`yamlInline` соответствующего свойства. Выбор правила элемента определяется
регистрацией типа коллекции, поэтому объект правил не содержит циклической
ссылки на самого себя.

Регистрация сохраняет существующий XML-элемент `Item`, ключевое поле `name` и
сегмент индекса конфигурации `Предопределенный`. Следовательно, смысловые
logicalAddress и идентификаторы существующих предопределённых счетов не
изменяются.

## Изменения компонентов

### Построитель правила

В `metadataChartOfAccounts/builders.ts` появляется построитель широкого правила
для `ChartOfAccountsPredefinedItemCollection`. Он объявляет только конкретный
тип свойства и принимает существующие параметры коллекции. Новые поля в общие
типы `BasePropertyRule`, `PropertyRule` и параметры существующих построителей не
добавляются.

### Правила предопределённых счетов

В `metadataChartOfAccounts/predefined/rules.ts`:

- `childItems` переопределяется поверх общего правила и получает конкретный тип
  коллекции при сохранении `xml: ChildItems` и `yaml: Элементы`;
- корневое `items` получает тот же конкретный тип при сохранении `xml: Item`,
  встроенного YAML-представления и прежнего внутреннего имени;
- тип коллекции регистрируется через `defineMetadataItemCollectionRule` с
  `ChartOfAccountsPredefinedItemRules`.

Общие `PredefinedItemRules` и `PredefinedItemCollection` не меняются: каталоги,
планы видов характеристик и планы видов расчёта продолжают использовать свой
существующий договор.

### Статическая композиция

Новая регистрация включается в сгенерированный статический список правил тем же
способом, что существующие коллекции признаков учёта и видов субконто плана
счетов. Нейтральные слои runtime, импорта, доказательства XML-аномалий и
валидации не получают условий по типу объекта.

## Поток данных

При XML → YAML каждая коллекция `Item` разрешает
`ChartOfAccountsPredefinedItemRules`. Если элемент содержит `ChildItems`, его
свойство снова входит в тот же тип коллекции. Поэтому все уровни получают один
набор полей плана счетов.

При YAML → XML выполняется тот же рекурсивный выбор. Контрольный экспорт
восстанавливает свойства вложенных счетов из смыслового YAML, структурное
сравнение становится точным, и импорт не создаёт `!xml/raw` на всём свойстве.

## Проверка

Регрессионный тест использует компактный `PredefinedData` с верхним и вложенным
счётом. У вложенного счёта должны быть представлены все специфичные поля:

- `AccountType`;
- `OffBalance`;
- `Order`;
- `AccountingFlags`;
- `ExtDimensionTypes`.

Тест проверяет:

- наличие соответствующих полей во вложенном смысловом YAML;
- отсутствие добавленного общим правилом `IsFolder`;
- точное структурное XML → YAML → XML совпадение без reference XML и raw;
- прежний сегмент logicalAddress `Предопределенный` для вложенного элемента;
- JSON Schema вложенного элемента, содержащую поля плана счетов.

После локальных тестов выполняются обязательные проверки репозитория и полный
ERP round-trip настоящим MCP. Итоговый YAML
`ПланСчетов/Хозрасчетный/Свойства.yaml` не должен содержать
`Предопределенные: !xml/raw`, предупреждение `xml_raw_scope_too_broad` должно
исчезнуть, а XML-расхождений быть не должно. Три ранее классифицированных
`unresolved_data_path` не входят в эту доработку.

## Ограничения

- Новые применения `!xml` не добавляются.
- Исходные XML-фикстуры не изменяются; регрессия использует компактный inline
  XML внутри нового интеграционного теста.
- Общий механизм выбора правил коллекции не расширяется отложенными функциями и
  не получает условий для плана счетов.
- `.agents/architecture.md` не изменяется: направление зависимостей и границы
  metadata-слоёв остаются прежними.

## Критерии готовности

- Вложенные предопределённые счета используют полный набор правил плана счетов
  на любой глубине.
- Существующие logicalAddress и идентификаторы сохраняются.
- Компактная регрессия проходит без raw и XML-расхождений.
- ERP импорт завершается без `xml_raw_scope_too_broad`.
- ERP round-trip не создаёт XML-расхождений.
- `pnpm duplicates -- --base c751974c86b5c4ee59206513ccc91a0685e6ff7c`,
  архитектурные проверки и `pnpm test` проходят.

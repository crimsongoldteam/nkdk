# Валидация всех верхнеуровневых metadata item

## Цель

`nkdk validate <yaml-dir>` должен проверять все верхнеуровневые объекты,
которые поддерживает configuration walker, а также корневой
`Конфигурация.yaml`.

Сейчас список валидации в `validationProjectSpecs` заполнен вручную и уже
разошёлся с `TopLevelMetadataItemRules`: например, `Язык/Русский/Свойства.yaml`
и `Конфигурация.yaml` не попадают в проверку. Из-за этого некорректные YAML-ключи
и ссылки в этих файлах проходят незамеченными.

## Архитектура

Основным источником верхнеуровневых объектов для валидации станет
`TopLevelMetadataItemRules`.

`validationProjectSpecs` нужно формировать из этого реестра:

- для объектов с уже существующими специальными экспортёрами или импортёрами
  сохранить переопределения;
- для остальных объектов использовать общий путь:
  `exportMetadataItemToJSONSchema` и `importMetadataItemFromYAML`;
- объект без `itemTypePrefix` не должен попадать в список каталогов
  `<Вид>/<Имя>/Свойства.yaml`.

Так `validate` будет автоматически покрывать новые верхнеуровневые правила,
если они добавлены в `TopLevelMetadataItemRules` и имеют `itemTypePrefix`.

## Корневая конфигурация

`Конфигурация.yaml` не соответствует шаблону
`<Вид>/<Имя>/Свойства.yaml`, поэтому для него нужен отдельный тип
`ValidationProjectFile`.

Для корневой конфигурации:

- путь `Конфигурация.yaml` должен обнаруживаться при полном обходе проекта;
- `--file Конфигурация.yaml` должен быть допустимым;
- схема строится по `MetadataConfigurationRules`;
- импорт выполняется через `importMetadataItemFromYAML` с именем
  `Конфигурация`;
- после импорта запускаются те же структурные проверки, что и для объектов:
  уникальные имена и обход `metadataTarget`.

## Ошибки и совместимость

Сообщение об ошибке для неподдержанного `--file` нужно расширить:
ожидаются либо `Конфигурация.yaml`, либо пути вида
`<Вид>/<Имя>/Свойства.yaml` и `<Вид>/<Имя>/Формы/<Форма>/Форма.yaml`.

Поведение существующих поддержанных объектов должно сохраниться. Особые схемы и
импорт для `Справочник`, `Документ`, `Перечисление` остаются, потому что они уже
закрепляют текущие договоры YAML.

## Тестирование

Нужны тесты, которые защищают список от повторного расхождения.

Проверки:

- каждый объект из `TopLevelMetadataItemRules` с `itemTypePrefix` имеет
  соответствующий `ValidationProjectSpec`;
- для каждого такого объекта `discoverValidationProjectFiles` находит
  `<itemTypePrefix>/<Имя>/Свойства.yaml`;
- `Конфигурация.yaml` находится при полном обходе проекта;
- `resolveValidationProjectFile` принимает `Конфигурация.yaml`;
- `validateProject` реально запускает проверку для каждого верхнеуровневого
  объекта через минимальный YAML-файл;
- `validateProject` ловит неверную ссылку в `Конфигурация.yaml`, например в
  `ОсновнойЯзык`;
- существующие тесты `validate`, схем и CLI продолжают проходить.

После реализации нужно запустить точечные тесты в `packages/core` и
`packages/cli`, затем полный `pnpm test` из корня worktree.

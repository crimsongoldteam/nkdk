# Прямой импорт XML в YAML без metadata-модели

## Контекст

Текущий импорт XML выполняется в два прохода через полную metadata-модель объекта:

1. worker читает и разбирает XML, строит модель и сохраняет её до получения глобального индекса метаданных;
2. после получения индекса worker преобразует сохранённую модель в YAML.

На больших конфигурациях построение и хранение моделей увеличивает время импорта и пиковое потребление памяти. При этом `fromXML` и `toYAML` используются здесь как две последовательные части одного преобразования, а не как независимые этапы импорта.

## Цель

Импорт должен строить YAML непосредственно из XML единым обходом `rules.ts`, не создавая и не сохраняя полную metadata-модель объекта. Импорт и validation должны собирать сведения для `DataPath` общим механизмом типизированных фактов без совместимых объектов `model`, `modelStub` или их аналогов.

После первого прохода worker хранит YAML-данные и пути значений, которые требуется уточнить после построения глобального индекса метаданных. Разобранные XML-данные после обработки задания освобождаются.

## Не цели

- Не менять внешний договор `nkdk.import_from_xml`.
- Не менять формат XML-выгрузки, YAML-проекта или файла индекса конфигурации.
- Не переводить в этой задаче синхронизацию YAML → XML, переименование и поиск ссылок на безмодельную обработку.
- Не добавлять частные условия по `itemType`, именам XML-корней или конкретным типам свойств в общие metadata-слои.
- Не сохранять совместимый запасной путь импорта через полную metadata-модель.
- Не сохранять переходный модельный договор для `DataPath`: обработчики должны читать типизированные факты владельца напрямую.
- Не объединять два worker-прохода: глобальный индекс по-прежнему требует сведений обо всех объектах.

## Выбранный подход

Добавляется единый преобразователь XML → YAML, который рекурсивно обходит `rules.ts` и соединяет обязанности существующих процедур `fromXML` и `toYAML`.

Для атомарного свойства преобразователь:

1. находит исходное XML-значение с учётом XML-имени, альтернативных имён, контейнеров и значения по умолчанию;
2. вызывает зарегистрированное `fromXML` и получает временное типизированное значение;
3. немедленно передаёт это значение в зарегистрированное `toYAML`;
4. записывает результат в создаваемый YAML-объект.

Временное типизированное значение существует только внутри обработки свойства. Оно не записывается в родительский объект и не становится частью полной metadata-модели.

Для составного свойства, описанного через `rules.ts`, преобразователь сразу рекурсивно строит соответствующий YAML-объект или YAML-коллекцию. Промежуточный объект модельной формы не создаётся.

Правила пропуска, `fromXML: false`, `toYAML: false`, YAML-имена, неявные значения, внешние свойства, порядок XML и данные файла индекса конфигурации сохраняют действующее поведение. XML обрабатывается в исходном порядке для файла индекса конфигурации, а итоговый YAML собирается в порядке свойств `rules.ts`. Для этого преобразователь временно хранит только готовые YAML-фрагменты по ключам правил, а не модельные значения.

## Результат первого прохода

Для одного задания преобразователь создаёт:

- YAML-данные будущего файла;
- список путей значений, требующих глобального индекса;
- типизированные факты владельца и индекс его полей;
- сведения, необходимые существующим сборщикам связанных файлов и файла индекса конфигурации.

Состояние самого преобразования между проходами состоит только из YAML и отложенных путей. Исходное значение не дублируется рядом с путём: второй проход читает текущее значение непосредственно из YAML.

Служебное описание задания, целевой путь и описания внешних файлов остаются частью состояния worker, но не являются metadata-моделью объекта.

После получения результата задания worker освобождает XML-текст и разобранные XML-данные.

## Отложенное уточнение YAML

Общий слой не должен знать, что глобальный индекс требуется конкретному типу вроде `DataPath`. Зависимость объявляется через нейтральную регистрацию операции типа свойства `finalizeImportedYAML`.

Наличие зарегистрированной операции означает, что первый проход:

1. выполняет обычное XML → YAML и сохраняет предварительное YAML-значение;
2. добавляет путь этого значения и путь соответствующего правила в список отложенной обработки.

После объединения глобального индекса второй проход:

1. находит текущее значение в YAML по сохранённому пути;
2. находит зарегистрированный обработчик по декларативному пути правила;
3. передаёт обработчику YAML-значение, правило, контекст владельца и глобальный индекс;
4. записывает уточнённое YAML-значение по тому же пути.

Отложенная запись не содержит XML, временного типизированного значения или копии YAML-значения. Она содержит только координаты YAML и правила, достаточные для повторного нахождения обработчика.

Обработчик вызывается один раз. Если значение невозможно разрешить, он возвращает предупреждение, а предварительное YAML-значение сохраняется.

## Общий сбор фактов

Импорт и validation используют общий нейтральный договор `OwnerFacts`. Он содержит только сведения, необходимые глобальному индексу и обработчикам `DataPath`: тип владельца, его поля, владельцев, движения регистров, планы счетов и виды субконто, предопределённые значения, значения перечислений и другие зарегистрированные компактные сведения. Полная metadata-модель, синтетическая модель, `modelStub`, модельный текст и копия YAML в этот договор не входят.

Общий `OwnerFactsCollector` принимает окончательные YAML-значения свойств и формирует `OwnerFacts` и `ObjectFieldIndex`. Способ чтения YAML-значения регистрируется для типа свойства операцией `collectOwnerFactsFromYAML`. Если одинаковый тип свойства имеет разный смысл в разных местах, конкретный `PropertyRule` задаёт его полем `ownerFactRole`. Например, тип коллекции ссылок определяет способ чтения ссылок, а `ownerFactRole: "owners"` сообщает, что они задают владельцев объекта; `basedOn` такой роли для `DataPath` не имеет.

Импорт вызывает зарегистрированный обработчик сразу после формирования окончательного YAML-фрагмента свойства. Поэтому после завершения XML → YAML он не запускает повторный полный обход YAML или `rules.ts` ради локального индекса. Validation обходит существующий YAML по правилам и передаёт найденные значения в те же обработчики. Оба пути используют общий накопитель и получают одинаковые факты на одинаковом YAML.

Для навигации импорт и validation используют общий `YamlRuleCursor`. `YAML-путь` указывает на окончательное значение, а `Путь правила` — на соответствующий `PropertyRule`, включая тип конкретного полиморфного элемента формы. Импорт продвигает курсор во время построения YAML, validation — во время чтения существующего YAML.

Факты, зависящие от готового составного YAML-значения, например локальный индекс формы, строятся общим зарегистрированным обработчиком после завершения этого значения. Это не является повторным полным обходом всего YAML-файла.

После завершения задания накопитель отдаёт локальный индекс worker. Глобальный индекс хранит типизированные факты напрямую в едином неизменяемом двоичном снимке. Все обработчики `DataPath` читают факты из этого снимка; поле `OwnerMetadata.model` и восстановление совместимого модельного объекта удаляются.

Проверка JSON Schema, уникальности имён, обычных `metadataTarget`-ссылок и формирование validation-диагностик остаются обязанностью validation и не запускаются импортом.

## Локальный и глобальный индексы

Локальный индекс формируется общим накопителем фактов из окончательных YAML-значений по декларациям `rules.ts`. Общий слой не проверяет имена модельных свойств и не содержит ветвлений по типам объектов.

Сведения, необходимые глобальному индексу, не могут зависеть от отложенного уточнения: иначе возникнет цикл «индекс нужен для YAML, YAML нужен для индекса». Если новый тип создаёт такую зависимость, для него требуется отдельный предварительный факт, объявленный через регистрацию типа, а не возврат к полной модели.

Глобальный индекс остаётся единым неизменяемым двоичным снимком в общей памяти. Worker получают его перед вторым проходом, как и сейчас.

## Формы и специальные преобразователи

Требование отсутствия полной модели распространяется на формы и другие специальные ветви импорта.

Специализированный преобразователь может иметь собственный внутренний обход XML, но обязан вернуть тот же нейтральный результат:

- YAML-данные;
- отложенные YAML-пути;
- сведения для связанных файлов и локального индекса.

Worker не должен различать обычный объект и форму по форме сохранённого состояния. Общий metadata-слой не получает знаний о конкретных формах или прикладных объектах.

## Поток данных

### Первый проход worker

1. Прочитать все XML-файлы задания.
2. Разобрать XML.
3. Единым обходом правил построить YAML и список отложенных путей.
4. Извлечь из XML фрагмент данных файла индекса конфигурации.
5. Завершить общий накопитель фактов и получить локальный индекс без повторного полного обхода YAML.
6. Сохранить YAML и отложенные пути в состоянии worker.
7. Освободить XML.

### Между проходами

1. Главный процесс объединяет локальные индексы worker.
2. Главный процесс создаёт глобальный снимок в общей памяти.
3. Главный процесс передаёт описание снимка каждому worker.

### Второй проход worker

1. Для каждого сохранённого пути уточнить текущее YAML-значение.
2. Сериализовать окончательный YAML.
3. Записать YAML и создаваемые преобразованием связанные файлы.
4. Освободить YAML и список путей завершённого задания.

Второй проход не повторяет полный обход `rules.ts`, не читает XML и не читает YAML других объектов.

## Ошибки и предупреждения

- Ошибка чтения или разбора XML относится к заданию и не оставляет состояние этого задания для второго прохода.
- Ошибка прямого преобразования XML → YAML содержит исходный XML-путь, целевой YAML-путь и путь правила, если он известен.
- Отсутствующий путь во втором проходе или несоответствие ожидаемого типа значения считается внутренней ошибкой импорта.
- Неразрешимый `ПутьКДанным` остаётся предупреждением: предварительное YAML-значение сохраняется.
- Worker продолжает текущий проход для остальных заданий и возвращает все диагностики.
- При любой ошибке worker следующий этап импорта не начинается; файл индекса конфигурации не записывается.
- Прямой импорт остаётся нетранзакционным: уже записанные файлы не откатываются, а для повтора целевой компонент нужно очистить.

## Профилирование

Профиль импорта должен отражать новую архитектуру.

Удаляются этапы:

- `Построение модели`;
- `Экспорт модели в YAML-объект`.

Добавляются или уточняются этапы:

- `Преобразование XML в YAML` в первом проходе;
- `Сбор локального индекса метаданных`;
- `Уточнение отложенных значений YAML` во втором проходе;
- `Сериализация YAML`;
- `Запись основного YAML-файла`;
- `Запись связанного файла`.

Профиль должен отдельно показывать первый и второй worker-проходы, чтобы было видно, что второй проход обрабатывает только отложенные пути.

## Проверка

Минимальный набор тестов:

- атомарное свойство вызывает `fromXML`, затем `toYAML`, и записывает только YAML-значение;
- вложенный объект и коллекция строятся напрямую по `rules.ts`;
- альтернативные XML-имена, XML-контейнеры, значения по умолчанию и порядок обрабатываются как раньше;
- `fromXML: false`, `toYAML: false`, неявные значения и внешние свойства сохраняют поведение;
- отложенный путь работает для объекта, массива и вложенной коллекции;
- второй проход читает предварительное значение из YAML и меняет только указанное место;
- неразрешимое значение сохраняется и создаёт предупреждение;
- импорт и validation получают одинаковые типизированные факты владельца и индекс полей из одинакового YAML;
- локальный индекс содержит сведения владельцев, реквизитов, табличных частей и стандартных реквизитов;
- общий снимок и обработчики `DataPath` не содержат `model`, `modelStub`, модельного текста или синтетической metadata-модели;
- формы используют общий результат первого прохода без сохранения полной модели;
- validation обнаруживает и проверяет `DataPath` внутри single-элементов формы (`КонтекстноеМеню`, `РасширеннаяПодсказка`, `AutoCommandBar`) по полному YAML-пути, включая вложенные `Элементы`;
- состояние worker после первого прохода не содержит XML и metadata-моделей;
- существующие интеграционные тесты импорта дают тот же YAML и связанные файлы на неизменённых XML-фикстурах;
- полный `pnpm test` проходит;
- профиль ERP подтверждает отсутствие модельных этапов и показывает время и память новой схемы.

## Критерии готовности

- Импорт XML → YAML нигде не создаёт полную metadata-модель объекта.
- После первого прохода worker хранит YAML и отложенные пути, но не XML.
- Второй проход меняет только значения по сохранённым путям.
- Импорт и validation используют один договор, накопитель и зарегистрированные обработчики типизированных фактов.
- Обработчики `DataPath` читают факты напрямую; совместимого модельного представления в локальном или глобальном индексе нет.
- Общие слои не содержат условий по конкретным `itemType`, XML-корням, каталогам или типам свойств.
- Результат импорта на существующих XML-фикстурах не меняется.
- В профиле отсутствуют этапы построения и экспорта полной модели.

# Быстрое раскрытие discriminated union для массовой validation

## Контекст

В validation YAML сейчас используется двухфазная проверка TypeBox:

1. `validateParsedFile` быстро вызывает `schema.Check(parsed.data)`.
2. При ошибке вызывается `schema.Errors(parsed.data)`.
3. `typeboxErrorsToDiagnostics` передает ошибки в `expandDiscriminatedUnionErrors`.
4. `expandDiscriminatedUnionErrors` раскрывает грубую ошибку `Union` по `discriminantKey`, компилирует или берет из кэша выбранную ветку и повторно запускает `Errors` на значении.

Это сохраняет понятные сообщения для элементов коллекций: вместо `Expected union value` пользователь видит ошибку конкретной ветки по `Вид`. Цена появляется на массовой проверке проекта, когда один большой YAML-файл содержит много ошибочных элементов коллекции.

Ссылки, которые рассматривались:

- TypeBox issue #1017 предлагает `SetErrorFunction`, но это улучшает только текст общей union-ошибки и не дает подробные ошибки выбранной ветки.
- TypeBox issue #1038 и discussion #988 подтверждают общий подход: доменную навигацию по union приходится делать внешним слоем.
- `typebox-validators` реализует похожую идею, но README просит не использовать библиотеку, а ее `peerDependency` рассчитана на старый TypeBox.

## Цель

Ускорить ошибочный путь массовой validation проекта без потери понятности первых диагностик по элементам коллекций.

## Выбранный подход

Сделать локальный индекс discriminated union внутри `packages/core/metadata/validation/discriminatedUnionErrors.ts`.

Для каждой union-схемы с `discriminantKey` кэш хранит:

- имя discriminator-поля;
- ожидаемые literal-значения;
- соответствие `literal -> branch schema`;
- лениво скомпилированный `TypeCheck` выбранной ветки.

При раскрытии union-ошибки код читает значение discriminator из данных, находит ветку по индексу и запускает `Errors` только на этой ветке. Если значение неизвестно, отсутствует или нестроковое, создается текущая targeted diagnostic по discriminator-полю.

Это развитие текущего `unionSchemaCache`, а не новый валидатор и не смена JSON Schema.

## Защитный лимит

Для массовой проверки добавить лимит подробного раскрытия discriminated union на один YAML-файл. Предлагаемый начальный предел: 100 раскрытых union-ошибок.

До лимита поведение остается подробным: ошибки выбранной ветки, полный JSON Pointer path, привязка дополнительных свойств к ключу YAML.

После лимита не запускать дополнительные branch `Errors`, а возвращать короткую структурную диагностику на текущем узле union: подробные discriminated-union ошибки ограничены, чтобы validation не тратила непропорционально много времени на лавину однотипных проблем.

Лимит должен применяться только к раскрытию discriminated union. Обычные TypeBox-ошибки и синтаксические ошибки YAML не ограничиваются этим механизмом.

## Поведение

Сохраняем текущие гарантии:

- известный `Вид` раскрывается в ошибки выбранной ветки;
- неизвестный `Вид` показывает ожидаемые значения;
- отсутствующий или нестроковый `Вид` показывает `не задано`;
- вложенные union сохраняют полный path;
- `ObjectAdditionalProperties` по-прежнему диагностируется на ключе YAML;
- если схема не поддержана, код возвращается к исходной TypeBox-ошибке.

Новое поведение появляется только при превышении лимита подробного раскрытия: пользователь получает меньше однотипных подробных сообщений, но validation завершается быстрее.

## Границы

- Не добавляем зависимость `typebox-validators`.
- Не используем OpenAPI `discriminator` как новый формат схем.
- Не меняем schema CLI и формат JSON Schema для подсказчика.
- Не пишем частных условий по metadata itemType в общем validation-слое.
- Не меняем XML-фикстуры.

## Отличие от спеки 2026-07-01

Спека `2026-07-01-validation-fast-discriminant-errors-design.md` описывает более широкий быстрый сборщик, который пытается обойти полный `schema.Errors` раньше.

Текущий дизайн более узкий: он оптимизирует существующий слой `expandDiscriminatedUnionErrors`, сохраняет двухфазную TypeBox-проверку и добавляет лимит для массовой validation. Это меньше по риску и проще проверить на текущей архитектуре.

## Тестирование

Нужны focused-тесты в `packages/core/metadata/validation/validateFile.test.ts` или рядом:

- текущие сценарии discriminated union остаются зелеными;
- повторное раскрытие использует кэш веток и не пересобирает контекст ссылок;
- лимит не влияет на первые подробные ошибки;
- после лимита возвращается короткая диагностика без запуска новых branch `Errors`;
- обычный union без `discriminantKey` остается TypeBox-ошибкой.

После реализации:

1. `pnpm --filter @nakidka/core test -- metadata/validation/validateFile.test.ts`
2. `pnpm --filter @nakidka/core type-check`
3. `pnpm test`
4. Сравнить время массовой validation на проблемном YAML-проекте.

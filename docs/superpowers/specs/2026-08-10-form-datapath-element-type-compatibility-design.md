# Дизайн: совместимость вида элемента формы и типа `ПутьКДанным`

## Контекст

Общий resolver уже проверяет, что `ПутьКДанным` управляемой формы существует,
проходит по реквизитам, колонкам, стандартным реквизитам и объектам владельца и
возвращает тип конечного значения. Но существование пути ещё не означает, что
конечный тип допустим для выбранного вида элемента формы.

Например, реквизит типа `Строка | Булево` существует и разрешается resolver, но
Конфигуратор позволяет представить его только как `ПолеВвода` или
`ПолеНадписи`. `ПолеФлажка` для такого составного типа выбрать нельзя. Аналогично
ведут себя проверенные сочетания:

- `Картинка | Строка`;
- `Число | Картинка`;
- `Число | Булево`.

Для одиночного типа выбор шире. Отдельной проверкой в Конфигураторе подтверждено,
что `ПолеКартинки` допустимо не только для `Картинка`, но и для одиночных
`Строка` и `Число`.

Исследование
`/Users/nikita/git/nkdk_service/research/form-datapath-types/form-datapath-allowed-types.xlsx`
охватывает 79 727 управляемых форм и 833 026 свойств `DataPath` только из файлов
`*/Forms/*/Ext/Form.xml`. Оно содержит прямые примеры, но прямой пример XML не
всегда доказывает допустимость в Конфигураторе. В частности, найденные привязки
`CheckBoxField` к `string`, `dateTime` и `EnumRef.*` проверены как ошибочные.

## Цель

После успешного разрешения основного свойства `ПутьКДанным` проверять
совместимость конечного типа с видом элемента формы:

- при validation обычного YAML выдавать ошибку для несовместимого сочетания;
- при XML → YAML сохранять установленное в XML несовместимое сочетание через
  согласованный тег `!xml`;
- при YAML → XML восстанавливать исходный путь без попадания `!xml` в XML;
- применять один декларативный договор из `rules.ts` во всех проходах.

## Не цели

В задачу не входят:

- перепроектирование resolver, если он уже возвращает достаточную информацию о
  конечном типе;
- проверка допустимости самого `TypeDescription`, например запрет
  `ValueTable | string`: такое сочетание отклоняется на уровне реквизита, а не
  элемента формы;
- вывод допустимости только из количества примеров в XML;
- изменение общего формата или общего смысла `!xml`;
- проверка дополнительных свойств путей, перечисленных в разделе
  «Исключения»;
- проверка видов элементов, для которых исследование не дало ни прямого
  примера, ни отдельно подтверждённой гипотезы.

## Источник договора

Договор строится в следующем порядке:

1. Ручная проверка поведения Конфигуратора имеет приоритет над XML-корпусом.
2. Прямые примеры корпуса считаются подтверждением только после исключения
   известных ошибочных сочетаний.
3. Две гипотезы для `Table` отдельно подтверждены разработчиком:
   `CalculationRegisterRecordSet.*` и `ChartOfAccountsTabularSection.*`.
4. Пустая клетка матрицы не превращается автоматически в запрет для элемента,
   который вообще не покрыт исследованием.

Поэтому `CheckBoxField → string`, `CheckBoxField → dateTime` и
`CheckBoxField → EnumRef.*` остаются входными примерами ошибочного XML, а не
разрешёнными сочетаниями.

## Нормализация конечных типов

Политика сравнивает не широкие категории `scalar` и `object`, а нормализованные
группы типов из исследования.

Правило для именованных типов:

```text
CatalogRef.Номенклатура       → CatalogRef.*
DocumentRef.РеализацияТоваров → DocumentRef.*
CatalogTabularSection.Товары  → CatalogTabularSection.*
```

Общий тип без имени остаётся отдельной группой:

```text
CatalogRef → CatalogRef
DocumentRef → DocumentRef
```

Примитивные и платформенные типы сохраняют точное имя:

```text
string, decimal, boolean, dateTime, Picture, ValueTable, Chart, ...
```

Нормализатор получает тип из результата resolver. Он не разбирает текст YAML
пути и не ищет реквизит повторно. Если для точной классификации resolver уже
хранит тип в `sourceText`, `nextTypes` или `table`, используются эти данные. Его
договор расширяется только в случае, когда точная конечная ветвь действительно
теряется.

`DefinedType.*` раскрывается существующим механизмом до эффективного состава.
Нормализация сохраняет как группу объявления `DefinedType.*`, так и эффективные
ветви. Для одиночного эффективного типа политика может явно разрешить саму
группу `DefinedType.*`, как это делают поля ввода, надписи и переключателя.
Составной эффективный тип всегда подчиняется общему правилу составных типов и не
становится допустимым только из-за разрешённой группы `DefinedType.*`.

## Декларативные политики элементов

Допустимые группы задаются существующим параметром `allowedKinds` правила
`DataPath`. Параметр начинает хранить точные нормализованные группы, а не только
широкие категории. Для составности используется существующий `allowComposite`.
Новые поля в `BasePropertyRule`, `PropertyRule` или параметры построителей правил
не добавляются.

Двоичное состояние проекта уже хранит `allowedKinds` как строки и
`allowComposite` как флаг, поэтому формат и версия состояния не меняются.
Отложенная проверка `DataPath` дополнительно должна помнить, помечено ли
значение как `!xml`. Этот флаг размещается в существующей записи pending check,
не создавая новую таблицу состояния; нулевое значение старого состояния означает
обычный YAML.

## Алгоритм проверки

Для основного `ПутьКДанным` элемента:

1. Выполнить существующее разрешение пути.
2. Если путь не разрешён, вернуть действующую diagnostic resolver и не делать
   вывод о совместимости.
3. Получить эффективные конечные ветви и признак составности.
4. Если тип составной, разрешить его только для полей ввода и надписи, не
   применяя к отдельным ветвям списки одиночных групп.
5. Если тип одиночный, нормализовать его и сравнить с `allowedKinds` элемента.
6. Применить контекстное исключение
   `PictureField + ValueTable + КартинкаЗначений`.
7. Вернуть единый результат `compatible`, `incompatible` или
   `notResolved` потребителям validation и import.

Составной тип не проверяется по принципу «совпала хотя бы одна ветвь». Например,
`boolean | string` несовместим с `CheckBoxField`, несмотря на наличие ветви
`boolean`.

`any` и `unknown` различаются. `any` является известным произвольным типом и
явно присутствует в списках полей ввода и надписи. `unknown` означает недостаток
данных resolver; для элемента с политикой это `notResolved`, а не доказанная
несовместимость.

## Diagnostics обычного YAML

Обычное несовместимое значение даёт ошибку точно на свойстве
`ПутьКДанным`. Сообщение содержит:

- сам путь;
- вид элемента;
- фактическую нормализованную группу или состав типов;
- допустимые группы либо указание, что составной тип разрешён только полям ввода
  и надписи.

Примеры:

```text
ПутьКДанным "ФлагСтрокой": тип string несовместим с CheckBoxField;
допустимо: boolean или decimal
```

```text
ПутьКДанным "СоставноеЗначение": составной тип string | boolean несовместим
с CheckBoxField; составной тип допустим только для InputField и LabelField
```

Неразрешимый путь сохраняет существующую ошибку или предупреждение resolver.
Проверка совместимости не подменяет её сообщением о типе.

## Транспортное исключение `!xml`

Разработчик явно согласовал новое применение `!xml` ко всем успешно разрешённым,
но несовместимым сочетаниям основного `ПутьКДанным` и вида элемента формы.

XML → YAML для такого сочетания создаёт:

```yaml
ПутьКДанным: !xml ФлагСтрокой
```

Тег означает только следующее: путь установлен в исходном XML, resolver его
успешно разрешил, но конечный тип несовместим с видом элемента по данной
спецификации.

Внутри `!xml` хранится исходная XML/internal-строка `DataPath`, а не её
канонизированный YAML-вариант. Для большинства пользовательских имён строки
совпадают; различие важно для служебных сегментов и стандартных реквизитов.
Tagged-путь разрешается resolver в XML/internal-режиме и всё равно даёт
каноническую цель зависимости.

`!xml` не используется:

- для неразрешимого пути;
- при недостатке сведений о конечном типе;
- для обхода отсутствующего правила элемента;
- для дополнительных свойств пути из раздела «Исключения»;
- для совместимого сочетания.

Validation продолжает разрешать путь внутри `!xml`, сохраняет его зависимость и
не скрывает ошибки отсутствующей цели. Тег подавляет только локальную ошибку
совместимости вида элемента и конечного типа. `!xml` у совместимого сочетания
считается необоснованным и получает diagnostic.

YAML → XML удаляет транспортный тег и записывает содержащуюся в нём
XML/internal-строку `DataPath` без дополнительного перевода имён. Текст `!xml`
никогда не попадает в XML.

## Поток XML → YAML

Проверка совместимости может требовать сведений владельца и поэтому выполняется
после того, как resolver получил проектный снимок:

- `resolved + compatible` — оставить обычную строку YAML;
- `resolved + incompatible` — заменить обычное представление на
  `!xml <исходная XML/internal-строка>`;
- `notResolved` — сохранить действующее предупреждение и обычное значение, не
  добавляя `!xml`.

Import не дублирует собственный resolver и не пытается классифицировать тип по
сырому XML элемента. Он использует тот же отложенный `DataPath` check, что и
validation.

## Исключения

В этой задаче проверяется только основной `ПутьКДанным`, тип которого определяет
вид самого элемента. Следующие свойства продолжают проходить обычное разрешение
пути, но не получают проверку совместимости с видом элемента:

- `ПутьКДанным` у `Button` и `CommandBarButton`: это данные параметра команды,
  а не тип отображаемого поля;
- `ПутьКДаннымПодвала`;
- `ПутьКДаннымКартинкиСтроки` таблицы;
- `ПутьКДаннымКартинкиМножественногоЗначения`;
- `ПутьКДаннымПредставленияМножественногоЗначения`;
- `ПутьКДаннымЗначенияМножественногоЗначения`;
- пути заголовков и остальные дополнительные свойства `DataPath`, не являющиеся
  основным источником элемента.

Это ограничение добавляется в `.agents/restrictions.md`. Для каждого такого
свойства отдельное исследование должно определить собственный контекст и
допустимые конечные типы.

`DendrogramField`, `PeriodField` и другие основные элементы, отсутствующие в
подтверждённой матрице, пока также не получают закрытую политику совместимости.
Их наличие и путь продолжают проверяться resolver; ограничение фиксируется до
отдельного исследования, а тип не выводится только из `defaultType` правила.

## Архитектурные границы

- Матрица остаётся декларацией конкретных элементов в их `rules.ts`.
- Общий `validation/dataPath` знает только нормализацию, составность и применение
  переданной политики; он не содержит `switch` по `elementType`.
- Контекстное исключение картинки остаётся узким зарегистрированным договором
  основного `ПутьКДанным` и `КартинкаЗначений`.
- Resolver отвечает за существование и эффективный тип пути; политика отвечает
  только за совместимость этого типа с элементом.
- Import, validation, поиск ссылок и операции используют один результат
  resolver и один нормализатор.
- Нейтральные слои проекта не получают частных условий по именам элементов или
  XML-тегам.

## Тестирование

### Нормализация

- именованный `CatalogRef.Номенклатура` превращается в `CatalogRef.*`;
- общий `CatalogRef` остаётся `CatalogRef`;
- табличные части и наборы записей нормализуются по семействам;
- примитивы и платформенные типы сохраняют точное имя;
- DefinedType раскрывается до одиночного или составного эффективного типа;
- стандартные реквизиты дают ту же группу, что явный аналогичный тип.

### Политики

- таблица случаев покрывает каждую строку подтверждённой матрицы;
- `CheckBoxField` принимает `boolean` и `decimal`;
- ошибочные XML-примеры `string`, `dateTime`, `EnumRef.*` для
  `CheckBoxField` отклоняются;
- `PictureField` принимает одиночные `string`, `decimal`, `boolean`,
  `EnumRef.*`, `Picture`, `ValueStorage`;
- `ValueTable` для поля картинки принимается только при `КартинкаЗначений`, а
  другой `tableSource` в этом контексте остаётся несовместимым;
- оба подтверждённых источника `Table` принимаются;
- специализированные элементы принимают только перечисленные одиночные группы;
- пустые клетки не создают политику для неисследованного элемента.

### Составные типы

- `string | boolean` допускается для поля ввода и поля надписи;
- `Picture | string`, `decimal | Picture` и `decimal | boolean` допускаются для
  поля ввода и поля надписи;
- те же составы отклоняются у флажка, картинки и остальных ограниченных полей;
- совпадение одной ветви больше не разрешает составной тип;
- недопустимый на уровне `TypeDescription` состав проверяется своим существующим
  валидатором, а не этой политикой.

### Import и `!xml`

- каждый успешно разрешённый несовместимый основной путь импортируется с
  `!xml`;
- совместимый путь импортируется обычной строкой;
- неразрешимый путь не получает `!xml` и сохраняет прежнюю diagnostic;
- `!xml` у несовместимого пути подавляет только ошибку совместимости;
- `!xml` у совместимого пути отклоняется;
- tagged-путь со стандартным или служебным internal-сегментом разрешается в
  internal-режиме и сохраняет каноническую цель зависимости;
- ссылка внутри `!xml` остаётся в индексе зависимостей и участвует в
  переименовании;
- XML → YAML → XML точно восстанавливает строку `DataPath` без текста `!xml`.

### Исключения и регрессии

- `Button` и `CommandBarButton` не получают проверку совместимости типа;
- дополнительные пути из раздела «Исключения» не используют матрицу основного
  элемента;
- существующие diagnostics resolver для отсутствующих корней, колонок,
  стандартных реквизитов и неизвестных типов не меняются;
- двоичная запись и чтение `allowedKinds` и `allowComposite` сохраняют точные
  декларации без изменения версии формата;
- полный набор тестов, архитектурные проверки и проверка дублей проходят.

## Критерии готовности

- Для каждого покрытого основного элемента `rules.ts` содержит согласованную
  декларацию совместимости.
- Обычный несовместимый YAML получает одну предметную ошибку на
  `ПутьКДанным`.
- Несовместимый, но существующий XML-путь сохраняется через `!xml` и делает
  точный round-trip.
- Неразрешимые пути не маскируются `!xml`.
- Составной тип принимают только поля ввода и надписи.
- Ошибочные примеры `CheckBoxField` не считаются разрешёнными только потому, что
  встречаются в XML-корпусе.
- Исключённые свойства перечислены в `.agents/restrictions.md`.

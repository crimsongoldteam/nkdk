# `AnyRef` в описании типов расширения конфигурации

## Контекст

Импорт расширения `/Users/nikita/git/sed_xml/cfe/дкз` завершается ошибкой для восьми объектов. В их описаниях типов встречается конструкция:

```xml
<v8:TypeSet>cfg:AnyRef</v8:TypeSet>
```

Общий преобразователь `TypeDescription` знает `AnyIBRef`, но не знает `AnyRef`, поэтому не может сформировать YAML и прекращает импорт всего объекта.

Исследование двух каталогов расширений показало:

- `/Users/nikita/git/sed_xml/cfe/дкз` содержит 18 значений `cfg:AnyRef` и не содержит `cfg:AnyIBRef`; режим совместимости расширения — `Version8_3_20`;
- `/Users/nikita/git/round-trip-compact/cfe/all-extension` содержит 4 значения `cfg:AnyIBRef` и не содержит `cfg:AnyRef`; режим совместимости расширения — `Version8_3_27`;
- оба обозначения записываются в `v8:TypeSet`;
- `cfg:AnyIBRef` в новом расширении встречается как у собственных, так и у заимствованных объектов. Поэтому выбор обозначения не зависит от `ObjectBelonging=Adopted`.

[Официальное описание платформы 8.3.24](https://dl05.1c.ru/content/Platform/8_3_24_1738/1cv8upd_8_3_24_1738.htm) называет `AnyIBRef` представлением типа `ЛюбаяСсылка` и сохраняет прежнее поведение в режиме совместимости 8.3.22. Документ описывает пространство XDTO `data/enterprise`, а не формат `cfg` метаданных. Поэтому порог для `cfg` является принятым договором, подтверждённым исследованными выгрузками, но не прямым утверждением документации.

## Требуемое поведение

В YAML существует одно каноническое смысловое значение:

```yaml
Тип: ЛюбаяСсылка
```

Импорт принимает оба XML-обозначения:

```text
cfg:AnyRef   ─┐
              ├─> ЛюбаяСсылка
cfg:AnyIBRef ─┘
```

При экспорте расширения обозначение определяется полем `РежимСовместимостиРасширенияКонфигурации`:

```text
Версия8_3_22 и более ранняя → cfg:AnyRef
Версия8_3_23 и более поздняя → cfg:AnyIBRef
НеИспользовать              → cfg:AnyIBRef
поле отсутствует            → cfg:AnyIBRef
```

Отсутствующее поле уже имеет неявное значение `Версия8_3_27` в `rules.ts`; отдельное значение по умолчанию для этой задачи не вводится.

## Архитектура

### Входной синоним `TypeDescription`

`AnyRef` добавляется как входной синоним семантического типа `AnyIBRef`. Нормализация выполняется при чтении XML до преобразования `TypeDescription` в YAML.

`AnyRef` не становится вторым полноценным элементом `TypeDescriptionRules`: два правила с одинаковым YAML-именем `ЛюбаяСсылка` сделали бы обратное преобразование неоднозначным. Таблица входных синонимов отделена от канонического реестра экспортируемых типов.

Нормализация относится только к значениям внутри `TypeDescription`. Она не меняет одноимённые типы и значения в произвольных XDTO-документах.

### Политика XML-имён компонента

Профиль full sync расширения один раз получает каноническое значение режима совместимости из корневого YAML расширения. Для типа `AnyIBRef` профиль формирует явную политику XML-имени:

```text
AnyIBRef → AnyRef   для режимов до 8.3.22 включительно
AnyIBRef → AnyIBRef для остальных режимов
```

Политика передаётся всем воркерам через профиль компонента и контекст экспорта. Общая оркестрация только переносит непрозрачные для неё настройки профиля и не содержит условий по `configurationExtension`.

Общий экспортёр `TypeDescription` по-прежнему определяет смысловой тип и его обычный префикс через `TypeDescriptionRules`. Затем он применяет переданное XML-имя. Сам экспортёр не знает о расширениях и версиях платформы.

Политика расширения задаёт имя явно даже для современного режима. Поэтому она имеет приоритет над написанием, восстановленным из reference XML: смена режима совместимости должна менять `AnyRef` на `AnyIBRef` или обратно, а не сохранять устаревшую форму.

### Область применения

Политика применяется ко всем `TypeDescription` расширения:

- к свойствам прикладных объектов;
- к реквизитам и колонкам форм;
- к собственным и заимствованным объектам;
- к остальным metadata items, использующим общий `TypeDescription`.

Готовая XML-модель рекурсивно не обходится, а произвольные строки `cfg:AnyIBRef` не заменяются. Благодаря этому изменение не затрагивает поля с другой семантикой.

Снимок конфигурации, `!xml`, индекс зависимостей и индекс метаданных для выбора написания не используются: необходимый режим уже является смысловым свойством корневого YAML.

## Диагностика

- `cfg:AnyRef` является допустимым входом и не создаёт предупреждение.
- Неизвестные типы по-прежнему создают существующую ошибку `Type ... not found in TypeDescriptionRules`.
- Неизвестный режим совместимости отклоняется существующей JSON Schema. Экспорт не угадывает ближайшую версию.
- Ошибка чтения корневой конфигурации или режима останавливает подготовку full sync до запуска воркеров и сообщает путь к корневому YAML.

## Проверка

Тесты следуют `.agents/testing.md`; существующие XML-фикстуры не изменяются.

### Модульные тесты

- `cfg:AnyRef` и `cfg:AnyIBRef` импортируются в одно YAML-значение `ЛюбаяСсылка`.
- Пограничные режимы выбирают ожидаемое XML-имя:
  - `Версия8_3_20` и `Версия8_3_22` — `AnyRef`;
  - `Версия8_3_23` и `Версия8_3_27` — `AnyIBRef`;
  - `НеИспользовать` и отсутствующее поле — `AnyIBRef`.
- Политика имеет приоритет над противоположным написанием из reference XML.
- Остальные типы `TypeDescription` не изменяются.

### Интеграционные тесты

- full sync расширения старого режима формирует `cfg:AnyRef` в metadata item и отдельном `Form.xml`;
- full sync расширения нового режима формирует `cfg:AnyIBRef`;
- собственные и заимствованные объекты используют одну политику режима;
- обычная конфигурация продолжает формировать канонический `cfg:AnyIBRef` без политики расширения.

### Проверка на реальном проекте

1. Повторно импортировать `/Users/nikita/git/sed_xml/cfe/дкз` в `/Users/nikita/git/sed_nkdk/cfe/дкз`.
2. Убедиться, что восемь ранее пропущенных объектов импортированы и ошибок `AnyRef` нет.
3. Выполнить валидацию `/Users/nikita/git/sed_nkdk` и отдельно проверить отсутствие диагностик `AnyRef`.
4. Выполнить полный набор тестов проекта и проверку дублей согласно `AGENTS.md`.

## Вне границ задачи

- сохранение исходного обозначения `AnyRef`/`AnyIBRef` независимо от режима совместимости;
- изменение формата YAML;
- хранение технической формы XML в снимке или индексах;
- изменение правил других XDTO-пространств;
- доказательство формата `cfg` для всех версий платформы, для которых нет исследованной выгрузки.

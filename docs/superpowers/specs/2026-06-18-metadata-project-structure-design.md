# Универсальная модель структуры metadata-проекта

## Цель

Команды `schema`, `validate` и `sync` должны иметь одно представление о
структуре metadata-проекта.

Это представление не должно дублировать структуру, уже описанную в `rules.ts`.
Новый слой должен интерпретировать существующие правила и зарегистрированные
операции типов, чтобы отвечать на вопросы:

- что означает проектный путь;
- какие metadata-ресурсы существуют в конкретном каталоге проекта;
- какие YAML/XML/asset-файлы потенциально связаны с metadata object;
- какой `MetadataItemRule` или типовой обработчик отвечает за ресурс.

Миграции не входят в эту модель.

## Источники истины

Структура остаётся децентрализованной.

Основные источники:

- `MetadataConfigurationRules` описывает корневую конфигурацию и связанные
  корневые внешние файлы;
- `TopLevelMetadataItemRules` агрегирует верхнеуровневые `MetadataItemRule`;
- `MetadataItemRule.itemTypePrefix` задаёт YAML-каталог объекта;
- `MetadataItemRule.xmlDir` задаёт XML-каталог объекта;
- свойства `filePath`, `xmlPath`, `nkdkDir`, `externalFile`,
  `syncExternalOnly`, `derivedFrom` описывают внешние файлы;
- `registerTypeRule(..., "syncExternalFromXML" | "syncExternalToXML", ...)`
  описывает динамическую синхронизацию файлов, которую нельзя полностью вывести
  только по статическим полям правила.

Новый слой не вводит отдельный постоянный реестр путей. Если структура объекта
меняется, правится его `rules.ts` или типовой обработчик, а общий слой только
иначе интерпретирует эти правила.

## Новый слой

Добавить нейтральный слой `packages/core/metadata/project/`.

Он не должен зависеть от `metadata/validation`, `commands/schema` или
конкретной реализации `sync`. Направление зависимостей:

```text
rules.ts + typeRuleRegistry
  -> metadata/project
  -> schema / validate / sync
```

### Основные операции

```ts
classifyMetadataProjectPath(projectPath: string): MetadataProjectResourceRef | undefined
```

Классифицирует путь без обращения к файловой системе. Это нужно для схем и
подсказок редактора, где файл может ещё не существовать.

Примеры:

- `Конфигурация.yaml` — корневая конфигурация;
- `Справочник/Товары/Свойства.yaml` — свойства справочника `Товары`;
- `Подсистема/Администрирование/Подсистемы/Настройки/Свойства.yaml` —
  свойства вложенной подсистемы;
- `Документ/Заказ/Формы/ФормаДокумента/Форма.yaml` — форма документа;
- `Справочник/Товары/МодульМенеджера.bsl` — внешний файл, если он описан
  правилами или типовым обработчиком;
- путь миграции — `undefined`.

```ts
discoverMetadataProjectResources(projectDir: string): MetadataProjectResourceRef[]
```

Обходит существующий проект и возвращает реальные metadata-ресурсы. Это нужно
для `validate` и `sync`.

```ts
describeMetadataRuleResources(rule: MetadataItemRule): MetadataProjectResourceDescriptor[]
```

Возвращает потенциальные ресурсы, которые можно вывести из конкретного
`MetadataItemRule`: YAML properties, основной XML, внешние XML-файлы по
`filePath`, внешние файлы по `externalFile`, а также маркеры динамических
ресурсов для типов с `syncExternal*`.

### Типы ресурсов

Минимальный публичный результат должен различать:

```ts
type MetadataProjectResourceRef =
  | MetadataProjectConfigurationYamlRef
  | MetadataProjectPropertiesYamlRef
  | MetadataProjectFormYamlRef
  | MetadataProjectExternalXmlRef
  | MetadataProjectAssetRef
```

Общие поля:

- `projectPath` — путь относительно корня YAML-проекта;
- `kind` — общий вид ресурса: `yaml`, `xml`, `asset`;
- `role` — роль внутри metadata: `configuration`, `properties`, `form`,
  `externalXml`, `module`, `template`, `picture`, `help`, `binary`,
  `unknownExternal`;
- `owner` — вид и имя владельца, если ресурс принадлежит объекту;
- `rule` или `propertyRule` — ссылка на правило, которое описывает ресурс;
- `exists` не хранится в результате `classify`, потому что путь может быть
  виртуальным.

Для ресурсов, которые нельзя надёжно описать статически, слой должен возвращать
дескриптор динамического обработчика, а не пытаться угадать все файлы.

## Поведение команд

### `schema`

`schema` использует только `classifyMetadataProjectPath`.

Поток:

1. нормализовать target как проектный путь или имя схемы;
2. если target выглядит как проектный путь, вызвать `classifyMetadataProjectPath`;
3. для `configuration` и `properties` построить JSON Schema по `rule`;
4. для `form` использовать схему `ClientApplicationForm`;
5. для ресурсов без YAML-схемы вернуть понятную ошибку;
6. сохранить поддержку режимов `--json-schema`, `--inline`, `--keys`,
   `--required`, `--search`, `--exact`.

Путь не обязан существовать на диске.

### `validate`

`validate` использует `discoverMetadataProjectResources`, затем фильтрует YAML,
которые можно валидировать.

Валидация оставляет свои специализированные слои:

- `ProjectYamlCache` читает и кэширует текст + `ParsedYaml`;
- `OwnerMetadataCache` импортирует модели владельцев и строит индекс полей;
- `ProjectMetadataResolver` проверяет `metadataTarget`;
- `DataPath` остаётся валидаторской логикой форм.

Общий слой не должен читать YAML и не должен импортировать модели.

### `sync`

`syncToXML` должен постепенно перейти на общий слой для построения плана
существующих YAML-ресурсов.

В первой реализации достаточно:

- получать корневую конфигурацию и верхнеуровневые `Свойства.yaml` через
  `discoverMetadataProjectResources`;
- использовать `rule.xmlDir`, `itemTypePrefix` и имя владельца из общего
  результата вместо повторного ручного обхода;
- оставить миграции, reference XML, `XmlSyncManifest` и внешние обработчики
  в текущем коде синхронизации.

Формы, шаблоны, модули, справка и картинки пока продолжают синхронизироваться
через существующие `syncExternal*` обработчики. Общий слой только помогает
описать, что такие ресурсы связаны с правилами.

`syncFromXML` использует общий слой иначе: не через обход YAML-проекта, а через
реестр правил для построения выходных YAML-путей из XML-каталогов.

## Ошибки и границы

Если путь не является metadata-ресурсом проекта, общий слой возвращает
`undefined`. Потребитель сам решает, какое сообщение показать.

Если путь является metadata-ресурсом, но для него нет JSON Schema, команда
`schema` должна сообщить, что схема для этого вида ресурса не поддерживается.

Если ресурс динамический и его файлы нельзя вывести без чтения модели или
каталога, общий слой не должен выдумывать точный список. Он возвращает
дескриптор динамического ресурса, а `sync` вызывает соответствующий
`syncExternal*` обработчик.

Миграции, служебные файлы состояния и временные каталоги не классифицируются
как metadata-ресурсы.

## План внедрения

1. Создать `metadata/project` с типами и классификацией YAML-путей.
2. Перенести из `metadata/validation/projectSpecs.ts` нейтральную часть
   построения `spec` из `TopLevelMetadataItemRules`.
3. Перевести `schema` на `classifyMetadataProjectPath`.
4. Перевести `validate` на `discoverMetadataProjectResources`, сохранив
   текущие кэши и структурные проверки.
5. Перевести верхний обход `syncToXML` на общий список YAML properties.
6. Добавить описание внешних XML/asset-ресурсов из `filePath`, `externalFile`
   и динамических `syncExternal*` как отдельный шаг, не меняя их поведение.

## Проверки

Нужны тесты:

- `classifyMetadataProjectPath` принимает несуществующие пути для
  `Конфигурация.yaml`, верхнеуровневых properties, вложенных подсистем и форм;
- миграционные пути не классифицируются;
- `discoverMetadataProjectResources` находит тот же набор YAML-файлов, который
  сейчас находит `discoverValidationProjectFiles`;
- `schema` строит сводку и JSON Schema для `Конфигурация.yaml` и вложенной
  подсистемы;
- `validate` сохраняет текущие проверки `metadataTarget` и `DataPath`;
- `syncToXML` создаёт те же задачи для верхнеуровневых объектов, что и раньше;
- внешний ресурс по `filePath` описывается как ресурс правила, но его
  синхронизация остаётся за существующим кодом.

После реализации нужно запустить точечные тесты затронутых модулей и затем
`pnpm test` из корня worktree.

# Слоистая матрица частичной синхронизации

## Контекст

Текущий ручной e2e частичной синхронизации строит плоский план: после каждой
операции он проверяет весь проект, дважды вызывает `sync_to_infobase` и заменяет
единственную контрольную копию. Постоянный MCP-сеанс и постоянный платформенный
сеанс уже устранили повторный запуск платформы, но число контрольных циклов
остаётся главным источником времени.

Актуальная матрица содержит 47 корневых объектов, 76 подчинённых объектов и 18
форм. Вместе с автоматически построенным обратным удалением это 282 операции.
Расширение матрицы изменениями свойств, внешних файлов и расширения увеличит
плоский план более чем до 350 операций.

## Цель

Сгруппировать декларативные операции в смысловые слои и выполнять для каждого
слоя не более двух контрольных циклов:

1. пробный блок с одной явно выбранной операцией;
2. массовый блок со всеми остальными операциями слоя.

Каждый непустой блок должен один раз проверить проект, отправить один частичный
ZIP, подтвердить `unchanged` повторным вызовом и опубликовать одну контрольную
копию. Сценарий должен покрыть жизненный цикл основной конфигурации и
`cfe/Расширение_All`, включая собственные и заимствованные объекты расширения.

Целевое время расширенного сценария на текущей файловой базе — 7–12 минут.
Время выводится как диагностический показатель и не является жёстким порогом,
зависящим от нагрузки машины.

## Границы

В изменение входят:

- декларативная иерархия `слой -> блок -> операция`;
- возобновление с последнего подтверждённого блока;
- один набор validation/sync/unchanged/checkpoint на блок;
- новые операции изменения и удаления в основной конфигурации;
- операции над собственными и заимствованными объектами расширения;
- итоговая полная проверка `cf` и `cfe/Расширение_All`;
- одно намеренное прерывание и реальное восстановление контрольной копии;
- раздельное измерение времени стадий блока.

Не входят:

- переименование объектов, подчинённых объектов, форм и макетов;
- другие e2e-расширения;
- автономный режим для клиент-серверных баз;
- добавление сценария в обычные `pnpm test`, `pnpm test:e2e` или CI;
- проверка каждого свойства каждого metadata-типа: полнота правил остаётся
  ответственностью обычных и round-trip-тестов.

## Декларативная модель

Матрица объявляет операции и группирует их в слои. Исполнитель не содержит
условий по конкретным metadata-типам.

```ts
type ScenarioLayer = {
  key: string
  componentPath: "cf" | `cfe/${string}`
  probeOperationKey: string
  operations: readonly ScenarioOperation[]
}

type ScenarioBlock = {
  key: `${string}:probe` | `${string}:bulk`
  layerKey: string
  componentPath: "cf" | `cfe/${string}`
  operations: readonly ScenarioOperation[]
}
```

Пробный блок содержит ровно операцию `probeOperationKey`. Массовый блок
содержит остальные операции слоя в декларативном порядке. Если операция в
слое одна, массовый блок не создаётся. Представитель задаётся явно, чтобы
результат не зависел от сортировки деклараций.

Операция по-прежнему является набором файловых переходов `before -> after`.
Несколько операций одного блока могут последовательно изменять один файл,
если их состояния образуют непрерывную цепочку. Построитель отклоняет
пересекающиеся переходы, порядок которых неоднозначен.

Построитель плана проверяет:

- уникальность ключей слоёв, блоков и операций;
- существование пробной операции в своём слое;
- единый `componentPath` всех операций блока;
- доступность зависимостей пробной операции до начала пробного блока;
- доступность остальных зависимостей до соответствующей операции;
- отсутствие пустых блоков и циклов;
- корректность последовательных переходов одного пути;
- обратный порядок удаления зависимых объектов и владельцев.

Хэш плана строится по каноническому представлению слоёв, блоков, операций и
файловых переходов.

## Исполнение блока

Для каждого блока исполнитель:

1. последовательно применяет все файловые переходы блока к NKDK-проекту;
2. один раз вызывает `nkdk.validate_project` для всего проекта;
3. один раз вызывает `nkdk.sync_to_infobase` для `componentPath` блока и
   требует `synchronized`;
4. повторяет тот же вызов и требует `unchanged`;
5. заменяет единственную контрольную копию базы и проекта;
6. атомарно записывает ключ завершённого блока в `state.json`;
7. выводит время стадий и список операций блока.

Проверка `unchanged` сохраняется и у пробного, и у массового блока. Она
подтверждает публикацию снимка и отсутствие повторно отправляемого ZIP.

Промежуточные полные выгрузки не выполняются. Основной MCP-сеанс и
платформенный сеанс переиспользуются между блоками, включая переход от `cf` к
расширению. Обновление конфигурации базы выполняется после каждого принятого
частичного ZIP штатным договором платформенного адаптера.

## Состояние и восстановление

Формат состояния повышается до версии 3:

```json
{
  "version": 3,
  "scenario": "partial-sync-layered-matrix",
  "completedBlock": "cf-root-create:bulk",
  "checkpoint": "checkpoints/current",
  "planHash": "..."
}
```

Состояние версии 2 не продолжается автоматически. Без `--reset` сценарий
сообщает о несовместимости и не меняет каталог. С `--reset` он удаляет только
распознанные управляемые каталоги, сохраняя журналы.

Если ошибка происходит до публикации контрольной копии, `completedBlock` не
изменяется. При следующем запуске база и проект восстанавливаются из
`checkpoints/current`, после чего весь незавершённый блок выполняется заново.
Контрольная копия продолжает исключать `.nkdk/platform-sessions` и
`.nkdk/tmp`.

Один объявленный блок используется как проверка реального восстановления. На
его первой попытке тест после успешной частичной загрузки, но до публикации
контрольной копии, намеренно завершает текущий MCP-сеанс. Новый запуск
координатора восстанавливает предыдущую базу и проект, повторяет блок и
получает штатный результат. Инъекция выполняется только тестовым координатором
и не добавляет публичных MCP-параметров.

## Слои основной конфигурации

Сценарий покрывает следующие формы изменений.

### Корень конфигурации

- изменение безопасного свойства конфигурации;
- изменение внешнего файла интерфейса команд;
- сохранность остальных корневых файлов после частичного применения.

### Корневые и подчинённые объекты

- создание всех 47 поддерживаемых корневых типов;
- добавление всех объявленных комбинаций подчинённого типа и владельца;
- изменение хотя бы одного безопасного свойства каждого созданного корневого
  и подчинённого объекта;
- на представителях — изменение типа и длины реквизита, обязательности,
  индексирования и metadata-ссылки;
- перестановка реквизитов, табличных частей, измерений, ресурсов, команд,
  значений перечисления и предопределённых элементов;
- отдельное удаление подчинённых элементов;
- удаление владельца с оставшимися подчинёнными элементами и проверка
  рекурсивного удаления поддерева.

Изменение metadata-ссылки означает замену свойства, указывающего на другой
объект конфигурации, например ссылочного типа реквизита, регистратора регистра
или связанного бизнес-процесса. Это остаётся частью слоя изменения свойств, а
не отдельным механизмом.

### Формы

- создание одной минимальной формы у каждого поддерживающего формы владельца;
- добавление реквизита формы, команды, обработчика, обычного поля, группы и
  таблицы с привязкой к данным;
- изменение свойств и порядка элементов;
- изменение модуля формы;
- отдельное удаление элемента, команды и реквизита с сохранением формы;
- отдельное удаление формы с сохранением владельца;
- удаление другого владельца вместе с существующей формой.

### Макеты

Представителем является текстовый макет:

- создание и изменение текста;
- отдельное удаление макета с сохранением владельца;
- удаление другого владельца вместе с существующим макетом.

### Модули и внешние файлы

- изменение модуля объекта;
- изменение общего модуля;
- добавление, изменение и удаление модуля команды;
- изменение модуля формы;
- изменение свойства владельца при уже существующих модулях, формах,
  макетах и командах без потери их файлов;
- изменение XML-файла прав роли;
- изменение HTML-файла справочной информации;
- изменение двоичного файла общей картинки;
- изменение определения WS-ссылки или пакета XDTO.

Эти операции проверяют текстовые, XML- и двоичные элементы ZIP, а также
сохранность зависимых файлов, которые сами не изменялись.

## Слои расширения

Базовая подготовка загружает `Расширение_All`, затем импортирует в рабочий
проект оба компонента: `cf` и `cfe/Расширение_All`. Операции расширения идут
после слоёв основной конфигурации и синхронизируют только
`cfe/Расширение_All`.

### Собственные объекты

- создание собственного корневого объекта;
- добавление и изменение реквизита, табличной части, команды, формы,
  текстового макета и модуля;
- изменение свойств объекта и подчинённых элементов;
- отдельное удаление формы и макета;
- удаление другого собственного владельца с существующими формой и макетом;
- удаление остальных добавлений и собственного объекта.

### Заимствованные объекты

- добавление существующего объекта основной конфигурации в структуру
  расширения;
- изменение разрешённого свойства и состояния заимствованного свойства;
- изменение свойства, содержащего metadata-ссылку;
- добавление собственных реквизита, команды, формы и текстового макета;
- расширение заимствованной формы реквизитом, командой, элементом и модулем;
- отдельное удаление собственных формы и макета;
- удаление заимствованной формы или макета только из расширения;
- удаление заимствованного владельца из расширения.

После каждого удаления, затрагивающего заимствованный объект, итоговая
проверка `cf` подтверждает, что объект основной конфигурации, его формы и
макеты не изменились.

## Итоговая проверка

После последнего блока сценарий:

1. закрывает основной платформенный сеанс;
2. очищает отдельный проверочный проект;
3. полностью импортирует `cf`;
4. полностью импортирует `cfe/Расширение_All`;
5. сравнивает оба компонента с рабочим NKDK-проектом;
6. закрывает проверочный платформенный сеанс.

XML сравнивается семантически, YAML — без учёта завершающего перевода строки,
обычный текст нормализуется существующим помощником. Любая потеря зависимого
файла, изменение основной конфигурации операцией расширения или несовпадение
структуры завершает сценарий ошибкой.

## Измерение времени и диагностика

Для каждого блока отдельно измеряются:

- применение файловых переходов;
- validation;
- первая частичная синхронизация;
- повторный `unchanged`;
- создание и проверка контрольной копии.

Для итоговой фазы отдельно измеряются закрытие основного сеанса, полные импорты
двух компонентов и сравнение. Итоговый отчёт содержит время слоя, блока, всего
сценария и долю платформенных операций. Ошибка содержит ключи слоя и блока,
список операций, изменённые пути и каталог журналов.

Ожидается 40–50 платформенных циклов вместо более чем 350 при плоском плане.
Фактическое время фиксируется после одного полного автономного прогона. Полный
агентный прогон не обязателен: для агентного режима достаточно пробных блоков
основной конфигурации и расширения, если автономный полный сценарий прошёл.

## Автоматические проверки без платформы

Быстрые тесты фиксируют:

- полноту 47 корневых типов и всех зарегистрированных комбинаций дочерних
  объектов;
- уникальность и зависимости слоёв, блоков и операций;
- явный и корректный `probeOperationKey` каждого слоя;
- отсутствие пустого массового блока у слоя с одной операцией;
- последовательность нескольких изменений одного пути;
- один validation, два sync-вызова и одна контрольная копия на блок;
- отсутствие публикации при ошибке любой операции или стадии блока;
- возобновление со следующего блока после успеха;
- повтор всего блока после сбоя до публикации;
- несовместимость состояния версии 2 без `--reset`;
- выбор `cf` и `cfe/Расширение_All` по декларации блока;
- итоговый импорт и сравнение обоих компонентов;
- сохранность основной конфигурации при удалении заимствованных объектов;
- корректное формирование отчёта времени.

Реальный ручной e2e остаётся единственной проверкой того, что объединённые ZIP
пробных и массовых блоков принимаются платформой, обновляют конфигурацию базы и
возвращаются без потерь полной контрольной выгрузкой.

## Критерии готовности

- каждая операция принадлежит ровно одному декларативному слою;
- каждый многооперационный слой имеет пробный и массовый блок;
- число validation/sync/checkpoint-циклов определяется блоками, а не числом
  операций;
- после каждого блока повторная синхронизация возвращает `unchanged`;
- основной MCP- и платформенный сеансы переиспользуются между блоками;
- состояние версии 3 возобновляет сценарий с последнего завершённого блока;
- намеренное прерывание действительно восстанавливает предыдущую контрольную
  копию и успешно повторяет блок;
- итоговые `cf` и `cfe/Расширение_All` совпадают с рабочим проектом;
- удаление заимствованного владельца не изменяет основную конфигурацию;
- полный автономный прогон формирует отчёт времени и укладывается в
  диагностическую цель 7–12 минут на текущей машине.

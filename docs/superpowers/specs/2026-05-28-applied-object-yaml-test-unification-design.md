# Унификация YAML-тестов прикладных объектов

## Цель

Добавить YAML-покрытие для всех прикладных объектов, у которых уже есть `rules.ts`, но не хватает явных проверок `toYAML`, `fromYAML`, `convertFromXML` или `syncToXML`.

Вместо отдельных однотипных тестовых файлов рядом с каждым объектом вводится общий табличный каркас, похожий на `packages/core/metadata/forms/elements/__tests__/fixtures.ts`. Объект подключается к покрытию одной записью в таблице.

## Границы

Входит:

- общий список сценариев для applied objects;
- общие тесты YAML round-trip на разобранном объекте;
- общие тесты `XML -> YAML` через `convertAppliedObjectFromXML`;
- общие тесты `YAML -> XML` через `syncAppliedObjectToXML`;
- подключение объектов с существующим `rules.ts`;
- точечные YAML-аннотации в `rules.ts`, если тест вскрывает простой и однозначный дефолт или YAML-only/XML-only исключение.

Не входит:

- добавление новых прикладных объектов;
- изменение XML-фикстур;
- ручные `fromXML/toXML/fromYAML/toYAML` переходники без отдельного решения;
- преобразование табличного документа и СКД как отдельный формат данных. Эти задачи остаются отдельными пунктами в `todo.md`.

## Архитектура тестов

Добавляется общий каталог тестов для прикладных объектов:

`packages/core/metadata/appliedObjects/__tests__/`

В нём вводится таблица сценариев:

```ts
type AppliedObjectYAMLFixture = {
  group: string
  name: string
  rule: MetadataItemRule
  importMetaUrl: string
  fixtures?: Array<{ fixture: string; name: string }>
  sync?: {
    name: string
    expectedYAML: string
    expectedFiles: string[]
    binaryExpectedFiles?: string[]
    externalObjectDir?: boolean
  }
}
```

Поле `fixtures` покрывает модельный YAML round-trip: XML fixture импортируется в модель, экспортируется в YAML, затем YAML импортируется обратно и повторный экспорт должен дать тот же объект YAML. Это сравнение намеренно работает с разобранным YAML-представлением, а не со строковым форматированием.

Поле `sync` покрывает файловый цикл:

- `convertFromXML`: `__fixtures__/sync/xml` -> `Свойства.yaml` и внешние файлы YAML-проекта;
- `syncToXML`: `__fixtures__/sync/yaml` -> XML-файлы и внешние файлы.

Для внешних файлов таблица хранит ожидаемые пути. Обычные текстовые файлы сравниваются с нормализацией переводов строк; бинарные файлы сравниваются как `Buffer`.

## Миграция существующих тестов

Уже существующие объектные тесты не удаляются механически в первом шаге, если они содержат особые проверки. Их можно оставить рядом с объектом как специализированные тесты.

Однотипные проверки, которые полностью покрываются общей таблицей, можно переносить в общий каркас. Для объектов вроде регистров накопления и сведений специальные проверки поведения остаются рядом, если они проверяют не только общий цикл, а конкретные правила скрытия дефолтов, внешние модули или особые формы.

## Обработка ошибок

Если общий тест падает:

- простой отсутствующий YAML-дефолт, `toYAML:false/fromYAML:false` или очевидная XML-only ссылка исправляется в `rules.ts`;
- расхождение в подчинённом или чужом metadataItem не чинится в рамках общей задачи без отдельного решения;
- если для объекта нет достаточной sync YAML-фикстуры, добавляется YAML на основе фактического результата `convertFromXML` и затем проверяется обратный `syncToXML`;
- если внешний файл непрозрачен (`Template`, `Module`, `Help`, `Package.bin`), тест проверяет копирование, но не выводит его содержимое в YAML-свойства.

## Проверка

Минимальная проверка после добавления каркаса:

- точечный запуск общего applied object YAML-теста;
- точечные тесты изменённых объектов;
- `pnpm test` из корня перед завершением работы.

## Самопроверка спеки

- Плейсхолдеров и незаполненных разделов нет.
- Границы не требуют новых XML-фикстур и не противоречат запрету на ручные переходники.
- Дизайн допускает частичное подключение объектов: неподготовленный XML-цикл не блокирует весь каркас.
- Табличный документ и СКД оставлены отдельными задачами, чтобы не смешивать форматные преобразования с покрытием существующих `rules.ts`.

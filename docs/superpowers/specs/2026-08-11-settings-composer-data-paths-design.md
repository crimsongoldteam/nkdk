# Пути данных КомпоновщикаНастроек

## Цель

Добавить двустороннее преобразование русских и английских сегментов путей данных для `КомпоновщикНастроекКомпоновкиДанных` и валидировать пути с учётом источника, типов промежуточных и конечного значений, а также вида элемента формы.

Преобразование должно использовать общие механизмы путей данных формы. Частные сведения о `КомпоновщикНастроекКомпоновкиДанных` подключаются через регистрацию типов и свойств, не через условия в общем resolver.

## Источники сведений о типах

- `model.xdtodcscore_root.res` и `settings.xsddcscore_root.res` задают сериализуемый граф объектов: `SettingsComposer`, `Settings`, `UserSettings`, коллекции и элементы коллекций.
- Справка 1С задаёт русские имена, типы свойств и специальные представления формы, которых нет в XSD.
- `ТекущиеДанныеСтруктурыНастроекКомпоновкиДанных` задаёт проекцию текущей строки таблицы структуры настроек. Состав её свойств зависит от типа текущей строки и режима настройки.
- Фикстура общей формы `КомпоновщикНастроек` подтверждает реальные пути и допустимые виды элементов формы.

Одной XSD недостаточно: она не описывает `Элементы.<Имя>.ТекущиеДанные` и специальные проекции текущих строк таблиц.

## Владельцы КомпоновщикаНастроек

Один и тот же граф `КомпоновщикНастроекКомпоновкиДанных` доступен из трёх источников:

| Источник | YAML-путь | XML-путь |
| --- | --- | --- |
| реквизит формы | `КомпоновщикНастроек.Настройки` | `КомпоновщикНастроек.Settings` |
| объект отчёта | `Отчет.КомпоновщикНастроек.Настройки` | `Отчет.SettingsComposer.Settings` |
| динамический список | `Список.КомпоновщикНастроек.Настройки.Отбор` | `Список.SettingsComposer.Settings.Filter` |

`КомпоновщикНастроек` у объекта отчёта и динамического списка является свойством только для чтения типа `КомпоновщикНастроекКомпоновкиДанных`. Это подтверждено справкой 1С, XDTO/XSD и реальными формами конфигураций.

Все три входа переходят в одну регистрацию графа типов. Для объекта отчёта используется существующий `traversalTransition`; прежняя непрозрачная регистрация `SettingsComposer` заменяется типизированным переходом. Для `DynamicList` зарегистрированное свойство `SettingsComposer` проверяется существующим механизмом табличных источников до непрозрачного завершения остальных полей динамического списка. Новый resolver и отдельная проверка типов не создаются.

## Источники путей данных

Пути делятся не по положению элемента в дереве формы, а по источнику первого сегмента.

### Независимый путь от реквизита формы

Путь начинается с имени реквизита формы и далее проходит по реальным свойствам его типа:

```text
КомпоновщикНастроек.Настройки.ПараметрыДанных
```

В XML тот же путь записан английскими именами платформы:

```text
КомпоновщикНастроек.Settings.DataParameters
```

Такой путь не зависит от текущей строки какого-либо элемента формы. От реквизита могут идти не только три верхние таблицы, но и любые вложенные прямые пути, существующие в графе типов реквизита.

### Зависимый путь от текущей строки таблицы

Путь начинается со служебного сегмента `Элементы`, ссылается на элемент формы вида `ТаблицаФормы` и переходит к его текущей строке:

```text
Элементы.КомпоновщикНастроекНастройки.ТекущиеДанные.ПараметрыДанных
```

В XML:

```text
Items.КомпоновщикНастроекНастройки.CurrentData.DataParameters
```

Такой путь зависит от текущей строки указанной таблицы. Для таблицы структуры настроек типом текущих данных является специальная проекция `ТекущиеДанныеСтруктурыНастроекКомпоновкиДанных`, а не просто тип `НастройкиКомпоновкиДанных`.

Сегмент `ТекущиеДанные` разрешён только после ссылки на таблицу формы. Ссылка на поле, группу, кнопку или отсутствующий элемент является ошибкой.

### Опорные таблицы формы

Три таблицы с путями:

```text
КомпоновщикНастроек.Настройки
КомпоновщикНастроек.ПользовательскиеНастройки
КомпоновщикНастроек.ФиксированныеНастройки
```

являются опорными таблицами конкретной фикстуры: они создают контекст текущей строки для зависимых элементов. Это не ограничение платформы и не означает, что только эти три таблицы могут иметь путь от реквизита.

### Сохранение выбранной формы пути

Прямой и зависимый пути могут приводить к значениям совместимого типа, но имеют разную семантику и не нормализуются друг в друга:

```text
КомпоновщикНастроек.Настройки.ПараметрыДанных
Элементы.КомпоновщикНастроекНастройки.ТекущиеДанные.ПараметрыДанных
```

Импорт и экспорт переводят имена сегментов, сохраняя исходную структуру пути.

## Профиль `RowFilter`

Существующий классификатор служебных узлов таблицы продолжает принимать решение по разрешённому конечному типу источника. Поддержка КомпоновщикаНастроек дополняет его следующими случаями:

| Источник таблицы | Профиль | `RowFilter` |
| --- | --- | :---: |
| непосредственный реквизит `DynamicList` | `dynamicList` | нет |
| `DynamicList.SettingsComposer.…` | `none` | нет |
| `ReportObject.SettingsComposer.…` | `none` | нет |
| реквизит формы `SettingsComposer.…` | `none` | нет |
| коллекция КомпоновщикаНастроек через `Элементы.…ТекущиеДанные.…` | `none` | нет |
| `ValueTable`, табличная часть или `RegisterRecordSet` | `rowFilter` | да |

Наблюдение проверено на существующих конфигурациях: в 697 формах найдены 1584 таблицы с прямым путём через `.SettingsComposer`, и ни одна из них не содержит `RowFilter`. Среди 384 таблиц с зависимым путём через `CurrentData` в тех же формах 383 не содержат `RowFilter`.

Одна таблица `Items.КомпоновщикНастроекНастройки.CurrentData.ItemOrder` содержит явный `<RowFilter xsi:nil="true"/>`, тогда как остальные таблицы с тем же конечным типом его не содержат. Это состояние нельзя вывести из типа источника. Для него явно согласовано исключительное транспортное представление:

```yaml
ПутьКДанным: Элементы.КомпоновщикНастроекНастройки.ТекущиеДанные.ЭлементПорядок
ОтборСтрок: !xml
```

Маркер добавляется при XML → YAML только когда исходный `RowFilter` присутствует, а вычисленный профиль равен `none`. При YAML → XML пустой `!xml` создаёт канонический `<RowFilter xsi:nil="true"/>`. Для вычисляемого профиля `rowFilter` маркер не создаётся. `ОтборСтрок` не входит в предметную JSON Schema и не участвует в смысловой валидации; незарегистрированное или непустое применение `!xml` отклоняется транспортным механизмом.

Configuration index не используется для восстановления этого исключения: он не заменяет явно согласованное сохранение невосстановимой формы XML.

## Последовательные зависимости элементов

Таблица сама может иметь зависимый путь. Поэтому разрешение выполняется рекурсивно:

1. найти таблицу по имени после `Элементы`;
2. разрешить её собственный путь данных;
3. определить проекцию текущей строки терминального табличного типа;
4. продолжить обход оставшихся сегментов;
5. обнаруживать циклические ссылки элементов.

Пример цепочки:

```text
КомпоновщикНастроек.Настройки
→ Элементы.КомпоновщикНастроекНастройки.ТекущиеДанные.ЭлементПараметрыДанных
→ Элементы.КомпоновщикНастроекНастройкиЭлементПараметрыДанных.ТекущиеДанные.Параметр
```

## Допустимые виды элементов формы

Совместимость проверяется существующим `allowedKinds` после разрешения терминального типа. Поддержка КомпоновщикаНастроек добавляет платформенные типы в существующие группы, но не создаёт отдельную проверку.

| Терминальные значения | Допустимые виды элементов |
| --- | --- |
| `Settings`, `FixedSettings`, `UserSettings`, `Structure`, `DataParameters`, `ItemDataParameters`, `OutputParameters`, `ItemOutputParameters`, `UserFields`, `ItemUserFields` и пять коллекций `*AvailableFields` | только `ТаблицаФормы` |
| `Filter`, `ItemFilter`, `GroupFields`, `ItemGroupFields`, `Selection`, `ItemSelection`, `Order`, `ItemOrder`, `ConditionalAppearance`, `ItemConditionalAppearance`, `Appearance`, `Fields` | `ТаблицаФормы`, `ПолеВвода`, `ПолеНадписи` |
| значение типа `ПолеКомпоновкиДанных` (`Field`) | `ПолеВвода`, `ПолеНадписи` |
| `ComparisonType`, оба варианта `GroupType`, `Application`, `Placement`, `AdditionType`, `OrderType` | `ПолеВвода`, `ПолеНадписи`, `ПолеПереключателя` |

## Зависящие от типа свойства таблицы

Тип, полученный при разрешении пути таблицы, определяет не только её колонки и проекцию `ТекущиеДанные`, но и доступные свойства самого элемента формы.

Свойство:

```text
ПодробноеОтображениеИменованныхЭлементовНастройки
```

с XML-именем:

```text
SettingsNamedItemDetailedRepresentation
```

предоставляется расширением таблицы формы только для следующих терминальных типов данных:

- `ОтборКомпоновкиДанных` (`DataCompositionFilter`);
- `УсловноеОформлениеКомпоновкиДанных` (`DataCompositionConditionalAppearance`).

Для остальных типов таблиц это свойство недопустимо. Записываемые типозависимые свойства таблиц КомпоновщикаНастроек образуют следующую матрицу:

| Терминальный тип | Дополнительные свойства |
| --- | --- |
| `ОтборКомпоновкиДанных` | `РежимОтображения`, `ПодробноеОтображениеИменованныхЭлементовНастройки` |
| `УсловноеОформлениеКомпоновкиДанных` | `ПодробноеОтображениеИменованныхЭлементовНастройки` |
| `ПользовательскиеНастройкиКомпоновкиДанных` | `РежимОтображения` |

Расширения таблиц доступных полей и значений параметров также предоставляют `ОграниченияИспользования` (`UseRestrictions`), но это свойство доступно только для чтения во время исполнения. Оно не является свойством описания формы и не сериализуется в XML/YAML.

Доступность расширения определяется по разрешённому терминальному типу пути независимо от того, получен он напрямую от реквизита или через цепочку `Элементы.<Таблица>.ТекущиеДанные`.

Это общий договор типозависимых расширений элементов формы: конкретный тип регистрирует набор дополнительных свойств, а нейтральная валидация сопоставляет их с результатом разрешения пути. Наличие свойства в общем типе `ТаблицаФормы` само по себе не делает его допустимым для любой таблицы.

## Общие свойства таблицы вне объёма

Начальные значения `РежимВыбора`, `РазрешитьНачалоПеретаскивания`, `РазрешитьПеретаскивание`, `Ширина`, отображения, линий, автозаполнения и состава команд зависят от поведения Конфигуратора, но остаются изменяемыми общими свойствами `ТаблицаФормы`.

Эта работа не выводит их заново из пути данных, не добавляет для них контекстную валидацию и не меняет существующие `implicitValueYAML`. Round-trip продолжает сохранять их по действующим общим правилам таблицы.

## Диагностики

Используются действующие категории и место привязки диагностики — свойство `ПутьКДанным` конкретного элемента формы:

- неизвестный владелец в начале пути — `неизвестный корень`;
- неизвестное свойство зарегистрированного объекта — `неизвестный реквизит`;
- неизвестный член табличной проекции — `неизвестная колонка`;
- `Items` / `CurrentData` в YAML — предложение русских `Элементы` / `ТекущиеДанные`;
- ссылка `Элементы.<Имя>.ТекущиеДанные` на элемент без табличного источника — существующая диагностика отсутствующего источника текущих данных;
- рекурсивная цепочка элементов — `обнаружен цикл CurrentData`;
- разрешённый тип не подходит виду элемента — существующая диагностика `тип …, ожидается …` из политики `allowedKinds`.

Для этих случаев не вводятся отдельные коды ошибок, зависящие от КомпоновщикаНастроек.

## Проверки

- модульно проверить все 68 пар имён в обе стороны и убедиться, что пользовательские имена элементов и реквизитов не переводятся;
- проверить одинаковое разрешение графа от реквизита формы, `ReportObject.SettingsComposer` и `DynamicList.SettingsComposer`;
- проверить все группы проекций текущей строки, включая цепочку из нескольких таблиц и обнаружение цикла;
- проверить матрицу `ТаблицаФормы` / `ПолеВвода` / `ПолеНадписи` / `ПолеПереключателя` положительными и отрицательными примерами;
- проверить типозависимые свойства таблицы и отсутствие новых ограничений для общих свойств таблицы;
- проверить обычные профили `RowFilter` и исключительный round-trip `ОтборСтрок: !xml` в обе стороны;
- прогнать round-trip новой XML-фикстуры и существующие проверки конфигурации и расширения.

## Реестр расхождений

### 1. `doc/InformationRegisters/ДанныеДокументовПредприятия.xml`

Фрагмент: ресурс `Содержание`.

XML-источник содержит явный пустой синоним:

```xml
<Synonym/>
```

После YAML-цикла появляется синоним по имени:

```xml
<Synonym>
  <v8:item>
    <v8:lang>ru</v8:lang>
    <v8:content>Содержание</v8:content>
  </v8:item>
</Synonym>
```

Причина: общий механизм уже умеет сохранять пустой `Synonym` из `source`, когда YAML опускает `Синоним`; это покрыто тестом `preserves explicit empty synonym from source when YAML omits synonym` в `packages/core/metadata/orchestration/property/fromYAML.test.ts`. Проблема локальная: `packages/core/metadata/commonObjects/metadataRegisterResource/register.ts` после импорта вызывает `dropImplicitEmptySynonym(properties)`, и эта функция удаляет сохраненный `{ items: {} }`.

Вывод: нужно убрать или сузить `dropImplicitEmptySynonym` для ресурсов регистров так, чтобы `source`-пустой `Synonym` доходил до XML, а намеренное восстановление синонима из имени продолжало работать.

### 2. `doc/InformationRegisters/РеестрДокументовПредприятия.xml`

Фрагмент: ресурс `Содержание`.

Расхождение полностью совпадает с пунктом 1: пустой XML `Synonym` ресурса превращается в синоним `ru=Содержание`.

Вывод: это не дефект общего source fallback, а такой же локальный эффект `dropImplicitEmptySynonym` в коллекции ресурсов.

### 3. `doc/Subsystems/ДокументыИФайлы/Ext/CommandInterface.xml`

Фрагмент: `CommandsVisibility`, `CommandsPlacement`, `CommandsOrder` с повторяющимися `Command name="0"`.

В XML несколько записей имеют одинаковое имя команды, но разный контекст группы/порядка. В `RootCommandInterfaceRules` свойства `ВидимостьКоманд` и `РазмещениеКоманд` представлены как `Record<string, ...>`, то есть ключом выступает имя команды. Для повторяющихся `name="0"` это не биективно: одна YAML-запись не может сохранить несколько XML-записей с тем же ключом.

Вывод: для командного интерфейса подсистемы нужен YAML-формат списка записей, который сохраняет повторы и порядок. Карты подходят только для уникальных команд.

### 4. `doc/Subsystems/СовместнаяРабота/Ext/CommandInterface.xml`

Фрагмент: такой же тип изменений `Command name="0"` в `CommandInterface.xml`.

Причина совпадает с пунктом 3: повторяющиеся команды проходят через YAML-карты по имени и теряют индивидуальность.

Вывод: исправлять нужно общий тип `RootCommandInterface`, а не отдельную подсистему; направление - переход от карт к спискам записей для командных свойств.

### 5. `erp/Ext/StandaloneConfigurationContent.bin`

Файл удаляется целиком после YAML -> XML.

Причина: корневой бинарный файл не описан как часть YAML-модели конфигурации.

Вывод: `StandaloneConfigurationContent.bin` нужно включить в модель корня конфигурации, а не прятать как reference-only исключение.

### 6. `erp/InformationRegisters/АналитикаПланированияСтруктуры.xml`

Фрагмент: измерение `Организация`.

XML-источник содержит `<Synonym/>`, после YAML-цикла появляется `ru=Организация`.

Причина совпадает с пунктами 1-2, но для коллекции измерений: `packages/core/metadata/commonObjects/metadataRegisterDimension/register.ts` удаляет сохраненный `{ items: {} }` через свой `dropImplicitEmptySynonym`.

Вывод: решение должно покрывать ресурсы и измерения регистров одним механизмом, не ломая существующее восстановление синонима из имени.

### 7. `erp/.../РисковыеСобытия/Ext/CommandInterface.xml`

Файл: `Subsystems/ПодсистемыУХ/Subsystems/ИнтеграцияУправлениеРисками/Subsystems/РисковыеСобытия/Ext/CommandInterface.xml`.

Фрагмент: удаление/перестановка нескольких `Command name="0"` и `Command name="0:744f..."`.

Причина: тот же класс дефекта `RootCommandInterface`, но здесь видны не только автоматические `0`, а еще команды с составным идентификатором. Повторяемость и позиция в списке важнее простого имени.

Вывод: будущий тест для списочного YAML-формата должен включать и `name="0"`, и UUID-подобные команды с одинаковым префиксом/контекстом.

### 8. `erp/.../ЦенныеБумагиБУ/Ext/CommandInterface.xml`

Файл: `Subsystems/ПодсистемыУХ/Subsystems/ЦенныеБумагиБУ/Ext/CommandInterface.xml`.

Фрагмент: перестановка UUID-команд и изменение одного `xr:Common` с `false` на `true`.

Причина: `CommandInterfaceVisibilityMap` хранит видимость как карту по имени команды. При коллизиях и восстановлении из reference часть записей сопоставляется не с тем элементом, из-за чего меняется не только порядок, но и значение видимости.

Вывод: исправление через списки записей должно проверять не только порядок XML, но и неизменность `xr:Common`/role visibility.

### 9. `small/DataProcessors/.../МастерФормированияЗаявкиНаПодключениеУпрощенное/Ext/Form.xml`

Фрагмент: удаляются две кнопки `ЕстьКЭП` и `НетКЭП` с `id=1314/1316`; первая пара `id=1823/1824` остается.

В коде уже есть `packages/core/metadata/forms/knownAnomalies.ts`, который знает последовательность четырех кнопок и восстанавливает `id`/`ExtendedTooltip id`. Это предыдущий локальный костыль для ошибочного XML конкретной конфигурации.

Согласованная трактовка: исходный XML содержит ошибочный дубль. В YAML должно быть по одному `ЕстьКЭП` и `НетКЭП`; общую логику повторяющихся `childItems` менять не нужно.

Вывод: оставить направление на локальный known-anomaly костыль/подавление diff для этой формы, не расширять общую модель `childItems` ради ошибочного дубля и не менять XML-источник.

### 10. `small/Ext/Help.xml`

Файл удаляется целиком.

Причина: это корневая справка конфигурации, а существующая поддержка `commonObjects/help` подключена для прикладных объектов, например документов, но не для корня конфигурации.

Вывод: корневая конфигурация должна синхронизировать `Ext/Help.xml` как Help-объект в YAML-модели корня.

### 11. `small/Ext/Help/ru.html`

Файл удаляется целиком.

Причина связана с пунктом 10: HTML-страницы справки живут рядом с `Ext/Help.xml`, но при замене XML-каталога результатом временного XML не переносятся.

Вывод: решение для корневой справки обязано сохранять и envelope `Ext/Help.xml`, и содержимое `Ext/Help/`.

### 12. `small/Ext/Logo.xml`

Файл удаляется целиком.

Причина: корневая картинка конфигурации не подключена к модели корня и не сохраняется как reference-only.

Вывод: нужно покрыть корневой `Logo` через существующий тип внешних картинок в YAML-модели корня.

### 13. `small/Ext/Logo/Picture.png`

Бинарный файл удаляется целиком.

Причина связана с пунктом 12: метаданные картинки и бинарное тело должны сохраняться вместе. Сохранение только `Logo.xml` будет неполным.

Вывод: решение должно копировать/синхронизировать весь каталог `Ext/Logo/`, включая бинарное содержимое.

### 14. `small/InformationRegisters/ЖурналДействийКассира/.../Form.xml`

Файл: `InformationRegisters/ЖурналДействийКассира/Forms/ФормаСписка/Ext/Form.xml`.

Фрагмент: два значения DCS меняют тип:

```diff
- <dcscor:value xsi:type="xs:dateTime">0001-01-01T00:00:00</dcscor:value>
+ <dcscor:value xsi:type="dcscor:Field">01.01.0001 00:00:00</dcscor:value>
```

В `DcsMetadataTypedValueRegistry.dateTime.detect` строка `01.01.0001 00:00:00` распознается как `dateTime`. Но импорт затем идет через `importPrimitiveFromYAML -> importMetadataValueFromYAML`, и на выходе в этом контексте получается значение, которое экспортируется как `dcscor:Field`.

Вывод: `DcsMetadataTypedValue` должен сам сохранить тип `dateTime` после собственного детекта и не отдавать строковую дату на переинтерпретацию общему `MetadataValue`.

### 15. `trade/Ext/StandaloneConfigurationContent.bin`

Файл удаляется целиком.

Причина совпадает с пунктом 5, но на другой конфигурации. Это подтверждает, что `StandaloneConfigurationContent.bin` - общий корневой внешний файл, а не особенность ERP.

Вывод: покрывать надо все конфигурационные каталоги, где есть этот файл, через модель корня конфигурации.

### 16. `.agents/skills/round-trip-yaml/round-trip.sh --all-configs`

Симптом: общий запуск нашел `DIFF_COUNT=15`, но тела diff для конфигураций, обработанных до последней, были пустыми.

Причина: скрипт в цикле делает `git -C "${NKDK_XML_REPO}" restore .` перед обработкой следующей конфигурации. Он сохраняет `DIFF_FILES`, `DIFF_FILE_DIRS`, `DIFF_FILE_YAML_DIRS`, но печатает diff позже через `git -C "${active_dir}" diff`. К этому моменту изменения предыдущих конфигураций уже откатились.

Вывод: `--all-configs` должен сохранять содержимое diff сразу после обработки каждой конфигурации и печатать уже сохраненный текст. Одних путей файлов недостаточно.

## Предлагаемая последовательность будущего плана

1. Исправить диагностику `--all-configs`, чтобы следующие разборы не требовали ручных per-config запусков.
2. Разделить реальные модельные дефекты на независимые серии:
   - `Synonym` с явным пустым XML через сужение `dropImplicitEmptySynonym`;
   - `RootCommandInterface` с повторяющимися командами через списочный YAML-формат;
   - корневые внешние файлы `Ext/*` через YAML-модель корня;
   - локальный known anomaly для ошибочных дублей `CommandBarButton`;
   - `DcsMetadataTypedValue` dateTime без переинтерпретации через общий `MetadataValue`.
3. Для каждой серии сначала добавить узкий красный тест на минимальном XML/YAML-примере, затем исправлять код.
4. После каждой серии прогонять focused tests и соответствующий `round-trip-yaml` каталог (`doc`, `erp`, `small`, `trade`).
5. Перед закрытием серии прогнать `pnpm test` из корня рабочего дерева.

## Границы

- Не изменять существующие XML-фикстуры: они источник истины.
- Не добавлять новые правила `fromXML/toXML/fromYAML/toYAML` без необходимости; если достаточно `rules.ts`, использовать его.
- Не добавлять `order` в `rules.ts`, если порядок можно вывести из reference.
- Не исправлять все группы одним большим изменением: причины независимы и требуют отдельных проверок.
- Для корневых внешних файлов выбран полноценный YAML-путь: не добавлять их как новые reference-only исключения.
- По дублям `ЕстьКЭП`/`НетКЭП` не менять общую логику `childItems`: это локальная ошибка исходной конфигурации.

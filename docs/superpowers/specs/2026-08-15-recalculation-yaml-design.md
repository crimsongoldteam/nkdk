# Перерасчёты регистров расчёта в YAML

## Цель

Заменить непрозрачное хранение XML перерасчёта смысловым YAML-представлением и
проверять связи измерений перерасчёта так же, как их ограничивает платформа 1С.
XML-фикстуры остаются источником истины для состава полей, порядка XML и
поведения расширений.

## Размещение в проекте

Перерасчёт остаётся файловым дочерним объектом регистра расчёта:

```text
РегистрРасчета/<ИмяРегистра>/Перерасчеты/<ИмяПерерасчета>/Свойства.yaml
РегистрРасчета/<ИмяРегистра>/Перерасчеты/<ИмяПерерасчета>/МодульНабораЗаписей.bsl
```

Ему соответствует XML:

```text
CalculationRegisters/<ИмяРегистра>/Recalculations/<ИмяПерерасчета>.xml
CalculationRegisters/<ИмяРегистра>/Recalculations/<ИмяПерерасчета>/Ext/RecordSetModule.bsl
```

Список имён из XML родительского регистра используется для обнаружения
дочерних объектов, но содержимое перерасчёта не дублируется в
`Свойства.yaml` регистра. Существующий промежуточный файл `Recalculation.xml`
исключается из проектного представления после включения смыслового импорта.

## Смысловое представление

Перерасчёт содержит только свойства, подтверждённые XDTO и фикстурами:

- `Синоним`;
- `Комментарий`;
- `РежимУправленияБлокировкойДанных`;
- `Измерения`;
- внешний `МодульНабораЗаписей.bsl`.

Свойство `Использование` удаляется из правила: его нет в XDTO, выгрузках и
интерфейсе конфигуратора.

Для измерения перерасчёта вводится отдельное правило, не являющееся обычным
измерением регистра. Его YAML-свойства:

- `Синоним`;
- `Комментарий`;
- `ИзмерениеРегистра`;
- `ДанныеВедущихРегистров`.

Пример канонического YAML:

```yaml
Синоним: Перерасчет все свойства
Комментарий: Комментарий
РежимУправленияБлокировкойДанных: Автоматический
Измерения:
  ИзмерениеПерерасчетаВсеСвойства:
    Синоним: Синоним
    Комментарий: Комментарий
    ИзмерениеРегистра: ИзмерениеВсеСвойства
    ДанныеВедущихРегистров:
      - ИзмерениеВсеСвойства
      - РегистрРасчета.РегистрРасчетаВедущий.Измерение.ИзмерениеПараметрыВыбора
  ИзмерениеПоУмолчанию:
    ИзмерениеРегистра: ИзмерениеПоУмолчанию
    ДанныеВедущихРегистров:
      - ИзмерениеПоУмолчанию
      - РегистрРасчета.РегистрРасчетаВедущий.Измерение.ИзмерениеПараметрыВыбора
```

Ссылка на измерение текущего регистра сокращается до имени. Ссылка на поле
другого регистра содержит русский корень, имя регистра, вид поля и имя поля.
XML продолжает использовать каноническую платформенную форму
`CalculationRegister.<Имя>.<Dimension|Attribute>.<Имя>`.

## Правила ссылок

`ИзмерениеРегистра` обязательно для собственного измерения перерасчёта и
может указывать только на измерение родительского регистра расчёта. Реквизит,
измерение другого регистра и отсутствующее поле недопустимы.

`ДанныеВедущихРегистров` — список измерений и реквизитов регистров расчёта.
Ресурсы и поля объектов других видов недопустимы. Текущий регистр также может
быть источником ведущих данных.

Типы `ИзмерениеРегистра` и элементов `ДанныеВедущихРегистров` не сравниваются.
Платформа принимает, например, связь строкового измерения основного регистра
со ссылочным измерением ведущего регистра.

Проверяется полнота явно настроенных связей. Множество участвующих ведущих
регистров строится как объединение владельцев всех ссылок из
`ДанныеВедущихРегистров` всех измерений одного перерасчёта. Каждый такой
регистр должен присутствовать хотя бы одной ссылкой в каждом измерении этого
перерасчёта. Иначе платформа не может заполнить полную строку таблицы
перерасчёта и сообщает, что в измерениях неверно заданы связи с этим регистром.

Например, если `РегистрРасчетаВедущий` указан у первого из двух измерений
перерасчёта, он должен быть указан и у второго. Выбранные поля могут иметь
разные типы. Один регистр может быть представлен измерением или реквизитом.

Полная связь из фикстуры выглядит так:

| Измерение перерасчёта | `РегистрРасчетаВсеСвойства` | `РегистрРасчетаВедущий` |
|---|---|---|
| `ИзмерениеПерерасчетаВсеСвойства` | `ИзмерениеВсеСвойства` | `ИзмерениеПараметрыВыбора` |
| `ИзмерениеПоУмолчанию` | `ИзмерениеПоУмолчанию` | `ИзмерениеПараметрыВыбора` |

Ошибка возникает, если оставить ячейку пустой, например указать
`РегистрРасчетаВедущий` для `ИзмерениеПерерасчетаВсеСвойства`, но не указать
ни одного его поля для `ИзмерениеПоУмолчанию`. Если регистр отсутствует во
всех строках, он не участвует в этом перерасчёте и заполнять его столбец не
требуется.

Обычный `metadataTarget` отвечает за синтаксис ссылки, допустимого владельца,
вид поля и существование цели. Предметная проверка перерасчёта группирует уже
разрешённые цели по владельцам и проверяет прямоугольность этой связи. Частные
условия по перерасчётам не добавляются в нейтральные слои runtime.

Регистры, полностью отсутствующие во всех `ДанныеВедущихРегистров`, не
считаются ошибкой: для них автоматическое формирование записей этого
перерасчёта просто не настраивается. Поэтому вычислять теоретическое множество
ведущих регистров через граф планов видов расчёта не требуется.

## Расширения конфигурации

Собственные перерасчёты расширения используют те же правила. У заимствованного
измерения перерасчёта `ИзмерениеРегистра` и `ДанныеВедущихРегистров` могут
отсутствовать в XML и YAML: значения наследуются из основной конфигурации.
Экспорт расширения не материализует унаследованные значения и сохраняет
`ObjectBelonging` и `ExtendedConfigurationObject` существующим механизмом
расширений.

## Поток данных

При XML → YAML топология обнаруживает XML каждого перерасчёта, применяет его
правило и пишет отдельный `Свойства.yaml`; модуль набора записей копируется как
внешний файл. На втором проходе ссылки сокращаются или переводятся в русскую
форму через общий индекс.

При YAML → XML имя дочернего объекта восстанавливается из пути, свойства и
измерения преобразуются правилом перерасчёта, а ссылки возвращаются в
платформенную форму. Модуль возвращается в прежний каталог `Ext`.

При проверке проекта локальный проход проверяет YAML и форму ссылок. Общий
проход разрешает родительский регистр и поля ведущих регистров, группирует
ссылки по владельцам и проверяет присутствие каждого участвующего регистра во
всех измерениях перерасчёта.

## Диагностики

Используются существующие диагностики битых и недопустимых `metadataTarget`-
ссылок. Для неполной связи добавляется предметная диагностика, которая
указывает:

- путь к измерению перерасчёта;
- имя отсутствующего ведущего регистра;
- что в `ДанныеВедущихРегистров` требуется его измерение или реквизит.

Если отдельная ссылка не разрешилась, проверка полноты не создаёт для неё
дополнительную каскадную ошибку: сначала сообщается существующая диагностика
битой ссылки.

Отсутствие унаследованных связей у заимствованного измерения расширения не
является ошибкой.

## Проверки

1. XML → YAML по обновлённой фикстуре подтверждает отдельный файл перерасчёта,
   два узких измерения и русские ссылки.
2. YAML → XML восстанавливает `RegisterDimension` и коллекцию
   `LeadingRegisterData` с правильными `xr:MDObjectRef`.
3. Узкие тесты целей отклоняют чужое `ИзмерениеРегистра`, ресурс ведущего
   регистра и объект другого вида.
4. Проверка проекта принимает связи разных типов, если каждый участвующий
   регистр представлен в каждом измерении перерасчёта.
5. Проверка проекта отклоняет случай, когда ведущий регистр указан в первом,
   но отсутствует во втором измерении перерасчёта.
6. Проверка расширения принимает отсутствующие унаследованные связи у
   заимствованного измерения и не записывает их при обратном экспорте.
7. Топология подтверждает `Свойства.yaml` и модуль набора записей без
   `Recalculation.xml`.
8. Сквозной round-trip для основной конфигурации и расширения
   подтверждает смысловое совпадение XML перерасчётов; загрузка в 1С в
   рамки этой работы не выполняется.

Итоговая проверка включает `pnpm type-check`, `pnpm test`,
`pnpm test:architecture:rules`, `pnpm test:architecture` и
`pnpm duplicates -- --base origin/develop`.

## Границы изменения

- Существующие XML-фикстуры не переписываются вручную и остаются источником
  истины.
- Случайные изменения окончаний строк после выгрузки не включаются в изменение.
- `!xml` для перерасчётов и их измерений не вводится.
- Общие типы правил и параметры построителей не расширяются, если договор
  выражается существующими правилами и предметной проверкой.
- `.agents/architecture.md` менять не требуется: новая проверка следует уже
  описанному разделению локальной проверки и проверки связей проекта.

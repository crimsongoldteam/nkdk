# Дизайн: ограничения TypeDescription в YAML-схеме

Тип: дизайн-документ.

## Контекст

Сейчас YAML-схема `TypeDescription` слишком широкая: поле типа описано как
`string | string[] | { ИдентификаторТипа }`. Из-за этого JSON Schema и
`validateFile` принимают почти любую строку, хотя в 1С набор допустимых типов
зависит от объекта и свойства.

Первая версия нужна для реквизитов справочника. Позже тот же механизм должен
распространиться на остальные `TypeDescription` проекта.

Ограничения должны задаваться в `rules` объекта. Для справочника это означает
отдельное правило реквизита справочника, а не изменение общего
`MetadataAttributeRules` для всех владельцев.

## Цели первой версии

- Добавить декларативные ограничения к property-rule типа `TypeDescription`.
- Сделать строгую JSON Schema: неизвестные YAML-типы не проходят валидацию.
- Включить ограничения только для `Реквизиты` справочника.
- Сохранить текущий YAML-формат: одиночный тип строкой, составной тип массивом
  строк.
- Валидировать примитивный DSL типов: `Строка(10)`, `Число(10, 2)`,
  `ПоложительноеЧисло(10, 2)` и похожие формы.
- Вернуть ограничения в JSON Schema, чтобы команда `schema` и `validateFile`
  использовали один источник истины.

## Не цели первой версии

- Не проверять существование конкретного объекта конфигурации. Например,
  `Справочник.Несуществующий` проходит schema-валидацию как корректная форма
  типа; проверка наличия цели остаётся отдельной проектной/графовой
  диагностикой.
- Не менять XML-фикстуры и XML round-trip.
- Не добавлять отдельный пост-валидатор с доменными сообщениями об ошибках.
  Ошибки первой версии идут через TypeBox diagnostics.
- Не распространять ограничения на документы, табличные части, DCS, формы и
  другие `TypeDescription` до отдельного шага.

## Правила

В `TypeDescriptionPropertyRule` добавляется поле ограничений, условно:

```ts
type TypeDescriptionPropertyRule = BasePropertyRule & {
  type: "TypeDescription"
  allowedTypes?: TypeDescriptionAllowedTypes
}
```

`TypeDescriptionAllowedTypes` использует внутренние английские имена типов.
Русские YAML-имена, шаблоны, описания и графовые подсказки выводятся из общего
реестра типов.

Форма значения:

```ts
type TypeDescriptionAllowedType =
  | TypeDescriptionRuleName
  | `${TypeDescriptionRuleName}.*`

type TypeDescriptionAllowedTypes = readonly TypeDescriptionAllowedType[]
```

`TypeDescriptionRuleName` — имя из реестра `TypeDescriptionRules`, например
`string`, `decimal`, `CatalogRef`, `DefinedType`.

Пример правила для реквизита справочника:

```ts
allowedTypes: [
  "string",
  "decimal",
  "date",
  "boolean",
  "ValueStorage",
  "UUID",
  "CatalogRef",
  "CatalogRef.*",
  "DocumentRef",
  "DocumentRef.*",
  "EnumRef",
  "EnumRef.*",
  "DefinedType.*",
  "Characteristic.*",
  "ExternalDataSourceTableRef.*",
  "ExternalDataSourceCubeDimensionTableRef.*",
]
```

`allowedTypes` отвечает только на вопрос «что разрешено в этом свойстве».
Свойства самих типов — как они выглядят в YAML, можно ли использовать их в
составном типе, какой Cypher-запрос помогает найти реальные варианты — не
дублируются в каждом правиле, а описываются один раз в общем реестре
`TypeDescription`.

Для первой версии создаётся `MetadataCatalogAttributeRules` на основе текущего
`MetadataAttributeRules`. Отличие — свойство `type` получает
`allowedTypes`. Коллекция `MetadataAttributes`, используемая в
`MetadataCatalogRules.attributes`, должна строить JSON Schema и YAML-импорт по
`MetadataCatalogAttributeRules`.

Общие `MetadataAttributeRules`, `MetadataDocumentAttributeRules` и
`MetadataTabularSectionAttributeRules` в первой версии не ужесточаются.

`importTypeDescriptionFromYAML` тоже должен учитывать `rule.allowedTypes`, если
они заданы. Это нужно, чтобы прямой импорт YAML не расходился со схемой:
некорректный тип должен быть отвергнут до XML-экспорта, а не падать позже как
неизвестный внутренний тип.

## Реестр свойств типов

Существующий `TypeDescriptionRules` уже связывает внутренний тип и enterprise
имя, например `CatalogRef -> Справочник`, `DefinedType -> ОпределяемыйТип`,
`decimal -> Число`. Первую версию ограничений нужно строить вокруг этих
внутренних имён.

Для генерации YAML Schema к этому реестру добавляется слой schema-метаданных:

- какие YAML-формы генерируются для внутреннего типа;
- какие `description` и `examples` вернуть в JSON Schema;
- запрещён ли тип в составном значении;
- какой `x-nkdk-graph.query` подсказывает ИИ, где найти реальные варианты.

Примитивы не требуют графа. Их структура описывается в реестре один раз:

```ts
string -> Строка | Строка(длина) | ФиксированнаяСтрока(длина)
decimal -> Число | Число(длина) | Число(длина, точность)
decimal -> ПоложительноеЧисло | ПоложительноеЧисло(длина) | ПоложительноеЧисло(длина, точность)
date -> Дата | Время | ДатаВремя
boolean -> Булево
```

В `description` для `Число(10, 2)` обязательно объясняется, что первый аргумент
— длина, второй — точность. ИИ не должна выводить это из регулярного выражения.

Ссылочные типы, зависящие от конкретной конфигурации, получают графовую
подсказку. Формат расширения JSON Schema минимальный:

```json
{
  "x-nkdk-graph": {
    "query": "MATCH (n:MetadataObject {kind: 'MetadataCatalog'}) RETURN n.name ORDER BY n.name"
  }
}
```

Запрос не обязан возвращать готовую YAML-строку. Он задаёт основу для поиска
реальных имён в графе проекта, а форму YAML задаёт соседний `pattern` ветки
schema. Например ветка `CatalogRef.*` сама знает, что значение пишется как
`Справочник.<имя>`.

## Семантика групп

Для групп ссылочных типов нужны два независимых разрешения:

- общий тип группы, например `Справочник`;
- конкретный тип группы, например `Справочник.Контрагенты`.

Если оба разрешения включены, комбинация в составном типе валидна:

```yaml
Тип:
  - Справочник
  - Справочник.Контрагенты
```

Это соответствует поведению 1С: флажок может стоять и на группе целиком, и на
конкретном объекте этой группы.

## Запреты составности

Часть типов можно выбрать только как одиночный тип. В первой версии фиксируем:

- `ХранилищеЗначения`;
- `УникальныйИдентификатор`;
- конкретные `ОпределяемыйТип.<имя>`;
- конкретные `Характеристика.<имя>`;
- таблица внешнего источника данных;
- таблица измерения куба внешнего источника данных.

Общие `ОпределяемыйТип` и `Характеристика` вообще не разрешаются: выбрать можно
только конкретные `ОпределяемыйТип.<имя>` и `Характеристика.<имя>`.

Запрет составности — свойство типа в общем реестре, а не настройка конкретного
property-rule. Поэтому `allowedTypes` не содержит флагов вроде `composite` или
`singleOnly`; правило свойства только перечисляет разрешённые имена типов.

Для внешних источников запрет составности задаётся по шаблону, а не по
конкретной конфигурации:

- `ВнешнийИсточникДанных<Имя>.Таблица<Имя>`;
- `ВнешнийИсточникДанных<Имя>.Куб<Имя>.ТаблицаИзмерения<Имя>`.

Это не совпадает с текущим общим форматированием `TypeDescriptionRules`, где
есть внутренние базовые типы `ExternalDataSourceTableRef` и
`ExternalDataSourceCubeDimensionTableRef` с enterprise-именами
`ВнешнийИсточникДанныхТаблица` и
`ВнешнийИсточникДанныхКубТаблицаИзмерения`. Для первой версии нужен отдельный
YAML-адаптер для этих шаблонов:

- YAML `ВнешнийИсточникДанныхВсеСвойства.ТаблицаВсеСвойства` импортируется как
  внутренний тип
  `ExternalDataSourceTableRef.ВнешнийИсточникДанныхВсеСвойства.ТаблицаВсеСвойства`;
- YAML
  `ВнешнийИсточникДанныхВсеСвойства.КубВсеСвойства.ТаблицаИзмеренияВсеСвойства`
  импортируется как внутренний тип
  `ExternalDataSourceCubeDimensionTableRef.ВнешнийИсточникДанныхВсеСвойства.КубВсеСвойства.ТаблицаИзмеренияВсеСвойства`;
- обратный YAML-экспорт должен возвращать короткую пользовательскую форму без
  `ВнешнийИсточникДанныхТаблица.` и
  `ВнешнийИсточникДанныхКубТаблицаИзмерения.`.

Примеры:

```yaml
Тип: ОпределяемыйТип.ДенежнаяСумма
```

валидно.

```yaml
Тип:
  - Строка
  - ОпределяемыйТип.ДенежнаяСумма
```

невалидно, потому что `ОпределяемыйТип.<имя>` запрещён в составном типе.

## JSON Schema

Схема `Тип` строится как `anyOf` из одиночной строки и массива строк. Свободный
`string` не используется.

Условный вид:

```json
{
  "anyOf": [
    {
      "description": "Одиночный тип",
      "anyOf": [
        {
          "type": "string",
          "pattern": "^Строка(?:\\([1-9][0-9]*\\))?$",
          "description": "Строка или Строка(длина). Длина — максимальное количество символов.",
          "examples": ["Строка", "Строка(10)"]
        },
        {
          "type": "string",
          "pattern": "^ФиксированнаяСтрока\\([1-9][0-9]*\\)$",
          "description": "ФиксированнаяСтрока(длина). Длина — точное количество символов.",
          "examples": ["ФиксированнаяСтрока(10)"]
        },
        {
          "type": "string",
          "pattern": "^Число(?:\\([1-9][0-9]*(?:\\s*,\\s*[0-9]+)?\\))?$",
          "description": "Число, Число(длина) или Число(длина, точность). Длина — общее количество цифр, точность — количество дробных цифр.",
          "examples": ["Число", "Число(10)", "Число(10, 2)"]
        },
        {
          "type": "string",
          "pattern": "^ПоложительноеЧисло(?:\\([1-9][0-9]*(?:\\s*,\\s*[0-9]+)?\\))?$",
          "description": "ПоложительноеЧисло, ПоложительноеЧисло(длина) или ПоложительноеЧисло(длина, точность). Длина — общее количество цифр, точность — количество дробных цифр.",
          "examples": ["ПоложительноеЧисло", "ПоложительноеЧисло(10)", "ПоложительноеЧисло(10, 2)"]
        },
        { "type": "string", "enum": ["Дата", "Время", "ДатаВремя", "Булево", "ХранилищеЗначения", "УникальныйИдентификатор"] },
        { "type": "string", "const": "Справочник" },
        {
          "type": "string",
          "pattern": "^Справочник\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*$",
          "x-nkdk-graph": {
            "query": "MATCH (n:MetadataObject {kind: 'MetadataCatalog'}) RETURN n.name ORDER BY n.name"
          }
        },
        { "type": "string", "pattern": "^Документ(?:\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*)?$" },
        { "type": "string", "pattern": "^Перечисление(?:\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*)?$" },
        { "type": "string", "pattern": "^ОпределяемыйТип\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*$" },
        { "type": "string", "pattern": "^Характеристика\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*$" },
        { "type": "string", "pattern": "^ВнешнийИсточникДанных[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*\\.Таблица[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*$" },
        { "type": "string", "pattern": "^ВнешнийИсточникДанных[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*\\.Куб[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*\\.ТаблицаИзмерения[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*$" }
      ]
    },
    {
      "description": "Составной тип",
      "type": "array",
      "minItems": 1,
      "uniqueItems": true,
      "items": {
        "anyOf": [
          { "type": "string", "pattern": "^Строка(?:\\([1-9][0-9]*\\))?$" },
          { "type": "string", "pattern": "^ФиксированнаяСтрока\\([1-9][0-9]*\\)$" },
          { "type": "string", "pattern": "^Число(?:\\([1-9][0-9]*(?:\\s*,\\s*[0-9]+)?\\))?$" },
          { "type": "string", "pattern": "^ПоложительноеЧисло(?:\\([1-9][0-9]*(?:\\s*,\\s*[0-9]+)?\\))?$" },
          { "type": "string", "enum": ["Дата", "Время", "ДатаВремя", "Булево"] },
          { "type": "string", "const": "Справочник" },
          {
            "type": "string",
            "pattern": "^Справочник\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*$",
            "x-nkdk-graph": {
              "query": "MATCH (n:MetadataObject {kind: 'MetadataCatalog'}) RETURN n.name ORDER BY n.name"
            }
          },
          { "type": "string", "pattern": "^Документ(?:\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*)?$" },
          { "type": "string", "pattern": "^Перечисление(?:\\.[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*)?$" }
        ]
      }
    }
  ]
}
```

В реализации повторяющиеся куски должны собираться программно, а не
дублироваться строками в каждом объекте. Общий шаблон имени берётся из
`METADATA_NAME_YAML_PATTERN`:

```ts
const metadataName = "[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*"
```

Примитивные числовые параметры должны совпадать с текущим YAML DSL
`TypeDescription`: пробелы вокруг запятой допустимы.

`x-nkdk-graph` — проектное расширение. Обычный JSON Schema валидатор его
игнорирует, а ИИ и скиллы могут читать `query`, чтобы понять, в какую область
графа идти за реальными типами текущей базы.

## Валидация

`validateFile` уже компилирует и применяет TypeBox-схему, поэтому отдельный
валидатор не нужен. Если `exportTypeDescriptionToJSONSchema` учтёт
`rule.allowedTypes`, строгая ошибка появится и в `nkdk schema`, и в
валидации YAML.

Ожидаемые примеры:

```yaml
Реквизиты:
  Контрагент:
    Тип:
      - Справочник
      - Справочник.Контрагенты
```

валидно.

```yaml
Реквизиты:
  Идентификатор:
    Тип:
      - Строка
      - УникальныйИдентификатор
```

невалидно.

```yaml
Реквизиты:
  Таблица:
    Тип:
      - Строка
      - ВнешнийИсточникДанныхВсеСвойства.ТаблицаВсеСвойства
```

невалидно.

```yaml
Реквизиты:
  Таблица:
    Тип: ВнешнийИсточникДанныхВсеСвойства.ТаблицаВсеСвойства
```

валидно по форме.

## Тесты

Нужны тесты на контракты:

1. JSON Schema справочника содержит строгую схему для `Реквизиты.*.Тип`.
2. `validateFile` принимает `Справочник` вместе со
   `Справочник.Контрагенты` в составном типе.
3. `validateFile` принимает primitive DSL: `Строка(10)`, `Число(10, 2)`,
   `ПоложительноеЧисло(10, 2)`.
4. `validateFile` отклоняет неизвестную строку типа.
5. `validateFile` отклоняет общий `ОпределяемыйТип` и общий
   `Характеристика`.
6. `validateFile` принимает одиночный `ОпределяемыйТип.<имя>` и
   `Характеристика.<имя>`.
7. `validateFile` отклоняет `ОпределяемыйТип.<имя>` и
   `Характеристика.<имя>` внутри массива.
8. `validateFile` принимает одиночные типы внешнего источника данных по
   шаблонам.
9. `validateFile` отклоняет типы внешнего источника данных внутри массива.
10. Схема документа пока остаётся широкой для `Реквизиты.*.Тип`, чтобы первая
    версия не меняла поведение документов.

## Открытые вопросы для продолжения разбора

- Полный список групп, доступных для реквизита справочника, нужно перенести из
  скриншотов в явное правило `MetadataCatalogAttributeRules`.
- Нужно уточнить, какие группы разрешают общий тип, какие только конкретные
  элементы, а какие не разрешены вовсе.
- Нужно решить, остаётся ли форма `{ ИдентификаторТипа: [...] }` допустимой для
  реквизитов справочника. Текущее предположение первой версии: не разрешать,
  пока нет явного правила.

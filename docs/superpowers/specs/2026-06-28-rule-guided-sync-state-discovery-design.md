# Ускорить sync state через правила проекта

## Контекст

После перехода `init-sync-state` на прямое чтение YAML и XXH3-64 построение `.nkdk-sync.yaml` для ERP занимает около 100 секунд. Команда уже не импортирует XML заново, поэтому оставшаяся стоимость состоит из обхода большого YAML-дерева, чтения файлов и записи итогового YAML.

Текущий обход читает все файлы под `yamlDir`, а затем исключает отдельные служебные случаи. Это слишком широкий договор: состояние XML-синхронизации должно отражать файлы metadata-проекта, которые описаны правилами, а не любые файлы, случайно лежащие в каталоге.

## Цель

Сделать построение списка файлов для `.nkdk-sync.yaml` rule-guided:

- брать структуру YAML-проекта из существующих `rules.ts`-источников;
- не обходить весь `yamlDir`;
- не индексировать файлы вне описанной metadata-структуры;
- хешировать найденные кандидаты параллельно через ограниченный пул задач;
- сохранить формат state `xxh3-64:<hex>` и детерминированный итоговый YAML.

## Не цели

- Не читать `.gitignore` и не вводить договор "индексировать то, что хранится в Git".
- Не добавлять `mtime`/size-кэш.
- Не менять формат `.nkdk-sync.yaml`.
- Не менять публичный CLI-договор `nkdk init-sync-state <yaml-dir> <xml-dir>`.
- Не включать `Миграции/*.yaml` в sync state.
- Не добавлять worker threads.

## Источник структуры

Список кандидатов строится из существующего metadata-договора:

- `metadataProjectSpecs` задает top-level metadata-каталоги через `itemTypePrefix`;
- `describeMetadataRuleResources(rule)` описывает ресурсы правила: properties YAML, внешние XML-файлы, asset-каталоги и динамические внешние ресурсы;
- `directoryStructure.ts` уже содержит проектные соглашения вроде `Свойства.yaml`, `Формы/<ИмяФормы>/Форма.yaml` и вложенных подсистем.

Новый код не должен дублировать руками большой список прикладных объектов. Он должен переиспользовать эти источники или вынести общий helper рядом с ними.

## Построение кандидатов

Алгоритм строит относительные пути файлов-кандидатов:

1. Добавить корневой YAML конфигурации, если он существует.
2. Для каждого `MetadataProjectSpec` найти каталог `<itemTypePrefix>`.
3. Для каждого объекта внутри каталога добавить `<itemTypePrefix>/<ИмяОбъекта>/Свойства.yaml`, если файл существует.
4. Для форм объекта читать только объявленный каталог `Формы`: добавлять `Формы/<ИмяФормы>/Форма.yaml` и файлы формы, которые описаны ресурсами/динамическими внешними ресурсами.
5. Для внешних ресурсов правила читать только объявленные правилом файлы или подкаталоги внутри конкретного объекта.
6. Для подсистем поддержать вложенную структуру `Подсистемы/<ИмяПодсистемы>/...` по существующему проектному договору.

Если правило описывает динамический ресурс без точного имени файла, разрешен ограниченный обход соответствующего объявленного подкаталога. Обход всего проекта запрещен.

Неизвестные файлы вне описанной структуры не попадают в `.nkdk-sync.yaml`. Это осознанное поведение: если файл должен участвовать в XML-синхронизации, он должен быть выражен в правилах проекта.

## Параллельное хеширование

После сбора кандидатов:

- нормализовать пути к `/`;
- удалить дубликаты;
- отсортировать относительные пути;
- читать и хешировать существующие файлы через `p-limit`;
- использовать дефолтную параллельность `16`;
- возвращать тот же `Record<string, string>` со значениями `xxh3-64:<16 hex>`.

Порядок выполнения чтения может быть параллельным, но порядок итогового state остается стабильным за счет сортировки.

## API

`hashProjectFiles` остается основной точкой входа:

```ts
hashProjectFiles(projectDir, { concurrency?: number })
```

`initializeXmlSyncState` может принимать необязательный `hashConcurrency` и передавать его дальше, но CLI на этом этапе использует дефолт. Публичные аргументы CLI не меняются.

## Ошибки

Если `yamlDir` не существует или не читается, команда завершается ошибкой. Если конкретный файл-кандидат исчез между сбором списка и чтением, можно пропустить его только если он больше не существует; остальные ошибки чтения должны всплывать, чтобы не писать неполный state молча.

## Проверка

Тесты должны покрыть:

- state строится только по rule-guided кандидатам, а неизвестные файлы рядом с проектом не попадают в результат;
- `Миграции/*.yaml` не попадают в state;
- кандидаты из известных metadata-каталогов и форм попадают в state;
- параллельный лимит не меняет результат относительно последовательного набора кандидатов;
- `init-sync-state` продолжает писать `xxh3-64` state без изменения CLI-договора.

Ручная проверка ERP:

```bash
/usr/bin/time -p pnpm --filter @nakidka/cli dev -- init-sync-state /Users/nikita/git/nkdk-yaml /Users/nikita/git/round-trip/erp
```

Ожидаемый результат: время заметно меньше текущих ~100 секунд, state содержит только файлы metadata-проекта, описанные правилами, и не содержит миграции.

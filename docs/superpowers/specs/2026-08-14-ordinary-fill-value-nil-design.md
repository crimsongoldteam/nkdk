# `xsi:nil` в `FillValue` обычных полей

## Контекст

Полный round-trip Storekeeper меняет XML-форму пустого значения заполнения у
строковых измерений и ресурсов регистра:

```diff
- <FillValue xsi:nil="true"/>
+ <FillValue xsi:type="xs:string"/>
```

Обе формы дают одно и то же неявное смысловое значение, поэтому обычного поля
`ЗначениеЗаполнения` в YAML нет. Однако выбрать исходную XML-форму только по
типу нельзя. Для единственного строкового типа канонической формой является
пустой `xs:string`, а исходный `xsi:nil` должен сохраняться явным транспортным
маркером:

```yaml
ЗначениеЗаполнения: !xml/value Nil
```

Такой договор уже действует для `MetadataAttribute`, но обработчик привязан к
конкретному `itemType`. Поля регистров и другие обычные поля используют то же
свойство `FillValue`, однако не подключены к этому договору полностью.

## Подтверждённое распределение

Сканирование всех конфигураций `round-trip-compact/cf`, кроме `all`, дало
следующее количество строковых полей с `<FillValue xsi:nil="true"/>`. Для
Storekeeper учтён исходный XML до диагностического round-trip.

| `itemType` | Количество | Состояние |
|---|---:|---|
| `MetadataAttribute` | 25 246 | договор уже действует |
| `MetadataRegisterAttribute` | 2 681 | договор отсутствует |
| `MetadataRegisterDimension` | 2 610 | договор отсутствует |
| `MetadataRegisterResource` | 4 362 | договор отсутствует |
| `MetadataCommonAttribute` | 33 | договор отсутствует |

У остальных перечисленных ниже семейств строковый `xsi:nil` в исследованных
конфигурациях не найден. Они входят в договор, потому что используют то же
обычное типизированное свойство `FillValue`; отсутствие примера в текущем
наборе конфигураций не должно менять семантику свойства.

## Граница обычных полей

Единый договор применяется к следующим `itemType`:

| Семейство | `itemType` |
|---|---|
| обычный реквизит | `MetadataAttribute` |
| общий реквизит | `MetadataCommonAttribute` |
| реквизит адресации задачи | `MetadataTaskAddressingAttribute` |
| поле регистра | `MetadataRegisterAttribute`, `MetadataRegisterDimension`, `MetadataRegisterResource` |
| признаки учёта | `AccountingFlag`, `ExtDimensionAccountingFlag` |
| поле внешнего источника данных | `MetadataExternalDataSourceField`, `MetadataExternalDataSourceCubeDimension`, `MetadataExternalDataSourceCubeResource` |

Список закрытый. `StandardAttributeDescription` не является обычным полем и
сохраняет отдельный договор пустых XML-форм. Другие свойства типа
`MetadataValue` не получают поддержку `Nil` автоматически только из-за общего
типа значения.

## YAML-договор

Для каждого перечисленного обычного поля действуют одинаковые правила:

| Эффективный тип и XML | YAML |
|---|---|
| единственный `Строка`, `<FillValue xsi:nil="true"/>` | `ЗначениеЗаполнения: !xml/value Nil` |
| единственный `Строка`, `<FillValue xsi:type="xs:string"/>` | поле отсутствует |
| единственный нестроковый тип, `<FillValue xsi:nil="true"/>` | поле отсутствует |
| составной тип, `<FillValue xsi:nil="true"/>` | поле отсутствует |

`!xml/value Nil` описывает только XML-форму отсутствующего значения. Он не
превращает `Nil` в смысловое значение и не добавляется в configuration index.

Маркер допустим только у обычного поля с единственным эффективным строковым
типом. Для нестрокового или составного типа он является ошибкой валидации. Пока
определяемый тип не разрешён, действующая зависимая проверка сообщает, что
эффективный тип установить нельзя.

Особый `!xml/value Null` полей внешнего источника данных остаётся отдельным
транспортным значением и не объединяется с `Nil`.

## Импорт XML → YAML

- Обработчик определяет эффективный тип после построения полного элемента.
- Строковый `xsi:nil` преобразуется в `!xml/value Nil`, а не удаляется как
  обычное неявное значение.
- Канонический пустой `xs:string` удаляется из YAML и восстанавливается по
  эффективному типу.
- Нестроковый и составной `xsi:nil` также не создаёт YAML-поля.
- Преобразование одинаково для всех `itemType` из закрытого списка и не
  зависит от reference XML или снимка конфигурации.

## Экспорт YAML → XML

- `ЗначениеЗаполнения: !xml/value Nil` создаёт ровно
  `<FillValue xsi:nil="true"/>`.
- При отсутствии `ЗначениеЗаполнения` сохраняется действующая политика наличия
  `FillValue` конкретного правила. Если элемент должен быть создан, единственный
  строковый тип использует канонический `<FillValue xsi:type="xs:string"/>`, а
  нестроковый или составной тип — `<FillValue xsi:nil="true"/>`.
- Договор не заставляет необязательные поля внешнего источника данных создавать
  отсутствующий XML-элемент.
- Явное смысловое значение продолжает экспортироваться обычным обработчиком
  `MetadataValue`.

## Архитектурная граница

Договор остаётся в предметном модуле `commonObjects/fillValue`. Реализация
должна подключить существующие анализ, импорт, структурные ссылки и
транспортный маркер к каждому перечисленному `itemType`, не добавляя частных
условий в нейтральные слои runtime.

Новые поля в `BasePropertyRule`, `PropertyRule` и параметры построителей rules.ts
не требуются. Существующие XML-фикстуры не изменяются.

Реестр `.agents/xml-anomalies.md` должен перечислять все обычные `itemType`, для
которых разрешён `!xml/value Nil`.

## Проверки будущей реализации

1. Для каждого `itemType` из закрытого списка регистрационная проверка
   подтверждает поддержку `Nil` и зависимой обработки `fillValue`.
2. Импорт строкового `xsi:nil` у реквизита, измерения и ресурса регистра создаёт
   `!xml/value Nil`.
3. Импорт строкового `xsi:nil` у общего реквизита создаёт
   `!xml/value Nil`.
4. Представители адресации задачи, признаков учёта и внешнего источника данных
   используют тот же договор.
5. YAML → XML восстанавливает `xsi:nil` без reference и configuration index.
6. Отсутствующее YAML-поле сохраняет действующую политику XML-присутствия; для
   создаваемого элемента единственный строковый тип использует пустой
   `xs:string`.
7. `Nil` у нестрокового и составного типа отклоняется валидацией.
8. `StandardAttributeDescription` и `!xml/value Null` сохраняют действующее
   поведение.
9. Полный round-trip исходного регистра Storekeeper не меняет десять
   обнаруженных `FillValue`.

## Не входит в изменение

- новые разновидности XML-аномалий и новые YAML-теги;
- изменение классификации смысловых значений `FillValue`;
- вывод XML-формы из reference или configuration index;
- исправление других round-trip расхождений Storekeeper.

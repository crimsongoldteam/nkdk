# XML-договор управляемой формы без reference

## Статус

Согласованная первая часть XML-договора формы. В документ включены выводы,
подтверждённые анализом конфигураций в `/Users/nikita/git/round-trip-compact/cf`
и явно согласованные решения. Остальные расхождения разбираются и добавляются
последовательно.

## Цель

Восстанавливать XML управляемых форм из YAML без исходного XML-каталога и без
параметра `reference`. Различия между явным XML-значением и значением,
представленным отсутствующим тегом, должны описываться в договоре rules.ts или
сохраняться явно в YAML.

Исходные XML-фикстуры не изменяются. Для анализа используются конфигурации
`acc`, `all`, `doc`, `erp`, `small` и `trade` из
`/Users/nikita/git/round-trip-compact/cf`; всего исследовано 34 322 файла
`Form.xml`.

## Общий принцип

Отсутствующий XML-тег и отсутствующий YAML-ключ не считаются одним состоянием
автоматически. Если они означают разные значения, правило должно описывать оба
неявных значения. Если значение невозможно однозначно вывести из YAML и
контекста формы, оно должно оставаться явным в YAML.

Reference XML и служебные признаки присутствия XML-тегов не используются.

## Подтверждённые договоры

### `Button.Type`

`Type` является обязательным явным свойством кнопки и не имеет значения по
умолчанию в YAML.

Во всех исследованных конфигурациях `Type` присутствует у каждой из 227 492
кнопок. Обнаружены значения:

- `CommandBarButton` — 191 788;
- `UsualButton` — 25 599;
- `Hyperlink` — 9 711;
- `CommandBarHyperlink` — 394.

Следствие для правил: `UsualButton` нельзя исключать из YAML через
`implicitValueYAML`. Импорт XML сохраняет любое значение `Type`, а валидация
YAML требует это поле у каждой кнопки.

Документация платформы объявляет `Button.Type` без default, а перечисление
`ManagedFormButtonType` не содержит значения `Auto`.

### `ClientApplicationForm.UseForFoldersAndItems`

Присутствие свойства определяется типом основного реквизита формы:

- для `cfg:CatalogObject.*` и
  `cfg:ChartOfCharacteristicTypesObject.*` XML-тег присутствует всегда;
- для остальных типов основного реквизита и для форм без основного реквизита
  XML-тег отсутствует всегда.

Среди исследованных форм обнаружено 2 241 значение `Items` и 216 значений
`Folders`. `Folders` остаётся явным значением YAML. Если значение отсутствует
в YAML, но основной реквизит имеет один из двух перечисленных типов, XML должен
получить `UseForFoldersAndItems=Items`. Для остальных форм отсутствующий
YAML-ключ не создаёт XML-тег.

Контекстное условие относится к правилам формы и не должно добавлять знания о
формах или типах прикладных объектов в общую orchestration.
Локальное правило читает признак `ОсновнойРеквизит` из сырого YAML формы, а
нормализованный тип берёт из уже построенного `formDataPathIndex`. Это не
дублирует преобразование имён типов YAML и поддерживает составные описания
типов; подходящими считаются owner kinds `СправочникОбъект` и
`ПланВидовХарактеристикОбъект`.
Документация объявляет `UseForFoldersAndItems` необязательным свойством без
default, поэтому значение `Items` восстанавливается именно из контекста формы,
подтверждённого конфигурациями, а не как безусловный default платформы.

### `FormGroup.EnableContentChange`

В XML присутствует только явное значение `true`: оно обнаружено 8 188 раз.
Явное значение `false` не обнаружено; в 341 579 группах тег отсутствует.

Отсутствующий XML-тег означает `false`: XDTO-модель из `1c_res` задаёт
`default=false`. При этом default свойства в Конфигураторе равен `true`, что
подтверждается снимком палитры свойств. Поэтому XML и YAML имеют разные
неявные значения, а действующий `implicitValueYAML=true` корректен:

| Исходное представление | Результат |
|---|---|
| XML `true` | YAML-ключ отсутствует |
| XML-тег отсутствует | явный YAML `false` |
| YAML-ключ отсутствует | XML `true` |
| явный YAML `false` | XML-тег отсутствует |

Один договор применяется к `UsualGroup`, `Page`, `ColumnGroup`, `Pages`,
`CommandBar`, `ButtonGroup` и `Popup`. Правило использует
`implicitValueYAML=true` и `implicitValueXML=false`; 341 579 отсутствующих
XML-тегов становятся явными значениями `Ложь` в YAML. Reference не требуется.

### `FormField.AutoCellHeight`

Свойство относится к ячейкам таблиц. Из 3 315 явных
`AutoCellHeight=true`:

- 3 293 находятся внутри элемента `Table`;
- 22 находятся вне визуального `Table`, но их `DataPath` имеет вид
  `Items.*.CurrentData.*` и указывает на текущую строку таблицы.

При этом у аналогичных элементов таблиц тег отсутствует 169 200 раз. Всего у
поддержанных `InputField`, `LabelField`, `PictureField` и `CheckBoxField` тег
отсутствует 327 731 раз. Поэтому принадлежность таблице или путь к текущей
строке определяет область применения свойства, но сама по себе не определяет
его XML-представление.

Отсутствующий XML-тег означает `false`, и default Конфигуратора также равен
`false`. Это подтверждается снимком свойства табличной ячейки в
Конфигураторе, документацией платформы и существующими полными XML-фикстурами
полей. Явное XML `false` в исследованных конфигурациях не встречается.

Текущее `implicitValueYAML=true` ошибочно. Договор должен быть симметричным и
компактным:

| Исходное представление | Результат |
|---|---|
| XML `true` | явный YAML `true` |
| XML-тег отсутствует | YAML-ключ отсутствует |
| явный YAML `true` | XML `true` |
| YAML-ключ отсутствует | XML-тег отсутствует |

Правило использует `implicitValueYAML=false` и `implicitValueXML=false`.
Существующие YAML-ожидания фикстур, в которых отсутствующий XML-тег
представлен явным `Ложь`, должны быть приведены к этому договору. В YAML
останутся только 3 315 явных значений `Истина`.

Выводить значение по типу реквизита, `DataPath` или основному реквизиту формы
нельзя: у одинаковых контекстов одновременно встречаются явный `true` и
отсутствующий XML-тег.

### `RadioButtonField.RadioButtonType`

`RadioButtonField.RadioButtonType` присутствует у каждого из 6 969
исследованных элементов:

- `Auto` — 4 983;
- `Tumbler` — 1 377;
- `RadioButtons` — 609;
- отсутствующих значений — 0.

Все элементы `RadioButtonField` расположены вне `Table`. Значение представления
не выводится из `DataPath` или типа реквизита: для `Auto`, `RadioButtons` и
`Tumbler` одновременно встречаются как минимум `xs:decimal`, `xs:string`,
ссылки на перечисления и вложенные пути. Это выбор внешнего вида элемента, а
не следствие типа данных.

`Auto` является самостоятельным значением системного перечисления: платформа
сама выбирает представление элемента. Это значение преобладает, но его
присутствие в XML обязательно и не обозначается отсутствующим тегом.
Документация конфигурационной модели задаёт для `RadioButtonType` default
`Auto`.

Есть отдельная неоднозначность XML-псевдонима. `RadioButton` и
`RadioButtons` оба преобразуются в YAML `Переключатель`. Во всех исследованных
конфигурациях используется `RadioButtons`; существующая XML-фикстура проекта
также подтверждает поддержку формы `RadioButton`. Явность YAML-поля не
различает эти два XML-написания. Существующий configuration index сохраняет
исходный неканонический псевдоним без reference XML; при создании XML только из
авторского YAML должно использоваться одно выбранное каноническое значение.

В отличие от `Button.Type`, это перечисление содержит значение `Auto`.
Поэтому `Auto` остаётся неявным YAML-default, но восстанавливается в XML
обязательным явным тегом:

| Исходное представление | Результат |
|---|---|
| XML `Auto` | YAML-ключ отсутствует |
| XML `RadioButton`/`RadioButtons` | явный YAML `Переключатель` |
| XML `Tumbler` | явный YAML `Тумблер` |
| YAML-ключ отсутствует | XML `Auto` |
| явный YAML `Переключатель` | канонический XML переключателя |
| явный YAML `Тумблер` | XML `Tumbler` |

Правило сочетает `implicitValueYAML=Auto` и обязательный XML-default `Auto`.
`RadioButtonType` не становится обязательным полем YAML. Сохранение
неканонического XML-псевдонима переключателя остаётся отдельной обязанностью
существующего configuration index.

### `PredefinedItem.Code` и `PredefinedItem.Description`

У каждого предопределённого элемента XML-поля `Code` и `Description`
структурно обязательны. В модели XDTO они объявлены в `PredefinedItemBase`
без `lowerBound="0"`. Это относится ко всем наследникам: элементам
справочников, планов видов характеристик, планов счетов и планов видов расчёта.

Полные XML исследованных конфигураций подтверждают схему: у каждого
предопределённого элемента присутствуют оба тега — либо с текстом, либо как
пустые элементы. Отсутствующих тегов в исходных XML не найдено. В round-trip
`doc` потеряно 975 пустых `<Code/>` и 208 пустых `<Description/>`.

Пустая строка не несёт полезной информации в YAML, поэтому оба значения
остаются компактными:

| Исходное представление | Результат |
|---|---|
| XML `<Code/>` / `<Description/>` | YAML-ключ отсутствует |
| XML с непустым текстом | явное значение YAML |
| YAML-ключ отсутствует | обязательный пустой XML-тег |
| явное значение YAML | XML-тег с этим значением |

Для обоих правил используется существующий декларативный механизм
`defaultValueXMLRaw: ""`. Специальное знание о предопределённых элементах в
общие metadata-слои не добавляется. `PredefinedCode` продолжает отдельно
обрабатывать числовой код с `xsi:type`; пустой код преобразуется в отсутствие
YAML-значения и восстанавливается правилом как пустой XML-тег.

### Контейнер `Characteristics`

`Characteristics` является обязательным XML-контейнером у всех типов, в
которых он объявлен моделью XDTO. Свойство не имеет `lowerBound="0"` у
справочника, документа, перечисления, плана обмена, бизнес-процесса, задачи,
планов счетов, видов расчёта и видов характеристик, а также таблицы и куба
внешнего источника данных.

В round-trip `doc` потеряно 748 пустых `<Characteristics/>`:

- перечисления — 469;
- справочники — 249;
- документы — 27;
- планы видов характеристик — 3.

Непустой контейнер представлен в YAML массивом `Характеристики`. Пустой массив
полезной информации не несёт и в YAML не записывается:

| Исходное представление | Результат |
|---|---|
| XML `<Characteristics/>` | YAML-ключ отсутствует |
| XML с характеристиками | явный массив YAML |
| YAML-ключ отсутствует | обязательный `<Characteristics/>` |
| непустой массив YAML | XML-контейнер с характеристиками |

Текущий `defaultValueXMLRaw: {}` при `xmlParents` создаёт только родительский
путь и не создаёт сам элемент `Characteristics`. Ранее пустой контейнер
восстанавливался из configuration index, поэтому узкие тесты со снимком
импорта проходили, но преобразование без reference и без снимка теряет его.

Договор выражается существующим параметром правил:
`defaultValueXMLRaw: ""`. Такое правило уже используется для
`MetadataExchangePlan`; оно должно быть одинаковым у всех владельцев
`Characteristics`. Изменять общий metadata-слой или добавлять новый параметр
правила не требуется.

### `StyleItem.Type`

`StyleItem.Type` является обязательным XML-полем: в модели XDTO оно объявлено
без `lowerBound="0"` и без default. Допустимы три значения: `Font`, `Color` и
`Border`. Во всех исследованных конфигурациях каждый элемент стиля содержит
явный `<Type>`; отсутствующих значений не найдено.

В `doc` все 357 элементов стиля имеют XML-тип: 90 `Font` и 267 `Color`.
Round-trip теряет только 90 `<Type>Font</Type>`, потому что правило исключает
`Font` из YAML как default, но не задаёт обязательное значение для XML.

В YAML внешний `Тип: Шрифт` остаётся неявным: это default Конфигуратора, а
тип дополнительно однозначно выражен дискриминатором `Значение.Вид: Шрифт`.
`Цвет` и `Рамка` продолжают записываться явно:

| Исходное представление | Результат |
|---|---|
| XML `Font` | YAML-ключ отсутствует |
| XML `Color` / `Border` | явный YAML `Цвет` / `Рамка` |
| YAML-ключ отсутствует | обязательный XML `Font` |
| явный YAML `Цвет` / `Рамка` | XML `Color` / `Border` |

Правило сочетает существующие `implicitValueYAML: "Font"` и
`defaultValueXML: "Font"`. Это не меняет договор `Button.Type`, где YAML-поле
обязательно и не имеет значения по умолчанию: одинаковое XML-имя относится к
разным объектам и разным системным перечислениям.

### Дополнения таблицы `GanttChartField`

Вложенная `Table` поля диаграммы Ганта в XML Конфигуратора содержит три
структурных одиночных дополнения:

- `SearchStringAddition`;
- `ViewStatusAddition`;
- `SearchControlAddition`.

Проверены все 18 таблиц диаграмм Ганта в конфигурациях `all`, `erp` и `doc`.
Каждая содержит полную тройку. Это верно и для трёх таблиц, у которых
`SearchStringLocation`, `ViewStatusLocation` и `SearchControlLocation` равны
`None`, поэтому наличие дополнений не выводится из значений свойств положения.
В остальных 15 таблицах свойства положения отсутствуют, а дополнения всё равно
присутствуют.

Схема XDTO формально допускает отсутствие этих элементов у `Table`, но полный
XML Конфигуратора показывает более узкий структурный default именно для
вложенной таблицы `GanttChartField`. В YAML пустые автоматически именуемые
дополнения не записываются; пользовательские свойства дополнения записываются
в соответствующем YAML-объекте.

| Исходное представление | Результат |
|---|---|
| каноническое пустое XML-дополнение | YAML-ключ отсутствует |
| XML-дополнение с пользовательскими свойствами | явный YAML-объект |
| YAML-ключ отсутствует у таблицы диаграммы Ганта | каноническое XML-дополнение |
| явный YAML-объект | XML-дополнение с заданными свойствами |

Текущий `GanttChartFieldTable` содержит защитный `transformOutput`, который
удаляет автоматически построенные дополнения, когда они отсутствуют в YAML и
reference XML. После отказа от reference это условие удаляет всю тройку. В
round-trip `doc` поэтому одновременно потеряны три дополнения формы
`Catalogs/ПроектныеЗадачи/Forms/ФормаПланаПроекта`.

Специальный фильтр должен быть удалён. Существующий переходник
`createSingletonElementYAMLToXMLNestedRule` и `TableRules` уже строят
канонические имена, `AdditionSource`, `ContextMenu`, `ExtendedTooltip` и
идентификаторы одиночных элементов. Отдельные правила fromXML/toXML и знания о
диаграмме Ганта в общем metadata-слое не требуются.

Reference для выбора порядка не нужен. Импорт и fallback экспорта должны
использовать подтверждённый единый порядок
`Command, Type, Attribute, CommandGroup, Index, DefaultVisible, Visible`.
Отсутствующие поля просто пропускаются; порядок оставшихся полей остаётся
каноническим.

## Проверка результата

Для каждого согласованного договора нужны проверки четырёх направлений, где
они применимы:

- явное XML-значение → YAML;
- отсутствующий XML-тег → YAML;
- явное YAML-значение → XML;
- отсутствующий YAML-ключ → XML.

Обязательные поля дополнительно проверяются валидацией YAML. Условия,
зависящие от основного реквизита формы, проверяются минимум для подходящего и
неподходящего типа. После реализации выполняются целевые тесты, полный
`pnpm test` и round-trip конфигурации `doc`; расхождения `Period`,
`TopLevelParent` и `RowFilter` при этой диагностике рассматриваются отдельно.

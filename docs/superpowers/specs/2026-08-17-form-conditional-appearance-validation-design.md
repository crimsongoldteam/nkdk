# Проверка условного оформления управляемой формы

## Цель

Добавить смысловую проверку `УсловноеОформлениеРеквизитов` управляемой формы:

- закрытого набора параметров оформления и типов их значений;
- полей, к которым применяется оформление;
- левого и правого операндов отбора;
- существования и доступности путей типа `Поле`;
- совместимости типов двух разрешённых операндов.

Проверка должна использовать общий resolver путей формы и расширить его
универсальным декларативным графом составных типов. Отдельный resolver только
для условного оформления не создаётся.

## Исследованные данные

В `/Users/nikita/git/round-trip-compact/cf` найдено 6 113 форм с верхнеуровневым
условным оформлением и 25 564 операнда типа `Field`. Глубина пути достигает
пяти сегментов. Среди корневых типов представлены `ValueTable`, `ValueTree`,
объекты и ссылки метаданных, наборы записей регистров, `ValueList`,
`ConstantsSet`, `SettingsComposer`, `GanttChart`, `Planner`, `StandardPeriod` и
`StandardBeginningDate`.

Правый операнд бывает полем, булевым, строковым, числовым или датовым
значением, а также `DesignTimeValue`, `StandardBeginningDate`, `ValueListType`
и `Order`. Слева, помимо поля, в реальных конфигурациях встречаются булевы и
числовые константы.

2 350 полей имеют корень-реквизит типа `DynamicList`. Ещё 2 885 полей имеют
корень, отсутствующий среди явно сохранённых реквизитов формы. Среди них есть
платформенно и программно создаваемые источники, а также сохранённые пути,
которые невозможно достоверно восстановить только по XML формы.

Документация `DataCompositionFilterAvailableField` подтверждает, что доступное
поле несёт собственный тип значения, допустимые сравнения и доступные
значения. Тип правого значения зависит от левого поля.

## Границы

В работу входят:

- верхнеуровневое `УсловноеОформлениеРеквизитов` управляемой формы;
- условное оформление реквизита формы типа `DynamicList`;
- общий декларативный граф составных типов;
- отдельные представления доступных полей для назначений resolver;
- перенос существующей модели `SettingsComposer` на общий граф;
- графы `Planner`, `StandardPeriod` и `StandardBeginningDate`;
- разрешение путей в левом и правом операндах типа `Поле`;
- типовая совместимость двух успешно разрешённых операндов;
- классификация неразрешимых импортированных операндов через `!xml/value`;
- классификация неразрешимых импортированных оформляемых элементов через
  `!xml/reference`;
- документирование временных ограничений.

В работу не входят:

- матрица допустимости `ВидСравнения × тип значения`;
- автоматическое исправление импортированных аномальных путей;
- проверка совместимости, если тип хотя бы одного операнда неизвестен;
- смысловая проверка `AppearanceFields.Текст` и `AppearanceFields.Формат` со
  значением типа `Поле`, уже отдельно указанная в `restrictions.md`.

## Общий типизированный граф

### Разделение ответственности

Граф типов описывает структуру значений независимо от потребителя. Каждый
узел принадлежит самому типу, а не родительскому объекту и не условному
оформлению. Например:

```text
DataCompositionSettingsComposer
└─ Settings → DataCompositionSettings
   └─ Filter → DataCompositionFilter
      └─ RightValue → any
```

`DataCompositionSettings` владеет свойством `Filter`, а
`DataCompositionFilter` — свойством `RightValue`. Это позволяет повторно
использовать те же узлы из других корней и проходить пути произвольной
глубины.

### Декларация в rules.ts

Граф регистрируется в `dataPaths` собранных metadata rules. Обычные
`BasePropertyRule` и `PropertyRule` не расширяются.

Декларативный договор:

```ts
defineTypedDataPathGraph({
  types: {
    Planner: structuredType({
      aliases: ["Планировщик"],
      members: [
        member({
          internal: "BeginOfRepresentationPeriod",
          yaml: "НачалоПериодаОтображения",
          target: terminal("dateTime"),
        }),
        member({
          internal: "ShowCurrentDate",
          yaml: "ОтображатьТекущуюДату",
          target: terminal("boolean"),
        }),
      ],
    }),
  },
})
```

Поддержанные цели ребра:

- конечный тип или набор конечных типов;
- другой составной узел;
- коллекция или таблица;
- объект метаданных;
- зарегистрированный динамический resolver для полей, зависящих от
  конфигурации.

Общий исполнитель графа отвечает за:

- поиск узла по типу и псевдониму;
- перевод внутреннего и YAML-имени сегмента;
- рекурсивный переход;
- накопление трассы типов и свойств;
- формирование конечного `typeInfo`;
- диагностику неизвестного свойства известного типа.

### Составное значение и коллекция

Составной тип не представляется фиктивной таблицей. Граф различает:

- `structured` — значение с именованными свойствами;
- `collection` — табличный источник с полями элемента;
- `terminal` — конечное сравниваемое значение.

Существующая модель `SettingsComposer`, которая использует
`DataPathTableInfo.Registered` и `tableColumn` для всех узлов, переносится на
этот договор. Реальные коллекции остаются коллекциями, но `Planner`,
`StandardPeriod` и `StandardBeginningDate` становятся составными значениями.

## Представления доступности

Существование свойства и его доступность в конкретном окне платформы — разные
факты. Документация `Planner` содержит больше свойств, чем окно выбора поля
условного оформления, поэтому допустимость нельзя выводить только из наличия
свойства или его типа.

Доступный подграф задаётся отдельной декларацией:

```ts
defineDataPathView({
  purpose: "formConditionalFilter",
  types: {
    Planner: fields([
      "BeginOfRepresentationPeriod",
      "EndOfRepresentationPeriod",
      "ShowCurrentDate",
      "MinColumnWidth",
    ]),
  },
})
```

Resolver остаётся нейтральным: он возвращает разрешённую трассу. Проверка с
назначением `formConditionalFilter` пропускает эту трассу через соответствующее
представление. Отсутствие свойства в представлении означает `unavailable`, а
не отсутствие свойства у типа.

Представление строится по узлам, а не по полным строкам путей. Поэтому
разрешённые переходы автоматически составляются в пути любой глубины.

## Planner

Начальный профиль `Planner` соответствует полям, показанным платформой в
фикстуре общей формы. Синтакс-помощник подтверждает следующие группы типов:

- `dateTime`: `НачалоПериодаОтображения`, `КонецПериодаОтображения`;
- `boolean`: выравнивание границ по шкале времени, отображение перенесённых
  заголовков, отображение текущей даты, автоматическая минимальная ширина и
  высота, фиксация заголовков измерений и шкалы времени;
- `decimal`: кратность периодического варианта, отступы переноса шкалы времени,
  минимальная ширина колонки и минимальная высота строки.

В граф не включаются остальные свойства `Planner` без подтверждения их
доступности в `formConditionalFilter`.

## Результат разрешения

Проверка различает четыре результата:

- `resolved` — путь существует, доступен в указанном представлении, конечный
  тип известен;
- `unavailable` — путь существует в графе, но запрещён представлением;
- `deferred` — источник сознательно не разрешается текущей реализацией;
- `error` — известный тип не содержит указанного свойства либо структура пути
  противоречит известному типу.

Неизвестный корень импортированного пути не превращается в обычную ошибку:
импорт классифицирует такой путь как XML-аномалию. Неизвестный путь, вручную
записанный в YAML без тега аномалии, остаётся ошибкой.

## DynamicList

Отдельного исключения для `DynamicList` нет. Один обработчик условного
оформления используется для верхнеуровневого оформления формы и оформления,
принадлежащего реквизиту типа `DynamicList`.

Resolver пытается разрешить известные поля набора данных `DynamicList`. Если
поле разрешено, к нему применяются те же представление доступности и проверка
типов, что и к остальным источникам. Если импортированный путь нельзя
разрешить, он регистрируется как аномалия через `!xml/value`. Ручной
неразрешимый путь без тега остаётся ошибкой.

В `.agents/restrictions.md` фиксируется только неполнота разрешения полей
набора данных `DynamicList`, а не полный пропуск его условного оформления.

## Аномалии импортированных полей

Для `ЛевоеЗначение` и `ПравоеЗначение` типа `Поле` согласовано новое место
применения существующего тега `!xml/value`:

```yaml
ЛевоеЗначение: !xml/value РеквизитыПоиска.Предустановленное
ПравоеЗначение: Истина
```

Payload содержит исходный внутренний путь из XML. Импорт ставит тег, если
resolver возвращает `unavailable`, `deferred` или `error`. Импорт не выдаёт
предупреждение: сам тег является устойчивой и достаточной регистрацией
аномалии.

Экспорт значения с `!xml/value` выводит payload дословно и не переводит имена
сегментов. Смысловая validation не проверяет существование, доступность и тип
помеченного операнда. Второй операнд проверяется независимо, но совместимость
пары не проверяется.

Validation проверяет только допустимое место `!xml/value` и непустой payload.
Resolver для помеченного значения не запускается, тег не признаётся
избыточным автоматически и исключает значение из смысловой проверки, пока
пользователь сам его не удалит.

Новое место применения добавляется в `.agents/xml-anomalies.md`. Новый вид
тега не вводится. Этот договор относится только к операндам типа `Поле` в
условиях DCS. Он не меняет существующую семантику `!xml/value` для обычных
реквизитов формы типа `ПутьКДанным`.

## Проверка операндов

Пустое поле `.` сохраняется и принимается как платформенное пустое значение.
Обе стороны могут содержать как поле, так и константу.

Проверка выполняется независимо для каждого операнда:

1. определить вид значения;
2. для поля разрешить путь и применить `formConditionalFilter`;
3. получить нормализованный конечный тип;
4. если оба операнда имеют известные типы, проверить их совместимость.

Если хотя бы один операнд помечен `!xml/value` или не имеет достоверного типа,
совместимость пары не проверяется. Константа получает тип из своего
представления DCS.

Два известных типа сравниваются консервативно по нормализованным группам:

- неизвестный тип и `<any>` не дают диагностику;
- составные типы совместимы, если пересекается хотя бы одна ветвь;
- одинаковые нормализованные группы совместимы;
- конкретные ссылки одного семейства, например два `CatalogRef.*`, совместимы
  независимо от имени объекта;
- `AnyIBRef` совместим с любым ссылочным семейством;
- ошибка выдаётся только для заведомо непересекающихся групп.

Полная матрица `ВидСравнения × тип значения` не выводится из частот корпуса и
не реализуется без отдельного подтверждённого договора. Ограничение записывается
в `.agents/restrictions.md`.

## Параметры оформления и оформляемые поля

### Оформляемые поля

`Поля` содержит локальные ссылки на элементы формы, а не пути к реквизитам.
Обычная строка и поле `Поле` расширенной записи разрешаются через эффективный
индекс элементов формы. Индекс учитывает:

- явно объявленные элементы;
- заимствованные элементы основной формы;
- вычисляемые одиночные элементы, например расширенную подсказку;
- платформенно проецируемые элементы, которые можно достоверно восстановить из
  структуры формы.

На первом этапе проверяется только существование ссылки на элемент. Вид
элемента не ограничивается: исследованный корпус не доказывает полноту
закрытого списка. Механизм представлений сохраняется для будущего
`formConditionalAppearanceTarget`, но ограничивающее представление в этой
работе не регистрируется.

Отсутствие свойства `Поля` допустимо и сохраняет платформенную семантику
условного оформления без явно выбранного списка. Структурные свойства
расширенной записи (`Использование`, заголовки и режим отображения) продолжают
проверяться существующими `AvailableFields` rules.

В корпусе 6 126 из 29 306 оформляемых полей ссылаются на платформенно
созданные элементы, отсутствующие явно в XML формы. Если импорт не может
разрешить такую локальную ссылку, она сохраняется как:

```yaml
Поля:
  - !xml/reference ОрганизацииСтатус
```

В расширенной записи тег ставится непосредственно на скаляр ссылки, а
остальные свойства записи сохраняются:

```yaml
Поля:
  - Поле: !xml/reference ОрганизацииСтатус
    Использование: Истина
```

Payload содержит исходное внутреннее имя. Импорт не выдаёт предупреждение.
Экспорт выводит payload дословно, а validation проверяет только допустимое
место тега и непустой payload. Resolver не запускается, тег не признаётся
избыточным автоматически и исключает ссылку из смысловой проверки, пока
пользователь сам его не удалит. Ручное неизвестное имя без тега остаётся
ошибкой. Это новое место применения существующего `!xml/reference` добавляется
в `.agents/xml-anomalies.md`.

### Параметры оформления

Параметры оформления проверяются по закрытому каталогу `AppearanceFieldsRules`:

- `ЦветФона`, `ЦветТекста` — цвет или `null`;
- `Шрифт` — описание шрифта или `null`;
- `ГоризонтальноеПоложение` — системное перечисление `HorizontalAlign` или
  `null`;
- `Формат`, `Текст` — строка, многоязычная строка, форматированная строка либо
  значение типа `Поле`;
- `ВыделятьОтрицательные`, `ОтметкаНезаполненного`, `Видимость`,
  `Доступность`, `ТолькоПросмотр`, `Отображать` — булево или `null`.

Для каждого параметра разрешена определённая `SettingsParameterValue`
обёртка со служебными свойствами. JSON Schema и импорт проверяют тип значения,
допустимые служебные свойства и запрещают неизвестные параметры и поля.
Каталог оформления остаётся отдельным от графа путей.

Для `Текст` и `Формат` со значением типа `Поле` пока проверяется только
строковая структура. Существование и допустимость такого поля остаются в
`restrictions.md` до отдельного проектирования.

## Проверки

Необходимые уровни тестирования:

- модульные тесты декларации и обхода типизированного графа;
- модульные тесты представлений доступности;
- рекурсивные пути `SettingsComposer` после переноса на общий механизм;
- все показанные поля `Planner` и их конечные типы;
- `StandardPeriod.ДатаНачала`, `StandardPeriod.ДатаОкончания` и
  `StandardBeginningDate.Дата`;
- неизвестное свойство известного составного типа;
- путь, существующий в графе, но отсутствующий в представлении;
- разрешимое поле `DynamicList` проходит обычную проверку;
- импорт неразрешимого поля, включая поле `DynamicList`, в `!xml/value` и
  обратный XML без предупреждения;
- ручной неизвестный путь без тега как ошибка;
- пропуск совместимости пары при помеченном или неизвестном операнде;
- совместимость составных типов по пересечению ветвей, ссылочных семейств и
  `AnyIBRef`;
- совместимость двух известных полей и поля с константой;
- проверка закрытых параметров оформления и оформляемых элементов формы;
- импорт неразрешимого оформляемого элемента в `!xml/reference` и обратный XML
  без предупреждения;
- бессрочный пропуск resolver для помеченных `!xml/value` и `!xml/reference`;
- ручное неизвестное оформляемое поле без тега как ошибка;
- интеграционный прогон общей формы `УсловноеОформление`;
- корпусная проверка `/Users/nikita/git/round-trip-compact/cf`, при которой
  импортированные неразрешимые пути классифицируются и не создают последующих
  ошибок validation.

Существующие XML-фикстуры не изменяются.

## Документация ограничений

После реализации `.agents/restrictions.md` должен явно содержать:

- resolver пока может не определять часть полей набора данных `DynamicList`;
  при XML-импорте такие пути регистрируются через `!xml/value` и не
  проверяются;
- матрица совместимости вида сравнения с типами операндов не проверяется;
- совместимость операндов не проверяется, если хотя бы один тип нельзя
  достоверно определить или он зарегистрирован как импортированная аномалия.

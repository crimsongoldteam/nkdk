# Оптимизация импорта и контрольного round-trip

Спецификация фиксирует согласованные два чтения XML, подготовку фактов
зависимостей первым проходом, объединение преобразования и проверки во втором
проходе, общий рекурсивный исполнитель rules, требования к производительности,
смысловую валидацию и обработку формы расширения вместе с её основой.
До итогового просмотра спецификации и составления плана реализация не начинается.

## 1. Два чтения XML без MessagePack — согласовано

Единственный способ передачи работы между двумя основными проходами импорта —
повторное чтение и разбор исходных XML-файлов. Альтернативную стратегию хранения
разобранного XML в MessagePack не сохраняем.

1. Первый проход читает и разбирает XML, извлекает факты для общих индексов.
   После обработки задания его полное XML-дерево освобождается; для второго
   прохода не сохраняются ни упакованное дерево, ни исходный XML-буфер.
2. После завершения первого прохода собираются общие индексы, необходимые для
   окончательного преобразования конфигурации.
3. Второй проход заново читает и разбирает XML задания, строит окончательный YAML
   с готовыми индексами и выполняет контрольное обратное преобразование.
   Проверка использует уже разобранное во втором проходе дерево, не требует
   третьего чтения исходного файла или повторного разбора контрольного XML.

Удаляются промежуточное MessagePack-хранилище XML, операции упаковки/распаковки,
их профилирование и выбор стратегии через `NKDK_IMPORT_XML_STRATEGY`.
Типы входных XML-документов больше не должны зависеть от модуля упаковки.
Прямую зависимость от `msgpackr` удаляем, если после удаления этого механизма
не остаётся других потребителей.

Решение относится только к промежуточному хранению входного XML между проходами:
оно не меняет договор снимка проекта, сохранения исходных ID и XML-аннотаций.
Обязательные данные индексов и восстановления XML продолжают сохраняться.

### Проверка результата

- Обычный импорт без переменных окружения использует повторное чтение XML.
- В профиле отдельно видны чтение и разбор первого и второго проходов;
  операций MessagePack в пути импорта нет.
- На неизменных входных данных сохраняются YAML, диагностика и результат
  round-trip относительно прежнего поведения.
- Время и пиковая память сравниваются на конфигурации `doc` в одинаковых условиях.
  Ускорение от отказа от MessagePack заранее не гарантируется: упаковку и
  распаковку заменяют повторное чтение и разбор XML.

## 2. Преобразование и проверка во втором проходе — согласовано

Первый проход остаётся сбором фактов, как сейчас. Объединение относится к работе
rules-оркестратора внутри второго прохода, а не к объединению двух чтений XML.

Во втором проходе оркестратор преобразует XML в YAML и, где значение уже готово
к обратному преобразованию, сразу восстанавливает из него контрольный XML.
В этом же обходе выявляются аномалии и XML-данные, которые преобразование
не сохранило. Результат второго прохода — итоговый YAML с необходимыми
аннотациями аномалий, а не промежуточный YAML для отдельного полного round-trip.

Аномалии здесь означают отклонения входных данных и расхождения XML → YAML → XML
второго прохода. Сравнение версий файлов между первым и вторым чтением не является
предметом этого решения; отдельный договор такого сравнения не согласовывался.

Учёт прочитанных XML-узлов не заменяет проверку восстановленных значений,
атрибутов и порядка. Объединение должно сохранять полноту существующей проверки,
в том числе обнаружение потерянных и лишних XML-данных.

## 3. Факты зависимостей готовятся первым проходом — согласовано

Первый проход собирает необходимые для преобразования факты зависимостей,
включая сведения о соседних свойствах. Готовые факты и индексы доступны
воркеру до начала преобразования XML во втором проходе.

Для уже рассмотренных случаев:

- `ЗначениеЗаполнения` получает тип своего реквизита заранее. Решение о неявном
  значении и его восстановлении не ждёт появления соседнего `Тип` в YAML.
- `DataPath`, включая `Items.Строки.CurrentData.Значение`, получает готовый индекс
  реквизитов формы, таблиц и колонок, а также необходимые сведения о владельце.
  Существующий сбор индекса формы первым проходом переиспользуется.

Во втором проходе эти значения сразу преобразуются в окончательное смысловое
представление YAML, обратно в контрольный XML и проверяются. Отдельная очередь
отложенной проверки для перечисленных зависимостей не нужна; порядок обработки
соседних свойств не должен влиять на результат.

Между проходами сохраняются факты, а не полные XML-деревья или промежуточный YAML
всей конфигурации. Первый проход не принимает окончательные решения об аномалиях:
они выявляются при преобразовании и проверке во втором проходе.

### Проверка результата

- Для `ЗначениеЗаполнения` проверяется одинаковый результат независимо от порядка
  обработки этого свойства и `Тип`.
- Для `CurrentData` проверяются обычные и дополнительные колонки таблицы,
  использование индекса первого прохода и отсутствие последующего исправления
  уже проверенного пути YAML.
- На этих случаях проверяется совпадение итогового YAML, аннотаций и контрольного
  XML с действующим договором, без отдельного полного обхода ради финализации.

## 4. Локальная проверка в объединённом обходе — согласован вариант (А)

Свойство проверяется сразу после получения его окончательного смыслового
значения YAML и обратного преобразования. При завершении содержащего объекта
проверяются только его собственная структура, атрибуты, порядок и состав
непосредственных дочерних узлов, а также оставшиеся необработанные XML-данные.
Уже проверенные дочерние поддеревья повторно не обходятся и не сравниваются.
Собственные атрибуты, уже проверенные как свойства, также не требуют повторной
проверки значения, но учитываются при проверке полноты состава атрибутов.

Например, `Title` у `InputField` проверяется при обработке этого свойства.
При завершении `InputField` проверяется положение `Title` среди соседних узлов
и наличие неизвестных тегов, без повторного сравнения содержимого `Title`.
Граница проверки родителя не означает автоматического расширения локальной
аномалии до raw всего родителя.

Связь обработанного значения с конкретным исходным XML-узлом сохраняется
непосредственно при выполнении правила. Для проверки не требуется заново искать
его по строковому пути во всём дереве. Эта связь является внутренним состоянием
текущего обхода, а не новым полем итогового YAML или заменой снимка проекта.
Иными словами: взяли фрагмент XML, преобразовали в YAML и обратно, сравнили
с тем же исходным фрагментом, который ещё доступен в текущем обходе.
Существующая обработка дублей и их представление в YAML не меняются;
новый механизм идентификации дублей не вводится.

### Проверка результата

- Расхождение в дочернем значении выявляется локально и не вызывает повторного
  сравнения его поддерева на каждом уровне родителей.
- При совпадающих значениях обнаруживаются пропущенные и лишние узлы/атрибуты,
  а также изменение значимого порядка дочерних узлов.
- Неизвестные остатки не теряются из-за того, что соседнее свойство уже проверено.
- На вложенном примере счётчики проверок подтверждают отсутствие повторного
  обхода проверенных поддеревьев и глобального поиска исходных узлов по путям.

## 5. Аномалии оформляются без повторной проверки — согласовано

В рамках импорта фрагмент преобразуется из XML в смысловой YAML, обратно
в контрольный XML и сравнивается с исходным фрагментом один раз.
Найденное отклонение оформляется существующим механизмом аномалий в итоговом
YAML. После применения аннотации повторный контрольный экспорт и сравнение
не запускаются — ни для изменённого фрагмента, ни для всего объекта.
Не вводится цикл «применить аннотацию — проверить — уточнить аннотацию».

Это ограничение относится к контрольному round-trip внутри импорта и не отменяет
обычную смысловую валидацию или тесты. Корректность восстановления XML из YAML
с аннотациями проверяется отдельными автоматическими тестами и e2e round-trip,
а не дополнительным сравнением после каждого применения аннотации в импорте.
Проверка состава и порядка родителя по разделу 4 остаётся самостоятельной
проверкой его структуры, а не повторной проверкой содержимого дочернего узла.

### Проверка результата

- Тест со специально вызванным расхождением подтверждает оформление аномалии
  без повторного вызова контрольного преобразования для этого фрагмента.
- Отдельные тесты обычного экспорта итогового YAML подтверждают восстановление
  исходного XML с существующими видами аннотаций.

## 6. Окончательный YAML и независимые порядки — согласовано

### Окончательность результата второго прохода — согласовано

Все смысловые упрощения выполняются до единственного сравнения соответствующего
фрагмента. Это относится также к удалению неявного `ВводПоСтроке` и сокращению
путей данных формы с учётом наследования: необходимые зависимости готовятся
заранее. После сравнения допускается только оформление обнаруженных аномалий,
а не последующее изменение смысловых значений YAML.

Второй проход возвращает окончательный YAML: значения, набор и порядок ключей,
коллекции и аннотации уже сформированы. После его завершения не допускаются
дополнительная сортировка, нормализация или дописывание аннотаций. Сериализация
записывает готовый результат, а последующая диагностика не изменяет его.

### Два заранее подготовленных порядка

Порядок ключей YAML независим от порядка экспорта XML. При подготовке плана rules
однократно вычисляются позиции обычных YAML-полей по существующему сравнению
ключей. Для XML используется план обычного экспорта (`yamlToXMLOrder`) с учётом
конкретного правила и контекста. Порядок XML не выводится из порядка YAML
или простым копированием порядка входного XML.

Во время обхода XML готовые значения помещаются в предназначенные им YAML-позиции.
При завершении родителя итоговый объект собирается по этим позициям с пропуском
отсутствующих полей. Полная сортировка обычных ключей для каждого экземпляра
объекта не нужна. Динамические ключи аномалий размещаются в том же локальном
построителе согласно действующему договору представления.

Формирование и проверка порядка завершаются внутри обработки родителя:

- При обработке дочерних свойств сохраняются готовые значения и сведения об их
  месте в XML, включая вклад локальных аномалий. Проверенные значения повторно
  не преобразуются.
- При завершении родителя однократно сопоставляется порядок его непосредственных
  XML-узлов с порядком, получаемым обычным экспортом по действующим правилам
  конкретного контекста. Уже оформленные локальные raw учитываются до этого
  сопоставления, без повторного контрольного экспорта.
- Если исходный XML-порядок восстанавливается существующими правилами, `#order`
  не добавляется. Для действительно невосстановимого порядка используется
  существующая локальная аннотация порядка; её договор не расширяется.
- После оформления структурных аномалий родителя его YAML-ключи размещаются
  в окончательном порядке по существующим правилам представления. Порядок
  элементов коллекций не подменяется сортировкой ключей свойств.

Родитель возвращает готовый результат, и последующего прохода по дереву YAML
для исправления порядка нет. Пока родитель строится, его локальные записи могут
накапливаться; требование окончательности относится к возвращённому результату,
а не к записи каждого ключа в выходной файл сразу при чтении XML.

Проверяются случаи обычного порядка, локального raw
в обычной позиции без лишнего `#order`, действительно необычного XML-порядка
и стабильного порядка YAML после добавления аннотаций. Отдельный тест задаёт
разные правильные порядки XML и YAML: различие между ними само по себе
не должно создавать аномалию.

## 7. Время жизни контрольного XML и производительность

Результаты обратного преобразования не накапливаются для последующей сборки
полного контрольного XML-документа. Контрольный фрагмент существует только
на время его однократного сравнения и оформления обнаруженной аномалии;
затем ссылки на него освобождаются. Проверенный дочерний XML не передаётся
родителю как сохраняемое поддерево и не строится заново при завершении родителя.

Для проверки состава и порядка родителю остаются только компактные сведения
о непосредственных узлах: их имена/вхождения, присутствие и место в порядке
экспорта, включая вклад локальных аномалий. Эти сведения не содержат копий
текстовых значений или XML-поддеревьев. Они освобождаются после завершения
соответствующего контейнера. Это не требование постоянной памяти: объём таких
сведений зависит от числа непосредственных узлов открытых контейнеров.

Ограничение не относится к исходному XML, прочитанному во втором проходе,
итоговому YAML и XML-данным, которые необходимо сохранить в его аномалиях
или в существующем снимке проекта. Они не являются кэшем контрольного экспорта.

Высокая скорость — основная цель изменения. Для обычных статических полей
подготовка порядка выполняется один раз на план rules; заполнение и сборка
используют прямое обращение к позициям и линейный проход по плану. Проверка
порядка линейна по последовательностям непосредственных XML-узлов, без поиска
по всему дереву, повторного преобразования и сравнения дочерних поддеревьев.

Критерии проверки: отсутствие накопления контрольных XML-поддеревьев,
отсутствие повторной сортировки обычных ключей на каждом экземпляре,
счётчики посещений на растущих коллекциях и сравнение времени стадий импорта
и пиковой памяти на `doc` до и после изменения в одинаковых условиях.
Тесты и измерения должны выявлять скрытые повторные обходы; конкретный прирост
скорости до измерений не заявляется.

## 8. Логическое исключение проверенных частей — согласовано

При вызове одного rule из другого дочернее rule завершает проверку принадлежащей
ему части XML. Эта часть логически исключается из дальнейшего сравнения:
родитель не сравнивает её повторно и не заходит в завершённое поддерево.
Если внутри фрагмента уже работали дочерние rules, проверка родителя относится
только к оставшимся частям, а не ко всему исходному блоку целиком.

Отметка завершения хранится в отдельном состоянии текущего обхода с привязкой
к существующему идентификатору XML-узла внутри документа. Исходное XML-дерево
не изменяется и не копируется ради удаления проверенных частей: оно остаётся
доступным для диагностики и формирования аннотаций. Новые поля в YAML
и в исходных XML-узлах не вводятся.

Прочитанное или распознанное значение ещё не считается проверенным. Часть
завершается после однократного сравнения, когда установлено совпадение либо
обнаруженное отклонение оформлено действующим механизмом аномалий. Отметка
не должна скрывать неизвестные или непроверенные дочерние узлы и атрибуты.
Полное поддерево можно пропускать только после завершения всех его частей.

Завершённое содержимое исключается из повторной проверки значений, но сведения
о присутствии и позиции узла остаются в проверке состава и порядка его родителя.
Наличие исходного узла само по себе не доказывает его наличие в результате
экспорта: учитываются сведения обеих сторон сравнения, в том числе лишние узлы.

### Проверка результата

- Вложенные rules сравнивают каждую принадлежащую им часть один раз; родитель
  не сравнивает и не обходит повторно завершённое дочернее содержимое.
- Неизвестный соседний узел или непроверенный атрибут не исчезает из проверки
  после завершения известного дочернего свойства.
- Проверка родителя выявляет изменение состава и порядка при уже завершённых
  проверках значений детей.
- Оформленная аномалия не запускает повторную проверку её фрагмента, а исходное
  дерево остаётся неизменным.

## 9. Общий рекурсивный исполнитель rules — согласовано

Импорт и экспорт используют один механизм выполнения объектов, свойств
и коллекций. Общность не ограничивается вызовом одного `toXML`: общими остаются
переходы во вложенные rules, подготовка контекста, получение зависимостей,
экспортные решения о значениях по умолчанию и пропусках, построение атрибутов,
контейнеров и порядка XML. Направленные преобразования `fromXML`, `toYAML`,
`fromYAML` и `toXML` сохраняют собственный смысл и не подменяют друг друга.

Основа — существующий `CompiledPropertyPlan`: неизменяемый план со статическими
маршрутами, разрешёнными обработчиками и порядками. Для импорта и экспорта
не создаются два независимо развивающихся плана с копиями этих решений.
Общий исполнитель остаётся нейтральным: конкретные виды метаданных и их
особенности предоставляются rules и зарегистрированными обработчиками.

### Различия на входе и выходе

- При импорте источник подаёт XML и соответствующие правила. Полученное
  окончательное значение YAML сразу проходит общую экспортную часть;
  результат передаётся локальному сравнению, а не сборщику полного XML.
- При обычном экспорте источник подаёт готовые значения YAML, а та же экспортная
  часть передаёт результат сборщику выходного XML в экспортном порядке.
- Экспортная часть использует действительное окончательное представление YAML,
  включая его служебные метаданные. Нельзя ради ускорения сравнивать исходный XML
  с его копией или восстанавливать значение в обход обычного YAML → XML.
- Вложенное правило выполняется через общий механизм один раз на элемент
  и требуемое направление преобразования. Импорт не запускает затем полный
  экспорт готового родительского YAML. Родитель завершает только собственную
  оболочку, состав и порядок, используя сведения о завершённых детях.
- Обычный экспорт вправе сохранять дерево своего конечного результата.
  Импортный потребитель не сохраняет его аналог и не требует предварительно
  собрать целиком XML объекта или коллекции, чтобы затем разбить на фрагменты.

Общая рекурсия не требует одинаковой последовательности входных полей:
XML-источник следует исходным узлам, YAML-источник — плану экспорта. Независимые
порядки XML и итогового YAML сохраняются по разделу 6. Чтение файлов, запись
результатов и управление воркерами остаются снаружи внутреннего исполнения rules.

### Отсутствующие поля и дополнительные XML-узлы

XML-источник находит правила через подготовленные маршруты, без перебора всех
rules для каждого XML-узла. При завершении объекта выполняются ещё не выполненные
правила из заранее подготовленного набора: правила для отсутствующего XML,
а также экспортные правила, способные создать XML при отсутствующем YAML.
Этот набор не ограничивается импортными значениями по умолчанию; учитываются
экспортные стратегии `default` и `evaluate` и существующие обязательные узлы.

Отсутствующее поле и присутствующее пустое поле различаются. Если правило
без исходного узла создаёт XML, результат сравнивается с отсутствием узла
и оформляется существующим механизмом аномалий. Его позиция определяется общим
экспортным планом и учитывается в проверке порядка родителя. Например, при
исходном порядке `A, C` и результате `A, B, C` обнаруживается лишний `B`,
а не ошибочное перемещение `C`. Повторное выполнение уже обработанных правил
и отдельный повторный проход по готовому YAML для поиска таких случаев не нужны.

### Проверка результата

- Вложенные объекты и коллекции в обоих направлениях используют общий
  рекурсивный механизм; дочерний экспорт не дублируется родительским.
- Тесты обычного экспорта и локального сравнения подтверждают одинаковые
  решения о значениях, пропусках, атрибутах, контейнерах и порядке. Изменение
  общего экспортного решения обнаруживается импортной проверкой без правки
  отдельной реализации проверочного экспортёра.
- Проверяются отсутствующие и пустые поля, XML из отсутствующего YAML,
  обычные и контекстные значения по умолчанию, вложенные коллекции,
  дубли, псевдонимы XML-имён, ID и существующие аннотации.
- Обработчики, меняющие экспортную форму, завершают изменение соответствующей
  части до её единственного сравнения. Поздняя правка уже проверенного XML
  либо скрытая сборка большого контрольного дерева не являются обходным решением.

## 10. Требования к быстрому исполнению — согласовано

Главный приоритет — исключить повторную работу, затем уменьшать стоимость
отдельных вызовов. В сохранённом CPU-профиле `doc` поиск соответствий через
`resolveExportedProofPath` занимает около 70% выборки самой проверки аномалий,
не всего импорта. Код повторно перебирает XML-якоря и разрешает родительские пути.
Прямая связь с исходным узлом по разделу 4 должна устранить эту потребность
в новом пути исполнения, а не перенести такой же поиск в другой общий модуль.

### Подготовка один раз, минимум работы на поле

- Разрешённые функции преобразования, XML-маршруты, статические YAML-позиции,
  экспортный порядок и наборы правил для отсутствующих значений готовятся
  один раз на план и версию реестра. План переиспользуется между заданиями
  одного runtime/воркера; значения, деревья и изменяемые контексты в нём не кэшируются.
  Контекстные решения не замораживаются как статические значения по умолчанию.
- Внутри обработки поля — прямые вызовы подготовленных функций. Нет `Promise`,
  очереди событий или отдельного межпоточного сообщения на каждый XML-узел.
  Адаптеры входа и выхода выбираются на границе запуска; общность не требует
  повторного разрешения обработчиков и построения цепочки обёрток для каждого поля.
- Позиции, завершение проверки и связь с исходным узлом доступны напрямую.
  Не выполняются поиск по всему документу, перебор всех якорей, сортировка
  кандидатов по глубине или рекурсивное восстановление пути для каждого значения.
  Строковые пути для диагностики переиспользуются либо оформляются при необходимости.
- Коллекции не ищут соответствие каждого элемента линейным перебором всех
  соседей: используются существующие идентификаторы и локальные индексы,
  сохраняющие неоднозначность и порядок повторных вхождений.
- Неизменяемые индексы и факты зависимостей переиспользуются. Не создаются их
  глубокие копии для каждого свойства. Локальный контекст не протекает
  между соседними элементами, в том числе между вариантами объектов расширений.

### Работа и память растут со входными данными

Целевая стоимость общего обхода и сопоставления линейна по числу обрабатываемых
XML-узлов, необходимых позиций плана и объёму сравниваемых значений. Число правил
не становится множителем при поиске правила для каждого исходного узла.
Это требование к оркестратору, а не заявление о постоянной стоимости любых
предметных преобразователей или сравнения строк произвольной длины.

Исходное дерево, окончательный YAML и обязательные данные восстановления остаются
необходимой памятью операции. Дополнительно допускаются состояния активных
контейнеров и компактный учёт завершённых частей; полный контрольный XML,
второе дерево событий или копии всех проверенных фрагментов не создаются.
Учёт состава и порядка хранит идентификаторы и позиции, а не содержимое детей.
Ссылки на временные фрагменты не остаются в кэшах и диагностических замыканиях
после завершения задания. Само присваивание `undefined` не считается
доказательством освобождения памяти — это проверяется измерением удержания.

Для совпадающего фрагмента не строятся подробные различия и текст ошибки.
При аномалии её локальная диагностика формируется один раз без повторного
контрольного экспорта. Массовые аномалии не должны превращать поиск соответствий
в попарное сравнение всех элементов; обязательные данные raw при этом не теряются.
Смысловая валидация, точность сравнения и существующие проверки не отключаются
ради улучшения времени.

### Как подтвердить ускорение

1. Зафиксировать исходный коммит, состав входных данных, версии Node.js,
   параметры запуска и число воркеров. Сравнить до/после на `doc` с одинаковой
   диагностикой и отдельным обычным экспортом готового YAML. Сборку не включать
   во время операции; между сравниваемыми версиями не менять число воркеров.
2. Отдельно измерить первый запуск в новом процессе и не менее трёх повторных
   прогонов. Показать медиану и разброс, общее время, процессорное время и пиковый
   RSS. Первый запуск не называть гарантированно холодным файловым кэшем ОС.
3. Разделить чтение/разбор обоих проходов, сбор фактов/индексов, объединённое
   преобразование с проверкой, смысловую валидацию и запись. Время воркеров
   не складывать с длительностью операции как независимые величины. CPU-профиль
   использовать для объяснения затрат; итоговое ускорение подтверждать отдельными
   прогонами без подробного CPU-профилирования.
4. В инструментированных тестах увеличивать размеры коллекций и глубину
   вложенности; считать вызовы преобразователей, сравнения значений, посещения
   оболочек и компиляции планов. Проверить совпадающий XML, массовые локальные
   аномалии, отсутствующие поля, перестановки и дубли. Родитель не увеличивает
   число сравнений уже завершённых дочерних значений. Счётчики и подробные
   измерения каждого поля не добавляются в обычный быстрый путь без необходимости.
5. Проверить удерживаемую память на большой коллекции: рост итогового YAML,
   исходного XML и обязательного raw отделить от запрещённого накопления
   контрольных XML-поддеревьев. В обычном экспорте конечный выходной XML
   не считать лишним контрольным деревом.

Объединение считается удачным только при сохранении корректности и измеримом
снижении времени полного импорта, выходящем за разброс измерений. Для обычного
экспорта требуется отсутствие устойчивого замедления и роста пиковой памяти
из-за общего исполнителя. Если выигрыша нет либо он получен ценой отключённых
проверок, работу нельзя объявлять завершённой оптимизацией. Конкретный процент
ускорения до реализации и одинаковых замеров не обещается.

## 11. Смысловая валидация в общем проходе — согласовано

Совпадение исходного и восстановленного XML не доказывает допустимость данных.
Смысловая проверка остаётся самостоятельной частью обработки значения или
объекта, но не требует отдельного позднего исправления готового YAML.

Порядок обработки соответствующей границы:

1. Получить окончательное смысловое значение YAML по правилам и готовым фактам.
2. Выполнить существующие смысловые проверки и оформить предусмотренные ими
   аннотации до обратного преобразования.
3. Через общую экспортную часть восстановить XML из этого представления
   и единственный раз сравнить с исходным фрагментом.
4. При XML-расхождении оформить его по разделу 5 и завершить эту часть YAML
   без повторного контрольного экспорта или изменения смыслового значения.

Например, при уже согласованном ограничении на единственный определяемый тип
дополнительный исходный элемент сохраняется как `!xml/invalid` ещё до сравнения.
Общий экспорт восстанавливает оба исходных XML-узла, а первое допустимое
значение остаётся обычным YAML. Это пример действующего договора, не новое
применение тега и не специальное условие для `DefinedType` в общем исполнителе.

Используется общая смысловая логика с обычной проверкой проекта, а не отдельные
копии валидаторов для импорта. Межполевые и межфайловые проверки получают
подготовленные факты и индексы. Проверки целого объекта выполняются при
готовности необходимой границы и не запускают повторную проверку содержимого
уже завершённых детей. Первый проход остаётся сбором фактов, без оформления
окончательных аномалий.

Существующие ограничения и правила принятия уже отмеченных аномалий сохраняются:
`!xml/invalid` не отключает остальные проверки значения или соседних элементов.
Внутренние ошибки преобразования/валидации не превращаются в аномалии исходных
данных. Применение `!xml` к новым свойствам или классам значений этим решением
не разрешается.

После завершения второго прохода YAML не дополняется аннотациями и не меняет
значения. Не сохраняется цикл из `validateAndApplyImportedIssues`, в котором
контрольный экспорт уже закончился, а YAML затем исправляется и повторно
сериализуется/проверяется. Договор обычной проектной проверки и проверки
сериализации не отменяется; их организация не должна возвращать этот цикл.

### Проверка результата

- Допустимый XML и точно восстанавливаемый XML со смысловой ошибкой различаются
  по результату смысловой проверки, а не только по XML-сравнению.
- Для согласованных `singleOnly`-случаев лишний элемент отмечен до единственного
  обратного преобразования; прочие ограничения продолжают проверяться.
- Локальные, межполевые и межфайловые решения используют ту же смысловую логику,
  что обычная проверка проекта, и готовые зависимости вместо поздней правки YAML.
- Счётчики подтверждают отсутствие повторного round-trip после аннотации,
  а тесты окончательного YAML — отсутствие последующих изменений результата.

## 12. Форма расширения и сохранённая основа — согласовано

Рабочая форма и вложенный в её XML узел `BaseForm` обрабатываются как две
логические части одного задания, общим исполнителем правил тела формы.
У них свои контексты, привязки к исходным узлам и YAML-результаты; обработка
основы не означает повторного импорта рабочей формы или её файла метаданных.

### Состав фактов для путей

Существующий договор `formDataPathContext.ts` и его тестов сохраняется:

- От импортируемой формы нужны имена и виды элементов, принадлежность колонок
  таблицам, наличие и значение исходного пути, основной реквизит, индекс
  реквизитов и дополнительных колонок. Пустой путь отличается от отсутствующего.
- От текущей формы `cf` нужны действующие пути и индексы, основной реквизит
  и наличие элементов. Собственные реквизиты имеют приоритет над унаследованными;
  происхождение корня сохраняется.
- Сохранённая основа участвует в определении заимствованных имён. Её старые пути
  не заменяют действующие пути текущей формы. В тесте значение `Старое.Значение`
  исторического элемента не становится источником текущего пути.

### Последовательность двух проходов

1. Первый проход один раз читает и разбирает XML-файл формы. Из его рабочей
   части и вложенного `BaseForm` собираются отдельные факты; полные YAML обеих
   частей и контрольный XML ещё не строятся. Полное XML-дерево после сбора
   фактов освобождается по разделу 1.
2. Между проходами, после сборки общих индексов, один раз подготавливаются
   зависимости из актуальной формы `cf` и фактов импортируемого XML. Получаются
   контексты расчёта путей и выбранный источник основы для обычного экспорта.
   Здесь нет предварительного полного импорта рабочей формы или основы в YAML.
3. Второй проход повторно читает и разбирает файл, затем общий исполнитель
   обрабатывает рабочую форму. На `BaseForm` он вызывает правила тела формы
   с контекстом основы и отдельным YAML-результатом. Нужные зависимости готовы
   до этого вызова: готовый YAML соседней части не требуется для исправления
   уже обработанного значения.
4. Значения обеих частей проходят смысловую проверку и единственное обратное
   преобразование по общему договору. Рабочая форма не экспортирует основу
   повторно после завершения её обработки; при закрытии родителя учитываются
   только оболочка, наличие и позиция `BaseForm`, без сравнения его содержимого.
5. Результат — окончательный YAML рабочей формы и, если она необходима,
   `БазоваяФорма.yaml`. Решение о сохранении основы не запускает повторный импорт,
   переписывание возвращённого YAML или повторный контрольный экспорт.

При обработке пути сразу выбирается его окончательная форма — отсутствующее,
пустое или явное значение — по существующим правилам. Последующий обход готового
дерева через `compactImportedFormDataPaths`/`materializeInheritedRootFormDataPaths`
для исправления значений не сохраняется. Сбор фактов и их интерпретация остаются
в предметном модуле форм; нейтральный исполнитель не получает частных условий
для форм расширений.

### Выбор источника основы между проходами

Проверка необходимости сохранённой основы сохраняет смысл существующего
`isRedundantClientApplicationBaseForm`: сопоставляются результаты отбора данных
текущей `cf` и исторической основы с учётом рабочей формы расширения. Это не
сравнение всех свойств двух форм без отбора. Учитываются состав и иерархия
элементов, виды, наличие свойств и участвующие значения, а также действующие
правила проекции вложенных объектов, коллекций и ссылок.

Первый проход собирает необходимые для этого факты в дополнение к фактам путей.
После подготовки индексов общий механизм проекции сравнивает соответствующие
части по этим фактам без сборки двух полных YAML-проекций и их нормализованных
копий. Он переиспользует предметные решения обычного построения основы
и обычной проектной проверки, а не содержит отдельную упрощённую реализацию.
Смысловая нормализация и исключение технических полей при этом сохраняются.

Первое значимое отличие доказывает необходимость основы; дальнейшее сравнение
ради этого решения не требуется. Если весь необходимый состав и значения
совпадают, источником становится проекция текущей `cf`, отдельный файл основы
не сохраняется. Например, участвующая в проекции `Ширина: 20` у текущей формы
и `Ширина: 99` у исторической основы требуют сохранения основы.
Выбранный источник и соответствующий экспортный контекст, включая работу с ID,
известны до начала второго прохода и не переключаются после сравнения XML.

Эта проверка сравнивает два источника основы, а не выполняет дополнительный
XML → YAML → XML. Нельзя получить её входы скрытым полным предварительным
импортом обеих форм между проходами. Достаточность состава фактов подтверждается
тестами совпадения решений с существующей проверкой, а не предполагается
на основании одного индекса путей.

### Основу без отдельного YAML тоже проверяем

Отсутствие необходимости в `БазоваяФорма.yaml` не разрешает пропустить
исходный `BaseForm`. Во втором проходе его XML сопоставляется с фрагментами,
получаемыми обычным экспортом выбранного источника — в этом случае проекцией
текущей `cf`. Совпадение смысловых проекций само по себе не заменяет эту проверку:
различия XML-формы, неизвестные узлы и атрибуты должны быть обнаружены.
Сохранение необходимых данных использует существующие договоры снимка
и аннотаций, без нового применения `!xml`, не согласованного отдельно.

Если основа сохраняется, её окончательный YAML является результатом операции,
а не запрещённым промежуточным YAML всей конфигурации. Ни в одном случае
не накапливаются XML-поддеревья её контрольного экспорта.

### Проверка результата

- XML-файл с вложенным `BaseForm` читается и разбирается один раз в каждом
  основном проходе, а не отдельно для основы и рабочей формы.
- Счётчики подтверждают отсутствие предварительного полного YAML-импорта
  между проходами и повторного экспорта/сравнения основы у её родителя.
- Решение о необходимости основы совпадает с текущим договором на различиях
  значений, состава реквизитов/команд/параметров, иерархии элементов,
  технических полей и вложенных проекций.
- Проверяются собственные и заимствованные элементы, новые колонки таблиц,
  пустые и отсутствующие пути, унаследованные реквизиты и элемент, оставшийся
  только в исторической основе. Его старый путь не подменяет текущий.
- Для избыточной основы отдельный файл не создаётся, но неизвестный XML-узел
  или отличие XML-формы внутри `BaseForm` не остаётся без проверки.
- Обычный экспорт итоговых файлов восстанавливает XML с тем же выбранным
  источником основы; после возврата второго прохода YAML не изменяется.

## 13. Перед составлением плана

При детализации плана существующие финализаторы сопоставляются с указанными
границами выполнения и готовыми фактами. Их нельзя механически удалить только
из-за наличия первого прохода или заменить скрытым повторным импортом.

С разрешения разработчика `.agents/architecture.md` обновлён под эту согласованную
целевую схему. Он явно отличает её от ещё не изменённой реализации с MessagePack
и отдельным полным контрольным экспортом. Изменения реализации не входят
в запись спецификации и архитектурного описания.

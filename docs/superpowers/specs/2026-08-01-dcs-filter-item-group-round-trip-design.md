# Сохранение групп DCS при XML ↔ YAML

## Цель

Сохранить логическое дерево отбора DCS при XML → YAML → XML для `AndGroup`, `OrGroup` и `NotGroup`, включая вложенные группы и reference-only свойства. Исправление ограничивается типом `FilterItem` и не меняет общий механизм metadata-коллекций.

## Причина

`importFilterItemFromXMLToYAML` сейчас считает любой объект с полем `dcsset:item` контейнером коллекции. Но `FilterItemGroup` использует то же поле для дочерних условий. Поэтому единственная корневая группа разворачивается, а её `groupType` и свойства теряются.

Дополнительно `referenceIdentity.fromYAML` распознаёт `ГруппаИ` и `ГруппаИли`, но не `ГруппаНе`, хотя `NotGroup` входит в системное перечисление и встречается в XML.

## Решение

### Распознавание входа XML

В `filterItem/fromXMLToYAML.ts` разделить два случая:

- объект с `_xsi:type` является готовым `FilterItemComparison` или `FilterItemGroup` и импортируется целиком;
- объект без `_xsi:type` является контейнером, из которого можно извлечь `dcsset:item`;
- массив уже является коллекцией элементов и не преобразуется перед обходом.

Рекурсивное свойство `FilterItemGroup.items` продолжит использовать существующий `filterItemRule`, поэтому одна логика сохранит группы на любой глубине.

### Сопоставление reference XML

В `filterItem/types.ts` получать XML-тип группы через существующее `DataCompositionFilterItemsGroupTypeFromYAML`. Это даст одинаковый договор для `ГруппаИ`, `ГруппаИли` и `ГруппаНе` без ручного неполного ветвления.

## Тестовый договор

Расширить существующие тесты `filterItem/fromXMLToYAML.test.ts` и `filterItem/fromYAMLToXML.test.ts`, не изменяя XML-фикстуры.

Проверить наблюдаемое поведение:

1. одиночная корневая `OrGroup` с дочерними `AndGroup` сохраняет всё дерево;
2. `AndGroup` с вложенной `NotGroup` сохраняет оператор и детей;
3. несколько корневых элементов не получают лишнюю обёртку и не теряют группы;
4. вложенность из четырёх уровней проходит XML → YAML без распрямления;
5. `NotGroup` сопоставляется с reference XML и сохраняет вложенные reference-only значения;
6. `presentation`, `use`, `viewMode` и `userSettingID` корневой группы не теряются.

Новые проверки должны расширять существующие сценарии того же договора. XML для уникальных структур задаётся непосредственно в тесте, чтобы не менять существующие фикстуры — источник истины.

## Проверка

1. Запустить тесты `filterItem/fromXMLToYAML.test.ts` и `filterItem/fromYAMLToXML.test.ts`.
2. Запустить тесты соседних DCS-модулей.
3. Запустить `pnpm test` из корня.
4. Повторить `round-trip-yaml` на диагностическом XML-каталоге и убедиться, что группы DCS больше не распрямляются.

## Границы

- Не добавлять частные знания DCS в общие orchestration-слои.
- Не менять общие типы правил и параметры построителей.
- Не добавлять специальные `fromXML`/`toXML`/`fromYAML`/`toYAML` в `rules.ts`.
- Не исправлять в этом изменении остальные категории XML-diff: служебные default, заголовки колонок и порядок командного интерфейса.

## Критерии готовности

- логическое дерево `AND`/`OR`/`NOT` совпадает до и после round-trip;
- reference XML сопоставляется для всех трёх типов групп;
- существующие DCS-тесты и полный `pnpm test` проходят;
- исправление остаётся локальным для `FilterItem`.

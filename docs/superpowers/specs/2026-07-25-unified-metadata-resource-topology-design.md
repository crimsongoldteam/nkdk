# Единая топология ресурсов метаданных

## Контекст

Полный XML → YAML → XML round-trip каталога `cf/all` оставляет 218 удалённых файлов. Сопоставление результата с планом полной XML-синхронизации показало:

- удалено 218 файлов;
- план содержит 339 XML-целей;
- ни один удалённый файл не присутствует в плане.

Это не 218 независимых ошибок преобразования. Новый полный экспорт строит неполную структуру Проекта и XML-результата:

- задание верхнеуровневого объекта содержит только основной XML и не включает дополнительные XML-свойства из того же `Свойства.yaml`;
- корневые ресурсы Конфигурации и ресурсы вложенных объектов распознаются неполно;
- вложенные объекты поддерживаются отдельными случаями, прежде всего формами;
- полная синхронизация, частичная синхронизация, XML-import и validation используют разные способы обхода и классификации структуры.

В кодовой базе уже существуют необходимые части:

- рекурсивная компиляция `xmlImportRoutes`, которая обходит `rules.ts`, регистрации типов и `childCollections`;
- декларации `projectResources`, `xmlSyncRoutes` и зарегистрированные обработчики частичной XML-синхронизации;
- обработчики построения дополнительных XML и переноса внешних файлов в прежней синхронизации.

Проблема не требует нового набора частных правил. Требуется единый нейтральный механизм, который соберёт существующие декларативные знания в одну топологию и предоставит её разным операциям.

## Цель

Ввести единую скомпилированную топологию ресурсов метаданных, которая является общим представлением структуры Проекта и XML-выгрузки для:

- XML → YAML;
- полной YAML → XML синхронизации;
- частичной YAML → XML синхронизации;
- классификации файлов validation и других проектных операций.

Топология должна описывать корневые и вложенные объекты, несколько XML-документов одного задания и переносимые внешние файлы без знаний о конкретных реализациях метаданных в общей оркестрации.

## Архитектурные инварианты

Общие слои `metadata/orchestration`, `metadata/project`, `metadata/validation` и новый компилятор топологии:

- не проверяют конкретные `itemType`;
- не знают имена XML-корней;
- не содержат названия каталогов вроде `Формы`, `Макеты`, `Команды` или `Шаблоны`;
- не ветвятся по типам форм, макетов, справки и других ресурсов;
- не читают содержимое XML или файлов Проекта во время компиляции;
- не строят metadata-модель;
- работают только с нейтральными ролями, шаблонами путей, владением, логическими адресами и зарегистрированными возможностями.

Знание о конкретном типе остаётся рядом с его `rules.ts` или регистрацией. Например, регистрация формы описывает её два XML-документа, но общий компилятор видит только два выхода одного задания.

## Выбранный подход

Из `rules.ts`, регистраций типов и `childCollections` один чистый компилятор строит неизменяемую `CompiledMetadataResourceTopology`.

Операции не обходят правила самостоятельно. Они используют проекции общей топологии:

- классификатор путей XML;
- классификатор путей Проекта;
- построитель заданий полного экспорта;
- определитель затронутых выходов частичной синхронизации;
- определитель роли, правила и владельца файла для validation.

Существующие алгоритмы и обработчики переиспользуются:

- рекурсивный обход берётся из текущего компилятора XML-import маршрутов;
- знания из `projectResources`, `xmlImportRoutes` и `xmlSyncRoutes` переносятся в единый договор декларации ресурса;
- зарегистрированные преобразователи и обработчики копирования сохраняют своё поведение, но подключаются к узлам топологии;
- прежние параллельные компиляторы и специальные случаи удаляются после перевода потребителей.

Слой совместимости между старым и новым внутренним договором не требуется. После миграции не должно остаться двух источников истины.

## Модель топологии

### Содержательный файл Проекта

Базовая единица задания — один содержательный файл Проекта. Это не обязательно YAML по расширению: им может быть `Свойства.yaml`, `Форма.yaml` или содержательный `Template.xml`.

Узел задания содержит:

- шаблон пути файла Проекта;
- роль файла;
- правило содержимого;
- описание владельца;
- схему вычисления логического адреса;
- потенциальные XML-документы;
- связанные внешние файлы.

Одно задание принадлежит ровно одному содержательному файлу Проекта и одному worker. Одно задание может сформировать несколько XML-документов.

### XML-документ

XML-документ топологии содержит:

- шаблон XML-пути;
- роль документа внутри задания: основной, metadata, body или property;
- зарегистрированную возможность чтения XML в задание;
- зарегистрированную возможность подготовки XML из задания;
- правило XML-дерева для отложенных значений и снимка конфигурации;
- признак обязательности либо условного формирования.

Условный выход разрешается после чтения содержательного файла Проекта и снимка конфигурации. Поэтому топология описывает потенциальные выходы, а подготовленное задание — окончательный ожидаемый список XML-файлов.

Примеры:

- `ОбщаяФорма/Additional/Свойства.yaml` формирует `CommonForms/Additional.xml` и `CommonForms/Additional/Ext/Form.xml`;
- `.../Формы/Форма/Форма.yaml` формирует metadata XML формы и `Ext/Form.xml`;
- одно `Свойства.yaml` может дополнительно сформировать `Ext/AdditionalIndexes.xml`, `Ext/Predefined.xml` и `Ext/Help.xml`.

### Внешний файл

Внешний файл не преобразуется общим слоем. Его ребро содержит:

- шаблон пути Проекта;
- шаблон XML-пути;
- владельца или задание, к которому файл относится;
- необязательное правило выбора по манифесту;
- зарегистрированный обработчик переноса, если простого копирования недостаточно.

К этой категории относятся модули, HTML справки, изображения, бинарные данные и содержимое макетов.

### Владение и вложенность

Корень Конфигурации, верхнеуровневые объекты и вложенные объекты представлены одним договором владения.

Рекурсивный компилятор:

1. начинает с зарегистрированных project spec;
2. добавляет содержательный файл текущего объекта;
3. добавляет вклады его свойств;
4. рекурсивно раскрывает `childCollections`;
5. подставляет локальные параметры имени и владельца;
6. формирует логические адреса через декларативные сегменты;
7. создаёт индексы путей для обеих сторон.

Подсистемы, объекты внешнего источника, формы, макеты, команды и перерасчёты проходят один и тот же алгоритм. Разница задаётся только декларациями.

## Единый договор декларации

Финальный внутренний договор заменяет раздельные описания `projectResources`, `xmlImportRoutes` и `xmlSyncRoutes`.

Регистрация типа может вернуть нейтральные вклады:

- новый содержательный файл и его XML-документы;
- дополнительный XML-документ текущего задания;
- внешний файл;
- явно игнорируемый путь;
- вложенную коллекцию с правилом элемента и схемой владения.

Направленные обработчики остаются отдельными возможностями узла, потому что чтение XML и построение XML не всегда симметричны. Однако пути, владение и принадлежность заданию объявляются один раз.

Компилятор обязан проверить, что для каждого направления, в котором ресурс участвует, зарегистрирована необходимая возможность. Отсутствие обработчика не должно превращаться в молчаливое отсутствие XML-выхода.

## Проекции для операций

### XML → YAML

1. Топология компилируется до чтения файлов.
2. XML-каталог обходится один раз.
3. Пути сопоставляются с XML-индексом топологии.
4. Несколько XML-документов и внешних файлов группируются вокруг одного содержательного файла Проекта.
5. Задание передаётся worker.

Текущая оптимизированная структура сопоставления XML-путей сохраняется как проекция общей топологии.

### Полная YAML → XML синхронизация

1. Проект обходится один раз.
2. Каждый содержательный файл классифицируется по индексу путей Проекта.
3. Из узла топологии создаётся задание со всеми потенциальными XML-выходами.
4. Worker читает содержательный файл один раз и подготавливает все фактические XML-документы задания.
5. После уточнения отложенных значений worker записывает все подготовленные документы.
6. Главный процесс переносит внешние файлы.

Специальная ветка `assignment.role === "form"` в подготовке полной синхронизации удаляется. Формы используют тот же зарегистрированный договор подготовки задания, что и другие типы.

### Частичная YAML → XML синхронизация

Изменённый путь Проекта разрешается через тот же индекс топологии:

- изменение содержательного файла выбирает его задание и все затронутые XML-документы;
- изменение внешнего файла выбирает его ребро переноса;
- добавление или удаление вложенного объекта обновляет также состав владельца и необходимые общие XML-файлы.

Частичная синхронизация не содержит собственного разбора каталогов и типов. Она отличается от полной только отбором узлов топологии и правилами сохранения неизменённой части результата.

### Validation и проектные операции

Классификация файла возвращает:

- роль;
- правило содержимого;
- владельца;
- логический адрес;
- влияние на состав;
- связанные XML-выходы.

Validation использует только нужную ей проекцию и не обязана загружать внешние файлы. Поиск ссылок, переименование и наблюдение за изменениями могут использовать ту же классификацию без знания конкретных типов метаданных.

## Ошибки и защитные проверки

### Во время компиляции

Компиляция завершается ошибкой до чтения содержимого, если обнаружены:

- конфликтующие шаблоны путей;
- два владельца одного XML-выхода;
- неизвестный или недостижимый владелец;
- повторный логический адрес;
- ресурс без необходимого обработчика направления;
- проектный ресурс без политики XML-экспорта;
- XML-документ без принадлежности заданию;
- несовместимые роли одного физического пути.

### Во время обнаружения файлов

Путь, попавший в ветку топологии метаданных, должен быть классифицирован либо явно объявлен игнорируемым. Служебные пути вне пространства метаданных могут по-прежнему не участвовать в операции.

Обязательный содержательный файл проверяется отдельно от необязательного внешнего файла. Ошибка должна указывать путь, ожидаемый шаблон, владельца и источник декларации.

### После подготовки и записи

После первого прохода каждого задания известен окончательный список фактических XML-документов. Перед записью проверяется уникальность их целевых путей.

После второго прохода главный процесс сравнивает:

- все фактические выходы подготовленных заданий;
- все фактически записанные XML;
- все запланированные переносы внешних файлов.

Успешная операция невозможна, если ожидаемый выход не записан. Проверка не должна опираться только на предварительный план потенциальных путей.

## Тестирование

### Компилятор топологии

Нужны unit-тесты:

- корневого ресурса Конфигурации;
- верхнеуровневого объекта;
- обычной и рекурсивной вложенности;
- нескольких XML-документов одного задания;
- дополнительного XML-свойства текущего задания;
- внешнего файла и остаточного шаблона пути;
- выбора файла по манифесту;
- явного игнорирования;
- конфликтов пути, владельца и обработчика.

### Общий договор

Контрактный тест по всем зарегистрированным metadata rules должен подтверждать:

- каждый содержательный файл имеет хотя бы один допустимый результат операции;
- каждый экспортируемый XML принадлежит ровно одному заданию;
- каждый внешний файл имеет обе стороны маршрута или явно однонаправлен;
- все вложенные декларации достижимы рекурсивным обходом;
- общая оркестрация не содержит условий по конкретным `itemType` и каталогам.

### Операции

Для одной небольшой структуры с корнем и вложенными объектами проверяется одинаковая топология во всех проекциях:

- XML-import группирует правильные входы;
- полный экспорт создаёт все XML-выходы;
- частичный экспорт выбирает тот же узел по изменённому пути;
- validation получает то же правило и владельца.

Отдельные интеграционные тесты покрывают:

- общую форму с metadata XML и `Ext/Form.xml` из одного `Свойства.yaml`;
- вложенную форму с двумя XML-документами;
- макет с metadata и содержимым;
- модуль вложенной команды;
- справку с `Help.xml` и HTML;
- изображения и бинарные ресурсы;
- рекурсивные подсистемы;
- вложенные объекты внешнего источника данных.

Существующие XML-фикстуры не изменяются.

### Round-trip

После реализации выполняется полный `round-trip-yaml` для `/Users/nikita/git/round-trip/cf/all`.

Первый критерий успеха этой спецификации:

- ни один файл не удаляется только потому, что отсутствовал в плане;
- все ранее удалённые 218 путей либо восстановлены, либо для них получена явная диагностическая причина;
- план и фактически записанные пути согласованы.

Расхождения содержимого восстановленных XML, например defaults, порядок или особые значения, анализируются следующими отдельными задачами.

Перед завершением обязательно выполняется `pnpm test`.

## Миграция к единому механизму

Реализация выполняется по слоям, сохраняя работоспособность каждого завершённого шага:

1. ввести нейтральные типы топологии и чистый рекурсивный компилятор;
2. перенести декларации ресурсов и маршрутов в единый договор под контрактными тестами;
3. построить из топологии XML-import проекцию и подтвердить равенство текущих заданий;
4. перевести классификацию файлов Проекта и validation;
5. перевести полный XML-экспорт на задания с несколькими документами;
6. перевести частичную XML-синхронизацию;
7. удалить старые направленные компиляторы, специальные случаи форм и дублирующие тесты реализации;
8. обновить `.agents/architecture.md`, чтобы все операции ссылались на общее действие компиляции топологии ресурсов.

Промежуточный слой совместимости не остаётся в финальной архитектуре.

## Не входит в задачу

- изменение пользовательского формата YAML;
- изменение формата снимка конфигурации;
- создание metadata-модели в общих операциях;
- изменение правил сериализации конкретных свойств;
- исправление содержательных XML-расхождений после восстановления файлов;
- транзакционная запись всего XML-каталога;
- подключение к 1С.

# Дизайн: произвольные типы реквизитов формы в индексе метаданных

## Контекст

При проверке импортированной конфигурации корректные пути данных формы ошибочно
считаются неизвестными:

```yaml
Реквизиты:
  РеквизитыОбъекта:
    Тип: ТаблицаЗначений
    Колонки:
      Значение:
        Заголовок: Новое значение

Элементы:
  РеквизитыОбъектаЗначение:
    Вид: ПолеВвода
    ПутьКДанным: РеквизитыОбъекта.Значение
```

В исходном XML колонка объявлена с пустым типом:

```xml
<Column name="Значение" id="4">
  <Type/>
</Column>
```

Пустой `<Type/>` означает `Произвольный`: колонка существует, но её значение не
ограничено конкретным типом. В YAML это выражается отсутствием поля `Тип`, а не
явной строкой `Произвольный`.

Действующий сборщик `FormDataPathIndex` узнаёт о реквизите или колонке только из
события свойства `Тип`. Поэтому элемент без этого свойства вообще не попадает в
индекс. Resolver затем ошибочно сообщает `неизвестный корень` или `неизвестная
колонка`.

Проблема одинаково относится к двум конструкциям:

- реквизит формы без `Тип`, например `Параметры: {}`;
- колонка `ТаблицаЗначений` без `Тип`, например `Значение: {}`.

В проверенной конфигурации встречаются реальные примеры обоих видов. Дополнительно
проверены 85 250 XML-форм из `/Users/nikita/git/round-trip-compact/cf`: путей,
которые продолжаются после действительно произвольного реквизита или колонки, не
обнаружено. Типы `GanttChart` и `TypeSet` при исследовании учитывались как явные,
а не произвольные.

## Цель

Сохранять каждый объявленный реквизит формы и каждую объявленную колонку в общем
индексе метаданных независимо от наличия поля `Тип`.

Один договор формирования индекса должен использоваться:

- при XML → YAML import;
- при validation существующего YAML;
- при YAML → XML;
- при проверке и форматировании `ПутьКДанным`;
- при поиске ссылок и операциях rename/delete.

## Семантический договор

Отсутствие `Тип` у реквизита формы или колонки означает известный тип
`Произвольный`, а не невозможность определить тип.

В `DataPathTypeInfo` эти состояния различаются:

- `kinds: ["any"]` — элемент объявлен с типом `Произвольный`;
- `kinds: ["unknown"]` — тип не удалось определить из-за неполных или
  неподдержанных данных.

Для `Произвольный` используется компактная проекция:

```ts
{
  kinds: ["any"],
  nextTypes: [],
  sourceText: "Произвольный",
}
```

Явный `Тип` заменяет эту начальную проекцию результатом общего преобразователя
`TypeDescription`. `TypeSet` и составные типы продолжают обрабатываться этим же
преобразователем.

YAML-договор не меняется: import не добавляет `Тип: Произвольный`, а сохраняет
существующую компактную запись `{}` или остальные свойства элемента без `Тип`.

## Архитектура

### Факт объявления metadata-item

Существующий поток локальных фактов дополняется нейтральным событием объявления
элемента коллекции. Событие содержит только сведения, доступные общему обходу:

- `itemType`;
- окончательный YAML-путь элемента;
- путь правил;
- имя или ключ элемента.

Import отправляет событие после определения окончательного YAML-ключа элемента.
Validation отправляет такое же событие при обходе существующего YAML по тем же
`rules.ts`.

Общий слой orchestration не проверяет `itemType`, имена `Реквизиты`/`Колонки` или
пути форм. Он только сообщает о факте объявления. Конкретный смысл события задаёт
зарегистрированный обработчик владельца metadata-item.

Это событие необходимо не только для пустых объектов: существование элемента
является самостоятельным фактом метаданных и не должно выводиться из наличия
какого-либо его свойства.

### Проекция формы

Обработчик форм принимает объявления `FormAttribute` и
`FormAttributeColumn` и добавляет их в `FormDataPathIndex`:

1. объявление реквизита создаёт корень с типом `Произвольный`;
2. объявление колонки создаёт колонку с типом `Произвольный`;
3. событие свойства `Тип` уточняет уже созданную запись;
4. событие `ДинамическийСписок` уточняет источник таблицы по существующему
   договору;
5. повторное получение объявления не создаёт дубликат и не стирает уже
   уточнённый тип.

Результат не зависит от того, пришло объявление до или после событий свойств.
Это позволяет одинаково использовать потоковый import и обход YAML при
validation.

### Индекс метаданных и индекс зависимостей

`FormDataPathIndex` остаётся частью локального индекса метаданных формы. При
объединении проекта его корни и колонки сохраняются в общем индексе метаданных и
в `.nkdk/cache/project-state.bin` обычным механизмом вкладов файла.

Новый вид таблицы состояния проекта не нужен: двоичный договор уже хранит корни,
колонки и `DataPathTypeInfo`, а значение `any` уже входит в договор типа.

Индекс зависимостей хранит сами обращения `ПутьКДанным`, их YAML-пути и
координаты диагностики. Он не дублирует описания реквизитов и колонок.

Таким образом:

- индекс метаданных отвечает, какие реквизиты и колонки существуют и какого они
  типа;
- индекс зависимостей отвечает, какой `ПутьКДанным` к ним обращается;
- второй проход сопоставляет обращение с неизменяемым снимком индекса метаданных.

### Общие потребители

Все потребители получают один `FormDataPathIndex` и вызывают общий resolver.
Отдельные списки произвольных реквизитов для import, validation или операций не
создаются. Частные условия по формам не добавляются в
`metadata/orchestration`, `metadata/validation` или `metadata/project`.

## Поток данных на примере

Для YAML:

```yaml
Реквизиты:
  РеквизитыОбъекта:
    Тип: ТаблицаЗначений
    Колонки:
      Значение: {}
```

первый проход сохраняет в индекс метаданных:

```text
Реквизит формы «РеквизитыОбъекта» существует и имеет тип ТаблицаЗначений.
Колонка «РеквизитыОбъекта.Значение» существует и имеет тип Произвольный.
```

Для найденного свойства:

```yaml
ПутьКДанным: РеквизитыОбъекта.Значение
```

в индекс зависимостей сохраняется обращение с координатами YAML. На втором
проходе resolver находит сначала реквизит, затем колонку и успешно завершает
путь.

## Правила разрешения пути

Путь, заканчивающийся на реквизите или колонке типа `Произвольный`, корректен:

```text
РеквизитыОбъекта.Значение
```

Путь нельзя продолжать после `Произвольный`, потому что индекс не знает структуру
значения:

```text
РеквизитыОбъекта.Значение.Поле
```

Такой путь получает ошибку:

```text
ПутьКДанным "РеквизитыОбъекта.Значение.Поле": промежуточный реквизит
"Значение" имеет произвольный тип
```

Это отдельная причина диагностики, а не `неизвестный тип`. Ошибка должна быть
одинаковой для произвольного корня формы и произвольной колонки.

Если имя не объявлено, сохраняются действующие ошибки:

- `неизвестный корень`;
- `неизвестная колонка`.

Наличие хотя бы одной объявленной колонки означает, что состав колонок таблицы
известен. Произвольная колонка участвует в этом признаке наравне с типизированной,
поэтому исправление не должно ослаблять поиск опечаток.

## Обновление состояния проекта

Вклад формы заменяется атомарно вместе с остальными вкладами её YAML-файла.
Повторный import или validation заменяет старые записи. Удаление файла формы
удаляет принадлежащие ему корни и колонки обычным каскадным механизмом.

Формат двоичного состояния и его версия не меняются. В действующем формате
элементы `DataPathTypeInfo.kinds` сохраняются как строки, поэтому значение `any`
уже поддерживается записью, чтением и проверкой состояния проекта.

## Ошибки и устойчивость

- Явный корректный `Тип` всегда имеет приоритет над начальным `Произвольный`.
- Ошибка разбора явного `Тип` не должна молча превращать его в `Произвольный`.
- Неизвестный `itemType` игнорируется зарегистрированными проекторами и не требует
  условия в общем обходе.
- Повторное событие одного объявления идемпотентно.
- Дублирующиеся YAML-имена продолжают проверяться существующим механизмом и не
  скрываются объединением записей индекса.

## Тестирование

### Накопитель

- пустой реквизит формы создаёт корень с `kinds: ["any"]`;
- пустая колонка создаёт колонку с `kinds: ["any"]`;
- явный `Тип` уточняет ранее объявленный элемент;
- результат не зависит от порядка объявления и свойства `Тип`;
- import и validation формируют одинаковый `FormDataPathIndex` для одного YAML.

### Состояние проекта

- произвольный корень и произвольная колонка сохраняются и читаются из двоичного
  состояния без потери `typeInfo`;
- замена и удаление файла удаляют его старые записи;
- существующие типизированные корни и колонки не меняются.

### Resolver

- конечный произвольный реквизит проходит проверку;
- конечная произвольная колонка проходит проверку;
- продолжение после каждого из них выдаёт ошибку про произвольный тип;
- отсутствующий корень и отсутствующая колонка остаются ошибками;
- явные `TypeSet`, составные типы и специальные источники формы сохраняют текущее
  поведение.

### Интеграция

- validation конфигурации `sed_nkdk` больше не сообщает ложную ошибку для
  `РеквизитыОбъекта.Значение`;
- обе ссылки `ОшибкиСертификатов.Ошибки` и
  `ОшибкиСертификатов.ОшибкиНаСервере` проходят проверку;
- специально добавленная опечатка в имени колонки остаётся ошибкой;
- import и последующая чистая validation дают одинаковый результат для этих
  путей.

## Не цели

- Не угадывать фактический тип значения `Произвольный` по имени или месту
  использования.
- Не разрешать переход к полям после `Произвольный`.
- Не добавлять `Тип: Произвольный` в предметный YAML.
- Не ослаблять проверки неизвестных корней и колонок.
- Не создавать отдельный индекс форм рядом с индексом метаданных.
- Не добавлять частные условия по именам форм, реквизитов или колонок в общие
  metadata-слои.

## Критерии готовности

- каждый объявленный реквизит формы и каждая колонка представлены в индексе
  метаданных;
- отсутствие `Тип` представлено как `any`, а не `unknown`;
- import и validation используют общий механизм событий и один проектор формы;
- общий resolver принимает конечный `Произвольный` и запрещает продолжение после
  него;
- известные ложные ошибки `sed_nkdk` устранены без подавления реальных опечаток;
- профильные тесты, `pnpm test` и проверка дубликатов проходят.

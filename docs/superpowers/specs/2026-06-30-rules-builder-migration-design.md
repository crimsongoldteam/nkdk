# Rules Builder Migration Design

## Контекст

После удаления центральных `PropertyTypeRegistry` и `MetadataItemTypeRegistry` общие слои больше не должны хранить список допустимых concrete property/item-типов. При этом часть проверки допустимых полей правила потеряла прежнюю опору на центральный union: строгая локальная проверка сейчас работает только для правил, собранных через builders, как в `metadataLanguage/rules.ts`.

В `rules.ts` остаётся большой объём прямых объектов вида `{ type: "..." }`. Их нужно перенести на локальные builders для всех property-типов, но сделать это быстро и безопасно, без ручного переписывания тысяч правил.

## Цель

Все правила в `packages/core/metadata/**/rules.ts` должны собираться через локальные builders:

```ts
name: stringRule({
  xmlParents: properties,
})
```

вместо:

```ts
name: {
  type: "string",
  xmlParents: properties,
}
```

Builder добавляет фиксированный `type`, а допустимые параметры проверяются рядом с реализацией property-типа. Для простых и уже типизированных property-типов builder должен быть строгим сразу. Для сложных типов допускается временный широкий builder, но он должен быть явно виден в отчёте как долг на уточнение типов.

## Не Цель

- Не менять смысл fromXML/toXML/fromYAML/toYAML.
- Не менять порядок XML/YAML-полей.
- Не переписывать реализации property-типов вручную в рамках одного большого изменения.
- Не возвращать центральный список допустимых property-типов в orchestration.

## Подход

### 1. Инвентаризация

Нужен скрипт, который собирает из `packages/core/metadata/**/rules.ts` все прямые правила с `type: "..."` и строит таблицу:

- `property type`;
- количество использований;
- список файлов;
- есть ли builder;
- откуда импортировать builder;
- строгий builder или временно широкий;
- можно ли безопасно переносить автоматически.

Этот отчёт нужен перед изменениями и после каждой партии, чтобы видеть остаток и не гадать по `rg`.

### 2. Builders Для Всех Типов

Для каждого property-типа должен появиться builder рядом с его типом или регистрацией. Примеры:

- `stringRule`, `uuidRule`, `xmlRootRule`, `i8nTextRule`, `systemEnumerationRule` уже существуют и являются образцом.
- `booleanRule`, `numberRule`, `moduleRule`, `pictureRule`, `colorRule` и другие добавляются постепенно.

Строгий builder использует локальный интерфейс параметров и `ExactRuleParams`, чтобы чужие поля не проходили компиляцию. Временный широкий builder допустим только для сложного типа, если точный интерфейс ещё не выделен. Такой builder должен иметь имя обычного вида, но попадать в отчёт как `wide`.

Важно: широкий builder является переходным механизмом переноса, а не конечной архитектурой.

### 3. Механический Перенос

AST-преобразователь меняет прямые объекты правил на вызовы builders:

```ts
picture: {
  type: "Picture",
  metadataTarget: { kind: "object", roots: ["CommonPicture"] },
  xmlParents: properties,
}
```

становится:

```ts
picture: pictureRule({
  metadataTarget: { kind: "object", roots: ["CommonPicture"] },
  xmlParents: properties,
})
```

Преобразователь должен:

- удалять поле `type` из параметров builder;
- сохранять остальные поля без изменения;
- сохранять функции, spread, `metadataTarget`, `defaultItemRule`, вложенные правила;
- добавлять недостающие imports;
- не менять файл, если для типа нет разрешённого builder;
- уметь запускаться по списку типов и по списку файлов.

### 4. Партии Переноса

Перенос выполняется партиями:

1. базовые частые типы: `string`, `boolean`, `number`, `uuid`, `XMLRoot`, `I8nText`, `SystemEnumeration`;
2. частые инфраструктурные типы: `Module`, `InternalInfo`, `DataPath`, `TypeDescription`, `MetadataItemLink(s)`, `Events`;
3. child/project/resource типы: `ChildFormNames`, `ChildTemplateNames`, `ChildFileItemNames`, `ExternalFile`, `ExternalPicture`;
4. остальные зарегистрированные common/form/applied property-типы по убыванию количества использований.

После каждой партии запускается TypeScript. Если строгий builder выявляет лишнее поле, исправляется либо правило, либо локальный интерфейс property-типа, но не расширяется общий orchestration-тип.

### 5. Границы И Защита От Отката

После полного переноса добавляется boundary-тест, запрещающий новые прямые `type: "..."` в production `rules.ts`. Исключения допускаются только явно:

- тестовые файлы;
- временный список сложных мест, если их нельзя перенести в текущей партии;
- не-property объекты, где `type` является бизнес-данными, а не discriminator правила.

Исключения должны быть точечными и видимыми в тесте.

## Проверки

Минимальная проверка каждой партии:

```bash
pnpm --filter @nakidka/core exec tsc --noEmit
pnpm --filter @nakidka/core test
```

Перед завершением всей миграции:

```bash
pnpm test
```

Дополнительно:

- отчёт инвентаризации показывает ноль прямых property-rule `{ type: "..." }` вне разрешённых исключений;
- boundary-тест падает, если добавить новое прямое правило в `rules.ts`;
- существующие tests для builders проверяют лишние поля хотя бы на базовых типах;
- для wide-builders есть отдельный отчёт/список долгов.

## Риски

Главный риск - механический перенос может изменить не property-rule объект, а обычные данные с полем `type`. Поэтому преобразователь должен работать только внутри `properties`, `defaultItemRule` и других известных rule-позиций, а не заменять все объекты с `type` по тексту.

Второй риск - слишком ранняя строгая типизация сложных типов может раздуть изменение. Поэтому широкий builder разрешён как переходный слой, но только если он явно отмечен и не маскирует цель миграции.

Третий риск - массовые импорты могут ухудшить читаемость. Поэтому imports должны добавляться из уже существующих локальных модулей property-типа, а не из нового центрального barrel со всеми builders.

## Ожидаемый Результат

`rules.ts` больше не пишут discriminator `type` вручную. Новое правило собирается через builder конкретного property-типа, а проверка допустимых полей живёт рядом с этим типом. Общие слои остаются нейтральными, а список оставшихся широких builders становится явным планом дальнейшего уточнения.

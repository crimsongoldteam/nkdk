# Значения по умолчанию владельца при проверке значения заполнения

## Контекст

Проверка `ЗначениеЗаполнения` стандартного реквизита `Код` определяет его
эффективный тип по свойствам справочника:

- `ТипКода`;
- `ДлинаКода`;
- `ДопустимаяДлинаКода`.

В YAML эти свойства не записываются, когда равны неявным значениям из
`rules.ts`. Например, для справочника тип кода по умолчанию — `Строка`, а длина
кода по умолчанию — `9`. Текущая проверка читает только явно присутствующие
YAML-ключи и поэтому не видит действующий тип или длину.

На контрольном импорте SED это создаёт 23 ложных предупреждения:

- 20 раз — `не определён тип кода`;
- 3 раза — `не определена длина кода`.

## Цель

При проверке зависимого свойства использовать явное значение свойства
владельца, а при его отсутствии — статическое `implicitValueYAML` из того же
правила `rules.ts`.

Это должно одинаково работать:

- при нормализации результата XML → YAML;
- при последующей проверке YAML-проекта.

## Границы

В задачу входит только построение эффективных свойств владельца для предметной
проверки `ЗначениеЗаполнения`.

В задачу не входят:

- раскрытие `DefinedType`;
- обработка отсутствующего списка владельцев справочника;
- изменение общих типов правил или параметров построителей правил;
- добавление отдельных констант с платформенными значениями по умолчанию;
- вычисление функционального `implicitValueYAML`.

## Договор эффективного значения

Для каждого свойства владельца, которое описано в корневом `rules.ts`, значение
определяется в следующем порядке:

1. Если соответствующий YAML-ключ присутствует, используется его значение.
2. Если YAML-ключ отсутствует и правило содержит статическое
   `implicitValueYAML`, используется это неявное значение.
3. Если ключ отсутствует, а статического `implicitValueYAML` нет, свойство
   остаётся неопределённым.

Явное YAML-значение всегда имеет приоритет. `defaultValueXML` для этой задачи не
читается: проверяется смысл YAML-модели, поэтому источником неявного значения
служит именно `implicitValueYAML`.

Функциональное `implicitValueYAML` не вызывается. Для вычисления такой функции
нужен отдельный договор контекста, а все три свойства кода используют
статические значения.

## Архитектура

Логика остаётся в предметном модуле `commonObjects/fillValue`.
`ownerProperties()` продолжает обходить свойства корневого правила, но формирует
эффективное значение по описанному договору вместо простого пропуска
отсутствующего YAML-ключа.

Общие metadata-операции и общие типы `PropertyRule` не меняются. Проверка не
дублирует значения `Строка` и `9`: они уже объявлены владельцем поведения в
`metadataCatalog/rules.ts`.

Существующий `classifyStandardAttributeFillValue()` используется и импортом, и
validation. Поэтому эффективные свойства должны подготавливаться перед этим
общим классификатором, без отдельных условий для двух операций.

## Поведение импорта

После подстановки неявных свойств классификатор получает полный эффективный тип
кода.

- Пустая строка и строка из пробелов считаются неявным заполнением кода.
- Такое `ЗначениеЗаполнения` удаляется из итогового YAML.
- Точная исходная XML-форма сохраняется существующим снимком конфигурации и
  восстанавливается при YAML → XML.
- Содержательное значение проверяется по эффективному типу и остаётся в YAML,
  если ему соответствует.

Новый формат снимка и новое применение `!xml` не требуются.

## Поведение validation

Повторная проверка импортированного проекта использует те же неявные свойства,
что и импорт. Отсутствие `ТипКода` или `ДлинаКода` в YAML само по себе больше не
создаёт предупреждение.

Если пользователь явно записал несовместимое значение заполнения, сохраняется
обычная предметная ошибка классификатора. Если правило действительно не
позволяет определить нужное свойство, сохраняется предупреждение
`unresolved` — задача не подменяет неизвестные значения догадками.

## Проверки

Модульные проверки должны подтвердить:

1. Явные `ТипКода`, `ДлинаКода` и `ДопустимаяДлинаКода` имеют приоритет.
2. При отсутствии YAML-ключей используются их статические `implicitValueYAML`.
3. `defaultValueXML` без `implicitValueYAML` не участвует в проверке.
4. Функциональное `implicitValueYAML` не вызывается.
5. Пустое и пробельное заполнение строкового кода удаляется при XML-импорте и
   сохраняется в снимке.
6. Содержательное значение `--` для строкового кода длиной `3` проходит
   проверку и остаётся в YAML.
7. Импорт и чистая validation одного YAML дают одинаковую классификацию.

## Контрольный импорт SED

После реализации повторный чистый импорт должен устранить все 23 предупреждения
этой группы:

- 22 пустых или пробельных значения заполнения кода отсутствуют в окончательном
  YAML и восстанавливаются из снимка;
- `Справочник.СтраныМира` сохраняет содержательное значение `--`;
- предупреждений `не определён тип кода` и `не определена длина кода` нет.

Остальные группы предупреждений не изменяются этой задачей.

# Эталонный NKDK-проект для e2e

## Цель

Разделить существующую замкнутую проверку `XML → NKDK → XML` на две независимые проверки через сохранённый эталонный NKDK-проект. Это должно отдельно обнаруживать изменения YAML-представления и изменения генерации XML, включая взаимно компенсирующие ошибки импорта и экспорта.

## Эталонные данные

- Исходные XML хранятся в `e2e/fixtures/xml` без изменения текущей структуры.
- Полный эталонный NKDK-проект хранится в `e2e/fixtures/nkdk`.
- Эталон повторяет реальную структуру проекта: `cf` и все компоненты `cfe`, перечисленные в `E2E_COMPONENTS`.
- Служебный кеш `.nkdk` в эталон не входит.
- Пути и содержимое файлов сравниваются побайтно.

## Прямое направление: XML → NKDK

Существующий импорт всех компонентов продолжает создавать временный NKDK-проект через реальный runtime и workers. Отдельная e2e-проверка сравнивает полученное дерево с `e2e/fixtures/nkdk`.

При расхождении тест сообщает добавленные, удалённые и изменённые пути. Подробности записываются в `reports/e2e/nkdk-import`: `summary.txt` и обычные `.diff` для изменённых файлов.

## Обратное направление: NKDK → XML

Существующая проверка побайтового XML round-trip перестаёт использовать только что импортированный NKDK-проект. Вместо этого она копирует `e2e/fixtures/nkdk` во временный каталог, синхронизирует из этой копии каждый компонент и сравнивает результат с соответствующим каталогом `e2e/fixtures/xml`.

Эталонный каталог не используется как рабочий: тест не должен создавать в нём `.nkdk` или менять сохранённые файлы.

## Валидация

Существующая проверка чистой валидации остаётся и использует временный проект, полученный прямым импортом, поскольку отдельное побайтовое сравнение подтверждает его равенство эталону.

## Обновление эталона

В корневом `package.json` появляется команда:

```text
pnpm fixtures:e2e:nkdk
```

Команда запускает импорт тех же `E2E_COMPONENTS` с теми же контекстами и реальными workers, что e2e. Если хотя бы один компонент содержит ошибку импорта, команда завершается с ошибкой и не меняет текущий эталон.

Успешный результат сначала копируется во временный каталог рядом с `e2e/fixtures/nkdk`. После полной подготовки каталоги заменяются переименованием; при ошибке замены прежний эталон восстанавливается. Это исключает сохранение частично обновлённого проекта.

Команда всегда обновляет весь проект. Частичное обновление одного компонента не поддерживается.

## Общие компоненты e2e

Логика создания runtime, импорта компонентов и очистки временного проекта остаётся общей для тестов и команды обновления. Сравнение файловых деревьев продолжает использовать `compareFileTrees`: YAML и остальные текстовые файлы получают обычный diff, а вложенные XML-файлы — дополнительно нормализованный XML-diff.

## Обработка ошибок

- Ошибка импорта блокирует обновление эталона и выводится вместе с диагностикой компонента.
- Отсутствующий эталон допустим только при первом успешном запуске команды обновления; e2e в этом состоянии завершается ошибкой.
- Любое различие прямого или обратного направления проваливает соответствующий тест.
- Временные каталоги удаляются и после успеха, и после ошибки.

## Проверки реализации

- Модульный тест подтверждает, что неуспешный импорт не заменяет существующий каталог.
- Модульный тест подтверждает успешную замену полного каталога и очистку временных данных.
- Проверка структуры фикстур требует `Configuration.xml` в XML-компонентах, `Конфигурация.yaml` в NKDK-компонентах и запрещает `.DS_Store` и `.nkdk`.
- e2e отдельно проверяет побайтовое равенство `XML → NKDK` и `NKDK → XML` для конфигурации и всех расширений.
- `pnpm test:e2e` остаётся единой командой полной проверки.

# Общие lookup-индексы полной XML-синхронизации

**Статус:** проект решения согласован, письменная спецификация ожидает проверки

**Дата:** 2026-08-04

## Контекст

Профиль полной YAML → XML синхронизации ERP с `concurrency: 4` показал:

- 119 781 обработанный YAML и 139 194 записанных XML-файла;
- 594,67 секунды реального времени без CPU-инструментирования;
- 1 484,18 секунды user CPU и 661,90 секунды system CPU;
- 6,73 ГиБ максимального RSS;
- обязательный `refreshAndValidate` занимает 11,9 секунды и не определяет общую длительность sync.

Основные user CPU-затраты находятся в двух общих структурах чтения:

1. Для каждого назначения worker вызывает `state.composition.assignments()`, а подготовка XML повторно преобразует весь список композиции. При 119 781 назначении это создаёт квадратичную работу и большое число временных объектов.
2. Каждый worker при первом обратном поиске в configuration index декодирует все строки и строит собственный `Map<string, number>`. Аналогичные локальные `Map` лениво строятся для файлов, entity и группировки entity по исходному пути.

Validation уже решает похожую задачу иначе: неизменяемые lookup-таблицы находятся в `SharedArrayBuffer`, используют линейное пробирование с заполнением не выше 80% и проверяют исходный ключ после совпадения хэша. Worker создают только лёгкие представления и ленивые локальные кэши реально прочитанных значений.

## Цели

- Удалить полный обход композиции из цикла обработки назначений.
- Не создавать полные обратные `Map` configuration index в каждом worker.
- Переиспользовать один проверенный алгоритм неизменяемого двоичного hash-index в project state, композиции sync и configuration index.
- Хранить общие lookup-таблицы в `SharedArrayBuffer` и строить их один раз на операцию.
- Сохранить дисковый формат configuration index `1.3` и формат project state побайтно совместимыми.
- Сохранить XML/YAML-семантику, порядок результатов и существующие round-trip расхождения.

## Не входит в решение

- Изменение дискового формата configuration index.
- Изменение дискового формата или версии project state.
- Отключение либо упрощение `refreshAndValidate`.
- Изменение степени параллелизма sync.
- Частичная синхронизация.
- Изменение `rules.ts`, прикладных metadata-типов или XML-фикстур.
- Оптимизация сериализации и записи 139 тысяч XML-файлов, если после устранения двух найденных причин они останутся следующим узким местом.
- Жёсткий временной порог в CI, зависящий от файловой системы и машины.

## Рассмотренные подходы

### (А) Общий неизменяемый двоичный hash-index

Выбран. Алгоритм project state извлекается в нейтральный metadata-модуль и используется тремя потребителями. Формат 16-байтовой ячейки и поведение project state сохраняются.

Преимущества:

- один алгоритм построения, поиска, проверки коллизий и обхода;
- общие данные не копируются между worker;
- одинаковые ограничения заполнения и повреждения;
- отсутствие предметной зависимости sync от project state.

Цена — контролируемое изменение импортов существующего project state, которое требует проверки dependency-cruiser и побайтовой совместимости.

### (Б) Отдельная копия алгоритма для sync

Отклонён. Меньше затрагивает project state, но создаёт две реализации линейного пробирования, которые могут разойтись по формату, проверке коллизий и ограничениям заполнения.

### (В) Сортированные массивы и бинарный поиск

Отклонён как общий подход. Он экономит таблицу хэшей, но требует отдельных правил сортировки для каждого составного ключа и даёт более дорогой массовый поиск. Сортированные диапазоны остаются внутренней частью группировки одинаковых ключей, но не заменяют lookup-таблицу.

## Нейтральный двоичный hash-index

Новый модуль `packages/core/metadata/binary/hashIndex.ts` не знает о validation, project state, XML, композиции или configuration index.

Он предоставляет:

- представление 16-байтовой ячейки `{ hash, recordId, occupied, reserved }`;
- расчёт ёмкости с заполнением не выше 80%;
- построение неизменяемой таблицы в `SharedArrayBuffer` из `BigUint64Array` хэшей и `Uint32Array` идентификаторов записей;
- поиск с линейным пробированием;
- обязательный callback проверки исходного ключа при совпадении хэша;
- обход занятых ячеек для построителей и проверок;
- проверку ёмкости, границ буфера и корректности входных массивов.

Хэширование и кодирование предметного ключа остаются у потребителя. Общий модуль работает только с готовым 64-битным хэшем и числовым `recordId`.

Существующий `projectState/binary/hashIndex.ts` заменяется импортом нейтрального модуля. Представление ячейки переносится без изменения порядка полей, размеров и порядка байтов. Дисковый project state должен читать ранее записанные таблицы и формировать те же байты для эквивалентного входа.

## Индексированная композиция sync

### Общий снимок

`FullXmlSyncSharedCompositionSnapshot` продолжает содержать компактную таблицу назначений и общий пул строк. Дополнительно он содержит:

- записи детей, сгруппированные по `ownerLogicalAddress`;
- диапазоны детей каждого владельца;
- hash-index `ownerLogicalAddress → rangeId`;
- сведения, достаточные для однократного построения `itemTypeByYamlDir` без создания полного массива предметных объектов.

Снимок строится главным процессом один раз из текущего `FullXmlSyncPlan` и передаётся worker как набор ссылок на `SharedArrayBuffer`.

### Договор чтения

Capability получает нейтральный предметный запрос вместо полного массива:

```ts
interface MetadataXmlPrepareComposition {
  children(ownerLogicalAddress: string): readonly MetadataXmlPrepareCompositionEntry[]
}
```

`children()` вычисляет хэш владельца, находит диапазон и декодирует только принадлежащие ему записи. Коллизия подтверждается сравнением исходного `ownerLogicalAddress`. Владелец без детей получает пустой массив.

`collectCompositionChildPropertyValues` запрашивает детей текущего владельца и группирует только их по `itemType`. Общий metadata-слой не содержит условий по конкретным `itemType`, именам объектов или каталогам.

Полный `assignments()` удаляется из capability-договора и не вызывается внутри цикла назначения. Если внутренний reader сохраняет диагностический полный обход, production-путь подготовки XML его не использует.

### Подготовка YAML

`itemTypeByYamlDir` строится один раз при инициализации full-sync состояния каждого worker. Reader проходит сырые компактные записи без материализации `FullXmlSyncCompositionEntry[]`; локально остаётся только небольшое отображение каталогов в типы.

Повторные `executeBatch` используют готовое отображение. Состояние операции очищается существующей командой `dispose`; постоянные schema/rules-кэши универсального worker сохраняются как прежде.

## Общие lookup-таблицы configuration index

### Построение

Дисковый файл `configuration-index.bin` версии `1.3` остаётся источником истины. Import заполняет его, а успешный sync обновляет как прежде.

При `snapshotConfigurationIndex()` главный процесс:

1. проверяет существующие секции `1.3`;
2. копирует байты и таблицы смещений в общую память;
3. один раз строит дополнительные неперсистентные lookup-таблицы;
4. передаёт один `SharedConfigurationIndexSnapshot` всем worker операции.

После завершения операции таблицы освобождаются вместе со снимком. Следующий процесс способен восстановить их только из неизменённого файла `1.3`, поэтому отдельная миграция не нужна.

### Состав lookup-таблиц

Снимок содержит:

- `UTF-8 string → stringId` для обратного поиска строки;
- `projectPath stringId → file record`;
- `logicalAddress stringId → entity offset`;
- `sourceProjectPath stringId → range entity offsets` для `entitiesBySourceProjectPath()`.

Строковый индекс хэширует UTF-8 байты и при коллизии сравнивает байты непосредственно в секции строк, не декодируя весь пул. Остальные индексы используют каноническое двоичное кодирование числового `stringId` и подтверждают совпадение полем исходной записи.

Для группировки entity по исходному пути строится отдельный массив смещений и таблица диапазонов по тому же принципу, что lookup владельцев validation. Полная объектная копия entity не создаётся.

### Reader

Каждый `ConfigurationIndexReader` создаёт только представления над общими буферами и лениво кэширует декодированные найденные строки. Поля `stringIds`, `fileOffsetByPathId`, `entityOffsetByAddressId` и `entityOffsetsBySourcePathId` в виде локальных полных `Map` удаляются.

Публичный договор `ConfigurationIndexReader` и результаты методов `file()`, `entity()`, `entitiesBySourceProjectPath()`, `files()` и `entities()` не меняются.

## Поток данных

1. Import либо предыдущий sync записывает configuration index `1.3`.
2. Sync выполняет обычный `refreshAndValidate`.
3. Координатор читает и проверяет `1.3`, строит один shared lookup-снимок configuration index.
4. Координатор строит один индексированный shared-снимок композиции из актуального плана.
5. Универсальные worker получают ссылки на оба снимка и создают лёгкие reader.
6. Worker один раз строит `itemTypeByYamlDir`.
7. Для каждого назначения worker читает только YAML, нужные записи configuration index и детей текущего владельца.
8. Worker записывает XML и возвращает существующий двоичный результат.
9. Главный процесс объединяет фрагменты и записывает новый configuration index `1.3`.
10. Временное состояние full-sync операции и его reader очищаются; постоянное состояние универсального worker остаётся.

## Ошибки и целостность

- Hash-index никогда не принимает совпадение одного хэша за совпадение ключа.
- Некорректная ёмкость, выход `recordId` или диапазона за буфер, повреждённый заголовок и невозможный коэффициент заполнения являются технической ошибкой.
- Заголовки, ёмкости и границы всех lookup-таблиц проверяются при открытии reader. Несовпадение исходного ключа при корректном совпадении хэша является обычной коллизией; недопустимый `recordId` или диапазон, обнаруженный при поиске, является технической ошибкой существующей операции.
- Резервного полного `Map` или линейного поиска нет: такой fallback скрыл бы регрессию производительности.
- Ошибка построения новых lookup-таблиц не изменяет configuration index на диске.
- Порядок возвращаемых детей и entity остаётся детерминированным и совпадает с текущим предметным порядком, а не с расположением hash-слотов.

## Совместимость и архитектурные границы

- Configuration index остаётся версией `1.3`; его кодирование не включает lookup-таблицы.
- Версия и байты project state не меняются.
- Общий `metadata/binary/hashIndex.ts` зависит только от structurae-представления ячейки и стандартных двоичных типов JavaScript.
- `projectState`, `fullSyncToXml` и `configurationIndex` зависят от нейтрального модуля, но не друг от друга.
- `metadata/orchestration`, `metadata/validation` и `metadata/project` не получают условий по `itemType` или структуре прикладных объектов.
- `.dependency-cruiser.mjs`, baseline и сам инструмент dependency-cruiser менять не планируется.
- `.agents/architecture.md` не требует изменения: решение сохраняет описанный общий снимок project state, компонентный снимок `1.3` и универсальные worker.

## Проверки

Тесты следуют `.agents/testing.md`: сначала усиливается ближайший существующий тест, новый тест добавляется только для самостоятельного договора.

### Общий hash-index

- поиск существующего и отсутствующего ключа;
- несколько ключей с одинаковым хэшем и проверка исходного ключа;
- граница заполнения 80%;
- отклонение несовпадающих массивов и повреждённых границ;
- побайтовый тест 16-байтовой ячейки;
- существующие persistence- и hash-index тесты project state подтверждают совместимость формата.

### Композиция

- поиск детей одного владельца среди большого числа чужих записей;
- одинаковые имена и `itemType` у разных владельцев;
- владелец без детей;
- детерминированный порядок результатов;
- коллизия хэшей владельцев;
- `itemTypeByYamlDir` строится один раз на инициализацию worker и переиспользуется между batch;
- подготовка одного назначения не вызывает полный обход композиции.

### Configuration index

- несколько reader используют одни и те же lookup-буферы;
- обратный поиск строки не декодирует весь пул;
- корректный поиск файла, entity и entity по исходному пути;
- коллизии хэшей и отсутствующие ключи;
- декодируется только найденное значение;
- кодирование `1.3` до и после изменения даёт прежние байты на фиксированном снимке.

### Интеграция и профиль

- целевые тесты `fullSyncToXml`, `configurationIndex` и `projectState`;
- `pnpm type-check`;
- `pnpm test`;
- `pnpm test:architecture` после изменения импортов и структуры модулей;
- ERP round-trip с `concurrency: 4`: 119 781 YAML успешно обрабатываются, а набор 52 известных несвязанных расхождений не изменяется;
- повторный профиль полной генерации сравнивается с 594,67 секунды и 6,73 ГиБ RSS;
- `prepareAssignment` с полной композицией и `findStringId` с полным `Map` должны исчезнуть из ведущих CPU-затрат.

Точное время не становится CI-порогом. Структурные тесты запрещают квадратичный путь, а профиль подтверждает практический эффект на ERP.

## Проверка дублей и архитектуры по слоям

Базовый коммит реализации: `3c9281164`.

После каждого законченного слоя и перед завершением выполняются:

```bash
pnpm check:duplicates -- --base 3c9281164
pnpm test:architecture
```

Слои:

1. извлечение нейтрального hash-index и перевод project state;
2. индексированная композиция sync;
3. shared lookup-таблицы configuration index;
4. итоговая интеграция и профиль.

`pnpm test:architecture` должен завершиться без новых нарушений dependency-cruiser. Известные нарушения учитываются существующим baseline и не маскируют новые.

`pnpm test:architecture:rules` запускается только если реализация вынужденно изменит `.dependency-cruiser.mjs` или `tools/dependency-cruiser`; такие изменения требуют отдельного согласования и сейчас не входят в проект.

`pnpm check:duplicates` использует установленный jscpd и блокирует только новые дубли относительно базового коммита.

## Критерии готовности

- Один нейтральный hash-index используется минимум project state, композицией sync и configuration index.
- Дисковые форматы project state и configuration index `1.3` не изменились.
- В цикле назначения нет `state.composition.assignments()` и полного преобразования композиции.
- Ни один `ConfigurationIndexReader` не строит полный локальный обратный `Map` строк, файлов или entity.
- Все функциональные, типовые и архитектурные проверки проходят.
- jscpd не обнаруживает новых дублей относительно `3c9281164`.
- ERP round-trip сохраняет результат, а повторный профиль документирует время, RSS и новые ведущие затраты.

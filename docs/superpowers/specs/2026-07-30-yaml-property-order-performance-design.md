# Оптимизация сортировки свойств YAML

## Контекст

Во время XML-import функция `sortYamlRuleProperties` упорядочивает свойства
каждого объекта, сформированного через `importPropertiesFromXMLToYAML`.
`Заголовок` и `Синоним` получают первый приоритет, затем идут `Вид` и `Тип`,
остальные ключи сортируются по русскому алфавиту через общий экземпляр
`Intl.Collator`.

Текущая реализация строит массив пар через `Object.entries`, сортирует его и
создаёт новый объект через `Object.fromEntries`. CPU profile на `cf/doc`
показывает около `274 мс` внутри этой функции. Примерно `74–80 мс` приходится
на сравнение ключей, а основная часть — на работу с массивом пар, сортировку и
создание результата.

Изолированный benchmark на Node `26.4.0` показал:

| Ключей | Текущая реализация | `Object.keys` + `for` | Ускорение |
|---:|---:|---:|---:|
| 4 | 503 нс | 394 нс | 1,28× |
| 10 | 1 808 нс | 1 521 нс | 1,19× |
| 30 | 9 975 нс | 7 322 нс | 1,36× |
| 80 | 33 685 нс | 26 005 нс | 1,30× |

Замена условий в `priority` на `switch` не дала измеримого выигрыша.

## Цель

Уменьшить время и количество краткоживущих выделений памяти при сортировке
свойств YAML, полностью сохранив существующий порядок ключей.

Ожидаемый выигрыш всего импорта невелик — около `50–80 мс` на `cf/doc`.
Изменение оправдано локальностью и отсутствием нового архитектурного механизма.

## Границы

Изменяется только реализация `sortYamlRuleProperties`.

Не изменяются:

- приоритеты `Заголовок`, `Синоним`, `Вид` и `Тип`;
- русский `Intl.Collator` и его единственный экземпляр на модуль;
- место вызова сортировки;
- правила XML → YAML;
- порядок элементов коллекций;
- порядок произвольных вложенных словарей;
- формат итогового YAML.

Кэш порядка ключей не добавляется: CPU profile не показывает достаточной
стоимости сравнений, чтобы оправдать дополнительное состояние.

## Решение

Функция:

1. получает массив собственных перечислимых строковых ключей через
   `Object.keys`;
2. сортирует ключи существующим сравнением `priority + collator.compare`;
3. создаёт новый обычный объект;
4. переносит значения в отсортированном порядке императивным циклом `for`.

Это исключает массивы пар `[key, value]` и накладные расходы
`Object.fromEntries`.

Для ключа `__proto__` обычное присваивание меняет прототип вместо создания
собственного свойства. Такой ключ переносится через `Object.defineProperty`
с флагами `enumerable`, `configurable` и `writable`, чтобы сохранить поведение
текущей реализации.

Импорт формирует обычные объекты с data-свойствами. Объекты с getters, setters
или Proxy не являются поддерживаемым входом этой внутренней функции.

## Корректность

Существующие тесты продолжают подтверждать:

- особые ключи располагаются согласно приоритету;
- остальные ключи сортируются по русскому алфавиту;
- вложенные значения не сортируются рекурсивно.

Добавляются проверки:

- оптимизированный результат совпадает с эталонной реализацией
  `Object.fromEntries(Object.entries(...).sort(...))` для разных наборов
  ключей;
- собственное свойство `__proto__` сохраняется и не меняет прототип
  результата;
- пустой объект и объект из одного свойства обрабатываются без особых веток.

## Производительность

Изолированный benchmark сравнивает текущий эталон и новую реализацию на
объектах с `4`, `10`, `30` и `80` ключами. Значения результата участвуют в
контрольной сумме, чтобы V8 не удалил вычисления.

Критерии:

- новая реализация формирует те же ключи и значения;
- она быстрее эталона на всех четырёх размерах после прогрева;
- полный `cf/doc` не показывает регрессии времени или Peak RSS;
- небольшой выигрыш полного импорта не считается обязательным из-за шума,
  превышающего ожидаемые `50–80 мс`.

## Ошибки и совместимость

Функция не вводит новых ошибок и не меняет обработку ошибок импорта.
Публичные сигнатуры и правила не изменяются. Изменение совместимо с текущими
вызовами и не требует миграции.

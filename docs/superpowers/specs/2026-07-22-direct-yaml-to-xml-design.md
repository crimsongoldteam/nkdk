# Прямое преобразование YAML в XML без metadata-модели

## Контекст

Синхронизация сейчас сначала преобразует YAML в полную metadata-модель, а затем преобразует модель в XML. Два общих обхода правил увеличивают время работы и потребление памяти, а также сохраняют модельный промежуточный договор там, где итоговой операции нужен только XML.

Обратное направление уже объединено: импорт строит YAML непосредственно из XML единым обходом правил и использует только атомарные преобразования конкретных типов. Для симметрии синхронизация YAML → XML должна работать так же.

Переименование и поиск ссылок также строят metadata-модели только ради навигации и изменения YAML. Они должны перейти на общий YAML-ориентированный обход, чтобы общая оркестрация YAML → metadata-модель больше не требовалась.

## Цель

Все виды синхронизации должны создавать XML непосредственно из YAML за один обход `rules.ts` для каждого YAML-объекта, без полной или частичной metadata-модели и без переходника, имитирующего её интерфейс.

Переименование и поиск ссылок должны читать и изменять исходные YAML-данные через тот же общий механизм навигации по правилам. После перехода общие property-level операции `fromYAML` и `toXML` удаляются. Остаются только атомарные преобразования конкретных типов, например преобразования `I8nText`.

## Не цели

- Не менять форматы YAML, XML и файла индекса конфигурации.
- Не менять внешний договор команд полной и частичной синхронизации, переименования и поиска ссылок.
- Не менять существующую семантику default/reference-значений, XML-порядка, альтернативных XML-имён и неизвестных узлов исходного XML.
- Не вводить запасной путь через metadata-модель для неподдержанных правил.
- Не добавлять частные условия по `itemType`, именам XML-корней или конкретным прикладным объектам в общие metadata-слои.
- Не делать запись XML транзакционной и не удалять автоматически уже записанные файлы после ошибки.

## Выбранный подход

Добавляется единая общая оркестрация YAML → XML. Она кэширует подготовленное описание правил, но для каждого YAML-объекта выполняет только один основной обход `rules.ts`.

Для каждого свойства оркестрация:

1. определяет участие свойства и его место в XML с учётом исходного XML и файла индекса конфигурации;
2. читает исходное YAML-значение, default/reference-значение или связанный внешний файл;
3. вызывает зарегистрированное атомарное преобразование конкретного типа из YAML;
4. сразу передаёт временное значение атомарному преобразованию того же типа в XML;
5. записывает результат в нужный XML-файл и обновляет данные файла индекса конфигурации;
6. освобождает временное значение перед переходом к следующему свойству.

Если для типа нет отдельного атомарного обработчика одного из направлений, единая оркестрация применяет действующую семантику простого значения, default и XML-обёртки. Общих промежуточных `importPropertyFromYAML` и `exportPropertyToXML` не остаётся.

## Общий YAML-ориентированный обход

Обход работает с исходными YAML-ключами и общим `YamlRuleCursor`. Он предоставляет нейтральные сведения:

- текущее YAML-значение и его путь;
- текущее правило и путь правила;
- наличие соседнего YAML-свойства и возможность точечно прочитать его исходное значение;
- контекст владельца, исходного XML и файла индекса конфигурации;
- целевые XML-файлы, в которые направляется результат.

Обход не предоставляет объект с полями metadata-модели. Условия правил, которые сейчас читают такую модель, переводятся на проверку исходного YAML, контекста или декларативного признака правила.

Для зависимостей формы и других составных свойств разрешён компактный контекст, лениво вычисляемый из конкретного YAML-поддерева. Он содержит только необходимые сведения и не становится моделью. Отдельного предварительного обхода всех properties нет.

Вложенные rules-объекты и коллекции рекурсивно используют тот же механизм. Точечное чтение соседнего YAML-значения не запускает повторный обход набора правил и не сохраняет преобразованное значение в объекте модельной формы.

## Формирование XML

Один обход YAML-объекта формирует все связанные с ним результаты:

- основной XML объекта;
- дополнительные XML-файлы;
- для формы — описание формы и `Ext/Form.xml`;
- задания записи или копирования внешних файлов;
- фрагмент данных файла индекса конфигурации.

Правило сразу направляет свойство в один или несколько требуемых XML-файлов. Формы, внешние свойства и вложенные коллекции не требуют повторного перебора `rules.ts`.

Каждый XML-результат независимо учитывает:

- порядок и наличие свойств в исходном XML;
- альтернативные XML-имена;
- `xmlParents` и корневые атрибуты;
- служебные идентификаторы;
- неизвестные узлы исходного XML, которые требуется сохранить.

Полная и частичная синхронизация используют один преобразователь. Они отличаются только набором запрошенных XML-результатов. Запасного пути через старые операции нет.

## Внешние и вложенные файлы

Обработка внешних файлов включается в единый обход. Правило свойства создаёт задание чтения, записи или копирования тогда, когда это свойство посещается. После основного обхода отдельного перебора всех правил ради внешних файлов нет.

Вложенный объект, находящийся в отдельном YAML-файле, считается самостоятельным заданием и проходит один собственный обход. Вложенная коллекция внутри текущего YAML рекурсивно обрабатывается в рамках обхода текущего задания.

## Переименование и поиск ссылок

Снимок metadata-операции хранит разобранный YAML, координаты, правило и сведения о файле. Поле `model` удаляется.

Разрешение цели переименования идёт по декларациям `operationTarget`, YAML-ключам и правилам вложенных коллекций. Переименование изменяет непосредственно ключ записи или YAML-поле. Объект верхнего уровня, имя которого задаётся каталогом, переименовывается без искусственного добавления имени в YAML.

Структурные ссылки собираются во время общего YAML-обхода. Если зарегистрированному обработчику ссылки нужно типизированное значение, вызывается атомарное преобразование конкретного типа из YAML. После изменения значение возвращается в YAML атомарным преобразованием конкретного типа; общей property-level операции нет.

Поиск и изменение `ПутьКДанным` используют существующий YAML-ориентированный сбор фактов validation и общий индекс метаданных. Форма-модель для этого не создаётся.

Изменённые YAML-данные сериализуются напрямую. Сохраняются действующие режимы plan/apply, формирование миграций, проверка конфликтов имён и файловые перемещения.

## Удаление прежней оркестрации

После перевода всех потребителей удаляются:

- общие property-level операции `fromYAML` и `toXML`;
- metadataItem- и metadataCollection-обёртки над ними;
- отдельные оркестрационные пути форм, которые строят модель между YAML и XML;
- построение metadata-модели в снимке переименования и поиска ссылок;
- импорты, регистрации и проверки, существующие только для прежней общей оркестрации.

Атомарные обработчики конкретных типов `fromYAML`, `toXML` и необходимые атомарные `toYAML` сохраняются. Они вызываются только новой единой оркестрацией или точечной обработкой значения при YAML-операциях.

## Ошибки

Ошибка атомарного преобразования получает путь исходного файла, путь объекта, YAML-путь и путь правила. Сообщение должно указывать конкретное свойство, на котором остановилась операция.

Существующая семантика записи не меняется: worker пишут XML непосредственно в целевой каталог, а уже записанные результаты после последующей ошибки автоматически не удаляются. Файл индекса конфигурации обновляется только по действующим правилам завершения операции.

Отсутствие требуемого атомарного обработчика или нарушение договора правила считается явной ошибкой. Переход к удалённой модели не допускается.

## Проверка

Существующие XML-фикстуры остаются источником истины и не изменяются. Новый путь должен создавать тот же результат для прикладных объектов, конфигурации, форм, вложенных элементов и внешних файлов.

Добавляются проверки:

- один основной обход `rules.ts` на YAML-объект;
- правильная последовательность атомарных преобразований YAML → временное значение → XML;
- отсутствие накопления преобразованных соседних свойств;
- одновременное формирование всех XML-файлов формы;
- одинаковое поведение полной и частичной синхронизации;
- сохранение XML-порядка, альтернативных имён, служебных идентификаторов и неизвестных reference-узлов;
- обработка default/reference-значений и внешних файлов;
- переименование объектов и вложенных целей непосредственно в YAML;
- поиск и изменение структурных ссылок и `ПутьКДанным` без metadata-модели;
- точные координаты ошибок;
- отсутствие импортов и вызовов удалённой property-level оркестрации;
- отсутствие metadata-моделей и модельных переходников в sync и metadata-операциях.

Перед завершением реализации выполняется полный `pnpm test` из корня вортри.

## Критерии готовности

- Все виды синхронизации используют единый прямой путь YAML → XML.
- Каждый YAML-объект проходит один основной обход `rules.ts`.
- Полная, частичная и форменная синхронизация не создают metadata-модель.
- Переименование и поиск ссылок не создают metadata-модель.
- Общая property-level оркестрация `fromYAML` и `toXML` удалена.
- Сохранены только атомарные преобразования конкретных типов.
- Существующие XML-фикстуры проходят без изменения.
- Полный набор тестов проходит.

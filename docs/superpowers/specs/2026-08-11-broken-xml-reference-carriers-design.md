# Переносчики битых XML-ссылок

## Контекст

Последние 19 коммитов `/Users/nikita/git/round-trip-compact` сохраняют ссылки,
которые платформа оставила в XML в технической форме, но которые нельзя
преобразовать в смысловой адрес NKDK. Найдены три класса:

- `xr:DesignTimeRef` с парой UUID;
- `xr:MDObjectRef` с одиночным UUID;
- локальные ссылки управляемых форм с числовыми сегментами и UUID.

Сейчас отдельные пути ведут себя по-разному. Пара UUID уже проходит некоторые
преобразования как обычная строка, пустой `DesignTimeRef` имеет частную обработку
в `fillValue`, `DataPath` допускает непустой `!xml`, а остальные технические
формы могут быть отклонены преобразованием или semantic validation. Из-за этого
нет одного проверяемого договора: где `!xml` разрешён, как проверяется его
payload и какой XML должен быть восстановлен.

Допустимые места документируются в `.agents/xml-anomalies.md`. Реестр содержит
только наблюдавшиеся объекты и свойства; расширение списка требует отдельного
согласования разработчика.

## Цель

Добавить декларативный реестр переносчиков битых XML-ссылок. Каждый переносчик:

1. распознаёт только свой тип свойства и строгую техническую форму XML;
2. при XML → YAML автоматически сохраняет исходный текст локальным тегом
   `!xml`;
3. при YAML → XML проверяет payload и восстанавливает исходный XML без reference
   XML и снимка компонента;
4. исключает значение только из смысловой проверки существования ссылки;
5. оставляет синтаксическую, структурную и контекстную проверку включённой.

## Не входит в задачу

- Разрешение битых ссылок в существующие объекты или элементы формы.
- Использование `!xml` для обычных ссылок, которые можно восстановить по
  конфигурационному индексу.
- Отключение validation всего свойства, файла или проекта.
- Сохранение payload в `.nkdk`-снимке либо чтение reference XML при экспорте.
- Общие частные условия по `itemType`, именам XML-элементов или видам форм в
  `validation`, `project`, `projectState` и других нейтральных слоях.
- Новые поля в `BasePropertyRule`, `PropertyRule` и параметрах построителей
  rules.ts.
- Поддержка произвольного `!xml` у незарегистрированных свойств.

## Пользовательский договор

`!xml` применяется только к битой ссылке. Импорт формирует тег автоматически;
пользователь может перенести или отредактировать значение вручную, но payload
должен соответствовать грамматике зарегистрированного переносчика.

```yaml
ЗначениеЗаполнения: !xml 447e2bd8-fa43-442e-91db-b17634e036d9.c26f06ab-fb3e-46a7-a391-fdccd77b4231
Состав:
  - !xml ea868745-71fc-483c-aa6e-f242c06c673f
ИмяКоманды: !xml 1:8969c93a-23e5-4bef-941d-aaef315858d2
```

Строка хранится в разобранном YAML как `!xml <payload>`, а scalar-tag `xml`
остаётся отдельной пометкой для канонической сериализации. Кавычечная строка
`"!xml <payload>"` без локального YAML-тега не является транспортной ссылкой и
проходит обычные правила свойства.

## Поддержанные переносчики

### `DesignTimeRef UUID`

Переносчик применяется к свойству типа `MetadataValue`, только если XML имеет
`xsi:type="xr:DesignTimeRef"`, а текст совпадает с:

```text
UUID.UUID
```

Оба UUID записываются в канонической форме
`8-4-4-4-12`, регистр шестнадцатеричных цифр не меняется. YAML хранит только
исходную пару после `!xml`. Обратное преобразование создаёт тот же
`xr:DesignTimeRef` и тот же текст.

Пустой `xr:DesignTimeRef` остаётся существующим отдельным договором
`!xml DesignTimeRef` для `ЗначениеЗаполнения`; новый переносчик его не поглощает.

### `MDObjectRef UUID`

Переносчик применяется к элементам свойства типа `MetadataItemLinks`, только
если элемент XML имеет `xsi:type="xr:MDObjectRef"`, а текст является одним UUID
в канонической форме `8-4-4-4-12`.

Каждый элемент коллекции обрабатывается независимо. Именованные
`MDObjectRef`, например `Catalog.Товары`, остаются обычными ссылками. При
экспорте тегированный элемент восстанавливается как:

```xml
<xr:Item xsi:type="xr:MDObjectRef"><UUID></xr:Item>
```

В исследованной выборке этот случай найден в `Subsystem.Content`.

### Локальная ссылка формы

Переносчик применяется только к зарегистрированным свойствам формы и сохраняет
полный исходный текст XML. Для каждого XML-элемента задаётся отдельная
грамматика:

| XML-элемент | Payload после `!xml` |
|---|---|
| `Command` | целое число либо `<целое число>:<UUID>` |
| `CommandName` | `<целое число>:<UUID>` |
| `Field` | `<целое число>/<целое число>:<UUID>` с необязательными повторениями `/<целое число>:<UUID>` |
| `DataPath` | та же сегментная грамматика, что у `Field` |
| `xr:DataPath` | `<целое число>:<UUID>/<целое число>` |
| `CommandGroup` | один UUID |
| `GroupList` | `<целое число>:<UUID>` |
| `UserSettingsGroup` | `<целое число>:<UUID>` |

Числа не нормализуются, UUID и разделители сохраняются побайтно как текст.
Обычные смысловые значения (`Form.Command.Записать`, `Объект.Код`,
`FormNavigationPanelGoTo`) не совпадают с этими грамматиками и проходят
существующее преобразование.

## Архитектура

### Нейтральный реестр

В `@nkdk/runtime` появляется реестр `BrokenXMLReferenceCarrier`, собранный как
часть `MetadataRulesDefinition`. Общий слой знает только договор переносчика и
не содержит названий объектов или конкретных XML-форматов.

Регистрация имеет имя и `propertyType`, а обработчики получают `PropertyRule`,
исходное XML-значение, обычный результат XML → YAML либо разобранное YAML со
scalar-tag marks. Обработчик возвращает `undefined`, если значение ему не
принадлежит. Успешный результат содержит преобразованное значение и пути
scalar-узлов, которые нужно пометить `xml`. Коллекционный переносчик может
пометить отдельные индексы, не превращая всю коллекцию в транспортное значение.

В обратную сторону обработчик вызывается только для зарегистрированного типа и
фактически помеченного scalar. Он либо возвращает точное XML-значение, либо
диагностику строгой грамматики. Совпадение текста без scalar-тега не запускает
переносчик.

Реестр входит в `PropertyRuleRegistrySet` и доступен через уже существующий
`PropertyRuleExecution`. Составление выполняется в `metadata/composition`; новые
глобальные регистрации и скрытое изменяемое состояние не добавляются.

### XML → YAML

`ruleRuntime/property/fromXMLToYAML` сначала выполняет обычное преобразование
свойства. Затем реестр получает исходный XML и полученный YAML:

- `DesignTimeRef` заменяет пару UUID на строку `!xml <UUID>.<UUID>`;
- `MDObjectRef` заменяет только UUID-элементы массива;
- переносчики форм заменяют только значения строгого технического формата.

Пометки применяются к результирующему YAML до сбора validation-фактов и
сериализации. Обычное значение и вклад конфигурационного индекса не подменяются
для несовпавших данных.

### YAML → XML

`ruleRuntime/property/fromYAMLToXML` перед обычным `importFromYAML` спрашивает
реестр о помеченных значениях. Переносчик разбирает payload и возвращает точную
XML-форму. Для смешанной коллекции обычные элементы проходят стандартное
преобразование, а транспортные элементы материализуются переносчиком с
сохранением порядка.

Экспорт не использует reference XML и не генерирует новые UUID. Ошибка
грамматики привязывается к YAML-пути конкретного scalar и прекращает синхронизацию
так же, как другая ошибка преобразования YAML → XML.

### Validation

Внутренняя validation-схема добавляет только зарегистрированные варианты:

- строковый `pattern` для scalar-переносчика;
- объединение обычной item-схемы с `pattern` для элементов коллекции.

Схемы подсказок не показывают `!xml`. Semantic validation сверяется с тем же
реестром и не создаёт pending reference/DataPath check только для scalar с тегом
`xml`, подходящим зарегистрированному переносчику. Проверяются:

- допустимость `!xml` для данного типа свойства;
- точная грамматика payload;
- форма коллекции и остальные её элементы;
- все нессылочные правила владельца и файла.

Обычная битая ссылка без `!xml` продолжает выдавать существующую диагностику.
`!xml` с неверным payload отклоняется и не становится способом отключить
validation.

## Конкретные регистрации

Регистрации живут рядом с предметными преобразованиями:

- `commonObjects/metadataValue` — `DesignTimeRef UUID`;
- `commonObjects/metadataRef` — `MDObjectRef UUID` в `MetadataItemLinks`;
- `forms` — локальные ссылки формы, включая адаптеры составных значений
  `Command` и `CommandGroup`.

Границы объектов остаются в `.agents/xml-anomalies.md` и тестовых примерах.
Нейтральный реестр не проверяет `Catalog`, `Document`, `Subsystem` и другие
конкретные типы.

## Совместимость

Это канонизирующее изменение YAML: повторный XML-import добавит `!xml` к ранее
нетегированным техническим ссылкам. YAML с обычными именованными ссылками не
меняется.

Ранее сохранённая без тега пара UUID у `MetadataValue` перестаёт считаться
канонической. Для синхронизации её нужно получить повторным XML-import либо
явно записать с `!xml`. Автоматическая миграция существующего YAML не требуется.

## Проверки

1. Реестр отклоняет конфликтующие регистрации и не применяется к другому типу
   свойства.
2. `DesignTimeRef UUID` проходит XML → YAML → XML без reference XML, а пустой и
   именованный `DesignTimeRef` сохраняют прежнее поведение.
3. Смешанный `MetadataItemLinks` помечает только `MDObjectRef UUID`, сохраняет
   порядок и не затрагивает именованные ссылки.
4. Для каждого из восьми XML-элементов формы параметризованный тест принимает
   наблюдавшийся технический формат и отклоняет соседние неверные формы.
5. Интеграционный импорт формы автоматически записывает `!xml`, а последующий
   экспорт восстанавливает исходные XML-тексты.
6. Внутренняя JSON Schema принимает только зарегистрированные payload; схема
   подсказок не содержит `!xml`.
7. Semantic validation пропускает только помеченную битую ссылку, продолжает
   проверять обычную ссылку и отклоняет неверный payload.
8. Поиск ссылок и переименование не включают транспортные значения в граф
   ссылок.
9. Полный metadata round-trip сохраняет все добавленные тестовые XML-фрагменты.

После каждого законченного слоя выполняется
`pnpm duplicates -- --base origin/develop`. Перед завершением выполняются
`pnpm type-check`, `pnpm test`, `pnpm test:architecture:rules` и
`pnpm test:architecture`.

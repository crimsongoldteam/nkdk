# Подход: граф FalkorDB и Cypher в правилах метаданных

Дата: 2026-04-27
Тип: архитектурный обзор (направление развития), не имплементационная спецификация.

## Контекст

В `rules.ts` есть свойства, чьё поведение зависит не от самого объекта, а от других объектов конфигурации. Пример — `<Period>` и `<TopLevelParent>` у `Table` в форме: они появляются в XML только если `dataPath` указывает на FormAttribute с типом `DynamicList`. Сегодня эта проверка сделана отдельной функцией `isDynamicListAttribute`, которая читает данные из контекста экспорта.

Таких случаев в системе много: проверки `dataPath`, валидация ссылочных полей в прикладных объектах (Owner, Type, MainTable и так далее), кросс-объектные правила сериализации, ограничения на допустимые значения полей. Хочется единый механизм, а не россыпь локальных функций.

Решение, к которому пришли: использовать **граф связей метаданных в FalkorDB** как основу для таких запросов и писать в `rules.ts` запросы на **Cypher**.

## Принципы

1. **Источник правды — YAML-файлы на диске.** Их редактируют пользователи, кладут в git, читают сторонние инструменты. Граф и XML — производные.

2. **Граф в FalkorDB — производный указатель над YAML.** Используется только для запросов: кросс-объектных правил сериализации, валидации ссылок, ограничений на значения полей, навигации в IDE, автодополнения. Без графа базовая цепочка работы (конвертация форматов) продолжает действовать.

3. **XML — только внешний формат обмена с 1С.** Внутри системы XML не хранится. Читается один раз при импорте, генерируется при экспорте.

4. **Парсеры пишут в граф; сериализаторы читают из графа.** Кросс-объектные запросы в правилах живут только в одном направлении — `toXML`.

5. **graphology уходит.** Граф полностью переезжает в FalkorDB; пакет `@nakidka/graph` становится единственным способом работы с ним.

## Жизненный цикл данных

```
   Первоначальный импорт (один раз):
   XML-файлы → парсер XML → YAML-файлы на диск
                                    │
                                    │  fromYAML или отдельная команда
                                    ▼
                          Граф в FalkorDB
                                    │
                                    │
   Каноничное состояние:  YAML на диске + Граф (синхронны)
                                    │
                  ┌─────────────────┼─────────────────┐
                  │                                    │
            Правка YAML                          Экспорт XML
            (пользователь сохраняет           (toXML читает граф +
             файл → fromYAML →                 Cypher для кросс-объектных
             обновление графа)                  правил → XML файлы)
```

В этой схеме **граф не используется при первоначальном импорте XML → YAML**. Конвертация — пара `fromXML` + `toYAML` без участия графа. Граф появляется только тогда, когда YAML уже есть на диске и его кто-то загружает (`fromYAML` или отдельная команда сборки).

## Парность направлений и роль графа

Четыре направления сериализации работают парами:

| Сценарий | Пара | Граф |
|---|---|---|
| Конвертация XML в YAML | `fromXML` + `toYAML` | Не нужен |
| Загрузка YAML в граф | `fromYAML` | Запись в граф |
| Экспорт XML из графа | `toXML` | Чтение из графа + Cypher |

Подробнее:

- **`fromXML`** — разбирает XML, передаёт результат в `toYAML`. С графом не взаимодействует. Запросов на Cypher не делает.
- **`toYAML`** — получает данные от `fromXML` и пишет YAML-файл. С графом не взаимодействует. Кросс-объектных правил в YAML-сериализации нет (ссылки выводятся как строки).
- **`fromYAML`** — разбирает YAML и **пишет узлы и рёбра в FalkorDB**, попутно сохраняет на узлах координаты YAML. Запросов во время разбора не делает: только запись.
- **`toXML`** — **читает** данные из графа (одним пакетным запросом на объект метаданных), затем рендерит XML по правилам. Здесь же выполняются Cypher-запросы для кросс-объектных правил. Дополнительно перед экспортом загружается **референсный XML-файл** (если он есть рядом) — чтобы сохранить UUID объектов и порядок полей при обратной записи. Это нужно для байт-точного round-trip и не зависит от графа.

## Две роли Cypher в правилах

Cypher в `rules.ts` решает две разные задачи. Их объединяет общий механизм, но семантика разная.

### Роль 1 — условия экспорта в XML

Запрос определяет, эмитировать ли свойство в XML и/или какое значение по умолчанию подставлять. Срабатывает в `toXML`, влияет только на сериализацию.

Пример — `<Period>` у `Table`: эмитировать только если `dataPath` указывает на FormAttribute с типом `DynamicList`. Это и есть наш изначальный случай с `isDynamicListAttribute`.

### Роль 2 — ограничения на допустимые значения поля

Запрос описывает множество значений, допустимых для свойства. Используется для:
- валидации при сохранении YAML (выдать ошибку, если значение не из множества);
- автодополнения в IDE (предложить только допустимые варианты);
- проверки конфигурации в CLI до экспорта.

Не влияет на сериализацию `toXML`. Напротив, при экспорте такие правила обычно не запускаются — данные уже валидированы при сохранении YAML или при сборке.

Пример — поле `binaryDataStorageLocationUseField` у `metadataAttribute` (в YAML — `ПолеИспользованияХраненияВХранилищеДвоичныхДанных`). Допустимое значение — имя реквизита того же объекта-владельца, у которого тип `boolean`. Cypher идёт от объекта-владельца, ищет среди его реквизитов те, у которых тип `boolean`, возвращает их имена.

```ts
binaryDataStorageLocationUseField: {
  yaml: "ПолеИспользованияХраненияВХранилищеДвоичныхДанных",
  xml: "BinaryDataStorageLocationUseField",
  type: "string",
  allowedValues: cypherSet({
    query: `
      MATCH (scope)-[:ATTRIBUTE]->(a:Attribute)-[:VALUE_TYPE]->(:Type {name: "Boolean"})
      RETURN a.name AS name
    `,
  }),
}
```

## Что меняется в rules.ts

В долгосрочном виде `rules.ts` содержит запросы на Cypher там, где требуется кросс-объектная логика, — для условий экспорта или для ограничений на значения. Для большинства свойств правила остаются обычными — Cypher там не нужен.

Минимальный пример оформления для условия экспорта (форма обсуждалась, но не финализирована):

```ts
period: {
  type: "boolean",
  toXML: cypherPredicate({
    query: `
      MATCH (scope:Form {id: $scope})-[:ATTRIBUTE]->(a:FormAttribute)
            -[:VALUE_TYPE]->(:Type {name: "DynamicList"})
      RETURN a.name AS name
    `,
    test: (el, rows) => rows.some(r => r.name === el.dataPath?.split(".")[0]),
  }),
  defaultValueXMLRaw: { ... },
}
```

Принципы запроса:

- **Параметр `$scope`** — идентификатор текущего объекта метаданных, его автоматически подставляет обработчик правил. Запросы без `$scope` — глобальные по всему графу.
- **Запрос всегда стартует от ближайшего объекта метаданных** или от корня графа. Сам элемент-носитель (`Table`) внутри Cypher не упоминается — за себя элемент отвечает локально через функцию `test`.
- Один запрос отдаёт **факты о текущей области** (например, «какие FormAttribute этой формы — DynamicList»), а не сразу boolean-ответ для одного элемента. Финальное решение по конкретному элементу — функция `test`.

Это позволяет сохранить синхронную цепочку `toXML`: запрос выполняется один раз на форму до начала обхода свойств, дальше элементы синхронно проверяют принадлежность.

## Где живёт кеширование запросов

Кеширование — отдельный слой между `rules.ts` и пакетом `@nakidka/graph`. Назовём его обработчиком правил. Не в графовом пакете (он остаётся обёрткой без состояния над FalkorDB) и не в самих правилах (у них нет общей видимости).

- Кеш — `Map<ключ, Promise<строки>>`. Хранит обещание (Promise), а не сам результат — это позволяет схлопнуть параллельные одинаковые вызовы в один.
- Время жизни кеша — один цикл экспорта или валидации. Создаётся свежим в начале, выкидывается в конце.
- Ключ — хеш текста запроса плюс параметры (включая `$scope`).

## Долгосрочное направление: граф как единственный носитель данных при экспорте

В долгосрочной форме `toXML` работает целиком на графе. Объектов модели в виде классов JavaScript (`Catalog`, `Form`, `Document`) в этой цепочке нет. Вместо них для каждого вида объекта метаданных есть **функция-загрузчик**, которая:

1. Делает один пакетный запрос на Cypher для объекта.
2. Раскладывает результат в типизированную структуру нужной формы.
3. Передаёт её сериализатору вместе с референсным XML, если он есть.

Загрузчики не пишутся руками. Их **создаёт генератор кода** на основе `rules.ts`: он знает, какие у объекта свойства, какие вложенные коллекции, какие ссылки, и сам пишет `loadCatalog`, `loadDocument`, `loadForm` и так далее. Когда `rules.ts` меняется, генератор перезапускается, загрузчики обновляются.

Зачем такая сложность: видов объектов метаданных в системе десятки, у каждого десятки полей и вложенных коллекций. Писать загрузчики руками — сотни функций, расхождения с `rules.ts` по мере правок, ручная поддержка. Генератор кода это всё снимает.

Что вне этой долгосрочной формы остаётся прежним:
- Парсеры XML и YAML — пишут в граф напрямую (для `fromYAML`) или передают данные `toYAML` без участия графа (для `fromXML`).
- `toYAML` — обходится простым чтением узлов; для него генератор кода тоже может пригодиться, но запросы на Cypher не нужны.
- Загрузка референсного XML при экспорте — отдельный шаг, не относящийся к графу. Нужен для сохранения UUID и порядка полей.

## Поэтапный переход

Переход к долгосрочной форме — постепенный. Пять этапов, каждый самостоятелен и не ломает предыдущее.

1. **Cypher-запросы в `rules.ts` для условий экспорта.** Появляется обработчик правил, оформление `cypherPredicate`, предварительный проход с пакетным выполнением запросов, кеширование. Заменяется `isDynamicListAttribute`. JS-модель и остальная цепочка не меняются.
2. **Cypher-запросы для ограничений на значения полей.** Появляется оформление `cypherSet` (или похожее), которое описывает множество допустимых значений. Подключается к валидации YAML и автодополнению в IDE.
3. **Расширение применения Cypher на остальные кросс-объектные случаи.** Тот же механизм применяется ко всем проверкам `dataPath` и ссылочным полям. Граф дополняется недостающими узлами и рёбрами.
4. **Загрузчики данных.** Появляется генератор кода, для каждого объекта метаданных появляется функция-загрузчик. Сериализатор `toXML` начинает принимать структуру данных вместо JS-объекта; работает рядом с JS-моделью под флагом включения, до подтверждения корректности.
5. **`fromYAML` пишет напрямую в граф, JS-модель уходит из роли канона при экспорте.** `toXML` целиком работает через загрузчики. Удаление JS-модели как канона; параллельная работа и сохранение состояния для случая многих процессов.

После каждого этапа система остаётся рабочей. Можно остановиться и не идти дальше, если приоритеты сменились.

## Открытые вопросы (для следующих документов)

Эти решения отложены, потому что зависят от того, какой этап мы возьмём первым:

- **Синхронность и асинхронность цепочки `toXML`.** На этапе 1 — синхронная цепочка через предварительный проход. После этапа 4 (загрузчики) — асинхронная по факту, поскольку пакетное чтение из FalkorDB асинхронное. Где проходит граница и как её перейти аккуратно — отдельная тема.
- **Тестовая инфраструктура для FalkorDB.** Как тесты получают граф: реальный Redis в CI, имитация в памяти, или наполнение через CLI на YAML-фикстуре. Каждый вариант со своими компромиссами.
- **Итоговая форма `cypherPredicate` и `cypherSet`.** `test` (гибкая функция) против `elementKey` (декларативная проверка принадлежности множеству). Возможен компромисс — поддерживать оба.
- **Обработка вложенных областей.** Когда контекст глубже одного уровня (Form → Table → InputField). Что обработчик правил подставляет как `$scope` — ближайший объект метаданных, или нужны именованные точки (`$scope.form`, `$scope.parent`).
- **Где работает генератор загрузчиков — во время сборки или во время работы.** Скрипт, создающий `.ts`-файлы перед компиляцией, или динамический обход `rules.ts` в момент первого обращения.
- **Параллельная работа и блокировки.** Когда CLI и расширение для VSCode делят один FalkorDB. До этапа 5 не критично.
- **Куда подключаются ограничения на значения полей.** На этапе 2 — это валидация YAML и автодополнение в IDE. Запускать ли проверки при сохранении файла, при сборке, или и там, и там — отдельный вопрос.

## Что не входит в этот подход

- Граф не становится «всем» — YAML остаётся каноном, в графе нет данных, которых не было бы в YAML.
- Парсеры XML и YAML не разделяют общую структуру — они остаются раздельными по форматам, объединяет их только то, что результат складывается в граф.
- XML внутри системы не хранится. Полный цикл XML → ... → XML выполняется через YAML и граф.
- Этот подход не решает задачу одновременной работы нескольких процессов с одним FalkorDB — это отдельная задача (этап 5).

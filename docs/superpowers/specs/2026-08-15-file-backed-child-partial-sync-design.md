# Частичная синхронизация файловых подчинённых объектов

## Контекст

Частичный e2e создаёт текстовый макет отчёта двумя файлами проекта:
`Свойства.yaml` описывает подчинённый metadata-объект, а `Макет.txt` содержит
его данные. Топология классифицирует оба пути как ресурсы одного
`fileBackedTarget`.

Текущий планировщик структурно обрабатывает добавление и удаление только тогда,
когда изменённый путь классифицирован как `content`. Для `externalFile` он
включает в ZIP только сам файл. В результате ZIP нового макета не содержит XML
владельца, а платформа отклоняет пакет: подчинённый metadata-объект нельзя
добавить без загрузки родительского объекта.

Проблема относится к общему договору файловых подчинённых объектов, а не к
конкретному типу `Template` или каталогу `Шаблоны`.

## Цель

При частичной синхронизации корректно создавать и удалять любой подчинённый
объект, ресурсы которого объявлены через `fileBackedTarget`. Частичный ZIP
должен содержать согласованное текущее представление коллекции и загружать её
владельца.

## Границы

В изменение входят:

- обработка добавленных `externalFile` с `fileBackedTarget`;
- обработка удалённых `externalFile` с `fileBackedTarget`;
- включение XML владельца в payload и `load.lst` при структурном изменении;
- включение текущих ресурсов той же коллекции в payload;
- модульные тесты планировщика для создания и удаления;
- повторный запуск блока создания текстового макета в частичном e2e.

Не входят:

- специальные условия по metadata-типу, имени XML-корня или каталогу;
- изменение формата топологии и общих типов правил;
- загрузка владельца при обычном изменении содержимого существующего файла;
- новые частичные политики для каждого типа владельца;
- расширение матрицы e2e новыми операциями.

## Договор планирования

### Структурное изменение

Добавление или удаление ресурса, объявленного как `fileBackedTarget`, считается
структурным изменением коллекции независимо от того, классифицирован путь как
`content` или `externalFile`.

Планировщик:

1. определяет владельца через `ownerProjectPattern` объявления
   `fileBackedTarget`;
2. включает текущее XML-задание владельца в payload;
3. добавляет XML владельца в список загрузки;
4. включает в payload все существующие ресурсы той же коллекции у этого
   владельца без самостоятельной загрузки каждого ресурса;
5. устраняет повторы обычными множествами планировщика, если одно структурное
   изменение представлено несколькими добавленными или удалёнными путями.

XML владельца является единственной точкой загрузки коллекции. Все текущие
файлы коллекции нужны в ZIP как данные, на которые ссылается структура
владельца.

Для удаления удалённый файл отсутствует среди текущих ресурсов. Планировщик
включает владельца и оставшиеся текущие ресурсы коллекции; отсутствие элемента
в XML владельца сообщает платформе об удалении. Удалённый путь считается
обработанным и не попадает в общую ошибку «удалённый внешний файл нельзя
включить в XML-пакет».

### Обычное изменение содержимого

Изменение существующего `externalFile` не является структурным. Планировщик
включает и загружает только изменённый внешний файл по действующему прямому
правилу. XML владельца и остальные элементы коллекции не добавляются.

Так сохраняется минимальность частичного ZIP для частого случая изменения
текста макета, модуля или другого файлового содержимого.

## Изменения в коде

Основное изменение выполняется в
`packages/rules/metadata/partialSyncToXml/impactPlanner.ts`.

Структурная ветка должна принимать оба вида ресурсов — `content` и
`externalFile`. Для `content` объявление берётся из
`assignment.fileBackedTarget`, для `externalFile` — из
`externalFile.fileBackedTarget`. Общую операцию включения коллекции следует
отделить от assignment-политики: сам договор уже полностью выражен топологией
через `fileBackedTarget`.

Операция структурного включения получает классифицированный ресурс и:

- находит текущего владельца;
- вызывает включение владельца с запросом загрузки;
- выбирает из `currentResources` только ресурсы с тем же видом коллекции и тем
  же путём владельца;
- включает XML-ресурсы коллекции как assignment без загрузки, а внешние файлы
  — как external без загрузки.

Внешний файл может входить в файловый подкаталог `content` assignment, не имея
собственного объявления `fileBackedTarget`, как модуль формы. Такой файл
определяется как участник коллекции через `assignment.fileBackedTarget` и
включается вместе с ней, но его самостоятельное добавление или удаление не
запускает структурную операцию. Для запуска операции у `externalFile` требуется
собственное `externalFile.fileBackedTarget`, как у файлов макета.

Существующие структурные политики остаются для тех связей, где они задают
дополнительное поведение. Для самого `fileBackedTarget` наличие отдельной
политики не требуется.

## Ошибки

Планировщик завершает работу понятной ошибкой, если при структурном изменении:

- объявление `fileBackedTarget` неполно;
- по `ownerProjectPattern` не найден текущий XML-владелец;
- найденный владелец не является `content` assignment.

Ошибки не должны молча превращать структурную операцию в прямую отправку одного
файла: такой ZIP заведомо не применим платформой.

## Проверка

Модульные тесты `impactPlanner.test.ts` используют нейтральную синтетическую
топологию и проверяют два сценария.

При создании файлового подчинённого объекта:

- в selection присутствуют владелец, XML элемента и его внешний файл;
- `assignmentDocumentIds` содержит документы владельца и элемента;
- `externalProjectPaths` содержит внешний файл;
- `loadTargets` содержит владельца, но не отдельные файлы элемента.

При удалении файлового подчинённого объекта:

- в selection присутствует текущий владелец и оставшиеся ресурсы коллекции;
- удалённый путь не вызывает общую ошибку внешнего файла;
- `loadTargets` содержит владельца;
- удалённый внешний файл отсутствует в payload.

Дополнительно существующий тест изменения внешнего файла должен подтверждать,
что владелец не добавляется. После модульных проверок частичный e2e продолжается
с контрольной копии перед слоем макетов и должен успешно пройти создание
текстового макета. Полный массив e2e повторно не запускается.

## Критерии готовности

- планировщик одинаково распознаёт структурное добавление и удаление для
  `content` и `externalFile` ресурсов `fileBackedTarget`;
- ZIP создания макета содержит XML владельца и все файлы создаваемого элемента;
- `load.lst` загружает владельца коллекции;
- изменение содержимого существующего файла сохраняет минимальный пакет;
- модульные тесты, проверки слоя и блок создания макета в частичном e2e проходят;
- реализация не содержит условий по конкретным metadata-типам и каталогам.

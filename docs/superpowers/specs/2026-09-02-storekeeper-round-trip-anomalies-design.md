# Исправление round-trip Storekeeper

## Контекст

Round-trip конфигурации
`cf/StorekeeperDevelopers_2_0_108_1_setup1c` показывает четыре независимые
группы расхождений:

1. Проверка проекта считает лишними 24 тега `!xml/invalid` у английских
   переводов во вложенных формах четырёх общих форм. В конфигурации
   зарегистрирован только язык `ru`, а исходные `Ext/Form.xml` действительно
   содержат `v8:lang` со значением `en`.
2. Экспорт добавляет отсутствующий в исходном XML стандартный реквизит
   `ExchangeDate` плана обмена и вкладывает служебный `_name` внутрь семи
   существующих стандартных реквизитов.
3. Восемь неразрешённых UUID в составе подсистем корректно импортируются как
   `!xml/invalid`, но обычный YAML → XML повторно требует разрешить их как
   смысловые ссылки и завершает задания ошибкой «Неизвестный корень».
4. Точечный raw отсутствующего `ExchangeDate` становится границей целого item,
   но не получает указатель основного XML-документа. У плана обмена несколько
   потенциальных XML-выходов, поэтому full sync считает границу неоднозначной.

Первая группа является ошибкой обхода вложенного YAML при validation. Вторая —
ошибкой планирования минимальных XML-границ: `completeItemNames` дополняет
канонический состав коллекции, но proof не создаёт границу отсутствующего
канонического item внутри уже существующего XML-контейнера.
Третья группа является ошибкой общего переноса принятой XML-аннотации до
resolver при YAML → XML. Четвёртая — неполной привязкой raw item к документу,
хотя обычная raw-граница без `filePath` и `tag` уже считается относящейся к
основному документу.

Историческая спецификация
`docs/superpowers/specs/2026-08-14-standard-attribute-item-absence-design.md`
решала второй случай частным тегом `!xml/absent`. После унификации XML-аномалий
этот тег намеренно удалён. Настоящая спецификация сохраняет общий договор
`!xml/raw` и не возвращает частный тег.

## Цели

- Сохранить отсутствующий `ExchangeDate` точечным `!xml/raw` с `$xml: null`.
- Не поднимать raw до всей коллекции стандартных реквизитов.
- Не создавать ложные raw у скрытого свойства `_name` существующих элементов.
- Проверять локализованные значения во всех поддержанных видах вложенных
  `yamlToXMLNestedRule`, включая `ClientApplicationForm` общей формы: её XML
  является внешним файлом, но YAML вложен в `Свойства.yaml`.
- После импорта считать корректными принятые `!xml/invalid en`, но продолжать
  отклонять незарегистрированный язык без тега.
- При YAML → XML сохранять неразрешённый UUID metadata-ссылки только в том
  конкретном вхождении, которое помечено `!xml/invalid`; UUID без тега
  продолжать отклонять.
- Привязывать raw целого item без внешнего пути и XML-тега к основному
  XML-документу так же, как обычную raw-границу свойства.
- Получить чистый round-trip исследуемой конфигурации без изменения исходных
  XML-фикстур.

## Не входит в задачу

- Возврат `!xml/absent` или других удалённых частных тегов.
- Специальная проверка по имени `ExchangeDate`, виду `ExchangePlan` или каталогу
  `CommonForms` в нейтральных слоях.
- Изменение состава стандартных реквизитов, DataPath или configuration index.
- Изменение правил регистрации языков.
- Переработка всех существующих обходов metadata YAML в один общий модуль.
- Исправления из ещё не влитой ветки `codex/tester-round-trip-fixes`.

## Договор отсутствующего элемента именованной коллекции

### Публичный YAML

Исходный XML содержит контейнер `StandardAttributes`, но не содержит
канонический item `ExchangeDate`. Импорт сохраняет это состояние на устойчивом
YAML-ключе отсутствующего item:

```yaml
СтандартныеРеквизиты:
  ДатаОбмена: !xml/raw
    $xml: null
  Наименование:
    ПроверкаЗаполнения: ВыдаватьОшибку
  Код:
    ПроверкаЗаполнения: ВыдаватьОшибку
```

`$значение` отсутствует: у маркера нет отдельного смыслового payload. Известный
стандартный реквизит остаётся частью правил и индексов, а raw управляет только
присутствием соответствующего `xr:StandardAttribute` в XML.

### Планирование proof-границы

При обходе свойства-коллекции с `completeItemNames` proof выполняет следующие
действия:

1. Получает канонические внутренние имена тем же `completeItemNames`, которое
   использует обычный YAML → XML.
2. Получает внутренние имена фактически присутствующих item из audit-якорей
   коллекции.
3. Для каждого отсутствующего канонического имени вычисляет публичный YAML-ключ
   через уже зарегистрированное правило `recordYamlKeyFromYAML`. Его параметры
   дополняются текущим `propertyRule`, чтобы стандартная коллекция могла взять
   точное имя из `standartAttributeNames`, включая отсутствующий в общей
   таблице `ExchangeDate → ДатаОбмена`. Фабрика коллекции передаёт эту
   существующую функцию в исполнительный descriptor; новый параметр rules.ts
   не вводится.
4. Добавляет границу с `presentInSource: false`, точным XML-путём будущего
   `xr:StandardAttribute` и YAML-путём вида
   `СтандартныеРеквизиты/ДатаОбмена`.
5. Обычное доказательство сравнивает эту границу с контрольным экспортом. Если
   экспорт действительно создаёт item, существующий общий механизм записывает
   raw с `$xml: null`.

Граница создаётся только когда одновременно выполнены условия:

- XML-контейнер коллекции присутствует;
- `completeItemNames` зарегистрирован;
- коллекция имеет именованную YAML-форму `record`;
- зарегистрировано однозначное преобразование внутреннего имени в YAML-ключ;
- такого физического item нет в исходном XML.

Массивы, динамические item, неизвестные имена и полностью отсутствующий
контейнер сохраняют нынешнее поведение. Proof не угадывает YAML-ключ и не
добавляет частных условий для стандартных реквизитов.

### Экспорт

Обычный экспорт по-прежнему формирует полный канонический набор через
`completeItemNames`. После него общий применитель raw удаляет только
`xr:StandardAttribute` для `ДатаОбмена`. Семь исходных item не сдвигаются при
сопоставлении proof-границ, поэтому для их скрытого `_name` не возникают
ложные raw и вложенные `<_name>`.

Если в пользовательском YAML удалить точечный raw, следующий экспорт вправе
создать `ExchangeDate` согласно Rules. Если пользователь добавит смысловые
поля внутрь `ДатаОбмена`, это уже обычный элемент коллекции, а не отсутствие;
правила raw не должны молча отбрасывать эти данные.

## Договор обхода вложенной формы при validation

### Причина

`Свойства.yaml` общей формы проверяется корневым правилом
`MetadataCommonForm`. Поле `Форма` имеет тип `ClientApplicationForm`: descriptor
помечен как `externalFile`, потому что XML хранится в `Ext/Form.xml`, однако
YAML формы вложен непосредственно в `Свойства.yaml`. Текущий рекурсивный
валидатор разрешает только `collectionItemRule`, поэтому до содержимого
`Форма` не доходит. В результате
ошибка «незарегистрированный язык en» не создаётся, а последующая проверка
справедливо считает `!xml/invalid` необоснованным.

### Новый обход

Проверка файла свойств использует существующий
`traverseMetadataRuleYaml` и на каждом посещённом объекте вызывает
`validateRuleYAMLObjectProperties` без внутренней рекурсии. Обход уже различает:

- фиксированный вложенный `item`;
- `collection` в форме массива и именованной записи;
- `polymorphicRecord`;
- динамический `resolveItemRule` коллекции;
- `externalFile` с зарегистрированным `nestedItemRule`, когда его значение
  действительно является вложенным YAML-объектом.

Имя корневого объекта передаётся вложенному item без изменения.
Для элемента именованной коллекции именем становится его YAML-ключ после
действующего преобразования ключа, для массива используется имя из самого
item. Это сохраняет поведение `excludeIfEqualNameYAML`.

Для `!xml/invalid en` последовательность остаётся общей:

1. Обход находит английское значение внутри `Форма` и создаёт адресную ошибку
   незарегистрированного языка.
2. Проверка XML-аннотаций сопоставляет ошибку с `!xml/invalid` на том же ключе.
3. Принятая ошибка не выводится пользователю, а тег не считается лишним.

То же значение `en` без `!xml/invalid` остаётся ошибкой проекта. Допустимый
`ru` не создаёт диагностику. Счётчик локализованных свойств должен учитывать
вложенную форму так же, как самостоятельную форму.

Специализированная проверка самостоятельного файла `Форма.yaml` в этой задаче
не переписывается. Регрессионная проверка подтверждает, что её результат не
изменился.

## Договор принятого неразрешённого UUID

`!xml/invalid` относится к точному YAML-вхождению, а не ко всему свойству и не
ко всему режиму операции. При обходе metadata-ссылок YAML → XML исполнитель:

1. Находит исходное вхождение по `MetadataTargetOccurrence.location`.
2. Читает его value- или key-аннотацию из общей таблицы XML-аннотаций.
3. Для аннотированного YAML-ключа использует `logicalKey`, а не технический
   runtime-ключ парсера.
4. Если значение является UUID и точная аннотация имеет вид `invalid`, оставляет
   UUID без смыслового разрешения и передаёт его обычному XML-преобразователю.
5. В остальных случаях выполняет действующий resolver без послаблений.

В обычном полном sync договор зависит только от точной аннотации и действует
для metadata-ссылок как в значениях, так и в YAML-ключах (`UserVisible`).
Внутренний контрольный экспорт импорта выполняется раньше окончательной
проверки, когда `!xml/invalid` ещё не назначен. В нём сохраняется отдельное
узкое разрешение для UUID, уже прочитанного из исходного XML; после
контрольного экспорта обычная проверка обязана либо разрешить ссылку, либо
назначить ей точный `!xml/invalid`. Это разрешение недоступно пользовательскому
YAML → XML и не ослабляет обычный sync.
Неразрешённая строка не-UUID даже под `!xml/invalid` не получает автоматического
обхода resolver: эта задача сохраняет только уже исследованный обратимый UUID.

## Договор документа для raw целого item

Raw целого элемента коллекции использует export claim и до разрешения claim
имеет служебный путь `$item`. Привязка документа определяется тем же порядком,
что и для raw свойства:

- `filePath` даёт точный `documentPath`;
- XML `tag` даёт `tag` документа;
- если нет ни `filePath`, ни `tag`, ставится `documentSelector: ""`, то есть
  основной XML-документ assignment.

Это не расширяет raw и не выбирает документ по числу сформированных выходов.
Для `ДатаОбмена` граница остаётся одним отсутствующим
`xr:StandardAttribute`, но full sync однозначно применяет её к
`ExchangePlans/ОбменСМобильнымиПриложениями.xml`, а не к внешнему файлу состава
плана обмена.

## Размещение изменений

Предполагаемые границы модулей:

- `packages/runtime/metadata/ruleRuntime/property/fromYAMLToXMLTypes.ts` —
  исполнительный descriptor получает существующее преобразование внутреннего
  имени item в YAML-ключ.
- `packages/runtime/metadata/ruleRuntime/metadataCollection/fromXMLToYAML.ts` —
  передаёт `propertyRule` существующему `recordYamlKeyFromYAML`.
- `packages/runtime/metadata/ruleRuntime/metadataCollection/ruleFactory.ts` —
  передаёт `recordYamlKeyFromYAML` в descriptor без нового параметра фабрики.
- `packages/rules/metadata/commonObjects/standardAttributeDescription/registerCollectionRule.ts`
  — вычисляет YAML-ключ по `standartAttributeNames` текущего свойства.
- `packages/rules/metadata/importFromXml/anomalyProof.ts` — планирует
  отсутствующие канонические item существующей именованной коллекции.
- новый
  `packages/rules/metadata/validation/metadataRuleYamlProperties.ts` выполняет
  общий обход вложенного YAML и вызывает объектную проверку без рекурсии;
  `metadataRuleYamlTraversal.ts` входит во внешний XML-descriptor, если у него
  есть вложенное item-правило, а `projectValidationPasses.ts` использует helper
  для файлов свойств.
- `packages/runtime/metadata/ruleRuntime/property/metadataTargetOccurrences.ts`
  связывает точное вхождение metadata-ссылки с `!xml/invalid`; общий
  `fromYAMLToXML.ts` и `UserVisible/fromYAML.ts` передают исходное YAML-дерево,
  таблицу аннотаций и существующий узкий признак контрольного экспорта.
- `packages/rules/metadata/fullSyncToXml/xmlAnomalyAssignment.ts` назначает
  основному документу пустой selector для raw целого item без внешней
  документной привязки.

Нейтральные runtime-слои не получают проверок по `itemType`, XML-корню или
имени стандартного реквизита. Направление зависимостей из
`.agents/architecture.md` не меняется, поэтому обновление архитектурного файла
не требуется. Реестр `.agents/xml-anomalies.md` уже определяет `$xml: null` для
отсутствующего узла; при реализации достаточно добавить точный пример
именованного канонического item, не меняя общий договор.

## Ошибки и защитные условия

- Если для канонического имени нельзя получить непустой YAML-ключ, proof не
  создаёт выдуманный путь. Для текущего единственного
  `completeItemNames`-типа это является ошибкой декларации и должно быть
  защищено тестом фабрики.
- Повторный YAML-ключ для двух канонических имён запрещён тестом descriptor:
  иначе минимальную границу нельзя адресовать однозначно.
- Уже существующий физический item никогда не получает границу отсутствия.
- Точечный raw не должен скрывать диагностику или смысловые данные соседних
  стандартных реквизитов.
- Общий validation-обход не должен выдавать одну диагностику дважды.
- Обычный неразрешённый UUID без `!xml/invalid` должен по-прежнему завершать
  YAML → XML ошибкой resolver.
- `!xml/invalid` на одном UUID не должен разрешать соседние неаннотированные
  значения.
- Raw item внешнего файла или tagged-документа не должен быть ошибочно
  перенаправлен в основной документ.

## Проверки

### Отсутствующий стандартный реквизит

1. Unit-тест proof: существующая именованная коллекция с
   `completeItemNames = [Code, Description, ExchangeDate]` и физическими
   `Code`, `Description` получает одну границу
   `ДатаОбмена`, `presentInSource: false`.
2. Unit-тест proof: присутствующий `ExchangeDate` не получает такую границу.
3. Unit-тест descriptor: существующий `recordYamlKeyFromYAML` доступен proof и
   даёт устойчивый ключ без добавления параметра rules.ts.
4. Интеграционный тест control export: импорт создаёт точный
   `ДатаОбмена: !xml/raw` с `$xml: null`, а обратный XML совпадает с исходным и
   не содержит вложенных `<_name>`.
5. Существующие проверки полностью отсутствующего контейнера и полной
   стандартной коллекции остаются зелёными.

### Вложенная локализация

1. Unit-тест общего обхода: вложенная форма с внешним XML действительно
   посещается один раз.
2. Интеграционный тест project validation для `MetadataCommonForm`: `en` без
   тега даёт ошибку по точному пути внутри `Форма`.
3. Тот же YAML с `!xml/invalid en` не даёт ошибки и не сообщает о лишнем теге.
4. Допустимый `ru` остаётся без ошибок.
5. Существующая проверка самостоятельной формы с незарегистрированным языком
   остаётся зелёной.

### UUID и документная привязка raw

1. Интеграционный тест подсистемы: `!xml/invalid <uuid>` в `Состав` возвращает
   тот же UUID в `xr:Item`, а такой же UUID без тега остаётся ошибкой.
2. Unit-тест `UserVisible`: неразрешённый UUID на YAML-ключе сохраняется только
   с `!xml/invalid`, включая восстановление `logicalKey`.
3. Интеграционный тест raw named-collection item: граница `$item` без
   `filePath` и `tag` получает `documentSelector: ""`.
4. Реальный full sync плана обмена с несколькими выходами больше не сообщает о
   неоднозначной raw-границе.

## Критерии готовности

- В YAML отсутствующий `ExchangeDate` представлен только точечным
  `ДатаОбмена: !xml/raw` с `$xml: null`.
- XML после YAML → XML побайтно или структурно совпадает с исходным, включая
  отсутствие `ExchangeDate` и вложенных `_name`.
- Все 24 английских значения общей формы сохраняют обоснованный
  `!xml/invalid`; проект не сообщает о лишних тегах.
- Восемь UUID состава подсистем сохраняются в XML только благодаря точечным
  `!xml/invalid`; те же UUID без тега по-прежнему отклоняются.
- Raw `ДатаОбмена` однозначно связан с основным XML-документом плана обмена и
  не расширяется до всего item или assignment.
- Незарегистрированный язык без тега по-прежнему является ошибкой.
- Нет частных условий по Storekeeper, общей форме или стандартному реквизиту в
  нейтральных слоях.
- Не добавлены новые поля в `BasePropertyRule`, `PropertyRule` и параметры
  построителей rules.ts; используется существующая функция отображения имени.
- Полный набор тестов и архитектурные проверки проходят.

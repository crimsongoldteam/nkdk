# Общий преобразователь YAML-описания типа

## Проблема

Основной `TypeDescription.fromYAML` и предварительный индекс зависимостей независимо преобразуют YAML-описание типа во внутренний `TypeDescription`. Упрощённый преобразователь предварительного индекса не повторяет всю семантику основного преобразователя. В частности, `Дата` превращается в отдельный внутренний тип `date`, тогда как основной fromYAML правильно представляет её как `dateTime` с уточнением `Date`.

Из-за расхождения корректный реквизит формы

```yaml
ОтображаемаяДата:
  Тип: Дата
```

попадает в предварительный индекс с типом, который не удовлетворяет требованию элемента формы `dateTime`. В результате валидация выдаёт ложную ошибку.

## Цель

Основной fromYAML, предварительный индекс формы и индекс фактов владельца должны использовать один чистый преобразователь YAML → `TypeDescription`. Семантика типов не должна дублироваться между этапами обработки проекта.

## Не входит в изменение

- исправление пропущенных реквизитов и колонок формы без явно заданного типа;
- исправление вложенных путей `CurrentData`;
- изменение правил допустимых типов в `rules.ts`;
- изменение архитектурного порядка проходов валидации;
- изменение представления `TypeDescription` в YAML или XML.

## Архитектура

В `commonObjects/typeDescription/fromYAML.ts` выделяется чистая функция преобразования YAML-значения в `TypeDescription`. Она не зависит от `ConfigurationContext`, `PropertyRule`, валидатора, индекса проекта или конкретного объекта метаданных.

Функция отвечает за единственную семантику:

- простые типы и их параметры;
- `Дата`, `Время` и `ДатаВремя` вместе с уточнениями;
- ссылочные типы;
- составные типы;
- внешние источники данных;
- системные перечисления;
- описание через `ИдентификаторТипа`;
- пустое или структурно неподходящее значение.

`importTypeDescriptionFromYAML` остаётся переходником уровня правил. Он проверяет `allowedTypes`, после чего передаёт значение общей функции. Таким образом, ограничения конкретного `rules.ts` не проникают в общий преобразователь.

Предварительный индекс формы и индекс фактов владельца получают результат той же функции через нейтральный реестр `indexValueFromYAMLRegistry`. Статический импорт реализации из `commonObjects` запрещён границей metadata-слоёв и создаёт цикл. Локальная упрощённая `typeDescriptionFromYAML` из `validation/dataPath/formYamlIndex.ts` удаляется.

```text
YAML-описание типа
        │
        ▼
общий чистый преобразователь
        │
        ├──► основной TypeDescription.fromYAML
        └──► нейтральный реестр проекций индекса
                    │
                    ├──► предварительный индекс формы
                    └──► индекс фактов владельца
```

## Договор преобразования

Для даты общий результат имеет вид:

```text
Дата      → type: [dateTime], dateFractions: Date
Время     → type: [dateTime], dateFractions: Time
ДатаВремя → type: [dateTime], dateFractions: DateTime
```

Предварительный индекс затем сводит этот `TypeDescription` к своему `DataPathTypeInfo`. Все три варианта считаются значением вида `dateTime`; уточнение продолжает храниться в полном `TypeDescription` и не подменяется отдельным типом `date`.

Структурно неподходящее значение не должно приводить к собственной диагностике преобразователя: оно даёт `undefined`, а ошибку формирует существующая проверка JSON Schema. Это позволяет использовать функцию во время потокового первого прохода, когда вход ещё имеет тип `unknown`.

## Поток проверки формы

1. Первый проход читает YAML и проверяет JSON Schema.
2. Событие свойства `Реквизиты.<Имя>.Тип` передаётся сборщику предварительного индекса.
3. Сборщик запрашивает нормализованное значение в нейтральном реестре, где для `TypeDescription` зарегистрирован общий преобразователь.
4. Полученный `TypeDescription` преобразуется в `DataPathTypeInfo`.
5. Проверка `ПутьКДанным` сопоставляет требуемый вид значения с тем же внутренним типом, который использует основной fromYAML.

Для `Тип: Дата` шаг 4 получает вид `dateTime`, поэтому корректное поле даты проходит проверку.

## Проверки

Модульные тесты общего преобразователя переиспользуют существующие фикстуры `TypeDescription` и проверяют совпадение результата с `importTypeDescriptionFromYAML` для:

- `Дата`, `Время`, `ДатаВремя`;
- строк и чисел с параметрами;
- ссылочных типов;
- составных типов;
- идентификаторов типа;
- внешних источников и системных перечислений;
- пустых и неподходящих значений.

Тест предварительного индекса отдельно подтверждает, что `Дата`, `Время` и `ДатаВремя` дают `DataPathTypeInfo.kinds = ["dateTime"]`.

Интеграционная проверка на `/Users/nikita/git/sed_nkdk` должна устранить восемь ошибок `конечный тип не подходит, ожидается dateTime`, не меняя остальные группы диагностик.

## Критерии готовности

- в проекте остаётся одна реализация семантики YAML → `TypeDescription`;
- основной fromYAML использует функцию напрямую, а оба потребителя индекса — через единый нейтральный реестр;
- восемь ложных ошибок даты исчезают при чистой валидации;
- существующие проверки TypeDescription и всего проекта проходят;
- новые дубликаты относительно базового коммита отсутствуют;
- архитектурный план `.agents/architecture.md` не меняется.

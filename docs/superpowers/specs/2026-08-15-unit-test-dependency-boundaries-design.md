# Границы зависимостей unit-тестов

## Цель

Unit-тесты NKDK должны проверять предметную логику полностью в памяти и не
обращаться к внешнему окружению. Сеть, файловая система, базы данных, дочерние
процессы и настоящие worker запрещены; вместо них используются управляемые моки,
фейки или нейтральные порты. Интеграционные тесты сохраняют минимальные проверки
реальных адаптеров и подчиняются тому же пределу длительности test case — 50 мс.

## Классификация тестов

Обычный `*.test.ts` является unit-тестом. Его наблюдаемый договор не должен
зависеть от состояния машины, системного временного каталога или доступности
внешней службы.

`*.integration.test.ts` применяется только тогда, когда проверяемый договор
состоит именно во взаимодействии с реальным адаптером:

- чтении, записи, атомарной замене или правах файлов;
- схеме, сериализации, транзакции или совместимости базы данных;
- сетевом протоколе либо жизненном цикле процесса/worker.

Перенос в integration не используется для обхода лимита. Если внешний ресурс не
является частью договора, тест остаётся unit и получает подмену зависимости.

## Прямые запреты для unit-тестов

Unit-тестам запрещено вызывать:

- файловую систему: `fs`, `node:fs`, `node:fs/promises`, временные каталоги и
  файловые фикстуры, читаемые во время теста;
- сеть: `fetch`, HTTP/HTTPS, TCP/UDP, DNS, TLS, WebSocket и настоящие клиенты SSH;
- базы данных и дисковые хранилища, включая LMDB и `node:sqlite`;
- `child_process`, настоящие `worker_threads.Worker` и Piscina;
- команды и службы, доступность которых находится вне процесса Vitest.

Статические примеры данных разрешены как импорты TypeScript/JSON либо как
небольшие литералы и test builders. Мок обязан воспроизводить используемый
договор, порядок и ошибки зависимости; заранее подготовленный предметный ответ
не должен подменять тестируемую логику.

## Автоматическое соблюдение границы

Защита состоит из двух взаимодополняющих проверок:

1. Структурная проверка классифицирует тесты по имени и запрещает обычным
   `*.test.ts` прямые импорты модулей файловой системы, сети, БД, процессов и
   worker. Она охватывает все пакеты и сообщает файл и запрещённую зависимость.
2. Unit-конфигурация Vitest подключает общий guard, который завершает тест
   понятной ошибкой при фактическом вызове внешней зависимости через production-
   код. Интеграционные проекты этот guard не подключают.

Уже существующий запрет настоящего Piscina становится частью общего guard.
In-memory transport MCP и другие чистые фейки разрешены, поскольку не открывают
сокеты и не обращаются к системе.

## Миграция существующих тестов

Сначала полный unit- и integration-прогон фиксирует превышения длительности, а
структурная проверка формирует полный список нарушений изоляции. Для каждого
обычного теста выбирается самый узкий вариант:

- заменить внешний вызов mock-портом, если проверяется предметная логика;
- вынести маленький тест реального адаптера в `*.integration.test.ts`, если
  файловая система, БД, сеть, процесс или worker являются частью договора;
- удалить дублирующий сценарий только когда тот же договор уже защищён более
  узкой проверкой.

XML-фикстуры не изменяются. Unit-тесты, которым нужны их данные, получают
статический test-only модуль или минимальный литерал; интеграционные проверки
чтения исходных XML-фикстур остаются отдельными.

## Лимиты длительности

- цель test case: 10 мс, превышение выводится как предупреждение;
- жёсткий предел unit test case: 50 мс;
- жёсткий предел integration test case: 50 мс;
- lifecycle test file и package setup продолжают проверяться действующим
  переходником без специальных исключений для отдельных тестов;
- лимиты нельзя повышать параметром, переменной окружения или переносом теста в
  integration.

Фактические превышения исправляются после трёх воспроизводимых прогонов: дорогая
внешняя работа заменяется портом либо остаётся единственной узкой интеграционной
проверкой, повторная тяжёлая подготовка выносится из test case, а проверка
сохраняет тот же наблюдаемый договор.

## Проверка результата

- структурная самопроверка сначала падает на искусственном unit-тесте с каждой
  категорией запрещённых зависимостей и принимает соответствующий integration-
  тест;
- runtime guard имеет отдельные проверки понятной ошибки и разрешённых моков;
- `pnpm test` запускает все unit- и integration-тесты и обязательную проверку
  лимитов;
- `pnpm test:isolated`, `pnpm type-check`, `pnpm test:architecture:rules` и
  `pnpm test:architecture` проходят;
- `pnpm duplicates -- --base <исходный-коммит>` не обнаруживает новых дублей;
- итог перечисляет переклассифицированные, изменённые, добавленные и удалённые
  тесты с указанием сохранённого договора.

## Границы изменения

- production-поведение не меняется ради тестовой инфраструктуры, кроме введения
  нейтрального порта там, где исследование подтвердит скрытую внешнюю связь;
- общие типы rules.ts и XML-фикстуры не меняются;
- архитектурные baseline не перезаписываются;
- реальные e2e-сценарии не считаются unit/integration и остаются отдельной
  командой `pnpm test:e2e`.

# Обработка файлов проекта в воркерах при актуализации

## Назначение

Эта спецификация уточняет только чтение, хэширование и локальную обработку файлов внутри внутреннего блока «Актуализация и проверка состояния проекта».

Цель — читать каждый файл не более одного раза за один вызов актуализации, не накапливать содержимое всего проекта в основном процессе и выполнять хэширование параллельно с локальной validation изменённых YAML.

Спецификация не изменяет import, полную sync, переименование, поиск ссылок, схему SQLite и публичные договоры MCP. Защита изменяющих операций от изменения файлов между validation и записью остаётся за их собственными договорами.

## Принятое решение

Каждый validation worker получает путь файла, его вид, логическую идентичность и сохранённый хэш. Worker сам читает файл, вычисляет новый хэш и принимает решение о дальнейшей локальной обработке:

- если хэш совпал, worker немедленно освобождает прочитанные байты и возвращает признак неизменности;
- если новый или изменённый файл является YAML, worker из тех же байтов выполняет разбор, локальную validation и сбор нормализованного вклада в индекс;
- если новый или изменённый файл является внешним ресурсом, worker возвращает только новый хэш;
- после передачи результата worker освобождает исходные байты и разобранный YAML до получения следующего задания.

Validation worker не открывает SQLite и не выполняет SQL. Сохранённые хэши передаются ему как входные данные, а результаты записываются отдельным владельцем состояния через абстракцию `ProjectStateStore`.

## Рассмотренные варианты

### Сначала прочитать весь проект

Основной процесс читает и хэширует все файлы, сравнивает полный набор хэшей с SQLite и только затем передаёт изменённые YAML воркерам.

Подход прост, но удерживает содержимое всех файлов до завершения сравнения. Максимальная память зависит от суммарного размера проекта.

### Читать в основном процессе

Основной процесс читает очередной файл и передаёт его байты validation worker. Память можно ограничить очередью, но основной процесс принимает на себя весь ввод-вывод и передаёт через границу worker содержимое каждого файла, включая неизменённые ресурсы.

### Читать и обрабатывать в validation worker

Worker получает путь и сохранённый хэш, сам читает и хэширует файл, а изменённый YAML сразу обрабатывает из тех же байтов. Выбран этот вариант: он совмещает одно чтение, ограниченную память и параллельную обработку, не выдавая worker доступ к хранилищу.

## Участники

### Координатор актуализации

Координатор:

1. Находит и классифицирует все управляемые правилами файлы проекта.
2. Через `ProjectStateStore` получает сохранённые хэши найденных путей.
3. Сравнивает найденные пути с сохранённым составом и определяет исчезнувшие файлы.
4. Формирует ограниченную очередь заданий для validation worker.
5. Передаёт результаты владельцу состояния по мере завершения заданий.
6. После окончания локальной обработки запускает полную validation зависимостей.

Координатор не читает содержимое файлов и не удерживает их байты. Список путей и восьмибайтовые хэши допускается держать в памяти: они не дублируют содержимое проекта и нужны для определения состава.

### Validation worker

Одно задание содержит только данные, необходимые для обработки одного файла:

- абсолютный путь для чтения;
- нормализованный путь проекта;
- компонент и вид ресурса;
- роль YAML, если она применима;
- сохранённый хэш либо признак нового файла;
- переносимые разрешения и контекст локальной validation, не раскрывающие SQLite.

В каждый момент один worker обрабатывает не более одного файла. Он не сохраняет байты, разобранный YAML или локальный индексный вклад между заданиями.

### Владелец состояния проекта

Единственный владелец записи работает с SQLite через реализацию `ProjectStateStore`. Он принимает нейтральные результаты worker, заменяет состояние файлов и выполняет межфайловую validation. Оркестрация, validation worker и правила метаданных не знают таблиц, соединений и SQL.

## Поток одного задания

1. Worker получает путь, идентичность и сохранённый хэш.
2. Worker открывает файл, читает все его байты и закрывает файл.
3. По прочитанным байтам вычисляется xxHash64.
4. Новый хэш сравнивается с сохранённым хэшем задания.
5. При совпадении worker возвращает `unchanged` без байтов файла.
6. Для нового или изменённого внешнего ресурса worker возвращает идентичность и новый хэш.
7. Для нового или изменённого YAML worker из уже прочитанных байтов выполняет:
   - разбор YAML;
   - проверку JSON Schema;
   - локальные проверки;
   - извлечение нормализованных строк индекса и отложенных проверок.
8. Worker возвращает один нейтральный результат файла: новый хэш, локальные diagnostics и индексный вклад. Исходные байты и разобранный YAML в результат не входят.
9. После передачи результата worker освобождает данные задания и только затем принимает следующее.

Изменённый YAML не перечитывается между хэшированием, локальной validation и сбором индекса. Все результаты файла относятся к одному и тому же массиву прочитанных байтов.

## Ограничение памяти и обратное давление

Координатор выдаёт задания и принимает результаты через ограниченные очереди. Число одновременно читаемых файлов ограничено числом validation worker; размер очереди результатов также имеет явную верхнюю границу.

Если владелец состояния не успевает записывать результаты, worker после передачи результата ждёт подтверждения приёма и не начинает неограниченно создавать новые результаты. Протокол результата не содержит исходные байты файла, поэтому задержка записи не удерживает содержимое уже обработанного файла.

Максимальная память этапа должна зависеть от:

- числа validation worker;
- размеров файлов, одновременно читаемых этими worker;
- ограниченного числа нормализованных результатов в очереди;
- размера одного особенно крупного файла.

Она не должна зависеть от суммарного размера всех файлов проекта.

## Определение изменений без `stat` и `fstat`

Источником истины являются фактически прочитанные байты и вычисленный по ним хэш. Актуализация не вызывает дополнительные `stat` или `fstat` до либо после чтения и не выполняет завершающий обход `stat` по всем путям.

Поля `size`, `mtimeNs`, `dev` и `inode`:

- не входят в задание worker;
- не входят в его результат;
- не хранятся в SQLite;
- не используются для определения изменений или решения о повторе актуализации.

Совпадение этих признаков не доказывает неизменность содержимого. Файл можно заменить данными того же размера, сохранить либо восстановить время изменения, а физическая идентичность файла не является идентичностью логического пути проекта. Две проверки `fstat` и последующий `stat` обнаруживают обычные параллельные изменения, но добавляют системные вызовы и повторные проходы, не создавая атомарный снимок файловой системы.

Для validation принимается семантика снимка по прочитанным байтам:

- хэш, локальные diagnostics и индексный вклад одного файла относятся к одним прочитанным байтам;
- изменение файла после чтения может сразу сделать результат устаревшим;
- изменение во время неатомарной записи может дать worker промежуточное содержимое;
- вся актуализация из-за этого не перезапускается;
- следующий вызов заново прочитает управляемые файлы и обнаружит другую версию по хэшу.

Эта семантика достаточна для читающей операции validation и не объявляется атомарным снимком всего проекта на момент фиксации.

## Исчезновение и появление файлов во время прохода

Состав проекта определяется первоначальным обходом и результатами чтения заданий:

- путь из сохранённого состояния, отсутствующий в первоначальном обходе, считается удалённым;
- `ENOENT` при чтении найденного пути также превращает его в удалённый файл текущего прохода;
- файл, появившийся после первоначального обхода, не входит в текущий результат и будет найден следующим вызовом;
- ошибка чтения, отличная от отсутствия файла, является технической ошибкой.

Повторный полный обход для попытки получить атомарный состав не выполняется.

## Фиксация состояния

До выдачи заданий владелец состояния начинает одну транзакцию актуализации. Результаты worker применяются по мере готовности; порядок завершения заданий не влияет на итог, потому что каждый результат привязан к нормализованному пути.

- Неизменённый файл не изменяет сохранённое состояние.
- Новый или изменённый YAML атомарно заменяет хэш, локальный результат, diagnostics и весь индексный вклад исходного файла.
- Новый или изменённый внешний ресурс заменяет только хэш и сведения о файле.
- Удаление файла каскадно удаляет его хэш, локальные результаты и индексные строки.
- Ошибки локальной validation являются содержательным результатом и не откатывают состояние.

После приёма всех результатов владелец состояния выполняет полную validation зависимостей по итоговому общему индексу. Межфайловые diagnostics возвращаются вызывающей операции и не сохраняются в SQLite.

Успешный проход фиксирует транзакцию в памяти и атомарно заменяет дисковый снимок состояния. Ошибка чтения, сбой worker, отмена, нарушение протокола либо ошибка хранилища откатывает всю транзакцию и не заменяет опубликованный снимок.

## Договоры результатов

Протокол различает три результата задания:

- `unchanged` — идентичность файла без содержимого и без нового индексного вклада;
- `resourceChanged` — идентичность и новый восьмибайтовый хэш;
- `yamlChanged` — идентичность, новый хэш, локальный результат, diagnostics и нормализованный индексный вклад.

Хэш на границах worker и хранилища остаётся восьмибайтовым xxHash64 в согласованном порядке байтов. DTO не содержит `size`, `mtimeNs`, `dev`, `inode`, файловый дескриптор, разобранный YAML, функции, объекты правил или SQLite-соединение.

Конкретная упаковка нескольких результатов в общий буфер является деталью реализации при соблюдении следующих условий:

- один результат однозначно сопоставляется одному пути;
- байты исходных файлов не пересекают границу результата;
- пакет имеет ограниченный размер;
- результат допускает передачу между worker через структурное клонирование;
- прикладные слои не зависят от SQLite.

## Обработка ошибок

| Событие | Результат |
|---|---|
| Локальная ошибка YAML или JSON Schema | Возвращается и сохраняется как содержательная diagnostic текущего хэша. |
| Неразрешённая зависимость | Возвращается полной межфайловой validation; состояние локальных вкладов фиксируется. |
| `ENOENT` при чтении | Файл считается удалённым в текущем проходе. |
| Нет доступа, ошибка ввода-вывода или повреждение протокола | Вся транзакция откатывается. |
| Сбой validation worker | Вся транзакция откатывается; незавершённые задания отменяются. |
| Отмена операции | Новые задания не выдаются, выполняемые задания получают сигнал отмены, транзакция откатывается. |
| Ошибка SQLite или создания снимка | Транзакция либо незавершённое состояние отбрасывается; предыдущий дисковый снимок сохраняется. |

## Проверка решения

### Договорные тесты

Тесты подтверждают, что:

- неизменённый YAML читается и хэшируется, но не разбирается и не проверяется локально;
- изменённый YAML читается ровно один раз;
- хэш, diagnostics и индекс изменённого YAML получены из одних байтов;
- внешний ресурс не разбирается и сохраняет только новый хэш;
- байты файла и разобранный YAML отсутствуют в результате задания;
- один worker не обрабатывает одновременно больше одного файла;
- общее число одновременно читаемых файлов ограничено числом worker;
- ограниченная очередь создаёт обратное давление при медленной записи;
- разный порядок завершения заданий даёт одинаковое состояние и diagnostics;
- удаление файла удаляет все его сохранённые вклады;
- локальные validation-ошибки фиксируются, а технические ошибки и отмена откатывают обновление;
- повторный вызов обнаруживает изменение, произошедшее во время предыдущего прохода;
- договоры и обработка не используют `stat`, `fstat`, `size`, `mtimeNs`, `dev` и `inode`.

Юнит-тесты используют поддельный `ProjectStateStore` и поддельную файловую границу там, где проверяется оркестрация. Желательное время одного теста — до 10 мс, предельное — 50 мс. Небольшие интеграционные тестовые файлы с настоящей SQLite также должны оставаться быстрыми; весь такой тестовый файл должен завершаться не дольше 1 секунды.

### Профиль проекта

Готовая реализация измеряется через compiled standalone validation на `/Users/nikita/git/nkdk-yaml` без изменения пользовательского проекта и его кэша. Для холодной и прогретой validation фиксируются:

- полное время;
- максимальная резидентная память;
- число прочитанных и хэшированных файлов;
- число разобранных YAML;
- время чтения и хэширования;
- время локальной и межфайловой validation.

Прогретый проход обязан прочитать и хэшировать все управляемые файлы, но разобрать ноль YAML при неизменном проекте. Максимальная память должна определяться ограниченной параллельностью и размерами одновременно обрабатываемых файлов, а не суммарным размером проекта.

### Итоговые проверки

- Mutation testing в этой задаче не запускается.
- `pnpm check:duplicates -- --base e768ba6321fc99b2623e04f1fe72a06c77f07b38` не должен находить новых дублей в изменённых строках.
- Перед завершением реализации один раз выполняются `pnpm type-check` и полный `pnpm test`.

## Критерии готовности

Решение готово, когда одновременно выполняются следующие условия:

- содержимое файлов читают validation worker, а не координатор актуализации;
- каждый файл читается не более одного раза за один вызов актуализации;
- изменённый YAML проверяется и индексируется из тех же байтов, по которым вычислен хэш;
- неизменённый файл не передаёт байты за пределы worker и не проходит локальную validation;
- память ограничена числом worker и размером ограниченных очередей;
- SQLite доступна только через абстракцию состояния проекта;
- результаты фиксируются по мере готовности в одной откатываемой транзакции;
- полная validation зависимостей выполняется после применения всех локальных вкладов;
- `stat`, `fstat`, `size`, `mtimeNs`, `dev` и `inode` отсутствуют в новом потоке;
- последующий вызов обнаруживает изменения, сделанные после чтения предыдущего вызова;
- все договорные, интеграционные и итоговые проверки проходят в установленных бюджетах.

# Файловые цели в общих индексах проекта

## Контекст

В YAML существуют смысловые ссылки на элементы метаданных, чьё существование подтверждается отдельными файлами Проекта. Сейчас это прежде всего:

- форма объекта: `Формы/{Имя}/Форма.yaml`;
- макет объекта: `Макеты|Шаблоны/{Имя}/Template.xml|txt|bin` либо содержимое каталога `Ext`.

Сами ссылки уже извлекаются из YAML и сохраняются в индексе зависимостей как `pendingReferences`. Ошибка находится на другой стороне разрешения ссылки: цели `Form` и `Template` частично строятся непосредственным просмотром файловой системы через `existsSync`, `statSync` и `readdirSync`.

Такой просмотр нарушает общий договор состояния проекта и даёт разный результат в разных операциях. Во время XML-import локальные YAML уже сформированы, но внешние файлы макетов ещё не переданы в Проект. Предварительный просмотр каталога не находит их, хотя перед Б5 файлы будут записаны и хэшированы. Обычная validation тех же окончательных файлов, напротив, видит макеты. На контрольном импорте это создаёт отдельную группу ложных неразрешённых ссылок.

В проекте уже есть два нужных логических индекса:

- индекс метаданных содержит существующие цели и типизированные факты;
- индекс зависимостей содержит ссылки, `ПутьКДанным`, координаты источника и обратное отображение.

Оба входят в единое восстанавливаемое `ProjectState`, связанное с таблицей хэшей файлов. Новый индекс не требуется.

## Цель

Сделать файлы Проекта единственным источником существования файловых целей и разрешать ссылки на них общим механизмом `ProjectState` во всех операциях:

- validation;
- XML-import;
- полная YAML → XML синхронизация;
- поиск ссылок;
- переименование метаданных.

Ссылка на файловую цель должна разрешаться только тогда, когда соответствующий ресурс классифицирован общей `resourceTopology`, фактически прочитан и представлен актуальным хэшем.

## Не входит в задачу

- проверка каждого внешнего файла только потому, что он объявлен в топологии;
- ошибка для отсутствующего файла, на который нет смысловой ссылки;
- введение ссылок на модули, справку, изображения, XSD и другие ресурсы, для которых правила не объявляют смысловой тип цели;
- проверка полноты XML-выгрузки или обязательных XML-выходов;
- новый дисковый индекс рядом с `project-state.bin`;
- отдельный валидатор или отдельные правила для import;
- перенос Б5 в worker или распараллеливание полной dependency validation;
- перенос копирования внешних файлов внутрь первого прохода import;
- автоматический откат частично скопированных или перемещённых файлов при технической ошибке import.

## Архитектурные инварианты

### Разделение двух индексов

Индекс зависимостей хранит ребро:

```text
YAML-файл + YAML path + canonical target + constraint
```

Например:

```text
Отчет.Продажи.ОсновнаяСхемаКомпоновкиДанных
  → Отчет.Продажи.Template.ОсновнаяСхема
```

`Template` здесь является внутренним canonical-сегментом индекса. В YAML та же ссылка сохраняет пользовательское представление `Макет.ОсновнаяСхема`.

Индекс метаданных хранит цель:

```text
canonical target + componentPath + sourceProjectPath + details
```

Например:

```text
Отчет.Продажи.Template.ОсновнаяСхема
  ← cf/Отчет/Продажи/Макеты/ОсновнаяСхема/Template.xml
```

Б5 сопоставляет ребро зависимости с целью метаданных с учётом видимости компонентов. Таблица хэшей не заменяет ни один индекс: она подтверждает, что исходный файл цели действительно прочитан в той же версии состояния.

### Один источник истины о файлах

Файловая цель добавляется в индекс метаданных только как вклад конкретного хэшированного ресурса. Нельзя создавать такую цель из:

- имени в коллекции `Формы` или `Макеты` родительского YAML;
- ожидаемого пути;
- результата `existsSync`;
- предварительного списка файлов import до их передачи и хэширования.

Если файл исчез, Б1 фиксирует отсутствие, Б4 удаляет его хэш и индексный вклад, а Б5 видит оставшуюся ссылку как неразрешённую.

### Общая топология без частных условий

`resourceTopology` уже является общим описанием ресурсов. Она должна дополнительно предоставлять нейтральную проекцию файловой цели:

- вид цели: `member`;
- `memberKind`, например `Form` или `Template`;
- параметр имени элемента, например `itemName`;
- владелец цели через существующую цепочку владения assignment;
- путь ресурса, создавшего вклад;
- путь каталога файлового элемента;
- путь содержательного YAML владельца.

Знание о каталогах `Формы`, `Макеты`, `Шаблоны`, именах `Template.*` и видах элементов остаётся в декларациях `ChildFormNames` и `ChildTemplateNames`. Общие слои `project`, `validation`, `projectState` и `orchestration` не ветвятся по этим именам или `itemType`.

Начальный набор деклараций ограничен существующими смысловыми видами `Form` и `Template`. Механизм допускает новые файловые цели только через явную декларацию топологии и существующую грамматику `MetadataTarget`.

## Представление файловой цели

`MetadataContentDeclaration` и `MetadataExternalFileDeclaration` получают необязательную декларацию:

```ts
interface MetadataFileBackedMemberTargetDeclaration {
  readonly kind: "member"
  readonly memberKind: MetadataMemberKind
  readonly itemNameParameter: string
  readonly itemProjectPattern: string
  readonly owner: "assignment" | "assignmentOwner"
}
```

`itemProjectPattern` задаёт общий каталог файлового элемента явно; общий код не выводит его удалением последнего сегмента произвольного пути. `owner` выбирает текущее содержательное assignment для внешнего макета либо владельца вложенного assignment для формы. Компилятор проверяет наличие параметра имени, достижимость выбранного владельца и совместимость шаблона каталога со всеми ресурсами цели. Конкретный владелец вычисляется тем же общим механизмом `metadataTargetOwner` (`self`/`inherit`/`resolver`), что и при преобразовании YAML; это охватывает вложенные объекты внешних источников данных без частных условий в топологии.

Из скомпилированной декларации и `MetadataProjectResourceMatch` чистая проекция без доступа к диску строит:

```ts
interface MetadataFileBackedTargetContribution {
  readonly kind: "member"
  readonly memberKind: MetadataMemberKind
  readonly owner: MetadataTargetOwner
  readonly itemName: string
  readonly evidenceProjectPath: string
  readonly itemProjectPath: string
  readonly ownerProjectPath: string
}
```

Внутренний договор называется `MetadataFileBackedTargetContribution` и не содержит абсолютных путей как идентификаторов.

- `evidenceProjectPath` указывает на хэшированный файл, доказывающий существование цели;
- `itemProjectPath` указывает на общий каталог формы или макета и одинаков для всех файлов одной цели;
- `ownerProjectPath` указывает на содержательный YAML владельца и позволяет изменяющим операциям загрузить владельца без поиска по каталогам.

Для формы вклад создаёт только содержательный `Форма.yaml`. Модуль, справка и другие связанные внешние файлы не доказывают существование формы.

Для макета цель подтверждает любой содержательный вариант, который уже признаёт топология:

- `Template.xml`;
- `Template.txt`;
- `Template.bin`;
- файл внутри остаточного пути макета, включая `Ext/...`.

Несколько файлов одного макета дают одну canonical-цель. Двоичный построитель группирует вклады с одинаковыми `componentPath`, canonical-адресом, владельцем и `itemProjectPath` как одну логическую цель. Они не считаются неоднозначностью. Несовпадающий владелец или каталог для одного canonical-адреса остаётся конфликтом.

Исходные вклады сохраняют принадлежность `evidenceProjectPath`, чтобы удаление одного файла не удалило цель, пока остаётся другой подтверждающий файл. Запрос цели возвращает логическую цель, её `itemProjectPath` и `ownerProjectPath`, а не случайно выбранный файл-доказательство.

## Изменения в `ProjectState`

### Вклады файлов

Любой `ProjectStateFileUpdate` передаёт ноль или несколько целевых записей, объявленных топологией. Для содержательного YAML они добавляются к целям, извлечённым из его данных. `ProjectStateResourceUpdate` получает ту же возможность для внешнего файла без YAML. YAML-update продолжает передавать:

- цели, извлечённые из содержимого YAML;
- ожидающие разрешения ссылки;
- типизированные факты владельцев и полей;
- локальные diagnostics.

Resource-update передаёт только идентичность ресурса, хэш и объявленные топологией цели. Он не содержит разобранный YAML или предметную metadata-модель. Поэтому `Форма.yaml` остаётся обычным YAML-update, а её цель `Form` возникает из классификации того же файла, а не из отдельной записи ресурса.

Двоичный формат хранит целевые записи resource-update в той же таблице целей, что и целевые записи YAML-update. `resolveTargets` применяет к ним тот же canonical-поиск и компонентную видимость. Отличие ограничено происхождением и путями файловой цели, которые нужны проектным операциям; отдельного алгоритма разрешения ссылок нет.

### Удаление и замена

Индексный вклад принадлежит записи файла и удаляется вместе с ней. Поведение должно быть следующим:

- файл и хэш не изменились — прежний вклад переиспользуется;
- файл изменился — хэш и вклад заменяются одной версией;
- файл удалён — его вклад удаляется;
- один из нескольких файлов макета удалён — цель остаётся, если существует другой хэшированный вклад;
- удалены все подтверждающие файлы — цель исчезает;
- ссылка осталась — Б5 выдаёт обычную diagnostic неразрешённой ссылки.

Физический формат остаётся деталью двоичного адаптера. Публичные операции зависят от `ProjectStateStore` и `ProjectStateReadSession`, а не от расположения таблиц в `project-state.bin`.

## Общий поток операций

### Исполнение Б5

Validation и import вызывают один общий `validateDependencyDiagnosticBatches()` над окончательными двоичными буферами `ProjectState`. Б5 выполняется в главном процессе после приёма вкладов всех worker и до публикации нового состояния.

Worker выполняют хэширование, разбор и локальную validation отдельных файлов, но не получают неопубликованное окончательное состояние для полной проверки зависимостей. Перенос Б5 в worker потребовал бы отдельной общей оптимизации: выдачи read-token состояния-кандидата, разбиения всех зависимостей на пачки и объединения diagnostics. Это не требуется для корректного разрешения файловых целей и в эту задачу не входит.

### Обычная актуализация и validation

1. Б1 обнаруживает ресурсы через `resourceTopology`, читает их и вычисляет хэши.
2. Для изменённых YAML Б2 извлекает цели, ссылки и факты.
3. Для хэшированных файловых ресурсов общая проекция топологии создаёт целевые вклады.
4. Б4 атомарно заменяет вклады изменённых файлов и удаляет вклады исчезнувших.
5. Б5 разрешает все ссылки индекса зависимостей по окончательному индексу метаданных.
6. Б6 публикует и сохраняет согласованные хэши, оба индекса и локальные diagnostics.

Дополнительного `stat` или обхода каталога внутри построения индекса нет.

### XML-import

Порядок import остаётся последовательным в части передачи файлов:

1. discovery строит задания по `resourceTopology`;
2. первый проход создаёт готовые YAML и рабочий индекс для отложенных преобразований;
3. второй проход завершает оставшиеся YAML;
4. объединяется и проверяется список файлов результата;
5. внешние файлы копируются либо перемещаются отдельным этапом;
6. переданные файлы читаются, хэшируются и дают файловые целевые вклады через ту же проекцию топологии;
7. строится окончательное состояние import session;
8. Б5 выполняет тот же общий dependency validator;
9. состояние публикуется и сохраняется.

Рабочий индекс между первым и вторым проходами не обязан содержать файловые цели: он нужен уточнению отложенных YAML-значений. Существование ссылочных целей проверяется только на Б5 по окончательному состоянию.

Import не создаёт цели из discovery: найденный исходный XML-файл ещё не подтверждает наличие итогового файла Проекта. Цель появляется только после успешной передачи и хэширования целевого файла.

Если передача или хэширование завершается технической ошибкой, import session не публикуется. Уже переданные файлы не откатываются. Для режима `move` допускается частично изменённая исходная XML-выгрузка.

### Поиск ссылок и переименование

`find_references` и `rename_item` уже начинают с общей актуализации и обращаются к `ProjectStateReadSession`. Они продолжают использовать:

- одну таблицу ожидающих ссылок для обратного поиска;
- одну таблицу целей для подтверждения исходной цели;
- те же canonical-адреса и правила компонентной видимости.

Для файловой цели индексированный результат содержит `itemProjectPath` и `ownerProjectPath`. Поиск ссылок использует каталог элемента, чтобы отличить внутренние ссылки его дерева от внешних. Переименование загружает YAML владельца, переписывает найденные ссылки и переименовывает весь каталог элемента. Оно не подтверждает цель через `existsSync`, не требует вымышленного основного файла макета и не обходит каталог для получения списка соседних целей: имена занятых целей читаются из общего индекса метаданных.

Переименование изменяет только YAML-проект и пути его ресурсов согласно существующему плану файловых операций. Оно не читает и не изменяет XML-выгрузку. Специального поиска ссылок на формы или макеты не добавляется.

### Полная синхронизация в XML

Полная sync начинает с той же актуализации и Б5. Поэтому отсутствующая файловая цель блокирует sync обычной validation diagnostic, если `ignoreValidationErrors` не установлен.

После проверки sync использует общую классификацию `resourceTopology` и хэши из того же `ProjectState` для построения XML-заданий и передачи внешних файлов. Отдельная проверка существования формы или макета в sync не нужна.

## Удаляемые параллельные механизмы

После перехода не должны остаться:

- прямые `existsSync`-contributors для `Form` и `Template` в `metadataTargetProjectResolvers`;
- специальное построение цели формы из `ValidationProjectFile` вне проекции `resourceTopology`;
- `buildTemplateFileMemberIndexEntries` и обход каталогов макетов внутри validation;
- построение целей `Form` и `Template` только из коллекций родительского YAML;
- `existsSync` и `readdirSync` для подтверждения файловой цели и поиска занятых имён внутри `rename_item`;
- import-специфичная проверка наличия скопированного файла;
- дополнительный предварительный индекс файловых зависимостей.

Коллекции родительского YAML могут оставаться предметными фактами для fromXML/toXML и других правил, но не доказывают физическое существование файловой цели.

## Diagnostics и ошибки

Отсутствующая файловая цель использует существующий договор неразрешённой metadata-ссылки:

- diagnostic принадлежит YAML-файлу со ссылкой;
- `yamlPath`, строка и колонка указывают на значение ссылки;
- сообщение содержит canonical-цель;
- компонентная видимость совпадает с остальными metadata-ссылками;
- одинаковая причина даёт одинаковую diagnostic в import и последующей чистой validation.

Отсутствующий файл без смысловой ссылки не создаёт diagnostic этой задачи.

Конфликт деклараций топологии, при котором один путь даёт несовместимые цели, является технической ошибкой компиляции топологии. Два физических файла, законно подтверждающих одну цель макета, конфликтом не являются.

## Производительность

Файловые цели строятся во время уже существующего хэширования и не требуют дополнительного обхода файловой системы. Неизменённые файлы переиспользуют сохранённые вклады.

Копирование остаётся отдельным этапом после второго прохода. Измерение compiled MCP stdio с четырьмя worker показало:

| XML-каталог | Режим | Cold | Warm avg |
|---|---:|---:|---:|
| `/Users/nikita/git/sed_xml/cf` | отдельное копирование | 19,44 с | 14,70 с |
| `/Users/nikita/git/sed_xml/cf` | параллельно первому проходу | 17,90 с | 15,04 с |
| `/Users/nikita/git/round-trip/cf/erp` | отдельное копирование | 144,10 с | 145,59 с |
| `/Users/nikita/git/round-trip/cf/erp` | параллельно первому проходу | 160,31 с | 185,46 с |

На ERP параллельное копирование увеличило тёплое время на 27%: первый проход конкурировал с копированием за чтение XML и запись YAML. Поэтому изменение порядка передачи файлов в эту задачу не входит.

## Тестирование

### Топология

Unit-тесты общей проекции подтверждают:

- `Форма.yaml` создаёт цель `Form`;
- модуль или справка формы без `Форма.yaml` не создаёт цель `Form`;
- каждый допустимый вариант содержимого макета создаёт одну цель `Template`;
- два файла одного макета создают одну разрешаемую canonical-цель;
- проекция одинаково вычисляет `itemProjectPath` и `ownerProjectPath` для всех файлов одного макета;
- внешний файл без декларации смысловой цели не создаёт target contribution;
- проекция работает только по `MetadataProjectResourceMatch` и не обращается к диску.

### Договор `ProjectStateStore`

Общие контрактные тесты двоичного состояния проверяют:

- разрешение файловой цели;
- обратный поиск ссылки на неё;
- компонентную видимость `cfe → cf` и приоритет локальной цели расширения;
- удаление единственного подтверждающего файла;
- сохранение цели после удаления одного из нескольких подтверждающих файлов;
- конфликт при несовместимых владельцах или каталогах одной canonical-цели;
- сохранение и повторную загрузку целевых вкладов resource-update.

### Validation

Интеграционные тесты проверяют:

- ссылка на существующую форму разрешается;
- ссылка на существующий макет разрешается;
- ссылка на макет без подтверждающих файлов даёт diagnostic;
- имя макета в родительском YAML без файла не создаёт цель;
- отсутствующий файл без ссылки не создаёт diagnostic;
- удаление файла между двумя validation удаляет цель без полного повторного разбора неизменённого YAML;
- проверка не вызывает файловые `existsSync`-contributors для разрешения ссылок.

### Import

Интеграционный тест фиксирует порядок:

```text
first pass → working index → second pass → transfer → hash → final state → Б5
```

Дополнительно проверяется:

- цель внешнего макета отсутствует до передачи и появляется после хэширования;
- Б5 видит окончательную цель;
- import и чистая validation записанного проекта возвращают одинаковые diagnostics;
- ошибка передачи или хэширования не публикует import session;
- `copy` и `move` используют один путь построения целевых вкладов.

### Операции

Контрактный сценарий над одним проектом подтверждает, что одна и та же ссылка на файловую цель:

- валидируется Б5;
- находится через `find_references`;
- переписывается через `rename_item`;
- переименовывается целиком по `itemProjectPath` без проверки XML и прямого обхода каталога;
- блокирует полную sync при удалённом файле;
- одинаково обрабатывается после XML-import.

## Изменение архитектурного описания

На этапе реализации `.agents/architecture.md` уточняется без изменения существующего порядка Б1–Б6:

- общий индекс метаданных включает цели, созданные хэшированными файловыми ресурсами;
- индексный вклад ресурса принадлежит хэшу файла и каскадно удаляется вместе с ним;
- Б5 разрешает ссылки по окончательным целям YAML и файловых ресурсов;
- import передаёт внешние файлы отдельным этапом после второго прохода и до окончательной Б5;
- прямые проверки существования файлов вне общего состояния запрещены.

## Критерии готовности

- ссылки на `Form` и `Template` находятся в общем индексе зависимостей;
- существование `Form` и `Template` подтверждается только хэшированными ресурсами общего индекса метаданных;
- `resourceTopology` является единственным источником классификации файловых целей;
- validation, import, sync, поиск ссылок и переименование используют один `ProjectState` и его запросы;
- validation и import выполняют одну реализацию Б5 в главном процессе;
- отсутствуют специальные проверки существования файлов для import и validation;
- удаление всех файлов цели делает существующую ссылку неразрешённой;
- отсутствующий файл без ссылки не создаёт ошибку;
- import и чистая validation одинакового Проекта возвращают одинаковые dependency diagnostics;
- копирование и перемещение остаются отдельным этапом после второго прохода;
- новый дисковый индекс не создаётся;
- проектные тесты и `pnpm duplicates -- --base <commit>` проходят.

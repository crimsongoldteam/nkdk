# MCP npm publish design

## Цель

Опубликовать NKDK в npm как MCP-сервер для ИИ-агентов. Основной пользовательский сценарий:

```json
{
  "mcpServers": {
    "nkdk": {
      "command": "npx",
      "args": ["-y", "@nkdk/mcp"]
    }
  }
}
```

Пользователь не должен клонировать репозиторий, запускать `pnpm install` в рабочем дереве или знать структуру монорепозитория.

## Не цели

- Не публиковать `@nkdk/core` как самостоятельный публичный пакет.
- Не публиковать `@nkdk/cli` как основной пользовательский продукт.
- Не публиковать root-пакет `nkdk` как исполняемый пакет в этом изменении.
- Не менять MCP tools и поведение YAML/XML-операций.

## Архитектура пакетов

Единственный публикуемый npm-пакет: `@nkdk/mcp`.

`@nkdk/core` остаётся workspace-пакетом для разработки, тестов и локального разделения кода. При публикации MCP core-код включается в сборку `@nkdk/mcp` как внутренняя реализация, а не как npm-зависимость `@nkdk/core`.

Root-пакет `nkdk`, `@nkdk/core` и `@nkdk/cli` должны быть защищены от случайной публикации через `private: true` или через явно документированный publish-процесс, который публикует только `packages/mcp`.

## Сборка `@nkdk/mcp`

В `packages/mcp` нужен отдельный build-сценарий для публикации. Он создаёт `dist`-набор, а не один файл:

- `dist/bin/nkdk-mcp.mjs` — исполняемый entrypoint с `#!/usr/bin/env node`;
- `dist/projectValidationWorker.js` — отдельный worker-файл для `Piscina`;
- `dist/projectValidationAjvStandalone.js` — standalone AJV-модуль, который worker загружает рядом с собой;
- дополнительные служебные файлы допускаются только если они нужны runtime-загрузчику и перечислены в `files`.

MCP entrypoint бандлится через `esbuild`. Импорты из `@nkdk/core` или из `packages/core` должны попадать в bundle, кроме validation worker и standalone AJV-модуля, которые остаются отдельными файлами.

Существующая логика `projectValidationWorkerPool.ts` уже различает `.ts` и `.js`: для собранного `.js`-runtime она ищет `projectValidationWorker.js` рядом с текущим файлом. Публикационная сборка должна сохранить это соглашение: worker и standalone AJV лежат в одном runtime-каталоге или адаптер явно передаёт корректный путь.

## Runtime-зависимости

`@nkdk/mcp` не должен зависеть от `workspace:*` во время публикации.

Возможны два допустимых варианта:

- бандлить core и большую часть внутренних зависимостей в `dist`;
- оставлять внешними только стабильные npm-зависимости, которые корректно указаны в `dependencies` `@nkdk/mcp`.

Недопустимые runtime-ссылки:

- `pnpm --filter`;
- путь от bin к корню монорепозитория через `../../..`;
- запуск TypeScript-исходников через локальный `tsx`;
- зависимость опубликованного `@nkdk/mcp` от непубликуемого `@nkdk/core`.

## Состав npm-пакета

В `packages/mcp/package.json` нужно задать:

```json
{
  "bin": {
    "nkdk-mcp": "./dist/bin/nkdk-mcp.mjs"
  },
  "files": [
    "dist",
    "README.md",
    "LICENSE"
  ]
}
```

Если `README.md` и `LICENSE` остаются только в корне репозитория, publish-сценарий должен копировать их в пакет перед `npm pack` или список `files` должен отражать фактическую структуру пакета.

`prepack` может запускать build автоматически, но release-процесс всё равно должен явно выполнять build и dry-run, чтобы состав архива был виден до публикации.

## Документация

Основной README должен показывать npm-подключение:

```json
{
  "mcpServers": {
    "nkdk": {
      "command": "npx",
      "args": ["-y", "@nkdk/mcp"]
    }
  }
}
```

Локальный запуск из клона остаётся отдельным разделом для разработки и проверки изменений.

## Проверки перед публикацией

Перед `npm publish` обязательны:

1. `pnpm test`;
2. `pnpm --filter @nkdk/mcp build`;
3. `npm pack --dry-run` из `packages/mcp`;
4. smoke test из временного каталога:
   - собрать tarball `@nkdk/mcp`;
   - установить или запустить его как внешний пакет;
   - проверить, что `nkdk-mcp` стартует;
   - проверить, что MCP server регистрирует tools;
   - выполнить минимум один read-only tool, например `nkdk.get_schema` или `nkdk.describe_project_structure`.

## Публикация

Публикуется только `packages/mcp`:

```sh
cd packages/mcp
npm publish --access public
```

Перед публикацией нужно проверить npm-аутентификацию (`npm whoami`) и доступ к scope `@nkdk`.

Если `0.0.3` уже опубликована или была частично опубликована, версия должна быть повышена до следующей перед повторной публикацией.

## Риски

- Worker/standalone AJV: если файлы окажутся не рядом, validation упадёт только на реальном запуске, поэтому нужен smoke test именно установленного tarball.
- Размер пакета: standalone AJV крупный, но это осознанная плата за быстрый validation runtime.
- Ошибочная публикация внутренних пакетов: `private: true` и явный publish-процесс должны предотвращать публикацию root/core/cli.
- Расхождение dev/runtime: локальные тесты через TypeScript не заменяют проверку собранного npm-пакета.

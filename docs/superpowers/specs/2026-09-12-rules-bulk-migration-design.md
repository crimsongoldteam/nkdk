# Массовый перенос правил и тестов в декларации и Rust

Следующий архитектурный этап — [единый план преобразования](2026-09-13-unified-conversion-plan-design.md).
Общие сочетания записей, вложенности и коллекций определяются один раз при
сборке. Ускорение подтверждается полной приёмкой семейства и повторным
использованием механизма следующим семейством; число выпущенных проекций
само по себе не означает завершение переноса.

Статус: архитектурные решения согласованы; массовый перенос выполняется. Текущие результаты и незавершённые задачи отражены в плане.

Этот документ описывает процесс и временный инструмент миграции, а не новый
язык. Единственная спецификация языка —
[язык деклараций](2026-09-10-declaration-language-design.md).
Исполнение — по [плану](../plans/2026-09-12-rules-bulk-migration.md).

## 1. Результат и охват

Цель — автоматизировать механическую часть полного перехода на Rust,
сохранив краткие декларации, проверку данных и обратимое сохранение аномалий.
В итоговом приложении нет зависимости от TypeScript. Временный инструмент
миграции допускается на TS с использованием синтаксического анализатора;
после передачи объекта YAML становится источником истины.

Инвентаризация охватывает определения, а не только файлы `rules.ts`:

- common и системные перечисления;
- общие фрагменты и построители;
- реквизиты, табличные части, графы, команды и прочие вложенные объекты;
- формы, элементы форм и их вложенность;
- владельцы, включая Document и DocumentJournal;
- регистрацию, индексы, ссылки, внешние XML, модули и прочие файлы.

Common, вложенные объекты и владельцы используют один язык с разными ролями.
Common остаются самостоятельными модулями, доступными через явные ссылки
и параметры. Их не превращают в владельцев и не копируют в потребителей.
Enterprise исключён: целевые преобразования XML ↔ YAML.

## 2. Способ переноса

Основной источник — статический разбор TS с разрешением импортов, символов,
констант, общих фрагментов и переопределений. Регулярные выражения не заменяют
синтаксический анализ. Для каждого перенесённого свойства сохраняется
происхождение: файл, символ и позиция исходного определения.

Дополнительная проверка читает собранные TS-правила и сравнивает итоговый
перечень свойств. Она не является источником семантики функций или структуры
общих фрагментов. Загрузка выполняется отдельным контролируемым процессом
на локальном коде проекта; недоступность сборки явно отражается в отчёте.

Преобразователь поддерживает конечный набор исследованных конструкций:
вызовы построителей, литералы, ссылки, композицию и согласованные выражения.
Неизвестные конструкции группируются по форме и зависимостям, с примерами
использования. Произвольный TS не исполняется для угадывания значения.

Частные обработчики по имени объекта запрещены в общем Rust-механизме.
Например, путь `Commands/${name}/Ext/CommandModule.bsl` должен выражаться
общим шаблоном пути. Новые возможности языка добавляются только после
установления, что существующих декларативных средств недостаточно.

## 3. Полнота, композиция и повторный запуск

Перенос включает XML/YAML-имена и пути, порядок, отсутствие и пустые значения,
значения по умолчанию, ограничения, связи, дочерние коллекции, регистрацию,
индексы и файлы. Приоритеты TS-переопределений сохраняются; общие фрагменты
остаются общими. Противоречие целевому договору нельзя разрешать молча.

Каждое исходное свойство получает один результат: перенесено, исключено по
согласованной причине либо заблокировано с конкретной причиной. Исключение
из миграции не является аномалией данных. Неполная декларация не подключается
к рабочему каталогу; независимые готовые модули могут проверяться отдельно.

Генерация идёт в отдельный каталог кандидатов. Одинаковые исходники и версия
инструмента дают одинаковые файлы. Уже доработанные YAML не перезаписываются:
инструмент сравнивает кандидата с существующей декларацией и выдаёт различия.
Смена исходного файла после инвентаризации определяется по хешу и требует
повторного анализа. Происхождение хранится в отчёте, не раздувает YAML.

Используется существующий `tests/migration/coverage.json`; детализация
свойств и тестов дополняет его, а не создаёт независимый реестр готовности.
Пользовательский чеклист остаётся бинарным; системные перечисления — один
пункт. Генерация YAML не устанавливает галочку завершения.

## 4. Common и порядок зависимостей

Сначала инвентаризируются все common и потребители, включая элементы форм.
Не требуется вручную завершать весь каталог common перед генерацией.
Поддержанные конструкции переносятся автоматически, затем группы идут по
готовности зависимостей. Приоритет получают common, открывающие наибольшее
число потребителей. Циклы и неразрешённые ссылки выводятся явно; произвольный
порядок обхода не считается решением цикла.

Document и DocumentJournal служат проверочными образцами. Перед массовым
запуском также проверяется представитель элемента формы: только владельцы
не доказывают поддержку всех ролей. Конкретные группы и очередность
определяются отчётом, без заранее обещанного процента автоматизации.

## 5. Перенос тестов

Переносятся защищаемые договоры и данные, а не число файлов TS-тестов.
У каждой исходной проверки фиксируются договор, новая проверка либо
оставшаяся защита при объединении. Неизвлекаемые динамические проверки
попадают в отчёт, а не пропускаются. Существующие XML-фикстуры неизменны.

Переносимые случаи содержат вход XML/YAML, независимо установленный
ожидаемый результат, подготовленные входы/индексы, ожидаемые аномалии и
критерий сравнения XML. Смысловое равенство и восстановление исходной формы
различаются явно: нельзя требовать случайного форматирования там, где оно
не является договором, или нормализовать значимую аномалию.

Общий Rust-запускатель выполняет данные случаев для всех ролей. Проверяются:

1. XML → ожидаемый YAML и YAML → ожидаемый XML независимо.
2. XML → YAML → XML без скрытой зависимости от исходного XML; необходимые
   сведения об аномалии находятся в YAML, обычные зависимости — во входах.
3. Значение, расположение и восстановление аномалий, порядок и повторы,
   отсутствие и пустые состояния.
4. Сборка владельца с вложенными объектами, индексами и внешними файлами.

Общая небольшая матрица защищает механизмы языка и преобразователя TS:
композицию, переопределения, разрешение ссылок, неизвестные выражения,
полноту и повторяемость. Объектные данные защищают предметные различия.
Новые копии одинаковых unit-тестов не создаются; следовать `.agents/testing.md`.
Реальный корпус на этом этапе ограничен существующим e2e.

Сравнение с TS временное и вспомогательное. Точные десятичные числа и
сохранение записанного времени даты — согласованные различия. Для каждого
такого отличия нужен конкретный ожидаемый результат; широкие исключения
из сравнения запрещены. Новая реализация не генерирует собственный эталон.
Старые тесты удаляются только после появления равноценной защиты; round-trip,
фикстуры, снимки и регрессии автоматически не удаляются.

### 5.1. Ответственность тестов

Обязательна [четырёхуровневая схема](../../../.agents/testing.md#декларации-и-rust-четыре-уровня-проверок):

1. **Common:** общая матрица проверяет преобразование, валидацию и аномалии
   булевого значения, числа, коллекции и других механизмов. Не копировать
   эту матрицу для каждого использующего common свойства.
2. **Декларация объекта:** независимые пары XML/YAML проверяют сразу набор
   свойств — их пути, имена, параметры и ограничения. Дополнительные случаи
   нужны для непокрытых особенностей и взаимодействий, а не для каждого поля.
3. **Оркестраторы:** небольшие проверочные декларации защищают выбор правил,
   передачу контекста и индексов, обработку вложенных объектов и файлов,
   сбор аномалий и размещение результатов. Common-проверки не дублируются.
4. **E2E:** настоящий проект проходит через настоящие оркестраторы и декларации.

Например, boolean проверяется общей матрицей, а boolean-свойство документа —
примером документа с ожидаемыми XML и YAML. Добавление второго такого свойства
обычно расширяет эти данные, не создавая новые тесты boolean и оркестратора.
Пример обязан различать проверяемое поведение: одного default-значения
недостаточно для доказательства всех настроек свойства.

Декларация позволяет выбирать общие проверки, но не генерировать единственный
эталон собственной правильности. Проверки направлений независимы, round-trip
их дополняет. При объединении старых тестов сохраняется соответствие исходного
сценария новой защите. Рост числа проверок допустим для нового поведения;
копирование одинаковой защиты и полное перемножение параметров не требуются.

Размещение в существующих Rust-матрицах, данных миграции, проверках приложения
и e2e описано в `.agents/testing.md`; новые каталоги по названиям уровней
создавать не требуется. Этот договор не означает, что реорганизация уже выполнена.

## 6. Аномалии и производительность

Декларация описывает нормальные значения; общий механизм выводит возможные
отклонения и сохраняет их обратимо. Отдельный перечень аномалий каждого
объекта не нужен. Ошибки данных не прерывают преобразование; ошибки
компилятора, ввода-вывода и пробелы миграции не маскируются аномалиями.

YAML компилируется в Rust при сборке. Нельзя внедрять runtime-интерпретацию
правил, повторный разбор документа на каждое свойство или копирование
полного контекста. Проверяются также дубли сгенерированного кода, размер
бинарного файла и время сборки. Цели 10× скорости и 10× сокращения памяти
остаются целями: генерация правил их не доказывает. Сопоставимые замеры
e2e фиксируют операции, входы, режим сборки, время и пиковую память.

## 7. Условия приёмки

Объект завершён, когда перенесены все свойства и зависимости в согласованных
границах, декларация компилируется, оба направления и аномалии проверены,
сборка с файлами и вложенными объектами работает, каждому старому договору
соответствует проверка, а свидетельства записаны в реестр и чеклист.

Первый результат работы — полный отчёт о конструкциях, зависимостях и тестах.
Он не изменяет рабочие правила и не устанавливает новые флажки готовности.


## Наследование поведения common при переносе

Ссылка на common наследует его декларацию отсутствия, пустых состояний
и сокращений. Переносчик не подставляет общий `yaml.missing = absent`,
если исходное правило не задаёт такого переопределения: это может отключить
вычисление значения по имени. Явный `noImplicitValueYAML` сохраняется.
Повторяющееся поведение не копируется из common в каждое свойство.

Тестовые договоры переносят входы контекста вместе с данными. Нельзя заменять
отсутствующий ownerName произвольной строкой или передавать уже преобразованное
имя вместо исходного: это меняет смысл сокращений. Для I8nText при доступном
имени отсутствующий YAML восстанавливает перевод по имени, а явная пустая
карта обозначает отсутствие свойства — согласно существующей декларации.

Если правило задаёт пустой XML по умолчанию, отсутствие смыслового значения
само по себе не удаляет эту оболочку. Для точного восстановления исходного
отсутствия общий механизм сохраняет удаление оболочки как аномалию.

## Уточнения проверки составных правил

Цели извлечения включают rules.ts и childRules.ts. Локальное правило проверяется
через структурный путь экспортированного владельца, без вызова getters.
Для реквизита выбирается правило его владельца из childRules.ts: общий
MetadataAttribute не заменяет проверку фактического реквизита документа.

Проверочные проекции используют существующие XML/YAML, сохраняют порядок,
повторы, теги и исходные пространства имён. Пропущенные свойства перечисляются
явно. Проекция не закрывает флажок полного объекта. Пустые значения по умолчанию
списков переносятся только для исследованного сочетания параметров; неизвестные
параметры блокируют перенос и не превращаются в аномалии пользовательских данных.

### Источники XML и неявные значения

Метка исходного файла (`tag`) является частью маршрута свойства. Проекции
группируются по метке и XML-корню: одинаковое имя корня не объединяет
свойства Metadata и Form. Чистые фрагменты преобразования могут разделяться
между маршрутами. Метка сохраняется в происхождении кандидата; она не является
тегом значения YAML и не требует частных условий в Rust.

Приёмка формы должна охватывать оба исходных файла и их общий YAML, затем
дочерние элементы и ресурсы. Проверка поддержанного подмножества каждого файла
сама по себе не закрывает приёмку полной формы.

Неявное значение только для YAML не является командой создавать XML-элемент.
Если отдельный XML-default не задан, такое значение записывается канонически
как отсутствие XML. Это выражается существующим условием `canonical: missing`.
Явное отличие исходного XML сохраняет общий механизм аномалий; автор правила
не перечисляет его отдельно. Сохранение явного default в YAML выражается
отсутствием `omitWhen`, без нового специального параметра языка.

### Общая матрица одинаковых профилей

Одинаковые изолированные договоры могут ссылаться на одну исполняемую матрицу.
Совпадение нужно проверять автоматически по типу и параметрам common,
представлениям, присутствию и типам используемых входов, разрешая локальные
имена импортов. Совпадение одного имени common недостаточно. Межполевые
ограничения нельзя удалять ради такого сравнения. Происхождение обоих правил
и связь с общей матрицей записываются в отчёте; изменение договора требует
пересмотра покрытия. Проверка композиции владельца остаётся отдельной.

Проверка отдельного поля сохраняет относящиеся к нему ограничения. Условие,
которое использует другое поле, требует совместной проекции; ограничение без
определённой границы не отбрасывается. Постоянные числовые границы переводятся
в обычные сравнения языка, без отдельного списка аномалий. Дробные и слишком
большие границы требуют разбора точной исходной записи, а не округления JS.

Префиксы в XML-путях связываются с проверенным источником URI. Неизвестные
связи остаются блокировками; непомеченные пространства имён владельца не
угадываются. Смена префикса при прежнем URI не меняет смысл XML.

### Статически доказанные постоянные значения

Временный переносчик может извлекать defaultValue из синхронной стрелочной
функции без аргументов, если тело — только литерал или список таких литералов.
Нужны происхождение и отдельная отметка доказанного извлечения: похожий объект
в исходном правиле не считается доказательством. Ссылки, вызовы и динамические
функции остаются блокировками. Полученное значение сопоставляется с проверенным
профилем common; функция не переносится в рабочую декларацию.

XML-default не обязательно означает удаление значения из YAML: явный договор
сохранения проверяется отдельно, включая обратный вход без поля. Текстовый
boolean-default YAML определяется по таблице common, без частных слов в
переносчике. Одинаковые пустые string-default и raw-default допускают объединение
только при доказанном тождественном преобразовании строки.

## Контроль универсальности

Принята [обязательная проверка](../../../.agents/declarative-review.md) перед
изменением общих механизмов, после законченного блока и на ревью перед слиянием.
Она проверяет как зависимости, так и скрытые ограничения сочетаний полей.
Найденный узкий путь composite.rs (коллекция и boolean-атрибут) требует
обобщения; отсутствие предметных имён само по себе не доказывает универсальность.
Проверка `pnpm test:architecture:rust` реализована и подключена к CI. Она проверяет граф пакетов, а не условия внутри функций.

## Смешанный порядок переноса

Рабочий блок соединяет массовое подключение общего механизма и полную
приёмку ближайшего к готовности владельца. Жёсткой квоты «один common — один
владелец» нет: последовательность определяется зависимостями.

1. Выбирать общий механизм по ожидаемому охвату, трудоёмкости, зависимостям
   и приближению конкретных владельцев к завершению. Включать в сравнение
   общие параметры правил, не только новые common. Число заблокированных
   вхождений — потенциальный охват, а не обещание их полной готовности.
2. Реализовать общий механизм, проверить его поведение и универсальность,
   автоматически пересоздать все затронутые кандидаты.
3. Повторно оценить оставшиеся задачи владельцев. Если до полной приёмки
   ближайшего владельца остаётся ограниченная работа на готовых механизмах,
   завершить её, проверить объект целиком и только затем поставить флажок.
4. Если нужен ещё один большой общий механизм, записать его как кандидата
   следующего блока и сравнить с остальными по тем же критериям. Частный
   обработчик или обход ради завершения владельца запрещён.

В конце блока фиксировать фактический охват, ближайшего владельца и точные
причины его незавершённости. Не переходить к следующему common автоматически,
не проверив возможность завершить владельца. Обновлять существующий реестр
и бинарный чеклист; дополнительных статусов готовности для пользователя нет.

## Пробные пакеты на готовых механизмах (2026-09-13)

Выбирать пакет по числу полностью завершаемых объектов и стоимости недостающих
работ. До ранжирования читать причины снятых флажков в чеклисте: готовая
декларация и большая частота использования сами по себе не означают дешёвую
полную приёмку. Число групп-потребителей не выдавать за число новых переносимых
свойств; уже работающие свойства повторно в выигрыш не включать.

Крупное расширение языка или общего выполнения выносится из пробного пакета;
остальные объекты продолжаются. Общие матрицы проверяются вместе с Clippy
сгенерированного кода до итогового полного прогона. Поведение common не
дублируется у каждого свойства владельца. Успешная генерация не даёт флажка.

В результате пакета записывать: принятые объекты, оставшиеся зависимости,
изменения общих механизмов, полные пересборки каталога и полные прогоны тестов.
Не обещать ускорение по расходу токенов или времени без сопоставимых измерений.

## Выборочная сборка проверок (2026-09-13)

Согласовано: ускорять цикл проверки выбранного пакета без второго генератора.
Существующий `tools/rules-migration/runtime` компилирует тем же Rust-компилятором
только декларации проверяемых случаев, их транзитивные imports и явно заданные
в манифесте источники индексов. Затем выполняет прежние независимые XML/YAML
ожидания, обратное преобразование и проверки валидации. Clippy проверяет именно
этот сгенерированный код. Неполная зависимость — ошибка выбора, не аномалия.

Выбор задаётся проверяемым JSON-пакетом с идентификаторами случаев. Неизвестный
или пустой выбор запрещён. Источники и выбранные сгенерированные декларации
проверяются на актуальность. Малый каталог хранится в target отдельно от
рабочих деклараций; неизменные файлы не перезаписываются, чтобы повторный запуск
использовал кэш. Изменение только XML/YAML-ожиданий не требует пересборки Rust.

Первое испытание: Document/DocumentJournal, 48 свойств в двух проекциях,
четыре независимых случая из существующих e2e. Это проверка уже полученных
кандидатов, не 48 новых подключений. После неё выполняется полный набор;
измеряются первый и повторный запуски отдельно. Приёмка полных владельцев и
флажки common не следуют из успешного испытания инструмента.

## Автоматическое подключение готовых деклараций

Реестр привязок владельцев задаёт декларацию, фрагмент, соответствия входов
и идентификаторы индексов. Проверяется реальный compose владельца независимо
от имён его импортов. Отсутствующее, повторное или отличающееся подключение
блокирует проверку. Внешние XML сравниваются по пути и содержимому после
экспорта с новым контекстом без исходных документов; количество файлов само
по себе недостаточно. Уже существующие подключения не считаются новыми.

Согласовано 13 сентября: временный инструмент переноса использует единый
реестр соответствий старых правил готовым декларациям. Запись проверяет весь
профиль параметров и сохраняет внешние файлы, ресурсы, входы и зависимости.
Знание старых построителей остаётся в инструменте миграции, не в Rust-оркестраторе.
Первый пакет — Help и AdditionalIndexes для документа и журнала документов.

Для каждого свойства отчёт различает созданного кандидата, готовую декларацию
с ещё не подключённым контекстом и точную причину блокировки. Наличие common
не доказывает готовность владельца. Неизвестные параметры не отбрасываются.
Автоматизация формирует проверяемые изменения; ожидания берутся из независимых
существующих XML/YAML, а не вычисляются из новой декларации. Контекст, индексы
и внешние ресурсы проверяются перед включением в рабочую сборку.

Число новых подключений показывается отдельно от числа повторно проверенных
свойств. Машинный отчёт служит основой сводки; флажок объекта ставится только
после полной приёмки. Подготовка кандидата флажок не меняет.

### Совпадающие пути внешнего документа

Точный профиль миграции может явно содержать одновременно filePath и xmlPath,
если старый код выбирает xmlPath и обе записи равны. Это проверенное
соответствие параметров, не разрешение игнорировать любой xmlPath. Вычисляемые
и отличающиеся пути остаются блокировками до переноса их договора. Для Help
подтверждены два профиля Ext/Help.xml с разным присутствием отключённых
fromXML/toXML; рабочий XML/YAML-договор задаёт готовый fragment.help.

### Соединение с основной декларацией

Подключение внешнего фрагмента к проекции основных свойств сохраняет её
состав, порядок, независимые ожидания и все индексы. Входы внешнего фрагмента
получают отдельные имена; конфликт импортов или входов блокирует сборку.
Составной кандидат проверяется с отсутствующим и присутствующим внешним
документом. Комбинирование независимых e2e-примеров обозначается явно и не
считается доказательством полного преобразования исходного владельца.

### Каталог владельца и относительный путь документа

Вычисляемый префикс имени владельца сохраняется в договоре размещения:
`sourceRoot: [{input: name}]`; полный путь исходного TS также сохраняется
в `xmlSourcePath`. Внутренний фрагмент по-прежнему описывает Ext/Help.xml
относительно source_root групповой операции. Переход от каталога коллекции
к каталогу владельца выполняется один раз на границе сборки, не в common.
Наличие соответствия не отменяет проверки этой привязки для полного владельца.
Распознавание функции допускается по проверенному ограниченному AST без
исполнения кода. Произвольные функции не сводятся к этому шаблону.

### Фиксированные привязки файловых сборок

Реестр подключения допускает `fixedBindings` для декларативных выражений,
которые полностью получены из старого правила. Проверяются три стороны:
старое свойство, принятый профиль и фактическая композиция рабочей сборки.
Вход не может одновременно быть постоянным и переданным владельцем.
При нескольких применениях одного фрагмента выбирается ровно одно точное
соответствие; отсутствие и повтор соответствия останавливают приёмку.

Файловая сборка может быть самостоятельной (`kind: resources`). Она не
подменяет незавершённый основной документ объекта и не засчитывается как
полный владелец. Проверяется общий файловый механизм и реальная привязка
каждого маршрута, без копирования общей матрицы тестов на все свойства.


## Ускорение сборки и проверка идентичности вложенных объектов

После реализации общих зависимостей автоматический перенос охватывает целую
декларацию объекта: свойства, общие фрагменты, дочерние коллекции и ресурсы.
Неизвестная конструкция остаётся явной блокировкой. Следующий пакет выбирается
по числу полностью завершаемых объектов и разблокируемых свойств. Проверка
полноты и подключения выполняется автоматически; ручная проверка требуется
для новых механизмов и исключений. Проверки одинаковых свойств не размножаются.

Идентичность вложенного объекта включает компонент, идентичность владельца,
вид и имя. Отдельно расположенные объекты получают владельца из объявленной
топологии. Собственный UUID, соответствие объекту основы, присутствие XML-ссылки
на основу и режим её проверки — отдельные сведения. Восстановимый UUID не
становится обычным полем YAML; наблюдаемые состояния отсутствия ссылки и
Notify сохраняются существующими смысловыми формами YAML. Их описывает
декларация, а не условие по имени EnumValue в общем механизме.

Инвентаризация e2e является независимым источником случаев, но сама по себе
не означает реализации или приёмки. Перед массовым подключением необходимы
проверки элемента, коллекции владельца и сохранения состояний расширения.


### Источник связи коллекции с элементом

Генератор объединяет свойство rules.ts с регистрацией типа коллекции.
Сначала учитывается itemRule конкретного свойства, затем общее правило
регистрации. Ссылка сохраняет исходное объявление, включая импортированные
алиасы; совпадение формы двух правил не заменяет разрешение ссылки.
Семейство регистраций из статического массива разбирается программно.
Функции проекта при этом не запускаются.

Граф хранит XML-путь, YAML-имя, ключ элемента и объявленные сведения владельца.
Неизвестные выражения и переопределения, несколько регистраций одного типа
и неразрешённые правила остаются явными блокировками. Готовность графа не
означает готовность исполняемой декларации либо полноту семантики регистрации.
Ручная привязка каждой коллекции исключается из обычного процесса переноса.


Выпуск коллекции использует только полное поддержанное правило элемента.
Он сохраняет порядок полей и явные параметры, создаёт элемент, коллекцию
и свойство владельца одной операцией. Неперенесённые свойства, особые режимы
регистрации, необъявленные пространства имён и неразрешённый контекст
блокируют выпуск, а не удаляются. Компиляция и проверка преобразования
генерируемого примера входят в повторяемую команду проверки инструмента.
Текущая реализация ограничена массивами записей без контекста элемента;
это ограничение реализации, а не целевого декларативного языка.

### Именованные коллекции в автоматическом выпуске

`keyField` из исходной регистрации переносится в `yaml: {kind: record-mapping,
key: ...}`. Сборщик проверяет наличие текстового поля ключа и использует полную
декларацию записи. Массив сохраняется массивом при `yamlAsArray: true`.
Неполная запись, неизвестные параметры, отсутствующий контекст или вклад
в индексы продолжают блокировать выпуск: словарь не обходит эти требования.

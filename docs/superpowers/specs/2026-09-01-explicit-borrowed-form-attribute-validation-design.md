# Явное заимствование реквизитов формы для путей расширения

## Контекст

Заимствованная форма расширения может использовать реквизиты основной формы в
двух разных режимах:

- неизменённые элементы основной формы продолжают видеть унаследованные
  реквизиты и пути основной конфигурации;
- новый или явно изменённый путь расширения работает только через реквизит
  формы, явно добавленный в `Реквизиты` рабочей формы расширения.

Например, основной реквизит формы часто называется `Объект`, но это не
зарезервированное имя. Тем же правилам подчиняются `Контрагент`, `Таблица`,
`Данные` и любой другой реквизит формы.

```yaml
Реквизиты:
  Контрагент:
    Тип: СправочникСсылка.Контрагенты

Элементы:
  ИНН:
    Вид: ПолеВвода
    ПутьКДанным: Контрагент.ИНН
```

Наличие `Контрагент` в `Реквизиты` является смысловым указанием на явное
заимствование, если одноимённый реквизит существует в соответствующей форме
основной конфигурации. Отдельное поле `ЗаимствованныеРеквизиты`, числовой XML
ID или частный признак для имени `Объект` не вводятся.

Исследованные выгрузки 1С и проект
[`cc-1c-skills`](https://github.com/Nikolay-Shirokov/cc-1c-skills) подтверждают
платформенный договор: для сохранения привязок расширения основной реквизит
должен присутствовать в `Attributes` внешней формы и `BaseForm`, а связанные
реквизиты объекта должны быть доступны в расширении. В NKDK этот договор
реализуется через смысловые индексы и resolver; регулярные выражения и
жёстко заданный `id="1000001"` не используются.

## Цели

1. Запретить новому или явно изменённому пути расширения использовать только
   унаследованный, не заимствованный реквизит формы.
2. Применять правило к любому имени реквизита формы и ко всем
   зарегистрированным свойствам-путям.
3. Проверять весь разрешаемый путь, включая сложные типы, табличные части,
   колонки и неявные пути элементов.
4. Восстанавливать платформенное представление заимствованного реквизита формы
   при синхронизации без зависимости от сохранённого XML ID.
5. При импорте сохранять некорректное исходное состояние точечным
   `!xml/invalid`, не исправляя его молча.
6. Сохранить действующее поведение неизменённых элементов основной формы.

## Не входит в работу

- автоматическое добавление реквизитов формы или metadata-зависимостей в YAML;
- частное правило для имени `Объект`;
- хранение числовых ID формы в YAML;
- изменение общей модели XML-аномалий;
- изменение правил видимости компонентов проекта;
- живой e2e-прогон с информационной базой 1С.

## Смысловая модель

### Происхождение корневого реквизита

Контекст пути формы различает два источника корневого реквизита:

- `working` — реквизит явно присутствует в `Реквизиты` рабочей YAML-формы;
- `inherited` — реквизит найден только в соответствующей форме `cf`.

При объединении индекса рабочей формы с резервным индексом `cf` происхождение
не теряется. Оно является частью результата разрешения пути, но не новым полем
пользовательского YAML.

Реквизит из `working` дополнительно классифицируется относительно `cf`:

- если в основной форме существует одноимённый реквизит, он явно
  заимствованный;
- иначе это собственный реквизит формы расширения.

Сравнение выполняется по смысловому адресу и имени в соответствующей форме, а
не по числовому XML ID.

### Какие пути требуют явного реквизита

Явный корневой реквизит из `working` обязателен для пути, созданного или
изменённого расширением:

- явно записанного свойства-пути собственного элемента;
- явно записанного свойства-пути заимствованного элемента;
- вычисляемого неявного пути собственного элемента или собственной колонки;
- любого другого зарегистрированного свойства типа `DataPath`, а не только
  первичного `ПутьКДанным`.

К проверяемым свойствам относятся, в частности, пути заголовка, подвала,
множественных значений и другие свойства, зарегистрированные правилами формы.
Список не дублируется в проверке вручную: обход использует реестр правил.

Неизменённый элемент основной формы, чей путь наследуется из `cf` и отсутствует
в рабочем YAML, продолжает использовать `inherited`-реквизит без ошибки. Это
позволяет открыть заимствованную форму без принудительного заимствования всех её
реквизитов.

### Разрешение сложного пути

Проверка выполняется существующим resolver посегментно. Для пути
`Данные.Товары.Количество` она:

1. находит корневой реквизит формы `Данные` и проверяет его происхождение;
2. по типу `Данные` находит владельца метаданных;
3. разрешает `Товары` как реквизит или табличную часть владельца;
4. разрешает `Количество` в полученном контексте;
5. останавливается на первом недоступном сегменте.

Неявные пути колонок сначала материализуются в эффективный путь через таблицу,
после чего проходят ту же проверку. Синтаксис индексированных путей, например
`Таблица[4].Реквизит`, обрабатывается действующим resolver, а не отдельным
разбором этой проверки.

### Видимость metadata-зависимостей

Явное заимствование корневого реквизита формы не раскрывает содержимое `cf`
целиком. Каждый следующий metadata-сегмент должен быть видим в компоненте
расширения по действующим правилам:

- собственный реквизит объекта расширения видим непосредственно;
- реквизит основной конфигурации должен быть представлен как заимствованный;
- при входе в заимствованную табличную часть проверяется её платформенно
  необходимый состав, включая колонки;
- ссылки на зависимые справочники, перечисления и определяемые типы проверяются
  существующим общим механизмом metadata-ссылок.

Форма не добавляет частных обходов строгой видимости компонента.

## Диагностика

Для отсутствующего явного корня формируется одна ошибка на конкретное
свойство-путь:

> Путь `Объект.ДатаАктуальности` использует реквизит формы `Объект`, который не
> добавлен в `Реквизиты` заимствованной формы.

Если корень присутствует, но недоступен следующий metadata-сегмент, формируется
ошибка первого недоступного сегмента:

> Путь `Контрагент.ИНН` обращается к реквизиту `ИНН`, который недоступен в
> компоненте расширения.

Обе ошибки для одного пути одновременно не выдаются. Диагностика указывает
файл формы и YAML-путь проверяемого свойства.

Собственный реквизит формы, отсутствующий в `cf`, не считается ошибкой
заимствования. Обычная проверка типа и внутренней связности пути продолжает
работать независимо.

## Импорт XML → YAML

Импорт отражает состав исходного XML и не исправляет его автоматически:

1. реквизит, явно присутствующий во внешнем `Attributes`, импортируется в
   `Реквизиты` рабочей формы;
2. отсутствующий реквизит не синтезируется из `cf`;
3. после построения YAML выполняется обычная проверка путей с информацией об их
   происхождении;
4. смысловая ошибка классифицируется действующим механизмом импортных решений;
5. ошибочное свойство-путь получает `!xml/invalid`.

```yaml
ПутьКДанным: !xml/invalid Объект.ДатаАктуальности
```

Если ошибочный путь был неявным и потому отсутствовал в компактном YAML,
импорт материализует его на границе диагностики и применяет тег к созданному
свойству. Благодаря этому пользователь видит исправляемую причину, а
контрольный экспорт сохраняет исходное некорректное состояние.

Каждое ошибочное зарегистрированное свойство-путь помечается отдельно. Сам
реквизит формы, metadata-объект или вся форма не переводятся в `!xml/raw`.
`!xml/raw` остаётся только для XML-структуры, которую невозможно однозначно
восстановить из смыслового YAML и индексов.

Корректно заимствованный реквизит и корректные зависимости импортируются без
аномалий.

## Синхронизация YAML → XML

При подготовке профиля восстановления XML синхронизатор классифицирует каждый
явный реквизит рабочей формы:

1. находит соответствующую форму в `cf`;
2. проверяет наличие одноимённого реквизита основной формы;
3. при совпадении выбирает платформенный вариант заимствованного реквизита;
4. при отсутствии совпадения выбирает вариант собственного реквизита формы.

Распределитель ID остаётся единственным владельцем числовых идентификаторов:

- использует допустимый ID из снимка, если он доступен;
- иначе назначает свободный ID пространства расширения;
- согласованно использует выбранный ID во внешней форме и `BaseForm`;
- не полагается на имя `Объект` и не фиксирует конкретное число `1000001`.

Результат не зависит от наличия прежнего снимка: пустой снимок не должен
превращать явно заимствованный реквизит в собственный или базовый.

## Архитектурные границы

- Общий `dataPath` resolver разрешает путь и возвращает происхождение корня,
  но не знает о политике заимствованных форм.
- Политика обязательного явного реквизита принадлежит concrete-модулю
  `clientApplicationForm`.
- Общие слои `validation`, `projectState`, `ruleRuntime` и
  `resourceTopology/core` не получают условий по имени `Объект`, папкам форм
  или конкретным metadata-типам.
- Обход свойств-путей выполняется через регистрации правил формы.
- Классификация импортных ошибок и применение `!xml/invalid` используют
  существующий общий конвейер без нового вида аномалии.
- Классификация XML-варианта и распределение ID используют существующий профиль
  восстановления и индекс формы.

Действующая `.agents/architecture.md` уже описывает эти направления
зависимостей и подпроцессы. Её изменение для этой работы не требуется.

## Проверки

### Проверка правил и интеграции

1. Произвольный корень `Контрагент` работает так же, как `Объект`.
2. Новый явный путь через отсутствующий в working-реквизит выдаёт ошибку
   явного заимствования.
3. Неявный путь собственного элемента выдаёт ту же ошибку и материализуется
   при импорте.
4. Неизменённый базовый элемент использует inherited-реквизит без ошибки.
5. Собственный реквизит формы не требует соответствия в `cf`.
6. При наличии корня недоступный metadata-сегмент выдаёт только ошибку этого
   сегмента.
7. Проверяются глубокие пути, табличные части, колонки, индексированные пути и
   дополнительные зарегистрированные свойства-пути.
8. Повторные проверки одного пути не создают полных дублей диагностик.
9. Импорт применяет `!xml/invalid` к явному ошибочному пути.
10. Импорт материализует и помечает ошибочный неявный путь.
11. Корректный импорт не создаёт `!xml/invalid` или `!xml/raw`.
12. Синхронизация без сохранённого ID назначает реквизиту формы ID расширения и
    одинаково использует его во внешней форме и `BaseForm`.

### Проверка существующих e2e-фикстур

`ОбщаяФорма.InputField` используется как положительный универсальный пример:

- заимствованный реквизит `Таблица` присутствует в рабочем YAML;
- пути `Таблица.Реквизит`, `Таблица[4].Реквизит` и пути множественных значений
  разрешаются;
- собственный `ТаблицаExt` не классифицируется как заимствованный;
- exact XML → YAML → XML round-trip остаётся зелёным.

Форма `ДокументВсеСвойства.ФормаДокумента` подтверждает допустимость
унаследованных базовых элементов без явно заимствованного `Объект`, а
`ФормаДокументаВсеСвойства` — положительный случай явно заимствованного
`Объект`.

Отрицательные варианты создаются в тесте как производные копии YAML и не
изменяют существующие XML-фикстуры — источник истины проекта.

После реализации выполняются целевые тесты, e2e round-trip без живой 1С,
`pnpm duplicates -- --base <commit>` и полный `pnpm test`. Живой прогон загрузки
в информационную базу остаётся отдельной последующей проверкой.

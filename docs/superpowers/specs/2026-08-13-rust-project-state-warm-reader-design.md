# Оптимизация прогретого Rust-reader ProjectState

## Цель

Устранить оставшиеся известные накладные расходы TypeScript-переходника и разделить холодное открытие Rust-reader от работы уже прогретого worker. Публичные интерфейсы `ProjectState`, формат снимка и двоичный протокол не меняются.

## Изменения read session

Для каждого запроса ключ кэша `componentPath + "\0" + canonicalTarget` вычисляется ровно один раз. Переходник хранит ключи текущей пачки в массиве, использует их для отбора новых целей и повторно использует при сборке результатов.

`TypedProjectStateReader` создаётся один раз на read session. Этот экземпляр передаётся в резервный TypeScript `ProjectStateQueryPort` и используется при восстановлении подробностей числового ответа Rust. Так оба пути разделяют ленивые индексы и кэши чтения фактов.

Для TDD внутренние фабрики reader и функция построения ключа доступны только через необязательные зависимости `openRustProjectStateReadSession`. Публичный рабочий вызов не меняется.

## Холодное и прогретое измерение

Один набор worker выполняет два одинаковых раунда:

1. холодный — включает первую загрузку native-дополнения и первое открытие reader;
2. прогретый — выполняется теми же worker, но с новым read token и пустым кэшем запросов.

Каждый раунд создаёт новую read session, поэтому прогретый результат не использует результаты поиска холодного раунда. Повторно используются только процесс worker, загруженные модули и native-дополнение.

Главный процесс измеряет оба раунда отдельно. Результаты JSON содержат `coldLookupMs` и `warmLookupMs`; общий `elapsedMs` остаётся служебной длительностью всего процесса и больше не используется для сравнения скорости запросов.

## Проверка и решение

Тесты фиксируют:

- один вызов функции построения ключа на каждый входной запрос;
- один `TypedProjectStateReader` на Rust read session и передачу того же экземпляра в резервный порт;
- два последовательных раунда на одном пуле и отдельные времена холодного и прогретого поиска;
- равенство found/missing между раундами.

После реализации выполняются пять изолированных прогонов TypeScript и Rust для повторяющейся и уникальной нагрузки. Для решения о следующем слое сравниваются медианы `warmLookupMs` и RSS. Холодное время сообщается отдельно как стоимость запуска.

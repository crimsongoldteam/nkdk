# Разбор схемных ошибок validation форм

## Цель

Сократить массовые ошибки validation группы (Б): `Expected union value` и `Unexpected property` в `Форма.yaml`. Первый шаг должен вернуть корректное распознавание дерева элементов формы, не ослабляя проверку всех форм через `additionalProperties: true`.

## Контекст

Полный запуск validation на `/home/nikita/git/temp-yaml` нашел `38831 error` и `36173 warning`. В группе (Б) основные сообщения:

- `Unexpected property`: `14104`
- `Expected union value`: `11647`

Для `Expected union value` самые частые значения поля `Вид`: `Группа`, `ТаблицаФормы`, `Страницы`, `КоманднаяПанель`. Эти виды уже есть в `CollectableElementTypeToYAML`, поэтому проблема похожа не на неизвестные элементы, а на построение JSON Schema для контейнеров `Элементы`.

Для `Unexpected property` самые частые ключи: `Автозаполнение`, `УсловноеОформление`, `Элементы`, `Группа`, `Таблица`. Часть этих ошибок может исчезнуть после корректного выбора схемы элемента по `Вид`; оставшийся хвост надо разбирать как неполноту правил отдельных элементов.

## Решение

### Шаг 1. Восстановить generic-схему дерева элементов

Добавить focused-тест для `validateProject` или `validateFile`, который проверяет минимальную форму с вложенными элементами:

- верхний уровень `Элементы`
- `Группа`
- вложенная `ТаблицаФормы`
- вложенные `Страницы`
- `КоманднаяПанель`

Тест должен падать на текущей проблеме `Expected union value` и проходить после исправления.

Проверить построение schema в `exportChildItemsToJSONSchema`: generic-схема `GroupChildItems` должна принимать все допустимые дочерние элементы группы и рекурсивно описывать вложенные `Элементы` через корректный тип контейнера. Для разных контейнеров должны сохраняться разные наборы допустимых детей:

- `GroupChildItems`: обычные элементы формы, включая `Группа`, `ТаблицаФормы`, `Страницы`, `КоманднаяПанель`.
- `TableChildItems`: колонки таблицы.
- `PagesChildItems`: страницы.
- `CommandBarChildItems`: кнопки и группы командной панели.

### Шаг 2. Разобрать оставшиеся `Unexpected property`

После исправления `Expected union value` повторно запустить validation на `/home/nikita/git/temp-yaml` и пересчитать частотность `Unexpected property`. Только оставшиеся ключи считать реальной неполнотой правил/схем, например `Автозаполнение`, `УсловноеОформление`, `ДополнительныеКолонки`.

## Границы

- Не меняем XML-фикстуры.
- Не меняем YAML-формат форм.
- Не отключаем `additionalProperties: false` для форм целиком.
- Не трогаем группу (А) с предупреждениями динамических списков.
- Не трогаем группу (В) с семантической проверкой `ПутьКДанным`.

## Проверка

- Точечные тесты validation для схемы `Элементы`.
- `pnpm --filter @nakidka/core exec vitest run metadata/validation`.
- Контрольный запуск validation на `/home/nikita/git/temp-yaml` с пересчетом групп (Б).
- Перед закрытием работы полный `pnpm test`.

### Случай 1. Убрать Вариантность Из YAML-Ключей

Ранее эта спека запретила принимать и выгружать пустой синтаксис:

```yaml
ЗапретитьИспользование: {}
```

Это решение остаётся в силе. Новый слой ошибок другой: YAML содержит непустые словари
ролей, например:

```yaml
ЗапретитьРедактирование:
  Role.ДобавлениеИзменениеПерсУчета: Истина
```

Такую форму не нужно чинить добавлением `yamlDeny` в JSON Schema. Проблема глубже:
вариант значения сейчас закодирован в имени YAML-ключа. Для `UserVisible` это пары
`Разрешить*` / `Запретить*`, для `FormattedI8nText` такая же идея выражена парой
`Заголовок` / `ФорматированныйЗаголовок` через `yamlFormatted`.

Новый контракт: имя YAML-ключа должно обозначать свойство, а вариант должен жить
внутри значения. Это соответствует остальным YAML-объектам, где тип/стиль/режим
задаётся значением, а не сменой имени поля.

#### Решение

Для `UserVisible` заменить пары ключей на один базовый ключ:

- `РазрешитьИспользование` / `ЗапретитьИспользование` -> `Использование`;
- `РазрешитьПросмотр` / `ЗапретитьПросмотр` -> `Просмотр`;
- `РазрешитьРедактирование` / `ЗапретитьРедактирование` -> `Редактирование`.

Значение свойства:

```yaml
Использование:
  Разрешить: Ложь
  Роли:
    Role.ПолныеПрава: Истина
```

Правила:

- `Разрешить` можно писать только как `Ложь`;
- если `Разрешить` отсутствует, считается `Истина`;
- `Роли` содержит детализацию по ролям и хранит фактические значения ролей;
- если нет детализации по ролям и `Разрешить` не `Ложь`, поле не выгружается;
- пустые карты по-прежнему не считаются валидным полезным YAML.

Когда `Разрешить = Истина`, явное поле `Разрешить` не пишется:

```yaml
Использование:
  Роли:
    Role.ОграниченнаяРоль: Ложь
```

Если детализации по ролям нет, `Использование` полностью отсутствует.

Для `FormattedI8nText` убрать вариантность из имени ключа:

```yaml
Заголовок:
  Стиль: Форматированный
  Значение:
    ru: "<b>Заголовок</>"
```

Если `Стиль` отсутствует, значение считается обычной строкой. Обычный компактный
формат остаётся допустимым:

```yaml
Заголовок:
  ru: Заголовок
```

Старые специальные поля правил `yamlDeny` и `yamlFormatted` не развивать как
механизм JSON Schema. Их нужно заменить общим value-based контрактом для этих типов.

#### Фактическое Состояние Перед Реализацией

Код пока соответствует старому контракту:

- `UserVisibleKeysYAML`, `UserViewKeysYAML`, `UserEditKeysYAML` задают пары
  `Разрешить*` / `Запретить*`;
- `exportUserVisibleToYAML` выгружает `rule.yaml` при `common: true` и
  `rule.yamlDeny` при `common: false`;
- `importUserVisibleFromYAML` читает `rule.yaml`, а deny-ключ ищет отдельно через
  `yaml[rule.yamlDeny]`;
- `exportPropertiesToJSONSchema` добавляет только `rule.yaml`, поэтому непустые
  `Запретить*` становятся `Unexpected property`;
- фикстуры форм и ручной `commandInterface` всё ещё используют старые ключи.

Реализация должна перевести именно контракт `UserVisible`, а не расширять schema
под старый `yamlDeny`:

- правила форм получают базовые ключи `Использование`, `Просмотр`, `Редактирование`;
- `UserVisible` экспортирует новый объект `{ Разрешить?: Ложь, Роли: {...} }`;
- импорт принимает только новый формат;
- `yamlDeny` удаляется из механизма `UserVisible`: его не используют правила,
  import/export, YAML-типы и JSON Schema;
- старые `Разрешить*` / `Запретить*` не поддерживаются как совместимость чтения и
  считаются невалидным YAML после перехода;
- новая выгрузка и перегенерированный `/home/nikita/git/temp-yaml` не должны
  содержать `РазрешитьИспользование`, `ЗапретитьИспользование`,
  `РазрешитьПросмотр`, `ЗапретитьПросмотр`, `РазрешитьРедактирование`,
  `ЗапретитьРедактирование`.

#### Проверка

- focused YAML/schema-тесты для `UserVisible`:
  - `Использование: { Роли: { Role.X: Ложь } }` проходит и импортируется как
    `common: true`;
  - `Использование: { Разрешить: Ложь, Роли: { Role.X: Истина } }` проходит и
    импортируется как `common: false`;
  - `Использование: { Разрешить: Истина }` не принимается;
  - `Использование: {}` не принимается schema и не выгружается, если возникло из
    модели без детализации.
- focused YAML/schema-тесты для `FormattedI8nText`:
  - обычный компактный `Заголовок: { ru: Заголовок }` проходит;
  - форматированный `Заголовок: { Стиль: Форматированный, Значение: { ru: ... } }`
    проходит;
  - вариантный ключ `ФорматированныйЗаголовок` больше не считается целевым форматом.
- пересчёт `Unexpected property` должен снять подгруппу непустых `Запретить*` после
  повторной выгрузки YAML в новом формате.

### Случай 2. `Оформление` И `SettingsParameterValue`

Самая большая подгруппа `Unexpected property` находится внутри `Оформление`:

```yaml
Оформление:
  ЦветТекста: ЭлементСтиля.ТекстЗапрещеннойЯчейкиЦвет
  ЦветФона: ЦветФонаПодсказки
  Шрифт:
    ...
  Видимость: Ложь
```

Поля уже описаны в `AppearanceFieldsRules`: `ЦветФона`, `ЦветТекста`, `Шрифт`,
`ГоризонтальноеПоложение`, `Формат`, `Текст`, `Видимость`, `Доступность`,
`ТолькоПросмотр`, `Отображать` и другие. Причина не в отсутствии этих ключей.
Причина ниже: тип `SettingsParameterValue` имеет import/export YAML/XML, но не имеет
`exportToJSONSchema`. Из-за этого схема `AppearanceFields` строится неполной, и
реальные параметры оформления становятся `Unexpected property`.

#### Решение

Добавить `exportToJSONSchema` в два слоя: `MetadataDcsMetadataValue` и
`SettingsParameterValue`.

`MetadataDcsMetadataValue` отвечает только за YAML-схему значения по `valueType`.
Он должен переиспользовать уже существующие схемы базовых типов:

- `Color` -> фактическая YAML-схема цвета. Текущую `ColorJSONSchema` нужно
  синхронизировать с `importColorFromYAML`/`exportColorToYAML`: принять style,
  windows и web-цвета, `ЭлементСтиля.<Имя>`, абсолютный `#RRGGBB` и raw-ref;
- `Font` -> `FontJSONSchema`;
- `Field` -> `MetadataFieldJSONSchema` плюс явные typed-значения, которые уже
  поддерживает YAML-цикл;
- `DesignTimeValue` -> `I8nTextJSONSchema`, `MetadataValueJSONSchema` и явные
  `{ Тип: Поле | ЗначениеВремениПроектирования, Значение: string }`;
- `Primitive` -> `MetadataValueJSONSchema` и явное DCS-системное перечисление
  `{ Тип: СистемноеПеречисление, Имя, Значение }`;
- `Parameter` -> `ChoiceParametersJSONSchema`;
- `TypeLink` -> `TypeLinkJSONSchema`;
- `ChoiceParameterLinks` -> `ChoiceParameterLinksJSONSchema`;
- `SystemEnumeration` -> текущий `exportSystemEnumerationToJSONSchema` по
  `rule.typeSE`.

`SettingsParameterValue` поверх этого значения строит целевой YAML-контракт:

```yaml
Оформление:
  ЦветТекста: "#1C55AE"
  Видимость: Ложь
  ГоризонтальноеПоложение: Лево
  Шрифт:
    Вид: ШрифтТекста
```

или полную форму:

```yaml
Оформление:
  ЦветФона:
    Использовать: Ложь
    Значение: ЦветФонаПодсказки
    РежимОтображения: Обычный
    ИдентификаторПользовательскойНастройки: BackColor
    ПредставлениеПользовательскойНастройки:
      ru: Цвет фона
    Элементы:
      - Значение: "#FFFFFF"
```

Правила полной формы:

- разрешённые ключи: `Использовать`, `Значение`, `РежимОтображения`,
  `ИдентификаторПользовательскойНастройки`,
  `ПредставлениеПользовательскойНастройки`, `Элементы`;
- `Использовать` может быть только `Ложь`; `Истина` не пишется и не считается
  целевым YAML;
- `Параметр` не входит в целевую схему: имя параметра уже задано внешним
  YAML-ключом, например `ЦветТекста`;
- лишние ключи в полной форме не принимаются;
- `Значение` валидируется той же схемой, что и компактное значение; для типов,
  где YAML-цикл выгружает несколько значений, допускается массив этих значений;
- `Элементы` содержит массив таких же `SettingsParameterValue`-значений
  рекурсивно;
- пустой объект не является полезным целевым YAML и не должен приниматься.

Схема описывает формат выгрузки YAML, а не все исторически принимаемые послабления
импорта. Поэтому обёртка вида `{ ИмяПараметра: ... }`, которую импорт умеет
разобрать в отдельных сценариях, не добавляется в `SettingsParameterValue`
schema.

#### Проверка

- focused schema-тесты для `AppearanceFields`:
  - `ЦветТекста: ЭлементСтиля.ТекстЗапрещеннойЯчейкиЦвет`;
  - `ЦветФона: ЦветФонаПодсказки`;
  - `ЦветТекста: "#1C55AE"`;
  - `Видимость: Ложь`;
  - `Формат: '"ЧДЦ=1"'`;
  - `Шрифт` в полном YAML-виде;
- focused schema-тесты для `SettingsParameterValue`:
  - компактная форма проходит;
  - полная форма с `Использовать: Ложь`, `Значение`, пользовательскими настройками
    и `Элементы` проходит;
  - `Использовать: Истина` не проходит;
  - `Параметр` и другие лишние ключи не проходят;
  - пустой объект не проходит;
- validation на реальном `/home/nikita/git/temp-yaml` должен снять основной пласт
  `Оформление / SettingsParameterValue schema`.

### Случай 3. `ДополнительныеКолонки`

YAML для реквизита формы использует словарь таблиц, а внутри каждой таблицы словарь
дополнительных колонок:

```yaml
Реквизиты:
  Объект:
    ДополнительныеКолонки:
      Объект.Товары:
        Артикул:
          Тип: Строка
```

Import/export для `ДополнительныеКолонки` уже существуют как отдельная логика
`FormAttributeAdditionalColumns`. Ошибка validation возникает потому, что JSON Schema
для этого типа не зарегистрирована. Поэтому схема реквизита формы либо не знает
вложенный словарь таблиц, либо валидирует его не как `Record<table, Record<column,
FormAttributeColumn>>`.

#### Решение

Добавить `exportToJSONSchema` для `FormAttributeAdditionalColumns`:

- внешний уровень: `Type.Record(Type.String(), ...)`, где ключ — путь таблицы
  (`Объект.Товары`, `НаборЗаписей`, `СвойстваПоказателей.ТаблицаЗначений`);
- внутренний уровень: `Type.Record(Type.String(), FormAttributeColumnSchema)`, где
  ключ — имя дополнительной колонки;
- `FormAttributeColumnSchema` строится через существующий `FormAttributeColumnRules`;
- пустой объект таблицы допустим только если текущий import/export реально сохраняет
  такую форму. Если пустая таблица не несёт информации, предпочтительно не выгружать
  её, а не расширять schema под шум.

#### Проверка

- focused schema-тест: `ДополнительныеКолонки: { Объект.Товары: { Артикул: { Тип:
  Строка } } }` проходит;
- focused schema-тест для пустой таблицы фиксирует выбранное поведение;
- validation на `/home/nikita/git/temp-yaml` должен снять подгруппу
  `ДополнительныеКолонки`.

### Следующие Случаи После Первых Трёх

После случаев 1-3 нужно повторно пересчитать `Unexpected property`. Только оставшиеся
ошибки считать следующим слоем. Предварительные кандидаты:

- `Команды / Группа` в `Свойства.yaml`: вероятно, схема команд прикладного объекта
  не применяет `MetadataCommandRules` или применяет неполный тип;
- `Команды / Таблица` в формах: поле есть в `FormCommandRules`, но нужно проверить
  schema для типа `AssociatedTable`;
- `Значение` реквизитов формы: отдельно разобраться, является ли это допустимым
  runtime/default-значением или лишней выгрузкой.

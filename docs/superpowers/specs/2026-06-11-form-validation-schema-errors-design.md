# Разбор схемных ошибок validation форм

## Цель

Сократить массовые ошибки validation группы (Б): `Expected union value` и `Unexpected property` в `Форма.yaml`. Первый шаг должен вернуть корректное распознавание дерева элементов формы, не ослабляя проверку всех форм через `additionalProperties: true`.

## Контекст

Полный запуск validation на `/home/nikita/git/temp-yaml` нашел `38831 error` и `36173 warning`. В группе (Б) основные сообщения:

- `Unexpected property`: `14104`
- `Expected union value`: `11647`

Для `Expected union value` самые частые значения поля `Вид`: `Группа`, `ТаблицаФормы`, `Страницы`, `КоманднаяПанель`. Эти виды уже есть в `CollectableElementTypeToYAML`, поэтому проблема похожа не на неизвестные элементы, а на построение JSON Schema для контейнеров `Элементы`.

Для `Unexpected property` самые частые ключи: `Автозаполнение`, `УсловноеОформление`, `Элементы`, `Группа`, `Таблица`. Часть этих ошибок может исчезнуть после корректного выбора схемы элемента по `Вид`; оставшийся хвост надо разбирать как неполноту правил отдельных элементов.

## Решение

### Шаг 1. Восстановить generic-схему дерева элементов

Добавить focused-тест для `validateProject` или `validateFile`, который проверяет минимальную форму с вложенными элементами:

- верхний уровень `Элементы`
- `Группа`
- вложенная `ТаблицаФормы`
- вложенные `Страницы`
- `КоманднаяПанель`

Тест должен падать на текущей проблеме `Expected union value` и проходить после исправления.

Проверить построение schema в `exportChildItemsToJSONSchema`: generic-схема `GroupChildItems` должна принимать все допустимые дочерние элементы группы и рекурсивно описывать вложенные `Элементы` через корректный тип контейнера. Для разных контейнеров должны сохраняться разные наборы допустимых детей:

- `GroupChildItems`: обычные элементы формы, включая `Группа`, `ТаблицаФормы`, `Страницы`, `КоманднаяПанель`.
- `TableChildItems`: колонки таблицы.
- `PagesChildItems`: страницы.
- `CommandBarChildItems`: кнопки и группы командной панели.

### Шаг 2. Разобрать оставшиеся `Unexpected property`

После исправления `Expected union value` повторно запустить validation на `/home/nikita/git/temp-yaml` и пересчитать частотность `Unexpected property`. Только оставшиеся ключи считать реальной неполнотой правил/схем, например `Автозаполнение`, `УсловноеОформление`, `ДополнительныеКолонки`.

## Границы

- Не меняем XML-фикстуры.
- Не меняем YAML-формат форм.
- Не отключаем `additionalProperties: false` для форм целиком.
- Не трогаем группу (А) с предупреждениями динамических списков.
- Не трогаем группу (В) с семантической проверкой `ПутьКДанным`.

## Проверка

- Точечные тесты validation для схемы `Элементы`.
- `pnpm --filter @nakidka/core exec vitest run metadata/validation`.
- Контрольный запуск validation на `/home/nikita/git/temp-yaml` с пересчетом групп (Б).
- Перед закрытием работы полный `pnpm test`.

Разбирать эти причины нужно по порядку, не ослабляя strict validation через
`additionalProperties: true`.

### Случай 1. Непустые `yamlDeny`-Права

Ранее эта спека запретила принимать и выгружать пустой синтаксис:

```yaml
ЗапретитьИспользование: {}
```

Это решение остаётся в силе. Новый слой ошибок другой: YAML содержит непустые словари
ролей, например:

```yaml
ЗапретитьРедактирование:
  Role.ДобавлениеИзменениеПерсУчета: Истина
```

Такая форма допустима, потому что `UserVisible` уже поддерживает пары
`yaml` / `yamlDeny` на import/export. Проблема в генераторе JSON Schema:
`exportPropertiesToJSONSchema` добавляет в схему только основной `yaml`-ключ
(`РазрешитьИспользование`, `РазрешитьПросмотр`, `РазрешитьРедактирование`) и не
добавляет парный `yamlDeny`-ключ.

#### Решение

Расширить общий генератор свойств JSON Schema:

- если у свойства есть `yamlDeny`, добавить в результат schema ещё один optional-ключ;
- использовать для `yamlDeny` ту же схему значения, что и для основного `yaml`;
- не менять import/export `UserVisible`;
- не принимать пустые карты как специальный случай: пустой `ЗапретитьИспользование: {}`
  по-прежнему считается ошибкой выгрузки, а не валидным YAML.

#### Проверка

- focused schema-тест: rule с `yaml` и `yamlDeny` принимает оба непустых ключа;
- focused validation-тест: `ЗапретитьИспользование: { Role.X: Истина }` проходит,
  а `ЗапретитьИспользование: {}` остаётся запрещённым;
- пересчёт `Unexpected property` должен снять подгруппу непустых `Запретить*`.

### Случай 2. `Оформление` И `SettingsParameterValue`

Самая большая подгруппа `Unexpected property` находится внутри `Оформление`:

```yaml
Оформление:
  ЦветТекста: ЭлементСтиля.ТекстЗапрещеннойЯчейкиЦвет
  ЦветФона: ЦветФонаПодсказки
  Шрифт:
    ...
  Видимость: Ложь
```

Поля уже описаны в `AppearanceFieldsRules`: `ЦветФона`, `ЦветТекста`, `Шрифт`,
`ГоризонтальноеПоложение`, `Формат`, `Текст`, `Видимость`, `Доступность`,
`ТолькоПросмотр`, `Отображать` и другие. Причина не в отсутствии этих ключей.
Причина ниже: тип `SettingsParameterValue` имеет import/export YAML/XML, но не имеет
`exportToJSONSchema`. Из-за этого схема `AppearanceFields` строится неполной, и
реальные параметры оформления становятся `Unexpected property`.

#### Решение

Добавить `exportToJSONSchema` для `SettingsParameterValue`.

Схема должна описывать текущий YAML-формат, а не модель:

- компактное значение параметра: строка, число, `Истина`/`Ложь`, ссылка, цвет, шрифт
  или другое значение, допустимое соответствующим `valueType`;
- полный объект параметра с ключами `Использовать`, `Значение`,
  `РежимОтображения`, `ИдентификаторПользовательскойНастройки`,
  `ПредставлениеПользовательскойНастройки`, `Элементы`;
- `Значение` внутри полного объекта валидируется той же схемой, что и компактное
  значение;
- `Элементы` рекурсивно содержит такие же `SettingsParameterValue`-элементы.

Если точное schema-представление для отдельных `valueType` уже есть у
`MetadataDcsMetadataValue`, использовать его. Если общего экспортера для
`MetadataDcsMetadataValue` нет, первый шаг должен добавить его минимально для
используемых здесь `valueType`: `Primitive`, `DesignTimeValue`, `Color`, `Font`,
`SystemEnumeration`, `Field`.

#### Проверка

- focused schema-тесты для `AppearanceFields`:
  - `ЦветТекста: ЭлементСтиля.ТекстЗапрещеннойЯчейкиЦвет`;
  - `Видимость: Ложь`;
  - `Формат: '"ЧДЦ=1"'`;
  - `Шрифт` в полном YAML-виде;
- validation на реальном `/home/nikita/git/temp-yaml` должен снять основной пласт
  `Оформление / SettingsParameterValue schema`.

### Случай 3. `ДополнительныеКолонки`

YAML для реквизита формы использует словарь таблиц, а внутри каждой таблицы словарь
дополнительных колонок:

```yaml
Реквизиты:
  Объект:
    ДополнительныеКолонки:
      Объект.Товары:
        Артикул:
          Тип: Строка
```

Import/export для `ДополнительныеКолонки` уже существуют как отдельная логика
`FormAttributeAdditionalColumns`. Ошибка validation возникает потому, что JSON Schema
для этого типа не зарегистрирована. Поэтому схема реквизита формы либо не знает
вложенный словарь таблиц, либо валидирует его не как `Record<table, Record<column,
FormAttributeColumn>>`.

#### Решение

Добавить `exportToJSONSchema` для `FormAttributeAdditionalColumns`:

- внешний уровень: `Type.Record(Type.String(), ...)`, где ключ — путь таблицы
  (`Объект.Товары`, `НаборЗаписей`, `СвойстваПоказателей.ТаблицаЗначений`);
- внутренний уровень: `Type.Record(Type.String(), FormAttributeColumnSchema)`, где
  ключ — имя дополнительной колонки;
- `FormAttributeColumnSchema` строится через существующий `FormAttributeColumnRules`;
- пустой объект таблицы допустим только если текущий import/export реально сохраняет
  такую форму. Если пустая таблица не несёт информации, предпочтительно не выгружать
  её, а не расширять schema под шум.

#### Проверка

- focused schema-тест: `ДополнительныеКолонки: { Объект.Товары: { Артикул: { Тип:
  Строка } } }` проходит;
- focused schema-тест для пустой таблицы фиксирует выбранное поведение;
- validation на `/home/nikita/git/temp-yaml` должен снять подгруппу
  `ДополнительныеКолонки`.

### Следующие Случаи После Первых Трёх

После случаев 1-3 нужно повторно пересчитать `Unexpected property`. Только оставшиеся
ошибки считать следующим слоем. Предварительные кандидаты:

- `Команды / Группа` в `Свойства.yaml`: вероятно, схема команд прикладного объекта
  не применяет `MetadataCommandRules` или применяет неполный тип;
- `Команды / Таблица` в формах: поле есть в `FormCommandRules`, но нужно проверить
  schema для типа `AssociatedTable`;
- `Значение` реквизитов формы: отдельно разобраться, является ли это допустимым
  runtime/default-значением или лишней выгрузкой.

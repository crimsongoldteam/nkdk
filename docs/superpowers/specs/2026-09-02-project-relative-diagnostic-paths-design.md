# Относительные пути диагностик проекта

## Контекст

`configuration-index.lmdb` уже переносим между каталогами: ключи таблиц
`hashes`, `blocks` и `pending*` являются нормализованными путями относительно
компонента. Двоичный `project-state.bin` также хранит таблицу файлов по путям
относительно корня NKDK-проекта и не сохраняет `filePath` внутри локальной
диагностики.

Нарушение возникает позже, при проверке связей проекта. Обработчики
структурированных документов получают относительный `projectPath`, но часть из
них формирует `Diagnostic.filePath` через `join(projectDir, projectPath)`.
Например, проверка заимствованной формы возвращает абсолютный путь. MCP
принимает от Core только путь проекта и поэтому завершает всю validation
сообщением `Core вернул путь диагностики вне NKDK-проекта` вместо предметной
ошибки формы.

## Цель

Закрепить единый договор: все сохраняемые пути проекта и все пути в
диагностиках между слоями NKDK являются нормализованными путями относительно
корня проекта. Абсолютные пути создаются только на границе файловой системы и
не попадают в снимки или результаты Core.

## Не входит в задачу

- изменение двоичного формата или версии `configuration-index.lmdb`;
- миграция существующих снимков конфигурации;
- разрешение абсолютных путей в публичном ответе MCP;
- изменение текстов и предметной логики диагностик;
- исправление отдельных ошибок YAML проекта `sed_nkdk`.

## Договор путей

Путь проекта:

- использует `/` независимо от операционной системы;
- не является абсолютным путём Windows или POSIX;
- не содержит `.` и `..` как сегменты;
- относится к корню NKDK-проекта и включает путь компонента, например
  `cfe/дкз/Справочник/Виджеты/Свойства.yaml`;
- преобразуется в абсолютный путь только непосредственно перед операцией с
  файловой системой.

Этому договору подчиняются:

- `ProjectStateFileIdentity.projectPath`;
- `ProjectStateStructuredDocumentEntry.workingProjectPath`;
- `itemProjectPath` и `ownerProjectPath` файловых целей;
- `Diagnostic.filePath`, возвращаемый проверкой связей проекта;
- ключи файлов в `configuration-index.lmdb`.

## Изменения архитектуры

### Обработчики структурированных документов

Обработчик продолжает получать `projectDir`, если он нужен для чтения файлов,
но указывает в диагностике готовый `projectPath` из факта проекта. Он не
соединяет `projectDir` и `projectPath` для формирования результата.

Все существующие обработчики структурированных документов переводятся на этот
договор вместе, чтобы новая общая проверка не оставила скрытых нарушителей.
Предметная проверка заимствованных форм после исправления возвращает исходную
диагностику с путём вида `cfe/дкз/.../Форма.yaml`.

### Граница состояния проекта

Проверка переносимого DTO должна применять существующий разбор пути проекта ко
всем сохраняемым путевым полям. Недостаточно проверить, что поле является
строкой: абсолютный путь или выход через `..` должен отклоняться до записи
`project-state.bin`.

Для `workingProjectPath`, который хранится относительно компонента, проверка
разрешает только нормализованный относительный путь без префикса компонента.
При выдаче диагностики используется `projectPath` факта, уже включающий путь
компонента.

### Граница диагностик

Общий сборщик диагностик проверки связей проверяет каждый `filePath` через
единый разбор пути проекта. Нарушение считается внутренней ошибкой конкретного
обработчика и сообщает недопустимый путь; оно не исправляется молча.

MCP сохраняет существующую защиту. Она остаётся последней границей публичного
протокола, но корректный Core до неё передаёт только относительные пути.

### Снимок конфигурации

Кодек и версия `configuration-index.lmdb` не меняются. Добавляется проверка
переносимости: снимок, созданный и закрытый в одном корне, переносится в другой
корень, открывается новым descriptor и возвращает те же относительные ключи и
блоки без упоминания прежнего каталога.

## Ошибки

- Абсолютный или ненормализованный путь при создании вклада `project-state`
  отклоняется до публикации снимка с указанием поля DTO.
- Недопустимый путь, возвращённый обработчиком диагностики, останавливает
  validation как внутренняя ошибка с самим путём и названием границы проверки.
- Предметные ошибки продолжают возвращаться обычными диагностиками; их уровень,
  сообщение и YAML-путь не меняются.

## Проверки

1. Unit-тест проверки DTO отклоняет абсолютные и выходящие из проекта значения
   `projectPath` и `workingProjectPath`.
2. Тест обработчика заимствованной формы ожидает относительный `filePath`.
3. Тест общего сборщика передаёт ошибочный обработчик с абсолютным путём и
   ожидает понятную внутреннюю ошибку.
4. Интеграционный тест LMDB создаёт снимок в одном временном корне, закрывает и
   переносит его в другой, после чего читает прежние относительные ключи и
   блоки.
5. Интеграционный тест project state строит диагностику в одном корне и читает
   её при другом `projectDir`; результат не содержит прежний абсолютный корень.
6. Полные проверки проекта: type-check, тесты, архитектурные проверки и поиск
   новых дублей относительно зафиксированной базовой ревизии.

## Документация

В `.agents/architecture.md` рядом с описанием снимка компонента и состояния
проекта явно фиксируется правило: постоянные ключи и межслойные диагностики
используют пути проекта, абсолютные пути принадлежат только адаптеру файловой
системы.

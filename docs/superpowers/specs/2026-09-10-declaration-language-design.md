# Язык деклараций NKDK: common и rules

Уточнение типизированных атрибутов: поле XML-record с `attribute` использует
обычный скалярный преобразователь, а не отдельный обработчик объекта.
Для строки, boolean, точного десятичного числа и перечисления доступны общие
правила отсутствия и значения по умолчанию. Неправильная или неканоническая
запись сохраняется автоматически: `$xml` на границе атрибута содержит его
исходный текст, а `null` означает отсутствие. Элементы и коллекции внутри
этой границы недопустимы. Дополнительного разрешения аномалий в декларации нет.
Это расширение XML-record; прежние ограничения атрибутов элементов коллекций
не считаются автоматически снятыми.

В общей оболочке составной записи коллекция сочетается со скалярными
атрибутами и полями-элементами. Число и тип скаляров не задаются отдельным
профилем объекта: их обрабатывает обычный преобразователь записи.
Параметры присутствия специализируются при сборке. Атрибуты передаются
записывателю коллекции напрямую, без временного списка; обычный YAML
распределяется потоком событий без промежуточной сериализации.
Если поправку атрибута можно перенести на оболочку без потери смыслового
значения, она сохраняется на этой границе. Если значение без поправки нельзя
представить в YAML, сохраняется поправка самого поля. Это выводится из
присутствия и представления поля, а не из его имени.
Текущая реализация этого составного пути поддерживает одну коллекцию в общей
оболочке; несколько коллекций требуют дальнейшего расширения маршрутизации.
Пересечение XML-путей скаляров и коллекции диагностируется при компиляции.

Присутствие вложенной записи и присутствие её полей независимы. Если записи
нет, значения по умолчанию её полей не создают запись. Если запись есть,
применяются обычные правила присутствия полей, включая сокращение YAML.
Разница между отсутствующим XML-полем и явно записанным значением по умолчанию
сохраняется общим механизмом аномалий, без дополнительной декларации случая.
Ограничения вложенной записи применяются только при её наличии. Регистрация
аномалий работает относительно полей самой записи; наружу ошибки и
предупреждения выходят с полным путём через свойство владельца. Вложенность
не требует повторной декларации ограничений или обработки аномалий.

| Поле | Значение |
|---|---|
| Статус | Частичная реализация компилятора и скалярных операций; перенос каталога и сложные профили открыты |
| Редакция документа | 0.2, 2026-09-10 |
| Предлагаемый идентификатор формата | `nkdk-declarations/1` |
| Назначение | Единый договор XML ↔ YAML, проверки и подключения правил |
| Основание | [Обзор common](2026-09-10-common-declarative-design.md), исходники на `2af2f299ed8241eac78d4db46b4a8421efe2f8f7` |
| Согласованное решение | Common и rules используют один язык YAML, одну общую спецификацию и один компилятор; целевой файл правил владельца — `rules.yaml` |

Слова **обязательно**, **запрещено**, **допускается** задают требования предлагаемого языка, а не описывают уже существующий компилятор. Примеры показывают согласованную форму записи; импорты ссылаются на предлагаемый будущий каталог деклараций. Синтаксическая корректность YAML не доказывает полноту переноса объекта.

**Этот файл — единственная спецификация языка деклараций для common и rules.** Общие синтаксис, типы, условия, ограничения и композиция описываются один раз; требования, зависящие от роли декларации, оформляются разделами этого же документа. Отдельных спецификаций или диалектов common-YAML и rules-YAML нет. Обзор common, карточки объектов и первоначальный эскиз интерфейса служат материалами исследования, а не второй спецификацией языка.

[План реализации на Rust](../plans/2026-09-10-rust-yaml-declarations.md) разделён на компилятор, перенос каталога и завершение миграции приложения. Это планы исполнения одной спецификации. По указанию пользователя написание плана не запускает реализацию автоматически.

## 1. Результат и границы

**D-01. Один источник поведения.** Одна декларация содержит смысловой тип, XML- и YAML-представления, ограничения и объявленные зависимости. Из неё получаются две законченные операции преобразования и проверка значения. Отдельных пользовательских `fromXML`, `toYAML`, `fromYAML`, `toXML`, `validate` и ссылок на функции common в языке нет.

Пара XML/YAML-представлений — это две записи одного значения. Ограничение допустимости числа или ссылки нельзя угадать по названиям XML-полей: оно записывается явно в той же декларации.

**D-02. Полный переход на Rust.** Конечная система состоит из YAML-деклараций и Rust-компилятора/общих механизмов. TypeScript не нужен для сборки или работы конечного конвертера. На переходном этапе текущая версия служит независимым источником сравнительных результатов.

**D-03. Совместимость.** Меняется способ описания правил. Действующие XML, пользовательский YAML, ограничения проверки и регистрация аномалий сохраняются. Файл `rules.yaml` является исходником конвертера и не добавляется в пользовательскую конфигурацию.

Цели ускорения в 10 раз и сокращения пикового потребления памяти в 10 раз остаются измеряемыми целями. Сам выбор YAML или Rust этих результатов не доказывает.

<a id="layers"></a>
## 2. Common, rules и составление проекта

Согласован один язык для common и rules. В нём определены четыре вида деклараций: они используют одинаковую систему типов и выражений и различаются обязанностями. Выбор роли не создаёт отдельного языка или отдельной спецификации.

| `kind` | Содержание | Примеры |
|---|---|---|
| `value` | Самостоятельное повторно используемое значение и его представления | Boolean, I8nText, Font, TypeDescription |
| `fragment` | Именованная группа полей с представлениями, ограничениями и параметрами для включения в объект | Идентичность реквизита, его оформление, настройки поиска |
| `object` | Полный договор конкретного объекта: поля, подключённые фрагменты, оболочки и размещение | Справочник, общий модуль, элемент формы; отдельный common-record тоже может быть объектом |
| `resources` | Самостоятельная сборка файловых маршрутов без основного документа | Двоичные файлы конфигурации и XDTO-пакета |

`kind: resources` — исполняемая файловая сборка без основного XML/YAML-документа.
Она использует обычные `compose` и `resources`; после композиции поля и поведение
значений должны отсутствовать. Для неё доступны подготовка входов и перенос
файлов, но не преобразование/валидация основного документа и не его JSON Schema.
Подробный договор и рабочие примеры: [ресурсные интерфейсы](2026-09-10-common-declarative/08-resources-interfaces.md#исполняемая-файловая-сборка).

`kind` не задаёт архитектурный слой. Common и объект владельца остаются разными модулями даже при одинаковом `kind: object`.

**D-04. Направление зависимостей.** Common может подключать общие значения и системные перечисления; он не импортирует forms/appliedObjects. Rules владельца подключает common и передаёт параметры. Forms не зависит от appliedObjects. Предметные словари не переносятся в нейтральный Rust-код.

**D-05. Явные входы.** Вместо всей конфигурации common получает объявленные типизированные входы: основной язык, набор языков, ограничения типа, индекс нужной категории ссылок. Подключение владельцем не разрешает common читать произвольное соседнее поле или имя внешнего XML-корня.

Сборка каталога и подключение подготовленных входов происходят в одном месте композиции. Исходники деклараций не исполняют регистрацию при импорте. `imports` связывает определения при сборке; `inputs` получает данные конкретной операции. Это разные связи.

Rules переиспользует common через `use` с параметрами и объявленными входами. Преобразования и проверки подключённого компонента не копируются в rules. Общая схема исходных деклараций и единый типизатор проверяют как общий синтаксис, так и допустимые секции каждой роли.

<a id="files"></a>
## 3. Файлы и синтаксис

Предлагаемое размещение исходников будущего языка:

```text
declarations/
  common/
    boolean.yaml
    i8n-text.yaml
    metadata-attribute/
      rules.yaml
      presentation.fragment.yaml
  system-enumerations/
    code-type.yaml
  applied-objects/
    catalog/rules.yaml
    common-module/rules.yaml
  forms/
    input-field/rules.yaml
```

Каталоги показаны как целевая организация; текущей задачей они не создаются. Один файл экспортирует одно определение с уникальным `id`; локальные вспомогательные типы живут в `types`. Имя файла не определяет публичный тип автоматически.

**D-06. Ограниченный YAML.** Основой служит [YAML 1.2.2](https://yaml.org/spec/1.2.2/). Профиль исходников NKDK требует UTF-8, один документ на файл, строковые ключи, два пробела для отступа. Повторные ключи, anchors/aliases, merge key `<<`, пользовательские YAML-теги и подстановка переменных окружения запрещены. Повторное использование задаётся через типизированные `imports`, `use`, `with` и `compose`.

В исходниках `true`/`false` — логические литералы, `null` — явный null. Строки, похожие на числа, даты или специальные значения, записываются в кавычках. Для чисел допускается конечная десятичная запись; точность смыслового числа задаётся его типом, а не числом с плавающей точкой загрузчика деклараций. Форматирование не меняет смысл.

**D-07. Порядок.** Порядок ключей YAML-карты не используется как семантический порядок. Значимые последовательности представлены списками: поля, варианты упорядоченного выбора, стадии композиции, части шаблона. Для порядка XML действует приоритет: действующий договор референса, затем явно заданный именованный XML-порядок, затем резервный порядок композиции. Резервный порядок: поля фрагментов в последовательности списка `compose`, затем собственные поля в последовательности списка `value.fields`; вложенные композиции раскрываются по тому же правилу. Явный XML-порядок задаётся при необходимости формата отдельно от композиции и не меняет порядок вычисления зависимостей. Нельзя вводить числовое `order` каждому полю. Исключение оформляется именованным XML-порядком только для подтверждённого требования.

Ограничения этого раздела относятся к **исходникам деклараций**. Они не запрещают существующие теги аномалий или повторные логические вхождения в **пользовательском YAML**. Эти вхождения хранит отдельная модель представления конвертера.

<a id="document"></a>
## 4. Структура декларации

| Ключ | Обязательность | Значение |
|---|---|---|
| `format` | Всегда | Точное значение `nkdk-declarations/1`; неизвестная версия — ошибка |
| `kind` | Всегда | `value`, `fragment`, `object` или `resources` |
| `id` | Всегда | Уникальный стабильный идентификатор, например `common.i8n-text` |
| `description` | Необязательно | Человекочитаемое описание без влияния на преобразование |
| `imports` | При внешних ссылках | Карта локальный псевдоним → публичный `id` |
| `namespaces` | При QName | Карта XML-префикс → URI; QName сравниваются по URI и локальному имени |
| `parameters` | При настройке компонента | Статические типизированные параметры, их допустимость и значения по умолчанию |
| `inputs` | При внешних данных | Именованные типизированные данные операции; отсутствие готового входа не означает пустое значение |
| `types` | При локальных типах | Карта локальных имён → смысловые типы |
| `compose` | Только record у fragment/object | Список включаемых fragment и явных привязок |
| `value` | Всегда | Смысловой тип; у fragment/object — record, дополненный compose |
| `representations` | Для представленных частей | `xml` и `yaml`, описывающие то же смысловое значение |
| `presence` | При нетривиальном присутствии | Различимые состояния и их восстановление, см. раздел 6 |
| `normalization` | При нескольких эквивалентных внутренних состояниях | Ограниченная идемпотентная нормальная форма, см. раздел 6.4 |
| `constraints` | При ограничениях | Именованные проверки и диагностика, см. раздел 7 |
| `topology` | Только object | Относительное размещение объекта в компоненте и его XML-оболочки |
| `contributions` | При публикации фактов | Типизированные вклады в индексы, идентичности и ресурсы |

Неизвестный ключ запрещён на каждом уровне. «Свободный объект дополнительных настроек» отсутствует. Отсутствующая секция означает отсутствие её договора, а не включение предметных настроек по имени `id`.

**D-08. Статическое и динамическое.** `parameters` выбирают специализацию при сборке: например, допустимые типы, XML-профиль числа, политика сокращения текста. `inputs` привязывают подготовленные данные операции. `with` передаёт статические параметры, `bind` — динамические входы. Передача выражения от runtime-данных в `with` запрещена.

Начальная форма объявления скалярных параметров — именованная карта `parameters`, каждая запись имеет обязательный `type` и необязательный `default`. `type` использует общую грамматику типов, `default` содержит непосредственно скалярный литерал, а не выражение. Например, `preserveEmptyXML: {type: {kind: scalar, scalar: boolean}, default: false}`. Отсутствие default означает обязательную передачу через with; явный null не означает отсутствие default. Совместимость default с типом проверяется при связывании. Выражения, читающие inputs, в default запрещены. Составные defaults и дополнительные ограничения параметров требуют отдельного описания грамматики до реализации.

Параметр содержит `type`, при необходимости `default` и `constraints`; вход содержит `type`. Ссылка на локальный тип имеет вид `{local: translation}`, на импорт — `{use: text}`. Для встроенного типа используется `{kind: scalar, scalar: text}`. Смешивать эти три формы в одном узле нельзя.

В ссылке `use` секция `with` — именованная карта статических аргументов, секция `bind` — именованная карта выражений для входов подключённого компонента. Для начального скалярного профиля with принимает непосредственно скалярные литералы, как default; bind использует общую грамматику выражений. Числовая запись with сохраняется точно. Допустимость имён и типов аргументов проверяется по подключённому определению при связывании; наличие корректного YAML само по себе не подтверждает эту допустимость.

## 5. Типы, представления и подключения

### 5.1. Смысловые типы

| Форма | Поля и смысл |
|---|---|
| `scalar` | `scalar`: text, boolean, integer, number или calendar; числовой и календарный профили задаются явно |
| `enum` | `variants`: список уникальных `name` и смысловых литералов |
| `record` | `fields`: список `{name, type}`; поле имеет стабильное имя, не зависящее от языка представления |
| `sequence` | `item`: тип вхождения; порядок и повторы сохраняются |
| `choice` | `variants`: список `{name, type}`; правила распознавания принадлежат представлению |
| `local` | Ссылка на определение из `types` текущего файла |
| `use` | Импортированный тип с необязательными `with` и `bind` |

Наличие поля record само по себе не означает обязательное присутствие XML-узла или YAML-ключа. Без дополнительного договора представленное поле обязательно; другие случаи описывает `presence`. Поле без публичной записи должно иметь явное восстанавливаемое значение или привязку, а не скрытый XML-only callback.

#### Точные десятичные числа — согласованное отличие от TypeScript

По решению пользователя числовой смысл переносится на точные десятичные значения, а не JS Number/binary64. `9007199254740993` не округляется, длинная дробь не теряет разряды. Декларация: `value: {kind: scalar, scalar: number, profile: decimal}`, XML `{kind: text}`, YAML `{kind: scalar, scalar: number}`. Профиль обязателен; неизвестный профиль не подменяется стандартным. YAML принимает числовой литерал, но не строку `"42"`, null, NaN, Infinity или шестнадцатеричную запись.

Смысловая форма хранит знак, значащие десятичные цифры и степень десяти; сравнение не использует f64 и не разворачивает экспоненту в нули. Число значащих цифр не ограничено фиксированными 28/38 разрядами; практический предел задаётся размером входа. Степень и степень канонической научной записи обязаны помещаться в signed 64-bit, иначе явный отказ. Ноль имеет единственный числовой смысл без отрицательного знака. Лексика: необязательный знак, цифры с необязательной точкой (минимум одна цифра), необязательная экспонента e/E со знаком и цифрами.

Каноническая запись убирает лишние нули и плюс; при десятичном порядке от −6 до 20 используется обычная запись, вне него — точная научная запись с e и явным плюсом положительной степени. Это выбор формы, не округление: все значащие цифры сохраняются. Физические различия исходного XML (например, 1.2300 против 1.23) по-прежнему обязаны пройти proof; новая raw-граница чисел этим решением не вводится. Пока восстановление такой формы не реализовано, конвертер явно отказывает. Сравнение со старым TS для потери точности фиксируется как согласованное отличие, а не обновление ожиданий по старому округлённому результату.

Числовые литералы ограничений используют тот же точный тип, что данные. Константы подготавливаются при сборке; валидация не разбирает их заново. Структурная JSON Schema сохраняет точные числовые границы и помечает профиль `x-nkdk-number-profile: decimal`. Внешний валидатор схем обязан поддерживать такую точность, чтобы его результат совпадал с Rust. Проверка схемы через binary64 не заменяет штатную валидацию NKDK.

#### Начальный профиль перечислений

В начальном исполняемом профиле `enum` список `variants` содержит `{name, value}`: `name` — непустое уникальное имя варианта, `value` — уникальный строковый смысловой литерал. XML `kind: text` задаёт `values: [{value, text}]`, YAML `kind: scalar` — `values: [{value, literal}]`. Каждая таблица обязана покрывать все смысловые значения ровно один раз и иметь неповторяющиеся записи. Порядок таблиц не определяет соответствие: связывание идёт по `value`.

Числовые и логические смысловые литералы в этом профиле пока отвергаются, а не приводятся к строке. Алиасы `accept` и аннотации неизвестных вариантов относятся к последующим профилям. Компилятор выпускает Rust enum и прямые match для обоих направлений; пользовательские названия не вставляются в Rust-идентификаторы. Проверка YAML использует ту же таблицу. Трёхвариантный `code-type-enum.yaml` — синтетический пример языка, не объявление состава перечисления 1С.

### 5.2. Представления

Представление выбирает структуру формата и связывает её со смысловым значением. Для скаляра это текст или YAML-литерал; для record — поля; для коллекции — последовательность либо именованная карта; для choice — дискриминатор или непересекающиеся формы.

| `kind` представления | Назначение |
|---|---|
| `text`, `scalar` | Текст XML или YAML-скаляр; `values` задаёт пары смысловой литерал ↔ запись |
| `record`, `mapping` | Список полей по их смысловым именам; XML `path`/`attribute`, YAML `key` |
| `element-sequence`, `sequence` | Оболочка и представление каждого вхождения |
| `keyed-mapping` | Поля ключа и значения вхождения; сохраняет адрес каждого повтора |
| `choice` | Дискриминатор, таблица вариантов, явное принятие альтернативных форм |
| `text-pattern` | Ограниченная разбираемая и печатаемая грамматика со слотами и escaping |

Для record запись поля состоит из `field` и маршрута в текущем формате. При `use` маршрут задаёт внешнюю оболочку, а подключённая декларация — содержимое внутри неё. Обходить XML-оболочку второй раз или повторно создавать модель подключённого common не требуется.

**D-09. Единственная каноническая запись.** Таблица `values` указывает канонические записи. Дополнительные принимаемые формы записываются отдельно в `accept`; каждая имеет единственное смысловое значение. Их наличие не расширяет автоматически публичную YAML-схему: применимость к импорту XML, публичному YAML или техническому входу задаётся явно.

В XML-путях используется список QName, без XPath и выполнения строк. Префиксы разрешаются через `namespaces` при сборке. Узел может принадлежать одному полю либо объявленной композиции на общей оболочке; случайное двойное владение — ошибка.

Имена маршрутов проверяются как QName по [Namespaces in XML 1.0](https://www.w3.org/TR/xml-names/#ns-qualnames), включая Unicode-правила [NCName](https://www.w3.org/TR/xml/#NT-NameStartChar). Зарезервированные привязки xml/xmlns и пустой URI префиксного пространства запрещены по правилам стандарта; корректность проверяется и у неиспользуемых привязок. Объявления xmlns не являются смысловыми атрибутами поля и задаются только секцией namespaces.

#### Маршрут атрибута XML

В записи поля XML `path` задаёт список дочерних элементов от текущей оболочки. Необязательное `attribute` задаёт QName атрибута последнего элемента этого пути; `path: []` с `attribute` адресует атрибут текущей оболочки. Без `attribute` поле владеет содержимым элемента. Например, `{field: formatted, path: [], attribute: formatted}` и `{field: text, path: [v8:item]}` занимают разные части оболочки.

Непрефиксный атрибут всегда имеет пустое пространство имён, даже при объявленном пространстве имён по умолчанию. Префиксный атрибут разрешается по URI; разные префиксы одного URI не создают разных атрибутов. Атрибут и дочерний элемент с одинаковым QName не сталкиваются. Два владельца одного атрибута либо владение целым элементом одновременно с его внутренним атрибутом — ошибка с обоими источниками. Этот маршрут не задаёт политику аномалий и сам по себе не разрешает raw.

При подключении use проверяется фактическое XML-владение объявленного типа. Путь [] может помещать дочернюю коллекцию на оболочку вместе с отдельным атрибутом владельца: formatted на оболочке и v8:item внутри неё не конфликтуют. Повторяющийся элемент принадлежит коллекции целиком, включая его атрибуты; второе поле не может независимо владеть этим элементом или его внутренними частями. Атрибут принимает скалярное текстовое представление (включая boolean-таблицу), но не record, коллекцию или представление с собственными XML-атрибутами. Эти проверки выполняются при сборке после разрешения импортов, а не на каждом значении.

#### Канонические атрибуты оболочки

`xml.kind: with-attributes` оборачивает обычное XML-представление, не меняя смысловой тип. Обязательные поля — `attributes` и `content`; attributes содержит список `{name, value, when?}`, content — вложенное XML-представление того же значения. value имеет ровно одну форму: `{text: строка}` либо `{qname: QName}`. Во втором случае компилятор разрешает URI и локальное имя, а writer выбирает корректный префикс. when — логическое выражение над значением, объявленными inputs, parameters и литералами. Компилятор специализирует статические части и генерирует остальные условия в Rust; отдельные callback не допускаются. Условие вычисляется при записи атрибута и не изменяет смысловое значение. Повтор атрибута по URI/локальному имени запрещён, включая конфликт с атрибутом вложенного представления на той же оболочке.

```yaml
xml:
  kind: with-attributes
  attributes:
    - name: xsi:type
      value: {qname: v8:LocalStringType}
      when: {parameter: typedXML}
  content:
    kind: element-sequence
    path: [v8:item]
    item:
      kind: record
      fields:
        - {field: language, path: [v8:lang]}
        - {field: content, path: [v8:content]}
```

Так задаётся каноническая форма, а не разрешение игнорировать атрибуты входа. Несовпавший, лишний или отсутствующий атрибут участвует в общем proof формы; исправлять исходник без сохранения договорённой формы нельзя. Новая raw-политика из этой конструкции не возникает. Смысловой атрибут, например formatted, по-прежнему является полем record с маршрутом attribute; каноническая оболочка его не заменяет.

### 5.3. Повторное использование

Обычный список сохраняет порядок и повторы. Его YAML-представление имеет форму `{kind: sequence, item: представление}`; `item` описывает скаляр или отображение полей записи. Например, текстовый список использует `value: {kind: sequence, item: {kind: scalar, scalar: text}}`, XML `{kind: element-sequence, path: [Field], item: {kind: text}}` и YAML `{kind: sequence, item: {kind: scalar, scalar: text}}`. Пространство имён `Field` разрешается из декларации. Отсутствие свойства и пустой список различаются; сокращение пустого списка задаётся обычным правилом присутствия. Никаких подразумеваемых сортировки, устранения повторов или отбрасывания пустого элемента нет.

**D-10. Композиция без скрытых переопределений.** `compose` включает целые фрагменты с типизированными параметрами. Столкновение имён полей, маршрутов, ограничений или вкладов — ошибка с указанием обоих источников. Правило «последний wins» запрещено.

Канонические атрибуты with-attributes входят в композицию вместе с record: условия фрагмента получают его статические аргументы, атрибуты владельца сохраняются. Повтор одного расширенного имени атрибута отвергается с двумя позициями источника, в том числе между фрагментом и владельцем.

Владелец меняет компонент через объявленный параметр или выбирает именованный профиль. Произвольное наложение YAML-карт, скрытое удаление constraint, наследование с переопределением внутреннего поля common запрещены. Существующие расширения через object spread исследуются и превращаются в явную композицию либо профиль.

Локальные `types` применяются для небольших внутренних структур. Новый общий фрагмент выделяется при общем предметном договоре; одинаковые три строки в двух несвязанных объектах сами по себе не основание связывать их новым импортом.

### Состояние чтения записи

Компилятор разделяет создание состояния, приём события и завершение записи.
Два элемента имеют независимые значения и позиции. XML и YAML используют
существующие преобразователи значений и проверки; состояния не содержат ветвлений
по именам предметных объектов. Вложенность должна передавать события от одного
разбора, а запись результата — использовать общий буфер.

При сохранении аномалии повторяющегося XML-поля выбирается его конкретное
вхождение по исходной позиции, а не только по пути. Обычный путь не создаёт дерево
XML; механизм сохранения дерева применяется лишь при необходимости сохранить
отклонение. Готовое состояние чтения не требуется удерживать после обработки
элемента: этот договор не разрешает создавать второй полный контекст проекта.

## 6. Присутствие и сокращения

Правило `presence` поля заменяет правило `self` импортированного common целиком.
Если у типа пропуск разрешён, а у свойства он запрещён, достаточно записать
`presence: [{target: {field: enabled}}]`: отсутствие `missing` не разрешает пропуск.
Схема YAML и исполняемый преобразователь используют один и тот же выбранный
договор. Отсутствие обязательного XML-поля сохраняется как аномалия с возможностью
восстановления; отсутствие YAML-поля при проверке даёт диагностику. Ни имя поля,
ни тип boolean не требуют отдельного условия в сборщике.


**D-11. Разные состояния.** Отсутствующий узел, пустой текст, пустой контейнер, nil, явно записанный default и недоступный факт не склеиваются в одно `None`/`null`. Смысловое значение может совпадать, но требование восстановления формы проверяется отдельно.

`presence` задаётся для `self` или смыслового поля. Для каждой стороны отдельно указывается, какое полное значение обозначает отсутствие, какие пустые формы допускаются и что записывается при отсутствии формы для восстановления. Это данные отношения состояний, а не отдельная процедура преобразования.

| Конструкция presence | Договор |
|---|---|
| `xml.missing.denotes` / `yaml.missing.denotes` | Полное значение отсутствующего представления; выражение использует только объявленные входы и поля |
| `xml.empty` / `yaml.empty` | Явные формы пустоты и их смысл; текст `""`, nil и пустой record различаются |
| `yaml.omitWhen` | Проверяемое условие сокращения; разрешено только при совпадении с восстановлением из missing.denotes |
| `xml.canonical` | Способ записи при отсутствии сведений формы/референса: узел, пустой узел, nil или отсутствие |

Закрытая структура узлов определена ниже. Применение ко всем профилям I8nText ещё завершается в А1; до проверки полной таблицы нельзя объявлять I8nText перенесённым.

### 6.1. Закрытая структура presence

`presence` — список записей с обязательным `target` (`self` либо `{field: имя}`) и необязательными `xml`/`yaml`. Два договора одного target запрещены. Каждая сторона имеет только ключи `missing`, `empty`; дополнительно XML имеет `canonical`, YAML — `omitWhen`. В отсутствие записи действует обязательное обычное представление.

- `missing` содержит только `denotes`: выражение полного смыслового значения либо `{absent: true}`. Отсутствие данных и `{literal: null}` — разные результаты. `absent` допускается только в позиции presence и явных ветвях выбора отсутствия.
- `empty` — список `{form, denotes}`. Формы XML: `empty-element`, `empty-text`, `nil`; YAML: `empty-string`, `empty-mapping`, `empty-sequence`, `null`. Повтор формы запрещён. Пустой XML-элемент и пустой текст различаются на границе чтения; объединение допускается только после проверки восстановления.
- `canonical` — список `{when, form}`, где form принадлежит `ordinary`, `empty-element`, `nil`, `missing`. Последняя запись может не иметь when и задаёт резервный случай. Порядок выбора явный: первая истинная запись. Отсутствие подходящей записи означает `ordinary`. Условие читает смысловое значение, объявленные inputs и parameters; исходный XML ему недоступен.
- `omitWhen` — одно логическое выражение. Оно только предлагает отсутствие; сокращение разрешается после проверки равенства значения результату `missing.denotes`. Исключённые переводы, повторы и аннотации входят в проверяемое равенство.

Статические параметры специализируют эти таблицы при сборке. Динамические условия проверяются один раз для текущего значения, без повторной материализации модели. Выбор `missing` при каноническом экспорте не разрешает незаметно потерять присутствующее XML: механизм восстановления независимо проверяет границу.

Для коллекции правило присутствия владельца с `target: {field: имя}` заменяет
правило common целиком, как у скаляров. Выражения читают это свойство и входы
владельца; компилятор переводит их в область значения коллекции. Пустой список
по умолчанию задаётся `{sequence: []}`, без предметного флага. Если YAML
подразумевает оболочку, которой не было в XML, общий контрольный экспорт
сохраняет её исходное отсутствие как удаление свойства, а не выдаёт ошибку.

### Вложенная XML-форма элемента коллекции

Для прямого списка текстовых XML-элементов `presence.xml.empty` дополнительно
принимает `form: empty-item`: ровно одно вхождение с пустым текстом. Его `denotes`
различает отсутствие и пустую последовательность. Это форма представления,
а не перечень аномалий. Несколько элементов, включая пустые, не попадают под неё.
Обычный YAML-список различает физические `[]`, `{}` и короткий литерал до
применения `presence`: сокращение до пустой последовательности не становится
физическим `[]`. Пустая карта принимается и включается в схему только при её
явном объявлении. Непустая карта на этом месте запрещена.

`element-sequence.item` может иметь `kind: tree` и `children`. Каждый узел
содержит `name`, необязательные `attributes` и один источник содержимого:
`field: имя` для поля записи, `self: true` для скалярного элемента,
`text: строка` для постоянного текста либо `children` для вложенных узлов.
Отсутствие источника означает постоянный пустой текст. Постоянные оболочки
не создают фиктивных полей смыслового значения.

Каждое поле связывается ровно один раз; соседние узлы не могут иметь одинаковое
расширенное XML-имя. Условия атрибутов используют значение **текущего элемента**
коллекции и объявленные входы. Два атрибута с одним именем допустимы только
при доказуемо противоположных условиях `p` и `not p`; оба значения никогда
не выводятся одновременно. Повторное условие вычисляется один раз для узла.

Компилятор превращает дерево декларации в маршруты потокового чтения и прямую
запись XML. Дерево данных для обычного преобразования не создаётся. Отличия
постоянного текста, состава атрибутов или оболочек выявляются общим контрольным
экспортом и сохраняются существующим механизмом аномалий; перечислять их в YAML
или добавлять обработчик конкретного common не требуется.

### Постоянная короткая запись списка

Для обычного текстового списка `shorthand` допускает постоянный литерал без
захвата. Например:

```yaml
yaml:
  kind: sequence
  item: {kind: scalar, scalar: text}
  shorthand:
  - id: pair
    representation: {kind: literal, value: Пара}
    denotes: {sequence: [{literal: первое}, {literal: второе}]}
```

Чтение `Пара` восстанавливает ровно два указанных элемента. Запись сокращается
только при точном совпадении всей последовательности, включая порядок и повторы.
Обычный список остаётся полной формой. Повтор идентификатора, короткого литерала
или полного значения отвергается при сборке: у записи должен быть один обратный
переход. Первая реализация этой формы принимает только последовательности
постоянных текстовых литералов; выражения от входов и записи с захватом относятся
к другим формам shorthand и не подразумеваются автоматически.

Допустимые элементы задаются обычным `constraints`: `each` проверяет элемент,
а `diagnostic.at: {self: true}` указывает всю коллекцию. Из нарушения выводится
`!xml/invalid` на полном списке; отдельный перечень аномалий не нужен.
Сокращение и опускание значения по умолчанию не могут скрыть такое нарушение.
При чтении YAML тег проверяется тем же ограничением: неизвестное значение
без тега и тег без нарушения не считаются корректным пользовательским YAML.
Первая реализация обычных списков поддерживает эту общую границу; адресация
отдельных вхождений не объявляется реализованной автоматически.

Сравнение с постоянной последовательностью и выбор короткой записи не создают
временную коллекцию в куче. Смысловые строки создаются при чтении; правила не
разбираются во время преобразования. Атрибуты самого скалярного XML-элемента
списка задаются существующим `with-attributes` вокруг `item: {kind: text}`.

### 6.2. Закрытая структура shorthand

`shorthand` разрешён только внутри YAML-представления и содержит список `{id, representation, denotes, when?}`. `id` уникален внутри представления. `representation` описывает короткую форму обычной грамматикой представлений, `denotes` строит полный смысл из захваченного короткого значения `{capture: имя}` и объявленных входов. `when` ограничивает применимость записи при сокращении.

Формы импорта должны различаться по структуре либо явному дискриминатору; пересечение — ошибка компиляции. Для экспорта несколько равнозначных коротких форм выбираются в порядке списка. Кандидат обязательно повторно интерпретируется через denotes и сравнивается с окончательным значением с учётом разрешённых аннотаций. Для строки I8nText это ровно одно физическое вхождение основного языка; проверка числа различных ключей недостаточна.

`capture` живёт только внутри соответствующей короткой формы и не предоставляет исходный XML или произвольный контекст. Нельзя использовать shorthand как две несвязанные функции импорт/экспорт.

### 6.3. Распознавание пустоты и условный смысл

При чтении сначала проверяется отсутствие, затем явно объявленная пустая форма из presence, затем обычное представление и его shorthand. Обработанная presence форма исключается из области распознавания обычного представления. Поэтому `empty-string` и общий строковый shorthand не являются пересекающимися ветвями: пустая строка принадлежит presence, остальные строки — shorthand. Если presence не объявляет empty-string, общий строковый shorthand включает её. Этот порядок общий для всех компонентов, без условия по имени I8nText.

В позиции denotes разрешено типизированное выражение `{if: условие, then: выражение, else: выражение}`. Обе ветви имеют один тип либо общий optional-тип при явном absent. Условие по parameter вычисляется при сборке; условие по input остаётся проверкой в подготовленной операции. Предметные функции в ветвях запрещены.

Для I8nText при включённом excludeIfEqualNameYAML пустая YAML-строка обозначает пустую последовательность. При выключенном параметре — одно физическое вхождение основного языка с пустым текстом. Это различие записывается непосредственно в presence, а не условием в Rust:

```yaml
presence:
  - target: self
    yaml:
      empty:
        - form: empty-string
          denotes:
            if: {parameter: excludeIfEqualNameYAML}
            then: {sequence: []}
            else:
              sequence:
                - record:
                    language: {input: defaultLanguage}
                    content: {literal: ""}
```

Этот фрагмент задаёт только чтение пустой короткой формы. Он не объявляет полный профиль I8nText перенесённым. В частности, preserveEmptyXML без excludeIfEqualNameYAML сохраняет в текущем TypeScript пустой XML-контейнер через YAML-строку, которая при обратном чтении создаёт пустой основной перевод. Структура внутренней модели меняется, хотя обычный XML восстанавливается. Полная декларация должна явно описать нормализацию этого состояния и проверить восстановление; простое ослабление равенства всех коллекций запрещено.

### 6.4. Ограниченная нормальная форма

Первая поддерживаемая форма `normalization` имеет ровно `{when, from, denotes}`. `from` равно `empty-sequence`; применять её можно только к смысловому типу sequence. `when` читает статические parameters. `denotes` — непустой литеральный конструктор sequence, его поля могут читать объявленные inputs. Отсутствие не является пустой последовательностью. Другие формы нормализации запрещены до описания их договора.

Нормализация применяется после декодирования полного значения, включая presence и shorthand, одинаково с обеих сторон. Она не применяется повторно к каждому полю и не затрагивает непустую последовательность. Компилятор проверяет непустоту результата по форме конструктора: повторное применение ничего не меняет, поэтому идемпотентность не требует произвольного доказательства выражений.

Для P=true,N=false пустой XML-контейнер и YAML-пустая строка получают одну нормальную форму — один пустой основной перевод:

```yaml
normalization:
  when:
    and:
      - {parameter: preserveEmptyXML}
      - {not: {parameter: excludeIfEqualNameYAML}}
  from: empty-sequence
  denotes:
    sequence:
      - record:
          language: {input: defaultLanguage}
          content: {literal: ""}
```

Сравнение короткой формы использует нормализованные полные значения. Отдельно контрольный экспорт сравнивает полученный XML с исходной границей. Нормализация не даёт proof и не скрывает атрибуты, nil или фактический item: если обычный экспорт их теряет, граница остаётся несовпавшей и обрабатывается существующим разрешённым механизмом аномалий. Для нескольких пустых переводов, повторов языка или непустого текста эта нормализация не срабатывает.

**D-12. Короткая форма через полное значение.** `shorthand` задаёт принимаемую короткую структуру и `denotes` — полное значение, которое она обозначает. Обратный выбор короткой записи возможен только при равенстве всех значимых частей и сохранении разрешённых аннотаций. Например, строка I8nText означает ровно один перевод на основном языке. Два вхождения одного языка не удовлетворяют этому условию.

Произвольное выражение не считается автоматически обратимым. Если отсутствие или сокращение нельзя однозначно восстановить, значение остаётся явным; импортированный исходник нельзя тайно использовать как ответ контрольного экспорта.

Для scalar-text первая версия компилятора допускает ровно один неизменённый capture внутри структурных конструкторов record/sequence. Остальные части вычисляются только по подготовленному контексту. Неиспользованный capture, его повтор или произвольное выражение вокруг него отвергаются как noninvertible_shorthand: вычислить полное значение недостаточно, нужно также уметь извлечь короткое. Более общий алгоритм доказательства обратимости пока не поддержан.

#### Boolean, представленный отсутствием

Таблица YAML boolean может содержать один литерал, если второе значение однозначно представляется отсутствием: self.presence.yaml.missing восстанавливает его, а omitWhen истинно ровно для этого значения. Например, values содержит только `{value: true, literal: Истина}`, missing denotes `{literal: false}`, omitWhen `{not: {self: true}}`. Это общий договор признака, применимый к formatted без отдельной функции преобразования. XML-таблица по-прежнему содержит оба значения.

Компилятор проверяет оба возможных boolean-значения. Начальное доказательство допускает self, boolean-литералы, not/and/or/eq/if; динамические входы и неподдержанные выражения не считаются доказательством. Если отсутствующий литерал нельзя восстановить или omitWhen скрывает другое значение, декларация отвергается. Явная YAML-строка Ложь не входит в таблицу и не становится допустимой из-за missing: default применяется к отсутствию, а не к неизвестному литералу.

### 6.5. Обратимые шаблоны остатка коллекции

**Выбор обычной формы по частоте.** По согласованному критерию пользователя обычным остаётся отсутствие основного перевода, физическое пустое вхождение при неоднозначности — исключением. В e2e (1125 XML) найдено 913 пустых Synonym и 10 Synonym только с другими языками, ни одного физического пустого ru; проверенный поднабор N=true Catalog/Document содержит 5 пустых контейнеров и 47 непустых. [Методика и ограничения выборки](../reports/2026-09-10-i8n-e2e-frequency.md). Пустой маркер сохраняет значение «ru отсутствует». Если реальное пустое вхождение невозможно восстановить обычной формой, оно сохраняется через минимальную необходимую raw-границу с проверкой обеих сторон; редкость не является основанием помечать обратимые значения raw. При N=false существующее обратимое представление не меняется. Физическая граница и окончательный YAML должны быть подтверждены round-trip, а не только частотным подсчётом.


Согласованный подход и примеры: [обратимые шаблоны коллекций](2026-09-10-common-declarative/02-reversible-collection-patterns-proposal.md). Это расширение D-12 того же языка.

В shorthand для keyed-mapping допускается `representation: {kind: keyed-mapping, capture: имя, prefix: [...], suffix: [...], absentKeys: [...]}`. Поля prefix/suffix/absentKeys необязательны, отсутствие означает пустой список. Тип вхождения и имена key/value наследуются от полной keyed-mapping. prefix/suffix содержат выражения полных фиксированных вхождений, capture захватывает единственный непрерывный остаток. absentKeys запрещает указанные смысловые ключи именно в остатке; совпадение проверяется по значению ключа, а не по имени YAML-аннотации.

`denotes` для такой формы содержит либо `{capture: имя}`, либо `{sequence-pattern: {prefix: [...], rest: {capture: имя}, suffix: [...]}}`. prefix/suffix здесь описывают фиксированные части полного смыслового значения. rest обязателен, содержит ровно один захват этой формы; второй захват и произвольное преобразование остатка запрещены. Фиксированные части не читают self, поля ещё не восстановленного значения, captures или переменные обхода; они вычисляются по inputs/parameters и общим выражениям. Недоступный результат фиксированной части делает вариант неприменимым. Обычное отсутствие обязательного подготовленного входа остаётся ошибкой операции.

```yaml
shorthand:
  - id: name-and-rest
    representation:
      kind: keyed-mapping
      capture: otherTranslations
      absentKeys: [{input: defaultLanguage}]
    denotes:
      sequence-pattern:
        prefix:
          - record:
              language: {input: defaultLanguage}
              content: {input: nameText}
        rest: {capture: otherTranslations}
    when: {parameter: excludeIfEqualNameYAML}
  - id: absent-primary-marker
    representation:
      kind: keyed-mapping
      capture: otherTranslations
      prefix:
        - record:
            language: {input: defaultLanguage}
            content: {literal: ""}
      absentKeys: [{input: defaultLanguage}]
    denotes: {capture: otherTranslations}
    when:
      and:
        - {parameter: excludeIfEqualNameYAML}
        - exists:
            in: {capture: otherTranslations}
            as: translation
            where: {literal: true}
```

В примере nameText — явно объявленный подготовленный текст, а не вызов предметной функции. Полный профиль связывает его с общей декларацией текстового преобразования имени; пример сам по себе не объявляет эту привязку реализованной.

При чтении проверяется форма prefix/suffix, тип остатка, absentKeys и when. При записи тот же структурный шаблон denotes сопоставляется с полным значением: вычисленные фиксированные части должны совпасть точно, остаток получает захват, после чего проверяются when и ограничения представления. Возвращать исходный XML вместо такого сопоставления запрещено. Выбор сокращения идёт в порядке shorthand; полная карта служит резервной записью.

Несколько коротких форм чтения обязаны быть доказуемо непересекающимися. Первая версия проверки доказывает различие scalar и keyed-mapping; для двух карт — конфликт фиксированного ключа одной формы с absentKeys другой формы без prefix/suffix. Не доказанное различие отвергается компилятором, даже если автор считает условия when несовместимыми. Это ограничение проверяющего алгоритма, а не разрешение first-wins при чтении.

Сопоставление имеет единственное разбиение по длинам фиксированных частей и не перебирает позиции остатка. Остаток сохраняет физические адреса, порядок и аннотации. Синтетическая фиксированная часть не выдаётся за исходное вхождение; проверка восстановления и допустимости аномалий остаётся общей.

## 7. Ограничения и зависимости

Constraint содержит `id`, `appliesTo`, необязательный `when`, обязательный `assert` и `diagnostic`. `id` стабилен внутри компонента. `appliesTo` является списком из `xml-import`, `yaml-validation`: экспорт YAML→XML применяет те же проверки `yaml-validation`, а не ещё один вручную написанный валидатор.

`diagnostic` содержит обязательные `severity`, `at`, `message` и при наличии в исходном публичном договоре `code` и `source`. `at` указывает на поле, всю коллекцию или отдельное вхождение; runtime дополняет его файлом и позицией источника. Уровень и код при переносе сохраняют текущий публичный договор; новые имена в учебных примерах не заменяют существующие коды. Стабильный constraint.id не превращается автоматически в публичный code. В текущей диагностике локализованного текста code отсутствует, source равен `structure`: новое поле нельзя добавлять ради удобства генератора.

**D-13. Ограниченный язык выражений.** Выражения представлены деревом YAML-узлов, не строками кода.

| Узел | Значение |
|---|---|
| `{literal: ...}` | Типизированное по месту применения постоянное значение |
| `{field: name}` | Разрешённое поле текущего record; отсутствующее значение требует явного разбора состояния |
| `{input: name}` / `{parameter: name}` | Объявленный динамический вход / статический параметр |
| `eq`, `lt`, `lte`, `and`, `or`, `not` | Типизированные логические операции и сравнения; первые пять принимают список операндов, `not` — один узел |
| `present`, `isNull`, `isReady` | Раздельные проверки состояния значения и готовности входа |
| `match` | Конечный разбор вариантов с исчерпывающим выбором |
| `record`, `sequence` | Построение смыслового значения из именованных полей или упорядоченных выражений |
| `each`, `exists`, `uniqueBy` | Проверки конечной коллекции с локальным именем вхождения |
| `lookup` | Объявленный поиск в подготовленном типизированном индексе |

Сравнения имеют ровно два операнда, `and`/`or` — непустой список. Null, отсутствие и неготовность не преобразуются в false неявно. `lookup` различает found/missing/ambiguous; `isReady` не подменяет отсутствующую цель ссылки.

При необходимости строковая грамматика, преобразование регистра или разделение имени задаются общими детерминированными текстовыми операторами с установленной Unicode-семантикой. Специального оператора `makeCatalogSynonym` нет. Новая общая конструкция требует отдельного описания входов, результата, ограничений и стоимости.

Начальная форма `match` для необязательного результата: `{match: {value: выражение, present: {as: имя, then: выражение}, absent: выражение}}`. Обе ветви обязательны, другие варианты запрещены. value вычисляется один раз и имеет тип Optional<T>; в ветви present переменная имеет тип T без необязательности, в absent она недоступна. Выполняется только выбранная ветвь. Типы результатов должны совпадать либо различаться явным отсутствием; во втором случае результат Optional<T>. Нельзя извлечь отсутствующее значение через приведение или подставить false/пустую строку. Это позволяет восстановить коллекцию из вычисленного текста имени в present и оставить отсутствие в absent. Переменные локального match допустимы внутри фиксированной части шаблона, если само value зависит только от подготовленного контекста; переменные внешнего обхода и остаток по-прежнему запрещены.

#### Адресуемый обход коллекции

Constraint может дополнительно объявлять `forEach: {in: выражение, as: имя}`. Выражение имеет тип sequence; тело when/assert/diagnostic применяется к каждому физическому вхождению в порядке источника. В выражениях `{self: true}` обозначает полное значение компонента, `{var: имя}` — вхождение, `{get: {of: выражение, field: имя}}` — проверенное поле record. Ссылка на имя вне области видимости и повторное объявление имени во вложенной области запрещены.

Необязательный `forms` ограничивает constraint фактически прочитанными формами представления текущего компонента, например `[keyed-mapping]`. Допустимы только формы, объявленные соответствующей стороной representations; неизвестная форма — ошибка сборки. Форма сохраняется компактным идентификатором на границе чтения, без копирования исходного документа. Для экспортируемого из XML кандидата YAML проверяется форма именно этого кандидата. `forms` не подменяет проверку типа схемой и не выбирается по имени common.

`exists` и `each` имеют форму `{in, as, where}` и возвращают boolean; each на пустой последовательности истинен, exists — ложен. `diagnostic.at: {occurrence: имя, field: имя}` сохраняет физический адрес и позицию соответствующего ключа/поля представления. `{self: true}` в diagnostic.at адресует границу всей коллекции. Выражение не собирает промежуточный словарь уникальных ключей.

Для проверки регистрации языка используется общий поиск в заранее подготовленном индексе либо exists над объявленным малым набором. Компилятор может подготовить множество один раз на операцию; повторное построение множества для каждого перевода запрещено. Строковая интерполяция сообщений задаётся `{parts: [строка, выражение, ...]}`; сборка сообщения выполняется только при ошибке, не в успешном пути преобразования.

Пример условия XML-импорта; `registeredLanguages` объявляется входом sequence<text> в этом же компоненте. Правило YAML-проверки имеет другую область исключения служебных кодов, поэтому ниже не перечислено в appliesTo:

```yaml
constraints:
  - id: registered-language-on-import
    appliesTo: [xml-import]
    forEach: {in: {self: true}, as: translation}
    when:
      not:
        or:
          - eq:
              - {get: {of: {var: translation}, field: language}}
              - {literal: ""}
          - eq:
              - {get: {of: {var: translation}, field: language}}
              - {literal: "#"}
    assert:
      exists:
        in: {input: registeredLanguages}
        as: registered
        where:
          eq:
            - {var: registered}
            - {get: {of: {var: translation}, field: language}}
    diagnostic:
      severity: error
      source: structure
      at: {occurrence: translation, field: language}
      message:
        parts:
          - "Незарегистрированный язык "
          - {get: {of: {var: translation}, field: language}}
```

Пример описывает смысловой отказ и точную границу. Назначение invalid выполняет существующая зарегистрированная политика; наличие constraint само по себе не регистрирует новый тег.

Для YAML-карты условие регистрации отличается: служебный код в любом вхождении отключает этот смысловой блок, а пустой текст проверяется отдельным constraint и не порождает одновременно сообщение о незарегистрированном языке. Короткая строка сюда не входит:

```yaml
constraints:
  - id: registered-language-in-yaml-map
    appliesTo: [yaml-validation]
    forms: [keyed-mapping]
    forEach: {in: {self: true}, as: translation}
    when:
      and:
        - not:
            exists:
              in: {self: true}
              as: candidate
              where:
                or:
                  - eq:
                      - {get: {of: {var: candidate}, field: language}}
                      - {literal: ""}
                  - eq:
                      - {get: {of: {var: candidate}, field: language}}
                      - {literal: "#"}
        - not:
            eq:
              - {get: {of: {var: translation}, field: content}}
              - {literal: ""}
    assert:
      exists:
        in: {input: registeredLanguages}
        as: registered
        where:
          eq:
            - {var: registered}
            - {get: {of: {var: translation}, field: language}}
    diagnostic:
      severity: error
      source: structure
      at: {occurrence: translation, field: language}
      message:
        parts:
          - "Незарегистрированный язык "
          - {get: {of: {var: translation}, field: language}}
```

Подвыражение поиска служебного кода не зависит от translation. Компилятор обязан вынести его из обхода forEach и вычислить не более одного раза на значение. При совместных constraints одинаковые чистые подвыражения могут разделять результат. Декларативное описание не разрешает квадратичный повторный обход карты для каждого языка.

#### Порядок, пустой текст и маркер

Общий предикат `ordered` содержит `{in, as, key, unique, first, comparison}`. `in` — sequence, key вычисляет строковый ключ текущего вхождения. `unique: true` означает, что проверка порядка рассматривает только первое вхождение каждого ключа; исходная последовательность не изменяется. `first` — список предпочтительных ключей в требуемом порядке, отсутствующие ключи не материализуются. Остальные ключи сравниваются по явно заданному `comparison: utf16`. `unique: false` проверяет все ключи с неубывающим порядком. Уникальность как ограничение допустимости задаётся отдельно, не следует из ordered.

Для I8nText утверждение каноничности имеет вид:

```yaml
assert:
  ordered:
    in: {self: true}
    as: translation
    key: {get: {of: {var: translation}, field: language}}
    unique: true
    first: [{input: defaultLanguage}]
    comparison: utf16
```

Оно применяется только к forms=[keyed-mapping] в yaml-validation и только при отсутствии служебного кода в любой позиции, как в предыдущем примере. Ошибка относится к `{self: true}`, сообщение — «Неканонический порядок языков локализованного текста». Проверка выполняет один проход по ключам, с множеством уже встреченных ключей для unique; сортировать или перестраивать данные для проверки не требуется.

Проверки пустого текста имеют тот же фильтр формы и служебных кодов. Для каждого вхождения с content=`""`:

| Условие | Результат |
|---|---|
| N выключен либо language не равен defaultLanguage | Ошибка «Пустое значение языка не представляет XML-текст» на этом вхождении |
| N включён и language равен defaultLanguage, но первый физический ключ карты другой | Ошибка «Маркер отсутствующего основного языка должен быть первым» на этом вхождении |
| N включён и первый физический ключ равен defaultLanguage | Пустой маркер допустим; этот constraint не утверждает допустимость повторов |

Сравнение первого ключа не равно проверке индекса текущего вхождения: повторный пустой default проверяется существующим механизмом повторов отдельно. Для выражения первого элемента допускается `{take: {in: выражение, count: 1}}`, возвращающее ограниченный вид последовательности без копирования элементов; exists над таким видом возвращает false для пустой коллекции. `count` — неотрицательный статический integer. Материализация полной последовательности ради take запрещена.

Диагностика порядка предшествует адресным сообщениям о пустоте и регистрации, как в текущем валидаторе. Порядок constraints — порядок сообщений; внутри forEach сохраняется физический порядок вхождений. Объединение обходов компилятором не должно переставлять публичную диагностику.

### 7.1. Детерминированное преобразование текста

Для вывода текста из имени нужен общий декларативный конечный преобразователь, а не стандартный Unicode word-break. Определение живёт в `types` как `kind: text-transform`; это вычислимый типизированный договор text → optional text, который не имеет собственного XML/YAML-представления. Выражение вызова имеет вид `{transform: {local: имя, value: выражение}}`. Это ссылка на локальные данные, не имя Rust-функции. Подключение внешнего преобразователя подчиняется обычным imports и архитектурным ограничениям.

У определения только поля `kind`, `units`, `classes`, `state`, `transitions`, `result`. `units` здесь равно `utf16`; классы — именованные списки включительных диапазонов кодовых единиц. Непарные суррогаты не классифицируются как буквы. Декларация I8nText задаёт uppercase `[A-ZА-ЯЁ]`, lowercase `[a-zа-яё]`, digit `[0-9]`; это данные конкретного профиля. Обобщение этих классов до всех букв Unicode изменило бы поведение.

`state` объявляет булевы флаги с начальными значениями. `transitions` — упорядоченный список `{when, emit, set}`: when читает класс текущей единицы, состояние и готовую классификацию следующей единицы после серии текущего класса; emit выбирает `append`, `start-token` или `discard`, set одновременно присваивает объявленные флаги. В каждом шаге потребляется ровно одна единица; произвольных циклов, рекурсивных вызовов и чтения внешнего контекста нет. Неизвестные флаги/классы запрещены. Последний переход обязан быть безусловным.

`result` задаёт `separator`, `first`, `rest`, `emptyInput`, `noTokens`. Политики first/rest выбираются из `identity` и `lower-first-unless-all-in-class` с явно названным классом. Для профиля синонима первый токен сохраняется; у остальных первая буква понижается, кроме полностью uppercase-токена. Пустой исходник даёт пустой текст. Непустой исходник без токенов сейчас даёт отсутствие, а не пустой текст; достижимость такого имени у владельцев проверяется отдельно, потребители не могут неявно подменить это состояние.

Следующая единица после серии вычисляется за один обратный проход либо на границах серий. Повторный поиск от каждой цифры запрещён: время O(n), временная память ограничена размером одного значения. Число состояний и переходов ограничено декларацией и проверяется при сборке; предметный автомат специализируется в Rust.

Независимые примеры записаны в `tests/migration/name-text-contract.json`. Существенные границы: `XMLParser` остаётся `XMLParser`; `Version12Number` → `Version 12 number`; `Version12a` сохраняется; `ÉcoleTest` → `cole test`; `Имя_Тест` → `Имя тест`. Запрещено заменять эти ожидания более привычной токенизацией без отдельного решения о совместимости.

#### Таблица переходов профиля вывода имени

Условия переходов имеют закрытую грамматику: `{class: имя}`, `{flag: имя}`, `{tokenEmpty: true}`, `{nextAfterRun: {class: имя, is: имя}}`, `{nextAfterRun: {class: имя, end: true}}`, а также and/or/not из общей грамматики. `nextAfterRun` пропускает только непрерывную серию указанного класса, не игнорирует пунктуацию и не меняет позицию чтения. `set` — карта объявленных флагов в boolean-литералы; пропущенные флаги сохраняются. Начало нового токена само по себе не сбрасывает флаги.

`classes` содержит списки пар целочисленных границ UTF-16 включительно. Для понижения регистра `result.lowercase` содержит таблицу `{from: [начало, конец], offset: число}` с непересекающимися диапазонами. Никакая версия Unicode-библиотеки не меняет эти данные. Отсутствующие в таблице единицы сохраняются. `noTokens` разрешает `absent` или `empty-text`; `emptyInput` имеет те же варианты. Выбор emptyInput производится до обхода.

Полное локальное определение в секции types:

```yaml
name-words:
  kind: text-transform
  units: utf16
  classes:
    upper: [[65, 90], [1040, 1071], [1025, 1025]]
    lower: [[97, 122], [1072, 1103], [1105, 1105]]
    digit: [[48, 57]]
  state:
    abbreviation: true
    hasDigit: false
  transitions:
    - when: {and: [{class: upper}, {tokenEmpty: true}]}
      emit: append
      set: {abbreviation: true, hasDigit: false}
    - when: {and: [{class: upper}, {flag: abbreviation}]}
      emit: append
      set: {}
    - when: {class: upper}
      emit: start-token
      set: {abbreviation: true, hasDigit: false}
    - when: {class: lower}
      emit: append
      set: {abbreviation: false}
    - when:
        and:
          - {class: digit}
          - {not: {tokenEmpty: true}}
          - {not: {flag: hasDigit}}
          - or:
              - {nextAfterRun: {class: digit, is: upper}}
              - {nextAfterRun: {class: digit, end: true}}
      emit: start-token
      set: {abbreviation: false, hasDigit: true}
    - when: {class: digit}
      emit: append
      set: {abbreviation: false, hasDigit: true}
    - emit: discard
      set: {}
  result:
    separator: " "
    first: {kind: identity}
    rest: {kind: lower-first-unless-all-in-class, class: upper}
    lowercase:
      - {from: [65, 90], offset: 32}
      - {from: [1040, 1071], offset: 32}
      - {from: [1025, 1025], offset: 80}
    emptyInput: empty-text
    noTokens: absent
```

Результат text-transform нельзя использовать как тип сериализуемого поля: он доступен только через выражение transform и явный разбор optional-состояния. На этой границе компилятор проверяет отсутствие обходного вызова Rust и запрещает обращение к input/field из переходов. Шаблон владельца передаёт единственный текст аргументом выражения.

**D-14. Вычисление зависимостей.** Компилятор выводит граф обращений к полям из выражений и bind. Текстовый порядок fields не является порядком вычислений. Цикл вычисления локальных значений — ошибка сборки; цикл предметных ссылок обрабатывает только явно заданная конструкция обхода графа.

Общая проверка типа/значения принадлежит common; ограничение конкретного владельца принадлежит его rules. Например, Number задаёт числовое представление, а Catalog задаёт `ДлинаКода ≤ 38`, когда `ТипКода = Number`. Если эта связь повторяется как один договор нескольких владельцев, она оформляется параметризованным fragment.

### QName: договор пространства имён М6

QName в значении XML сравнивается по URI и локальному имени. Префикс разрешается
в пространстве имён текущего элемента, включая предков и локальное переопределение;
части текста из обычных событий, CDATA и символьных ссылок объединяются до разбора.
Переименование префикса при неизменном URI не является аномалией. Некорректное имя
или неизвестный префикс сохраняются как буквальный XML и не превращаются в
выдуманный URI. Обычный текст с двоеточием не считается QName без указания
представления в декларации.

Представление записи из двух текстовых полей имеет форму
`xml: {kind: qname, namespace: namespace, local: name}`: значения `namespace` и
`local` ссылаются на разные поля записи; обычная YAML-карта задаёт их внешние
названия. Имя common и название XML-свойства не влияют на разбор или выбор URI.
Отсутствие и пустое XML-значение задаются общим `presence`.

На исключительном пути корректное QName внутри XML-поправки хранится атомарной
парой `"#qname": [URI, локальноеИмя]`. Это служебная форма поправки, не поле
декларации и не новый тег аномалии. Она несовместима с `#text` и дочерними XML-узлами.
Некорректный QName остаётся буквальным `#text`; строка вида `{URI}имя` не получает
смысл QName по внешнему виду. Благодаря этому поправка атрибутов не сохраняет
ненужную замену префикса, а неизвестные имена восстанавливаются без догадок.

### Подготовленные индексы: договор хранения М6

Индекс содержит типизированные ключи и ссылки на строки фактов. Форма ключа
задаётся декларацией проекции; для ссылок это обычно вид, владелец и имя.
Общий Rust-индекс не знает названий видов метаданных и не разбирает XML-пути.
Строковые значения и сведения об источниках хранятся в отдельных колонках;
ключи используют компактные идентификаторы этих значений, без копии контекста.

Подготовка принимает порции записей, затем сортирует накопленный массив на месте
и публикует неизменяемое поколение. Поиск выполняется по упорядоченному массиву,
возвращает заимствованную строку и не выделяет память. Дубликаты ключа сохраняются:
они означают неоднозначность, а не выбор первого совпадения. Пустой готовый индекс
возвращает «не найдено»; индекс другого поколения — «не готов». Это разные
состояния, ни одно из них не превращается в допустимую пустую ссылку.

Если вклад одного из объявленных источников невозможно прочитать, затронутый
индекс остаётся «не готов» и после успешных последующих порций: непрочитанный
источник может содержать как искомый ключ, так и его дубликат. Известное совпадение
тогда тоже нельзя объявлять однозначным. Это не меняет готовность независимых
индексов. Только полная повторная подготовка может подтвердить полноту.

Имена, URI и другие строковые колонки одного поколения используют общее
хранилище UTF-8 и четырёхбайтовые идентификаторы. Одинаковые строки разделяют
байты, поиск по тексту и получение текста по идентификатору не создают копий.
Регистр и Unicode-запись сохраняются буквально; нормализация возможна только
как отдельный договор декларации. Операция ограничивает число уникальных строк
и сумму их байтов; неудачное добавление не расходует идентификатор и бюджет.

Состав ключа, разрешённые цели, проекция исходных полей и зависимости потребителей
принадлежат декларации. Подготовка выполняется вне преобразования отдельного
значения; потребители одного индекса используют одно поколение. Сам общий поиск
не считается завершённой миграцией ссылок: для приёмки нужны сгенерированные
проекции, привязки входов и независимые проверки XML ↔ YAML.

#### Вклад владельца в индекс

Владелец объявляет проекцию уже прочитанного смыслового значения. Короткая
запись текстового индекса:

```yaml
contributions:
  - index: project.names
    key: {field: code}
    value: {field: title}
```

`index` — имя связываемого при сборке набора фактов, а не имя обработчика.
`key` и `value` используют общие типизированные выражения; поля должны быть
объявлены владельцем. Отдельные функции извлечения из XML и YAML отсутствуют:
проекция получает результат соответствующего чтения. Нельзя молча пропустить
неподдержанную проекцию при генерации. Ошибку исходных данных возвращает этап
подготовки; затронутые индексы получают состояние «не готов», и последующие
успешные вклады не скрывают неполноту. Независимые индексы сохраняют готовность.

Реализованная форма — текстовый ключ, перечисление либо непустая запись таких
компонентов и текстовое значение. Вклады фрагментов наследуются через `compose`
в порядке включения, затем добавляются собственные вклады владельца. Ссылки на
поля перенумеровываются вместе с полями, параметры и входы подставляются тем же
механизмом, что в ограничениях; отдельного реестра вкладов фрагмента нет.

Для строк из текстовых полей ключ и значение могут использовать общие
типизированные выражения над строкой и подготовленными входами, включая
декларативное преобразование текста и обработку отсутствующего результата.
Они компилируются при сборке. Это позволяет, например, получить часть имени
типа до точки без частного обработчика InternalInfo. Вычисляемые выражения над
составным типизированным хранением строк пока явно отклоняются; непосредственное
чтение поддержанных полей таких строк сохраняется.

Для коллекции используется общий `forEach`, как в ограничениях:

```yaml
contributions:
  - index: project.names
    forEach: {in: {field: rows}, as: row}
    key: {get: {of: {var: row}, field: code}}
    value: {get: {of: {var: row}, field: title}}
```

Начальная генерация обходит один подключённый common-список текста или
текстовых записей у владельца. Объявленные ограничения common проверяются до
публикации вклада, в том числе у значений с пометкой допустимой аномалии.
Сама пометка не превращает недостоверный источник в готовый индекс. Несколько
вложенных коллекций и ограничения владельца пока явно отклоняются.
Проекция обходит смысловые элементы, поэтому последовательность или карта
YAML и XML используют одинаковые выражения. Повторы не удаляются. Если смысл
коллекции не удалось получить и доступен только сохранённый XML, индекс
остаётся неготовым, а не считается полным пустым списком. Отсутствующая по
нормальному договору коллекция может законно не публиковать ни одной строки.

План подготовки строится для переданного списка исходных файлов из тех же contributions: каждый файл — отдельный шаг, каждый индекс — один общий шаг после всех его источников. Привязки входов потребителей добавляют рёбра от соответствующих индексов к потребителям. Источник вкладов также может потреблять другие индексы: его шаг зависит от них перед публикацией собственных вкладов. Общий граф проверяет циклы и распространяет изменения через всю цепочку; наличие contributions не отменяет зависимости inputs. Бюджет рёбер проверяется до накопления лишних связей.

Сгенерированный каталог связывает имена индексов с числовыми идентификаторами
один раз. Подготовка хранит ключи как массивы TextId фиксированной длины и значения TextId в отсортированных индексах и
общее хранилище UTF-8; повторные имена и значения не копируются между
индексами. Бюджеты ограничивают строки, байты и количество вкладов. При
превышении бюджета индекс не публикуется как полный. Поиск возвращает
заимствованное значение и различает неизвестный ключ, неоднозначность,
неполноту источников и устаревшее поколение.

#### Подготовленный вход и поиск

Потребитель объявляет структуру требуемого индекса, не имя источника:

```yaml
inputs:
  names:
    type:
      kind: index
      key: {kind: scalar, scalar: text}
      value: {kind: scalar, scalar: text}
```

Выражение `{lookup: {in: {input: names}, key: {field: target}}}` возвращает
необязательное значение указанного типа. Отсутствующий ключ даёт отсутствие;
неоднозначность, цикл и неготовность дают различные диагностические коды
`fact.ambiguous`, `fact.cycle`, `fact.unready`. Их запрещено превращать в
отсутствующее значение. Ограничение нормального значения формулируется общим
`matchOptional`, без предметного обработчика поиска.

У входа объекта-владельца можно указать `index: project.names` рядом с `type`.
Компилятор проверяет наличие вкладов и совпадение структуры ключа и значения, а
сборка подставляет общий подготовленный индекс. Common не привязывает вход
к глобальному имени. На этом этапе привязка допустима у потребителя, который
сам не публикует вклады: многоступенчатая подготовка индексов через другие
индексы пока отклоняется явно. Несколько потребителей входят в тот же граф
подготовки; изменение файла затрагивает его индексы и только их потребителей.

У владельца достаточно `inputs: {names: {index: project.names}}`: тип выводится
из вкладов при сборке. Явный `type` остаётся допустимым и проверяется. Common
по-прежнему объявляет тип входа без имени глобального индекса.

Составной ключ задаётся обычным выражением записи, например
`{record: {owner: {input: owner}, kind: {literal: field}, name: {field: name}}}`.
Все компоненты — текст, набор имён одинаков у всех источников и потребителей.
Порядок записи компонентов в YAML несущественен: компилятор назначает позиции
по именам. Компоненты не склеиваются разделителем: `a.b` + `c` и `a` + `b.c`
остаются разными ключами. При поиске используется массив на стеке, без
создания промежуточной строки. Сейчас генерация принимает конструктор записи;
произвольное вычисление целого ключа-записи явно отклоняется.

Проверку обычного текстового common можно выразить через его вход индекса и
`lookup` от `self`. Владелец подключает его через `use` и `bind`, например
`{use: target, bind: {names: {input: targets}}}`. Компилятор подставляет входы
и переносит ограничение на поле при сборке; отдельного обработчика ссылки нет.
Начальная поддержка этого сочетания ограничена простым текстовым представлением
без параметров, условий присутствия и сокращений; другие сочетания явно отклоняются.

Индексы и содержащие их структуры нельзя сравнивать как смысловые значения; сравниваются результаты lookup. `isReady` проверяет полноту и поколение привязанного индекса.

Индекс передаётся на границе операции как общий неизменяемый объект с
поколением и идентификатором. Его нельзя подменить строкой или картой из YAML
входов; подготовка выполняется отдельно. Несколько правил разделяют данные,
а поиск возвращает заимствованное значение без выделения памяти. Начальная
генерация поддерживает текст или запись текстовых компонентов → текст; другие структуры не должны молча
приводиться к строкам. Привязка источника к входу принадлежит сборке операции,
а common знает только объявленный договор индекса.

Порядок подготовки задаётся графом объявленных зависимостей: источники →
проекции → индексы → потребители. Общий план не содержит имён метаданных.
Каждый узел выполняется один раз после всех входов; два потребителя разделяют
подготовку общего узла. При изменении источника устаревают он сам и только
достижимые потребители. Повторные рёбра не вызывают повторных вычислений.
Цикл в плане подготовки — ошибка декларации, а цикл в данных раскрываемого
объединения — состояние факта; эти случаи не смешиваются. План строится
нерекурсивно, проверяет ссылки на узлы и бюджет рёбер до публикации.

Раскрытие графа объединений готовится один раз для поколения. Узлы содержат
либо ссылку на конечное типизированное значение, либо список идентификаторов
других узлов, либо состояние недоступного факта. Это общий механизм объединения,
а не обработчик DefinedType: извлечение рёбер и допустимых конечных значений
остаётся частью декларации. Результат — множество идентификаторов конечных
узлов в стабильном порядке идентификаторов; одинаковое значение не копируется.
Одинарные цепочки разделяют готовый результат, поиск отдаёт заимствованный срез.

Подготовка использует нерекурсивный обход и обратные рёбра. Цикл и все зависящие
от него объединения получают состояние «цикл», даже если у них есть другие
готовые ветви. В ациклической части несколько причин недоступности объединяются
однозначно: «не готов» прежде «неоднозначно», затем «не найдено». Нельзя выдавать
частичное множество как готовое. Пустое объявленное объединение отличается от
неразрешённой ссылки и является готовым пустым множеством.

Общий бюджет ограничивает количество узлов, рёбер и сохранённых идентификаторов
раскрытия. Превышение возвращает отдельную причину незавершённой подготовки;
неполное поколение не публикуется и не заменяется пустым готовым индексом.
Эти ограничения задаёт операция, а не отдельный объект метаданных.

<a id="collections"></a>
## 8. Сложные коллекции

Существующий обзор требует следующих общих механизмов. Они входят в проект интерфейса; сложные отношения ниже нуждаются в отдельных полных примерах до реализации.

| Механизм | Что обязательно описать |
|---|---|
| `keyed-mapping` | Поля ключа/значения, физические вхождения, диагностический адрес, фактический и ожидаемый порядок; правило уникальности отдельно |
| `keyed-join` | Участники, ключи и кардинальность, отсутствие каждой стороны, порядок и обратное распределение полей; нельзя терять непарные элементы |
| `canonical-members` | Источник ожидаемых членов, восстановление сокращённых членов и различие отсутствующего/изменённого состава |
| `graph-expansion` | Рёбра подготовленного графа, результат, cache/visited, missing/cycle и лимиты; превышение лимита даёт диагностику, не обрезает результат |
| `state-relation` | Конечная таблица XML-состояний, YAML-значений и допустимых тегов для профилей cf/cfe/full/adopted |
| `resource` / `identity` | Типизированные запросы и вклады операции; имя и относительный путь как данные |

**D-15. Коллекция не равна словарю.** Первый повтор, последующие повторы и их порядок остаются адресуемыми. Проекция в карту не уничтожает исходную последовательность. Collection<T> отличается от T, который сам является коллекцией; это особенно существенно для DCS ParameterValue с ChoiceParameterLinks.

Общий вид `{firstBy: {in: выражение, as: имя, key: выражение}}` выбирает первые физические вхождения различных ключей в порядке источника. Это вид для вычисления условия, не замена исходной коллекции: полная последовательность продолжает хранить все вхождения и аннотации. Ключ должен иметь тип с точным сравнением; адрес выбранного вхождения сохраняется. Вычисление использует один проход и множество ключей, результат может быть итератором без второй полной модели.

Для совместимости I8nText условие пустоты определяется по firstBy(language): каждый выбранный язык должен быть основным с пустым content. По пустой последовательности условие истинно. Это отличается от each по всем физическим вхождениям. Например, ru=`""`, затем ru=`"Второй"` текущий isEmptyI8nText считает пустым; при skipEmptyToXML обычный атомарный экспорт отсутствует. Обратный порядок считается непустым. Это наблюдение требует отдельной проверки полного контрольного экспорта: пропуск непустого повтора не объявляется допустимой потерей, а поведение нового конвертера нельзя выбирать по одному атомарному помощнику.

Порядок I8nText проверяется по первым вхождениям уникальных языков: основной первым, остальные по существующему сравнению UTF-16. Исходный порядок не исправляется сортировкой. Служебные `#`/пустой код требуют условий применимости из [карточки I8nText](2026-09-10-common-declarative/02-text-style.md), а не единственного глобального исключения языка.

**Согласованное исправление дефекта TS.** Полный round-trip для ru=`""`, затем ru=`"Второй"` при skipEmptyToXML падает в TS с ошибкой «Не найдено вхождение 2 XML-сегмента Title; raw-границы [Title]». Пользователь выбрал исправление непосредственно в Rust без предварительного исправления TS. Оба физических вхождения и их порядок обязаны сохраниться. Условие skipEmptyToXML проверяет всю последовательность и не может игнорировать непустые повторы через firstBy. Это уточнение заменяет требование совместимости именно с ошибочным сокращением; остальные правила диагностики и аннотаций сохраняются. Контрольный экспорт обязан восстановить оба вхождения из окончательного YAML. Новое применение !xml этим решением не разрешается. Исходные TS-наблюдения и согласованное ожидание Rust разделены в tests/migration/i8n-duplicate-empty-observations.json.

**D-16. Эффекты принадлежат операции.** Чистое правило не открывает файлы, не создаёт UUID, не выполняет сетевые запросы и не меняет индекс. Операция один раз готовит нужные идентичности/ресурсы и передаёт их. Контрольное восстановление использует те же подготовленные идентичности. Вывод фактов не разрешает повторный обход всего объекта при каждом потребителе.

Первый исполняемый профиль ресурсов — необязательная группа альтернативных
файлов с неизменяемым содержимым. `resources` размещается в object/fragment
рядом с остальными договорами и переносится при compose. Никаких фиктивных
свойств в YAML и специальных функций Module/Template не требуется.

```yaml
resources:
- oneOf:
  - xml: {sequence: [{literal: Commands}, {input: name}, {literal: Ext}, {literal: CommandModule.bsl}]}
    yaml: {sequence: [{literal: Команды}, {concat: [{input: name}, {literal: '.bsl'}]}]}
  - xml: {sequence: [{literal: Commands}, {input: name}, {literal: Ext}, {literal: CommandModule.bin}]}
    yaml: {sequence: [{literal: Команды}, {concat: [{input: name}, {literal: '.bin'}]}]}
```

Каждая сторона вычисляет последовательность относительных сегментов пути.
В начальном профиле используются подготовленные входы, литералы, sequence
и concat; значения XML/YAML-узлов не читаются, IO отсутствует. Связи входов
перенумеровываются при композиции тем же общим механизмом. Пустая группа,
неизвестные ключи, неподходящий тип пути и неподдержанная зависимость — ошибки
декларации, а не незаметно пропущенные ресурсы.

У группы разрешён существующий `forEach: {in: {input: forms}, as: name}`.
Он разворачивает группу по подготовленной последовательности имён; сегменты пути
могут ссылаться на `{var: name}`. Проверяются те же типы выражений и подстановки
compose. В этом профиле источник перечисления — подготовленная последовательность
текста или её буквальная запись; XML/YAML не перечитываются. Ограничения групп,
маршрутов и байтов действуют на весь план, а не отдельно на каждого ребёнка.

Обычно найден ноль или один файл группы: отсутствие модуля допустимо,
пустой файл существует и сохраняется. Отсутствие всего каталога ресурсов
владельца также означает отсутствие файлов, если чтение завершилось NotFound. Несколько найденных альтернатив —
аномалия, выведенная из oneOf; все найденные файлы сохраняются по собственным
парным маршрутам. Отдельная декларация этой аномалии не пишется. Совпавшие
пути назначения разных исходных файлов не разрешают перезапись: такая группа
не публикуется. Повторный запрос той же пары источник/назначение использует
одну копию. Повторная ссылка на тот же файл не означает несколько альтернатив.

Общий Rust-план содержит пары проверенных относительных путей и группы;
направление выбирается операцией. Он не знает имён метаданных, папок и расширений. Сегменты
не могут быть пустыми, `.`/`..`, содержать разделитель пути, NUL или задавать
абсолютный/дисковый путь. Подготовка ограничивается бюджетом путей и байтов.

Файловый адаптер приложения проверяет нахождение источника внутри заданного
корня и копирует содержимое в отдельный временный каталог потоком, без полного
байтового содержимого файла в памяти. Он возвращает отложенную группу файлов
и диагностики. До передачи группы проектной операции выходной каталог
пользователя не меняется; ошибка или отмена удаляет временную группу.
Контрольный экспорт использует тот же подготовленный снимок, а не повторно
выбирает альтернативу по изменившемуся источнику.

Остаток каталога описывается парой префиксов вместо oneOf:

```yaml
- forEach: {in: {input: templates}, as: name}
  remainder:
    xml: {sequence: [{literal: Templates}, {var: name}]}
    yaml: {sequence: [{literal: Шаблоны}, {var: name}]}
```

Сначала определяются все явные пары файлов. Затем файловый адаптер один раз
обходит остаток дерева; исходные файлы, уже взятые явными парами, исключаются.
Остальные относительные пути и байты сохраняются. Это одинаково работает в
обоих направлениях: например, явная пара переносит Ext/Template.txt в Template.txt,
а остаток не создаёт вторую копию Ext/Template.txt. Нельзя одновременно указать
oneOf и remainder у одной группы. Предметные имена известны только декларации.

Действительно пустые каталоги сохраняются. Каталог, ставший пустым только после
исключения явно перенесённых файлов, не добавляется. Обход и полученные пути
ограничены бюджетами; конфликт назначения или невозможность прочитать дерево
не приводит к частичной публикации. Выход за исходный корень запрещён.

Тот же remainder используется для Ext/Help ↔ Справка. Перечень непосредственных
файлов с заданным суффиксом извлекается из уже подготовленного набора, без нового
обхода диска; имена упорядочиваются по байтам UTF-8. Декларация common.help-pages
описывает обычную последовательность Page, версию оболочки и YAML-default из
подготовленных страниц. Аномалии выводятся существующими механизмами коллекций
и контрольного восстановления, без отдельного обработчика Help.

Внешнее XML-свойство подключается к YAML владельца маршрутом file, описанным
ниже. Shared-definition остаётся следующим профилем.
Наличие файлового договора само по себе не завершает Help или Template.


### Внешний XML-файл свойства

В XML-маршруте поля необязательное `file` задаёт путь относительно каталога
владельца. Отсутствие `file` означает основной XML-файл. Например:

```yaml
- field: help
  file: [Ext, Help.xml]
  path: ['ep:Help']
```

Common описывает только Help/Page, атрибуты и значение коллекции. Выбор файла
принадлежит сборке владельца. Начальный профиль использует постоянные сегменты
пути; пустой путь, `.`/`..` и встроенные разделители запрещены. Одно внешнее
поле владеет всем соответствующим XML-файлом. Два поля не могут публиковать
один и тот же файл. Порядок обычных и внешних полей свободный; он задаёт порядок YAML, а не порядок файлового IO.

Подготовленные источники передаются отдельно от смысловых входов; содержимое
каждого файла передаётся читателю без построения второго общего XML-дерева.
YAML распределяется между свойствами одним существующим маршрутизатором.
Экспорт возвращает основной XML и отдельную группу внешних документов.
Отсутствие документа отличается от пустого корня; пустой результат внешнего
документа означает, что файл не создаётся. Каждая граница проверяется общим
механизмом восстановления, включая восстановление без исходного XML.



<a id="anomalies"></a>
## 9. Аномалии и восстановление XML

**Обязательный принцип, уточнённый пользователем.** Декларация описывает нормальные значения, структуру, представления и ограничения. Общий механизм сам выводит из них возможные отклонения. Отдельно перечислять аномалии, дублировать условия или писать предметные обработчики аномалий не нужно и не допускается.

Отклонение входных данных не должно прерывать преобразование или приводить к потере данных. Если смысл определим, сохраняются смысл и соответствующая пометка. Если смысл не определим либо обычный экспорт теряет исходную форму, сохраняется исходное представление на минимальной устойчивой границе. Выдумывать нормальное значение вместо нестандартного запрещено. Окончательный результат проверяется обратным преобразованием с восстановлением исходного XML; обработка остальных данных продолжается.

Пример: boolean объявляет только `true/false` и `Истина/Ложь`. Для `<Value/>` и `<Value>1</Value>` не добавляются отдельные условия аномалий: общий механизм выявляет несоответствие и сохраняет физическое свойство через `!xml/raw`, не придумывая Истина/Ложь. Пользователь согласовал эту область boolean; её реализация пока не завершена. Ранее согласованные области I8nText и FormattedI8nText сохраняются.

Невозможность разобрать повреждённый вход также требует общего пути сохранения исходного фрагмента или документа без потери байтов. Этот резервный путь необходимо реализовать и проверить; его готовность здесь не заявляется. Ошибки самого конвертера, противоречия декларации и сбои чтения/записи не маскируются под аномалии данных и успешное преобразование. Неполная реализация не является основанием обходить недостающую функциональность через raw.

**D-17. Сохраняется действующая методика.** Сначала определяется смысл, затем применяются ограничения, строится окончательный кандидат YAML и проверяется восстановление XML из этого кандидата и разрешённых фактов. Совпавшая смысловая ошибка и невосстановимая форма XML — разные исходы.

Ограничение объявляется один раз. Его диагностика при XML-импорте участвует в действующем механизме аннотаций; при проверке пользовательского YAML проверяется тот же договор с учётом разрешённых аннотаций. Условия применимости двух входов могут различаться, как в текущем I8nText со служебными языками.

**D-18. Аномалии следуют из самой декларации.** Это основной принцип: отдельный список аномалий, поле `annotations.contract`, повторные условия и отдельные функции проверки не требуются. Ограничение определяет смысловое нарушение и его точный адрес; описание именованной коллекции определяет повтор ключа; правила порядка определяют неканоническую последовательность. Эти сведения компилятор использует и для проверки, и для назначения/принятия `!xml/invalid`.

Невосстановимая физическая форма определяется контрольным преобразованием, а минимальная устойчивая граница её сохранения — владением XML-узлами в той же декларации. Наличие ошибки само по себе не разрешает поднимать raw до родителя или скрывать неизвестную конструкцию языка. Отдельного YAML-договора аномалий и ручного перечня их условий не вводится. Общий механизм тегов соблюдает действующую методику из [реестра XML-аномалий](../../../.agents/xml-anomalies.md); при переносе новых типов сохраняется требование согласовывать новые применения `!xml`. Согласованы границы I8nText, FormattedI8nText и простых скалярных свойств (boolean, string, number) по указанию распространить поведение на оставшиеся простые типы; готовность их реализации учитывается отдельно. Имена `!xml/*` являются частью формата пользовательского YAML, а не исполняемыми тегами исходника декларации.

Аннотации карты и языкового ключа принимают ошибки только своей точной границы. Префиксное совпадение пути запрещено: родительский тег не принимает дочернюю ошибку. Совмещённые теги проверяются независимо; лишний тег получает `xml/anomaly-tag-unnecessary` с существующим kind=`semantic`. Для повторов адрес включает occurrence. Три комбинации проверены в `tests/migration/i8n-annotation-contract.json`; вспомогательные fixture-коды этого файла не являются публичными кодами конвертера.

Наблюдения атомарного I8nText для всех сочетаний флагов записаны в `tests/migration/i8n-presence-observations.json`. Они включают типизированные пустые оболочки и nil. Обычный атомарный экспорт может не восстановить форму такого входа; это ещё не доказательство допустимости потери и не разрешение нового raw. Подтверждение минимальной границы и действующей регистрации требуется отдельно до включения случая в корпус полного round-trip.

Наличие ограничения выводит смысловую аномалию и её адрес, но не разрешает новое применение raw. Неизвестное правило, неполный resolver или неописанная конструкция языка не разрешают raw. Эта спецификация не расширяет набор разрешённых применений тегов.

Выпуск подробной диагностики несовпадения может использовать медленный путь. Обычное успешное восстановление должно переиспользовать подготовленные сведения и компактное описание границ XML; допустимая оптимизация не меняет точность проверки. Без референса экспорт обязан восстанавливать всё, что выводится из пользовательского YAML и индексов; границы невозможного восстановления остаются явными.

## 10. Примеры

### 10.1. Common: одна таблица для обоих направлений

Фрагмент показывает канонические непустые boolean-значения. Терпимые технические входы существующей TS-реализации и presence подключений должны быть описаны отдельно перед полным переносом Boolean.

```yaml
format: nkdk-declarations/1
kind: value
id: common.boolean
description: Логическое значение

value:
  kind: scalar
  scalar: boolean

representations:
  xml:
    kind: text
    values:
      - {value: true, text: "true"}
      - {value: false, text: "false"}
  yaml:
    kind: scalar
    values:
      - {value: true, literal: Истина}
      - {value: false, literal: Ложь}
```

Это задаёт `<Server>true</Server>` ↔ `Сервер: Истина` при подключении ниже. Имя Server не принадлежит common.boolean.

### 10.2. Rules: владелец задаёт место подключения

Пример — часть будущего `applied-objects/common-module/rules.yaml` для одного явно присутствующего поля. UUID, остальные поля, расширения, отсутствие/default и внешняя XML-оболочка здесь намеренно не заявляются описанными. Размещение модуля BSL относится к `topology`/`contributions` полного объекта.

```yaml
format: nkdk-declarations/1
kind: object
id: applied.common-module

imports:
  boolean: common.boolean

namespaces:
  md: "http://v8.1c.ru/8.3/MDClasses"

value:
  kind: record
  fields:
    - name: server
      type: {use: boolean}

representations:
  xml:
    kind: record
    fields:
      - field: server
        path: [md:Properties, md:Server]
  yaml:
    kind: mapping
    fields:
      - field: server
        key: Сервер
```

Правило владельца не повторяет таблицу Истина/Ложь и не содержит функции преобразования. Внутреннее имя `server`, XML-маршрут и YAML-ключ описаны явно. XML-пути отсчитываются от текущей границы объекта.

### 10.3. Коллекция сложных значений

Ниже связаны смысловая часть I8nText, оба представления и короткая строка. Пример описывает обычное непустое значение; presence, сворачивание имени, ограничения и аннотации должны быть включены в этот же компонент до полной приёмки.

```yaml
format: nkdk-declarations/1
kind: value
id: common.i8n-text

namespaces:
  v8: "http://v8.1c.ru/8.1/data/core"

inputs:
  defaultLanguage:
    type: {kind: scalar, scalar: text}

types:
  translation:
    kind: record
    fields:
      - name: language
        type: {kind: scalar, scalar: text}
      - name: content
        type: {kind: scalar, scalar: text}

value:
  kind: sequence
  item: {local: translation}

representations:
  xml:
    kind: element-sequence
    path: [v8:item]
    item:
      kind: record
      fields:
        - field: language
          path: [v8:lang]
        - field: content
          path: [v8:content]
  yaml:
    kind: keyed-mapping
    key: language
    value: content
    shorthand:
      - id: primary-language-string
        representation:
          kind: scalar
          scalar: text
          capture: text
        denotes:
          sequence:
            - record:
                language: {input: defaultLanguage}
                content: {capture: text}
```

`element-sequence` содержит только `kind`, `path`, `item`: path выбирает повторяющиеся элементы относительно текущей границы, item задаёт содержимое одного вхождения. `keyed-mapping` содержит `kind`, `key`, `value` и необязательный shorthand; key/value ссылаются на разные поля record-элемента. Ключ имеет тип text, value получает тип указанного поля. Поля record, не представленные ни ключом, ни значением, требуют явного восстановления; их молчаливое отбрасывание запрещено.

`capture` допускается у скалярного представления внутри shorthand и объявляет локальное имя соответствующего скаляра. Тип `scalar` обязан совпасть с типом захваченного выражения. Вне shorthand этот ключ запрещён. При обратном сопоставлении единственного конструктора sequence компилятор связывает capture с content и проверяет language против defaultLanguage. Два физических вхождения не совпадают с одноэлементным конструктором, даже когда языковые ключи одинаковы.

### 10.3.1. Проверенные условия переноса I8nText

Эта таблица фиксирует исходный договор для А1; она не утверждает, что грамматика профилей уже завершена. Основной язык в примерах — `ru`. `P`, `N`, `S`, `T` обозначают существующие preserveEmptyXML, excludeIfEqualNameYAML, skipEmptyToXML, typedXML; будущая декларация обязана выразить их сочетания без вызова функций common.

| Условие | Установленное поведение |
|---|---|
| Отсутствующее XML-значение | Обычный импорт возвращает отсутствие; default владельца исследуется отдельно |
| XML-контейнер без item | При P или N получается пустая коллекция и YAML `""`; иначе отсутствие |
| YAML `""`, N включён | Пустая коллекция, не один item с пустым текстом |
| YAML `""`, N выключен | Один перевод ru с пустым текстом; его XML зависит от P/S |
| Пустое значение, S включён | XML отсутствует; этот выбор предшествует P/N и T |
| Пустое значение, S выключен, P или N включён | Пустая XML-оболочка; текущий ранний выход не добавляет xsi:type даже при T |
| Непустое значение, T включён | xsi:type=`v8:LocalStringType` |
| Единственный неповторяющийся ru | Короткая строка YAML |
| Повтор ru с разным текстом | Хранить физические вхождения; короткая строка недопустима |
| N включён, основной текст точно выводится из имени | Сокращается только основной перевод; другие сохраняются |
| N включён, исходная непустая коллекция без ru | В YAML добавляется первый ru: `""`, запрещающий восстановление отсутствующего перевода из имени |
| YAML отсутствует, N включён | Восстановление из имени только при явном restoreExcludedEqualName и наличии имени |
| YAML содержит пустой маркер ru | Маркер удаляется из item; восстановление имени запрещено |
| `Форматированный: Истина`, поле Текст отсутствует | Допустимое значение formatted=true с пустой коллекцией |

**Области проверки не совпадают.** При XML-импорте незарегистрированный язык помечается на соответствующем вхождении; `#` и пустой код освобождают только собственное вхождение. При YAML-проверке наличие хотя бы одного `#` или пустого кода отключает весь блок проверок порядка, регистрации и пустоты текста для этой карты. Структурная схема при этом сохраняется. Нельзя унифицировать эти условия ценой изменения поведения.

**Порядок и повторы.** Каноничность проверяется по первым различным кодам: основной впереди, остальные по сравнению кодовых единиц UTF-16. Физические повторы сохраняются независимо от этой проверки. Совмещённые аннотации карты и ключей проверяются отдельно; карта не должна терять второе или третье вхождение из-за словаря уникальных ключей.

**Вывод текста из имени.** Текущий алгоритм классифицирует только `[A-ZА-ЯЁ]`, `[a-zа-яё]` и `[0-9]`, игнорирует прочие символы и по-особому группирует цифры и аббревиатуры. Общий Unicode word-break не эквивалентен ему. Примеры договора: `TestTest` → `Test test`, `BackInUSSR` → `Back in USSR`, `ИсторияКПП` → `История КПП`. Новый общий текстовый механизм должен задавать классы и переходы декларативно; недопустима скрытая функция «синоним». Пограничные входы вне этих алфавитов требуется проверить до утверждения грамматики.

Источники: i8nText/{fromXML,fromYAML,toXML,toYAML,fromXMLToYAML}.ts, formattedI8nText/fromYAML.ts, runtime/metadata/validation/localizedTextYAML.ts и runtime/metadata/helpers/canConvertToPascalCase.ts; ревизия договора записана в tests/migration/baseline.json.

### 10.4. Межполевая проверка в rules

Следующая секция включается в Catalog, где `codeType` и `codeLength` уже объявлены. Это перевод существующего `maximumWhen` числового правила; `Number` — смысловой вариант перечисления, не пользовательский текст. Базовые границы 0..50 задаются при подключении Number. Приведённый диагностический код учебный; при переносе нужно сохранить действующую диагностику.

```yaml
constraints:
  - id: numeric-code-length
    appliesTo: [xml-import, yaml-validation]
    when:
      eq:
        - {field: codeType}
        - {literal: Number}
    assert:
      lte:
        - {field: codeLength}
        - {literal: 38}
    diagnostic:
      code: example.numeric-code-length
      severity: error
      at: {field: codeLength}
      message: Числовой код не может быть длиннее 38 знаков
```

При неготовом codeType проверка ждёт объявленной зависимости. Если поле содержит ошибку типа, зависимая проверка сообщает о невозможности проверить связь согласно принятому договору диагностик, а не сравнивает строку с числом или добавляет произвольный default.

<a id="rules-migration"></a>
## 11. Перенос rules.ts

**D-19. Rules тоже являются данными.** Целевой файл владельца — `rules.yaml`. Его смысловые поля, XML/YAML-привязки, defaults, ограничения, состав детей и вклад в топологию записываются тем же языком, что common. Конечная система не требует TypeScript-построителя поверх YAML.

Существующие исходники показывают разные классы работы, поэтому переименования расширения файла недостаточно.

| Сегодня | Целевое описание | Проверка полноты |
|---|---|---|
| `booleanRule`, `numberRule`, `i8nTextRule` | `use` и типизированный `with`/`bind` | Все используемые параметры имеют договор |
| `properties`, `xml`, `xmlParents`, `yaml` | Record и представления полей | Однозначные маршруты и сохранённые публичные имена |
| `typeSE` и таблицы перечислений | Импорт отдельной enum-декларации | Варианты, алиасы, каноническая запись и namespace |
| `xmlOrder`, order от референса | Договор порядка представления | Исходный и резервный порядок, дети и атрибуты не смешаны |
| `implicitValueYAML`, `defaultValueXML`, `defaultValueXMLEmpty` | Presence и каноническое восстановление | Отсутствие, явный default, пустота и nil отдельно |
| `defaultValue: function` | Общее типизированное выражение | Все поля/входы явны; нет эффекта и скрытого контекста |
| `toXML: function` для adopted defaults | Отношение состояний и зависимость от объявленных полей | Полная матрица cf/cfe/full/adopted и изменённых свойств |
| Spread и `composeMetadataItemRule` | Fragment/compose с параметрами | Коллизии отвергаются, overrides не исчезают |
| `metadataTarget`, `uniqueNameScopes` | Reference/constraints и индексные вклады | Существование, допустимый вид, rename/reference occurrences |
| `moduleRule`, childFileItemNames, внешние файлы | Topology/resource со структурированными шаблонами путей | Обе стороны, владельцы, альтернативы, пустые файлы |
| `propertyStates.ts` | Декларативные профили и таблицы state-relation | Допустимые состояния и точные области их применения |
| Registry с функциями | Каталог деклараций, построенный при сборке | Нет скрытого special-case по id или itemType |

Примеры фактических источников: [CommonModuleRules](../../../packages/rules/metadata/appliedObjects/metadataCommonModule/rules.ts), [CatalogRules](../../../packages/rules/metadata/appliedObjects/metadataCatalog/rules.ts), [фрагменты MetadataAttribute](../../../packages/rules/metadata/commonObjects/metadataAttribute/fragments.ts), [композиция фрагментов](../../../packages/rules/metadata/commonObjects/metadataRuleFragment.ts), [InputFieldRules](../../../packages/rules/metadata/forms/elements/inputField/rules.ts).

**D-20. Учёт каждого исключения.** При переносе конкретного rules составляется таблица «исходное поле/ветвь → декларация → независимый пример». Неописанная функция остаётся открытым пунктом. Нельзя объявить объект перенесённым, оставив Rust/TS callback «временно» внутри целевого языка.

Упорядочивание работ: подтвердить общие конструкции на common → описать соответствующий rules целиком → сравнить обе стороны и диагностики → расширять покрытие владельцев. TS и Rust при сравнении выполняют целые одинаковые операции отдельно; постоянной передачи объектов между ними не требуется.

Это порядок проектирования и будущего переноса, не разрешение выполнять реализацию в текущей задаче. Ранее принятые ограничения предметной проверки сохраняются; переход в YAML не закрывает автоматически недостающую проверку CharacteristicsDescription или AdditionalIndex.

## 12. Компиляция, скорость и сопровождение

**D-21. Исходный YAML не исполняется на каждом объекте.** Сборка читает декларации, проверяет версии/импорты/типы/обратимость допустимых конструкций, раскрывает композицию и статические параметры, затем выдаёт специализированный Rust-код. Динамические факты остаются входами операции и не запекаются в результат сборки.

```text
common/*.yaml + */rules.yaml
            ↓
разбор и проверка общего языка
            ↓
типизированное описание и специализация
            ↓
Rust: XML→YAML | YAML→XML | validation
            + схемы, каталог зависимостей, позиции исходных деклараций
```

**D-22. Минимум промежуточных данных.** Горячий путь не читает YAML-декларацию, не ищет обработчик по строковому имени и не строит цепочку XML-модель → универсальный объект → JSON → YAML-модель. Временное типизированное значение допускается там, где нужно для зависимостей, коллекций и проверки восстановления; оно не обязано материализовать каждый узел языка отдельным выделением памяти.

**Настоящая декларативность (уточнение пользователя).** Общий Rust-обработчик не является местом накопления частных случаев common-объектов. Компилятор различает конструкции языка (`sequence`, `record`, представления, ограничения), а предметные имена, значения, сокращения и условия находятся в YAML. Переименование объекта и его XML/YAML-полей при сохранении структуры не должно требовать изменения Rust. При переносе нового семейства проверять этот принцип отдельно; нехватка общей конструкции не оправдывает условие по имени объекта внутри общего обработчика.

Одинаковые входы/индексы подготавливаются один раз. Ссылки на входной буфер заимствуются, когда это допускает время жизни; декодирование XML entities, изменение текста и запись результата могут требовать памяти. Обещания полного zero-copy для любого преобразования нет.

**D-23. Валидация без построения XML.** Те же constraints работают над разобранным YAML и подготовленными фактами. Компилятор может объединять обходы, если сохраняются порядок зависимостей, результаты и диагностические адреса. Отдельная validation не генерирует XML и не публикует файлы ради повторного использования преобразователя.

Для 10× сравниваются одинаковые законченные операции на согласованном e2e-наборе, одинаковые входы/выходы и условия кэша. Учитываются разбор данных, подготовка фактов, преобразование, proof, запись и диагностика; отдельно фиксируются холодный запуск, время сборки и размер исполняемого файла. Измерение одного скалярного перехода не является результатом всего конвертера.

**D-24. Удобство изменения человеком и ИИ.** Схема исходного языка проверяет имена ключей и структуры; типизатор проверяет imports/with/bind и совместимость. Диагностика генератора указывает YAML-файл, строку и связанное объявление, даже если ошибка обнаружена в сгенерированном Rust. Сгенерированный код вручную не редактируется.

Из того же типизированного описания получаются документация полей, схема пользовательского YAML в выражаемой части и граф зависимостей. Схема **языка деклараций** отдельно сопровождает грамматику компилятора; схема **пользовательских данных** генерируется из конкретных деклараций. Это два разных продукта, их нельзя подменять друг другом.

Схема реализованной грамматики: [nkdk-declarations.schema.json](../../../schemas/nkdk-declarations.schema.json), команды описаны в [schemas/README.md](../../../schemas/README.md). Она проверяется независимым валидатором на корпусе допустимых деклараций и структурных ошибок. Исходные ограничения YAML и семантические проверки остаются в `parse/link`; JSON Schema не объявляет их выполненными.

Изменение `format` требует явной миграции исходников; новая версия синтаксиса не меняет неявно значения пользовательского YAML. Хэш результата учитывает декларации, все транзитивные импорты и версию компилятора. Генерация детерминирована и не зависит от порядка обхода файловой системы.

## 13. Проверки и незакрытые договоры

### 13.1. Критерии языка

- Ошибочная декларация отвергается до преобразования данных: неизвестный ключ, повтор id, импорт не из разрешённого слоя, цикл композиции, отсутствующий параметр, несовместимый bind, коллизия пути, неоднозначный variant или сокращение без восстановления.
- Для record/sequence/choice проверяются содержательные свойства и граничные случаи. Для join отдельно проверяется обратное распределение, для graph-expansion — цикл/missing/лимит.
- Runtime-ошибка значения отличается от ошибки декларации и от неготового факта; диагностика сохраняет точный адрес вхождения.
- Статическая проверка заявляет гарантии только для определённого подмножества конструкций. Произвольная эквивалентность выражений не считается решённой; спорные случаи ограничиваются или требуют проверяемого отношения.
- Дубли исходников и архитектурные импорты проверяются до генерации. Повторяющиеся фрагменты сгенерированного Rust не считаются автоматически дублированием предметных правил.

### 13.2. Критерии переноса объекта

Один набор независимых примеров задаёт XML, канонический YAML, допустимый обратный результат и ожидаемые диагностики. Те же случаи используются для двух направлений и проверки; не создаётся отдельный unit-test на каждую строку декларации. Общие операторы проверяются один раз, сочетания механизмов — на сложных представителях.

Существующие XML-фикстуры не изменяются. Эталон нельзя сгенерировать из проверяемой декларации и использовать как доказательство её правильности. Сравнение с TS дополняется действующим документированным договором: случайный дефект старой реализации не принимается молча за новое требование.

### 13.3. Что остаётся развернуть

Редакция 0.2 не является готовой спецификацией всего компилятора. Дополнения вносятся сюда последовательно с номером редакции и связанным проверочным примером.

Детали существующего поведения уточняются по исходникам и фикстурам без перекладывания исследования на пользователя. Отдельное решение пользователя потребуется, если обнаружится необходимость изменить публичный формат, усилить действующую проверку или разрешить новое применение `!xml`; такой вопрос формулируется с конкретным примером и вариантами после исследования.

Карточки [исследования common](2026-09-10-common-declarative/README.md) сохраняют наблюдения и источники. Этот файл становится единым местом развития **синтаксиса языка**; прежний [эскиз интерфейса](2026-09-10-common-declarative/10-interface.md) остаётся исследовательским материалом. При противоречии примеров синтаксиса применяется более новая редакция этого документа; фактический договор переноса проверяется по источникам и фикстурам.

### Передача параметров вложенному значению

`with` принимает литерал или ссылку на статический параметр текущей декларации: `with: {excludeIfEqualNameYAML: {parameter: excludeIfEqualNameYAML}}`. Типы должны совпадать; неизвестное имя и данные операции вместо параметра отвергаются. При сборке владельца ссылка заменяется постоянным аргументом до генерации Rust. Составной объект переиспользует режимы вложенного значения без копирования его правил.

### Сохранение формы составного текста

Для FormattedI8nText пользователь подтвердил существующую оболочку свойства `!xml/raw`, в частности `_formatted: null`, когда обычный экспорт добавляет отсутствующий в исходнике атрибут. Необходимость сохранения выводится из декларации и доказанного расхождения контрольного экспорта; отдельного предметного условия или реестра аномалий нет.

Порядок XML-атрибутов остаётся значимым. Если точечные изменения не восстанавливают порядок, `$xml` перечисляет все сохраняемые атрибуты в исходном порядке, без копирования неизменившихся дочерних элементов. Полностью перечисленные атрибуты задают порядок; неполный набор сохраняет обычный порядок и добавляет новые атрибуты в конце. Пустая карта `{}` означает отсутствие изменений; пустое значение сохраняет отдельный договор пустого XML-узла.


### Сохранение пространств имён в скалярной аномалии

Если для имени XML в сохраняемом фрагменте нет объявленного префикса, общий формат использует `{URI}локальноеИмя` (для атрибута — с обычным префиксом `_`). Это не новая настройка декларации. Восстановление получает пространство имён из самого фрагмента; `xsi:type` учитывается как XML-имя с пространством имён, поэтому смена префикса не меняет смысл контрольного сравнения. Обычные скалярные значения не строят такое представление.
## Уточнение скалярного присутствия и календарных представлений

`presence` скаляра задаётся в common (`target: self`) либо в правиле владельца (`target: {field: имя}`). Полная запись владельца заменяет запись common для этого свойства. Отсутствие может обозначать `absent` или типизированную константу; `yaml.omitWhen` использует общие выражения. Если правило исключает явное значение из YAML, генератор и схема проверяют это одинаково. Сохранение явного default выражается отсутствием условия сокращения; дополнительного флага языка не требуется. При недоступном значении, которое читает условие сокращения, сокращение не применяется.

XML-оболочка `with-attributes` применяется и к скалярам. Постоянный `xsi:type` выводится непосредственно при записи, без промежуточного дерева; несовпадение исходной формы сохраняется общим контролем обратимости. Условия атрибутов скалярного генератора пока не реализованы и явно отвергаются при сборке.

Для скаляра с материализуемым значением по умолчанию `$xml: null` отменяет материализацию отсутствующего XML-свойства. Пустой существующий узел сохраняется отдельной непустой YAML-записью XML-формы (`{}` для самостоятельного пустого узла, `""` для замены содержимого и атрибутов). Старое чтение `$xml: null` как пустого boolean без материализуемого default сохранено. Значение отсутствия выводится из договора присутствия, а не из предметной проверки имени свойства.

Календарное представление записывается так:

```yaml
value: {kind: scalar, scalar: text}
representations:
  xml: {kind: calendar, format: iso, zone: written}
  yaml: {kind: calendar, format: day-month-year, precision: minutes, zeroTime: omit}
```

`precision` принимает `minutes` или `seconds`, `zeroTime` — `omit` или `keep`. `written` означает сохранение записанных компонентов часов без пересчёта часового пояса — пользователь явно выбрал эту политику. Смещение, дробные секунды и потерянные при минутном представлении секунды сохраняются общим механизмом XML-разницы. Само календарное значение хранится компактными числовыми компонентами, без обращения к системному часовому поясу. Нормальный профиль ограничен положительным четырёхзначным годом, существующей календарной датой и временем 00:00:00–23:59:59; остальные XML-формы сохраняются как аномалии. Схема проверяет форму записи, полная проверка календаря выполняется в Rust. Границы смещения сверяются с [договором XSD dateTime](https://www.w3.org/TR/xmlschema11-2/#dateTime); нормальный профиль не объявляется полной реализацией всей лексики XSD.


### Короткое ограничение текста

```yaml
value:
  kind: scalar
  scalar: text
  pattern: '[A-Za-zА-Яа-яЁё_][A-Za-zА-Яа-яЁё0-9_]*'
```

`pattern` проверяет всю строку. Из него выводятся ограничение `value.pattern`, проверка XML/YAML и смысловая пометка нарушения; отдельная декларация аномалии не нужна. Для ссылочного поля ограничение common переносится на поле владельца. Автомат регулярного выражения строится при сборке; Rust использует готовые таблицы. Сокращённая форма доступна корневому текстовому common; сложные выражения могут использовать `matches: {value: выражение, pattern: шаблон}`.


При совпадении сокращаемого значения с default исходная неканоническая запись не должна скрывать доступный смысл: `-0.00` сохраняется как `$значение: 0` вместе с `$xml: "-0.00"`. Если таблица намеренно не имеет YAML-записи для значения (например, ложный сокращаемый флаг), новую запись компилятор не выдумывает. Обычный путь сокращения остаётся без разбора XML-дерева; добавление смыслового поля происходит только при доказанном расхождении или уже найденной аномалии.

### М1: размеченный выбор скалярного значения

Начальный профиль объединяет текст и точное число без отдельного предметного преобразователя:

```yaml
value: {kind: scalar-choice, variants: [text, number], profile: decimal}
representations:
  xml:
    kind: scalar-choice
    attribute: xsi:type
    empty: absent
    cases:
      - scalar: number
        in: [xs:decimal, xs:integer, xs:double, xs:float]
        emit: xs:decimal
    otherwise: text
  yaml: {kind: scalar-choice}
```

`in` содержит QName, раскрываемые через `namespaces`: смена префикса не меняет выбор. `emit` задаёт канонический QName числового варианта; при его отсутствии XML-атрибут не печатается. В текстовом варианте атрибут не печатается. XML без подходящего дискриминатора имеет текстовый смысл, даже если текст похож на число. Пустой XML имеет смысл отсутствия; существующий узел сохраняется общим механизмом отличий от обычного экспорта. Отсутствие самого свойства задаётся обычным presence.

YAML выбирает вариант по типу скаляра: кавычки сохраняют строковый тип `"001"`, число читается как точное десятичное значение. Невозможность разобрать выбранное XML-число не переключает его на текст и не подставляет ноль. Нестандартные QName, дополнительные атрибуты, исходная числовая запись и пустота сохраняются общим механизмом аномалий и проверяются обратным преобразованием. При семантически неизвестном XML-типе действует явно объявленный текстовый вариант, а атрибут сохраняется как отличие XML.

Компилятор проверяет однократное перечисление вариантов, непустую таблицу, отсутствие повторных QName и принадлежность `emit` выбранному варианту. Реализованный профиль ограничен текстом/числом, одним числовым множеством и QName-дискриминатором `xsi:type`; внешняя композиция атрибутов этого профиля пока отвергается. Это первая часть общего выбора, не заявление о поддержке всех составных вариантов языка.

StringOrNumber использует профиль без `emit`; PredefinedCode — с `emit: xs:decimal`. Эти различия находятся только в декларациях. Для XML→YAML неизменность исходного XML подтверждается proof; для вновь написанного YAML число у StringOrNumber намеренно экспортируется без типа, как в существующем договоре. Поэтому равенство смыслового типа после дополнительного YAML→XML→YAML для такого нового числа не обещается: у XML без типа смысл текстовый. Изменять этот публичный договор без отдельного решения нельзя.


### Скалярные профили: параметры, разделитель числа и пустая XML-форма

Постоянные аргументы `with` скалярного common разрешаются при сборке. Одинаковые наборы аргументов используют одну специализацию; в преобразование отдельный контекст параметров не передаётся. Условия из постоянных логических выражений упрощаются при сборке. Оставшееся условие атрибута от значения компилируется тем же механизмом выражений, что и ограничения/сокращения. Отсутствующее скалярное значение не вычисляется как текст или число. Атрибуты выбираются без создания динамического списка в куче.

Например, `typedXML: false` убирает атрибут полностью. У типизированного текста `typeForEmptyXML: false` добавляет тип только при непустом значении. Это параметры конкретной декларации, а не новые встроенные признаки каждого common. Скаляры с входами подготовленных индексов или непостоянными аргументами пока требуют следующего слоя связывания; компилятор не игнорирует их.

Для точного числа XML-представление может задать разделитель:

```yaml
value: {kind: scalar, scalar: number, profile: decimal}
representations:
  xml: {kind: text, decimalSeparator: ",", acceptDecimalSeparators: [".", ","]}
  yaml: {kind: scalar, scalar: number}
```

Без этих настроек сохраняется обычная десятичная точка. Если указан только разделитель, принимается только он. Допустимы точка и запятая; повторяющийся список или список без выходного разделителя запрещён. Разделители тысяч не поддерживаются. YAML всегда хранит точное число с точкой. При чтении запятая заменяется в уже полученном буфере, без промежуточного числа с плавающей точкой. Исходные тип, разделитель, лишние нули и прочие различия восстанавливает общий механизм аномалий.

Отсутствие смыслового значения может иметь обычное XML-представление `nil` или пустой элемент, заданное существующим `presence`. Например, договор свойства владельца:

```yaml
presence:
  - target: {field: value}
    xml:
      missing: {denotes: {absent: true}}
      empty:
        - {form: empty-element, denotes: {absent: true}}
        - {form: nil, denotes: {absent: true}}
      canonical: [{when: {not: {present: {field: value}}}, form: nil}]
    yaml: {missing: {denotes: {absent: true}}}
```

Для этого профиля отсутствующий YAML экспортируется как элемент с `xsi:nil="true"`. Такой исходный XML не получает аномалию; отсутствующий узел или иная пустая оболочка сохраняют отличие для обратного восстановления. Обычное пустое состояние распознаётся до числового разбора, без создания ошибки. Пустая оболочка не получает атрибуты обычного непустого значения. Начальная поддержка скаляров ограничивает `canonical` одним условием отсутствия собственного значения и формами `missing`, `empty-element`, `nil`; иные формы/условия отвергаются при сборке, а не пропускаются.


Календарный литерал в смысловом выражении/default записывается в ISO, как значение календарного скаляра: `literal: "0001-01-01T00:00:00"`. При сборке компилятор проверяет дату и создаёт константу из компонентов; при каждом отсутствующем свойстве строка повторно не разбирается. При выводе структурной схемы тот же литерал переводится в объявленную форму YAML. Поэтому сокращение первой даты года запрещает явное `01.01.0001`, а не недопустимую для YAML строку ISO. Проверка календаря общая для входных строк и констант.


### Компактные перечисления и упаковка каталога

Для большого набора однотипных деклараций вводится упаковка `kind: catalog`: обязательные `format` и непустой список `declarations`. Элементы списка — обычные декларации того же языка; только format наследуется от упаковки. Вложенные каталоги и неявное слияние параметров/импортов не допускаются. Идентификаторы разрешаются в общей области с обычными файлами; повтор остаётся ошибкой. Каталог не является типом значения и не попадает в runtime.

Короткое перечисление — `kind: value` с `enum` вместо value/representations. Карта `enum: {Number: Число, String: Строка}` задаёт смысловые варианты и их YAML-названия; имя варианта одновременно определяет обычный XML. Необычный вариант записывается как `Switch: {yaml: Переключатель, xml: Switcher, accept: [Switch]}`. Полная и короткая формы не смешиваются. Порядок карты не имеет смыслового значения. Состояния отсутствия/default и остальные договоры продолжают задаваться обычными presence/constraints; упаковка не придумывает их.

`accept` относится только к входной XML-записи и не расширяет YAML-схему. Внутри таблицы канонические и принимаемые записи не могут противоречить друг другу. Различие принятой записи с канонической сохраняется общей обратной проверкой. Никаких отдельных функций для CheckBoxType или RadioButtonType в Rust не требуется.


У перечисления могут быть статические `projections: [{id, xml}]`. Проекция наследует смысловые варианты, YAML и остальные договоры, заменяя только XML-представление; это отдельный связываемый идентификатор, а не переключатель во время преобразования. В `xml: {kind: text}` без values компилятор выводит тождественную запись смысловых вариантов. Обёртка with-attributes использует ту же форму. Так типизированный профиль DCS задаёт xsi:type и исходное имя варианта один раз, не копируя русскую таблицу. Проекции ограничены common enum; вложенные проекции и переопределение смыслового типа/YAML не допускаются.

При выводе тождественной XML-таблицы проекция сохраняет ранее принимаемые записи common, включая прежнюю каноническую запись, если она отличается от смыслового имени. Так типизированный Switch остаётся каноническим, а Switcher читается с тем же смыслом и сохраняется как отличие XML. Пересечение альтернатив с другими вариантами проверяется при связывании.

Если обязательный скаляр отсутствует в XML и декларация не задаёт нормального смысла отсутствия, общий механизм сохраняет отсутствие через существующую оболочку свойства с `$xml: null`. Значение не выдумывается; отдельное правило аномалии не требуется. Обычный YAML без обязательного поля по-прежнему получает диагностику валидации.

Диспетчер скомпилированных операций выбирает функцию до создания значения. Стек разных ветвей не суммируется: размер каталога не должен создавать кадр стека, вмещающий временные данные всех операций. Проверка полного каталога выполняется с обычным размером стека потока.

### Вложенная запись со скалярными полями

Запись common использует обычные `value.fields`, относительные XML-маршруты и YAML-ключи. Владелец задаёт путь оболочки и один YAML-ключ; при сборке XML-маршруты соединяются. XML-атрибуты оболочки задаются существующим `with-attributes`. Начальный исполняемый профиль поддерживает одного такого потребителя, статические атрибуты и обычное отсутствие записи; неподдержанные параметры, условия и ограничения композиции отклоняются при сборке.

Отсутствующая запись отличается от присутствующей записи с отсутствующим обязательным полем. Первая не порождает вложенных значений; вторая сохраняет аномалию отсутствующего поля. Нормальный вложенный YAML разбирается одним потоком событий, без промежуточного документа. Аномалия скаляра сохраняется внутри записи; отличие оболочки и структура, которую нельзя выразить её полями, сохраняются на границе записи. Эти границы выводятся из композиции, а не из отдельного перечня аномалий.

Календарь с `precision: seconds, zeroTime: keep` всегда выводит часы, минуты и секунды, включая полночь. Для standardPeriod не вводится условие «начало не позже окончания». Профили вариантов StandardPeriodVariant и StandardBeginningDateVariant в пространстве data/core отличаются от XML DCS с пространством data/enterprise и задаются статическими проекциями общей таблицы.

### Основа обратимого строкового шаблона

Первый низкоуровневый профиль `core::text_pattern::Pattern<N>` — проверенная при
подготовке череда непустых литералов и нумерованных слотов. Каждый слот встречается
ровно один раз; соседние слоты неоднозначны и запрещены. Соседние литералы должны
быть объединены компилятором. XML- и YAML-шаблон могут располагать те же слоты
в разном порядке; перевод содержимого слотов выполняют их объявленные типы.

Чтение полностью потребляет строку, ищет первый следующий литерал и не возвращается
назад для подбора альтернатив. Результат — массив срезов исходной строки без копий
и динамического словаря. Пустой слот не равен отсутствию: допустимость пустого
значения определяет тип слота. Вложенные варианты, повторения и escaping ещё
не входят в этот профиль; это не готовая грамматика всех ссылок.

Печать добавляет результат в переданный буфер с ограничением числа новых байт.
Она проверяет, что результат читается в те же слоты, включая наложение разделителя
на конец значения. При отказе исходное содержимое буфера сохраняется. Например,
слот `ab` перед литералом `aba` не разрешается молча печатать так, чтобы при чтении
получился пустой слот. Эта защита общая, без условий по именам common.

Запись фиксированного `text-pattern` в YAML и проверка типов полей подключены к
синтаксису, связыванию и схеме языка. Генерация обоих преобразований подключена
для парных шаблонов с текстовыми и табличными слотами (boolean/enum). Шаблон
готовится один раз; разбор заимствует части исходной строки, проверка разделителей
не строит временную выходную строку. Нарушения структуры сохраняются общим
механизмом аномалий свойства; отдельного реестра аномалий шаблона нет.
Ограничения самого шаблона и его скалярных common-полей переносятся на
свойство владельца при сборке. Смысловое нарушение сохраняет разобранное
значение с `!xml/invalid`; нарушение структуры использует общий raw-механизм.
Отдельно объявлять аномалии шаблона не нужно. Структурная JSON Schema отмечает
необходимость проверки строкового представления сгенерированным валидатором.
Числовые и календарные слоты, динамические входы шаблона и повторения ещё не подключены;
наличие механизма не завершает metadataPath.


#### Короткая запись фиксированного шаблона

Для значения-записи XML и YAML могут независимо использовать `text-pattern`:

```yaml
representations:
  xml:
    kind: text-pattern
    parts: [{field: domain}, {literal: '::'}, {field: name}]
  yaml:
    kind: text-pattern
    parts: [{literal: '['}, {field: name}, {literal: '] '}, {field: domain}]
```

`field` ссылается на поле `value.fields`; `literal` — строковая постоянная,
без неявного приведения чисел и boolean. Каждый элемент содержит ровно один
из этих ключей. Соседние литералы объединяются, пустые удаляются при чтении
декларации. После этого два соседних поля запрещены. В каждом представлении
каждое смысловое поле встречается ровно один раз. Неизвестное поле, повтор,
потеря поля и вложенная запись в слоте отвергаются при сборке. Коллекция
допустима только как последний хвост по договору композиции ниже.
Ссылки на скалярные common и перечисления проверяются по разрешённому типу.

Шаблон относится к физической форме XML-текста или YAML-скаляра; его смысл
остаётся записью. Он не объявляет обработчик, не содержит кода и не читает
окружение. Повторения, альтернативы, escaping и сокращения не подразумеваются
этой начальной формой и будут описываться отдельными общими узлами.

#### Фиксированные части с общим разделителем

Согласовано 12 сентября 2026 года: `text-pattern` может указать непустой
`separator`. Тогда каждый элемент `parts` — одна часть, разделитель между
частями вставляется автоматически. Части-поля не поглощают разделитель,
включая последнее поле. Без `separator` сохраняется прежняя свободная грамматика.

```yaml
yaml:
  kind: text-pattern
  separator: '.'
  parts:
  - {literal: ЖурналДокументов}
  - {field: journal}
  - {literal: Форма}
  - {field: form}
```

Короткая форма с тем же разделителем и `parts: [{field: form}]` содержит
ровно одну часть. Компилятор доказывает непересечение короткой и полной формы
по их синтаксису; порядок вариантов и ограничения имён не используются
как приоритет. Неверное имя внутри однозначной формы остаётся обычной аномалией
значения. Лишняя часть нарушает форму и сохраняется общим механизмом XML.

Пустые части не выбрасываются; их допустимость определяется типами полей.
Литерал обозначает одну фиксированную часть и не может содержать разделитель
или создавать его раньше положенной границы. Многосимвольные разделители
проверяются с учётом перекрывающихся префиксов. Обратная запись проверяет
границы до изменения выходного буфера. Неоднозначность обычных форм остаётся
ошибкой декларации, а не поводом выбрать первую ветвь.

Компилятор разворачивает короткую запись в обычные литералы и ограниченные
слоты при сборке. Во время преобразования не нужен список разделённых строк
или перебор вариантов. Подготовленные значения пропущенных YAML-слотов
восстанавливаются существующим `yaml.default`; новый механизм сокращений
для форм не вводится. Начальный профиль ограничен фиксированными скалярными
слотами: коллекция не считается одной частью.

#### Необязательная группа текстового YAML

Группа описывает части строки, которые исключаются вместе. `optional`
ссылается на управляющее поле, а условие берётся из его существующего
`yaml.omitWhen`. Значения отсутствующих частей восстанавливаются через
`yaml.missing`; отдельных функций сокращения и восстановления нет.

```yaml
representations:
  yaml:
    kind: text-pattern
    parts:
    - {field: path}
    - optional: index
      parts: [{literal: '('}, {field: index}, {literal: ')'}]
presence:
- target: {field: index}
  xml: {missing: {denotes: {literal: 0}}}
  yaml:
    missing: {denotes: {literal: 0}}
    omitWhen: {eq: [{field: index}, {literal: 0}]}
```

Для `{path: alpha, index: 0}` запись — `alpha`, для индекса 2 — `alpha(2)`.
Полная запись `alpha(0)` также принимается и даёт тот же XML: условие группы
задаёт каноническое сокращение, а не запрет полной формы. В отличие от
отдельного YAML-поля, часть строки не требует отдельного ключа или отметки.

Каждая группа начинается непустым литералом и содержит управляющее поле.
Управляющие поля не повторяются, все исключаемые поля имеют восстановление
из `yaml.missing`. Начальные литералы доступных необязательных групп не
пересекаются по префиксу; неоднозначный договор отвергается при сборке.
Несколько групп и вложенные группы обрабатываются одной грамматикой;
перебор всех комбинаций форм не создаётся. Если значение занимает разделитель
и потому не восстанавливается из обычной строки, общий механизм сохраняет
его XML как аномалию. Перечень таких случаев в декларации не пишется.

Текущая генерация подключена к XML-записи с текстовым YAML, в том числе
при размещении как свойства. Для XML-текстового шаблона и режима общего
`separator` необязательные группы пока явно запрещены; это оставшаяся
граница реализации, а не отдельный обработчик TypeLink.

Обычные фиксированные шаблоны сохраняют прежний прямой разбор. Для групп
один автомат и его рабочая память создаются при первом обращении в потоке
и затем переиспользуются; найденные части заимствуются из входной строки.
Проверка печати подтверждает, что полученная строка восстанавливает именно
переданные части. Цель 10× этим архитектурным решением не подтверждается:
стоимость первого обращения и установившийся режим входят в будущие замеры.

#### Основа повторяемой текстовой записи

Первый профиль цепочки — последовательность записей одинаковой ширины с одним
непустым разделителем между всеми ячейками. Ширина выводится из представления
элемента при сборке, а не определяется по именам метаданных. Пустой текст
представляет пустую последовательность; пустые ячейки внутри непустой цепочки
сохраняются и проверяются ограничениями своего типа. Неполная последняя запись
не отбрасывается. Порядок и одинаковые записи сохраняются.

Разбор занимает один проход и возвращает заимствованные ячейки.

Потоковый интерфейс выдаёт одну полную запись за раз, без промежуточного списка
ячеек всей цепочки. Генератор передаёт запись прямо в типизированный элемент.
Ошибка неполного хвоста или бюджета завершает поток ошибкой; нельзя публиковать
успешный результат по одному уже прочитанному префиксу. Для потребителей,
которым нужен список, сбор выполняется тем же разбором с проверкой выделения
памяти.

Запись сначала проверяет всю последовательность, включая совпадение разделителя на границе
ячеек и лимиты строк/байтов, затем дописывает результат. Одна пустая ячейка
в одноячеечной записи неотличима от пустой последовательности; общий механизм
не должен объявлять её обратимой. Последняя ячейка не имеет следующего
разделителя: совпадение только с его префиксом в конце текста не запрещается.

Эта основа реализована в core; синтаксис и связывание описаны ниже.
Генерация самостоятельной цепочки, ограничений элементов и аномалий
физического свойства подключена.
Она также используется для последней коллекции в text-pattern, по договору композиции ниже.

#### Декларативная форма цепочки

Используется существующий смысловой тип sequence; новой разновидности значений
не требуется. Новая форма представления — `text-sequence`:

```yaml
format: nkdk-declarations/1
kind: value
id: common.object-segments
imports: {segment: common.object-segment}
value: {kind: sequence, item: {use: segment}}
representations:
  xml: {kind: text-sequence, separator: '.'}
  yaml: {kind: text-sequence, separator: '.'}
```

`common.object-segment` — обычная текстовая запись с полями «вид» и «имя»:

```yaml
format: nkdk-declarations/1
kind: value
id: common.object-segment
imports: {kind: common.path-object-kind, name: common.metadata-name}
value:
  kind: record
  fields:
  - {name: kind, type: {use: kind}}
  - {name: name, type: {use: name}}
representations:
  xml: {kind: text-pattern, parts: [{field: kind}, {literal: '.'}, {field: name}]}
  yaml: {kind: text-pattern, parts: [{field: kind}, {literal: '.'}, {field: name}]}
```

Например, цепочка `Table.Items.Cube.Statistics` представляется как
`Таблица.Items.Куб.Statistics`. Список не ограничен двумя элементами. Вид
переводится словарём, имя проверяется MetadataName; оба договора наследуются,
а не переписываются внутри цепочки. Допустимость такой цепочки у конкретного
владельца проверяется отдельно нормальными ограничениями владельца.

Начальный профиль компилятор принимает только при следующих условиях:

- Элемент ссылается на запись с парными text-pattern либо на выбор таких записей.
  Состояния, атрибуты, параметры и входы компактных элементов пока не поддержаны.
  Все варианты имеют одинаковую ширину; перестановка полей выводится отдельно
  для каждой стороны каждого варианта. Неизвестный договор не игнорируется при сборке.
- В каждой стороне шаблон начинается и заканчивается полем; между полями
  находится ровно separator соответствующей стороны. Других литералов нет.
- Ширина строки и перестановка ячеек в смысловые поля выводятся из шаблона
  элемента. Порядок полей XML и YAML может различаться; порядок записей нет.
- Поля элемента используют уже поддержанные текстовые/словарные скаляры.
  Ограничения каждого поля и всей записи применяются к каждому вхождению.
  Отсутствие реализации переноса ограничения — ошибка сборки декларации.
- Непустой separator задаётся явно; число ячеек, функции чтения/записи,
  повторяющиеся ограничения и перечень аномалий не задаются.

Нарушение нормального ограничения у прочитанного элемента сохраняется как
аномалия смыслового значения. Невозможность восстановить исходную запись
проверяется общим механизмом формы. У физического YAML-скаляра тег относится
к свойству целиком; номер проблемного элемента сохраняется в сообщении.
Поле occurrence остаётся номером повторяющегося ключа YAML.
Чтение корректного префикса не означает успешное чтение всей цепочки.

Компилятор должен выводить перестановки ячеек и обе стороны один раз при
сборке. Во время преобразования используются потоковый разбор и read_slots,
без временных строк и второго списка необработанных ячеек. Выбор получает
исходный срез строки для автомата и уже разобранные ячейки для выбранного
варианта: повторный разбор шаблона не требуется. Проверяются только ограничения
выбранной записи. Эта запись пока
принимается авторской JSON Schema и разбором компилятора; связывание проверяет
шаблон элемента и выводит порядок ячеек. Генератор преобразует физическое
свойство в обе стороны и применяет ограничения каждого элемента. Собственные
параметры, входы, состояния, нормализация и ограничения всей последовательности
в этом профиле пока отклоняются при генерации, а не игнорируются. Внешний фиксированный префикс и хвост соединяются по следующему договору.
Это ещё не завершение metadataPath: допуск владельцем и существование цели
проверяются отдельными нормальными ограничениями.

#### Поиск цели по подготовленным индексам

В индексных ключах допустимы текст и перечисления, отдельно или в составе
записи. Перечисление использует смысловое значение, а не его перевод YAML.
Типы колонок проверяются при связывании; компоненты ключа передаются отдельно,
без склейки пути и повторного разбора. Проекция значения индекса пока текстовая.

Для составного пути используются два обычных индекса:

- корни: `{kind, name} → identity`;
- дочерние объекты: `{parent, kind, name} → identity`.

`identity` — непрозрачный идентификатор; имя ребёнка всегда ищется у конкретного
владельца. Индексы разделяют хранилище строк и поколение операции. Подготовка
не повторяется для каждой ссылки. Неоднозначность и неготовность индекса
не превращаются в отсутствие цели.

Обычная коллекция может объявлять `item: {use: значение}` при текстовом физическом элементе XML и строковом YAML. Первый реализованный профиль — запись с фиксированным началом и типизированным текстовым хвостом. Коллекция хранит разобранные значения, сохраняет порядок и повторы; она не хранит параллельные списки XML- и YAML-строк. XML разбирается общим обходом, YAML передаёт очередной физический элемент типизированному чтению сразу. Входы индексов common задаются типами и передаются владельцем через `bind`, без самостоятельной привязки common к глобальному индексу. Унаследованные ограничения значений также проверяются. `each` над коллекцией и вложенный `fold` используют типизированные поля, без сборки промежуточных путей.

Для типизированного хвоста `text-sequence` оператор `eq` сравнивает последовательности по длине, порядку и смысловым полям элементов, включая перечисления. `take` возвращает срез без копирования. Поэтому `eq(tail, take(tail, 0))` означает пустой хвост, а `eq(tail, take(tail, 1))` — не более одного элемента. Повторы не исчезают. Это позволяет ограничениям владельца задавать допустимую глубину без специальных обработчиков путей в Rust.

Общий оператор `fold` передаёт результат шага следующему элементу коллекции:

```yaml
present:
  fold:
    in: {get: {of: {field: path}, field: tail}}
    initial:
      lookup:
        in: {input: roots}
        key: {record: {kind: {get: {of: {field: path}, field: root}}, name: {get: {of: {field: path}, field: name}}}}
    as: segment
    state: parent
    next:
      lookup:
        in: {input: children}
        key: {record: {parent: {var: parent}, kind: {get: {of: {var: segment}, field: kind}}, name: {get: {of: {var: segment}, field: name}}}}
```

Начальный поддержанный профиль: `in` — типизированный хвост text-sequence,
`initial` и `next` возвращают optional text, а переменная `state` внутри шага —
найденный текст. `as` обозначает текущую запись. Имена имеют лексическую область
видимости и не могут перекрывать уже существующие переменные.

Пустой хвост возвращает начальный результат. Отсутствие останавливает проход;
следующий индекс тогда не читается. Ошибка индекса сохраняет свою диагностику.
Компилятор выпускает обычный линейный цикл Rust: без рекурсии, промежуточных
строк пути и списка результатов. Во время выполнения декларация не интерпретируется.

Ограничения свойства остаются самостоятельными нормальными утверждениями:
например, `each` над тем же хвостом проверяет разрешённые значения. Он читает
поля уже разобранных записей. Поэтому «цель существует» и «это свойство допускает
такую цель» не смешиваются. Отдельные перечни аномалий не требуются: ложное
утверждение сохраняется общей смысловой аномалией свойства.

Предметные проверочные декларации: metadata-root-index, metadata-child-index
и metadata-indexed-object-path. Они проверяют общий механизм; подключение
источников целого проекта и полный набор ограничений metadataTarget остаются
условиями окончательного принятия ссылочных common.

#### Композиция текстового пути

Обычная запись может заканчиваться ссылкой на text-sequence. Новые функции
преобразования и отдельное перечисление аномалий не нужны:

```yaml
format: nkdk-declarations/1
kind: value
id: common.metadata-object-chain-path
imports:
  root: common.path-root
  name: common.metadata-name
  tail: common.metadata-object-segments
value:
  kind: record
  fields:
  - {name: root, type: {use: root}}
  - {name: name, type: {use: name}}
  - {name: tail, type: {use: tail}}
representations:
  xml: {kind: text-pattern, parts: [{field: root}, {literal: '.'}, {field: name}, {literal: '.'}, {field: tail}]}
  yaml: {kind: text-pattern, parts: [{field: root}, {literal: '.'}, {field: name}, {literal: '.'}, {field: tail}]}
```

Начальные поля — поддержанные текстовые/словарные скаляры; последняя смысловая
коллекция должна быть последним полем обоих шаблонов. Все разделители каждой
стороны совпадают с разделителем хвоста этой стороны. Порядок начальных полей
и полей элемента XML/YAML может различаться; ширина выводится при сборке.
Другая позиция коллекции, несовместимый разделитель или неподдержанная
зависимость отвергаются при сборке.

Разделитель перед хвостом соединяет реальные ячейки: при пустой коллекции он
не выводится. Поэтому `Catalog.Products` — начало без хвоста, а
`Catalog.Products.Table.Items` — начало с одним элементом. Явная точка в конце
не теряется при чтении: она начинает хвост; для двухъячеечного элемента такой
хвост неполон и сохраняется как аномалия формы общим механизмом.

Ограничения начальных скаляров и каждого элемента наследуются. Неверное имя
в начале или хвосте даёт смысловую аномалию всего физического свойства.
Проверки, требующие входов, параметров или выражений над всей коллекцией,
пока требуют отдельной специализации и не должны молча игнорироваться.

Генератор читает фиксированные ячейки и поток хвоста напрямую в типизированные
значения. Промежуточные строки начала/элементов не создаются. Перед записью
общий проход проверяет границы, включая стык начала и хвоста, вычисляет размер
и проверяет переполнение; итоговая строка резервируется один раз.

#### Переиспользование текста и открытый словарь

Для нового написания уже объявленного текстового common смысл и ограничения
переиспользуются через `value: {use: name}`:

```yaml
imports: {name: common.metadata-name, words: common.some-vocabulary}
value: {use: name}
representations:
  xml: {kind: text}
  yaml: {kind: text-table, use: words}
```

Проверку имени повторять не нужно. Компилятор наследует ограничения исходного
common и добавляет локальные. Начальный профиль допускает источник с обычным
XML-текстом без параметров, входов, состояний, сокращений, нормализации,
преобразований текста и вкладов в индексы. Неподдержанный договор отвергается
при сборке декларации, чтобы его части не потерялись при переиспользовании.

Текст может использовать переводы существующего перечисления, сохраняя все
остальные значения без изменения:

```yaml
imports: {words: common.some-vocabulary}
value: {kind: scalar, scalar: text}
representations:
  xml: {kind: text}
  yaml: {kind: text-table, use: words}
```

Смысл — исходное XML-написание. Связывание один раз сопоставляет канонические
XML/YAML-написания перечисления по смыслу варианта. Таблица переводов остаётся
в одном месте. Источник должен быть обычным перечислением без параметров,
входов, дополнительных ограничений, состояний и альтернативных XML-написаний;
неподдержанное подключение отвергается при сборке, а не теряет свой договор.

В YAML известное XML-написание переводится, остальной текст остаётся прежним.
При чтении YAML перевод восстанавливает XML-написание; неизменённое модельное
имя также допустимо и при печати получает канонический перевод. Например,
при паре `Ref: Ссылка` имя `Executed` сохраняется, а `Ref` печатается как `Ссылка`.
Входной XML-текст `Ссылка`, не являющийся XML-ключом таблицы, столкнулся бы с
переводом `Ref`: общий механизм сохраняет такую необратимую форму как аномалию.
Пары с одинаковым XML/YAML-написанием и перестановки известных ключей допустимы.

Ограничения текста применяются к смыслу после обратного перевода. JSON Schema
обозначает необходимость проверки сгенерированным валидатором, чтобы ошибочно
не применять ограничение исходного имени к его переведённому написанию.
Таблица превращается в Rust при сборке; поиска деклараций или построения
словаря на каждом значении нет. Неизменённый самостоятельный скаляр сохраняет
свой исходный буфер, а слоты строкового шаблона читают заимствованные строки.

#### Основа детерминированного выбора строковой формы

Компилятор строит один автомат для набора полных строковых форм. Начало и конец
строки закреплены для каждой формы: совпадение префикса не считается выбором.
Пересечение обнаруживается обходом достижимых состояний и проверкой завершения
входа; порядок вариантов не разрешает неоднозначность. Проверяются также пустая
строка и Unicode. Ошибка сообщает номера пересекающихся форм, которые следующий
слой связывает с именами и адресами вариантов декларации.

Размер автомата и рабочей памяти детерминизации ограничен 64 МиБ каждый;
анализ пересечений ограничен 65 536 достижимыми состояниями. Превышение лимита
завершает компиляцию диагностикой. При единственной форме анализ пересечений
не требуется. Готовые данные сохраняются с нужным выравниванием и порядком байт,
загружаются один раз; выбор возвращает номер варианта либо отсутствие совпадения
без перебора отдельных преобразователей и построения временных строк.

Эта основа используется также существующей проверкой строковых ограничений.
Смысловой `choice` подключён для непересекающихся фиксированных строковых шаблонов; исполняемый профиль описан ниже.
Выбор формы не заменяет проверку значения: неверное значение однозначно
распознаваемого варианта должно сохранять смысл и `!xml/invalid`. Неоднозначные
обычные декларации нельзя принимать через raw; необратимый аномальный вход
обрабатывается общим механизмом сохранения исходной формы.


#### Исполняемый выбор фиксированных строковых шаблонов

```yaml
imports: {first: common.first-form, second: common.second-form}
value:
  kind: choice
  variants:
  - {name: first, type: {use: first}}
  - {name: second, type: {use: second}}
representations:
  xml: {kind: choice}
  yaml: {kind: choice}
```

Каждый вариант ссылается на самостоятельный common с парой `text-pattern`.
Имена вариантов уникальны и непусты; пустой выбор, неизвестные ссылки и циклы
отвергаются. Обе формы выбираются независимо, а смысл хранится сгенерированным
Rust enum с типизированной записью выбранного варианта.

Профиль доказывает непересечение форм по литералам, разделителям и закрытым
словарям типов. Для enum/boolean используются допустимые записи соответствующей
стороны, включая XML-алиасы. Текстовый слот перед разделителем читается точно
до первого полного вхождения, включая пустой префикс. Это верно и для
многосимвольных разделителей с повторяющимися частями. Ограничения смысловых
значений не участвуют в выборе.
Например, `a:123` выбирает форму `a:имя`, а затем
нарушение ограничения имени даёт `!xml/invalid` на физическом свойстве. Общий
механизм сохраняет исходную форму, когда ни один вариант невозможно разобрать.
Отдельных записей аномалий у `choice` нет. При пересечении диагностика указывает
сторону XML/YAML, имена и исходные позиции двух вариантов; порядок не помогает
разрешить пересечение.

Открытый словарь остаётся текстом, поскольку разрешает неизвестные слова.
В последнем слоте допускается весь оставшийся текст. Различение только по
смысловым ограничениям по-прежнему не входит в этот профиль: например, нельзя
подменять распознавание формы проверкой правильности имени.
Вариант может получать подготовленные входы через обычный `bind`: владелец
передаёт вход выбору, выбор — своему варианту. Компилятор подставляет эти связи
при сборке и переносит проверку варианта с его условием выбора. Перестановка
входов владельца не меняет значение связи. Во время преобразования новый
контекст для варианта не создаётся. Подготовленные входы используются проверками
и восстановлением текстовых слотов, опущенных в YAML через `yaml.default`.
Для таких слотов поддерживается только восстановление значения: дополнительные
пустые состояния, собственные XML-атрибуты вариантов и вложенный выбор
не входят в этот исполняемый профиль. Общая оболочка выбора может
иметь собственные атрибуты и состояния присутствия; условия её атрибутов
поддерживают проверку наличия значения и подготовленные входы.

Обычная `sequence` может ссылаться на такой выбор как на тип элемента:
XML использует `element-sequence` с текстовым элементом, YAML — последовательность
строк. Каждый элемент хранит типизированный вариант; порядок и повторы сохраняются.
Проверяются ограничения только выбранной ветви, в том числе при YAML-валидации.
Неизвестная форма сохраняется общей аномалией с доказательством восстановления,
а нарушение ограничения известного варианта — общей диагностикой данных.
Подготовленные входы передаются по той же цепочке `bind`: владелец → коллекция
→ тип элемента → выбранный вариант. Компилятор подставляет номера входов
на каждом участке при сборке; проверки элементов используют один подготовленный
контекст владельца, без его копирования и повторной подготовки индексов.
Независимая проверка меняет значение входа, его позицию у владельца и ветвь
элемента. В текстовом элементе, включая выбранный вариант, пропущенные YAML-слоты
восстанавливаются тем же `yaml.default` из подготовленных текстовых входов.
При XML-импорте проверяется совпадение с восстанавливаемым значением;
несовпадение сохраняется как аномалия общей коллекции. Данные другого владельца
не подменяются текущим префиксом. При смене подготовленного имени следующий
экспорт короткого YAML использует новое имя; порядок и повторы элементов сохраняются.
Ограничения записываются в вариантах; их условия, сообщения и адрес свойства
переносятся общим механизмом и выполняются только для выбранного варианта.

Выбор выполняет один проход общего автомата, затем разбирается только выбранный
шаблон. Ни перебора преобразователей, ни промежуточного JSON-дерева нет. XML и YAML
используют заранее скомпилированные автоматы. Обратная запись обращается напрямую
к типизированному варианту.

Шаблон выбора компилируется непосредственно из литералов, закрытых словарей,
чтения до разделителя и остатка строки. Для разделителя строятся состояния
совпавшего префикса с переходами возврата; завершённое первое вхождение сразу
передаёт управление следующей части. Поиск более позднего вхождения запрещён.
Слова закрытого словаря, пересекающие следующую границу, проверяются тем же
правилом обратимости, что и обычная запись шаблона. Никаких выражений поиска
или служебных признаков в декларацию добавлять не требуется.

Промежуточный автомат ограничен 65 536 состояниями; его построение вместе с
таблицами префиксов проверяет бюджет 64 МиБ. Детерминизация и итоговый автомат
сохраняют свои ограничения. Во время преобразования эти таблицы не строятся.

### Совместное чтение свойств владельца

Генерируемые читатели скаляров и коллекций получают заимствованные XML-события
общего разбора документа. Источник исходных байтов передаётся отдельно и
остаётся доступным для адресов ошибок и исключительного сохранения формы.
Нельзя реализовывать композицию повторным чтением полного XML для каждого
свойства, сборкой XML-фрагментов или накоплением дерева событий.
Самостоятельное чтение свойства — тот же читатель с источником DocumentSource.
Передача события другому читателю не клонирует текст или атрибуты.
Для QName источник с областью имён (ScopedSource) передаёт текущие привязки
пространств имён вместе с событием. Привязки не копируются и не удерживаются
после события; вложенное переопределение префикса учитывается непосредственно
парсером. Источник без такой области не выдаёт выдуманные привязки.


### Исполняемый профиль текстовых атрибутов записи

Существующее соответствие `attribute` связывает смысловое поле с атрибутом
контейнера. Новых параметров языка для UUID и версии не требуется:

```yaml
value:
  kind: record
  fields:
    - {name: identity, type: {kind: scalar, scalar: text}}
    - {name: name, type: {kind: scalar, scalar: text}}
representations:
  xml:
    kind: record
    fields:
      - {field: identity, path: [Root, Item], attribute: uuid}
      - {field: name, path: [Root, Item, Name]}
  yaml:
    kind: mapping
    fields:
      - {field: identity, key: UUID}
      - {field: name, key: Имя}
```

Генератор читает атрибут в том же обходе XML, что и поля элементов. При выдаче
сначала открываются контейнеры с атрибутами, затем записываются потомки.
Текст хранится как смысловое значение; пустая строка отличается от отсутствия.
Отсутствие обязательного атрибута выводит аномалию отсутствия автоматически,
без отдельного условия в декларации. Пространство имён берётся из имени
атрибута; переводы строк и другие специальные символы сохраняются.

Текущая граница реализации: обычный текст без переопределения присутствия;
несколько связанных атрибутов на контейнер; контейнеры образуют цепочку
предков, а поля элементов находятся ниже последнего контейнера. Допускается
запись только из атрибутов. Вложенный common с полями элементов и текстовыми
атрибутами использует общую агрегатную оболочку; постоянные атрибуты этой
оболочки объединяются со связанными атрибутами при одном открытии контейнера.
Группы определяются XML-маршрутом при сборке. У всех атрибутов группы
позиция указывает на один контейнер; его повтор проверяется один раз.
Выдача использует массив необязательных атрибутов без динамического буфера.
Вложенная запись только из атрибутов пока не поддержана. Остальные схемы
пока отвергаются при компиляции,
а не исполняются с потерей данных. Это ограничение реализации, не языка.
Для вложенного common отклонения оболочки восстанавливаются существующей
агрегатной аномалией записи: отсутствующие, изменённые и дополнительные
атрибуты, в том числе другой порядок. Пустой и отсутствующий common различаются.
Для полного владельца неизвестные атрибуты и агрегатные аномалии контейнеров
ещё требуют подключения; готовность обработки всех его отклонений не заявляется.


### Общий буфер YAML и повторная запись аномалий

Поддержанная составная запись с коллекцией и атрибутом записывается прямо
в буфер владельца. Вложенные строки получают отступ при выдаче; отдельный
дочерний YAML-документ и последующее копирование его строк не требуются.
На верхнем уровне запись без отступа непосредственно добавляет строку.
Пустое свойство не оставляет разделителя, ошибка подготовки откатывает весь
добавленный участок, сохраняя предыдущие свойства.

Подготовка диагностик обычных списков и keyed-mapping читает созданный
участок общего буфера. Обе формы поддерживают заданный отступ и повторную
запись уже прочитанного YAML с сохранённой поправкой XML.
Если требуется смысловой тег, этот участок заменяется полной формой с тегом.
Это пока сохраняет повторный разбор для вывода диагностик; устранение
дочернего буфера не означает устранения всех контрольных разборов.

Сохранённая поправка XML записывается как поправка, без применения к пустому
дереву: применение уничтожило бы команды удаления. Пустой контейнер, пустой
список и отсутствие различаются. Это общее правило повторной записи уже
принятых аномалий скалярных полей, вложенных записей и составной записи.
Дополнительный буфер для упаковки существующего `!xml/raw` остаётся только
на исключительном пути; новых предметных правил аномалий не добавляется.

### Автоматическая сборка записи владельца: исполняемая граница

Автоматическая сборка объединяет скаляры, коллекции, вложенные записи,
QName, I8nText и FormattedI8nText с общими входами. Условия отсутствия
и независимые проверки полей владельца перенумеровываются вместе с полями.
Постоянные атрибуты оболочки и связанные текстовые атрибуты выдаются вместе.

XML выбирает обработчик на входе в поддерево; YAML — один раз на свойство.
Вложенные события идут непосредственно выбранной части, без обхода всех
обработчиков и без копирования узлов. Обычная выдача использует общие буферы.

Аномалии свойств сохраняются на их прежних границах. Оставшаяся разница
оболочки и порядка записывается поправкой владельца после контрольного
экспорта. Поправка не может менять известные свойства: их проекции
проверяются до и после применения. Исправлена общая потеря порядка разных
дочерних элементов при одинаковых значениях; такой случай получает #order.

Независимые условия присутствия и ограничения перенумеровываются по местам
полей в части, включая сообщения диагностик. Выражение, обращающееся к другой
части или всему владельцу, пока отвергается при сборке; оно не отбрасывается.
Атрибуты образуют цепочку контейнеров над обычными свойствами; условия
постоянных атрибутов владельца пока требуют дальнейшего подключения.

Поправка оболочки использует ту же пару смыслового значения и XML-поправки:

```yaml
!xml/raw
$значение:
  Имя: Пример
$xml:
  _format: null
```

Смысловое значение обязано быть обычным отображением свойств. Неизвестные,
повторные и вложенные служебные поля оболочки отвергаются. Удаление корня
XML недопустимо. Запись владельца не перечисляет возможные аномалии:
поправка выводится после неуспешного сравнения восстановленного XML.
Её применение дополнительно сравнивает все уже принадлежащие частям
свойства; изменение их содержимого этой поправкой запрещено.
Отдельные документы и деревья создаются только на исключительном пути.

Следующее: вклады целого владельца в индексы, зависимости между частями,
подготовленные UUID/InternalInfo, полный состав полей Document/DocumentJournal,
дочерние объекты, ресурсы и единая операция проекта. Полные владельцы ещё
не приняты; чеклист остаётся 15/90. Не использовать аномалию оболочки для
сокрытия известного, но не перенесённого свойства: требуется отдельная
проверка полноты по исходным rules.ts и неизменённому e2e.


### Вклады и подготовленные значения в сборке владельца

`contributions` целого владельца читает его уже разобранные типизированные части.
Скалярный ключ может ссылаться на одну часть, значение — на другую. `forEach`
по коллекции получает её типизированные строки. Повторное преобразование
смыслового значения через XML/YAML для извлечения вклада не требуется.
Ограничения декларации проверяются до публикации индекса, даже когда
преобразование разрешает сохранить нарушение как аномалию. Недоступный смысл
отличается от достоверной пустой коллекции; при недоступности индекс не готов.

Отсутствующее скалярное значение может восстанавливаться независимым выражением
над подготовленными входами. Например, для поля текстового XML-атрибута:

```yaml
presence:
- target: {field: identity}
  xml: {missing: {denotes: {absent: true}}}
  yaml:
    missing: {denotes: {input: identity}}
    omitWhen: {eq: [{field: identity}, {input: identity}]}
```

Такой договор сокращает совпавший UUID и сохраняет отличающийся явно. Если
в исходном XML атрибут физически отсутствовал, общий механизм сохраняет это
как аномалию свойства: значение из входа не должно незаметно добавлять атрибут.
Подготовка самого снимка идентичностей относится к операции проекта; выражение
преобразования не создаёт новый UUID.


### Атрибуты в элементах коллекции

Поля записи внутри последовательности используют тот же `attribute`, что
поля владельца. Они могут сочетаться с дочерними текстовыми элементами:

```yaml
item:
  kind: record
  fields:
  - {field: name, path: [], attribute: name}
  - {field: category, path: [], attribute: category}
  - {field: typeId, path: [xr:TypeId]}
  - {field: valueId, path: [xr:ValueId]}
```

Это обычные смысловые поля записи. Порядок экземпляров сохраняется; атрибуты
имеют развёрнутые XML-имена и не зависят от выбранного префикса. Отсутствующий
или лишний атрибут выводится как аномалия общим механизмом проверки обратимости.
Текущая реализация поддерживает текстовые атрибуты самого элемента коллекции;
атрибуты вложенных контейнеров и типизированные атрибуты ещё требуют расширения.
Это основа формы GeneratedType, а не завершение всего InternalInfo и снимка
идентичностей владельца.


При подключении снимка InternalInfo ключ сгенерированного типа не должен
зависеть от имени владельца после точки в `GeneratedType.name`. Действующая
реализация использует первую часть имени; переименование владельца сохраняет
TypeId и ValueId. Это должно выражаться общей декларативной структурой имени
или выражением, без ветвления Rust по названиям типов метаданных. Само чтение
текстовых атрибутов не закрывает этот договор.

### Краткое описание восстановимого значения

`presence[].yaml.default` задаёт одним выражением два уже существующих договора:
отсутствующее YAML-свойство означает указанное значение, а совпадающее значение
при записи сокращается. Компилятор раскрывает запись в `missing.denotes` и
`omitWhen: eq` с правильной целью (`self` или поле владельца). Вместе с
`default` нельзя указывать `missing` или `omitWhen`; неоднозначная декларация
отклоняется. Старые подробные записи остаются допустимыми.

```yaml
presence:
- target: {field: types}
  xml: {missing: {denotes: {absent: true}}}
  yaml:
    default:
      sequence:
      - record:
          name: {concat: [{literal: 'DocumentObject.'}, {input: name}]}
          category: {literal: Object}
          typeId:
            require:
              lookup:
                in: {input: typeIds}
                key: {record: {owner: {input: owner}, name: {literal: DocumentObject}}}
```

Пример показывает часть записи; полный GeneratedType также содержит ValueId.
`concat` соединяет текстовые выражения в указанном порядке без разделителя,
экранирования или изменения регистра. Нетекстовые аргументы запрещены.
Пустой список означает пустую строку. Строка строится в одном результирующем
буфере; найденный UUID не преобразуется через XML, YAML или JSON.

`require` извлекает обязательный результат подготовленного вычисления из
optional-значения. Восстановление идентичности использует его для чтения UUID
из снимка: отсутствие нужного UUID означает неполную подготовку операции,
а не пустой UUID и не разрешение создать случайный UUID при контрольном
экспорте. Новые идентичности выделяет операция до преобразования. Для обычных
нарушений входных данных продолжают использоваться нормальные ограничения
и автоматически выводимые аномалии; `require` не заменяет их.

Если XML физически не содержит восстанавливаемого списка, обычный пропуск
YAML восстановил бы список и изменил исходный XML. Общая проверка обратного
преобразования выявляет различие и сохраняет поправку отсутствия. Отдельно
объявлять такую аномалию или обработчик конкретного объекта не требуется.

### Соседние коллекции без собственной оболочки

У `element-sequence` пустой `path: []` означает, что путь свойства владельца
указывает непосредственно на повторяемый элемент. Например, пути
`[MetaDataObject, DocumentJournal, ChildObjects, Form]` и
`[MetaDataObject, DocumentJournal, ChildObjects, Template]` описывают две
независимые коллекции внутри общего `ChildObjects`. Имена элементов задаются
только декларациями. Общие обработчики не знают, что такое Form или Template.

При чтении элементы передаются своей коллекции, при записи общая оболочка
создаётся один раз. Проекция для сохранения аномалии содержит только элементы
своей коллекции; порядок разных коллекций восстанавливается поправкой владельца.
Поправка одной коллекции не может дописывать элементы другой коллекции или
менять атрибуты общей оболочки. Такие атрибуты принадлежат владельцу.

Подготовленный список текстовых значений можно использовать непосредственно
в `yaml.default: {input: names}`. При совпадении список не записывается в YAML,
при обратном преобразовании восстанавливается из подготовленного входа.
Например, имена форм и шаблонов берутся из найденных файлов ресурсов. Порядок
и повторы сравниваются без сортировки и без устранения дублей. Отклонение
от подготовленного списка остаётся явно представимым; потеря формы XML
сохраняется общим механизмом аномалий.

### Восстановимые части короткого текстового представления

Для ссылки на собственную форму общий принцип тот же, что у восстановимого
поля записи. XML содержит владельца и имя формы, YAML — только имя формы.
Недостающая часть задаётся существующим `presence[].yaml.default`, а не
отдельной функцией чтения или записи. Например:

```yaml
inputs:
  owner: {type: {kind: scalar, scalar: text}}
value:
  kind: record
  fields:
  - {name: owner, type: {kind: scalar, scalar: text}}
  - {name: form, type: {kind: scalar, scalar: text}}
representations:
  xml:
    kind: text-pattern
    parts: [{field: owner}, {literal: '.Form.'}, {field: form}]
  yaml:
    kind: text-pattern
    parts: [{field: form}]
presence:
- target: {field: owner}
  yaml: {default: {input: owner}}
```

При входе `owner: Document.Заказ` XML
`Document.Заказ.Form.Основная` преобразуется в YAML `Основная`.
Обратно владелец восстанавливается из того же подготовленного входа.
Поле, отсутствующее в текстовом представлении, обязательно имеет однозначное
правило восстановления. Пропуск без такого правила — ошибка декларации.

Если исходный владелец отличается, контрольное восстановление обнаруживает
разницу и сохраняет её обычным механизмом аномалий. Проверка допустимой цели
ссылки остаётся смысловым ограничением декларации. Пустая ссылка определяется
состояниями свойства владельца, а не специальной строкой внутри обработчика.

Генерация проверена на независимых именах для самостоятельных скалярных
свойств и подключена к ссылкам на собственные формы Document/DocumentJournal.
Поддерживаются также текстовые варианты `choice` и элементы обычной
`element-sequence` ↔ YAML `sequence`, включая выбранный вариант элемента.
Для компактной `text-sequence` этот договор пока не реализован.


Непредставимая восстановимая часть определяется общей проверкой шаблона:
фактическое значение сравнивается с объявленным восстановлением. Если они
различаются, сохраняется исходное значение целиком, без ложного смыслового
значения в коротком YAML. Окончательный результат обязан пройти контрольное
восстановление. Отдельное объявление аномалии для владельца формы не требуется.
Ошибка отсутствующего подготовленного входа не заменяется аномалией данных.

### Текстовый шаблон элемента коллекции и тип ключа

Обычная коллекция может содержать запись, представленную парой текстовых
шаблонов. Например, XML `Document.<имя>` и YAML `<имя>` описываются литералом
префикса и одним полем. Проверки поля и коллекции выводятся из их обычных
типов и ограничений; неподходящий префикс сохраняется общей аномалией.
Это не требует отдельного вида коллекции или обработчика предметной ссылки.

В `lookup.key` литерал варианта перечисления получает тип из ожидаемого
ключа индекса, также внутри записи. В `presence` такой же литерал получает
тип свойства, состояние которого он обозначает, в том числе в `yaml.default`. Вариант должен принадлежать перечислению.
Произвольное строковое выражение не становится перечислением автоматически.

### Уточнение состояния коллекции владельцем

Правило свойства владельца уточняет соответствующие части common,
не стирая остальные. Указанные `missing` и `omitWhen` заменяют одноимённые
части; пустые формы заменяются по виду формы; условия канонической XML-формы
владельца проверяются перед условиями common. Отсутствующая часть наследуется.
Привязки входов и постоянные параметры common специализируются до объединения.
Так можно кратко потребовать пустую XML-оболочку для отсутствующего значения,
сохранив сокращения YAML и проверки общего типа.

### Совместная проверка соседних скалярных свойств

Ограничение может читать несколько соседних скалярных полей владельца.
Компилятор объединяет связанные поля в типизированную часть, сохраняя их
XML-пути и YAML-ключи. Проверка и отметка аномалии остаются у поля, указанного
в `diagnostic.at`; отдельный обработчик для предметного объекта не нужен.

Первая поддерживаемая граница — соседние поля одного XML-контейнера.
Несоседние поля, коллекции и динамические привязки между свойствами пока
требуют следующего расширения; компилятор не игнорирует такие зависимости.
Проекция исключительного XML сохраняет только принадлежащие группе элементы,
не захватывая соседние свойства и атрибуты общей оболочки.


Общий читатель коллекции также хранит состояние отдельно от источника событий.
XML-состояние владеет строками и текущими полями; YAML-состояние принимает события
значения и сразу преобразует завершённую строку. Внешний сборщик отвечает за
направление событий, а не за типы и имена полей. Завершение применяет прежние
правила присутствия и проверки. На обычном пути нельзя накапливать вторую
коллекцию исходных строк или повторно разбирать документ для каждого элемента.


Состояние владельца объединяет состояния частей. Маршрутизация XML хранит
только активную часть и глубину её оболочки; маршрутизация YAML выбирает часть
один раз на свойство и передаёт вложенные события напрямую. Проверка границ
отображения и оболочки свойства используется и в обычных точках входа, и при
прямом наполнении состояния. Поддержка состояния добавляется преобразователям
поэтапно: остальные продолжают использовать общий потоковый путь; их наличие
не разрешает считать полную вложенность реализованной. Нормальный путь не
преобразует события обратно в XML/YAML для передачи дочернему преобразователю.


Состояние вложенной скалярной YAML-записи сохраняет отдельный признак присутствия
оболочки. Отсутствующая оболочка не подменяется пустым отображением: завершение
записи применяет её собственные правила присутствия и обязательности полей.
Родитель передаёт исходные события; сериализация и повторный разбор записи
для подключения её к родителю не допускаются на обычном пути.

### Коллекция со ссылкой на целую декларацию элемента

Если `value.item` ссылается на common через `use`, представления коллекции могут
не содержать `item`. Это означает подключение **всего договора элемента**:

```yaml
imports: {row: common.row}
value: {kind: sequence, item: {use: row}}
representations:
  xml: {kind: element-sequence, path: [Item]}
  yaml: {kind: sequence}
```

`Item` — оболочка отдельного XML-элемента. XML-пути декларации строки остаются
относительными к этой оболочке, YAML-поля — полями одного элемента списка.
Пространства имён разрешаются в исходной декларации, а не по одноимённым
сокращениям коллекции. Порядок и повторения строк сохраняются.

Наследуются собственные представления строки, присутствие полей, ограничения,
параметры и проверенные привязки входов. `self` остаётся значением строки;
номера её полей не превращаются в номера полей владельца. Специализация
параметров создаёт отдельный договор при сборке, не меняя исходный common.
Схема YAML использует этот договор: обязательные поля, допустимые пропуски
и выражаемые в схеме ограничения не перечисляются в коллекции повторно.

Опускать `item` нужно с обеих сторон. Смешение унаследованного XML и отдельно
заданного YAML (или наоборот) отклоняется с `incomplete_item_contract`.
У встроенного типа без `use` опускать представление элемента нельзя.
Существующая явная запись представлений остаётся доступной.

Состояние реализации: общий генератор подключает декларацию записи как состояние
одной строки. Поддержаны скалярные поля и вложенные коллекции с обычным или
унаследованным представлением элемента. Поля, значения по умолчанию,
параметры и ограничения строки не копируются в декларацию коллекции.
Схема YAML также сохраняет вложенную структуру и обязательность полей.

Обычное преобразование передаёт события в состояние текущей строки и пишет
результат в общий буфер. На строку не создаются отдельный XML writer,
временный XML или повторный разбор YAML. Повторный разбор сохранённой YAML-строки
допустим только при восстановлении её исключительной формы.

При контрольном сравнении XML учитывается номер каждого вхождения на пути.
Разные строки могут иметь разные аномалии на одном пути: решение о скалярном
тексте принимается для конкретной строки, а не для всех строк сразу.
Нарушения смыслового договора используют существующие аннотации; остаточная
невосстановимая форма сохраняется общей поправкой коллекции после контрольного
экспорта. Нового перечня аномалий в декларации нет.

Текущие ограничения генератора диагностируются при сборке: собственные
ограничения, сокращения/нормализация и вычисляемые формы присутствия всей коллекции,
представление строки XML-tree/условной оболочкой и формы строки без независимого
состояния событий, а также собственные ресурсы/вклады строки требуют дальнейшего
расширения. Они не должны молча
игнорироваться. Подготовленные идентичности, внешний файл и корневой YAML-массив
остаются отдельными условиями приёмки AdditionalIndexes.


### 2026-09-13: целый YAML-документ и зависимые значения строки

Запись с единственным полем может использовать `yaml: {kind: projection,
field: indexes}`. YAML-документом становится представление самого поля:
например, массив строк без служебного ключа. Это форма представления, а не
отдельный преобразователь AdditionalIndexes. Компилятор проверяет единственность
поля, строит схему его значения и сохраняет аномалии на границе документа.

Значение отсутствующего поля может вычисляться из других полей той же записи
и подготовленных входов. Зависимости проверяются на циклы; вычисление идёт после
чтения нужных полей, независимо от порядка XML и YAML. Порядок вывода остаётся
порядком декларации. Текущий сборщик объединяет соседние скалярные зависимости;
несоседние и структурные зависимости пока явно диагностируются.

Пример: идентификатор строки находится по паре «владелец, имя». Совпавший
идентификатор сокращается, отличный остаётся явным. Неоднозначность индекса
означает, что сокращение не доказано: значение также остаётся явным.
Это общее поведение `omitWhen`, а не обработчик имени объекта. Отсутствующий,
неподготовленный индекс и ошибки его формы не приравниваются к неоднозначности.
Подготовка новых UUID остаётся обязанностью операции (D-16); чистое правило
получает их в том же снимке, что и существующие UUID.

Скалярная группа может одновременно владеть XML-атрибутами и элементами одного
контейнера. Атрибуты выводятся при открытии контейнера один раз, элементы — на
своём месте; вложенные коллекции используют общий поток событий и writer.
Текстовые поля типизированной строки доступны общему извлечению вкладов без
промежуточной сериализации. Статические текстовые атрибуты оболочки коллекции
поддерживаются; условные и QName-значения её атрибутов пока явно диагностируются,
до расширения выражений и каталога QName этой границы.

## Именованные полные записи в YAML

```yaml
value: {kind: sequence, item: {use: item}}
representations:
  xml: {kind: element-sequence, path: [Item]}
  yaml: {kind: record-mapping, key: name}
```

`key` обозначает смысловое поле записи, а не имя предметного типа. Полная
декларация `item` определяет XML, остальные свойства YAML и их проверки.
Вместо `[{Имя: Первый, Включено: Истина}]` получается
`{Первый: {Включено: Истина}}`; при чтении ключ возвращается в поле имени.
Пустая коллекция записывается `{}`. Поле ключа должно быть текстовым и иметь
YAML-сопоставление в собственной декларации элемента. Неизвестный ключ и
нетекстовый тип — ошибки декларации, а не аномалии пользовательских данных.

Если YAML должен содержать непосредственно одно поле записи, указывается
`value`: `yaml: {kind: record-mapping, key: name, value: value}`. Тогда
`[{Имя: Первый, Значение: 10}]` записывается как `{Первый: 10}`. Компилятор
проверяет оба поля по полной декларации элемента и выводит схему значения из
поля `value`; исполнитель не знает ни предметного типа, ни имён `Имя` и
`Значение`. Пустой словарь и `null` на месте проецируемого значения означают
отсутствие этого поля. Обратная запись использует `{}`, когда поле отсутствует;
его XML-форму, например `xsi:nil`, задаёт обычный договор присутствия записи.

Нормальный путь читает события YAML и передаёт их читателю записи, добавляя
ключ как поле. При записи ключ не сериализуется повторно внутри записи.
Весь словарь не строится заново и не пропускается через второй YAML-парсер.
Порядок первых вхождений сохраняется. Повторные XML-имена не помещаются в
обычный словарь дважды: контрольное восстановление выявляет различие,
общая аномалия сохраняет точный исходный XML, включая повторные элементы.

Первый исполняемый профиль включает простые и составные записи с независимым
полем ключа. Группы взаимозависимых полей, куда входит ключ, пока получают
явную диагностику неподдержанного механизма. Это ограничение компилятора,
не новое правило языка и не разрешение на частные обработчики объектов.
Передача контекста элемента и восстановление служебного XML проверяются
отдельно; наличие словаря не означает готовности реальной коллекции метаданных.


### Компактная запись, открытый выбор и атрибуты оболочки

Одна запись может иметь XML-поля и строковое представление YAML. Составные
текстовые поля сохраняют собственные проверки. Если нарушение относится к
компоненту общей строки, ближайшая доступная граница тега — вся строка:
`СвязьТипа: !xml/invalid ...`. Список возможных аномалий не дублируется
в декларации. Необоснованный тег по-прежнему отклоняется при проверке YAML.
Если одновременно требуется сохранить форму XML, смысл внутри `!xml/raw`
может сохранять свой семантический тег; сам raw не отменяет проверку значения.

У текстового `choice` может быть один остаточный скалярный текстовый вариант.
Он применяется только вне различителей структурных вариантов; ошибка уже
выбранной структуры не переключает значение в остаточный вариант. Пересечение
различителей отклоняется компилятором. Совпадение исходного текста с различителем
обратного представления сохраняется общим механизмом аномалий.

Ссылка `value: {use: ...}` может повторно использовать такой выбор с собственной
XML-оболочкой. Атрибуты оболочки записи используют общий договор атрибутов,
включая QName и условия от значений и входов; предметные имена не попадают
в оркестратор. Параметры статического экземпляра записи передаются вложенным
правилам при компиляции, без построения второго контекста во время преобразования.


### Единственный элемент текстовой последовательности

`yaml: {kind: sequence, singleton: scalar, item: {kind: scalar, scalar: text}}`
задаёт одну строку для одного элемента, обычный YAML-список для нескольких и
`[]` для пустого списка. При чтении принимаются обе непустые формы. Элемент
всегда проходит тот же типизированный преобразователь и те же ограничения;
сокращение не превращает его в непроверяемый текст. Аномалия единственного
элемента сохраняется на доступной границе значения.

Режим нельзя смешивать с сокращениями списка до постоянной строки: одна
строка могла бы означать как собственный элемент, так и несколько элементов.
Компилятор отклоняет это пересечение. Режим относится к текстовым элементам;
он не угадывает, является ли словарь целой коллекцией или одним её элементом.
Для TypeDescription этот режим обслуживает только внешнюю форму списка;
правила имён и общих квалификаторов описываются независимо.

### Структурированное поле только в YAML и условное восстановление

Поле записи может иметь обычный тип и YAML-представление, но не иметь
XML-маршрута. Такое поле участвует в схеме, проверке и YAML-преобразовании,
а XML-чтение и XML-запись его не создают. Компилятор определяет этот случай
по отсутствию XML-сопоставления; имя common или свойства ему неизвестно.

Отсутствующий YAML-ключ может восстанавливать запись условным выражением над
объявленными входами. Обе ветви выражения типизированы тем же типом поля;
пустая последовательность записи задаётся обычным декларативным значением.
Это позволяет перенести принятые значения по умолчанию из `rules.ts` без
обработчика конкретного объекта. Невыполнимая ветвь и потеря XML обнаруживаются
общим контрольным восстановлением и оформляются как аномалия данных.

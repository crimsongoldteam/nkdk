# Единый вариант собственных и заимствованных объектов расширения

## Статус

Согласованный дизайн универсального различения собственных и заимствованных
объектов расширения при XML → YAML и YAML → XML. Ошибка импорта
`дкз_ОбменТипы` служит регрессионным примером, но решение не привязано к планам
обмена или к конкретному виду метаданных.

## Контекст

Импорт `/Users/nikita/git/sed_xml/cf` в проект NKDK проходит: импортировано
10 091 значение, а единственное предупреждение относится к неразрешённому
`ПутьКДанным` и не останавливает импорт. Импорт расширения
`/Users/nikita/git/sed_xml/cfe/дкз` останавливается на собственном плане обмена
`дкз_ОбменТипы`:

```text
Для элемента состава «Справочник.ПроектныеЗадачи» не задан режим ExtensionProperty
```

В XML этого плана нет `ObjectBelonging=Adopted`: это собственный объект
расширения. Тем не менее импорт `ExchangePlanContent` безусловно объединяет
`Item` с `ExtensionProperty`, как для состава заимствованного плана. Такой же
риск есть в других местах, где выбор формы XML определяется только видом
компонента `configurationExtension`.

Собственный объект расширения имеет полную форму XML и должен обрабатываться
как собственный объект обычной конфигурации. Специальные состояния расширения
относятся только к заимствованному объекту и его вложенным значениям.

## Цель

Ввести один общий договор варианта текущего объекта и использовать его во всех
зависящих от принадлежности правилах:

- `full` — собственный объект конфигурации или расширения;
- `adopted` — заимствованный объект расширения;
- вложенное значение без собственной принадлежности наследует вариант
  владельца.

Вид компонента остаётся отдельным признаком. Он применяется только там, где
сама XML-форма действительно различается у всех объектов расширения независимо
от их принадлежности.

## Основной договор

### Определение варианта при XML → YAML

Перед импортом свойств каждого metadata item runtime вызывает предварительный
метод зарегистрированного `MetadataItemXmlImportAugmenter`. Метод получает
текущий контекст, правило и XML-источник и может вернуть вариант текущего
объекта.

Дополнение расширения определяет вариант без перечня конкретных `itemType`:

1. Если rules.ts текущего metadata item объявляет служебное свойство
   принадлежности, точное значение `ObjectBelonging=Adopted` даёт `adopted`.
2. Для такого же объекта отсутствие `ObjectBelonging=Adopted`, в том числе
   отсутствие поля или значение `Native`, даёт `full`.
3. Если текущее вложенное правило не объявляет собственной принадлежности,
   новый вариант не создаётся: оно наследует вариант ближайшего владельца.
4. В обычной конфигурации исходным вариантом является `full`.

Определение выполняется до импорта обычных свойств. Поэтому все вложенные
преобразователи видят правильный вариант, в том числе `ExchangePlanContent`,
предопределённые элементы, составные свойства и пустые смысловые коллекции.

### Область жизни контекста

В `fromXML` добавляется поле текущего варианта объекта. Runtime создаёт
локальный контекст для рекурсивного вызова, записывает в него вычисленный или
унаследованный вариант и передаёт этот контекст импорту всех свойств и
последующему `augment`.

После выхода из metadata item восстанавливать изменяемое глобальное состояние
не требуется: родительский контекст не изменяется. Соседние элементы не могут
унаследовать вариант друг друга.

Предварительный метод является необязательным. Компоненты без дополнения и
существующие дополнения, которым вариант не нужен, продолжают работать без
изменений. Нейтральный runtime знает только значения варианта и порядок
вызовов; он не знает про `ObjectBelonging`, расширения или конкретные виды
метаданных.

### Симметрия YAML → XML

Экспорт не вычисляет принадлежность заново из частных свойств. Он использует
существующий `xmlDefaultVariantByLogicalAddress`, который уже классифицирует
адреса как `full`, `adopted` или `indexed` по индексам целевого компонента и
основной конфигурации.

Правила, зависящие от принадлежности, получают текущий `borrowed`/вариант из
этого профиля:

- `full` формирует обычную полную XML-форму;
- `adopted` формирует служебные состояния расширения;
- `indexed` сохраняет существующее поведение обычной конфигурации и не
  приравнивается к `adopted`.

Таким образом, XML → YAML и YAML → XML используют один смысловой договор, но
каждое направление получает факт из уже доступного надёжного источника: XML
текущего объекта при импорте и профиль адресов при экспорте.

## Применение договора

### Состояния свойств и коллекций

Обработка `PropertyState`, `ExtensionProperty`, состояний предопределённых
элементов и других служебных секций выполняется только при `adopted`.

Для состава плана обмена это означает:

| Вариант владельца | Импорт XML → YAML | Экспорт YAML → XML |
| --- | --- | --- |
| `full` | обычные `Item`, без объединения с `ExtensionProperty` | только обычные `Item` |
| `adopted` | объединение `Item` и состояний `ExtensionProperty` | `Item` и требуемые `ExtensionProperty` |

Параметр `borrowed`, уже передаваемый экспорту состояния коллекции, становится
обязательной развилкой поведения, а не игнорируется для
`ExchangePlanContent`.

### Пустые смысловые значения

Общий экспортёр не должен считать пустое свойство «свойством расширения» лишь
потому, что весь компонент является расширением. Решение о специальной пустой
форме принимается по варианту текущего логического адреса. Собственное пустое
свойство расширения получает ту же каноническую XML-форму, что и в обычной
конфигурации.

### Проверка существующих частных условий

В ходе реализации проверяются все ветвления по
`componentKind === configurationExtension` в metadata-правилах и runtime.
Каждое ветвление классифицируется:

- зависящее от принадлежности переводится на текущий вариант;
- действительно общее для всего расширения остаётся на `componentKind` и
  закрепляется тестом собственного и заимствованного объекта;
- сомнительное не меняется без XML-примеров, подтверждающих требуемую форму.

В частности, различие `FillValue` стандартного реквизита может быть
компонентным, а не связанным с принадлежностью: в исследованном собственном
объекте расширения встречается `xsi:nil`. Его нельзя механически переводить на
вариант объекта вместе с состояниями коллекций.

## Ошибки и диагностика

- У `adopted` обязательное состояние остаётся обязательным. Если элементу
  состава или свойству нужен режим, но он отсутствует, импорт/экспорт
  завершается существующей содержательной ошибкой с адресом элемента.
- У `full` наличие `PropertyState`, `ExtensionProperty` или другого маркера,
  допустимого только у заимствованной формы, является противоречием XML и
  завершается ошибкой. Маркер не игнорируется молча.
- Неизвестное значение `ObjectBelonging` не угадывается и проходит через
  существующую проверку системного перечисления.
- Отсутствие предварительного метода дополнения означает наследование текущего
  варианта, а не неявное предположение `adopted`.

## Изменения интерфейсов

Пользователь явно согласовал расширение общих интерфейсов для этого договора.
Планируемые изменения ограничены двумя точками:

1. Необязательный предварительный метод в
   `MetadataItemXmlImportAugmenter`, определяющий вариант до импорта свойств.
2. Поле текущего варианта в `FromXMLConfigurationContext`.

Новые поля в `BasePropertyRule`, `PropertyRule` и параметрах построителей
правил не вводятся. Зависимые правила читают вариант из контекста, а не
получают отдельные частные флаги.

## Проверка

Тесты следуют `.agents/testing.md`; существующие XML-фикстуры не изменяются.

### Модульные тесты runtime

- предварительный метод вызывается до импорта свойств;
- `full` и `adopted` доступны всем вложенным преобразователям;
- вложенное значение без собственной принадлежности наследует вариант;
- metadata item с собственной принадлежностью переключает вариант;
- после возврата соседний элемент получает вариант своего владельца, а не
  предыдущего элемента;
- отсутствие предварительного метода сохраняет прежнее поведение.

### Матрица правил расширения

Одинаковые механизмы проверяются минимум в трёх вариантах: обычная
конфигурация, собственный объект расширения и заимствованный объект расширения.
Матрица охватывает:

- `PropertyState`;
- составное свойство с вложенными metadata items;
- предопределённые элементы;
- пустую смысловую коллекцию;
- `ExchangePlanContent` как регрессионный случай.

Тесты подтверждают как успешную каноническую форму, так и ошибки при
противоречивом сочетании варианта и служебных секций.

### Проверка на реальном проекте

1. Импортировать `/Users/nikita/git/sed_xml` во временный проект, не изменяя
   рабочий `/Users/nikita/git/sed_nkdk`.
2. Убедиться, что `cf` и `cfe/дкз` импортированы, а ошибка
   `дкз_ОбменТипы` отсутствует.
3. Выполнить round-trip обоих компонентов и сравнить результат с исходным XML
   штатными средствами проекта.
4. Проверить, что предупреждение `ПутьКДанным` в `cf` не превратилось в ошибку
   и по-прежнему сохраняет исходное значение.
5. Выполнить `pnpm test`, `pnpm duplicates -- --base <базовый-коммит>`,
   `pnpm test:architecture:rules` и `pnpm test:architecture`.

## Документация архитектуры

В реализации обновляется `.agents/architecture.md`:

- в subprocess XML → YAML добавляется предварительное определение варианта
  текущего metadata item;
- описывается наследование варианта вложенными значениями;
- фиксируется разделение ответственности между текущим вариантом импорта,
  `xmlDefaultVariantByLogicalAddress` экспорта и видом компонента.

Обновление документа явно согласовано пользователем. Если реализованный поток
будет отличаться от этой спецификации, архитектурный документ не подгоняется
молча: расхождение сначала выносится на согласование.

## Вне границ задачи

- частные исключения по имени `дкз_ОбменТипы`, `ExchangePlanContent` или
  конкретному `itemType`;
- изменение формата смыслового YAML;
- добавление новых `!xml`;
- изменение или перезапись существующих XML-фикстур;
- механическая замена всех проверок `componentKind` без подтверждения XML;
- исправление самого неразрешённого `ПутьКДанным` в `cf`;
- изменение общей классификации адресов профиля восстановления XML, если
  проверка не обнаружит самостоятельного дефекта в ней.

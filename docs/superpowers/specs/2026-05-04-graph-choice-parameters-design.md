# Дизайн: `choiceParameters` в графе

Тип: дизайн-документ.

## Контекст

`ChoiceParameters` в JS-модели представлены массивом элементов:

```ts
interface ChoiceParameter {
  name: string
  value?: MetadataValue
}
```

В YAML это record-форма:

```yaml
ПараметрыВыбора:
  Отбор.ОтветственноеЛицо: Пользователь()
```

Сейчас без отдельной графовой регистрации `choiceParameters` проходят через
`flattenItem` и превращаются в свойства родительского узла вида
`p_choiceParameters_Отбор.ОтветственноеЛицо`. Это неверно по двум причинам:

- `choiceParameters` являются дочерней коллекцией, а не простым свойством
  владельца;
- ключи record-формы содержат точки и русские сегменты, что плохо подходит для
  плоских имён свойств графа.

`choiceParameterLinks` не входит в этот дизайн. Это отдельный случай и должен
проектироваться отдельно.

## Решение

`ChoiceParameters` регистрируется как type-specific `buildGraphFromModel`.
Если обработчик создаёт графовые операции, оркестратор добавляет
`choiceParameters` в `skipKeys` родительского узла, поэтому
`p_choiceParameters_*` не появляется.

Каждый элемент `ChoiceParameter` становится owned-узлом:

```text
(:MetadataAttribute {id: "Документ.АвансовыйОтчет.Реквизит.Руководитель"})
  -[:CHOICE_PARAMETER {yaml: "ПараметрВыбора", index: 0}]->
(:ChoiceParameter {
  id: "Документ.АвансовыйОтчет.Реквизит.Руководитель.ПараметрВыбора[0]",
  name: "Отбор.ОтветственноеЛицо"
})
```

`CHOICE_PARAMETER` добавляется в реестр `edgeKinds` как owning-ребро.
Атрибут `index` обязателен: хотя YAML использует record-форму, порядок элементов
нужен для будущего восстановления модели и стабильного round-trip.

## Значение параметра

Поле `value` остаётся частью узла `ChoiceParameter`.

Простые значения `MetadataValue` сохраняются в props узла через общий механизм
`flattenItem`, например как `p_value_type` и `p_value_value`.

Ссылочные и объектные значения обрабатываются существующим
`MetadataValue buildGraphFromModel`:

- `type: "ref"` создаёт reference-ребро `VALUE`;
- `type: "objectRef"` создаёт reference-ребро `OBJECT`.

Источник этих рёбер — узел `ChoiceParameter`, а не владелец реквизита или
элемента формы.

## Идентификаторы

Идентификатор узла строится от владельца и позиции элемента:

```text
<parentNodeId>.ПараметрВыбора[<index>]
```

`name` хранится как свойство узла и используется для восстановления YAML-ключа.
Позиционный идентификатор выбран намеренно: имя параметра может содержать точки,
русские сегменты и другие символы пути, а `index` уже является частью контракта
ordered-коллекции.

## Границы

Этот дизайн не реализует восстановление `граф -> модель`, но фиксирует контракт
для него:

- `choiceParameters` не дублируются в props владельца;
- порядок задаётся `index` на `CHOICE_PARAMETER`;
- YAML-ключ восстанавливается из `ChoiceParameter.name`;
- значение восстанавливается из props узла и рёбер `VALUE`/`OBJECT`.

`choiceParameterLinks` специально исключён из границ дизайна.

## Проверка

Нужны тесты на контракт:

1. Родительский узел с `choiceParameters` не содержит ключей
   `p_choiceParameters_*`.
2. Для каждого параметра создаётся узел `ChoiceParameter` и owning-ребро
   `CHOICE_PARAMETER` с `index`.
3. Параметр со ссылочным `MetadataValue` создаёт `VALUE` или `OBJECT` от узла
   `ChoiceParameter`.
4. Прямой импорт `buildGraph` из CLI-контекста поднимает регистрацию
   `ChoiceParameters`.

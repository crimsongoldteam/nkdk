# XML-свойства заполнения реквизитов табличных частей

## Контекст

После отказа YAML → XML от `preserveFromReferenceXML` полный round-trip
`cf/doc` добавляет реквизитам табличных частей бизнес-процессов:

```xml
<FillFromFillingValue>false</FillFromFillingValue>
<FillValue xsi:nil="true"/>
```

В первом diff `BusinessProcesses/Исполнение.xml` эта пара добавляется 35
раз. Во всём текущем diff она добавляется 2 193 раза.

Причина находится в общем `MetadataTabularSectionAttributeRules`: оно
содержит `fillFromFillingValue` и `fillValue` для всех владельцев
табличных частей. Раньше отсутствие тегов переносилось из reference XML и
маскировало слишком широкое правило.

Проверенные XML-фикстуры показывают два разных договора:

- у табличных частей каталогов, документов, задач, бизнес-процессов,
  планов обмена, планов счетов, планов видов расчёта и планов видов
  характеристик свойства заполнения отсутствуют;
- у табличных частей отчётов и обработок свойства заполнения присутствуют;
- реквизиты адресации задачи также поддерживают свойства заполнения.

## Рассмотренные варианты

### Один общий набор свойств с условным экспортом

Обработчик мог бы проверять владельца и решать, выводить ли `Fill*`.
Вариант отклонён: он возвращает знание о конкретных `itemType` в общий
слой и оставляет JSON Schema шире фактического XML-договора.

### Всегда исключить свойства заполнения

Удаление `fillProperties` из общего правила устранило бы текущий diff, но
сломало бы отчёты, обработки и реквизиты адресации задачи.

### Разделить варианты rules.ts

Выбранный вариант: базовое правило реквизита табличной части не содержит
`Fill*`, а специализированное правило добавляет их только там, где они
допустимы. Выбор выполняется декларативно правилами владельца.

## Архитектура

`MetadataTabularSectionAttributeRules` становится базовым вариантом без:

- `fillFromFillingValue`;
- `fillValue`;
- соответствующих элементов `xmlOrder`.

Рядом объявляется специализированный вариант с этими двумя свойствами.
Он используется коллекциями реквизитов табличных частей:

- `MetadataDataProcessorTabularSectionRules`;
- `MetadataReportTabularSectionRules`.

Остальные варианты табличных частей продолжают использовать базовое
правило.

`MetadataTaskAddressingAttributeRules` расширяет специализированный
вариант, поскольку его XML-договор включает свойства заполнения.

Для выбора варианта используется существующая регистрация property type
и декларация свойства `attributes`. Новых условий по владельцу в
`orchestration`, `validation` и `project` не добавляется.

## YAML и проверка

Для реквизитов табличных частей базового варианта поля
`ЗаполнятьИзДанныхЗаполнения` и `ЗначениеЗаполнения` перестают входить в
JSON Schema и считаются неизвестными.

Для отчётов, обработок и реквизитов адресации задачи поля остаются
доступными. Неявные значения не записываются в YAML, а при YAML → XML
восстанавливаются непосредственно по `rules.ts`, без reference XML и
снимка.

## Тестирование

Существующие XML-фикстуры не изменяются.

Наблюдаемый договор фиксируется существующей фикстурой
`metadataAttribute/__fixtures__/documentTabular.xml`:

1. её XML → YAML → XML не добавляет `FillFromFillingValue` и `FillValue`;
2. табличный реквизит отчёта или обработки сохраняет явные `Fill*`;
3. реквизит адресации задачи сохраняет явные `Fill*`;
4. JSON Schema базового и специализированного вариантов отражает разные
   допустимые поля.

После узких тестов выполняются `pnpm test` и повторный полный round-trip
`cf/doc`. В первом diff не должно остаться 35 добавленных пар `Fill*`;
остальные добавления этой пары классифицируются по владельцу.

## Вне границ

- Возврат `preserveFromReferenceXML`.
- Хранение признака присутствия тегов в YAML или снимке.
- Исправление других XML-default и перестановок.
- Частные проверки владельца в общих metadata-слоях.

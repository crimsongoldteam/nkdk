# Контроль свойств расширения конфигурации в YAML

## Цель

Значимые режимы свойств заимствованных объектов хранятся в YAML. Снимок
конфигурации не хранит эти режимы и не участвует в их восстановлении.

Спецификация не меняет устройство снимка, его файловый формат или используемое
хранилище.

## Пользовательская модель

Конфигуратор показывает режим свойства значком. YAML сохраняет именно этот
режим, а не буквальное устройство `xr:PropertyState`:

| Значок в Конфигураторе | Смысл | YAML |
|---|---|---|
| Значка нет | Собственное значение объекта расширения | Обычное значение без тега |
| Сине-красный | Значение контролируется | Обычное значение без тега |
| Зелёный | Значение проверяется с предупреждением | `!проверять` |
| Оранжевый | Значение изменяется расширением | Обычное значение, если это единственный доступный режим; иначе `!изменять`; для вынесенного содержимого — раздел `Изменять` |
| Значок режима снят | Заимствованное свойство не участвует в расширении | Свойство отсутствует |

Отсутствие значка и снятый значок режима — разные случаи. У собственного
свойства режима контроля нет, однако его значение принадлежит расширению и
сохраняется в YAML. У заимствованного свойства снятый значок означает, что
свойство не участвует в расширении и отсутствует в YAML.

Это различие определяется не формой значения и не именем YAML-поля, а ролью
свойства в конкретном metadata-объекте. Например, `Синоним` конфигурации
расширения является собственным значением без значка, а `Синоним`
заимствованного справочника — модифицируемым свойством с оранжевым значком.

Набор доступных значков зависит от свойства. YAML проверяется по той же модели:

- `ОбъектРасширяемойКонфигурации` допускает отсутствие, обычный контроль и
  `!проверять`; изменять это свойство нельзя;
- основные формы и другие свойства, для которых Конфигуратор показывает только
  оранжевый значок, записываются обычным значением: само наличие поля означает
  `Изменять`;
- `Тип` допускает составные режимы только у тех объектов, для которых это
  разрешает платформа; в остальных правилах он остаётся обычным контролируемым
  свойством;
- элементы `Состав` общего реквизита допускают только отсутствие или обычный
  сине-красный контроль без `!проверять` и `!изменять`;
- для остальных свойств допустимые режимы определяются видом metadata-объекта и
  версией платформы.

Недопустимый для свойства режим является ошибкой валидации YAML.

## Возможности свойств

Каждая пара «вид metadata-объекта + свойство» задаёт набор разрешённых
возможностей. Это не взаимоисключающие классы:

| Возможность | Представление в YAML |
|---|---|
| Собственное значение | Обычное значение; теги режимов запрещены |
| Контролировать | Обычное значение без тега |
| Проверять | `!проверять` |
| Изменять | Обычное значение для свойства только с этим режимом; `!изменять` для многорежимного свойства; для вынесенного содержимого — раздел `Изменять` |
| Составные режимы | Режим задаётся отдельным частям значения |

Одно свойство может разрешать несколько возможностей. Например, `ДлинаКода`,
`ДопустимаяДлинаКода` и `ДлинаНаименования` плана обмена допускают обычный
контроль, `!проверять` и `!изменять`. Элементы `Состав` общего реквизита
допускают только обычный контроль, а наличие основной формы само означает
единственный доступный ей режим `Изменять`.

Наличие одной возможности не означает наличия другой. Допустимый набор нельзя
надёжно вывести только из XML-имени свойства, YAML-имени или типа его значения.
Он задаётся правилами конкретного вида metadata-объекта.
Повторяющиеся группы объявляются один раз в общих фрагментах `rules.ts`, а
особенности конкретного объекта — рядом с его правилами. Полная плоская таблица
всех свойств не дублируется в отдельном центральном модуле.

Допустимость режима и операции не является настраиваемой политикой NKDK. В том
числе возможность изменить отсутствующее в расширяемой конфигурации значение
или внешнее содержимое должна точно повторять поведение Конфигуратора для пары
«вид объекта + свойство» при выбранном режиме совместимости расширения. Такие
ограничения исследуются по Конфигуратору и описываются в `rules.ts`, а не
согласовываются как отдельные правила YAML-формата.

## Доступность свойств заимствованного объекта

Обычный metadata-объект и его заимствованное представление имеют разные
закрытые списки полей. Поле сначала должно быть доступно для данного вида
заимствованного объекта, затем выбранный YAML-режим должен входить в набор его
возможностей. Остальные поля запрещены и не восстанавливаются из снимка.

### Общие профили

Профиль — повторяемая группа правил. Он подключается в rules.ts конкретного
вида объекта; совпадение имени свойства само по себе профиль не подключает.

| Профиль | Возможности |
|---|---|
| База заимствованного объекта | `Имя`, `Комментарий` — собственные; `ОбъектРасширяемойКонфигурации` — контролировать или проверять |
| Изменяемый синоним | `Синоним` — изменять |
| Модули | перечисленные видом объекта модули — изменять вынесенное содержимое |
| Основные формы | перечисленные основные формы — изменять |
| Представления | перечисленные представления и `Пояснение` — изменять |
| Дочерняя форма | база + изменяемые `Синоним` и вынесенное содержимое `Форма` |
| Дочерний макет | За границами этой спецификации: `Template.xml` пока сохраняется как непрозрачный внешний XML вместе с `PropertyState` |
| Типизированное поле | `Тип` — контролировать или проверять; применимые форматы, `Подсказка` и `ФормаВыбора` — изменять |
| Табличная часть | база + изменяемая `Подсказка`; режим `Синонима` задаётся отличием владельца |
| Команда | база + собственный `ТипПараметраКоманды` + изменяемые `Синоним`, `МодульКоманды`, `Подсказка` и `Картинка`; режим `Группы` задаётся отличием владельца |
| Регистровое поле | база + изменяемый `Синоним` + типизированное поле; специальные признаки поля подключаются отдельно |

Профили описывают итоговые возможности, а не значок, выбранный на отдельном
снимке. Значки используются только как подтверждение профиля или отличия.

### Подключение профилей к видам объектов

Во всех строках ниже подразумевается профиль «База заимствованного объекта».
Колонка «Специальные свойства» содержит только дополнения к перечисленным
профилям.

| Виды объектов | Дополнительные профили | Специальные свойства |
|---|---|---|
| Регистры расчёта, бухгалтерии, накопления и сведений | Изменяемый синоним, модули, основные формы, представления | Контролируемые свойства регистра задаются его видом: периодичность, режим записи, вид регистра, план счетов или параметры расчёта |
| План обмена, справочник, планы видов характеристик, счетов и расчёта | Изменяемый синоним, модули, основные формы, представления | Иерархия, владельцы, состав, предопределённые данные и параметры кода задаются видом объекта |
| Документ, нумератор, бизнес-процесс, задача | Изменяемый синоним, модули, основные формы, представления | Нумерация, адресация, карта маршрута, задачи и движения задаются видом объекта |
| Обработка, отчёт, перечисление, журнал документов | Изменяемый синоним, модули, основные формы, представления | Основная СКД отчёта и регистрируемые документы журнала задаются видом объекта |
| Последовательность | Изменяемый синоним, модули | Измерения последовательности подключаются отдельно |
| Константа | Изменяемый синоним, модули, основные формы, представления, типизированное поле | — |
| Подсистема | Изменяемый синоним | `Состав`, командный интерфейс, пояснение и картинка изменяются |
| Общий модуль | Изменяемый синоним, модули | Флаги выполнения контролируются или проверяются |
| Параметр сеанса, роль | Изменяемый синоним | `Тип` параметра контролируется; `Права` роли изменяются |
| Общий реквизит | Изменяемый синоним, типизированное поле | `Состав` целиком изменяется; его элементы только контролируются; автоиспользование и разделение данных контролируются или проверяются |
| Критерий отбора | Изменяемый синоним, основные формы, команды | `Тип` контролируется; элементы состава только контролируются |
| Подписка на событие | Изменяемый синоним | `Источник` изменяется; остальные свойства, отсутствующие на панели, запрещены |
| Регламентное задание | Изменяемый синоним | Другие свойства обычного задания, отсутствующие на панели, запрещены |
| Бот | Изменяемый синоним, модули | `Картинка` изменяется; остальные свойства, отсутствующие на панели, запрещены |
| Функциональная опция | Изменяемый синоним | `Размещение` контролируется или проверяется; доступность `СоставаФункциональнойОпции` зависит от типа размещения |
| Параметр функциональных опций | Изменяемый синоним | `Использование` недоступно и запрещено |
| Определяемый тип | Изменяемый синоним | `Тип` контролируется и допускает составную запись |
| Хранилище настроек | Изменяемый синоним, модули, основные формы, представления | Дополнительные формы и макеты подключаются как дочерние объекты |
| Элемент стиля, стиль, язык | Изменяемый синоним | Вид элемента и код языка контролируются; значение элемента или Style.xml изменяются |
| Пакет XDTO | Изменяемый синоним | Пространство имён и вынесенный пакет допускают все режимы |
| Web-, HTTP- и интеграционные сервисы, WebSocket-клиент | Изменяемый синоним, модули | Структурные ограничения дочерних объектов приведены отдельно |
| WS-ссылка и дочерние объекты Web-/HTTP-сервисов | Изменяемый синоним | Другие пользовательские свойства не подтверждены |
| Внешний источник данных | Изменяемый синоним | Таблицы, кубы и функции подключаются как дочерние объекты |
| Таблица и куб внешнего источника данных | Изменяемый синоним, модули, основные формы, представления | Вид таблицы контролируется; соответствие внешней схеме задаётся отличиями |
| Таблица измерения куба | Изменяемый синоним, модули, основные формы, представления | Соответствие внешней схеме задаётся отличиями |

Корневая конфигурация расширения не использует базовый профиль: её `Имя`,
`Синоним`, `Комментарий`, назначение, префикс, язык, поставщик и версия —
собственные значения. Связь с основной конфигурацией и режимы совместимости
контролируются или проверяются; роли, интерфейсы, стиль, картинки и основные
формы изменяются.

### Повторяющиеся дочерние объекты

| Вид | Профиль | Отличия |
|---|---|---|
| Реквизит, измерение, ресурс | Регистровое поле | `Ведущее`, `Балансовый`, `ПризнакУчета` и подобные свойства подключаются только поддерживающими их видами |
| Реквизит адресации задачи | Регистровое поле | `ИзмерениеАдресации` допускает все режимы |
| Поле таблицы внешнего источника данных | Регистровое поле | Имя в источнике, только чтение и разрешение Null допускают все режимы |
| Измерение куба | Регистровое поле | Форма выбора и подсказка изменяются |
| Ресурс куба | Регистровое поле | Имя в источнике допускает все режимы; форматы и подсказка изменяются |
| Табличная часть | Табличная часть | У справочника `Синоним` проверяется; у остальных подтверждённых видов изменяется |
| Форма | Дочерняя форма | Расширенное представление изменяется, когда оно доступно |
| Команда | Команда | Режим `Группы` задаётся отличием владельца |
| Макет | За границами этой спецификации | `Template.xml` пока сохраняется как непрозрачный внешний XML |
| Значение перечисления, перерасчёт | База + изменяемый синоним | Специальных свойств не подтверждено |
| Измерение последовательности | Регистровое поле | Кроме `Тип` специальных свойств не подтверждено |
| Графа журнала документов | База + изменяемый синоним | `Ссылки` контролируются или проверяются |
| Признак учёта плана счетов | Регистровое поле | Форматы и подсказка изменяются |
| Функция внешнего источника данных | База + изменяемый синоним | `Тип` — собственное значение; возвращаемое значение и выражение допускают все режимы |

### Отличия команд

| Случай | Отличие от общего профиля |
|---|---|
| Общая команда | `Группа` допускает все режимы |
| Остальные подтверждённые команды | `Группа` контролируется или проверяется |

### Специальные ограничения

Набор YAML-полей заимствованного объекта закрытый. Для него разрешены только
свойства, перечисленные в подключённых профилях, отличиях вида и таблице
«Свойства, допускающие все режимы». Полная схема обычного metadata-объекта к
нему неприменима: произвольное свойство, допустимое у собственного объекта
расширения, у заимствованного объекта запрещено, если его нет в этих списках.

| Случай | Правило |
|---|---|
| Элемент `Состав` общего реквизита или критерия отбора | Только отсутствие или обычный контроль; проверять и изменять нельзя |
| `СоставФункциональнойОпции` с булевым `Размещением` | Изменяется целиком |
| `СоставФункциональнойОпции` с небулевым `Размещением` | Недоступен и запрещён; доступность определяется типом объекта из `Размещения`, а не именем опции |
| `Тип` с разными режимами подтипов | Используется составная запись из раздела «Составной тип» |
| `ТипФормы`, `ТипМакета` | Могут присутствовать в XML как служебные копии, но в YAML запрещены |
| Вспомогательные формы хранилища настроек | Недоступны и запрещены; дочерние формы и макеты заимствуются независимо |
| Общая картинка | Недоступные у заимствованного объекта свойства выбора и оформления в YAML запрещены |
| Свойства сервисов, отсутствующие на панели | URL, обработчики, имена процедур, сеансовые параметры и подобные поля в YAML запрещены |
| Свойство, отсутствующее в профиле и отличиях вида | Запрещено, даже если существует у обычного metadata-объекта |

### Ограничения структуры расширения

Собственным считается объект без связи `ОбъектРасширяемойКонфигурации`;
заимствованным — объект, связанный с объектом основной конфигурации. Возможность
добавить собственный дочерний объект зависит от вида заимствованного владельца.

Для корневого заимствованного объекта связь хранится в
`ОбъектРасширяемойКонфигурации`. Для дочернего объекта отдельная связь в YAML
не нужна: он считается заимствованным при совпадении вида и имени внутри
соответствующего владельца основной конфигурации. Если совпадения нет, объект
считается собственным. Собственные дочерние объекты разрешены по умолчанию,
кроме явно перечисленных ниже запретов; создать собственный одноимённый объект
вместо заимствованного нельзя.

| Владелец или раздел | Что разрешено | Что запрещено |
|---|---|---|
| Заимствованная подсистема | Добавлять собственные дочерние подсистемы | Помещать заимствованную подсистему внутрь собственной подсистемы |
| Конфигурация расширения | Заимствовать существующие общие реквизиты, боты, хранилища настроек, языки и WebSocket-клиенты, если их свойства поддержаны | Создавать собственные общие реквизиты, боты, хранилища настроек, языки и WebSocket-клиенты |
| Заимствованный Web-сервис | Заимствовать существующие операции | Добавлять собственные операции |
| Заимствованная операция Web-сервиса | Заимствовать существующие параметры | Добавлять собственные параметры |
| Заимствованный HTTP-сервис | Заимствовать существующие шаблоны URL | Добавлять собственные шаблоны URL |
| Заимствованный шаблон URL HTTP-сервиса | Заимствовать существующие методы | Добавлять собственные методы |
| Заимствованный журнал документов | Заимствовать существующие графы | Добавлять собственные графы |
| Заимствованный план видов характеристик | Заимствовать существующие реквизиты, табличные части и реквизиты табличных частей | Добавлять собственные реквизиты, табличные части и реквизиты табличных частей |
| Заимствованный план счетов | Заимствовать существующие реквизиты, признаки учёта, признаки учёта субконто, табличные части и реквизиты табличных частей | Добавлять собственные объекты перечисленных видов |
| Заимствованный план видов расчёта | Заимствовать существующие реквизиты, табличные части и реквизиты табличных частей | Добавлять собственные реквизиты, табличные части и реквизиты табличных частей |
| Любой заимствованный регистр | Заимствовать существующие измерения, ресурсы и реквизиты | Добавлять собственные измерения, ресурсы и реквизиты |
| Заимствованный регистр расчёта | Заимствовать существующие перерасчёты | Добавлять собственные перерасчёты |

Ограничения применяются одновременно на двух уровнях:

- валидация обязана выдавать ошибку для запрещённого свойства, объекта или
  отношения владения, даже если общие rules.ts умеют прочитать такую структуру;
- схема и автодополнение должны предлагать только допустимые свойства и
  дочерние объекты с учётом вида и принадлежности владельца. Если ограничение
  зависит от других файлов или индекса основной конфигурации и не выражается
  статической JSON Schema, подсказки формируются контекстным слоем из того же
  реестра ограничений, который использует валидация.

Валидация является обязательной и окончательной проверкой. Подсказки схемы
помогают не создать запрещённую запись, но их отсутствие или неполнота не
делают такую запись допустимой.

Валидация всегда выполняется для всего проекта. Отдельного режима валидации
одного изменённого YAML-файла или его зависимостей нет. Состояние проекта может
повторно использовать результаты для неизменённых файлов, но обход проекта и
проверка зависимостей выполняются по полному актуальному состоянию.

Индекс расширяемой конфигурации обязателен для валидации расширения. Без него
нельзя отличить заимствованный дочерний объект от собственного и проверить
закрытые списки свойств; поэтому отсутствие индекса является ошибкой, а не
предупреждением.

### Структура заимствованных сервисов

| Заимствованный родитель | Дочерний объект | Ограничение |
|---|---|---|
| Web-сервис | Операция | Новую операцию добавить нельзя; в YAML допустимы только операции, уже заимствованные из расширяемой конфигурации |
| Операция Web-сервиса | Параметр | Новый параметр добавить нельзя; в YAML допустимы только параметры, уже заимствованные из расширяемой конфигурации |
| HTTP-сервис | Шаблон URL | Новый шаблон добавить нельзя; в YAML допустимы только шаблоны, уже заимствованные из расширяемой конфигурации |
| Шаблон URL HTTP-сервиса | Метод | Новый метод добавить нельзя; в YAML допустимы только методы, уже заимствованные из расширяемой конфигурации |
| Сервис интеграции | Канал | Новый собственный канал расширения добавить можно; это исключение из ограничений Web- и HTTP-сервисов |

Ограничение относится только к родителю с принадлежностью `Заимствованный`.
Объект, созданный самим расширением, сохраняет обычные правила создания
дочерних объектов.

Элементы `Состав` общего реквизита образуют вложенную контролируемую группу:
для каждого объекта доступно только включение с сине-красным флажком либо
исключение из состава.

### Исходные пробелы, закрываемые этой спецификацией

| Возможность спецификации | Требуемая реализация |
|---|---|
| `!проверять`, `!изменять` | Зарегистрировать локальные YAML-теги наряду с `!xml` |
| Возможности свойства по владельцу | Хранить профили и отличия во внешнем реестре, не расширяя `PropertyRule` |
| Закрытый список полей заимствованного объекта | Строить отдельную схему заимствованного представления |
| Импорт `Notify` | Создавать тег `!проверять` |
| Импорт и экспорт обычного `Extended` | Поддержать скалярные свойства и вынесенные сегменты без записи режима в снимок |
| Разделы `Проверять` и `Изменять` | Реализовать двустороннее преобразование вынесенных свойств |
| `MultiState` для `Тип` | Разбирать и собирать `CheckValue`, `NotifyValue`, `ExtendValue` |
| `Состав` общего реквизита | Проверять режим списка и ограничения его элементов |
| Условный `СоставФункциональнойОпции` | Проверять доступность состава по типу размещения |
| Режим внешнего `Пакет` XDTO | Зарегистрировать имя `Пакет` как вынесенное свойство, оставив `Package.bin` внешним файлом |
| Проверка допустимости режима | Диагностировать неизвестный или запрещённый режим и конфликт разделов |

Следовательно, смысловые значения всех обычных свойств подтверждённых матриц
уже имеют правила. Для внешнего `Пакет` XDTO режим привязывается к имени
вынесенного свойства, а `Package.bin` продолжает копироваться без
преобразования. Преобразование дочернего макета в смысловой YAML вынесено в
отдельное ограничение проекта и не входит в эту спецификацию. Общая
инфраструктура режимов также требует расширения; добавлять тысячи копий обычных
property rules не требуется.

## Теги YAML

`!проверять` и `!изменять` — локальные теги формата NKDK, как и существующий
`!xml`. Тег добавляет к смысловому значению режим свойства и не меняет тип
самого значения:

```yaml
ОбъектРасширяемойКонфигурации: !проверять
ДлинаКода: !изменять 12
Формат: !проверять "ДФ=dd.MM.yyyy"
```

`!изменять` ставится только у многорежимного свойства, для которого необходимо
отличить `Изменять` от `Контролировать` и `Проверять`. Если свойство допускает
только `Изменять`, используется обычное значение без тега:

```yaml
Синоним: Новый синоним
```

`!проверять` сохраняется даже при полном совпадении значения с расширяемой
конфигурацией. Тег обозначает выбранный режим свойства, а не наличие
расхождения. Пустое значение с `!проверять` не является особым случаем: если
базовое значение непустое, валидация выдаёт предупреждение, а не ошибку.

`!изменять` также сохраняется при совпадении значения с расширяемой
конфигурацией: тег обозначает явно выбранный режим свойства, а не обязательное
расхождение значений.

Пустое изменяемое значение записывается без искусственного значения:

```yaml
Нумератор: !изменять
```

Это не то же самое, что отсутствие поля. Пустой `!изменять` означает явно
очистить значение многорежимного свойства. Отсутствие поля означает, что
заимствованное свойство не участвует в расширении. В XML первый случай
представлен одновременно пустым `<Numerator/>` и состоянием
`PropertyState(Numerator, Extended)`.

Разборщик и сериализатор YAML поддерживают кириллицу в именах этих тегов как
расширение формата NKDK. Новый YAML всегда записывает канонические имена
`!проверять` и `!изменять`.

Старого раздела `Контроль` в публичном формате нет: он не читается, не
записывается и не мигрируется.

Обычный сине-красный контроль отдельного тега не имеет:

```yaml
Тип: ХранилищеЗначения
```

Существующий `!xml` сохраняет прежний смысл: это исключительное точное
XML-значение, которое нельзя восстановить из смыслового YAML. Он не обозначает
режим контроля свойства и не позволяет обходить предметный реестр
`PropertyState`. Неизвестное свойство, неизвестное состояние и известный режим,
недопустимый для свойства по `rules.ts`, останавливают импорт с ошибкой.

Импортированный и написанный вручную `!xml` равноправны только для уже
согласованных предметных XML-значений. Для них действуют общие правила `!xml`:
применение должно быть зарегистрировано для свойства, а данные должны иметь
корректную структуру. Служебное представление `PropertyState` через `!xml` не
поддерживается.

## Составной тип

Если у подтипов разные значки, `Тип` записывается списком. Тег ставится на тот
подтип, к которому относится соответствующий режим.

Проверяемый и изменяемый подтипы:

```yaml
Тип:
  - !проверять Дата
  - !изменять Булево
```

Контролируемый и изменяемый подтипы:

```yaml
Тип:
  - Справочник.СправочникПолный
  - !изменять Справочник.СправочникРеквизит
```

Даже единственный изменяемый подтип записывается списком:

```yaml
Тип:
  - !изменять Строка(10)
```

Эта форма означает `MultiState`, содержащий только `ExtendValue`, и точно
восстанавливает выгрузку Конфигуратора.

Пустая контролируемая часть сохраняется пустым элементом списка без тега:

```yaml
Тип:
  - []
  - !изменять Справочник.ПроектныеЗадачи
```

## Состав общего реквизита

`Состав` заимствованного общего реквизита является изменяемым структурным
свойством с оранжевым значком. Каждый объект внутри состава имеет только два
состояния: контроль снят либо установлен обычный сине-красный контроль. Зелёный
и оранжевый режимы для отдельного объекта недоступны.

В YAML `!изменять` ставится на список целиком, а элементы не получают тегов
режима:

```yaml
Состав: !изменять
  - Объект: Справочники.СправочникОбщиеРеквизиты
    Использование: Использовать
  - Объект: ПланыВидовРасчета.ПланРасчетаВсеСвойства
    Использование: НеИспользовать
```

Отсутствие объекта в списке означает снятый флажок. `!проверять` запрещён для
списка целиком; `!проверять` и `!изменять` запрещены на отдельном элементе.

`Состав` не использует модель `MultiState`: это отдельное правило сложного
свойства `CommonAttributeContent`. Вложенные сине-красные элементы являются
ожидаемой копией соответствующих элементов основной конфигурации. Если
контролируемый элемент или его параметры `Использование` и
`УсловноеРазделение` отличаются от основной конфигурации, NKDK выдаёт ошибку
валидации, не дожидаясь отказа проверки совместимости платформы.

## Вынесенное содержимое

У форм, модулей, прав, командных интерфейсов, картинок и другого вынесенного
содержимого значение находится в отдельном YAML-, BSL-, XML- или двоичном
файле. Режим относится к свойству metadata-объекта, а не к внешнему файлу.

Оранжевый режим задаётся в разделе `Изменять` YAML-файла самого объекта:

```yaml
Изменять:
  - Форма
  - МодульОбъекта
```

Содержимое продолжает храниться отдельно, например:

```text
Формы/ФормаЭлемента/Форма.yaml
МодульОбъекта.bsl
ПакетXDTO/ПакетОбмена/Package.bin
```

Для пакета XDTO `Пакет` является именем вынесенного свойства. Его режим
хранится в разделе `Проверять` или `Изменять` файла `Свойства.yaml`, а
`Package.bin` копируется без преобразования. При `Проверять: [Пакет]`
валидация сравнивает файл с `Package.bin` соответствующего пакета расширяемой
конфигурации побайтово.

Если `Пакет` указан в `Проверять` или `Изменять`, файл `Package.bin` обязателен.
Отсутствие файла является ошибкой; отдельного YAML-представления очистки
пакета нет.

Наличие имени в разделе `Изменять` означает оранжевый режим. Отсутствие имени
означает, что специальный режим для свойства не задан. Зелёный и сине-красный
режимы этим разделом не представляются.

Если таблица конкретного вида объекта разрешает зелёный режим вынесенного
свойства, он задаётся отдельным разделом `Проверять`:

```yaml
Проверять:
  - Пакет
```

Наличие внешнего файла без имени свойства в `Проверять` или `Изменять`
означает обычный сине-красный контроль. Отсутствие файла означает отсутствие
свойства. При обычном контроле внешний файл должен побайтово совпадать с файлом
расширяемой конфигурации. Для сравнения используются уже сохранённые
`contentHash`: хэш файла расширения из состояния проекта и хэш базового файла
из индекса конфигурации; повторно читать базовый файл не требуется. Одно имя
нельзя одновременно поместить в оба раздела. Раздел
`Проверять` запрещён для вынесенных свойств, которым таблица разрешает только
оранжевый режим.

Подтверждённые имена вынесенных свойств:

| YAML-имя | XML-имя |
|---|---|
| `Форма` | `Form` |
| `Модуль` | `Module` |
| `МодульОбъекта` | `ObjectModule` |
| `МодульМенеджера` | `ManagerModule` |
| `Права` | `Rights` |
| `Состав` | `Content` |
| `Предопределенные` | `Predefined` |
| `КомандныйИнтерфейс` | `CommandInterface` |
| `РабочаяОбластьНачальнойСтраницы` | `HomePageWorkArea` |
| `КомандныйИнтерфейсОсновногоРаздела` | `MainSectionCommandInterface` |
| `КартинкаОсновногоРаздела` | `MainSectionPicture` |
| `Логотип` | `Logo` |
| `Заставка` | `Splash` |
| `Пакет` | `Package` |

Перечень не является общей матрицей возможностей платформы. Допустимость имени
определяется правилами конкретного вида metadata-объекта и версией платформы.

## XML-модель

Платформа определяет пять значений `xr:PropertyState`:

| XML-состояние | Смысл |
|---|---|
| `NotSet` | Режим не задан |
| `Checked` | Значение контролируется |
| `Notify` | Значение проверяется с предупреждением |
| `Extended` | Значение изменяется расширением |
| `MultiState` | Части значения имеют разные режимы |

Соответствие пользовательского режима XML не всегда буквальное:

- обычный сине-красный контроль обычно хранится обычным XML-значением без
  `xr:PropertyState`;
- зелёный режим хранится как `xr:State=Notify`;
- оранжевый режим обычного свойства хранится как `xr:State=Extended`;
- у свойств, допускающих только оранжевый режим, платформа может выводить режим
  из самого присутствия XML-свойства без `xr:PropertyState`;
- разные режимы частей типа хранятся как `xr:State=MultiState` и значение
  `xr:ExtendedProperty` с `xr:CheckValue`, `xr:NotifyValue` и
  `xr:ExtendValue`.

Например, пустая изменяемая основная форма объекта выгружается без
`xr:PropertyState`:

```xml
<DefaultObjectForm/>
```

Зелёный режим свойства выгружается явно:

```xml
<xr:PropertyState>
  <xr:Property>ExtendedConfigurationObject</xr:Property>
  <xr:State>Notify</xr:State>
</xr:PropertyState>
```

Составной тип с контролируемой и изменяемой частями:

```xml
<xr:PropertyState>
  <xr:Property>Type</xr:Property>
  <xr:State>MultiState</xr:State>
</xr:PropertyState>
<Type xsi:type="xr:ExtendedProperty">
  <xr:CheckValue xsi:type="v8:TypeDescription">
    <v8:Type>cfg:CatalogRef.СправочникПолный</v8:Type>
  </xr:CheckValue>
  <xr:ExtendValue xsi:type="v8:TypeDescription">
    <v8:Type>cfg:CatalogRef.СправочникРеквизит</v8:Type>
  </xr:ExtendValue>
</Type>
```

## Предопределённые данные

`Изменять: [Предопределенные]` относится ко всему свойству `Predefined`.
Режимы отдельных заимствованных предопределённых элементов хранятся внутри их
смысловой YAML-структуры и не подменяются этим разделом.

## Импорт XML → YAML

1. Собственное XML-свойство импортируется обычным значением и не получает тег
   режима.
2. Отсутствующее заимствованное XML-свойство не создаёт YAML-поля.
3. Обычное контролируемое XML-значение импортируется без тега.
   Присутствующее свойство не удаляется из YAML при совпадении с расширяемой
   конфигурацией: его наличие обозначает выбранный обычный контроль.
4. `Notify` превращается в `!проверять` на значении.
5. `Extended` многорежимного свойства превращается в `!изменять` на значении,
   включая пустое значение; у свойства только с режимом `Изменять` значение
   записывается без тега.
6. Зелёный режим вынесенного свойства добавляет его имя в раздел `Проверять`.
7. Оранжевый режим вынесенного свойства добавляет его имя в раздел `Изменять`.
8. `MultiState` разбирается в список обычных, `!проверять` и `!изменять`
   частей.
9. Ни один режим не записывается в снимок конфигурации.
10. Импорт не сравнивает значение `!проверять` с расширяемой конфигурацией и
    не выдаёт предупреждение о несовпадении: это задача валидации.
11. Известный режим, недопустимый для свойства по `rules.ts`, останавливает
    импорт с ошибкой и не маскируется служебным `!xml`.
12. Неизвестное значение `PropertyState` является ошибкой импорта. Способ его
    сквозного сохранения пока не определяется.

## Экспорт YAML → XML

1. Обычное значение собственного свойства создаёт XML-свойство без режима
   контроля.
2. Обычное значение контролируемого свойства создаёт контролируемое
   XML-свойство в платформенном представлении этого свойства.
3. `!проверять` создаёт зелёный режим в платформенном XML-представлении.
4. `!изменять` многорежимного свойства и обычное значение свойства только с
   режимом `Изменять` создают оранжевый режим в платформенном XML-представлении.
5. Список частей типа создаёт `xr:ExtendedProperty` и
   `xr:State=MultiState`.
6. Имена из раздела `Проверять` создают зелёный режим вынесенных свойств.
7. Имена из раздела `Изменять` создают оранжевый режим вынесенных свойств.
8. Порядок `xr:PropertyState` определяется порядком XML-свойств в `rules.ts`, а
   не порядком YAML.
9. Уже согласованный предметный `!xml` экспортируется своим зарегистрированным
   правилом и не используется для представления режима свойства.

## Диагностики

- Неизвестный локальный тег является ошибкой YAML.
- Поле, существующее у обычного metadata-объекта, но недоступное у его
  заимствованного представления, является ошибкой валидации YAML.
- Тег режима на собственном свойстве является ошибкой валидации.
- Разделы `Проверять` и `Изменять` у собственного объекта расширения являются
  ошибкой валидации: режимы контроля применимы только к заимствованным
  объектам и их свойствам.
- Режим, недоступный для данного свойства, является ошибкой валидации.
- `!xml` не отключает проверку `PropertyState`; он применяется только к уже
  согласованной предметной форме самого XML-значения.
- Неизвестное значение `PropertyState` является ошибкой импорта; `!xml` для
  такого состояния автоматически не создаётся.
- Если обычное контролируемое свойство без `!проверять` не совпадает со
  значением в расширяемой конфигурации, валидация выдаёт ошибку.
- Если внешний файл с обычным контролем без имени в `Проверять` или `Изменять`
  побайтово не совпадает с файлом расширяемой конфигурации, валидация выдаёт
  ошибку.
- Если значение свойства с `!проверять` не совпадает со значением в
  расширяемой конфигурации, валидация выдаёт предупреждение и завершается
  успешно. При импорте это предупреждение не выдаётся.
- Если `Package.bin` из `Проверять: [Пакет]` побайтово отличается от пакета
  расширяемой конфигурации, валидация выдаёт предупреждение и завершается
  успешно. Отсутствие локального файла или соответствующего базового пакета
  является ошибкой.
- `Изменять: [Пакет]` без локального `Package.bin` является ошибкой.
- Несовпадение контролируемого элемента `Состава` общего реквизита либо его
  параметров `Использование` и `УсловноеРазделение` с расширяемой
  конфигурацией является ошибкой.
- Отсутствие заимствованного объекта или свойства в расширяемой конфигурации
  является ошибкой независимо от режима, в том числе при `!проверять`.
- Неразрешённая ссылка в значении `!изменять` является обычной ошибкой ссылки,
  если цель отсутствует и в расширяемой конфигурации, и в самом расширении.
- Обычное контролируемое значение и значение с `!проверять` не могут ссылаться
  только на собственный объект расширения: цель должна существовать в
  расширяемой конфигурации. Ссылка на собственный объект допустима в
  изменяемом значении.
- Имя в разделе `Проверять`, не зарегистрированное для данного вида
  metadata-объекта как проверяемое вынесенное свойство, является ошибкой.
- Имя в разделе `Изменять`, не зарегистрированное для данного вида
  metadata-объекта, является ошибкой валидации.
- Тег на части значения разрешён только правилам, поддерживающим составное
  представление.
- Одно свойство нельзя одновременно пометить `!изменять` и добавить в раздел
  `Изменять`.
- Режим, который нельзя представить согласованными средствами YAML и
  предметного реестра, является ошибкой импорта; в снимок и `!xml` он не
  записывается.

## Сбор полной матрицы правил

Исследуемая полная матрица относится к платформе 1С 8.3.27. Доступность
объектов, дочерней структуры, свойств и режимов дополнительно ограничивается
полем `РежимСовместимостиРасширенияКонфигурации`. Если поле отсутствует или в
XML имеет значение `Не использовать`, подразумеваются возможности 8.3.27; при
импорте это значение по умолчанию в YAML не записывается.

`РежимСовместимости` основной конфигурации не участвует в выборе этой матрицы.
Он остаётся отдельным контролируемым свойством, но набор возможностей
расширения определяется только режимом совместимости расширения.

Версионность хранится в rules.ts как упорядоченный набор дельт между соседними
режимами совместимости. Базовая матрица описывает самый старый поддерживаемый
режим; каждая следующая дельта добавляет или удаляет разрешённые объекты,
дочерние коллекции, свойства и режимы контроля. Матрица выбранного режима
получается последовательным применением дельт, а не отдельной копией всех
правил для каждой версии.

Обычные свойства наследуют ограничение из подключённого профиля; исключение
задаётся рядом с конкретным свойством или коллекцией дочерних объектов. Эти же
данные используют валидация, схема и автодополнение. `Не использовать`
приравнивается к `Версия8_3_27`.

Порядок режимов задаётся один раз и не выводится из строк лексикографическим
сравнением. В 8.3.27 перечисление проекта содержит `Версия8_1`,
`Версия8_2_13`, `Версия8_2_16`, все значения `Версия8_3_1`—`Версия8_3_27` и
`НеИспользовать`. Свойство режима расширения появилось в платформе 8.3.8, а в
переданных примерах минимально подтверждено значение `Версия8_3_6`.
Допустимость более старых значений именно в этом свойстве требует отдельной
выгрузки из Конфигуратора 8.3.27; наличие значения в общем системном
перечислении само по себе этого не доказывает.

### Подтверждённые исторические границы

Версия выпуска платформы не является входом валидации. Таблица нужна только
для проверки происхождения возможностей; в работе используется значение
`РежимСовместимостиРасширенияКонфигурации`.

Переданный протокол проверки применимости расширения в Конфигураторе 8.3.27
содержит точные сообщения вида «недопустимо в режиме совместимости X и ниже».
Такая формулировка подтверждает дельту непосредственно: возможность появляется
в следующем режиме после X.

| Возможность | Недопустима по X включительно | Доступна начиная с |
|---|---|---|
| Собственные Web-сервисы, HTTP-сервисы, WS-ссылки и пакеты XDTO | `Версия8_3_6` | `Версия8_3_7` |
| Переопределение свойств заимствованных объектов | `Версия8_3_7` | `Версия8_3_8` |
| Собственные общие картинки, общие макеты, общие команды, группы команд и общие формы как дочерние объекты расширения | `Версия8_3_7` | `Версия8_3_8` |
| Собственные общие модули и роли | `Версия8_3_8` | `Версия8_3_9` |
| Собственные каналы заимствованного сервиса интеграции | `Версия8_3_8` | `Версия8_3_9` |
| Собственные справочники, документы и регистры сведений | `Версия8_3_10` | `Версия8_3_11` |
| Собственные перечисления | `Версия8_3_11` | `Версия8_3_12` |
| Собственные планы видов характеристик, планы счетов, планы видов расчёта, регистры накопления, бухгалтерии и расчёта | `Версия8_3_12` | `Версия8_3_13` |
| Собственные параметры сеанса | `Версия8_3_13` | `Версия8_3_14` |
| Переопределение исследованного свойства корня конфигурации | `Версия8_3_13` | `Версия8_3_14` |
| Действие при подключении `Предупреждать` | `Версия8_3_14` | `Версия8_3_15` |
| Собственные константы, функциональные опции, параметры функциональных опций и критерии отбора | `Версия8_3_15` | `Версия8_3_16` |
| Изменение типа заимствованного реквизита | `Версия8_3_17` | `Версия8_3_18` |
| Наборы типов и определяемые типы в расширении | `Версия8_3_19` | `Версия8_3_20` |

Протокол также подтверждает отдельное ограничение `Версия8_3_26` и ниже:
длина номера строки собственных табличных частей расширения должна быть равна
`5`. Начиная с `Версия8_3_27` это ограничение снимается. Правило относится к
валидации структуры табличной части, а не к PropertyState.

Повторная проверка полной исследуемой конфигурации в режимах
`Версия8_3_20`—`Версия8_3_24` дала один и тот же полный список ошибок: только
ограничение длины номера строки для собственных табличных частей. При
`Версия8_3_19` дополнительно запрещены наборы типов и определяемые типы;
после их исключения также остаётся только ограничение длины номера строки.
Следовательно, определяемые типы появляются точно с `Версия8_3_20`, а
присутствующие в фикстуре регламентные задания, источники данных,
бизнес-процессы, задачи, журналы документов и XDTO принимаются уже при
`Версия8_3_19`. Последующие проверки показали, что при `Версия8_3_18`
дополнительно запрещены только наборы типов, а при `Версия8_3_17` и
`Версия8_3_16` — наборы типов и изменение типов заимствованных реквизитов.
После исключения этих возможностей остальной исследованный набор принимается
уже при `Версия8_3_16`. Для установления его точной нижней границы нужна
проверка более старых соседних режимов.

Проверки `Версия8_3_15`—`Версия8_3_12` подтвердили ранее найденные дельты:

- собственные константы, функциональные опции, параметры функциональных
  опций и критерии отбора запрещены по `Версия8_3_15` включительно;
- действие при подключении `Предупреждать` запрещено по `Версия8_3_14`
  включительно;
- собственные параметры сеанса и переопределение исследованного свойства
  корня конфигурации запрещены по `Версия8_3_13` включительно;
- собственные планы видов характеристик, планы счетов, планы видов расчёта,
  регистры накопления, бухгалтерии и расчёта запрещены по `Версия8_3_12`
  включительно.

Ограничения истории данных образуют отдельную матрицу и не определяют
доступность самого metadata-объекта:

| Объекты расширения в истории данных | Недопустимы по режим включительно | Доступны начиная с |
|---|---|---|
| Справочники, документы, бизнес-процессы, задачи и регистры сведений | `Версия8_3_10` | `Версия8_3_11` |
| Планы видов характеристик и планы счетов | `Версия8_3_11` | `Версия8_3_12` |
| Константы, планы обмена и планы видов расчёта | `Версия8_3_12` | `Версия8_3_13` |

Независимо от режима Конфигуратор также запрещает включать в историю данных
ряд объектов и полей, добавленных самим расширением. Это структурная проверка,
а не версионная дельта PropertyState.

Проверки `Версия8_3_11`—`Версия8_3_7` подтвердили следующие границы без новых
промежуточных дельт:

- собственные перечисления появляются с `Версия8_3_12`;
- собственные справочники, документы и регистры сведений — с
  `Версия8_3_11`;
- собственные общие модули и роли — с `Версия8_3_9`;
- переопределение свойств заимствованных объектов и добавление исследованных
  общих дочерних объектов — с `Версия8_3_8`.

Протокол содержит и постоянные ограничения, которые нельзя записывать как
дельты режима совместимости:

- план обмена, добавленный расширением, нельзя использовать в распределённой
  информационной базе;
- метаданные расширения, влияющие на структуру данных, запрещаются, когда
  выбранные назначение расширения и режим работы платформы не допускают таких
  изменений;
- запреты на собственные объекты и поля в истории данных действуют отдельно
  от доступности этих metadata-объектов в расширении.

Номер выпуска платформы нельзя механически использовать как ключ дельты.
Например, в выпуске 8.3.9 только появилось общее значение совместимости
`Версия8_3_8`. Поэтому возможность из статьи попадает в rules.ts только после
одного из двух подтверждений: статья прямо называет старое поведение при
конкретном режиме либо Конфигуратор принимает и выгружает минимальный режим с
этой возможностью.

Пока точная граница не подтверждена, дельта считается исследованной по
содержанию, но не готовой к реализации. Валидация не должна угадывать порог и
разрешать возможность в старом режиме. Режимы, для которых в таблице нет
изменений, также нельзя объявлять пустой дельтой: отсутствие найденного
изменения ещё не доказывает совпадение матриц.

### Представление дельт в rules.ts

Дельта содержит только отличия от предыдущего режима:

| Поле дельты | Содержание |
|---|---|
| `mode` | Режим, начиная с которого действует изменение |
| `allowObjectKinds` | Новые допустимые собственные или заимствованные виды объектов |
| `forbidObjectKinds` | Виды объектов, переставшие быть допустимыми |
| `allowChildren` | Новые допустимые дочерние коллекции у конкретного вида объекта |
| `forbidChildren` | Дочерние коллекции, переставшие быть допустимыми |
| `allowPropertyStates` | Новые свойства или режимы `Проверять` / `Изменять` |
| `forbidPropertyStates` | Удалённые свойства или режимы контроля |
| `xmlPolicies` | Версионные отличия XML-представления, например `AnyRef` / `AnyIBRef` |

Поля с пустым значением не записываются. Для нескольких соседних режимов без
подтверждённых отличий отдельные записи не создаются; они получают результат
последней применённой дельты. При неизвестной границе правило остаётся в списке
исследования и не включается ни в `allow`, ни в `forbid`.

XML-выгрузки достаточно, чтобы установить выбранный режим, но недостаточно,
чтобы узнать все режимы, разрешённые Конфигуратором для свойства. Матрица для
текущего целевого режима уже собрана. При появлении нового вида объекта или
поддержке старого режима совместимости необходимы:

1. Полная панель свойств заимствованного объекта с видимыми значками возле
   каждого свойства.
2. XML-выгрузка этого объекта после сохранения выбранных режимов.
3. Для неоднозначных свойств — отдельные выгрузки после каждого доступного
   состояния: снято, сине-красный, зелёный и оранжевый.
4. Для `Тип` — примеры одиночного и составного типа, включая разные режимы
   подтипов.
5. Номер версии платформы и режим совместимости расширения, на которых получен
   пример.

Базовая конфигурация и выгрузка расширения должны передаваться вместе: по ним
проверяются соответствие объектов, исходное значение свойства и точное XML-
представление результата. Скриншот нужен только для определения разрешённых
вариантов; выбранное состояние и XML-представление извлекаются из выгрузки.

Сначала исследуются общие семейства свойств — идентификация заимствованного
объекта, локальные `Имя` и `Комментарий`, представления, формы, модули,
вынесенное содержимое и `Тип`. После этого для каждого вида metadata-объекта
остаются только его специальные свойства. Так матрица собирается по группам,
без ручного переписывания одинаковых правил для каждого объекта.

## Подтверждённые примеры

Новая выгрузка
`e2e/fixtures/xml/cfe/all-extension/Catalogs/СправочникВладелец.xml`
подтверждает:

- снятый флажок `Объект расширяемой конфигурации` удаляет
  `ExtendedConfigurationObject`;
- зелёный флажок этого свойства и `Тип` создаёт `xr:State=Notify`;
- пустой флажок `Тип` удаляет XML-свойство;
- оранжевый флажок всего `Тип` создаёт `MultiState` только с `ExtendValue`;
- разные значки подтипов создают `CheckValue`, `NotifyValue` и `ExtendValue`.

Новая выгрузка того же справочника подтверждает, что оранжевая пустая
`Основная форма объекта` записывается как `<DefaultObjectForm/>` без
`xr:PropertyState`.

доступны контроль, проверка и изменение.

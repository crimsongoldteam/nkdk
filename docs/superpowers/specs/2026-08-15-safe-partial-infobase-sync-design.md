# Безопасная частичная синхронизация с базой

## Цель

Уточнить поведение `nkdk.sync_to_infobase` по подтверждённой трассировке ЕДТ,
устранить найденные ревью ошибки контрольной копии и проверить изменения на
нескольких показательных операциях без повторного запуска всей матрицы.

## Режим загрузки файлов

NKDK по-прежнему формирует ZIP только из изменённых файлов и передаёт точный
`load.lst`. Ключ `config load-files --partial` имеет отдельный смысл: он
разрешён, только если каждый путь загрузки является модулем `.bsl`. Если среди
целей есть хотя бы один XML-файл, команда остаётся выборочной за счёт
`--list-file`, но выполняется без `--partial`.

Классификация находится в платформенном слое и едина для агентного режима
Конфигуратора и автономного сервера. Пустой список целей не считается
модульной загрузкой. Построитель команды получает уже вычисленное значение и
добавляет `--partial` только для модульного случая.

Успешный ответ `sync_to_infobase` получает обязательное поле
`loadMode: "partial" | "selected"` для состояния `synchronized`. Оно позволяет
сквозному тесту зафиксировать реально выбранный договор, не сохраняя внутренний
журнал успешной платформенной попытки. `unchanged` не содержит это поле.

## Обновление конфигурации базы данных

После каждого успешного `config load-files` оба режима обязательно выполняют:

```text
config update-db-cfg --session-terminate="prompt"
```

Успех доставки подтверждается только после успеха обеих команд. Ошибка или
неизвестный результат обновления базы обрабатывается как ошибка всей доставки;
снимок NKDK при этом не публикуется. Отдельного пользовательского ключа для
отключения обновления нет.

## Ограничение автономного сервера

Автономный режим временно разрешён только для файловых строк подключения
`File=...`. Строка `Srvr=...;Ref=...` отклоняется до запуска `ibcmd`, создания
временных файлов и обращения к СУБД с диагностикой, что клиент-серверная база в
автономном режиме пока не поддерживается. Агентный режим сохраняет поддержку
файловых и клиент-серверных баз.

## Надёжная контрольная копия e2e

Механизм контрольных копий остаётся исключительно разработческой e2e-обвязкой
и не входит в MCP. На диске хранится одна подтверждённая копия `current`; каталог
`previous` существует только во время замены или восстановления после сбоя.

Публикация выполняется как файловая транзакция:

1. `base` и `project` копируются во временный каталог;
2. manifest строится и полностью проверяется;
3. прежний `current` переименовывается в `previous`;
4. временная копия переименовывается в `current`;
5. `state.json` атомарно записывается и служит точкой фиксации;
6. `previous` удаляется как необязательная очистка.

Сбой до записи состояния возвращает прежний `current`. Сбой удаления
`previous` после записи состояния не откатывает уже зафиксированную копию:
лишний каталог удаляется при следующем открытии или восстановлении.

Восстановление сначала ищет целую копию, manifest которой соответствует
`state.json`. Оно допускает отсутствие или повреждение `current`, если имеется
ровно один подходящий `previous`. Замена рабочих `base` и `project` отслеживает
каждое выполненное переименование отдельно и откатывает только фактически
сделанные шаги. Временный `state.json.tmp`, оставшийся после аварии, признаётся
управляемым файлом и удаляется только после проверки основного состояния.

## MCP-договор и документация

Схема успешного ответа снова является строгим объединением двух вариантов:

- `unchanged` требует `diagnostics` и запрещает поля выполненной загрузки;
- `synchronized` требует сведения о пакете, целях, платформенном режиме,
  `loadMode`, публикации снимка и предупреждениях.

README должен прямо говорить, что операция обновляет конфигурацию базы данных,
а автономный режим ограничен файловыми базами. Подтверждение записи должно
называть фактически выбранный `componentPath`, включая расширение.

## Проверки

Модульные тесты покрывают:

- модульный список с `--partial` и структурный либо смешанный список без него;
- обязательный `update-db-cfg` в обоих платформенных режимах;
- ранний отказ автономного режима для клиент-серверной базы;
- строгие варианты MCP-ответа и `loadMode`;
- сбои каждой границы публикации и восстановления контрольной копии;
- открытие каталога после оставшегося `state.json.tmp` и `previous`.

Реальная проверка использует существующую файловую базу сценария и только два
представителя: изменение одного модуля и одно структурное изменение. Каждый
представитель выполняется отдельно в агентном режиме Конфигуратора и через
автономный сервер. Проверяется список файлов ZIP, `loadTargets`, `loadMode`,
повторный ответ `unchanged` и совпадение после обратного импорта. Расширение и
полная матрица объектов повторно не проверяются.

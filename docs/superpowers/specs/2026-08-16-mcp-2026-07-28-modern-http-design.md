# Переход MCP на спецификацию 2026-07-28

## Контекст

`@nkdk/mcp` использует монолитный `@modelcontextprotocol/sdk` v1 и обслуживает
семейство протокола 2025 года через `initialize`/`notifications/initialized`.
Сервер запускается только через stdio. Внутренние smoke- и e2e-клиенты,
тесты и режим `--watch` также зависят от старого начального согласования.

Спецификация MCP `2026-07-28` вводит modern-era: запросы становятся
самодостаточными, `initialize` удаляется, сведения о сервере доступны через
`server/discover`, а версия и возможности клиента передаются в `_meta` каждого
запроса. TypeScript SDK v2 реализует эту эпоху через раздельные пакеты сервера,
клиента и адаптеров транспорта.

Одновременно MCP-договоры NKDK исторически написаны на Zod, хотя основной
стек JSON Schema проекта использует TypeBox. В `projectCache.ts` уже существует
дублирование одной входной схемы в TypeBox и Zod.

## Цель

Перевести `@nkdk/mcp` только на MCP `2026-07-28`, добавить локальный Streamable
HTTP и сделать TypeBox единственным источником входных и выходных схем MCP.

После перехода:

- stdio остаётся транспортом по умолчанию;
- HTTP включается явно и слушает только loopback-интерфейс;
- сервер и внутренние клиенты принимают только `2026-07-28`;
- все tools, resources и prompts регистрируются одной фабрикой;
- прикладные договоры и поведение существующих инструментов не меняются;
- `@nkdk/mcp` не импортирует SDK v1 и Zod.

## Не входит в границы

- поддержка протокольных версий `2025-*`;
- удалённое размещение HTTP-сервера;
- OAuth, токены, пользовательская авторизация и TLS;
- HTTP reverse proxy, балансировка и доверие к forwarded-заголовкам;
- Tasks, MCP Apps, MRTR и новые серверные запросы к клиенту;
- пользовательские cache hints и `x-mcp-header` для аргументов инструментов;
- перевод `@nkdk/platform` с Zod на TypeBox;
- изменение прикладных служб metadata и platform;
- изменение `.agents/architecture.md`.

## Совместимость

Это намеренное несовместимое изменение. Клиент обязан поддерживать modern-era
и `server/discover`. Старый клиент, начинающий соединение с `initialize`,
получает ошибку несовместимой версии; сервер не выполняет скрытый fallback.

Команда существующей stdio-конфигурации не меняется: запуск `nkdk-mcp` без
параметров по-прежнему открывает MCP поверх stdin/stdout. Меняется только
требуемая версия протокола клиента.

## Зависимости

Монолитный `@modelcontextprotocol/sdk` удаляется. Пакет использует:

- `@modelcontextprotocol/server` как runtime-зависимость сервера;
- `@modelcontextprotocol/node` как runtime-адаптер локального HTTP;
- `@modelcontextprotocol/client` как devDependency для smoke, e2e и protocol
  integration-тестов;
- `typebox` как единственную библиотеку прикладных MCP-схем.

`@modelcontextprotocol/client` не попадает в установленный runtime: клиентские
скрипты не входят в публикуемые `files`. Packed smoke подтверждает, что tarball
выполняется без клиентского пакета.

## Архитектура сервера

### Единая фабрика

`createNkdkMcpServer()` остаётся единственной фабрикой прикладного MCP-сервера.
Она создаёт новый `McpServer`, регистрирует полный набор tools, resources и
prompts и не выбирает транспорт.

Модуль регистрации принимает минимальный интерфейс с `registerTool`,
`registerResource` и `registerPrompt`, поэтому unit-тесты набора возможностей
не зависят от транспорта.

### stdio

Обычный запуск использует modern-aware entrypoint `serveStdio(factory)`, а не
прямое соединение `McpServer` с `StdioServerTransport`. Legacy-режим явно
отклоняется настройкой SDK.

Первым согласующим запросом является `server/discover`. После него SDK
закрепляет соединение за `2026-07-28`. Все дальнейшие запросы несут сведения о
версии и клиенте в modern `_meta` envelope.

### Streamable HTTP

HTTP включается параметром `--http`. Сервер:

- привязывается только к `127.0.0.1`;
- по умолчанию использует порт `3000`;
- принимает MCP только на `POST /mcp`;
- использует `createMcpHandler(factory)` в modern-only режиме;
- преобразует Web Standard handler в Node.js HTTP через
  `@modelcontextprotocol/node`;
- возвращает `404` для остальных путей;
- не включает CORS и не доверяет forwarded-заголовкам.

Каждый HTTP-запрос получает отдельный экземпляр `McpServer`, как требует
stateless-модель протокола. Это не делает прикладное состояние NKDK
одноразовым: metadata runtime, проектный кеш и менеджер соединений платформы
остаются process-level handles.

Инструменты адресуют проект через явный `projectDir`, поэтому состояние не
зависит от скрытого MCP session id. Существующие инструменты закрытия соединений
с платформой сохраняются.

## Командная строка

Поддерживаются режимы:

```text
nkdk-mcp
nkdk-mcp --watch
nkdk-mcp --http
nkdk-mcp --http --port 3000
```

Правила разбора:

- без параметров запускается stdio;
- `--watch` применим только к stdio;
- `--http` включает локальный HTTP;
- `--port` принимает целое число от 1 до 65535 и допустим только с `--http`;
- неизвестный параметр, повтор параметра, отсутствующее значение порта,
  некорректный порт и `--http --watch` завершают процесс с кодом `2`;
- ошибка транспорта или занятый порт завершают процесс с кодом `1`.

При успешном старте HTTP фактический адрес печатается в stderr. stdout не
используется для служебных сообщений, чтобы stdio-режим всегда сохранял чистый
протокольный канал.

## TypeBox-договоры

### Единственный источник схемы

Каждый входной и выходной договор объявляется TypeBox-схемой. TypeScript-типы
выводятся через `Type.Static`; ручные дубли типов допускаются только для
внешнего типа, который явно проверяется на совместимость compile-time тестом.

Строгость текущих договоров сохраняется:

- бывший `z.strictObject` становится `Type.Object` с
  `additionalProperties: false`;
- бывший `z.looseObject` явно разрешает дополнительные свойства;
- дискриминированные варианты выражаются через `Type.Union` объектов с
  литеральным дискриминатором;
- рекурсивные значения используют рекурсивную схему TypeBox;
- ограничения строк, чисел, enum и optional переносятся без ослабления.

### Граница SDK

TypeBox 1.3 создаёт JSON Schema, но не реализует Standard Schema напрямую.
Один именованный адаптер на границе MCP оборачивает TypeBox-схему через
публичный `fromJsonSchema()` SDK v2. Если для сохранения статического типа
нужно приведение, оно находится только внутри этого адаптера и покрывается
тестами регистрации и фактической валидации.

Прикладные службы получают уже проверенные входные данные. Для прямой проверки
договоров используются `Value.Check` или `Value.Parse`, а не вторая схема.

### Выход инструментов

Успешный и ошибочный payload описываются одной TypeBox-схемой с реальными
вариантами результата. Обходной Zod-построитель `publishedToolOutputSchema`,
который был нужен для ограничений SDK v1 и legacy structured content,
удаляется.

Сервер продолжает возвращать обязательный `content` и типизированный
`structuredContent`. Текущие правила `isError` сохраняются: прикладная ошибка
является ошибкой MCP, кроме диагностического результата, который специально
остаётся обычным результатом.

## Поток запроса

### stdio

1. Клиент SDK v2 вызывает `server/discover` и требует `2026-07-28`.
2. `serveStdio` создаёт сервер через общую фабрику и закрепляет modern-era.
3. SDK проверяет `_meta`, имя метода и аргументы инструмента.
4. TypeBox-адаптер проверяет входной payload.
5. Обработчик вызывает существующую прикладную службу.
6. Результат формируется как `content` и `structuredContent` и проверяется
   выходной схемой.

### HTTP

1. Node.js HTTP принимает запрос только на loopback-интерфейсе.
2. Защитные адаптеры проверяют `Host`, `Origin`, `Content-Type` и MCP-заголовки.
3. `createMcpHandler` проверяет modern envelope и создаёт MCP-сервер для
   запроса.
4. Дальнейший путь совпадает со stdio, начиная с проверки входного payload.
5. Закрытие клиентом response stream отменяет операцию через
   `ctx.mcpReq.signal`.

Обработчики импорта, синхронизации и чтения расширений получают
`ctx.mcpReq.signal` вместо старого плоского `extra.signal` и передают тот же
`AbortSignal` существующим службам.

## Локальная безопасность HTTP

Отсутствие авторизации допустимо только потому, что процесс слушает
`127.0.0.1`. Защита состоит из нескольких независимых условий:

- адрес bind нельзя переопределить аргументом командной строки или окружением;
- проверка `Host` допускает только локальный адрес с фактическим портом;
- присутствующий `Origin` допускается только для локального источника;
- отсутствие `Origin` разрешено для CLI и desktop-клиентов;
- `Content-Type` обязан быть `application/json`;
- modern-заголовки `MCP-Protocol-Version`, `Mcp-Method` и `Mcp-Name`
  проверяются SDK на соответствие телу;
- сервер не публикует Access-Control-Allow-Origin для произвольных сайтов;
- README прямо запрещает выставлять этот endpoint во внешнюю сеть или через
  reverse proxy без отдельного проекта авторизации.

## Кеширование протокольных ответов

SDK modern-era обязан добавлять `ttlMs` и `cacheScope` к кешируемым результатам.
В первой версии используются безопасные значения SDK по умолчанию:
`ttlMs: 0` и `cacheScope: private`.

Собственная политика кеширования не вводится. Прикладной проектный кеш NKDK не
связан с cache hints протокола и продолжает работать как раньше.

## Watch-режим

`--watch` остаётся stdio-only режимом разработки. Watch-host больше не хранит
и не повторяет `initialize`/`notifications/initialized`.

Он сохраняет первый успешный `server/discover`. После обновления собранной
точки входа host:

1. завершает прежний worker;
2. запускает новый worker;
3. повторяет `server/discover` с внутренним id;
4. не пересылает служебный ответ наружу;
5. после успешного ответа передаёт накопившиеся запросы новому worker.

Запросы, пришедшие во время переключения, сохраняют порядок. Ошибка запуска или
discover нового worker закрывает соединение с явной ошибкой вместо отправки
запросов в неинициализированный процесс.

## Ошибки

- неподдерживаемая версия возвращает протокольную ошибку несовместимости без
  fallback;
- ошибки заголовков, пути, метода и content type формируются транспортным
  слоем SDK;
- ошибки входных данных формируются стандартной MCP-валидацией;
- ожидаемые прикладные ошибки сохраняют текущий безопасный `structuredContent`;
- неожиданные ошибки не публикуют пароли, команды платформы, stdout или stderr;
- путь временной выгрузки возвращается только там, где это уже предусмотрено
  текущим безопасным договором.

## Завершение процесса

`SIGINT`, `SIGTERM`, закрытие stdio и остановка HTTP используют единый
идемпотентный shutdown coordinator:

1. прекращается приём новых запросов;
2. закрывается активный транспорт или HTTP listener;
3. metadata runtime и менеджер платформенных соединений закрываются через
   `Promise.allSettled`;
4. первая ошибка завершения возвращается вызывающему коду после попытки
   закрыть все независимые ветви.

Принятые HTTP-запросы при shutdown отменяются сигналом транспорта; отдельного
неограниченного ожидания для них нет. Существующая платформа завершает
запущенный NKDK процесс 1С через `SIGTERM`, а после штатного пятисекундного
периода — через `SIGKILL`, если процесс не остановился.

## Тестирование

### Unit

- разбор всех допустимых и ошибочных сочетаний CLI;
- регистрация полного набора tools, resources и prompts;
- TypeBox-схемы принимают текущие валидные payload и отклоняют текущие
  невалидные payload;
- адаптер TypeBox → Standard Schema сохраняет проверку и JSON Schema;
- обработчики передают `ctx.mcpReq.signal` прикладным службам;
- watch-host повторяет только `server/discover`, сохраняет порядок очереди и
  обрабатывает сбой нового worker;
- shutdown остаётся идемпотентным и пытается закрыть все ветви.

### Protocol integration

`InMemoryTransport` SDK v2 проверяет только legacy-era и поэтому не используется
как доказательство поддержки `2026-07-28`.

- stdio modern проверяется клиентом SDK v2 с
  `versionNegotiation: { mode: { pin: "2026-07-28" } }` и дочерним процессом
  `serveStdio`;
- отдельный stdio-тест отправляет legacy `initialize` и проверяет отказ;
- HTTP modern проверяется `StreamableHTTPClientTransport` через fetch-функцию
  `createMcpHandler`, без реального сокета;
- HTTP-защита проверяется запросами с неверными `Host`, `Origin`,
  `Content-Type`, версией и MCP-заголовками;
- проверяются `server/discover`, `tools/list`, один read-only tool, один
  инструмент подтверждения записи, resource и prompt.

### Packed smoke

Установленный tarball проверяется отдельно от workspace:

- modern stdio перечисляет инструменты и вызывает `nkdk.get_schema`;
- локальный HTTP-процесс запускается на свободном порту, отвечает на `/mcp` и
  выполняет тот же минимальный modern-сценарий;
- tarball не полагается на workspace-пакеты во время выполнения;
- runtime не содержит `@modelcontextprotocol/sdk`, Zod и исходные пути
  workspace.

### Полная проверка

Перед завершением реализации выполняются:

```text
pnpm --filter @nkdk/mcp test
pnpm --filter @nkdk/mcp type-check
pnpm --filter @nkdk/mcp build
pnpm --filter @nkdk/mcp smoke:packed
pnpm duplicates -- --base <commit>
pnpm test
pnpm test:architecture:rules
pnpm test:architecture
```

XML-фикстуры не изменяются.

## Документация

README описывает:

- обязательную поддержку клиентом MCP `2026-07-28`;
- неизменившийся stdio-запуск;
- локальный запуск `nkdk-mcp --http --port 3000`;
- endpoint `http://127.0.0.1:3000/mcp`;
- отсутствие legacy fallback;
- ограничение HTTP только локальной машиной;
- запрет внешней публикации без отдельной авторизации и TLS.

Раздел совместимости README явно называет изменение несовместимым.

## Критерии готовности

Переход завершён, когда одновременно выполнены условия:

1. Сервер обслуживает только MCP `2026-07-28` по stdio и локальному HTTP.
2. `initialize` не используется production-кодом, watch-host и внутренними
   клиентами; он встречается только в отрицательных тестах.
3. В `@nkdk/mcp`, его скриптах и `.agents/tools/mcp` нет импортов
   `@modelcontextprotocol/sdk`.
4. В `@nkdk/mcp` нет импортов Zod и прямой зависимости от него.
5. Все MCP-договоры имеют единственный TypeBox-источник.
6. HTTP нельзя привязать к нелокальному интерфейсу.
7. Старые stdio-конфигурации сохраняют команду запуска, но legacy-клиенты
   получают явный отказ.
8. Исходный и упакованный сервер проходят modern stdio и HTTP smoke.
9. Полный набор тестов, архитектурные проверки и поиск дубликатов проходят.

# Диагностика рассинхронизации заимствованных форм

## Контекст

После унификации построения ProjectState XML-import основной конфигурации и
расширения сохраняет структурные документы форм без промежуточного rebuild.
Благодаря этому межфайловая validation начала видеть расхождения между:

- текущей формой основной конфигурации `cf`;
- рабочей формой расширения `cfe`;
- сохранённой основой заимствованной формы в `cfe`.

На `/Users/nikita/git/sed_xml` validation выдаёт 261 диагностику уровня `error`:

- 192 элемента текущей формы `cf` отсутствуют в рабочей форме расширения;
- 69 элементов сохранённой основы отсутствуют в текущей форме `cf`.

Проверка исходного XML подтвердила 259 расхождений. Два сообщения — для
`ПодобратьТовары` и `ТоварыДобавить` — ложные: элементы присутствуют в текущей
форме `cf` внутри вложенной командной панели, но структурный индекс их не
собирает.

Импорт при этом записывает все XML-файлы и YAML-файлы. Расхождения не означают,
что исходные данные повреждены или результат невозможно обработать.

## Решение

### Уровни диагностики

Отсутствие компонента при сравнении текущей формы `cf`, рабочей формы `cfe` и
сохранённой основы считать рассинхронизацией и выдавать как `warning`. Это
относится ко всем сообщениям, построенным сравнением наборов компонентов:

- компонент текущей основной формы отсутствует в рабочей форме расширения;
- компонент сохранённой основы отсутствует в рабочей форме расширения;
- элемент сохранённой основы отсутствует в текущей форме `cf`.

Диагностики, указывающие на противоречие внутри обрабатываемой структуры,
остаются `error`:

- пустой `ПутьКДанным` заимствованного элемента;
- избыточный явно заданный вычисляемый `ПутьКДанным` собственного элемента;
- необъявленный корень `ПутьКДанным` сохранённой основы;
- синтаксические, схемные и технические ошибки построения индекса.

XML-import считается успешным при наличии только предупреждений. Validation
возвращает их в общей коллекции diagnostics, но они не увеличивают счётчик
ошибок.

### Единый обход элементов формы

`formComponentIndex` не должен самостоятельно обходить только поле `Элементы`.
Для сбора элементов он использует существующий обход YAML по `rules.ts`, который
уже проходит вложенные коллекции формы, включая командные панели и контекстные
меню.

Общий обход остаётся единственным источником сведений о расположении элементов.
Индекс компонентов добавляет поверх него только собственный договор:

- сохраняет имя и полный YAML-путь каждого элемента;
- отклоняет повтор имени элемента;
- отдельно индексирует реквизиты, команды и параметры формы.

Проекция структуры ProjectState, проверка совместимости основы, XML-import и
validation продолжают использовать один `formComponentIndex`. Частные обходы
для импорта или для двух обнаруженных имён не добавляются.

## Вывод большого числа диагностик

Действующий механизм MCP сохраняется без изменений. В ответе показывается не
более 100 diagnostics и не более 512 КБ. Если превышен любой предел, полный
список ошибок и предупреждений записывается в
`.nkdk/reports/<операция>-<id>.jsonl`, а ответ содержит ссылку на отчёт.

Перевод рассинхронизации в `warning` не меняет порог, формат и очистку отчётов.

## Тесты

1. `formComponentIndex` собирает кнопки из вложенной командной панели и
   контекстного меню с полным YAML-путём.
2. Повтор имени элемента, найденный в разных вложенных коллекциях, остаётся
   структурной ошибкой.
3. Сравнение наборов компонентов заимствованной формы возвращает `warning` для
   каждого вида рассинхронизации.
4. Ошибки `ПутьКДанным` сохраняют уровень `error`.
5. Интеграционный XML-import `cf` и `cfe` без rebuild на минимальной фикстуре с
   вложенной командной панелью не выдаёт ложных сообщений для её кнопок.
6. Импорт и последующая validation возвращают одинаковые предупреждения,
   построенные из одного ProjectState.
7. При количестве diagnostics больше 100 MCP оставляет краткий ответ и
   записывает полный JSONL-отчёт, включая предупреждения.

Дополнительно production-путём повторяется импорт
`/Users/nikita/git/sed_xml`: ожидаются 0 ошибок и отсутствие ложных сообщений
для `ПодобратьТовары` и `ТоварыДобавить`. Число предупреждений заранее не
фиксируется: полный обход может обнаружить дополнительные реальные
расхождения во вложенных коллекциях; полученный набор нужно сохранить и
классифицировать во время проверки реализации.

## Вне границ

- автоматическое обновление заимствованных форм исходного расширения;
- подавление или скрытие предупреждений пользователем;
- новый строгий режим, повышающий рассинхронизацию до `error`;
- изменение формата ProjectState и diagnostic report;
- частные правила для конкретных форм, имён элементов или каталогов.

# YAML-представление metadataTarget

## Статус

Черновик для ревью.

## Проблема

После импорта `/home/nikita/git/round-trip/erp` в YAML валидация показывает большую группу ошибок, где свойство является ссылкой на метаданные, но значение записано в модельной/платформенной форме.

Главный пример — ссылки на локальные формы:

```yaml
ОсновнаяФормаОбъекта: Document.АвансовыйОтчет.Form.ФормаДокумента
```

Схема для `metadataTarget: { kind: "localChild", owner: "this", childKind: "Form" }` уже ожидает только локальное имя дочернего объекта:

```yaml
ОсновнаяФормаОбъекта: ФормаДокумента
```

Это не частная проблема форм. Такой же архитектурный случай появляется везде, где часть пути можно однозначно восстановить из контекста или ограничения цели:

- `Role.Администратор` можно записать как `Администратор`, если свойство допускает только роли.
- `DocumentNumerator.ДенежныеДокументы` нужно записывать через YAML-корень: `НумераторДокументов.ДенежныеДокументы`.
- `Document.АвансовыйОтчет.Form.ФормаДокумента` можно записать как `ФормаДокумента`, потому что текущий владелец и вид дочернего объекта уже известны.

Сейчас эти правила разнесены по разным местам: сокращение ролей сделано отдельно в `metadataRef`, отображение корней живет в `metadataTargets`, а `localChild` описан в типах и JSON Schema, но не реализован в parse/format. Кроме того, обычные свойства `type: "string"` с `metadataTarget` не вызывают metadataTarget-форматтер и разборщик YAML, поэтому поля форм не смогут заработать даже после реализации `localChild` внутри `metadataTargets`.

## Цели

- Хранить в модели каноническое значение: строки модели продолжают использовать платформенные пути вроде `Role.X`, `Document.X.Form.Y`, `DocumentNumerator.X`.
- Сокращать YAML-представление только тогда, когда пропущенную часть можно доказуемо восстановить.
- Описывать поведение через существующий контракт `metadataTarget`, а не через новые точечные fromYAML/toYAML-правила в applied objects.
- Согласовать JSON Schema, YAML export, YAML import и validate на одной форме записи.
- Закрыть текущие поля `localChild` для форм/макетов и обычные строковые metadata-ссылки с переводом корней, например `DocumentNumerator.X` -> `НумераторДокументов.X`.

## Не цели

- Не менять XML import/export и XML-фикстуры.
- Не чинить в этой задаче другие группы валидации: `DataPath` с `~...`, колонки динамического списка, неизвестные импортированные сегменты объектов.
- Не переписывать graph import. Это задача про YAML-сериализацию и валидацию скалярных metadata-ссылок.
- Не добавлять индивидуальные fromYAML/toYAML-правила в applied objects, если поведение можно выразить через `metadataTarget`.

## Основное решение

Добавить явный слой YAML-представления для metadata targets:

```ts
type MetadataTargetYAMLPresentation =
  | "full"
  | "singleRoot"
  | "relativeToOwner"
  | "localChild"
```

Представление — это политика записи и чтения, а не ограничение цели. `metadataTarget.kind`, `roots`, `owner`, `childKind` и похожие поля по-прежнему отвечают за допустимые значения. Представление отвечает только за то, какую часть канонического модельного пути писать в YAML.

Умолчания должны быть консервативными:

- `localChild` по умолчанию использует `localChild`.
- `object`/`field`/`value` с единственным разрешенным корнем могут использовать `singleRoot` только когда схема и текущий YAML-контракт явно допускают пропуск корня. В первой реализации это лучше сделать явным включением, кроме уже существующих договоренностей.
- остальные цели по умолчанию используют `full`.

Так первая доработка остается узкой: `localChild` и перевод корней для строковых metadata-ссылок исправляются сразу, а роли и прочие single-root сокращения можно перенести постепенно, без внезапного изменения большого числа YAML-значений.

## Правила путей

Форматтер идет от канонического значения модели к YAML:

- `full`: перевести корни и сегменты в YAML-имена, сохранить полный путь.
- `singleRoot`: если канонический корень является единственным разрешенным корнем, убрать корень; иначе оставить `full`.
- `relativeToOwner`: если канонический путь начинается с пути текущего владельца, убрать префикс владельца.
- `localChild`: если канонический путь имеет вид `<owner>.<childKind>.<name>`, записать только `<name>`.

Разборщик выполняет обратную операцию:

- `full`: разобрать YAML-корни и сегменты в канонические модельные имена.
- `singleRoot`: если в YAML нет корня и разрешен ровно один корень, добавить этот модельный корень.
- `relativeToOwner`: если значение относительное и есть контекст владельца, добавить путь владельца.
- `localChild`: если значение является локальным именем, восстановить `<owner>.<childKind>.<name>`.

Для формы:

```text
Document.АвансовыйОтчет.Form.ФормаДокумента
-> Form.ФормаДокумента
-> ФормаДокумента
```

Первый шаг — `relativeToOwner`, второй — отсечение известного вида дочернего объекта. В реализации это может быть одна политика `localChild`, потому что `owner` и `childKind` уже известны из ограничения.

## Контекст владельца

Слою представления нужен контекст владельца. Сейчас YAML-оркестратор уже передает `name` в `exportPropertiesToYAML` / `importPropertiesFromYAML`, и в `ConfigurationContext.exportToYAML.parent?.name` есть имя родителя, но для `localChild` нужен канонический путь владельца, а не только локальное имя.

На границе applied-object экспорта/импорта `Свойства.yaml` нужно добавить небольшой вычислитель owner path. Он должен передавать в YAML-контекст канонический путь:

```text
Document.АвансовыйОтчет
```

Для orchestration это должно остаться универсальным контрактом: applied-object слой знает item rule и может вывести корень из зарегистрированных метаданных объекта, а общий property/metadataTarget код получает только готовую строку `ownerPath`.

## Форма реализации

1. Расширить вход parse/format metadataTarget необязательным YAML-контекстом:

```ts
interface MetadataTargetYAMLContext {
  ownerPath?: string
}
```

2. Реализовать `localChild` в `parseMetadataTargetFromYAML` и `parseMetadataTargetFromModel`.

3. Добавить общий property-level hook для скалярных строковых свойств с `metadataTarget`:

- export: перед записью обычной строки в YAML вызвать `formatMetadataTargetToYAML`;
- import: перед записью обычной строки в модель вызвать `parseMetadataTargetFromYAML`;
- пустые строки и `undefined` оставить под текущими правилами default-значений.

4. Сохранить существующие специализированные обработчики для `MetadataItemLink`, `MetadataField`, `MetadataValue`, `StyleItem`, `CommonPicture` и похожих типов, но постепенно переводить их metadataTarget-поведение на общий слой там, где это безопасно.

5. JSON Schema должна использовать ту же политику представления:

- `localChild` остается `^METADATA_NAME_PATTERN$`;
- `full` сохраняет текущие шаблоны с YAML-корнями;
- `singleRoot` не включается по умолчанию, пока для него не описан явный шаблон.

## Ошибки

- Если представлению нужен `ownerPath`, но его нет, import/export должен падать с понятной ошибкой настройки, где названы вид ограничения и YAML-свойство.
- Если каноническое значение модели не совпадает с ожидаемым владельцем или `childKind` для `localChild`, export должен падать, а не записывать вводящий в заблуждение полный путь.
- Если YAML для `localChild` содержит значение с точками, разборщик может принять полную каноническую форму как совместимость, но export всегда должен нормализовать значение до короткого локального имени.
- Ошибки validate должны по возможности продолжать указывать на YAML-свойство и использовать формулировки схемы.

## Тестирование

Нужны тесты в трех слоях:

- `metadataTargets`: parse/format для `localChild`, включая короткое YAML-значение, полную совместимую форму, неправильного владельца, неправильный child kind и отсутствие owner context.
- property orchestration: `type: "string"` с `metadataTarget` проходит через metadataTarget formatter/parser.
- applied object sample: свойство документа/отчета/справочника с `ОсновнаяФорма...` экспортируется в короткий YAML и импортируется обратно в канонический путь модели.

Регрессионная проверка:

```bash
pnpm test
packages/cli/bin/nkdk import /home/nikita/git/round-trip/erp /home/nikita/git/temp-yaml
packages/cli/bin/nkdk validate /home/nikita/git/temp-yaml
```

Первый ожидаемый эффект — исчезновение local form/template части ошибок `строка не соответствует шаблону имени`.

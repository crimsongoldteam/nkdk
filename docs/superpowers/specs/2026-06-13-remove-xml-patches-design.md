# Удаление XML-патчей

## Контекст

В проекте есть два патча зависимостей:

- `patches/fast-xml-builder@1.0.0.patch`;
- `patches/fast-xml-parser@5.3.3.patch`.

Оба патча меняют одно поведение XML builder: массив `ChildItems` должен печататься внутри одного тега `<ChildItems>...</ChildItems>`, даже когда общая опция `oneListGroup` выключена. При этом текущая зависимость проекта — `fast-xml-parser@5.4.2`; патч `fast-xml-parser@5.3.3` уже не соответствует основной версии, а реально применяемое поведение держится через патч вложенного `fast-xml-builder@1.0.0`.

Цель — убрать каталог `patches` и зависимость от patch-механизмов, не изменив XML, который генерирует проект.

## Подход

Особое поведение `ChildItems` переносится в наш слой XML-экспорта: `packages/core/xml/export/exporter.ts`.

`xmlExport` должен перед вызовом `XMLBuilder` преобразовывать объект так, чтобы массивы под ключом `ChildItems` сериализовались как единая группа. Это правило должно быть локальным для XML-экспортёра: metadata-правила продолжают возвращать привычную модель `ChildItems: [{ InputField: ... }, ...]`, а знание о формате вывода остаётся рядом с остальными настройками XML-сериализации.

Уже существующий preserve-order путь с `xmlOrderedChildren` остаётся отдельным механизмом. Новое правило не должно ломать preserve-order экспорт: если данные требуют preserve-order, используется текущая ветка `preserveOrderBuilder`; если нет — применяется обычный builder с предварительной нормализацией `ChildItems`.

## Изменения

1. Добавить в `packages/core/xml/export/exporter.ts` небольшой преобразователь данных для обычной ветки экспорта.
2. Преобразователь рекурсивно обходит записи и массивы.
3. Если ключ равен `ChildItems`, массив остаётся значением одного XML-узла, а его элементы становятся дочерними тегами этого узла.
4. Удалить устаревший комментарий про патчи в `exporter.ts`.
5. Удалить `patches/fast-xml-builder@1.0.0.patch` и `patches/fast-xml-parser@5.3.3.patch`.
6. Удалить `patch-package` и `postinstall` из корневого `package.json`.
7. Удалить `patchedDependencies` из `package.json`, `pnpm-workspace.yaml` и `pnpm-lock.yaml`.

## Проверка

Нужно добавить focused-тест для `xmlExport`, который фиксирует ключевой случай:

```ts
xmlExport({ ChildItems: [{ InputField: { _name: "A" } }, { LabelField: { _name: "B" } }] }, false)
```

Ожидаемый результат должен содержать один внешний `<ChildItems>` с двумя дочерними элементами, а не два соседних `<ChildItems>`.

После реализации нужно запустить:

```bash
pnpm --filter @nakidka/core test -- xml/export
pnpm test
```

## Ошибки и ограничения

Если преобразователь встретит `ChildItems` не как массив, он не должен менять значение: это сохранит совместимость с уже подготовленными XML-объектами и пограничными случаями импорта/экспорта.

Если после удаления патчей focused-тесты форм начнут расходиться по XML, реализация считается неполной: нужно расширить преобразователь в XML-слое, а не возвращать патчи.

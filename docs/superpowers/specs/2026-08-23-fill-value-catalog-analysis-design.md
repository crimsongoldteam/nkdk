# Исследование значений заполнения по XML-каталогу

## Цель

Создать воспроизводимое исследование XML-выгрузок конфигураций, которое
показывает, какая XML-форма `FillValue` встречается у реквизитов каждого типа.
Результат служит источником фактов для уточнения импорта, проверки и
канонического восстановления `FillValue`, но сам не меняет правила metadata.

Исследование оформляется как проектный навык с проверяемым скриптом. Навык и
формат отчёта рассчитаны на последовательное расширение по мере появления
новых XML-конструкций и уточнения договоров.

## Границы первой версии

Первая версия:

- рекурсивно исследует все XML-файлы во всех непосредственных подкаталогах
  заданного каталога конфигураций;
- различает обычные и стандартные реквизиты;
- учитывает как присутствующий, так и отсутствующий `FillValue`;
- сохраняет факты XML отдельно от определения типа по текущим `rules.ts`;
- создаёт подробный агрегированный JSON и сводный Markdown;
- явно сообщает о неразобранных конструкциях и неразрешённых типах.

В первую версию не входят изменение `rules.ts`, выбор нового канонического
значения, импорт XML в YAML, запись в LMDB и проверка round-trip. XML-каталог
только читается.

## Архитектура

### Прямое исследование XML

Анализатор находится в `packages/rules/scripts`, читает XML напрямую через
существующий `parseXmlWithSaxes` из `@nkdk/runtime` и не запускает полный
импорт. Парсер уже используется основной архитектурой импорта и умеет
сохранять точный текст, пустые элементы и `xsi:nil`. Файлы обрабатываются
независимо с ограниченной параллельностью, поэтому в памяти одновременно
находится только ограниченное число документов.

Навык содержит тонкий `.mjs`-запускатель. Он передаёт аргументы анализатору
через `pnpm --filter @nkdk/rules exec tsx`, не дублируя разбор XML и правила
обогащения. Такое разделение оставляет исследовательский интерфейс рядом с
навыком, а зависимости и доступ к runtime-композиции — в пакете-владельце.

Прямой разбор выбран вместо анализа импортированной модели: модель уже может
удалить неявный `FillValue` или заменить исходную XML-форму смысловым
значением. Новый XML-парсер и регулярные выражения не создаются: первый
дублировал бы runtime, вторые не дают надёжно учитывать пространства имён,
атрибуты и отсутствующие элементы.

Сбор наблюдений и обогащение типами являются отдельными стадиями:

1. XML-сканер извлекает наблюдение без предположений о правильности правил.
2. Обогатитель пытается определить эффективный тип по данным XML.
3. Для стандартного реквизита обогатитель отдельно запрашивает действующую
   композицию `rules.ts` и помечает этот результат источником `rules`.
4. Построитель отчёта группирует наблюдения, не смешивая факты XML с выводами
   действующей реализации.

### Поиск реквизитов

Обычным считается поддержанный metadata-узел реквизита, у которого описание
типа находится в дочернем элементе `Type`, а значение заполнения — в
`FillValue`. Тип разбирается из XML самого реквизита и получает источник
`xml`.

Стандартным считается `xr:StandardAttribute`. Его внутреннее имя читается из
атрибута `name`, а владелец определяется по окружающему metadata-объекту и
пути файла. Если тип не указан непосредственно в XML, он разрешается через
декларацию стандартного реквизита в действующей композиции и получает источник
`rules`.

Конструкция, похожая на реквизит, но не соответствующая поддержанным формам,
записывается в `unresolved`; она не должна исчезать из отчёта молча.

### Сигнатура типа

Для обычного реквизита JSON хранит два представления типа:

- исходные XML-данные, достаточные для проверки результата;
- нормализованную сигнатуру: набор альтернатив типов и влияющие на значение
  заполнения квалификаторы строки, числа и даты.

Порядок альтернатив не влияет на нормализованную сигнатуру. Исходный порядок
сохраняется отдельно. Ссылка на конкретный metadata-объект остаётся частью
сигнатуры и не объединяется с произвольной ссылкой.

Для стандартного реквизита дополнительно сохраняются вид владельца, внутреннее
имя реквизита, декларация политики `FillValue` и свойства владельца, от которых
зависит тип. Благодаря этому вывод из `rules.ts` можно проверить независимо от
наблюдаемой XML-формы.

## Модель наблюдения и агрегации

XML-сканер сначала создаёт внутреннее наблюдение для каждого реквизита. Перед
записью JSON одинаковые наблюдения объединяются по уникальному сочетанию типа,
смысловой категории и точного значения. Поэтому повторяющиеся случаи не
раздувают файл, но ни один вариант значения не теряется.

Агрегированная запись содержит следующие основные поля:

| Поле | Смысл |
|---|---|
| `configuration` | Имя подкаталога конфигурации |
| `file` | Относительный путь XML-файла |
| `ownerKind` | Вид metadata-владельца либо `unresolved` |
| `attributeKind` | `ordinary` или `standard` |
| `attributeNames` | Имена реквизитов, объединённых записью |
| `typeSource` | `xml`, `rules` или `unresolved` |
| `sourceType` | Разобранное исходное описание типа |
| `effectiveType` | Нормализованная сигнатура либо причина неопределённости |
| `fillValueForm` | Наблюдаемая XML-форма |
| `xsiType` | Точное значение `xsi:type`, если оно есть |
| `text` | Точный текст элемента, если он есть |
| `valueCategory` | Смысловая категория значения |
| `occurrences` | Число одинаковых наблюдений |
| `configurations` | Конфигурации, где найден вариант |
| `examples` | Ограниченный список относительных путей-примеров |

`fillValueForm` принимает закрытый набор значений:

- `absent` — элемент отсутствует;
- `nil` — установлен `xsi:nil="true"`;
- `typedEmpty` — указан `xsi:type`, текст пуст;
- `typedText` — указан `xsi:type` и текст;
- `untypedEmpty` — тип не указан, текст пуст;
- `untypedText` — тип не указан, текст присутствует.

JSON также содержит версию формата, параметры запуска, общие счётчики и список
`unresolved`. Абсолютные пути в него не записываются, чтобы результат был
воспроизводим на другой машине. Сортировка записей, конфигураций и примеров
детерминирована.

### Смысловые категории значений

Категория определяется независимо от частоты и не объявляет значение
правильным или ошибочным. Для примитивных типов используются категории:

- отсутствует;
- пустое XML (`xsi:nil` или пустой элемент);
- начальное значение типа: пустая строка, числовой ноль или начальная дата;
- явное значение;
- неразбираемое значение.

Точная исходная запись сохраняется рядом с категорией. Например,
`0001-01-01T00:00:00` относится к начальной дате, а корректная дата 2026 года —
к явной дате. Все разные явные даты образуют отдельные точные варианты в JSON,
но сворачиваются в одну категорию основной Markdown-таблицы.

Для ссылочных типов применяется иерархия:

1. семейство `reference`;
2. допустимый целевой metadata-тип или набор типов;
3. категория значения: пустая ссылка, предопределённое значение, значение
   перечисления, конкретная ссылка либо несовместимое/неразобранное значение;
4. точное исходное значение.

Таким образом, `Catalog.Контрагенты` и `Catalog.Номенклатура` доступны как
отдельные срезы, а сотни конкретных значений не превращаются в сотни строк
основной таблицы. Полный набор уникальных значений остаётся в JSON.

Поверх независимой смысловой категории записывается отдельная оценка текущих
`rules.ts`: `implicit`, `explicit`, `invalid`, `unresolved` или
`notSpecified`. Источник оценки всегда помечен как `rules`; она не смешивается
с фактом XML и смысловой категорией.

Имя обычного реквизита не входит в ключ агрегации: одинаковое точное значение
одного типа объединяется между разными реквизитами, а их имена сохраняются в
`attributeNames`. Для стандартного реквизита вид владельца и внутреннее имя
остаются частью ключа, поскольку его предметная политика зависит от них.

## Сводный Markdown

Markdown содержит:

1. параметры и итоговые счётчики исследования;
2. таблицу по семействам типов: строка, число, дата и время, булево, ссылка и
   другие обнаруженные семейства;
3. вложенные срезы по точному типу и его параметрам;
4. отдельную таблицу стандартных реквизитов по виду владельца и внутреннему
   имени;
5. варианты, где одной группе соответствуют разные категории или XML-формы,
   и отдельные противоречия текущим `rules.ts`;
6. неразрешённые типы и неразобранные XML-конструкции;
7. ограниченное число точных значений и относительных путей-примеров для
   каждой строки.

В каждой строке показываются семейство и точная сигнатура типа, категория
`FillValue`, XML-форма, количество наблюдений, число уникальных точных
значений, число конфигураций и состояние:

- `однозначно` — у группы одна наблюдаемая категория и XML-форма;
- `варианты` — обнаружено несколько категорий или XML-форм;
- `противоречит rules` — хотя бы один вариант классифицирован текущими
  `rules.ts` как недопустимый;
- `тип не определён` — тип нельзя надёжно установить.

`Однозначно` означает только единообразие исследованного каталога. Это не
автоматическое решение о каноническом XML и не разрешение удалить `!xml`.
Несколько точных явных значений одной категории сами по себе не образуют
противоречие.

## Интерфейс запуска

Навык использует команду:

```shell
node .agents/skills/analyze-fill-value-defaults/analyze-fill-value-defaults.mjs \
  /Users/nikita/git/round-trip-compact/cf \
  --output /private/tmp/fill-value-defaults
```

Команда создаёт:

- `fill-value-observations.json` — полный машиночитаемый результат;
- `fill-value-summary.md` — сводку для обсуждения.

Дополнительные параметры первой версии:

- `--concurrency N` — число одновременно разбираемых XML-файлов;
- `--examples N` — максимальное число примеров в строке Markdown;
- `--configuration NAME` — повторяемый фильтр конфигураций.

При ошибочном аргументе, отсутствующем каталоге, ошибке чтения или
неразбираемом XML скрипт завершает работу с ненулевым кодом. Неподдержанная,
но корректная XML-конструкция является данными раздела `unresolved`, а не
аварией.

## Навык

Навык `analyze-fill-value-defaults`:

1. принимает каталог конфигураций и каталог результата;
2. запускает скрипт без изменения исходных файлов;
3. сначала читает сводку и разделы конфликтов;
4. при необходимости обращается к полному JSON и XML-примерам;
5. явно разделяет подтверждённые XML-факты и типы, выведенные из `rules.ts`;
6. не предлагает изменение правил без разбора конфликтов и не применяет
   `!xml` как обход неизвестного случая.

Точка входа навыка вызывает
`packages/rules/scripts/analyze-fill-value-defaults.ts`; предметная логика и
её модульные тесты принадлежат пакету `@nkdk/rules`.

## Проверки

Скрипт разрабатывается через тесты на временном мини-каталоге, не изменяя
существующие XML-фикстуры. Проверки покрывают:

1. обычный строковый, числовой и датовый реквизит;
2. категории начальной и явной даты;
3. отсутствующий, `xsi:nil`, пустой типизированный и непустой `FillValue`;
4. пустую ссылку, предопределённое значение и несколько целевых ссылочных
   типов;
5. стандартный реквизит с типом из действующей композиции;
6. явное различение источников `xml`, `rules` и `unresolved`;
7. объединение повторов при сохранении всех уникальных точных значений;
8. конфликт одной сигнатуры между несколькими конфигурациями;
9. устойчивую сортировку JSON и Markdown;
10. относительные пути и ограничение примеров;
11. ошибочные аргументы и повреждённый XML;
12. сохранение неизвестной корректной конструкции в `unresolved`.

Отдельная проверка навыка запускает его команду на небольшом каталоге и
подтверждает наличие обоих файлов результата и разделов, необходимых для
анализа.

## Критерии готовности

- один запуск исследует весь `/Users/nikita/git/round-trip-compact/cf`;
- JSON содержит все уникальные точные значения, их счётчики и источники типов;
- Markdown позволяет увидеть единообразные случаи, конфликты и пробелы
  покрытия без ручного поиска по XML;
- повторный запуск на неизменном каталоге создаёт одинаковое содержимое;
- XML-каталог и правила metadata не изменяются;
- тесты скрипта, проверка навыка и обязательные проверки проекта проходят.

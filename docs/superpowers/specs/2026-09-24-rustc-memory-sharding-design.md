# Разделение предварительно скомпилированных правил для снижения памяти rustc

## Проблема и измеренная причина

`nkdk-compiled-rules-probes` и `nkdk-compiled-rules` передают одному
процессу `rustc` соответственно 31,4 и 30,3 МБ созданного Rust-кода.
Проверочный каталог содержит около 39 тысяч функций. На проверке
заимствований измерен пик 4811 МБ; он возникает до LLVM. Ограничение
параллелизма Cargo уменьшает суммарную память одновременных процессов, но
не этот пик одного процесса.

В производственном каталоге три кандидатных профиля реквизитов дают около
21,8 МБ из 30,3 МБ Rust-исходника. Они должны остаться вызываемыми, пока
считаются принятыми: простое исключение из сборки недопустимо. В
проверочном каталоге крупные семейства `MetadataValue`, `FillValue`,
`TypeDescription` и выборов тоже нельзя удалять ради замера.

## Договор

1. Декларации YAML и далее компилируются до запуска программы. XML ↔ YAML
   исполняется скомпилированным Rust-кодом, без интерпретации деклараций и
   без нового преобразования значения на границе пакетов.
2. Компилятор назначает каждому исполняемому правилу один устойчивый
   внешний `EntryId`; внутренние номера пакета остаются скрытыми. Связи
   импортов замыкаются в том пакете, который использует правило.
3. Разделение проходит по независимо вызываемым семействам. Связанные
   источники и потребители фактов либо находятся в одном семействе, либо
   используют общий каталог фактов с одинаковыми индексами; несогласованные
   локальные индексы запрещены.
4. Общая точка входа создаётся из метаданных компилятора. В ней нет условий
   по именам объектов, типов или свойств. Она сохраняет `entry_id`,
   подготовку входов, преобразование, проверку, аномалии, ресурсы и факты.
5. Ни один существующий вызов принятого правила и ни один тест не удаляется.
   XML-фикстуры остаются неизменными. Сравнение двух направлений, аномалий
   и фактов производится на тех же входах до и после разделения.
6. В обычной локальной сборке ни один процесс `rustc` не должен достигать
   прежних 4,8 ГБ. Целевой предел — 2 ГБ на пакет при одном задании Cargo;
   если наиболее крупное связное семейство превышает его, отдельно
   сокращается повторная генерация внутри этого семейства.
7. Время преобразования на одинаковых release-входах не должно
   воспроизводимо вырасти. Измерять оба направления, не менее пяти прогонов
   каждого. Замер сборки фиксирует отдельно генерацию, `rustc`, пик RSS и
   полную сборку.

## Границы реализации

Первый этап — точный выбор семейства по корневым правилам, включая
кандидатные каталоги и варианты системных перечислений. Второй —
независимые пакеты с полным покрытием нынешних проверок. Третий —
производственный фасад и общий договор фактов. Разбиение считается
завершённым только после третьего этапа и измерений; локальное ускорение
одного теста не является исправлением полного каталога.

# Диагностика отсутствующих toXML-обработчиков в round-trip-yaml

## Контекст

После предыдущих исправлений `round-trip-yaml` проходит стадию `XML -> YAML`, но на стадии `YAML -> XML` остаются ошибки:

- `MetadataCatalog "СканированныеДокументыДляПередачиВЭлектронномВиде": Cannot read properties of undefined (reading 'toXML')`
- `MetadataDocument "ЗаявлениеАбонентаСпецоператораСвязи": Cannot read properties of undefined (reading 'toXML')`

Сообщение не показывает тип значения, свойство или правило, из-за которого реестр вернул `undefined`.

## Цель

Сделать ошибку диагностируемой: при отсутствии `toXML`-обработчика бросать понятное исключение с типом значения и ближайшим контекстом правила.

## Границы

В этой задаче не исправляется сам отсутствующий обработчик. Цель - получить точную следующую ошибку, чтобы потом отдельно спроектировать поведенческое исправление.

XML-фикстуры не меняются. YAML-формат не меняется.

## Подход

Добавить защитную проверку в узких точках, где сейчас возможен `undefined.toXML`:

- `DcsMetadataTypedValueRegistry[modelValue.type].toXML`
- `primitiveValueHandlers[value.type].toXML`

Если обработчика нет, ошибка должна явно назвать неподдержанный тип. Если доступен `rule.type`, его тоже нужно включить в сообщение.

## Проверка

Минимальная проверка:

- точечный тест на DCS typed value с неизвестным типом, который ожидает понятную ошибку;
- точечный тест на MetadataValue с неизвестным типом, который ожидает понятную ошибку.

После этого запускается `round-trip-yaml`, чтобы получить конкретный первый отсутствующий тип для следующего разбора.

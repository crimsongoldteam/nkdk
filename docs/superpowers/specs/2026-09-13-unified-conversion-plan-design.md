# Единый план преобразования в компиляторе деклараций

Дата: 13 сентября 2026 года. Спецификация согласована пользователем;
подготовлен [подробный план реализации](../plans/2026-09-13-unified-conversion-plan.md).
Выполнение начато: сохранена исходная база, следующий блок — общий план записи.

Связанные договоры: [язык деклараций](2026-09-10-declaration-language-design.md),
[массовый перенос правил и тестов](2026-09-12-rules-bulk-migration-design.md),
[текущий план подключений](../plans/2026-09-13-ready-declaration-attachment.md).

## 1. Проблема и результат

В `rule-compiler/src/generate` записи, вложенные записи, составные объекты
и элементы коллекций проходят через разные пути генерации. Они уже
переиспользуют часть функций, но по-разному определяют поддержанные сочетания,
контекст, группы зависимых полей и границы сохранения XML.

Пример: имя, значение по умолчанию и именованная коллекция работают отдельно,
однако вынос имени из группы зависимых полей потребовал дополнительной
поддержки. Отсутствие YAML-сопоставления уже допускается проверкой полноты
при наличии восстановления, но новая проверка схемы обнаружила обязательный
поиск такого сопоставления и аварийное завершение генератора схемы.

Результат этапа: значение получает единый договор преобразования независимо
от того, где используется. Декларация common, поле объекта и элемент коллекции
используют одни правила восстановления, проверки и сохранения аномалий.

Основная мера результата — количество полностью перенесённых объектов,
которые инструмент выпускает без изменения общих механизмов компилятора.
Количество внутренних тестов и сгенерированных YAML-файлов не заменяет её.

## 2. Принятое решение и границы

Компилятор строит единый типизированный план преобразования **при сборке**,
после связывания деклараций. Из него генерируется Rust для обоих направлений
и проверки YAML; структурная схема использует тот же план.

Первый этап охватывает записи, вложенные записи, состав полей и коллекции:
массивы и словари именованных записей. В него входят зависимые значения,
привязки контекста, XML-поля без обычного YAML-представления и аномалии.
Готовые преобразователи простых значений сохраняются за единым договором
значения. Ресурсные операции и публичные команды приложения сохраняют свои
границы; их подключение к записи использует существующие явные маршруты.

Это внутреннее представление компилятора, а не новый пользовательский формат
правил. Общая YAML-спецификация для common и rules сохраняется. Предметные
названия, значения по умолчанию и зависимости описываются декларациями.
Неизвестное выражение из `rules.ts` остаётся явной блокировкой переноса.

Альтернатива — объединять отдельные функции существующих генераторов.
Она даёт меньший начальный объём изменений, но сохраняет несколько мест,
которые могут независимо определять смысл одной конструкции. Поэтому выбран
единый план, вводимый постепенно на существующем компиляторе.

## 3. Устройство и ответственность

При сборке:

```text
rules.ts → инструмент переноса → YAML-декларации
                                  ↓
                     разбор, связывание, типизация
                                  ↓
                    единый план преобразования
                         ↙               ↘
              сгенерированный Rust     JSON Schema
```

| Часть | Отвечает за | Получает и выдаёт |
|---|---|---|
| Инструмент переноса | Извлечение исходных правил и полноту автоматического выпуска | `rules.ts` → декларации, происхождение полей, блокировки |
| Связывание | Имена, параметры, ссылки и типы выражений | Декларации → существующая связанная модель |
| Подготовка плана | Однозначное значение каждого поля, зависимости, области контекста и маршруты | Связанная модель → проверенный план |
| Генерация Rust | Хранение значений, чтение событий, вычисления, запись и диагностику | План → Rust |
| Генерация схемы | Структурные ограничения доступного пользователю YAML | Тот же план → схема и признак необходимых проверок Rust |
| Оркестратор | Подготовку индексов и документов, запуск операции, сбор результатов | Входные файлы и подготовленные данные → результат операции |

План размещается внутри `rule-compiler`, отдельными модулями подготовки
значений, областей контекста и маршрутов. Он зависит от `rule-model`;
преобразователи XML/YAML и общие средства аномалий остаются в `conversion-core`.
Оркестратор не получает YAML-декларации для интерпретации при каждом запуске.

План содержит ссылки на значения и экземпляры их специализации. Повторная
ссылка на common не копирует его дерево без необходимости. Рекурсивная
структура вложенных элементов не разворачивается в бесконечный код: план
использует ссылки, а обработка подчиняется фактической глубине входных данных
и ограничениям ресурсов. Цикл вычисления значений по умолчанию при этом
остаётся ошибкой декларации.

## 4. Единый договор значения и поля

Для значения план определяет тип, представления, присутствие, ограничения
и способ обращения к его подчинённым значениям. Для поля дополнительно
определяются место в записи, XML-маршрут, необязательное YAML-сопоставление,
привязки контекста и зависимости от других полей.

Запись хранит поля и порядок вычислений. Коллекция перебирает элементы и
вызывает тот же договор значения. Именованная коллекция переносит объявленное
поле в ключ YAML, сохраняя полное смысловое значение записи для вычислений
и проверки. Это изменение представления, а не удаление поля из модели.

Пустота коллекции, повторы, порядок, отсутствие записи и отсутствие поля
остаются отдельными состояниями. Значения по умолчанию внутри отсутствующей
записи не создают её автоматически. Составление из фрагментов разворачивается
один раз при подготовке плана с сохранением происхождения и согласованного
порядка полей.

В каждом месте использования работают одинаковые общие операции:
прочитать значение, восстановить отсутствующее, проверить смысл,
определить обычное представление и сохранить доказанную потерю XML.
Нельзя добавлять отдельный вариант этих операций для UUID, I8nText,
документа или элемента формы в генератор записи или оркестратор.

## 5. Контекст и порядок вычислений

План различает подготовленные входы операции, область владельца и область
текущего элемента. Привязки берутся из объявленных входов и выражений;
имена предметных ролей разрешаются в декларациях, не в нейтральном коде.

Сначала читаются явно представленные данные записи. Затем вычисляются
отсутствующие значения в порядке их зависимостей, выполняются ограничения
и подготавливается обычное представление. XML-порядок чтения и записи
не обязан совпадать с порядком вычислений. Вложенное значение получает
подготовленные привязки, даже если нужное поле владельца встретилось позже
в XML. Для этого допустимо удерживать необходимое состояние текущей записи;
повторно разбирать исходный файл для каждого поля нельзя.

Контекст элемента состоит из ссылок на общие неизменяемые входы и его
собственных значений. Индексы не копируются для каждого элемента. Привязки
проверяются на тип и доступность при подготовке плана; циклы вычислений
и обращения за пределы объявленной области диагностируются до запуска.

Пример использования: имя прочитано из XML либо YAML-ключа; идентификатор
восстановлен по подготовленному индексу; обычный синоним вычислен из имени.
Эти зависимости должны работать в отдельной записи, дочернем объекте
и элементе коллекции одним способом.

## 6. Служебное XML и аномалии

Отсутствующее YAML-сопоставление означает, что обычного пользовательского
ключа нет. Поле должно иметь предусмотренное декларацией восстановление;
отсутствие сопоставления само по себе не разрешает потерю XML. Служебный
идентификатор не превращается в обычное поле YAML или скрытый ключ для
обхода ограничения компилятора.

Декларация описывает нормальные значения. Общий механизм выводит из неё
допустимые состояния и распознаёт отклонения без отдельных списков аномалий
для каждого объекта. Перед сохранением `!xml/raw` проверяется, что обычный
экспорт действительно теряет XML-форму и её нельзя восстановить по смыслу
и подготовленным индексам.

План знает границы владения XML. При расхождении используется минимальная
граница, на которой поправку можно однозначно записать и применить; если
более узкая граница неоднозначна из-за порядка или повторов, сохраняется
охватывающая запись или коллекция. Теги и содержимое аномалий проходят
проверку, обратное преобразование выполняется с заново подготовленными
входами без доступа к исходному XML.

Некорректные предметные данные сохраняются как аномалии согласно общему
договору. Ошибка компилятора, неподготовленный обязательный индекс, нарушение
его поколения или ошибка ввода-вывода не маскируются под аномалию данных.
Неизвестное правило не считается поддержанным через сохранение всего XML.

## 7. Валидация и производительность

Rust-проверка работает с полным восстановленным значением. JSON Schema
описывает видимый YAML: служебные поля не попадают в `properties` и `required`.
Если ограничение зависит от скрытого значения, индекса или поля, вынесенного
в ключ коллекции, проверка остаётся в Rust и отмечается как требующая его
выполнения. Генератор схемы не должен аварийно завершаться из-за отсутствия
YAML-ключа и не должен молча объявлять такую проверку выполненной.

Во время преобразования нет интерпретатора плана и обязательного второго
дерева всего документа. Генератор выпускает типизированное состояние и
прямые вызовы общих преобразователей; пути и статические привязки известны
при сборке. Коллекции по возможности обрабатываются последовательно;
буферизация зависит от объявленных взаимосвязей, а не от имени объекта.

Обычный путь не сериализует промежуточный YAML для передачи между слоями.
Повторные проходы, необходимые существующему доказательству round-trip,
измеряются отдельно и сохраняются. Деревья для поправок материализуются
на исключительном пути. Унификация не разрешает отключить проверку
восстановления ради ускорения.

Цель проекта — 10× по скорости и 10× по памяти — сохраняется, но данным
изменением не объявляется достигнутой. Сравнение выполняется в release
на одинаковом поддержанном наборе e2e: время обоих направлений, пиковая
память, размер сгенерированного кода и время его сборки. Для обычных и
аномальных данных результаты приводятся раздельно.

## 8. Семейства и порядок перехода

До перестройки механизма составляется единая матрица требований трёх семейств:

| Семейство | Основные источники и отличия |
|---|---|
| Значения перечислений | `MetadataEnumerationValueRules`: идентичность, коллекция `enumValues`, синоним, принадлежность и связь расширения с основой |
| Реквизиты документа | Фактический `itemRule` коллекции документа: наследование и переопределения, описание типа, зависимые значения и ссылки |
| Элементы форм | `InputFieldRules`, `TableInputFieldRules`, `FormAttributeRules` и вложенные группы: области контекста, вложенность, коллекции и особенности размещения |

Первым принимается семейство значений перечислений, включая рабочее
подключение коллекции к владельцу, индексы и случаи расширений. Проверочная
оболочка свойства не считается такой приёмкой. Следующим проверяется
автоматический перенос реквизитов документа на том же механизме.
Элементы форм служат ранней проверкой требований; полная миграция всех
форм не входит в первый этап унификации.

Порядок внедрения:

1. Сохранить исходный перечень блокировок и сопоставление старых проверок;
   отдельно зафиксировать незавершённые изменения текущей ветки.
2. Подготовить матрицу трёх семейств и выбрать полный набор зависимостей
   для приёмки первого семейства.
3. Ввести внутренний план и единый договор значения. Перенести существующие
   пути генерации по общим конструкциям, сохраняя проверенные преобразователи.
4. Подключить автоматический выпуск первого семейства и проверить рабочую
   интеграцию в обоих направлениях.
5. Повторить перенос для реквизитов документа, учитывая отдельно изменения
   деклараций, инструмента извлечения и общих механизмов компилятора.

Для уже перенесённой конструкции не остаются два независимо определяющих
её смысл пути. Временный переходник делегирует общему плану; его удаление
входит в тот же законченный блок. Новый предметный common описывается YAML;
добавление обхода по имени common в Rust блокирует приёмку.

## 9. Проверки и условия приёмки

Сохраняется [четырёхуровневая архитектура тестов](../../../.agents/testing.md).
Механизм проверяется на небольшой общей матрице; объект — на независимых
входах и ожиданиях; оркестратор — на передаче контекста и маршрутов;
e2e — на рабочем пути проекта. XML-фикстуры не изменяются.

Матрица сочетаний содержит обычную запись, вложенную запись и элемент
массива/словаря; встроенное значение и ссылку на common; зависимости от
соседа и владельца; служебный XML-атрибут; отсутствие, несовпадение,
порядок, повтор и аномалию внутри подчинённого значения. Это представители
разных договоров, а не полное произведение всех свойств всех объектов.

Каждый сценарий проверяет XML → ожидаемый YAML и YAML → ожидаемый XML
независимо. Round-trip дополняет их. Удаление старой проверки допускается
только после записи, какой сценарий сохранил её защиту; ожидания нельзя
получать исключительно из проверяемой декларации.

После небольшого изменения запускаются затронутые проверки. Полный набор
Rust, Clippy, архитектурные ограничения и jscpd выполняются после законченного
блока; обязательные проверки проекта перед закрытием issue и PR сохраняются.
Самопроверка универсальности выполняется по
[договору ревью](../../../.agents/declarative-review.md). Субагенты и таймер
не используются; самопроверка не называется независимым ревью.

Первый этап принят, когда одновременно выполнены условия:

- Общая матрица и прежние поддержанные договоры проходят новый путь.
- Первое семейство переносится автоматически полностью и подключено к
  рабочему владельцу; нет необъяснённых пропусков свойств или зависимостей.
- Следующее семейство проверено на том же плане. Изменения common-деклараций
  и извлечения `rules.ts` учитываются отдельно; если пришлось менять общий
  механизм для уже заявленного сочетания, критерий переиспользования не пройден.
- Сравнение производительности выполнено на одинаковом поддержанном e2e;
  необъяснённая регрессия не скрыта за более широким охватом.
- Отчёты отделяют извлечённое, скомпилированное и полностью принятое.
  Пользовательский чеклист сохраняет только флажок полной готовности объекта.

## 10. Исходное состояние и план реализации

Сохранённый отчёт коллекций содержит 142 заблокированные связи и 0 кандидатов;
common-чеклист — 19/90. Эти числа не пересчитываются в готовые объекты из-за
принятия архитектуры. В ветке уже есть незавершённая поддержка служебного XML:
22 сценария коллекций прошли, но новая проверка схемы
`xml_only_fields_are_restored_by_runtime_not_exposed_by_schema` обнаруживает
отказ в `schema.rs` на отсутствующем сопоставлении. Это исходная известная
неисправность, а не результат новой архитектуры.

По согласованной спецификации составлен отдельный
[план реализации](../plans/2026-09-13-unified-conversion-plan.md)
с конкретными файлами, блоками переноса, интерфейсами, командами проверки
и условиями приёмки. Подготовка плана не меняет статусы текущих объектов
и не запускает реализацию.

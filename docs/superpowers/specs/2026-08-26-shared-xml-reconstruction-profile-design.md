# Общий профиль восстановления XML компонента

## Статус

Согласованный дизайн переиспользования экспортного профиля при контрольном
экспорте во время импорта XML → YAML.

## Контекст

Импорт проверяет результат через контрольный YAML → XML: после первого прохода
он экспортирует полученный YAML и сравнивает XML с источником. Для расширения
этому экспорту необходимо знать для каждого объекта:

- является ли объект собственным или заимствованным;
- какой вариант XML-значений применять: `full`, `adopted` или `indexed`;
- UUID объекта основной конфигурации, если объект заимствован.

Полная и частичная синхронизация уже получают эти сведения из индексов целевого
и базового компонентов. Импорт вместо этого читает корневой XML каждого задания
и распознаёт только UUID корневого `ExtendedConfigurationObject`. Вложенные
объекты в профиль не попадают.

Из-за этого контрольный экспорт расширения ошибочно считает заимствованные
вложенные объекты собственными. Он не восстанавливает `ObjectBelonging`, UUID и
зависящие от них XML-значения, а proof сохраняет расхождение как `!xml/raw`.
Обратная ошибка возникает у собственного вложенного объекта: при отсутствии
точной записи он наследует `adopted` от родительского логического адреса и не
выводит собственные XML-значения по умолчанию.

В текущих e2e YAML это даёт 319 лишних тегов:

- 157 `ПринадлежностьОбъекта: !xml/raw`;
- 157 парных `Properties: !xml/raw` у тех же заимствованных объектов;
- 4 локальных raw собственных свойств `IntegrationServiceChannel`;
- 1 родительский raw порядка `Properties` у этого канала.

## Цель

Выделить из существующего экспортного профиля чистый общий построитель и
использовать один и тот же результат в импорте, полной и частичной
синхронизации.

После изменения контрольный экспорт должен получать точный профиль всех
адресуемых объектов компонента. Перечисленные 319 тегов должны исчезнуть без
новых YAML-полей и без изменения XML-фикстур.

## Не входит в задачу

- анализ и устранение остальных 72 тегов `!xml` в e2e YAML;
- изменение правил `fromXML`, `toXML`, `fromYAML` или `toYAML`;
- добавление полей в `PropertyRule`, `BasePropertyRule` или параметры
  построителей правил;
- изменение XML-фикстур;
- проверка каталога `cf/doc`;
- миграция старых YAML или режим совместимости со старым контрольным профилем;
- перенос экспортных сведений о формах, путях файлов и состоянии снимка в общий
  профиль восстановления XML.

## Выбранный подход

Из экспортного профиля выделяется чистый построитель **«Подготовить профиль
восстановления XML компонента»**. Он находится вне `importFromXml`,
`fullSyncToXml` и `partialSyncToXml`, чтобы все три операции зависели от одного
общего механизма.

Построитель не запускает полную синхронизацию и не принимает
`ConfirmedComponentState`. Он работает с уже подготовленными сведениями
индексов:

- логическими адресами целевого компонента;
- логическими адресами базовой конфигурации для расширения;
- сохранёнными UUID/XML ID по этим адресам;
- видом компонента.

Он не открывает LMDB, не читает XML/YAML, не создаёт воркеры и не проверяет
согласованность снимка. Эти обязанности остаются у вызывающей операции.

### Почему не другие подходы

Полный вызов `profile.confirm` из импорта не подходит: он требует
`ConfirmedComponentState`, проверяет согласованность YAML со снимком и содержит
сведения, нужные только синхронизации. Во время импорта целевой YAML ещё не
опубликован.

Отдельный импортный сборщик также не подходит: он продублирует правила
классификации, из-за расхождения которых и возникла ошибка.

## Договор профиля

Профиль восстановления XML содержит только данные, общие для преобразования
YAML → XML:

```ts
interface XmlComponentReconstructionProfile {
  readonly componentKind: ComponentAddress["kind"]
  readonly adoptedUuids: Readonly<Record<string, string>>
  readonly xmlDefaultVariantByLogicalAddress:
    Readonly<Record<string, XMLDefaultVariant>>
}
```

Точные имена типов могут быть уточнены при реализации, но граница и состав
данных остаются такими.

### Инварианты

1. Каждый логический адрес, который может стать текущим адресом экспортируемого
   объекта, имеет собственную точную запись в
   `xmlDefaultVariantByLogicalAddress`.
2. Алгоритм может использовать существующую иерархическую семантику для
   вычисления результата, но перед передачей воркеру материализует её в точные
   записи. Воркер не должен случайно наследовать вариант соседнего или
   родительского объекта.
3. Для основной конфигурации сохраняется действующий договор `indexed`: объект,
   чьи сохраняемые UUID/XML ID получены из индекса, и его явно относящиеся к
   нему адреса получают вычисленный `indexed`; остальные адреса получают
   `full`.
4. Для расширения адрес, присутствующий в основной конфигурации, получает
   `adopted`; собственный адрес получает `full`. Корень `Конфигурация`
   расширения получает `adopted`.
5. Ключи один раз приводятся к каноническому формату, который использует
   `configurationIndex.logicalAddress` в воркере.
6. `adoptedUuids` содержит UUID базового объекта под тем же каноническим
   ключом. Собственный объект не получает заимствованный UUID.
7. Если для заимствованного объекта его правила требуют UUID, а базовый индекс
   его не содержит, подготовка завершается понятной ошибкой до запуска
   контрольных экспортов. Ошибка содержит логический адрес.
8. Профиль после создания неизменяем и один раз передаётся всем воркерам
   компонента.

## Поток данных

```text
индекс целевого компонента ─┐
                            ├─→ общий построитель
индекс базовой конфигурации ┘       │
                                    ├─ точный вариант каждого адреса
                                    └─ UUID заимствованных объектов
                                               │
                    ┌──────────────────────────┼────────────────────────┐
                    ▼                          ▼                        ▼
              импорт: proof            полная синхронизация    частичная синхронизация
              YAML → XML                  YAML → XML                YAML → XML
```

### Импорт

1. Первый проход импортирует XML и создаёт рабочий индекс целевого компонента.
2. Для расширения опубликованное состояние основной конфигурации уже
   актуализировано существующим предусловием импорта.
3. Координатор читает необходимые индексные сведения один раз и строит профиль
   восстановления всего компонента.
4. Профиль включается в общую инициализацию второго прохода и переиспользуется
   всеми контрольными экспортами.
5. `executeImportControlExport` больше не читает исходный XML ради корневого
   UUID и не создаёт локальную карту только для текущего задания.

Специфичные для компонента сведения, вычисляемые из корневого YAML, например
`typeDescriptionXMLNameByType`, подготавливаются координатором один раз и
добавляются к профилю воркера отдельно от общего построителя.

### Полная и частичная синхронизация

Существующие `configuration` и `configurationExtension` профили продолжают:

- подтверждать состояние компонентов и снимков;
- подготавливать базовые формы и пути;
- выполнять проверки, относящиеся только к синхронизации.

Но карты `adoptedUuids` и `xmlDefaultVariantByLogicalAddress` они получают из
общего построителя. Поэтому обычный экспорт и proof импорта больше не могут
расходиться в классификации одного адреса.

## Границы компонентов

Общий построитель размещается в нейтральном metadata-модуле рядом с общими
данными XML-экспорта. Он может зависеть от типов индекса, канонизации логических
адресов и типов runtime-контекста, но не от операций импорта или синхронизации.

Направление зависимостей:

```text
importFromXml ───────────┐
fullSyncToXml ──────────┼─→ xmlReconstructionProfile → runtime types
partialSyncToXml ───────┘
```

Профиль полной синхронизации композиционно добавляет к общему профилю
экспортные сведения `baseForms`, пути и состояние снимка. Общий модуль не знает
об этих полях.

## Ошибки

Ошибки построения профиля являются ошибками подготовки операции, а не
XML-аномалиями. Они не должны превращаться в `!xml/raw`.

Ожидаемые отдельные случаи:

- для расширения нет подтверждённой основной конфигурации;
- отсутствует обязательный UUID заимствованного объекта;
- один канонический адрес получил противоречащие сведения;
- вид компонента не поддержан построителем.

Импорт отменяет временное состояние обычным путём и возвращает диагностику.
Синхронизация не начинает запись XML.

## Производительность и память

Профиль строится один раз на компонент за `O(n + m)`, где `n` и `m` — число
логических адресов целевого и базового компонентов. Для поиска используются
множества и словари.

В памяти находятся только канонические адреса, варианты и UUID. XML-деревья,
строки исходных документов и отдельные профили заданий не копируются.

Запрещены:

- повторное построение профиля для каждого задания;
- чтение исходного XML из `executeImportControlExport` ради классификации;
- открытие LMDB внутри чистого построителя;
- линейный поиск по базовому индексу для каждого целевого адреса.

## Проверка

### Модульные тесты общего построителя

- основная конфигурация материализует точные `indexed` и `full`;
- корень расширения получает `adopted` и UUID основной конфигурации;
- вложенный заимствованный объект получает `adopted` и свой UUID;
- вложенный собственный объект под заимствованным родителем получает точный
  `full`, а не наследует `adopted`;
- адреса канонизируются одинаково с воркером;
- отсутствие обязательного UUID возвращает адресную ошибку;
- противоречащие сведения отклоняются.

### Интеграционные тесты импорта

- заимствованный реквизит расширения восстанавливает `ObjectBelonging`, UUID и
  порядок `Properties` без raw;
- собственный `IntegrationServiceChannel` восстанавливает четыре стандартных
  свойства и порядок без raw;
- несколько заданий одного компонента получают один и тот же заранее
  построенный профиль;
- контрольный экспорт больше не вызывает чтение исходного XML ради UUID.

### Регрессия экспорта

Существующие тесты профилей `configuration` и `configurationExtension`
сохраняются. К ним добавляется проверка, что полная и частичная синхронизация
используют общий построитель и не меняют ожидаемый XML.

### Приёмка e2e

1. Импортируются только e2e-фикстуры; каталог `cf/doc` не используется.
2. В повторно созданных e2e YAML отсутствуют все 319 тегов этой группы.
3. Оставшиеся `!xml` повторно подсчитываются и рассматриваются отдельно.
4. XML-фикстуры не изменены.
5. Проходит `pnpm test:e2e`.
6. Перед завершением проходят обязательные проверки проекта, включая
   `pnpm duplicates -- --base <исходный-коммит>` и `pnpm test`.

## Последовательность реализации

1. Зафиксировать текущую классификацию в модульных тестах общего построителя.
2. Выделить чистое построение карт из профилей полной синхронизации.
3. Перевести полную и частичную синхронизацию на общий результат без изменения
   их экспортных дополнений.
4. Построить профиль после рабочего индекса первого прохода импорта и передать
   его второму проходу.
5. Удалить корневой `readAdoptedUuid` и локальное дополнение контекста
   контрольного экспорта.
6. Добавить интеграционные регрессии для заимствованного и собственного
   вложенных объектов.
7. Повторить импорт e2e, проверить число `!xml` и запустить обязательные тесты.

# Конечная таблица состояния

Уточнение согласованного `state-relation`: одна таблица связывает состояние
YAML с сочетанием признаков XML. Компилятор выводит из неё оба направления,
используя существующие выражения и правила присутствия. Во время преобразования
нет интерпретатора таблицы или повторного разбора декларации.

## Запись

Фрагмент применяется к записи с полями `state`, `base`, `notice`.
`state` ссылается на перечисление со значениями `default`, `empty`, `tagged`,
`text`; его обычная декларация задаёт четыре формы YAML. В XML сопоставлены
`base` и `notice`, в YAML — `state`.

```yaml
state-relations:
- field: state
  sources:
    base: {present: {input: baseId}}
    notice: {equals: {literal: Notify}}
  states:
    default: [base]
    empty: []
    tagged: [base, notice]
    text: [notice]
```

Полный компилируемый пример —
[`state-projections.yaml`](../../../rust/crates/rule-compiler/tests/fixtures/state-projections.yaml).

- `present` означает: признак активен, если исходное поле присутствует.
  Выражение внутри задаёт значение для восстановления активного поля.
- `equals` означает: признак активен, если поле присутствует и его значение
  совпадает с результатом выражения. То же выражение задаёт восстановление.
  Отсутствующее поле не читается для сравнения.
- Строка `states` перечисляет активные источники. Остальные неактивны.
  При экспорте неактивное поле отсутствует.

В примере UUID берётся из подготовленного `baseId`; запись режима
восстанавливается как `Notify`. Таблица не содержит отдельной процедуры
импорта, экспорта или регистрации аномалий. Отличающаяся исходная запись XML
сохраняется существующим механизмом проверки восстановления.

## Проверяемый договор

Каждое сочетание активности источников должно встречаться ровно один раз.
Таблица также обязана покрывать всё перечисление состояния после разрешения
импортов. Нельзя повторять источник внутри строки, ссылаться на неизвестный
источник или использовать поле состояния как собственный источник.

Результат отношения имеет только YAML-проекцию, источники — только XML-проекции.
Нельзя одновременно задать для этих полей ручные правила присутствия или
второе отношение: два независимых определения восстановления отвергаются.
Типы выражений и зависимостей проверяются обычным связыванием декларации.
Ошибки самой таблицы обнаруживаются при сборке и не превращаются в аномалии
данных. Недоступный подготовленный вход остаётся ошибкой подготовки.

Количество источников не привязано к двум. При импорте компилятор строит дерево
решений: на выбранном пути проверяется каждый источник один раз. При экспорте
из тех же строк выводится набор состояний, в которых восстанавливается источник.
Состояния остаются типизированными вариантами Rust; промежуточные строки
для выбора состояния не создаются.

## Граница текущего механизма

Эта форма описывает конечные сочетания признаков присутствия/равенства полей.
Она не объявляет готовыми выбор строки общей коллекции, сохранение её остатка,
обратную вставку строки, профили применимости или источник базового индекса.
Для `ExtendedConfigurationObject` эти части должны быть подключены и проверены
на настоящей структуре `InternalInfo/xr:PropertyState`. Временный скалярный
`Notice` в проверочном примере не является перенесённой коллекцией.

Составная запись и независимое дополнительное поле используют те же таблицы.
Проверки включают четыре прежние формы YAML в обычной и составной записи,
сохранение неизвестного значения XML, а также отдельный пример с тремя
источниками и восемью состояниями без изменения компилятора.

## Вычисляемый источник состояния

Источник таблицы может получать значение из общей коллекции. Необязательный
`from` содержит обычное типизированное выражение, например `select`/`match`:

```yaml
sources:
  notice:
    equals: {literal: Notify}
    from: # выражение чтения режима выбранной записи
      input: selectedMode
```

Такой источник — смысловое поле без собственного XML-пути и без YAML-ключа.
В XML-направлении значение вычисляется из `from`; в YAML-направлении таблица
восстанавливает его тем же `equals` или `present`, что и физический источник.
Далее обычное правило коллекции использует восстановленное значение при сборке.
Нельзя одновременно объявить `from` и физический XML-путь этого источника:
это два владельца одного значения. Типы, циклы и порядок зависимостей проверяются
существующим механизмом выражений отдельно для каждого направления.

`from` не является самостоятельной обратной функцией. Таблица по-прежнему одна;
выражение лишь указывает, откуда читается её признак. Правило восстановления
общей коллекции обязано сохранить остальные строки и форму XML. Само наличие
вычисляемого источника не доказывает завершение этого правила.

## Применимость и базовый индекс

Источник `present` может восстанавливаться через обычный `require/lookup`.
Индекс связи с базой использует составной ключ компонента и собственной
идентичности; готовая строка UUID не должна подставляться вместо рабочей
проверки этого соединения. Устаревшее поколение индекса остаётся ошибкой
подготовки, а не аномалией XML-значения.

Поле состояния может дополнительно использовать существующее
`presence.yaml.omitWhen`, например при отсутствии применимого профиля.
Такое условие дополняет, а не заменяет сокращение отсутствующего варианта
в таблице YAML-форм: условия объединяются через «или». Собственная таблица
по-прежнему определяет восстановление значений; ручное правило `missing`,
`empty` или другое переопределение присутствия с ней конфликтует.

Применимость задаётся входом декларации. Этот же вход участвует в условии
восстановления ссылки на базу. Проверка явного YAML-значения там, где правило
требует отсутствие поля, уже выводится из `omitWhen`: отдельный реестр аномалий
или специальная проверка для `ExtendedConfigurationObject` не нужны.

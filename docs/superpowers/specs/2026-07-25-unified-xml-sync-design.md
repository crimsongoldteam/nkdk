# Унифицированная синхронизация конфигурации и расширений в XML

## Контекст

NKDK уже выполняет полную синхронизацию компонента `cf` в XML. Расширения хранятся отдельными компонентами `cfe/<Имя>` и требуют дополнительных данных основной конфигурации:

- UUID заимствованных объектов и дочерних элементов;
- составного поиска `cfe → cf`;
- служебных XML-данных расширения;
- построения `BaseForm` для заимствованных форм.

Эти отличия не должны приводить к отдельной реализации координатора, worker, формирования XML и записи снимка.

В проекте также предусмотрена частичная синхронизация с информационной базой. Её правила выбора изменившихся объектов ещё не определены, но будущая операция должна использовать тот же исполнитель XML, что полная синхронизация.

Документ дополняет решения [об импорте расширений](2026-07-25-configuration-extensions-design.md), [о полной синхронизации в XML](2026-07-20-full-xml-sync-design.md) и [о единой топологии ресурсов](2026-07-25-unified-metadata-resource-topology-design.md). Определённые там форматы YAML и снимков сохраняются, если ниже не указано иное. Маршруты файлов берутся только из проекций единой топологии ресурсов.

## Цели

- Поддержать полную синхронизацию одного выбранного `cfe` в отдельный XML-каталог.
- Сохранить существующую полную синхронизацию `cf`.
- Использовать один координатор и один исполнитель XML-заданий для `cf` и `cfe`.
- Не создавать отдельные исполнители для полной и частичной синхронизации.
- Использовать общую топологию ресурсов и её XML-проекцию вместо отдельного набора маршрутов синхронизации.
- Вынести получение структуры, хэшей и индексов из синхронизации с расчётом на кэширование в долгоживущем MCP-процессе.
- Проверять, что структура, хэши и индексы относятся к одному состоянию файлов.
- Читать форму `cf` только тогда, когда строится XML соответствующей заимствованной формы.
- Полностью удалить генерацию `ConfigDumpInfo.xml`: этот файл создаёт платформа 1С.

## Границы текущей реализации

В текущую реализацию входят:

- общий механизм полной синхронизации `cf` и `cfe` в XML;
- профиль основной конфигурации;
- профиль расширения;
- независимые договоры получения структуры, хэшей и индексов;
- договор исполнителя, принимающего полный либо явно заданный состав файлов;
- удаление генератора `ConfigDumpInfo.xml`.

В текущую реализацию не входят:

- определение состава частичной синхронизации;
- правила включения владельца при добавлении или удалении формы и других внешних свойств;
- публичная операция частичной синхронизации;
- создание временных каталогов и вызов `load-config-from-files`;
- кэш MCP;
- экспорт, валидация и YAML-схемы расширений.

Таким образом, частичная синхронизация учитывается в границах общего исполнителя, но не реализуется как законченная пользовательская операция.

## Основное архитектурное решение

Используется один координатор синхронизации компонента и два профиля:

- профиль `cf`;
- профиль `cfe`.

Координатор отвечает за общую последовательность:

1. проверку входов и целевого каталога;
2. получение структуры компонента;
3. чтение и проверку компонентного снимка;
4. получение текущих хэшей;
5. получение индекса метаданных и индекса зависимостей;
6. проверку согласованности состояния;
7. построение списка XML-заданий из выбранного состава;
8. выполнение заданий worker;
9. перенос внешних файлов;
10. проверку записанного результата;
11. формирование и запись следующего снимка компонента.

Профиль компонента не повторяет эту последовательность. Он предоставляет только различия:

- адрес компонента и его снимка;
- правила корневого metadata-item;
- дополнительные исходные компоненты;
- способ подготовки поискового контекста;
- обработчики служебных XML-данных;
- дополнение задания формы базовым представлением.

Профиль не составляет собственный список файловых маршрутов: структура YAML, XML-документов, внешних и игнорируемых файлов получается из общей топологии ресурсов.

Общие metadata-слои не знают имена `cf`, `cfe`, `ObjectBelonging`, `ExtendedConfigurationObject` и `BaseForm`. Эти сведения остаются в регистрации вида компонента, правилах конкретных metadata-item и зарегистрированных возможностях топологии.

## Независимые источники начальных данных

### Структура компонента

Отдельный механизм возвращает полную текущую структуру одного компонента:

- YAML-файлы;
- внешние файлы;
- роли;
- владельцев;
- применимые правила, возможности и маршруты из проекции топологии.

При холодном запуске механизм компилирует единую топологию из `rules.ts`, project spec и регистраций property-типов, затем сканирует каталог и классифицирует пути через её проекцию для компонента. В будущем MCP может возвращать актуальную структуру из кэша. Содержимое файлов в структуре не хранится.

Расширение получает структуру только выбранного `cfe` и отдельно структуру `cf`. Другие расширения не рассматриваются.

### Хэши файлов

Отдельный механизм возвращает полный набор путей и текущих хэшей одного компонента. Он не строит индексы и не разбирает YAML ради метаданных.

Полный набор хэшей является версией состояния компонента. При отсутствии кэша механизм читает файлы. Это чтение не обязано переиспользоваться механизмом индексов или исполнителем XML.

### Индексы компонента

Отдельный механизм возвращает:

- индекс метаданных;
- индекс зависимостей;
- привязку обоих индексов к полному набору исходных хэшей.

Источником могут быть:

- подтверждённые вклады компонентного снимка;
- актуальный кэш долгоживущего процесса;
- повторный разбор отсутствующих или устаревших YAML.

Повторное чтение одного YAML механизмом хэшей, механизмом индексов и исполнителем XML допустимо. Синхронизация не должна объединять эти механизмы ценой удержания разобранных YAML или подготовленного XML в памяти.

### Снимок конфигурации

Чтение снимка остаётся отдельным механизмом. Снимок предоставляет UUID, порядок, наличие XML-узлов, особые значения и сохранённые вклады проекта.

Каждый компонент имеет собственный снимок:

```text
.nkdk/components/cf/configuration-index.bin
.nkdk/components/cfe/<ИмяРасширения>/configuration-index.bin
```

Снимок `cf` и снимок выбранного `cfe` не объединяются.

## Согласованность состояния

После получения начальных данных координатор проверяет:

- структура содержит ровно тот состав файлов, для которого получены хэши;
- индексы привязаны к этому полному набору хэшей;
- компонент снимка совпадает с выбранным компонентом.

Исполнитель дополнительно вычисляет хэш каждого YAML непосредственно при чтении перед формированием XML. Значение должно совпасть с подтверждённым состоянием.

Для базовой формы расширения аналогично проверяется хэш YAML-формы `cf`.

При любом расхождении:

- операция прекращается;
- снимок компонента не обновляется;
- уже записанные XML не удаляются и не откатываются.

Это соответствует принятой нетранзакционной модели записи: готовые файлы записываются сразу, без накопления всего результата в памяти.

## Единый состав и исполнитель XML

Исполнитель получает явный состав синхронизации:

- `all` — все задания структуры компонента;
- `selected` — готовый список выбранных YAML и внешних файлов.

Исполнитель не определяет, почему файл попал в состав. Он:

1. преобразует состав в обычные XML-задания через XML-проекцию единой топологии;
2. распределяет задания между worker;
3. читает и проверяет один YAML;
4. строит окончательный XML по готовым индексам;
5. применяет дополнения профиля компонента;
6. сериализует и сразу записывает XML;
7. освобождает YAML и XML текущего задания;
8. копирует выбранные внешние файлы;
9. возвращает записанные пути и частичные вклады снимка.

Полная синхронизация передаёт `all`. Будущая частичная синхронизация передаст `selected`. Типы заданий, worker и построение XML при этом не меняются.

## Полная синхронизация `cf`

Профиль `cf` не имеет базового компонента.

Координатор:

1. получает структуру, снимок, хэши и индексы `cf`;
2. проверяет их согласованность;
3. формирует полный состав;
4. выполняет общий исполнитель XML;
5. переносит все внешние файлы;
6. полностью пересобирает снимок `cf` из текущего состояния и новых частичных вкладов.

Подготовленный XML всех заданий между этапами не хранится.

## Полная синхронизация `cfe`

### Предварительные проверки

Координатор получает структуру и снимок выбранного расширения, а также структуру и снимок `cf`.

Для `cf` он:

1. получает полный набор текущих хэшей;
2. требует точного совпадения состава и хэшей со снимком `cf`;
3. получает индексы `cf`;
4. проверяет их привязку к подтверждённым хэшам.

Любое изменение `cf`, ещё не отражённое в снимке основной конфигурации, блокирует полную синхронизацию расширения.

Для выбранного `cfe` координатор независимо получает текущие хэши и локальные индексы и проверяет их согласованность.

### Составной поиск и заимствование

Профиль расширения создаёт поисковый контекст:

```text
локальный индекс выбранного cfe
→ индекс cf
```

Другие расширения в контекст не включаются.

Заимствование объекта или дочернего элемента определяется совпадением логического адреса с элементом `cf`. Для каждого заимствованного элемента снимок `cf` обязан содержать UUID. Отсутствие UUID является ошибкой до запуска XML-заданий.

Профиль расширения добавляет:

- `ObjectBelonging`;
- `ExtendedConfigurationObject`;
- состояния из YAML-поля `Контроль`;
- состояния `Extended` и другие служебные значения из снимка расширения.

Общий исполнитель вызывает зарегистрированные обработчики, но не знает конкретные XML-имена этих данных.

### Значения по умолчанию заимствованных объектов

Заимствованный объект использует сокращённый набор XML-свойств. Поэтому обычный
`defaultValueXML`, предназначенный для полного объекта `cf` или собственного объекта
`cfe`, не должен автоматически добавлять отсутствующее свойство заимствованному
объекту.

Свойство, значение по умолчанию которого платформа требует и в заимствованном
представлении, объявляет его отдельно:

```ts
defaultValueXML: "Balance",
defaultValueAdoptedXML: "Balance",
```

Значения указываются независимо и могут различаться. При формировании
заимствованного объекта действуют правила:

- явное значение YAML имеет приоритет;
- при отсутствии значения YAML используется `defaultValueAdoptedXML`, если оно
  объявлено;
- обычный `defaultValueXML` без `defaultValueAdoptedXML` не создаёт свойство;
- собственный объект `cfe` и объект `cf` продолжают использовать
  `defaultValueXML`.

Например, управляемая форма объявляет оба значения:

```ts
defaultValueXML: "Managed",
defaultValueAdoptedXML: "Managed",
implicitValueYAML: "Managed",
```

Поэтому `FormType` восстанавливается и для собственной, и для заимствованной формы,
но не занимает место в компактном YAML.

`defaultValueAdoptedXML` управляет только формированием XML и само по себе не
исключает значение из YAML при импорте. Компактность YAML по-прежнему задаётся
отдельным `implicitValueYAML`. Признак заимствования предоставляет профиль
компонента; общая обработка свойств не проверяет `itemType` и не знает про каталоги
`cf` или `cfe`.

В первой реализации набор таких свойств определяется только по подтверждённым
примерам:

```text
cfe/all-extension
cfe/control
cfe/default
```

Для каждого свойства сопоставляются заимствованный объект, собственный объект `cfe`
и соответствующий объект `cf`. Значение добавляется в `rules.ts` только при
подтверждении XML-примерами. Полная таблица разрешённых и обязательных свойств
заимствованных объектов относится к отдельному исследованию валидации и не
выводится предположением из обычного `defaultValueXML`.

### Корневое описание расширения

Корневой `Configuration.xml` расширения содержит
`<ObjectBelonging>Adopted</ObjectBelonging>`, но не является заимствованным
прикладным объектом из `cf`. Он всегда формируется по отдельному
`MetadataConfigurationExtensionRules`.

Для корня расширения:

- свойства, которые платформа создаёт всегда, используют обычный
  `defaultValueXML`;
- необязательное свойство без YAML-значения не создаётся;
- `defaultValueAdoptedXML` не применяется;
- набор и порядок проверяются по корням `all-extension`, `control` и `default`.

Общая обработка свойств получает режим корневого правила из зарегистрированного
описания компонента и не определяет его по XML-значению `ObjectBelonging`.

### Преобразование `DataPath`

YAML использует локализованные имена стандартных реквизитов формы, а XML платформы —
внутренние имена. Например, путь проходит полный цикл:

```text
XML:  Объект.Code
YAML: Объект.Код
XML:  Объект.Code
```

Обратное преобразование использует два независимых источника:

- готовый индекс текущей формы определяет тип корневого реквизита `Объект`;
- индекс метаданных определяет стандартные реквизиты найденного типа.

Индекс формы нельзя заменять индексом, заново построенным из отсутствующих в
контексте реквизитов формы. Исполнитель всегда передаёт готовый индекс обрабатываемой
формы. Для `cf` он используется с индексом основной конфигурации, для `cfe` — с
составным представлением `cfe → cf`.

Общий преобразователь `DataPath` не содержит условий по виду компонента. Профиль
компонента отвечает только за предоставление соответствующего индекса метаданных.

### Формы

YAML расширения хранит полную итоговую форму. Вложенный исходный `BaseForm` не хранится ни в YAML, ни в снимке расширения.

Для собственной формы профиль не читает форму `cf`.

Потребность в базовой форме определяется не ролью и не путём YAML-файла, а
декларацией XML-задания `ClientApplicationForm`. Топология переносит эту декларацию
в задание независимо от способа хранения формы:

- дочерняя форма прикладного объекта хранится в отдельном `Форма.yaml`;
- общая форма хранится в свойстве `Форма` файла `Свойства.yaml`.

Если форма заимствована, worker лениво читает соответствующий YAML-источник `cf`.
Зарегистрированный обработчик формы извлекает значение либо из отдельного файла
формы, либо из свойства владельца. Если форма создана только в `cfe`, соответствующего
источника `cf` нет, базовая форма не читается и `BaseForm` не создаётся.

Для заимствованной формы во время выполнения её XML-задания:

1. читается полная итоговая YAML-форма расширения;
2. по сведениям заимствования находится соответствующая YAML-форма `cf`;
3. хэш формы `cf` проверяется по подтверждённому состоянию основной конфигурации;
4. зарегистрированное правило формы строит новое базовое представление в контексте итоговой формы расширения;
5. базовое представление встраивается в XML по договору формы;
6. данные обеих форм освобождаются после записи XML.

Это не копирование XML основной формы. Представление строится заново по правилам формы.

### Снимок расширения

После записи результата полностью пересобирается только снимок выбранного `cfe`. Снимок `cf` не изменяется.

Снимок расширения не содержит:

- данные основной конфигурации;
- составной поисковый контекст;
- `BaseForm`;
- данные других расширений.

## Совместимость с частичной синхронизацией

Будущая частичная синхронизация сначала получает готовые составы изменений по компонентам. Алгоритм вычисления составов находится вне общего исполнителя и вне текущей реализации.

Документация 1С допускает загрузку с `--partial` отдельного файла внешнего свойства, включая форму, без файла описания всего объекта. Поэтому сам исполнитель не должен автоматически расширять изменение формы до всего владельца. Правила для добавления, удаления и других структурных изменений будут спроектированы отдельно. См. [описание `load-config-from-files`](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_4._Startup_command_lines_of_system_components_and_description_of_additional_utilities/4.7._Running_Designer_in_agent_mode/4.7.6._config_group_commands/?language=en).

Частичная синхронизация проекта соблюдает один барьер:

1. если изменён `cf`, его XML формируется и загружается первым, затем обновляется снимок `cf`;
2. после этого все затронутые `cfe` используют новое подтверждённое состояние `cf`;
3. расширения не видят друг друга и могут обрабатываться независимо, в том числе параллельно;
4. ограничения одновременной загрузки в платформу относятся к внешнему исполнителю, а не к формированию XML.

Полная и частичная синхронизация различаются только:

- способом получения состава: `all` или `selected`;
- каталогом результата: постоянный или временный;
- завершением: полная замена снимка либо замена записей затронутых файлов после подтверждённой загрузки.

Профили `cf` и `cfe` одинаковы для обоих режимов.

## `ConfigDumpInfo.xml`

NKDK не создаёт, не обновляет и не хранит `ConfigDumpInfo.xml`.

Из проекта удаляются:

- генератор полной синхронизации;
- общий модуль `metadata/appliedObjects/configDumpInfo`;
- связанные типы, обновления снимка и тесты генерации.

Платформа создаёт этот файл самостоятельно, когда он нужен её операциям обновления XML-выгрузки.

## Ошибки

До запуска worker операция завершается ошибкой при:

- отсутствии или несовместимости снимка выбранного компонента;
- несогласованности структуры, хэшей и индексов;
- несинхронизированном `cf` для операции `cfe`;
- отсутствии UUID заимствованного элемента в снимке `cf`;
- конфликте целевых XML-путей.

Во время выполнения задания операция завершается ошибкой при:

- изменении YAML после получения подтверждённых хэшей;
- изменении нужной базовой формы `cf`;
- ошибке преобразования или записи XML.

Диагностика содержит компонент, путь YAML, целевой XML-путь и логический адрес, когда они известны.

## Проверки

### Модульные и договорные тесты

- Холодное чтение и кэшированные поставщики возвращают одинаковую структуру, хэши и индексы.
- Индексы, привязанные к другому набору хэшей, отклоняются до формирования XML.
- Изменение YAML после получения хэшей прерывает задание и не обновляет снимок.
- При одинаковом явном составе полный и частичный режимы формируют одинаковые XML.
- Профили `cf` и `cfe` используют один координатор и один исполнитель заданий.
- Оба профиля используют одну топологию ресурсов; отдельные таблицы маршрутов для расширения не создаются.
- Профиль `cfe` строго проверяет состояние `cf`.
- Договорный тест различает `defaultValueXML` полного объекта и
  `defaultValueAdoptedXML` заимствованного объекта.
- Корень расширения использует только свои подтверждённые `defaultValueXML` и не
  переходит в режим заимствованного прикладного объекта.
- Преобразователь `DataPath` использует переданные готовый индекс формы и индекс
  метаданных, не заменяя один другим.
- Собственная форма не вызывает чтение формы `cf`.
- Дочерняя и общая заимствованные формы лениво читают нужный YAML-источник `cf`,
  проверяют его хэш и строят новое базовое представление.
- Ошибка не удаляет уже записанные XML, но сохраняет прежний снимок.
- Полная синхронизация не создаёт `ConfigDumpInfo.xml`.

### Интеграционные проверки

- Существующие проверки полной синхронизации `cf` остаются зелёными.
- Полная синхронизация расширения проверяется на собственных и заимствованных объектах, дочерних элементах и формах.
- Критерий точного round-trip совпадает с основной конфигурацией: сформированный
  XML заменяет исходный XML-каталог, после чего `git diff` должен быть пустым.
  Применяется обычная нормализация Git, включая настроенный `eol=lf`; отдельное
  сохранение исходного вида переводов строк в снимке не требуется.
- Расхождения построенного `BaseForm` не исключаются из проверки автоматически.
  Сначала устанавливается их причина; допустимое отличие должно быть отдельно
  согласовано.
- Результат загружается платформой как выбранное расширение.
- После реализации выполняется приёмочная проверка на:
  - `/Users/nikita/git/round-trip/cf/all`;
  - всех расширениях из `/Users/nikita/git/round-trip/cfe`.

XML-фикстуры не изменяются и остаются источником истины.

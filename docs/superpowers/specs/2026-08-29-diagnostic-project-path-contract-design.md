# Договор путей диагностик проекта

## Контекст

NKDK использует два представления пути:

- `fileSystemPath` — абсолютный нативный путь для чтения и записи файлов;
- `projectPath` — переносимый путь внутри NKDK-проекта, относительный к его корню и использующий `/`.

Эти значения имеют разное назначение и не должны подменять друг друга.

## Проблема

Проверка владельцев DataPath строит абсолютный путь ожидаемого файла, например:

```text
C:\git\sed_nkdk\cf\Документ\Продажа\Свойства.yaml
```

Такой путь нужен `ownerCache` для доступа к YAML, но сейчас он же попадает в
`cross-file`-диагностику. Публичный договор Core требует вместо него путь проекта:

```text
cf/Документ/Продажа/Свойства.yaml
```

`@nkdk/mcp` намеренно отвергает абсолютные пути диагностик. Поэтому одна
некорректная диагностика прерывает выдачу всего результата `validate_project`
ошибкой `Core вернул путь диагностики вне NKDK-проекта`.

На исследованном проекте Core вернул 211 таких диагностик. Все они имели источник
`cross-file` и сообщение `Не найден владелец ...`.

## Решение

Диагностика должна получать корректный `projectPath` непосредственно в месте
создания. Генерировать абсолютный путь диагностики с последующим преобразованием
на выходе `validateProject` не требуется.

Для отсутствующего владельца используются два независимых значения:

```text
fileSystemPath:
C:\git\sed_nkdk\cf\Документ\Продажа\Свойства.yaml

diagnosticProjectPath:
cf/Документ/Продажа/Свойства.yaml
```

`fileSystemPath` остаётся внутренней деталью чтения YAML. Путь диагностики
формируется из уже известных `componentPath`, каталога типа владельца, имени
владельца и имени файла `Свойства.yaml`.

Для основной конфигурации результат имеет вид:

```text
cf/Документ/Продажа/Свойства.yaml
```

Для расширения результат имеет вид:

```text
cfe/дкз/Документ/Продажа/Свойства.yaml
```

Формирование пути использует общий договор `projectPath`: сегменты проверяются
через существующую границу путей проекта, а ручная конкатенация непроверенных
внешних значений не допускается.

## Ответственность компонентов

`projectStateDependencyValidation` располагает `componentPath` текущей проверки
и передаёт его при создании результата отсутствующего владельца.

`ownerCache` сохраняет абсолютный путь только там, где он требуется для доступа
к файлу или внутренних сведений найденного владельца. Конструктор диагностики не
выводит публичный путь из абсолютного пути файловой системы, а получает готовый
проверенный `projectPath`.

`validateProject` возвращает диагностики без дополнительного исправления путей.
Это сохраняет ленивую двоичную коллекцию и не добавляет материализацию или
повторное кодирование всех диагностик.

`@nkdk/mcp` не преобразует пути Core. Он сохраняет защитную проверку через
`parseProjectPath` и возвращает `core_error`, если Core нарушил договор. Благодаря
этому новая утечка абсолютного или внешнего пути обнаруживается сразу, а не
маскируется на публичной границе.

## Обработка ошибок

- существующий корректный `projectPath` возвращается без изменения;
- путь основной конфигурации начинается с `cf/`;
- путь расширения начинается с `cfe/<Имя>/`;
- абсолютный путь, URI, `.`/`..`, пустой сегмент и смешанный некорректный путь не
  могут стать путём диагностики;
- путь за пределами проекта не нормализуется и не скрывается — это нарушение
  внутреннего договора Core.

## Проверка

Тесты `ownerCache` разделяют путь для чтения владельца и путь создаваемой
диагностики.

Тесты `projectStateDependencyValidation` проверяют отсутствующего владельца:

- в `cf` — диагностика указывает `cf/<Тип>/<Имя>/Свойства.yaml`;
- в `cfe/дкз` — диагностика указывает
  `cfe/дкз/<Тип>/<Имя>/Свойства.yaml`;
- ни одна возвращённая диагностика не содержит абсолютный путь.

Интеграционный тест `validateProject` воспроизводит отсутствующего владельца и
проверяет публичный `projectPath`. Интеграционный тест MCP подтверждает, что
`validate_project` возвращает эту диагностику, а не `core_error`.

Отдельный защитный тест MCP продолжает передавать поддельную абсолютную
диагностику Core и ожидает отказ. Это закрепляет ответственность Core за
формирование пути.

## Вне границ изменения

- формат и содержание сообщений validation не меняются;
- существующая граница `parseProjectPath` не ослабляется;
- абсолютные пути внутренних файловых операций не заменяются на `projectPath`;
- общая двоичная коллекция диагностик не получает новый преобразующий слой.

# DataPath validation design

Дата: 2026-06-10

Статус: согласовано для планирования реализации.

## Контекст

Нужно заново реализовать валидацию `DataPath` внутри форм. Поддержка через граф
удаляется: графовые `DATA_PATH`-рёбра, form-local разрешение путей и связанные
тесты больше не являются целевой архитектурой.

Проверка должна жить в диагностическом слое формы: `validateForm` возвращает
`Diagnostic[]`. Импорт YAML и синхронизация XML сами по себе не должны падать
из-за ошибок `DataPath`.

Проверка формы всегда глобальная относительно YAML-проекта. Локальный режим
`validateForm({ formDir, formName })` без корня проекта и владельца формы не
имеет смысла и должен быть заменён новым контрактом.

Валидатор работает только с YAML-проектом. XML-фикстуры и XML round-trip в этой
задаче не меняются.

Вне форм `DataPath` пока не проверяется.

## Цели

- Проверять существование `DataPath` внутри `Форма.yaml`.
- Разрешать пути через реквизиты формы, колонки таблиц формы, стандартные
  реквизиты и прикладные объекты владельцев.
- Запрещать неразрешимые промежуточные типы: если дальнейший сегмент требует
  выбора одного типа, а текущий реквизит имеет несколько типов, не имеет типа
  или имеет произвольный тип, путь невалиден.
- Проверять конечный тип только там, где для свойства задана явная политика.
- Лениво читать соседние `Свойства.yaml` и кэшировать результат на один запуск
  валидации.
- Удалить зависимость проверки `DataPath` от графа.

## Не входит в первую версию

- `DataPath` вне форм.
- Полная поддержка шаблона `Items.*.CurrentData.*`. В первой версии такой путь
  даёт `warning`, потому что правило разрешения отложено.
- Полная проверка известных платформенных источников данных формы, например
  путей компоновщика настроек. В первой версии такие источники дают `warning`.
- Жёсткие политики конечных типов для всех элементов формы. Где политики нет,
  первая версия проверяет только разрешимость пути.

## Общая архитектура

Проверка проекта строится как единый конвейер без повторного парсинга YAML.

1. `validateProject` собирает список поддержанных YAML-файлов проекта.
2. Для каждого файла один раз вызывается `parseMetadataYaml(text)`. Результат
   хранится в `ProjectYamlCache` как `{ text, parsed }`.
3. Структурная проверка JSON Schema получает `parsed.data` и уже
   скомпилированную схему.
4. Если файл — `Форма.yaml`, из того же `parsed.data` импортируется модель
   формы через `importClientApplicationFormFromYAML`.
5. `validateFormDataPaths` обходит модель по `ClientApplicationFormRules` и
   правилам элементов; YAML AST из `parsed` используется для координат
   диагностик.
6. `OwnerMetadataCache` при необходимости читает внешний `Свойства.yaml` через
   тот же загрузчик файлов, поэтому повторный запрос берёт уже распарсенный файл
   из `ProjectYamlCache`.

Конвейер работает по принципу best effort: каждая стадия возвращает все ошибки,
которые можно получить без недостоверных предположений. Ошибки JSON Schema не
блокируют импорт модели формы и DataPath-проверку, если YAML распарсился и модель
формы удалось построить. Если модель формы импортировать нельзя, возвращается
ошибка импорта, а DataPath-проверка этой формы пропускается, потому что иначе
пришлось бы дублировать импорт формы отдельным неполным разбором YAML.
Для внешнего `Свойства.yaml` действует то же правило: структурные ошибки файла
владельца возвращаются как диагностики, но не блокируют переход по `DataPath`,
если модель владельца всё же удалось импортировать. Если импорт владельца
невозможен, резолвер возвращает ошибку владельца и останавливает только ту ветку
пути, которая от него зависит.

DataPath-проверка делится на три доменных слоя.

1. `FormDataPathIndex` строит локальную `Map` по модели формы:
   - реквизиты формы;
   - колонки реквизитов формы с типом `ValueTable` и `ValueTree`;
   - элементы формы и их `dataPath`, если они нужны для контекстной проверки;
   - известные платформенные источники данных формы, которые уже встречаются в
     формах, например `КомпоновщикНастроекКомпоновкиДанных.Settings.Filter`.

   Если внутри одной области поиска встречаются два одинаковых имени, это
   диагностическая ошибка неоднозначного имени. Валидатор не выбирает первый
   элемент молча.

2. `OwnerMetadataCache` лениво читает соседние `Свойства.yaml`:
   - ключ кэша — канонический владелец вроде `Catalog.Товары`;
   - значение — импортированная модель владельца или состояние `not-found`;
   - повторное обращение к тому же владельцу не читает файл заново;
   - поддерживается общий список верхнеуровневых объектов, для которых уже есть
     `Metadata*Rules`.

`validateItem` создаёт общий кэш на один запуск проверки объекта и передаёт его
во все формы этого объекта. `validateForm` получает корень проекта, директорию
формы, имя формы и владельца формы:

```ts
validateForm({
  projectDir,
  formDir,
  formName,
  owner: { dir: "Справочник", name: "Товары" },
  cache,
})
```

3. `DataPathResolver` идёт по сегментам пути:
   - первый сегмент ищется в локальном индексе формы;
   - при переходе через тип прикладного объекта резолвер обращается к
     `OwnerMetadataCache`;
   - каждый промежуточный сегмент обязан иметь ровно один следующий
     разрешимый тип;
   - конечный сегмент возвращается вместе с типом, чтобы политика свойства могла
     принять или отклонить путь.

## Правила путей

Первый сегмент пути всегда должен быть явно описанным источником формы. Имя
`Объект` не является служебным: это обычное имя реквизита формы. Если реквизита
`Объект` нет в `Реквизиты`, путь `Объект.*` невалиден, даже если форма лежит
внутри объекта-владельца.

Сегменты `DataPath` сравниваются с YAML-именами строго по регистру. Например,
если реквизит формы называется `Объект`, путь `объект.Товары` невалиден.

Стандартные реквизиты в YAML-пути пишутся только русскими именами: `Ссылка`,
`Наименование`, `Код`, `Номер`, `Дата` и т.п. Платформенные имена вроде `Ref`,
`Description`, `Number` в обычных YAML-путях считаются ошибкой. Набор
стандартных реквизитов берётся из существующих правил и карт имён проекта, а не
из отдельного ручного списка валидатора.

Стандартный реквизит может быть промежуточным, если его тип однозначно ведёт
дальше. Например, путь вида `Объект.Ссылка.Ссылка.Номер` проверяется по тем же
правилам: каждый промежуточный `Ссылка` должен иметь один следующий тип.

Промежуточный сегмент без типа или с произвольным типом не может вести дальше:
резолвер не знает, какие поля доступны на следующем шаге. Как конечный сегмент
такой реквизит допустим, если у свойства нет `allowedKinds`.

Специальные типы, которым нужна отдельная доменная семантика, например
`Характеристика.<ПланВидовХарактеристик>`, в первой версии не поддерживаются
как промежуточные. Как конечный тип без `allowedKinds` они допустимы; при
продолжении пути через такой тип выдаётся ошибка «тип не поддержан как
промежуточный в DataPath».

Ссылочные и объектные типы прикладных объектов поддерживаются одинаково:
`Справочник.Товары`, `СправочникОбъект.Товары`, `Документ.Заказ` и
`ДокументОбъект.Заказ` ведут к полям соответствующего объекта. Стандартный
реквизит `Ссылка` возвращает тот же прикладной объект как следующий источник
данных, поэтому цепочки `Ссылка.Ссылка.*` возможны. Скалярные стандартные
реквизиты вроде `Наименование`, `Код`, `Дата`, `Номер` завершают путь; идти
дальше через них нельзя.

Отсутствующий `DataPath` и пустая строка не диагностируются: это трактуется как
отсутствие привязки.

Если путь невозможно проверить из-за отсутствующего внешнего `Свойства.yaml`
или неподдержанного владельца, это `error`, а не пропуск проверки.
Если внешний `Свойства.yaml` найден, но не парсится или не импортируется по
правилам метаданных, `validateForm` возвращает диагностическую ошибку, а не
пробрасывает исключение наружу.

При переходе через прикладной объект валидатор ищет только поля данных объекта.
Формы, команды, макеты и другие неданные коллекции в `DataPath` первой версии не
участвуют.

Коллекции данных определяются из `rules.ts`: валидатор смотрит на свойства
`Metadata*Rules` и выбирает дочерние коллекции, которые описывают поля данных
объекта, например реквизиты, табличные части, измерения, ресурсы и аналогичные
коллекции регистров. Отдельная ручная карта по каждому виду объекта не
создаётся.

Для прикладных объектов уникальность имён между совместимыми коллекциями тоже
задаётся через `rules.ts` и проверяется общей структурной валидацией YAML, а не
специальной логикой `DataPath`. Например, у справочника нельзя иметь реквизит и
табличную часть с одним именем; у регистра нельзя иметь реквизит, измерение и
ресурс с одним именем. `DataPathResolver` использует те же rules-объявления как
области поиска и может рассчитывать, что такая неоднозначность уже превращена в
диагностику структурной проверки.
Для этого в rules добавляется декларативный механизм `uniqueNameScopes`: каждая
область перечисляет коллекции модели, внутри которых имена должны быть
уникальны между всеми элементами области. В первой версии такие области
добавляются только для объектов и коллекций, которые нужны `DataPathResolver`, а
не для всех возможных `Metadata*Rules`.
Если такая проверка нашла дубликат во внешнем владельце, переход по `DataPath`
через этого владельца останавливается как неоднозначный: резолвер не выбирает
одну из конфликтующих коллекций.
`uniqueNameScopes` сравнивает только непустые имена. Отсутствующие или пустые
имена диагностируются обычными правилами обязательности и импорта модели.
Сравнение имён в `uniqueNameScopes` тоже строгое по регистру.
Координата ошибки дубликата указывает на второй повторившийся элемент, чтобы ИИ
получал точную точку исправления.

## Контекст таблиц формы

Для дочерних элементов таблицы формы проверяется совпадение с источником данных
родительской таблицы.

Если у родительской таблицы:

```yaml
ПутьКДанным: Объект.Товары
```

то дочернее поле валидно только с путём, начинающимся на:

```yaml
ПутьКДанным: Объект.Товары.<Колонка>
```

Пути `Товары.<Колонка>` или `ДругаяТаблица.<Колонка>` для этого дочернего
элемента невалидны, даже если сами по себе такие пути можно было бы разрешить.

## Политики конечных типов

В первой версии политики задаются выборочно и декларативно через `rules.ts`.
Для свойства с `type: "DataPath"` правило может указывать настройки проверки
прямо на этом же объекте:

```ts
dataPath: {
  type: "DataPath",
  yaml: "ПутьКДанным",
  allowedKinds: ["boolean"],
  allowComposite: false,
}
```

`allowedKinds` задаёт допустимые категории конечного значения внутренними
именами проекта, например `"boolean"`, `"dateTime"`, `"Picture"`,
`"tableSource"`, а
`allowComposite` говорит, можно ли принимать составной конечный тип. Эти поля
имеют смысл только для `DataPath`-свойств; `defaultType` остаётся механизмом
Enterprise-выгрузки и не используется как источник правил валидации.
В первой версии `allowedKinds` и `allowComposite` не экспортируются в JSON
Schema: это внутренние настройки `rules.ts` для валидатора.

Если `allowedKinds` не указан, валидатор проверяет только существование пути и
корректность промежуточных переходов. В этом случае составной конечный тип
разрешён.

Если `allowedKinds` указан, а `allowComposite` не указан, значение по умолчанию
— `false`. Категория `"dateTime"` покрывает все варианты платформенной даты:
`Дата`, `Время` и `ДатаВремя`.

Если путь найден, но у конечного реквизита или колонки не указан тип, результат
зависит от правила свойства:

- без `allowedKinds` это валидно и не диагностируется;
- с `allowedKinds` это ошибка, потому что соответствие ограничению нельзя
  доказать.

Обязательные политики:

- `Table.dataPath` должен указывать на табличный источник. В первую версию
  входят `ValueTable`, `ValueTree`, `DynamicList` и табличные части прикладных
  объектов. Конечный тип не может быть составным.
- Дочерние поля таблицы должны указывать на существующую колонку источника
  родительской таблицы. Если для конкретного дочернего элемента есть политика
  типа, она применяется к типу этой колонки.
- `CheckBoxField.dataPath` и `TableCheckBoxField.dataPath` должны иметь
  конечный тип `boolean`.
- `PictureField.dataPath`, `TablePictureField.dataPath` и
  `Table.rowPictureDataPath` должны иметь конечный тип `Picture`.
- `CalendarField.dataPath` должен иметь конечный тип `dateTime`; составной
  конечный тип не допускается.

Для элементов без явной политики первая версия проверяет только, что путь
существует и корректно разрешается. Например, `InputField.dataPath` и
`LabelField.dataPath` допускают составной конечный тип. То же правило
применяется к остальным табличным `DataPath`-свойствам первой версии, включая
`TableInputField.dataPath`, `TableLabelField.dataPath`,
`ColumnGroup.headerDataPath` и дополнительные пути множественных значений
`InputField`, унаследованные `TableInputField`: они проверяются без ограничения
конечного типа, пока для них не задана отдельная политика через `rules.ts`.

Колонки табличных источников:

- для `ValueTable` и `ValueTree` колонки берутся только из
  `Реквизиты.<Имя>.Колонки` формы;
- если у `ValueTable`/`ValueTree` нет колонок, сам `Table.dataPath: <Имя>`
  валиден, но путь `<Имя>.<Колонка>` невалиден;
- для табличной части объекта колонки берутся из её явных реквизитов и
  стандартных реквизитов строки табличной части, например `НомерСтроки`;
- `DynamicList` как `Table.dataPath` валиден, но разрешение
  `ДинамическийСписок.<Поле>` до колонок первой версией откладывается и даёт
  предупреждение.
- известные платформенные источники данных формы пока не разворачиваются и не
  проверяются на табличность. Если путь точно совпадает с таким источником из
  `FormDataPathIndex`, валидатор выдаёт `warning`, а не `error`.
  Если путь начинается с такого источника и имеет продолжение, хвост пути тоже
  не проверяется, а результат остаётся `warning`.
  Для `Table.dataPath` это временно перекрывает политику
  `allowedKinds: ["tableSource"]`: валидатор предупреждает, что проверка такого
  источника пока не реализована, и не выдаёт ошибку типа.
  Начальный список таких источников берётся только из уже встреченных случаев в
  `/home/nikita/git/round-trip`.

## Диагностика

Результат — массив `Diagnostic`.

Координаты диагностики указывают на YAML-значение конкретного `DataPath`, если
его можно найти через YAML AST. Если точное место найти не удалось, используется
fallback `line: 1, col: 1`.

Ошибки:

- первый сегмент не найден;
- имя в локальном индексе формы или колонках неоднозначно;
- имя поля данных прикладного объекта дублируется между коллекциями, которые по
  `rules.ts` входят в одну область уникальности;
- промежуточный сегмент имеет составной тип;
- промежуточный сегмент не имеет типа или имеет произвольный тип;
- промежуточный сегмент имеет специальный неподдержанный тип;
- сегмент не найден в прикладном объекте или колонках;
- внешний `Свойства.yaml` владельца нужен, но не найден;
- внешний `Свойства.yaml` владельца не удалось прочитать, распарсить или
  импортировать;
- конечный тип не подходит под политику свойства;
- у конечного реквизита не указан тип, но свойство задаёт `allowedKinds`;
- дочерний элемент таблицы указывает не внутрь `dataPath` родительской таблицы;
- стандартный реквизит записан платформенным именем в обычном YAML-пути.

Предупреждения:

- путь соответствует отложенному шаблону `Items.*.CurrentData.*`.
- путь обращается к полю `DynamicList`, а колонки динамического списка ещё не
  поддержаны валидатором.
- путь указывает на известный платформенный источник данных формы, который
  первой версией валидатора не проверяется: «проверка источника пока не
  реализована».

## CLI

В CLI добавляется команда:

```bash
nkdk validate <yaml-dir>
nkdk validate <yaml-dir> --file <path>
```

Без `--file` проверяется весь YAML-проект. С `--file` проверяется один файл
проекта, но проверка всё равно остаётся глобальной: для формы валидатор знает
корень проекта и может лениво читать соседние `Свойства.yaml`.

Полная проверка проекта включает:

- структурную проверку всех поддержанных `Свойства.yaml` и `Форма.yaml` по JSON
  Schema;
- проверку всех `DataPath` внутри всех форм.

Неподдержанные YAML-файлы при обходе проекта пока игнорируются без
диагностики.

Семантика `--file`:

- если передан `Форма.yaml`, проверяются структурная схема файла и все
  `DataPath` внутри этой формы;
- если передан `Свойства.yaml` объекта, проверяется только сам файл свойств;
  формы этого объекта не обходятся;
- если передан неподдержанный YAML-файл, это ошибка CLI: файл не может быть
  проверен текущим валидатором;
- путь в `--file` обязан находиться внутри `<yaml-dir>`; внешний путь считается
  ошибкой CLI;
- если нужно проверить все формы объекта, запускается `validate <yaml-dir>` без
  `--file`.

Формат вывода:

```text
Справочник/Товары/Формы/Форма/Форма.yaml:12:18 error: ПутьКДанным "Объект.Контрагент.Наименование": промежуточный реквизит "Контрагент" имеет составной тип
summary: 1 error, 0 warning
```

Вывод один и рассчитан на использование из ИИ: каждая диагностика занимает одну
строку с фиксированным порядком полей, затем всегда идёт итоговая строка вида
`summary: 0 error, 0 warning`. Диагностики валидации пишутся в `stdout`, а ошибки
некорректного запуска команды — в `stderr`.
Служебные слова формата (`summary`, `error`, `warning`) пишутся ASCII, тексты
диагностик остаются на русском языке.
Перед выводом диагностики сортируются стабильно по `file`, затем `line`, затем
`column`.
`warning` выводятся в том же общем списке диагностик перед итоговой строкой и
сортируются по тем же правилам.
Строка диагностики содержит только место, важность и текст ошибки. Если ошибка
относится к конкретному YAML-полю, имя поля или YAML-путь включается в текст,
например `Реквизиты.Таблица.Тип: ожидается строка`.
Текст диагностики короткий и прямой, без советов по исправлению.

Код выхода:

- `1`, если есть хотя бы один `error`;
- `2`, если команда запущена некорректно: `<yaml-dir>` не существует, это не
  директория, `--file` указывает наружу проекта или передан неподдержанный файл;
- `0`, если диагностик нет или есть только `warning`.

## Тестирование

Нужны focused-тесты для `validateForm`:

- валидный путь к реквизиту формы;
- валидный путь к колонке `ValueTable` и `ValueTree`;
- валидный путь к табличной части владельца формы через ленивое чтение
  `Свойства.yaml`;
- повторное чтение одного владельца берётся из кэша;
- промежуточный составной тип даёт ошибку;
- `Table.dataPath` на булево даёт ошибку;
- `Table.dataPath` на `DynamicList` валиден, а `DynamicList.<Поле>` даёт
  предупреждение;
- `CalendarField.dataPath` на недату или составной тип даёт ошибку;
- `InputField` и `LabelField` допускают составной конечный тип;
- `TableInputField`, `TableLabelField`, `ColumnGroup.headerDataPath` и
  дополнительные `DataPath` множественных значений проверяются без ограничения
  конечного типа;
- дочерний элемент таблицы обязан начинаться с `dataPath` родительской таблицы;
- обычный путь с `Ref` вместо `Ссылка` даёт ошибку;
- `Items.*.CurrentData.*` даёт предупреждение.

Перед закрытием задачи нужен полный `pnpm test` из корня проекта.

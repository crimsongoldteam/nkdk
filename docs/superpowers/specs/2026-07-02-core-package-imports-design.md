# Пакетные импорты core без alias ~

## Контекст

В проекте `~/*` используется как короткий путь к `packages/core`. TypeScript понимает этот alias через `tsconfig`, Vitest отдельно дублирует его через `alias`, а прямые запуски через `tsx` и рабочие потоки Node не получают единый договор автоматически. Из-за этого один и тот же импорт может работать в тестах, но падать при validation или отдельном `tsx`-запуске.

Нужно убрать сам класс ошибок: не поддерживать `~` через набор локальных resolver-ов, а перейти на пакетные границы. Внешние пакеты должны зависеть от `@nakidka/core`, а не от внутренних папок `packages/core`.

## Цели

- Сделать `@nakidka/core` единственной внешней точкой входа для `packages/cli` и `packages/mcp`.
- Убрать все импорты `~/*` из `packages/core` за один проход, без долгого переходного периода.
- Удалить `paths["~/*"]` из `tsconfig` и `alias "~"` из конфигураций тестов после миграции.
- Сохранить архитектурные границы metadata-слоёв: общие слои не получают знания о конкретных applied-объектах.
- Добавить проверку, что прямой `tsx`-запуск и validation worker работают без alias-магии.

## Не цели

- Не открывать произвольные subpath exports вида `@nakidka/core/metadata/...`.
- Не менять XML/YAML-поведение, rules.ts и round-trip-логику.
- Не проводить содержательный рефакторинг metadata-модулей сверх замены импортов.
- Не менять публичный формат CLI/MCP-команд.

## Решение

Публичная граница `@nakidka/core` остаётся строгой: `packages/core/package.json` экспортирует только `"."`, а `packages/core/index.ts` явно перечисляет API, который нужен внешним потребителям. Если `cli` или `mcp` сейчас используют что-то неэкспортированное, нужный тип или функцию добавляем в `index.ts` осознанно.

Внутри `packages/core` alias `~` заменяется на относительные импорты. Это не делает внутренние модули публичными и не требует runtime resolver-а. При замене важно не маскировать архитектурные нарушения: если относительный путь показывает зависимость общего слоя от applied/form-слоя, такой импорт не переносится механически, а исправляется через уже существующий нейтральный договор, регистрацию или публичный helper подходящего слоя.

`packages/cli` и `packages/mcp` используют только `@nakidka/core` для core API. Импорты между собственными файлами этих пакетов остаются относительными.

## Поток миграции

1. Собрать список всех `~/*` импортов в `packages/core`, `packages/cli` и `packages/mcp`.
2. Проверить, что во внешних пакетах все обращения к core можно выразить через `@nakidka/core`; при необходимости расширить `packages/core/index.ts`.
3. Механически заменить `~/*` внутри `packages/core` на относительные пути с сохранением существующей структуры файлов.
4. Заменить оставшиеся `~/*` во внешних пакетах на `@nakidka/core` или локальные относительные импорты.
5. Удалить `compilerOptions.paths["~/*"]` из tsconfig-файлов и `alias "~"` из Vitest-конфигураций.
6. Добавить тест/скриптовую проверку, которая запускает через `tsx` код, импортирующий validation entrypoint и создающий worker.

## Проверка

- `rg 'from "~/|import\\("~/|alias:\\s*\\{|paths.*~' packages` не находит рабочих зависимостей от `~`.
- `pnpm --filter @nakidka/core type-check`.
- `pnpm test` из корня.
- Отдельный `tsx`-запуск validation entrypoint без `tsconfig-paths` и без Vite alias.
- Если ветка используется для benchmark YAML parser-ов, повторить benchmark после миграции, чтобы убедиться, что изменение импортов не исказило измерение.

## Риски

Главный риск — слишком широко раскрыть внутренности core через `index.ts`. Поэтому публичный API расширяется только под реальные внешние потребители, а не как зеркало всех внутренних модулей.

Второй риск — большая механическая правка может спрятать архитектурные нарушения. Для этого после замены нужно отдельно пройти импорты из `metadata/orchestration`, `metadata/validation` и `metadata/project`: они не должны начать зависеть от конкретных applied/form/commonObjects реализаций вопреки AGENTS.md.

Третий риск — объём изменения. Его снижают автоматическая проверка отсутствия `~`, type-check и полный `pnpm test`; частичных переходных alias после реализации оставаться не должно.

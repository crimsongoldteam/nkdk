# Полная синхронизация Проекта в XML

## Цель

Заменить текущую полную YAML → XML синхронизацию, зависящую от каталога XML-reference, на двухпроходную операцию с worker. Операция должна сформировать полный XML-проект из Проекта, используя файл индекса конфигурации как единственный источник идентификаторов и данных восстановления XML.

Результат не должен зависеть от числа worker. Полные metadata-модели, разобранные YAML и полный файл индекса конфигурации не должны копироваться между главным процессом и worker.

## Границы

В эту итерацию входит только операция `Полная синхронизация в XML`.

Отдельная операция `Синхронизация изменившихся файлов в XML` остаётся частью архитектуры, но не реализуется по этой спецификации. Она должна переиспользовать чтение Проекта, задания, worker и доступ к индексам; отличаться будет отбор заданий по хэшам.

В эту итерацию не входят:

- подключение к 1С;
- передача сформированного XML в Конфигурацию;
- проверка версии Конфигурации;
- полноценная validation Проекта;
- автоматическая очистка целевого XML-каталога;
- изменение формата файла индекса конфигурации версии 1.0;
- реализация синхронизации только изменившихся файлов.

До появления передачи в 1С успешное формирование полного XML-проекта считается успешным завершением синхронизации и точкой обновления файла индекса конфигурации. После реализации передачи эта точка должна быть перенесена за подтверждение успешной операции со стороны 1С.

## Входы и результат

Операция получает:

- корень Проекта;
- целевой каталог XML-результата;
- идентификатор привязки файла индекса конфигурации, по умолчанию `default`;
- контекст преобразования;
- необязательное число worker.

Каталог XML-reference не является входом операции. Параметр `referenceDir` не входит в новый договор полной синхронизации.

Перед запуском worker должны выполняться условия:

- Проект доступен для чтения;
- файл индекса выбранной привязки существует, структурно корректен и совместим с текущей версией NKDK;
- целевой XML-каталог отсутствует либо пуст.

Если целевой каталог отсутствует, главный процесс создаёт его. Если каталог непустой, операция завершается ошибкой без удаления файлов.

Успешный результат содержит:

- полный XML-проект;
- число успешно обработанных заданий;
- предупреждения;
- путь атомарно обновлённого файла индекса конфигурации.

Неуспешный результат содержит диагностики. Если второй проход уже начался, целевой каталог может содержать неполный XML-результат.

## Логические операции

Архитектура различает две самостоятельные операции:

- `Полная синхронизация в XML` выбирает все YAML и внешние файлы, описанные правилами структуры Проекта;
- `Синхронизация изменившихся файлов в XML` в будущем выберет задания по сравнению текущих хэшей с файлом индекса конфигурации.

Полная синхронизация вычисляет хэши для нового файла индекса, но не использует их для отбора заданий. Отсутствующие в текущем Проекте объекты и файлы не попадают в XML-результат и в новое содержимое индекса.

## Компоненты

### Координатор полной синхронизации

Главный процесс:

- проверяет входы;
- находит файлы Проекта;
- строит и распределяет задания;
- создаёт общий снимок файла индекса конфигурации;
- управляет двумя проходами worker;
- обобщает глобальный индекс метаданных и результаты worker;
- копирует внешние файлы;
- формирует `ConfigDumpInfo.xml`;
- последним атомарно обновляет файл индекса конфигурации.

Координатор не разбирает YAML и не строит metadata-модели.

### Описание задания синхронизации

Одно задание привязано ровно к одному исходному YAML и описывает все XML-файлы, которые формируются из этого YAML. Задание содержит только пути, роль YAML, владельца, правила и описание выходных XML-путей; разобранные YAML-данные в него не входят.

Задания строятся до чтения YAML по правилам структуры Проекта. Это симметрично импорту: импорт объединяет несколько исходных XML вокруг одного целевого YAML, а синхронизация объединяет несколько целевых XML вокруг одного исходного YAML.

Другие YAML во втором проходе не читаются. Сведения о владельцах, составе дочерних объектов, ссылках и `ПутьКДанным`, необходимые заданию, извлекаются в первом проходе и доступны через глобальный индекс метаданных.

Внешние файлы, которые переносятся без построения metadata-модели, не назначаются worker. Главный процесс формирует для них отдельный список копирования.

### Worker

Каждый worker является долгоживущим участником одной операции и хранит только назначенные ему YAML-данные и временные модели.

Первый проход worker:

- читает исходные байты назначенных YAML;
- вычисляет хэш по этим же байтам;
- разбирает YAML;
- сохраняет разобранные данные локально;
- извлекает компактные сведения для глобального индекса метаданных;
- возвращает только диагностики, хэши и компактные сведения.

Второй проход worker:

- получает описание глобального индекса метаданных и общего снимка файла индекса конфигурации;
- строит metadata-модель каждого назначенного YAML;
- строит и сериализует все XML-файлы задания;
- записывает XML непосредственно в целевой каталог;
- собирает данные фактически использованного XML в фрагмент нового файла индекса конфигурации;
- освобождает metadata-модель после завершения задания;
- возвращает диагностики, предупреждения, список записанных XML-путей и один передаваемый буфер фрагментов индекса.

### Глобальный индекс метаданных

Глобальный индекс метаданных содержит только компактные сведения, необходимые другому заданию при YAML → XML преобразовании. В него входят сведения о владельцах `ПутьКДанным`, составе объектов и другие факты, объявленные общими договорами и правилами.

Полные YAML-данные и metadata-модели в глобальный индекс не входят. Главный процесс объединяет worker-факты, создаёт один неизменяемый двоичный снимок в общей памяти и передаёт worker только его описание.

### Общий снимок файла индекса конфигурации

Главный процесс один раз читает и полностью проверяет бинарный файл индекса конфигурации версии 1.0. Проверенное содержимое представляется одним неизменяемым снимком в общей памяти.

Worker получают доступ к идентификаторам и данным восстановления XML по `logicalAddress`. Каждый worker может держать небольшой локальный кэш найденных записей, но не создаёт полную копию строк и секций индекса.

Снимок заменяет все чтения XML-reference. Построение XML не должно читать существующий XML-результат, старую XML-выгрузку или другой каталог reference.

### Сборщик нового индекса

Главный процесс формирует единый контекст генерации из стабильного отпечатка исходного индекса и целевого поколения индекса. Зарегистрированные генераторы используют этот контекст вместе с `logicalAddress` и видом значения для новых UUID, XML-идентификаторов и создаваемых версий общих XML-файлов.

При YAML → XML преобразовании правила одновременно:

- читают существующие идентификаторы и данные восстановления из общего снимка;
- создают отсутствующие идентификаторы для новых объектов и вложенных элементов;
- фиксируют фактически использованные идентификаторы, порядок полей и другие данные восстановления XML в локальном сборщике задания.

Worker объединяет фрагменты своих заданий в один компактный передаваемый буфер. Главный процесс проверяет и объединяет worker-буферы без повторного чтения сформированного XML.

Полная синхронизация строит индекс заново из фрагментов текущего Проекта. Старые записи, которые не были сформированы текущими заданиями, в новый индекс не переносятся.

### Перенос внешних файлов

После успешного завершения всех worker главный процесс:

- проверяет списки записанных worker XML-файлов;
- проверяет отсутствие конфликтов с целевыми путями внешних файлов;
- копирует внешние файлы с ограниченным параллелизмом;
- вычисляет хэш каждого файла по тем же байтам, которые записывает в XML-результат.

Worker не читают и не копируют переносимые без преобразования внешние файлы.

### Общие XML-файлы

Задание `Конфигурация.yaml` формирует `Configuration.xml`. Состав дочерних объектов оно получает из глобального индекса метаданных.

`ConfigDumpInfo.xml` формирует главный процесс после успешного завершения worker и копирования внешних файлов. Для него используются объединённые сведения обо всех созданных XML-файлах и идентификаторах.

## Последовательность полной синхронизации

1. Главный процесс проверяет Проект, наличие файла индекса конфигурации и целевой XML-каталог.
2. Главный процесс находит YAML и внешние файлы, формирует задания по одному исходному YAML и статически распределяет их между worker.
3. Главный процесс один раз читает и полностью проверяет файл индекса конфигурации, затем создаёт его неизменяемое представление в общей памяти.
4. Worker выполняют первый проход: читают и разбирают YAML, вычисляют хэши по прочитанным байтам, сохраняют данные YAML и возвращают компактные сведения о метаданных.
5. Главный процесс объединяет сведения в глобальный индекс метаданных и передаёт worker описание его общей памяти.
6. Worker выполняют второй проход: строят metadata-модели и XML, пишут XML непосредственно в целевой каталог и собирают фрагменты нового индекса. Задание `Конфигурация.yaml` формирует `Configuration.xml`.
7. Главный процесс проверяет списки записанных XML-файлов и объединяет фрагменты нового индекса.
8. Главный процесс асинхронно копирует внешние файлы единым списком и вычисляет их хэши по копируемым байтам.
9. Главный процесс формирует `ConfigDumpInfo.xml`.
10. Главный процесс объединяет хэши YAML и внешних файлов с данными сформированного XML, увеличивает `indexGeneration` на единицу и атомарно записывает новый файл индекса конфигурации.

## Обновление файла индекса конфигурации

Новый индекс должен содержать:

- текущую версию NKDK как `producerVersion`;
- тот же `baseId`;
- `indexGeneration`, увеличенный на единицу;
- прежние `baseFingerprint` и `configurationVersion` без изменения;
- хэши всех описанных правилами YAML и внешних файлов текущего Проекта;
- идентификаторы и данные восстановления, фактически использованные при формировании полного XML-результата.

Пустые `baseFingerprint` и `configurationVersion`, созданные импортом из готовой XML-выгрузки, разрешены для локального формирования XML. Они по-прежнему не подтверждают возможность применения результата к 1С.

Индекс записывается только после успешного завершения всех worker, копирования всех внешних файлов и формирования общих XML-файлов. Запись выполняется атомарно по спецификации формата 1.0. Существующий индекс не изменяется при любой предшествующей ошибке.

## Параллелизм и владение данными

- По умолчанию используется та же степень параллелизма, что и в новом импорте: не более четырёх worker с учётом доступных процессоров.
- Задания статически распределяются по кругу, поэтому одно задание всегда выполняет один worker.
- Один исходный YAML принадлежит ровно одному заданию.
- Один создаваемый XML-путь принадлежит ровно одному заданию либо главному процессу.
- Главный процесс проверяет конфликты объявленных выходных путей до второго прохода и фактически записанных путей после него.
- Разобранные YAML и metadata-модели не покидают worker.
- Общий снимок файла индекса конфигурации и глобальный индекс метаданных существуют в одном экземпляре в общей памяти.
- Новые идентификаторы и версии формируются детерминированно зарегистрированными генераторами из контекста операции, `logicalAddress` и вида значения. Повтор операции с теми же входами, порядок выполнения заданий и число worker не влияют на результат.
- Изменение числа worker не меняет XML-результат и содержимое файла индекса конфигурации. Конфликт одинаковых `logicalAddress` является ошибкой.

## Ошибки

Ошибки проверки Проекта, файла индекса или целевого каталога завершают операцию до запуска второго прохода и до записи XML.

В первом проходе worker продолжает обработку остальных назначенных заданий и возвращает все обнаруженные ошибки. При наличии хотя бы одной ошибки второй проход не начинается.

Во втором проходе ошибка одного задания не отменяет уже записанные XML-файлы и не мешает worker собрать диагностики остальных назначенных заданий. После завершения worker главный процесс не начинает копирование внешних файлов, формирование `ConfigDumpInfo.xml` и обновление индекса.

Аварийное завершение worker останавливает операцию без автоматического перезапуска и повторения заданий.

Ошибка копирования внешнего файла, формирования общего XML-файла или записи нового индекса завершает операцию. Частичный XML-результат сохраняется для диагностики. Операция ничего не удаляет и не откатывает; существующий индекс остаётся неизменным, если его атомарная замена не завершилась.

Предупреждение не блокирует продолжение операции, если правило смогло сформировать допустимый XML. Ошибка построения модели или XML всегда блокирует успешное завершение.

Повторный запуск после ошибки требует отсутствующего либо очищенного пользователем целевого XML-каталога.

## Тестирование

### Модульные тесты

- проверка отсутствующего, пустого и непустого целевого каталога;
- построение одного задания на один исходный YAML и все объявленные выходные XML-пути;
- обнаружение конфликтов выходных путей;
- полный снимок индекса существует в одном экземпляре и доступен нескольким worker;
- существующие идентификаторы читаются из индекса, новые создаются и попадают в новый фрагмент;
- новые идентификаторы не зависят от порядка заданий и числа worker;
- старые записи удалённого объекта не попадают в новый индекс;
- хэш YAML вычисляется по разобранным байтам;
- хэш внешнего файла вычисляется по копируемым байтам;
- `indexGeneration` увеличивается только при успешной операции.

### Тесты границы worker

- YAML читается только назначенным worker;
- разобранные YAML и metadata-модели не возвращаются главному процессу;
- второй проход не начинается при ошибках первого;
- задание не читает YAML другого задания во втором проходе;
- один и четыре worker формируют одинаковый XML и одинаковый индекс для Проекта без новых идентификаторов;
- авария worker останавливает операцию без перезапуска.

### Интеграционные тесты

- import небольшой XML-фикстуры создаёт Проект и индекс, после чего полная синхронизация без XML-reference восстанавливает ожидаемый XML;
- форма с `ПутьКДанным` использует сведения владельца из глобального индекса метаданных;
- `Конфигурация.yaml` формирует `Configuration.xml`, а главный процесс — `ConfigDumpInfo.xml`;
- YAML, создающий несколько XML-файлов, обрабатывается одним заданием;
- внешние файлы копируются главным процессом после успешного завершения worker;
- добавленный объект получает идентификаторы, которые сохраняются в обновлённом индексе;
- удалённый объект отсутствует в XML-результате и новом индексе;
- ошибка второго прохода оставляет частичный XML и прежний индекс;
- ошибка копирования внешнего файла оставляет прежний индекс;
- непустой целевой каталог не изменяется.

Тесты используют небольшие временные Проекты и не должны зависеть от измерения времени. Отдельное профилирование ERP выполняется после реализации вне обычных тестов. Перед завершением реализации выполняется `pnpm test`.

## Задел для синхронизации изменившихся файлов

Будущая операция должна переиспользовать:

- обнаружение файлов Проекта;
- договор задания;
- первый проход и глобальный индекс метаданных;
- общий снимок файла индекса конфигурации;
- второй проход worker;
- сборщик фрагментов индекса;
- копирование внешних файлов и обработку ошибок.

Она добавит сравнение хэшей и отбор затронутых заданий. Способ сохранения неизменённых записей индекса и удаления устаревших записей изменённого задания требует отдельной спецификации. Формат файла индекса версии 1.0 в рамках полной синхронизации не изменяется.

## Согласованность с архитектурой

- Полная синхронизация использует шаги `Чтение проекта`, `Подготовка синхронизации конфигурации`, `Построение модели`, `Вычисление хэшей файлов проекта`, `Формирование данных файла индекса конфигурации` и `Запись файла индекса конфигурации`.
- Шаги `Проверка по схеме` и `Проверка зависимостей` не выполняются: полноценная validation остаётся отдельной операцией.
- Шаги `Подключение к 1С`, `Проверка соответствия версии конфигурации` и `Применение изменений в 1С` не выполняются.
- Общие metadata-слои не содержат условий по конкретным `itemType`, XML-каталогам или именам объектов; задания и межфайловые сведения определяются правилами и регистрациями.

# Универсальный пул worker метаданных

## Контекст

Сейчас validation создаёт собственный пул перед Б1–Б4 и уничтожает его сразу после обработки файлов. Import и полная sync используют отдельные worker и отдельные протоколы. Из-за этого следующая операция повторно запускает потоки, загружает модули и создаёт кэши схем, а общие действия над уже разобранным YAML реализуются в нескольких местах.

Контрольный замер на временной копии `/Users/nikita/git/nkdk-yaml/cf` с четырьмя worker показал:

- validation с новым пулом над прогретым состоянием — 10,92 с;
- следующая validation с тем же пулом — 9,37 с;
- создание и подготовка четырёх worker до готовности — 1,21 с;
- повторная инициализация готового пула — менее 0,01 мс.

Пул выгодно связать с жизнью MCP, а не отдельной операции. При этом единый пул не должен превращаться в один большой обработчик: операции имеют разные входы и временное состояние, но используют одинаковые схемы, правила, общие буферы и блоки обработки YAML.

## Цели

- Использовать один лениво создаваемый пул для import, validation, полной sync, переименования и поиска ссылок.
- Сохранять worker до завершения MCP и переиспользовать прогретые схемы и правила.
- Хранить в worker ссылки на актуальные общие буферы состояния проекта без копирования данных.
- Реализовать общие действия над YAML один раз и вызывать их из обработчиков разных операций.
- Проверять импортированный YAML как уже готовый объект без повторного чтения и разбора записанного файла.
- Ограничивать память числом worker, размером пачки и явно сохраняемыми отложенными YAML.
- Сохранить раннюю запись готовых YAML во время import.
- Доводить import до успешного ответа MCP и профилировать все этапы завершения операции.

## Не входит в задачу

- Новый договор параллельного выполнения нескольких операций над проектом.
- Частичная sync; архитектура только не препятствует её последующему добавлению.
- Изменение двоичного формата состояния проекта `0.4.2`.
- Изменение правил validation и состава diagnostics.
- Поколения снимков, журнал изменений и совместимость с не выпущенными прежними реализациями состояния.
- Mutation testing.

## Владение и жизненный цикл

MCP владеет одним `MetadataWorkerPoolHandle`. Он создаёт универсальный пул при первой операции, которой нужен worker, и закрывает его во время общего завершения MCP. Завершение отдельной операции пул не закрывает.

Пул содержит отдельную однопоточную линию Piscina на каждый логический worker. Требуемая параллельность задаёт число используемых линий:

- если линий недостаточно, пул лениво добавляет их;
- после уменьшения параллельности лишние линии остаются прогретыми, но не получают задания;
- линии удаляются только при завершении MCP либо после аварии конкретного worker.

Таким образом, явный параметр `concurrency` import и полной sync сохраняет прежний смысл. Пул может вырасти до наибольшего запрошенного значения за время MCP, но не пересоздаёт уже готовые worker.

## Устройство worker

У worker одна точка входа и отдельные обработчики команд:

- актуализация и validation;
- первый и второй проходы import;
- полная sync;
- переименование;
- поиск ссылок;
- установка и очистка состояния проекта;
- завершение накопленного двоичного фрагмента.

Точка входа только проверяет вид команды и передаёт её соответствующему обработчику. Знания import, sync или переименования не попадают в общий обработчик validation.

Каждый worker содержит общий контекст двух видов.

Постоянный контекст живёт между операциями:

- кэш JSON Schema;
- снимок правил validation и скомпилированные нейтральные правила проекта;
- шаблоны компонентов validation;
- ссылки только для чтения на текущие `SharedArrayBuffer` состояния проекта;
- подготовленные типизированные представления поисковых таблиц.

Временный контекст принадлежит одной операции:

- накопитель двоичного фрагмента;
- счётчики и агрегированный профиль;
- текущая пачка;
- отложенные YAML конкретного import;
- открытые представления и промежуточные результаты обработчика.

Временный контекст очищается после успеха, ошибки или отмены. После передачи двоичного фрагмента через `Piscina.move()` worker забывает переданные `ArrayBuffer`. Постоянный контекст сохраняется, пока жив worker.

## Общие модули

Обработчики операций используют одни и те же модули, а не копии логики:

1. Локальная validation принимает уже разобранный YAML, индекс расположений, описание файла, контекст и кэш схем. Она не читает файл и не разбирает YAML повторно.
2. Извлечение сведений индекса принимает тот же объект YAML и добавляет нормализованные сведения в переданный накопитель.
3. Двоичный накопитель живёт в worker на протяжении фазы и принимает результаты нескольких ограниченных пачек.
4. Установка состояния открывает типизированные представления над переданными общими буферами без JSON и без копирования.
5. Диспетчер пачек выдаёт следующую пачку линии только после завершения предыдущей и обеспечивает обратное давление.
6. Профиль накапливает только агрегаты worker и возвращает одну сводку на фазу.

Различается только получение объекта:

- validation читает байты YAML, вычисляет хэш и разбирает изменившийся файл;
- import получает готовый YAML из преобразования XML;
- sync читает проверенный YAML для формирования XML;
- переименование и поиск ссылок читают типизированные сведения актуального индекса.

## Установка состояния проекта

Главный процесс остаётся единственным владельцем построения и публикации состояния. Worker никогда не изменяют общие буферы на месте.

После загрузки либо публикации состояния главный процесс отправляет каждой существующей линии команду установки. Команда заменяет ссылки worker на весь согласованный набор общих буферов и открывает новые типизированные представления. MCP ждёт подтверждение всех существующих worker до запуска действия, читающего новый индекс.

Если пул ещё не создан, владелец сохраняет ссылки в главном процессе. Новая линия при ленивом создании сначала получает схемы, правила и последние опубликованные буферы и только после этого считается готовой.

При сбросе состояния главный процесс удаляет дисковый файл, очищает опубликованные буферы и отправляет существующим worker команду очистки. Версии и поколения для этого протокола не вводятся.

## Validation

1. Главный процесс обнаруживает пути и выдаёт ограниченные пачки.
2. Worker читает файл и вычисляет хэш из тех же байтов.
3. Байты неизменённого файла освобождаются сразу.
4. Изменённый YAML разбирается один раз.
5. Общие модули выполняют локальную validation и извлекают сведения индекса из одного объекта.
6. Результаты добавляются в накопитель этой линии; отдельный фрагмент на каждую пачку не создаётся.
7. После окончания потока каждая линия передаёт не более одного логического фрагмента.
8. Главный процесс строит кандидат общих буферов и выполняет по нему полную dependency validation всего проекта.
9. После успешной технической проверки главный процесс публикует кандидат, устанавливает его во всех worker и планирует сохранение состояния.

Пул после Б1–Б4 не закрывается. Следующая validation использует готовые потоки, схемы, правила и установленные буферы.

## Import

Import использует те же локальную validation, извлечение сведений и двоичный накопитель, но получает YAML из XML.

Первый проход обрабатывается ограниченными пачками; начальное значение размера пачки — 256 заданий. Размер подтверждается профилем на `cf/all` и `cf/doc`, после чего при необходимости сравниваются 128 и 512.

Для каждого готового YAML один worker последовательно:

1. формирует объект YAML из XML;
2. собирает сведения компонентного снимка и основного индекса;
3. если отложенное уточнение не требуется, сериализует объект один раз и сразу записывает файл;
4. вычисляет хэш по записываемым байтам;
5. выполняет общую локальную validation непосредственно над тем же объектом;
6. добавляет окончательные сведения в накопитель;
7. освобождает объект.

`ownerFacts`, `validationContribution`, разобранный YAML и отдельный результат каждого задания главному процессу не передаются. Те же сведения уже находятся в двоичном фрагменте. Главный процесс не удерживает массив результатов всех заданий.

Если YAML требует общего индекса, worker сохраняет только необходимый отложенный объект у себя. После завершения первого прохода линии передают основные фрагменты, главный процесс строит рабочий индекс и устанавливает его во всех worker. Во втором проходе каждый worker уточняет только принадлежащие ему отложенные YAML, записывает и проверяет тот же объект, добавляет окончательные сведения в новый накопитель и сразу освобождает объект.

После второго прохода главный процесс:

1. применяет окончательные фрагменты;
2. передаёт внешние файлы и добавляет их хэши;
3. строит окончательное состояние;
4. выполняет полную dependency validation;
5. записывает компонентный снимок;
6. публикует общие буферы и устанавливает их в worker;
7. планирует атомарное сохранение на диск;
8. возвращает результат MCP.

Каждый из этих этапов имеет отдельное агрегированное время профиля.

## Sync, переименование и поиск ссылок

Полная sync, переименование и поиск ссылок сначала выполняют общую актуализацию Б1–Б6 через тот же универсальный пул. После публикации worker уже содержат ссылки на актуальные общие буферы.

- Полная sync передаёт пачки проверенных YAML обработчику формирования XML. Частичная sync пока отсутствует.
- Поиск ссылок выполняет типизированные запросы к установленному индексу.
- Переименование выполняет актуализацию до построения плана, применяет разрешённый план и повторяет актуализацию после записи.

По умолчанию error-diagnostics блокируют продолжение этих операций. `ignoreValidationErrors: true` разрешает продолжить, но не пропускает актуализацию, не скрывает diagnostics и не разрешает технические ошибки.

## Ошибки и отмена

- Локальные YAML- и schema-diagnostics являются содержательным результатом и сохраняются вместе с хэшем файла.
- Dependency diagnostics вычисляются полностью и не сохраняются.
- Техническая ошибка, отмена, повреждённый фрагмент или ошибка сборки не публикуют кандидат состояния.
- Незавершённые накопители и отложенные YAML текущей операции очищаются во всех затронутых worker.
- Уже записанные ранние YAML import не откатываются, но незавершённое состояние проекта не публикуется.
- При аварии отдельной линии пул удаляет её постоянный и временный контекст. Перед следующим заданием новая линия получает схемы, правила и последние опубликованные буферы.
- Исправные линии и их постоянные кэши после ошибки операции сохраняются.

## Проверка решения

### Договорные тесты

Тесты подтверждают наблюдаемое поведение:

- пул создаётся только при первой операции с worker;
- одна линия используется последовательными операциями и закрывается только вместе с MCP;
- увеличение `concurrency` добавляет недостающие линии, а уменьшение использует подмножество существующих;
- новая линия получает последние схемы, правила и общие буферы до первого задания;
- публикация и сброс состояния заменяют либо очищают ссылки во всех существующих worker;
- данные `SharedArrayBuffer` не копируются и доступны только для чтения;
- временное состояние очищается после успеха, ошибки и отмены;
- аварийно завершившаяся линия полностью инициализируется заново;
- import и validation вызывают один модуль локальной validation и один формат двоичного накопителя;
- готовый импортированный YAML не читается и не разбирается повторно;
- ранняя запись выполняется до построения рабочего индекса;
- главный процесс не получает дублирующие `ownerFacts` и `validationContribution` и не удерживает результаты всех заданий;
- worker передаёт не более одного логического фрагмента на фазу;
- переименование выполняет актуализацию до и после записи;
- `ignoreValidationErrors` разрешает продолжение только после полной актуализации.

Unit-тесты используют поддельные линии worker и поддельную границу состояния. Желательное время одного теста — до 10 мс, предельное — 50 мс. Небольшие интеграционные тесты с настоящими worker должны проверять только создание, повторное использование и закрытие пула и также оставаться быстрыми.

### Профиль

- Validation измеряется compiled standalone на временной копии `/Users/nikita/git/nkdk-yaml` без изменения пользовательского `.nkdk`.
- Профиль отдельно показывает создание потоков до готовности, подготовку схем и повторное использование готового пула.
- Import сначала измеряется на `/Users/nikita/git/round-trip-compact/cf/all`, затем на `cf/doc`; итоговый прогон выполняется на `cf/erp` четырьмя worker.
- Профиль import содержит агрегаты по worker и отдельные времена первого прохода, рабочего индекса, второго прохода, внешних файлов, окончательной сборки, dependency validation, публикации, сохранения и формирования ответа MCP.
- Подробный профиль не создаёт строку на каждый объект и не удерживает журнал, пропорциональный числу файлов.

Критерий производительности — успешный ответ MCP и заметное ускорение относительно текущего профиля. Дополнительно повторная validation с сохранённым пулом не должна включать примерно 1,21 с повторного запуска четырёх worker, обнаруженного контрольным замером.

### Итоговые проверки

- Mutation testing не запускается.
- `jscpd` не должен обнаруживать новые дубли изменённого кода.
- Перед рецензией задачи один раз выполняются `pnpm type-check` и полный `pnpm test`.

## Критерии готовности

Решение готово, когда:

- один универсальный пул обслуживает все пять операций;
- пул лениво создаётся и живёт до завершения MCP;
- worker сохраняют схемы, правила и ссылки на актуальные общие буферы между операциями;
- код общих блоков import и validation не дублируется;
- import проверяет готовый объект YAML без повторного чтения или разбора;
- ранняя запись и ограничение удерживаемых YAML сохранены;
- главный процесс не удерживает результаты каждого импортного задания;
- технические ошибки не публикуют частичное состояние;
- профили показывают все существенные этапы до успешного ответа MCP;
- договорные и итоговые проверки проходят в установленных бюджетах.

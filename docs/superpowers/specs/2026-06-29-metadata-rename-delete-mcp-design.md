# Переименование и удаление metadata-объектов через core и MCP

Дата: 2026-06-29

Статус: черновик во время brainstorming.

## Контекст

В первой версии MCP были доступны schema, validate, import, sync и init sync state. Переименование и удаление намеренно не входили в первый сценарий: агент мог менять YAML руками, но не имел безопасной операции, которая учитывает идентичность XML, миграции и ссылки.

В CLI уже есть команды `rename`, `delete` и `generate-migration`, но текущая семантика узкая: команды создают миграционные YAML-файлы, а не выполняют полную операцию над проектом. Новая архитектура ведет к тому, что MCP и CLI должны быть тонкими входами, а бизнес-логика должна жить в `@nakidka/core`.

## Цель

Спроектировать операции переименования и удаления metadata-объектов и их дочерних элементов так, чтобы:

- MCP и CLI вызывали общий core-слой;
- core сам менял YAML-файлы и каталоги при разрешенной записи;
- UUID-сущности сохраняли идентичность через миграции и reference remap;
- структурные ссылки в YAML оставались согласованными;
- удаление не оставляло битые ссылки.

## Принятые решения

### Граница core, MCP и CLI

Логика операций должна жить в `@nakidka/core`. MCP и CLI остаются тонкими слоями: проверяют входные аргументы, требуют явное разрешение на запись и возвращают структурированный результат. Они не должны самостоятельно разбирать YAML-структуру проекта, применять миграции или искать ссылки.

### Два класса объектов

Все объекты должны поддерживаться, но с разной механикой:

- для объектов и дочерних элементов, где важна XML-идентичность через UUID/reference, операция переименования должна писать миграцию;
- для форм, макетов, команд и похожих ссылочных/fileItem-объектов миграция не нужна, но нужен контроль и обновление структурных ссылок.

К первому классу относятся уже поддержанные текущей migration-моделью структурные узлы: верхнеуровневые объекты, реквизиты, табличные части, измерения, ресурсы и похожие дочерние элементы с XML-идентичностью.

### Переименование

Переименование выполняется самим core-слоем:

- меняет YAML-файл или каталог объекта;
- меняет имя внутри YAML-модели, если имя хранится в содержимом;
- пишет миграцию для UUID-сущностей;
- переписывает структурные ссылки во всем YAML-проекте;
- не трогает текстовые вхождения в `.bsl`, сыром XML, шаблонах, комментариях и произвольных строках.

Миграция в новом договоре нужна только для сохранения XML/reference identity при переименовании. Если агент или пользователь вручную удалил один YAML-узел и создал другой без `rename_item`, core не угадывает намерение: при `sync_to_xml` это считается удалением старого узла и созданием нового.

### Удаление

Удаление выполняется самим core-слоем, но блокируется, если найдены структурные ссылки на удаляемую цель.

При наличии ссылок операция должна вернуть список мест, которые мешают удалению. Автоматически чистить ссылки на первом этапе не нужно.

Ссылки внутри самого удаляемого поддерева не блокируют удаление, потому что исчезают вместе с ним. Блокирующими считаются только внешние структурные ссылки из YAML-узлов, которые остаются в проекте после удаления.

Удаление не создает migration-запись. Отсутствие YAML-узла относительно reference-состояния означает удаление при синхронизации в XML.

В режиме без записи `delete_item` возвращает только план удаления и `blockedReferences`. Поля `createdMigration` у удаления не бывает.

### Структурные ссылки

На первом этапе операция работает только со структурными ссылками, которые NKDK умеет разобрать через правила и валидаторы: `metadataTarget`, metadata path/value/type, DataPath и родственные YAML-значения, где строка действительно означает ссылку на metadata-цель.

Перечень первого этапа широкий: операция должна учитывать все ссылки, которые уже проходят через существующие структурные механизмы NKDK. Если значение сейчас разбирается или проверяется как metadata-ссылка, metadata-путь, metadata-значение, typeDescription или DataPath, оно входит в поиск и переписывание. Отдельные исключения не вводятся.

Текстовые вхождения в коде и сырых файлах не входят в первый этап. Примеры не входящих значений:

- `Справочники.Товары.НайтиПоКоду(...)` в `.bsl`;
- строка `"Справочник.Товары"` в пользовательском тексте;
- `Catalog.Товары` в сыром XML или шаблоне;
- комментарии.

### Формат цели операции

Основной договор входа — структурированный JSON, а не строковый metadata-путь. MCP должен принимать цель как объект с явным видом, владельцем, ролью и именем. Это уменьшает неоднозначность для агентов и позволяет валидировать вход через JSON Schema до запуска операции.

Строка вида `Справочник.Товары.Реквизит.Артикул` не является основным MCP-договором. CLI может иметь человекочитаемый синтаксис и преобразовывать его в тот же структурированный core-target, но core-операция должна получать нормализованную структурную цель.

Чтобы ИИ-агент не угадывал поля target-объекта, core должен экспортировать JSON Schema для `MetadataOperationTarget`. Эта схема используется MCP input schema напрямую. `kind` выступает дискриминатором, а каждая ветка задает свои обязательные поля и допустимые enum-значения.

Пример цели реквизита:

```json
{
  "kind": "attribute",
  "owner": {
    "itemTypePrefix": "Справочник",
    "name": "Товары"
  },
  "name": "Артикул"
}
```

Пример цели формы:

```json
{
  "kind": "fileItem",
  "owner": {
    "itemTypePrefix": "Справочник",
    "name": "Товары"
  },
  "role": "form",
  "name": "ФормаЭлемента"
}
```

### Поиск доступных целей

MCP должен дать агенту способ получить готовые target-объекты из проекта, а не собирать их вручную. Для этого нужен отдельный безопасный tool, например `nkdk.list_operation_targets`.

Вход:

```ts
{
  projectDir: string
  query?: string
  kind?: MetadataOperationTarget["kind"]
  owner?: {
    itemTypePrefix: string
    name: string
  }
  limit?: number
}
```

Выход содержит готовые цели:

```ts
{
  ok: true
  targets: Array<{
    target: MetadataOperationTarget
    displayPath: string
    projectPath?: string
    canRename: boolean
    canDelete: boolean
    requiresMigration: boolean
  }>
}
```

`displayPath` нужен для человека и CLI-подсказок, но не является основным входом операции. `target` — единственный надежный машинный договор.

### Инструкции для MCP-агента

Агент должен получать правило переименования из MCP, без отдельной внешней инструкции:

- guide `nkdk://guides/config-edit-yaml` должен явно говорить: если пользователь хочет переименовать metadata-объект или дочерний элемент с сохранением identity, нельзя править YAML руками; нужно вызвать `nkdk.rename_item`;
- описание tool `nkdk.rename_item` должно называть его единственным MCP-способом сохранить XML/reference identity при переименовании;
- описание `nkdk.delete_item` должно говорить, что удаление не пишет миграцию: отсутствующий YAML-узел будет удален при XML-синхронизации;
- prompt редактирования YAML должен повторять это правило перед обычными файловыми изменениями;
- `sync_to_xml` должен возвращать только технический результат применения: какие миграции были бы применены в режиме без записи или применены при записи, и какие XML-файлы изменились;
- отдельный MCP-tool для просмотра миграций не нужен: для проверки цепочки агент использует `sync_to_xml` без записи.

`sync_to_xml` на первом этапе не возвращает отдельный смысловой итог по identity: какие узлы будут переименованы, созданы заново или удалены. Если пользователь ожидал сохранения identity, агент должен предложить выполнить переименование через `nkdk.rename_item` до `sync_to_xml`, ориентируясь на наличие или отсутствие migration-операции.

### Режим без записи и запись

Режим без записи не является отдельным обязательным шагом, но операции должны уметь работать без изменения файлов. Если `allowWrite !== true`, `rename_item` и `delete_item` ничего не меняют и возвращают план операции: какие файлы будут изменены, какие ссылки будут переписаны, какая миграция будет создана для переименования и что блокирует удаление.

Для `sync_to_xml` режим без записи должен проверить всю цепочку ожидающих применения миграций и вернуть, какие миграции были бы применены, либо структурированные ошибки цепочки. Это правило одинаково для полной и частичной XML-синхронизации: частичный режим не выбирает подмножество миграций. В режиме без записи `sync_to_xml` не пишет XML и не обновляет `.nakidka-migrations.yaml`.

Успешный ответ `sync_to_xml` без записи включает список миграций, которые были бы применены:

```ts
{
  ok: true
  mode: "plan"
  migrationsToApply: Array<{
    fileName: string
    from: string
    to: string
  }>
}
```

`from` и `to` возвращаются полными migration-путями после последовательного применения предыдущих файлов.

В отличие от `rename_item` без записи, здесь `fileName` известен заранее: `sync_to_xml` работает с уже существующими migration-файлами.

Если `allowWrite: true`, операция применяет тот же план и возвращает результат применения. Запись требует явного разрешения, но отдельный двухшаговый протокол не обязателен.

После успешной записи `sync_to_xml` возвращает тот же список как `migrationsApplied`, чтобы агент мог показать пользователю, какие переименования были учтены и записаны в `.nakidka-migrations.yaml`. Дополнительно результат содержит `changedXmlFiles`: список XML-файлов, которые фактически были изменены, созданы или удалены, с видом изменения.

`.nakidka-migrations.yaml` обновляется только если вся XML-синхронизация завершилась без ошибок. Если хотя бы один объект не синхронизировался, имена migration-файлов не добавляются в `applied`.

Поле `migrationsApplied` возвращается только при полностью успешном `sync_to_xml` с `allowWrite: true`. Если синхронизация завершилась с ошибками, `migrationsApplied` отсутствует.

Успешный ответ `sync_to_xml` с записью:

```ts
{
  ok: true
  mode: "applied"
  migrationsApplied: Array<{
    fileName: string
    from: string
    to: string
  }>
  changedXmlFiles: Array<{
    path: string
    change: "added" | "changed" | "deleted"
  }>
}
```

Если ожидающих применения миграций нет, это не ошибка: `sync_to_xml` возвращает пустой список `migrationsToApply: []` или `migrationsApplied: []`.

Если миграции успешно проверены и применены, но XML-файлы фактически не изменились, это тоже успешный результат. `changedXmlFiles` возвращается пустым списком, а имена примененных файлов миграций все равно добавляются в `.nakidka-migrations.yaml`.

Вид изменения в `changedXmlFiles` определяется относительно XML-каталога до запуска операции:

- `added` — файла не было, после синхронизации он появился;
- `changed` — файл был и остался, но содержимое изменилось;
- `deleted` — файл был удален.

Вид изменения описывает итоговое состояние XML-конфигурации, а не промежуточные файловые операции. Если файл был удален и затем создан заново в рамках одной синхронизации по тому же относительному пути, он возвращается как `changed`.

`changedXmlFiles` всегда содержит файлы, а не каталоги. Если операция удаляет внешний XML-каталог, в результате перечисляется каждый удаленный XML-файл с `change: "deleted"`.

`changedXmlFiles.path` хранится относительно XML-каталога синхронизации и использует `/` как разделитель независимо от операционной системы. Пример: `Catalogs/Товары.xml`, а не полный путь `/repo/xml/Catalogs/Товары.xml`.

### Ошибки записи и атомарность

Core не должен обещать автоматический откат файловых изменений. Перед записью операция строит полный план и проверяет известные препятствия, но если ошибка произошла уже во время применения, tool возвращает аварийный результат.

Такой результат должен явно сообщать:

- на каком шаге произошла ошибка;
- какие файлы уже были изменены или созданы;
- какие запланированные изменения не были применены;
- исходное сообщение ошибки.

Пользователь или агент после этого решает, как восстановить проект: через Git, ручную правку или повторный запуск после устранения причины. Core не должен делать вид, что может надежно откатить произвольные файловые операции.

Для `sync_to_xml` действует тот же принцип: если XML частично записан, а затем синхронизация вернула ошибки, core не откатывает уже записанные XML-файлы. При этом migration-файлы не отмечаются примененными в `.nakidka-migrations.yaml`, пока вся синхронизация не завершится успешно.

Следующий запуск `sync_to_xml` после частичной ошибки снова увидит те же migration-файлы как ожидающие применения. Это ожидаемое поведение: пользователь или агент должен устранить причину ошибки и повторить синхронизацию.

### Результат операций

На первом этапе результат MCP/core должен быть компактным и машинно читаемым.

Для успешного режима без записи или применения достаточно вернуть:

```ts
{
  ok: true
  mode: "plan" | "applied"
  changedFiles: string[]
  rewrittenReferences: Array<{
    filePath: string
    yamlPath: Array<string | number>
    from: string
    to: string
  }>
  createdMigration?: {
    from: string
    to: string
    fileName?: string
  }
  blockedReferences: []
}
```

В режиме без записи `rename_item` возвращает только `from/to` будущей миграции. `fileName` появляется только после записи, потому что фактическое имя файла выбирается в момент применения и может отличаться от предварительного расчета.

Для целей, которым миграция не нужна, например fileItem-объектов, `createdMigration` отсутствует.

Для удаления, которое заблокировано внешними структурными ссылками:

```ts
{
  ok: false
  code: "references_found"
  message: string
  changedFiles: []
  rewrittenReferences: []
  blockedReferences: Array<{
    filePath: string
    yamlPath: Array<string | number>
    value: string
  }>
}
```

Дополнительные поля можно добавить позже, но первый договор должен покрывать четыре вопроса: какие файлы меняются, какие ссылки переписаны, какая миграция создана при переименовании и что блокирует удаление.

### Конфликт имени

Новое имя должно проходить текущее правило имени metadata: первый символ — буква или `_`, дальше буквы, цифры или `_`. Точка, пробелы, пустая строка и полный путь вместо локального имени недопустимы. Если имя не проходит это правило, rename блокируется с ошибкой `invalid_name`.

Если новое имя уже занято в той же области имен, rename блокируется с ошибкой `name_conflict`. Операция не должна подбирать свободное имя и не должна применять частичные изменения.

Область имен определяется типом цели:

- верхнеуровневый объект конфликтует с объектами того же `itemTypePrefix`;
- дочерний элемент конфликтует с соседями той же коллекции владельца;
- fileItem вроде формы или макета конфликтует с fileItem того же вида у того же владельца.

Сравнение имен для конфликта с соседями выполняется без учета регистра. Например, если рядом уже есть `товары`, переименование другого объекта в `Товары` блокируется. При этом переименование того же самого узла только сменой регистра, например `Товары` -> `товары`, допустимо и не считается `name_conflict`. Unicode-нормализация отдельно не выполняется: на первом этапе учитывается только регистр. Это правило применяется и к обычному `rename_item`, и к проверке целевых путей в цепочке migration-файлов.

### Sync state

Rename/delete не выполняют XML-синхронизацию и не обновляют `.nkdk-sync.bin`. Эти операции меняют только YAML-проект, структурные ссылки и, для переименований UUID/reference-сущностей, migration-файлы.

Состояние инкрементальной XML-синхронизации остается ответственностью `nkdk.sync_to_xml` и `nkdk.init_sync_state`. После rename/delete пользователь или агент отдельно запускает нужный sync-сценарий.

Каталог `Миграции/**` не должен попадать в `.nkdk-sync.*`: состояние инкрементальной синхронизации описывает YAML-файлы проекта, а не служебную историю переименований. При этом `sync_to_xml` обязан читать каталог `Миграции` отдельным шагом при любой XML-синхронизации.

### Частичная XML-синхронизация и миграции

Если `sync_to_xml` запускается в частичном режиме, core все равно проверяет и применяет все ожидающие применения миграции. Частичность относится только к набору XML-областей, которые будут записаны по разнице из `.nkdk-sync.*` и по затронутым миграциями путям.

Порядок для частичной XML-синхронизации:

1. Прочитать `.nakidka-migrations.yaml` из XML-каталога.
2. Прочитать все файлы миграций из YAML-каталога, которых нет в списке примененных.
3. Проверить и свернуть всю цепочку миграций относительно текущего XML/reference-состояния.
4. Построить обычный частичный план по разнице из `.nkdk-sync.*`.
5. Добавить в план XML-области, затронутые каждой ожидающей применения миграцией.
6. Записать только итоговый частичный план.
7. После полного успеха обновить `.nakidka-migrations.yaml`, добавив все примененные файлы миграций, и пересчитать `.nkdk-sync.*` по всему текущему YAML-проекту.

Наличие ожидающих применения миграций само по себе делает частичную синхронизацию ненулевой работой, даже если `.nkdk-sync.*` не видит изменений YAML-файлов. Это важно для случая, когда YAML уже находится в новом состоянии, а XML еще не получил перенос идентичности.

Обновление `.nkdk-sync.*` после успеха не ограничивается файлами, попавшими в частичный план. Core записывает состояние всех учитываемых YAML-файлов проекта, даже если конкретный YAML-файл не был помечен измененным до запуска. Каталог `Миграции/**` по-прежнему в это состояние не входит.

Для построения XML-областей по миграциям core использует те же нейтральные правила проекта, что и обычный инкрементальный план. Нельзя добавлять частные условия по конкретным типам объектов в общие слои. Переименование верхнеуровневого объекта затрагивает область владельца и корневую `Configuration.xml`; переименование дочернего UUID/reference-узла затрагивает область владельца, потому что его XML обычно записывается вместе с владельцем.

Если миграция затрагивает путь, для которого нет правила частичной XML-синхронизации, это ошибка договора правил проекта. Core блокирует частичную синхронизацию с общей ошибкой `migration_chain_invalid` и не переходит автоматически на полную синхронизацию.

Если переименование меняет XML-путь верхнеуровневого объекта, частичная синхронизация должна удалить старый XML-файл или старый внешний XML-каталог этого объекта после успешной записи нового состояния. Эти удаления входят в тот же план применения и возвращаются в `changedXmlFiles` с `change: "deleted"`. Если запись или удаление завершились ошибкой, `.nakidka-migrations.yaml` и `.nkdk-sync.*` не обновляются.

Внешний результат частичной синхронизации не раскрывает внутренний список XML-областей, добавленных из-за миграций. Достаточно вернуть `migrationsApplied` и `changedXmlFiles`.

### Ожидающие применения миграции

Если в YAML-проекте уже есть ожидающие применения миграции, новая операция не блокируется сама по себе. Core создает новый migration-файл поверх существующей цепочки.

`rename_item` и `delete_item` не проверяют применимость всей цепочки ожидающих применения миграций. Эта проверка возможна только при наличии XML/reference-состояния и выполняется в `sync_to_xml`. Операции переименования и удаления работают с текущим YAML-проектом: проверяют существование цели в YAML, конфликт имени или структурные ссылки в YAML и создают файловые изменения поверх текущего состояния.

### Формат migration-файла

Целевой договор сохраняет короткий текущий формат YAML-словаря:

```yaml
"Справочник.Товары.Реквизит.Артикул": КодПоставщика
```

Ключ — полный исходный migration-путь узла в текущем состоянии цепочки, то есть после применения всех предыдущих migration-файлов. Ключ должен быть строкой и поддерживаемым migration-путем для сущности с XML/reference identity; формы, команды и другие цели, которым миграция не нужна, в migration-файле недопустимы.

Значение — новое локальное имя этого же узла. Оно должно проходить то же правило имени metadata, что и `rename_item`: первый символ — буква или `_`, дальше буквы, цифры или `_`. Число, объект, `null`, пустая строка, строка с точкой, пробелами или полный путь считаются ошибкой `invalid_migration_file`.

Переименование в то же локальное имя запрещено. Такая запись блокирует цепочку с ошибкой `noop_migration`, потому что не меняет путь identity.

Если ключ слева не найден в текущем состоянии цепочки, это всегда ошибка всей цепочки. Core не применяет ни одну ожидающую применения миграцию и возвращает ошибку отсутствующего исходного пути.

Если целевой путь уже занят в текущем состоянии цепочки, это тоже ошибка всей цепочки. Core не поддерживает скрытые перестановки имен и не применяет частичные изменения.

В новом договоре один migration-файл содержит ровно одну запись `path: newName`. Если файл не разбирается как YAML-словарь, содержит ноль записей или больше одной записи, core блокирует всю цепочку с ошибкой `invalid_migration_file`. Порядок применения определяется только именами migration-файлов.

Имя migration-файла остается текущим timestamp-форматом и отвечает только за порядок применения. Бизнес-смысл в имя файла не добавляется: путь и новое имя хранятся внутри YAML. Уникальность имени обеспечивается текущим правилом: если новый timestamp не больше последнего файла, используется следующая секунда.

Все migration-файлы лежат в одном корневом каталоге YAML-проекта `Миграции`. Раскладывать миграции по объектам или типам не нужно: порядок всей цепочки должен быть общим для проекта.

Каталог `Миграции` считается строгим только для файлов с расширением `.yaml`. Если в нем лежит `.yaml`-файл с именем, не соответствующим migration timestamp-формату, core блокирует всю цепочку с ошибкой `invalid_migration_file_name`. Файлы с другими расширениями, включая `.yml`, игнорируются.

В новом договоре migration-файл хранит только переименования и не имеет служебных значений. Строки `Удалить` и `Добавить` не имеют особого смысла: запись `"Справочник.Товары.Реквизит.Артикул": Удалить` означает переименование реквизита `Артикул` в `Удалить`, если такое имя допустимо. Удаление и создание выводятся из различий между текущим YAML и reference-состоянием.

### Текущее поведение migration-цепочки

Сейчас migration-файлы читаются в порядке имен файлов, кроме уже applied-записей из `.nakidka-migrations.yaml`. Каждый файл содержит YAML-словарь `path -> action`, где action может быть новым локальным именем, `Удалить` или `Добавить`.

`applyPendingMigrationFiles` применяет файлы последовательно. Внутри одного файла текущая реализация тоже применяет entries последовательно:

- `Удалить` удаляет путь и всех потомков;
- `Добавить` создает путь без `referencePath`;
- rename строит целевой путь заменой последнего сегмента и переносит узел вместе с потомками;
- `referencePathByCurrentPath` строится из финального состояния и сохраняет исходные reference-пути для переименованных узлов.

Это текущее поведение, а не целевой договор новой архитектуры. В новом договоре migration-файлы содержат только переименования и не сохраняют совместимость со служебными действиями `Удалить`/`Добавить`. Удаления и добавления выводятся из различий между текущим YAML и reference-состоянием.

Текущая модель хорошо поддерживает цепочки вида: сначала переименовать объект, затем переименовать реквизит уже по новому пути объекта.

Обмен именами двух существующих узлов сейчас не продуман как отдельный сценарий. Если два реквизита меняются именами `А <-> Б`, то:

- `detectMigrationConflicts` не увидит конфликт, если множество имен на уровне осталось тем же;
- явная миграция `А: Б`, `Б: А` упадет на первом шаге, потому что целевой путь уже существует;
- обход через временное имя тоже не проходит текущую `validateAppliedMigrationTarget`, потому что target-checks ожидают отсутствие старого пути, а после обмена этот путь снова существует, но уже с другой reference-идентичностью.

Для новых core-операций это отдельное требование: обмен именами внутри одной области не поддерживается как особая перестановка и должен блокироваться понятной ошибкой.

### Сворачивание миграций

Лучший целевой подход — перед проверкой и sync сворачивать ожидающие применения миграции в итоговое соответствие reference-путей текущим YAML-путям, но делать это последовательно. Каждый следующий шаг проверяется относительно состояния, полученного после предыдущих шагов.

Текущая реализация мыслит rename как последовательное изменение ключей в `Map`: `А -> Б` невозможно, пока `Б` существует. Для операций над metadata это слишком низкоуровневый взгляд. Миграция описывает не файловую последовательность шагов, а изменение идентичности: какой reference-узел должен соответствовать какому текущему YAML-узлу после всех ожидающих применения миграций.

Целевая модель:

```text
 reference state + ожидающие применения миграции
        ↓
collapsed migration state
        ↓
finalPath -> referencePath
        ↓
reference remap при sync
```

В такой модели обмен реквизитов `А <-> Б` не является допустимой особой перестановкой:

```yaml
"Справочник.Товары.Реквизит.А": Б
"Справочник.Товары.Реквизит.Б": А
```

Первый же шаг пытается переименовать `А` в уже занятое имя `Б`, поэтому цепочка должна остановиться с ошибкой:

```text
name_conflict: Справочник.Товары.Реквизит.Б уже существует
```

Если пользователю действительно нужно обменять имена, он должен сделать это через явное промежуточное имя и отдельные корректные шаги, где каждый шаг допустим в своем промежуточном состоянии.

Сворачивание должно сохранять текущие полезные свойства:

- несколько ожидающих применения файлов применяются в порядке имен файлов;
- последующие файлы могут ссылаться на уже переименованный путь;
- rename в занятый путь не допускается, даже если этот путь позже освобождается другой ожидающей применения операцией;
- два разных reference-узла не могут претендовать на один и тот же финальный путь.

Для этого `targetChecks` в текущем виде `exists/absent` недостаточны. Их нужно заменить или расширить пошаговой проверкой состояния: какой путь сейчас существует, какую reference-идентичность он несет, свободен ли целевой путь прямо сейчас, и из какого migration-файла пришла операция. Итоговое соответствие `finalPath -> referencePath` строится только после того, как вся последовательность прошла без ошибок.

### Конкурентные миграции из Git

YAML-проект живет в Git, поэтому два пользователя могут независимо создать миграции для одного и того же узла. После merge такие миграции могут оказаться рядом в каталоге `Миграции`, а XML-каталог может содержать состояние, где часть миграций уже применена, а часть еще ожидает применения.

Если миграция уже применена и записана в `.nakidka-migrations.yaml`, ее содержимое больше не является источником правды для новых операций. Core не перечитывает примененные migration-файлы для сворачивания, не хранит и не проверяет hash их содержимого. Если примененный файл позже изменили или удалили через Git, это не блокирует rename/delete/sync само по себе: примененный результат уже должен быть отражен в текущем XML/reference-состоянии.

Файл `.nakidka-migrations.yaml` остается простым состоянием применения:

```yaml
applied:
  - 2026-06-30T12-34-56.yaml
```

В него не добавляются hash, копии entries или дополнительные сведения о миграции.

Если `.nakidka-migrations.yaml` отсутствует, это не ошибка: состояние применения считается пустым, как `applied: []`.

Если `.nakidka-migrations.yaml` существует, но core не может прочитать или разобрать его как YAML, это ошибка всей цепочки. Если файл читается, но `applied` отсутствует или не является списком, это тоже ошибка состояния применения. Каждый элемент `applied` должен быть строкой с корректным timestamp-именем migration-файла `.yaml`; остальные значения блокируют всю цепочку. Дубли имен в `applied` тоже считаются ошибкой состояния применения. Без корректного состояния применения нельзя надежно определить, какие migration-файлы еще ожидают применения.

Если имя примененного файла есть в `.nakidka-migrations.yaml`, но самого файла уже нет в каталоге `Миграции`, это не ошибка. Такой файл уже не участвует в новых расчетах. Если файл с примененным именем физически существует, core все равно не читает и не валидирует его содержимое.

Порядок имен внутри `applied` не задает порядок применения заново. Для новых расчетов `applied` используется только как множество имен, которые нужно исключить из списка ожидающих применения migration-файлов.

Целевой обработчик миграций должен различать не только имена файлов, но и claims к идентичностям:

- один reference-узел не может быть переименован в два разных финальных пути;
- один финальный YAML-путь не может получить две разные reference-идентичности;
- одинаковая повторная миграция той же identity в тот же финальный путь блокируется как дубликат, а не применяется молча;
- миграция из устаревшей ветки, которая ссылается на путь, уже переименованный applied-миграцией, не получает отдельного режима совместимости и проверяется как обычная запись цепочки.

Если при `sync_to_xml` среди ожидающих применения миграций найдена любая ошибка, core должен блокировать синхронизацию целиком, а не только конфликтующие узлы. В этом случае `sync_to_xml` не пишет XML, не обновляет `.nakidka-migrations.yaml` и не применяет частичные изменения. До разрешения ошибки состояние identity-цепочки считается недостоверным для XML-синхронизации. `rename_item` и `delete_item` не блокируются ошибками миграционной цепочки, потому что работают только с текущим YAML-проектом. `validate_project` не блокируется ошибками миграционной цепочки и продолжает проверять YAML-проект независимо. `import_from_xml` не использует каталог `Миграции` и игнорирует его содержимое.

Ошибки цепочки возвращаются в машинно читаемом виде с верхним кодом `migration_chain_invalid`:

```ts
{
  ok: false
  code: "migration_chain_invalid"
  message: string
  migrationErrors: Array<{
    fileName?: string
    code:
      | "invalid_migration_file_name"
      | "invalid_migration_file"
      | "invalid_applied_migrations_state"
      | "missing_source_path"
      | "name_conflict"
      | "noop_migration"
      | "duplicate_migration"
      | "same_reference_conflict"
      | "missing_incremental_sync_rule"
    message: string
    path?: string
    value?: string
    conflictingFileName?: string
  }>
}
```

`message` нужен для человека, а `migrationErrors` — для агента и тестов. MCP не должен заставлять агента разбирать текст ошибки.

На первом этапе отдельной команды автоматического разрешения конфликтов не нужно. Пользователь или агент должен вручную исправить историю в Git: удалить лишний migration-файл, изменить спорную запись или объединить миграции так, чтобы после сворачивания осталась однозначная цепочка.

Сценарий, когда обе миграции еще ожидают применения:

```text
M1: Справочник.Товары.Реквизит.А -> X
M2: Справочник.Товары.Реквизит.А -> Y
```

После сворачивания это конфликт `same_reference_conflict`: одна исходная identity претендует на два разных финальных пути. Если обе миграции дают один и тот же финальный путь, это отдельный конфликт `duplicate_migration`: результат совпадает, но история содержит лишнюю migration-запись.

Переименование дочернего узла после переименования его исходного родителя оценивается строго последовательно. Если исходного пути уже нет в текущем состоянии цепочки, это ошибка отсутствующего исходного пути:

```text
M1: Справочник.Товары -> Номенклатура
M2: Справочник.Товары.Реквизит.А -> X
```

После первого шага старого пути `Справочник.Товары` уже нет, поэтому второй шаг должен ссылаться на актуальный путь `Справочник.Номенклатура.Реквизит.А`.

Обратный порядок может быть допустим:

```text
M1: Справочник.Товары.Реквизит.А -> X
M2: Справочник.Товары -> Номенклатура
```

Сначала дочерний узел существует и может быть переименован, затем родитель переносит уже обновленную структуру на новый путь.

Сценарий, когда более ранняя миграция уже applied, а более поздняя пришла из старой ветки:

```text
applied M1: A -> X
ожидает применения M2: A -> Y
```

Текущий `applied: [M1]` исключает `M1` из списка ожидающих применения миграций, и это остается правильной границей. Для новой модели важно не перечитывать applied-файл, а начать сворачивание от текущего XML/reference-состояния, где результат `M1` уже должен быть материализован.

Для этого не нужно перечитывать файл `M1`: базой становится текущее XML/reference-состояние после уже примененных миграций. Если `M2` пытается переименовать уже примененную identity из старого пути `A`, а в базовом состоянии такого пути уже нет, операция возвращает обычную ошибку `missing_source_path`. Даже если `M2` совпадает с уже примененным итогом `A -> X`, отдельной совместимости нет: пользователь или агент должен явно удалить лишний migration-файл или объединить историю.

Сценарий, когда более поздняя миграция уже applied, а более ранняя пришла позже через Git:

```text
applied M2: A -> Y
ожидает применения M1: A -> X
```

Это тоже обычная ошибка цепочки: XML/reference state уже соответствует одной цепочке, а новая ожидающая применения миграция ссылается на исходный путь, которого больше нет в базовом состоянии. Порядок имени файла не должен позволять "откатить" уже applied identity без явной новой операции.

Практический вывод: `.nakidka-migrations.yaml` со списком имен applied-файлов полезен как граница применения, а текущее XML/reference-состояние является базой для новых ожидающих применения миграций. Для надежного Git-сценария collapsed migration state должен иметь provenance по ожидающим применения entries: из какого файла пришел claim, какой referencePath он затрагивает и какой finalPath требует. Конфликт должен возвращать спорящие migration-файлы и требуемые финальные пути, чтобы агент мог показать пользователю, какие ветки спорят за один реквизит.

Дубликаты не считаются безопасным успехом. Это намеренно строгий договор: история миграций должна быть понятной после Git merge, а лишние migration-файлы должны удаляться осознанно.

## Открытые вопросы

Открытых неархитектурных решений для первого черновика не осталось. Архитектурные уточнения по форме `MetadataOperationTarget`, перечислению `kind` и внутренней форме свернутого состояния миграций вынесены на следующий этап.

## Архитектурное направление

Целевой слой в core можно оформить как `metadata/operations`. Он должен зависеть от нейтральных договоров проекта и правил metadata, а не от MCP или CLI.

Операции должны опираться на будущий descriptor-слой `metadata/project`: классификацию цели, связь проектных путей с metadata-узлами, владельцев, fileItem-ресурсы, XML routes и информацию о том, какие изменения требуют migration/reference remap.

MCP-tools будущего этапа:

- `nkdk.list_operation_targets`;
- `nkdk.rename_item`;
- `nkdk.delete_item`.

CLI-команды `rename` и `delete` после переноса должны вызывать тот же core-слой, а не содержать отдельную бизнес-логику.

## Черновой поток rename

1. Принять цель и новое имя.
2. Провалидировать структурный target и разрешить его через core-слой проекта.
3. Проверить конфликт имени в области владельца.
4. Построить план файловых изменений.
5. Найти структурные ссылки во всем YAML-проекте.
6. Построить план переписывания ссылок.
7. Для UUID-сущности добавить запись миграции.
8. Если `allowWrite !== true`, вернуть план без записи.
9. При `allowWrite: true` применить изменения.
10. Вернуть структурированный результат.

## Черновой поток delete

1. Принять цель.
2. Провалидировать структурный target и разрешить его через core-слой проекта.
3. Найти внешние структурные ссылки во всем YAML-проекте.
4. Если внешние ссылки есть, вернуть блокирующий результат без записи.
5. Если ссылок нет, построить план удаления файлов/YAML-узлов.
6. Если `allowWrite !== true`, вернуть план без записи.
7. При `allowWrite: true` применить изменения.
8. Вернуть структурированный результат.

## Тестирование

Будущая реализация должна иметь тесты на уровне core:

- переименование объекта пишет миграцию, переносит каталог и сохраняет UUID при последующем sync;
- переименование реквизита пишет миграцию и переписывает структурные ссылки;
- переименование формы не пишет миграцию, но переписывает структурные ссылки;
- удаление объекта с внешними ссылками блокируется и возвращает список ссылок;
- удаление объекта без внешних ссылок не пишет миграцию и удаляет YAML-структуру;
- текстовые `.bsl`/XML-вхождения не переписываются на первом этапе.

MCP и CLI тестируются как тонкие оболочки: входные параметры, `allowWrite`, JSON-результат и вызов core-сервиса.

# Общий механизм подготовки YAML-проекта

## Цель

Перевести операции над YAML-проектом на общий шаг подготовки, чтобы валидация, подсказка схем, переименование, удаление и синхронизация переиспользовали одно чтение, разбор YAML и индексы проекта.

Операции не должны каждая заново искать, читать и разбирать YAML-файлы. Вместо этого они получают подготовленные `Worker данные YAML`, `Глобальный индекс метаданных`, назначенный `Worker индекс зависимостей` и описания файлов ресурсов проекта.

## Направление

Целевое направление - постепенно уходить от `Metadata-модель` на уровне проекта. Общий механизм не строит модель и не требует ее от потребителей.

Если текущая реализация операции пока зависит от `Metadata-модель`, это считается временным адаптером внутри самой операции. Такой адаптер не входит в договор общего механизма и не должен продлевать время жизни модели на весь проект.

## Связь с архитектурой

Эта спека уточняет шаг `Подготовка YAML-проекта` из `.agents/architecture.md`. Названия шагов и артефактов в этом документе должны совпадать с архитектурным документом.

Матрица операций в архитектуре остается источником истины по тому, какие операции используют общий шаг подготовки. Эта спека описывает внутреннее устройство подготовки и порядок использования ее результатов.

## Область

В общий механизм входят:

- распределение файлов;
- обязательное распределение YAML-файлов через worker-пул для любого размера проекта;
- чтение и разбор YAML без построения позиций YAML-узлов;
- сохранение `Worker данные YAML` в памяти worker;
- извлечение `Worker индекс метаданных`;
- извлечение `Worker индекс зависимостей`;
- построение `Глобальный индекс метаданных`;
- временное построение `Глобальный индекс зависимостей`;
- распределение `Глобальный индекс зависимостей` обратно в `Worker индекс зависимостей`.

В общий механизм не входят:

- проверка по схеме;
- построение `Metadata-модель`;
- проверка зависимостей;
- изменение YAML-файлов;
- запись XML;
- запись YAML;
- запись файлов ресурсов проекта;
- позиции YAML-узлов.

Эти действия остаются отдельными шагами, потому что разные операции используют их по-разному.

## Использование worker

Подготовка YAML-проекта всегда использует worker-пул. У общего механизма не должно быть отдельной синхронной ветки для малых проектов и порога вида "использовать worker только от 128 файлов".

Координатор всегда строит `Worker список YAML-файлов` и передает его worker. Для маленького проекта активным может оказаться один worker, а остальные worker могут не получить файлов, но договор выполнения остается тем же: чтение, разбор YAML, сохранение `Worker данные YAML` и извлечение worker индексов выполняются в worker.

Это решение делает одинаковыми порядок действий, время жизни данных и диагностики для валидации, подсказки схем, переименования, удаления и синхронизации.

## Ключевое решение по позициям YAML

Целевое состояние - полностью убрать позиции YAML-узлов из кода проекта. Общий механизм работает с чистым разбором YAML: текст файла, YAML-данные и синтаксические диагностики. Индекс позиций YAML-узлов в общий подготовленный результат не входит и не строится позднее ради диагностики.

Причина: позиции сильно удорожают массовую подготовку проекта и усложняют общий разбор YAML. Ошибки должны ссылаться на файл и логический путь в YAML-данных, а не на точные строку и колонку. Синтаксические диагностики YAML могут сохранять строку и колонку из самого YAML-парсера, но проект не должен строить собственный индекс позиций узлов.

## Диагностики без позиций

Диагностики должны постепенно перейти на договор, где основная привязка ошибки - файл, роль файла и логический путь в YAML:

```ts
interface YamlDiagnosticTarget {
  filePath: string
  projectPath: string
  yamlPath?: readonly (string | number)[]
}
```

`line` и `col` не должны быть обязательной частью диагностики. Для ошибок схемы, зависимостей и операций достаточно `yamlPath`, сообщения и источника ошибки. Точная позиция допустима только как внешнее свойство синтаксической ошибки, пришедшее напрямую от парсера YAML.

## Артефакты общего шага

| Артефакт | Владелец | Назначение |
|---|---|---|
| `Список файлов проекта` | Координатор | Найденные YAML и файлы ресурсов проекта с их ролями и правилами. |
| `Worker список YAML-файлов` | Worker | YAML-файлы, назначенные одному worker для локальной обработки. |
| `Описание файла ресурса проекта` | Координатор | Путь файла ресурса проекта, его роль и правила соответствующего свойства метаданных. |
| `Worker данные YAML` | Worker | Назначенные worker YAML-файлы вместе с текстом, YAML-данными и синтаксическими диагностиками. |
| `Worker индекс метаданных` | Worker, временно | Индекс метаданных, собранный worker из назначенных ему YAML-файлов. |
| `Worker индекс зависимостей` | Worker | Индекс ссылок, DataPath и других зависимостей, собранный worker или назначенный worker после распределения глобального индекса. |
| `Глобальный индекс метаданных` | Координатор, затем каждый worker | Объединенный индекс метаданных всех YAML-файлов проекта. |
| `Глобальный индекс зависимостей` | Координатор, временно | Объединенный индекс ссылок, DataPath и других зависимостей всех YAML-файлов до распределения между worker. |

После обобщения индексов worker удаляет временные `Worker индекс метаданных` и первичный `Worker индекс зависимостей`. После распределения координатор удаляет `Глобальный индекс зависимостей`. Каждый worker продолжает хранить `Worker данные YAML`, `Глобальный индекс метаданных` и назначенный ему `Worker индекс зависимостей`.

## Цепочка подготовки

1. Координатор выполняет `Распределение файлов`: находит и классифицирует YAML и файлы ресурсов проекта, затем делит YAML-файлы между worker.
2. Координатор передает `Worker список YAML-файлов` в worker даже для маленького проекта.
3. Worker выполняет `Чтение и разбор YAML`: читает назначенные YAML-файлы и разбирает их без построения позиций YAML-узлов.
4. Worker выполняет `Сохранение worker данных YAML`: сохраняет `Worker данные YAML` в памяти для последующих шагов операции.
5. Worker выполняет `Извлечение локальных индексов`: извлекает `Worker индекс метаданных` и первичный `Worker индекс зависимостей`.
6. Координатор выполняет `Обобщение индексов`: объединяет `Worker индекс метаданных` в `Глобальный индекс метаданных`, а первичные worker индексы зависимостей - во временный `Глобальный индекс зависимостей`.
7. Координатор выполняет `Распределение индекса зависимостей`: делит временный `Глобальный индекс зависимостей` между worker и передает каждому worker `Глобальный индекс метаданных` и назначенный `Worker индекс зависимостей`.

## Использование операциями

| Операция | Использование общего шага |
|---|---|
| Валидация | Использует `Worker данные YAML`, `Глобальный индекс метаданных` и `Worker индекс зависимостей`; диагностики выводит по файлу и логическому YAML-пути, без построения позиций узлов. |
| Подсказка схем | Использует классификацию файла, правила структуры проекта и при необходимости `Worker данные YAML` без позиций. |
| Переименование | Использует индексы и `Worker данные YAML`; текущая архитектура может выполнять переходное `Построение модели` позднее, но общий шаг подготовки модель не создает. |
| Удаление | Использует индексы и `Worker данные YAML`; текущая архитектура может выполнять переходное `Построение модели` позднее, но общий шаг подготовки модель не создает. |
| Синхронизация в XML | Использует `Worker данные YAML` и индексы, затем выполняет отдельные XML-шаги, проверку по схеме, построение модели, проверку зависимостей и запись XML согласно архитектуре. |

## Порядок действий операций

### Валидация

1. MCP получает запрос на валидацию YAML-проекта.
2. Координатор запускает `Подготовка YAML-проекта`.
3. Worker читают и разбирают YAML без позиций, сохраняют `Worker данные YAML`, собирают worker индексы метаданных и зависимостей.
4. Координатор строит `Глобальный индекс метаданных` и распределяет `Worker индекс зависимостей` обратно по worker.
5. Worker выполняют `Проверка по схеме` для своих `Worker данные YAML`.
6. Worker выполняют `Проверка зависимостей` по `Глобальный индекс метаданных` и своему `Worker индекс зависимостей`.
7. Координатор собирает диагностики, сортирует и удаляет дубли.
8. MCP возвращает диагностики с привязкой к файлу и логическому YAML-пути.
9. После ответа worker освобождают `Worker данные YAML` и индексы, если подготовленный проект не переиспользуется следующим запросом.

### Синхронизация в XML

1. MCP получает запрос на синхронизацию YAML-проекта в XML.
2. Координатор запускает `Подготовка YAML-проекта`.
3. Worker читают и разбирают YAML без позиций, сохраняют `Worker данные YAML`, собирают worker индексы метаданных и зависимостей.
4. Координатор строит `Глобальный индекс метаданных` и распределяет `Worker индекс зависимостей`.
5. Координатор отдельно выполняет `Поиск XML-файлов выгрузки` и `Классификация XML-файлов выгрузки`, если операции нужен исходный XML-каталог.
6. Операция выполняет `Чтение XML`, `Парсинг XML` и при необходимости `Чтение файла ресурса проекта`, чтобы сохранить данные исходной XML-выгрузки.
7. Операция выполняет `Проверка по схеме` и `Проверка зависимостей`, чтобы не записывать XML из некорректного YAML-проекта.
8. Операция выполняет `Построение модели` как текущий переходный шаг, пока синхронизация еще зависит от `Metadata-модель`.
9. Worker выполняют `Построение XML` и `Сериализация XML`.
10. Координатор выполняет `Запись XML`, `Учёт XML-файлов`, `Удаление устаревших XML-файлов` и при необходимости `Запись файла ресурса проекта`.
11. После записи освобождаются промежуточные XML-данные; подготовленный YAML-проект может быть освобожден или сохранен для следующей операции без записи.

### Переименование

1. MCP получает запрос на переименование объекта или вложенного элемента.
2. Координатор запускает `Подготовка YAML-проекта`.
3. Операция выполняет `Проверка по схеме` и `Проверка зависимостей`, чтобы работать только с согласованным YAML-проектом.
4. Операция выполняет `Построение модели` как текущий переходный шаг, если конкретная реализация переименования еще зависит от `Metadata-модель`.
5. По `Глобальный индекс метаданных` операция находит переименуемую сущность и проверяет конфликт имени в нужной области.
6. По `Worker индекс зависимостей` worker находят ссылки, которые должны быть изменены.
7. Операция строит план изменений: правка YAML-данных, `Переименование путей` и `Запись YAML`.
8. Если найдены неоднозначные или неподдержанные зависимости, операция возвращает блокирующие диагностики без записи.
9. Если запись не разрешена, MCP возвращает только план.
10. Если запись разрешена, план применяется к YAML-проекту.
11. После записи подготовленный снимок считается устаревшим и должен быть удален из памяти.

### Удаление

1. MCP получает запрос на удаление объекта или вложенного элемента.
2. Координатор запускает `Подготовка YAML-проекта`.
3. Операция выполняет `Проверка по схеме` и `Проверка зависимостей`, чтобы работать только с согласованным YAML-проектом.
4. Операция выполняет `Построение модели` как текущий переходный шаг, если конкретная реализация удаления еще зависит от `Metadata-модель`.
5. По `Глобальный индекс метаданных` операция находит удаляемую сущность.
6. По `Worker индекс зависимостей` worker ищут зависимости от удаляемой сущности.
7. Операция отделяет внутренние зависимости внутри удаляемого поддерева от внешних зависимостей из остального проекта.
8. Если есть внешние зависимости, операция возвращает блокирующие диагностики без записи.
9. Если внешних зависимостей нет, операция строит план удаления: удаление YAML-узла, `Удаление путей` и `Запись YAML`.
10. Если запись не разрешена, MCP возвращает только план.
11. Если запись разрешена, план применяется к YAML-проекту.
12. После записи подготовленный снимок считается устаревшим и должен быть удален из памяти.

## Предлагаемый договор

Общий механизм должен выдавать объект `PreparedYamlProject`, который не привязан к валидации и не содержит `Metadata-модель`:

```ts
interface PreparedYamlProject {
  projectDir: string
  files: ProjectFileDescriptor[]
  resourceFiles: ProjectResourceFileDescriptor[]
  metadataIndex: GlobalMetadataIndex
  workers: PreparedYamlWorkerPartition[]
}

interface PreparedYamlWorkerPartition {
  yamlFiles: PreparedYamlFile[]
  dependencyIndex: WorkerDependencyIndex
}

interface PreparedYamlFile {
  filePath: string
  projectPath: string
  role: ProjectYamlFileRole
  owner: ProjectFileOwner
  text: string
  data: unknown
  syntaxDiagnostics: YamlSyntaxDiagnostic[]
}
```

В этом договоре намеренно нет `locations`, `Metadata-модель` или другого результата, который заставляет общий шаг подготовки платить за конкретную операцию.

`workers` заполняется всегда. Даже если проект маленький, потребители не должны иметь отдельный путь для "без worker".

## Проверка согласованности с архитектурой

- Общий механизм соответствует шагу `Подготовка YAML-проекта` и не включает поздние шаги `Проверка по схеме`, `Построение модели` и `Проверка зависимостей`.
- Общий механизм всегда идет через worker-пул и не содержит отдельной ветки для малых проектов.
- Названия артефактов совпадают с `.agents/architecture.md`: `Worker данные YAML`, `Глобальный индекс метаданных`, `Worker индекс зависимостей`, `Описание файла ресурса проекта`.
- Для синхронизации в XML спека учитывает отдельные шаги чтения и парсинга XML; подготовка YAML-проекта их не заменяет.
- Для синхронизации, переименования и удаления спека не обещает работу в обход текущего шага `Построение модели`; модель описана как переходная часть операции, а не как результат подготовки.
- `Глобальный индекс зависимостей` остается временным результатом координатора и не хранится после распределения.
- `Worker данные YAML` не содержат позиции YAML-узлов; диагностики используют файл и логический YAML-путь.

## Открытые вопросы

### По операциям

- Валидация: должен ли подготовленный проект переиспользоваться между быстрыми повторными запросами MCP или всегда освобождаться после ответа?
- Валидация: какие ошибки схемы считаются блокирующими для последующей проверки зависимостей?
- Подсказка схем: достаточно ли ей классификации файла и правил структуры проекта, или ей всегда нужны `Worker данные YAML`?
- Синхронизация в XML: какие ошибки должны полностью блокировать запись XML, а какие могут быть предупреждениями?
- Синхронизация в XML: какие данные исходной XML-выгрузки нужно сохранять для round-trip, пока используется переходное `Построение модели`?
- Переименование: должен ли первый вариант менять только YAML и пути, или сразу учитывать файлы ресурсов проекта?
- Переименование: как операция должна вести себя при частично неподдержанных зависимостях - блокировать все изменение или возвращать частичный план?
- Удаление: какие связанные файлы ресурсов проекта удаляются автоматически, а какие требуют явного подтверждения?
- Удаление: как отличать внутренние зависимости удаляемого поддерева от внешних зависимостей в общем индексе?

### По шагам

- Нужен ли отдельный режим подготовки для одного файла, или все операции должны работать только через подготовку всего проекта?
- Должен ли общий механизм уметь жить между вызовами MCP как долгоживущий дескриптор, или первая версия должна быть одноразовой?
- Где лучше разместить код: новый слой `metadata/projectPreparation` или расширение текущего `metadata/project`?
- Распределение файлов: нужно ли распределять только YAML или также заранее назначать worker файлы ресурсов проекта?
- Распределение файлов: как выбирать число активных worker для маленького проекта при обязательном worker-пути?
- Чтение и разбор YAML: хранить ли исходный текст всегда или только для операций, которые могут записывать YAML обратно?
- Сохранение worker данных YAML: какой ключ использовать для кеша worker - абсолютный путь, путь проекта или описание файла?
- Извлечение локальных индексов: какие виды зависимостей входят в `Worker индекс зависимостей` в первой реализации?
- Обобщение индексов: как представлять конфликтующие объявления метаданных - как элемент индекса или как отдельную диагностику?
- Распределение индекса зависимостей: делить зависимости по файлам, по владельцам метаданных или по целевым объявлениям?

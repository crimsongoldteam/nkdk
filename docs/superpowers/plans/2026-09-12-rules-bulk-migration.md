# План массового переноса правил и тестов

> **Для исполнителя:** использовать superpowers:executing-plans. Работать без субагентов. Написание этого плана не запускает реализацию.

**Цель:** автоматизировать перенос common, вложенных объектов, элементов форм
и владельцев из TS в проверенные YAML-декларации для Rust.

**Архитектура:** статический разбор TS — основной способ; собранные правила —
дополнительная проверка полноты. Кандидаты отделены от рабочего каталога.
После приёмки источник истины — YAML, итоговое приложение полностью на Rust.

**Инструменты:** временный TS-инструмент с анализатором TypeScript, существующие
Rust-компилятор деклараций и проверочные средства, JSON-реестр и e2e-фикстуры.

**Спецификация:** [согласованные решения](../specs/2026-09-12-rules-bulk-migration-design.md).

## Общие ограничения

- Один язык деклараций, разные роли; никаких частных Rust-обработчиков объектов.
- XML-фикстуры не изменять; реальный корпус пока только e2e; Enterprise исключён.
- Общая матрица механизмов вместо копирования тестов по объектам.
- Существующие YAML не перезаписывать, старые тесты автоматически не удалять.
- Сохранять точные числа, записанное время дат и выводимые из правил аномалии.
- Реестр готовности — `tests/migration/coverage.json`, флажки — существующий
  `2026-09-10-rust-yaml-object-checklist.md`; системные перечисления одним пунктом.
- Продолжать существующую изолированную ветку, сохранять накопленные изменения.

## 5. Проверочные объекты и массовые группы

Порядок каждого блока — [массовый охват с завершением владельца](../specs/2026-09-12-rules-bulk-migration-design.md#смешанный-порядок-переноса):

Порядок сборки вложенного элемента после выделения состояний:

1. Сборщик записи создаёт состояния её полей и направляет им события по уже
   вычисленным XML-путям/YAML-ключам. Все состояния одной записи завершаются
   на её закрывающем событии; внешний элемент коллекции владеет готовой записью.
2. Элемент хранит исходную позицию своей XML-оболочки. Сохранение аномалии
   повторяющейся вложенной коллекции должно выбирать это вхождение, а не первый
   узел с одинаковым путём. Нужна проверка двух соседних элементов с разными
   аномалиями и одинаковыми именами полей.
3. Запись элемента использует общий подготовленный writer; обычный путь не
   сериализует элемент во временные XML/YAML-байты ради следующего обработчика.
4. Только после общей матрицы подключаются AdditionalIndexes, подготовленные id,
   внешний файл и корневой YAML-массив. Ненулевые id из e2e обязательны в приёмке.

Завершение состояний скалярных записей и списков само по себе не снимает
ограничение вложенности и не является основанием для флажка common/владельца.


Перед подключением AdditionalIndexes проверить повторное использование декларации
элемента: поля, правила присутствия и ограничения записи должны подключаться
в коллекцию целиком. Их копирование в отдельное описание коллекции недопустимо.
Текущая модель представлений требует `item` отдельно; поддержка ссылки на
составную декларацию элемента должна сохранять её собственные договоры и
разрешённые имена, а не только забирать список полей. Это часть общего
подключения записи, а не особое правило дополнительных индексов.

Перед использованием связанного элемента в генераторе:

- проверить подстановку параметров и входов во всех выражениях, включая
  сокращения, нормализацию и условия атрибутов внутри XML-дерева; текущая
  приёмка схемы покрывает поля, присутствие и ограничения скалярной записи;
- определить возможности приёма событий по типу представления до генерации
  Rust, а не по наличию имён функций в сгенерированном тексте;
- проверить два повторяющихся XML-элемента с разными аномалиями: сохранение
  и проверка восстановления должны различать вхождения с одинаковым путём;
- только после этих проверок подключить обычный путь коллекции к новому
  договору. Сам по себе успешный разбор декларации не означает готовый конвертер.

## Автоматическое подключение готовых деклараций

Согласовано 13 сентября: временный инструмент переноса использует единый
реестр соответствий старых правил готовым декларациям. Запись проверяет весь
профиль параметров и сохраняет внешние файлы, ресурсы, входы и зависимости.
Знание старых построителей остаётся в инструменте миграции, не в Rust-оркестраторе.
Первый пакет — Help и AdditionalIndexes для документа и журнала документов.

Для каждого свойства отчёт различает созданного кандидата, готовую декларацию
с ещё не подключённым контекстом и точную причину блокировки. Наличие common
не доказывает готовность владельца. Неизвестные параметры не отбрасываются.
Автоматизация формирует проверяемые изменения; ожидания берутся из независимых
существующих XML/YAML, а не вычисляются из новой декларации. Контекст, индексы
и внешние ресурсы проверяются перед включением в рабочую сборку.

Число новых подключений показывается отдельно от числа повторно проверенных
свойств. Машинный отчёт служит основой сводки; флажок объекта ставится только
после полной приёмки. Подготовка кандидата флажок не меняет.

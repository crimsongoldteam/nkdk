**Goal:** Выразить все существующие common и rules владельцев/форм единым языком, расширить Rust-генератор общими конструкциями и получить преобразование полного e2e-проекта с сохранением проверок и аномалий.

**Architecture:** Сложные операции раскладываются на общие конструктивные отношения и предметные YAML-декларации. Каталог компилируется с типизированными параметрами/входами; индексы и ресурсы подготавливает операция. Coverage связывает каждый исходный договор с конкретной декларацией и независимыми случаями.

**Tech Stack:** Workspace этапа А, сгенерированный Rust, существующий e2e и corpus. Нейтральные механизмы не содержат таблиц конкретных типов метаданных.

**Spec:** [Единый язык](../specs/2026-09-10-declaration-language-design.md), особенно §8, §11, §13.3; [реестр common](../specs/2026-09-10-common-declarative/README.md). Все условия [главного плана](2026-09-10-rust-yaml-declarations.md) обязательны.

**Отдельный пакет: все системные перечисления — принят.** 678 перечислений и 3501 пара перенесены одним каталогом деклараций; общая проверка охватывает обычный и типизированный XML DCS, коллизии, неизвестный литерал и восстановление XML. В чеклисте остаётся один пункт. Особые договоры владельцев относятся к их переносу.

Подготовка М3: в неизменённом e2e обнаружены пять значений StandardBeginningDate в форме «УсловноеОформление»: стандартные варианты, пользовательская дата и первая дата первого года. Значений StandardPeriod с явным XML-типом в этом корпусе не обнаружено. Оба объекта требуют общего генератора вложенной записи со скалярными полями и календарной точности до секунд; существующий генератор составного текста эту структуру не поддерживает. Отсутствие реальных случаев StandardPeriod фиксировать отдельно от синтетических проверок механизма.

**Сквозной механизм аномалий.** Неизвестная структура, смешанный XML, повторы самого свойства и повреждённый синтаксис остаются работой общего резервного пути. Закрывать связанные случаи вместе с семейством, где они встречаются; не писать предметные обработчики. Перед полной приёмкой проекта проверить и оставшиеся классы отклонений. Ошибки реализации и IO не превращать в успешный результат с пометкой данных.

**Порядок ближайшей работы:** М1 → М2 → весь каталог системных перечислений → М3 → М4 → М6 → завершение М5 → М7 → идентичности М9 → М8 → остаток М9 → М10 → оставшиеся подключения М11. Готовые подключения М11 можно принимать раньше, когда доступны их импорты. Перенос М6 перед приёмкой М5 устраняет ожидание ссылочных проверок оформления. UUID не задерживает весь пакет обычных скаляров.

### Цикл одного семейства

- [ ] Прочитать одну карточку договора и затронутые исходники; перечислить все потребители нового механизма и необходимые профили. Не перечитывать весь каталог.
- [ ] Подключить в проверку минимум двух разных потребителей, если они есть: для М1 это stringOrNumber и predefinedCode. Зафиксировать независимые ожидаемые значения до реализации.
- [ ] Реализовать общий механизм и декларации семейства. Язык расширять только при невозможности выразить договор существующими средствами; не создавать функции конкретных common.
- [ ] Во время изменения выполнять узкие проверки механизма. Для деклараций использовать параметризованную проверку корпуса; добавлять отдельный тест только для нового наблюдаемого договора.
- [ ] После законченного семейства выполнить полные проверки слоя по командам ниже. Если проверка выявила общий дефект, после исправления повторить затронутые проверки и необходимые общие проверки.
- [ ] Для каждого принятого объекта обновить чеклист и coverage в тех же изменениях; один итоговый результат семейства записать в журнал. Обновить короткое текущее состояние и продолжить следующий доступный пакет без ожидания подтверждения.

Для служебного реэкспорта `infrastructure` нужно указать, где обеспечивается его ответственность. Checker проверяет точное равенство множества исходных записей, а не только число 90.

## Общая граница фактов

Сигнатуры для Б2–Б6; определения находятся в conversion-core, подготовка файлов и IO — вне чистого правила:

```rust
pub struct FactId(pub u32);
pub struct Generation(pub u64);
pub struct PreparedFacts { /* закрытые типизированные колонки */ }
pub struct FactRequest { pub fact: FactId, pub owner: String }
pub enum FactState<T> { Ready(T), Missing, Ambiguous, Cycle, Unready }
pub struct FactPlan { /* проверенные проекции и зависимости из деклараций */ }
pub struct SourceBatch<'a> { pub files: Vec<(&'a str, &'a [u8])> }
pub struct FactBuilder { /* накопление компактных колонок поколения */ }

impl FactBuilder {
    pub fn new(plan: &FactPlan, generation: Generation) -> Self;
    pub fn push(&mut self, source: SourceBatch<'_>) -> Result<(), Vec<RuntimeDiagnostic>>;
    pub fn finish(self) -> Result<PreparedFacts, Vec<RuntimeDiagnostic>>;
}

pub fn prepare_facts(
    plan: &FactPlan, source: SourceBatch<'_>, generation: Generation,
) -> Result<PreparedFacts, Vec<RuntimeDiagnostic>>;
```

Комментарии в закрытых структурах обозначают намеренно непубличное хранение, не право хранить произвольный JSON/полный контекст. FactPlan генерируется из contributions/inputs; фактическое значение не выводится из имени FactId. Typed-колонки и layout описываются в спеке перед реализацией Б2. Сгенерированные адаптеры превращают разрешённые facts в PreparedInputs конкретного EntryId из этапа А.

SourceBatch — ограниченная порция файлов по общему бюджету памяти, а не все исходники проекта. FactBuilder.push объединяет компактные индексные колонки разных порций; исходные буферы освобождаются после push. Только finish публикует готовое поколение и окончательно разрешает зависимости. prepare_facts — удобная граница для одного полного небольшого набора, внутри использующая тот же builder. Runtime хранит поколение фактов, а не копии XML для каждого потребителя.

### Б3. Выразить MetadataValue и FillValue декларативно

21 сентября полностью приняты `MetadataValue`, `ChoiceParameters`,
`ChoiceParameterLinks` и вложенные рекурсивные варианты. Их корпус и доказательства
собраны в [отчёте приёмки](../reports/2026-09-20-recursive-value-runtime.md).
При проверке Б3 обнаружена отдельная проблема сборки: один проверочный каталог
системных перечислений порождал 1356 однотипных обёрток в общей библиотеке;
таблицы автоматов дополнительно разворачивались в числовые литералы Rust.
Автоматы теперь хранятся отдельными двоичными файлами сборки, а полный корпус
перечислений проверяется восемью последовательными частями без исключения
значений. Обычная библиотека не содержит эти проверочные обёртки. Размер
генерируемого исходника уменьшен с 436 до 24 МБ; для библиотеки и каждой
части установлены пределы 32 и 8 МиБ. Это ограничение относится к затратам
сборки, а не к целевым замерам скорости и памяти преобразования.
Оставшаяся часть Б3 — `FillValue` и его зависимости от типа владельца.
Из e2e получены 1080 наблюдений FillValue (761 nil, 231 отсутствие, 51 пустой
`xs:string`, 4 `v8:Null`, 33 прочих значений). XML полностью разобран;
112 оценок старых rules остались `unresolved` из-за ограничений определения
типа. [Таблица договора](../specs/2026-09-10-common-declarative/03-types-references.md#наблюдаемый-договор-fillvalue-на-e2e)
разделяет факты и прежнюю оценку.

Порядок реализации внутри Б3: сначала проверяем передачу профиля XML
`exportNilValue` и формы присутствия на неизменённых e2e (обычный строковый
реквизит и стандартный реквизит с `nil`); затем общий выбор альтернатив
из `TypeDescription`; после него ограничения значения и обход `DefinedType`.
Только после этого подключаем политики стандартных реквизитов и приёмку
целого `FillValue`. Переносчик различает два профиля и формирует для пустого
`xs:string` декларативную каноническую форму. Из соседнего
`TypeDescription` уже выводится признак единственного строкового типа;
экспорт без XML-референса проверен для строкового, числового и составного
типа. Это не заменяет проверку совместимости явного значения с объявленным
типом и разрешение ссылок на `DefinedType`.
Пустой `xs:string` встречается 51 раз: общая форма присутствия должна уметь
выпускать пустой элемент с объявленным `xsi:type` и выводить её из типа,
без проверки имени `FillValue` в генераторе. Пустая форма у другого типа
не должна автоматически превращаться в строку. Четыре пустых `v8:Null`
и одна `xr:DesignTimeRef` требуют отдельной проверки обратимости,
но не расширения набора `!xml` без согласования.
Выбор канонической формы с условиями теперь общий для корня значения и поля
записи (`generate/canonical.rs`). Пустой `xs:string` из e2e-корпуса
`MetadataValue` восстанавливается из YAML без XML-референса. Это завершает
механизм формы, но не классификацию и приёмку целого `FillValue`.
Проверка с соседним скалярным полем уже подтверждает выбор между `xsi:nil` и
`xs:string` без XML-референса. Тот же общий доступ к записи теперь работает
для составного `TypeDescription`: проверено условие от его поля
`stringLength`, без отдельного обработчика в оркестраторе. Для полного
`FillValue` общий заимствованный доступ теперь читает и вложенный `items`:
одно строковое значение выбирает пустой `xs:string`, число и составной тип —
`xsi:nil`. Проверка создаёт XML из YAML без референса. Следующие зависимости —
подключение этой формы к переиспользуемому `FillValue`, проверки значения и
графа ссылок.
Проверка владельца дополнена обратным направлением без XML-референса:
`Тип: Строка` порождает пустой типизированный элемент, `Тип: Число` и
составной тип — `xsi:nil`; повторный импорт возвращает тот же YAML.
Первую проверку выполнял проверочный владелец. Попытка вынести всё значение в
`common.fill-value` как вложенную запись показала ограничение генератора:
такой путь обрабатывается как обёртка коллекции. Вместо дополнительного
обработчика выбор пустой формы теперь принадлежит `common.metadata-value`:
владелец передаёт вычисленный из соседнего `TypeDescription` признак
единственного строкового типа и параметр `exportNilValue`. Остальным
потребителям передаётся `false`, их действующий XML-договор не меняется.
Следующий шаг — проверить профили на реальных владельцах, затем ограничения
значения и граф ссылок. `FillValue` до этого не отмечать в чеклисте.
Переносчик `rules.ts` различает `exportNilValue` и оба XML-профиля пустого
`MetadataValue`; общая передача `onlyStringType` из соседнего
`TypeDescription` работает внутри фрагмента и через сборку владельца.
Общий генератор присутствия теперь допускает составное поле, когда условию
нужна лишь его доступность. Полные проверочные проекции трёх реквизитов
документа проходят XML → YAML → XML без референса, включая пустой `xs:string`
и `xsi:nil`. Если подходящего соседа нет, переносчик явно блокирует свойство.
При этом
коллекции из записей с выбором пустой XML-формы остаются заблокированными
до поддержки в общем генераторе коллекций; составная запись с одновременными
правилами для полей и всей записи также пока не выпускается как готовый
кандидат. `FillValue` и владельцев ещё
нужно полностью подключить и принять на e2e; флажок чеклиста не ставить.
При проверке коллекций исправлено общее вычисление канонической XML-формы:
условие, читающее отсутствующее значение, считается неприменимым без паники.
После правки проходят 87 сценариев коллекций и 127 сценариев переноса правил.
Корпус владельцев расширен четырьмя неизменёнными e2e-реквизитами справочника
и регистра сведений. В нём есть явное число `1234`, строковый, календарный и
булев пустые профили; 131 проверка выполняет XML → ожидаемый YAML и обратный
экспорт из YAML с заново подготовленными входами, без XML-референса. Это
подтверждает подключение ещё двух семейств, но не покрывает ограничения длины,
точности, несовместимые значения, `DefinedType` и политики стандартных
реквизитов. Флажок `FillValue` остаётся снятым.
Отдельная регрессия для фиксированной строки выявила, что условие
`onlyStringType` учитывало только `Строка`: экспорт без референса ошибочно
выдавал `xsi:nil`. Общее выражение теперь распознаёт также
`ФиксированнаяСтрока`; проверка покрывает исходную декларацию и
автоматически собранную декларацию реквизита. При этой проверке обнаружено
ещё одно несоответствие: ограничение `TypeDescription` сопоставляло
`ФиксированнаяСтрока(10)` с внутренним полем `value`, хотя длина находится в
отдельном поле `first`. Ограничение теперь проверяет оба поля декларативно.
Та же ошибка в ветвях обычной строки и числа позволяла `Строка(abc)` и
`Число(abc)`. Отрицательные случаи добавлены к проверке владельца;
декларация проверяет `value`, `first` и `second` как отдельные поля.
Совместимость явного значения с единственным объявленным простым типом теперь
проверяется декларативно для строки, числа, булева и календарного значения. Общее выражение
`isVariant` типизируется компилятором; ограничения хранятся в
`common.fill-value-compatibility.yaml`, а переносчик автоматически разворачивает
их в проекции владельцев с парой `Type`/`FillValue`. Генератор составного
значения исполняет проверки после выбора ветви; прежде они терялись при
разбиении владельца. 142 независимых сценария проходят, включая четыре
несовместимых явных значения у документа, справочника и регистра: YAML и XML восстанавливаются,
диагностика сохраняется без остановки. Дополнительно проверена строка `"1234"`
при объявленном числовом типе: кавычки YAML сохраняют строковый вариант и
исходный `xs:string`. Для переменной и фиксированной строки проверяются
соответственно верхняя граница и точная длина в единицах UTF-16; граничные
и ошибочные значения проходят двусторонний корпус без потери XML. Это ещё не
полная классификация: ссылки,
`DefinedType`, неявные значения и
политики стандартных реквизитов ещё не приняты; `FillValue` остаётся без флажка.
Календарный вид проверяется общей операцией над уже разобранным значением:
`Дата` допускает только нулевое время, `Время` — исходную дату `0001-01-01`,
`ДатаВремя` допускает оба компонента. Числовые квалификаторы проверяются
непосредственно на точном десятичном значении без `f64`: общая операция
сравнивает длину целой и дробной частей, а также знак. Знак проверяется и
при нулевой (неограниченной) разрядности. Корпус содержит 154
случаев, включая число выше безопасного целого JavaScript, границу точности,
лишнюю дробную часть и запрещённый отрицательный знак, а также
ошибочное значение даты с временем и допустимую дату в полночь. Реальный
`xr:DesignTimeRef` со ссылкой на предопределённое значение справочника проходит
XML → YAML → XML без XML-референса через реквизит документа. Для единственного
ссылочного типа добавлена декларативная проверка варианта значения: явная
строка сохраняется, но получает предупреждение. Та же проверка действует для
наблюдаемого в e2e `TypeSet` без имени объекта (`Тип: Справочник`): допустимая
ссылка проходит, текст получает предупреждение; обе формы восстанавливают XML.
Ссылка на документ при
объявленном типе справочника пока не получает диагностику; это остаётся
обязательным случаем приёмки ссылочной совместимости.

### Б8. Добавить архитектурные проверки, дубли и полный e2e

**Interfaces:** команды `nkdk-dev architecture check`, `nkdk-dev duplicates --base SHA`, `nkdk-dev e2e --xml DIR --yaml DIR --work DIR`. Инструменты возвращают ненулевой код для нарушения/неполного покрытия; пустой e2e — ошибка.

На этом этапе e2e — пакетное преобразование всех файлов компонента с общими facts в временный каталог. Постоянное состояние, инкрементальные операции и публикация рабочего проекта принадлежат В1; тестовый runner переиспользует generated-rules и подготовку из Б2/Б6, не создаёт второй предметный runtime.


  `check_duplicate_fixture(&str) -> DuplicateReport { passed: bool, pairs: Vec<(String,String)> }` — helper dev/tests/duplicates.rs, использующий заранее заданные base/head версии файлов в памяти. Порог Rust-токенов закрепить равным существующим 50 токенам/5 строкам; порог осмысленного rule-фрагмента определить явными положительными/отрицательными fixtures, не длиной форматированного YAML.

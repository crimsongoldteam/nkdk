# Rust с декларативными common и rules — план реализации

> **Для исполнителя:** использовать `superpowers:executing-plans`, выполнять связанные планы последовательно, отмечать шаги `- [ ]`. Работать без субагентов по указанию пользователя. Исполнение разрешено последующим явным поручением пользователя; состояние фиксируется в журнале.

**Статус:** отдельное поручение на исполнение получено. Работать без субагентов; если требуется ответ пользователя, продолжать независимые части, сохраняя вопрос открытым. [Журнал выполнения](../reports/2026-09-10-rust-yaml-progress.md) отражает фактически выполненные шаги.

**Goal:** Полностью перевести NKDK на Rust, задавая предметное поведение common и rules единым YAML-языком, сохранив публичные результаты, проверки и аномалии и проверив цели 10× по времени и пиковой памяти.

**Architecture:** YAML-декларации компилируются при сборке в прямые Rust-преобразования XML→YAML, YAML→XML и проверки. Нейтральный исполнитель предоставляет общие операции представлений и подготовленные факты; предметные таблицы, ограничения и композиция принадлежат декларациям. Самостоятельные Rust-приложения выполняют проектные операции и MCP без вызова TypeScript.

**Tech Stack:** Rust/Cargo, компиляция деклараций через `build.rs`, XML/YAML-переходники, типизированное описание языка, генерируемый Rust. Rust 1.98 / edition 2024, quick-xml 0.42.0 и yaml-rust2 0.11.0 — зафиксированные кандидаты существующего эксперимента, а не новое утверждение о лучших версиях; этап А проверяет их пригодность и фиксирует принятые версии в Cargo.lock. TypeScript используется только отдельным сравнительным эталоном до окончательного удаления.

**Spec:** [Единая спецификация языка, редакция 0.2](../specs/2026-09-10-declaration-language-design.md). [Реестр 90 common-каталогов](../specs/2026-09-10-common-declarative/README.md) — материал исследования, не второй язык. Действующие публичные операции сверяются с [архитектурой проекта](../../../.agents/architecture.md) и [ограничениями](../../../.agents/restrictions.md).

## Обязательные условия всех этапов

- Один YAML-язык, одна общая спецификация и один компилятор для common и rules.
- Конечные сборка, тесты, CI, запуск CLI/MCP и вспомогательные средства работают без TypeScript/Node.js. Отдельное выполнение старого приложения разрешено только для сравнения периода миграции.
- Предметные `fromXML`, `toXML`, `fromYAML`, `toYAML`, валидаторы и Rust-callbacks в декларациях запрещены. `OperationImplementation`, `prepared_operations` и строковый путь к функции из старого эксперимента не становятся частью нового языка.
- Общие механизмы могут быть написаны на Rust; условие по имени common, itemType или конкретному XML-корню не заменяет декларацию.
- Common не зависит от forms/appliedObjects; forms не зависит от appliedObjects. Импорты, параметры и входы проверяются до генерации.
- Форматы XML и пользовательского YAML, области проверок и диагностики сохраняются. Ошибку текущей реализации не закреплять молча: расхождение исследовать и предъявлять конкретный договор.
- Порядок, повторные вхождения, отсутствие, пустота, nil, default и неготовые факты различаются.
- Контрольный экспорт выполняется из окончательного кандидата YAML и разрешённых фактов. Скрытая исходная модель не может подменять восстановление.
- Существующие XML-фикстуры не меняются. Эталонные результаты не генерируются из проверяемой декларации.
- Действующий договор аномалий сохраняется; новые применения `!xml` требуют отдельного согласования. Неполный язык или resolver не обходится raw.
- Цели времени и пикового RSS — не более 10% сопоставимого результата TS. До новых указаний измерения ограничены `e2e/fixtures/xml` и `e2e/fixtures/nkdk`; каталоги реальных конфигураций вне e2e не используются.
- Тесты защищают наблюдаемые договоры, а не каждое поле реализации. Следовать [.agents/testing.md](../../../.agents/testing.md).
- Перед исполнением выполнить `git fetch origin develop`, проверить изолированный worktree по `superpowers:using-git-worktrees`. В develop/main не изменять файлы и не создавать коммиты.
- Не менять `.agents/architecture.md` и архитектурные baseline без предусмотренного проектом согласования. После реализации сообщить о расхождении документа с кодом.
- PR, push, merge, удаление веток и публикация не выполняются автоматически этим планом. План заканчивается проверенным локальным результатом и отчётом.

## Исходное состояние и уже выполненная работа

План подготовлен в `codex/common-declarative-spec`, HEAD перед планом — `77e41357b0de73a88e64523e38b2b603e9b54dbb`. После fetch `origin/develop` равен `2af2f299ed8241eac78d4db46b4a8421efe2f8f7`. В этой ветке нового Rust-workspace ещё нет; здесь находятся исследование и единая спецификация.

Ветка `codex/rust-fill-value-spec`, проверенная ревизия `4e1a2818879434c57cd93e4616f875fd9479dfc9`, содержит предыдущий эксперимент: `rust/`, `tests/conversion-corpus/`, инструменты проверки корпуса и архитектуры. Это источник отдельных механизмов и независимых ожиданий. Он не удовлетворяет новому запрету специальных предметных функций.

Для текущей цели этот план заменяет порядок исполнения старых `2026-09-09-rust-declarative-conversion-foundation.md` и `2026-09-09-rust-conversion-experiment.md`. Их выполненные результаты учитываются при разборе повторного использования, но старые требования к предметным функциям не переносятся.

Проверенные примеры несовместимости: `rust/crates/rule-model/src/declarations.rs` содержит сигнатуры предметных операций; `rust/crates/rule-compiler/src/prepared.rs` генерирует их вызовы; `rust/crates/pilot-rules/build.rs` подключает `prepared_operations()`. Эти части заменяются, а не механически переводятся из JSON в YAML.

Незакоммиченные файлы ограниченного benchmark в прежнем worktree не копировать и не удалять автоматически. Замер четырёх скалярных фрагментов не подтверждает общую цель и не заменяет новые измерения законченных операций.

## Порядок реализации

| Этап | Отдельный план | Проверяемый результат |
|---|---|---|
| А | [Компилятор и первое сквозное преобразование](2026-09-10-rust-yaml-foundation.md) | Rust читает единые YAML-декларации, генерирует обе стороны и validation; скаляры и I8nText проходят независимые случаи с аномалиями |
| Б | [Полное покрытие common и rules](2026-09-10-rust-yaml-catalog.md) | Все договоры common, владельцев и форм учтены и перенесены; нет специальных функций common; проектный конвертер работает на полном e2e |
| В | [Проектные операции, MCP и отказ от TS](2026-09-10-rust-yaml-application.md) | Состояние, sync, rename, references, платформа и MCP на Rust; приёмка, измерения, сборка без Node и удаление TS |

Это три плана реализации одной спецификации языка. Разделение отражает разные проверяемые результаты и не вводит отдельные языки common/rules.

```text
Уточнить договоры и независимые ожидания
  → загрузчик и типизатор YAML-деклараций
  → генератор обеих сторон и validation
  → присутствие, коллекции, аномалии: I8nText
  → ссылки, типы, FillValue, состояния, DCS, ресурсы
  → полный каталог common + rules владельцев и форм
  → проектные операции, состояние и платформа
  → MCP, измерения, приёмка без Node
  → удаление TypeScript
```

Уточнение сложного оператора включено перед его реализацией в соответствующем этапе. Оно добавляет точную грамматику и независимые примеры в существующую единую спецификацию. При изменении публичного поведения исполнитель приостанавливает только зависимую работу и предъявляет конкретное расхождение; сам факт необходимости исследовать код не требует нового вопроса пользователю.

| `rust/crates/compiled-rules` — `nkdk-compiled-rules` | Результат компиляции каталога; compiler только build-dependency, core — обычная зависимость |

| `rust/apps/mcp` — `nkdk-mcp` | MCP-контракты и подключение общих операций |
| `rust/tools/dev` — `nkdk-dev` | Корпус, проверка покрытия, зависимостей, дублей, e2e, замеры и итоговая приёмка |
| `tests/declaration-corpus/` | Независимые допустимые/ошибочные декларации и ожидаемые диагностики |

Модель компилятора не является универсальной моделью данных конвертера. JSON допустим для отчёта/manifest и MCP, но не промежуточной формой XML→YAML. Подготовленные runtime-входы типизированы и принадлежат операции; сгенерированное правило получает только свой набор входов.

## Проверки каждого законченного слоя

До окончательного удаления TS из корня выполняется существующая `pnpm duplicates -- --base <SHA-до-слоя>`. Текущая `.jscpd.json` покрывает TS/JS, поэтому её успешный результат **не** доказывает отсутствие дублей Rust/YAML. Этап Б добавляет отдельную проверку этих исходников на Rust.

После появления workspace:

```bash
cargo fmt --manifest-path rust/Cargo.toml --all -- --check
cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --locked -- -D warnings
cargo test --manifest-path rust/Cargo.toml --workspace --locked
```

Целевой тест запускается при разработке договора; весь workspace — на границе этапа и при изменении общих интерфейсов. Цель отрицательного теста — содержательная ошибка, а не отсутствующий dependency или сломанная среда. После зелёных проверок без новых оснований не повторять всё бесконечно.

Перед PR/закрытием issue, пока TS присутствует, обязательны действующие `pnpm type-check`, `pnpm test`, `pnpm test:architecture:rules`, `pnpm test:architecture`; LMDB-команды `pnpm test` и `pnpm test:e2e` выполняются вне песочницы. Окончательные Rust-эквиваленты и переход CI определены этапом В. Исходные сбои фиксируются отдельно; их нельзя называть результатом нового кода или игнорировать в итоговой приёмке.

Каждая задача заканчивается просмотром diff, проверкой нового договора, проверкой дублей и локальным коммитом по навыку `commit`. В журнал записываются команды, коды возврата и оставшиеся ограничения; галочка ставится по проверенному результату, не по наличию файла.

## Критерии завершения всей миграции

- Все записи исходного реестра имеют подтверждённое соответствие новой декларации либо явно обоснованы как служебный файл, не требующий отдельного типа; ни одна зарегистрированная операция не исчезла без разбора.
- Отдельные приложения TS/Rust совпадают по договору выходов, диагностик и аномалий на согласованном корпусе и полном e2e; аннотации и XML не нормализуются для сокрытия различий.
- Полные/частичные операции, холодное восстановление состояния, rename/references, Enterprise, платформа, MCP tools/resources/prompts и поддерживаемые транспорты защищены проверками.
- Rust-сборка и тесты проходят в окружении без Node/pnpm/tsx; затем удаляется TS и повторяется приёмка.
- Отчёт приводит время и пиковый RSS законченных операций. Если корректность достигнута, а 10× нет, производительная миграция по этому плану остаётся незавершённой; формулировка «весь проект переведён» не заменяет достижение измеримой цели.
- Для больших конфигураций вывод не делается по одному e2e. Ограничение измерений e2e сохраняется до нового указания пользователя.

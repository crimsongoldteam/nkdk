# Текстовые поля во внешних файлах: план реализации

> **Для исполнителя:** использовать superpowers:executing-plans, выполнять здесь последовательно, без субагентов. Флажок ставить после подтверждённой проверки задачи.

**Цель:** автоматически перенести stringRule.externalFile в декларацию и Rust,
сохранив XML ↔ текстовый файл без потерь и без специального обработчика QueryText.

**Архитектура:** файловое размещение — часть YAML-представления поля. Компилятор
заранее связывает выражения пути; преобразователь получает подготовленные
документы и возвращает FileResult.documents. IO и публикация остаются в
существующей операции приложения; common.external-file продолжает копировать
готовые файлы.

**Технологии:** YAML-декларации, Rust1.98.1, существующие XML/YAML и AOT-механизмы,
Node-переносчик TypeScript AST. Новые зависимости не нужны.

**Спецификация:** [текстовое поле во внешнем файле](../specs/2026-10-09-external-text-fields-design.md), согласована 2026-10-09.

## Ограничения

- Не изменять исходные XML-фикстуры, TypeScript-типы BasePropertyRule/PropertyRule
  и `.agents/architecture.md`.
- Никаких условий по QueryText, DynamicList, каталогу или расширению в общем Rust.
- Путь — последовательность безопасных относительных частей; тот же бюджет
  ограничивает весь набор запросов, не каждое поле отдельно.
- Текстовый файл — UTF-8 без YAML-оболочки; отсутствие и файл размером ноль различаются.
- Отдельные перечни XML-аномалий не добавлять: повтор, атрибуты и форма выводятся
  из декларации и существующего доказательства восстановления.
- Не добавлять интерпретатор YAML при исполнении, повторное чтение XML ради proof
  или копирование полного контекста ради документов.
- Лимит AOT-пакета16МиБ сохраняется. Не выполнять полную сборку workspace ради
  одного договора; использовать адресные кандидаты и общую AOT-сборку.
- Обычные поля без файлового размещения сохраняют прежний путь исполнения.
- Полный DynamicList не принимать до подключения полей, вычисляемых полей,
  параметров и остального договора владельца вместе.

## Что отдельно проверить

| Риск | Обязательная защита |
|---|---|
| Пустой файл исчезает из Snapshot | Задача4: действительно существует файл нулевого размера после публикации |
| Доказательство читает старый файл вместо результата импорта | Задачи2–3: overlay результата имеет приоритет, существующий контекст не копируется |
| Подстановка постоянного parentName скрывает потерю контекста | Задача5: два разных родителя через общий источник контекста |
| Два поля перезаписывают один путь | Задачи2 и4: конфликт диагностируется до публикации, целевые файлы прежние |
| Неизвестный атрибут исчезает при выносе текста | Задача3: файл содержит смысловой текст, primary YAML сохраняет только невосстановимую XML-дельту |

## Задача1. Грамматика файлового YAML-поля и связывание

**Файлы:** `rust/crates/rule-model/src/lib.rs`, `linked.rs`,
`rust/crates/rule-compiler/src/parse.rs`, `link.rs`, `link/resources.rs`,
`schema.rs` и затронутые помощники схемы.
**Проверки:** существующие `tests/external_documents.rs`, `tests/schema.rs`.

- [x] Дополнить матрицу external_documents примером `yaml.fields: [{field: text,
  file: {sequence: [{literal: Тексты}, {concat: [{input: parentName}, {literal: '.txt'}]}]}}]`.
  Получить RED на неизвестной конструкции file.
- [x] Выразить в модели два размещения YAML-поля: ключ либо файл. Разбор требует
  ровно одного размещения; пустой ключ и пустая последовательность пути запрещены.
  Существующие ключевые поля остаются совместимыми.
- [x] Связать файловое выражение как sequence(text) по существующим правилам
  выражений пути ресурсов. Вход/параметр допустим; зависимость от смыслового
  поля и произвольная функция не допускаются начальным профилем.
- [x] Сохранить связанные выражения и их входные зависимости в LinkedEntry;
  не выполнять выражения исходной модели во время исполнения.
- [x] Проверить границу scalar:text. Число, boolean, запись, коллекция и
  несовместимые key+file получают диагностику при сборке. До генерации кода
  новая форма не должна молча считаться обычным ключом.
- [x] Получить GREEN parsing/linking; схема основного YAML не требует
  файлового поля как ключа. Его чтение и проверка входят в скомпилированную validation.

## Порядок запуска

Исполнять задачи1–6 последовательно здесь без субагентов. Сначала RED→GREEN
на адресном договоре; широкий прогон после законченного слоя. Не запускать
одновременно полный pnpm test и сборки/замеры Rust. Журнал решений держать
в `.superpowers/sdd/2026-10-09-external-text-fields/progress.md`.

Сборка: `cargo +1.98.1 ... --offline --manifest-path rust/Cargo.toml
--target-dir rust/target/migration-contracts -j1`; конкретные `--test` выбирать
по изменённой существующей матрице. Не очищать target без необходимости,
не повышать память/лимит пакета ради завершения проверки.

Коммиты, push и PR не входят в этот шаг: сохранённые изменения остаются
reviewable в текущем отдельном worktree, без смешивания с develop.

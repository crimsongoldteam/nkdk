# Память `rustc` при проверке миграционных деклараций

28 сентября 2026 года общий проверочный пакет для 12 сценариев документа
содержал 258 объявлений и породил `generated.rs` размером 104 МБ. `rustc`
был завершён системой с `SIGKILL`; при наблюдении пользователя его память
достигала 25 ГБ. Причина в том, что сборщик выпускал Rust-код для каждого
объекта во входном каталоге, включая объекты, которые не являлись точками
входа проверяемых сценариев.

Сборщик теперь вызывает `compile_exporting` с явным списком преобразуемых
объектов и источников фактов. Все запускатели миграционных проверок передают
этот список. Сборка отклоняется до запуска `rustc`, если `generated.rs`
превышает 40 МиБ; отчёт `generation-sizes.tsv` показывает крупнейшие части.
Набор из нескольких сценариев всегда запускается последовательно по сценариям,
а не одним тяжёлым процессом компилятора. Число объявлений само по себе не
показывает объём создаваемого Rust-кода, поэтому порог по числу объявлений
не защищал бы другие семейства.

Раздельная сборка также обнаружила зависимость от случайно включённых соседних
правил: компилятор раньше предполагал, что у каждого читаемого индекса есть
производитель в этом же пакете, и аварийно завершался для пустого индекса.
Теперь каталог индексов включает и явно объявленные входы; пустой индекс
создаётся с его объявленной формой ключа. Проверка ссылки на команду документа
прошла без дополнительного фиктивного источника данных.

| Проверка | Код до | Код после | Пик `rustc` после |
|---|---:|---:|---:|
| Полный прежний пакет документа | 104 МБ | разбит на отдельные сценарии | общий прежний процесс убит по памяти |
| Заполненная табличная часть каталога | прежний размер не замерен | 15 МБ | 4,54 ГБ |
| Документ с двумя коллекциями | 49 МБ до исключения повторных источников фактов | 28,6 МБ | 4,35 ГБ |

Пики сняты обёрткой `tools/rust-build-profile/rustc-wrapper.py` для процесса
`nkdk_migration_contracts` через `getrusage`; это максимальный RSS одного
процесса, а не сумма стадий. Оба указанных сценария прошли XML ↔ YAML.
После исправления пустых индексов последовательно прошли все 12 сценариев
семейства документа. Самый тяжёлый совместный сценарий повторно измерен на
окончательном коде: 4 348 428 288 байт RSS и успешный XML ↔ YAML. Предыдущие
5,76 ГБ относились к промежуточному состоянию сборки.
Изменение ограничивает сборку; в исполняемом преобразовании нет нового
интерпретатора или дополнительного перехода между языками. Пик 4,35 ГБ
остаётся высоким: крупнейшие части совместного объекта занимают 13 и 7,7 МБ
созданного кода. Их повторное использование требует отдельного проверенного
изменения генератора с замером скорости XML ↔ YAML.

# Размер генерации Rust-каталога

Замер 2026-09-23 на `codex/common-declarative-spec`: тот же набор из 262 YAML-файлов, что у `nkdk-compiled-rules-probes`. Команда: `cargo build -p nkdk-rule-compiler --example profile`, затем `target/debug/examples/profile probes`. Полный машинный отчёт с каждым объектом и размером составных частей — [generation-size.json](2026-09-23-rust-generation-size.json).

Разбор и связывание 1814 деклараций заняли 0,49 с; генерация при исходном замере — **47,38 с** (повтор с подробным разделением — 46,74 с). Пик памяти процесса генерации в исходном замере — **243 МБ**. Результат занимает **46,92 МБ**: `generated.rs` — 31,43 МБ, двоичные автоматы и остальные файлы — 15,49 МБ. Сумма строк подробного отчёта точно равна сумме размеров созданных файлов.

Владельцы разделены на варианты, вложенные записи и каркас. В каждой из трёх проекций `MetadataValue` варианты `fixedArray` и `formChoice` дают примерно 0,93 и 0,91 МБ. Выборочная проверка созданного Rust-кода показала, что тела этих вариантов в трёх проекциях текстуально совпадают после замены только служебных числовых имён. Это основание проектировать общий модуль для одинаковой специализации, но не доказательство, что все параметры можно объединить: нужны исполняемые проверки и замер XML ↔ YAML. Размер двоичных автоматов учитывает обе версии для порядка байтов и не является размером Rust-исходника.

## Сборка

Контрольная сборка `nkdk-compiled-rules-probes` выполнена на Rust 1.97.1 с одним заданием Cargo, выключенными incremental и отладочной информацией. Изолированный каталог результатов гарантировал чистый первый прогон. Затем изменена только отметка времени `font-reference.yaml`. [Машинные измерения](2026-09-23-rust-build-baseline.json).
[Исходные журналы сборки](2026-09-23-rust-build-logs.tar.gz) сохранены отдельно.

| Этап | Чистая сборка | После одного YAML |
|---|---:|---:|
| Cargo целиком | 2 мин 48 с | 147,4 с |
| Генерация деклараций | 48,3 с | 48,1 с |
| `rustc` для каталога | 102,7 с | 97,3 с |
| Пиковая память `rustc` | 4,78 ГиБ | 5,23 ГиБ |

Первый повторный замер захватил также форматирование исходников и исключён; в таблице только повтор с изменением YAML. Он почти столь же дорог, как чистая сборка: причина — единый созданный файл и пересборка всего проверочного пакета. Отдельный небольшой каталог для `Font` создаёт около 256 КБ Rust-кода и пересобирается примерно за 3 секунды после изменения декларации. Это подтверждает направление разделения каталога, но не измеряет выигрыш для всего проекта.

## Контроль работы XML → YAML

Для будущего сравнения сохранён независимый профиль действующего TypeScript-маршрута: собранный MCP импортировал реальный `e2e/fixtures/xml/cf` в отдельный временный YAML-каталог, два запуска в одном процессе с тремя работниками. Холодный запуск — **5,847 с**, тёплый — **2,583 с**; каждый обработал 306 файлов с одной существующей предупреждающей записью и без ошибок. Пиковая RSS процесса — **1757,6 МиБ**. [Полный профиль](2026-09-23-ts-import-baseline.json), [исходные журналы](2026-09-23-ts-import-logs.tar.gz).

Это база только для XML → YAML в текущем TypeScript-приложении. Весь каталог ещё не проходит производственный Rust-маршрут; сопоставимый Rust e2e и YAML → XML пока не измерены. Поэтому заключения об ускорении преобразования или достижении цели 10× из этих цифр не следуют. При приёмке нового способа генерации нужно запускать одинаковые реальные входы в обе стороны и сверять результат вместе с аномалиями.

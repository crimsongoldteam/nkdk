# Оставшиеся зависимости значений перечисления

Повторный выпуск из `rules-extraction.json` с проверкой хешей исходников:
`MetadataEnumerationRules.enumValues` блокируют только UUID, состояние связи
с базовой конфигурацией и вклад коллекции в данные владельца. Привязки имени
элемента и языков уже проходят существующий автоматический выпуск.
Семейство ещё не принято; общий результат выпуска — 0/142 связей.

## UUID

Исходники: `packages/rules/metadata/commonObjects/uuid/fromXML.ts`, `toXML.ts`,
`rule.ts`. Импорт принимает текст, без проверки формата GUID; отсутствующее
значение остаётся отсутствующим. В YAML обычного поля UUID нет. Экспорт
использует сохранённую идентичность, а при её отсутствии — существующий
договор создания идентификатора. Внешний индекс получает итоговый UUID.

Нельзя объявить UUID обычной строкой и считать перенос законченным:
нужны импорт в индекс, восстановление при экспорте и область владельца.
Нельзя добавлять новую проверку GUID под видом переноса старого поведения.

## Связь с расширяемой конфигурацией

`runtimeOnly` не означает отсутствия поведения. Смысл описывается двумя
признаками: наличие UUID базового объекта и режим проверки.
В таблице `Поле` обозначает `ОбъектРасширяемойКонфигурации`.

| UUID базы | Режим | Существующий YAML |
|---|---|---|
| Есть | Контроль | Поле отсутствует |
| Нет | Контроль | `Поле:` |
| Есть | Уведомление | `Поле: !проверять` |
| Нет | Уведомление | `Поле: !проверять ""` |

Источник и готовые ожидания:
`packages/rules/metadata/appliedObjects/configurationExtension/extendedConfigurationObjectYAML.test.ts`.
Это смысловой тег, а не аномалия. Пустое поле и пустая строка различаются.

Независимый XML-экспорт уже проверяется в
`packages/rules/metadata/appliedObjects/configurationExtension/exportPropertyStates.test.ts`
в таблице `writes ExtendedConfigurationObject: $uuidPresent $mode`:
`Properties.ExtendedConfigurationObject` появляется при наличии UUID базы;
`InternalInfo.xr:PropertyState` с состоянием `Notify` — в режиме уведомления.
Применимость импорта определяется в `propertyStates.ts`: для расширения
конфигурации либо заимствованного объекта. Эти условия должны находиться
в декларации/данных переноса, не в общем Rust-исполнителе.

Для реализации использовать общий договор конечных состояний,
предусмотренный разделом 8 спецификации языка. Сначала записать полный
двунаправленный пример с применимостью и источником UUID; нельзя свести
его к отдельному обработчику `extendedConfigurationObject` в генераторе.

## Владелец коллекции и проверки

`ownerFactRole: enumValues` и `configurationIndexUidSegment: Значение`
описывают дополнительные связи. Произвольная склейка имени через точку
не заменяет существующее экранирование логического адреса.
Проверки идентичности должны различать собственный и базовый компоненты,
двух владельцев с одинаковым именем элемента и независимый экспорт YAML.

Матрица четырёх состояний проверяется один раз на общем механизме.
Для значения перечисления остаётся проверить параметры подключения,
источник UUID и работу внутри коллекции. Старые отрицательные ожидания
с ошибками нельзя автоматически объявлять принятой семантикой Rust:
сначала сопоставить их согласованному договору аномалий.

### Уточнение создания новых идентификаторов

В обычном экспорте через configurationIndex новый UUID не является отдельным
случайным вызовом на каждое поле. `configurationIndex/exportRuntime.ts`
вычисляет SHA-256 от 32 байт operationSeed, нулевого байта, вида идентификатора,
нулевого байта и UTF-8 логического адреса. Для UUID берутся первые 16 байт,
устанавливаются биты версии 4 и варианта RFC; xmlId использует 16 байт hex,
configVersion — 20 байт hex. Существующая идентичность имеет приоритет;
результат вновь записывается в collector. Повторные обращения к одному адресу
внутри операции стабильны, другое operationSeed даёт другой результат.

Это проверяемый исходный договор, а не новый алгоритм генерации. `sha2 0.10.9`
уже является зависимостью conversion-core; для самого вычисления новой
внешней библиотеки не требуется. Генерация случайного operationSeed и
сохранение итогового индекса относятся к подготовке/завершению операции,
а не к обработке каждого scalar-поля. Соответствие после переименования
определяется существующей картой referencePathByCurrentPath до генерации.

## Полный пример границ следующего отношения

Для заимствованного объекта с известной базовой идентичностью `base-id`
и XML-полем `ExtendedConfigurationObject` должны работать четыре независимых
направления из таблицы выше:

- `Поле` отсутствует: экспортирует `<ExtendedConfigurationObject>base-id</ExtendedConfigurationObject>`,
  не создаёт запись режима для этого свойства.
- `Поле:`: не экспортирует ссылку и запись режима.
- `Поле: !проверять`: экспортирует ссылку `base-id` и строку
  `<xr:PropertyState><xr:Property>ExtendedConfigurationObject</xr:Property><xr:State>Notify</xr:State></xr:PropertyState>`.
- `Поле: !проверять ""`: экспортирует только эту строку режима.

Ссылка находится под `Properties`, строка режима — под `InternalInfo`.
Это две проекции одного смысла, а не строковая подстановка тега. При импорте
наличие ссылки определяет первый признак, наличие соответствующей строки
`Notify` — второй. Значение ссылки сохраняется в базовом индексе, не в YAML.
Соседняя строка режима другого свойства не принадлежит этому отношению:
её нельзя удалить, поглотить или переписать при сборке результата.

Применимость задаётся объявленным профилем владельца. Старый импорт
`propertyStates.ts` проверяет вариант `adopted`, затем поддержку служебных
свойств; у корня расширения есть собственное объявленное применение.
Отсутствие профиля нельзя заменить веткой по имени объекта в исполнителе.
Неверные состояния исходных данных сохраняются по принятому общему договору
аномалий, хотя прежние TS-тесты ожидали исключение. Недостающий подготовленный
индекс остаётся ошибкой подготовки, а не аномалией значения.

Реализация таблицы должна проверять однозначность обеих проекций при сборке.
Четыре строки не дают права молча выбирать первую при совпавших условиях.
Неизвестный тег, повтор строки режима и лишние XML-данные должны пройти общий
контроль обратимости; специального списка аномалий для этого объекта нет.

Проверочные источники: `extendedConfigurationObjectYAML.test.ts` (четыре
кодировки и недопустимые формы), `exportPropertyStates.test.ts` (независимый
XML-экспорт), `propertyStates.test.ts` (применимость и соседние свойства).
Этот пример фиксирует исследованный договор, но не объявляет поддержку
`state-relation` реализованной и не снимает блокировку автоматического выпуска.

# Общие декларации и регистрации СКД

Исходный `dataCompositionSystem/index.ts` подключает регистрации частей СКД.
В нём нет преобразователя полного XML-документа DataCompositionSchema.
Готовность отдельных библиотек, их регистрации и полных владельцев проверяется
раздельно. Корневой флажок пока остаётся пустым: новое подключение не означает
приёмку всей схемы, формы и её состояния в расширении.

## Что опубликовано

| Исходный тип | Общая декларация | Проверяемая граница |
|---|---|---|
| ConditionalAppearance | common.conditional-appearance | Все 4 свойства; реальное свойство формы |
| CalculatedField | common.calculated-field | Все 9 свойств из прежнего rules.ts |
| DataCompositionSchemaDataSetField | common.data-composition-schema-data-set-field | Все 15 свойств; три вида поля |
| OrderItemFields | common.dcs-order-item-fields | Соответствие старого имени принятой коллекции |
| StructureItemGroupCollection | common.group-item-collection | Соответствие старого имени принятой коллекции |

Библиотеки получены общим `relativeSourceProjection`. Они содержат относительные
XML-пути и ссылки на общие типы. Индексы задаются на границе владельца;
внутри библиотеки остаются типизированные входы. Переносчик подключает эти
договоры обычным `mapProperty`; частных ветвей Rust не добавлено.

## Размещение и тип XML

Непрефиксованные элементы наследуют пространство имён владельца. При сборке
проекции оно передаётся явно как `defaultXmlNamespace`; переносчик квалифицирует
пути, сохраняя уже префиксованные элементы и непрефиксованные атрибуты.
Это проверено на `Form/Attributes/ConditionalAppearance` и на зарегистрированной
коллекции `DynamicListRules.fields`: элемент `Field` здесь находится в
пространстве имён формы. Исходные XML не изменены; для проверок в памяти выбран
один участок формы, полная форма не принимается этим примером.

У поля набора данных свойство `Вид` само записывает `xsi:type`. Первичная
публикация ошибочно добавила также постоянный тип из владельца. Линкер выявил
двух владельцев атрибута. Общая проекция теперь добавляет постоянный тип только
при отсутствии соответствующего свойства на той же границе. Прочие владельцы,
например сравнение отбора, сохраняют свой постоянный тип. Регрессия проверяет
оба случая; исключений по имени объекта нет.

## Проверка исходных регистраций

[Снимок](2026-10-09-dcs-registration-audit.json) содержит 32 имени, найденных в
вызовах `definePropertyTypeRule`, `defineMetadataItemRule` и
`defineMetadataItemCollectionRule`. Для каждого сохранены исходные файлы,
регистрация коллекции и использования из извлечённых rules.ts. Это аудит этих
трёх способов регистрации; проверки схем из `defineMetadataRules` и полная
приёмка владельца этим числом не подменяются.

- CalculatedFields, DataSetFieldFields и DCSParameters собираются по исходной
  регистрации коллекции и месту в DynamicListRules. Обычный mapProperty без
  подготовки владельца не обязан выбирать готовую коллекцию по одному имени.
- MetadataDcsMetadataValue требует профиль значения; SettingsParameterValue
  требует также имя параметра и включение в коллекцию. Все 12 свойств оформления
  имеют известные профили, но отдельное сопоставление сообщает
  `dcs-parameter-collection-required`. Это требование сборки, а не отсутствие
  преобразования. SettingsParameterValueCollection распознаётся с обеими
  реальными таблицами Field/Primitive.
- Внутренние варианты значений отбора не встречаются отдельными свойствами
  извлечённых rules.ts: они выбираются декларативным договором FilterItem.
- Старый отчёт emitCollections может показывать препятствие у коллекции,
  которая уже перенесена общей декларацией: например, исходный callback или
  отсутствие самостоятельного XML-корня. Для orderExpressions, FilterItem и
  OrderItemFields действует опубликованный договор. Такие строки нельзя
  считать потерянными свойствами или автоматически заменять аномалией.

## Проверки

Итоги приёмки 2026-10-09: 10/10 договоров условного оформления, 6/6 вычисляемых
полей и 13/13 полей набора данных прошли через общие AOT-пакеты. Прошли также
90 проверок переноса/публикации/сборки коллекций, 30 проверок схем, Clippy core и
компилятора с `-D warnings`, обе проверки архитектуры TypeScript и проверка
архитектуры Rust. Новых дублей относительно
`91a01277cbd10ccebd70bb0b4e7a32886dcf090f` нет; полный `pnpm test` завершился
с кодом 0 после окончания Rust-сборок. Пропуски, уже настроенные в проекте,
и мягкие предупреждения о длительности не означают проверку пропущенных сценариев.

Проверки нового кода
расширяют существующие матрицы. Исходные фикстуры неизменны. Проверочные
семейства используют общие AOT-пакеты с ограничением 16 МиБ, один процесс
компиляции; монолитная проверка вычисляемых полей остановлена и заменена этим
путём. Полный pnpm test запускается отдельно от Rust-сборок.

Этот блок изменяет сборку деклараций и проверочные подключения, а не
исполняющий движок. Предыдущие release-замеры не являются замерами всего
каталога или подтверждением цели 10×.

Реальная коллекция выявила дополнительный общий пропуск: emitCollections
вызывал mapProperty без списка соседних свойств. Условие по собственному
`Вид` превращалось во внешний `ownerKind`. Теперь список передаётся тем же
общему сопоставлению, что используется для одиночной записи. Регрессия
запрещает этот лишний вход в зарегистрированной коллекции; в Rust условий
по типу поля или владельца не добавлено. Новый YAML-пример библиотеки имеет
обычное именованное свойство; обработка порядка всего документа проверяется
на исходной границе владельца, без искусственной проекции пометки свойства
на корень YAML-документа.


Фактический максимальный размер создаваемого Rust в пакете каждого из трёх
каталогов — 2 293 497 байт, ниже предела 16 МиБ. Включая общий входной пакет,
получились 897/415/630 пакетов соответственно. Это размеры генерации,
а не замеры пика памяти. Предупреждения о неиспользуемых переменных в
создаваемом коде остаются; Clippy собственных core/compiler прошёл отдельно.

Во время приёмки закончился диск: старые завершённые проверочные исполняемые
файлы в target очищены, исходники и библиотеки не удалялись. Неудачную сборку
с повреждённым файлом не считали прохождением тестов; заключительный запуск
действительно выполнил все 13 случаев. Все шесть проверок актуальности
публикаций прошли; исходные XML-файлы имеют пустой git diff.

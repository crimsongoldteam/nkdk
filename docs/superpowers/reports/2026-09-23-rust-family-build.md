# Проверка раздельной сборки деклараций

Вместо ручного перечня YAML пакет получает корневые идентификаторы. Общий сборщик читает связи `imports`, выбирает только необходимые исходные файлы и нужные системные перечисления, затем регистрирует в Cargo только выбранные файлы. Полный синтаксический разбор выполняется лишь для выбранных файлов: ошибочный YAML вне семейства его не ломает. Сам компилятор деклараций остаётся общим. Проверены пакет `Font` (запись и выбор варианта) и отдельная коллекция `MetadataFields`; их зависимости и исполняемость проверены тестом компилятора.

Изменение только отметки времени YAML на той же машине и в одном кэше Cargo:

| Изменён файл | `Font` | `MetadataFields` |
|---|---:|---:|
| `font-reference.yaml` | пересборка 2,292 с | без пересборки 0,039 с |
| `metadata-fields.yaml` | без пересборки 0,038 с | пересборка 1,026 с |

Отдельный замер пакета `Font` после его YAML: весь Cargo — 2,201 с, собственный `rustc` — 0,586 с, пик RSS этого `rustc` — 278 347 776 байт (0,26 ГиБ). Для сравнения, полный проверочный каталог после одного YAML занимал 147,4 с и 5,23 ГиБ RSS `rustc` ([исходный замер](2026-09-23-rust-generation-size.md)). Разница показывает пользу разделения рабочего цикла, но **не** является ускорением всего приложения: производственный каталог пока остаётся монолитным.

Проба более компактной таблицы перечислений уменьшила созданный код `Font` с 261 217 до 260 581 байта, лишь на 636 байт. Для крупного искусственного вложенного перечисления выигрыш был около 8%; этого недостаточно, чтобы делать её основным средством ускорения, поэтому изменение отклонено. Следующий шаг — разделить производственный маршрут и проверить общие операции на больших составных записях и коллекциях без замедления XML ↔ YAML.

Повторное использование текстуально одинаковых вариантов выбора проверено отдельно на одном Rust 1.98.1 и тех же параметрах сборки ([измерения](2026-09-23-choice-sharing-comparison.json)). Созданный каталог уменьшился на 0,53 МБ, `rustc` работал 90,6–93,6 с вместо 103,7 с. Но пиковая память в двух прогонах составила 4,96 и 5,37 ГБ вместо 4,79 ГБ без объединения. Механизм потребовал дополнительного состояния генератора и распознавания служебных имён в созданном коде. Для поставленной цели снижения памяти и простоты изменений этот обмен не подходит, поэтому пробный механизм удалён.

Производственный пакет больше не следит за всем каталогом `declarations`: принятые пробные YAML перечислены по файлам, а каталоги `common`, `fragments`, `objects` и `resources` сохраняют автоматическое обнаружение новых файлов. Изменение неподключённого `probes/metadata-value.yaml` оставило пакет `nkdk-compiled-rules` готовым (`Cargo: Fresh`, 0,08 с); изменение принятого `probes/additional-indexes.yaml` запустило его пересборку на 2 мин 46 с. Это устраняет лишнюю полную сборку при работе над пробными декларациями, но изменение принятого common по-прежнему пересобирает крупный производственный каталог.

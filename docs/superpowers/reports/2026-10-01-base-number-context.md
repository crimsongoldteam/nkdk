# Отсутствующий контекст зависимого числа

При условной границе значение соседнего свойства берётся из локального
объекта, затем — из подготовленного индекса основы заимствованного объекта.
Собственный объект использует исходное объявленное умолчание. Если у
заимствованного объекта нет ни локального значения, ни факта основы,
проверка выдаёт `base.context.missing`, вместо молчаливого пропуска границы.
Сам переносчик не подставляет предполагаемый тип числа.

Это обычное условие декларации с проверками присутствия и поиском в индексе.
Никаких условий по DocumentNumerator или NumberType в Rust не добавлено.
То же условие участвует в сокращении истории: если число сохраняется как
аномалия, его строка состояния остаётся явной и XML восстанавливается.
Не допускается использовать аномалию вместо подключения полного индекса:
в проверочном случае отсутствие доказано удалением элемента из копии
реальной основы в памяти; исходные XML-фикстуры не менялись.

Проверены две разные ситуации на нумераторе:

- Тип есть локально, но отсутствует в основе: исходный XML преобразуется
  обычно; удаление локального типа из обычного YAML даёт точную диагностику.
- Тип отсутствует и локально, и в основе: XML сохраняется с аномалией числа
  и явной историей, восстанавливается без референса. Обычный YAML получает
  ту же диагностику. При явном локальном типе «Число» длина 38 допустима,
  длина 39 даёт `number.maximum`; проверяется также экспорт допустимого YAML.

Оба случая получены из неизменённых e2e-файлов с отмеченным изменением копий.
Исходный отрицательный прогон принял YAML без контекста; после исправления
тот же сценарий прошёл с ожидаемой диагностикой.

Числовой реестр содержит 13 сценариев; с InputByString — 75. Это проверки
кандидатных деклараций и их композиции, не полная приёмка новых владельцев.
Флажки чеклиста не меняются.

## Следующее подключение

Рабочие маршруты проекта сейчас включают DefinedType. Добавлять маршрут
нумератора или документа только с проверенными числовыми полями нельзя:
это потеряет остальные свойства. Сначала требуется полная сборка выбранного
владельца из деклараций, его фактов и вложенных объектов, затем маршрут.
Поле compatibility_mode в проектном контексте уже существует, но само по
себе не доказывает получение версии из конфигурации и полноту преобразования.

Для следующего полного владельца исследован нумератор документов: 12
исходных свойств, внешних ресурсов нет. Простая генерация пока блокирует
numberLength, xmlRoot и extendedConfigurationObject. Кроме проверенных
числа и его типа, пометки объявлены у numberAllowedLength, numberPeriodicity
и checkUnique; их обычные кандидатные декларации не заменяют этот договор.
Следующий блок должен закрыть их одним общим шаблоном скалярных состояний
и принять нумератор целиком, прежде чем включать проектный маршрут.


## Проверка результата

Прошли 13 числовых сценариев и повторные проверки справочника, документа
и составной декларации документа; финальный сценарий отсутствующего типа
дополнительно проверяет допустимый локальный тип и границу 38/39.
Пять проверок переносчика, три генератора --check, архитектура TS/Rust,
поиск новых дублей относительно 2af2 и git diff --check прошли.

Два полных pnpm test остановились на временных лимитах в разных прежних
тестах; функциональные утверждения до остановки прошли. Отдельный повтор
этих двух файлов (20 тестов) и worker.integration прошёл с теми же лимитами.
На машине одновременно есть другие процессы с высокой загрузкой CPU;
это возможный источник разброса, но причинная связь не доказана.
Лимиты не менялись, чужие процессы не останавливались. Полный набор в этом
блоке не объявляется зелёным; флажки полной приёмки не добавлены.

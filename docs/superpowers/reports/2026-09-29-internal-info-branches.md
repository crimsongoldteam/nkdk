# InternalInfo: ветви и оставшаяся граница

Переносчик читает `InternalInfo` из исходных `rules.ts`: все 45 найденных
применений распознаны без выполнения предметных функций при преобразовании.
Общий фрагмент `GeneratedType` дополнен декларациями `ThisNode` и
`ContainedObject`. Восстановление использует подготовленные индексы UUID;
обычный YAML этих служебных значений не содержит.

Пятьдесят проверок семейства охватывают XML → YAML → XML без XML-референса:
все 45 исходных применений `InternalInfo`, конфигурацию cf/cfe с
`ContainedObject` и план обмена cf/cfe с `ThisNode`. XML взят из неизменённых
e2e-фикстур; некоторые дополнительные формы получены преобразованием их копий.
Добавлены справочник, константа, регистр бухгалтерии, регистр сведений,
отчёт, план видов расчёта и план видов характеристик: проверены списки
длиной 1–8 и 11 строк,
но используется один механизм вывода из `rules.ts` и один Rust-маршрут.
Вложенный канал сервиса интеграции, перерасчёт и табличные части десяти
владельцев проверены отдельно: составные имена восстанавливаются из имён
родителей и элементов без вызова старых функций `getName`. Проверены все
корневые владельцы с реальными e2e XML, куб и коллекционные формы куба,
таблицы и таблицы измерения внешнего источника. Последние используют свой
объявленный XML-корень, полученный проекцией неизменённой фикстуры. Базовое
правило табличной части не задаёт стандартных типов: два типа реального XML
остаются явным списком YAML без сырой пометки. Каждый сценарий подготавливает
индексы только из собственного источника, чтобы независимые владельцы не
создавали ложных коллизий UUID при пакетном запуске.
Дополнительный `ContainedObject`, отсутствующий в списке стандартных классов,
остаётся читаемым в YAML и восстанавливается в XML без сырой XML-пометки.
Перестановка двух стандартных `ContainedObject` также сохраняет порядок без
сырой пометки; оба случая используют XML, полученный из неизменённой e2e-фикстуры.
Совмещённые ветви сохраняют оба вклада в индексы; отдельная проверка ловит
потерю одного из них. Общий компилятор сообщает диагностическую ошибку для
неподдержанной скрытой коллекции вместо аварийного завершения.
Дополнительная проверка повторяет настоящий `GeneratedType` из e2e XML:
при неоднозначном индексе компилятор не сокращает явный список до значения
по умолчанию, поэтому YAML сохраняет оба вхождения и их порядок. Это общее
правило сокращения коллекций, а не особый обработчик `InternalInfo`.
Ещё один сценарий добавляет неизвестный атрибут к первому `GeneratedType`
в копии e2e XML. Общий механизм сохраняет его через `!xml/raw` для списка
`ВнутренниеТипы`, оставляя все обычные строки в `$значение`, а обратное
преобразование восстанавливает атрибут. Сама декларация аномалию не перечисляет.
Граница сохранения пока охватывает список; локальное сохранение одной строки
остаётся возможным улучшением размера YAML, но не условием обратимости.
После добавления всех владельцев прошли 50 проверок семейства, проверки
переносчика, полный `pnpm test`, `pnpm type-check` и поиск дублей. Тесты
`nkdk-rule-compiler`, проверка архитектуры Rust и форматирования проходили
после предыдущего изменения общего механизма; Rust-компилятор в этом слое
не менялся.

Флажок `commonObjects/internalInfo` остаётся пустым. Проверка всех существующих
владельцев не охватывает создание каждого нового владельца без прежнего снимка:
для них UUID пока нет в индексах, а декларация требует их наличия.
Проектный маршрут различает новый YAML и удалённый снимок известного владельца.
Для нового определяемого типа `cf` общее выражение `identity` в декларациях
создаёт UUID владельца, TypeId и ValueId из seed операции и логических адресов.
Полный YAML-снимок записывается до XML. Проверены два последовательных
экспорта, повторный импорт созданного XML и ещё один экспорт: UUID и XML
сохраняются. Для нового собственного `cfe` базовая связь не создаётся;
для нового заимствованного `cfe` её UUID берётся из подготовленного снимка
одноимённого владельца явно переданного проекта `cf`. Повторный экспорт
использует сохранённую связь. После этого остаются создание остальных видов
владельцев и отклонения XML всех трёх ветвей; только затем можно обновить флажок и
реестр покрытия. `PropertyState` внутри того же XML-элемента обрабатывает
декларация владельца расширения: исходный common-обработчик читает только
идентичности и не интерпретирует состояния свойств. Проверять `PropertyState`
нужно при приёмке владельцев, не в зачёт этого common.

Перечень импортированных владельцев сохраняется рядом со снимками. Удаление
снимка известного пути не превращает его в новый и не создаёт другие UUID.
Для старого проекта без перечня отсутствие снимка остаётся ошибкой, а
существующий снимок продолжает работать. Подготовка нового `cf` использует
этот общий маршрут проекта, а не обработчик `InternalInfo`.

Для следующего владельца, `Enum`, добавлены декларативные источники UUID.
Генератор читает `rules.ts`, а не повторяет вручную список его трёх
`GeneratedType`: `EnumRef`, `EnumManager`, `EnumList`. Одна функция построения
деклараций используется также источниками `DefinedType`. Проверены создание
всех семи UUID без XML и подготовка индексов владельца/типов из неизменённой
e2e-фикстуры перечисления. Это ещё не создание нового перечисления в проекте:
полная декларация его свойств и маршрут XML ↔ YAML отсутствуют. Поэтому
`commonObjects/internalInfo` и родительское перечисление остаются без флажков.

# `metadataRef`: реальные типизированные ссылки

[Проверка](../../../tools/rules-migration/src/metadata-ref-check.mjs) извлекает
уникальные `<xr:Item xsi:type="xr:MDObjectRef">…</xr:Item>` и другие
типизированные ссылки из неизменённых e2e XML конфигурации и расширения.
Она запускает общий Rust-договор в обе стороны без XML-референса и требует
обычный YAML без `!xml`. Сейчас проходят **94 уникальные ссылки списка и
3 одиночные ссылки**.
Отдельный случай с недопустимым корнем в ссылке на роль автоматически
сохраняется как `!xml/raw`. Проверены также ограничения, автоматически
извлечённые из `metadataTarget.roots`: одиночная ссылка на `Document`, список
ссылок на `Catalog` и оба неверных корня. Неверные корни становятся
`!xml/invalid` и восстанавливаются из YAML. Из настоящих `rules.ts`
конфигурации перенесены также обязательный `DefaultLanguage` и пустой
`DefaultInterface`; отсутствие обязательной ссылки регистрируется и
восстанавливается без падения.
Сверка с сохранённым извлечением `rules.ts` показывает шесть свойств,
которые теперь автоматически получают эту декларацию: две ссылки
конфигурации, язык расширения, задача бизнес-процесса и две ссылки задачи.
`Document.RegisterRecords` теперь переносится из `rules.ts` автоматически:
четыре допустимых корня передаются как значения декларации, а пустые значения
обычного и заимствованного документа дают один пустой XML-контейнер.
Проверены реальные имена двух регистров и пустой контейнер из неизменённого
e2e XML, а неверный корень становится аномалией и восстанавливается.
Передача сведений
`ownerFactRole=registerRecords` в составном документе ещё проверяется отдельно.
Для `metadataTarget: {kind: object}` без перечисления корней добавлены
`common.metadata-object-link` и его коллекция. Вид объекта не ограничивается,
но само имя проверяется по индексу. Все 34 таких свойства теперь распознаются
автоматически. Для двух свойств измерения куба общее условие наличия свойства
переносится как декларация: отсутствующее значение не создаёт XML-элемент.
Это проверено на состоянии из настоящего e2e XML. Заполненных значений этих
двух свойств в корпусе нет. Отдельно проверен составленный из настоящей ссылки
последовательности пример с обоими заполненными полями; это проверка общего
договора, а не доказательство формы XML измерения куба. Поэтому приёмка
остаётся открытой.
На e2e XML конфигурации проверены `DefaultRoles` и `DefaultStyle`, а в
расширении — его `DefaultRoles`; ссылка на несуществующий стиль сохраняется
как обратимая аномалия. Проверены также оба списка последовательности,
базовые виды расчёта и обязательная ссылка в составе плана обмена.
Шесть коллекций с явно указанным владельцем теперь распознаются из `rules.ts`
через одну декларацию ссылок на членов. Она принимает прямой и вложенный
путь без отдельных ветвей Rust. На неизменённых e2e XML проверены заполненный
и пустой `Content` критерия отбора, `DocumentMap` и `RegisterRecordsMap`
измерения последовательности. Ограничения целевого члена и подключение
индекса владельца ещё не приняты.
Пять ссылок отчёта на свои или общие формы теперь используют существующий
общий выбор. Пустой вариант добавлен декларативно, с явным запасным разбором
короткого имени. Проверены пять XML-свойств настоящего отчёта и явная пустая
строка YAML для дополнительной формы.
Форма выбора документа теперь переносится из `rules.ts` в уже существующий
общий выбор своей, общей или журнальной формы. Пустой вариант определён в
той же декларации. Обычная и пустая формы проверены на неизменённых e2e XML.
Два договора измерения адресации задачи проверяют заполненное и пустое
значение из настоящего XML. Ограничения допустимого корня
`InformationRegister` и вида члена `Dimension` переносчик выводит из
`metadataTarget` в `rules.ts`; неверные значения отклоняются при проверке
YAML. Отдельного обработчика в Rust для этого свойства нет.
Основная схема компоновки отчёта перенесена тем же способом для дочернего
элемента своего владельца: XML содержит полный путь
`Report.<имя>.Template.<макет>`, YAML — имя макета. Общая декларация
`common.owner-member-link` восстанавливает пропущенные части из входов и
проверяет имя по коллекции дочерних элементов. На неизменённом e2e XML
проверены заполненная ссылка, пустой элемент и отклонение отсутствующего
макета. Одиночное измерение регистра внутри перерасчёта использует ту же
декларацию: корень `CalculationRegister` и вид `Dimension` берутся из
`metadataTarget`, имя регистра — из контекста владельца. Проверка на
неизменённом e2e XML восстанавливает короткий YAML и отклоняет неизвестное
имя измерения. Условие `toXML: hasOwnProperty(…)` переведено в общее
декларативное условие наличия поля.
Список ведущих данных перерасчёта теперь также извлекается из `rules.ts`:
одно общее текстовое правило сокращает ссылку на собственное измерение,
а ссылку на другой регистр оставляет полным путём. Обе строки взяты из
неизменённого e2e XML; проверены обратное преобразование без XML-референса
и отклонение неверного корня или вида члена. В Rust добавлен общий режим
необязательного фрагмента YAML для парных текстовых шаблонов, без условия
по имени перерасчёта. Список `Использование` параметра функциональных опций
повторно использует `common.metadata-item-links`: два e2e XML проверяют
ссылку на целый справочник и смешанный список справочника с измерением
регистра. `StandardAttributeDescription.choiceForm` проверен по реальному
`xr:ChoiceForm` справочника: существующая общая декларация восстанавливает
путь к форме, сохраняет пустое значение и отвергает отсутствующую форму при проверке YAML. Для этого
пробной сборке переданы пространство имён `xr` и индексы объектов и форм.
`MetadataFunctionalOptionRules.location` теперь переносится из `rules.ts` как
общий выбор прямого пути к объекту или его члену. Допустимые корни и пары
«корень — вид члена» берутся из `metadataTarget` и проверяются при импорте
XML и проверке YAML. Два настоящих значения `Location` — константа и реквизит
справочника — проходят XML ↔ YAML без XML-референса; неподходящие корень и
вид члена отклоняются. Список допустимых пар разворачивается компилятором в
условие, поэтому при преобразовании не создаётся промежуточная коллекция.
Общий [переносчик точных путей](../../../tools/rules-migration/src/allowed-metadata-paths.mjs)
выводит декларации для смешанной коллекции `xr:Object` непосредственно из
`allowedObjectPaths` и `allowedMemberPaths`: корневые ссылки, прямые и
вложенные члены, включая `ExternalDataSource.…Cube.…DimensionTable.…Field.…`.
Виды сегментов являются буквальными частями шаблона, поэтому неверное
сочетание отклоняется без поиска по списку разрешений во время преобразования.
Проверены три разные формы и весь настоящий список из 84 элементов
`ФункциональнаяОпцияВсеСвойства.xml` против независимо сохранённого YAML.
Пустой `Content` из `ФункциональнаяОпцияПоУмолчанию.xml` проверен отдельно:
YAML опускает свойство, обратная запись восстанавливает `<Content/>` по
декларативному правилу наличия владельца. Дополнительно реальный путь
`Subsystem.ПодсистемаВсеСвойства.Subsystem.ПодчиненнаяПодсистема` из XML
командного интерфейса проверен как элемент `Content` в обе стороны.
Для точных путей без повторяющегося сегмента переносчик выводит из той же
декларации проверку существования каждого звена. На настоящем
`Catalog.…TabularSection.…Attribute.…` проверены оба направления;
отсутствующий реквизит отклоняется по индексу `metadata.path-children`.
Пробный индекс собран из проверяемых фактов. Теперь тот же индекс проверяет
каждое звено повторяемого пути `Subsystem.…Subsystem.…`: существующая дочерняя
подсистема проходит, отсутствующая отклоняется. Та же проверка проходит через
декларацию свойства, автоматически извлечённую из `rules.ts`. Повторный массовый
выпуск кандидатов включает `content` в проекцию семи свойств функциональной
опции. Проектное наполнение индекса
ещё требуется, поэтому проверка существования пока не подключена к полному
составу опции.
Два варианта `ClientApplicationForm.settingsStorage` перенесены из `rules.ts`
одной декларацией: ссылка на объект хранилища, своя и чужая форма отчёта
проверены на существующих XML-путях в обе стороны. Своя форма сокращается
до имени; чужая сохраняет полный путь. Индексы проверяют существование
хранилища и формы. Итого 146 адресных договоров.
Когда политика разрешает только корневой объект, переносчик теперь передаёт
лишь `metadata.roots`, без ненужного `metadata.path-children`. Проверены ссылка
на справочник из XML функциональной опции и отклонение отсутствующей цели.
Рабочий маршрут Rust пока зарегистрирован только для `DefinedTypes`;
проектное наполнение смешанного индекса детей остаётся отдельной задачей.
Переносчик именованных коллекций теперь выводит запись
`metadata.path-children` из уже объявленной связи `metadata.own-identities`:
ключ содержит UUID владельца, вид и имя элемента, значение — его UUID.
На неизменённом XML `ДокументВсеСвойства.xml` коллекция реквизитов создала
факты; общая декларация пути `Document.…Attribute.…` приняла существующий
реквизит и отклонила отсутствующий. Проверка использовала рабочую декларацию
коллекции, а не вручную заполненный проверочный индекс. Это подтверждает
источник для одного вида дочерних элементов; остальные семейства и
проектный маршрут ещё не подключены, поэтому флажок `metadataRef` остаётся пустым.
Из 13 видов дочерних сегментов, допускаемых `FunctionalOption.content`,
проверены реальные источники `Attribute` и `Command` документа. Существующая
декларация команды журнала также публикует `metadata.path-children`, но её
проектный маршрут ещё не проверен. На неизменённом XML документа ссылка
`Document.ДокументВсеСвойства.Command.Команда1` преобразуется в обе стороны,
а отсутствующая команда отклоняется. Выборочная проверка сохраняет вложенные
источники фактов и добавляет только необходимые объявления типов индексов.
Полная кандидатная проверка семейства реквизитов документа теперь проходит
все пять сценариев, включая настоящий XML → YAML → XML и поиск цели по
индексу. Для сборки её полного владельца подключён уже существующий общий
источник `metadata.base-identities`; запускатель включает декларации всех
переданных источников фактов автоматически. Это не означает подключения
семейства к рабочему маршруту проекта.
Недопустимое `Document.…Dimension.…` отвергается при проверке YAML.
`nestedObjectRoots: [Subsystem]` теперь порождает общий повторяемый текстовый
путь. Одна декларация принимает короткий путь подсистемы и его вложенное
продолжение, не создавая пересекающихся вариантов. Пробный индекс подтверждает
каждое звено; проектный индекс ещё не подключён, поэтому `content` не считается
перенесённым целиком.
Повторяемая [проверка охвата](../../../tools/rules-migration/src/metadata-ref-coverage.mjs)
показывает: все 168 свойств типов `MetadataItemLink` и `MetadataItemLinks`
с `metadataTarget.kind=member` сейчас становятся кандидатами.
Восемь свойств другого типа,
`InputByStringFields`, имеют общий
обратный вызов и учитываются отдельно; прежняя оценка 155/168 смешивала
эти группы и была занижена. `StandardAttributeDescription.choiceForm`
учтён после передачи пространства имён владельца. Число кандидатов означает только
распознавание декларации, а не полную приёмку ссылок на членов.
Дополнительно проходят 26 Rust-проверок общего пакета коллекций, весь набор
тестов компилятора, Clippy компилятора и ограниченного проверочного каталога,
а также поиск новых дублей.
Clippy запускался с ограниченным каталогом `rust/target/metadata-ref-check/catalog`;
прямой запуск без него создаёт отдельную тяжёлую сборку проверочного
запускателя и не нужен для этой матрицы.

Две многоуровневые формы ранее восстанавливались только через `!xml/raw`:
`Catalog.…TabularSection.…Attribute.…` и
`ExternalDataSource.…Cube.…DimensionTable.…`. Теперь обе описаны общими
декларациями двух последовательных сегментов пути в
[`metadata-member-paths.yaml`](../../../rust/declarations/common/metadata-member-paths.yaml).
Общий выбор форм компилируется без пересечений. Частного Rust-обработчика
для справочника или куба нет.

Это ещё не полная приёмка `metadataRef`: переносчик теперь выпускает
декларативное ограничение для `metadataTarget.roots` с одним или несколькими
корнями и проверку объекта без ограничения вида, но допустимые виды членов,
фильтры и проектный маршрут
ещё не покрыты. Такие свойства остаются заблокированными, а не принимаются
без проверки. Флажок объекта остаётся пустым.

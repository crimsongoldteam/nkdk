# Идентичность вложенных объектов: независимая инвентаризация e2e

Источник: `tests/migration/checks/nested-identity-inventory.py`.
Результат: `tests/migration/nested-identity-inventory.json`.
Проверка: `python3 tests/migration/checks/nested-identity-inventory.py --check`.

Проверка читает исходные XML, сверяет полный отчёт и хэши, обнаруживает
ошибки разбора, повторные структурные ключи в файле и неоднозначную либо
несогласованную связь с основой. Фикстуры не изменяются. Это подготовка
договора, а не проверка Rust-преобразования или приёмка объекта.

## Найдено

- 1345 именованных MDClasses-объектов, в том числе 572 вложенных, 17 видов.
- У всех 572 вложенных объектов есть собственный UUID.
- Все 179 непустых ссылок на основу разрешаются в cf ровно в один объект;
  вид, имя и цепочка владельцев совпадают с соответствующим объектом расширения.
- Нет ошибок разбора и повторов ключа «файл + цепочка владельцев + вид + имя».
- 50 совпадений ключа без файлового контекста среди всех именованных объектов,
  в том числе одинаковые имена форм у разных владельцев. Это не дефекты входа:
  отчёт показывает недостаточность имени отдельно хранимого объекта без топологии.
- У одного вложенного реквизита обнаружено состояние Notify для ссылки на основу:
  cfe/all-extension/Catalogs/СправочникВладелец.xml, РеквизитСсылка.

## Первый потребитель: EnumValue

Девять значений в четырёх XML-файлах: пять в основной конфигурации,
два собственных в расширении и два заимствованных. У семи обычных значений
нет ObjectBelonging, ExtendedConfigurationObject и InternalInfo.
У двух заимствованных — Adopted, непустая ссылка на основу и пустой InternalInfo.
Это позволяет проверить три основных варианта без искусственных XML.

В существующем коде расширения есть ещё четыре смысловых состояния ссылки:
ссылка присутствует/отсутствует × обычная проверка/Notify. Они кодируются
отсутствием YAML-поля, пустым полем и тегом !проверять. В данном наборе EnumValue
не представлены все четыре сочетания. Их нельзя объявлять проверенными по этим
девяти элементам; соседний реквизит даёт настоящий пример Notify.

## Следствие для декларации

Собственный UUID, соответствующий объект основы и наличие XML-ссылки — разные
сведения. Ключ должен учитывать компонент, владельца, вид и имя. Присутствие
ссылки и режим её проверки не следует смешивать с UUID. Восстановимые UUID
не требуют !xml; отсутствие готового механизма не оправдывает raw.
Индексы в проверочных оболочках пока не заменяют рабочую подготовку идентичности
и привязку отдельно расположенных объектов к владельцам.

## Границы

Исследованы именованные MDClasses-объекты внутри MetaDataObject с Properties/Name.
Элементы формы из других пространств имён и именованные внешние файлы этим
обходом не принимаются. Поиск основы намеренно ограничен cf из текущего e2e;
это не универсальная схема выбора базовой конфигурации.

На этапе инвентаризации исполняемые декларации не изменялись. Чеклист сохраняет
19/90 common; MetadataEnumerationValue не отмечен. Самопроверка исследования
не является независимым ревью.


## Реализация подготовленных индексов

Добавлены два фрагмента без смысловых полей YAML:
`fragment.metadata-own-identity` и `fragment.metadata-base-identity`.
Они задают вклады из типизированных входов в два независимых индекса.
Собственный индекс имеет ключ component/owner/kind/name; связь с основой —
component/identity. Непосредственный владелец задаётся UUID, поэтому совпадение
имён в разных родительских объектах не создаёт один ключ.

В каталоге есть две проверочные композиции и один тест подключения на 572
строках независимого корпуса. Тест сверяет каждое значение собственного
индекса и наличие либо отсутствие связи с основой, а также отсутствие
совпадения для другого компонента. Все 179 связей проверяются в Rust.
Корпус теперь содержит UUID непосредственного владельца; его происхождение
проверяется повторным обходом неизменённых XML командой --check.

Компилятор, модель языка и нейтральный исполнитель не изменены. Предметные
имена находятся в YAML и тестовых данных. Это самопроверка подключения
существующего механизма вкладов, а не независимое ревью.

Граница реализации: пока проверено построение/чтение подготовленных индексов,
а не восстановление UUID-атрибута в полном XML EnumValue. Проверочные
композиции не являются преобразователем полных объектов. Путь генерации
скалярной записи сейчас требует YAML-сопоставление каждого поля; добавление
обычного YAML-поля UUID было бы обходом согласованного договора.
Следующий шаг — общее восстановление служебного XML из подготовленного
контекста с проверкой обратимости, затем подключение EnumValue к коллекции.


Проверено после реализации: 201 Rust-тест, 20 тестов инструментов переноса,
проверка актуальности инвентаризации, архитектуры Rust и отсутствие новых
дублей относительно 37acdae1f. Форматирование Rust и git diff --check прошли.

Дополнительно прошли Clippy всего workspace с -D warnings и 133 договора
подключения кандидатов. Итоговый diff не содержит ошибок пробелов.

# Сборка родительского перечисления

## Завершённый механизм

InternalInfo автоматически собирается из статических параметров исходного
правила: XML-корня и списка items. Имена, категории и порядок служебных типов
не перечисляются в Rust и не задаются отдельным профилем для каждого владельца.
Общий выпуск готовых подключений распознал 20 таких договоров.

В рабочем каталоге выпущен fragment.enumeration-internal-info. Команда
`node tools/rules-migration/src/internal-info-operation.mjs --check` проверяет
актуальность по rules.ts и входит в проверку переноса. Общий переносчик
использует тот же генератор для остальных владельцев.

Обычный XML восстанавливается из имени владельца и индексов идентификаторов.
Проверены исходные e2e InternalInfo документа, журнала и перечисления в обе
стороны: обычный YAML пуст, значения и порядок восстанавливаются без референса.
Существующие XML-фикстуры не изменены. Эти проверки относятся к служебным типам,
а не к полному файлу родителя или всем режимам InternalInfo.

## Что остаётся у перечисления

Кандидатная проекция 16 свойств `Properties` теперь смонтирована под настоящим
XML-корнем перечисления без переписывания правил. В той же Rust-операции
подключены XML-only списки форм и макетов: на неизменённой e2e-паре значения
YAML совпали после разбора, а XML восстановился без референса. Различается
только запись многострочного `Пояснение`: старый YAML использует блок `|`,
Rust — строку с `\n`; значение одинаковое. Общий проектор e2e теперь явно
поддерживает отсутствующие необязательные XML-поля и XML-only коллекции.

В этой же операции теперь собраны `InternalInfo` и оболочка файла: UUID
перечисления, версия XML и три служебных типа взяты из той же неизменённой
e2e-фикстуры. Их декларации выводятся из исходного `rules.ts`, а факты UUID
подготавливаются по XML. XML → YAML → XML без референса прошёл. Созданный
Rust-код пробного пакета занимает около 2,6 МиБ при лимите 4 МиБ.
Тот же составной договор теперь задаёт перенос `Ext/ManagerModule.bsl` в
`МодульМенеджера.bsl`; Rust проверяет маршрут и наличие обоих файлов в e2e.
Проверка покрытия берёт все 26 свойств из `rules.ts`: 23 присутствуют в этой
декларации, три ещё не включены (`standardAttributes`, `enumValues`,
`commands`). Это учёт состава декларации, не приёмка каждого режима. Проверка
падает, если исходный состав меняется без обновления переноса.

Состояние расширения `ExtendedConfigurationObject` объявлено через общий индекс
UUID основной конфигурации. Теперь и cf, и заимствованное cfe проходят
составной e2e-договор 16 свойств, форм и макетов, служебных UUID и оболочки:
XML → YAML совпадает со старой фикстурой по значениям, YAML → XML без
референса восстанавливает исходный проектированный XML. Проверка использует
неизменённые исходные e2e-файлы; для cfe записана отдельная их проекция.

Исправлены два общих дефекта. Коллекция из двух `<Form>` больше не попадает в
сохранение как одно свойство. Фрагменты, пишущие в общий `<Properties>`,
исполняются рядом, поэтому контейнер не выпускается повторно; восстановление
XML также умеет заменить повторённый контейнер единственным ожидаемым.
Вывод пустых переводов, ссылок на формы и пропущенных значений по умолчанию
в расширении задан условиями декларации, выведенными из исходных параметров
`rules.ts`; обработчик владельца не содержит ветвей по этим типам.
`PropertyState` для обычных и секционных свойств теперь также выводится из
извлечённого реестра правил и входит в тот же cfe-тест: строка
`ManagerModule/Extended` превращается в `Изменять: [МодульМенеджера]` и
восстанавливается обратно. Особое состояние помеченного свойства и другие
режимы ещё не приняты. Стандартные реквизиты, значения перечисления и команды
пока не включены в одну полную операцию. Родительский объект остаётся
непринятым.

Декларация стандартных реквизитов перечисления выпущена тем же генератором,
что уже выпускает журнал и табличную часть. Она берёт XML-маршрут из `rules.ts`
и остаётся отдельным фрагментом до общей сборки. Сам каталог стандартных
реквизитов генерирует около 17 МиБ Rust-кода; соединять его со всеми частями
в одном пробном пакете без контроля памяти нельзя.

Общий переносчик `child-names-operation.mjs` теперь выводит формы и макеты
из параметров `rules.ts` и XML-корня владельца. Он распознал все 21 семейство
верхнеуровневых владельцев с такими списками; для перечисления выпущен
`fragment.enumeration-child-names`. Пробная Rust-операция проверена на именах
форм и макета из неизменённого e2e XML перечисления: YAML сокращается,
а XML восстанавливается без референса. Списки внутри вложенных форм и
неполные маршруты файлов внешнего источника остаются отдельными подключениями;
переносчик явно сообщает о них и не объявляет владельца завершённым.

Четыре ссылки перечисления на собственные и общие формы теперь выводятся
вторым общим переносчиком из `MetadataItemLink`. Он принимает 18 семейств с
одинаковым исходным договором; отличающийся отчёт блокирует, а не подгоняет
под шаблон. Пробная Rust-операция проверена на двух настоящих ссылках из e2e
XML перечисления и двух пустых элементах: YAML содержит короткие имена,
обратный XML восстанавливается без референса. Это ещё не полная операция
перечисления.

Коллекция команд тоже выводится из параметров `rules.ts`: общий переносчик
сохраняет уже принятый договор строки команды, берёт XML-корень владельца и
имя поля YAML из исходного правила. Получены кандидаты для 17 семейств;
декларации документа и журнала совпали с существующими. Команда1 из e2e XML
перечисления прошла XML → YAML → XML без референса в отдельном небольшом
Rust-пакете. Отдельный пакет нужен потому, что добавление второй полной
коллекции команд в существующий пробный пакет превысило его лимит 4 МиБ
сгенерированного Rust-кода. Подготовка входов и индексов в обоих тестовых
пакетах использует один помощник; новых дублей нет. Оба Rust-пакета прошли
тесты и Clippy, полный `pnpm test`, проверка типов и архитектуры прошли.
Полный владелец пока не собран.

Соседняя проверка ссылок выявила неверное ожидание для отсутствующего
`<Owners>`: общий механизм сохраняет его отсутствие как `!xml/raw`, поскольку
без пометки обратный экспорт добавил бы `<Owners/>`. Проверка теперь отличает
отсутствующий элемент от пустого; все десять сценариев Rust-пакета прошли.
После изменения прошли полный `pnpm test`, `pnpm type-check`, обе проверки
архитектуры и поиск новых дублей относительно `2af2f299`.

Следующий шаг сделал подключение стандартных реквизитов общим: XML-маршрут
выводится из `XMLRoot` исходного правила, как и у других владельцев;
проверка перечисления не содержит отдельного обработчика Rust. Общая
коллекция уже проверена на настоящем примере перечисления в каталоге
договоров. Отдельную вторую Rust-проекцию с тем же кодом не выпускаем:
она превысила ограничение размера сгенерированного каталога. Поле пока
не включено в полную декларацию перечисления, поэтому флажок владельца
остаётся снятым.

Правило содержит 26 свойств. Коллекция EnumValue принята отдельно; полного
перечисления пока нет. Стандартные реквизиты и команды проверены отдельно,
но ещё не объединены с остальными свойствами. Характеристики требуют
полного переноса зависимостей. Среди отсутствующих подключений:
TypeDescription, TypeLink, MetadataValue, ChoiceParameterLinks, ChoiceParameters,
Picture, ссылки на таблицы и их поля. Также остаётся объединение остальных
файловых ресурсов, контекста и состояний расширения в одну рабочую операцию.

Флажок родителя остаётся снятым; common — 19/90, прикладные объекты и их части —
1/57. Успешная генерация 20 подключений не означает приёмку 20 объектов.

## Проверки и границы

- 80 сценариев коллекций прошли, включая три реальных договора InternalInfo.
- 133 сценария готовых подключений прошли; общий каталог из 101 декларации
  успешно скомпилирован после добавления автоматически собранных фрагментов.
- 30 проверок инструмента переноса прошли. Добавлена одна проверка договора
  генерации; e2e-случаи включены в существующий общий запускатель.
- Проверки архитектуры Rust и новых дублей относительно 086d322d9 прошли.

Самопроверка универсальности: Rust-компилятор и оркестратор не изменены;
переименование XML-корня и служебного типа проверено. Неизвестные параметры
и неоднозначные списки блокируют генерацию. Независимое ревью не выполнялось.

Общий выпуск дополнительно потребовал штатного обновления устаревшего хеша
теста в rules-contract-cases.json. Защита от устаревших источников сохранена.
Проверочная обёртка готового подключения теперь располагает контрольное поле
в том же объявленном XML-корне; это устройство теста, не особый путь конвертера.
Полный pnpm test и производительность 10× этим блоком не проверялись.

## Дополнение 2026-09-29: цельный владелец и пустые варианты

Составная операция теперь включает команды, значения и стандартные реквизиты
вместе с остальными свойствами. Проверены четыре реальные формы владельца:
заполненное перечисление cf, заимствованное заполненное cfe, пустое cf и
заимствованное пустое cfe. Во всех четырёх проверках XML → YAML → XML проходит
без XML-референса и без `!xml`. Пустые строки, списки и характеристики
выводятся из деклараций; генератор использует состояние владения объектом,
поскольку собственное перечисление расширения не эквивалентно заимствованному.

Пятая исходная форма, собственное перечисление расширения, пока не принята.
Её YAML использует `null` для пустых ссылок на формы, в том числе внутри
стандартных реквизитов. Текущий общий договор ссылки выдаёт пустую строку
или пропускает поле. Проверочный случай сохранён отключённым с причиной;
флажок полного переноса владельца не поставлен. Требуется общее правило
выбора представления пустой ссылки по контексту без условия в Rust-оркестраторе.

## Дополнение 2026-09-29: пять форм и аномалии

Общий договор `yaml.nullWhen` устранил различие пустых ссылок. Теперь все семь
неизменённых e2e-пар перечислений, включая простое cf и собственное заполненное
расширение, проходят через одну составную декларацию в обе стороны без
XML-референса; перечень из 26 исходных свойств не имеет пропусков. На копиях
XML в памяти проверены неверное булево значение, неизвестное системное
перечисление, повтор перевода и повтор стандартного реквизита. Обратный экспорт
восстанавливает XML, а правильные соседние поля остаются обычным YAML. Маршрут
модуля менеджера совпадает с исходной парой файлов, их байты равны.

Составная декларация пока исполняется в проверочном Rust-пакете. Проектный
маршрут `nkdk` в `rust/operations/routes.yaml` содержит только определяемые
типы. Общий маршрутизатор уже умеет объявленный вид YAML-пути
`ВидОбъекта/Имя/Свойства.yaml` через `yamlFile`; его двусторонний маршрут,
поиск файла и путь снимка проверены независимо от типа объекта. Поэтому флажок
полного владельца остаётся пустым: следующий шаг — выпустить производственную
декларацию перечисления, подготовить её факты и добавить маршрут в проектную
операцию, затем проверить все файлы владельца через неё, включая модуль
менеджера. Составная проба отделена от общих фрагментов: её зависимость от
кандидатной коллекции стандартных реквизитов больше не ломает сборку
производственного каталога.

## Дополнение 2026-09-29: производственная декларация

Генератор выпускает `metadata.enumeration` из того же состава фрагментов,
который проверялся на семи e2e-парах. Проверки перенесены в
`nkdk-compiled-rules/tests/enumeration.rs`; отдельный большой проверочный
пакет перечисления удалён. Все семь пар прошли через производственный каталог.
Размер созданного Rust-файла после включения правила — около 17,9 МБ при
предельном размере 32 МБ. Пик памяти этой сборки отдельно ещё не измерен.

Проектный маршрут теперь может брать вход из снимка фактов по объявленному
имени декларации и поля, составлять текст из частей и выбирать значения по
компоненту. Проверено, что UUID сначала извлекается из XML перечисления в
снимок, затем доступен при привязке входа владельца. Видов объектов в этих
операциях Rust нет. Это подготовка к маршруту перечисления: строка в
`rust/operations/routes.yaml` и полная проектная приёмка ещё не сделаны,
поэтому флажок владельца остаётся снятым.

Источник `migration.enumeration-child-names` перенесён из файла фрагментов
в каталог производственных объектов. На исходном XML он сохраняет порядок
`ФормаСписка`, `ФормаВыбора` и имя макета; проектная привязка принимает
из снимка не только строку UUID, но и список строк. Это позволяет вернуть
имена в XML, даже когда в `Свойства.yaml` они сокращены.

## Дополнение 2026-09-29: проектная операция

Производственный маршрут перечисления теперь собирает факты UUID владельца,
внутренних типов, значений, команд и основной конфигурации из сохранённых
снимков. Направление публикации фактов каждого источника задано в YAML:
XML владельца даёт исходные сведения при импорте, короткие снимки дочерних
коллекций восстанавливают их при экспорте. Общий проектный код не содержит
условий по перечислению, команде или значению.

Проверка `convert_component` использует все семь владельцев из исходных
каталогов cf/cfe: сравнивает смысловые YAML-значения, затем XML после
экспорта без референса. Дополнительно сравниваются байты модулей менеджера,
команды и формы. Проверено создание нового перечисления в cf и собственного
перечисления в cfe: повторный экспорт использует те же идентичности.
Проверка выявила и устранила общую ошибку пути ресурсов: они теперь читаются
и публикуются относительно каталога владельца, как задаёт декларация.

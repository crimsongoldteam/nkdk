# Воспроизводимая сборка полного реквизита

## Сделано

`source-record-owner.mjs` собирает декларацию из регистрации rules.ts:
общая история, связь с основой, обнаруженные состояния записей и остальные
свойства со связями между соседями. Корень XML берётся из исходной регистрации.
Новый common или объект не добавляет обработчик преобразования в Rust.

`record-owner-operation.mjs` записывает
`rust/declarations/candidates/catalog-attribute-owner.generated.yaml` и
`tests/migration/catalog-attribute-owner-coverage.json`. Команда с `--check`
проверяет воспроизводимость. Нативная CF/CFE-матрица использует тот же общий
сборщик вместо самостоятельного повторения сборки внутри теста.

Все 33 регистрации включены; служебная связь с основой не считается
дополнительным исходным свойством. Флажок полного реквизита не поставлен.
Уточнение по исходному TS и XML: synonym, editFormat, toolTip и choiceForm
имеют обычное представление (`plain`). Само наличие этих свойств не создаёт
PropertyState; неявный Extended выводится только для `semantic`.
Например, первый заимствованный реквизит содержит пустые Synonym и ToolTip,
а история содержит только Type=MultiState. Предыдущая запись о четырёх
«неподключённых состояниях» была ошибочной. Машинный отчёт различает договор
обычного значения и необходимость подключения истории.

## Размер рабочей области зависимостей

Профиль компилятора получил `--roots-only`: измеряется выбранная операция,
без публичного экспорта всех вспомогательных объявлений. Для
`metadata.catalog-attribute` выбраны 39 файлов, 151 объявление,
74 определения и 264 подключения. Генерация вместе с чтением/связыванием
заняла 6905 мс; это не время компиляции rustc или преобразования XML/YAML.

Общий объём файлов — 25 021 622 байта: generated.rs занимает 16 667 929
байт, бинарные таблицы автоматов — 8 331 116 байт. Бинарные таблицы не являются
Rust-кодом и не входят в лимит generated.rs; прежнее сравнение общего объёма
с лимитом пакета было неточным.
Два крупных источника: owner-collection-part — 2 994 535 байт,
owner-choice-variant grouped — 2 412 823 байта. Полная рабочая область
включает зависимости подготовки индексов; её нельзя приравнивать к размеру
изолированной проверочной библиотеки с вручную подготовленными индексами.
Подробности — в `2026-10-05-catalog-attribute-generation.json`.

Операция ещё не добавлена в рабочую сборку. Лимиты не повышались;
огромная холодная сборка не запускалась. Договор обычных свойств проверен
ниже; следующее действие — выбрать пакет для тела операции, проверить
рабочую область зависимостей и подключить проектную подготовку входов.

## Рабочий AOT-пакет и подготовка входов

`owner-index-requirements.mjs` переносит известные связи индексов по
объявленным привязкам. Проверяются переименование, одинаковая структура
разных индексов, конфликт, неизвестный поставщик и рекурсия. Предметных
типов и имён объектов в механизме нет. Машинный отчёт содержит шесть
привязок; фрагменты получают готовые значения, а корень получает `index`.

`record-owner-fact-sources.mjs` выводит независимые чтения имени/UUID, истории
и связи с основой из регистрации и уже собранной декларации. История и связь
используют существующие общие построители; отдельных Rust-обработчиков нет.
Для исходного XML матрица читает эти три источника через `contribute_file`,
а затем готовит входы через сгенерированный `prepare_fact_inputs`. Ручное
построение истории сохранено только у синтетических случаев создания XML
из YAML-пометок. Корни, формы и определяемые типы в этой матрице пусты:
их подготовка из полного проекта остаётся отдельной проверкой.

Манифест `production-bodies-3.txt` включает операцию и её три источника
в самостоятельный рабочий пакет. Экспортируются только корни; внутренние
значения не становятся отдельными операциями. Пакет использует общую
идентичность каталога и подключён к общему фасаду.

[Размер рабочего пакета](2026-10-05-catalog-attribute-working-generation.json):
16 637 055 байт Rust при пределе 16 777 216; все файлы — 26 367 230 байт.

Рабочая матрица прошла 16 случаев за 0,20 с вместе с чтением тестовых данных;

## Полная запись внутри коллекции

`recordOwnerCollectionItem` выводит привязки имени, UUID, вида объекта и связи
с основой из проверенных привязок композиции и исходного корня XML. Отсутствующее
значение принадлежности YAML нельзя восстанавливать через само это поле; здесь
используется подготовленная связь UUID с основой. Отдельного обработчика
реквизита в Rust нет. Сохраняются все шесть поставщиков разных индексов.

Нативная проверка сначала выявила неверный yamlOrder после включения имени
в ключ, затем циклическую привязку, затем input.not-ready при разборе значения
YAML до восстановления UUID. Порядок исправлен в общем сборщике; привязка
использует независимый факт; общий AOT-генератор откладывает только разделы,
использующие ещё не готовые соседние значения. Ошибку контекста не маскируют
XML-пометкой.

Прошли 12 нативных случаев: восемь реальных отдельных реквизитов CF/CFE и
четыре списка с четырьмя соседями в прямом и обратном порядке. Ожидания извлечены
из неизменённых XML/YAML-фикстур. Общий запускатель проверяет аномалии неверных
булевых значений и оба направления. Это кандидатный договор коллекции:
источники фактов ещё читаются из выделенных элементов, а не полного файла
владельца; корни, формы и определяемые типы остаются пустыми. Полный проект,
создание нового объекта и производительность этим прогоном не приняты.

Итог повторной проверки блока: 11/11 проверок семейств, включая прежние
24 самостоятельных случая; генерация 12/12, одна прежняя проверка разделения
кода отключена; внутренние проверки 18/18; переносчик 216/216. После сохранения
поставщиков в пробном владельце матрица полной коллекции повторно прошла все
12 случаев. Clippy компилятора, Bodies3 и Members2 прошёл с запретом предупреждений.
Архитектура Rust и новые дубли проверены. Самопроверка предметных границ:
отложенный разбор определяется зависимостями входов, а не именами объектов;
это не независимое ревью.

Обновлённый размер: Bodies3 — 16 748 047 байт, Members2 — 5 959 385 байт.
Оба прежних предела сохранены. Нативная компиляция ограничена одним заданием;
ненужные собственные временные файлы удалены. Холодная сборка всего проекта
и изменение скорости конвертера в этом блоке не измерялись. Полные `pnpm test`
и проектный round-trip ещё не выполнялись.
## Источники фактов из полного XML владельца

`recordOwnerFactCollections` выводит три источника из регистрации коллекции:
идентичности строк, историю и связь с основой. Они сохраняются в существующем
пакете Members2, без увеличения лимита. UUID родителя читается из заголовка,

Матрица использует полные неизменённые XML-файлы каталогов CF/CFE.

Добавление заголовка обнаружило `fact.unready`: составной сборщик пытался
читать узкую строку как полное преобразование. Исправлен общий AOT-путь отбора

события существующему читателю, не создаёт XML-копий, не знает имён объектов.
Обычный преобразователь остаётся строгим. Матрица 12 случаев прошла за 89,44 с
вместе с нативной компиляцией; это не замер скорости преобразования.
Проверки отсутствующего UUID и неверного корня прошли. Факты также сохраняются
в YAML и читаются из него для всех 12 сценариев; ручной передачи UUID нет.
Clippy рабочих пакетов прошёл за 2 мин 19 с. Новый размер Bodies3 —
16 748 852 байта, Members2 — 6 299 149 байт: прежние пределы сохранены.

## Подключение к сборке зарегистрированного владельца

Общий сборщик владельца теперь принимает вложения полной коллекции. Он
учитывает зарегистрированный служебный путь основы и показывает все остальные
неподдержанные свойства, вместо ошибки на первом из них. Для каталога
собраны 45/69 регистраций; 24 явно остаются в отчёте. Неполная операция
отклоняется перед публикацией. Это проверка сборки данных, не полного XML-файла.

Машинная регистрация коллекции сохраняет indexProviders: после чтения из файлов
не теряется ни один из шести поставщиков. Отдельный пропуск в собственных
ссылках каталога исправлен в общем договоре own-or-common form: корневой
индекс metadata.roots объявлен явно. Никакого угадывания индекса по форме типа.
Сгенерированная декларация характеристик пересоздана после этого изменения;
проверочные данные не изменены.

### 2026-10-05: текущие факты внешних файлов

Список имён и наличие файла определяются приложением перед использованием
сохранённых фактов YAML. `Catalog::refresh_resource_facts` обновляет только
источники файловой информации; идентичность и прочие сведения импорта сохраняются.
Обновление подключено перед подготовкой экспорта и при загрузке снимков для
внешних фактов. Если обнаружение завершилось ошибкой, снимки не обновляются частично.

Новый общий источник `resourcePresence` содержит имя факта и пару XML/YAML-путей.
Он различает отсутствие, существующий пустой файл и каталог; содержимое файла
не читается. Пути проверяет прежний защищённый файловый слой, включая запрет
выхода через символическую ссылку. Результат проходит обычную AOT-декларацию
`migration.resource-presence-source`, без условий по классу метаданных.
Внутренние логические скаляры используют текстовые записи `'true'`/`'false'`;
это служебный договор фактов, а не изменение пользовательского boolean YAML.
Неявный Control по наличию файла остаётся фактом проверки и не создаёт XML-строку.

`pnpm test:migration-resource-facts` выполняет одну общую матрицу файловых
проверок на настоящих модулях приложения и небольшом AOT-каталоге. Тот же
исходный код матрицы используется тестами приложения; проверки не копируются.
Новая проверка защищена отдельной возможностью `resource-boundary`, поэтому
обычные проверки кандидатов не собирают приложение повторно.

Следующий шаг: автоматически получить пары путей из проверенных регистраций
секционных свойств, подключить их как подготовленные факты режима и проверить
владельца целиком. Наличие общего файлового источника ещё не означает, что
все эти регистрации и проверки режимов уже подключены. Флажки владельцев не изменены.


Автоматическое получение файловых фактов добавлено в `assembleRecordStateOwner`:
`resourceFactSources` строятся из исходных секционных регистраций с `nkdkPath`,
XML/YAML-пути не вводятся вручную. `source-resource-facts.mjs` проверяет неизменность
регистраций и исходных файлов. Сохранённый перечень содержит 37 владельцев и
55 пар путей; 18 владельцев с вычисляемыми путями перечислены как заблокированные.
Секции без `nkdkPath` не относятся к этому файловому договору. При неизвестном
вычислении переносчик сообщает о блокировке, а не заменяет путь предположением.
Проверка приложения использует полученную этим генератором регистрацию XDTO.
Прежде чем собирать Rust, запускатель проверяет воспроизводимость перечня.
Подключение этих источников к полным операциям и проверки неявного Control по
всем версиям ещё нужны; один перечень не является приёмкой владельца.


Продолжение 2026-10-05 — изоляция блокировок массового переноса:
неизвестный путь внешнего файла отмечается у конкретного свойства с именем
параметра (`xmlPath` или `nkdkPath`). Остальные известные пути сохраняются,
следующие владельцы продолжают собираться. Непроверенная регистрация остаётся
ошибкой инструмента, а не аномалией пользовательских данных. Полнота сборки
вычисляется после подключения всех фрагментов и проверки файловых путей:
наличие любой блокировки исключает полную приёмку.

Общий сборщик допускает фрагмент с пустым перечнем присвоенных свойств:
история, ограничения и контекст могут существовать без отдельного обычного
значения. Фрагмент остаётся в композиции и не добавляет фиктивно завершённых
свойств. Этот случай проверен на исходной регистрации команды документа;
неизвестный путь её модуля остаётся блокировкой. Это не полная приёмка команды.

### 2026-10-05: потоковые отпечатки и декларативное сравнение внешних файлов

Файловый источник может явно запросить `resourcePresence.fingerprint.maxBytes`.
Это общий лимит содержимого всех его файлов, а не отдельный лимит для каждого.
Без этого запроса источник только проверяет наличие и не читает содержимое.
SHA-256 вычисляется потоком с буфером 64 КиБ; исходные данные не собираются
в `Vec<u8>`. Пустой файл имеет собственный отпечаток и отличается от отсутствия.
Проверки путей и символических ссылок используют прежний защищённый файловый слой.

`migration.resource-fingerprint-source` использует общую декларацию файлов и
вносит отпечатки в `metadata.resource-fingerprints` с ключом
`{component, owner, property}`. `owner` — идентичность объекта, а не его имя.
Отсутствующий файл и источник без запрошенного отпечатка не создают запись
отпечатка; пустой существующий файл создаёт её. Общие данные файлов вынесены
в `migration.resource-presence-data`, без второй реализации чтения.

`migration.resource-state-comparison` описывает проверки обычными выражениями
декларации: отсутствие выбранного файла, отсутствие свойства/файла основной
конфигурации и равенство отпечатков. При «Контролировать» различие — ошибка,
при «Проверять» — предупреждение; «Изменять» и сохранённый XML не требуют
равенства, но требуют существования выбранного файла. Rust не выбирает
поведение по имени режима или классу метаданных.

Входы `active` и `basePropertyExists` — подготовленный контекст проверки:
их нельзя заменять постоянным true при подключении владельца. Общая проверка
сама не устанавливает заимствование, режим или идентичность основной конфигурации.
Отключённая проверка позволяет пропустить обычный новый объект без явного режима;
при активной проверке отсутствие базового свойства диагностируется раньше
сравнения файлов. Наличие файла не создаёт XML-строку PropertyState Control.

Проверены настоящий файловый слой, подготовка индексов и скомпилированные
декларации вместе: пустота/отсутствие, эталонные SHA-256, два блока чтения,
изменение содержимого, общий лимит, четыре режима, отсутствие текущего/базового
файла, одинаковые файлы и отключение проверки. Расширена существующая матрица,
новых функций тестов не добавлено; повторяющиеся настройки используют общий
`fact_budget`, повтор проверки лимита убран.

Это приёмка общего договора файловых фактов и сравнения. Автоматическое
подключение к полноценной операции владельца с настоящим выбором UUID,
базового свойства и режима ещё требуется. Флажки владельцев не изменены.


Приёмка общего договора сравнения: 222/222 проверки переносчика, две матрицы
настоящего файлового слоя Rust и Clippy пройдены. Расширенная матрица проверяет
также отсутствие записи отпечатка в подготовленном индексе, эталон на два блока
чтения и совокупный лимит. Архитектурные проверки, формат и воспроизводимость
генераторов пройдены; новых дублей нет. Повторы подготовки фактов сведены к
общему запуску настоящего `facts::prepare`, без замены его имитацией.
Полный `pnpm test` не запускался. Контекст и запрос отпечатков ещё нужно

повторить проверку приложения. Поэтому флажок полной приёмки XDTO остаётся пустым.
Отчёт сборщика уже не содержит блокировок отсутствующего подключения состояний
и маршрутизации файлов для этой операции; это полнота сборки, а не отметка приёмки.


Отчёт `generation-sizes.tsv` теперь сохраняется до проверки предела размера;
сам `generated.rs` по-прежнему записывается только после успешной проверки.
Это позволяет исследовать переполнение, не передавая чрезмерный код rustc.
Для полного реквизита крупнейшие отмеченные участки: часть коллекции 3 027 901
байт, вариант grouped 2 450 627, fixedArray 1 237 970, formChoice 1 223 361;
три варианта plain/changed/notified — около 870 тысяч каждый. Размеры вложенных
участков могут пересекаться; складывать их как независимые расходы нельзя.
Отдельные двоичные автоматы занимают 9 372 357 байт и не равны размеру Rust-кода.
Следующий блок: устранить повтор общей обработки вариантов и коллекций,
сохранив AOT, исходные договоры и скорость исполнения.


### 2026-10-05 — повторное использование одинаковых тел записей в AOT

Общий генератор сохраняет полностью совпадающее тело записи один раз и
подключает его через ссылки Rust на модуль. Ключ — весь созданный код:
XML-пути, условия, привязки входов, значения по умолчанию и числовые ID
остаются частью сравнения. Похожие тела с разными параметрами не объединяются.
Это не исполнение деклараций во время преобразования: сохраняются заранее
скомпилированные функции, без нового посредника в пути выполнения.

Перенос видимости выполняется по токенам Rust; текстовые литералы, включая
русский текст и `pub(super)`, сохраняются. Компилятор использует `proc-macro2`
только при генерации; приложение от этой библиотеки не зависит. Общий Session
очищает временные данные XML-путей и записей после успеха и раннего возврата.

Пакет полного реквизита уменьшился с 16 807 091 до 15 099 807 байт
(примерно 10,2%). Лимит 16 777 216 байт не увеличен, существующие входные
точки и проверки сохранены. Повторное использование разных размещений с
разными ID остаётся отдельной задачей; прежняя проверка размера для этого
случая не объявляется пройденной.

Штатная файловая операция XDTO прошла все шесть исходных e2e-XML в составе
каталога приложения. Обратный экспорт выполняется после удаления входного
XML: сравниваются полные XML-события и содержимое внешних файлов. Проверены
создание нового объекта, его имя и Namespace, стабильный UUID при повторном
экспорте. Исходные фикстуры не менялись. Окончательные общие проверки ещё
выполняются; флажок полной приёмки будет установлен после их результата.

### 2026-10-05 — проверка значений по умолчанию и настоящих файлов XDTO

- Матрица InputByString обнаружила повторение значения по умолчанию как пустого YAML-скаляра (`ДлинаКода: null` вместо пропуска значения по умолчанию). Обнаружены две общие ошибки: сравнение полной записи зависело от внутренней оболочки, а повторная обработка свойства при сохранении аномалии соседа обходила правило пропуска значения по умолчанию. На изолированном настоящем примере подтверждено: сравнение уже возвращало истину, но обработчик выбранного значения снова добавлял `null`. Сравнение теперь использует единый интерфейс `RecordInput` и проверяет все смысловые поля записи, включая скрытые. XML-пути, названия объектов и частные типы не участвуют. Попытки изменять вывод `null` в оболочке и проекции отменены: явный `null` предусмотрен декларацией и должен сохранять свой смысл; пропуск обеспечивает сравнение с полным значением по умолчанию на уровне свойства, в том числе при повторной обработке. Перед повторной обработкой проверяется восстановление XML из отсутствующего YAML-свойства: исходная и восстановленная формы сравниваются в одной объявленной XML-границе. Только доказанное совпадение позволяет пропустить свойство; иначе работает прежнее сохранение аномалий. Это также исключает ложный `!xml/raw` у обычного отсутствующего свойства расширения.
- Удалена неподтверждённая попытка менять числовые ожидания: XML-элементы в проблемном примере присутствуют и содержат значения по умолчанию: `CodeLength=9`, `DescriptionLength=25`.
- Ожидания пустого `InternalInfo` получаются из исходного XML независимо от конвертера. Пустой элемент, пропускаемый обычным экспортом данного договора, сохраняется через общий механизм восстановления формы XML.
- В настоящем расширении `ПакетXDTOВсеСвойства` история требует изменения `Package`, но соответствующий `Ext/Package.bin` отсутствует. Проверка с временно добавленным файлом не заменяет проверку этой аномалии на неизменном корпусе. Полная приёмка должна отдельно подтвердить отсутствие ложной пометки при наличии файла и сохранение отсутствующего файла при обратном экспорте.
- Запускатель рабочих примеров теперь учитывает `CARGO_TARGET_DIR`, чтобы проверки не создавали второй каталог сборки и не компилировали одинаковые зависимости повторно.
- Приёмка XDTO и общий блок остаются незавершёнными до прохождения матрицы, полного проекта и обязательных проверок.

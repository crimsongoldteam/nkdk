# Пустое сокращение значения с пометкой состояния

Подготовлено общее сочетание двух существующих конструкций: выбор по YAML-тегу
и запись, представленная одним полем. Пометка `!изменять` не требует отдельного
Rust-обработчика числа, длины или документа.

В `rust/declarations/probes/tagged-default-state.yaml` показаны два варианта:
обычное число и число с состоянием. При числе 9 сокращённый вариант записывает
`Длина: !изменять null`; пустая запись `Длина: !изменять` имеет тот же смысл.
Число 11 записывается явно: `Длина: !изменять 11`.

Компилятор теперь восстанавливает заданное значение из объявленного пустого
YAML, отличая его от отсутствующего поля. Это проверяется также на тексте,
обычной YAML-записи и точном числе 9007199254740993. Для проекции выводится один
скаляр `null`, а не имя скрытого поля. Выбор с тегом проверяет, что проекция
скалярная; отсутствие тега передаёт значение единственному обычному варианту,
который сам проверяет его тип.

## Границы результата

Проверены два пути: явно переданный булев контекст и вычисление состояния
из соседней XML-коллекции. У последнего сохранены соседняя строка и два
повторяющихся состояния в исходном порядке, без обхода через `!xml`.

Первоначально связь с соседним полем терялась при предварительной подстановке
контекста выбора: ссылка превращалась в обычную ссылку на созданный вариант,
а выражение начинало адресовать внутреннее поле числа. Исправлено общее правило
подготовки: составной выбор, как запись, сохраняет связь с полем вызывающего
владельца до размещения. План заимствует нужное поле в отдельную область
контекста. Это защищено проверкой плана и исполнением сгенерированного Rust.
Имен владельцев или свойств в обработке нет.

Ограничения записи действуют и при её скалярном YAML-представлении.
Обычный вариант требует обычного состояния, вариант с тегом — изменённого.
Противоречащая контексту пометка отклоняется до экспорта; удаление явной
коллекции при сохранённом теге не приводит к потере состояния в XML.
Такие проверки выполняет рабочая валидация Rust; JSON Schema проекции
явно отмечает необходимость этой проверки через `x-nkdk-runtime-validation`.

Коллекция состояний в проверочном YAML пока сохраняется явно. Обратное
вычисление её сокращаемой части из тегов, с сохранением остальных строк,
ещё не подключено. Проверка связи не означает приёмку полного владельца.

Приёмка InputByString и полных владельцев остаётся открытой. Ранее проверенные
53 сценария используют числовую проекцию без InternalInfo; пометки PropertyState
в ней явно исключены из сравнения. Новый договор не заменяет эту оговорку.

Описание допустимого YAML теперь учитывает объявленный null и у проекций,
и у обычных записей через один общий помощник. Схема самого языка разрешает
существующий `nullWhen` как выражение; неизвестные ключи по-прежнему запрещены.

Большой проверочный договор компилятора упёрся в заполненный диск при
линковке временного пакета. Удалены только временные сборки этого прогона.
Общий помощник создания тестовых пакетов теперь отключает для них отладочные
данные и промежуточные кеши: эти пакеты после проверки удаляются. Повторная
проверка большого договора прошла. Рабочие профили конвертера не менялись.
Изменение ограничено временными проверочными пакетами.


В проверочном примере состояние одного поля находится через `exists`.
Перед массовым подключением нельзя повторять обход всей коллекции для каждого
поля: подготовить общий индекс один раз, а выбирать состояние через `lookup`.
Исходные строки остаются отдельными данными для восстановления порядка,
повторов и остальных состояний. Скорость преобразования этим примером
не измеряется, достижение 10× не заявляется.

# Автоматическое подключение контекста файлов Predefined

Переносчик файловых оболочек создаёт подключённые проекции владельцев
справочника, планов характеристик, счетов, видов расчёта и расширения.
Ручная проекция расширения заменена генерацией.

Корень XML, пути имени и принадлежности и русский префикс типа берутся
из регистрации rules.ts. Ключ UUID выводится обычным concat:
`component/тип.name`. Например, `cf/Справочник.Товары` и
`cfe/Справочник.Товары` принадлежат разным областям одного индекса.
Индекс объявлен на владельце; фрагмент получает типизированный вход.
Условие заимствования задаётся данными профиля. Нейтральный Rust не изменён.

`attachment.host` задаёт поля нужной проекции, их YAML-имена и роли контекста.
Выход `host` создаётся вместе с оболочкой и подключаемым фрагментом;
`--check` проверяет все результаты до записи. Неизвестные выражения,
неоднозначные свойства и повторные поля не принимаются молча.

Проекция ограничена контекстом и внешним файлом. Она не заменяет полный
договор свойств владельца: он использует свои common-декларации и проходит
отдельную приёмку. Текстовая принадлежность проверочной проекции также
не заменяет системное перечисление полного владельца.

## Проверки

- Матрица файлового переносчика 15/15, весь переносчик 215/215.
- Прежняя Rust-матрица четырёх обычных семейств расширена подключёнными
  владельцами на неизменённых e2e XML: 1/1 (34,38с). Сохранённый YAML
  восстанавливает индекс; обычный YAML экспортирует владельца и внешний
  файл без исходных XML-документов.
- Прежняя CFE-матрица 1/1 (44,64с): совместный индекс основы и расширения,
  вложенность, состояния и новое поколение UUID из сохранённого YAML.
- Число тестовых функций не увеличилось. XML-фикстуры не изменялись.
- Поиск новых дублей и архитектурная проверка Rust прошли.
- Рабочее приложение: facts45/45 и resources11/11; исправленный сборщик
  также завершился успешно, полностью кэшированный прогон занял9,075с.

При расширении матрицы исправлена ошибка использования API проверки:
сохранённый источник с явными UUID не является обычным YAML после подготовки
индекса. Проверка разделяет снимок источника, подготовку фактов и обычные
import/export; ошибку не обходят тегом !xml.

Также полностью кэшированный запуск приложения выявил ошибку сборщика:
отсутствие rustc.jsonl ошибочно считалось сбоем после успешных тестов.
Регрессия RED→GREEN теперь проверяет отсутствие журнала и обычный журнал;
при отсутствии запусков rustc отчёт показывает ноль компиляторов.

Полные рабочие маршруты пяти владельцев и окончательная приёмка XMLRoot
ещё не завершены. Флажки common-объектов остаются прежними.

## Подключение к существующей декларации

`attachExternalFileOwner` дополняет готовую декларацию, сохраняя её поля,
common-типы, проверки, существующий compose и входы. Контекст ищется
также в составных частях. XML-пути сравниваются с исходной регистрацией
по URI пространств имён; совпадения имени поля недостаточно, чтобы
подключить файл к владельцу другого типа.

Для конфликтующих имён входов создаётся отдельное имя. Ссылки на типы
входов переносятся через общий composeOwnerFragments. Отсутствующие поля,
неполные связи, циклы, повторное подключение и несовместимый component
отклоняются до создания Rust. Существующая Node-матрица проверяет все
пять профилей, сохранение исходных ограничений и импортные типы индекса.

В файловой операции можно задать:

```yaml
attachment:
  # Остальные параметры регистрации остаются прежними.
  target:
    declaration: metadata.original-owner
    id: metadata.connected-owner
outputs:
  # Остальные выходы остаются прежними.
  connected: rust/declarations/objects/connected-owner.generated.yaml
```

Отдельный ID сохраняет исходную декларацию и воспроизводимость --check.
При сборке в памяти функция подключения сохраняет ID владельца.

Для пяти типов дополнительно создана проверочная сборка настоящих
common.string и system.ObjectBelonging из исходных регистраций через
emitCandidates. Rust проверил связи и создал84файла (15622606байт).
Это проверка генерации, а не native round-trip новых деклараций.
Выбор финальных маршрутов и сборка остальных свойств владельцев остаются
следующим этапом; готовность общего подключения не закрывает эти пункты.

## Следующая сборка владельцев

Повторный отчёт обычного переносчика по исходным регистрациям:

| Владелец | Свойств | Кандидаты | Не включены обычным переносчиком |
|---|---:|---:|---:|
| Справочник | 69 | 42 | 27 |
| План счетов | 63 | 45 | 18 |
| План видов расчёта | 59 | 42 | 17 |
| План видов характеристик | 65 | 50 | 15 |

Это состав обычного переносчика, а не количество незавершённых common:
ресурсы, XMLRoot и ряд коллекций уже имеют отдельные принятые механизмы
сборки, которые он ещё не объединяет в эту проекцию. Нельзя повторно
реализовывать их по отметке unsupported-common. Полный список причин
сохранён в predefined-full-owner-next-blockers.json в журнале.
Следующий порядок — объединить существующие сборщики для плана видов
характеристик, затем устранить действительно отсутствующие договоры.

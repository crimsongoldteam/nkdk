# Проверка конечных форм YAML

Реализован общий скалярный профиль таблицы состояний:
[договор](../specs/2026-09-14-yaml-state-forms.md).
Семантика — обычный enum. Компилятор выпускает сопоставления Rust и выводит
восстановление отсутствующего поля. Во время преобразования таблица YAML
не читается. Смысловые теги отделены от тегов аномалий.

Проверены четыре формы в обычной записи и в словаре записей; неизвестное
XML-значение сохраняется и проходит обратную проверку общим механизмом.
Таблица участвует в типизации, схеме редактирования деклараций и JSON Schema
значений. Проверки смысловых тегов остаются в Rust: JSON не различает их.

Обычный XML-договор владельца не отменяет унаследованные формы YAML.
Конфликтующее повторное описание YAML-присутствия диагностируется при сборке.
Проверяются полнота таблицы, повтор формы, недопустимый тег, отсутствие поля,
пустое поле и пустая строка. XML-фикстуры не изменены, новых предметных
обработчиков в исполнителе нет. Проверки добавлены в существующие матрицы
связывания и сгенерированного кода.

Целевые проверки и полный Rust-прогон прошли: 212 тестов. Новых дублей нет,
Clippy компилятора и проверка архитектуры прошли. Дополнительно проверена
таблица с единственным отсутствующим состоянием: её свойство запрещено
схемой, а не описано недопустимым пустым enum. После этих уточнений повторно
прошла матрица сгенерированных преобразований; полный Clippy workspace
также прошёл. Схема передаёт Rust проверку смысловых предикатов состояния,
в том числе присутствия, поскольку отсутствующее YAML-поле может уже иметь
восстановленное смысловое значение.

## Следующая граница

Полное отношение ExtendedConfigurationObject ещё не реализовано. Оно требует
смыслового поля, не имеющего собственного XML-узла: состояние вычисляется из
ссылки на базовый объект и режима, а при обратном преобразовании восстанавливает
эти физические данные. Связывание уже допускает поле без XML при объявленном
восстановлении (`plan::check_coverage`), но генератор записи требует XML-путь,
а размещение составных частей диагностирует отсутствие места хранения.

Следующий шаг — хранение таких полей в общем плане без выдуманного XML-пути.
Это симметрично уже работающим скрытым YAML-полям. Физические маршруты и
смысловое хранение должны оставаться разными понятиями. Затем требуется
согласованная работа с общей коллекцией PropertyState, включая соседние
свойства; её нельзя подменять обработчиком одного имени или общей raw-обёрткой.
Скалярная таблица сама по себе не переносит все допустимые формы старого
свойства, например явно записанную пустую карту, и не снимает его блокировку.
Пользовательский чеклист остаётся без новых флажков.

При подготовке следующего шага подтверждена ещё одна общая граница:
`plan::scopes::dependencies` объединяет `xml_missing` и `yaml_missing`, затем
проверяет общий граф. Обратимое отношение «при импорте состояние из полей,
при экспорте поля из состояния» образует ложный цикл в таком объединении.
До подключения отношения необходимо проверять и выполнять порядок полей
отдельно для каждого направления. Общий набор захватываемого контекста
может сохраняться, но не должен определять порядок обоих преобразований.

Повторная проверка переноса: 61 сценарий коллекций и 26 проверок инструмента
прошли; Clippy каталога запускателя также прошёл.

# Реквизиты документа: готовность автоматических кандидатов

Источник семейства — `MetadataDocumentAttributeRules` из
`metadataDocument/childRules.ts`. Переносчик теперь распознаёт все **31 из 31**
свойств этого семейства; до изменения распознавал 27. Это проверка кандидатов,
а не полная приёмка реквизита или документа.

Компилятор обрабатывает объявленную коллекцию записей с договором пустого
XML-элемента и обычной формой вывода. Он выводит форму из правила владельца,
не по имени `ChoiceParameterLinks` или `ChoiceParameters`. Отдельная проверка
сгенерированного Rust-кода различает отсутствующий XML-узел и пустой элемент:
первый автоматически сохраняется как аномалия, второй восстанавливается из
пустого YAML без XML-референса.

Ссылка с сокращённым YAML-именем может одновременно иметь значения по
умолчанию для частей имени и правило отсутствия всей ссылки. Для корня,
заданного системным перечислением, компилятор переводит смысловое значение
в YAML-написание перед разбором шаблона. Переносчик даёт имени содержащего
объекта отдельный вход `containingOwnerName`: имя самого реквизита остаётся
входом `ownerName` для его синонима. Проверочный контекст документа и список
булевых реквизитов извлекаются из неизменённого e2e XML.

Прошли **169 независимых договоров** с реальными проекциями трёх реквизитов
документа и четырьмя новыми отдельными случаями. Для
`BinaryDataStorageLocationUseField` пустой XML-элемент отличается от обычного
экспорта отсутствующего значения, поэтому общий механизм сохраняет форму как
выведенную аномалию. Для `LinkByType` пустая форма предусмотрена правилом и
не требует аномалии.

Следующий критерий приёмки: подключить выпущенную декларацию
`MetadataDocumentAttributeRules` и коллекцию `MetadataDocumentRules.attributes`
к проектному маршруту; проверить целые XML ↔ YAML ↔ XML пары cf/cfe, включая
вложения, факты и аномалии, затем выполнить все проверки блока 9 плана.
Флажок `appliedObjects/metadataDocument` пока остаётся снятым.

22 сентября: переносчик выпускает
[`document-attributes.generated.yaml`](../../../rust/declarations/candidates/document-attributes.generated.yaml)
с полным элементом, коллекцией и фрагментом для владельца. Реальный cf XML
`ДокументВсеСвойства` проходит как самостоятельная операция в
[`document-attributes-operation.json`](../../../tests/migration/document-attributes-operation.json):
XML → YAML → XML без исходного референса. Всего проходит 88 договоров
коллекций. Вложение фрагмента в полную сборку документа выявило недостаток
специализации входов повторно используемых значений. Компилятор теперь
переносит связанные входы скалярных профилей в область содержащего владельца;
изолированный владелец с переставленными входами проходит XML → YAML → XML.
`BinaryDataStorageLocationUseField` остаётся читаемым полем
`ПолеИспользованияХраненияВХранилищеДвоичныхДанных`, без ложного `!xml/raw`.
Тот же случай закреплён общей проверкой компилятора для составного владельца
и объявленной коллекции. Полная сборка документа ещё упирается в контекстную ветвь
`common.document-choice-form`. Требование маршрута владельца сохранено в
отчёте генератора и не считается выполненным. Ни реквизит как рабочий
объект документа, ни документ целиком пока не приняты.

`FillValue` также остаётся отдельным незавершённым common-объектом. В этом
примере `common.metadata-value` читает обычные варианты и сохраняет форму XML,
а декларативное ограничение проверяет совместимость с типом. Полная приёмка
требует неявных значений, стандартных реквизитов, ссылок и всех владельцев,
которые сейчас обслуживаются `commonObjects/fillValue/register.ts`.

Декларация реквизитов находится в `rust/declarations/candidates` до
подключения к рабочему маршруту. Проверочные каталоги продолжают её собирать,
а рабочий `compiled-rules` исключает весь каталог кандидатов. Это устранило
ложный рост рабочего сгенерированного Rust-кода с 29,3 до 36,3 МБ и сохранило
ограничение сборки 32 МБ; сам компилятор не получил частного исключения для
реквизитов документа.

После переноса кандидата повторно прошли полный Rust workspace и 169
независимых договоров переноса из 286 деклараций. Проверка состава кандидата
подтверждает неизменность его содержимого; `compiled-rules` собирается с
29,3 МБ сгенерированного исходника. Проверки архитектуры, типов TypeScript,
форматирования и новых дублей также прошли.

В предыдущем проходе прошли 88 договоров коллекций. После перемещения
кандидата повторно прошли 133 договора подключения, общий `pnpm test` и
Clippy для всего Rust workspace.
Уточнено уже существовавшее архитектурное правило: приложение `nkdk`
использует тот же локально исправленный `yaml-rust2`, что и общие Rust-слои.
Команда `test:migration-family` в текущем `package.json` ещё не существует;
семейная приёмка остаётся частью следующего этапа, а вывод
`migration:families` пока отражает только состав кандидатов и блокировки.

# Подключение составного состояния к исходному правилу реквизита

## Сделано

- `ownerStateRecords` выбирает структурированные свойства по зарегистрированным
  возможностям состояния из rules.ts. Короткий договор подключения расположен в
  `tools/rules-migration/contracts/record-state-profiles.yaml`.
- Для `common.type-description` обычные состояния и `MultiState` используют
  уже существующие декларации. Составное значение — отдельный вариант рядом
  с обычным, изменяемым и проверяемым, без второго вложенного преобразователя.
- Режим берётся из подготовленного индекса по владельцу и XML-имени свойства.
  Ограничения версий получены из исходных правил; история восстанавливается
  декларативным значением по умолчанию.
- `metadataAttributeTypesOnly` передаётся во все группы. Их преобразование и
  аномалии остаются ответственностью common, а не сборщика или оркестратора.
- История записывается перед свойствами, как в исходном XML.
- Сборщик сразу отклоняет неподключённые зависимости между частями: после
  замены `type` нельзя оставить ссылки FillValue/ChoiceForm на удалённое поле.
  Это ошибка сборки договора, а не аномалия входного XML.
- Генератор исправлен для вспомогательной записи без физических полей и для
  условного добавления строк с пустой ветвью. Предупреждения не подавлялись.

## Граница приёмки

Используются Type и PropertyState двух исходных реквизитов СправочникПолный
из e2e: СтроковыйРеквизитСИндексом и РеквизитСправочника. Ожидаемый YAML взят
независимо из существующей фикстуры. Их XML помещён в проверочный контур
Attribute/InternalInfo/Properties; это всё ещё не проверка всех свойств
исходного Attribute целиком.

33 обычных свойства реального rules.ts компилируются отдельно. Полная
интеграция состояния требует смысловой проекции Type для FillValue и формы
выбора, общей принадлежности, ссылки на основную конфигурацию и UUID от
родителя. Защитная проверка зависимостей не заменяет этот договор. Ни один
новый флажок полной приёмки не установлен; common остаются 56/90.

# Добавление нового объекта метаданных

## Принцип работы

Процесс **итеративный**, не линейный. Два отдельных цикла: XML-цикл и YAML-цикл. Каждый цикл начинается с round-trip — это жёсткий барьер: пока round-trip не зелёный, следующие шаги цикла не запускаются. Ошибка на любом шаге цикла → фикс `rules.ts` → перезапуск цикла с round-trip.

> **Жёсткий барьер: XML-цикл сначала, YAML-цикл потом.**
> Пока XML-цикл не завершён полностью, запрещено касаться:
> - `<fixtureName>YAML`-экспортов в TS-фикстурах (`__fixtures__/<name>.ts`);
> - файлов `fromYAML.test.ts` и `toYAML.test.ts`;
> - YAML-поведенческих аннотаций в `rules.ts`: `defaultValueYAML`, `toYAML: false`, `fromYAML: false`, `excludeIfEqualNameYAML`, `useAsShortValueYAML` и т.п.
>
> **Разрешено и нужно** сразу — в `rules.ts` писать английские TS-ключи свойств (`numberType`, `checkUnique`) и **русские имена** в поле `yaml: "..."` (`"ТипНомера"`, `"КонтрольУникальности"`), а также `itemType` и `itemTypePrefix`. Это имена, они часть структуры правила и согласуются на шаге 1 (бриф). Остальные YAML-аннотации собираются в брифе «в память» и применяются только на шаге 11.

## Точка входа

**Новый объект** — начинай с шага 1 (Бриф).

**Существующий объект** (диагностика, починка свойства) — пропускай шаги 1–6 и начинай сразу с XML-цикла (шаг 7). Если XML-цикл уже зелёный и проблема только в YAML — начинай с YAML-цикла (шаг 11).

## Шаг 1. Бриф (последовательный)

Не задавай сразу всё списком. Перед каждым вопросом — **быстро исследуй кодовую базу** (XML-фикстуры в каталоге, `types.ts` рядом, 1–2 похожих соседних metadataItem, `schema/*.xsd`) и спрашивай только то, что из кода не выводится. Показывай пользователю, что ты нашёл, и проси **подтверждения/корректировки** — это короче, чем опрос с нуля.

Пункты брифа — в этом порядке, по одному:

**XML-сторона:**

1. Путь к каталогу нового объекта метаданных (обычно дан в аргументе команды).
2. XML-фикстуры — проверь, что в `__fixtures__/` лежит 1–3 файла с разным заполнением. Если меньше — попроси добавить **до** продолжения.
3. Схема объекта (XSD) — её нужно получить от пользователя, если в репозитории нет соответствующего `.xsd`.
4. Свойства, не встречающиеся в XML-фикстурах (например, `runtimeOnly`-поля) — запроси отдельным пунктом с типом и признаком `runtimeOnly`.
5. Родительский каталог для `index.ts` — выводится из пути аргумента.
6. Дочерние коллекции — извлеки из XML-фикстуры, подтверди наличие/отсутствие.
7. Известные ограничения (read-only из XML, «только на запись» и т.п.) — явный вопрос.

**YAML-сторона (обязательно спрашиваем заранее, хотя применим только на шаге 11):**

8. YAML-имена ключей для каждого свойства (проверь `types.ts` / соседний metadataItem — если там уже есть `XxxYAML`-интерфейс, показывай его и проси подтверждения).
9. `itemTypePrefix` — YAML-префикс объекта верхнего уровня (например, `"Нумератор"`, `"Документ"`, `"Перечисление"`).
10. Для каких свойств нужен `defaultValueYAML` — чтобы в YAML при экспорте опускались значения-дефолты.
11. Свойства, исключённые из YAML (`toYAML: false`, `fromYAML: false`) — обычно технические/служебные.
12. Особые YAML-флаги на полях (`excludeIfEqualNameYAML`, `useAsShortValueYAML`) — только если пользователь их знает; иначе — по аналогии с соседом, явно предложи.

Правило для каждого пункта: если ответ виден в коде или схеме — **не спрашивай**, показывай пользователю что ты нашёл и проси подтверждения/корректировки.

Без брифа не начинай работу.

## Шаг 2. Анализ

Прочитай XML-фикстуры, схему, список свойств. Сверься с 1–2 **похожими существующими metadataItem** в `packages/core/metadata/` — как они решают аналогичные задачи (композиты, ссылки, коллекции).

## Шаг 3. `types.ts`

Создай файл типов. Подробнее — [types.md](references/types.md).

## Шаг 4. `rules.ts` — первое приближение ⟲

Создай файл правил. Подробнее — [rules.md](references/rules.md).

Правило: **предпочитай `rules.ts`** вместо ручных `fromXML`/`toXML`/`fromYAML`/`toYAML`.

## Шаг 5. Регистрация типов

Без регистрации round-trip не запустится — движок не узнает тип. Нужно **три** точки правки, не две:

**5.1. `MetadataItemTypeRegistry`** — `packages/core/metadata/orchestration/metadataItem/registry.ts`.
Добавь ключ типа: `<ObjectName>: { metadata: <ObjectName>; yaml: <ObjectName>YAML }`.

**5.2. `PropertyTypeRegistry` + `PropertyRuleTypeKeys`** — `packages/core/metadata/orchestration/property/registry.ts`.
В **том же файле** правятся две структуры:
- `PropertyTypeRegistry` — добавь ключ `<ObjectName>: { item: <ObjectName>; yaml: <ObjectName>YAML }`.
- Массив `PropertyRuleTypeKeys` ниже в файле — добавь строку `<ObjectName>: "<ObjectName>"`. Без этого type-check пройдёт, но движок на runtime не увидит тип в итерациях.

**5.3. Привязка правила к типу** — в `types.ts` самого объекта вызови `registerMetadataItemRule({ propertyType, itemRule })` (см. [types.md](references/types.md)). Это связывает XML/YAML import/export функции с типом через реестр runtime-функций.

**Развилка: одиночный объект vs коллекция.** Если объект в модели представлен как `T[]` (массив), используй `registerMetadataItemCollectionRule` вместо `registerMetadataItemRule` — см. [types.md](references/types.md), раздел «Одиночный объект vs коллекция».

## Шаг 6. `index.ts`

Создай `index.ts` в каталоге объекта. Пропиши его в `index.ts` вышестоящего каталога.

## XML-цикл

Шаги 7–9 образуют цикл. Ошибка на любом шаге → фикс → перезапуск с шага 7.

## Шаг 7. XML round-trip ⟲ (жёсткий барьер)

Напиши `fromXML.test.ts` с **round-trip блоком**: импорт XML → экспорт полученной структуры → сравнение с исходным XML (строковое, без канонизации). Шаблоны и правила сравнения — [tests.md](references/tests.md).

Запусти тест. Если расхождения — не переходи к шагу 8, устрани расхождения:

1. Применяй **протокол эскалации** ([tests.md](references/tests.md) → раздел «Протокол эскалации»):
   - простые случаи (отсутствие правила для известного свойства, булева нормализация, лишний default) — чини сам
   - композиты/ссылки, неизвестные атрибуты, расхождения смысла значений — спрашивай пользователя
2. Правь `rules.ts`, перезапускай цикл с шага 7
3. После 3 итераций без прогресса — стоп, покажи текущий diff пользователю
4. Блок вопросов пользователю — **одним сообщением** с пронумерованным списком и предлагаемым решением

**Если расхождение во фрагменте подчинённого объекта** (тег принадлежит другому metadataItem) — стоп. Одним сообщением пользователю: имя подчинённого, путь к его каталогу, XML-фрагмент из фикстуры родителя, на котором падает round-trip. Жди решения пользователя, не правь чужой `rules.ts` сам.

## Шаг 8. TS-фикстуры

На каждую XML-фикстуру `<name>.xml` — отдельный TS-файл `__fixtures__/<name>.ts` с ожидаемой формой объекта (результат импорта из прошедшего round-trip). Имя TS-файла и имя экспорта совпадают со slug'ом XML-файла. Подробнее — [fixtures-data.md](references/fixtures-data.md).

YAML-поля на этом шаге **не заполняй** — `<fixtureName>YAML` добавляется на шаге 11 после обсуждения черновика YAML в барьере.

> Существующие объекты метаданных, ещё использующие единый `data.ts`, не переписывай насильно. Новая конвенция применяется к новым фикстурам; старые мигрируют при естественной правке.

## Шаг 9. fromXML тест

Допиши в `fromXML.test.ts` блок `it("import <name>")` с `expect(result).toEqual(<fixtureName>)` для каждой XML-фикстуры. Round-trip блок **остаётся** в `fromXML.test.ts` как регресс.

Если тест падает → фикс → перезапуск цикла с шага 7.

## Шаг 10. toXML тест

Создай `toXML.test.ts`.

Если тест падает → фикс → перезапуск цикла с шага 7.

## Барьер: обсуждение YAML-структуры

Не переходи к YAML-циклу, пока XML-цикл не завершён полностью (шаги 7–10 зелёные).

Сгенерируй **черновик YAML** из TS-фикстур по аналогии с 1–2 похожими соседними metadataItem. Покажи пользователю черновик + список явных вопросов (названия ключей, вложенность vs плоскость, опускать ли опциональные поля с default). Без подтверждения пользователя YAML-правила не пиши.

## YAML-цикл

Шаги 11–13 образуют цикл. Ошибка на любом шаге → фикс → перезапуск с шага 11.

## Шаг 11. YAML round-trip ⟲ (жёсткий барьер)

Допиши YAML-часть в `rules.ts`. Напиши `fromYAML.test.ts` с **round-trip блоком**: импорт YAML → экспорт → сравнение с исходным YAML **на уровне parsed object** (не строкой — форматирование не семантика). Добавь экспорт `<fixtureName>YAML` рядом с TS-фикстурой в том же `__fixtures__/<name>.ts`.

Если round-trip падает — не переходи к шагу 12, устрани расхождения (тот же протокол эскалации). Перезапускай цикл с шага 11.

**Если расхождение во фрагменте подчинённого объекта** (ключ принадлежит другому metadataItem) — стоп. Одним сообщением пользователю: имя подчинённого, путь к его каталогу, YAML-фрагмент из фикстуры родителя, на котором падает round-trip. Жди решения пользователя, не правь чужой `rules.ts` сам.

## Шаг 12. fromYAML тест

Допиши в `fromYAML.test.ts` блок `expect(result).toEqual(<fixtureName>)`. Round-trip остаётся как регресс.

Если тест падает → фикс → перезапуск цикла с шага 11.

## Шаг 13. toYAML тест

Создай `toYAML.test.ts`.

Если тест падает → фикс → перезапуск цикла с шага 11.

## Шаг 14. Отчёт о покрытии

В финальном сообщении пользователю приведи **явный список свойств**, **не покрытых ни одной XML-фикстурой** (правила написаны, но поведение не проверено). Пользователь решает, докидывать ли фикстуру.

Формат:

```
Покрытие свойств фикстурами: 12/15
Непокрытые: Parent, Comment, UseStandardCommand
```

# Добавление нового объекта метаданных

## Принцип работы

Процесс **итеративный**, не линейный. Шаги с маркером ⟲ повторяются, пока round-trip не станет OK — не переходи к следующему этапу, пока есть расхождения. При неясных расхождениях — останавливайся и обращайся к пользователю по протоколу эскалации (см. [tests.md](references/tests.md)).

Идея: написать первое приближение `rules.ts` → прогнать round-trip на XML-фикстуре → найти потери → чинить `rules.ts` или спрашивать пользователя → повторять, пока source XML и экспортированный XML не совпадут. Только после этого переходить к `data.ts`, раздельным тестам и YAML.

## Шаг 1. Бриф

Запроси у пользователя **одним сообщением**:

1. Путь к каталогу нового объекта метаданных
2. XML-фикстуры (1–3 файла с разным заполнением) в `__fixtures__/` каталога объекта
3. Схему объекта (XSD или описание)
4. Полный список свойств — для каждого:
   - имя XML-атрибута/тега
   - YAML-синоним (русский)
   - тип (примитив / ссылка на metadataItem / перечисление / композит)
   - обязательность, значение по умолчанию
5. Родительский каталог (в какой вышестоящий `index.ts` регистрируется)
6. Дочерние коллекции (tabular sections, attributes, forms и т.п.)
7. Известные ограничения (например, свойство только для чтения из XML)

Без брифа не начинай работу.

## Шаг 2. Анализ

Прочитай XML-фикстуры, схему, список свойств. Сверься с 1–2 **похожими существующими metadataItem** в `packages/core/metadata/` — как они решают аналогичные задачи (композиты, ссылки, коллекции).

## Шаг 3. `types.ts`

Создай файл типов. Подробнее — [types.md](references/types.md).

## Шаг 4. `rules.ts` — первое приближение ⟲

Создай файл правил. Подробнее — [rules.md](references/rules.md).

Правило: **предпочитай `rules.ts`** вместо ручных `fromXML`/`toXML`/`fromYAML`/`toYAML`.

## Шаг 5. Регистрация типов

Зарегистрируй объект метаданных в двух реестрах:

- `PropertyTypeRegistry` — `packages/core/metadata/orchestration/property/registry.ts`
- `MetadataItemTypeRegistry` — `packages/core/metadata/orchestration/metadataItem/registry.ts`

Без регистрации round-trip не запустится — движок не узнает тип.

## Шаг 6. `index.ts`

Создай `index.ts` в каталоге объекта. Пропиши его в `index.ts` вышестоящего каталога.

## Шаг 7. XML round-trip ⟲

Напиши `fromXML.test.ts` с **round-trip блоком**: импорт XML → экспорт полученной структуры → сравнение с исходным XML (строковое, без канонизации). Шаблоны и правила сравнения — [tests.md](references/tests.md).

Запусти тест. Если расхождения:

1. Применяй **протокол эскалации** ([tests.md](references/tests.md) → раздел «Протокол эскалации»):
   - простые случаи (отсутствие правила для известного свойства, булева нормализация, лишний default) — чини сам
   - композиты/ссылки, неизвестные атрибуты, расхождения смысла значений — спрашивай пользователя
2. Правь `rules.ts`, повторяй прогон
3. После 3 итераций без прогресса — стоп, покажи текущий diff пользователю
4. Блок вопросов пользователю — **одним сообщением** с пронумерованным списком и предлагаемым решением

Переходи к шагу 8 только когда round-trip зелёный.

## Шаг 8. `data.ts`

Создай `__fixtures__/data.ts`. Используй **результат импорта** из прошедшего round-trip как основу для внутренних фикстур. Подробнее — [fixtures-data.md](references/fixtures-data.md).

YAML-фикстуры на этом шаге **не заполняй** — структура YAML согласуется на шаге 10.

## Шаг 9. Раздельные XML-тесты

Допиши в `fromXML.test.ts` блок с `expect(result).toEqual(fixtureMyObject)`. Создай `toXML.test.ts`. Round-trip блок **остаётся** в `fromXML.test.ts` как регресс.

## Шаг 10. Обсуждение YAML-структуры

Сгенерируй **черновик YAML** из `data.ts` по аналогии с 1–2 похожими соседними metadataItem. Покажи пользователю черновик + список явных вопросов (названия ключей, вложенность vs плоскость, опускать ли опциональные поля с default). Без подтверждения пользователя YAML-правила не пиши.

## Шаг 11. YAML-правила ⟲

Допиши YAML-часть в `rules.ts`. Напиши `fromYAML.test.ts` с **round-trip блоком**: импорт YAML → экспорт → сравнение с исходным YAML **на уровне parsed object** (не строкой — форматирование не семантика).

Итерации по тому же протоколу эскалации. Заполни `fixtureMyObjectYAML` в `data.ts`.

## Шаг 12. Раздельные YAML-тесты

Допиши в `fromYAML.test.ts` блок `expect(result).toEqual(fixtureMyObject)`. Создай `toYAML.test.ts`. Round-trip остаётся как регресс.

## Шаг 13. Отчёт о покрытии

В финальном сообщении пользователю приведи **явный список свойств**, **не покрытых ни одной XML-фикстурой** (правила написаны, но поведение не проверено). Пользователь решает, докидывать ли фикстуру.

Формат:

```
Покрытие свойств фикстурами: 12/15
Непокрытые: Parent, Comment, UseStandardCommand
```

## Диагностика неверно работающего свойства

Если пользователь сообщает, что свойство уже существующего metadataItem работает неверно:

1. Добавить в фикстуру минимальный пример с этим свойством (если его нет — попросить пользователя)
2. Запустить существующий round-trip в `fromXML.test.ts` (или добавить его, если объект старый и round-trip отсутствует)
3. Применить протокол эскалации как при создании
4. Починить `rules.ts`
5. Прогнать все тесты каталога, убедиться что старые не сломались

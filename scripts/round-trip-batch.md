# Пакетная проверка конфигураций через YAML

```bash
node scripts/round-trip-batch.mjs --repo /Users/nikita/git/round-trip-compact
```

Путь можно передать и переменной окружения `NKDK_XML_REPO`. Аргумент `--repo`
имеет приоритет. `.env` для выбора пакетного репозитория не читается.
Скрипт можно вызвать по абсолютному пути из любого каталога; он использует
`round-trip.sh` и код MCP из того же checkout NKDK, в котором находится сам.
Перед запуском установите зависимости NKDK командой `pnpm install`.

Для пробного запуска на трёх самых маленьких конфигурациях:

```bash
node scripts/round-trip-batch.mjs --test --repo /Users/nikita/git/round-trip-compact
```

`--test` выполняет настоящий round-trip и создаёт ветку, XML-коммиты и отчёт,
а не имитирует запуск. Размер — сумма размеров всех обычных файлов внутри
конфигурации в байтах, включая вложенные каталоги. Символические ссылки
при подсчёте отклоняются. Выбор и обработка идут по возрастанию размера,
при равенстве — по имени; если конфигураций меньше трёх, выбираются все.
Отчёт содержит выбранные конфигурации и их исходные размеры; остальные
конфигурации не запускаются и не входят в таблицу результатов.

Для каждой выбранной конфигурации `round-trip.sh` собирает MCP командой
`pnpm --filter @nkdk/mcp build` и запускает локальный
`node packages/mcp/dist/bin/nkdk-mcp` как дочерний процесс. Одна stdio-сессия
используется для `nkdk.import_from_xml` и `nkdk.sync_to_xml`, затем закрывается.
Настраивать соединение MCP в приложении или открывать сетевой порт не требуется.

## Источник и ветка

Ожидается один Git-репозиторий с конфигурациями `cf/<имя>/Configuration.xml`.
Конфигурации перебираются по имени последовательно, каждая как самостоятельный
компонент `cf` отдельного MCP-проекта. Обычные каталоги без `Configuration.xml`
не обрабатываются. Вложенные репозитории и символические ссылки на каталоги
конфигураций не поддерживаются. Расширения вне `cf` не входят в этот прогон.

Перед подготовкой ветки скрипт очищает весь указанный XML-репозиторий:
`git reset --hard HEAD` сбрасывает tracked/staged-изменения, `git clean -fdx`
удаляет untracked- и ignored-файлы и каталоги, в том числе `.DS_Store`.
Это необратимо для не сохранённых в Git данных; резервной копии не создаётся.
Наличие репозитория на GitHub позволяет восстановить только отправленные коммиты.
Путь проверяется как корень Git-репозитория, локальная `main` должна существовать.
Перед очисткой проверяется отсутствие вложенных Git-репозиториев (включая bare)
и подмодулей:
при их обнаружении запуск запрещён, принудительного `git clean -ff` нет.
Очистка относится только к XML-репозиторию из `--repo`, не к checkout NKDK.
Если ignored-файлы внутри конфигураций появились заново после очистки,
проверка безопасности остановит запуск.
Должны быть настроены Git-имя и email для коммитов.

Всегда от локальной ветки `main` создаётся новая ветка вида
`codex/round-trip-2026-09-02_16-30-00-123Z` (время старта в UTC).
Без локальной `main` запуск запрещён: `master`, `origin/main` и текущая ветка
не используются как запасные варианты. Конфигурации, размеры и настройки
игнорирования читаются уже из дерева `main`, даже если запуск сделан с ветки
предыдущего прогона. Сама `main` и предыдущие ветки не передвигаются.
Скрипт не скачивает изменения и не делает push. Для проверок дерево `main`
при необходимости открывается с detached HEAD; при ошибке подготовки
восстанавливается исходная ветка или исходный detached HEAD.
После успешного запуска остаётся выбрана новая ветка прогона.
Не редактируйте XML-репозиторий и не запускайте второй прогон одновременно.

## Коммиты и отчёт

Для каждой конфигурации вызывается существующий
`.agents/skills/round-trip-yaml/round-trip.sh`: XML → YAML → XML.
После успешного завершения:

- все Git-различия конфигурации (изменения, добавления и удаления) сохраняются
  отдельным коммитом; изменения предыдущих конфигураций не откатываются;
- если различий нет, отдельного коммита нет, но строка отчёта всё равно появляется:
  `без расхождений`, `0`, `—`;
- отчёт `round-trip-reports/<время-старта>.md` обновляется на диске после каждого
  результата, а в конце сохраняется отдельным коммитом вместе с журналами
  `round-trip-reports/<время-старта>.logs/log-N.txt`.

В шапке отчёта только время начала, состояние и название ветки.
Поясняющих абзацев до или после результатов нет.
В отчёте ровно одна сводная таблица: результаты, исходные размеры (в `--test`),
статистика всех семи видов тегов, количество широких raw и ссылки на журналы.
Последняя строка содержит суммы доступных данных. Тексты ошибок находятся
в отдельном разделе `Ошибки`, сгруппированном по конфигурациям, без дополнительных
таблиц. Диагностика MCP читается из сохранённых результатов операций; при
сокращении ответа используется полный JSONL-отчёт. Если операция не успела
записать диагностику, сохраняется вывод runner.
Считаются реальные различия Git, включая известные допустимые различия,
которые одиночный диагностический скрипт может скрывать в своём выводе.

Столбцы `Импорт`, `Экспорт`, `Всего` используют формат `мм:сс`:
например, `02:15` — 2 минуты 15 секунд. Время округляется до ближайшей
секунды, минуты могут превышать 59.
Импорт и экспорт измеряются по времени создания и завершения
операций MCP, включая ожидание в очереди и неуспешные операции. Для этапа,
который не запускался или не сохранил завершённую операцию, выводится `—`.
Общее время измеряется отдельно для каждой конфигурации: запуск и сборка MCP,
round-trip, статистика, сохранение диагностики, XML-коммит и очистка временных
файлов. Подготовка всего репозитория и итоговый коммит отчёта сюда не входят.
В строке «Итого» суммируются доступные длительности без предварительного
округления; общее время не обязано совпадать с суммой импорта и экспорта.

Для анализа выберите строки `есть расхождения` и откройте указанный коммит:

```bash
git -C /Users/nikita/git/round-trip-compact show <хеш-коммита>
```

## Статистика тегов и широкие raw

После каждой проверки в отчёт и `log-N.txt` добавляется статистика YAML,
в том числе если XML-различий нет. Чистый round-trip может обеспечиваться raw,
поэтому для выбора конфигураций на анализ смотрите также статистику:

- В единой таблице: число YAML-файлов и вхождений `!xml/raw`, `!xml/invalid`,
  `!xml/important`, `!xml/uuid`, `!xml/string`, `!xml/name`,
  `!xml/standard-attributes` по конфигурациям и суммарно. Последние три — теги
  формы XML, но они также включены в статистику отдельными видами.
- В журналах: конфигурация, логический каталог и YAML-файл широких raw,
  число предупреждений `xml_raw_scope_too_broad`. YAML-пути указаны относительно
  каталога импортированной конфигурации, без префикса `cf/`. Сам временный YAML
  после сбора статистики удаляется.

Считаются физические теги синтаксических узлов YAML: как ключи, так и значения.
`!xml/invalid/2` и последующие номера входят в `invalid`. Комментарии, строковые
значения с текстом `!xml/...` и повторные ссылки через YAML-алиасы не увеличивают
счётчики. Список видов и обработка тегов режимов берутся из production-реестра
NKDK, используется та же версия YAML-парсера.

Широкий raw определяется предупреждением импортёра, а не размером XML.
Число таких предупреждений не обязано совпадать с числом raw-тегов. Если MCP
сократил inline-диагностику, читается весь JSONL-отчёт без повторного учёта preview.

При ошибке sync статистика уже успешно импортированного YAML также сохраняется.
Если импорт не завершён или статистика недоступна, в таблице стоит `—`, не `0`;
причина указывается отдельно, а суммарная строка включает только доступные данные.
При ошибке сбора статистики после успешного round-trip XML-различия всё равно
коммитятся, конфигурация помечается ошибочной, обработка остальных продолжается.

## Ошибки и временные файлы

При ошибке импортирования, синхронизации, статистики или Git-фиксации текущая
конфигурация получает статус `ошибка`, но скрипт переходит к следующей.
После обработки всех конфигураций итоговый статус — `завершён` (код `0`)
или `завершён с ошибками` (код `1`). При ошибке import/sync исходный XML
не заменяется неполным экспортом. Предыдущие и последующие успешные коммиты
остаются, отчёт и журналы сохраняются итоговым коммитом.
Частичные изменения неуспешной конфигурации остаются на диске/в индексе для
диагностики и не попадают в коммит отчёта или следующей конфигурации. Ошибки
общих проверок безопасности, записи отчёта/журналов и удаления временных файлов
останавливают прогон: уже сохранённые результаты остаются на диске.

Временные YAML, XML и MCP-проекты создаются в собственном каталоге
`${TMPDIR:-<системный временный каталог>}/nkdk-round-trip-batch-*` и удаляются
после каждой конфигурации, в том числе ошибочной, после записи статистики
и диагностики в репозиторий. В конце удаляется и корневой временный каталог.
Журналы `log-N.txt` остаются в ветке XML-репозитория. Исторические временные
пути в выводе runner после очистки недоступны; XML-diff смотрите через Git.
Номер лога соответствует номеру строки конфигурации в отчёте.
Старые `NKDK_XML_DIR` и `NKDK_ROUND_TRIP_YAML_DIR` переопределяются внутри прогона,
поэтому не влияют на выбор конфигураций и не очищаются.

Автоматического продолжения после остановки нет. При аварийном завершении
процесса итоговый коммит отчёта и очистка временных каталогов не гарантированы,
но уже сохранённые XML-коммиты, журналы и последняя запись отчёта остаются.
Перед повторным запуском сохраните нужные результаты: следующая подготовка
сбросит незакоммиченные изменения и удалит неотслеживаемые файлы отчётов и журналов.

## Проверки самого скрипта

```bash
pnpm test:round-trip-batch
```

Тесты используют временные Git-репозитории и настоящий `round-trip.sh`, заменяя
только тяжёлый MCP-прогон. Реальные конфигурации пользователя не затрагиваются.
Проверки также включены в `pnpm test`.

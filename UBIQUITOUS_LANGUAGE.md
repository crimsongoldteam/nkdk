# Ubiquitous Language

## Граф и его структура

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Граф** | Долгоживущий объект на graphology, хранящий все объекты метаданных и связи между ними | Дерево зависимостей, dependency tree |
| **Узел (Node)** | Вершина графа, представляющая один объект метаданных — прикладной объект, реквизит, табличную часть или элемент формы | Элемент графа, вершина |
| **Узел-заглушка (Stub Node)** | Узел без атрибута `item` — объект ещё не импортирован или был удалён, но на него есть входящие ссылки | Phantom node, placeholder |
| **NodeId** | Уникальный идентификатор узла в формате пути без промежуточных сегментов: `Справочник.Товары.Цена`, `Справочник.Товары.Состав.Количество` | Ключ, идентификатор |
| **Composition-ребро** | Связь структурного владения между родителем и дочерним объектом (справочник → реквизит, справочник → табличная часть) | Структурная связь |
| **Reference-ребро** | Ссылочная связь между объектами — один объект ссылается на другой по типу или по пути | Зависимость, dependency |
| **Битая ссылка** | Reference-ребро, ведущее на узел-заглушку без `item` — целевой объект не существует | Dangling reference, orphan |

## Объекты метаданных

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Прикладной объект** | Top-level объект метаданных: справочник, документ, регистр и т.д. | Метаданные (слишком общее) |
| **Реквизит** | Пользовательское свойство прикладного объекта с именем и типом | Атрибут, поле |
| **Стандартный реквизит** | Реквизит, всегда присутствующий у объекта определённого типа (`Код`, `Наименование`, `Ссылка`) — создаётся в графе даже без явного описания в YAML | Системный реквизит |
| **Табличная часть** | Вложенная таблица прикладного объекта, содержащая собственные реквизиты | Таблица (неоднозначно — есть таблица формы) |
| **Составной тип** | Тип реквизита, допускающий несколько типов значений одновременно (`Справочник.Договоры \| Справочник.Контрагенты`) | Множественный тип, union type |

## Формы и элементы

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Элемент формы** | Визуальный компонент формы (InputField, Table, Button), являющийся узлом в графе | Контрол, виджет |
| **DataPath** | Путь от элемента формы к данным объекта, может быть составным: `Объект.Договор.Владелец.ГрафикПлатежей[1].Сумма` | Привязка данных, binding |
| **Индексация `[N]`** | Обращение к конкретной строке табличной части или таблицы формы в dataPath — допустимо только для таблиц, значение не валидируется | Доступ по индексу |

## Импорт и обновление

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Полный импорт** | Парсинг всех YAML и NKDK файлов проекта при старте workspace или CLI с построением графа | Начальная загрузка, bootstrap |
| **Инкрементальное обновление** | Обновление графа при изменении одного файла — удаление узлов файла и переимпорт | Частичный импорт |
| **Обратный индекс** | `Map<filePath, Set<nodeId>>` — позволяет быстро найти все узлы, порождённые конкретным файлом | File index |
| **Walker** | Алгоритм обхода графа для резолвинга составных dataPath — на каждом шаге переходит по reference-рёбрам, при составных типах ветвится (union-семантика) | Resolver, traverser |

## Внешние файлы свойств (из диалога о `QueryText` динамического списка)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Динамический список** (`DynamicList`) | Тип настроек **реквизита формы**, описывающий источник данных списка | — |
| **Произвольный запрос** (`ManualQuery` / `customQuery`) | Булев признак **динамического списка**: текст запроса задан вручную | Ручной запрос, manual query |
| **Текст запроса** (`QueryText` / `queryText`) | Строка на языке запросов 1С, используемая при **произвольном запросе** = `true` | Запрос, SQL |
| **Внешний файл** (`externalFile`) | Файл рядом с YAML, хранящий значение одного свойства, которое не выгружается в YAML | Sidecar, вложение |
| **Каталог формы** (`formDir`) | Директория YAML-выгрузки формы (`Формы/<ИмяФормы>/`) | Папка формы |
| **Опция `externalFile`** | Поле **правила свойства** в `rules.ts`, объявляющее хранение значения во **внешнем файле** (`dir`, `extension`, `nameFrom`) | — |
| **`nameFrom: "parent"`** | Указание: имя **внешнего файла** берётся из `name` родителя в дереве модели (у `DynamicList` — имя **реквизита формы**) | — |
| **Round-trip (XML ↔ YAML+query)** | Последовательность `XML → модель → YAML+внешние файлы → модель → XML` с идентичным результатом | Круговой обход |
| **Расширение `.query`** | Каноничное расширение **внешнего файла** с **текстом запроса** согласно документации формата | `.bsl` (устаревшее, было багом инструмента) |

### Relationships внешних файлов

- **Реквизит формы** с типом **динамический список** и **произвольным запросом** = `true` имеет один **внешний файл** `<formDir>/ДинамическийСписок/<ИмяРеквизита>.query`.
- В **YAML-представлении** нет ни **текста запроса**, ни **произвольного запроса** — факт наличия **внешнего файла** ⇔ `ManualQuery=true` в XML.
- При импорте (YAML→XML) отсутствие файла → `ManualQuery=false`; пустой файл → `ManualQuery=true` с пустым **текстом запроса**.

## Наследование правил и фикстур (из диалога о `formGroup`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Семейство элементов** | Группа однотипных **элементов формы** с общей основой в отдельной папке (`formField`, `formGroup`); сама папка не является зарегистрированным `itemType` | Базовый класс, abstract element |
| **Наследник** (child) | Конкретный элемент семейства (например, `ColumnGroup` для `formGroup`), чьи **правило** и **фикстуры** подмешивают общую часть | Потомок, subtype |
| **Общие свойства** (`formGroupCommonProperties`) | Экспортируемый из `<семейство>/rules.ts` объект свойств, подмешиваемый в `properties` **правил** наследников | Shared props, base props |
| **Базовая фикстура** (`fullFormGroupCommonFixture`) | Объект в `<семейство>/__fixtures__/data.ts` с каноничными значениями **общих свойств** — в четырёх формах: TS / Enterprise / PartialYAML / TypedYAML | Common fixture |
| **Канонические значения** | Единый эталонный набор значений **общих свойств** для всего семейства; источник — `formField`, распространяется на `formGroup` | Дефолты, defaults |
| **Подмешивание** (spread) | Включение `...formGroupCommonProperties` / `...fullFormGroupCommonFixture` без переопределения общих полей | Merge, inherit |
| **Override после spread** | Переопределение общего поля в наследнике после **подмешивания** — **запрещено** в данной модели наследования | — |
| **`runtimeOnly`** | Флаг **правила свойства**: свойство существует только в рантайме, **не попадает** ни в YAML, ни в Enterprise XML, ни в **XML-фикстуру**, ни в TS-фикстуру | inMemoryOnly |
| **Селективное отключение сериализации** (`toYAML: false`, `fromYAML: false`) | Точечные флаги в **правиле свойства** **наследника**, отключающие конкретное **направление** только для этого наследника. Свойство остаётся в типах и в других **формах представления** (например, в Enterprise XML), но в YAML не пишется и не читается. Применяется, когда поле есть в спецификации 1С, но в практике XML-фикстуры конкретного элемента отсутствует | skip serialization |
| **«Не общее» поле** | Свойство, объявленное в **общих свойствах** семейства, но фактически присутствующее в **XML-фикстурах** не всех **наследников**. Каноничный паттерн: убрать из **общих свойств**, добавить в `properties` тех наследников, где оно есть; у остальных — либо не объявлять, либо использовать **селективное отключение сериализации** | partially-shared |
| **`defaultValueYAML`** | Значение **правила свойства**, подставляемое при отсутствии свойства в YAML; при введении **общих свойств** переносится от наследника в **общие** | Fallback |
| **Форма представления** | Один из четырёх способов сериализации элемента: TS-объект (модель) / Enterprise XML / PartialYAML / TypedYAML | Variant, flavor |

### Relationships наследования

- **Наследник** принадлежит ровно одному **семейству элементов**.
- **Правило** наследника подмешивает `<семейство>CommonProperties` и добавляет специфичные свойства, включая `childItems` (разного типа у разных наследников).
- **Фикстура** наследника подмешивает `full<Семейство>CommonFixture` во всех четырёх **формах представления**.
- Свойство с `runtimeOnly: true` отсутствует во всех формах — в том числе в TS-**фикстуре** (хотя в рантайм-объектах может присутствовать через другие механизмы).
- **XML-фикстура** перестаёт быть абсолютным источником истины, когда вводятся **канонические значения**: допускается правка `full.xml` под канонику семейства.

## Семейство `formDecoration` (из диалога о базовых правилах декораций)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Декорация формы** | Визуальный **элемент формы**, не связанный с данными (надпись, картинка); сопоставлен с `FormDecoration` в 1С | Декоратор, украшение |
| **Семейство `formDecoration`** | Папка `formDecoration/` с `rules.ts` и `__fixtures__/data.ts`; экспортирует **общие свойства** и **базовую фикстуру** для **наследников** `LabelDecoration` и `PictureDecoration` | FormDecoration family |
| **`LabelDecoration`** | **Наследник** семейства `formDecoration` — форматированная надпись; `title` имеет тип `FormattedI8nText` | Лейбл, подпись |
| **`PictureDecoration`** | **Наследник** семейства `formDecoration` — картинка; `title` имеет тип `I8nText` (без форматирования) | Изображение |
| **Типовое расхождение свойства** | Ситуация, когда свойство формально есть у всех **наследников**, но имеет разный `type` в **правилах свойства** (например, `title` у декораций: `FormattedI8nText` vs `I8nText`). Паттерн: такое свойство **не выносим** в **общие свойства** — каждый наследник объявляет его у себя | Тип-полиморфное поле |
| **`Вид` как `runtimeOnly`-наследника** | Свойство `type`/`Вид` в **правилах** `UsualGroup` / `LabelDecoration` / `PictureDecoration` объявляется индивидуально с `runtimeOnly: true` — не в **общих свойствах**, несмотря на то что имя и смысл одинаковы | type в spread |

### Relationships семейства `formDecoration`

- **`LabelDecoration`** и **`PictureDecoration`** — два **наследника** семейства `formDecoration`; оба подмешивают `formDecorationCommonProperties` и `fullFormDecorationCommonFixture`.
- Свойство **`title`** — пример **типового расхождения свойства**: не входит в **общие свойства**.
- Свойство **`onMainServerUnavalableBehavior`** — входит в **общие свойства** с одинаковым **каноническим значением** `"MakeDisable"` в обеих XML-фикстурах декораций.
- Свойства `name`, `parent`, `type` — по паттерну `formGroup` не входят в **общие свойства**; `type` в каждом наследнике объявляется как **`Вид` как `runtimeOnly`-наследника**.

## Разделение правил по дискриминатору (из диалога о `button`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Разделение по дискриминатору** | Паттерн, при котором одна внешняя сущность (один XML-тег, одна YAML-секция) превращается в **несколько `itemType`** на стороне NKDK — выбор `itemType` делается по значению **дискриминирующего свойства** на входе | Подтипы, полиморфизм |
| **Дискриминирующее свойство** | Свойство элемента, по значению которого **fromXML** / **fromYAML** выбирает конкретный `itemType` (у кнопки — `type` / `Вид`, значения `FormButtonType`) | type-tag |
| **`FormButtonType`** | Системное перечисление 1С с 4 значениями `UsualButton`, `Hyperlink`, `CommandBarButton`, `CommandBarHyperlink`; служит **дискриминирующим свойством** кнопки | — |
| **`Button` (itemType)** | `itemType` формы для кнопок вне командной панели; допустимые значения `type` — `UsualButton` \| `Hyperlink` | Обычная кнопка (неоднозначно — ср. `UsualButton`) |
| **`CommandBarButton` (itemType)** | `itemType` формы для кнопок внутри командной панели; допустимые значения `type` — `CommandBarButton` \| `CommandBarHyperlink` | — |
| **`UsualButton`** | Значение **`FormButtonType`** для обычной кнопки с рамкой/заливкой; в **NKDK** — `<"Заголовок" Имя>` | Кнопка (слишком общее) |
| **`Hyperlink`** | Значение **`FormButtonType`** для гиперссылки — текста-команды без рамки; в **NKDK** — `<~"Заголовок" Имя>` | Ссылка |
| **Контекст размещения** | Позиция элемента в дереве формы, от которой зависит допустимый `itemType` наследника: `GroupChildItems` → только `Button`, `CommandBarChildItems` → только `CommandBarButton` | Родитель, parent |
| **`resolveItemTypeFromXMLTag`** | Функция в `childItems/fromXML.ts`, выбирающая `itemType` по **XML-тегу** + **контексту размещения** + значению **дискриминирующего свойства** в XML | XML-роутер |
| **`xmlFolder`** | Поле записи в `__tests__/fixtures.ts`, явно задающее папку **XML-фикстур** для группы, когда они физически лежат не в папке, совпадающей с `group` | — |
| **Маркер `~` в NKDK** | Префикс перед `Titled Name` внутри правила `Button` и `CommandBarButton` в грамматике Langium, означающий, что `type` = `Hyperlink` / `CommandBarHyperlink` | Underline marker |
| **AST-поле `hyperlink`** | Булев атрибут в сгенерированном AST (`packages/language/src/generated/ast.ts`), отражающий наличие **маркера `~`** в исходнике NKDK | isLink, hyperlinked |
| **`exportCommandBarButtonToNKDK`** | Функция toNKDK для `itemType: "CommandBarButton"`; не оборачивает в `<>` (в отличие от `exportButtonToNKDK`), так как грамматика `CommandBarButton` — `Titled Name` без внешних скобок | — |

### Relationships разделения по дискриминатору

- Одна **XML-фикстура** `<Button>` → один из двух `itemType` (`Button` \| `CommandBarButton`) по значению `<Type>`.
- Одна **YAML-секция** с `Тип: Кнопка` → тот же выбор по полю `Вид`.
- Оба `itemType` сериализуются **обратно** в один и тот же XML-тег `<Button>` и один и тот же YAML `Тип: Кнопка` — различие хранится только в свойстве `type` / `Вид`.
- **Общие свойства** кнопки вынесены в `commonButtonProperties` (паттерн **семейства элементов**), но папка остаётся одна (`button/`), а не две.
- В **NKDK** разделение устроено иначе: Langium уже разводит `Button` и `CommandBarButton` на уровне AST по позиции в грамматике; `Hyperlink` / `CommandBarHyperlink` различаются внутри каждого правила через **AST-поле `hyperlink`**.

## Операции верхнего уровня (из диалога о командах CLI)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Импорт конфигурации** | Операция полного преобразования XML-выгрузки в YAML-проект; вызывает `syncConfigurationFromXML` из ядра | Загрузка, import configuration |
| **Синхронизация конфигурации** | Операция преобразования YAML-проекта в XML-выгрузку; вызывает `syncConfigurationToXML` из ядра. Предпочтительнее термина «экспорт», так как подчёркивает направленный мердж, а не перезапись | Экспорт, export |
| **Команда расширения** | Зарегистрированная в `packages/extension/package.json` команда VS Code c префиксом `nkdk.*` (`nkdk.importConfigurationFromXml`, `nkdk.syncConfigurationToXml`) | VSCode action |
| **Команда CLI** | Подкоманда бинарника `nkdk` в `packages/cli` (`nkdk import`, `nkdk sync`, `nkdk validate`) | Скрипт, утилита |
| **Бинарник `nkdk`** | Исполняемый файл CLI, объявленный в `packages/cli/package.json` как `bin.nkdk` | Инструмент, tool |
| **Контекст конвертации** (`ConfigurationContext`) | Параметры вызова `syncConfiguration*` из ядра: `language`, `version`, конфигурации `exportToYAML` / `exportToXML`. В расширении берётся из настроек workspace, в CLI временно захардкожен | Настройки импорта |
| **Операция валидации** | Команда `nkdk validate`, обходящая граф и сообщающая о **битых ссылках**; ориентирована на CI/CD, не имеет аналога в расширении | Линтинг, проверка |

### Relationships операций верхнего уровня

- **Команда расширения** и **команда CLI** одной семантики (импорт / синхронизация) вызывают одну и ту же функцию ядра с одинаковым **контекстом конвертации**.
- **Импорт конфигурации** внутри себя многократно применяет **направление** `fromXML` к отдельным `itemType`; **синхронизация конфигурации** — **направление** `toXML`. **Операция** относится к уровню всей конфигурации, **направление** — к одному объекту.
- **Операция валидации** не преобразует файлы, а читает **граф** и ищет **битые ссылки**.

## Relationships

- **Прикладной объект** связан с **реквизитами** и **табличными частями** через **composition-рёбра**
- **Реквизит** ссылается на другие **прикладные объекты** через **reference-рёбра** (тип реквизита)
- **Табличная часть** содержит собственные **реквизиты** — их NodeId включает имя табличной части
- **Стандартные реквизиты** всегда создаются при импорте **прикладного объекта**, набор определяется типом
- **Элемент формы** ссылается на **реквизиты** через **dataPath** (reference-ребро)
- **DataPath** резолвится **walker'ом**, который на каждом шаге может ветвиться из-за **составных типов**
- **Узел-заглушка** возникает когда целевой объект ещё не импортирован или удалён — наличие заглушки без `item` = **битая ссылка**
- Один **прикладной объект** порождается одним YAML-файлом; одна форма — двумя файлами (`.yaml` + `.nkdk`)

## Example dialogue

> **Dev:** "Добавляю **табличную часть** `Состав` в справочник. В YAML нет `Синоним`. Откуда он берётся в XML?"

> **Domain expert:** "`synonym` в **правиле** объявлен с **`defaultValue` как функцией** — `addDefaultLanguageNameToSynonym`. При импорте из YAML `getValueOrDefault` видит `value === undefined` и вызывает функцию с `name = \"Состав\"`. В XML-экспорте `synonym` уже заполнен."

> **Dev:** "А если `Состав` пустой — нет реквизитов. `<ChildObjects>` нужен в XML?"

> **Domain expert:** "Да, **XML-фикстура** — источник истины: пустой контейнер `<ChildObjects/>` обязателен. Это достигается через `defaultValueXMLRaw: {}` на правиле свойства `attributes` с `xmlParents: [\"ChildObjects\"]`. `setXMLValue` при пустом массиве создаёт контейнер-родитель, дочерний ключ `Attribute` не ставит."

> **Dev:** "Пользователь удалил файл `Справочник.Категории.yaml`. Что происходит с графом?"

> **Domain expert:** "Через **обратный индекс** находим все **узлы**, порождённые этим файлом. Удаляем те, на которые нет входящих **reference-рёбер**. Узел `Справочник.Категории` превращается в **узел-заглушку** — у него убирается `item`, но сам узел остаётся, потому что на него ссылаются реквизиты других объектов. Теперь это **битая ссылка**."

> **Dev:** "Как резолвится `Объект.Договор.Владелец.ГрафикПлатежей[1].Сумма`?"

> **Domain expert:** "**Walker** идёт по шагам. `Договор` — **реквизит** объекта, тип — **составной**: `Справочник.ДоговорПоставки | Справочник.ДоговорУслуг`. Walker ветвится по обоим типам. `Владелец` — **стандартный реквизит**. `ГрафикПлатежей` — **табличная часть**. `[1]` — **индексация**. `Сумма` — **реквизит** табличной части."

## Фикстуры прикладного объекта

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Полная фикстура (`full.xml`)** | XML-фикстура прикладного объекта с максимально заполненными свойствами — все ветви парсинга покрыты хотя бы одним значением | Max fixture |
| **Минимальная фикстура (`minimal.xml`)** | XML-фикстура с именем-маркером `ПоУмолчанию` / `По умолчанию`, где все свойства явно выставлены в платформенный дефолт; при парсинге возвращает **минимальный TS-объект** | Defaults fixture (неоднозначно, см. `defaults.xml`) |
| **`defaults.xml`** | **(Устаревший паттерн)** Отдельная XML-фикстура, хранившая набор дефолтных значений; заменена `minimal.xml` | — |
| **Минимальный TS-объект** | TypeScript-объект объекта метаданных, содержащий только `name` + `itemType` + поля, чей тип не позволяет стрипинг через `===` (например, `I8nText`-синоним и `MetadataFields`-поля) | Empty object, stub |
| **`data.ts` (фикстура)** | Файл `__fixtures__/data.ts` с ожидаемыми TypeScript-объектами (`full`, `minimal`) и YAML-объектами (`fullYAML`, `minimalYAML`); **ведомый** относительно XML-фикстур — обновляется под фактический вывод парсера | Test data |
| **Стрипинг по `defaultValueXML`** | Механизм в `importPropertiesFromXML` (стр. 53): `cleanValue = value === rule.defaultValueXML ? undefined : value`; работает только для **примитивов** (string, number, boolean) из-за строгого `===`; объекты (`I8nText`, `MetadataFields`, массивы) не стрипнутся, даже если выставить `defaultValueXML` | Deep-equal default stripping |

### Relationships фикстур

- **`full.xml`** и **`minimal.xml`** являются источниками истины; **`data.ts`** обновляется под их фактический вывод.
- **`minimal.xml`** → парсер → **минимальный TS-объект** ≠ `{name, itemType}`, если свойство-примитив отсутствует в правиле дефолта, или поле типа `I8nText`/`MetadataFields` непусто в XML.
- **Стрипинг** по `defaultValueXML` применяется автоматически ко всем примитивам; для объектов — требуется либо новый механизм (deep-equal, не реализован), либо принятие того, что они войдут в **минимальный TS-объект**.

## Flagged ambiguities

- **"Таблица"** используется в двух контекстах: **табличная часть** прикладного объекта и **таблица формы** (элемент формы типа Table). Это разные сущности — табличная часть хранит данные, таблица формы отображает их. В dataPath и при индексации `[N]` допустимы обе.
- **"Зависимость"** (dependency) — ранее использовалось для обозначения любых связей. Теперь разделено на **composition** (структурное владение) и **reference** (ссылка на внешний объект).
- **"Контекст"** — `ConfigurationContext` используется и как контейнер настроек импорта, и как носитель графа. Граф передаётся в контекст снаружи, но не является его частью по смыслу.
- **"Произвольный запрос"** использовалось и как имя свойства (`ПроизвольныйЗапрос` / `customQuery` / `ManualQuery`), и как неформальное описание «запроса, написанного разработчиком». Канонично — **булев признак** на **динамическом списке**; сам текст называется **текстом запроса** и хранится во **внешнем файле**, а не в YAML.
- **"Внешний файл"** — не любой файл рядом с YAML, а файл под управлением опции `externalFile` **правила свойства** с детерминированным путём `<formDir>/<dir>/<parent.name>.<extension>`.
- **Расширение файла запроса** — в ранних версиях инструмент записывал **текст запроса** в файл с расширением `.bsl`, что противоречит документации формата (`.bsl` — встроенный язык 1С, а не язык запросов). Каноничное расширение — **`.query`**; `.bsl` при чтении не поддерживается.
- **"Наследник" vs "потомок"** — в обсуждениях использовались как синонимы; закрепляем **наследник** (child), «потомок» избегать.
- **"Spread"** — обозначает **только подмешивание** `...commonProperties` / `...commonFixture`. Переопределение общего поля после spread — отдельное понятие **override после spread**, и оно запрещено в текущей модели наследования.
- **"runtimeOnly"** — трактуется буквально: свойство не попадает ни в одну **форму представления**, включая TS-фикстуру (несмотря на интуитивное ожидание «только в TS-объекте»).
- **`runtimeOnly` vs `toYAML/fromYAML: false`** — не синонимы. `runtimeOnly` исключает свойство из **всех** форм представления; `toYAML: false, fromYAML: false` отключает только направление YAML, оставляя свойство в типах и в Enterprise XML. Первое — глобальное свойство правила, второе — точечный флаг наследника для **«не общего» поля**.
- **`UsualButton` vs `Button`** — на уровне NKDK `Button` это **`itemType`** (семейство «кнопки вне командной панели»), а `UsualButton` — одно из значений **`FormButtonType`** внутри этого `itemType`. В русскоязычном обсуждении говорить «обычная кнопка» → имеется в виду **`UsualButton`**, а не `Button` в целом.
- **`CommandBarButton` как `itemType` vs как значение `FormButtonType`** — одноимённые сущности на разных уровнях. `itemType: "CommandBarButton"` применим и к `type: "CommandBarHyperlink"`; строго различать «`itemType` командной кнопки» и «значение перечисления `CommandBarButton`».
- **`minimal` vs `defaults`** — исторически существовал отдельный `defaults.xml`; сейчас роль «все по умолчанию» играет **`minimal.xml`** (маркер-имя `ПоУмолчанию`). Не путать: **`minimal.xml`** — XML-фикстура, **`minimal`** (объект в `data.ts`) — TypeScript-представление того, что парсер вернёт; оно не обязано быть минимальным (`{name, itemType}`), если в XML есть I8nText/MetadataFields-поля с непустым значением.
- **`defaultValueXML` для объектных типов** — выставить `defaultValueXML: {...}` на I8nText или MetadataFields-поле **не поможет** (стрипинг использует `===`, не deepEqual); такие поля всегда попадают в **минимальный TS-объект** если присутствуют в XML. Попытка обойти это через `defaultValueXML: []` для массивов аналогично не сработает.
- **«Импорт» на двух уровнях** — термин **импорт конфигурации** относится к операции верхнего уровня (вся XML-выгрузка → YAML-проект). Не путать с **направлением** `fromXML` одного `itemType`. Из контекста обычно ясно, но в документации предпочитать полные формы «импорт конфигурации» и «направление `fromXML`».
- **`MetadataCommand` vs `MetadataCommands`** (singular vs plural `propertyType`) — `MetadataCommand` это `itemType` (одиночный объект метаданных, регистрируется в `MetadataItemTypeRegistry`), а `MetadataCommands` это `propertyType` коллекции (регистрируется в `PropertyTypeRegistry`). Внешние консьюмеры импортируют либо одиночный (`MetadataCommandYAML`, `MetadataCommandXML`), либо коллекционный (`MetadataCommandsYAML`, `MetadataCommandsXML`) тип в зависимости от контекста. Тот же паттерн: `MetadataAttribute` / `MetadataAttributes`, `DCSParameter` / `DCSParameters`. В обсуждениях явно различать «правило элемента» (`itemRule: MetadataCommandRules`) и «правило коллекции» (`propertyType: "MetadataCommands"`).
- **«Синхронизация» vs «экспорт»** — в кодовой базе используется **синхронизация** (`syncConfigurationToXML`, команда `nkdk sync`, команда расширения `nkdk.syncConfigurationToXml`). Слово «экспорт» зарезервировано за **направлением** `toXML` отдельного объекта и за конфигурацией `exportToXML` внутри **контекста конвертации**. На уровне операций CLI/расширения — только **синхронизация**.
- **`type` / `Вид` / `itemType`** — три разные сущности. `itemType` — дискриминатор рантайм-модели (`"LabelDecoration"`); `type` внутри **правила свойства** — тип значения (`"string"`, `"SystemEnumeration"`); свойство элемента `type`/**`Вид`** — перечисление вида декорации/группы (`FormDecorationType`/`FormGroupType`), в **правилах** наследников объявляется индивидуально как `runtimeOnly`. В обсуждениях использовать полные формы: **itemType**, **тип свойства**, **`Вид` элемента**.
- **«Составной тип»** имеет два значения на разных уровнях: (1) **составной тип реквизита** — union допустимых типов значений (`Справочник.А \| Справочник.Б`); (2) структурный тип внутри **`MetadataValue`** — `fixedArray` / `formChoiceListDesTimeValue`. Второе значение переименовано в **агрегатный тип значения**, чтобы избежать коллизии.
- **`type` внутри `MetadataValue`** vs **`type` внутри правила свойства** vs **`itemType`** — три разных `type`. Внутри `MetadataTypedValue` поле `type` — это **тип значения** (`"string"` / `"decimal"` / `"fixedArray"` и т.п.), **не** тип свойства из правила и **не** `itemType` объекта метаданных.
- **`valueType`** против **тип свойства (`rule.type`)** — `rule.type: "MetadataValue"` задаёт семейство (что это вообще **`MetadataValue`**), а `rule.valueType: ["string"]` — ограничение на допустимые **типы значения** внутри этого семейства. Два разных поля правила, нельзя взаимозаменять.
- **«Резолвер»** без уточнения — неоднозначно. В кодовой базе уже есть **walker** по графу (для dataPath) и **именованные фильтры** (для referenceScope). Новый **резолвер зависимого типа** — третья сущность и пока не реализован. При упоминании всегда добавлять уточнение (_walker_ / _фильтр_ / _резолвер зависимого типа_).
- **«required» на двух уровнях** — `required: true` в `BasePropertyRule` означает «свойство обязательно в данных модели» (валидация на уровне модели), `requiredXMLParents` в `MetadataItemRule` означает «XML-тег-контейнер обязателен в выходе». Это разные сущности на разных уровнях (свойство vs объект) и на разных этапах (валидация vs сериализация). При обсуждении всегда уточнять: **обязательное свойство** vs **обязательный XML-родитель**.
- **«Пустой контейнер `<ChildObjects/>`»** — теперь достигается двумя механизмами с разной семантикой: **`defaultValueXMLRaw: {}`** на правиле свойства-коллекции (контейнер появляется, когда коллекция есть, но пуста) vs **`requiredXMLParents`** на правиле объекта (контейнер появляется всегда, даже если ни одно связанное свойство не присутствует). Для `minimal.xml` каталога работает только второй механизм — свойств-детей нет ни одного. Для `<ChildObjects/>` табличной части в `full.xml` — первый.

## Сериализация пустых/nil XML-тегов (из диалога о #56 `StandardAttributeDescription`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Группа стандартных реквизитов** | Коллекция всех `StandardAttributeDescription` одного **прикладного объекта** — единица правила **All-or-nothing** в XML | StandardAttributes (тег), секция стандартных реквизитов |
| **Изменённый стандартный реквизит** | `StandardAttributeDescription`, у которого хотя бы одно свойство отличается от своего дефолта — предикат `!isEmptyMetadataItem({ignoreKeys: ["name"]})` | Non-default, кастомный |
| **Изменённая группа** | **Группа стандартных реквизитов**, в которой есть хотя бы один **изменённый стандартный реквизит** | — |
| **All-or-nothing (XML)** | Правило XML-экспорта **группы стандартных реквизитов**: неизменённая группа не печатается; изменённая — печатается **полностью**, включая неизменённые реквизиты с их дефолтами | Группа целиком |
| **Only-changed (YAML)** | Правило YAML-экспорта **группы стандартных реквизитов**: печатаются только **изменённые стандартные реквизиты** | — |
| **Канонический список (стандартных реквизитов)** | Полный перечень имён стандартных реквизитов для данного **прикладного объекта**, заданный `standartAttributeNames` в его **правиле** (для Catalog — `MetadataCatalogStandardAttributeNames`) | Полный список |
| **Раздутие группы** (Group expansion) | Процесс дополнения модели `Stub item`-ами для всех имён **канонического списка** при срабатывании **All-or-nothing** на экспорте | Заполнение по канону |
| **Stub item** (стандартного реквизита) | Минимальный `StandardAttributeDescription` `{itemType, name}` без пользовательских значений, используемый при **раздутии группы** | Заглушка-реквизит |
| **`defaultValueXML`** | Поле **правила свойства**: модельное значение, подставляемое на экспорт если value ≡ defaultValue; прогоняется через `typeExportFn` и `wrapWithNamespace` | — |
| **`defaultValueXMLRaw`** | Поле **правила свойства**: сырая XML-форма (`""` → пустой тег, `{"_xsi:nil": true}` → `xsi:nil="true"`, `{}` → пустой контейнер-родитель для коллекции), подставляемая **без** `typeExportFn` и `wrapWithNamespace`. Два триггера: (1) `exportedValue === rule.defaultValue`; (2) `value = []` + `xmlParents` → `setXMLValue` создаёт контейнер с `defaultValueXMLRaw`, не ставя дочерний ключ. Взаимоисключим с `defaultValueXML` | defaultValueXMLAfter |
| **Пустой тег** (empty tag) | Сериализационная форма «пусто» для строковых / `I8nText` / `TypeLink` / коллекционных полей: `<xr:Format/>` | Null-тег |
| **`xsi:nil`** | Сериализационная форма «значение отсутствует» для числовых / `MetadataValue`-полей: `<xr:MaxValue xsi:nil="true"/>` | Nil-тег, null |
| **`isEmptyMetadataItem`** | Хелпер в `metadata/orchestration/formElement/helper.ts`: возвращает `true`, если все свойства item равны своим дефолтам (учитывает `defaultValue`, `defaultValueXML`, `defaultValueYAML`). Основа предиката **изменённости** | — |
| **Issue #56** | Round-trip-дефект: из `StandardAttribute` терялись пустые и `xsi:nil`-теги из-за `suppressEmptyNode: true` в XMLBuilder и `ignoreAttributes: ["xsi:nil"]` в XMLParser | — |

### Relationships сериализации пустых/nil тегов

- **Группа стандартных реквизитов** ⊆ **прикладной объект**; её состав определяется **каноническим списком** родителя.
- **All-or-nothing** и **Only-changed** — независимые правила: первое живёт только в XML-экспортёре, второе — только в YAML-экспортёре.
- **Раздутие группы** срабатывает iff группа — **изменённая**; при этом каждое отсутствующее свойство stub-а заполняется через **`defaultValueXML`** или **`defaultValueXMLRaw`** своего **правила свойства**.
- **Пустой тег** производится из `defaultValueXMLRaw: ""` / `{}`; **`xsi:nil`** — из `defaultValueXMLRaw: {"_xsi:nil": true}`. Оба варианта решают issue #56 без хака `defaultValueXML: []` + `emitEmptyTagIfDefaultArray`.
- **Место хука** — кастомный `toXML` в `registerCollectionRule.ts` для `StandardAttributeDescriptions` (specific-handler, не общий механизм `registerMetadataItemCollectionRule`).

## Регистрация коллекций объектов метаданных (из диалога о рефакторинге `metadataAttribute`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **`registerMetadataItemCollectionRule`** | Функция-фабрика в `metadata/orchestration/metadataCollection/ruleFactory.ts`, регистрирующая все четыре **направления** + `exportToJSONSchema` для коллекции через один вызов; принимает кастомные `fromXML`/`toXML`/`fromYAML`/`toYAML` как необязательные параметры | Ручная регистрация всех направлений |
| **`register.ts`** | Единый файл точки входа для объекта метаданных, вызывающий `registerMetadataItemCollectionRule` и регистрирующий кастомный `fromYAML`; заменяет отдельные `fromXML.ts`, `toXML.ts`, `fromYAML.ts`, `toYAML.ts`, `toJSONSchema.ts` | index.ts, init.ts |
| **`xmlParents`** | Поле **правила свойства** — массив XML-ключей, описывающий путь к узлу в вложенной XML-структуре (`["Properties"]` → свойство находится внутри `<Properties>`); используется как в импорте (`getXMLValue`), так и в экспорте (`setXMLValue`) | xmlPath, xmlNesting |
| **`forReferenceOnly`** | Флаг **правила свойства**: при `forReference: false` свойство пропускается при импорте из XML (не попадает в модель); при `forReference: true` — читается для построения **референсных метаданных** | importOnlyForRef |
| **Тип `"uuid"`** | Новый тип в `PropertyTypeRegistry`, реализованный в `commonObjects/uuid/`; `exportToXML` возвращает `referenceValue ?? getUUID(context)` — UUID из референса или сгенерированный | GeneratedUUID, string+generator |
| **`uuidPropertyRule`** | Переиспользуемый объект `PropertyRule` в `commonObjects/uuid/rule.ts`: `{ type: "uuid", xml: "_uuid", forReferenceOnly: true, toYAML: false, fromYAML: false }` — подключается в `rules.ts` объектов с UUID-обёрткой | uuid helper |
| **`getUUID(context)`** | Хелпер в `metadata/helpers/uuid.ts`: в `testMode` возвращает константный `UUID_TEST`, иначе `v4()` | v4() напрямую |
| **Кастомный `fromYAML` с трекингом графа** | Параметр `fromYAML` в `registerMetadataItemCollectionRule`, сохраняющий специфичную логику создания узлов и рёбер в **графе** при импорте коллекции из YAML; подключается когда стандартный `importMetadataItemCollectionFromYAMLAsRecord` недостаточен | — |
| **`removeDefaults`** | **(Устаревший паттерн)** Явный вызов функции очистки модели от дефолтных значений после импорта; заменён стандартной механикой: `cleanValue = value === rule.defaultValueXML ? undefined : value` в `importPropertiesFromXML` | — |
| **`useAsShortValueYAML`** | Флаг **правила свойства**: если все остальные поля объекта пустые — это поле выгружается как скалярное значение вместо раскрытого объекта (`{ Имя: "Строка" }` вместо `{ Имя: { Тип: "Строка" } }`); обрабатывается в `handleShortFormatYAML` | shortValue, short format flag |
| **Обёртка `<Properties>`** | XML-элемент `<Properties>` внутри `<Attribute uuid="...">`, хранящий все свойства реквизита; адресуется через `xmlParents: ["Properties"]` во всех правилах свойства | — |
| **`defaultValue` как функция** | `defaultValue: ({ context, name, operation }) => ...` в **правиле свойства**; `getValueOrDefault` вызывает её когда value === undefined — позволяет вычислять дефолт из контекста; применяется для `addDefaultLanguageNameToSynonym` в свойстве `synonym` | Computed default, factory default |
| **`addDefaultLanguageNameToSynonym`** | Хелпер в `metadata/helpers/synonymHelpers.ts`: создаёт I8nText-синоним из имени объекта на языке по умолчанию; подключается в `rules.ts` через **`defaultValue` как функцию** для `synonym` — вместо кастомного `fromYAML` | Auto-synonym |
| **Пустой контейнер `<ChildObjects/>`** | XML-элемент, генерируемый даже при пустой коллекции реквизитов табличной части; достигается сочетанием `defaultValueXMLRaw: {}` + `xmlParents: ["ChildObjects"]`; `setXMLValue` при пустом массиве создаёт контейнер-родитель без дочернего ключа | Empty wrapper |

### Relationships регистрации коллекций

- **`register.ts`** ⊃ один вызов `registerMetadataItemCollectionRule` + опциональный кастомный `fromYAML` для трекинга **графа**.
- **`xmlParents: ["Properties"]`** на всех полях `rules.ts` заменяет кастомный `fromXML`/`toXML` для извлечения/упаковки **обёртки `<Properties>`**.
- **`uuidPropertyRule`** с `forReferenceOnly: true` позволяет UUID попадать в **референсные метаданные** при полном XML-импорте, и использоваться при экспорте через тип `"uuid"` (`referenceValue ?? getUUID(context)`).
- **`defaultValueXMLRaw`** + **`xmlParents`** в `rules.ts` полностью покрывают empty/nil-поля — отдельный `defaults.ts` становится избыточным и удаляется.
- Короткий YAML-формат реквизита (`{ Имя: "Строка" }`) обрабатывается стандартным `handleShortFormatYAML` через флаг `useAsShortValueYAML: true` на правиле свойства — кастомный `fromYAML` для этого не нужен.
- **Пустой контейнер `<ChildObjects/>`** требует `defaultValueXMLRaw: {}` на свойстве коллекции + изменения `setXMLValue`: при `value = []` + `xmlParents` + `defaultValueXMLRaw` → создаётся контейнер-родитель (последний из `xmlParents`) со значением `defaultValueXMLRaw`, дочерний ключ (`xml`) не ставится. Семантика: «контейнер присутствует, но пуст».
- **`defaultValue` как функция** заменяет кастомный `fromYAML` для синонима-по-умолчанию: `synonym.defaultValue = ({ context, name }) => addDefaultLanguageNameToSynonym(context, undefined, name ?? "")` — стандартная машинерия вызывает её при `value === undefined` без custom-кода в `fromYAML`.

## Миграция legacy-обёрток в rules-only (из диалога о `metadataCommand`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Wrapper-модуль** (legacy) | Файл-обёртка одного **направления** (`fromXML.ts`, `toXML.ts`, `fromYAML.ts`, `toYAML.ts`) у объекта метаданных, делегирующий в **оркестрацию** через `importMetadataItemFromXML`/`exportMetadataItemToYAML` и т.п. Промежуточная стадия между **legacy-путём** и **rules-only путём**: `rules.ts` уже есть, но направления зарегистрированы через четыре файла, а не через один `register.ts` | Legacy-обёртка |
| **Миграция wrapper → rules-only** | Удаление **wrapper-модулей** объекта с заменой их на один `register.ts` через `registerMetadataItemCollectionRule`, перенос XML-дефолтов из `defaults.ts` в **правила свойств**, перенос фикстур из глобального `tests/fixtures/<name>/` в локальное `__fixtures__/`, переписывание тестов на `testImportPropertyFromXML`/`testExportPropertyToXML` | — |
| **`xmlElement`** (параметр) | Параметр `registerMetadataItemCollectionRule`: имя XML-тега каждого элемента коллекции (`"Command"`, `"Attribute"`, `"Parameter"`). Прокидывается в стандартный `importMetadataItemCollectionFromXML(itemRule, xmlElement)` | XML-имя элемента |
| **`keyField`** (параметр) | Параметр `registerMetadataItemCollectionRule`: имя поля **правила**, чьё значение становится ключом YAML-map при экспорте `Record<string, ItemYAML>` (для `MetadataCommands`/`MetadataAttributes` — `"name"`) | yamlKey, mapKey |
| **`yamlAsArray`** (параметр) | Альтернатива `keyField`: коллекция сериализуется в YAML как массив (а не `Record<string, ItemYAML>`); для `MetadataCommands` не используется — у команд имя является ключом | — |
| **Глобальный каталог фикстур** (`tests/fixtures/<name>/`) | **(Устаревший паттерн)** Глобальная папка для фикстур объекта метаданных в `packages/core/tests/fixtures/`. При миграции переносится в локальный **`__fixtures__/`** рядом с `rules.ts` объекта | Глобальные фикстуры |
| **Локальные фикстуры** (`__fixtures__/`) | Папка `__fixtures__/` рядом с `rules.ts` объекта, содержащая XML-фикстуры и `data.ts`. Каноничное расположение в **rules-only пути** | Co-located fixtures |
| **Барьер XML-цикл → YAML-цикл** | Жёсткое правило из скилла `new-metadata-item`: пока **XML-цикл** не зелёный (round-trip + раздельные fromXML/toXML), запрещено касаться YAML-кода (YAML-полей `data.ts`, YAML-частей `rules.ts`, файлов `fromYAML.test.ts`/`toYAML.test.ts`). При миграции wrapper → rules-only означает: на первой итерации удаляются YAML-тесты вместе с YAML-данными, YAML-цикл проходит отдельной итерацией | — |
| **Эталонный объект** | Существующий объект метаданных, реализованный по целевому паттерну, на который опирается миграция. Для коллекций именованных элементов с `<Properties>`-обёрткой эталон — `commonObjects/metadataAttribute` | Reference impl, образец |

### Relationships миграции wrapper → rules-only

- **Wrapper-модуль** уровня `fromXML`/`toXML`/`fromYAML`/`toYAML` после миграции исчезает; его роль выполняет один **`register.ts`** через `registerMetadataItemCollectionRule({ propertyType, itemRule, xmlElement, keyField })`.
- **`defaults.ts`** объекта при миграции исчезает: каждое значение переносится в **правила свойства** как `defaultValueXML` (или `defaultValueXMLRaw: ""` для пустых самозакрывающихся тегов).
- **Глобальный каталог фикстур** объекта целиком удаляется после переноса всех XML-файлов и `data.ts` в **локальные фикстуры**.
- Внешние потребители **wrapper-модулей** (например, `metadataDocument`, использующий `importMetadataCommandsFromXML`) до собственной миграции либо комментируются, либо переключаются на `importPropertyFromXML({ context, rule: { type: "<Plural>" }, value })`.
- На первой итерации миграции `__fixtures__/data.ts` содержит **только TS-фикстуры** (`fullMetadataCommandsFromXML`, `minimalMetadataCommandsFromXML`); поля `*YAML` появляются на второй итерации после прохождения **барьера XML-цикл → YAML-цикл**.

## Значения произвольных типов (из диалога о рефакторинге `metadataValue`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **`MetadataValue`** | Значение свойства, несущее в себе свой тип — в XML выгружается как элемент с `xsi:type="xs:string"` и т.п.; применяется для `FillValue`, `app:value` параметров выбора, `TypesFilterValue` и подобных | Типизированное значение |
| **Тегированная форма** | Представление **`MetadataValue`** в доменной модели — объект `{ type, value }`, где `type` — один из **типов значения**. Каноничная форма хранения согласно «варианту T» | Wrapped value, typed wrapper |
| **Примитивный тип значения** | Одно из: `string`, `decimal`, `dateTime`, `boolean`, `ref`, `objectRef` — несущие одиночное скалярное `value` | Скалярный тип |
| **Агрегатный тип значения** | Один из: `fixedArray` (массив других **`MetadataValue`**), `formChoiceListDesTimeValue` (пара «представление + значение») — структурные типы внутри **`MetadataValue`** | Составной тип (конфликт со **составным типом** реквизита), композитный тип |
| **`valueType`** | Поле **правила свойства** типа `"MetadataValue"`: массив допустимых **типов значения**. `undefined` — любой тип, `["string"]` — фиксированный, `["string", "decimal"]` — **набор типов** | valueType как строка (устаревшая форма до `[α]`-миграции) |
| **Набор типов** | Форма **`valueType`** с длиной массива > 1 — заранее известен ограниченный перечень допустимых **типов значения**; применяется там, где одно свойство может нести несколько семантик (например, `app:value` параметров выбора) | Multi-type, union valueType |
| **Фиксированный тип значения** | Форма **`valueType`** с единственным элементом, например `["string"]` — в XML `xsi:type` избыточен с точки зрения модели, но оставляется для совместимости с 1С | Mono-type |
| **Самоописываемый YAML** | Конвенция кодовой базы: в YAML **тип значения** однозначно выводится из синтаксиса — `"..."` → string, число → decimal, `Истина`/`Ложь` → boolean, путь с точками → ref. Исключает необходимость эвристик при парсинге | YAML inference, YAML heuristics |
| **Строгая валидация `valueType`** | Контрактное поведение: несовпадение фактического **типа значения** с объявленным в **`valueType`** → `throw`. Применяется во всех четырёх **направлениях** — `fromXML`/`toXML`/`fromYAML`/`toYAML` | Лояльная валидация |
| **Фасад `AssociatedTable`** | Самостоятельный `itemType` (`AssociatedTable`) в реестре, делегирующий конверсию в **`MetadataValue`** с `valueType: ["string"]`; после миграции на **тегированную форму** домен хранит `MetadataStringValue`, не голую строку | Alias, thin wrapper |
| **Резолвер зависимого типа** | (Отложено) Именованная функция в `rules.ts`, вычисляющая `valueType` из **графа** — по значению соседнего свойства или по имени стандартного реквизита. На момент обсуждения не реализована; конвертеры **`MetadataValue`** её не вызывают | Type dependency, type computer |
| **`withType`** | **(Устаревший флаг)** Поле **правила свойства**: переключало домен между **тегированной формой** и примитивом, а YAML — между кавычками и голым видом. Удаляется при переходе на «вариант T» | — |

### Relationships значений произвольных типов

- **`MetadataValue`** в доменной модели всегда в **тегированной форме** — независимо от **`valueType`**. Форма хранения универсальна; **`valueType`** влияет только на сериализацию и **строгую валидацию**.
- **Агрегатные типы значения** рекурсивно содержат **`MetadataValue`** — `fixedArray.value: MetadataTypedValue[]`, `formChoiceListDesTimeValue.value: MetadataTypedValue`.
- **Самоописываемый YAML** означает: `fromYAML` не нуждается в **резолвере зависимого типа** — тип однозначно выводится из синтаксиса. Текущие эвристики регулярок в `importStringValueFromYAML` заменяются детерминистской диспетчеризацией.
- **Фасад `AssociatedTable`** регистрируется как отдельный `itemType`, но внутренние конвертеры вызывают `MetadataValue`-машинерию с `rule: { type: "MetadataValue", valueType: ["string"] }`.
- **`valueType`**: массив — единственная канонична форма после миграции. Совместимость с одиночной строкой не сохраняется.
- **Модуль `metadataValue/`** после рефакторинга: диспетчерская таблица хендлеров на **примитивные типы значения** в одном файле + подпапки `fixedArray/` и `formChoiceList/` со своими тестами для **агрегатных типов значения**.

## Обязательные XML-родители (из диалога о `<ChildObjects/>` в `minimal.xml`)

| Термин | Определение | Избегать |
| ------ | ----------- | -------- |
| **Обязательный XML-родитель** | XML-тег-контейнер, который должен присутствовать в выходном XML всегда — даже если у него нет ни одного дочернего элемента (сериализуется как `<Тег/>`). Применяется к `<ChildObjects>` у `MetadataCatalog`, где fixture требует пустой контейнер при отсутствии детей | Required tag, mandatory tag |
| **`requiredXMLParents`** | Поле **правила объекта метаданных** (`MetadataItemRule`): массив путей к **обязательным XML-родителям**, форма — `string[][]`. Каждый путь — массив ключей от корня результата (например, `[["Catalog", "ChildObjects"]]`), симметричен `xmlParents` на уровне **правила свойства** | alwaysEmitTags |
| **Сигнал «тег требуется»** | Соглашение между **оркестрацией** и кастомной post-обработкой: если **оркестрация** поставила ключ со значением `{}` в результат `exportPropertiesToXML`, значит тег обязателен и его нельзя выбрасывать. Проверяется как `result.X !== undefined`, а не `Object.keys(result.X).length > 0` | Always-emit flag |
| **Два механизма пустого контейнера** | Путь 1 — **`defaultValueXMLRaw: {}`** + `xmlParents` на **правиле свойства** коллекции: контейнер появляется, когда коллекция есть, но пуста (см. `attributes`, `tabularSections` — при `value = []`). Путь 2 — **`requiredXMLParents`** на **правиле объекта**: контейнер появляется всегда, независимо от наличия свойств-детей. Для `minimal.xml` каталога нужен путь 2 — ни одного свойства-детей нет вообще | — |
| **Post-обработка `ChildObjects`** | Участок в `metadataCatalog/toXML.ts`: результат **оркестрации** разбирается, `ChildObjects` из rules соединяется с `forms`/`templates`/`commands` из **контекста конвертации** в фиксированном порядке `Attribute → TabularSection → Form → Template → Command`. Кастомна: **оркестрация** не знает о forms/templates | — |

### Relationships обязательных XML-родителей

- **`requiredXMLParents`** читается в `exportPropertiesToXML` после основного цикла: для каждого пути walker гарантирует существование узла со значением `{}` если он отсутствует. **Оркестрация** не знает про конкретные теги — только про список путей из правила.
- Кастомная **post-обработка `ChildObjects`** использует **сигнал «тег требуется»**: `alwaysEmit = catalogFromRules.ChildObjects !== undefined` → эмит контейнера независимо от наличия forms/templates/commands.
- `requiredXMLParents` и `defaultValueXMLRaw: {}` ортогональны: первое декларирует факт на уровне объекта метаданных, второе — поведение одной коллекции при пустом массиве.
- `forms` и `templates` в `exportToXML.context` относятся к **контексту конвертации** — список «соседних» форм/шаблонов каталога в конфигурации. Для `minimal.xml` эти массивы пустые, для `full.xml` — заполнены именами форм.

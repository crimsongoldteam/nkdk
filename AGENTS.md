# AGENTS.md

## Общение

- пиши ответы на русском языке
- задавай вопросы по одному
- если на вопрос можно ответить, исследовав кодовую базу, исследуй кодовую базу вместо того, чтобы спрашивать
- отвечай кратко: по умолчанию 1-3 предложения; варианты разворачивай, когда уместно сравнить подходы
- варианты нумеруй кириллицей: (А), (Б), (В), (Г) - не (A), (B), (C), (D)
- избегай ненужных англицизмов и жаргона, когда есть нейтральный русский эквивалент: не «катим», а «выпускаем» / «доставляем в main»; не «скоуп», а «границы»; не «артефакты», а «результат» / «файлы»; не «slice-by-slice», а «по слоям»; не «break-change», а «несовместимое изменение»
- устоявшиеся технические термины проекта оставляй как есть: XML, YAML, PR, CI, round-trip, fromXML/toXML, rules.ts

## Git

- перед изменением репозитория выполни `git fetch origin develop` и создай отдельный worktree от актуального `origin/develop`, используя навык `superpowers:using-git-worktrees`
- никогда не изменяй файлы и не создавай коммиты непосредственно в `develop` или `main`

## Написание тестов

- не изменяй существующие XML-фикстуры, они являются источником истины
- при добавлении или изменении функциональности следуй [архитектуре тестов](.agents/testing.md)

## Написание rules.ts

- не пиши новые правила fromXML/toXML/fromYAML/toYAML без явного запроса пользователя, предпочитай использование rules.ts
- не указывай поле `order` без явной необходимости - порядок полей, как правило, определяется по референсу
- не добавляй новые поля и служебные признаки в общие типы правил (`BasePropertyRule`, `PropertyRule`) и параметры построителей правил (например, `BooleanRuleParams`) без явного одобрения пользователя; сначала проверь, нельзя ли выразить договор существующими параметрами

## Исключительный тег !xml

- считай `!xml` исключительным механизмом для сохранения формы XML, которую невозможно однозначно восстановить из смысловых данных YAML и индексов метаданных
- перед каждым новым применением `!xml` к свойству или классу значений получай явное согласование разработчика, даже если общий механизм тега уже реализован
- не используй `!xml` для обхода неполного resolver, отсутствующего правила или ещё не исследованного round-trip расхождения; сначала установи, нельзя ли восстановить XML по данным конфигурации

## TypeScript

- минимизируй `as any` и `as unknown`; если приведение неизбежно, держи его на границе интеграции, дай переходнику понятное имя и покрой поведение тестом

## Запуск тестов

- весь проект тестируется командой `pnpm test` из корня - она рекурсивно запускает тесты во всех пакетах `packages/*`
- перед закрытием issue **обязательно** прогнать `pnpm test` и убедиться, что все тесты зелёные
- после каждого законченного слоя и перед завершением реализации обязательно выполни `pnpm duplicates -- --base <commit>`; поддерживаемые файлы и исключения определены в `.jscpd.json`
- перед созданием PR и запуском `finish-pr-cycle` обязательно выполни `pnpm test:architecture:rules` и `pnpm test:architecture`; не продолжай PR-цикл, если любая из команд завершилась с ошибкой
- не перезаписывай baseline dependency-cruiser ради обхода нарушения без явного согласования разработчика

## Архитектура metadata-слоёв

- при изменении общих metadata-операций сверяйся с [архитектурой metadata-операций](.agents/architecture.md); если на стадии планирования архитектурный файл требуется актуализировать, явно запроси у пользователя разрешение и обновляй файл только после полученного согласия; если после реализации план расходится с кодом, сообщи об этом пользователю вместо самостоятельного изменения файла
- существующие ограничения проекта собраны в [restrictions.md](.agents/restrictions.md)
- Нейтральные слои `ruleRuntime`, `diagnostics`, `validation`, `projectDefinition`, `project`, `projectState` и `resourceTopology/core` не знают про конкретные реализации метаданных: никаких частных условий по `itemType`, именам XML-корней, папкам вроде `Формы`/`Макеты` или типам вроде `ChildFormNames`
- concrete-зависимости направлены к более общим слоям: `systemEnumerations` не зависит от `forms` и `appliedObjects`, `commonObjects` не зависит от `forms` и `appliedObjects`, `forms` не зависит от `appliedObjects`
- runtime-сборка находится только в `metadata/composition`; обычные metadata-модули получают собранные зависимости через параметры или нейтральные регистрации

# Инвентаризация миграции

Из корня существующей рабочей копии:

```sh
node --test tools/rules-migration/test/inventory.test.mjs
node tools/rules-migration/src/cli.mjs
```

Команда читает TS-файлы `packages/rules`, `packages/runtime` и `e2e`, не исполняет правила и
перезаписывает только два своих результата:

- `tests/migration/rules-inventory.json` — определения, зависимости, координаты
  конструкций, проверки, хеши, связь с существующим coverage.json;
- `docs/superpowers/reports/2026-09-12-rules-migration-inventory.md` — сводка.

Используется уже установленный TypeScript 6.0.3 из инструмента
dependency-cruiser. TypeScript 7 в корне не предоставляет compiler API.
Новые зависимости не устанавливаются. Код анализатора написан на JavaScript
в существующем формате инструментов `.mjs`; анализируемый язык — TypeScript.

Реестр — воспроизводимый снимок, а не второй источник готовности. Не читайте
его целиком в контекст ИИ: выбирайте файл/группу программно или читайте сводку.
В `source`/`target` отсутствие `path` означает путь содержащей записи файла;
`sites` — пары `[line, column]` с нумерацией от 1. Длинные выражения усечены
с признаком `truncated`; исходник доступен по координатам и SHA-256.

Неизвестный spread/вычисление блокирует полноту соответствующего объекта.
Известные поля в таком объекте — нижняя граница. Частоты вызовов не равны
числу конечных свойств, а регистрации тестов не равны числу запусков.
`literal-candidate` описывает только аргументы ожиданий: он не доказывает
переносимость входов, hooks или пользовательского тестового помощника.

Семантическая приёмка, генерация YAML и перенос тестов относятся к следующим
этапам. Реализованное извлечение и сравнение ключей описаны ниже.

## Извлечение и сравнение ключей

```sh
pnpm migration:extract
```

Команда требует актуальный снимок инвентаризации: проверяет перечень файлов
и каждый хеш. Статически извлекает объявления `*Rules` из `rules.ts`, затем
запускает отдельный Node/tsx-процесс для чтения экспортированных объектов.
Совпадение ключей и их порядка не доказывает семантическую эквивалентность.
Неэкспортированные объявления сохраняются в результате без ложной отметки
успеха. Неподдержанные операторы/циклы/изменённые проверенные функции блокируют
извлечение; частичное совпадение не становится полным.

Результаты: `tests/migration/rules-extraction.json` и
`docs/superpowers/reports/2026-09-12-rules-extraction.md`. Код 1 означает
несовпадение или ошибку загрузки; зарегистрированные статические блокировки
в отчёте допустимы для этапа исследования, но запрещают автоматическую приёмку.
Проверенное соответствие `metadataRuleFragment` привязано к SHA-256 исходного
файла; обновлять его можно только после повторной проверки договора функции.

## Генерация кандидатов

```sh
pnpm migration:candidates
rust/target/debug/nkdk-dev declarations check --dir tests/migration/rules-candidates
rust/target/debug/nkdk-dev declarations compile --dir tests/migration/rules-candidates
```

Генератор пишет только в `tests/migration/rules-candidates` и собственный отчёт.
Каталог содержит проекции поддержанных свойств, общие фрагменты, снимки
используемых зависимостей и manifest.json. Контекст полного владельца ещё
не связан; включать эти проекции в рабочую сборку автоматически запрещено.
Ручная правка, удаление или добавление постороннего файла прерывает повторную
генерацию. Manifest содержит исходные тексты принадлежащих генератору YAML
для точной проверки изменений, хеши входов и явные причины блокировок.

`declarations compile` генерирует Rust в памяти и сообщает размер результата;
команда не запускает rustc и не проверяет round-trip. Для справки по расхождениям
с рабочим каталогом читать `existingComparison`: это структурные кандидаты на
соответствие, не разрешение на замену декларации.

## Выборочная проверка пакета

После обновления кандидатов и независимых ожиданий:

```sh
pnpm migration:candidates
pnpm migration:contracts
pnpm migration:check:focused --batch tests/migration/batches/document-journal.json
```

Команда проверяет актуальность снимков, выбирает целые декларации случаев,
транзитивные imports и поставщиков нужных индексов. Она не вырезает отдельные
поля из декларации и не ослабляет ожидания. Существующий Rust-запускатель
выполняет преобразования, валидацию и Clippy через прежний компилятор.

`document-journal.json` выбирает четыре случая, охватывающих 48 свойств.
Это проверка кандидатов, не автоматическая приёмка владельцев или новые
подключения. Для другого пакета задайте `id`, список `cases` из
`rules-contract-cases.json` и при необходимости `expectedPropertyCount`.

Каталог, выбранные случаи, журналы и времена сохраняются в
`rust/target/migration-focused/<id>/`. Неизменные файлы не перезаписываются:
повторный запуск использует кэш. Общий Cargo target — `rust/target/migration-contracts`;
смена пакета или переход к полному каталогу может потребовать пересборки.
Первый запуск на пустом кэше зависимостей будет дольше измерений этого эксперимента.
После пакета сохраняется полный контроль: `pnpm test:migration-contracts`.
Рабочий `rust/declarations` не меняется от выборочной проверки.

Переменная `NKDK_MIGRATION_CATALOG` используется только существующим проверочным
runtime и отслеживается Cargo. Без неё runtime собирает прежний полный каталог.
# Подключение готовых фрагментов

`pnpm migration:attachments` проверяет точные профили из
`profiles/ready-attachments.json` и формирует отдельные кандидаты подключения.
`pnpm test:migration-attachments` повторяет генерацию и проверяет 72 случая
из e2e, включая восстановление внешних XML без исходного референса.
Оболочка Probe и поставщик идентификаторов служат только для проверки.
Совпавший профиль не означает полную приёмку владельца.

`pnpm test:migration-attachments --owners` дополнительно проверяет рабочие
сборки документа и журнала. `profiles/owner-attachments.json` связывает
исходное свойство с декларацией владельца и её входами. Генерация прекращается,
если согласованное подключение исчезло, стало неоднозначным или изменились
привязки. Именованный индекс сверяется по идентификатору; совместимость его
схемы проверяет Rust-компилятор. Проверка состава декларации не заменяет
проверку поведения владельца.

Массовый пакет Help: два дополнительных точных профиля с одинаковыми
filePath/xmlPath распознают ещё 17 вхождений. Различающиеся и вычисляемые
пути не нормализуются молча. Проверка подключений охватывает 68 e2e-файлов
(39 Help, 29 AdditionalIndexes); для Help языки берутся из имён HTML-страниц.
Это проверка внешних фрагментов, а не 68 принятых владельцев.

Составные кандидаты конфигурации и общей формы проверяют основные свойства
вместе с Help (четыре дополнительных случая). Это проекции Properties;
присутствующая справка комбинируется из независимых e2e-данных. Генерация
проверяет актуальность снимка контрактов; после изменения его источников
нужно выполнить `pnpm migration:contracts`.

ExternalFile добавляет четыре вхождения и три ресурсных кандидата. Пути
передаются общему common.external-file через фиксированные bind. 76 случаев
проверяют в том числе маршруты из исходных rules.ts; ресурсные Rust-тесты
проверяют двоичные e2e-файлы, пустой файл, отсутствие и безопасные сегменты.
Это ещё не подключение к полным сборкам конфигурации и XDTO-пакета.


`pnpm migration:collections` извлекает граф коллекций в
`tests/migration/collection-links.json`. Тот же граф включён в manifest
`migration:candidates`. Разбор разрешает статические регистрации, семейства
map и ссылки itemRule с учётом переопределения свойства; код метаданных
не исполняется. `linked-structure` не означает принятую декларацию.


`migration:candidates` также пытается выпустить полные поддержанные массивы
записей по графу. Результат и причины блокировки — collectionEmission в
manifest и `docs/superpowers/reports/2026-09-13-collection-emission.md`.
`pnpm test:migration-collections` проверяет выпуск через настоящий Rust-компилятор
и двустороннее преобразование. Именованные словари записей и контекст элементов
пока явно блокируются; неполное правило элемента не выпускается.

Именованные коллекции используют `record-mapping` и исходный `keyField`.
`test:migration-collections` проверяет массивы и словари на одном механизме
записи, в том числе вложенные свойства, пропущенные/повторные имена и аномалии.
Полнота записей и контекст по-прежнему проверяются до выпуска; наличие
сгенерированного свойства не означает приёмку полного владельца.


### Составной кандидат плана видов характеристик

```sh
node tools/rules-migration/src/characteristic-owner-operation.mjs
node tools/rules-migration/src/characteristic-owner-operation.mjs --check
```

Операция соединяет обычную генерацию с готовыми сборщиками стандартных
реквизитов, ввода по строке, команд, имён дочерних объектов и внешних файлов.
Сохраняются дерево compose, связи полей, XML-порядок исходной регистрации и
существующая сортировка YAML. Одно исходное свойство нельзя присвоить двум
частям. Кандидат не включается в рабочую сборку автоматически.

`tests/migration/characteristic-owner-coverage.json` перечисляет соединённые
свойства и оставшиеся условия. `complete: false` нельзя заменять флажком
полного переноса: нужны контекстные источники и e2e-приёмка основы и расширения.

Проверочные примеры подключённых коллекций генерируются отдельно:

```sh
node tools/rules-migration/src/characteristic-collections-cases.mjs
node tools/rules-migration/src/characteristic-collections-cases.mjs --check
```

Матрица использует неизменные e2e-фикстуры; приёмка коллекций основы
не заменяет полную приёмку владельца и расширения.

Связь с объектом основы и её совместная история проверяются отдельно:

```sh
node tools/rules-migration/src/characteristic-base-state-cases.mjs
node tools/rules-migration/src/characteristic-base-state-cases.mjs --check
```

Пять случаев используют прежние e2e-данные, принятую границу Notify и
отклонение порядка XML. Проверяются общая история чисел, булевого значения,
перечисления и ссылки на основу, а также подключение TypeDescription.
Это не полная приёмка всех свойств заимствованного владельца и MultiState.
Канонический порядок пропущенных в старой xmlOrder полей заголовка задан
в `contracts/owner-property-order.yaml`; явный порядок rules.ts приоритетен.


## Матрица создания значений по умолчанию

`pnpm test:migration-family --family record-defaults` проверяет общий путь
от существующего `presence.yaml.missing.denotes.record` до хранилища Rust.
Примеры обычных и вложенных записей, фрагментов, условий и строки коллекции
содержат независимые XML/YAML-ожидания. Проверка по одному случаю:
`pnpm test:migration-family --family record-defaults --case record-default-nested-context`.
Каждый случай собирается отдельно для ограничения памяти `rustc`.
Эта матрица проверяет механизм и не ставит флажки приёмки common-объектов.

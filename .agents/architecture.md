# Архитектура

## Термины

| Термин | Значение |
|---|---|
| Проект | NKDK-проект в YAML-представлении, включая связанные внешние файлы. |
| Конфигурация | Конфигурация внутри информационной базы «1С:Предприятие». |

## MCP-договор компонентов проекта

MCP tools принимают `projectDir` как корень NKDK-проекта. В этом корне находится единственная папка `.nkdk`, а YAML-компоненты размещаются так:

```text
projectDir/
  .nkdk/
  cf/
  cfe/<ИмяРасширения>/
  erf/<ИмяОтчета>/
  epf/<ИмяОбработки>/
```

`componentPath` - относительный путь компонента: `cf`, `cfe/<Имя>`, `erf/<Имя>` или `epf/<Имя>`. Если `componentPath` не передан, MCP использует `cf`, включая операции записи. Core metadata-операции на этом этапе не знают о структуре `cf/cfe/erf/epf`: граница находится в `packages/mcp`, где `projectDir + componentPath` преобразуется в каталог одного YAML-компонента.

`nkdk.import_from_xml` импортирует один XML-компонент из заданного `xmlDir` в `projectDir/componentPath`; целевой каталог компонента должен отсутствовать или быть пустым. `nkdk.sync_to_xml` выгружает один YAML-компонент `projectDir/componentPath` в заданный `xmlDir`. В текущем MCP-договоре `xmlDir` не вычисляется как `xmlRootDir/componentPath`, MCP не подключается к 1С и не импортирует все компоненты проекта за один вызов.

Будущий импорт из базы должен сначала выгружать базу во временный `xmlRootDir` со структурой `cf`, `cfe/<Имя>`, `erf/<Имя>`, `epf/<Имя>`, а затем загружать выбранные компоненты через тот же одно-компонентный XML-договор.

### Последовательность импорта из готовой XML-выгрузки

Импорт выполняется в два прохода, потому что при построении YAML одного объекта могут потребоваться сведения обо всех метаданных Конфигурации.

1. Главный процесс подготавливает `Правила структуры XML-выгрузки`, рекурсивно находит XML-файлы и связанные внешние файлы и классифицирует найденные пути по структуре XML-выгрузки, не читая XML. Неизвестный файл или конфликт маршрутов завершает подготовку ошибкой; иначе главный процесс формирует задания по одному итоговому YAML-файлу и статически распределяет список заданий между worker по кругу.
2. Каждый worker читает и разбирает XML-файлы назначенных заданий, строит metadata-модели и извлекает необходимые факты. Все XML-файлы одного задания обрабатываются одним worker.
3. Каждый worker извлекает привязанные к целевым YAML-файлам локальный индекс метаданных и `Фрагмент данных файла индекса конфигурации`, объединяет свои фрагменты в один передаваемый буфер и освобождает XML-данные. До второго прохода в worker остаются metadata-модели и компактные сведения о связанных внешних файлах.
4. Главный процесс объединяет локальные индексы в `Глобальный индекс метаданных`, обобщает `Worker буфер данных файла индекса конфигурации` в `Данные конфигурации для индекса` и передаёт глобальный индекс всем worker.
5. Главный процесс отправляет каждому worker одну команду второго прохода. Каждый worker последовательно строит YAML из сохранённых моделей с использованием `Глобальный индекс метаданных`, записывает YAML и создаваемые преобразованием связанные файлы напрямую в Проект и освобождает обработанные модели. Преобразование не читает YAML других объектов.
6. Каждый worker формирует `Worker список файлов результата импорта`: записанные worker файлы и внешние файлы назначенных объектов из XML-выгрузки с их целевыми путями.
7. Главный процесс объединяет worker списки в `Список файлов результата импорта` и проверяет целевые пути.
8. Главный процесс асинхронно с ограниченным параллелизмом копирует внешние файлы XML-выгрузки по единому списку.
9. Главный процесс вычисляет хэши файлов результата импорта по `Список файлов результата импорта`.
10. Главный процесс формирует и последним записывает файл индекса конфигурации напрямую в итоговый путь.

Если чтение XML, построение модели или построение любого YAML завершилось ошибкой, копирование внешних файлов XML-выгрузки и запись файла индекса конфигурации не начинаются.

Ошибка одного задания не останавливает текущий проход: worker обрабатывает остальные назначенные задания и возвращает все обнаруженные ошибки. Переход к следующему проходу либо к копированию внешних файлов выполняется только при успешном результате всех worker и отсутствии конфликтов при обобщении индексов и списка файлов.

Если при построении YAML не удалось разрешить `ПутьКДанным`, worker сохраняет исходное значение из XML и возвращает предупреждение. Такое предупреждение не блокирует копирование внешних файлов и запись файла индекса конфигурации.

При любом неуспешном завершении импорта файл индекса конфигурации не записывается. Так как импорт пишет в целевой компонент напрямую, каталог может остаться частично заполненным; перед повтором его нужно очистить.

Импорт в непустой целевой каталог компонента запрещён на уровне MCP-договора; операция принимает отсутствующий либо пустой каталог компонента.

Worker файлы и внешние файлы XML-выгрузки записываются напрямую по целевым путям. Запись всего набора не является транзакцией. При ошибке новые операции не запускаются, успешно записанные файлы не откатываются, а файл индекса конфигурации не записывается.

Аварийное завершение worker останавливает импорт без автоматического перезапуска и повторения его заданий. Копирование внешних файлов XML-выгрузки и запись файла индекса конфигурации не выполняются.

## Чтение проекта

Этап читает проект для синхронизации, валидации, подсказки схем, переименования и поиска ссылок. Проверка по схеме, построение metadata-модели и проверка зависимостей выполняются позднее.

| Шаг | Описание | Входящие артефакты | Исходящие артефакты | Worker |
|---|---|---|---|---:|
| Распределение файлов | Находит и классифицирует YAML и внешние файлы проекта, затем делит YAML-файлы между worker. | `Корень проекта`<br>`Правила структуры проекта` | `Список файлов проекта`<br>`Worker список YAML-файлов` |  |
| Чтение и разбор YAML | Читает назначенные YAML-файлы и разбирает их без построения позиций YAML-узлов. | `Worker список YAML-файлов` | `Worker данные YAML` | ✓ |
| Сохранение worker данных YAML | Сохраняет `Worker данные YAML` в памяти worker для последующих шагов операции. | `Worker данные YAML` | `Worker данные YAML` | ✓ |
| Извлечение локальных индексов | Извлекает worker индексы метаданных и worker индексы зависимостей из worker данных YAML. | `Worker данные YAML` | `Worker индекс метаданных`<br>`Worker индекс зависимостей` | ✓ |
| Обобщение индексов | Объединяет worker индексы метаданных в глобальный индекс метаданных, а worker индексы зависимостей — во временный глобальный индекс зависимостей. | `Worker индекс метаданных`<br>`Worker индекс зависимостей` | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` |  |
| Распределение индекса зависимостей | Делит глобальный индекс зависимостей между worker и передаёт каждому worker глобальный индекс метаданных и worker индекс зависимостей. | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` | `Глобальный индекс метаданных`<br>`Worker индекс зависимостей` |  |

После обобщения worker удаляет `Worker индекс метаданных` и `Worker индекс зависимостей`. После распределения координатор удаляет `Глобальный индекс зависимостей`. Каждый worker продолжает хранить `Worker данные YAML`, `Глобальный индекс метаданных` и свой `Worker индекс зависимостей`.

Целевое состояние: `Worker данные YAML` не покидают worker, а операции выполняют последующие шаги командами worker. Временное состояние реализации: для validation распарсенные YAML-данные уже не передаются в главный поток; синхронизация в XML, переименование и поиск ссылок ещё используют переходную передачу YAML-данных и должны быть переведены на worker-команды отдельно.

Синхронизация, как и импорт, выполняется в два прохода. В первом проходе worker читают назначенные YAML, сохраняют их и извлекают компактные сведения для `Глобальный индекс метаданных`. Во втором проходе одно задание получает один исходный YAML и формирует все относящиеся к нему XML-файлы. Другие YAML во втором проходе не читаются; межфайловые зависимости разрешаются через глобальный индекс метаданных.

Этап формирует полный или выбранный по изменениям XML-результат из Проекта. Файл индекса конфигурации является единственным источником идентификаторов и данных восстановления XML; локальная XML-выгрузка как reference не используется.

| Построение и запись XML | Преобразует назначенные YAML в metadata-модели, строит XML с использованием общего индекса метаданных и файла индекса конфигурации и пишет XML непосредственно в целевой каталог. | `Worker список заданий синхронизации`<br>`Worker данные YAML`<br>`Глобальный индекс метаданных`<br>`Общий снимок файла индекса конфигурации`<br>`rules.ts`<br>`Подтверждённый корень XML-результата` | `XML-файл`<br>`Фрагмент данных файла индекса конфигурации` | ✓ |

Полная синхронизация приводит XML-результат к полному составу Проекта: отсутствующие в Проекте объекты и файлы не попадают в результат и удаляются из нового содержимого файла индекса конфигурации. Хэши вычисляются для формирования нового индекса, но не используются для отбора заданий.

Worker записывают XML непосредственно в пустой целевой каталог. Если одно из заданий завершается ошибкой, операция останавливается, частичный XML-результат сохраняется для диагностики и запись файла индекса конфигурации не начинается. После успешного формирования всего XML-результата основной файл индекса конфигурации записывается напрямую в итоговый путь.

### Последовательность полной синхронизации

1. Главный процесс проверяет Проект, наличие файла индекса конфигурации и отсутствие содержимого в целевом XML-каталоге.
2. Главный процесс по правилам находит YAML и внешние файлы, формирует задания по одному исходному YAML и статически распределяет их между worker.
3. Главный процесс один раз читает и полностью проверяет файл индекса конфигурации, затем создаёт его неизменяемое представление в общей памяти.
4. В первом проходе worker читают и разбирают YAML, вычисляют хэши по тем же прочитанным байтам, сохраняют `Worker данные YAML` и извлекают компактные сведения о метаданных и составе Проекта.
5. Главный процесс объединяет сведения worker в `Глобальный индекс метаданных` и передаёт его worker через общую память.
6. Во втором проходе worker строят metadata-модели и XML с использованием `Глобальный индекс метаданных` и `Общий снимок файла индекса конфигурации`, записывают XML непосредственно в целевой каталог и собирают фрагменты нового файла индекса конфигурации. Задание `Конфигурация.yaml` формирует `Configuration.xml`.
7. Главный процесс проверяет списки записанных XML-файлов и объединяет фрагменты файла индекса конфигурации, полученные от worker.
8. После успешного завершения всех worker главный процесс асинхронно копирует внешние файлы единым списком и вычисляет их хэши по тем же копируемым байтам.
9. Главный процесс формирует `ConfigDumpInfo.xml` из объединённых сведений обо всём XML-результате.
10. Главный процесс объединяет хэши YAML и внешних файлов с данными фактически сформированного XML, формирует полное новое содержимое файла индекса конфигурации и последним записывает его напрямую в итоговый путь.

## Именование данных

- Материализованная коллекция явно называется списком; независимо обрабатываемые элементы называются в единственном числе.
- Создающий и потребляющий шаги используют одно и то же точное название.
- Каждое название записывается отдельно и выделяется как код.

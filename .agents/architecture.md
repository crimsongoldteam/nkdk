# Архитектура

## Термины

| Термин | Значение |
|---|---|
| Проект | NKDK-проект в YAML-представлении, включая связанные внешние файлы. |

## Операции

## Подготовка импорта конфигурации

### Последовательность импорта из готовой XML-выгрузки

Импорт выполняется в два прохода, потому что при построении YAML одного объекта могут потребоваться сведения обо всех метаданных Конфигурации.

1. Главный процесс подготавливает `Правила структуры XML-выгрузки`, рекурсивно находит XML-файлы и связанные внешние файлы и классифицирует найденные пути по структуре XML-выгрузки, не читая XML. Неизвестный файл или конфликт маршрутов завершает подготовку ошибкой; иначе главный процесс формирует задания по одному итоговому YAML-файлу и статически распределяет список заданий между worker по кругу.
2. Каждый worker читает и разбирает XML-файлы назначенных заданий, строит metadata-модели и извлекает необходимые факты. Все XML-файлы одного задания обрабатываются одним worker.
3. Каждый worker извлекает привязанные к целевым YAML-файлам локальный индекс метаданных и `Фрагмент данных файла индекса конфигурации`, объединяет свои фрагменты в один передаваемый буфер и освобождает XML-данные. До второго прохода в worker остаются metadata-модели и компактные сведения о связанных внешних файлах.
4. Главный процесс объединяет локальные индексы в `Глобальный индекс метаданных`, обобщает `Worker буфер данных файла индекса конфигурации` в `Данные конфигурации для индекса` и передаёт глобальный индекс всем worker.
5. Главный процесс отправляет каждому worker одну команду второго прохода. Каждый worker последовательно строит YAML из сохранённых моделей с использованием `Глобальный индекс метаданных`, записывает YAML и создаваемые преобразованием связанные файлы в свой временный каталог и освобождает обработанные модели. Преобразование не читает YAML других объектов.
6. Каждый worker формирует `Worker список файлов результата импорта`: подготовленные файлы из своего временного каталога и внешние файлы назначенных объектов из XML-выгрузки с их целевыми путями.
7. Главный процесс объединяет worker списки в `Список файлов результата импорта` и проверяет целевые пути.
8. Главный процесс асинхронно с ограниченным параллелизмом переносит результат в Проект по единому списку: подготовленные worker файлы перемещает, внешние файлы XML-выгрузки копирует.
9. Главный процесс вычисляет хэши всех файлов полученного Проекта.
10. Главный процесс формирует и последним атомарно записывает файл индекса конфигурации, после чего удаляет временный корень операции.

Если чтение XML, построение модели или построение любого YAML завершилось ошибкой, перенос результата в Проект и запись файла индекса конфигурации не начинаются.

Ошибка одного задания не останавливает текущий проход: worker обрабатывает остальные назначенные задания и возвращает все обнаруженные ошибки. Переход к следующему проходу либо к переносу результата выполняется только при успешном результате всех worker и отсутствии конфликтов при обобщении индексов и списка файлов.

Если при построении YAML не удалось разрешить `ПутьКДанным`, worker сохраняет исходное значение из XML и возвращает предупреждение. Такое предупреждение не блокирует перенос результата и запись файла индекса конфигурации.

При любом неуспешном завершении импорта временные каталоги операции сохраняются, а путь временного корня возвращается вызывающей стороне. Автоматическая очистка таких каталогов пока не выполняется.

Автоматическая очистка целевого каталога пока не выполняется. При импорте в непустой каталог могут сохраниться отсутствующие в Конфигурации файлы; ограничение описано в `.agents/restrictions.md`.

Подготовленные worker файлы перемещаются из `.nkdk/tmp/import/`, а внешние файлы копируются из XML-выгрузки напрямую по целевым путям. Перенос всего набора не является транзакцией. При ошибке новые операции не запускаются, успешно заменённые файлы не откатываются, а файл индекса конфигурации не записывается.

Аварийное завершение worker останавливает импорт без автоматического перезапуска и повторения его заданий. Временные каталоги операции не удаляются, а их путь возвращается в ошибке; перенос в Проект и запись файла индекса конфигурации не выполняются.

## Чтение проекта

Этап читает проект для синхронизации, валидации, подсказки схем, переименования и поиска ссылок. Проверка по схеме, построение metadata-модели и проверка зависимостей выполняются позднее.

| Шаг | Описание | Входящие артефакты | Исходящие артефакты | Worker |
|---|---|---|---|---:|
| Распределение файлов | Находит и классифицирует YAML и внешние файлы проекта, затем делит YAML-файлы между worker. | `Корень проекта`<br>`Правила структуры проекта` | `Список файлов проекта`<br>`Worker список YAML-файлов` |  |
| Чтение и разбор YAML | Читает назначенные YAML-файлы и разбирает их без построения позиций YAML-узлов. | `Worker список YAML-файлов` | `Worker данные YAML` | ✓ |
| Сохранение worker данных YAML | Сохраняет `Worker данные YAML` в памяти worker для последующих шагов операции. | `Worker данные YAML` | `Worker данные YAML` | ✓ |
| Извлечение локальных индексов | Извлекает worker индексы метаданных и worker индексы зависимостей из worker данных YAML. | `Worker данные YAML` | `Worker индекс метаданных`<br>`Worker индекс зависимостей` | ✓ |
| Обобщение индексов | Объединяет worker индексы метаданных в глобальный индекс метаданных, а worker индексы зависимостей — во временный глобальный индекс зависимостей. | `Worker индекс метаданных`<br>`Worker индекс зависимостей` | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` |  |
| Распределение индекса зависимостей | Делит глобальный индекс зависимостей между worker и передаёт каждому worker глобальный индекс метаданных и worker индекс зависимостей. | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` | `Глобальный индекс метаданных`<br>`Worker индекс зависимостей` |  |

После обобщения worker удаляет `Worker индекс метаданных` и `Worker индекс зависимостей`. После распределения координатор удаляет `Глобальный индекс зависимостей`. Каждый worker продолжает хранить `Worker данные YAML`, `Глобальный индекс метаданных` и свой `Worker индекс зависимостей`.

Целевое состояние: `Worker данные YAML` не покидают worker, а операции выполняют последующие шаги командами worker. Временное состояние реализации: для validation распарсенные YAML-данные уже не передаются в главный поток; синхронизация в XML, переименование и поиск ссылок ещё используют переходную передачу YAML-данных и должны быть переведены на worker-команды отдельно.

## Подготовка синхронизации конфигурации

Этап определяет изменённые файлы проекта и подготавливает XML для применения в конфигурации.

| Шаг | Описание | Входящие артефакты | Исходящие артефакты | Worker |
|---|---|---|---|---:|
| Чтение файла индекса конфигурации | Проверяет и разбирает единый двоичный файл выбранной привязки. | `Файл индекса конфигурации` | `Данные файла индекса конфигурации`<br>`Ожидаемая версия конфигурации` |  |
| Сравнение хэшей проекта с индексом конфигурации | Сравнивает текущие хэши с хэшами из файла индекса конфигурации. | `Хэши файлов проекта`<br>`Данные файла индекса конфигурации` | `Список изменений проекта` |  |

## Именование данных

- Материализованная коллекция явно называется списком; независимо обрабатываемые элементы называются в единственном числе.
- Создающий и потребляющий шаги используют одно и то же точное название.
- Каждое название записывается отдельно и выделяется как код.

| `Подтверждённая версия конфигурации` | Версия конфигурации, подтверждённая 1С после проверки или успешного применения изменений. |
| `Корень XML-выгрузки` | Каталог исходной XML-выгрузки конфигурации. |
| `Правила структуры XML-выгрузки` | Подготовленное из `rules.ts` описание структуры XML-выгрузки, по которому пути быстро классифицируются как XML metadata-модели, внешние файлы, игнорируемые файлы или неизвестные пути. |

| `Описание XML-файла выгрузки` | Путь XML-файла, его роль и правила соответствующего объекта метаданных. |
| `Описание внешнего файла XML-выгрузки` | Путь внешнего файла XML-выгрузки, его роль и правила соответствующего свойства метаданных. |
| `Worker список заданий импорта` | Назначенные одному worker задания. Каждое задание формирует один итоговый YAML-файл и содержит его целевой путь, правила, описание владельца, XML-файлы metadata-модели и связанные внешние файлы. |
| `XML-текст` | Исходное или подготовленное текстовое содержимое XML-файла. |
| `XML-данные` | Разобранные структурированные данные XML-файла. |
| `Фрагмент данных файла индекса конфигурации` | Привязанные к целевому YAML-файлу логические записи будущих секций `IDENTITIES`, `XML_ORDERS`, `XML_NODES` и `XML_VALUES`. Заголовок, общие строки, привязка, хэши и контрольные суммы во фрагмент не входят. |
| `Worker буфер данных файла индекса конфигурации` | Один передаваемый `ArrayBuffer` с фрагментами всех назначенных worker заданий и локальным пулом строк. Владение передаётся главному процессу без копирования; на диск буфер не записывается. |
| `Данные конфигурации для индекса` | Извлечённые из XML данные, сохраняемые в файле индекса конфигурации. |
| `Временный каталог worker` | Изолированный подкаталог уникального временного корня операции внутри `.nkdk/tmp/import/`, в который worker записывает подготовленные YAML и создаваемые преобразованием связанные файлы. |
| `Worker список файлов результата импорта` | Источники файлов назначенных worker объектов и их целевые пути в Проекте. Источник находится во временном каталоге worker либо в XML-выгрузке. |
| `Список файлов результата импорта` | Проверенный объединённый список всех файлов, которые главный процесс должен переместить либо скопировать в Проект. |
| `JSON Schema` | Схема допустимой структуры разобранного YAML-файла. |
| `Диагностики YAML-схемы` | Ошибки соответствия worker данных YAML своей JSON Schema. |
| `rules.ts` | Декларативные правила преобразования metadata-модели. |
| `Metadata-модель` | Внутреннее представление объекта метаданных. |
| `ValidationPendingCheck` | Отложенная проверка metadata-модели, сформированная правилами и выполняемая после построения индексов. |
| `Диагностики зависимостей метаданных` | Ошибки ссылок на метаданные и путей к данным. |
| `Целевой путь` | Путь, по которому должен быть записан или перемещён файл. |
| `YAML-файл` | YAML-файл, записанный на диск. |
| `Внешний файл проекта` | Модуль, бинарный или другой внешний файл, записанный в проект. |
| `Исходный путь` | Текущий путь переименовываемого файла или каталога. |
| `Переименованный путь` | Новый путь переименованного файла или каталога. |

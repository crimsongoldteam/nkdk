# Архитектура

## Правила документа

| Правило | Требование |
|---|---|
| Основная форма | Архитектурные решения, договоры, ограничения, состояния и потоки данных описываются преимущественно таблицами. |
| Дополнительные формы | Списки используются для коротких перечислений, Mermaid-диаграммы — для связей и потоков, которые понятнее в графическом виде. |
| Свободный текст | Допускается только как короткая вводная связка, если таблица, список или диаграмма сделали бы смысл менее ясным. Длинные повествовательные абзацы не используются. |
| Строка таблицы | Описывает одно проверяемое утверждение или один архитектурный элемент. Несвязанные решения разносятся по разным строкам. |
| Именование | Названия шагов и артефактов должны совпадать во всех таблицах и диаграммах. |

## Термины

| Термин | Значение |
|---|---|
| Проект | NKDK-проект в YAML-представлении, включая связанные внешние файлы. |
| Конфигурация | Конфигурация внутри информационной базы «1С:Предприятие». |

## MCP-договор компонентов проекта

```text
projectDir/
  .nkdk/
  cf/
  cfe/<ИмяРасширения>/
  erf/<ИмяОтчета>/
  epf/<ИмяОбработки>/
```

| Элемент договора | Решение |
|---|---|
| `projectDir` | Корень NKDK-проекта. Содержит единственную папку `.nkdk` и каталоги YAML-компонентов. |
| `.nkdk` | Находится только в корне `projectDir`, а не внутри компонентов. |
| `componentPath` | Относительный путь `cf`, `cfe/<Имя>`, `erf/<Имя>` или `epf/<Имя>`. Значение по умолчанию — `cf`, включая операции записи. |
| Граница компонентов | `packages/mcp` преобразует `projectDir + componentPath` в каталог одного YAML-компонента. Core metadata-операции не знают о структуре `cf/cfe/erf/epf`. |
| `nkdk.import_from_xml` | Импортирует один XML-компонент из заданного `xmlDir` в `projectDir/componentPath`. Целевой каталог компонента должен отсутствовать или быть пустым. |
| `nkdk.sync_to_xml` | Выгружает один YAML-компонент из `projectDir/componentPath` в заданный `xmlDir`. |
| Текущие ограничения MCP | `xmlDir` не вычисляется как `xmlRootDir/componentPath`; MCP не подключается к 1С и не импортирует все компоненты проекта за один вызов. |
| Будущий импорт из базы | Сначала выгружает базу во временный `xmlRootDir` со структурой компонентов, затем импортирует выбранные компоненты через тот же одно-компонентный XML-договор. |

| Договор | Решение |
|---|---|
| Переименование и поиск ссылок | Временно используют `Построение модели`, но не запускают шаги validation. Полная validation остаётся отдельной операцией. |
| Источники validation | `Worker данные YAML`, YAML-факты, `Глобальный индекс метаданных` и `Worker индекс зависимостей`. `Построение модели` в worker не выполняется. |
| Общий сбор фактов | Импорт и validation используют `OwnerFactsCollector`. Импорт передаёт окончательное YAML-значение сразу после его формирования; validation — во время обхода существующего YAML. |
| Регистрация сборщика | Тип свойства регистрирует `collectOwnerFactsFromYAML`. Если смысл зависит от места свойства, `PropertyRule.ownerFactRole` задаёт роль факта. |
| Область validation | Проверка схемы, уникальности имён, обычных `metadataTarget`-ссылок и формирование validation-диагностик выполняются только validation. |
| Договор `DataPath` | `Факты владельца` и индекс полей являются единственным представлением данных владельца. Все обработчики читают типизированные факты напрямую. |
| Запрещённые данные `DataPath` | Полная или синтетическая metadata-модель, `model`, `modelStub`, модельный текст и восстановленный совместимый объект не входят в локальный или глобальный индекс. |
| Другие модельные операции | Полная metadata-модель может использоваться, например, в YAML → XML, но не участвует в сборе фактов, глобальном индексе или разрешении `DataPath`. |
| Общие координаты | `YamlRuleCursor` строит `YAML-путь` и `Путь правила`, включая правило конкретного полиморфного элемента формы. |
| Координаты импорта | Формируются во время единственного обхода XML → YAML. Повторный полный обход YAML для поиска отложенных значений не выполняется. |
| Координаты validation | Формируются во время обхода исходного YAML. |
| Формы в validation | Обходятся обычное дерево `Элементы` и зарегистрированные single-элементы `КонтекстноеМеню`, `РасширеннаяПодсказка`, `AutoCommandBar`, включая вложенные `Элементы`. Их `ПутьКДанным` проверяются общим механизмом. |

### Последовательность импорта из готовой XML-выгрузки

| Свойство | Решение |
|---|---|
| Число проходов | Два. YAML одного объекта может зависеть от сведений обо всех метаданных Конфигурации. |
| Первый проход | Строит YAML, отложенные пути, факты владельца и данные файла индекса конфигурации. |
| Состояние worker между проходами | YAML-данные, отложенные пути, служебное описание задания и компактные описания связанных внешних файлов. XML и metadata-модель не сохраняются. |
| Второй проход | Уточняет только сохранённые YAML-пути по глобальному индексу и записывает результат. |

| № | Исполнитель | Действие | Результат |
|---:|---|---|---|
| 1 | Главный процесс | Подготавливает `Правила структуры XML-выгрузки`, находит XML и связанные файлы без чтения XML, классифицирует пути, отклоняет неизвестные пути и конфликты, формирует задания по одному итоговому YAML и распределяет их по кругу. | `Worker список заданий импорта` |
| 2 | Worker | Читает и разбирает все XML задания. Единым обходом `rules.ts` строит YAML, отмечает отложенные координаты и передаёт окончательные YAML-значения в `OwnerFactsCollector`. Атомарное свойство последовательно выполняет `fromXML` и `toYAML`. | `Worker YAML-результат импорта`<br>`Worker отложенные пути YAML`<br>`Факты владельца` |
| 3 | Worker | Завершает накопитель фактов, получает локальный индекс, извлекает фрагмент файла индекса конфигурации, объединяет фрагменты в передаваемый буфер и освобождает XML. | `Worker индекс метаданных`<br>`Worker буфер данных файла индекса конфигурации` |
| 4 | Главный процесс | Объединяет локальные индексы и фрагменты, создаёт общий двоичный снимок и передаёт его worker. | `Глобальный индекс метаданных`<br>`Данные конфигурации для индекса` |
| 5 | Worker | По парам `YAML-путь`/`Путь правила` уточняет только отложенные значения, сериализует и напрямую записывает YAML и создаваемые преобразованием связанные файлы. Не читает YAML других объектов и не обходит `rules.ts` повторно. | `YAML-файл`<br>`Внешний файл проекта` |
| 6 | Worker | Формирует список записанных worker файлов и внешних файлов XML-выгрузки с целевыми путями. | `Worker список файлов результата импорта` |
| 7 | Главный процесс | Объединяет worker списки и проверяет уникальность и допустимость целевых путей. | `Список файлов результата импорта` |
| 8 | Главный процесс | Копирует внешние файлы XML-выгрузки с ограниченным параллелизмом. | `Внешний файл проекта` |
| 9 | Главный процесс | Вычисляет хэши файлов результата. | `Хэши файлов проекта` |
| 10 | Главный процесс | Формирует и последним записывает файл индекса конфигурации напрямую в итоговый путь. | `Файл индекса конфигурации` |

| Ситуация | Поведение |
|---|---|
| Непустой целевой компонент | Импорт не запускается. Допустим отсутствующий либо пустой каталог компонента. |
| Ошибка чтения XML, формирования YAML, сбора индекса или уточнения значения | Worker продолжает текущий проход для остальных заданий и возвращает все ошибки. Следующий проход, копирование внешних файлов и запись файла индекса конфигурации не начинаются. |
| Конфликт при обобщении индексов или списка файлов | Следующий этап не начинается. |
| Неразрешимый `ПутьКДанным` | Сохраняется предварительное YAML-значение и возвращается предупреждение. Предупреждение не блокирует дальнейшие шаги. |
| Аварийное завершение worker | Импорт останавливается без автоматического перезапуска и повторения заданий. Копирование внешних файлов и запись файла индекса конфигурации не выполняются. |
| Частичный результат | Успешно записанные файлы не откатываются. Файл индекса конфигурации не записывается. Перед повтором целевой компонент нужно очистить. |
| Атомарность | Worker файлы и внешние файлы пишутся напрямую. Запись всего набора не является транзакцией. |

## Чтение проекта

| Характеристика | Значение |
|---|---|
| Потребители | Синхронизация, validation, подсказка схем, переименование и поиск ссылок. |

|---|---|---|---|---:|

| Сохранение worker данных YAML | Сохраняет `Worker данные YAML` в памяти worker для последующих шагов операции. | `Worker данные YAML` | `Worker данные YAML` | ✓ |
| Извлечение локальных индексов | Обходит существующий YAML по `rules.ts`, передаёт значения в тот же накопитель типизированных фактов, что импорт, и отдельно собирает validation-зависимости и диагностики. | `Worker данные YAML`<br>`rules.ts` | `Факты владельца`<br>`Worker индекс метаданных`<br>`Worker индекс зависимостей` | ✓ |
| Обобщение индексов | Объединяет worker индексы метаданных в глобальный индекс метаданных, а worker индексы зависимостей — во временный глобальный индекс зависимостей. | `Worker индекс метаданных`<br>`Worker индекс зависимостей` | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` |  |
| Распределение индекса зависимостей | Делит глобальный индекс зависимостей между worker и передаёт каждому worker глобальный индекс метаданных и worker индекс зависимостей. | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` | `Глобальный индекс метаданных`<br>`Worker индекс зависимостей` |  |

| Момент | Данные worker | Данные координатора |
|---|---|---|
| До обобщения | `Worker данные YAML`<br>`Worker индекс метаданных`<br>`Worker индекс зависимостей` | — |
| После обобщения | `Worker данные YAML` | `Глобальный индекс метаданных`<br>`Глобальный индекс зависимостей` |
| После распределения | `Worker данные YAML`<br>`Глобальный индекс метаданных`<br>`Worker индекс зависимостей` | `Глобальный индекс зависимостей` удалён |

| Состояние реализации | Договор |
|---|---|
| Целевое | `Worker данные YAML` не покидают worker; последующие шаги запускаются командами worker. |
| Validation | Целевой договор уже выполняется: разобранный YAML не передаётся в главный процесс. |
| Синхронизация, переименование, поиск ссылок | Пока используют переходную передачу YAML и должны быть переведены на worker-команды отдельными изменениями. |

| Проход синхронизации | Действие |
|---|---|
| Первый | Worker читают и сохраняют назначенные YAML, извлекают компактные сведения для `Глобальный индекс метаданных`. |
| Второй | Одно задание получает один исходный YAML и формирует все относящиеся к нему XML. Другие YAML не читаются; межфайловые зависимости разрешаются через глобальный индекс. |

## Подготовка синхронизации конфигурации

| Характеристика | Значение |
|---|---|
| Результат | Полный либо выбранный по изменениям XML-результат из Проекта. |
| Источник идентификаторов | Файл индекса конфигурации. |
| Источник данных восстановления XML | Файл индекса конфигурации. |
| Локальная reference-выгрузка | Не используется. |

| Шаг | Описание | Входящие артефакты | Исходящие артефакты | Worker |
|---|---|---|---|---:|
| Проверка целевого каталога XML | До запуска worker проверяет, что целевой каталог отсутствует либо пуст. Существующее содержимое автоматически не удаляется. | `Корень XML-результата` | `Подтверждённый корень XML-результата` |  |
| Чтение файла индекса конфигурации | Проверяет единый двоичный файл выбранной привязки и создаёт его неизменяемое представление в общей памяти. | `Файл индекса конфигурации` | `Общий снимок файла индекса конфигурации` |  |
| Сравнение хэшей проекта с индексом конфигурации | Для синхронизации изменившихся файлов сравнивает текущие хэши с хэшами из файла индекса конфигурации. Полная синхронизация этот результат для отбора заданий не использует. | `Хэши файлов проекта`<br>`Общий снимок файла индекса конфигурации` | `Список изменений проекта` |  |
| Формирование и распределение заданий синхронизации | До чтения YAML формирует по правилам задания из найденных файлов Проекта: один исходный YAML и все создаваемые из него XML-файлы. Полная синхронизация распределяет все задания; синхронизация изменившихся файлов — только выбранные. | `Список файлов проекта`<br>`rules.ts`<br>`Список изменений проекта` (частичная синхронизация) | `Worker список заданий синхронизации` |  |
| Построение и запись XML | Преобразует назначенные YAML в metadata-модели, строит XML с использованием общего индекса метаданных и файла индекса конфигурации и пишет XML непосредственно в целевой каталог. | `Worker список заданий синхронизации`<br>`Worker данные YAML`<br>`Глобальный индекс метаданных`<br>`Общий снимок файла индекса конфигурации`<br>`rules.ts`<br>`Подтверждённый корень XML-результата` | `XML-файл`<br>`Фрагмент данных файла индекса конфигурации` | ✓ |
| Копирование внешних файлов в XML | Асинхронно копирует описанные правилами внешние файлы Проекта по их целевым XML-путям. | `Список файлов проекта`<br>`Подтверждённый корень XML-результата`<br>`rules.ts` | `Внешний файл XML-результата` |  |

| Договор | Решение |
|---|---|
| Полная синхронизация | XML-результат соответствует полному составу Проекта. Отсутствующие в Проекте объекты и файлы не попадают в результат и удаляются из нового содержимого файла индекса конфигурации. |
| Хэши полной синхронизации | Вычисляются для нового индекса, но не используются для отбора заданий. |
| Целевой каталог | Должен отсутствовать либо быть пустым. Worker пишут XML непосредственно в него. |
| Ошибка задания | Операция останавливается; частичный XML сохраняется для диагностики; файл индекса конфигурации не записывается. |
| Успешное завершение | Основной файл индекса конфигурации записывается напрямую в итоговый путь после формирования всего XML-результата. |

| № | Исполнитель | Действие | Результат |
|---:|---|---|---|

| 2 | Главный процесс | По правилам находит YAML и внешние файлы, формирует задания по одному исходному YAML и статически распределяет их между worker. | `Worker список заданий синхронизации` |
| 3 | Главный процесс | Один раз читает и полностью проверяет файл индекса конфигурации, создаёт неизменяемое представление в общей памяти. | `Общий снимок файла индекса конфигурации` |
| 4 | Worker | Читает и разбирает YAML, вычисляет хэши по прочитанным байтам, сохраняет YAML и извлекает компактные сведения о метаданных и составе Проекта. | `Worker данные YAML`<br>`Worker индекс метаданных`<br>`Хэши файлов проекта` |

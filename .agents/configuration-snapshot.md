# Снимок конфигурации

Версия спецификации: **1.3**
Статус: целевой логический договор.

## Назначение

Снимок хранит минимальные данные, которых нет в Проекте, но которые нужны для:

- восстановления поддержанного XML без reference-каталога;
- сохранения устойчивых идентификаторов;
- проверки неизменности файлов Проекта.

Спецификация описывает логические данные. Двоичный контейнер, расположение
секций, словарь строк и сжатие являются деталями реализации.

Один снимок относится ровно к одному компоненту: `cf`, `cfe/<Имя>` или другому
зарегистрированному компоненту.

## Источники данных

| Источник | Что является источником истины |
|---|---|
| XML | Идентификаторы и особое XML-представление, отсутствующее в YAML |
| YAML Проекта | Состав элементов, значения, порядок коллекций и путь файла |
| `rules.ts` и регистрации | XML-имена, обычный порядок свойств, значения по умолчанию, правила адресации и преобразования |
| Операция import/sync | Компонент и поколение снимка |
| Записанные файлы Проекта | Фактические пути и хэши содержимого |

Снимок дополняет YAML и правила: YAML хранит проектные данные и порядок
коллекций, правила — схему XML и каноническое представление, снимок —
идентификаторы и невосстановимые особенности исходного XML.

## Модель

```text
snapshot
  ├─ files
  └─ entities
       ├─ identities
       └─ xmlRepresentation
```

`logicalAddress` является первичным смысловым ключом. Все свойства элемента,
его идентификаторы и путь файла хранятся совместно в одной записи `entity`.

## `snapshot`

| Поле | Обязательность | Источник |
|---|---:|---|
| `specificationVersion` | да | Константа писателя: `1.3` |
| `indexGeneration` | да | `1` при import; предыдущее значение `+ 1` после успешного sync |
| `componentPath` | да | Адрес компонента, выбранный discovery/import |

## `file`

Одна запись соответствует одному фактически записанному файлу компонента.

| Поле | Обязательность | Источник |
|---|---:|---|
| `projectPath` | да | Маршрут структуры Проекта; нормализованный путь относительно корня компонента |
| `contentHash` | да | Хэш фактических байтов файла после завершения записи |

Путь назначается каждой записи в момент обработки конкретного XML-задания или
YAML-файла.

## `entity`

Одна запись соответствует одному элементу по `logicalAddress` и создаётся,
только если содержит хотя бы один идентификатор, `omittedChildren` или поле
особого XML-представления. `logicalAddress` и `sourceProjectPath` сами по себе
не являются основанием для записи. Состав элементов Проекта определяется по
актуальному YAML и `rules.ts`.

| Поле | Обязательность | Источник |
|---|---:|---|
| `logicalAddress` | да | Единый builder адресов; сегменты и способ адресации задают `rules.ts` и регистрации |
| `sourceProjectPath` | да | `targetProjectPath` XML-задания при import либо путь разбираемого YAML-файла при sync |
| `uuid` | нет | XML `_uuid` либо XML `_id`, когда правило объявляет `identityKind: "uuid"` |
| `xmlId` | нет | XML `_id`, если правило не объявляет его UUID |
| `xmlName` | нет | XML `_name`, только если значение нельзя восстановить из адреса и правил; пустая строка допустима |
| `omittedChildren` | нет | Последовательность дочерних объектов из XML, когда родительский YAML не содержит этот список |
| `extended` | нет | Признак расширенного элемента, извлечённый зарегистрированным правилом расширения |
| `xsiNil` | нет | XML `xsi:nil`, только если YAML и правило не представляют различие |
| `explicitEmpty` | нет | Явное пустое XML-значение, неотличимое в YAML от отсутствующего или значения по умолчанию |
| `xsiType` | нет | XML `xsi:type`, только если тип не задаётся значением YAML или правилом |
| `xmlText` | нет | Текст XML, если одно YAML-значение допускает несколько XML-представлений |
| `xmlPrefix` | нет | Namespace-префикс исходного XML, если правило не может выбрать его однозначно |

Пара `logicalAddress + sourceProjectPath` должна быть непротиворечивой:
один адрес принадлежит ровно одному файлу. Повторное наблюдение одинакового
значения допустимо, несовпадающие значения являются ошибкой. После удаления
последнего содержательного поля удаляется вся запись `entity`.

### Порядок дочерних объектов

`omittedChildren` нужен только тогда, когда дочерние объекты хранятся отдельными
файлами или каталогами, а родительский YAML не содержит их списка. По структуре
Проекта можно восстановить состав, но нельзя восстановить исходную
последовательность XML.

| Случай | Что находится вне родительского YAML | Что сохраняет `omittedChildren` |
|---|---|---|
| `Configuration.ChildObjects` | Объекты конфигурации разложены по каталогам видов метаданных | Последовательность пар «XML-вид + имя», включая чередование разных видов |
| `ChildFormNames` | Формы находятся в каталоге `Формы` | Последовательность имён XML-тегов `Form` |
| `ChildTemplateNames` | Макеты находятся в каталоге `Макеты` | Последовательность имён XML-тегов `Template` |
| `ChildFileItemNames` | Таблицы измерений куба внешнего источника данных находятся в отдельных файлах | Последовательность имён XML-тегов `DimensionTable` |

Для обычных XML-свойств источником порядка является `rules.ts`, а для
коллекций, записанных в YAML, — последовательность YAML.

### XML-представление

XML-имена свойств определяются `rules.ts`. Невосстановимое имя самого элемента
хранится в `xmlName`, включая пустое имя.

Различие между отсутствующим, пустым и специальным XML-значением представляют
конкретные поля `explicitEmpty`, `xsiNil`, `xsiType`, `xmlText` и `xmlPrefix`.
Каждое поле создаётся только зарегистрированным правилом, которое умеет
проверить его совместимость с актуальным YAML-значением.

## Формирование снимка

### Import XML

1. XML-задание получает точный `targetProjectPath`.
2. Оркестрация разбирает XML по `rules.ts` и формирует `logicalAddress`.
3. В `entity` добавляются только невосстановимые XML-факты и идентификаторы.
4. Хэши вычисляются по фактическим байтам готовых файлов.
5. Снимок публикуется только после успешного завершения всей операции.

### Sync YAML → XML

1. Хэши определяют изменённые файлы.
2. Их YAML повторно разбирается по текущим правилам.
3. Записи `entity` изменённых файлов заменяются целиком.
4. Сохранённое XML-представление применяется только если совместимо с текущим
   YAML-значением и правилом; иначе используется каноническое представление.
5. После успешного sync обновляются хэши и `indexGeneration`.

## Потребители

| Данные | Потребитель |
|---|---|
| `snapshot`, `file` | Проверка применимости снимка и поиск изменённых файлов |
| `entity.identities` | fromYAML/toXML, формы, InternalInfo и профиль расширения |
| `entity.xmlRepresentation` | fromYAML/toXML только через правило соответствующего свойства |
| `entity.omittedChildren` | Восстановление пропущенной последовательности дочерних объектов |

## Требования к двоичному представлению

- Один опубликованный файл на компонент.
- Строгая версия и проверка целостности всего файла.
- Чтение задаёт явный смысловой порядок независимо от порядка физических
  записей.
- Читатель проверяет точную совместимость с версией 1.3.
- Запись выполняется атомарно: частичный файл не считается снимком.

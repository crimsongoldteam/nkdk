# XML-аномалии

Поддерживаются три общих тега XML-аномалий: `!xml/raw`, `!xml/invalid` и
`!xml/important`. Прежние частные теги `!xml/present`, `!xml/absent`,
`!xml/type`, `!xml/value`, `!xml/reference`, `!xml/language`, `!xml/order` и
`!xml/duplicate` больше не читаются.

Отдельно поддерживается скалярный тег формы XML `!xml/string`. Он не является
XML-аномалией: значение остаётся обычной строкой и проходит ту же смысловую
проверку. Тег разрешён только типам, которые явно зарегистрировали такую
форму; сейчас это `DcsLocalStringType`, где обычный YAML строит
`v8:LocalStringType`, а `!xml/string` — `xs:string`. Тег не подавляет
диагностику и не участвует в назначении proof или raw.

`!xml/name` — скалярный тег формы XML для нестандартного технического имени
известного singleton элемента формы. Он записывается только как поле `Имя`
объекта, чей тип явно зарегистрировал поддержку явного XML-имени. Обычное
каноническое имя вычисляется из владельца и rules и в YAML не попадает. Если
нестандартное имя выбирает известный вариант суффиксов, тот же вариант
автоматически применяется к вложенным singleton; собственные поля `Имя` у них
не создаются. Поле `Имя` без `!xml/name`, тег у незарегистрированного типа и
нескалярное значение запрещены. Тег не является XML-аномалией, не содержит
`$xml`, не подавляет диагностику и не меняет смысловую модель элемента.

`!xml/standard-attributes` — пустой тег формы XML для точного типа
`StandardAttributeDescriptions`. Он означает, что в исходном XML присутствовал
полностью стандартный блок, который нужно восстановить по rules. Тег не имеет
payload, не является XML-аномалией, не подавляет диагностику и не содержит
`$xml`.

`!xml/raw` сохраняет XML-форму, которую нельзя однозначно получить из
смыслового YAML. Он ставится только на значение и всегда содержит явное
`$xml`; распознанное смысловое значение при наличии хранится отдельно в
`$значение`. Raw без `$xml`, raw на ключе и raw на корне объекта метаданных
запрещены.

`!xml/invalid` сохраняет обычное обратимое YAML-значение, которое нарушает
смысловое правило. `!xml/important` имеет тот же технический договор, но
применяется только для отдельно зарегистрированных классов ценных данных.
Сейчас таких регистраций нет. Оба тега исключают уже принятую ошибку из
повторной диагностики, но их значение остаётся доступным индексам и экспорту.

Повторы ключей именованной коллекции сохраняются без потерь: первое обычное
вхождение остаётся без тега, первый дубль получает `!xml/invalid`, следующие —
`!xml/invalid/2`, `!xml/invalid/3` и далее. Если первое вхождение само
недопустимо, оно также получает `!xml/invalid`, а номера продолжают обозначать
физические вхождения.

Неизвестный XML-фрагмент адресуется полным путём относительно текущего объекта,
например `Properties\Future`, а raw находится в значении этого служебного
YAML-свойства. Распознанная оболочка объекта не скрывается: raw поднимается
только до минимальной устойчивой границы.

Если один YAML формирует несколько XML-документов, неизвестный фрагмент
дополнительного документа получает краткий селектор, например
`@Form\Future`. Имя берётся из топологии без `Ext/` и `.xml`; основной документ
префикса не имеет, а одиночный `@` адресует его корень. Неизвестные атрибуты
хранятся как `_имя` внутри `$xml` самого элемента; отдельный `#attributes`
запрещён.

Пробельное оформление между дочерними XML-тегами не входит в нормализованное
дерево и не создаёт raw. Текст листового элемента сохраняется точно, включая
значение только из пробелов. Объединённый порядок известных и неизвестных детей
при необходимости хранится как `#order` внутри `$xml` родителя; отдельный путь
вида `Properties\#order` запрещён.

Назначение тегов при XML-импорте выполняется системно:

1. rules.ts импортируют смысловые данные, а потоковый разбор сохраняет только
   структурные хэши корней XML;
2. один контрольный экспорт задания сначала сравнивается по таким же хэшам;
   только несовпавшее задание повторно читается с полным аудитом владения,
   который создаёт минимальные raw; результат этого подробного импорта —
   смысловой YAML, аннотации и аудит — целиком заменяет черновой результат,
   иначе неизвестный XML мог бы попасть в порядок, но потерять собственное raw-значение;
3. структурированная проверка назначает invalid/important по точным путям;
4. полная и частичная синхронизация сначала выполняют обычный YAML → XML, затем
   применяют явные `$xml`-поправки.

Аудит Rules различает два случая, которые не создают смыслового YAML. Состояние
`semanticallyElided` означает, что присутствующее XML-поддерево полностью
прочитано известными Rules, преобразовано в пустой объект или массив и поэтому
канонически исключено из YAML. Исключение применяется атомарно ко всему
поддереву: неизвестный узел, атрибут или частично прочитанная ветвь запрещают
это состояние и остаются кандидатами на минимальный raw.

Состояние `structurallyClaimed` означает владение XML-only свойством с
`fromXML: false`: граница хранится один раз на корне, а потомки только ссылаются
на неё как на структурно покрытые. Такое владение не утверждает смысловую
эквивалентность и проверяется контрольным экспортом. Поэтому механизм нельзя
использовать для неизвестных или лишь частично распознанных поддеревьев.

Локальный raw XML-only свойства получает публичный путь через логическое имя
Rules, например `@Form\ОтборСтрок`. При обратном экспорте последний сегмент
разрешается через `PropertyRule` в XML-имя (`RowFilter`), а положение среди
соседей — через `xmlOrder`. Публичный YAML-путь не должен повторять внутреннее
XML-имя и не требует служебного `#order`, если канонический порядок известен
Rules.

Подробный повторный импорт не переносит все предварительные raw-кандидаты.
Пути XML-узлов, уже заявленных Rules или целями proof-аудита, заново доказываются
контрольным экспортом. Из подробного результата напрямую сохраняются только
публичные пути действительно неизвестных узлов (`Properties\Future`, `@Form` и
аналогичные). Имя `*:Item` само по себе не доказывает принадлежность коллекции:
предварительный raw такого узла удаляется только тогда, когда обычный экспорт
уже восстанавливает ту же XML-структуру. Действительно неизвестный `<Item>`
остаётся самостоятельным raw-свойством.

Родительская оболочка коллекции не поглощает различие принадлежащего ей
дочернего свойства: дочерние границы сравниваются самостоятельно. Для
common-типов, в которых повторные одноимённые XML-узлы образуют одно смысловое
значение, это объявляется общим признаком `repeatedXMLNodes`, а не частным
условием импортёра.

Точный контрольный экспорт удаляет предварительные raw-кандидаты и оставляет
смысловую проекцию, фактически использованную Rules. Скрытое свойство Rules без
`yamlKey` связывается с XML по `propertyKey`, но без тега в публичном YAML не
разрешено. Вложенный `#order` остаётся на своём XML-родителе и не переносится на
корень документа.

После проверки каждого файла подробная карта исходного XML немедленно
освобождается. Полный импорт и штатная проверка round-trip по умолчанию
используют не более двух рабочих линий: это ограничивает общий пик памяти, не
собирая данные всей конфигурации в одной куче.

# Архитектура тестов

## Цель

Сохранять минимальный набор тестов, достаточный для защиты наблюдаемых договоров.
Количество тестов само по себе не является целью; каждый тест должен иметь
уникальную причину существования.

## Выбор проверки

1. Опиши новый или изменяемый наблюдаемый договор.
2. Найди существующие проверки импортируемого символа, соседнего модуля и
   операции соответствующего уровня.
3. Сначала добавь случай в существующий `it.each`, затем рассмотри усиление
   существующего теста. Новый тест создавай только для самостоятельного договора.
4. Не размножай перестановки одного класса эквивалентности. Проверяй
   представителя класса и содержательные границы.
5. Размещай тест на самом узком стабильном уровне. Интеграционный тест нужен
   только для поведения между слоями.

## Декларации и Rust: четыре уровня проверок

Проверяем общее поведение один раз на соответствующем уровне, а у каждого
потребителя — правильность подключения. Новое свойство обычно добавляет данные
для существующего запускателя; новый механизм или особое сочетание поведения
добавляет проверку. Число функций тестов не является показателем качества:
объединение одинаковых запусков в таблицу само по себе не уменьшает работу.

| Уровень | Что защищает | Где размещать |
|---|---|---|
| Common и общие механизмы | Преобразования, валидацию, отсутствие, пустоту, значения по умолчанию, вывод и восстановление аномалий | Существующие матрицы `rust/crates/compiled-rules/tests/`; низкоуровневые договоры — рядом с `conversion-core` и `rule-compiler` |
| Декларация объекта | XML-пути, YAML-имена, параметры common, ограничения и совместную работу полей | Данные XML/YAML для общего запускателя в `tests/migration/`; рабочие проверки объекта — в существующих матрицах compiled-rules |
| Оркестратор | Выбор декларации, передачу контекста и индексов, вложенные объекты, внешние файлы, сбор аномалий и маршруты результатов | Рядом с соответствующей операцией; проверки приложения — `rust/apps/nkdk/tests/` |
| Проект целиком | Работу настоящих оркестраторов и деклараций вместе | Существующий e2e-корпус и его запускатель |

Это распределение ответственности, а не требование создать четыре новых
каталога или массово переместить существующие тесты. Временный запускатель
кандидатов сохраняет изоляцию от рабочего каталога; его перенос после приёмки
не должен терять защищаемые договоры.

### Пример: булево свойство документа

- В матрице boolean проверяем true, false, отсутствие, пустоту и неправильное
  значение с аномалией. Общие механизмы не проверяются заново у каждого поля.
- В примере документа задаём исходный XML и независимо проверенный YAML.
  Проверяем оба направления: неправильный путь, имя или default конкретного
  свойства должны обнаруживаться этой проверкой. Один пример может защищать
  несколько свойств; для непокрытого различия добавляем дополнительный случай.
- Оркестратор проверяем на небольших проверочных декларациях: выбрана нужная
  декларация, переданы зависимости, обработаны файлы и собраны аномалии.
  Boolean-матрица здесь не повторяется; имитировать сам проверяемый маршрут нельзя.
- E2E проверяет тот же путь на настоящем проекте со всеми частями вместе.

При добавлении второго boolean-поля обычно дополняем пример документа и
ожидаемый результат. Если поле взаимодействует с другим полем, индексом или
особым правилом присутствия, добавляем случай этого взаимодействия.

### Независимость ожиданий и контроль роста

- Декларация может определять выбор общих проверок, но не должна быть
  единственным источником ожидаемого результата для проверки самой себя.
  Эталоны берём из неизменных исходных фикстур, старых проверенных ожиданий
  или явно согласованного поведения. Ошибочный путь нельзя подтвердить его
  повторным чтением из той же декларации.
- Отдельно проверяем XML → ожидаемый YAML и YAML → ожидаемый XML. Round-trip
  дополняет их: согласованные ошибки двух направлений могут скрыть неверный YAML.
- Проверяем содержательные границы и взаимодействия, а не полное произведение
  всех параметров у всех объектов. Непокрытые различия нельзя скрывать под
  общим профилем; совпадение профилей должно учитывать параметры и контекст.
- Перед добавлением случая указываем, какую ещё не защищённую ошибку он ловит.
  Сначала расширяем существующую матрицу. Регрессию сохраняем как новый пример
  в ней, если ошибка не требует самостоятельного сценария.
- При переносе ведём соответствие «старый сценарий → новая проверка → сохранённые
  особенности». Объединение или удаление требует подтверждённой оставшейся защиты;
  сходство кода и отчёт jscpd не доказывают одинакового поведения.
- Не вводим жёсткий предел числа тестов. Контролируем уникальность защиты,
  количество реально выполняемых случаев, время и нестабильность запусков.

## Изоляция unit-тестов

Обычный `*.test.ts` является unit-тестом и выполняется полностью в памяти. Ему
прямо запрещены сеть, базы данных, файловая система, дочерние процессы и
настоящие worker; внешние зависимости заменяются управляемыми моками, фейками
или нейтральными портами.

Если проверяемый договор состоит именно во взаимодействии с реальным файловым,
сетевым, database-, process- или worker-адаптером, тест получает суффикс
`*.integration.test.ts`. Перенос в integration не используется для обхода
лимита: unit- и integration-test case обязаны укладываться в 50 мс.

## Процесс изменения

1. Получи падающую проверку нового договора.
2. Реализуй минимальное production-изменение и получи зелёный целевой тест.
3. Перед закрытием issue выполни из корня полную проверку:

   ```bash
   pnpm type-check
   pnpm test
   pnpm test:architecture
   ```
7. После каждого законченного слоя и перед завершением реализации выполни
   проверку новых дублей с подходящим базовым коммитом:

   ```bash
   pnpm check:duplicates -- --base <commit>
   ```

   Поддерживаемые файлы и исключения определены в `.jscpd.json`.

   `pnpm test` рекурсивно запускает тесты во всех пакетах `packages/*`.

   `pnpm test:architecture` обязателен после изменения импортов, структуры
   каталогов, `package.json`, архитектурных правил или baseline. Команда
   остаётся отдельной от `pnpm test` и предназначена для pre-push/CI: при
   изменённых исходниках она отключает кэш, чтобы не пропустить новый файл.

   После изменения `.dependency-cruiser.mjs` или файлов
   `tools/dependency-cruiser` дополнительно запусти самопроверку правил:

   ```bash
   pnpm test:architecture:rules
   ```

4. После завершения разработки проверь с помощью установленного в проекте
   `jscpd`, что относительно базовой ревизии не появились новые дубли.
   Существующие ранее дубли сами по себе не блокируют закрытие issue.

## Реорганизация тестов

Не удаляй автоматически round-trip, тесты по существующим XML/YAML-фикстурам,
snapshot-, архитектурные и связанные с issue регрессионные тесты.

## Итог задачи

Перечисли расширенные, добавленные, объединённые и удалённые тесты. Для каждого
нового теста назови уникальный договор, для удаления — оставшуюся защиту.

## Профиль длительности

Разовая длительность отдельного теста не является проверкой качества: общий
холодный старт может быть приписан случайному тесту. Для решений об оптимизации
используй три последовательных прогона:

```bash
pnpm test:profile -- --output reports/test-profile/current.json
```

Сравнивай медиану трёх прогонов. Максимум используй для поиска нестабильности,
но не как единственное основание для удаления теста или падения проверки.

### Проверки сгенерированного каталога Rust

У `nkdk-compiled-rules` проверки располагаются в `tests/*.rs`, а не внутри
сгенерированного `src/lib.rs`. Поэтому `lib.test = false` отключает только
пустую внутреннюю тестовую программу; интеграционные тесты и doctest сохраняются.
Новые проверки деклараций добавляются в соответствующую матрицу в `tests/`.

Для совместной проверки владельцев и файловых ресурсов используется один
`cargo test --workspace --test path_lexicons --test resources`. Набор пакетов
совпадает с полным прогоном: адресный запуск не меняет разрешение зависимостей
и не требует переключать сборку каталога между отдельными пакетами.

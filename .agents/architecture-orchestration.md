# Архитектура слоя `orchestration`

Документ фиксирует ключевые инварианты слоя `packages/core/metadata/orchestration/`. **Перед изменениями в этом слое — прочитать и при необходимости обновить.**

## Универсальность слоя

`orchestration` — универсальный слой правил и преобразований. Он не должен напрямую знать о прикладных объектах и формах: внутри слоя недопустимы прямые импорты из `~/metadata/appliedObjects/*` и `~/metadata/forms/*`, если они привязывают оркестратор к конкретному виду метаданных.

Конкретные объекты регистрируют своё поведение снаружи: правило, импорт модели, шаблон пути, парные файлы и внешние синхронизации. Оркестратор видит только зарегистрированные обработчики с общими контрактами XML/YAML/JSON Schema/validation.

Если старый публичный вход временно требует совместимости с конкретными объектами, эта конкретика должна жить в тонком переходном модуле вне универсального ядра. Новый API проектируется так, чтобы не требовать `as any` / `as unknown`; неизбежные приведения допустимы только в локальных переходниках с понятным именем и тестом.

Автоматические проверки границ покрывают универсальное ядро orchestration: при изменении общих модулей не добавляй прямые импорты конкретных appliedObjects/forms и не расширяй связанность универсального слоя.

## Регистрация типов

Каждый property-тип регистрируется через одну из двух фабрик:

- **`registerMetadataItemRule({ propertyType, itemRule })`** — регистрирует тип как полноценный объект (`MetadataItemRule`). Автоматически вешает обработчики `importFromXML`/`exportToXML`/`importFromYAML`/`exportToYAML` через единый реестр.
- **`registerMetadataItemCollectionRule({ propertyType, itemRule, xmlElement, keyField, yamlAsArray? })`** — регистрирует тип как коллекцию таких объектов. Автоматически вешает те же обработчики плюс `exportToJSONSchema`.

Сами обработчики хранятся в едином реестре `registerTypeRule(type, role, value)` (см. `orchestration/formElement/factory.ts`). По типу можно достать как функцию-обработчик, так и произвольное значение.

Тип property должен быть зарегистрирован в трёх местах TypeScript:
- `orchestration/property/registry.ts` — `PropertyTypeRegistry` (для `BasePropertyRule.type`),
- `orchestration/metadataItem/registry.ts` — `MetadataItemTypeRegistry` (для `MetadataItemRule.itemType`, только для item-типов),
- `orchestration/property/types.ts` — union `PropertyRule` (если тип имеет специфические поля сверх `BasePropertyRule`).

## Маркер `XMLRoot`

Свойство-маркер с типом `"XMLRoot"`, помеченное `forReferenceOnly: true`, описывает корневой XML-тег item-rule и его атрибуты:

```ts
xmlRoot: {
  type: "XMLRoot",
  container: "Catalog",        // или "PredefinedData", "AdditionalIndexes" и т.п.
  rootAttributes: { _xmlns: "...", _version: "2.20", ... },
  forReferenceOnly: true,
  isFileRoot?: true,           // см. ниже
}
```

`metadataItem/fromXML.ts`/`toXML.ts` ищут это свойство в `rule.properties` и используют его при импорте/экспорте.

Поле `isFileRoot?: true` различает два режима:

- **без `isFileRoot`** — корневой тег XML = `<MetaDataObject>`, `container` — внутренний тег (`<Catalog>`, `<DocumentNumerator>`); используется для прикладных объектов 1С.
- **`isFileRoot: true`** — корневой тег XML = `container` напрямую (`<PredefinedData>`, `<AdditionalIndexes>`); используется для внешних файлов вроде `Ext/Predefined.xml`.

## Свойства с `filePath`

Свойство item-rule с заданным `filePath: string` означает, что значение хранится во внешнем XML-файле (например, `Ext/Predefined.xml`). Тип такого свойства должен быть зарегистрирован как `MetadataItemRule` через `registerMetadataItemRule` и иметь маркер `XMLRoot` с `isFileRoot: true`.

Оркестраторы `appliedObject/{convertFromXML,syncToXML}.ts` обрабатывают `filePath`-свойства как обычные item-типы через `importPropertyFromXML`/`exportPropertyToXML`. Под капотом сериализатор сам надевает обёртку корневого тега и xmlns-атрибутов.

При экспорте `syncToXML.ts` дополнительно читает эталонный внешний файл (`referenceDir/<filePath>`), импортирует его как модель и передаёт в `exportPropertyToXML` через `referenceMetadata`. Это:
- сохраняет точный порядок полей по эталону,
- подмешивает атрибуты, помеченные `forReferenceOnly` (например, id-атрибут).

## Свойства с типом `ChildFormNames`

Свойство правила с типом `ChildFormNames` совмещает две роли:

1. **Сериализация в основной XML.** Даёт тег `<ChildObjects><Form>…</Form></ChildObjects>` в XML объекта. Реализация — обработчик `exportToXML`, зарегистрированный на типе.

2. **Синхронизация файлов форм.** Обработчики `syncExternalToXML`/`syncExternalFromXML`, зарегистрированные на типе, сканируют папку `nkdkDir/<folderName>` (на nkdk-стороне) или `xmlDir/<name>/Forms/` (на XML-стороне) и для каждой формы делегируют работу `syncFormToXML` / `convertFormFromXML`. Формы внутри одного объекта обрабатываются **последовательно**.

Сигнатура `SyncExternalToXMLFunction` / `SyncExternalFromXMLFunction` включает поля `name: string` (имя объекта) и `referenceDir?: string` (родитель эталонной директории объекта, для round-trip). Эти поля заполняет `appliedObject/syncToXML.ts` / `appliedObject/convertFromXML.ts`. Хуки `Module`/`Help`/`Template` их игнорируют.

## Флаг `yamlInline`

Опциональный флаг свойства `yamlInline?: true` на `BasePropertyRule`. Применяется только в YAML и JSON-схеме (модель и XML — без изменений).

Семантика: если у `MetadataItemRule` ровно одно содержательное свойство (без `forReferenceOnly`) с `yamlInline: true`, сериализация в YAML/JSON-схему использует значение этого свойства напрямую, без обёртки. Импорт симметричен. При наличии более одного `yamlInline`-свойства оркестратор кидает ошибку.

Реализация — в утилите `metadataItem/yamlInline.ts::findInlineProperty(rule)`, переиспользуется из `toYAML.ts`/`fromYAML.ts`/`toJSONSchema.ts`.

Типичный сценарий — внешний файл-обёртка (например, `Predefined`), где маркер `xmlRoot` несёт XML-обёртку, а единственное содержательное свойство `items: PredefinedItemCollection` помечено `yamlInline: true`, чтобы YAML каталога не получал лишнего уровня `items:`.

## Поток данных

**`convertAppliedObjectFromXML` (`appliedObject/convertFromXML.ts`):**
1. Читает основной XML объекта (`<inputDir>/<name>.xml`), парсит, передаёт в `importMetadataItemFromXML` с правилом объекта.
2. Для каждого свойства правила с `filePath`: читает внешний файл, передаёт распарсенный XML в `importPropertyFromXML(propRule)`. Маркер `XMLRoot` (с `isFileRoot: true`) сам снимает обёртку корневого тега.
3. Вызывает обработчики `syncExternalFromXML` для свойств с собственной логикой синхронизации (`Module`, `Help`, `Template`).
4. Записывает `Свойства.yaml` через `exportMetadataItemToYAML`.

**`syncAppliedObjectToXML` (`appliedObject/syncToXML.ts`):**
1. Читает `Свойства.yaml`, импортирует через `importMetadataItemFromYAML`.
2. Через `exportMetadataItemToXML` с правилом объекта собирает основной XML; `referenceData` подгружается из эталонного XML.
3. Для свойств с `filePath`: импортирует эталон внешнего файла как `referenceValue`, экспортирует модель через `exportPropertyToXML` с `referenceMetadata: referenceValue`. Записывает результат во внешний файл.
4. Вызывает `syncExternalToXML` для `Module`/`Help`/`Template`.

## Отложенные доработки

### Порядок элементов `CommandInterface`

`CommandInterfaceItem.index` хранит явное значение XML/YAML-поля `Index` / `Индекс` и не должен вычисляться из позиции элемента в массиве. При экспорте `Index` пишется только если поле задано в модели.

Текущая временная норма для round-trip: порядок самих элементов `NavigationPanel` и `CommandBar` берётся из физического порядка `<Item>` в XML. `fromXML` не должен сортировать элементы по `Index`; `toXML` пишет элементы в порядке массива модели.

Это временная мера, а не окончательная доменная семантика `Index`. В референсных XML встречаются группы, где физический порядок `<Item>` не совпадает с возрастанием `Index`, поэтому нельзя без дополнительного исследования сортировать элементы только по `Index`, `CommandGroup` или позиции внутри группы. Будущая доработка должна зафиксировать правило восстановления порядка по нескольким каталогам `/Users/nikita/git/round-trip-source/` и только после этого менять сортировку `fromXML`/`toXML`.

## Миграции структурных изменений

YAML остаётся целевым состоянием проекта и не хранит `_uuid`. Миграции фиксируют решения, которые нельзя безопасно вывести из сравнения YAML и эталонного XML: было ли сочетание «удалено + добавлено» на одном уровне переименованием, удалением или добавлением.

Миграции применяются к виртуальному состоянию XML сверху вниз и последовательно. Виртуальное состояние хранит для каждого текущего пути `referencePath`: путь в эталонном XML, откуда нужно читать `_uuid` и другие `forReferenceOnly`-данные. Экспорт пишет файлы по целевым YAML-путям, но reference-данные читает через `referencePath`.

Миграции хранятся в YAML-проекте в каталоге `Миграции/`. Один файл — одна миграция, идентификатор миграции — имя файла. Формат имени: `YYYY-MM-DD-HHmmss.yaml`, дата-время в UTC. При создании нового файла используется `max(nowUtc, latestValidMigrationTimestamp + 1s)`: если текущий момент не больше последней существующей миграции, имя сдвигается на секунду вперёд. Файлы в `Миграции/` с неправильным именем или не `.yaml` игнорируются молча.

Файл миграции — плоский YAML-словарь без служебных полей и комментариев:

```yaml
"Справочник.Товары": "Номенклатура"
"Справочник.Номенклатура.ТабличнаяЧасть.Состав": "Комплектующие"
"Справочник.Номенклатура.ТабличнаяЧасть.Комплектующие.Реквизит.Артикул": "НоменклатурныйАртикул"
"Справочник.Номенклатура.Реквизит.СтароеПоле": Удалить
"Справочник.Номенклатура.Реквизит.НовоеПоле": Добавить
```

Ключ — полный путь элемента. Значение:

- строка, отличная от `Удалить` и `Добавить`, означает переименование в новое локальное имя в том же владельце и той же коллекции;
- `Удалить` подтверждает удаление;
- `Добавить` подтверждает добавление;
- пустое значение — ошибка формата.

Если в миграции есть переименование родителя, дочерние строки пишутся через новое имя родителя. Например, после `"Справочник.Товары": "Номенклатура"` реквизит внутри нового объекта записывается как `"Справочник.Номенклатура.Реквизит.Артикул": "НовыйАртикул"`. Применение миграций поэтому строит карту соответствия сверху вниз, а не трактует каждую строку изолированно.

Цепочка файлов миграций применяется от старого состояния XML к новому состоянию YAML. Каждая следующая миграция адресует элементы в состоянии, полученном после предыдущих миграций. Если объект был переименован в одной миграции, следующая миграция пишет пути его дочерних элементов уже через актуальное имя объекта.

Порядок строк внутри одного файла миграции значим: строки применяются в порядке YAML-словаря. Отдельной проверки дубликатов ключей нет, используется поведение YAML-парсера: остаётся последнее значение. Если нужно несколько действий с одним элементом, каждая следующая строка должна использовать путь, актуальный после предыдущей строки.

В первой версии миграции покрывают только пути с именами без точек:

- верхнеуровневые объекты из `TopLevelMetadataItemRules`: `Справочник`, `Документ`, `Нумератор`, `Последовательность`;
- дочерние owning-коллекции с `uuid` и `keyField: "name"`: `Реквизит`, `ТабличнаяЧасть`, `Измерение`;
- реквизиты табличных частей с полным путём через сегмент коллекции: `Справочник.Товары.ТабличнаяЧасть.Состав.Реквизит.Артикул`.

`Перечисление`, `Команда`, `Форма`, `Макет` и внешние файлы с `filePath` не входят в первую версию миграций. Для `Нумератор` поддерживается только верхнеуровневое переименование.

Неподдерживаемый сегмент пути — ошибка формата. Если путь синтаксически поддержан, но владелец не может иметь такую коллекцию, это ошибка. Например, `Нумератор.X.Реквизит.Y` невалиден, потому что `Нумератор` в первой версии не имеет дочерних коллекций миграций.

Семантика операций:

- `rename`: ключ должен существовать в текущем промежуточном состоянии, значение — новое локальное имя без точки. Целевой путь строится заменой последнего сегмента ключа. Переименование в то же имя или в уже существующий путь — ошибка. При переименовании переносится весь `referenceData`, не только `_uuid`.
- `Удалить`: ключ должен существовать в текущем промежуточном состоянии. Операция удаляет путь и всех потомков из виртуального состояния.
- `Добавить`: ключа не должно быть в текущем промежуточном состоянии. Операция создаёт новый элемент без `referencePath`; при экспорте он получает новый `_uuid`.

Все операции валидируются относительно текущего промежуточного состояния. Если на этом этапе путь отсутствует или, наоборот, уже существует, это ошибка. Предупреждений для неприменимых строк миграции нет.

Сочетание `Удалить` + `Добавить` одного пути допустимо как пересоздание с новым `_uuid`, если порядок строк делает промежуточное состояние корректным. Чтобы заменить существующий целевой элемент старым `_uuid`, нужно сначала удалить текущий целевой путь, затем переименовать старый элемент в этот путь.

Сравнение выполняется сверху вниз. Сначала сопоставляются верхнеуровневые объекты. Дочерние коллекции проверяются только для пары владельцев, которые совпали по имени или были сопоставлены миграцией. Если объект новый, его дочерние элементы не проверяются как конфликтные: они считаются новым состоянием.

Один уровень сравнения — это один владелец и один тип коллекции. Например, реквизиты справочника сравниваются отдельно от его табличных частей; реквизиты табличной части сравниваются отдельно от реквизитов объекта.

Если на уровне есть только удаления или только добавления, миграция не нужна: `sync` применяет целевое YAML-состояние напрямую. Если на уровне одновременно есть удаления и добавления, это конфликт намерения. После применения всех неприменённых миграций `sync` проверяет остаточные конфликты; остаточный `deleted + added` на одном уровне — ошибка с подсказкой `nkdk generate-migration <yaml-dir> <xml-dir>`.

`generate-migration <yaml-dir> <xml-dir>` сравнивает XML как прошлое состояние и YAML как целевое состояние. Команда сначала виртуально применяет уже существующие неприменённые миграции из `Миграции/`; если в них ошибка, генерация падает. Если каталога `Миграции/` нет, список миграций считается пустым, а каталог создаётся только при записи нового файла. Затем команда идёт сверху вниз, интерактивно разбирает только конфликтные уровни и пишет один файл миграции только после полного завершения сессии. Если пользователь прерывает сессию, файл не создаётся.

В интерактивном режиме генератор использует `@inquirer/prompts` и выбор стрелками. Для каждого удалённого элемента на конфликтном уровне слева показывается полный путь, справа предлагаются короткие имена добавленных элементов и вариант `Удалить`. Выбранная добавленная цель убирается из списка. Все добавленные элементы, оставшиеся после разбора удалённых, записываются как `Добавить`. Автоматического угадывания переименований нет, даже для случая «одно удаление + одно добавление». Финального подтверждения нет: после последнего выбора файл сразу записывается. Если конфликтов нет, файл не создаётся, код завершения `0`. В режиме `--dry-run` при конфликтах код `1`, без конфликтов код `0`.

Ручные команды первой версии создают по одному новому файлу миграции без проверки XML/YAML:

```bash
nkdk rename <yaml-dir> <path> <new-name>
nkdk delete <yaml-dir> <path>
```

`rename` пишет строку `"path": "new-name"`. `delete` пишет строку `"path": Удалить`. Команды «тупые»: не читают XML, не читают существующие миграции, не обновляют YAML и ссылки. `<yaml-dir>` должен существовать; каталог `Миграции/` создаётся только при записи файла. `rename` проверяет, что путь не пустой, новое имя не пустое, новое имя без точки и отличается от последнего сегмента пути. `delete` проверяет только непустой путь. Успешная команда выводит только путь созданного файла.

Каждый XML-каталог хранит своё состояние применённых миграций в корневом файле `.nakidka-migrations.yaml` внутри `outputDir`:

```yaml
applied:
  - 2026-05-05-143000.yaml
```

Хранятся только имена файлов, без хэша содержимого и без признака успеха. В `.nakidka-migrations.yaml` допустимы только корректные имена миграций; дубликаты в `applied` — ошибка формата. Если `.nakidka-migrations.yaml` отсутствует, список применённых миграций пустой. Если файл повреждён или содержит имя неправильного формата, это ошибка. Если применённая миграция исчезла из YAML-проекта, `sync` молчит.

Миграции из `applied` считаются уже отражёнными в XML: `sync` не читает и не валидирует их. Все миграции из YAML-проекта, которых нет в `applied`, применяются автоматически по имени файла в порядке сортировки. `.nakidka-migrations.yaml` обновляется только после полного успешного экспорта и очистки; если экспорт или очистка упали, новые миграции не отмечаются применёнными. После успешного `sync` файл состояния создаётся всегда, даже если `applied: []`.

`sync` требует существующий YAML-каталог. `outputDir` создаётся при записи, если его ещё нет. `referenceDir` только читается, `outputDir` является местом записи XML и `.nakidka-migrations.yaml`. Если `referenceDir` явно указан и не существует, это не ошибка: он считается пустым эталоном. Если `referenceDir` отличается от `outputDir`, пользователь отвечает за согласованность эталонного XML с `.nakidka-migrations.yaml` в `outputDir`.

Если `rename`-миграция не может найти новый элемент в текущем YAML, это ошибка: пользователь зафиксировал переименование, но не привёл YAML к целевому состоянию. Уже неприменимая строка миграции для конкретного XML-каталога тоже считается ошибкой.

При переименовании верхнеуровневого объекта все reference-чтения идут через старый XML-путь, а запись — в новый: основной XML, формы, макеты, `Ext`, модули и другие внешние файлы объекта. Формы не мигрируются отдельными строками, но при переименовании объекта сохраняют `_uuid` через старую папку объекта. Переименование родителя распространяется вниз: если объект или табличная часть переименованы, дочерние одноимённые элементы без собственного переименования ищут reference-данные в старом владельце автоматически.

После экспорта `sync` выполняет обязательную очистку лишних файлов в `outputDir`. Для этого во время записи собирается список ожидаемых файлов относительно корня XML (`manifest`): основные XML, формы, макеты, `Ext`, модули и все другие файлы, которые создал экспорт. Затем удаляются все файлы и пустые папки внутри известных каталогов метаданных (`Catalogs`, `Documents` и подобных), которых нет в `manifest`. Корень XML не чистится, `.nakidka-migrations.yaml` не входит в `manifest`.

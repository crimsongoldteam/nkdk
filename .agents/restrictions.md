# Ограничения проекта

- В динамических списках пока не валидируются пути к данным.
- В динамических списках пока не преобразуются стандартные реквизиты в путях к данным, например `LineNumber`.
- Для нескольких привязанных баз пока не определено автоматическое согласование смены UUID, если объект удалили и создали заново вне NKDK под тем же логическим адресом, а пользовательские YAML-данные не изменились. Распространение нового UUID в другие базы и выбор канонической идентичности остаются за границами текущего проекта удалённого import и sync.
- При импорте из готовой XML-выгрузки используется привязка `default`, а файл индекса конфигурации не содержит отпечаток базы и подтверждённую версию Конфигурации. Привязка индекса к базе и проверка изменения Конфигурации после выгрузки пока не реализованы.
- Папка `.nkdk` должна находиться только в корне NKDK-проекта `projectDir/.nkdk`; внутри каталога компонента `.nkdk` запрещён.
- `componentPath` в MCP должен быть относительным путём `cf`, `cfe/<Имя>`, `erf/<Имя>` или `epf/<Имя>`; если он не передан, используется `cf`.
- `nkdk.import_from_xml` принимает готовый `xmlDir` одного компонента и не подключается к 1С. Целевой каталог `projectDir/componentPath` должен отсутствовать либо быть пустым.
- `nkdk.sync_to_xml` выгружает один выбранный компонент в заданный `xmlDir`; `xmlDir` не вычисляется как `xmlRootDir/componentPath`.
- Текущий MCP не импортирует и не синхронизирует все компоненты проекта за один вызов.
- Частичная синхронизация изменившихся файлов сейчас не реализована: `nkdk.sync_to_xml` всегда планирует или формирует полный XML выбранного компонента.
- Validation и поиск ссылок строят результат по фактически прочитанным байтам, а не по атомарному снимку файловой системы. Параллельное редактирование может сразу сделать результат устаревшим; следующая операция обнаруживает новую версию по хэшу.
- Переименование проверяет хэши всех затронутых YAML перед началом применения, но файловая система не обеспечивает атомарную запись многофайлового плана. Изменение уже во время применения или техническая ошибка могут оставить частичный результат; обязательная последующая актуализация его обнаруживает.
- Import из XML не публикует YAML, внешние файлы, файл индекса конфигурации и project state одной атомарной операцией. Файлы пишутся напрямую, а файл индекса конфигурации — перед финальным checkpoint project state; поэтому техническая ошибка checkpoint может оставить новый индекс при неопубликованном состоянии проекта. Для восстановления согласованного результата каталог компонента нужно очистить и import повторить.
- Синхронизация пока только формирует XML-каталог из Проекта. Подключение к 1С, передача XML в Конфигурацию, проверка её версии и перенос точки обновления файла индекса конфигурации за подтверждение 1С ещё не реализованы.
- Целевой каталог синхронизации в XML должен отсутствовать либо быть пустым. Операция не очищает его автоматически.
- Worker записывают XML непосредственно в целевой каталог. При ошибке может сохраниться неполный XML-результат; он не удаляется автоматически, а существующий файл индекса конфигурации не обновляется.
- Полная матрица допустимых изменений вида сопоставленного элемента заимствованной формы не исследована. Совместимость зависит как минимум от вида элемента в `cf`, вида элемента в `cfe` и типа реквизита формы, доступного по `ПутьКДанным`. До отдельного исследования validation считает одноимённый элемент присутствующим и оставляет проверку допустимости смены вида платформе 1С.
- Validation-схема `DcsExplicitSystemEnumerationValue` временно должна быть `Any` и не проверять структуру значения через JSON Schema до отдельного дизайна компактных `$ref` для DCS system enumeration values.
- Декларативная семантическая проверка `ЗначениеЗаполнения` у стандартных реквизитов пока покрывает только согласованный начальный набор: `Ссылка`, `ЭтоГруппа`, `Предопределенный`, `ИмяПредопределенныхДанных`, `ПометкаУдаления`, `Код` и `Владелец`. Остальные стандартные реквизиты должны использовать нейтральную политику `notSpecified`: значение сохраняется, а сама предметная политика не выдаёт ошибку или предупреждение до отдельного исследования и добавления декларации. Распознанные ссылки при этом остаются в индексе зависимостей и проходят обычную проверку Б5.
- Для `AppearanceFields.Текст` и `AppearanceFields.Формат` значение с `Тип: Поле` пока проверяется только структурно: `Значение` должно быть строкой. NKDK ещё не проверяет, что путь существует и допустим в контексте конкретного оформления. Перед семантической validation нужно отдельно определить доступные источники и правила разрешения таких полей.
- XML перерасчётов `Recalculations/Имя.xml` не преобразуется через `RecalculationRules`: при XML → YAML файл целиком копируется в `Перерасчеты/Имя/Recalculation.xml`, а при YAML → XML целиком копируется обратно. Поэтому `xmlOrder` в `RecalculationRules` не влияет на round-trip, пока действует этот договор.
- Для `Table.AutoInsertNewRow` NKDK использует единый YAML-default `Истина`, соответствующий обычной таблице. В Конфигураторе default равен `Ложь` для `DynamicList`, `GanttChart`, таблиц без `ПутьКДанным` и специальных таблиц `SettingsComposer`: `Filter`, `Order`, `Selection`, `ConditionalAppearance`, `UserSettings`, `Settings`, `DataParameters`, `FixedSettings`, `OutputParameters` и `UserFields`. Поэтому отсутствующий XML-узел у таких таблиц импортируется как явное YAML `АвтоВводНовойСтроки: Ложь`; тип источника по `DataPath` не определяется.
- `Table.Period`, `Table.TopLevelParent` и `Table.RowFilter` являются вычисляемыми XML-узлами и не входят в предметный YAML. Конечный источник определяется общим resolver по `ПутьКДанным`, включая поле после `Items.<Таблица>.CurrentData`: непосредственный `DynamicList` получает `Period` вместе с `TopLevelParent`; `ValueTable`, табличная часть и `RegisterRecordSet` получают `RowFilter`; остальные разрешённые источники не получают этих узлов. Отсутствующий, пустой или неразрешимый путь резервно получает `RowFilter`. Единственное транспортное исключение — `ОтборСтрок: !xml`, сохраняющий явно присутствующий `RowFilter`, который противоречит вычисленному профилю; поле скрыто от JSON Schema и semantic validation.
- Пустой локальный тег `!xml` имеет строковое значение `!xml`. Зарегистрированное свойство может интерпретировать его как транспортное XML-действие; у незарегистрированного свободного строкового поля это обычный текст. Validation-схема зарегистрированного ограниченного свойства получает литерал `!xml` только во внутреннем validation graph; схемы подсказок его не показывают.
- Для `HeaderHorizontalAlign` табличных `InputField`, `LabelField`, `PictureField` и `CheckBoxField` NKDK использует YAML-default `Auto`. Явный `<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>` сохраняется как `ГоризонтальноеПоложениеВШапке: !xml`; регистрация восстанавливает `Auto`, а прежняя форма `!xml Авто` не поддерживается. Для `CharacteristicsDescription` отсутствие XML-default сохраняется строковым `!xml` ровно у `dataPathField`, `multipleValuesUseField`, `multipleValuesKeyField` и `multipleValuesOrderField`.
- Пустой `panelDef` нестандартной панели сохраняется рядом с обычным UUID как `ПустоеОпределение: !xml`. При отсутствии поля `panelDef` не создаётся; прежний `UUID: !xml UUID` не поддерживается. Это различие не хранится в снимке.
- Для `Table.rowFilter` строковое `ОтборСтрок: !xml` сохраняет исключительный явный `RowFilter`, который не создаётся профилем источника. Любое новое применение `!xml` требует отдельного явного согласования разработчика. В исследованных конфигурациях `cf` найдено 34 тега для `HeaderHorizontalAlign`, все у колонок таблиц с `DataPath`; в конфигурации `all` и у `ColumnGroup` их нет.
- В YAML мобильных разрешений значения `PermissionGroupPhone`, `PermissionGroupCallLog`, `PermissionGroupSMS` и `PostNotifications` намеренно остаются без перевода: официальные русские имена не найдены в Синтакс-помощнике и методическом тексте. Остальные значения `RequiredMobileApplicationPermissions` и `RequiredMobileApplicationPermissionMessages` переводятся по системным перечислениям.

## Совместимость ПутьКДанным элементов формы (2026-08-10)

- Основные пути `Button` и `CommandBarButton` являются параметрами команды и пока исключены из проверки совместимости типа.
- `ПутьКДаннымПодвала`, `ПутьКДаннымКартинкиСтроки`, пути картинки, представления и значений для множественного выбора, пути шапки и прочие дополнительные DataPath проверяются только на существование.
- Для `DendrogramField`, `PeriodField` и остальных элементов без закрытой матрицы основной `ПутьКДанным` проверяется только на существование.
- Новую матрицу совместимости можно добавлять только после отдельного исследования. Её нельзя выводить из `defaultType` или частоты сочетаний в XML.

# Ограничения проекта

- В динамических списках пока не валидируются пути к данным.
- В динамических списках пока не преобразуются стандартные реквизиты в путях к данным, например `LineNumber`.
- Для нескольких привязанных баз пока не определено автоматическое согласование смены UUID, если объект удалили и создали заново вне NKDK под тем же логическим адресом, а пользовательские YAML-данные не изменились. Распространение нового UUID в другие базы и выбор канонической идентичности остаются за границами текущего проекта удалённого import и sync.
- При импорте из готовой XML-выгрузки используется привязка `default`, а файл индекса конфигурации не содержит отпечаток базы и подтверждённую версию Конфигурации. Привязка индекса к базе и проверка изменения Конфигурации после выгрузки пока не реализованы.
- MCP-договор компонентов проекта находится в `packages/mcp`: core metadata-слои не знают о папках `cf`, `cfe`, `erf` и `epf`.
- Папка `.nkdk` должна находиться только в корне NKDK-проекта `projectDir/.nkdk`; внутри каталога компонента `.nkdk` запрещён.
- `componentPath` в MCP должен быть относительным путём `cf`, `cfe/<Имя>`, `erf/<Имя>` или `epf/<Имя>`; если он не передан, используется `cf`.
- `nkdk.import_from_xml` принимает готовый `xmlDir` одного компонента и не подключается к 1С. Целевой каталог `projectDir/componentPath` должен отсутствовать либо быть пустым.
- `nkdk.sync_to_xml` выгружает один выбранный компонент в заданный `xmlDir`; `xmlDir` не вычисляется как `xmlRootDir/componentPath`.
- Текущий MCP не импортирует и не синхронизирует все компоненты проекта за один вызов.
- Импорт из XML не является транзакцией для всего Проекта. Worker и главный процесс пишут результат напрямую в целевой компонент; при ошибке часть файлов Проекта уже может содержать новый результат, а файл индекса конфигурации при этом не обновляется. Для восстановления согласованного результата каталог компонента нужно очистить и импорт повторить.
- При импорте из XML предварительные YAML-данные всех заданий хранятся в памяти до второго прохода, даже если у файла нет зависимостей от полного индекса метаданных. Досрочная запись таких файлов и освобождение их YAML после первого прохода пока не реализованы, поэтому импорт удерживает лишние данные и имеет повышенное пиковое потребление памяти.
- Синхронизация пока только формирует XML-каталог из Проекта. Подключение к 1С, передача XML в Конфигурацию, проверка её версии и перенос точки обновления файла индекса конфигурации за подтверждение 1С ещё не реализованы.
- Целевой каталог синхронизации в XML должен отсутствовать либо быть пустым. Операция не очищает его автоматически.
- Worker записывают XML непосредственно в целевой каталог. При ошибке может сохраниться неполный XML-результат; он не удаляется автоматически, а существующий файл индекса конфигурации не обновляется.
- Общие операции синхронизации, переименования и поиска ссылок не создают metadata-модель. Обработчики конкретных типов `fromYAML`/`toXML` преобразуют только одно атомарное значение и не обходят свойства, объекты или коллекции.
- Валидация согласованности заимствованной формы расширения с текущей формой основной конфигурации пока не реализована. В частности, не проверяется наличие в YAML расширения каждого элемента текущей формы `cf`, запрет удаления исходных элементов и совместимость изменения их вида. Синхронизация и построение `BaseForm` исходят из того, что эти ограничения уже соблюдены.
- Validation-схема `DcsExplicitSystemEnumerationValue` временно должна быть `Any` и не проверять структуру значения через JSON Schema до отдельного дизайна компактных `$ref` для DCS system enumeration values.
- XML перерасчётов `Recalculations/Имя.xml` не преобразуется через `RecalculationRules`: при XML → YAML файл целиком копируется в `Перерасчеты/Имя/Recalculation.xml`, а при YAML → XML целиком копируется обратно. Поэтому `xmlOrder` в `RecalculationRules` не влияет на round-trip, пока действует этот договор.
- Для `Table.AutoInsertNewRow` NKDK использует единый YAML-default `Истина`, соответствующий обычной таблице. В Конфигураторе default равен `Ложь` для `DynamicList`, `GanttChart`, таблиц без `ПутьКДанным` и специальных таблиц `SettingsComposer`: `Filter`, `Order`, `Selection`, `ConditionalAppearance`, `UserSettings`, `Settings`, `DataParameters`, `FixedSettings`, `OutputParameters` и `UserFields`. Поэтому отсутствующий XML-узел у таких таблиц импортируется как явное YAML `АвтоВводНовойСтроки: Ложь`; тип источника по `DataPath` не определяется.
- `Table.Period`, `Table.TopLevelParent` и `Table.RowFilter` являются только вычисляемыми XML-узлами и не хранятся в YAML. Конечный источник определяется общим resolver по `ПутьКДанным`, включая поле после `Items.<Таблица>.CurrentData`: непосредственный `DynamicList` получает `Period` вместе с `TopLevelParent`; `ValueTable`, табличная часть и `RegisterRecordSet` получают `RowFilter`; остальные разрешённые источники не получают этих узлов. Отсутствующий, пустой или неразрешимый путь резервно получает `RowFilter`.
- Для `HeaderHorizontalAlign` табличных `InputField`, `LabelField`, `PictureField` и `CheckBoxField` NKDK использует YAML-default `Auto`. Явный XML-тег `<HeaderHorizontalAlign>Auto</HeaderHorizontalAlign>` сохраняется как `ГоризонтальноеПоложениеВШапке: !xml Авто`; это единственное согласованное применение `!xml`. Любое новое применение транспортного тега требует отдельного явного согласования разработчика. В исследованных конфигурациях `cf` найдено 34 таких тега, все у колонок таблиц с `DataPath`; в конфигурации `all` и у `ColumnGroup` их нет.

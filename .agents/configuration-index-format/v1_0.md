# Файл индекса конфигурации

## Спецификация двоичного формата 1.0

Статус: проект формата. Реализация отсутствует.

## 1. Область применения

Файл `.nkdk/configuration-index/<base-id>.bin` представляет одну привязку Проекта к одной базе 1С.

Первая реализация NKDK поддерживает только одну привязку Проекта и допускает не более одного файла в каталоге `.nkdk/configuration-index/`. Ограничение реализации не изменяет формат файла и позволяет в будущем добавить несколько привязок без смены формата 1.0.

При формировании индекса из готовой XML-выгрузки без подключения к базе первая реализация использует `baseId = "default"` и путь `.nkdk/configuration-index/default.bin`.

Файл содержит:

- идентификатор привязки, а при наличии подтверждённой привязки — отпечаток базы и версию Конфигурации;
- хэши файлов Проекта;
- идентификаторы объектов и вложенных элементов 1С;
- данные, необходимые для восстановления исходного XML после преобразования XML в Проект.

Все перечисленные данные находятся в одном файле. Дополнительные файлы хэшей, идентификаторов или восстановления XML не создаются.

Формат 1.0 не хранит исходные XML-файлы, `XML_REFERENCE_RAW` и порядок коллекций, представленный в Проекте.

## 2. Нормативные требования

Слова «ДОЛЖЕН», «НЕ ДОЛЖЕН», «СЛЕДУЕТ» и «МОЖЕТ» обозначают обязательность требования.

Читатель ДОЛЖЕН отклонить файл при нарушении любого требования этой спецификации. Частичное чтение повреждённого файла и восстановление отдельных секций не допускаются.

## 3. Базовые типы

| Обозначение | Представление |
|---|---|
| `u8` | Беззнаковое целое, 1 байт |
| `u16` | Беззнаковое целое, 2 байта, little-endian |
| `u32` | Беззнаковое целое, 4 байта, little-endian |
| `u64` | Беззнаковое целое, 8 байт, little-endian |
| `bytes[N]` | Ровно `N` байт |
| `stringId` | `u32`, идентификатор строки из секции `STRINGS` |

Значение `stringId = 0` обозначает отсутствие строки. Остальные идентификаторы нумеруются с `1` в порядке записей секции `STRINGS`.

Все смещения отсчитываются от начала файла. Сложение смещения и длины ДОЛЖНО проверяться без целочисленного переполнения.

Зарезервированные поля, неизвестные биты флагов и байты выравнивания ДОЛЖНЫ быть равны нулю.

Заголовок, каталог секций, начала секций и начала записей переменной длины выравниваются по границе 8 байт.

## 4. Строки

Строки кодируются в UTF-8 без завершающего нулевого байта. Некорректный UTF-8 и символ `U+0000` запрещены.

Сравнение и сортировка строк выполняются по исходным байтам UTF-8 без учёта локали и нормализации Unicode.

Пустая строка допускается и имеет ненулевой `stringId`.

### 4.1. Логические адреса

`logicalAddress` использует формат `uid`, принятый в эксперименте `reference-order-spec`. Адрес строится из смыслового пути metadata/YAML, а не из имён XML-узлов или путей XML-файлов.

Адрес состоит из канонических русскоязычных сегментов, разделённых точкой:

- Конфигурация имеет адрес `Конфигурация`;
- адрес объекта метаданных имеет вид `<Вид>.<Имя>`;
- адрес именованного вложенного элемента дополняется парой `<Вид элемента>.<Имя>`;
- для безымянного элемента допускается только сегмент `<Вид элемента>[<индекс>]`, где индекс начинается с `0`.

Примеры:

```text
Документ.ПоступлениеТоваровУслуг
Документ.ПоступлениеТоваровУслуг.Форма.ФормаДокумента
Документ.ПоступлениеТоваровУслуг.Форма.ФормаДокумента.Команда.Провести
Документ.ПоступлениеТоваровУслуг.Форма.ФормаДокумента.Элемент.Товары.Элемент.ТоварыНоменклатура
Документ.ПоступлениеТоваровУслуг.Форма.ФормаДокумента.Элемент.Товары.ДинамическийСписок.Отбор[0]
```

Если элемент имеет устойчивое имя, индекс использовать запрещено. Канонические сегменты и способ выбора имени или индекса задаются правилами. Общий слой ДОЛЖЕН строить адрес через единый builder и НЕ ДОЛЖЕН склеивать частные адреса по знаниям о конкретных типах объектов.

Один и тот же `logicalAddress` обозначает один и тот же элемент во всех секциях файла индекса конфигурации.

## 5. Хэши и контрольные суммы

| Назначение | Алгоритм | Представление |
|---|---|---|
| Контрольная сумма каталога и секции | XXH3-128, seed `0` | младшие 64 бита как `u64`, затем старшие 64 бит как `u64` |
| Хэш файла Проекта | XXH3-64, seed `0` | `u64` |

Контрольная сумма секции вычисляется по всему её содержимому, включая внутренние байты выравнивания. Внешнее выравнивание между секциями в контрольную сумму не входит.

Хэши не обеспечивают криптографическую подлинность файла.

## 6. Структура файла

```text
+-----------------------------+
| Header, 64 bytes            |
+-----------------------------+
| Section directory           |
+-----------------------------+
| zero padding to 8 bytes     |
+-----------------------------+
| BINDING                     |
+-----------------------------+
| STRINGS                     |
+-----------------------------+
| PROJECT_FILES               |
+-----------------------------+
| IDENTITIES                  |
+-----------------------------+
| XML_ORDERS                  |
+-----------------------------+
| XML_NODES                   |
+-----------------------------+
| XML_VALUES                  |
+-----------------------------+
```

Каталог расположен непосредственно после заголовка. Секции расположены по возрастанию `sectionType`. Между секциями допускаются только нулевые байты выравнивания.

Файл заканчивается последним байтом секции `XML_VALUES`. Байты после последней секции запрещены.

## 7. Заголовок

Заголовок занимает 64 байта.

| Смещение | Размер | Поле | Значение 1.0 |
|---:|---:|---|---|
| 0 | 8 | `magic` | ASCII `NKDK1CIX` |
| 8 | 2 | `majorVersion` | `1` |
| 10 | 2 | `minorVersion` | `0` |
| 12 | 4 | `headerLength` | `64` |
| 16 | 1 | `byteOrder` | `1` — little-endian |
| 17 | 1 | `stringEncoding` | `1` — UTF-8 |
| 18 | 1 | `checksumAlgorithm` | `1` — XXH3-128 |
| 19 | 1 | `fileHashAlgorithm` | `1` — XXH3-64 |
| 20 | 4 | `directoryEntryLength` | `64` |
| 24 | 4 | `sectionCount` | `7` |
| 28 | 4 | `flags` | `0` |
| 32 | 8 | `directoryOffset` | `64` |
| 40 | 8 | `fileLength` | точный размер файла |
| 48 | 16 | `directoryChecksum` | XXH3-128 всех записей каталога |

## 8. Каталог секций

Каждая запись каталога занимает 64 байта.

| Смещение | Размер | Поле | Требование |
|---:|---:|---|---|
| 0 | 4 | `sectionType` | тип секции |
| 4 | 2 | `sectionMajorVersion` | `1` |
| 6 | 2 | `sectionMinorVersion` | `0` |
| 8 | 4 | `sectionFlags` | `1` — обязательная секция |
| 12 | 4 | `reserved` | `0` |
| 16 | 8 | `offset` | абсолютное смещение секции |
| 24 | 8 | `storedLength` | длина секции в файле |
| 32 | 8 | `logicalLength` | равна `storedLength` |
| 40 | 8 | `recordCount` | число записей секции |
| 48 | 16 | `sectionChecksum` | XXH3-128 секции |

Записи ДОЛЖНЫ быть отсортированы по `sectionType`. Повторение типа запрещено. Все семь секций обязательны, даже если число их записей равно нулю.

| `sectionType` | Секция | `recordCount` |
|---:|---|---:|
| 1 | `BINDING` | `1` |
| 2 | `STRINGS` | число строк |
| 3 | `PROJECT_FILES` | число файлов |
| 4 | `IDENTITIES` | число идентификаторов |
| 5 | `XML_ORDERS` | число уникальных порядков полей |
| 6 | `XML_NODES` | число XML-узлов |
| 7 | `XML_VALUES` | число значений с исходным представлением |

Сжатие секций в версии 1.0 не поддерживается.

## 9. Секция `BINDING`

Секция содержит один заголовок длиной 64 байта, за которым следуют два непрозрачных значения переменной длины.

### 9.1. Заголовок

| Смещение | Размер | Поле | Требование |
|---:|---:|---|---|
| 0 | 8 | `indexGeneration` | начинается с `1`; увеличивается после успешного import или sync |
| 8 | 4 | `producerVersionStringId` | непустая версия NKDK |
| 12 | 4 | `baseIdStringId` | идентификатор привязки |
| 16 | 4 | `baseFingerprintLength` | длина отпечатка базы |
| 20 | 4 | `configurationVersionLength` | длина подтверждённой версии Конфигурации |
| 24 | 40 | `reserved` | нули |

### 9.2. Данные переменной длины

Сразу после заголовка расположены:

1. `baseFingerprintLength` байт `baseFingerprint`;
2. `configurationVersionLength` байт `configurationVersion`;
3. нулевое выравнивание до 8 байт.

`baseFingerprint` и `configurationVersion` описывают подтверждённую привязку к базе. Если привязка подтверждена, оба значения ДОЛЖНЫ быть непустыми. Если индекс сформирован из готовой XML-выгрузки без подключения к базе, оба значения ДОЛЖНЫ быть пустыми. Состояние, в котором пусто только одно из двух значений, запрещено.

NKDK сравнивает непустые значения как непрозрачные последовательности байт. Пустые значения НЕ ДОЛЖНЫ использоваться для проверки соответствия базы или версии Конфигурации.

Строка `baseId` ДОЛЖНА:

- совпадать с именем файла без расширения `.bin`;
- содержать только ASCII `A-Z`, `a-z`, `0-9`, `.`, `_`, `-`;
- иметь длину от 1 до 128 байт.

Файл НЕ ДОЛЖЕН содержать SSH-реквизиты, пароли, закрытые ключи и строки подключения с секретами.

## 10. Секция `STRINGS`

Каждая запись имеет следующую структуру:

| Поле | Кодирование |
|---|---|
| `byteLength` | `u32` |
| `utf8Bytes` | `bytes[byteLength]` |
| `padding` | нулевое выравнивание записи до 8 байт |

Строки ДОЛЖНЫ быть уникальны и отсортированы по байтам UTF-8. `stringId` равен позиции строки в секции, начиная с `1`.

В секцию включаются все строки, на которые ссылаются остальные секции, и только они.

## 11. Секция `PROJECT_FILES`

Запись имеет фиксированный размер 16 байт.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `projectPathStringId` |
| 4 | 4 | `flags = 0` |
| 8 | 8 | `contentHash` |

Путь:

- задаётся относительно корня Проекта;
- использует разделитель `/`;
- не начинается и не заканчивается `/`;
- не содержит пустых сегментов, `.` и `..`;
- не указывает на каталог `.nkdk/`.

Записи ДОЛЖНЫ быть отсортированы по строке пути. Пути ДОЛЖНЫ быть уникальны.

`contentHash` вычисляется по исходным байтам файла без нормализации кодировки, переводов строк или содержимого.

Секция содержит все YAML и внешние файлы, обнаруженные правилами структуры Проекта.

## 12. Секция `IDENTITIES`

Запись имеет фиксированный размер 32 байта.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `logicalAddressStringId` |
| 4 | 2 | `identityKind` |
| 6 | 2 | `flags = 0` |
| 8 | 4 | `valueStringId` |
| 12 | 4 | `reserved = 0` |
| 16 | 16 | `uuidBytes` |

### 12.1. Виды идентификаторов

| `identityKind` | Имя | `valueStringId` | `uuidBytes` |
|---:|---|---|---|
| 1 | `UUID` | `0` | UUID, 16 байт |
| 2 | `XML_ID` | ненулевой | нули |
| 3 | `XML_NAME` | ненулевой | нули |

UUID кодируется удалением дефисов из канонической строки `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` и последовательным декодированием пар шестнадцатеричных цифр. Платформенный порядок полей UUID не применяется.

`logicalAddress` — устойчивый адрес элемента Проекта, сформированный по разделу 4.1. Адрес ДОЛЖЕН быть непустым.

Записи ДОЛЖНЫ быть отсортированы по `logicalAddress`, затем по `identityKind`. Пара `logicalAddress + identityKind` ДОЛЖНА быть уникальна.

`XML_NAME` записывается только тогда, когда исходное имя нельзя восстановить из логического адреса и правил.

## 13. Секция `XML_ORDERS`

Секция содержит словарь уникальных порядков XML-полей. `orderId` равен позиции записи, начиная с `1`; значение `0` обозначает отсутствие сохранённого порядка.

Запись имеет переменную длину:

| Поле | Кодирование |
|---|---|
| `propertyCount` | `u32` |
| `reserved` | `u32 = 0` |
| `propertyKeyStringIds` | `propertyCount × stringId` |
| `padding` | нулевое выравнивание записи до 8 байт |

`propertyCount` ДОЛЖЕН быть больше нуля. Идентификаторы свойств внутри записи ДОЛЖНЫ быть ненулевыми и уникальными.

Записи ДОЛЖНЫ быть уникальны и отсортированы лексикографически по последовательности `propertyKeyStringIds`.

Порядок описывает только XML-поля одного узла, описанного правилами. Порядок элементов коллекций в секцию не включается.

## 14. Секция `XML_NODES`

Секция содержит порядок XML-полей, исходные псевдонимы полей и признаки присутствия, потерянные при преобразовании XML в Проект.

### 14.1. Заголовок записи

Заголовок занимает 16 байт.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `logicalAddressStringId` |
| 4 | 4 | `orderId` |
| 8 | 4 | `aliasCount` |
| 12 | 4 | `presentCount` |

### 14.2. Данные переменной длины

После заголовка расположены:

1. `aliasCount` пар `propertyKeyStringId: u32`, `sourceXmlKeyStringId: u32`;
2. `presentCount` значений `propertyKeyStringId: u32`;
3. нулевое выравнивание записи до 8 байт.

`orderId` ДОЛЖЕН быть равен `0` либо ссылаться на запись `XML_ORDERS`.

Пары псевдонимов:

- ДОЛЖНЫ быть отсортированы по `propertyKeyStringId`;
- НЕ ДОЛЖНЫ повторять ключ свойства;
- ДОЛЖНЫ содержать исходное XML-имя, отличное от канонического имени правила.

Список присутствующих полей:

- ДОЛЖЕН быть отсортирован по `propertyKeyStringId`;
- НЕ ДОЛЖЕН содержать повторений;
- содержит только поля, для которых различие между отсутствием и присутствием влияет на восстановление XML.

Запись, у которой `orderId = 0`, `aliasCount = 0` и `presentCount = 0`, запрещена.

Записи ДОЛЖНЫ быть отсортированы по `logicalAddress`. Логические адреса ДОЛЖНЫ быть уникальны.

## 15. Секция `XML_VALUES`

Секция содержит исходное XML-представление значений, которое не представлено в Проекте.

Запись имеет фиксированный размер 32 байта.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `logicalAddressStringId` |
| 4 | 4 | `valueFlags` |
| 8 | 4 | `xsiTypeStringId` |
| 12 | 4 | `xmlTextStringId` |
| 16 | 4 | `xmlPrefixStringId` |
| 20 | 4 | `userSettingsIdStringId` |
| 24 | 8 | `reserved = 0` |

### 15.1. Флаги значения

| Бит | Имя | Значение |
|---:|---|---|
| 0 | `XSI_NIL` | исходное значение имело `xsi:nil="true"` |
| 1 | `EXPLICIT_EMPTY` | значение явно присутствовало в пустой форме |
| 2 | `HAS_XSI_TYPE` | задан `xsiTypeStringId` |
| 3 | `HAS_XML_TEXT` | задан `xmlTextStringId` |
| 4 | `HAS_XML_PREFIX` | задан `xmlPrefixStringId` |
| 5 | `HAS_USER_SETTINGS_ID` | задан `userSettingsIdStringId` |
| 6–31 | — | `0` |

Для полей `xsiTypeStringId`, `xmlTextStringId`, `xmlPrefixStringId` и `userSettingsIdStringId` выполняется правило:

- соответствующий `HAS_*` установлен — `stringId` ненулевой;
- соответствующий `HAS_*` не установлен — `stringId = 0`.

`xmlText` содержит текстовое значение после разбора XML. Исходное экранирование сущностей, пробелы форматирования между XML-узлами и порядок XML-атрибутов не сохраняются.

Запись с `valueFlags = 0` запрещена.

Записи ДОЛЖНЫ быть отсортированы по `logicalAddress`. Логические адреса ДОЛЖНЫ быть уникальны.

## 16. Формирование данных восстановления XML

При import данные секций `XML_ORDERS`, `XML_NODES` и `XML_VALUES` извлекаются только из XML-узлов и значений, описанных правилами.

В эти секции НЕ ДОЛЖНЫ включаться:

- данные, полностью представленные в Проекте;
- порядок элементов коллекций;
- исходные XML-файлы и непрозрачные XML-фрагменты;
- `XML_REFERENCE_RAW`;
- UUID, `id` и скрытые XML-имена, хранящиеся в `IDENTITIES`.

Исходное представление поля МОЖЕТ применяться при построении XML только после проверки правилами его совместимости с текущим значением Проекта. Для нового или несовместимого значения используется каноническое представление правил.

Для неизменённого Проекта и полностью поддержанной правилами XML-области построенный XML ДОЛЖЕН сохранять представление, описанное секциями `XML_ORDERS`, `XML_NODES` и `XML_VALUES`.

## 17. Проверка файла

Читатель ДОЛЖЕН выполнить проверки в следующем порядке:

1. Проверить `magic`, версию, алгоритмы, размеры и `fileLength`.
2. Проверить границы каталога и `directoryChecksum`.
3. Проверить состав, версии, сортировку и уникальность секций.
4. Проверить выравнивание, границы и отсутствие пересечений секций.
5. Проверить `sectionChecksum` каждой секции.
6. Разобрать `STRINGS`, проверить UTF-8, сортировку и уникальность.
7. Проверить все `stringId`, размеры записей, нулевые поля и `recordCount`.
8. Проверить ограничения сортировки и уникальности каждой секции.
9. Проверить ссылки `orderId` и внутренние ограничения записей.
10. Проверить совпадение `baseId` с именем файла.

После структурной проверки потребитель ДОЛЖЕН отдельно проверить:

- совпадение `producerVersion` с текущей версией NKDK;
- совпадение `baseFingerprint` с выбранной базой, если значение непустое;
- совпадение `configurationVersion` перед применением изменений, если значение непустое.

Индекс с пустыми `baseFingerprint` и `configurationVersion` НЕ ДОЛЖЕН использоваться для применения изменений к Конфигурации до подтверждения привязки к базе.

## 18. Запись файла

Файл версии 1.0 НЕ ДОЛЖЕН изменяться на месте.

После успешного import или sync писатель ДОЛЖЕН:

1. сформировать полный новый файл во временном пути каталога `.nkdk/configuration-index/`;
2. повторно открыть и полностью проверить его по разделу 17;
3. синхронизировать содержимое временного файла с файловой системой;
4. атомарно заменить `<base-id>.bin`;
5. синхронизировать каталог, если операция поддерживается платформой.

Существующий файл НЕ ДОЛЖЕН изменяться до успешного завершения import или подтверждения успешной операции sync с Конфигурацией.

## 19. Совместимость

- Изменение `majorVersion` означает несовместимый формат.
- Изменение `minorVersion` допускает только добавление значений и необязательных секций, которые старый читатель может безопасно пропустить.
- Читатель версии 1.0 принимает только контейнер 1.0 и секции версии 1.0.
- Неизвестный обязательный тип секции или ненулевой неизвестный флаг является ошибкой несовместимости.
- Файл, созданный другой версией NKDK, не используется для sync; требуется новый import.

## 20. Ограничения версии 1.0

- Файл полностью переписывается после каждой успешной операции.
- Секции не сжимаются.
- Криптографическая подлинность файла не проверяется.
- Непрозрачные XML-фрагменты не сохраняются.
- Автоматическое согласование смены UUID между несколькими базами не определяется.
